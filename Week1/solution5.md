# 과제 5-1 해설

API 서버는 사용자의 요청이 **유실되지 않을 정도로 안전한 위치에 기록된 뒤** 요청 접수 성공 응답을 반환해야 한다.

절대 다음 시점에 응답하면 안 된다.

```
요청을 메모리에 올린 순간
```

메모리는 서버가 종료되면 사라진다.

따라서 메모리에만 요청이 있는 상태에서 사용자에게 “접수되었습니다”라고 응답하면 위험하다.

요청 접수 성공 응답을 반환할 수 있는 기준은 보통 다음 중 하나다.

```
1. DB에 PENDING 상태로 저장된 뒤
2. Queue/Kafka에 메시지를 발행하고, 브로커로부터 ack를 확인한 뒤
3. DB 저장과 이벤트 발행을 함께 보장해야 하는 경우에는 Outbox에 이벤트 기록까지 저장된 뒤
```

1주차 수준에서는 다음 기준이 가장 이해하기 쉽다.

```
API 서버는 요청 상태를 DB에 PENDING으로 저장한 뒤 응답한다.
```

핵심은 사용자가 접수 응답을 받았다면,
서버가 죽어도 그 요청을 나중에 다시 찾아서 처리할 수 있어야 한다.

---

# 과제 5-2 해설

요청이 메모리에만 있는 상태에서 사용자에게 접수 성공 응답을 보내면 요청이 유실될 수 있다.

예를 들어 다음과 같은 상황이 생길 수 있다.

```
Client
→ API Server
→ 요청을 메모리에 저장
→ Client에게 “요청 접수 완료” 응답
→ API Server 장애 발생
→ 메모리에 있던 요청 사라짐
→ 실제 쿠폰 발급 처리 안 됨
```

이 경우 사용자는 분명히 “요청이 접수되었습니다.”라는 응답을 받았지만, 서버에는 요청 기록이 남아 있지 않다.

즉, 사용자는 접수된 줄 알지만 실제로는 발급 처리 대상에서 빠지는 문제가 생긴다.

따라서 메모리에만 저장된 상태에서 접수 성공 응답을 주는 것은 안전하지 않다.

# 과제 5-3 해설

요청 상태를 DB에 PENDING으로 저장한 뒤 응답하는 방식은 다음과 같다.

```
Client
  |
  v
API Server
  |
  | 요청 검증
  | requestId 생성
  | DB에 PENDING 저장
  v
Client
  |
  | 접수 완료 응답

--------------------------------

Worker
  |
  | PENDING 요청 조회
  | 실제 쿠폰 발급 처리
  | SUCCESS / FAILED로 상태 변경
```

### 장점

첫 번째 장점은 요청이 유실되지 않는다는 것이다.

DB에 저장되어 있기 때문에 API 서버가 죽어도 요청 기록은 남아 있다.

두 번째 장점은 사용자가 상태를 조회할 수 있다는 것이다.

```
PENDING → 처리 중
SUCCESS → 발급 성공
FAILED → 발급 실패
```

세 번째 장점은 장애 복구가 쉽다는 것이다.

Worker가 죽어도 DB에 남아 있는 PENDING 요청을 다시 처리하면 된다.

### 단점

단점은 API 요청마다 DB 쓰기가 발생한다는 것이다.

이벤트 시작 순간에 요청이 매우 많이 들어오면 DB에 PENDING 저장 부하가 생길 수 있다.

또한 Worker가 PENDING 요청을 어떻게 가져갈지도 설계해야 한다.

```
- 여러 Worker가 같은 PENDING 요청을 동시에 가져가지 않게 해야 함
- 처리 중 장애가 난 요청을 다시 복구해야 함
- 오래된 PENDING 요청을 감지해야 함
```

즉, 안정성은 좋아지지만 상태 관리 복잡도가 생긴다.

# 과제 5-4 해설

이 방식은 API 서버가 Queue 또는 Kafka에 요청 메시지를 넣고, 안전하게 적재되었다는 확인을 받은 뒤 응답하는 방식이다.

```
Client
→ API Server
→ Kafka에 메시지 발행
→ Kafka ack 확인
→ Client에게 접수 완료 응답
→ Worker가 Kafka 메시지 소비
→ 쿠폰 발급 처리
```

### 장점

```
DB가 모든 요청을 직접 맞지 않아도 됨
Kafka가 요청 버퍼 역할을 함
Worker가 처리 가능한 속도로 소비함
API 서버 응답이 빨라짐
```

Queue/Kafka가 요청을 받아주기 때문에 대량 트래픽을 완충하기 좋다.

Worker는 자신이 처리 가능한 속도로 메시지를 읽어가면 된다.

또한 Queue/Kafka에 메시지를 발행하고, 브로커로부터 ack를 확인한 뒤 응답하면 API 서버가 죽어도 메시지가 남아 있다.

### 단점

Kafka 발행 성공 여부를 확인해야 한다.

확인하지 않고 응답하면 메모리 유실 문제와 비슷한 문제가 생길 수 있다.

또한 Kafka에만 메시지가 있고 DB에는 PENDING 요청 상태가 없다면, 사용자가 상태 조회를 하기 어렵다.

결국 결과 조회를 위해 별도의 상태 저장소가 필요해진다.

그리고 DB 저장과 Kafka 발행을 함께 해야 하는 경우에는 또 다른 문제가 생긴다.

```
DB에는 PENDING 저장 성공
Kafka 발행 실패
```

또는 반대로 다음 문제가 생길 수 있다.

```
Kafka 발행 성공
DB 저장 실패
```

이 문제는 뒤 주차에서 다루는 Outbox Pattern과 연결된다.

# **과제 5-5 해설**

이 과제에서는 다음 방식을 기본 선택지로 본다.

```
API 서버는 요청을 검증한 뒤,
요청 상태를 DB에 PENDING으로 저장하고,
사용자에게 요청 접수 성공 응답을 반환한다.
```

즉, 사용자가 쿠폰 발급 버튼을 눌렀을 때 API 서버가 바로 최종 성공/실패를 응답하는 것이 아니라, 먼저 요청을 안전하게 접수한 뒤 다음과 같은 응답을 반환한다.

```
요청이 접수되었습니다.
현재 처리 중입니다.
```

전체 흐름은 다음과 같다.

```
Client
  |
  v
API Server
  |
  | 요청 검증
  | requestId 생성
  | DB에 PENDING 상태 저장
  v
Client
  |
  | 접수 완료 응답

--------------------------------

Worker
  |
  | PENDING 요청 조회
  | 실제 쿠폰 발급 처리
  | SUCCESS / FAILED로 상태 변경
```

## **이 방식을 선택한 이유**

### **첫째, 접수된 요청이 유실되지 않는다**

비동기 구조에서 가장 조심해야 하는 것은 사용자가 “접수 완료” 응답을 받았는데 실제로는 요청이 사라지는 상황이다.

예를 들어 API 서버가 메모리에만 요청을 들고 있다가 서버가 죽으면, 사용자는 접수 완료 응답을 받았지만 실제 요청은 처리되지 않을 수 있다.

하지만 DB에 PENDING 상태로 요청을 저장해두면 API 서버가 죽어도 요청 기록은 남아 있다.

```
DB에 PENDING 저장 성공
→ 사용자에게 접수 완료 응답
→ 이후 서버 장애가 발생해도 요청 기록은 남아 있음
```

따라서 사용자가 접수 완료 응답을 받은 요청은 나중에 Worker가 다시 확인해서 처리할 수 있다.

---

### **둘째, 사용자가 결과를 조회할 수 있다**

비동기 처리에서는 API 서버가 즉시 최종 성공/실패를 응답하지 않는다.

따라서 사용자는 나중에 자신의 요청이 어떻게 되었는지 확인할 수 있어야 한다.

DB에 요청 상태를 저장하면 다음과 같은 상태 조회 API를 만들기 쉽다.

```
PENDING  → 처리 대기 중
PROCESSING → 처리 중
SUCCESS  → 발급 성공
FAILED   → 발급 실패
```

예를 들어 사용자가 마이페이지나 쿠폰함에서 결과를 조회하면, 서버는 DB에 저장된 요청 상태를 기준으로 응답할 수 있다.

```
Client
  |
  | 결과 조회 요청
  v
API Server
  |
  | DB에서 requestId 또는 userId 기준으로 상태 조회
  v
Client
  |
  | PENDING / SUCCESS / FAILED 응답
```

이처럼 PENDING 상태를 저장해두면 비동기 구조에서도 사용자 경험을 관리하기 쉽다.

---

### **셋째, 장애 복구가 쉽다**

Worker가 쿠폰 발급을 처리하다가 중간에 죽을 수도 있다.

이때 DB에 요청 상태가 남아 있으면 복구 기준을 잡기 쉽다.

예를 들어 Worker가 처리하지 못한 PENDING 요청을 다시 조회하거나, 너무 오래 PROCESSING 상태로 남아 있는 요청을 찾아 재처리할 수 있다.

```
Worker 장애 발생
→ DB에는 PENDING 또는 PROCESSING 상태가 남아 있음
→ 복구 Worker가 오래된 요청을 다시 조회
→ 쿠폰 발급 재시도
```

즉, DB에 상태를 저장하면 단순히 요청을 저장하는 것뿐만 아니라 장애 복구의 기준점도 만들 수 있다.

---

## **이 방식의 단점**

이 방식에도 단점은 있다.

가장 큰 단점은 API 요청마다 DB 쓰기가 발생한다는 것이다.

```
요청 1 → DB에 PENDING 저장
요청 2 → DB에 PENDING 저장
요청 3 → DB에 PENDING 저장
...
```

선착순 쿠폰 이벤트처럼 특정 시간에 요청이 몰리는 상황에서는 DB에 PENDING 저장 부하가 커질 수 있다.

또한 Worker가 PENDING 요청을 어떻게 가져갈지도 설계해야 한다.

```
- 여러 Worker가 같은 PENDING 요청을 동시에 가져가지 않게 해야 한다.
- 처리 중 장애가 발생한 요청을 다시 복구해야 한다.
- 너무 오래 PENDING 또는 PROCESSING 상태로 남은 요청을 감지해야 한다.
```

즉, DB에 PENDING 상태를 저장하는 방식은 안정성과 조회 편의성은 좋지만, 대량 트래픽에서는 DB 부하와 상태 관리 복잡도가 생긴다.

---

## **그럼에도 1주차에서 이 방식을 선택하는 이유**

1주차의 핵심은 Kafka, Redis, Outbox 같은 세부 기술을 깊게 다루는 것이 아니다.

이번 주차의 핵심은 다음 질문에 답하는 것이다.

```
사용자가 쿠폰 발급 요청을 보냈을 때,
API 서버가 언제 응답해야 하는가?

최종 발급 결과를 기다렸다가 응답해야 하는가?
아니면 요청을 안전하게 접수한 뒤 먼저 응답해야 하는가?
```

이 관점에서 가장 중요한 기준은 다음과 같다.

```
빠른 응답도 중요하지만,
접수 완료라고 응답한 요청이 유실되지 않는 것이 더 중요하다.
```

그래서 1주차 수준에서는 DB에 PENDING 상태를 저장한 뒤 응답하는 방식이 가장 이해하기 쉽고 안정적인 기본안이다.

이 방식은 다음 개념을 설명하기 좋다.

```
- 비동기 요청 접수
- 요청 상태 관리
- 결과 조회 API
- Worker의 역할
- 장애 복구
```

따라서 1주차에서는 DB PENDING 저장 방식을 기본 구조로 선택한다.

---

## **실제 대규모 선착순 이벤트에서는 어떻게 달라질까?**

실제 대규모 선착순 이벤트에서는 API 요청마다 DB에 PENDING을 저장하는 방식이 병목이 될 수 있다.

예를 들어 쿠폰 수량은 1,000개인데 요청이 100,000개 들어온다고 해보자.

DB PENDING 저장 방식에서는 100,000개의 요청이 모두 DB에 저장될 수 있다.

```
요청 100,000건
→ DB에 PENDING 100,000건 저장
```

이 경우 DB가 이벤트 시작 순간의 트래픽을 직접 맞게 된다.

그래서 실제 대규모 구조에서는 Kafka, Redis, Outbox 같은 기술을 단계적으로 도입해 구조를 개선한다.

---

## **이후 주차에서 확장되는 구조**

### **1주차: 요청 처리 구조 설계**

1주차에서는 API 서버가 최종 결과를 기다리지 않고, 요청을 접수한 뒤 빠르게 응답하는 구조를 학습한다.

기본 구조는 다음과 같다.

```
Client
→ API Server
→ DB에 PENDING 저장
→ Client에게 접수 완료 응답
→ Worker가 뒤에서 처리
```

이 단계에서는 비동기 처리의 기본 흐름과 요청 상태 관리의 필요성을 이해하는 것이 목표다.

---

### **2주차: Kafka로 요청 완충하기**

2주차에서는 DB가 모든 요청을 직접 받지 않도록 Kafka를 도입한다.

구조는 다음과 같이 발전할 수 있다.

```
Client
→ API Server
→ Kafka에 쿠폰 발급 요청 메시지 발행
→ Kafka ack 확인
→ Client에게 접수 완료 응답

Worker
→ Kafka 메시지 소비
→ 쿠폰 발급 처리
```

Kafka를 사용하면 요청이 몰려도 Kafka가 중간에서 버퍼 역할을 한다.

Worker는 자신이 처리할 수 있는 속도로 메시지를 읽어가면 된다.

다만 Kafka에만 메시지가 있고 DB에 PENDING 상태가 없다면 사용자가 상태를 조회하기 어려울 수 있다.

따라서 상태 조회를 위해 Redis나 별도 결과 저장소가 필요해질 수 있다.

---

### **3주차: Redis로 선착순/중복 요청 걸러내기**

3주차에서는 Redis를 도입해서 DB에 가기 전에 선착순 여부와 중복 요청을 빠르게 판단한다.

예를 들어 다음과 같은 작업을 Redis에서 처리할 수 있다.

```
- 쿠폰 수량 차감
- 선착순 성공 여부 판단
- 사용자 중복 요청 방지
- 임시 처리 상태 저장
```

구조는 다음과 같이 발전한다.

```
Client
→ API Server
→ Kafka에 요청 적재
→ Worker가 Kafka 메시지 소비
→ Redis로 선착순/중복 판단
→ 성공한 요청만 DB 저장
```

이렇게 하면 모든 요청을 DB에 저장하지 않고, 실제로 발급 가능한 요청만 DB에 저장할 수 있다.

예를 들어 요청이 100,000건이고 쿠폰 수량이 1,000개라면 다음처럼 바뀐다.

```
기존 방식:
요청 100,000건 → DB에 PENDING 100,000건 저장

개선 방식:
요청 100,000건 → Kafka/Redis에서 완충 및 필터링
성공한 1,000건 → DB에 최종 발급 결과 저장
```

이 구조는 대규모 선착순 이벤트에서 DB 부하를 크게 줄일 수 있다.

---

### **4주차 이후: DB는 최종 정합성을 보장한다**

Redis와 Kafka를 사용하더라도 최종 발급 결과는 DB에 정확하게 저장되어야 한다.

예를 들어 같은 사용자가 같은 쿠폰을 두 번 발급받으면 안 된다.

그래서 DB에는 다음과 같은 제약 조건을 둘 수 있다.

```
UNIQUE(coupon_id, user_id)
```

이렇게 하면 Redis나 Kafka 단계에서 중복 요청을 걸러냈더라도, 마지막에 DB가 한 번 더 정합성을 보장한다.

즉, DB는 모든 요청을 받는 저장소가 아니라 최종 발급 결과의 정합성을 보장하는 저장소로 역할이 바뀐다.

---

### **6주차: Outbox Pattern으로 이벤트 발행 정합성 보장하기**

나중에 쿠폰 발급 결과를 다른 서비스에 알려야 할 수 있다.

예를 들어 쿠폰 발급이 성공하면 알림 서비스, 마이페이지 서비스, 통계 서비스가 이 사실을 알아야 한다.

```
쿠폰 발급 성공
→ 알림 발송
→ 마이페이지 쿠폰함 갱신
→ 통계 데이터 반영
```

이때 단순히 DB에 쿠폰 발급 결과를 저장한 뒤 Kafka 이벤트를 발행하면 다음 문제가 생길 수 있다.

```
DB에는 쿠폰 발급 성공 저장
Kafka 이벤트 발행 실패
```

그러면 DB에는 성공 기록이 있는데 알림이나 마이페이지 갱신 이벤트는 전달되지 않을 수 있다.

이 문제를 해결하기 위해 Outbox Pattern을 사용한다.

```
Worker
→ DB 트랜잭션 시작
→ 쿠폰 발급 결과 저장
→ Outbox 이벤트 저장
→ 커밋

Outbox Publisher
→ Outbox 이벤트 조회
→ Kafka 발행
→ 발행 완료 처리
```

Outbox Pattern은 DB 부하를 줄이는 기술이 아니다.

Outbox Pattern의 목적은 DB 저장과 이벤트 발행 사이의 정합성을 보장하는 것이다.

따라서 Outbox는 요청 접수 단계의 모든 요청에 붙이기보다는, 최종 발급 결과를 저장하고 후속 이벤트를 발행해야 하는 시점에 사용하는 것이 더 자연스럽다.

---

## **최종 정리**

1주차에서는 DB에 PENDING 상태를 저장한 뒤 응답하는 방식을 기본안으로 선택한다.

이 방식은 요청 유실 방지, 상태 조회, 장애 복구 측면에서 이해하기 쉽고 안정적이다.

```
Client
→ API Server
→ DB에 PENDING 저장
→ Client에게 접수 완료 응답
→ Worker가 뒤에서 처리
```

다만 실제 대규모 선착순 이벤트에서는 이 방식만으로는 부족할 수 있다.

API 요청마다 DB에 PENDING을 저장하면 이벤트 시작 순간에 DB가 병목이 될 수 있기 때문이다.

그래서 이후 주차에서는 구조를 다음과 같이 발전시킨다.

```
1주차:
DB PENDING 저장으로 요청 유실 방지와 상태 조회 구조 이해

2주차:
Kafka로 요청을 완충하고 Worker가 비동기로 처리

3주차:
Redis로 선착순 수량과 중복 요청을 빠르게 판단

4주차 이후:
DB Unique 제약으로 최종 발급 정합성 보장

6주차:
Outbox Pattern으로 DB 저장과 이벤트 발행의 정합성 보장
```

최종적으로 대규모 선착순 쿠폰 시스템은 다음 방향으로 발전한다.

```
Client
→ API Server
→ Kafka에 요청 적재
→ Worker가 Kafka 소비
→ Redis로 선착순/중복 판단
→ 성공한 요청만 DB 저장
→ Outbox로 발급 완료 이벤트 발행 보장
→ 알림/마이페이지/통계 서비스가 후속 처리
```

즉, 이번 주차의 결론은 다음과 같다.

```
1주차 기준으로는 DB에 PENDING 상태를 저장한 뒤 응답하는 방식이
요청 유실 방지와 상태 조회를 설명하기에 가장 적절한 기본 구조다.

하지만 실제 대규모 트래픽에서는 DB PENDING 저장이 병목이 될 수 있으므로,
이후 Kafka, Redis, Outbox를 도입해 더 확장 가능한 구조로 개선한다.
```
