# 1주차 과제: 요청 처리 구조 설계

## 주제

선착순 쿠폰 발급 요청을 API 서버에서 바로 처리할지, 요청만 접수하고 실제 발급은 비동기로 처리할지 설계한다.

---

# 1. 과제 목표

1주차 과제의 목표는 선착순 쿠폰 발급 요청이 들어왔을 때 **전체 요청 처리 구조를 어떻게 가져갈지** 설계하는 것이다.

이번 주차에서는 Kafka, Redis, Outbox 같은 세부 기술을 깊게 다루지 않는다.

핵심은 아래 질문에 답하는 것이다.

```
사용자가 쿠폰 발급 버튼을 눌렀을 때
API 서버가 바로 쿠폰 발급까지 처리할 것인가?

아니면 요청만 먼저 접수하고
실제 쿠폰 발급은 뒤에서 비동기로 처리할 것인가?
```

또한 단순히 “비동기가 좋다”라고 결론 내리는 것이 아니라, 비동기 구조에서 API 서버가 어디까지 처리해야 하는지, 언제 사용자에게 요청 접수 응답을 줄 수 있는지, 비동기처럼 보이지만 실제로는 문제가 있는 구조는 무엇인지까지 고민하는 것이 목표다.

---

# 2. 문제 상황

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 1개만 발급 가능
발급 방식: 선착순
```

이벤트 시작 시간이 되면 많은 사용자가 동시에 쿠폰 발급 버튼을 누른다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/d90874d2-601a-48e4-95df-636341db25cb" />

가장 단순한 구조는 다음과 같다.

```
Client
→ API Server
→ DB에서 쿠폰 수량 조회
→ DB에 쿠폰 발급 기록 저장
→ Client에게 성공/실패 응답
```

하지만 이 구조에서는 요청이 몰리는 순간 API 서버와 DB에 부하가 집중될 수 있다.

예를 들어 이벤트 시작 직후 1분 안에 10만 건의 요청이 들어온다면 다음과 같이 계산할 수 있다.

```
100,000건 / 60초 = 약 1,667 RPS
```

즉, 초당 약 1,667개의 요청이 들어올 수 있다.

실제로는 시작 0~5초에 몰려서 순간 RPS는 이보다 몇 배 높을 수 있다.

이 요청을 모두 API 서버가 바로 DB에 처리하려고 하면 DB 조회, DB 저장, Connection Pool 부족, Lock 증가, 응답 지연, Timeout 같은 문제가 생길 수 있다.

따라서 이번 과제에서는 요청을 바로 끝까지 처리하는 구조와 요청만 접수하고 실제 발급을 뒤에서 처리하는 구조를 비교하고, 선착순 쿠폰 이벤트에 더 적합한 구조를 설계해야 한다.

---

# 3. 알아야 할 간단한 개념

## 3-1. 동기 처리

동기 처리는 사용자의 요청이 들어왔을 때 API 서버가 바로 모든 처리를 끝내고 최종 결과를 응답하는 방식이다.

```
Client
→ API Server
→ DB 처리
→ Client에게 최종 성공/실패 응답
```

장점은 구조가 단순하고 사용자가 결과를 바로 알 수 있다는 점이다.

단점은 요청이 몰릴 때 API 서버와 DB에 부하가 집중될 수 있다는 점이다.

---

## 3-2. 비동기 처리

비동기 처리는 사용자의 요청을 받자마자 최종 발급까지 끝내지 않고, 요청만 먼저 접수한 뒤 실제 발급 처리는 뒤에서 수행하는 방식이다.

```
Client
→ API Server
→ 요청 접수 응답
→ 뒤에서 실제 쿠폰 발급 처리
→ 사용자는 나중에 결과 조회
```

장점은 요청 접수와 실제 발급 처리를 분리할 수 있다는 점이다.

단점은 사용자가 요청 직후 최종 결과를 바로 알 수 없기 때문에, 발급 결과를 나중에 확인할 수 있는 구조가 필요하다는 점이다.

---

## 3-3. 요청 접수와 발급 성공의 차이

비동기 처리에서는 **요청 접수**와 **발급 성공**이 다르다.

```
요청 접수:
서버가 사용자의 요청을 받았고, 이후 처리할 수 있도록 기록했다는 뜻

발급 성공:
실제로 쿠폰 발급 처리가 완료되었다는 뜻
```

예를 들어 사용자가 다음과 같은 응답을 받았다고 해서 쿠폰 발급이 성공한 것은 아니다.

```
상태: PENDING
메시지: 쿠폰 발급 요청이 접수되었습니다.
```

이 응답은 서버가 요청을 정상적으로 접수했고, 실제 발급 처리는 뒤에서 진행될 예정이라는 뜻이다.

---

## 3-4. 비동기 처리에서 기다리면 안 되는 이유

비동기 처리 구조를 선택했더라도 API 서버가 뒤쪽 처리 결과를 기다리면 비동기 처리의 장점이 줄어든다.

예를 들어 다음 구조를 보자.

```
Client
→ API Server
→ Queue에 요청 넣음
→ Worker가 쿠폰 발급 처리
→ API Server가 Worker 결과를 기다림
→ Client에게 최종 성공/실패 응답
```

이 구조는 Queue를 사용하고 있지만, API 서버가 Worker 결과를 기다리고 있다.

이 경우 사용자는 여전히 최종 결과가 나올 때까지 기다려야 하고, API 서버 스레드도 오래 점유된다.

따라서 비동기 처리 구조에서는 API 서버가 최종 발급 결과를 기다리지 않고, 요청 접수 응답을 빠르게 반환하는 방향으로 설계해야 한다.

## **3-5. 블로킹과 논블로킹**

동기/비동기와 함께 자주 헷갈리는 개념이 **블로킹/논블로킹**이다.

동기/비동기는 요청한 작업의 결과를 **같은 요청 흐름에서 직접 받아 처리하는가**, 아니면 요청 흐름과 실제 처리 흐름을 분리하는가에 대한 개념이다.

블로킹/논블로킹은 주로 **현재 실행 흐름이 멈추는가, 멈추지 않는가**에 대한 개념이다.

---

### **블로킹**

블로킹은 어떤 작업이 끝날 때까지 현재 실행 흐름이 멈춰 있는 방식이다.

예를 들어 API 서버가 DB에 쿠폰 발급 기록을 저장한다고 가정해보자.

```
API Server
→ DB 저장 요청
→ DB 응답이 올 때까지 기다림
→ DB 저장 완료
→ 다음 로직 실행
```

이때 API 서버의 해당 요청 처리 흐름은 DB 응답이 올 때까지 멈춰 있다.

이런 방식을 블로킹이라고 한다.

선착순 쿠폰 발급에서 모든 요청이 DB 처리 결과를 기다리면, 요청이 몰릴 때 API 서버의 스레드가 많이 점유될 수 있다.

```
Client
→ API Server
→ DB 수량 조회
→ DB 응답 대기
→ DB 발급 기록 저장
→ DB 응답 대기
→ Client에게 성공/실패 응답
```

이 구조는 이해하기 쉽지만, 요청이 많아질수록 API 서버와 DB에 부담이 커진다.

---

### **논블로킹**

논블로킹은 작업을 요청했을 때, 그 작업이 즉시 완료되지 않더라도 현재 실행 흐름을 멈추지 않고 바로 제어권을 돌려받는 방식이다.

예를 들어 API 서버가 외부 작업을 요청한 뒤 바로 다른 일을 할 수 있다면 논블로킹에 가깝다.

```
API Server
→ 작업 요청
→ 즉시 제어권 반환
→ 현재 흐름이 멈추지 않고 다음 작업 수행
```

논블로킹 방식에서는 요청 처리 흐름이 특정 작업 하나 때문에 오래 멈춰 있지 않는다.

다만 논블로킹이라고 해서 무조건 전체 시스템이 좋아지는 것은 아니다.

결과를 나중에 어떻게 받을지, 실패했을 때 어떻게 복구할지, 상태를 어디에 저장할지까지 함께 설계해야 한다.

---

### **동기/비동기와 블로킹/논블로킹의 차이**

두 개념은 비슷해 보이지만 기준이 다르다.

```
동기/비동기:
요청한 작업의 결과를 같은 흐름으로 직접 받아 처리하는가, 
아니면 다른 흐름에서 처리되도록 분리하는가?

블로킹/논블로킹:
작업이 끝날 때까지 현재 실행 흐름이 멈추는가,
아니면 바로 제어권을 돌려받는가?
```

예를 들어 동기 처리는 보통 블로킹 방식으로 구현되는 경우가 많다.

```
Client
→ API Server
→ DB 처리 완료까지 기다림
→ Client에게 최종 결과 응답
```

하지만 동기와 블로킹이 완전히 같은 뜻은 아니다.

동기는 **결과를 그 흐름 안에서 확인하는 방식**이고,
블로킹은 **기다리는 동안 실행 흐름이 실제로 멈춰 있는 방식**이다.

---

### **쿠폰 발급 시스템에서 중요한 점**

이번 과제에서 중요한 것은 용어를 외우는 것이 아니라, 다음 차이를 이해하는 것이다.

```
나쁜 구조:
API Server가 쿠폰 발급 최종 결과까지 기다림

좋은 구조:
API Server는 요청을 안전하게 접수한 뒤 빠르게 응답하고,
실제 쿠폰 발급은 뒤에서 처리함
```

즉, 선착순 쿠폰 이벤트에서는 API 서버가 모든 발급 처리를 끝까지 기다리게 만들면 문제가 생길 수 있다.

```
Client
→ API Server
→ DB 처리
→ 알림 처리
→ 마이페이지 갱신
→ Client에게 최종 응답
```

이 구조는 요청 하나가 처리되는 동안 API 서버가 많은 작업을 오래 붙잡고 있다.

반대로 요청 접수와 실제 발급을 분리하면 API 서버의 역할이 줄어든다.

```
Client
→ API Server
→ 요청 검증
→ 요청 상태 저장
→ Client에게 요청 접수 응답
→ Worker가 뒤에서 쿠폰 발급 처리
```

이 구조에서는 API 서버가 최종 발급 결과를 기다리지 않는다.

사용자는 먼저 요청 접수 응답을 받고, 실제 발급 결과는 나중에 조회한다.

---

### **정리**

```
동기 처리:
요청을 보낸 흐름에서 최종 결과까지 확인한다.

비동기 처리:
요청만 먼저 접수하고, 실제 처리는 뒤에서 진행한다.

블로킹:
작업이 끝날 때까지 현재 실행 흐름이 멈춘다.

논블로킹:
작업을 요청한 뒤 현재 실행 흐름이 멈추지 않는다.
```

이번 과제의 핵심은 “비동기를 사용한다”는 말이 아니라, API 서버가 최종 발급 결과까지 기다리는 구조인지, 요청만 접수하고 빠르게 응답하는 구조인지 구분하는 것이다.

선착순 쿠폰 발급 시스템에서는 API 서버가 발급 완료까지 기다리기보다, 요청을 안전하게 접수한 뒤 빠르게 응답하고 실제 발급은 뒤에서 처리하는 구조가 더 적합하다.
