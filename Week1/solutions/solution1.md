# 과제 1 해설 — 동기 처리와 비동기 처리 구조 비교



아래 다이어그램은 쿠폰 발급 요청이 들어왔을 때 **동기 처리 구조**와 **비동기 처리 구조**가 각각 어떤 순서로 동작하는지 비교한 것이다.

동기 처리는 API Server가 쿠폰 발급 요청을 받은 뒤, 쿠폰 수량 확인, 발급 기록 저장, 알림 발송, 마이페이지 갱신까지 하나의 요청 흐름 안에서 직접 처리하는 방식이다. 반면 비동기 처리는 API Server가 요청을 접수한 뒤 실제 쿠폰 발급 처리는 Queue 또는 Kafka에 메시지를 전달하고, Worker가 뒤에서 처리하는 방식이다.

---

## 1. 동기 처리 구조

동기 처리 구조에서는 사용자가 쿠폰 발급 요청을 보내면 API Server가 발급에 필요한 작업을 직접 수행한다.

흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
DB 조회 및 저장
  ↓
알림 발송
  ↓
마이페이지 데이터 갱신
  ↓
Client에게 최종 성공 / 실패 응답
```

API Server는 먼저 사용자가 로그인되어 있는지 확인하고, 현재 시간이 쿠폰 이벤트 기간에 포함되는지 확인한다.

그 다음 DB에서 남은 쿠폰 수량을 조회한다. 쿠폰 수량이 남아 있다면 DB에 쿠폰 발급 기록을 저장하고, 알림 발송과 마이페이지 데이터 갱신까지 수행한다. 모든 작업이 끝난 뒤에야 사용자에게 최종 응답을 반환한다.

예를 들어 발급에 성공하면 다음과 같은 응답을 줄 수 있다.

```json
{
  "status": "SUCCESS",
  "message": "쿠폰 발급이 완료되었습니다."
}
```

반대로 쿠폰이 모두 소진되었다면 다음과 같은 응답을 줄 수 있다.

```json
{
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

동기 처리의 장점은 구조가 단순하다는 것이다. 요청이 들어오고, 처리하고, 결과를 바로 응답하기 때문에 흐름을 이해하기 쉽다.

하지만 단점도 크다. 선착순 쿠폰 이벤트처럼 짧은 시간에 요청이 몰리는 상황에서는 API Server와 DB에 부하가 집중된다. API Server가 쿠폰 수량 조회, 발급 기록 저장, 알림 발송, 마이페이지 갱신까지 모두 직접 처리하면 요청 처리 시간이 길어진다. 요청 처리 시간이 길어질수록 동시에 처리할 수 있는 요청 수도 줄어든다.

따라서 동기 처리는 트래픽이 적고, 사용자가 즉시 최종 결과를 알아야 하는 기능에 더 적합하다.

---

## 2. 비동기 처리 구조

비동기 처리 구조에서는 API Server가 모든 작업을 끝까지 직접 처리하지 않는다.

사용자가 쿠폰 발급 요청을 보내면 API Server는 기본 검증과 요청 접수까지만 담당한다. 이후 실제 쿠폰 발급 처리는 Kafka에 메시지를 발행하고, Worker가 뒤에서 처리한다.

흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
요청을 PENDING 상태로 저장
  ↓
Kafka에 쿠폰 발급 요청 메시지 발행
  ↓
Client에게 접수 완료 응답
  ↓
Worker가 Kafka 메시지 소비
  ↓
쿠폰 수량 확인 및 차감
  ↓
DB에 발급 기록 저장
  ↓
발급 결과 저장
  ↓
알림 / 마이페이지 갱신
```

비동기 구조에서 API Server는 사용자의 로그인 여부와 이벤트 시간을 확인한 뒤, 요청을 접수한다. 그리고 해당 요청을 DB에 `PENDING` 상태로 저장한다.

단, DB에 PENDING 상태를 저장하고 Kafka에도 메시지를 발행하는 구조는 DB 저장과 Kafka 발행 사이의 정합성 문제가 생길 수 있다.

실제 시스템에서는 이 문제를 해결하기 위해 Outbox Pattern, 재시도 로직, 또는 요청 상태 복구 전략이 필요하다.

1주차 수준에서는 “사용자에게 접수 완료 응답을 주기 전에 요청이 DB나 Kafka 같은 안전한 위치에 기록되어야 한다”는 점을 이해하는 것이 핵심이다.

그 다음 Kafka에 쿠폰 발급 요청 메시지를 발행한다.

```
coupon.issue.requested
```

같은 Topic에 메시지를 넣을 수 있다.

중요한 점은 사용자에게 접수 완료 응답을 주는 시점이다. 단순히 요청을 받았다고 바로 성공 응답을 주면 안 된다. 최소한 `PENDING` 저장과 Kafka 메시지 발행이 성공한 뒤에 접수 완료 응답을 줘야 한다.

예를 들어 비동기 처리에서는 다음과 같은 응답을 줄 수 있다.

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다."
}
```

여기서 `PENDING`은 쿠폰 발급이 최종 성공했다는 뜻이 아니다. 단지 “요청이 정상적으로 접수되었고, 뒤에서 처리될 예정”이라는 의미다.

## 3. Worker의 역할

비동기 구조에서 실제 쿠폰 발급 처리는 Worker가 담당한다.

Worker는 Kafka에 쌓인 쿠폰 발급 요청 메시지를 읽고, 실제 발급 로직을 수행한다.

Worker의 주요 역할은 다음과 같다.

```
1. 쿠폰 수량 확인 및 차감
2. DB에 발급 기록 저장
3. 발급 성공 / 실패 결과 저장
4. 알림 발송, 마이페이지 반영에 필요한 후속 작업
```

여기서 가장 중요한 부분은 **쿠폰 수량 확인 및 차감은 원자적으로 처리되어야 한다**는 점이다.

예를 들어 남은 쿠폰이 1개인데 동시에 여러 요청이 들어온다고 가정해보자.

```
요청 A → 남은 수량 1개 확인
요청 B → 남은 수량 1개 확인
요청 C → 남은 수량 1개 확인
```

이런 식으로 여러 Worker가 동시에 수량이 남아 있다고 판단하면 실제 쿠폰 수량보다 더 많이 발급되는 문제가 생길 수 있다.

따라서 쿠폰 수량 확인과 차감은 분리해서 처리하면 안 되고, 하나의 원자적인 작업처럼 처리해야 한다.

예를 들어 다음과 같은 방법을 사용할 수 있다.

```
쿠폰 수량 초과 발급 방지:
- Redis atomic 연산
- Redis Lua Script
- DB Lock
- DB Transaction

사용자 중복 발급 방지:
- UNIQUE(coupon_id, user_id)
- requestId 기반 멱등성 처리
```

과제 1에서는 깊게 구현할 필요는 없지만, “Worker가 뒤에서 처리한다”는 것만으로는 부족하다. Worker가 처리할 때도 중복 발급과 초과 발급을 막는 설계가 필요하다.

## 4. 비동기 처리에서 최종 결과 확인 방법

비동기 처리에서는 사용자가 요청 직후 최종 성공 또는 실패 결과를 바로 받지 않는다.

사용자는 먼저 다음과 같은 접수 완료 응답을 받는다.

```
쿠폰 발급 요청이 접수되었습니다.
```

이후 실제 발급 결과는 Worker가 처리한 뒤에 결정된다.

따라서 비동기 구조에서는 최종 결과를 확인할 수 있는 방법이 필요하다.

대표적인 방법은 다음과 같다.

```
1. 마이페이지에서 확인
2. 쿠폰함에서 확인
3. 발급 결과 조회 API 호출
4. 알림 메시지 수신
5. WebSocket / SSE / 앱 푸시 알림
```

예를 들어 사용자는 쿠폰함에 들어가서 쿠폰이 실제로 발급되었는지 확인할 수 있다. 또는 발급 결과 조회 API를 호출해서 현재 상태를 확인할 수도 있다.

```
PENDING → 아직 처리 중
SUCCESS → 발급 성공
FAILED → 발급 실패
```

이런 상태값을 제공하면 사용자는 비동기 처리에서도 현재 진행 상황을 이해할 수 있다.

---

## 5. 동기 처리와 비동기 처리의 핵심 차이

동기 처리와 비동기 처리의 가장 큰 차이는 **사용자 요청 흐름 안에서 실제 발급까지 처리하느냐**, 아니면 **요청 접수와 실제 발급 처리를 분리하느냐**이다.

동기 처리에서는 API Server가 모든 작업을 직접 수행한다. 그래서 사용자는 최종 성공 또는 실패 결과를 바로 받을 수 있다. 하지만 요청이 몰리면 API Server와 DB에 부하가 집중된다.

비동기 처리에서는 API Server가 요청 접수까지만 담당하고, 실제 발급은 Worker가 뒤에서 처리한다. 그래서 API Server가 빠르게 응답할 수 있고, 대량 요청을 Kafka에 쌓아두고 Worker가 처리 가능한 속도로 소비하게 만들 수 있다.

다만 안정적인 처리를 위해서는 Kafka ack 확인, 중복 메시지 처리, 재시도, DLQ 같은 설계가 함께 필요하다.

다만 비동기 처리는 동기 처리보다 구조가 복잡하다. 요청 상태를 저장해야 하고, 실패한 메시지를 재처리해야 하며, 사용자가 최종 결과를 조회할 수 있는 방법도 제공해야 한다.

---

## 6. 선착순 쿠폰 이벤트에는 어떤 구조가 더 적합한가?

선착순 쿠폰 이벤트에서는 비동기 처리 구조가 더 적합하다.

이유는 요청이 짧은 시간에 집중되기 때문이다. 이벤트가 시작되는 순간 많은 사용자가 동시에 쿠폰 발급 요청을 보낼 수 있다. 이때 API Server가 모든 요청을 직접 처리하면 API Server와 DB에 부하가 집중된다.

반면 비동기 구조에서는 API Server가 요청을 빠르게 접수하고 Kafka에 메시지를 쌓아둘 수 있다. 

Worker는 Kafka 메시지를 소비하면서 실제 발급 처리를 수행한다.

Kafka는 Partition 내부 순서는 보장하지만, 여러 Partition을 사용하는 경우 전체 요청의 전역 순서가 항상 보장되는 것은 아니다.

따라서 정확한 선착순 처리와 수량 제어는 Redis 원자 연산, DB Lock, Transaction 같은 정합성 장치와 함께 설계해야 한다.

즉, 비동기 구조는 대량 요청을 한 번에 모두 처리하려고 하지 않고, 요청을 안정적으로 받아둔 뒤 뒤에서 처리하는 방식이다.

그래서 선착순 쿠폰 이벤트처럼 트래픽이 순간적으로 몰리는 기능에서는 요청 접수와 실제 발급 처리를 분리하는 비동기 구조가 더 적합하다.
