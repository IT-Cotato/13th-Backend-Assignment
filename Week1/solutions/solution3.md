### 문제 1. API 서버가 너무 많은 일을 한다

API 서버가 다음 작업을 모두 직접 처리한다.

```
- 쿠폰 수량 조회 및 차감
- 쿠폰 발급 기록 저장
- 알림 발송
- 마이페이지 데이터 갱신
- 최종 응답 생성
```

이번 선착순 쿠폰 이벤트처럼 트래픽이 순간적으로 몰리는 구조에서는 API 서버가 모든 발급 처리와 후속 작업을 직접 수행하기보다, 사용자 요청을 받고 기본 검증을 한 뒤 실제 처리를 Worker나 비동기 처리 흐름으로 넘기는 것이 더 적합하다.

그런데 이 구조에서는 API 서버가 발급 처리, 후속 작업, 응답까지 모두 책임진다.

이러면 API 서버의 요청 처리 시간이 길어진다.

요청 처리 시간이 길어질수록 동시에 처리할 수 있는 요청 수는 줄어든다.

---

### 문제 2. DB에 부하가 집중된다

모든 요청이 DB에서 쿠폰 수량을 조회하고, 다시 DB에 발급 기록을 저장한다.

```
요청 1 → DB 수량 조회 → DB 저장
요청 2 → DB 수량 조회 → DB 저장
요청 3 → DB 수량 조회 → DB 저장
...
```

선착순 이벤트에서는 짧은 시간에 수많은 요청이 들어온다.

이 요청들이 모두 DB에 직접 접근하면 DB가 병목이 된다.

특히 쿠폰 수량 조회와 차감은 동시에 일어나면 경쟁 조건이 생길 수 있다.

예를 들어 쿠폰이 1개 남아 있는데 두 요청이 동시에 들어왔다고 하자.

```
요청 A: 남은 수량 1개 조회
요청 B: 남은 수량 1개 조회

요청 A: 발급 성공
요청 B: 발급 성공

```

따라서 쿠폰 수량 확인과 차감은 단순 조회 후 저장 방식이 아니라, Redis 원자 연산, DB 조건부 업데이트, Lock, Transaction 등을 통해 원자적으로 처리해야 한다.

이렇게 처리되면 쿠폰이 1개밖에 없는데 2개가 발급될 수 있다.

물론 DB 락이나 조건부 업데이트로 막을 수 있지만, 트래픽이 커질수록 DB 부담은 더 커진다.

---

### 문제 3. 알림 발송 실패가 쿠폰 발급 응답에 영향을 줄 수 있다

쿠폰 발급 자체는 성공했는데 알림 발송이 실패할 수 있다.

```
DB에 쿠폰 발급 기록 저장 성공
→ 알림 발송 실패
→ API 서버가 에러 응답
```

이 경우 사용자는 실패했다고 생각할 수 있다.

하지만 실제로는 DB에 쿠폰이 발급되어 있을 수 있다.

그러면 상태가 이상해진다.

```
사용자 화면: 쿠폰 발급 실패
DB 상태: 쿠폰 발급 성공
```

이런 상태는 사용자 문의와 운영 이슈로 이어진다.

알림 발송은 쿠폰 발급의 핵심 로직이 아니다.

쿠폰 발급이 성공했다면 알림 발송은 나중에 재시도해도 된다.

따라서 알림 발송 실패가 쿠폰 발급 성공 여부를 흔들면 안 된다.

---

### 문제 4. 마이페이지 데이터 갱신 실패가 쿠폰 발급 응답에 영향을 줄 수 있다

마이페이지 데이터 갱신도 마찬가지다.

쿠폰 발급 기록 저장은 성공했는데 마이페이지 캐시나 조회용 데이터 갱신이 실패할 수 있다.

```
쿠폰 발급 기록 저장 성공
→ 마이페이지 데이터 갱신 실패
→ 사용자에게 실패 응답
```

이 경우도 문제가 된다.

마이페이지 데이터는 조회 편의를 위한 데이터일 수 있다.

원본 발급 기록이 정상적으로 저장되었다면, 마이페이지 갱신은 재처리하면 된다.

따라서 마이페이지 갱신 같은 후속 작업은 쿠폰 발급 트랜잭션과 강하게 묶지 않는 편이 좋다.

---

### 문제 5. 요청 처리 시간이 길어져 타임아웃이 발생할 수 있다

API 서버가 너무 많은 작업을 처리하면 응답 시간이 길어진다.

```
DB 조회 100ms
DB 저장 150ms
알림 발송 300ms
마이페이지 갱신 200ms
기타 처리 100ms
```

요청 하나는 괜찮아 보일 수 있다.

하지만 트래픽이 몰리면 각 작업의 응답 시간이 더 길어진다.

그 결과 다음 문제가 생긴다.

```
- API Gateway 타임아웃
- 클라이언트 타임아웃
- 사용자의 중복 요청
- 서버 스레드 고갈
- 장애 전파
```

특히 알림 서버나 마이페이지 서버가 느려지면 쿠폰 발급 API까지 느려진다.

즉, 후속 작업의 장애가 핵심 발급 기능으로 전파된다.

---

### 문제 6. 후속 작업을 재시도하기 어렵다

알림 발송이나 마이페이지 갱신이 실패했을 때, 이 작업만 따로 재시도하기 어렵다.

동기 구조에서는 하나의 요청 흐름 안에서 여러 작업이 묶여 있다.

따라서 일부 작업만 실패했을 때 상태를 나누어 관리하기가 어렵다.

좋은 구조에서는 다음처럼 분리해야 한다.

```
쿠폰 발급 성공
→ coupon.issue.completed 이벤트 발행
→ Notification Consumer가 알림 처리
→ MyPage Consumer가 조회 데이터 갱신
```

이렇게 하면 알림 발송이 실패해도 알림 처리만 재시도하면 된다.

# 3-2 해설

API Server가 너무 많은 일을 하면 가장 먼저 응답 시간이 길어진다.

응답 시간이 길어지면 서버 자원이 오래 점유된다.

API 서버는 보통 동시에 처리할 수 있는 요청 수에 한계가 있다.

요청 하나가 오래 걸리면, 그만큼 다음 요청을 처리할 여유가 줄어든다.

```
요청 처리 시간이 짧음
→ 서버 자원 빨리 반환
→ 더 많은 요청 처리 가능

요청 처리 시간이 김
→ 서버 자원 오래 점유
→ 동시에 처리 가능한 요청 감소
→ 대기 요청 증가
→ 응답 지연
```

또한 API 서버가 여러 외부 시스템에 의존하면 장애 전파 문제가 생긴다.

```
알림 서버 장애
→ 쿠폰 발급 API 지연
→ 사용자 응답 지연
→ 재시도 증가
→ API 서버 부하 증가
```

즉, API 서버가 많은 일을 직접 처리하면 시스템 전체가 강하게 결합된다.

# 3-3 해설

현재 구조에서는 알림 발송이나 마이페이지 데이터 갱신이 쿠폰 발급 응답 전에 실행된다.

따라서 이 작업들이 실패하면 API 서버가 실패 응답을 내려버릴 수 있다.

하지만 쿠폰 발급의 핵심은 다음이다.

```
사용자에게 쿠폰 발급 권한이 있는가?
쿠폰 수량이 남아 있는가?
DB에 발급 기록이 정상 저장되었는가?
```

알림 발송은 핵심 발급 로직이 아니다.

마이페이지 갱신도 핵심 발급 로직이라기보다는 조회 편의를 위한 후속 작업에 가깝다.

따라서 쿠폰 발급은 성공했는데 알림 발송이 실패했다고 전체 요청을 실패로 처리하면 안 된다.

좋은 설계에서 다음과 같이 처리할 수 있다.

```
쿠폰 발급 성공
→ 사용자가 조회할 수 있도록 발급 결과를 DB에 저장
→ 알림 발송은 별도 비동기 처리
→ 마이페이지 갱신도 별도 비동기 처리
```

이렇게 하면 알림 발송 기능과 쿠폰 발급 기능의 결합도를 낮출 수 있다.
