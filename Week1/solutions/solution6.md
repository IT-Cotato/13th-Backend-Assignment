## 6-1 해설

비동기 처리는 다음 상황에서 유리하다.

```
- 요청이 짧은 시간에 많이 몰리는 경우
- 실제 처리가 오래 걸리는 경우
- 사용자에게 최종 결과를 즉시 보여주지 않아도 되는 경우
- 알림, 메일, 정산, 로그 적재처럼 후속 작업이 많은 경우
- 외부 시스템 호출이 많아 장애 전파를 줄이고 싶은 경우
```

선착순 쿠폰 이벤트가 대표적인 예다.

사용자는 이벤트 시작 시간에 한꺼번에 쿠폰 발급 버튼을 누른다.

이때 모든 요청을 API 서버가 직접 처리하면 서버와 DB에 부하가 집중된다.

비동기 구조를 사용하면 API 서버는 요청을 빠르게 접수하고, Worker가 뒤에서 처리할 수 있다.

```
순간적인 요청 폭주
→ Queue/Kafka에 적재
→ Worker가 처리 가능한 속도로 소비
```

비동기는 요청 폭주 상황에서 API 서버의 응답 지연을 줄이고, 트래픽을 완충하는 데 유리하다.

하지만 실제 처리 완료까지의 시간은 Consumer 처리 속도와 Consumer Lag에 따라 늦어질 수 있다.

## 6-2 해설

동기 처리는 다음 상황에서 더 적합하다.

```
- 요청 수가 많지 않은 경우
- 처리 시간이 짧은 경우
- 사용자가 최종 결과를 즉시 알아야 하는 경우
- 상태 관리가 복잡해질 필요가 없는 경우
- 실패 시 바로 사용자에게 알려야 하는 경우
```

예를 들어 로그인 요청은 보통 동기 처리가 적합하다.

```
사용자 로그인 요청
→ 아이디/비밀번호 확인
→ 성공/실패 즉시 응답
```

사용자는 로그인 성공 여부를 바로 알아야 한다.

이걸 비동기로 처리해서 “로그인 요청이 접수되었습니다. 나중에 확인해주세요”라고 하면 이상하다.

결제 승인도 대부분 최종 결과를 바로 알아야 한다.

사용자가 결제를 했는데 “결제 요청이 접수되었습니다. 나중에 확인해주세요”라고만 보여주면 사용자 경험이 나빠질 수 있다.

물론 실제 결제 시스템 내부에는 비동기 후처리가 있을 수 있다.

하지만 사용자에게 보여주는 핵심 승인 결과는 동기적으로 처리하는 경우가 많다.

## 6-3 해설

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/cf924124-5480-4d50-b3d7-4c5841efd0a2" />

비동기 구조는 성능상 장점이 있지만 공짜가 아니다.

다음과 같은 복잡도가 추가된다.

예를 들어 사용자가 요청을 보냈는데 Worker 처리가 늦어질 수 있다.

그러면 사용자는 계속 PENDING 상태를 보게 된다.

이때 시스템은 다음을 관리해야 한다.

```
- 이 요청이 아직 처리 중인가?
- Worker가 죽어서 멈춘 것인가?
- 재처리해야 하는가?
- 이미 성공했는데 메시지만 중복으로 들어온 것인가?
```

또한 Queue/Kafka를 사용하면 Consumer Lag도 봐야 한다.

Consumer Lag이 커지면 사용자는 결과를 늦게 확인하게 된다.

```
요청 접수는 빠름
하지만 실제 발급 결과는 늦게 나옴
```

즉, 비동기 구조는 API 서버를 가볍게 만들지만, 전체 시스템 관점에서는 상태 관리와 운영 난이도가 올라간다.

## 6-4 해설

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/3c54e049-9322-4d23-a301-8091ead0330c" />

항상 적합하지 않다.

사용자가 최종 결과를 즉시 알아야 하는 기능은 동기 처리가 더 자연스럽다.

예를 들어 다음 기능을 보자.

```
- 로그인
- 회원가입
- 결제 승인
- 비밀번호 변경
```

이런 기능은 사용자가 요청을 보낸 뒤 바로 결과를 알아야 한다.

물론 내부적으로 일부 작업은 비동기로 분리할 수 있다.

예를 들어 회원가입 자체는 동기 처리하고, 가입 축하 이메일 발송은 비동기로 처리할 수 있다.

```
회원가입 요청
→ 계정 생성은 동기 처리
→ 이메일 발송은 비동기 처리
```

즉, 중요한 것은 기능 전체를 무조건 동기 또는 비동기로 나누는 것이 아니다.

핵심 결과는 동기로 처리하고, 부가 작업은 비동기로 분리할 수 있다.

## 6-5 해설

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/593bf509-d581-4c6b-aa97-3d8682c3471e" />

선착순 쿠폰 이벤트에서는 비동기 처리가 더 적합하다.

이유는 다음과 같다.

첫째, 요청이 특정 시간에 몰린다.

이벤트 시작 시간이 되면 많은 사용자가 동시에 버튼을 누른다.

API 서버가 모든 요청을 끝까지 처리하면 서버와 DB가 한 번에 큰 부하를 받는다.

둘째, 사용자가 반드시 즉시 최종 결과를 받을 필요는 없다.

“요청이 접수되었습니다. 결과는 잠시 후 확인해주세요”라는 UX가 가능하다.

셋째, 실제 발급 처리는 순서와 정합성이 중요하다.

Queue/Kafka를 사용하면 요청을 바로 DB에 몰아넣지 않고 메시지로 쌓아둘 수 있다.

이후 Worker가 처리 가능한 속도로 메시지를 소비하면서 발급 처리를 수행할 수 있다.

다만 Kafka를 사용한다고 해서 정해진 수량만 정확히 발급되는 것이 자동으로 보장되는 것은 아니다.

정확한 선착순 처리와 중복 방지를 위해서는 Redis 원자 연산, DB Unique 제약, requestId 기반 멱등성 처리 같은 정합성 장치가 함께 필요하다.

넷째, 알림이나 마이페이지 갱신 같은 후속 작업을 분리할 수 있다.

쿠폰 발급 성공 여부와 알림 발송 성공 여부를 강하게 묶지 않아도 된다.

정리하면 다음과 같다.

```
선착순 쿠폰 이벤트의 핵심 문제는
사용자에게 0.1초라도 빨리 최종 성공을 알려주는 것이 아니라,
순간적으로 몰리는 많은 요청을 안정적으로 받아내고,
정해진 수량만 정확하게 발급하는 것이다.
```

그래서 비동기 구조가 더 적합하다.

실제로 요청을 유실 없이 받으려면 Kafka뿐만 아니라 이런 설정과 설계가 필요하다.

```
- Producer 전송 실패 처리
- acks=all
- retry 설정
- idempotent producer
- DB 또는 Redis에 요청 접수 기록 저장
- 장애 상황에서 재처리 가능한 구조
```
