# 과제 2-1 해설

선착순 쿠폰 이벤트에는 구조 B가 더 적합하다.

선착순 쿠폰 이벤트는 이벤트 시작 순간에 요청이 한꺼번에 몰릴 수 있다.

이때 API 서버가 모든 사용자의 최종 발급 결과를 기다리면 서버 자원이 오래 점유된다.

반면 구조 B는 API 서버가 요청을 빠르게 접수하고 응답하므로, 많은 요청을 짧은 시간 안에 받아낼 수 있다.

다만 접수 완료 응답은 단순히 요청을 메모리에 올린 시점이 아니라, DB나 Queue/Kafka처럼 장애가 나도 다시 복구할 수 있는 위치에 요청이 기록된 뒤 반환하는 것이 안전하다.

실제 발급 처리는 Worker가 Queue나 Kafka에 쌓인 요청을 소비하면서 처리한다.

다만 Kafka를 사용하는 경우에는 Partition 내부 순서는 보장되지만, 여러 Partition을 사용하면 전체 요청의 전역 순서가 항상 보장되는 것은 아니다.

즉, 구조 B는 순간적으로 몰리는 요청을 Queue/Kafka에 쌓아두고, Worker가 처리 가능한 속도로 안정적으로 처리할 수 있게 만든다.

# 과제 2-2 해설

이 경우에는 비동기 처리의 핵심 장점이 줄어든다.

비동기 처리의 목적은 요청 접수와 실제 처리를 분리해서 API 서버가 빨리 응답하도록 만드는 것인데, 구조 A는 결국 API 서버가 최종 결과를 기다린다.

그래서 구조 A에서는 다음 문제가 생긴다.

```
- API 서버 요청 스레드가 오래 점유된다.
- HTTP 커넥션이 오래 유지된다.
- Worker 처리가 느려지면 API 응답도 느려진다.
- Queue에 요청이 쌓이면 사용자는 계속 기다려야 한다.
- 클라이언트나 API Gateway에서 타임아웃이 발생할 수 있다.
- 사용자가 재시도하면 중복 요청이 늘어날 수 있다.
```

결론적으로 구조 A는 Queue를 사용했지만, 사용자 요청 관점에서는 여전히 최종 결과를 기다리는 구조에 가깝다.

# 과제 2-3 해설

API Server가 Worker 결과를 기다리면 가장 큰 문제는 **API 서버의 자원이 오래 묶인다**는 것이다.

요청이 10개라면 괜찮을 수 있다.

하지만 이벤트 시작 순간에 10,000개, 100,000개의 요청이 들어온다면 문제가 커진다.

```
1. API 서버 스레드 고갈
2. HTTP 커넥션 증가
3. 응답 지연
4. 타임아웃 증가
5. 사용자 재시도 증가
6. 중복 요청 증가
7. Worker 결과 전달 구조 복잡도 증가
8. 장애 발생 시 요청 상태 추적 어려움
```

특히 선착순 쿠폰 이벤트에서는 응답이 늦어지면 사용자가 버튼을 여러 번 누를 수 있다.

그러면 시스템 입장에서는 실제 사용자 수보다 훨씬 많은 요청을 처리해야 한다.

# 과제 2-4 해설

구조 B에서는 사용자가 처음 받는 응답이 최종 결과가 아니다.

처음 응답은 “요청 접수 완료”다.

따라서 최종 발급 결과를 확인할 수 있는 별도 방법이 필요하다.

다음과 같은 방법이 가능하다.

```
1. 발급 결과 조회 API
2. 마이페이지 / 쿠폰함 조회
3. 알림 발송
4. WebSocket / SSE
5. 앱 푸시
```

### 1. 발급 결과 조회 API

사용자가 받은 `requestId`로 나중에 결과를 조회하는 방식이다.

```
GET /coupon-issue-requests/REQ-12345
```

응답 예시는 다음과 같다.

```
{
  "requestId":"REQ-12345",
  "status":"SUCCESS",
  "message":"쿠폰 발급이 완료되었습니다."
}
```

실패한 경우는 이렇게 응답할 수 있다.

```
{
  "requestId":"REQ-12345",
  "status":"FAILED",
  "reason":"쿠폰이 모두 소진되었습니다."
}
```

가장 기본적인 방식이다.

---

### 2. 마이페이지 / 쿠폰함 조회

사용자가 직접 API를 호출하지 않더라도, 마이페이지나 쿠폰함에 들어갔을 때 발급 결과를 보여주는 방식이다.

예를 들어 쿠폰함에 들어갔을 때 다음처럼 보여줄 수 있다.

```
발급 완료된 쿠폰 목록
- 10% 할인 쿠폰
- 무료배송 쿠폰
```

아직 처리 중이면 이렇게 보여줄 수 있다.

```
쿠폰 발급 요청 처리 중입니다.
잠시 후 다시 확인해주세요.
```

사용자 입장에서는 가장 자연스러운 방식이다.

---

### 3. 알림 발송

Worker가 쿠폰 발급 처리를 끝낸 뒤 사용자에게 알림을 보내는 방식이다.

```
쿠폰 발급이 완료되었습니다.
쿠폰함에서 확인해주세요.
```

실패한 경우도 알림으로 알려줄 수 있다.

```
쿠폰이 모두 소진되어 발급에 실패했습니다.
```

단, 알림 발송은 실패할 가능성이 있으므로 쿠폰 발급 로직과 강하게 결합해서는 안 된다.

쿠폰 발급은 핵심 비즈니스 로직이고, 알림 발송은 발급 이후에 수행되는 후속 작업이다. 따라서 알림 발송 실패가 쿠폰 발급 실패로 이어지면 안 된다.

예를 들어 쿠폰은 정상적으로 발급되었지만 알림 서버 장애, 외부 푸시 서비스 장애, 네트워크 오류 등으로 알림 전송에 실패할 수 있다. 이때 쿠폰 발급 트랜잭션까지 롤백하면 사용자 입장에서는 실제로 받을 수 있었던 쿠폰을 받지 못하는 문제가 생긴다.

따라서 쿠폰 발급 처리가 완료되면 `coupon.issue.completed`와 같은 이벤트를 발행하고, 알림 서비스는 해당 이벤트를 구독하여 비동기로 알림을 전송하는 구조가 적절하다.

알림 서비스는 쿠폰 발급 시스템과 분리된 별도 서비스로 설계할 수 있다. 이 서비스에서는 알림 전송 실패에 대비해 재시도 큐, DLQ, 재전송 처리 등을 구성할 수 있다. 또한 요구사항에 따라 최소 한 번 전송, 최대 한 번 전송, 중복 알림 방지 정책 등을 선택할 수 있다.

최소 한 번 전송은 알림이 중복될 수 있지만 유실 가능성을 줄이는 방식이고, 최대 한 번 전송은 중복 가능성은 줄지만 유실될 수 있는 방식이다. 따라서 실제 서비스에서는 중복 알림을 막기 위한 idempotency key 같은 장치도 함께 고려할 수 있다.

이렇게 설계하면 쿠폰 발급의 안정성을 유지하면서도, 알림 발송은 별도의 후속 작업으로 유연하게 처리할 수 있다.

### 4. WebSocket / SSE

사용자가 이벤트 페이지에 머무르고 있을 때 실시간으로 결과를 내려주는 방식이다.

예를 들어 사용자가 버튼을 누르면 화면에는 먼저 이렇게 표시한다.

```
쿠폰 발급 요청 처리 중...
```

선착순 쿠폰 발급 시스템에서는 특히 다음과 같은 흐름에 잘 어울린다.

```
Client
→ 쿠폰 발급 요청
→ API Server가 요청 접수
→ Client에게 "처리 중" 응답
→ Client가 SSE 또는 WebSocket 연결 유지
→ Worker가 쿠폰 발급 처리
→ DB에 SUCCESS / FAILED 저장
→ 서버가 실시간으로 결과 전송
→ Client 화면에 발급 결과 표시
```

다만 WebSocket이나 SSE는 클라이언트와 서버 사이의 연결을 일정 시간 유지해야 하므로, 단순한 조회 API보다 구현과 운영 난이도가 높다. 사용자가 많아지면 연결 수 관리, 타임아웃 처리, 재연결 처리, 서버 확장 방식도 함께 고려해야 한다.

따라서 모든 결과 확인을 WebSocket이나 SSE에만 의존하기보다는, 기본적으로는 쿠폰함 조회 API를 제공하고, 이벤트 페이지에 머무르는 사용자에게는 실시간 결과를 보여주는 보조 수단으로 사용하는 것이 좋다.

### WebSocket / SSE 사용 예시 1 - 티켓팅 대기열

예매 사이트에서 많이 쓰는 구조이다.

```
현재 대기 순번: 12,341번
예상 대기 시간: 약 3분
```

이런 정보는 사용자가 계속 새로고침해서 확인하는 것보다 서버가 실시간으로 내려주는 게 자연스럽다.

### WebSocket / SSE 사용 예시 2 - AI 답변 생성

ChatGPT처럼 답변이 한 번에 완성되는 게 아니라 조금씩 생성되는 경우에도 SSE를 많이 쓴다.

```
답변 생성 중...
문장 일부 도착
다음 문장 도착
최종 답변 완료
```

이것도 서버가 처리 완료될 때까지 기다렸다가 한 번에 응답하는 것보다, 중간 결과를 실시간으로 내려주는 방식이 사용자 경험이 좋다.

### 5. 앱 푸시

모바일 앱이라면 발급 결과를 푸시 알림으로 보낼 수 있다.

```
[쿠폰 발급 완료]
선착순 쿠폰이 발급되었습니다.
```

앱을 닫아도 결과를 알려줄 수 있다는 장점이 있다.

하지만 푸시 알림은 사용자에게 결과를 빠르게 알려주는 수단일 뿐, 발급 결과를 확인하는 유일한 방법이 되어서는 안 된다.

푸시 알림은 여러 이유로 실패할 수 있다. 사용자가 앱 알림 권한을 꺼두었을 수도 있고, 기기 네트워크 상태가 좋지 않을 수도 있으며, FCM이나 APNs 같은 외부 푸시 서비스 장애가 발생할 수도 있다. 또한 알림이 정상적으로 발송되었더라도 사용자가 알림을 지웠거나 확인하지 못할 가능성도 있다.

이런 상황에서 쿠폰 발급 결과를 푸시 알림에만 의존하면 사용자는 실제로 쿠폰이 발급되었는지, 실패했는지 알기 어렵다. 특히 선착순 쿠폰 이벤트에서는 사용자가 “내가 쿠폰을 받았는지”를 명확하게 확인하고 싶어 하기 때문에, 결과 확인 경로가 반드시 필요하다.

따라서 푸시 알림은 보조적인 안내 수단으로 사용하고, 쿠폰함 조회나 마이페이지 조회 같은 기본 확인 방식을 함께 제공해야 한다.

예를 들어 쿠폰 발급 요청이 접수되면 사용자는 처음에는 `처리 중` 상태를 볼 수 있고, Worker가 실제 발급 처리를 완료하면 쿠폰함에서 `발급 완료` 또는 `발급 실패` 상태를 확인할 수 있어야 한다. 알림은 이 상태 변경을 사용자에게 알려주는 역할만 한다.

즉, 시스템의 기준 데이터는 알림이 아니라 DB에 저장된 쿠폰 발급 결과여야 한다. 알림은 이 결과를 사용자에게 전달하는 부가 기능이고, 쿠폰함 조회 API는 사용자가 언제든지 신뢰할 수 있는 결과를 확인하는 기본 경로다.
