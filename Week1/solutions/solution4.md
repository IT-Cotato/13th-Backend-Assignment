# 과제 4 해설

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유 |
| --- | --- | --- | --- |
| 로그인 여부 확인 | O |  | 인증되지 않은 사용자의 요청은 애초에 접수하면 안 되기 때문이다. |
| 이벤트 시간 확인 | O | △ | 이벤트 시작 전 요청은 빠르게 거절해야 한다. 다만 Worker에서도 최종 방어용으로 한 번 더 확인할 수 있다. |
| 쿠폰 수량 최종 차감 |  | O | 수량 차감은 발급 성공/실패를 결정하는 핵심 처리이므로 Worker에서 일관되게 처리하는 것이 좋다. |
| DB 발급 기록 저장 |  | O | 실제 쿠폰 발급 결과를 저장하는 작업이므로 Worker가 처리한다. |
| 사용자에게 요청 접수 응답 | O |  | 사용자 요청에 대한 HTTP 응답은 API Server가 담당한다. |
| 발급 성공/실패 최종 결정 |  | O | 최종 성공/실패는 수량 차감과 DB 저장 결과를 바탕으로 결정되므로 Worker가 담당한다. |
| 요청을 Queue/Topic에 발행 | O |  | API Server는 검증된 요청을 비동기 처리 영역으로 넘겨야 한다. 단, 접수 완료 응답은 발행 성공 확인 후 주는 것이 안전하다. |

이번 1주차 기본 구조에서는 쿠폰 수량 차감, DB 발급 기록 저장, 최종 성공/실패 결정은 API Server가 직접 처리하지 않고 Worker가 담당하는 것으로 본다.

나중에 Redis를 도입하면 구조가 달라질 수 있다.

예를 들어 실제 대규모 선착순 이벤트에서는 API Server 쪽에서 Redis로 먼저 선착순 판정을 하고, 성공한 요청만 Kafka에 넣는 구조도 가능하다.

```
Client
→ API Server
→ Redis로 선착순/중복 판단
→ 성공한 요청만 Kafka 발행
→ Worker가 DB 저장
```
