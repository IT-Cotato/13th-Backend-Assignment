# 7-1 해설

# 1. 동기 / 비동기와 블로킹 / 논블로킹

## 1. 먼저 기준을 분리해서 이해해야 한다

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 판단 기준이 다르다.

동기/비동기는 **작업 완료와 결과 처리가 어떤 흐름에서 이어지는가**에 대한 개념이다.

블로킹/논블로킹은 **작업이 끝날 때까지 현재 실행 흐름이 멈추는가, 아니면 바로 제어권을 돌려받는가**에 대한 개념이다.

정리하면 다음과 같다.

```
동기 / 비동기
→ 결과 처리 흐름의 문제
→ 작업 완료와 결과 처리가 같은 호출 흐름에서 이어지는가?
→ 아니면 완료 시점에 별도 흐름으로 통지되어 처리되는가?

블로킹 / 논블로킹
→ 제어권 반환의 문제
→ 작업이 끝날 때까지 현재 스레드 또는 실행 흐름이 기다리는가?
→ 아니면 작업이 끝나지 않아도 바로 제어권을 돌려받는가?
```

즉, 동기/비동기는 **결과 처리 흐름**을 보는 기준이고, 블로킹/논블로킹은 **제어권 반환 여부**를 보는 기준이다.

따라서 하나의 시스템 안에서도 구간에 따라 서로 다른 조합이 등장할 수 있다.

예를 들어 선착순 쿠폰 발급 시스템에서 전체 구조는 비동기일 수 있지만, Worker 내부에서 DB를 조회하거나 저장하는 코드는 동기/블로킹일 수 있다.

```
Client → API Server → Kafka → Worker → DB

전체 쿠폰 발급 흐름:
비동기 처리 구조

Worker → DB 구간:
동기 / 블로킹 DB 호출
```

즉, 시스템 전체를 하나의 단어로만 설명하면 부정확해질 수 있다.

반드시 **어떤 구간을 기준으로 보는지**를 함께 설명해야 한다.

# 2. 네 가지 조합 설명

## 2.1 동기 / 블로킹

<img width="1491" height="1055" alt="image" src="https://github.com/user-attachments/assets/0dd472a9-7175-4cd0-a2d8-a1e2a645a767" />

동기/블로킹은 가장 일반적인 호출 방식이다.

작업을 요청한 뒤, 그 작업이 끝날 때까지 현재 실행 흐름이 멈춘다.

작업이 끝나면 같은 호출 흐름에서 결과를 받아 바로 다음 로직을 실행한다.

```
Caller
  |
  | 작업 요청
  v
Callee
  |
  | 작업 처리 중
  | Caller는 기다림
  v
Caller
  |
  | 결과를 받아 같은 흐름에서 처리
  v
다음 로직 실행
```

예시는 다음과 같다.

```java
Coupon coupon = couponRepository.findById(couponId);
```

이 코드는 DB 조회가 끝날 때까지 현재 스레드가 기다린다.

DB 조회 결과가 반환되면 그 결과를 같은 코드 흐름에서 바로 사용한다.

```
API Server
  |
  | DB 조회 요청
  v
DB
  |
  | 조회 중
  | API Server 스레드는 대기
  v
API Server
  |
  | 조회 결과를 받아 다음 로직 실행
```

대표적인 예시는 다음과 같다.

```
- 일반적인 함수 호출
- JDBC 기반 DB 조회
- Spring Data JPA Repository 호출
- 외부 API를 RestTemplate으로 호출하고 응답을 기다리는 경우
```

장점은 코드 흐름이 단순하고 이해하기 쉽다는 것이다.

하지만 작업 시간이 길어지면 현재 스레드가 오래 점유된다.

따라서 요청이 많아지는 상황에서는 서버 스레드가 빠르게 소진될 수 있다.

## 2.2 동기 / 논블로킹

<img width="1491" height="1055" alt="image" src="https://github.com/user-attachments/assets/1be910f4-38e0-4fdd-8ca7-5d79cb1a36f6" />

동기/논블로킹은 작업을 요청한 뒤 제어권은 바로 돌려받지만, 결과가 나왔는지 요청한 쪽이 직접 확인하는 방식이다.

작업이 끝날 때까지 현재 스레드가 완전히 멈춰 있지는 않는다.

하지만 결과 처리는 여전히 요청한 쪽의 흐름에서 직접 이어진다.

```
Caller
  |
  | 작업 요청
  v
Callee
  |
  | "아직 완료 안 됨" 바로 반환
  v
Caller
  |
  | 다른 작업 수행 또는 잠깐 대기
  |
  | 다시 완료 여부 확인
  v
Callee
  |
  | "아직 완료 안 됨" 바로 반환
  v
Caller
  |
  | 다시 확인
  v
Callee
  |
  | "완료됨" 반환
  v
Caller
  |
  | 결과를 직접 처리
```

대표적인 예시는 폴링 방식이다.

```
1. 작업을 요청한다.
2. 바로 제어권을 돌려받는다.
3. 아직 결과가 없으면 나중에 다시 확인한다.
4. 결과가 나올 때까지 주기적으로 확인한다.
5. 결과가 나오면 요청한 쪽이 직접 결과를 처리한다.
```

소켓 I/O 예시로 보면 다음과 같다.

```
read()
→ 읽을 데이터가 없음
→ 바로 반환

잠시 후 다시 read()
→ 아직 데이터 없음
→ 바로 반환

나중에 다시 read()
→ 데이터 있음
→ 데이터 읽기
```

이 방식은 현재 스레드가 작업 완료까지 완전히 멈추지 않는다는 장점이 있다.

하지만 결과가 나왔는지 계속 확인해야 하므로 폴링 비용이 발생할 수 있다.

따라서 동기/논블로킹은 일반적인 서버 비즈니스 로직의 핵심 흐름보다는, 논블로킹 I/O, 소켓 처리, 이벤트 루프 내부 구현, 또는 상태 확인용 폴링에서 더 자주 설명된다.

## 2.3 비동기 / 블로킹

<img width="1491" height="1055" alt="image" src="https://github.com/user-attachments/assets/2878e31e-4691-4b3f-8b47-d29ee07f7724" />

비동기/블로킹은 작업 실행 흐름은 분리했지만, 결과를 받는 쪽에서 다시 기다리는 구조다.

즉, 작업을 다른 스레드나 다른 시스템에 넘겼기 때문에 실행 자체는 비동기적으로 시작된다.

하지만 Caller가 그 결과를 기다리면 현재 실행 흐름이 블로킹된다.

```
Caller
  |
  | 비동기 작업 요청
  v
Async Worker
  |
  | 작업 처리 시작
  v
Caller
  |
  | Future.get()
  | 결과가 나올 때까지 기다림
  v
Async Worker
  |
  | 작업 완료
  v
Caller
  |
  | 결과를 받아 처리
```

Java 코드로 보면 다음과 같다.

```java
Future<Result> future = asyncService.process();

Result result = future.get();
```

`asyncService.process()`는 비동기 작업을 시작한다.

하지만 바로 아래에서 `future.get()`을 호출하면 결과가 나올 때까지 현재 스레드가 기다린다.

즉, 비동기 API를 사용했지만, 호출부 입장에서는 결과를 기다리는 블로킹 호출처럼 동작한다.

Kafka Producer에서도 비슷한 예시를 볼 수 있다.

```java
producer.send(record).get();
```

`send()` 자체는 메시지 전송을 비동기로 시작한다.

producer.send(record).get()을 사용하면 Kafka 브로커의 ack를 확인한 뒤 응답할 수 있다.

다만 메시지 내구성과 유실 방지 수준은 acks, retry, idempotent producer, min.insync.replicas 같은 설정에 따라 달라진다.

따라서 `producer.send(record).get()`은 비동기 전송 API를 사용했지만, 호출부 입장에서는 블로킹되는 구조라고 볼 수 있다.

이 방식이 항상 나쁜 것은 아니다.

Kafka에 메시지가 안전하게 적재되었는지 확인한 뒤 사용자에게 응답해야 하는 상황에서는 단순하고 안전한 구현 방식이 될 수 있다.

다만 요청이 폭증하는 API Server에서 매 요청마다 `.get()`으로 기다리면 API Server 스레드가 오래 점유될 수 있다.

따라서 안정성은 좋지만, 처리량 측면에서는 주의가 필요하다.

쿠폰 발급 구조로 보면 다음과 같은 구조가 비동기/블로킹에 가깝다.

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Queue에 요청 발행
  v
Worker
  |
  | 쿠폰 발급 처리
  v
API Server
  |
  | Worker 결과를 기다림
  v
Client
  |
  | 최종 성공/실패 응답 수신
```

이 구조는 Queue나 Worker를 사용하고 있으므로 겉으로는 비동기 구조처럼 보인다.

하지만 API Server가 Worker의 최종 처리 결과를 기다린다면, API Server 스레드는 계속 점유된다.

따라서 비동기 처리의 장점이 줄어든다.

정리하면 비동기/블로킹은 다음과 같다.

```
작업 실행 흐름은 분리되어 있다.
하지만 요청한 쪽이 결과를 기다린다.
그래서 현재 스레드 또는 실행 흐름이 블로킹된다.
```

## 2.4 비동기 / 논블로킹

<img width="1491" height="1055" alt="image" src="https://github.com/user-attachments/assets/499ced6a-55a4-41ec-9f48-9ed731e20666" />

비동기/논블로킹은 요청 흐름과 결과 처리 흐름이 분리되고, 작업을 요청한 쪽도 바로 제어권을 돌려받는 방식이다.

작업 결과는 나중에 콜백, 이벤트, 메시지, Future completion 등을 통해 처리된다.

```
Caller
  |
  | 작업 요청
  v
Callee
  |
  | 바로 반환
  v
Caller
  |
  | 다른 작업 수행
  |
  | 결과를 기다리지 않음
  |
  v
작업 완료 시점
  |
  | Callback / Event / Message
  v
결과 처리 로직 실행
```

Kafka Producer 예시는 다음과 같다.

```java
producer.send(record, (metadata, exception) -> {
    if (exception == null) {
        // 전송 성공 처리
    } else {
        // 전송 실패 처리
    }
});
```

이 코드는 메시지 전송을 요청한 뒤 현재 스레드가 계속 결과를 기다리지 않도록 만들 수 있다.

전송 결과는 나중에 콜백에서 처리된다.

다만 여기서 주의할 점이 있다.

`producer.send(record, callback)`을 호출했다고 해서 Kafka에 메시지가 안전하게 저장된 것은 아니다.

`send()`가 반환되었다는 것은 전송 요청을 Kafka Producer에게 맡겼다는 의미에 가깝다.

실제 전송 성공 여부는 나중에 callback에서 확인된다.

따라서 요청 접수 완료 응답이 **“발급 요청이 유실되지 않고 처리 대기열에 들어갔다”** 는 의미라면, Kafka ack 성공을 확인한 뒤 응답하는 것이 안전하다.

```
위험할 수 있는 방식:

API Server
→ producer.send(record, callback)
→ send()가 바로 반환됨
→ Client에게 접수 완료 응답
→ 이후 Kafka 전송 실패 가능
```

위 방식은 사용자가 접수 완료 응답을 받았는데 실제 요청 메시지는 Kafka에 없을 수 있다.

따라서 안전한 구조에서는 다음 기준을 지키는 것이 좋다.

```
Client에게 접수 완료 응답을 주는 시점
= Kafka에 메시지가 안전하게 적재되었다는 ack를 확인한 뒤
```

구현 방식은 크게 두 가지로 볼 수 있다.

첫 번째는 `.get()`으로 Kafka ack를 기다리는 방식이다.

```java
producer.send(record).get();
```

이 방식은 단순하고 안전하다.

하지만 API Server 스레드가 Kafka ack를 기다리므로 블로킹이 발생한다.

두 번째는 callback 또는 Future completion에서 Kafka ack 성공을 확인한 뒤 응답을 완료하는 방식이다.

```
API Server
  |
  | Kafka 발행 요청
  v
Kafka Producer
  |
  | 바로 반환
  v
API Server
  |
  | 현재 스레드는 다른 작업 가능

Kafka ack 성공
  |
  | callback 실행
  v
API Server
  |
  | Client 응답 완료
```

이 방식은 구현이 더 복잡하지만 API Server 스레드를 오래 붙잡지 않을 수 있다.

즉, Kafka Producer를 비동기/논블로킹에 가깝게 사용하려면 단순히 `send()`가 반환된 시점에 응답하는 것이 아니라, Kafka ack 성공을 비동기적으로 확인한 뒤 응답을 완료해야 한다.

WebFlux, Netty, 비동기 HTTP Client, 비동기 DB Driver 등도 비동기/논블로킹에 가까운 방식으로 동작할 수 있다.

```
요청
→ 바로 제어권 반환
→ 실제 I/O는 이벤트 루프나 별도 처리 흐름에서 진행
→ 완료되면 콜백 또는 이벤트로 결과 처리
```

이 방식의 장점은 적은 수의 스레드로 많은 요청을 처리할 수 있다는 것이다.

스레드가 작업 완료를 기다리며 멈춰 있지 않기 때문이다.

하지만 코드 흐름과 예외 처리가 복잡해질 수 있고, 디버깅 난이도가 올라갈 수 있다.

# 3. 선착순 쿠폰 발급 구조에서 실제로 등장하는 조합

이번 선착순 쿠폰 발급 구조에서는 4가지 조합이 모두 반드시 등장한다고 볼 필요는 없다.

중요한 것은 전체 시스템을 하나로 단정하지 않고, 구간별로 나누어 분석하는 것이다.

예시 구조는 다음과 같다.

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | 기본 검증
  | Kafka에 쿠폰 발급 요청 메시지 발행
  v
Client
  |
  | "요청 접수 완료" 응답 수신

Kafka
  |
  | 쿠폰 발급 요청 메시지 저장
  v
Worker
  |
  | 메시지 소비
  | DB에 쿠폰 발급 기록 저장
  | 결과 이벤트 발행
  v
Client
  |
  | 결과 조회 API 또는 알림으로 최종 발급 결과 확인
```

이 구조의 핵심은 API Server가 실제 쿠폰 발급까지 모두 처리하지 않는다는 것이다.

API Server는 요청을 접수하고, 실제 발급 처리는 Worker가 뒤에서 수행한다.

따라서 전체 쿠폰 발급 흐름은 비동기 처리 구조라고 볼 수 있다.

다만 모든 구간이 논블로킹이어야 하는 것은 아니다.

Worker 내부의 DB 저장은 동기/블로킹으로 동작할 수 있고, 결과 조회 API도 동기/블로킹으로 동작할 수 있다.

---

## 3.1 Client → API Server 구간

사용자가 쿠폰 발급 버튼을 누르면 Client는 API Server에 요청을 보낸다.

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | 요청 접수
  v
Client
  |
  | 접수 성공 응답
```

일반적인 HTTP 요청/응답 관점에서 Client는 API Server의 응답을 받은 뒤 다음 흐름으로 넘어간다.

따라서 사용자 요청 관점에서는 동기적 흐름에 가깝게 볼 수 있다.

다만 여기서 중요한 점은 Client가 기다리는 결과가 **최종 쿠폰 발급 결과**가 아니라는 것이다.

Client가 받는 응답은 다음과 같은 의미가 아니다.

```
"쿠폰 발급이 완료되었습니다."
```

Client가 받는 응답은 다음과 같은 의미다.

```
"쿠폰 발급 요청이 접수되었습니다."
```

따라서 Client → API Server의 짧은 요청/응답 구간은 동기적일 수 있지만, 전체 쿠폰 발급 처리 흐름은 비동기 구조라고 볼 수 있다.

추가로 브라우저, 모바일 앱, 비동기 HTTP Client 내부 구현에 따라 실제 UI 스레드가 반드시 블로킹되는 것은 아닐 수 있다.

하지만 이번 과제에서는 개념 설명을 위해 일반적인 HTTP 요청/응답 모델을 기준으로 이해하면 된다.

---

## 3.2 API Server → Kafka 구간

API Server는 쿠폰 발급 요청을 Kafka Topic에 발행한다.

```
API Server
  |
  | coupon.issue.requested 메시지 발행
  v
Kafka
```

이때 Kafka Producer를 어떻게 사용하느냐에 따라 조합이 달라진다.

먼저 다음처럼 사용하면 비동기 전송을 시작할 수 있다.

```java
producer.send(record, callback);
```

하지만 `send()`가 바로 반환되었다고 해서 Kafka에 메시지가 안전하게 저장된 것은 아니다.

요청 접수 완료 응답이 **“발급 요청이 유실되지 않고 처리 대기열에 들어갔다”** 는 의미라면, Kafka ack 성공을 확인해야 한다.

따라서 다음처럼 `send()`만 호출하고 바로 응답하면 위험할 수 있다.

```
API Server
  |
  | producer.send(record, callback)
  v
Kafka Producer
  |
  | 바로 반환
  v
API Server
  |
  | Client에게 접수 완료 응답

이후 Kafka 전송 실패 가능
```

이 경우 사용자는 접수 완료 응답을 받았지만, 실제 요청 메시지는 Kafka에 저장되지 않았을 수 있다.

안전성을 우선하면 다음처럼 사용할 수 있다.

```java
producer.send(record).get();
```

이 경우 흐름은 다음과 같다.

```
API Server
  |
  | Kafka 메시지 발행 요청
  v
Kafka Producer
  |
  | Kafka ack가 올 때까지 대기
  v
API Server
  |
  | ack 성공 확인 후 Client에게 응답
```

이 방식은 Kafka에 메시지가 안전하게 적재되었는지 확인한 뒤 응답할 수 있다.

하지만 `.get()`을 호출하는 동안 API Server 스레드가 기다리므로 호출부 입장에서는 블로킹 방식에 가깝다.

더 확장성 있는 방식으로는 callback 또는 Future completion에서 Kafka ack 성공을 확인한 뒤 Client 응답을 완료하는 구조를 사용할 수 있다.

```
API Server
  |
  | Kafka 메시지 발행 요청
  v
Kafka Producer
  |
  | 바로 반환
  v
API Server
  |
  | 현재 스레드는 다른 작업 가능

Kafka ack 성공
  |
  | callback 또는 completion 실행
  v
API Server
  |
  | Client에게 접수 완료 응답
```

이 방식은 API Server 스레드를 오래 붙잡지 않을 수 있으므로 비동기/논블로킹에 더 가깝다.

정리하면 API Server → Kafka 구간에서 중요한 기준은 다음과 같다.

```
빠르게 응답하는 것도 중요하지만,
접수 완료라고 응답한 요청이 유실되지 않는 것이 더 중요하다.

따라서 요청 접수 완료 응답이
“발급 요청이 처리 대기열에 안전하게 들어갔다”는 의미라면,
Kafka ack 성공을 확인한 뒤 응답하는 것이 안전하다.
```

---

## 3.3 API Server가 Worker 결과를 기다리는 구조

다음 구조는 피해야 한다.

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Kafka에 요청 발행
  v
Worker
  |
  | 쿠폰 발급 처리
  v
API Server
  |
  | Worker 결과를 기다림
  v
Client
  |
  | 최종 성공/실패 응답
```

이 구조는 Queue와 Worker를 사용하고 있기 때문에 겉으로는 비동기처럼 보인다.

하지만 API Server가 Worker의 최종 결과를 기다리면 API Server 스레드는 오래 점유된다.

그러면 사용자는 최종 발급 결과가 나올 때까지 기다려야 하고, API Server는 많은 요청을 빠르게 받아내기 어렵다.

이 구조는 이번 선착순 쿠폰 발급 시스템에서는 피해야 하는 비동기/블로킹 구조에 가깝다.

Queue와 Worker를 사용하더라도 API Server가 Worker의 최종 결과를 기다리면 API Server 스레드가 오래 점유되고, 요청 폭주를 완충하려는 비동기 처리의 장점이 줄어든다.

```
작업 처리는 Worker에게 넘김
→ 실행 흐름은 분리됨
→ 하지만 API Server가 결과를 기다림
→ API Server는 블로킹됨
```

선착순 쿠폰 이벤트에서는 요청이 짧은 시간에 몰린다.

이때 API Server가 Worker 결과를 기다리면 API Server의 처리량이 크게 떨어진다.

따라서 이번 구조에서는 API Server가 Worker의 최종 결과를 기다리지 않아야 한다.

---

## 3.4 Worker → DB 구간

Worker는 Kafka에서 메시지를 읽고 실제 쿠폰 발급 처리를 수행한다.

```
Worker
  |
  | 쿠폰 발급 기록 저장
  v
DB
  |
  | 저장 처리 중
  v
Worker
  |
  | 저장 결과를 받아 다음 로직 실행
```

일반적인 Spring Data JPA나 JDBC 기반 DB 접근을 사용한다면 이 구간은 동기/블로킹이다.

예시는 다음과 같다.

```java
couponIssueRepository.save(couponIssue);
```

DB 저장이 끝날 때까지 Worker 스레드는 기다린다.

저장이 성공하면 다음 로직으로 넘어가고, 실패하면 예외를 처리한다.

즉, 전체 쿠폰 발급 구조는 비동기일 수 있지만, Worker 내부의 DB 호출은 동기/블로킹일 수 있다.

이것은 잘못된 것이 아니다.

오히려 많은 실무 시스템은 전체 요청 흐름은 비동기로 분리하고, 내부 Worker에서는 동기/블로킹 DB 처리를 사용한다.

중요한 것은 API Server가 긴 DB 작업을 직접 처리하지 않고, Worker에게 분리한다는 점이다.

---

## 3.5 결과 조회 API 구간

쿠폰 발급 결과를 사용자가 나중에 조회하는 API가 있다고 가정해보자.

```
Client
  |
  | 발급 결과 조회 요청
  v
API Server
  |
  | DB에서 발급 상태 조회
  v
DB
  |
  | 조회 결과 반환
  v
API Server
  |
  | Client에게 결과 응답
```

이 구간은 일반적인 조회 API이므로 동기/블로킹에 가깝다.

사용자는 조회 요청을 보내고, API Server는 DB에서 현재 상태를 조회한 뒤 응답한다.

이때 응답은 다음 중 하나일 수 있다.

```
- 처리 중
- 발급 성공
- 수량 소진으로 실패
- 이미 발급됨
```

즉, 결과 조회 API 자체는 동기/블로킹 방식으로 동작할 수 있다.

하지만 최종 발급 처리가 처음 요청 흐름에서 분리되어 있기 때문에 전체 쿠폰 발급 구조는 비동기적이다.

---

## 3.6 알림 발송 구간

쿠폰 발급 결과를 알림으로 전달하는 경우도 있다.

```
Worker
  |
  | 발급 결과 이벤트 발행
  v
Notification Service
  |
  | 앱 푸시 / 이메일 / 카카오 알림 발송
  v
Client
```

이 구조는 쿠폰 발급 처리와 알림 발송이 분리되어 있으므로 비동기 구조에 가깝다.

Worker가 쿠폰 발급을 완료한 뒤 결과 이벤트를 발행하고, Notification Service가 별도로 알림을 처리한다.

단, Notification Service 내부에서 외부 푸시 서버를 호출할 때는 다시 동기/블로킹 HTTP 호출이 등장할 수도 있고, 비동기/논블로킹 HTTP Client를 사용할 수도 있다.

따라서 알림 발송도 구간에 따라 조합이 달라진다.

---

# 4. 이번 쿠폰 발급 구조에서 등장하는 조합 정리

이번 선착순 쿠폰 발급 구조에서 실제로 등장할 수 있는 조합은 다음과 같다.

---

## 4.1 동기 / 블로킹

등장한다.

대표 구간은 다음과 같다.

```
- Worker가 DB에 쿠폰 발급 기록을 저장하는 구간
- 결과 조회 API에서 API Server가 DB를 조회하는 구간
```

예시는 다음과 같다.

```java
couponIssueRepository.save(couponIssue);
couponIssueRepository.findByUserIdAndCouponId(userId, couponId);
```

일반적인 JPA/JDBC 기반 DB 호출은 작업이 끝날 때까지 현재 스레드가 기다리므로 동기/블로킹이다.

---

## 4.2 동기 / 논블로킹

이번 쿠폰 발급 구조의 핵심 흐름에서는 잘 등장하지 않는다.

동기/논블로킹은 결과를 요청한 쪽이 직접 계속 확인하는 폴링 방식에 가깝다.

예를 들어 내부적으로 다음과 같은 방식이 있다면 동기/논블로킹으로 볼 수 있다.

```
API Server
  |
  | 작업 상태 확인
  v
Worker 또는 상태 저장소
  |
  | 아직 완료 안 됨
  v
API Server
  |
  | 잠시 후 다시 확인
```

하지만 일반적인 쿠폰 발급 구조에서는 API Server가 이런 식으로 계속 Worker 상태를 확인하지 않는 것이 좋다.

그렇게 하면 API Server가 불필요하게 바빠지고, 비동기 처리의 장점이 줄어든다.

다만 사용자가 결과 조회 API를 여러 번 호출하는 방식은 넓은 의미에서 폴링처럼 보일 수 있다.

```
Client
  |
  | 결과 조회
  v
API Server
  |
  | 처리 중 응답

잠시 후 다시 조회
```

하지만 이것은 시스템 내부의 동기/논블로킹 I/O라기보다는 사용자 관점의 상태 조회 방식에 가깝다.

따라서 이번 과제에서는 핵심 조합으로 보지 않아도 된다.

---

## 4.3 비동기 / 블로킹

설계에 따라 등장할 수 있지만, 좋은 구조에서는 피해야 한다.

대표적인 나쁜 예시는 다음과 같다.

```
API Server
  |
  | Kafka에 요청 발행
  v
Worker
  |
  | 쿠폰 발급 처리
  v
API Server
  |
  | Worker 결과를 기다림
```

또는 Kafka Producer를 다음처럼 사용하는 경우다.

```java
producer.send(record).get();
```

이 경우 `send()`는 메시지 전송을 비동기로 시작하지만, `.get()`으로 Kafka ack를 기다리기 때문에 호출한 스레드가 블로킹된다.

다만 `producer.send(record).get()`은 Kafka에 메시지가 안전하게 적재되었는지 확인하기 위한 단순한 방법이 될 수 있다.

따라서 이 방식은 무조건 잘못된 것은 아니다.

하지만 요청이 폭증하는 API Server에서 매 요청마다 `.get()`으로 기다리면 스레드 점유 시간이 길어질 수 있다.

그래서 처리량이 중요한 구간에서는 callback 또는 Future completion을 활용해 Kafka ack 성공 후 응답을 완료하는 방식도 고려할 수 있다.

이번 선착순 쿠폰 발급 시스템에서는 API Server가 많은 요청을 빠르게 받아야 한다.

따라서 API Server가 Worker의 최종 결과를 기다리는 비동기/블로킹 구조는 적합하지 않다.

---

## 4.4 비동기 / 논블로킹

이번 선착순 쿠폰 발급 구조에서 지향할 수 있는 방향이다.

다만 전체 시스템 전체를 무조건 비동기/논블로킹이라고 단정하면 안 된다.

더 정확히는 다음과 같다.

```
전체 쿠폰 발급 흐름:
비동기 처리 구조

API Server → Kafka 구간:
구현 방식에 따라 비동기/논블로킹에 가깝게 설계 가능

Worker → DB 구간:
일반적인 JPA/JDBC를 사용하면 동기/블로킹
```

API Server는 쿠폰 발급 요청을 Kafka에 전달하고, 사용자에게는 최종 결과가 아니라 요청 접수 결과를 반환한다.

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Kafka에 요청 메시지 발행
  | Kafka ack 성공 확인
  v
Client
  |
  | 요청 접수 응답

Kafka
  |
  | 메시지 전달
  v
Worker
  |
  | 실제 쿠폰 발급 처리
```

이 구조에서는 요청 접수 흐름과 실제 쿠폰 발급 처리 흐름이 분리된다.

사용자는 처음 요청에서 최종 발급 성공/실패를 바로 받지 않는다.

대신 다음 방식으로 결과를 확인한다.

```
- 결과 조회 API
- 마이페이지 / 쿠폰함 조회
- 앱 푸시
- WebSocket / SSE
- 알림 메시지
```

따라서 이번 선착순 쿠폰 발급 구조의 핵심은 **비동기 처리 구조**라고 볼 수 있다.

그리고 API Server → Kafka 구간은 구현 방식에 따라 비동기/논블로킹에 가깝게 설계할 수 있다.

다만 모든 내부 구간이 논블로킹이어야 하는 것은 아니다.

Worker 내부 DB 저장은 동기/블로킹으로 처리될 수 있고, 이것은 전체 발급 흐름을 비동기로 분리하는 것과 모순되지 않는다.

---

# 5. 최종 정리

동기/비동기와 블로킹/논블로킹은 서로 다른 기준의 개념이다.

```
동기 / 비동기
→ 작업 완료와 결과 처리가 어떤 흐름에서 이어지는가?

블로킹 / 논블로킹
→ 작업이 끝날 때까지 현재 실행 흐름이 멈추는가?
```

선착순 쿠폰 발급 시스템에서는 전체 시스템을 하나의 단어로 단정하면 안 된다.

구간별로 나누어 봐야 한다.

```
Client → API Server
→ 일반적인 요청/응답 구간
→ 사용자 요청 관점에서는 동기적 흐름에 가깝다.
→ 다만 Client가 받는 것은 최종 발급 결과가 아니라 요청 접수 결과다.

API Server → Kafka
→ 구현 방식에 따라 달라진다.
→ send().get()은 비동기 API를 사용하지만 호출부는 블로킹된다.
→ callback 또는 Future completion에서 Kafka ack 성공을 확인한 뒤 응답을 완료하는 방식은 비동기/논블로킹에 더 가깝다.
		→ 다만 이를 제대로 활용하려면 HTTP 응답도 DeferredResult, CompletableFuture,
		  WebFlux 같은 방식으로 비동기적으로 완료할 수 있어야 한다.
		→ 단순히 callback을 사용했다고 해서 전체 요청 처리가 항상 논블로킹이 되는 것은 아니다.

API Server → Worker 결과 대기
→ 비동기/블로킹의 나쁜 예시다.
→ Queue를 사용해도 API Server가 최종 결과를 기다리면 비동기 장점이 줄어든다.

Worker → DB
→ 일반적인 JPA/JDBC 사용 시 동기/블로킹이다.
→ 전체 구조가 비동기라고 해서 내부 DB 호출까지 모두 논블로킹일 필요는 없다.

결과 조회 API
→ 일반적인 조회 API이므로 동기/블로킹에 가깝다.
→ 사용자는 처리 중, 발급 성공, 수량 소진 실패, 이미 발급됨 같은 상태를 조회한다.

알림 발송
→ 쿠폰 발급 처리와 알림 처리가 분리되므로 비동기 구조에 가깝다.
→ 다만 알림 서비스 내부 구현은 동기/블로킹일 수도 있고 비동기/논블로킹일 수도 있다.
```

이번 과제에서 가장 중요한 결론은 다음과 같다.

```
선착순 쿠폰 발급 구조의 핵심은
API Server가 최종 발급 결과를 기다리지 않고,
요청 접수 흐름과 실제 발급 처리 흐름을 분리하는 것이다.

즉, 전체 구조의 핵심은 비동기 처리 구조다.

다만 모든 구간이 논블로킹이어야 하는 것은 아니다.

Worker 내부 DB 저장은 동기/블로킹으로 처리될 수 있고,
API Server → Kafka 구간은 구현 방식에 따라 블로킹 또는 논블로킹으로 설계될 수 있다.
```

결국 핵심은 다음 한 문장으로 정리할 수 있다.

```
선착순 쿠폰 발급 시스템에서는
전체 흐름은 비동기로 분리하되,
각 구간의 구현 방식은 동기/블로킹일 수도 있고 비동기/논블로킹일 수도 있다.
```
