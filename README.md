# 주제

대규모 트래픽을 고려한 선착순 쿠폰 발급 시스템 아키텍처 설계

---

# 1. 목표

앞으로 1주차부터 8주차까지 다룰 **선착순 쿠폰 발급 시스템의 전체 흐름**을 먼저 이해한다.

이번 과제는 단순히 Kafka나 Redis를 써보는 것이 목표가 아니다.

실제 서비스에서 트래픽이 한 번에 몰리는 상황이 생겼을 때, 백엔드 시스템을 어떤 구조로 설계해야 하는지 고민해보는 것이 목표다.

이 페이지에서는 다음 내용을 먼저 정리한다.

- 선착순 쿠폰 발급 시스템이 어떤 문제를 가지고 있는지
- 전체 아키텍처를 대략적으로 어떻게 잡을 수 있는지
- 어떤 문제가 발생할 수 있는지
- 각 문제를 어떤 방향으로 해결할 수 있는지
- 각 문제가 몇 주차 과제와 연결되는지
- 필수 과제와 심화 과제는 어떻게 나뉘는지
- 1주차부터 8주차까지 어떤 순서로 진행되는지

이 자료를 바탕으로 1주차부터 각 부분을 하나씩 구체적으로 설계하게 된다.

# 2. 문제 정의

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

예시는 다음과 같다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
발급 조건: 사용자 1명당 1개만 발급 가능
이벤트 시작 시간: 정해진 날짜의 오후 12시
발급 방식: 선착순
```

이벤트 시작 시간이 되면 많은 사용자가 동시에 쿠폰 발급 버튼을 누른다.

겉으로 보면 단순해 보인다.

<img width="779" height="211" alt="image" src="https://github.com/user-attachments/assets/1595ba9d-f379-4fe8-ae3f-961f012d7012" />


하지만 실제 서비스에서는 이렇게 단순하게 처리하기 어렵다.

이벤트 시작 순간에 요청이 한 번에 몰릴 수 있고, DB에 부하가 생길 수 있으며, 같은 사용자가 여러 번 요청할 수도 있다.

또한 서버 장애나 Kafka 메시지 중복 처리 같은 문제도 고려해야 한다.

이번 과제에서는 이런 문제들을 주차별로 하나씩 나누어 해결하면서, 최종적으로 선착순 쿠폰 발급 시스템의 전체 아키텍처를 설계한다.

이번 과제에서 사용할 기본 가정은 다음과 같다.

```
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
최종 저장소: 쿠폰 발급 기록은 최종적으로 DB에 저장되어야 함
```

즉, 사용자는 요청을 보낸 직후에 반드시 “쿠폰 발급 성공”을 바로 받을 필요는 없다.

대신 서버는 사용자의 요청이 접수되었는지 빠르게 알려주고, 실제 발급 결과는 나중에 조회할 수 있게 한다.

예를 들면 이런 응답을 줄 수 있다.

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다."
}
```

# 3. 기본 설계 방향


이번 과제에서는 아래 구조를 기본 방향으로 잡는다.

1. 쿠폰 발급 요청은 바로 DB에 저장하지 않고 비동기로 처리한다.
2. API Server는 Redis를 이용해서 선착순 여부와 중복 발급 여부를 먼저 확인한다.
3. Redis 판정에 성공한 요청만 Kafka에 발행한다.
4. Kafka Consumer가 실제 쿠폰 발급 DB 저장을 처리한다.
5. DB는 최종 쿠폰 발급 기록을 보장하는 역할을 한다.
6. 같은 요청이나 같은 메시지가 여러 번 처리되어도 중복 발급되지 않도록 설계한다.
7. DB 저장과 이벤트 발행 사이의 불일치는 Outbox Pattern으로 해결한다.
8. 알림, 마이페이지, 통계 처리는 이벤트 기반으로 분리한다.
9. 실패한 메시지는 Retry Topic이나 DLQ로 분리해서 관리한다.

전체 흐름을 간단히 보면 다음과 같다.

```
Client
→ API Server
→ Redis 선착순 / 중복 판정
→ 성공한 요청만 Kafka 발행
→ Consumer가 DB 저장
→ Outbox Table에 결과 이벤트 저장
→ Outbox Publisher가 Kafka에 결과 이벤트 발행
→ Notification / MyPage / Analytics Service가 이벤트 소비
```

# 5. 발생할 수 있는 문제와 해결 방향

## 문제 1. API 서버와 DB에 요청이 한 번에 몰리는 문제

이벤트 시작 순간 많은 사용자가 동시에 쿠폰 발급 버튼을 누를 수 있다.

만약 API 서버가 모든 요청을 바로 DB에 저장하려고 하면 DB에 부하가 몰리고, 응답 시간도 길어질 수 있다.

```
Client
→ API Server
→ DB 조회
→ DB 저장
```

요청 수가 적을 때는 괜찮을 수 있지만, 이벤트 시작 직후처럼 요청이 한 번에 몰리는 상황에서는 위험하다.

### 해결 방향

쿠폰 발급 요청을 바로 처리하지 않고, 요청 접수와 실제 발급 처리를 분리한다.

사용자에게는 먼저 “요청이 접수되었습니다” 또는 “처리 중입니다” 같은 응답을 빠르게 반환한다.

실제 발급 결과는 나중에 조회 API나 마이페이지에서 확인하게 한다.

## 문제 2. 비동기 처리를 어떻게 구성할지 정해야 하는 문제

요청을 비동기로 처리하기로 했다면, 이제 어떤 방식으로 요청을 전달하고 처리할지 정해야 한다.

이번 과제에서는 Kafka를 사용해 쿠폰 발급 요청을 비동기로 처리한다.

Kafka를 사용할 때는 다음과 같은 내용을 설계해야 한다.

- Topic을 어떻게 나눌 것인가?
- Partition Key를 무엇으로 정할 것인가?
- Consumer Group을 어떻게 구성할 것인가?
- Consumer Lag이 생기면 사용자 경험은 어떻게 달라지는가?

### 해결 방향

API Server는 쿠폰 발급 요청 메시지를 Kafka Topic에 발행한다.

Consumer는 Kafka에서 메시지를 읽고 실제 쿠폰 발급 처리를 수행한다.

이때 Topic, Partition, Partition Key, Consumer Group을 잘 설계해야 대량 요청을 안정적으로 처리할 수 있다.

## 문제 3. 쿠폰 수량보다 많이 발급될 수 있는 문제

쿠폰 수량은 1,000개로 제한되어 있다.

그런데 동시에 많은 요청이 들어오면 여러 사용자가 거의 같은 시점에 남은 수량을 확인하고 발급에 성공할 수 있다.

예를 들어 남은 쿠폰이 1개뿐인데 여러 요청이 동시에 들어오면 다음과 같은 상황이 생길 수 있다.

```
현재 남은 쿠폰 수량: 1개

사용자 A가 남은 수량 1개 확인
사용자 B도 남은 수량 1개 확인
사용자 C도 남은 수량 1개 확인

A, B, C 모두 발급 성공 처리
→ 실제 쿠폰 수량보다 많이 발급됨
```

또한 같은 사용자가 버튼을 여러 번 눌러 중복 발급을 시도할 수도 있다.

### 해결 방향

Redis를 사용해서 선착순 여부와 중복 발급 여부를 빠르게 판단한다.

Redis Set을 사용하면 이미 발급받은 사용자 목록을 관리할 수 있고, Lua Script를 사용하면 수량 확인과 사용자 추가를 하나의 원자적인 작업처럼 처리할 수 있다.

기본 흐름은 다음과 같다.

```
Client
→ API Server
→ Redis에서 선착순 / 중복 판정
→ 성공한 요청만 Kafka 발행
→ Consumer가 DB 저장
```

## 문제 4. Redis 성공만으로 최종 발급을 보장할 수 없는 문제

Redis에서 선착순 판정에 성공했다고 해서 쿠폰 발급이 완전히 끝난 것은 아니다.

최종 쿠폰 발급 기록은 DB에 저장되어야 한다.

예를 들어 Redis에서는 발급 성공으로 처리되었지만, 이후 DB 저장이 실패할 수 있다.

```
Redis에는 사용자 A가 발급 성공으로 기록됨
→ Kafka 메시지 발행
→ Consumer가 DB 저장 시도
→ DB 저장 실패
```

이 경우 Redis에는 발급된 것처럼 남아 있지만 DB에는 발급 기록이 없다.

또한 Redis나 Kafka 쪽에서 실수가 발생하더라도, 최종적으로는 DB에서 중복 발급을 막을 수 있어야 한다.

### 해결 방향

DB에 쿠폰 발급 관련 테이블을 설계하고, `eventId + userId`에 Unique Key를 건다.

이렇게 하면 같은 사용자가 같은 이벤트 쿠폰을 두 번 받을 수 없다.

즉, Redis는 빠른 선착순 판정을 담당하고, DB는 최종 발급 기록을 보장하는 마지막 방어선 역할을 한다.

## 문제 5. 같은 요청이나 같은 메시지가 여러 번 처리될 수 있는 문제

사용자는 쿠폰 발급 버튼을 여러 번 누를 수 있다.

또는 네트워크 문제로 같은 요청이 다시 전송될 수도 있다.

Kafka Consumer도 장애나 재시도 상황에서 같은 메시지를 다시 처리할 수 있다.

```
Consumer가 메시지를 읽음
→ DB 저장 성공
→ offset commit 전에 Consumer 장애
→ Consumer 재시작
→ 같은 메시지를 다시 읽음
```

이런 상황에서도 쿠폰이 중복 발급되면 안 된다.

### 해결 방향

requestId를 사용해서 같은 요청을 구분한다.

같은 requestId가 다시 들어오면 새로운 요청으로 처리하지 않고, 기존 요청 상태를 확인한 뒤 같은 결과를 반환한다.

요청 상태는 예를 들어 다음과 같이 관리할 수 있다.

```
PENDING
PROCESSING
ISSUED
FAILED
```

여기서 requestId는 같은 요청의 재처리를 안전하게 만들기 위한 장치다.

반면 DB Unique Key는 같은 사용자가 같은 쿠폰을 두 번 받지 못하게 막는 최종 방어선이다.

## 문제 6. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패하는 문제

쿠폰 발급 기록을 DB에 저장한 뒤에는 다른 서비스에 발급 결과를 알려야 한다.

예를 들어 쿠폰 발급이 완료되면 `CouponIssued` 이벤트를 Kafka에 발행할 수 있다.

그런데 DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있다.

```
coupon_issue 테이블 저장 성공
→ CouponIssued 이벤트 발행 시도
→ Kafka 장애로 이벤트 발행 실패
```

이 경우 DB에는 쿠폰 발급 기록이 있지만, 알림 서비스나 마이페이지 서비스는 사용자가 쿠폰을 받았다는 사실을 모를 수 있다.

### 해결 방향

Outbox Pattern을 사용한다.

쿠폰 발급 기록을 DB에 저장할 때, 발행해야 할 이벤트도 Outbox Table에 함께 저장한다.

이 두 작업은 하나의 DB 트랜잭션으로 묶는다.

이후 별도의 Outbox Publisher가 Outbox Table을 읽어서 Kafka에 이벤트를 발행한다.

Kafka 발행에 실패하면 Outbox 상태를 `PENDING`으로 남겨두고 나중에 다시 발행할 수 있다.

## 문제 7. 알림, 마이페이지, 통계 서비스가 쿠폰 발급 서비스와 강하게 연결되는 문제

쿠폰 발급이 완료되면 여러 서비스가 발급 결과를 사용해야 한다.

예를 들어 다음과 같은 서비스가 있을 수 있다.

```
Notification Service: 사용자에게 쿠폰 발급 알림 전송
MyPage Service: 사용자의 보유 쿠폰 목록 조회
Analytics Service: 운영자용 쿠폰 발급 통계 생성
```

만약 쿠폰 발급 서비스가 이 서비스들을 직접 호출하면 서비스 간 결합도가 높아진다.

또한 알림 서비스에 장애가 생겼을 때 쿠폰 발급 처리까지 영향을 받을 수 있다.

```
Coupon Service
→ Notification Service
→ MyPage Service
→ Analytics Service
```

이 구조에서는 하나의 서비스 장애가 다른 서비스로 전파될 수 있다.

### 해결 방향

쿠폰 발급 결과를 이벤트로 발행한다.

알림 서비스, 마이페이지 서비스, 통계 서비스는 각각 이 이벤트를 구독해서 필요한 작업을 처리한다.

즉, 쿠폰 발급 서비스는 “쿠폰이 발급되었다”는 이벤트만 발행하고, 이후 작업은 각 서비스가 독립적으로 처리한다.

이렇게 하면 서비스 간 결합도를 낮출 수 있다.

## 문제 8. 실패한 메시지를 어떻게 처리할지 정해야 하는 문제

Consumer가 쿠폰 발급 처리 중 실패할 수 있다.

예를 들어 DB가 일시적으로 장애가 나거나, 메시지 형식이 잘못되었거나, 이미 처리된 요청일 수 있다.

실패한 메시지를 바로 버리면 요청이 유실될 수 있다.

그렇다고 계속 무한히 재시도하면 Consumer가 같은 메시지에서 계속 멈출 수 있다.

```
Consumer가 메시지 처리
→ DB 오류 발생
→ 계속 재시도
→ Consumer 처리 지연
→ Consumer Lag 증가
```

또한 Redis에서는 선착순 성공으로 처리되었는데 DB 저장이 실패한 경우, Redis와 DB 사이의 불일치를 어떻게 복구할지도 정해야 한다.

### 해결 방향

실패 유형을 나누어 처리한다.

| 실패 유형 | 예시 | 처리 방향 |
| --- | --- | --- |
| 일시적 실패 | DB 일시 장애, 네트워크 오류 | Retry Topic으로 재시도 |
| 영구 실패 | 잘못된 메시지 형식, 존재하지 않는 이벤트 ID | DLQ로 이동 |
| 비즈니스 실패 | 이미 발급받은 사용자, 쿠폰 품절 | 실패 상태 저장 후 정상 종료 |
| 외부 서비스 실패 | 알림 서비스 장애 | 쿠폰 발급과 분리하여 별도 재시도 |

Redis 성공 후 DB 저장 실패처럼 정합성이 깨질 수 있는 상황은 보상 트랜잭션을 통해 복구한다.

# 6. 설계 시 반드시 지켜야 할 규칙

이번 시스템을 설계할 때 아래 조건은 반드시 만족해야 한다.

1. 쿠폰은 정해진 수량보다 많이 발급되면 안 된다.
2. 한 사용자는 같은 이벤트에서 쿠폰을 한 번만 받을 수 있어야 한다.
3. 같은 requestId가 여러 번 들어와도 중복 처리되면 안 된다.
4. Kafka 메시지가 중복 소비되어도 쿠폰이 중복 발급되면 안 된다.
5. Redis에서 성공한 요청은 최종적으로 DB 저장까지 이어져야 한다.
6. DB 저장이 성공했다면 발급 결과 이벤트도 최종적으로 발행되어야 한다.
7. 알림 서비스 장애가 쿠폰 발급 자체의 실패로 이어지면 안 된다.
8. 실패한 메시지를 무한히 재시도하면 안 된다.

이 규칙들은 1주차부터 8주차까지 모든 설계에서 계속 기준이 된다.

# 7. 공통 용어 정리

이번 과제에서 자주 나오는 용어는 다음과 같다.

| 용어 | 의미 |
| --- | --- |
| Kafka | 요청이나 이벤트를 비동기로 전달하는 메시지 시스템 |
| Topic | Kafka에서 메시지가 저장되는 논리적 공간 |
| Partition | Topic을 나누어 병렬 처리할 수 있게 하는 단위 |
| Partition Key | 메시지를 어떤 Partition에 보낼지 결정하는 기준 |
| Consumer Group | 같은 Topic을 함께 나누어 처리하는 Consumer 묶음 |
| Consumer Lag | Consumer가 아직 처리하지 못하고 밀린 메시지 수 |
| Redis | 빠른 조회와 원자적 처리를 위해 사용하는 인메모리 저장소 |
| Redis Set | 중복 없는 값 목록을 저장하는 자료구조 |
| Lua Script | Redis에서 여러 명령을 원자적으로 처리하기 위한 스크립트 |
| requestId | 하나의 요청을 식별하기 위한 ID |
| 멱등성 | 같은 요청이 여러 번 처리되어도 결과가 한 번만 반영되는 성질 |
| Unique Key | DB에서 중복 데이터를 막기 위한 제약 조건 |
| Outbox Pattern | DB 저장과 이벤트 발행 사이의 정합성을 맞추기 위한 패턴 |
| Retry Topic | 일시적으로 실패한 메시지를 다시 처리하기 위한 Topic |
| DLQ | 정상 처리할 수 없는 메시지를 따로 보관하는 큐 |
| EDA | 이벤트를 기반으로 서비스 간 결합도를 낮추는 아키텍처 |
| CQRS | 명령 처리와 조회 처리를 분리하는 설계 방식 |

# 8. 예시 API와 메시지 구조

0주차에서는 전체 구조를 이해하기 위한 간단한 예시만 제공한다.

구체적인 API, 메시지 구조, 테이블 설계는 이후 주차 과제에서 직접 설계한다.

## 쿠폰 발급 요청 API 예시

```
POST /api/coupon-events/{eventId}/issue
```

### Request Body 예시

```json
{
  "userId": 1,
  "requestId": "req-001"
}
```

### Response Body 예시

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

## 발급 상태 조회 API 예시

```
GET /api/coupon-issue-requests/{requestId}
```

### Response Body 예시

```json
{
  "requestId": "req-001",
  "eventId": 100,
  "userId": 1,
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다."
}
```

## Kafka 메시지 예시

```json
{
  "requestId": "req-001",
  "eventId": 100,
  "userId": 1,
  "requestedAt": "2026-07-01T12:00:00"
}
```

이 메시지는 Redis 선착순 판정에 성공한 뒤 Kafka에 발행되는 쿠폰 발급 요청 메시지의 예시다.

# 9. 필수 과제와 심화 과제 기준

이번 과제는 모든 내용을 구현하는 것이 목표가 아니다.

핵심 목표는 대규모 트래픽 상황에서 발생할 수 있는 문제를 이해하고, 그 문제를 해결하기 위한 백엔드 아키텍처를 설계하는 것이다.

## 필수 과제

필수 과제는 구현보다 설계 문서 작성을 중심으로 한다.

각 주차별 필수 과제에서는 다음 내용을 작성한다.

```
1. 문제 상황 요약
2. 아키텍처 그림
3. 요청 처리 흐름
4. 핵심 설계 내용
5. 내가 선택한 방식의 이유
6. 다른 방식과의 비교
7. 장애 또는 예외 상황 처리
```

필수 과제에서는 다음을 중요하게 본다.

- 왜 이 문제가 발생하는지 이해했는가
- 어떤 구조로 해결하려고 했는가
- 선택한 방식의 이유를 설명할 수 있는가
- 다른 방식과 비교할 수 있는가
- 장애 상황을 어느 정도 고려했는가

## 심화 과제

심화 과제는 선택 과제다.

구현이 가능하거나 더 깊게 학습하고 싶은 경우 아래와 같은 내용을 추가로 수행할 수 있다.

```
- API 간단 구현
- Kafka Producer / Consumer 구현
- Redis Lua Script 구현
- DB Unique Constraint 테스트
- requestId 기반 멱등성 처리 구현
- Outbox Publisher 구현
- Retry Topic / DLQ 구현
- Consumer Lag 모니터링 조사
```

심화 과제를 수행하지 않아도 필수 과제를 충실히 작성하면 된다.

0주차에서는 전체 문제 상황과 아키텍처 초안을 이해한다.

1주차: 요청 처리 구조 설계

2주차: Kafka 기반 비동기 요청 처리 구조

3주차: Redis 선착순 판정 구조

4주차: DB 테이블 설계와 최종 정합성 보장

5주차: requestId 기반 멱등성과 중복 처리

6주차: Outbox Pattern과 이벤트 발행 정합성

7주차: EDA 기반 서비스 분리와 조회 구조
