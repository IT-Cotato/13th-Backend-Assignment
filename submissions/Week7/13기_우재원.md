### 1. 직접 호출 구조의 결합을 분석한다

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 쿠폰 발급 처리 완료 시점에 후속 서비스(Notification, MyPage, Analytics)가 반드시 기동 중이고 즉시 응답 가능한 상태여야 한다. 후속 서비스 중 하나라도 응답이 지연되거나 커넥션 타임아웃이 발생하면 API 전체 응답이 지연된다. | Event Producer(Coupon Service)는 Kafka Topic에 `CouponIssued` 이벤트 메시지만 발행(Publish)하고 즉시 응답을 반환한다. | 변경 결합 | 마케팅 알림, 정산, 감사(Audit) 등 후속 서비스가 새로 추가되거나 기존 후속 서비스의 API 엔드포인트/Request Body 규격이 변경될 때마다 Coupon Service의 코드 수정 및 재배포가 강제된다. | Producer는 공통 `CouponIssued` 이벤트 스키마 계약(Schema Contract)만 준수하면 되며, 신규 후속 서비스는 기존 쿠폰 발급 코드의 변경 없이 새로운 Consumer Group으로 독립 추가 및 배포가 가능하다. |
| 데이터 결합 | Coupon Service가 후속 서비스들의 내부 DB 구조, 식별자, 엔티티 모델에 직접 의존하거나, 반대로 후속 서비스가 API 호출 시 전달받는 인자 형태에 강하게 얽매이게 된다. | 이벤트에 정의된 표준적인 퍼블릭 비즈니스 데이터(Payload)만 전달받으므로 각 서비스가 독자적인 DB 스키마와 전용 조회 모델(Read Model)을 소유하여 데이터 경계가 격리된다. |

### 2. 다음 장애 상황을 분석한다

```text
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```text
이미 확정된 쿠폰 발급 상태:
Coupon Service DB의 `coupon_issue` 테이블에는 이미 발급 성공 기록이 저장되고 트랜잭션이 성공적으로 Commit되어 `ISSUED` 상태가 최종 확정된 상태다.

쿠폰 발급을 Rollback하면 안 되는 이유:
사용자 알림(SMS/Push)은 쿠폰 발급 확정 이후에 발생하는 부가적인 후속 처리(Side Effect)일 뿐, 선착순 발급 성공이라는 핵심 비즈니스 불변식을 취소시킬 수 없다. 알림 호출 실패를 이유로 이미 정당하게 선착순 자리를 확보하고 커밋된 쿠폰 발급을 롤백하는 것은 사용자의 정당한 수량 선점 권리를 부당하게 박탈하는 것이며, 롤백 과정에서 DB 정합성 붕괴 및 race condition을 유발할 수 있다.

다시 실행해야 하는 작업:
실패한 Notification Service의 알림 발송 작업만 독립적으로 재시도(Retry)해야 한다.

다시 실행하면 안 되는 작업:
Coupon Service의 선착순 수량 차감, `coupon_issue` DB 저장, requestId 검증 및 트랜잭션 커밋 등 이미 완료된 쿠폰 발급 처리.
```

### 5. EDA를 사용해도 남는 결합을 설명한다

```text
직접 API 계약 대신 남는 계약:
이벤트 메시지의 필드 구성, 데이터 타입, 필드의 비즈니스 의미, 하위 호환성을 규정하는 **이벤트 스키마 계약 (Event Schema Contract)**이 남는다.

이 계약을 관리해야 하는 이유:
Producer가 Consumer와 협의 없이 필드명을 임의로 수정하거나 필드를 삭제하면, 해당 이벤트를 구독하는 여러 Consumer에서 런타임 역직렬화 에러가 발생하거나 데이터가 유실된다. 따라서 Schema Registry나 호환성 검증 규칙(Backwards Compatibility Rule)을 두어 스키마 변경을 엄격히 관리해야 한다.

EDA가 반드시 MSA를 의미하지 않는 이유:
EDA는 시스템 구성 요소 간 이벤트를 주고받는 메시징 아키텍처 패턴이며, 반드시 독립된 물리적 마이크로서비스 서버 환경에서만 동작하는 것이 아니다. 단일 애플리케이션(Monolith) 내부에서도 Spring Event나 In-Memory Event Bus를 활용해 도메인 모듈 간의 결합을 끊는 EDA를 적용할 수 있다. 즉, EDA는 Logical Architecture의 패턴이며 MSA라는 Physical Deployment Topology에 구속되지 않는다.
```

| --- | --- | --- |

| Analytics | `analytics-coupon-issued` | `CouponIssued` 이벤트를 소비하여 `coupon_issue_fact`를 기입하고 `coupon_issue_stats` 집계를 증가시킨다. |

### 2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다

```text
같은 Group 안의 Consumer 관계:
Kafka에서 동일한 Consumer Group ID를 공유하는 Consumer들은 메시지를 "나누어 처리"하는 경쟁적 소비 관계(Competitive Consumers)가 된다.

CouponIssued 한 건의 전달 결과:
Topic-Partition에 저장된 단 한 건의 `CouponIssued` Record는 Group 내 파티션을 할당받은 단 하나의 Consumer 인스턴스에만 전달된다.

세 서비스 중 일부 작업이 누락될 수 있는 이유:
세 서비스가 모두 `coupon-result`라는 동일 Group ID를 사용하면, 이벤트를 세 서비스가 동시에 받지 못하고 셋 중 어느 하나의 서비스 인스턴스만 이벤트를 수신하게 된다. 결과적으로 메시지를 수신한 서비스만 처리되고 나머지 두 서비스에서는 해당 이벤트에 대한 후속 작업(알림/마이페이지/통계)이 완전히 누락된다.
```

### 3. 다음 Partition과 Consumer 배치를 분석한다

```text
coupon.issued Partition 수: 6

notification-coupon-issued Consumer 수: 2
mypage-coupon-projection Consumer 수: 4
analytics-coupon-issued Consumer 수: 1
```

| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | ---: | --- | --- |
| Notification | 2 | 없음 (2개 Consumer가 3개 파티션씩 나누어 담당) | 없음 (독립된 Group Offset 관리) |
| MyPage | 4 | 없음 (2개 Consumer는 2개 파티션, 2개 Consumer는 1개 파티션 담당) | 없음 (독립된 Group Offset 관리) |
| Analytics | 1 | 없음 (1개 Consumer가 6개 파티션 전체를 혼자 담당) | 없음 (독립된 Group Offset 관리) |

---

### 4. Consumer Group의 Committed Offset 의미를 설명한다

```text
Committed Offset이 나타내는 것:
해당 Consumer Group이 특정 Topic-Partition에서 "어디까지 메시지를 읽고 처리 완료 처리를 마쳤는지"를 나타내는 Kafka의 논리적 위치 지점(Logical Checkpoint)이다.

Committed Offset만으로 증명할 수 없는 것:
Consumer 내부 DB 트랜잭션이 실제 커밋되어 비즈니스 상태 반영이 최종 완성되었는지는 증명하지 못한다. DB 커밋 직후 Offset 커밋 전에 장애가 발생하면 DB는 완료되었으나 Offset은 커밋되지 않은 상태가 될 수 있다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
전혀 영향을 주지 않는다. Kafka는 각 Consumer Group별로 Offset을 `__consumer_offsets` 토픽에 완전히 독립적으로 저장하고 관리한다.
```

## 과제 3. CQRS와 MyPage Read Model 설계하기

### 1. Command Model과 Read Model을 비교한다

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 데이터 변경 처리 및 비즈니스 불변식(수량 제한, 중복 발급 방지) 검증 | 빠른 데이터 조회 응답 제공 및 특정 화면(마이페이지) 요구사항 최적화 |
| 대표 작업 | 쿠폰 발급 트랜잭션, Redis 선착순 판정, DB UNIQUE 제약 검증 | 마이페이지 보유 쿠폰 목록 조회, 운영자 발급 통계 조회 |
| 데이터 구조 | 정규화된 3NF 테이블 구조 (`coupon_issue`, `coupon_event`) | 비정규화된 Flat View 테이블 구조 (`user_coupon_view`) |
| 최종 원장 여부 | Yes (Source of Truth - 발급 여부의 최종 기준) | No (파생 데이터 - 언제든 원본에서 재구성 가능) |
| 장애 후 재구축 가능 여부 | No (삭제 시 데이터가 영구 유실됨) | Yes (원본 DB Snapshot 및 Kafka Replay로 재구축 가능) |

---

### 2. CQRS에 대해 다음 문장을 판단한다

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 단일 DB 인스턴스 내부에서도 Command용 테이블과 Query용 비정규화 테이블/뷰로 나누어 논리적 CQRS를 구현할 수 있다. |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 명령과 조회의 모델 분리 패턴이며, Event Sourcing은 상태 변화를 이벤트 스트림으로 저장하는 방식이다. 자주 함께 사용될 뿐 다른 개념이다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 모노리스 구조에서도 쓰기 전용 엔티티와 읽기 전용 DTO/조회 테이블을 구분하여 애플리케이션 수준 CQRS를 적용할 수 있다. |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 쓰기/읽기 트랜잭션 경로 분리, 모델의 비정규화, 이벤트 기반 동기화 등 책임과 모델의 실질적 분리가 수반되어야 CQRS다. |

---

### 3. `user_coupon_view` DDL을 완성한다

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    CONSTRAINT uk_user_coupon_view_user_event UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### 4. 각 제약과 인덱스의 역할을 작성한다

### 4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다

```text
PostgreSQL DB 트랜잭션 내부에서 일반 INSERT 실행 중 Unique 제약 조건 위반 예외(SQLState 23505)가 발생하면, 해당 DB 트랜잭션은 즉시 `InFailedSqlTransaction` (ABORTED) 상태로 전환된다.
이 상태에서는 Java 애플리케이션 레벨에서 `try-catch`로 예외를 잡아내더라도, 해당 DB 커넥션으로 전송되는 이후 모든 SQL 쿼리와 `COMMIT` 명령이 DB에 의해 거부되고 트랜잭션 전체가 롤백된다.
따라서 `ON CONFLICT DO NOTHING` 구문을 사용해 SQL 실행 레벨에서 중복을 정상 수용(0건 처리)하도록 제어해야 DB 트랜잭션이 ABORT 상태로 빠지지 않는다.
```

### 5. 다음 잘못된 처리 순서의 결과를 분석한다

```text
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```text
재전달 시 Consumer 판단:
`processed_event`에 이미 해당 `eventMessageId`가 존재하므로, Consumer는 "이미 처리 완료된 이벤트"로 판단하고 처리를 Skip한다.

최종 조회 모델 상태:
`user_coupon_view`에는 데이터가 반영되지 않은 채 영구히 누락되는 정합성 붕괴(Data Loss)가 발생한다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
`processed_event` 기록과 비즈니스 조회 모델(`user_coupon_view`) 갱신이 "All-or-Nothing"으로 함께 커밋되거나 함께 롤백되는 원자성(Atomicity)을 보장해야 하기 때문이다.
```

### 6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다

```text
DB Commit과 Kafka Offset Commit의 관계:
DB Commit과 Kafka Offset Commit은 원자적이지 않으며(Non-Atomic) 서로 다른 별개의 시스템 커밋 절차다. `processed_event` 저장과 비즈니스 데이터 변경만 단일 로컬 DB 트랜잭션으로 원자적으로 커밋되고, Offset 완료(`acknowledge()`)는 DB Commit 이후에 별도로 실행된다.

Consumer DB 상태:
`processed_event`와 `user_coupon_view` 저장이 하나의 로컬 DB 트랜잭션으로 정상 Commit 완료된다.

Consumer Group Offset:
DB Commit 완료 직후 Offset Ack 전에 장애가 발생했으므로 Kafka 브로커에는 Offset이 Commit되지 않은 미완료 상태로 남아있다.

재시작 후 전달:
Consumer가 재시작하면서 마지막 Committed Offset부터 읽어 동일한 메시지(Record)가 다시 재전달(Redelivery)된다.

재전달된 이벤트 처리:
DB Commit과 Offset Commit 간의 원자성이 보장되지 않아 발생한 메시지 재전달 상황에서도, Consumer가 DB 트랜잭션 내 `processed_event`에 INSERT 시도 시 `ON CONFLICT DO NOTHING`에 의해 `RETURNING` 결과가 0건이 된다. 이로 인해 비즈니스 갱신 없이 안전하게 Skip 처리되며, DB Commit 후 정상적으로 Kafka Offset이 완료된다. 즉, eventMessageId 기반 멱등성이 재전달 메시지를 안전하게 방어한다.
```

---

### 7. Offset 완료 정책을 작성한다

```text
1. `enable.auto.commit = false` 설정으로 Kafka 자동 커밋을 비활성화한다.
2. DB Commit과 Kafka Offset Commit은 원자적이지 않으므로, 수동 커밋 모드(Manual Ack)를 사용하여 반드시 "Consumer의 로컬 DB 트랜잭션 커밋이 성공적으로 완료된 직후"에 `acknowledgment.acknowledge()`를 호출한다.
3. Listener 내부에서 DB 예외나 비즈니스 처리 예외가 발생한 경우에는 `acknowledge()`를 호출하지 않고 예외를 상위로 던져 Offset 커밋을 차단하고 Kafka Retry/DLQ 메커니즘을 타게 한다.
4. 같은 파티션 내 메시지를 병렬 처리할 경우, 뒤선 메시지의 오프셋이 먼저 커밋되어 앞선 미완료 메시지의 처리가 누락되는 Out-of-Order Ack가 발생하지 않도록 순차적 Ack 또는 커밋 블로킹 정책을 적용한다. DB Commit 후 Offset Commit 전 장애로 재전달될 수 있음을 전제로 모든 Consumer는 eventMessageId 기반 멱등성을 보장해야 한다.
```

### 5. `coupon_issue_fact` 기반 집계 구조를 설계한다

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE coupon_issue_stats (
    coupon_event_id BIGINT PRIMARY KEY,
    issued_count BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```sql
BEGIN;

WITH inserted_fact AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id,
        event_message_id,
        coupon_event_id,
        user_id,
        issued_at
    ) VALUES (
        :couponIssueId,
        :eventMessageId,
        :couponEventId,
        :userId,
        :issuedAt
    )
    ON CONFLICT (coupon_issue_id) DO NOTHING
    RETURNING coupon_event_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE coupon_event_id = :couponEventId
  AND EXISTS (
      SELECT 1 FROM inserted_fact
  );

COMMIT;
```

```text
10:00:00.030  CouponIssued Kafka 저장
10:00:04.500  MyPage Consumer 처리 시작
10:00:05.200  user_coupon_view Commit
```

| --- | --- | --- |

### 2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다

```text
DB 발생 순서:
CouponIssued (aggregateVersion = 1, 10:00:00) -> CouponCancelled (aggregateVersion = 2, 10:00:01)

Publisher 처리 순서:
Outbox Publisher 1이 `FOR UPDATE SKIP LOCKED` 구문으로 조회하여 `aggregateVersion = 1` Outbox 행을 락(Lock)을 잡고 Kafka 전송을 시도하는 중 네트워크 지연/타임아웃으로 트랜잭션이 지연된다.
그직후 Outbox Publisher 2가 동시 수행될 때 `FOR UPDATE SKIP LOCKED`에 의해 Publisher 1이 락을 잡은 version 1 행을 건너뛰고(SKIP LOCKED) 아직 락이 걸리지 않은 `aggregateVersion = 2` Outbox 행을 먼저 조회하여 Kafka에 선행 발행(Publish)에 성공한다.

Kafka 저장 순서:
`CouponCancelled` (aggregateVersion = 2)가 Kafka Partition Offset 100에 먼저 저장되고, 뒤늦게 Publisher 1의 재시도가 완료되어 `CouponIssued` (aggregateVersion = 1)가 Offset 101에 저장된다.
```

### 3. `schemaVersion`과 `aggregateVersion`을 비교한다

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| `schemaVersion` | JSON 메시지 Payload 필드 구조의 버전 | 필드 추가/삭제/타입 변경 시 메시지 역직렬화 및 이벤트 하위 호환성 문제 | 이벤트에 새 필드가 추가되거나 구조 변경 시 `1 -> 2` |
| `aggregateVersion` | 특정 `CouponIssue` 엔티티의 비즈니스 상태 변경 순서 버전 | 메시지 비동기 순서 역전(Out-of-order)으로 과거 이벤트가 최신 상태를 덮어쓰는 문제 | ISSUED(v1) -> CANCELLED(v2) -> REISSUED(v3) 비즈니스 전이 시 |

### 4. 최신 상태 Projection의 UPSERT를 완성한다

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    aggregate_version,
    issued_at,
    updated_at
) VALUES (
    :couponIssueId,
    :userId,
    :couponEventId,
    :status,
    :aggregateVersion,
    :issuedAt,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = CURRENT_TIMESTAMP
WHERE user_coupon_view.aggregate_version < EXCLUDED.aggregate_version;
```

### 7. Version Gap 처리 정책을 작성한다

```text
Gap으로 판단하는 조건:
Consumer가 수신한 이벤트의 `incomingVersion > currentVersion + 1`인 경우 (예: 현재 v2인데 v4 수신).

즉시 반영해도 되는 Consumer:
최신 최종 Snapshot 상태만 유지하는 MyPage Read Model.

모든 전이가 필요한 Consumer의 처리:
해당 이벤트를 즉시 처리 완결하지 않고 Pending Holding Queue / Retry Topic으로 보낸 뒤 v3 메시지가 처리될 때까지 재시도 대기.

복구 방법:
일정 시간 재시도 후에도 Gap 메시지(v3)가 도착하지 않으면, Source of Truth DB에서 최신 상태를 직접 백필(Catch-up Query)하거나 Outbox Event Replay 수행.
```

### 2. `user_coupon_view_v2` 재구축 순서를 작성한다

```text
1. 새 Projection 테이블 생성
   `user_coupon_view_v2` 테이블 및 필요한 인덱스를 신규 생성한다.

2. 원본 DB Snapshot Backfill
   현재 시점의 Coupon Service DB Snapshot 데이터를 `user_coupon_view_v2`에 대량 이관한다.

3. 새 Consumer Group으로 Kafka Replay
   새로운 Group ID `mypage-coupon-projection-v2`를 생성하여 Topic의 처음 오프셋부터 이벤트 소비를 준비한다.

4. Backfill 경계 이후 이벤트 Catch-up
   Backfill 기준시점 이후 유입된 Kafka 이벤트를 v2 Consumer가 수신하여 `aggregate_version` 비교 UPSERT로 최신 상태를 따라잡는다.

5. 원본과 v2 정합성 검증
   `coupon_issue` 원본 테이블과 `user_coupon_view_v2` 간의 건수 및 상태 불일치(Mismatch Count = 0)를 검증한다.

6. 조회 API 전환
   마이페이지 조회 API의 DB 쿼리 대상을 구버전 테이블에서 `user_coupon_view_v2`로 블루/그린 전환한다.

7. 기존 Projection 보관 또는 제거
   안정화 기간 종료 후 구버전 `user_coupon_view` 테이블을 백업 후 백그라운드 제거한다.
```

### 3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다

```text
Kafka만으로 전체 Replay가 가능한가?
불가능하다 (retention period가 지난 오랜 이벤트는 Kafka 브로커에서 영구 삭제됨).

필요한 다른 복구 기준:
Coupon Service DB (Source of Truth)의 Snapshot 데이터.

Backfill 중 새 이벤트가 들어올 때 필요한 경계:
Snapshot 추출 시작 시점의 `snapshotTimestamp` 또는 `maxCouponIssueId`를 기준 경계로 설정하고, 경계 이전 데이터는 Snapshot으로 백필한 후 경계 이후 데이터는 Kafka 이벤트를 Catch-up하여 `aggregate_version` 비교 UPSERT로 병합한다.
```

### 4. 운영 지표를 완성한다

| 지표 | 의미 | 장애 신호 예시 |
| --- | --- | --- |
| Group별 Consumer Lag | 각 Consumer Group이 읽지 못하고 쌓여있는 Kafka 메시지 잔여 건수 | Lag 수치가 감소하지 않고 지속적으로 증가하는 현상 |
| Oldest Unprocessed Age | 읽히지 않고 파티션에 대기 중인 가장 오래된 메시지의 대기 시간 | Age 지표가 SLA 허용치(예: 10초)를 초과하여 계속 상승하는 현상 |
| Projection Delay | 이벤트 발생 시각(`occurredAt`)부터 Read Model DB Commit 완료 시각까지의 시차 | Projection Delay가 급증하여 수분 이상 지연되는 현상 |
| Handler Failure Count | Consumer 내부 비즈니스/DB 처리 중 예외가 발생한 횟수 | Failure Count 지표가 급증하는 현상 (DB 다운, 코드 버그) |
| Duplicate Event Count | `processed_event`에 이미 존재하여 멱등 Skip 처리된 중복 이벤트 건수 | Duplicate Count가 비정상적으로 높게 치솟는 현상 (Publisher 재전송 폭주) |
| Read Model Mismatch Count | 원본 `coupon_issue` DB와 Read Model `user_coupon_view` 간의 정합성 불일치 건수 | Mismatch Count > 0 (프로젝션 누락 또는 데이터 파손 발생) |

| 9 | 세 Listener가 단일 클래스 내 경계 불명확 | 알림, 마이페이지, 통계 등 후속 서비스별 데이터 소유권과 비즈니스 책임 경계가 불명확하여 도메인 모델과 DB 처리가 얽힘. | 단일 애플리케이션 내에서도 서비스별 독립된 DB/테이블, 엔티티, 전용 Consumer 클래스로 도메인 소유권과 논리적 책임 경계를 명확히 분리. |
| 10 | 관측성(Observability) 및 Correlation ID 로깅 부재 | Exception Handling, Correlation ID (`requestId`, `eventMessageId`, `couponIssueId`) 로깅, Lag 지표 수집 부재로 장애 추적 불가. | MDC 기반 Correlation ID 로깅 및 Consumer Lag / Failure Metrics 수집 코드 적용. |

## 핵심 질문

```text
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
각 서비스가 동일한 이벤트를 누락 없이 독립적으로 수신하고 자신의 DB를 변경하기 위함이다.

2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
이미 DB에서 발급이 커밋되어 바꿀 수 없는 과거의 사건이므로 Consumer가 쿠폰을 다시 발급하지 않고 후속 처리만 수행하기 위함이다.

3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
Coupon Service DB의 `coupon_issue` 테이블이 쿠폰 발급 여부의 유일한 Source of Truth다.

4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
Outbox Publisher의 재발행이나 Retry Topic 이동 시 Kafka 브로커에서 새로운 물리적 Offset을 부여받기 때문이다.

5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
메시지 처리 멱등 기록과 비즈니스 상태 변경을 원자적으로 "All-or-Nothing" 커밋하여 정합성 붕괴를 막기 위함이다.

6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
쿠폰 발급 DB 커밋과 비동기 MyPage Read Model 갱신 사이에 Consumer Lag에 의한 최종적 일관성(Eventual Consistency) 시차가 존재하기 때문이다.

7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
Partition Key만으로는 Publisher의 재시도나 멀티 토픽 발행에 의한 순서 역전을 막을 수 없으므로 Consumer의 버전 비교 검증이 추가로 필요하기 때문이다.

8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
Analytics나 Notification처럼 모든 상태 전이에 대한 집계나 알림이 필요한 Consumer는 중간 버전을 누락하면 통계 오염이나 알림 유실이 발생하기 때문이다.

9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
Read Model은 언제든 버그나 데이터 오염 시 원본 DB Snapshot과 Kafka Replay로 재구성 가능한 파생 데이터이기 때문이다.

10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
쿠폰 발급은 이미 완결된 성공 상태이므로 알림 장애로 인해 정당한 선착순 발급을 취소하거나 중복 발급을 시도하면 안 되기 때문이다.
```
