## 과제 1. 직접 호출 구조와 EDA 비교하기

### 1. 직접 호출 구조의 결합을 분석한다

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | Coupon Service가 호출하는 시점에 세 서비스가 모두 응답 가능한 상태여야 한다. 하나라도 응답 지연이 생기면 쿠폰 발급 응답 시간 전체가 늘어난다 | Kafka에 이벤트를 발행하고 반환한다. 세 서비스는 자신의 처리 가능 시점에 이벤트를 소비하므로 Coupon Service가 기다리지 않아도 된다 |
| 장애 결합 | Notification Service가 다운되면 Coupon Service의 발급 응답도 실패한다. 쿠폰은 이미 발급됐지만 클라이언트에게 오류가 반환된다 | Consumer 장애가 Coupon Service에 전파되지 않는다. Kafka에 이벤트가 저장된 후 해당 Consumer가 복구되면 자동으로 재처리한다 |
| 변경 결합 | Notification API 인터페이스가 변경되면 Coupon Service 코드도 함께 수정해야 한다. 세 서비스 중 하나의 스펙 변경이 Coupon Service에 직접 영향을 준다 | Coupon Service는 이벤트 스키마만 유지하면 된다. 각 Consumer는 독립적으로 이벤트를 해석하므로 Consumer 내부 구현이 바뀌어도 Producer는 영향받지 않는다 |
| 데이터 결합 | Coupon Service가 Notification에 어떤 데이터를 어떤 형태로 넘길지 알아야 한다. 서비스 간 데이터 구조 의존성이 생긴다 | 이벤트 Payload를 중심으로 계약이 정의된다. 각 서비스는 필요한 필드만 선택적으로 사용하므로 의존성이 줄어든다 |

### 2. 다음 장애 상황을 분석한다

```
이미 확정된 쿠폰 발급 상태:
coupon_event.issued_count 증가, coupon_issue 저장, coupon_issue_request ISSUED 변경이 모두 DB에 Commit됐다.
사용자에게 쿠폰이 발급된 사실은 PostgreSQL에 영속적으로 기록된 확정된 상태다.

쿠폰 발급을 Rollback하면 안 되는 이유:
DB Commit이 완료된 시점에서 쿠폰 발급은 이미 완료된 사실(fact)이다.
Notification API 실패는 발급 사실과 무관한 후속 작업 실패다.
발급을 Rollback하면 issued_count가 잘못된 값이 되고, 이미 발급 성공 정보를 다른 곳에서 참조했다면 정합성이 깨진다.
Rollback하더라도 이미 Commit된 DB 트랜잭션은 되돌릴 수 없으며, 별도의 보정 트랜잭션이 필요하다.

다시 실행해야 하는 작업:
Notification 발송. 아직 완료되지 않은 작업이므로 재시도해야 한다.

다시 실행하면 안 되는 작업:
쿠폰 발급. 이미 발급 기록이 DB에 있으므로 다시 실행하면 중복 발급이 발생한다.
MyPage 반영도 이미 완료됐다면 재실행하면 안 된다.
```

### 3. EDA 기반 전체 흐름을 완성한다

```
Coupon Issue Consumer
        |
        v
+------------------------------------------+
| Coupon Issue DB Transaction              |
|------------------------------------------|
| coupon_event.issued_count 증가           |
| coupon_issue 저장                        |
| coupon_issue_request ISSUED              |
| CouponIssued Outbox 저장 (PENDING)       |
+------------------------------------------+
        |
        | Commit → Kafka Offset Commit
        v
Outbox Publisher (Polling)
  Claim → 발행 → ACK → PUBLISHED
        |
        v
Kafka coupon.issued Topic
  |
  +--[notification-coupon-issued Group]--> Notification Consumer
  |                                           |
  |                                           v
  |                                      processed_event INSERT
  |                                      notification_job INSERT
  |                                      DB Commit → Offset Commit
  |                                      → Notification Sender (SMS)
  |
  +--[mypage-coupon-projection Group]--> MyPage Consumer
  |                                           |
  |                                           v
  |                                      processed_event INSERT
  |                                      user_coupon_view UPSERT
  |                                      DB Commit → Offset Commit
  |
  +--[analytics-coupon-issued Group]--> Analytics Consumer
                                             |
                                             v
                                        coupon_issue_fact INSERT
                                        coupon_issue_stats +1
                                        DB Commit → Offset Commit
```

### 4. 명령과 이벤트의 차이를 작성한다

| 이름 | 종류 | 의미 | Consumer가 쿠폰을 다시 발급하는가? |
| --- | --- | --- | --- |
| `IssueCoupon` | 명령(Command) | 쿠폰을 발급하라는 아직 처리되지 않은 요청. 미래에 수행할 행위를 나타내며 실패하거나 거절될 수 있다 | 가능하다. 명령은 처리되지 않았을 수 있으므로 재시도 시 발급 로직이 다시 실행된다 |
| `CouponIssued` | 이벤트(Event) | 쿠폰 발급이 이미 완료됐다는 확정된 사실. DB Commit 이후 생성되므로 되돌릴 수 없다 | 아니다. 이미 발급된 사실을 나타내므로 Consumer가 이 이벤트를 받더라도 발급을 다시 실행하면 안 된다 |

### 5. EDA를 사용해도 남는 결합을 설명한다

```
직접 API 계약 대신 남는 계약:
이벤트 스키마 계약. CouponIssued의 eventType, schemaVersion, 필드명, 필드 타입, Payload 구조가
Producer와 Consumer 사이의 계약이 된다.

이 계약을 관리해야 하는 이유:
Consumer는 이벤트를 역직렬화해 처리하므로 이벤트 스키마가 예고 없이 바뀌면 Consumer가 오류를 낸다.
schemaVersion을 올려 하위 호환성을 관리하거나 Schema Registry를 통해 스키마 진화를 제어해야 한다.
계약을 관리하지 않으면 Producer가 필드를 삭제하거나 타입을 바꿀 때 Consumer가 조용히 잘못된 데이터를 처리할 수 있다.

EDA가 반드시 MSA를 의미하지 않는 이유:
EDA는 서비스 간 통신 패턴이다. 단일 애플리케이션 안에서도 도메인별로 Command와 Event를 분리하고
애플리케이션 내부 이벤트 버스(Spring ApplicationEvent 등)를 사용해 EDA를 적용할 수 있다.
서비스를 물리적으로 분리하지 않아도 논리적으로 이벤트 기반 결합을 줄이는 것이 EDA다.
```

## 과제 2. Consumer Group과 서비스 책임 설계하기

### 1. 서비스별 Consumer Group을 작성한다

| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | notification-coupon-issued | 사용자에게 쿠폰 발급 완료 SMS/Push 알림 전송. notification_job에 작업을 저장하고 Sender가 외부 Provider에 발송 |
| MyPage | mypage-coupon-projection | 사용자의 쿠폰 목록 Read Model(user_coupon_view) 갱신. 사용자가 마이페이지에서 발급 쿠폰을 조회할 수 있도록 Projection 유지 |
| Analytics | analytics-coupon-issued | 발급 사실을 coupon_issue_fact에 저장하고 coupon_issue_stats의 집계 카운트를 증가. 운영자 통계 제공 |

### 2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다

```
같은 Group 안의 Consumer 관계:
같은 Consumer Group 내의 여러 Consumer는 Topic의 Partition을 나누어 처리한다.
하나의 Partition은 같은 Group 내에서 한 Consumer에게만 할당된다.

CouponIssued 한 건의 전달 결과:
같은 Group ID를 사용하면 Notification, MyPage, Analytics Consumer가 모두 같은 Group이 된다.
하나의 CouponIssued 이벤트는 그 Partition을 할당받은 Consumer 인스턴스 하나에게만 전달된다.
예를 들어 Partition 3의 이벤트를 Notification Consumer가 처리하면 같은 Group의 MyPage와 Analytics는 그 이벤트를 받지 못한다.

세 서비스 중 일부 작업이 누락될 수 있는 이유:
각 Partition이 하나의 Consumer에게만 할당되므로 Notification이 처리한 이벤트는 MyPage와 Analytics가 처리하지 않는다.
세 가지 작업(알림, 마이페이지 갱신, 통계 집계)이 골고루 처리되지 않고 하나의 Consumer만 처리하게 된다.
결과적으로 알림만 가고 마이페이지 갱신이 누락되거나, 통계만 집계되고 알림은 가지 않는 상황이 발생한다.
```

### 3. 다음 Partition과 Consumer 배치를 분석한다

| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | ---: | --- | --- |
| Notification | 2 | 4개 Partition이 Consumer 없이 남을 수 없으므로 2개 Consumer가 각 3개 Partition씩 처리. Consumer 수 초과 없음 | 없음. Consumer Group Offset이 완전히 독립적이므로 MyPage나 Analytics가 지연되어도 Notification 처리에 영향 없음 |
| MyPage | 4 | 6개 Partition에 4개 Consumer이므로 2개 Consumer가 2개 Partition씩, 나머지 2개 Consumer가 1개 Partition씩 처리. 미사용 Consumer 없음 | 없음. Group이 다르므로 독립적 |
| Analytics | 1 | Consumer가 1개이므로 6개 Partition을 모두 순차 처리. 5개 Partition이 동시에 처리되지 않음(처리량 병목) | 없음. Group이 다르므로 독립적 |

### 4. Consumer Group의 Committed Offset 의미를 설명한다

```
Committed Offset이 나타내는 것:
해당 Consumer Group이 특정 Partition에서 마지막으로 처리 완료를 확인한 위치다.
다음 Poll 시 Committed Offset 이후의 Record부터 읽기 시작한다.

Committed Offset만으로 증명할 수 없는 것:
비즈니스 처리가 실제로 완료됐다는 것. Offset을 Commit했더라도 Consumer 내부 DB 처리가 실패했을 수 있다.
enable.auto.commit을 사용하면 비즈니스 처리와 무관하게 Offset이 먼저 커밋될 수 있다.
또한 Committed Offset은 해당 Group의 진행 상황만 나타내며 다른 Group의 처리 여부와는 무관하다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
그렇지 않다. Consumer Group Offset은 Group별로 독립적으로 관리된다.
Notification Group이 Offset 100까지 커밋해도 MyPage Group은 Offset 50에 머물 수 있다.
Kafka는 Group별로 Offset을 별도 저장하며 서로 간섭하지 않는다.
```

### 5. 서비스별 책임과 데이터 소유권을 완성한다

| 서비스 | 소유하는 데이터 | 보장해야 하는 불변식 또는 책임 | 다른 서비스 DB 직접 수정 허용 여부 |
| --- | --- | --- | --- |
| Coupon Service | coupon_event, coupon_issue, coupon_issue_request | 발급 원장의 최종 진실. issued_count가 total_quantity를 초과하지 않음. 사용자당 1개 발급 제한 | 허용하지 않는다. 발급 원장의 무결성은 Coupon Service만 책임진다 |
| Notification Service | notification_job, notification_log | 발송 작업의 상태 관리. 중복 알림 방지. 발송 성공·실패 이력 보관 | 허용하지 않는다. 쿠폰 원장이나 Read Model을 직접 수정하면 데이터 소유권이 불분명해진다 |
| MyPage Service | user_coupon_view (Read Model) | 사용자가 조회하는 쿠폰 목록의 정확성. CouponIssued 기반 최신 상태 유지. Coupon Service 원장과의 최종적 일관성 | 허용하지 않는다. 읽기 전용 Projection을 다른 서비스가 수정하면 일관성이 보장되지 않는다 |
| Analytics Service | coupon_issue_fact, coupon_issue_stats | 발급 사실의 중복 없는 기록. 집계 카운트의 정확성. Fact와 Stats의 일관성 | 허용하지 않는다. 집계 데이터의 정합성은 Analytics Service가 단독으로 책임진다 |

## 과제 3. CQRS와 MyPage Read Model 설계하기

### 1. Command Model과 Read Model을 비교한다

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 비즈니스 상태를 변경하고 불변식을 보장한다 | 조회 요청에 빠르게 응답하기 위해 최적화된 형태로 데이터를 제공한다 |
| 대표 작업 | coupon_issue INSERT, issued_count UPDATE, coupon_issue_request 상태 전이 | GET /users/{userId}/coupons 목록 조회, 쿠폰 상세 조회 |
| 데이터 구조 | 정규화된 테이블 구조. coupon_event, coupon_issue 등이 분리되어 있음 | 조회에 필요한 필드를 하나의 테이블에 비정규화해 JOIN 없이 조회 가능 |
| 최종 원장 여부 | 그렇다. 발급 여부의 최종 진실(Source of Truth) | 아니다. Coupon Service의 Write Model을 기반으로 파생된 데이터 |
| 장애 후 재구축 가능 여부 | 재구축이 불가능하다. 이 데이터 자체가 원본 | 가능하다. Coupon Service DB 또는 Kafka 이벤트 이력에서 다시 만들 수 있다 |

### 2. CQRS에 대해 다음 문장을 판단한다

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | CQRS는 Command와 Query의 책임을 분리하는 패턴이다. 같은 DB 안에서 Command용 테이블과 Query용 테이블을 분리해도 CQRS를 적용한 것이다. DB를 물리적으로 분리하는 것은 선택 사항이다 |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 Command와 Query 책임을 분리하는 패턴이고, Event Sourcing은 상태를 이벤트 로그로 저장하는 패턴이다. 두 패턴은 자주 함께 사용되지만 서로 독립적이며 각각 따로 적용할 수 있다 |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 단일 애플리케이션 안에서도 발급 처리용 Write 경로와 조회용 Read 경로를 별도의 서비스 클래스나 레이어로 분리해 CQRS를 적용할 수 있다 |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 테이블 분리는 CQRS를 구현하는 수단 중 하나일 뿐이다. Command와 Query의 책임과 흐름을 명확하게 분리하고 Read Model이 Write Model의 파생임을 인식하는 설계가 CQRS의 핵심이다 |

### 3. `user_coupon_view` DDL을 완성한다

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id   BIGINT        NOT NULL,
    user_id           BIGINT        NOT NULL,
    coupon_event_id   BIGINT        NOT NULL,
    status            VARCHAR(20)   NOT NULL,
    aggregate_version BIGINT        NOT NULL DEFAULT 1,
    issued_at         TIMESTAMP     NOT NULL,
    updated_at        TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_user_coupon_view
        PRIMARY KEY (coupon_issue_id),

    CONSTRAINT uq_user_coupon_view_user_event
        UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### 4. 각 제약과 인덱스의 역할을 작성한다

| 장치 | 막거나 개선하는 문제 |
| --- | --- |
| `PRIMARY KEY (coupon_issue_id)` | 같은 couponIssueId에 대한 중복 행 생성을 방지한다. ON CONFLICT DO UPDATE 또는 DO NOTHING 기준이 된다. UPSERT 시 충돌 대상이 되어 원자적 갱신을 가능하게 한다 |
| `UNIQUE (user_id, coupon_event_id)` | 같은 사용자가 같은 쿠폰 이벤트의 발급 정보를 두 행으로 중복 저장하는 것을 막는다. 마이페이지에서 한 쿠폰 이벤트 당 한 건만 노출되어야 하는 제약을 보장한다 |
| `(user_id, issued_at DESC)` Index | 특정 사용자의 쿠폰 목록을 최신 발급 순으로 조회할 때 Full Table Scan 없이 인덱스 탐색으로 빠르게 반환한다. GET /users/{userId}/coupons 쿼리의 성능을 보장한다 |

### 5. 다음 조회 API가 Read Model을 사용하는 이유를 설명한다

```
원본 발급 DB를 매번 복잡하게 조회할 때의 문제:
coupon_issue, coupon_event, coupon_issue_request 등 여러 테이블을 JOIN해야 한다.
발급 이력이 쌓일수록 사용자별 조회 쿼리가 느려지고 Write 트랜잭션과 경합이 생긴다.
발급 트랜잭션 처리량이 높은 시간대에는 조회 부하가 발급 성능에 영향을 준다.

Read Model에 일부 데이터가 중복되어도 되는 이유:
Read Model은 조회 성능을 위해 의도적으로 비정규화한 파생 데이터다.
coupon_event_id, user_id, issued_at 등을 user_coupon_view에 중복 저장해도
원본 진실은 Coupon Service의 Write Model에 있으므로 정합성의 책임은 원본에 있다.
Read Model은 언제든 원본으로부터 재구축할 수 있으므로 중복 저장이 허용된다.

쿠폰 발급 성공의 최종 기준 데이터:
Coupon Service의 coupon_issue 테이블. 이 테이블에 행이 존재하고 coupon_issue_request가 ISSUED 상태인 것이 발급 성공의 원장이다.
MyPage user_coupon_view는 조회 편의를 위한 파생 Projection이므로 발급 여부의 최종 기준이 아니다.
```

### 6. 화면 표시용 데이터 전달 방법을 비교한다

| 방법 | 장점 | 단점 | 데이터 소유권·장애 결합에 미치는 영향 |
| --- | --- | --- | --- |
| `CouponIssued`에 Snapshot 포함 | Consumer가 이벤트만으로 Read Model을 완성할 수 있다. 외부 의존성 없이 처리 가능하다 | 이벤트 크기가 커지고 Coupon 메타데이터가 변경되면 이전 이벤트의 Snapshot은 구버전 정보를 담게 된다 | 데이터 소유권이 명확하다. 이벤트 발행 시점의 스냅샷이므로 Consumer가 Coupon Service에 의존하지 않는다. 장애 결합이 없다 |

| 이벤트 처리 중 Coupon Service API 동기 호출 | Read Model에 항상 최신 데이터를 반영할 수 있다 | Coupon Service 장애 또는 지연이 MyPage Consumer 처리를 막는다. Consumer 처리량이 Coupon Service API 응답 속도에 의존한다 | 장애 결합이 다시 발생한다. EDA로 분리한 이점을 상당 부분 잃는다 |
| Coupon Service DB 직접 조회 | 최신 데이터 보장 | 서비스 DB 경계가 무너진다. Coupon Service DB 스키마 변경이 MyPage Service에 직접 영향을 준다 | 데이터 소유권이 불명확해진다. Coupon Service DB에 대한 강한 의존성이 생겨 독립적 배포가 어려워진다 |

이벤트에 원본 Entity 전체를 넣으면 안 되는 이유:

```
이벤트는 특정 사실(fact)을 나타내는 최소한의 데이터만 포함해야 한다.
Entity 전체를 넣으면 이벤트 크기가 커져 Kafka 전송 성능이 저하되고 보관 비용이 증가한다.
Consumer가 필요하지 않은 데이터까지 역직렬화해 처리하므로 불필요한 결합이 생긴다.
Entity에 민감 정보(비밀번호, 개인식별번호 등)가 있다면 이벤트에 포함되어 보안 위험이 된다.
Entity 구조가 변경될 때마다 이벤트 스키마도 함께 변경되어 Consumer 호환성 관리가 어려워진다.
```

## 과제 4. Consumer 멱등 트랜잭션 설계하기

### 1. Offset과 eventMessageId를 비교한다

| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka Topic의 특정 Partition 내 물리적 Record 위치 | 그렇다. 재발행하면 새 Offset에 Record가 저장되어 Offset이 달라진다 | 아니다. 재발행 시 Offset이 달라지므로 같은 논리 이벤트를 다른 이벤트로 인식해 중복 처리가 발생한다 |
| eventMessageId | 논리 이벤트 자체의 고유 식별자. 이벤트 발생 시 한 번 생성되며 재발행해도 동일한 값 | 아니다. 재발행해도 eventMessageId는 변경되지 않는다 | 그렇다. 같은 논리 이벤트는 항상 같은 eventMessageId를 가지므로 중복 처리를 정확히 감지할 수 있다 |

### 2. `processed_event` DDL을 작성한다

```sql
CREATE TABLE processed_event (
    subscriber_id    VARCHAR(100)  NOT NULL,
    event_message_id UUID          NOT NULL,
    processed_at     TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_processed_event
        PRIMARY KEY (subscriber_id, event_message_id)
);
```

```
선택: mypage-coupon-projection

이유:
pod-a7f9c와 server-10.0.0.12는 프로세스 인스턴스 식별자다.
인스턴스가 재시작되거나 새 Pod로 교체되면 subscriber_id가 달라진다.
새 인스턴스가 같은 eventMessageId의 이벤트를 처리할 때 이전 인스턴스가 저장한 기록을 찾지 못해 중복 처리가 발생한다.
mypage-coupon-projection은 논리적 Consumer 역할을 나타내는 이름이므로 인스턴스가 교체되어도 subscriber_id가 동일하다.
같은 Consumer Group 내 어느 인스턴스가 처리해도 동일한 subscriber_id를 사용하므로 중복을 정확히 감지할 수 있다.
```

### 3. MyPage Consumer 트랜잭션을 완성한다

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (subscriber_id, event_message_id, processed_at)
    VALUES ('mypage-coupon-projection', :eventMessageId, NOW())
    ON CONFLICT (subscriber_id, event_message_id) DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    aggregate_version,
    issued_at,
    updated_at
)
SELECT
    :couponIssueId,
    :userId,
    :couponEventId,
    :status,
    :aggregateVersion,
    :issuedAt,
    NOW()
FROM accepted
ON CONFLICT (coupon_issue_id)
DO UPDATE SET
    status            = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at        = EXCLUDED.updated_at
WHERE user_coupon_view.aggregate_version < EXCLUDED.aggregate_version;

COMMIT;
```

### 4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다

```
PostgreSQL에서 UNIQUE 위반이나 PK 중복 예외가 발생하면 해당 트랜잭션은 aborted 상태가 된다.
aborted 상태의 트랜잭션에서는 이후 모든 SQL이 "ERROR: current transaction is aborted" 오류를 반환한다.
예외를 catch해서 계속 진행하더라도 그 안에서 실행되는 SELECT나 UPDATE가 모두 오류를 낸다.
정상적으로 처리를 계속하려면 반드시 ROLLBACK 후 새 트랜잭션을 시작하거나,
INSERT 전에 SAVEPOINT를 만들어 SAVEPOINT로 복구하는 방식을 사용해야 한다.
ON CONFLICT DO NOTHING이 이 문제를 해결하는 가장 깔끔한 방법이며 트랜잭션 중단 없이 충돌을 무시할 수 있다.
```

### 5. 다음 잘못된 처리 순서의 결과를 분석한다

```
재전달 시 Consumer 판단:
processed_event에 eventMessageId 기록이 이미 있으므로 중복 이벤트로 판단한다.
처리를 건너뛰고 Offset을 커밋해 정상 종료한다.

최종 조회 모델 상태:
user_coupon_view가 갱신되지 않았으므로 해당 쿠폰 발급 건이 마이페이지에 보이지 않는다.
processed_event에는 처리된 기록이 있지만 실제 Read Model은 반영되지 않아 영구적으로 불일치가 발생한다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
processed_event 기록과 user_coupon_view 변경이 원자적으로 처리되어야 한다.
processed_event만 Commit되고 조회 모델 변경이 실패하면, 재전달 시 이미 처리된 것으로 판단해 조회 모델이 영원히 갱신되지 않는다.
반대로 조회 모델만 변경되고 processed_event가 없으면 재전달 시 중복 반영이 발생한다.
두 작업을 같은 트랜잭션에 묶어야 둘 다 Commit되거나 둘 다 실패해 일관성이 보장된다.
```

### 6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다

```
Consumer DB 상태:
processed_event에 eventMessageId 기록됨. user_coupon_view UPSERT 완료됨. 조회 모델 갱신된 상태.

Consumer Group Offset:
Commit되지 않음. Kafka는 이 Record가 아직 처리되지 않은 것으로 판단한다.

재시작 후 전달:
Consumer 재시작 후 Committed Offset 이후부터 같은 이벤트를 다시 전달받는다.
(같은 eventMessageId, 같은 Partition의 같은 Offset)

재전달된 이벤트 처리:
INSERT INTO processed_event ON CONFLICT DO NOTHING → 0행 반환.
accepted CTE가 빈 결과이므로 user_coupon_view INSERT도 실행되지 않는다.
중복 반영 없이 Commit 후 Offset을 커밋한다. 정상 종료.
```

### 7. Offset 완료 정책을 작성한다

```
enable.auto.commit:
반드시 false로 설정한다. 자동 Offset Commit은 비즈니스 처리 완료와 무관하게 Offset을 커밋해 처리 실패 시 이벤트가 유실된다.

DB Commit과 Offset Commit 순서:
반드시 DB Commit이 먼저 성공한 후에 acknowledgment.acknowledge()로 Offset을 커밋한다.
순서가 바뀌면 Offset Commit 후 DB 처리 실패 시 해당 이벤트가 재전달되지 않아 영구 유실된다.

Listener 예외 처리:
일시적 DB 오류(Deadlock, Connection 실패, Timeout)는 예외를 던져 Consumer가 재처리할 수 있도록 한다.
비즈니스 최종 처리(중복 이벤트, 처리 불가 메시지)는 Offset을 커밋하고 정상 종료하거나 DLQ로 이동한다.
예외 없이 조용히 넘어가면 처리 실패가 감지되지 않으므로 반드시 적절한 예외를 발생시켜야 한다.

같은 Partition 병렬 처리 시 앞선 미완료 Record:
같은 Partition 내에서 Offset 100 처리 중 Offset 101을 먼저 Commit하면
Offset 100 처리 실패 후 재시작 시 101 이후부터 읽기 시작해 Offset 100이 유실된다.
AckMode.MANUAL을 사용할 때 앞선 Record가 완료되지 않은 상태에서 뒤의 Record Offset을 커밋하지 않아야 한다.
```

## 과제 5. Notification과 Analytics 처리 설계하기

### 1. Notification Consumer의 새로운 Dual Write를 분석한다

| 장애 지점 | DB 상태 | 외부 SMS 상태 | 재전달 시 문제 |
| --- | --- | --- | --- |
| SMS 성공 후 `processed_event` Commit 전 종료 | processed_event 없음. notification_job 없음 | SMS 발송됨 | 재전달 시 processed_event가 없으므로 최초 이벤트로 판단해 SMS를 다시 발송한다. 중복 SMS 전송 발생 |
| `processed_event` Commit 후 SMS 호출 전 종료 | processed_event 존재. notification_job 존재(또는 없음에 따라 다름) | SMS 발송 안 됨 | 재전달 시 processed_event가 있으므로 중복으로 판단해 처리를 건너뛴다. SMS가 영원히 발송되지 않을 수 있음 |

### 2. Notification 내부 처리 구조를 완성한다

```
CouponIssued 이벤트 소비 (notification-coupon-issued Group)
        |
        v
+------------------------------------------+
| Notification Consumer DB Transaction    |
|------------------------------------------|
| processed_event INSERT ON CONFLICT SKIP  |
| notification_job INSERT (status=PENDING) |
+------------------------------------------+
        |
        | DB Commit → Kafka Offset Commit
        v
notification_job (PENDING)
        |
        v
Notification Sender (별도 스케줄러 또는 폴링 서비스)
        |
        +--> 외부 Provider API 호출
        |     (notificationId = idempotency key)
        |
        +--> ACK 성공 → notification_job SENT 변경
        |
        +--> ACK 실패 → notification_job FAILED 또는 PENDING(재시도)
```

`processed_event`와 `notification_job`을 어떤 트랜잭션으로 처리해야 하는지:

```
두 INSERT를 반드시 같은 DB 트랜잭션으로 처리해야 한다.

processed_event만 Commit되고 notification_job INSERT가 실패하면:
재전달 시 processed_event가 있어 중복으로 판단하고 처리를 건너뛴다.
notification_job이 없으므로 SMS가 영원히 발송되지 않는다.

notification_job만 Commit되고 processed_event가 없으면:
재전달 시 최초 이벤트로 판단해 notification_job을 다시 INSERT해 중복 발송이 발생한다.

같은 트랜잭션으로 묶으면 두 작업이 원자적으로 처리되어 둘 다 성공하거나 둘 다 실패한다.
```

### 3. 외부 Provider가 Idempotency Key를 지원하지 않는 경우의 보장 수준을 작성한다

```
외부 알림 전송 보장 수준:
At-Least-Once 전송을 목표로 한다. SMS 발송에 실패하면 재시도하므로 중복 전송 가능성이 있다.
최소한 "발송 의도를 기록하고 결국 발송한다"는 것을 보장할 수 있다.

중복 전송 가능성을 완전히 제거할 수 있는가?
아니다. notification_job을 PENDING으로 처리하고 Sender가 발송한 후 SENT로 변경하는 사이에
프로세스가 종료되면 Sender가 재시작 후 같은 job을 다시 발송할 수 있다.
외부 Provider가 Idempotency Key를 지원하지 않으면 이 중복을 막을 수단이 없다.

운영에서 추가로 필요한 장치:
중복 발송 발생 시 사용자 민원에 대응할 수 있는 발송 이력 조회 시스템.
중복 발송 건수를 모니터링하고 임계치 초과 시 알람하는 지표.
재시도 횟수 제한(최대 attempt_count)을 설정해 무한 재시도로 인한 스팸 방지.
발송 실패 건을 DLQ로 이동해 운영자가 수동 재처리할 수 있는 운영 도구.
```

### 4. 다음 Analytics 구현의 문제를 설명한다

```
같은 eventMessageId가 두 번 전달되었을 때의 결과:
첫 번째 전달: UPDATE coupon_issue_stats SET issued_count = issued_count + 1 → issued_count가 1 증가
두 번째 전달: 멱등성 처리 없이 동일한 UPDATE 실행 → issued_count가 또 1 증가

최종 결과: issued_count가 실제 발급 건수보다 1 많은 값이 된다.
한 번 발급된 쿠폰이 두 번 집계되어 통계가 부정확해진다.
Kafka 재발행 또는 Consumer 재시작이 잦은 운영 환경에서 통계 오염이 누적된다.
```

WITH accepted AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id,
        event_message_id,
        coupon_event_id,

        issued_at
    )

| --- | --- | --- | --- |

### 2. 다음 상태가 서로 같은 의미인지 판단한다

| 상태 비교 | 같음/다름 | 이유 |
| --- | --- | --- |
| DB `ISSUED` vs Kafka Record 존재 | 다름 | DB ISSUED는 발급 트랜잭션이 Commit된 상태다. Kafka Record는 Outbox Publisher가 발행 성공한 상태다. Outbox가 아직 PENDING이면 DB는 ISSUED지만 Kafka Record가 없을 수 있다 |
| Kafka Record 존재 vs MyPage 반영 완료 | 다름 | Kafka에 Record가 있어도 MyPage Consumer가 아직 소비하지 않았거나 처리 중이면 user_coupon_view가 갱신되지 않은 상태다. Consumer Lag이 있으면 Record 존재와 MyPage 반영은 시간 차이가 생긴다 |
| MyPage Group Offset Commit vs Notification 완료 | 다름 | Consumer Group Offset은 Group별로 독립적이다. MyPage Group이 Offset을 Commit했어도 Notification Group은 다른 Offset 진행 상황을 가진다. 또한 Offset Commit이 비즈니스 처리 완료를 보장하지 않는다 |
| Outbox `PUBLISHED` vs 모든 Consumer 완료 | 다름 | PUBLISHED는 Outbox Publisher가 Kafka에 발행하고 ACK를 받은 상태다. 각 Consumer Group이 이 이벤트를 소비하고 비즈니스 처리까지 완료했는지는 Publisher가 알 수 없다 |

## 과제 7. 이벤트 순서와 버전 처리하기

### 1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다

```
같은 Topic이어야 하는가?
그렇다. 같은 Partition Key를 사용해도 Topic이 다르면 다른 Partition에 저장되어 순서가 보장되지 않는다.
같은 Topic 내에서 같은 Key를 가진 메시지만 같은 Partition에 배치된다.

같은 Key가 보장하는 범위:
같은 Topic, 같은 Partition Key를 가진 메시지들은 Producer가 발행한 순서대로 같은 Partition에 저장된다.
Consumer는 이 Partition 내에서 Offset 순서대로 메시지를 수신한다.

전역 순서를 보장하는가?
아니다. 전역 순서(모든 Partition에 걸친 순서)는 보장되지 않는다.
서로 다른 Key를 가진 메시지는 다른 Partition에 저장되며 전체적인 발생 순서가 보장되지 않는다.

서로 다른 Topic 사이의 순서를 보장하는가?
아니다. Topic 간 순서는 Kafka가 보장하지 않는다. Topic이 다르면 완전히 독립적인 스트림이다.
```

### 2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다

```
DB 발생 순서:
1. CouponIssued (aggregateVersion=1) → outbox_event INSERT
2. CouponCancelled (aggregateVersion=2) → outbox_event INSERT

Publisher 처리 순서:
Publisher A: CouponIssued(version=1) Claim → Kafka 발행 시도 → 실패 → Backoff 대기 중
Publisher B: CouponCancelled(version=2) FOR UPDATE SKIP LOCKED으로 별도 Claim
             (version=1은 잠겨 있어 SKIP, version=2 선택)
             → Kafka 발행 성공 → PUBLISHED

Publisher A: Backoff 만료 후 재시도 → CouponIssued(version=1) 발행 성공 → PUBLISHED

Kafka 저장 순서:
Partition X:
  Offset N   : CouponCancelled (aggregateVersion=2)
  Offset N+1 : CouponIssued (aggregateVersion=1)
  ← 비즈니스 발생 순서(1 → 2)와 반대로 저장됨
```

### 3. `schemaVersion`과 `aggregateVersion`을 비교한다

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| `schemaVersion` | 이벤트 Payload 구조(스키마)의 버전 | Consumer가 이벤트를 역직렬화할 때 어떤 구조로 파싱해야 하는지 알 수 있다. 하위 호환성 없는 스키마 변경 시 Consumer가 잘못 파싱하는 것을 방지한다 | CouponIssued에 `discountAmount` 필드가 추가돼 기존 Consumer가 파싱할 수 없게 되면 schemaVersion을 1에서 2로 올린다 |
| `aggregateVersion` | 특정 Aggregate 인스턴스의 상태 변경 순번 | 같은 Aggregate에서 여러 이벤트가 발생할 때 Consumer가 이벤트의 논리적 발생 순서를 알 수 있다. 순서 역전 방어에 활용된다 | couponIssueId=5001에서 쿠폰 발급(version=1) 후 취소(version=2)가 발생하면 aggregateVersion이 1 → 2로 증가한다 |

### 4. 최신 상태 Projection의 UPSERT를 완성한다

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET
    status            = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at        = EXCLUDED.updated_at
WHERE
    user_coupon_view.aggregate_version < EXCLUDED.aggregate_version;
```

### 5. Version 2가 먼저 도착한 경우를 분석한다

```
먼저 처리: CouponCancelled(version=2)
→ user_coupon_view에 status=CANCELLED, aggregate_version=2 저장됨

나중 처리: CouponIssued(version=1)
→ ON CONFLICT DO UPDATE WHERE user_coupon_view.aggregate_version < 1
→ 현재 aggregate_version=2이므로 2 < 1이 false
→ UPDATE 실행되지 않음 (0행)

최종 MyPage status: CANCELLED

최종 aggregate_version: 2

version=1 UPSERT의 affected rows: 0 (WHERE 조건 불만족으로 UPDATE 건너뜀)
낮은 버전이 최신 상태를 덮어쓰지 않으므로 올바른 동작.
```

### 6. 낮은 Version을 생략할 수 있는 범위를 판단한다

| Consumer | 낮은 Version 생략 가능 여부 | 필요한 전제 또는 추가 순서 정책 |
| --- | --- | --- |
| 완전한 최신 상태만 저장하는 MyPage | 가능하다 | 높은 Version이 이미 반영된 상태에서 낮은 Version이 도착해도 WHERE aggregate_version < EXCLUDED.aggregate_version 조건으로 자동 건너뛴다. 최종 상태의 정확성이 보장된다 |
| 모든 발급·취소를 집계하는 Analytics | 불가능하다 | 모든 이벤트를 빠짐없이 Fact에 기록해야 정확한 집계가 된다. 낮은 Version 이벤트를 생략하면 해당 발급 또는 취소 건이 통계에서 누락된다. 순서와 무관하게 모든 이벤트를 처리해야 한다 |
| 발급·취소 알림을 각각 보내는 Notification | 불가능하다 | 발급 알림과 취소 알림은 각각 독립적인 사실에 대한 알림이다. 낮은 Version을 생략하면 해당 알림이 누락된다. 단, processed_event 기반 중복 알림 방지와 함께 처리해야 한다 |

### 7. Version Gap 처리 정책을 작성한다

```
Gap으로 판단하는 조건:
현재 처리 중인 이벤트의 aggregateVersion이 마지막으로 처리한 aggregateVersion보다 2 이상 크면 Gap으로 판단한다.
예: 마지막 처리 version=2인데 version=4가 도착하면 version=3이 유실된 것으로 의심한다.

즉시 반영해도 되는 Consumer:
최신 상태만 저장하는 MyPage Projection. version=4가 version=3보다 최신이므로
version=3 없이 바로 반영해도 최종 상태는 정확하다.

모든 전이가 필요한 Consumer의 처리:
Analytics나 Notification처럼 모든 이벤트를 처리해야 하는 Consumer는
Gap을 감지하면 해당 이벤트를 Retry Topic 또는 대기 버퍼에 보관하고 누락된 Version을 기다린다.
일정 시간(예: 30초) 내에 도착하지 않으면 Gap을 경고 로그로 남기고 현재 이벤트를 처리한다.

복구 방법:
누락된 Version의 이벤트를 Outbox Publisher가 재발행할 수 있는지 확인한다.
outbox_event에서 해당 aggregateVersion 행이 PENDING이나 PROCESSING에 머물러 있는지 조회한다.
이미 PUBLISHED라면 Kafka Topic에 Record가 있지만 Consumer가 건너뛴 것이므로 Offset을 해당 위치로 되감아 재처리한다.
```

### 8. 이벤트 스키마 변경의 호환성을 판단한다

| 변경 | 호환 가능성 | 이유와 배포 방법 |
| --- | --- | --- |
| 선택 필드 `couponDisplayName` 추가 | 하위 호환 가능하다 | 기존 Consumer는 새 필드를 무시하고 동작한다. Consumer를 먼저 배포해 새 필드를 처리할 수 있게 한 뒤 Producer를 배포한다 |
| 기존 `userId` 필드 삭제 | 하위 호환 불가능하다 | 기존 Consumer가 `userId` 필드를 사용하고 있으면 NPE 또는 파싱 오류가 발생한다. schemaVersion을 올리고 모든 Consumer를 먼저 새 버전으로 업데이트한 후 Producer를 변경해야 한다 |
| `userId` 의미를 이메일 주소로 변경 | 하위 호환 불가능하다 | 필드명은 같지만 의미와 포맷이 달라 기존 Consumer가 숫자 ID로 처리하면 오류가 발생한다. 필드 삭제와 동일하게 schemaVersion을 올려 명시적으로 구분해야 한다 |
| 호환되지 않는 새 Payload를 같은 `schemaVersion=1`로 발행 | 호환 불가능하다(설계 오류) | Consumer는 schemaVersion=1을 보고 기존 구조로 파싱하려 하지만 실제 구조가 다르므로 조용히 잘못된 데이터를 처리하거나 역직렬화 오류가 발생한다. schemaVersion은 반드시 올려야 한다 |
| 불필요한 전화번호와 비밀번호를 이벤트에 추가 | 기술적으로 가능하지만 허용하면 안 된다 | 이벤트는 Kafka에 저장되어 여러 Consumer가 읽고 로그에 남을 수 있다. 민감 개인정보를 이벤트에 포함하면 개인정보보호법 위반 위험이 있고 보안 사고 시 피해가 크다. 반드시 제거해야 한다 |

| 데이터 | Source of Truth인가? | 삭제 후 재구축 가능한가? | 재구축 근거 |
| --- | --- | --- | --- |
| Coupon Service `coupon_issue` | 그렇다 | 재구축 불가능하다. 이 데이터 자체가 원본 | 다른 데이터에서 복원할 수 없다. 백업에서만 복구 가능 |
| MyPage `user_coupon_view` | 아니다 | 가능하다 | Coupon Service coupon_issue DB Snapshot Backfill 또는 Kafka coupon.issued Topic Replay |
| Analytics `coupon_issue_fact` | 아니다 | 가능하다 | Kafka coupon.issued Topic Replay 또는 Coupon Service coupon_issue Snapshot |
| Analytics `coupon_issue_stats` | 아니다 | 가능하다 | coupon_issue_fact에서 GROUP BY coupon_event_id COUNT(*)로 재집계 가능 |

### 2. `user_coupon_view_v2` 재구축 순서를 작성한다

```
1. 새 Projection 테이블 생성 (user_coupon_view_v2)
   목적: 기존 user_coupon_view를 유지하면서 새 구조로 병행 구축. 서비스 중단 없이 마이그레이션 준비.

2. 원본 DB Snapshot Backfill 시작 지점 기록
   목적: Backfill 시작 시각이나 coupon_issue의 마지막 처리 ID를 기록해 이후 새로 들어오는 이벤트와 경계를 구분할 기준을 확보.

3. 원본 DB Snapshot Backfill
   목적: Coupon Service coupon_issue 테이블을 읽어 Backfill 시작 시점까지의 발급 이력을 user_coupon_view_v2에 대량 삽입. Kafka 보관 기간 이전 데이터까지 복구.

4. 새 Consumer Group으로 Kafka Replay (Backfill 경계 이후 이벤트 Catch-up)
   목적: Backfill 시작 시점 이후 발생한 CouponIssued 이벤트를 새 Consumer Group(mypage-coupon-projection-v2)으로 소비해 user_coupon_view_v2에 반영. 멱등 처리로 Backfill 데이터와 중복 없이 병합.

5. 원본 user_coupon_view와 v2 정합성 검증
   목적: 두 테이블의 행 수, 샘플 데이터 비교, coupon_issue_id 기준 diff를 통해 누락이나 불일치가 없는지 확인.

6. 조회 API 전환
   목적: GET /api/users/{userId}/coupons가 user_coupon_view_v2를 조회하도록 코드·설정 변경. 순차 배포로 트래픽을 점진적으로 전환.

7. 기존 Projection 보관 또는 제거
   목적: 일정 기간 기존 user_coupon_view를 유지해 롤백 가능성을 보존. 정합성이 충분히 확인되면 스토리지 절약을 위해 제거.
```

### 3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다

```
Kafka만으로 전체 Replay가 가능한가?
아니다. Kafka Topic의 보관 기간(retention)이 지난 Record는 Kafka에서 삭제된다.
이 기간 이전의 이벤트는 Replay할 수 없다.

필요한 다른 복구 기준:
Coupon Service의 coupon_issue 테이블. 발급 원장 DB에서 Snapshot을 읽어 Backfill한다.
이 방법으로 Kafka retention 이전 데이터까지 복구할 수 있다.

Backfill 중 새 이벤트가 들어올 때 필요한 경계:
Backfill 시작 시각 또는 마지막 처리 coupon_issue_id를 기록한다.
Backfill로 처리하는 범위(시작~경계 이전)와 Kafka Replay로 처리하는 범위(경계 이후)를 명확히 나눈다.
경계 전후 데이터가 양쪽에서 모두 쓰일 수 있으므로 ON CONFLICT DO NOTHING 또는 UPSERT로 중복을 안전하게 처리한다.
```

### 4. 운영 지표를 완성한다

| 지표 | 의미 | 장애 신호 예시 |
| --- | --- | --- |
| Group별 Consumer Lag | 각 Consumer Group이 현재 처리하지 못하고 쌓인 미처리 Record 수 | Lag이 지속 증가 → Consumer 처리 속도가 생성 속도를 따라가지 못함. Consumer 장애 또는 처리량 부족 |
| Oldest Unprocessed Age | 가장 오래된 미처리 이벤트가 Kafka에 저장된 후 얼마나 지났는지 | SLA(예: 10초) 초과 → Consumer가 장시간 특정 이벤트를 처리하지 못하고 있음. 처리 오류 또는 재시도 루프 의심 |
| Projection Delay | 이벤트 occurredAt부터 Read Model이 Commit될 때까지 걸린 시간 | P99가 목표치 초과 → 사용자가 발급 직후 마이페이지에서 쿠폰을 볼 수 없는 시간이 길어짐 |
| Handler Failure Count | Consumer 처리 중 발생한 예외 건수 | 급증 → DB 오류, 역직렬화 실패, 의존 서비스 장애 가능성 |
| Duplicate Event Count | 같은 eventMessageId가 두 번 이상 처리된 건수 | 0보다 크면 재발행 또는 Consumer 재시작 발생. 멱등 처리가 제대로 동작하는지 확인 필요 |
| Read Model Mismatch Count | Source of Truth(coupon_issue)와 Read Model(user_coupon_view) 불일치 건수 | 0보다 크면 이벤트 유실 또는 멱등 처리 버그 가능성. 재구축 또는 Consumer 점검 필요 |

### 5. 다음 장애 상황에서 확인할 지표를 선택한다

```
가장 먼저 확인할 Consumer Group:
mypage-coupon-projection (MyPage Consumer Group)

확인할 지표:
1. Consumer Group Lag: 현재 미처리 이벤트 수와 증가 추이.
2. Oldest Unprocessed Age: 가장 오래된 미처리 이벤트 대기 시간. 10분 전 발급이면 해당 이벤트가 10분 이상 처리되지 않았을 가능성.
3. Handler Failure Count: 처리 중 오류 발생 여부. DB 오류나 역직렬화 실패로 처리가 막혔는지 확인.
4. Projection Delay P99: 평균 반영 지연 시간.

로그에서 연결할 식별자:
eventMessageId, requestId, couponIssueId, userId.
이 식별자로 Coupon Service 발급 로그 → Outbox Publisher 발행 로그 → MyPage Consumer 처리 로그를 연결해 어느 단계에서 지연이 발생했는지 추적한다.

Coupon Service 발급을 다시 실행해도 되는가?
아니다. 10분 전 쿠폰은 Coupon Service DB에 이미 ISSUED로 발급 완료됐다.
마이페이지에 보이지 않는 것은 MyPage Consumer 지연 문제이지 발급 자체의 문제가 아니다.
발급을 다시 실행하면 UNIQUE(event_id, user_id) 위반 또는 중복 발급이 발생한다.
```

### 6. 로그에 남길 상관관계 ID를 작성한다

```
1. requestId
   추적 범위: 사용자의 쿠폰 발급 요청부터 coupon_issue_request 상태 전이 전 과정. 클라이언트 요청과 서버 처리를 연결.

2. eventMessageId
   추적 범위: CouponIssued 이벤트가 Outbox에 저장된 시점부터 모든 Consumer가 처리할 때까지의 전 구간. 이벤트 재발행 시에도 동일한 ID로 추적 가능.

3. couponIssueId
   추적 범위: 특정 쿠폰 발급 건과 관련된 모든 이벤트, DB 변경, Consumer 처리를 하나의 발급 건 단위로 묶어 추적.

4. userId
   추적 범위: 특정 사용자와 관련된 모든 발급, 알림, 마이페이지 갱신, 통계 기록을 연결해 사용자 관점의 전체 흐름 추적.

5. traceId (분산 트레이싱 ID)
   추적 범위: Coupon Service → Outbox Publisher → Kafka → 각 Consumer Service에 걸쳐 하나의 요청 흐름을 분산 트레이싱 시스템(Jaeger, Zipkin 등)으로 단일 트레이스로 연결.
```

### 2. 반드시 찾아야 하는 문제를 연결한다

| 검토 항목 | 문제가 있는 코드 | 수정 방향 |
| --- | --- | --- |
| 세 서비스가 같은 Group ID 사용 | 세 @KafkaListener 모두 `groupId = "coupon-result"` | 서비스별로 notification-coupon-issued, mypage-coupon-projection, analytics-coupon-issued로 분리 |

| 서비스별 데이터 소유권 불명확 | 세 Consumer가 같은 Group에서 같은 이벤트를 나누어 처리함으로써 누가 어떤 데이터를 책임지는지 불명확 | Group 분리로 각 서비스가 독립적으로 자신의 DB만 변경하고 각자의 소유 데이터를 책임지도록 구조 변경 |

### 3. 수정된 전체 구조를 그린다

```
Kafka coupon.issued Topic
  |
  |--[notification-coupon-issued Group]---> Notification Consumer
  |                                             |
  |                                    BEGIN Transaction
  |                                    INSERT processed_event ON CONFLICT DO NOTHING
  |                                    INSERT notification_job (status=PENDING)
  |                                    COMMIT → acknowledgment.acknowledge()
  |                                             |
  |                                             v
  |                                    Notification Sender
  |                                    notification_job PENDING 폴링
  |                                    외부 Provider API 호출 (notificationId 사용)
  |                                    notification_job → SENT/FAILED
  |
  |--[mypage-coupon-projection Group]---> MyPage Consumer
  |                                             |
  |                                    BEGIN Transaction
  |                                    WITH accepted AS (
  |                                      INSERT processed_event ON CONFLICT DO NOTHING RETURNING
  |                                    )
  |                                    UPSERT user_coupon_view
  |                                      WHERE aggregate_version < EXCLUDED.aggregate_version
  |                                    FROM accepted (최초 이벤트만)
  |                                    COMMIT → acknowledgment.acknowledge()
  |
  +--[analytics-coupon-issued Group]---> Analytics Consumer
                                               |
                                      BEGIN Transaction
                                      WITH accepted AS (
                                        INSERT coupon_issue_fact ON CONFLICT DO NOTHING RETURNING
                                      )
                                      UPDATE coupon_issue_stats SET issued_count = issued_count + 1
                                        WHERE coupon_event_id = :id AND EXISTS (SELECT 1 FROM accepted)
                                      COMMIT → acknowledgment.acknowledge()
```

### 4. 수정된 구조의 보장 수준을 판단한다

| 항목 | 보장/조건부 보장/보장하지 않음 | 이유 |
| --- | --- | --- |
| 쿠폰 발급 DB의 최종 성공 | 보장 | Coupon Service의 DB 트랜잭션 Commit이 최종 원장이다. 이후 Consumer 처리와 독립적으로 보장된다 |
| 세 Group이 각자 이벤트를 소비할 기회 | 보장 | Group이 분리되어 각 Group이 독립적으로 모든 Partition의 이벤트를 소비한다 |
| Kafka Record의 물리적 Exactly-Once | 보장하지 않음 | Outbox Publisher 재발행으로 같은 eventMessageId의 Record가 두 개 생길 수 있다 |
| MyPage 중복 반영 방지 | 보장 | processed_event ON CONFLICT DO NOTHING과 UPSERT aggregateVersion 조건으로 중복 반영을 방지한다 |
| Analytics 중복 집계 방지 | 보장 | coupon_issue_fact PK ON CONFLICT DO NOTHING으로 Fact 중복을 막고, INSERT 성공 시에만 집계를 증가시킨다 |
| 외부 SMS Exactly-Once | 보장하지 않음 | 외부 Provider가 DB 트랜잭션 참여자가 아니므로 Dual Write 문제가 남는다. Provider Idempotency Key 지원 여부에 따라 조건부로 중복을 줄일 수 있다 |
| 발급 직후 MyPage의 즉시 일치 | 보장하지 않음 | Consumer Lag으로 인해 발급 직후 수 초~수십 초의 지연이 발생한다. 최종적 일관성만 보장한다 |

1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?

같은 Group의 Consumer는 Partition을 나누어 처리하므로 한 이벤트를 하나의 Consumer만 처리한다.
세 서비스가 같은 Group이면 이벤트가 세 서비스 중 하나에만 전달되어 나머지 작업이 누락된다.


2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?

DB 트랜잭션 Commit 이후 생성되므로 되돌릴 수 없는 확정된 사실이며,
Consumer는 이 사실에 반응할 뿐 발급을 다시 실행하거나 거절하지 않기 때문이다.


3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?

Coupon Service의 coupon_issue 테이블. MyPage Read Model은 파생 Projection이므로 발급 원장이 아니다.


4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?

Outbox Publisher가 재발행하면 같은 논리 이벤트가 Kafka의 새 위치(다른 Offset)에 Record로 저장되기 때문이다.


5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?

둘 중 하나만 성공하면 중복 처리 또는 영구 누락이 발생하므로 원자적으로 처리해야 하기 때문이다.


6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?

Kafka 발행, Consumer Lag, Consumer 처리 등 여러 비동기 단계를 거치면서 user_coupon_view 갱신에 지연이 생기기 때문이다.


7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?

aggregateVersion은 발생 순번을 나타내는 값일 뿐이며, Kafka에 발행되는 순서는 Publisher 처리 타이밍과 재시도에 따라 달라지기 때문이다.


8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?

Analytics와 Notification처럼 모든 이벤트를 처리해야 하는 Consumer는 낮은 Version 이벤트도 실제로 발생한 사실이므로 집계와 알림에 포함해야 하기 때문이다.


9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?

Read Model은 파생 데이터이므로 버그, 스키마 변경, 장애 등으로 불일치가 생겼을 때 원본에서 다시 만들어 복구할 수 있어야 하기 때문이다.


10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?

쿠폰 발급은 이미 Coupon Service DB에 Commit된 확정된 사실이므로 재실행하면 중복 발급이 발생하기 때문이다.
알림 누락은 Notification Consumer 재시작과 Kafka Offset 재처리로 해결해야 한다.
