### **1. 직접 호출 구조의 결합을 분석한다**

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 호출 시점에 상대 서비스가 반드시 실행 중이어야 한다. | 각 서비스에 해당하는Consumer가 각자 준비된 시점에 이벤트를 소비한다. |
| 장애 결합 | 상대 서비스의 지연과 장애가 호출자에게 전파된다. | 한 Consumer의 실패가 다른 서비스로 이어지지 않는다. |
| 변경 결합 | 후속 서비스 추가/변경 시 발급 코드가 변경된다. | Producer가 후속 서비스 Consumer의 수와 구현을 몰라도 된다. |
| 데이터 결합 | 다른 서비스의 테이블이나 내부 모델에 직접 의존하기 쉬워진다. | 각 서비스는 자기 DB만 변경한다. |

### **2. 다음 장애 상황을 분석한다**

```
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```
이미 확정된 쿠폰 발급 상태:
DB 트랜잭션이 Commit된 시점에 쿠폰 발급은 최종 성공이다.

쿠폰 발급을 Rollback하면 안 되는 이유:
알림 발송은 발급 과정에서 필요한 것이 아니라 발급 결과를 소비하는 후속 작업이다. 알림 실패를 이유로 발급을 되돌리면 수량 한정 쿠폰의 재고와 사용자별 중복 발급 판정이 흔들리게 된다.

다시 실행해야 하는 작업:
실패한 알림 작업만 재시도한다.

다시 실행하면 안 되는 작업:
쿠폰 발급 작업
```

```
직접 API 계약 대신 남는 계약:
이벤트 스키마 계약

이 계약을 관리해야 하는 이유:
이벤트는 여러 Consumer가 동시에 의존하는 공용 계약이고 각 Consumer는 독립적으로 배포되므로, Producer가 필드를 삭제하거나 의미를 바꾸면 Consumer가 그에 맞춰 대응할 수 없어 파싱이 실패하거나 잘못된 값이 Read Model에 쌓인다. 따라서 기존 필드는 임의로 바꾸지 않고 새 필드는 선택 필드로 추가하며, 호환되지 않는 변경은 새 schemaVersion이나 새 이벤트 타입으로 분리해 관리해야 한다.

EDA가 반드시 MSA를 의미하지 않는 이유:
EDA는 서비스 간 통신 방식에 대한 선택이고 MSA는 배포와 실행 단위에 대한 선택이라 서로 다르다. 하나의 애플리케이션 안에서도 모듈과 Consumer 책임을 나누고 서로 다른 Group ID로 같은 이벤트를 독립 소비하면 EDA의 핵심인 시간 결합과 장애 결합 완화를 확보할 수 있다.
```

## **과제 2. Consumer Group과 서비스 책임 설계하기**

### **1. 서비스별 Consumer Group을 작성한다**

| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | notification-coupon-issued | processed_event와 notification_job을 같은 트랜잭션으로 저장해 발송할 알림 작업을 확정한다. |
| MyPage | mypage-coupon-projection | processed_event와 user_coupon_view를 같은 트랜잭션으로 변경해 사용자별 쿠폰 조회 모델을 갱신한다. |
| Analytics | analytics-coupon-issued | processed_event와 coupon_issue_fact를 같은 트랜잭션으로 저장하고, Fact가 실제 INSERT된 경우에만 coupon_issue_stats의 발급 수를 증가시킨다. |

### **2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다**

```
같은 Group 안의 Consumer 관계:
Group 내부에서는 한 Partition이 한 시점에 한 인스턴스에만 할당되므로, 같은 Group의 Consumer들은 Record를 나누어 처리하는 경쟁 관계가 된다.

CouponIssued 한 건의 전달 결과:
세 서비스가 같은 Group ID를 사용하므로, 해당 이벤트가 저장된 Partition을 할당받은 인스턴스 하나에만 전달되어 세 작업 중 하나만 실행된다.

세 서비스 중 일부 작업이 누락될 수 있는 이유:
Partition을 할당받지 못한 인스턴스에는 Record가 전달되지 않아 해당 서비스의 작업이 실행되지 않는다. 그 결과 어떤 발급 건은 알림만 나가고 마이페이지에는 반영되지 않으며, 통계는 전체 발급의 일부만 집계된다.
```

```
mypage-coupon-projection Consumer 수: 4
```

| --- | --- | --- | --- |

### **4. Consumer Group의 Committed Offset 의미를 설명한다**

```
Committed Offset이 나타내는 것:
해당 Group이 그 Topic-Partition에서 처리를 완료했다고 선언한 위치다.

Committed Offset만으로 증명할 수 없는 것:
Offset은 그 Group이 어디까지 읽었는지를 나타낼 뿐, 각 Record가 실제로 어떤 결과를 만들었는지는 증명하지 못한다. DB Commit 이후 오류로 종료되면 DB 반영이 끝난 이벤트인데도 Offset이 진행되지 않아 재전달된다. 또한 Offset은 물리적 위치라 같은 논리 이벤트가 재발행되어 다른 Offset으로 저장되면 이미 처리한 것인지 구분하지 못하며, 그 판단은 eventMessageId 기반 processed_event가 담당한다. 외부 SMS 발송처럼 로컬 트랜잭션 밖에서 일어난 작업의 성공 여부도 알 수 없다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
Offset은 Group별로 독립 관리되므로 영향을 주지 않는다.
```

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 상태 변경을 처리하고 비즈니스 불변식을 보장한다. | 화면과 업무 목적에 맞는 형태로 빠르게 응답한다. |
| 대표 작업 | 쿠폰 발급 요청 처리, coupon_issue 저장과 요청 상태 전이, CouponIssued Outbox 저장 | 마이페이지 보유 쿠폰 목록 조회(GET /api/users/{userId}/coupons), 운영자용 발급 통계 조회 |
| 데이터 구조 | 정확한 쓰기와 제약 검사에 적합하게 설계한다. | 조회 패턴에 맞춰 비정규화할 수 있다. 화면에 필요한 값을 미리 모아 두고 (user_id, issued_at DESC)처럼 조회 전용 인덱스를 둔다. |
| 최종 원장 여부 | o | x |
| 장애 후 재구축 가능 여부 | x | o(원장 Snapshot Backfill, 보관 중인 이벤트를 새 Consumer Group으로 Replay) |

### **2. CQRS에 대해 다음 문장을 판단한다**

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 같은 DB 안에서 coupon_issue와 user_coupon_view를 두고 Command 경로와 Query 경로를 나누어도 CQRS는 성립한다. |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 변경 모델과 조회 모델을 분리하는 방식이고, Event Sourcing은 상태 대신 이벤트의 나열을 저장해 현재 상태를 계산해내는 저장 방식이다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 하나의 Spring 애플리케이션 안에서 발급 처리 경로와 마이페이지 조회 경로를 나누고, MyPage Consumer가 CouponIssued를 받아 user_coupon_view를 만들면 CQRS의 이점인 조회 단순화와 장애 격리를 확보할 수 있다. |

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001
```

### **1. Offset과 eventMessageId를 비교한다**

| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka Log에 저장된 Record의 물리적 위치 | o | x |
| eventMessageId | 논리 이벤트 한 건 | x | o |

### **2. `processed_event` DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

다음 세 값 중 올바른 `subscriber_id`를 고르고 이유를 작성한다.

```
pod-a7f9c
server-10.0.0.12
mypage-coupon-projection
```

```
선택:
mypage-coupon-projection

이유:
processed_event는 물리적인 실행 주체가 아니라 논리적인 구독 단위가 무엇을 이미 반영했는지를 기록하는 테이블이다. MyPage Consumer가 여러 인스턴스로 떠 있어도 user_coupon_view는 하나이므로, 어느 인스턴스가 처리했든 그 발급 건은 이미 반영된 것으로 판단해야 한다. 따라서 식별자는 Consumer Group 단위의 안정적인 이름이어야 한다.
위의 두 값과 달리 mypage-coupon-projection은 Consumer Group ID와 일치하는 논리 구독자 이름으로 인스턴스 수나 배포 환경이 바뀌어도 값이 유지되기 때문에 적절하다.
```

### **3. MyPage Consumer 트랜잭션을 완성한다**

다음 요구사항을 만족해야 한다.

```
ON CONFLICT DO NOTHING으로 최초 처리 권한 등록
RETURNING 결과로 최초·중복 판별
최초 이벤트일 때만 user_coupon_view 변경
processed_event와 조회 모델 변경의 원자성
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (
        subscriber_id,
        event_message_id
    ) VALUES (
        'mypage-coupon-projection',
        :eventMessageId
    )
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    aggregate_version,
    issued_at,
    updated_at
)
SELECT
    :couponIssueId,
    :userId,
    :couponEventId,
    :status,
    :aggregateVersion,
    :issuedAt,
    CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```
PostgreSQL은 트랜잭션 안에서 오류가 나면 그 트랜잭션을 aborted 상태로 만든다. 이후 명령은 모두 거부되므로 애플리케이션에서 PK 중복 예외를 잡고 계속 진행해도 user_coupon_view INSERT가 실행되지 않고 트랜잭션 전체가 Rollback된다. 예외를 잡았다는 것은 코드 흐름이 이어진다는 뜻일 뿐 트랜잭션이 정상 상태로 돌아온 것은 아니다. 그래서 예외를 발생시키지 않는 INSERT ... ON CONFLICT DO NOTHING RETURNING을 사용해 반환 행의 유무로 최초 처리 여부를 판단한다.
```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```
재전달 시 Consumer 판단:
processed_event에 해당 (subscriber_id, event_message_id) 행이 남아 있으므로 INSERT가 충돌해 RETURNING이 0행을 반환하고, 이미 처리한 이벤트로 판단해 아무 변경 없이 정상 종료한다.

최종 조회 모델 상태:
user_coupon_view에 해당 발급 건이 영원히 반영되지 않는다. 원장에는 ISSUED로 남아 있고 요청 상태 API도 성공을 반환하는데 마이페이지 쿠폰함에만 쿠폰이 보이지 않으며, 재전달로는 복구되지 않아 Backfill이나 Replay가 필요하다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
처리 기록과 실제 반영이 함께 Commit되거나 함께 Rollback되어야 둘이 어긋나지 않기 때문이다.
```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```
Consumer DB 상태:
processed_event와 user_coupon_view 변경이 하나의 트랜잭션으로 Commit되어 있다.

Consumer Group Offset:
Offset Commit 전에 종료되었으므로 Committed Offset은 해당 Record 이전 위치에 머물러 있다.

재시작 후 전달:
재시작 후 인스턴스가 Partition을 할당받으면 Committed Offset부터 다시 읽으므로 같은 Record가 같은 Offset과 같은 eventMessageId로 재전달된다.

재전달된 이벤트 처리:
processed_event INSERT가 충돌해 RETURNING이 0행을 반환하므로 조회 모델을 변경하지 않고 정상 종료한 뒤 Offset을 완료한다.
```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record
```

```
enable.auto.commit은 false로 두고 수동 Commit을 사용한다. 자동 Commit은 DB 반영 여부와 무관하게 Offset을 진행시켜 이벤트가 누락될 수 있다.

순서는 DB Commit 후 Offset 완료다. 반대로 하면 반영 없이 이벤트가 사라져 복구할 수 없으므로, 누락 대신 중복을 택하고 중복은 eventMessageId로 막는다.

Listener에서 예외가 나면 Offset을 완료하지 않고 재시도 대상으로 남긴다.

같은 Partition을 병렬 처리한다면 앞선 미완료 Record를 건너뛰고 더 높은 Offset을 Commit하지 않는다.
```

### **3. 외부 Provider가 Idempotency Key를 지원하지 않는 경우의 보장 수준을 작성한다**

```
외부 알림 전송 보장 수준:
At-Least-Once에 가깝다. 발송 후 응답을 받기 전에 종료되면 실제로 보냈는지 알 수 없는데, 재시도하지 않으면 알림이 누락되므로 재시도를 택하게 되고 그 결과 중복 발송 가능성이 남는다.

중복 전송 가능성을 완전히 제거할 수 있는가?
없다. 외부 호출은 로컬 트랜잭션에 포함할 수 없고, Provider가 멱등 키를 지원하지 않으면 같은 요청을 걸러낼 주체가 없다.

운영에서 추가로 필요한 장치:
notification_job 상태를 두고 실패한 작업만 재시도하되 재시도 횟수를 제한하며, 중복 발송 건수와 처리 실패 건수를 모니터링한다.
```

### **4. 다음 Analytics 구현의 문제를 설명한다**

```sql
UPDATE coupon_issue_stats

```

같은 `eventMessageId`가 두 번 전달되었을 때의 결과를 작성한다.

```
단순히 값을 1 증가시키는 연산이라 두 번 실행되어도 문법적으로 정상이고 위반할 제약이 없다. 이때 같은 eventMessageId가 두 번 전달되면 실제 발급은 한 건인데 issued_count는 2가 되어 통계가 이중 집계된다.
```

### **5. `coupon_issue_fact` 기반 집계 구조를 설계한다**

다음 요구사항을 만족해야 한다.

```
coupon_issue_id 중복 저장 방지
event_message_id 추적
coupon_event_id와 user_id 저장
발급 발생 시각 저장
Fact가 실제 INSERT된 경우에만 집계 +1
Fact INSERT와 집계 변경을 같은 트랜잭션으로 처리
```

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```sql
BEGIN;

WITH accepted AS (
	INSERT INTO coupon_issue_fact (
        coupon_issue_id,
        event_message_id,
        coupon_event_id,
        user_id,
        issued_at
    ) VALUES (
        :couponIssueId,
        :eventMessageId,
        :couponEventId,
        :userId,
        :issuedAt
    )
    ON CONFLICT DO NOTHING
    RETURNING coupon_issue_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId
  AND EXISTS (
			SELECT 1 FROM accepted
  );

COMMIT;
```

## **과제 7. 이벤트 순서와 버전 처리하기**

다음 두 이벤트가 같은 `couponIssueId = 5001`에서 발생했다고 가정한다.

```
CouponIssued
aggregateVersion = 1
status = ISSUED

CouponCancelled
aggregateVersion = 2
status = CANCELLED
```

### **1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다**

```
같은 Topic이어야 하는가?
Kafka의 순서 보장 단위는 같은 Topic의 같은 Partition이므로, 순서를 지켜야 하는 CouponIssued와 CouponCancelled는 같은 Topic에 두어야 한다.

같은 Key가 보장하는 범위:
같은 couponIssueId를 Key로 갖는 Record는 같은 Partition에 기록되어 그 Partition 안에서 저장 순서가 유지된다.

전역 순서를 보장하는가?
서로 다른 Key는 다른 Partition에 배정되므로 5001번과 5002번 발급 건 사이의 순서는 알 수 없다. Kafka가 보장하는 것은 Partition 내부의 순서뿐이다.

서로 다른 Topic 사이의 순서를 보장하는가?
보장하지 않는다. Key가 같아도 Topic이 다르면 별개의 Partition에 저장되므로 두 Topic 사이의 순서는 알 수 없다.
```

### **2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다**

다음을 포함한다.

```
여러 Publisher
SKIP LOCKED
version 1 발행 실패
Backoff
version 2 선행 발행
```

```
DB 발생 순서:
version=1가 먼저 Outbox에 저장되고, 이후 version=2가 저장된다.

Publisher 처리 순서:
version 1 발행이 실패해 Backoff 후 재시도로 밀리는 동안, version 2를 정상적으로 발행한다.

Kafka 저장 순서:
version=2가 먼저 저장되고, Backoff가 끝난 뒤 version=1이 나중에 저장된다.
```

### **3. `schemaVersion`과 `aggregateVersion`을 비교한다**

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| `schemaVersion` | JSON 필드 구조의 버전 | Producer와 Consumer가 독립적으로 배포되는 상황에서 Payload 구조가 바뀌었을 때 Consumer가 파싱 방식을 구분할 수 있게 한다. 호환되지 않는 변경으로부터 기존 Consumer를 보호하는 계약 관리 수단이다. | userId 필드를 삭제하고 memberUuid로 대체하는 등 기존 Consumer가 깨지는 변경을 배포할 때 1에서 2로 올린다. 선택 필드 추가처럼 호환되는 변경은 올리지 않아도 된다. |
| `aggregateVersion` | 한 CouponIssue에서 발생한 비즈니스 변경 순서 | 이벤트 순서가 역전되어 도착했을 때 오래된 상태가 최신 상태를 덮어쓰는 것을 막는다. | 5001번 발급 건에 CouponIssued가 1로 발행되고 이후 CouponCancelled가 2로 발행된다. 5002번 발급 건은 자신의 1부터 다시 시작한다. |

### **4. 최신 상태 Projection의 UPSERT를 완성한다**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET
		status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = CURRENT_TIMESTAMP
WHERE
	user_coupon_view.aggregate_version < EXCLUDED.aggregate_version
;
```

### **6. 낮은 Version을 생략할 수 있는 범위를 판단한다**

| Consumer | 낮은 Version 생략 가능 여부 | 필요한 전제 또는 추가 순서 정책 |
| --- | --- | --- |
| 완전한 최신 상태만 저장하는 MyPage | o | 이벤트마다 현재 상태 전체가 담겨 있어 중간 전이를 거치지 않아도 최신 값만으로 화면을 그릴 수 있어야 한다. |
| 모든 발급·취소를 집계하는 Analytics | x | 발급 수와 취소 수를 각각 세야 하므로 낮은 버전을 버리면 집계에서 누락된다. 순서와 무관하게 모든 이벤트를 반영하되 eventMessageId와 Fact PK로 중복만 방지한다. |
| 발급·취소 알림을 각각 보내는 Notification | x | 발급 알림과 취소 알림은 서로 다른 알림이므로 낮은 버전을 버리면 발급 알림이 발송되지 않는다. 다만 취소 알림을 먼저 받은 뒤 발급 알림을 보내면 사용자에게 혼란을 주므로, incomingVersion == currentVersion + 1인 경우만 처리하고 Gap이 있으면 보류·재시도하는 정책이 필요하다. |

### **7. Version Gap 처리 정책을 작성한다**

현재 Version이 2인데 Version 4가 먼저 도착했다고 가정한다.

```
Gap으로 판단하는 조건:
incomingVersion > currentVersion + 1인 경우

즉시 반영해도 되는 Consumer:
최신 상태만 저장하는 MyPage

모든 전이가 필요한 Consumer의 처리:
4를 바로 반영하지 않고 보류한다. 3이 도착할 때까지 대기하거나 재시도하며, 대기 시간이 목표를 초과하면 경고를 발생시킨다. Offset은 완료하지 않아 재전달 대상으로 남긴다.

복구 방법:
3이 오지 않으면 Kafka에 보관된 이벤트를 Replay하거나, 원본 DB에서 해당 couponIssueId의 이력을 조회해 누락된 전이를 보충한다. 재구축이 필요할 만큼 범위가 크면 새 Consumer Group으로 Projection을 다시 만든다.
```

### **8. 이벤트 스키마 변경의 호환성을 판단한다**

| 변경 | 호환 가능성 | 이유와 배포 방법 |
| --- | --- | --- |
| 선택 필드 `couponDisplayName` 추가 | o | 기존 Consumer는 모르는 필드를 무시하면 되므로 깨지지 않는다. schemaVersion을 올리지 않고 배포할 수 있으며, Consumer가 알 수 없는 필드를 무시하도록 역직렬화 설정이 되어 있어야 한다. |
| 기존 `userId` 필드 삭제 | x | userId를 읽던 Consumer가 파싱에 실패하거나 null을 반영한다. 새 schemaVersion으로 분리해 발행하고, 모든 Consumer가 새 버전을 처리할 수 있게 된 뒤 구 버전 발행을 중단하는 단계적 배포가 필요하다. |
| `userId` 의미를 이메일 주소로 변경 | x | 필드 이름과 타입이 그대로라 파싱은 성공하고 예외도 발생하지 않아, Consumer가 잘못된 값을 조회 모델과 통계에 조용히 쌓는다. 의미가 바뀐 값은 새 필드명으로 추가하고 기존 필드는 그대로 두거나 새 schemaVersion으로 분리해야 한다. |
| 호환되지 않는 새 Payload를 같은 `schemaVersion=1`로 발행 | x | Consumer가 버전으로 구조를 구분할 수 없어 방어할 방법이 사라진다. 버전 필드를 두는 목적 자체를 무력화하는 변경이므로, 구조가 바뀌면 반드시 schemaVersion을 올려야 한다. |
| 불필요한 전화번호와 비밀번호를 이벤트에 추가 | o | 선택 필드 추가라 기존 Consumer는 깨지지 않지만, 개인정보가 Kafka 보관 기간 동안 남고 모든 Consumer의 DB로 복제되어 유출 범위가 넓어진다. |

## **과제 8. Read Model 재구축과 운영 지표 설계하기**

### **1. 원본 데이터와 파생 데이터를 구분한다**

| 데이터 | Source of Truth인가? | 삭제 후 재구축 가능한가? | 재구축 근거 |
| --- | --- | --- | --- |
| Coupon Service `coupon_issue` | o | x | 발급 사실의 원본이므로 다른 데이터로부터 만들어낼 수 없다. 백업과 복제로 보호해야 하며, 조회 모델이나 통계로부터 역산하는 것은 원장과 파생 데이터의 관계를 뒤집는 것이라 허용되지 않는다. |

### **2. `user_coupon_view_v2` 재구축 순서를 작성한다**

다음 단계를 안전한 순서로 배치하고 각 단계의 목적을 설명한다.

```
새 Projection 테이블 생성
원본 DB Snapshot Backfill
새 Consumer Group으로 Kafka Replay
Backfill 경계 이후 이벤트 Catch-up
원본과 v2 정합성 검증
조회 API 전환
기존 Projection 보관 또는 제거
```

```
1. 새 Projection 테이블 생성
   user_coupon_view_v2를 만든다. 기존 테이블은 그대로 서비스하므로 무중단으로
   재구축을 시작할 수 있고, 실패하면 v2만 버리면 된다.

2. 원본 DB Snapshot Backfill
   특정 시점 T까지의 coupon_issue를 읽어 v2를 채운다. Kafka 보관 기간이 지난
   과거 구간은 이 단계로만 복구할 수 있다.

3. 새 Consumer Group으로 Kafka Replay
   mypage-coupon-projection-v2 같은 새 Group으로 이벤트를 소비한다. 기존 Group의
   Offset을 건드리지 않아 운영 중인 처리가 멈추지 않는다.

4. Backfill 경계 이후 이벤트 Catch-up
   경계 T 이후의 이벤트를 처리해 최신 상태까지 따라잡는다. 겹치는 구간은 멱등
   처리로 무시되므로 경계를 넉넉히 겹치게 잡아 누락이 생기지 않게 한다.

5. 원본과 v2 정합성 검증
   coupon_issue와 v2의 건수와 샘플 값을 대조하고 Lag이 해소되었는지 확인한다.
   여기서 문제가 발견되면 조회 대상을 바꾸기 전이므로 사용자 영향 없이 다시 만든다.

6. 조회 API 전환
   GET /api/users/{userId}/coupons가 v2를 바라보게 한다. 문제가 생기면 즉시
   기존 테이블로 되돌릴 수 있다.

7. 기존 Projection 보관 또는 제거
   일정 기간 지켜본 뒤 문제가 없으면 기존 테이블과 Consumer를 제거한다.
   바로 지우지 않는 이유는 롤백 경로를 남겨 두기 위해서다.
```

### **3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다**

```
Kafka만으로 전체 Replay가 가능한가?
불가능하다. Kafka는 보관 기간이 지난 Record를 삭제하므로, 보관 기간이 7일이라면
그 이전에 발급된 건의 이벤트는 이미 남아 있지 않다. 서비스 운영 기간이 보관 기간보다
길면 Replay만으로는 전체 조회 모델을 만들 수 없다.

필요한 다른 복구 기준:
Coupon Service의 coupon_issue Snapshot이다. 원장은 발급 사실을 모두 보관하고 있으므로
보관 기간이 지난 구간은 원장에서 직접 읽어 Backfill한다.

Backfill 중 새 이벤트가 들어올 때 필요한 경계:
Snapshot을 읽는 기준 시점 T를 정하고, T 이전은 Backfill로 T 이후는 Kafka Replay로
채운다.
```

### **4. 운영 지표를 완성한다**

| 지표 | 의미 | 장애 신호 예시 |
| --- | --- | --- |
| Group별 Consumer Lag | 각 Consumer Group이 Partition의 최신 Offset에 비해 얼마나 뒤처져 있는지를 나타낸다. | MyPage Group의 Lag만 수만 건으로 계속 증가하고 다른 Group은 정상이면 해당 Consumer가 중단되었거나 처리량이 부족한 상태다. |
| Oldest Unprocessed Age | 아직 처리되지 않은 이벤트 중 가장 오래된 것의 경과 시간이다. | 발급량이 적어 Lag은 작은데 경과 시간이 10분을 넘으면 특정 Partition이 막혀 있거나 처리가 멈춘 상태다. |
| Projection Delay | occurredAt부터 조회 모델 Commit까지 걸린 시간이다. | P99가 서비스 목표인 5초를 초과하면 쿠폰함 반영이 늦어져 사용자 문의가 발생할 수 있는 상태다. |
| Handler Failure Count | Consumer 처리 중 발생한 예외 건수다. | 특정 Group에서만 실패가 반복되면 잘못된 Payload나 스키마 불일치가 있어 Retry/DLQ 대상이 되는 상태다. |
| Duplicate Event Count | processed_event 충돌로 건너뛴 중복 이벤트 건수다. | 평소보다 급증하면 Outbox Publisher가 반복 재발행 중이거나 Consumer가 Offset을 완료하지 못하고 재시작을 반복하는 상태다. |
| Read Model Mismatch Count | 원장과 조회 모델의 건수 또는 값이 어긋난 건수다. | 0이 아닌 값이 유지되거나 증가하면 이벤트가 누락되었거나 잘못 반영된 것이므로 Backfill과 Replay를 통한 재구축이 필요한 상태다. |

### **6. 로그에 남길 상관관계 ID를 작성한다**

```

   사용자의 발급 요청 한 건을 식별한다. 클라이언트 요청부터 Redis 선착순 판정,

5. consumerGroupId
   어느 Consumer Group에서 처리한 로그인지 구분한다. 세 Group이 같은 이벤트를
   각자 처리하므로 이 값이 없으면 로그가 뒤섞여 어느 후속 작업이 실패했는지
   구분할 수 없다.
```

각 ID로 추적할 수 있는 범위도 간단히 설명한다.

## **과제 9. 잘못된 EDA 구현 리뷰하기**

다음 코드는 의도적으로 여러 문제가 포함되어 있다.

```java
@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void notify(CouponIssuedEvent event) {
    smsClient.send(event.userId(), "쿠폰 발급 완료");
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateMyPage(
    CouponIssuedEvent event,
    Acknowledgment acknowledgment
) {
    acknowledgment.acknowledge();

    if (processedEventRepository.existsById(
        event.kafkaOffset()
    )) {
        return;
    }

    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(event.kafkaOffset())
    );
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateAnalytics(CouponIssuedEvent event) {
    statisticsRepository.increaseIssuedCount(
        event.couponEventId()
    );
}
```

### **1. 문제를 최소 10개 찾는다**

각 문제를 다음 표에 작성한다.

| 번호 | 문제 코드 | 발생 가능한 장애 또는 데이터 오류 | 수정 방향 |
| --- | --- | --- | --- |
| 1 | 세 리스너가 모두 groupId = "coupon-result" | Kafka는 세 인스턴스를 한 Group의 워커로 인식해 Record를 나눠 준다. 한 발급 건에 대해 세 작업 중 하나만 실행되어 알림·조회 모델·통계가 각각 누락된다. | 서비스별로 notification-coupon-issued, mypage-coupon-projection, analytics-coupon-issued로 Group ID를 분리한다. |
| 2 | notify()에서 smsClient.send()를 직접 호출 | 외부 호출이 로컬 트랜잭션 밖이라 발송 후 종료되면 재전달 시 중복 발송되고, 반대 순서면 누락된다. 외부 API 지연이 Consumer Lag으로 전파된다. | processed_event와 notification_job을 한 트랜잭션으로 저장하고, 별도 Sender가 notificationId를 Idempotency Key로 사용해 발송한다. |
| 3 | updateMyPage()에서 acknowledge()를 맨 앞에서 호출 | DB 반영 전에 Offset이 완료되어, 이후 처리가 실패하면 이벤트가 재전달되지 않고 영구히 누락된다. | DB Commit 이후에 acknowledge()를 호출한다. |
| 4 | existsById() 확인 후 save() | 두 트랜잭션이 동시에 없다고 판단해 모두 진행하는 Race Condition이 발생한다. | INSERT ... ON CONFLICT DO NOTHING RETURNING으로 최초 처리 권한을 원자적으로 등록하고 반환 행으로 판정한다. |
| 5 | event.kafkaOffset()을 멱등성 Key로 사용 | Offset은 물리적 위치라 Outbox 재발행 시 같은 논리 이벤트가 다른 Offset을 갖는다. 중복을 걸러내지 못한다. | eventMessageId를 Key로 사용한다. |
| 6 | userCouponViewRepository.save()와 processedEventRepository.save()가 원자적으로 묶이지 않음 | 조회 모델만 저장되고 기록이 없으면 중복 반영되고, 기록만 남고 조회 모델이 실패하면 영구 누락된다. | 두 작업을 하나의 로컬 트랜잭션으로 처리한다. |
| 7 | processed_event에 subscriber 구분이 없음 | 세 Consumer가 같은 키 공간을 공유하면 한 서비스가 처리한 이벤트를 다른 서비스가 중복으로 판단해 건너뛴다. | PK를 (subscriber_id, event_message_id)로 두고 Group별로 다른 subscriber_id를 사용한다. |
| 8 | updateAnalytics()의 increaseIssuedCount() | 카운터 증가는 제약으로 막을 수 없어 중복 이벤트마다 이중 집계된다. | coupon_issue_fact를 ON CONFLICT DO NOTHING으로 저장하고 실제 INSERT된 경우에만 같은 트랜잭션에서 집계를 증가시킨다. |
| 9 | aggregateVersion 검사 없이 save()로 덮어씀 | 취소 이벤트가 먼저 도착한 뒤 발급 이벤트가 처리되면 취소된 쿠폰이 다시 ISSUED로 되살아난다. | ON CONFLICT (coupon_issue_id) DO UPDATE ... WHERE 저장된 버전 < 들어온 버전 형태의 조건부 UPSERT를 사용한다. |
| 10 | Analytics와 Notification에 멱등 처리와 Offset 제어가 없음 | 예외 발생 시 처리 결과를 알 수 없고, 자동 Commit이면 실패한 이벤트도 완료 처리된다. | 세 Consumer 모두 enable.auto.commit=false로 두고 processed_event 기반 멱등 처리와 수동 Offset 완료를 적용한다. |

### **2. 반드시 찾아야 하는 문제를 연결한다**

| 검토 항목 | 문제가 있는 코드 | 수정 방향 |
| --- | --- | --- |
| 세 서비스가 같은 Group ID 사용 | 세 @KafkaListener가 모두 groupId = "coupon-result" | 서비스별로 notification-coupon-issued, mypage-coupon-projection, analytics-coupon-issued로 분리해 각 Group이 같은 이벤트를 독립적으로 소비하게 한다. |
| 외부 SMS 직접 호출의 Dual Write | notify()의 smsClient.send(...) | 외부 발송을 이벤트 처리 경로에서 분리한다. Consumer는 processed_event와 notification_job만 한 트랜잭션으로 저장하고, 별도 Sender가 notificationId를 Idempotency Key로 사용해 job 단위로 재시도한다. |
| DB Commit 전 Offset 완료 | updateMyPage() 첫 줄의 acknowledgment.acknowledge() | enable.auto.commit=false로 두고 DB Commit이 끝난 뒤 맨 마지막에 acknowledge()를 호출한다. 예외 발생 시 Offset을 완료하지 않아 재전달 대상으로 남긴다. |
| `exists` 후 `save` Race Condition | processedEventRepository.existsById(...) 확인 후 save(...) | INSERT ... ON CONFLICT DO NOTHING RETURNING으로 최초 처리 권한을 원자적으로 등록하고, 반환 행의 유무로 최초·중복을 판별한다. |
| Kafka Offset을 멱등성 Key로 사용 | event.kafkaOffset()을 processed_event의 키로 사용 | eventMessageId를 키로 사용한다. Offset은 물리적 위치라 Outbox 재발행 시 같은 논리 이벤트가 다른 값을 갖는다. 또한 (subscriber_id, event_message_id) 복합키로 두어 한 Consumer의 처리 기록이 다른 Consumer의 처리를 건너뛰게 하지 않는다. |
| 조회 모델과 processed 기록의 원자성 없음 | userCouponViewRepository.save(...)와 processedEventRepository.save(...)가 별도로 호출됨 | 두 작업을 하나의 로컬 트랜잭션으로 묶어 함께 Commit되거나 함께 Rollback되게 한다. 한쪽만 남으면 영구 누락이나 중복 반영이 발생한다. |
| Analytics `+1` 중복 반영 | updateAnalytics()의 statisticsRepository.increaseIssuedCount(...) | coupon_issue_fact를 ON CONFLICT DO NOTHING으로 저장하고 실제 INSERT된 경우에만 같은 트랜잭션에서 집계를 증가시킨다. 집계가 어긋나면 Fact의 COUNT로 재계산한다. |
| 이벤트 Version과 순서 방어 없음 | UserCouponView.from(event)를 그대로 save해 무조건 덮어씀 | ON CONFLICT (coupon_issue_id) DO UPDATE ... WHERE 저장된 버전 < 들어온 버전 형태의 조건부 UPSERT로 늦게 도착한 과거 이벤트가 최신 상태를 덮어쓰지 않게 한다. |
| 서비스별 데이터 소유권 불명확 | 세 리스너가 한 클래스에 있고 Group과 트랜잭션 경계가 공유됨 | 서비스별 모듈과 Consumer로 분리하고 각자 자기 소유 테이블만 변경하게 한다. 필요한 값은 이벤트 계약으로 전달받는다. |
| 실패·Lag 관측 정보 없음 | 세 메서드 모두 로깅과 예외 처리, 지표 수집이 없음 | requestId, eventMessageId, couponIssueId, couponEventId, consumerGroupId를 로깅하고 Group별 Consumer Lag, Projection Delay, Handler Failure Count, Read Model Mismatch Count를 관측한다. |

### **4. 수정된 구조의 보장 수준을 판단한다**

| 항목 | 보장/조건부 보장/보장하지 않음 | 이유 |
| --- | --- | --- |
| 쿠폰 발급 DB의 최종 성공 | 보장 | coupon_issue 저장과 Outbox 저장이 하나의 트랜잭션으로 Commit되며, 이후 어떤 후속 처리가 실패해도 이 결과는 바뀌지 않는다. |
| 세 Group이 각자 이벤트를 소비할 기회 | 보장 | Group ID가 서로 다르므로 Kafka는 Group 사이에 브로드캐스트로 동작하고 Offset도 독립 관리된다. 한 Group의 지연이 다른 Group의 소비를 막지 않는다. |
| Kafka Record의 물리적 Exactly-Once | 보장하지 않음 | Outbox Publisher가 발행 후 PUBLISHED 갱신 전에 종료되면 같은 논리 이벤트가 다른 Offset으로 다시 저장되고, Consumer 쪽에서도 Offset Commit 전 종료나 Rebalance로 같은 Record가 재전달된다. 전달은 At-Least-Once다. |
| MyPage 중복 반영 방지 | 보장 | processed_event 등록과 user_coupon_view 변경이 같은 로컬 트랜잭션 안에서 이루어지고, PK와 UNIQUE 제약이 추가 방어선이 된다. 중복 Record가 와도 결과는 한 번만 반영된다. |
| Analytics 중복 집계 방지 | 보장 | coupon_issue_fact가 실제 INSERT된 경우에만 같은 트랜잭션에서 집계를 증가시키므로 비멱등 연산이 멱등 연산에 종속된다. 값이 어긋나도 Fact의 COUNT로 재계산할 수 있다. |
| 외부 SMS Exactly-Once | 조건부 보장 | 외부 호출은 로컬 트랜잭션에 포함할 수 없어 발송 여부와 DB 상태가 원자적으로 묶이지 않으므로, 중복 방지 여부는 Provider가 멱등 키를 지원하는지에 달려 있다. 지원하지 않으면 응답 유실 시 재시도로 인해 At-Least-Once에 가까워진다. |
| 발급 직후 MyPage의 즉시 일치 | 보장하지 않음 | 조회 모델은 이벤트를 통해 갱신되므로 원장 Commit과 동시에 반영되지 않는다. 최종적 일관성 구간이 존재하며, 발급 확정 여부는 요청 상태 API로 확인해야 한다. |

```
audit-coupon-issued

audit_log. 언제 어떤 발급 사실이 있었는지를 감사 목적으로 보관하는 테이블이며,
Audit Consumer만 쓰고 다른 서비스는 읽지도 쓰지도 않는다.

멱등성 Key:
eventMessageId. processed_event에 subscriber_id = 'audit-coupon-issued'로 기록하고
audit_log 저장과 같은 트랜잭션으로 묶는다.

원본 이벤트에 추가로 필요한 필드:
감사 기록은 누가 언제 어떤 경로로 발급했는지를 남겨야 하므로 요청 출처나 처리 주체를

기존 Consumer와 독립적으로 실패·복구하는 방법:
Group ID가 다르므로 Offset이 독립 관리되어 Audit이 중단되어도 다른 Group의 처리와
쿠폰 발급에는 영향이 없다. 복구는 Audit Group 안에서 이루어지며, 밀린 이벤트를 다시
소비하고 processed_event로 중복을 막는다. 보관 기간이 지난 과거 구간이 필요하면 원장
Snapshot으로 Backfill한다.
```

## **보너스 2. Projection 재구축 테스트 설계하기**

| 테스트 상황 | 준비 데이터 | 실행 방법 | 검증할 결과 |
| --- | --- | --- | --- |
| 동일 이벤트 2회 Replay | eventMessageId가 같은 CouponIssued 한 건 | 같은 이벤트를 두 번 소비시킨다 | user_coupon_view 행이 1건, processed_event 행이 1건. 두 번째 처리에서 예외 없이 변경 없음으로 종료되고 Offset은 정상 완료된다 |
| Version 2 뒤 Version 1 전달 | 같은 couponIssueId의 CouponCancelled(v2)와 CouponIssued(v1) | v2를 먼저, v1을 나중에 소비시킨다 | status는 CANCELLED, aggregate_version은 2 유지. v1 UPSERT의 affected rows가 0이고 예외는 발생하지 않는다 |
| Backfill 중 새 이벤트 유입 | 경계 시점 T 이전의 원장 데이터와 T 전후에 걸친 이벤트 | Backfill을 실행하는 도중 새 발급 이벤트를 발행한다 | 경계 구간이 중복 처리되어도 결과는 1건. 누락 구간 없이 원장과 v2의 건수가 일치한다 |
| Kafka 보관 기간 이전 데이터 존재 | 보관 기간이 지나 Kafka에 남아 있지 않은 과거 발급 건 | Replay만 수행한 경우와 Snapshot Backfill을 병행한 경우를 비교한다 | Replay만으로는 과거 구간이 비어 있고, Backfill을 함께 수행하면 원장과 일치한다 |
| Consumer DB Commit 직후 종료 | 처리 대상 이벤트 한 건 | DB Commit 이후 Offset 완료 전에 Consumer를 강제 종료하고 재시작한다 | 재전달된 이벤트가 processed_event에 걸려 조회 모델이 두 번 변경되지 않고, Offset은 재시작 후 정상 진행된다 |

한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유도 작성한다.

```
정상 실행은 이벤트가 한 번씩 순서대로 도착하고 아무 장애도 없는 경로만 확인한다. 그러나 실제 운영에서 문제가 되는 것은 재발행으로 인한 중복, 순서 역전, Commit과 Offset 완료 사이의 종료처럼 모두 비정상 경로에서 발생한다. 게다가 이런 결함은 예외를 던지지 않고 조용히 잘못된 데이터를 남기는 경우가 많아 로그나 Lag만으로는 드러나지 않는다. 따라서 중복, 순서 역전, 중간 종료, 보관 기간 경과 같은 상황을 의도적으로 만들어 검증해야 Projection이 안전하다고 말할 수 있다.
```

# **8. 핵심 질문**

과제를 마친 뒤 다음 질문에 한 문장씩 답한다.

```
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
같은 Group 안에서는 한 Partition이 한 인스턴스에만 할당되어 Record를 나누어 처리하므로,
같은 Group을 쓰면 한 발급 건에 대해 세 작업 중 하나만 실행되기 때문이다.

2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
발급은 DB Commit으로 이미 확정된 결과이고 Consumer는 그 사실을 각자 소비할 뿐,
거부하거나 다시 발급할 대상이 아니기 때문이다.

3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
Coupon Service의 coupon_issue이며, Read Model은 언제든 다시 만들 수 있는 파생
데이터이므로 두 데이터가 어긋나면 원장 쪽으로 맞춘다.

4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
Offset은 브로커가 저장 시점에 부여하는 물리적 위치라, Outbox Publisher가 같은 논리
이벤트를 재발행하면 새 Record로 저장되어 다른 Offset을 갖기 때문이다.

5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
한쪽만 남으면 처리 기록은 있는데 반영이 없어 이벤트가 영구히 누락되거나, 반영만 되고
기록이 없어 재전달 시 중복 반영되기 때문이다.

6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
조회 모델은 원장과 동시에 갱신되지 않고 이벤트가 발행되어 Consumer가 처리한 뒤에
반영되므로, 그 사이에 최종적 일관성 구간이 존재하기 때문이다.

7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
버전은 순서를 판단할 근거를 제공할 뿐이고, Consumer가 저장된 버전과 비교해 낮은
버전을 무시하는 처리를 직접 구현해야 실제로 방어되기 때문이다.

8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
Analytics나 Notification처럼 각 이벤트가 독립적인 결과를 만드는 Consumer는 중간
전이를 버리면 집계가 누락되거나 발급 알림이 발송되지 않기 때문이다.

9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
버그나 이벤트 누락으로 잘못된 값이 쌓였을 때 원장으로부터 재구축하는 것이 유일한
복구 수단이며, 재구축 가능성이 파생 데이터를 신뢰할 수 있게 하는 근거이기 때문이다.

10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
발급은 이미 확정되었고 실패한 것은 후속 작업뿐이므로, 재실행하면 중복 발급과 수량
오차가 생긴다. 재시도 대상은 실패한 Consumer 작업이다.
```
