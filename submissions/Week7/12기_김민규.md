## **1. 과제 목표**

이번 과제의 목표는 쿠폰 발급 이후의 알림, 마이페이지와 통계 작업을 `CouponIssued` 이벤트 기반으로 분리하고, 각 Consumer가 자신의 데이터를 안전하게 만드는 구조를 설계하는 것이다.

6주차까지 다음 흐름을 만들었다.

```text
Coupon Issue Consumer
        |
        v
+------------------------------------------+
| Coupon Issue DB Transaction              |
|------------------------------------------|
| coupon_issue 저장                        |
| request ISSUED                           |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        |
        | Commit
        v
Outbox Publisher
        |
        v
Kafka coupon.issued
```

7주차에서는 `coupon.issued` 이후를 설계한다.

```text
Kafka coupon.issued
  |
  +--> Notification Consumer
  |
  +--> MyPage Consumer
  |
  +--> Analytics Consumer
```

```text

- Coupon Service와 후속 서비스의 데이터 소유권은 어떻게 구분하는가?
- MyPage Read Model은 원본 DB와 무엇이 다른가?
- 중복 이벤트가 조회와 통계에 두 번 반영되지 않게 하려면 어떻게 하는가?
- DB ISSUED와 마이페이지 반영 사이의 지연을 사용자에게 어떻게 보여주는가?
- 이벤트 순서가 바뀌어도 최신 상태를 어떻게 지키는가?
- Read Model이 잘못되었을 때 어떻게 다시 만드는가?
```

## **3. 전제 조건**

```text

Consumer DB Commit 뒤 Offset을 완료 처리한다.

이번 주차는 Retry Topic과 DLQ의 상세 구현보다
```

## **과제 1. 직접 호출 구조와 EDA 비교하기**

Coupon Service가 쿠폰 발급 뒤 세 서비스를 순서대로 호출한다고 가정한다.

```text
Coupon Service
  |
  +--> Notification Service
  |
  +--> MyPage Service
  |
  +--> Analytics Service
```

### **1. 직접 호출 구조의 결합을 분석한다**

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 쿠폰 발급 요청 중 Notification, MyPage, Analytics API가 모두 응답할 때까지 기다려야 한다. 호출 시간이 누적되어 발급 응답이 느려진다. | Coupon Service는 `CouponIssued`를 Kafka에 전달한 뒤 후속 처리 응답을 기다리지 않는다. 각 Consumer는 자신의 처리 시점에 소비한다. |
| 장애 결합 | 후속 서비스 하나의 Timeout이나 장애가 이미 성공한 쿠폰 발급 요청까지 실패처럼 보이게 만들 수 있다. | 각 Group이 독립적으로 재처리한다. Notification 장애는 알림 지연으로만 남고 쿠폰 발급과 MyPage 처리까지 멈추게 하지 않는다. |
| 변경 결합 | 새 후속 서비스를 추가하거나 기존 API 요청 형식을 바꿀 때 Coupon Service 코드와 배포도 같이 바뀐다. | Producer는 안정적인 이벤트 계약만 유지한다. 새 Consumer는 별도 Group으로 추가할 수 있다. |
| 데이터 결합 | Coupon Service가 다른 서비스의 API DTO나 내부 테이블 구조를 알아야 하고, 직접 DB를 수정하는 구조로 커지기 쉽다. | Consumer는 이벤트의 필요한 필드만 받아 자신의 DB를 변경한다. 원본 DB의 내부 모델에는 직접 의존하지 않는다. |

### **2. 다음 장애 상황을 분석한다**

```text
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```text
이미 확정된 쿠폰 발급 상태:

`coupon_issue`가 Commit되어 있고 발급 요청 상태도 `ISSUED`이다. 같은 트랜잭션의 Outbox에도 `CouponIssued` 발행 의도가 저장되어 있어야 한다.


쿠폰 발급을 Rollback하면 안 되는 이유:

쿠폰 발급은 이미 DB에 확정된 최종 사실이다. 알림 실패는 후속 작업의 실패이므로 발급 원장을 단순 Rollback하면 사용자가 받아야 할 쿠폰을 잃거나 이미 Commit된 데이터를 거짓으로 되돌리게 된다.


다시 실행해야 하는 작업:

실패한 Notification Consumer 작업만 재시도하거나 `notification_job`을 다시 전송한다.


다시 실행하면 안 되는 작업:

이미 성공한 쿠폰 발급 명령 전체와 수량 차감, `coupon_issue` INSERT를 다시 실행하면 안 된다. 같은 `requestId`는 기존 `ISSUED` 결과를 반환해야 한다.

```

### **3. EDA 기반 전체 흐름을 완성한다**

```text
Coupon Issue Consumer
        |
        v
+------------------------------------------+
| Coupon Issue DB Transaction              |
|------------------------------------------|
| coupon_issue 저장                        |
| request -> ISSUED                        |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        |
        | DB Commit
        v
Outbox Publisher
        |
        v
Kafka coupon.issued
        |
        +--> notification-coupon-issued Group
        |       -> Notification Consumer -> notification_job
        |
        +--> mypage-coupon-projection Group
        |       -> MyPage Consumer -> user_coupon_view
        |
        +--> analytics-coupon-issued Group
                -> Analytics Consumer -> coupon_issue_fact / stats
```

다음 구성 요소를 모두 포함한다.

```text
Coupon Issue DB Transaction
CouponIssued Outbox
Outbox Publisher
Kafka coupon.issued
Notification Consumer
MyPage Consumer
Analytics Consumer
```

### **4. 명령과 이벤트의 차이를 작성한다**

| 이름 | 종류 | 의미 | Consumer가 쿠폰을 다시 발급하는가? |
| --- | --- | --- | --- |
| `IssueCoupon` | 명령(Command) | 쿠폰을 발급하라고 Coupon Service에 요청하는 의도이다. 처리 전에는 성공 여부가 확정되지 않았다. | 발급 Consumer가 명령을 처리해 발급한다. 후속 Consumer가 다시 처리하는 대상은 아니다. |
| `CouponIssued` | 이벤트(Event) | 쿠폰 발급 DB가 Commit된 뒤의 이미 발생한 과거 사실이다. | 아니다. Notification은 알림을 만들고, MyPage는 조회 모델을 갱신하며, Analytics는 발급 사실을 집계한다. |

### **5. EDA를 사용해도 남는 결합을 설명한다**

```text
직접 API 계약 대신 남는 계약:

`CouponIssued`의 이벤트 이름, 필드, 필드 의미, `schemaVersion`, 순서와 보관 정책에 대한 이벤트 계약이 남는다.


이 계약을 관리해야 하는 이유:

독립 배포된 Consumer가 같은 Payload를 해석한다. 필드 삭제나 의미 변경을 임의로 하면 Consumer가 실패하거나 잘못된 조회 데이터를 만들 수 있다.


EDA가 반드시 MSA를 의미하지 않는 이유:

이벤트 기반으로 책임과 처리 경로를 논리적으로 분리하는 것이 핵심이다. 처음에는 하나의 애플리케이션 안에서 모듈과 Consumer만 분리하고, 필요할 때 프로세스와 DB를 물리적으로 분리할 수 있다.

```

## **과제 2. Consumer Group과 서비스 책임 설계하기**

### **1. 서비스별 Consumer Group을 작성한다**

| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | `notification-coupon-issued` | 발급 알림 작업을 만들고 발송 상태를 관리한다. |
| MyPage | `mypage-coupon-projection` | 사용자 쿠폰함 조회 모델인 `user_coupon_view`를 갱신한다. |
| Analytics | `analytics-coupon-issued` | 발급 Fact를 저장하고 운영자용 발급 통계를 갱신한다. |

### **2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다**

```text
같은 Group 안의 Consumer 관계:

같은 Group의 Consumer 인스턴스는 같은 Record를 모두 받는 관계가 아니라 Partition을 나누어 처리하는 경쟁 Consumer 관계이다.


CouponIssued 한 건의 전달 결과:

한 Record는 그 시점에 Group 안의 한 Consumer에만 할당된다. 세 Listener가 같은 Group이라면 Notification, MyPage, Analytics 중 하나만 실행될 수 있다.


세 서비스 중 일부 작업이 누락될 수 있는 이유:

Kafka는 같은 Group에 브로드캐스트하지 않고 Offset을 함께 관리한다. 한 Listener가 Record를 처리하고 Offset을 Commit하면 나머지 서비스 Listener에는 전달 기회가 없다.

```

### **3. 다음 Partition과 Consumer 배치를 분석한다**

```text
coupon.issued Partition 수: 6

notification-coupon-issued Consumer 수: 2
mypage-coupon-projection Consumer 수: 4
analytics-coupon-issued Consumer 수: 1
```

| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | ---: | --- | --- |
| Notification | 2 | 유휴 Consumer는 없다. 6개 Partition은 2개 Consumer에 각각 여러 개씩 할당되어 한 Consumer 안에서 순차 처리된다. | 없음. Notification Lag은 이 Group의 Offset에만 남는다. |
| MyPage | 4 | 유휴 Consumer는 없다. 6개 Partition을 4개 Consumer가 나누어 처리한다. | 없음. MyPage Group은 자신의 Offset으로 독립 처리한다. |
| Analytics | 1 | 유휴 Consumer는 없지만 하나의 Consumer가 6개 Partition을 모두 처리하므로 Group 내부 병렬도는 1이다. | 없음. Analytics 지연이 다른 Group의 Offset을 멈추게 하지 않는다. |

### **4. Consumer Group의 Committed Offset 의미를 설명한다**

```text
Committed Offset이 나타내는 것:

해당 Consumer Group이 어느 Partition의 어느 위치까지 완료 처리로 기록했는지를 나타낸다. 재시작 시 그 다음 위치부터 다시 소비하는 기준이다.


Committed Offset만으로 증명할 수 없는 것:

Consumer의 DB 변경, 외부 SMS 실제 도착, 논리적으로 Exactly-Once 처리되었다는 사실을 직접 증명하지 않는다. DB Commit과 Offset Commit 사이에는 중복 재전달도 가능하다.


Notification Group의 Offset이 MyPage Group에 영향을 주는가?

영향 주지 않는다. Group ID마다 Committed Offset과 Lag을 별도로 관리한다.

```

### **5. 서비스별 책임과 데이터 소유권을 완성한다**

| 서비스 | 소유하는 데이터 | 보장해야 하는 불변식 또는 책임 | 다른 서비스 DB 직접 수정 허용 여부 |
| --- | --- | --- | --- |
| Coupon Service | `coupon_event`, `coupon_issue`, `coupon_issue_request`, Outbox | 수량 초과와 사용자 중복 발급을 막고 발급 여부의 최종 원장을 보장한다. | 허용하지 않는다. |
| Notification Service | `processed_event`, `notification_job`, 발송 상태 | 같은 이벤트로 알림 작업을 한 번만 만들고, 재시도와 발송 상태를 관리한다. | 허용하지 않는다. |
| MyPage Service | `processed_event`, `user_coupon_view` | 사용자에게 필요한 쿠폰 목록을 중복 없이 Projection으로 만든다. 원본 발급 여부를 판정하지 않는다. | 허용하지 않는다. |
| Analytics Service | `coupon_issue_fact`, 집계 테이블 | 발급 사실을 중복 없이 저장하고 Fact 기준 통계를 만든다. | 허용하지 않는다. |

### **6. 장애 격리 결과를 작성한다**

| 장애 | 쿠폰 발급 결과 | 영향받는 기능 | 영향받지 않아야 하는 기능 | 복구 단위 |
| --- | --- | --- | --- | --- |
| Notification Consumer 중단 | `ISSUED` 유지 | 발급 알림이 늦어지거나 재시도 대기한다. | 쿠폰 발급 확정, 마이페이지 조회 모델, 통계 처리 | Notification Group과 `notification_job` |
| MyPage Consumer 중단 | `ISSUED` 유지 | 쿠폰함 반영이 늦어진다. | 쿠폰 발급 확정, 알림 처리, 통계 처리 | MyPage Group과 `user_coupon_view` Projection |
| Analytics Consumer 중단 | `ISSUED` 유지 | 운영자 대시보드와 통계 갱신이 늦어진다. | 쿠폰 발급 확정, 알림, 사용자 쿠폰함 | Analytics Group과 Fact/집계 Projection |

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 쿠폰 발급 명령을 처리하고 수량·중복 불변식을 보장한다. | 화면과 운영 조회를 빠르고 단순하게 제공한다. |
| 대표 작업 | 발급 요청 상태 변경, 수량 조건부 증가, `coupon_issue` 저장 | 사용자별 쿠폰 목록 조회, 발급 통계 조회 |
| 데이터 구조 | 정합성과 변경에 맞춘 정규화된 원장 모델 | 화면별 접근 패턴에 맞춘 비정규화 Projection |
| 최종 원장 여부 | 발급 여부의 최종 기준이다. | 최종 원장이 아니다. 원본 사실을 화면에 맞게 복제한 파생 데이터이다. |
| 장애 후 재구축 가능 여부 | Read Model만으로 재구축하면 안 된다. 원장 자체를 안전하게 보존해야 한다. | 가능하다. 원본 DB Snapshot과 보관 중인 이벤트를 근거로 다시 만든다. |

### **2. CQRS에 대해 다음 문장을 판단한다**

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 핵심은 Command와 Query의 책임·모델 분리이다. 하나의 애플리케이션과 하나의 DB 안에서도 논리적으로 분리할 수 있다. |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 읽기와 쓰기 모델을 나누는 방식이고, Event Sourcing은 상태를 이벤트 기록으로 복원하는 저장 방식이다. 함께 사용할 수 있지만 같은 의미는 아니다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 발급 처리 테이블과 사용자 쿠폰함 Projection의 책임을 분리하면 된다. |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 같은 쓰기 모델을 그대로 두 테이블에 복사하기만 하면 조회 목적·처리 경로·소유권이 분리되지 않는다. |

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```text
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001
```

### **1. Offset과 eventMessageId를 비교한다**

| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka Topic 안의 물리적인 Record 위치 | 변경된다. 같은 논리 이벤트를 다시 발행하면 새 Record와 새 Offset을 가진다. | 적절하지 않다. 재발행된 같은 이벤트를 서로 다른 이벤트로 판단한다. |
| eventMessageId | `CouponIssued`라는 논리 이벤트 자체 | 변경되지 않아야 한다. 재전달·재발행에도 같은 값을 사용한다. | 적절하다. Consumer가 한 논리 이벤트의 비즈니스 결과를 한 번만 반영하는 기준이다. |

### **2. `processed_event` DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

다음 세 값 중 올바른 `subscriber_id`를 고르고 이유를 작성한다.

```text
pod-a7f9c
server-10.0.0.12
mypage-coupon-projection
```

```text
선택:

`mypage-coupon-projection`


이유:

`subscriber_id`는 실행 중인 pod나 서버가 아니라 논리적인 구독 처리기를 식별해야 한다.
pod와 서버 주소는 재시작·Scale Out 때 바뀌므로 인스턴스별 값을 사용하면 같은 이벤트를 다시 최초 이벤트로 판단할 수 있다.

```

### **3. MyPage Consumer 트랜잭션을 완성한다**

다음 요구사항을 만족해야 한다.

```text
ON CONFLICT DO NOTHING으로 최초 처리 권한 등록
RETURNING 결과로 최초·중복 판별
최초 이벤트일 때만 user_coupon_view 변경
processed_event와 조회 모델 변경의 원자성
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (
        subscriber_id,
        event_message_id
    ) VALUES (
        'mypage-coupon-projection',
        :eventMessageId
    )
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    aggregate_version,
    issued_at,
    updated_at
)
SELECT
    :couponIssueId,
    :userId,
    :couponEventId,
    'ISSUED',
    :aggregateVersion,
    :issuedAt,
    CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```text

일반 INSERT가 PK/UNIQUE 위반으로 실패하면 PostgreSQL은 현재 트랜잭션을 aborted 상태로 만든다.

예외만 잡고 다음 `user_coupon_view` INSERT를 실행해도 `current transaction is aborted` 오류가 발생하며, 먼저 Rollback해야 한다.

중복 이벤트는 예외 흐름으로 처리할 대상이 아니다. `INSERT ... ON CONFLICT DO NOTHING RETURNING`으로 최초 처리 여부를 정상 결과로 판별해야 한다.

```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```text
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```text
재전달 시 Consumer 판단:

이미 `processed_event`가 존재하므로 중복 이벤트라고 판단하고 `user_coupon_view` 변경을 생략한다.


최종 조회 모델 상태:

발급 사실은 원본 DB에 있지만 `user_coupon_view`에는 행이 없거나 이전 상태로 영원히 남을 수 있다.


두 작업을 같은 트랜잭션에 넣어야 하는 이유:

조회 모델 변경이 실패하면 처리 기록도 함께 Rollback되어야 재전달된 이벤트가 다시 조회 모델을 갱신할 수 있다. 둘은 함께 Commit되거나 함께 Rollback되어야 한다.

```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```text
Consumer DB 상태:

`processed_event`와 `user_coupon_view` 변경이 이미 Commit되어 있다.


Consumer Group Offset:

아직 Commit되지 않아 이전 위치를 가리킨다.


재시작 후 전달:

Kafka는 아직 완료되지 않은 Record로 보므로 같은 Record를 다시 전달한다.


재전달된 이벤트 처리:

`processed_event` PK 충돌로 중복임을 확인하고 조회 모델은 변경하지 않은 뒤 Offset을 완료 처리한다.

```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```text
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record
```

```text

`enable.auto.commit=false`로 둔다.

Listener는 먼저 자신의 DB 트랜잭션을 Commit하고, 성공한 경우에만 수동 Acknowledgment로 Offset을 완료 처리한다.

Listener에서 DB 변경이나 역직렬화 이외의 처리 오류가 발생하면 예외를 삼키거나 Offset을 Commit하지 않는다. 트랜잭션을 Rollback하고 해당 Record가 재전달되도록 하며, Retry/DLQ 정책은 별도로 적용한다.

같은 Partition을 병렬 처리하는 경우에도 앞선 Offset이 아직 완료되지 않았는데 뒤 Record의 Offset만 Commit하면 안 된다. Commit 가능한 Offset은 연속적으로 성공한 범위여야 하므로 앞선 미완료 Record를 먼저 복구해야 한다.

```

### **5. `coupon_issue_fact` 기반 집계 구조를 설계한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id 중복 저장 방지
event_message_id 추적
coupon_event_id와 user_id 저장
발급 발생 시각 저장
Fact가 실제 INSERT된 경우에만 집계 +1
Fact INSERT와 집계 변경을 같은 트랜잭션으로 처리
```

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL UNIQUE,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id,
        event_message_id,
        coupon_event_id,
        user_id,
        issued_at
    ) VALUES (
        :couponIssueId,
        :eventMessageId,
        :couponEventId,
        :userId,
        :issuedAt
    )
    ON CONFLICT DO NOTHING
    RETURNING coupon_event_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId
  AND EXISTS (
      SELECT 1 FROM accepted
  );

COMMIT;
```

| Consumer | 한 번만 반영해야 하는 비즈니스 결과 | 추가 제약 또는 Idempotency Key | 외부 시스템 포함 여부 |
| --- | --- | --- | --- |

## **과제 7. 이벤트 순서와 버전 처리하기**

다음 두 이벤트가 같은 `couponIssueId = 5001`에서 발생했다고 가정한다.

```text
CouponIssued
aggregateVersion = 1
status = ISSUED

CouponCancelled
aggregateVersion = 2
status = CANCELLED
```

### **1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다**

```text
같은 Topic이어야 하는가?

같은 `couponIssueId`의 상태 이벤트를 같은 Topic으로 발행해야 Key가 같은 Partition을 선택한다는 규칙을 적용할 수 있다.


같은 Key가 보장하는 범위:

같은 Topic에 안정적인 Partition 전략으로 발행된 같은 Key의 Record가 같은 Partition에 기록되고, 그 Partition에 실제 저장된 순서대로 한 Consumer에게 전달되는 범위까지 보장한다.


전역 순서를 보장하는가?

보장하지 않는다. 서로 다른 Partition에 있는 다른 쿠폰 발급 건 사이의 전역 순서는 보장하지 않는다.


서로 다른 Topic 사이의 순서를 보장하는가?

보장하지 않는다. Key가 같아도 Topic마다 Partition과 Producer 처리 흐름이 분리되어 있다.

```

### **2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다**

다음을 포함한다.

```text
여러 Publisher
SKIP LOCKED
version 1 발행 실패
Backoff
version 2 선행 발행
```

```text
DB 발생 순서:

`CouponIssued(version=1)` Outbox 저장 → `CouponCancelled(version=2)` Outbox 저장 순서이다.


Publisher 처리 순서:

Publisher A가 `SKIP LOCKED`로 version 1 행을 Claim했지만 Kafka 발행에 실패해 Backoff 상태가 된다. 그 사이 Publisher B가 version 2 행을 Claim해 먼저 발행한다. 이후 A가 version 1을 재시도한다.


Kafka 저장 순서:

`CouponCancelled(version=2)` → `CouponIssued(version=1)` 순서가 될 수 있다. 같은 Key는 Kafka에 저장된 뒤의 Partition 순서를 보장하지만 DB 발생 순서대로 발행되었음을 직접 보장하지 않는다.

```

### **3. `schemaVersion`과 `aggregateVersion`을 비교한다**

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| `schemaVersion` | 이벤트 JSON Payload 구조와 필드 계약의 버전 | Producer와 Consumer 사이의 역직렬화·호환성 문제 | 선택 필드 `couponDisplayName`를 새 계약으로 추가하거나 호환되지 않는 새 구조를 도입할 때 |
| `aggregateVersion` | 하나의 `CouponIssue` Aggregate에서 발생한 상태 변경의 논리 순번 | 늦게 도착한 과거 상태가 최신 Projection을 덮어쓰는 문제 | `CouponIssued=1` 뒤 `CouponCancelled=2`가 발생할 때 |

### **4. 최신 상태 Projection의 UPSERT를 완성한다**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET
    status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = EXCLUDED.updated_at


WHERE
    user_coupon_view.aggregate_version < EXCLUDED.aggregate_version

;
```

### **5. Version 2가 먼저 도착한 경우를 분석한다**

```text
먼저 처리:
CouponCancelled(version=2)

나중 처리:
CouponIssued(version=1)

최종 MyPage status:

`CANCELLED`


최종 aggregate_version:

`2`


version=1 UPSERT의 affected rows:

`0`이다. 기존 `aggregate_version=2`가 더 크므로 `WHERE` 조건을 만족하지 않아 과거 상태가 덮어쓰지 못한다.

```

### **6. 낮은 Version을 생략할 수 있는 범위를 판단한다**

| Consumer | 낮은 Version 생략 가능 여부 | 필요한 전제 또는 추가 순서 정책 |
| --- | --- | --- |
| 완전한 최신 상태만 저장하는 MyPage | 가능 | 최신 상태를 완전하게 표현하는 이벤트여야 한다. 더 큰 Version이 이미 저장되어 있으면 낮은 Version은 UPSERT 조건으로 생략한다. |
| 모든 발급·취소를 집계하는 Analytics | 불가능 | 각 이벤트가 집계에 필요한 사실이므로 낮은 Version이라고 버리면 통계가 빠진다. `eventMessageId` 중복 제거와 Fact 저장이 필요하다. |
| 발급·취소 알림을 각각 보내는 Notification | 일반적으로 불가능 | 모든 상태 전이의 알림이 필요하다면 Version Gap 감지, 버퍼링, 재조회 또는 Replay 정책으로 순서를 관리해야 한다. |

### **7. Version Gap 처리 정책을 작성한다**

현재 Version이 2인데 Version 4가 먼저 도착했다고 가정한다.

```text
Gap으로 판단하는 조건:

현재 저장된 Version이 2인데 들어온 `aggregateVersion`이 4처럼 `currentVersion + 1`보다 큰 경우이다. 아직 Projection이 없는 Aggregate에 Version 1보다 큰 값이 처음 오는 경우도 확인한다.


즉시 반영해도 되는 Consumer:

완전한 최신 상태만 저장하는 MyPage Projection은 version 4가 상태 전체를 포함한다는 전제에서 즉시 반영할 수 있다. 다만 Gap 자체는 관측해야 한다.


모든 전이가 필요한 Consumer의 처리:

Analytics와 Notification처럼 모든 전이가 필요한 Consumer는 version 4를 바로 완료 처리하지 않는다. 누락된 version 3을 보류·버퍼링하고, 재시도 또는 원본 조회 후 연속된 순서로 처리한다.


복구 방법:

같은 Group의 Offset Replay, 보관된 Topic 재소비, 원본 DB나 이벤트 저장소에서 누락 Version 재조회 후 재처리를 사용한다. 해결되지 않은 Gap은 오류·지연 지표와 함께 운영자가 확인한다.

```

### **8. 이벤트 스키마 변경의 호환성을 판단한다**

| 변경 | 호환 가능성 | 이유와 배포 방법 |
| --- | --- | --- |
| 선택 필드 `couponDisplayName` 추가 | 대체로 호환 가능 | 기존 Consumer가 알 수 없는 필드를 무시하고 새 Consumer가 optional/null을 처리한다는 전제다. Consumer를 먼저 호환되게 배포한 뒤 Producer가 필드를 발행한다. |
| 기존 `userId` 필드 삭제 | 호환되지 않음 | 기존 Consumer가 필수 필드를 읽지 못한다. 폐기 기간을 두거나 새 `schemaVersion`·새 이벤트 타입을 병행해야 한다. |
| `userId` 의미를 이메일 주소로 변경 | 호환되지 않음 | 필드 타입이 같아도 의미가 바뀌면 기존 Consumer가 사용자 식별자로 잘못 처리한다. 새 필드를 추가하거나 새 Version으로 분리한다. |

| 불필요한 전화번호와 비밀번호를 이벤트에 추가 | 사용하면 안 됨 | 이벤트는 여러 Consumer와 보관소에 복제될 수 있다. 데이터 최소화 원칙을 지키고 비밀번호는 절대 넣지 않으며 불필요한 개인정보는 제외한다. |

## **과제 8. Read Model 재구축과 운영 지표 설계하기**

### **1. 원본 데이터와 파생 데이터를 구분한다**

| 데이터 | Source of Truth인가? | 삭제 후 재구축 가능한가? | 재구축 근거 |
| --- | --- | --- | --- |
| Coupon Service `coupon_issue` | 예 | 원장 자체는 삭제 후 Projection처럼 재구축하면 안 된다. 백업·복구 대상으로 보존해야 한다. | 쿠폰 발급의 최종 DB 원장이다. |
| MyPage `user_coupon_view` | 아니오 | 가능 | Coupon Service `coupon_issue` Snapshot과 보관 중인 `CouponIssued`·상태 이벤트 |
| Analytics `coupon_issue_fact` | 아니오 | 가능 | Coupon Service 원본 발급 사실과 보관 중인 이벤트 |
| Analytics `coupon_issue_stats` | 아니오 | 가능 | 중복 없이 저장된 `coupon_issue_fact`를 `COUNT`하여 다시 계산 |

### **2. `user_coupon_view_v2` 재구축 순서를 작성한다**

다음 단계를 안전한 순서로 배치하고 각 단계의 목적을 설명한다.

```text
새 Projection 테이블 생성
원본 DB Snapshot Backfill
새 Consumer Group으로 Kafka Replay
Backfill 경계 이후 이벤트 Catch-up
원본과 v2 정합성 검증
조회 API 전환
기존 Projection 보관 또는 제거
```

```text
1.

`user_coupon_view_v2` 테이블과 필요한 PK, UNIQUE, 조회 인덱스를 새로 만든다. 기존 Projection을 건드리지 않아 언제든 되돌릴 수 있게 한다.

2.

원본 DB의 일관된 Snapshot 기준과 이벤트 경계(예: Outbox ID 또는 Kafka Offset)를 기록하고, 그 경계까지의 `coupon_issue`를 v2에 Backfill한다. Snapshot과 이후 이벤트의 빈 구간을 남기지 않는 것이 목적이다.

3.

새 `mypage-coupon-projection-v2` Consumer Group으로 기록한 경계부터 Kafka를 Replay한다. 보관 기간 안의 이전 이벤트도 다시 읽는 경우에는 `eventMessageId` 멱등성과 Version UPSERT로 중복·과거 덮어쓰기를 방어한다.

4.

Backfill 경계 뒤에 새로 발생한 이벤트를 계속 Catch-up한다. v2 Group의 Lag이 0에 가깝고 Snapshot 이후의 변경까지 반영될 때까지 기존 조회는 v1을 사용한다.

5.

Coupon Service 원장과 v2의 건수, 사용자별 목록, 상태·Version을 비교하여 정합성을 검증한다. 불일치 건은 원인을 확인하고 다시 Backfill 또는 Replay한다.

6.

검증이 끝나면 조회 API의 읽기 대상을 `user_coupon_view_v2`로 전환한다. 전환은 설정 또는 짧은 배포 단위로 원자적으로 수행한다.

7.

기존 `user_coupon_view`는 롤백 기간 동안 보관하고, v2가 안정적으로 운영된 뒤에만 정리한다.
```

### **3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다**

```text
Kafka만으로 전체 Replay가 가능한가?

불가능할 수 있다. Topic 보관 기간이 지난 Record는 Kafka에서 사라졌으므로 Offset을 처음으로 되돌려도 모든 과거 발급 사실을 얻지 못한다.


필요한 다른 복구 기준:

Coupon Service의 `coupon_issue` 원본 DB Snapshot, 백업 또는 별도 장기 보관 이벤트 저장소가 필요하다. Read Model은 원본 발급 사실에서 다시 만들 수 있어야 한다.


Backfill 중 새 이벤트가 들어올 때 필요한 경계:

Snapshot이 포함하는 마지막 원본 상태와 Kafka Replay가 시작할 위치를 연결하는 경계가 필요하다. 같은 경계를 기준으로 이후 이벤트를 Catch-up해야 Snapshot 이후 변경이 유실되지 않는다.

```

### **4. 운영 지표를 완성한다**

| 지표 | 의미 | 장애 신호 예시 |
| --- | --- | --- |
| Group별 Consumer Lag | Group의 최신 Kafka Offset과 Committed Offset 차이 | MyPage Group Lag이 계속 증가하거나 복구 후 줄지 않는다. |

## **과제 9. 잘못된 EDA 구현 리뷰하기**

다음 코드는 의도적으로 여러 문제가 포함되어 있다.

```java
@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void notify(CouponIssuedEvent event) {
    smsClient.send(event.userId(), "쿠폰 발급 완료");
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateMyPage(
    CouponIssuedEvent event,
    Acknowledgment acknowledgment
) {
    acknowledgment.acknowledge();

    if (processedEventRepository.existsById(
        event.kafkaOffset()
    )) {
        return;
    }

    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(event.kafkaOffset())
    );
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateAnalytics(CouponIssuedEvent event) {
    statisticsRepository.increaseIssuedCount(
        event.couponEventId()
    );
}
```

### **1. 문제를 최소 10개 찾는다**

각 문제를 다음 표에 작성한다.

| 번호 | 문제 코드 | 발생 가능한 장애 또는 데이터 오류 | 수정 방향 |
| ---: | --- | --- | --- |
| 1 | 세 Listener가 모두 `groupId = "coupon-result"`를 사용한다. | 한 Record가 세 서비스에 모두 전달되지 않고 한 Listener에만 할당되어 알림·쿠폰함·통계 중 일부가 누락된다. | Notification, MyPage, Analytics에 서로 다른 논리 Group ID를 사용한다. |
| 2 | `notify()`가 Consumer에서 `smsClient.send()`를 직접 호출한다. | SMS 성공 뒤 처리 기록 저장 전 종료 시 재전달되어 중복 발송되고, 반대 순서면 발송 유실이 생긴다. | Consumer는 `notification_job`만 저장하고 별도 Sender가 전송한다. |
| 3 | `acknowledgment.acknowledge()`가 DB 변경보다 먼저 호출된다. | DB 저장 실패 후에도 Offset이 넘어가 Record가 재전달되지 않아 MyPage가 영구 누락될 수 있다. | 자동 Commit을 끄고 Consumer DB Commit 뒤에만 Offset을 완료한다. |
| 4 | `existsById()` 후 `save()`로 중복을 확인한다. | 두 Consumer가 동시에 `exists=false`를 보고 둘 다 저장하는 Race Condition이 발생한다. | DB PK/UNIQUE와 `INSERT ... ON CONFLICT DO NOTHING RETURNING`으로 최초 처리 권한을 원자적으로 얻는다. |
| 5 | `event.kafkaOffset()`을 처리 기록 Key로 사용한다. | 같은 `eventMessageId`가 재발행되면 다른 Offset을 가지므로 중복 이벤트를 막지 못한다. | 논리 이벤트 ID인 `eventMessageId`를 `processed_event` Key로 사용한다. |
| 6 | `userCouponViewRepository.save()`와 `processedEventRepository.save()` 사이에 하나의 트랜잭션이 보이지 않는다. | 조회 모델만 저장되거나 처리 기록만 저장될 수 있어 재전달 때 중복 또는 영구 누락이 생긴다. | `processed_event`와 `user_coupon_view` 변경을 하나의 로컬 DB 트랜잭션으로 Commit한다. |
| 7 | Notification에 `notification_job`, 발송 상태, 안정적인 `notificationId`가 없다. | SMS 재시도와 성공 여부 추적이 불가능하고 외부 Provider 장애를 복구하기 어렵다. | 알림 작업 테이블과 Sender, Provider Idempotency Key, 상태 전이를 둔다. |
| 8 | Analytics가 `issued_count = issued_count + 1`만 수행한다. | At-Least-Once 전달이나 Replay마다 통계가 중복 증가한다. | `coupon_issue_fact`를 중복 없이 INSERT한 경우에만 같은 트랜잭션에서 집계를 증가한다. |
| 9 | `aggregateVersion`과 최신 상태 조건을 전혀 확인하지 않는다. | 취소 후 늦게 도착한 발급 이벤트가 MyPage 상태를 다시 `ISSUED`로 덮어쓸 수 있다. | 같은 `couponIssueId` Key와 Version 조건 UPSERT로 과거 상태를 막고 Gap 정책을 둔다. |
| 10 | Listener 예외, Retry/DLQ, Group Lag, 처리 실패·중복 지표가 없다. | 실패한 Record와 장기 지연을 발견·복구하지 못하고 사용자 쿠폰함 불일치가 오래 지속된다. | 예외는 Offset 완료 없이 전파하고, Group별 Lag·Delay·Failure·Duplicate 지표와 재처리 정책을 운영한다. |

### **2. 반드시 찾아야 하는 문제를 연결한다**

| 검토 항목 | 문제가 있는 코드 | 수정 방향 |
| --- | --- | --- |
| 세 서비스가 같은 Group ID 사용 | 세 `@KafkaListener`의 `groupId = "coupon-result"` | 서비스마다 독립 Group과 Offset을 사용한다. |
| 외부 SMS 직접 호출의 Dual Write | `smsClient.send(...)` | `processed_event + notification_job`을 저장하고 Sender가 Provider를 호출한다. |

| `exists` 후 `save` Race Condition | `existsById(...)` 뒤 `processedEventRepository.save(...)` | DB 제약과 `ON CONFLICT DO NOTHING RETURNING`을 사용한다. |
| Kafka Offset을 멱등성 Key로 사용 | `event.kafkaOffset()` | 불변 논리 ID인 `eventMessageId`를 사용한다. |
| 조회 모델과 processed 기록의 원자성 없음 | 두 Repository `save()`가 별도 호출 | 하나의 DB 트랜잭션에서 함께 Commit/Rollback한다. |
| Analytics `+1` 중복 반영 | `increaseIssuedCount(...)` | Fact INSERT 성공일 때만 집계를 +1 한다. |
| 이벤트 Version과 순서 방어 없음 | `UserCouponView.from(event)`에 Version 검사 없음 | `aggregateVersion` 조건 UPSERT와 Gap 정책을 둔다. |
| 서비스별 데이터 소유권 불명확 | 공통 `coupon-result` Group과 Repository 호출 | 서비스별 Consumer·DB·Projection의 책임을 분리하고 다른 DB를 직접 수정하지 않는다. |
| 실패·Lag 관측 정보 없음 | 세 Listener에 오류 처리와 지표 기록 없음 | Handler 실패, Lag, Oldest Age, Delay, Duplicate 지표와 Retry/DLQ를 운영한다. |

| 항목 | 보장/조건부 보장/보장하지 않음 | 이유 |
| --- | --- | --- |
| 쿠폰 발급 DB의 최종 성공 | 조건부 보장 | Coupon Service가 발급 원장과 Outbox를 한 DB 트랜잭션으로 Commit하면 후속 Consumer 실패와 독립적으로 `ISSUED`를 유지한다. |

| Kafka Record의 물리적 Exactly-Once | 보장하지 않음 | Outbox 재발행, DB Commit 후 Offset Commit 전 종료로 같은 논리 이벤트가 다시 전달될 수 있다. |

| 외부 SMS Exactly-Once | 보장하지 않음 | 로컬 DB와 외부 Provider는 하나의 원자적 트랜잭션이 아니다. Provider Idempotency Key가 있어도 Provider의 보장 범위에 의존한다. |
| 발급 직후 MyPage의 즉시 일치 | 보장하지 않음 | Coupon Service DB와 MyPage Projection은 별도 Consumer 처리 경로이므로 DB Commit 뒤 반영 지연이 가능하다. |

## **보너스 2. Projection 재구축 테스트 설계하기**

| 테스트 상황 | 준비 데이터 | 실행 방법 | 검증할 결과 |
| --- | --- | --- | --- |
| 동일 이벤트 2회 Replay | 같은 `eventMessageId`, 서로 다른 Offset의 `CouponIssued` 두 건 | 새 Group으로 두 Record를 순서대로 소비한다. | `processed_event`와 `user_coupon_view`는 한 번만 반영되고 Duplicate Count만 증가한다. |
| Version 2 뒤 Version 1 전달 | 같은 `couponIssueId`의 `CANCELLED(v2)`, `ISSUED(v1)` | v2를 먼저 전달한 뒤 v1을 전달한다. | View는 `CANCELLED`, `aggregate_version=2`를 유지하고 v1 UPSERT affected rows는 0이다. |
| Backfill 중 새 이벤트 유입 | Snapshot 경계 전 원장과 경계 후 새 발급·취소 이벤트 | v2 Backfill 중 경계를 기록하고 새 Group으로 이후 Record를 Catch-up한다. | Snapshot 이후 이벤트가 유실되지 않고 v2가 원본 최신 상태와 일치한다. |
| Kafka 보관 기간 이전 데이터 존재 | Kafka에서 만료된 과거 발급 건과 Coupon Service 원본 DB | Kafka Replay만 수행한 결과와 원본 Snapshot Backfill 결과를 비교한다. | Replay만으로는 누락되고, 원본 Snapshot을 포함한 v2는 전체 원장과 일치한다. |
| Consumer DB Commit 직후 종료 | 최초 이벤트와 Commit 후 Ack 전 강제 종료 지점 | DB Commit 뒤 Offset Commit 전에 Consumer를 종료하고 재시작한다. | 같은 Record가 재전달되지만 처리 기록으로 View는 중복되지 않고 이후 Offset이 완료된다. |

한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유도 작성한다.

```text

정상 실행은 중복 전달, Offset 재시작, 순서 역전, Version Gap, Backfill 경계, DB Commit과 Offset Commit 사이의 장애를 검증하지 못한다.

Projection은 재시도와 Replay가 가능한 환경에서 동작하므로 위와 같은 실패 경로를 포함한 테스트로 멱등성·순서 방어·재구축 안전성을 확인해야 한다.

```

# **8. 핵심 질문**

과제를 마친 뒤 다음 질문에 한 문장씩 답한다.

```text
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?

서로 다른 Group은 각자 모든 `CouponIssued`를 독립 Offset으로 소비하지만, 같은 Group의 Consumer는 Record를 나누어 처리하므로 세 후속 작업을 모두 수행할 수 없기 때문이다.


2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?

`CouponIssued`는 발급 DB가 Commit된 뒤의 과거 사실이어야 Notification, MyPage, Analytics가 쿠폰을 다시 발급하지 않고 각자의 후속 작업만 수행할 수 있기 때문이다.


3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?

수량과 중복 불변식을 보장하며 실제 발급 기록을 Commit하는 Coupon Service의 `coupon_issue`가 최종 기준이고, MyPage Read Model은 재구축 가능한 조회용 파생 데이터이다.


4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?

Outbox 발행 성공 뒤 상태 변경 전 장애나 운영 Replay로 같은 논리 이벤트가 Kafka에 다시 저장되면 새 물리 Record와 다른 Offset을 가지기 때문이다.


5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?

처리 기록만 Commit되고 비즈니스 변경이 실패하면 재전달 때 영구 누락되므로, 둘이 함께 Commit되거나 함께 Rollback되어야 하기 때문이다.


6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?

Coupon Service DB Commit 뒤 Outbox 발행과 MyPage Consumer의 별도 DB Commit이 이어지므로 그 사이에는 원장만 먼저 확정된 최종적 일관성 지연이 존재하기 때문이다.


7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?

`aggregateVersion`은 논리 순번을 알려 주는 값일 뿐 Publisher 재시도나 여러 Publisher 때문에 Kafka 저장 순서를 바꾸지 않으므로 Consumer의 Version 비교·Gap 정책이 추가로 필요하다.


8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?

MyPage처럼 최신 상태만 필요한 Projection과 달리 Analytics와 Notification은 각 발급·취소 사실과 상태 전이가 모두 필요하므로 낮은 Version을 단순히 버리면 통계나 알림이 빠질 수 있기 때문이다.


9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?

Projection 버그, 배포 오류, Kafka Replay, 스키마 변경으로 파생 데이터가 틀어질 수 있으므로 원본 발급 사실을 기준으로 안전하게 복구할 수 있어야 한다.


10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?

알림 장애는 이미 `ISSUED`인 원본 발급과 독립된 후속 작업의 실패이므로 발급을 재실행하면 중복 발급이나 수량 정합성 오류를 만들 수 있기 때문이다.
```
