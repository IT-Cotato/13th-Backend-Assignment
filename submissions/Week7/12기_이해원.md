# 7주차 과제: EDA 기반 서비스 분리와 조회 구조

## **과제 1. 직접 호출 구조와 EDA 비교하기**

Coupon Service가 쿠폰 발급 뒤 세 서비스를 순서대로 호출한다고 가정한다.

```text
Coupon Service
  |
  +--> Notification Service
  |
  +--> MyPage Service
  |
  +--> Analytics Service
```

### **1. 직접 호출 구조의 결합을 분석한다**

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 호출 시점에 상대 서비스가 반드시 실행 중이어야 한다. | Kafka가 이벤트를 보관하므로 Consumer가 나중에 실행되어도 처리할 수 있다. |
| 장애 결합 | 상대 서비스의 지연과 장애가 호출자에게 전파된다. | Consumer 장애가 발급 흐름에 전파되지 않고 해당 Group만 밀린다. |
| 변경 결합 | 후속 서비스 추가·변경 시 발급 코드도 바뀐다. | Producer는 Consumer 수와 구현을 몰라도 되어 발급 코드가 바뀌지 않는다. |
| 데이터 결합 | 다른 서비스의 테이블이나 내부 모델에 직접 의존하기 쉬워진다. | 이벤트 스키마 계약으로만 연결되어 내부 모델 의존이 사라진다. |

### **2. 다음 장애 상황을 분석한다**

```text
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```text
이미 확정된 쿠폰 발급 상태:
coupon_issue가 저장되고 request가 ISSUED로 Commit된 최종 발급 성공 상태다.

쿠폰 발급을 Rollback하면 안 되는 이유:
알림은 발급 성공 사실에 대한 후속 작업일 뿐이며 알림 실패는 발급 정합성과 무관하다.
이미 확정된 발급을 되돌리면 수량과 발급 기록이 훼손되고 사용자에게 안내된 발급이 뒤집힌다.

다시 실행해야 하는 작업:
실패한 Notification 작업 (알림 전송만 재시도)

다시 실행하면 안 되는 작업:
쿠폰 발급 자체 (issued_count 증가, coupon_issue INSERT)
```

### **3. EDA 기반 전체 흐름을 완성한다**

다음 구성 요소를 모두 포함한다.

```text
Coupon Issue DB Transaction
CouponIssued Outbox
Outbox Publisher
Kafka coupon.issued
Notification Consumer
MyPage Consumer
Analytics Consumer
```

```text
Coupon Issue DB Transaction
  | coupon_issue 저장 + request ISSUED + CouponIssued Outbox 저장
  | Commit
  v
CouponIssued Outbox (PENDING)
  |
  v
Outbox Publisher
  |
  v
Kafka coupon.issued
  |
  +--> Notification Consumer (group: notification-coupon-issued)
  |
  +--> MyPage Consumer       (group: mypage-coupon-projection)
  |
  +--> Analytics Consumer    (group: analytics-coupon-issued)
```

### **4. 명령과 이벤트의 차이를 작성한다**

| 이름 | 종류 | 의미 | Consumer가 쿠폰을 다시 발급하는가? |
| --- | --- | --- | --- |
| `IssueCoupon` | 명령 (Command) | 쿠폰을 발급하라는 요청 | 예 (아직 발급되지 않음) |
| `CouponIssued` | 이벤트 (Event) | 쿠폰이 이미 발급되었다는 과거의 사실 | 아니오 (후속 작업만 수행) |

### **5. EDA를 사용해도 남는 결합을 설명한다**

```text
직접 API 계약 대신 남는 계약:
이벤트 스키마 계약 (CouponIssued의 필드와 의미)

이 계약을 관리해야 하는 이유:
여러 Consumer가 독립 배포된 상태로 같은 이벤트를 사용하므로 기존 필드의 의미를 바꾸거나 삭제하면 Consumer가 깨진다.
따라서 필드를 호환성 있게 추가하고 버전으로 관리해야 한다.

EDA가 반드시 MSA를 의미하지 않는 이유:
하나의 애플리케이션 안에서도 모듈과 Consumer 책임을 논리적으로 나눌 수 있다.
서비스 분리는 실행 프로세스나 저장소 분리와 별개의 선택이다.
```

## **과제 2. Consumer Group과 서비스 책임 설계하기**

### **1. 서비스별 Consumer Group을 작성한다**

| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | notification-coupon-issued | 사용자에게 발급 완료 알림 전송 |
| MyPage | mypage-coupon-projection | 사용자 쿠폰 조회 모델(user_coupon_view) 갱신 |
| Analytics | analytics-coupon-issued | 발급 사실 저장과 발급 통계 집계 |

### **2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다**

```text
같은 Group 안의 Consumer 관계:
같은 Group의 Consumer들은 Partition을 나누어 Record를 분담 처리하며 브로드캐스트되지 않는다.

CouponIssued 한 건의 전달 결과:
한 건은 Group 안의 한 Consumer 인스턴스에만 전달된다.

세 서비스 중 일부 작업이 누락될 수 있는 이유:
세 서비스를 같은 Group에 넣으면 한 이벤트를 세 서비스가 각각 처리하는 것이 아니라 셋 중 하나의 인스턴스만 처리한다.
그래서 알림·조회 모델·통계 중 나머지 작업이 누락된다.
```

### **3. 다음 Partition과 Consumer 배치를 분석한다**

```text
coupon.issued Partition 수: 6

notification-coupon-issued Consumer 수: 2
mypage-coupon-projection Consumer 수: 4
analytics-coupon-issued Consumer 수: 1
```

| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | ---: | --- | --- |
| Notification | 2 | Consumer 2개가 각 3개 Partition 담당, 유휴 없음 | 없음 (Group별 Offset 독립) |
| MyPage | 4 | Consumer 4개가 6개 Partition 분담, 유휴 Consumer 없음 | 없음 |
| Analytics | 1 | Consumer 1개가 6개 Partition 모두 담당, 병렬성 낮음 | 없음 |

### **4. Consumer Group의 Committed Offset 의미를 설명한다**

```text
Committed Offset이 나타내는 것:
해당 Group이 각 Topic-Partition에서 어디까지 처리 완료로 기록했는지 나타내는 재시작 지점이다.

Committed Offset만으로 증명할 수 없는 것:
개별 이벤트의 비즈니스 처리가 실제로 정상 반영되었는지, 중복 없이 처리되었는지는 증명하지 못한다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
주지 않는다. Group마다 Offset을 독립 관리하므로 Notification이 밀려도 MyPage는 계속 진행한다.
```

### **5. 서비스별 책임과 데이터 소유권을 완성한다**

| 서비스 | 소유하는 데이터 | 보장해야 하는 불변식 또는 책임 | 다른 서비스 DB 직접 수정 허용 여부 |
| --- | --- | --- | --- |
| Coupon Service | coupon_event, coupon_issue, 요청 상태 | 수량 초과·사용자 중복 방지, 발급 확정 | 불가 |
| Notification Service | 알림 작업(notification_job), 발송 상태 | 발급 사실을 사용자에게 전달, 중복 발송 방어 | 불가 |
| MyPage Service | 사용자 쿠폰 조회 모델(user_coupon_view) | 조회 모델의 중복·순서 역전 방어 | 불가 |
| Analytics Service | 발급 사실(coupon_issue_fact), 집계 결과 | 이중 집계 방지, 통계 재구축 가능성 | 불가 |

### **6. 장애 격리 결과를 작성한다**

| 장애 | 쿠폰 발급 결과 | 영향받는 기능 | 영향받지 않아야 하는 기능 | 복구 단위 |
| --- | --- | --- | --- | --- |

| MyPage Consumer 중단 | ISSUED 유지 | 마이페이지 쿠폰함 반영 | 발급, 알림, 통계 | MyPage Group 재처리 |
| Analytics Consumer 중단 | ISSUED 유지 | 발급 통계 갱신 | 발급, 알림, 마이페이지 | Analytics Group 재처리 |

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 정확한 쓰기와 불변식 보장 | 화면에 맞는 빠른 조회 응답 |
| 대표 작업 | 발급 요청 처리, 수량·중복 검사 | 마이페이지 목록·통계 조회 |
| 데이터 구조 | 정규화된 쓰기 최적 구조 | 비정규화된 조회 최적 구조 |
| 최종 원장 여부 | 예 (Source of Truth) | 아니오 (파생 데이터) |
| 장애 후 재구축 가능 여부 | 원본이라 재구축 대상 아님 | 원본과 이벤트로 재구축 가능 |

### **2. CQRS에 대해 다음 문장을 판단한다**

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 물리적 DB 분리는 구현 선택이며 같은 DB에서도 모델을 나눌 수 있다. |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 명령·조회 모델 분리이고 Event Sourcing은 별개의 저장 방식이다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 처리 경로와 모델만 명확히 나누면 CQRS가 성립한다. |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 처리 경로와 모델 책임 분리가 없으면 이름만 다른 테이블일 뿐이다. |

### **3. `user_coupon_view` DDL을 완성한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id Primary Key
user_id와 coupon_event_id 저장
현재 status와 aggregate_version 저장
issued_at과 updated_at 저장
같은 사용자·이벤트의 중복 노출 방지
사용자별 최신 쿠폰 조회 인덱스
```

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### **4. 각 제약과 인덱스의 역할을 작성한다**

| 장치 | 막거나 개선하는 문제 |
| --- | --- |
| `PRIMARY KEY (coupon_issue_id)` | 같은 발급 건이 두 번 저장되는 것을 막는다. |
| `UNIQUE (user_id, coupon_event_id)` | 같은 사용자·이벤트 쿠폰이 조회 모델에 중복 노출되는 것을 막는다. |
| `(user_id, issued_at DESC)` Index | 사용자별 최신 쿠폰 목록 조회를 빠르게 한다. |

### **5. 다음 조회 API가 Read Model을 사용하는 이유를 설명한다**

```text
GET /api/users/{userId}/coupons
```

```text
원본 발급 DB를 매번 복잡하게 조회할 때의 문제:
여러 테이블 조인이나 다른 서비스 API 호출이 필요해 조회가 복잡하고 느려지며 조회 부하가 발급 쓰기 경로에 영향을 준다.

Read Model에 일부 데이터가 중복되어도 되는 이유:
비정규화로 화면에 필요한 값을 미리 모아 두면 조회가 단순하고 빨라지기 때문이다.

쿠폰 발급 성공의 최종 기준 데이터:
Coupon Service의 coupon_issue (Read Model은 파생 데이터)
```

### **6. 화면 표시용 데이터 전달 방법을 비교한다**

마이페이지에 `couponDisplayName`과 `discountAmount`가 필요하다고 가정한다.

| 방법 | 장점 | 단점 | 데이터 소유권·장애 결합에 미치는 영향 |
| --- | --- | --- | --- |
| `CouponIssued`에 Snapshot 포함 | 추가 조회 없이 표시값 확보 | 이벤트가 커지고 표시값 변경 반영이 어려움 | 소유권 유지, 동기 결합 없음 |
| `CouponEventCreated/Updated`로 메타데이터 Projection 관리 | 메타데이터를 독립 관리, 최신값 반영 용이 | 별도 이벤트·Projection 설계 필요 | 소유권 유지, 결합 낮음 |
| 이벤트 처리 중 Coupon Service API 동기 호출 | 항상 최신값 조회 | 상대 서비스 장애·지연에 다시 의존 | 장애 결합 재발생 |
| Coupon Service DB 직접 조회 | 구현이 단순해 보임 | 다른 서비스 테이블에 직접 의존 | 데이터 소유권 위반 |

이벤트에 원본 Entity 전체를 넣으면 안 되는 이유도 작성한다.

```text
Consumer가 필요로 하지 않는 필드와 변경 가능성이 큰 내부 필드까지 결합되고 개인정보가 불필요하게 노출된다.
Consumer가 실제로 필요로 하는 안정적인 값만 포함해야 계약이 견고해진다.
```

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```text
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001
```

### **1. Offset과 eventMessageId를 비교한다**

| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka 내 물리적 위치 | 변경됨 | 부적절 (같은 이벤트가 다른 Offset을 가짐) |
| eventMessageId | 논리 이벤트 자체 | 변경 안 됨 | 적절 |

### **2. `processed_event` DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

다음 세 값 중 올바른 `subscriber_id`를 고르고 이유를 작성한다.

```text
pod-a7f9c
server-10.0.0.12
mypage-coupon-projection
```

```text
선택:
mypage-coupon-projection

이유:
pod-a7f9c나 server-10.0.0.12는 배포·재시작·스케일링에 따라 바뀌는 인스턴스 식별자다.
바뀌면 같은 논리 구독자가 다른 subscriber_id로 인식되어 이미 처리한 이벤트를 다시 반영한다.
안정적인 논리 구독자 이름을 써야 인스턴스가 바뀌어도 중복 처리를 막는다.
```

### **3. MyPage Consumer 트랜잭션을 완성한다**

다음 요구사항을 만족해야 한다.

```text
ON CONFLICT DO NOTHING으로 최초 처리 권한 등록
RETURNING 결과로 최초·중복 판별
최초 이벤트일 때만 user_coupon_view 변경
processed_event와 조회 모델 변경의 원자성
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (subscriber_id, event_message_id)
    VALUES ('mypage-coupon-projection', :eventMessageId)
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id, user_id, coupon_event_id,
    status, aggregate_version, issued_at, updated_at
)
SELECT
    :couponIssueId, :userId, :couponEventId,
    :status, :aggregateVersion, :issuedAt, CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```text
PostgreSQL에서 제약 위반이 발생하면 해당 트랜잭션이 aborted 상태가 된다.
이 상태에서는 이후 명령이 모두 거부되고 ROLLBACK만 허용되므로 예외를 잡고 조회 모델 변경을 계속 진행할 수 없다.
따라서 ON CONFLICT DO NOTHING RETURNING으로 트랜잭션을 실패시키지 않고 원자적으로 최초 처리 여부를 판별해야 한다.
```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```text
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```text
재전달 시 Consumer 판단:
processed_event에 이미 기록이 있으므로 이미 처리한 이벤트로 판단한다.

최종 조회 모델 상태:
user_coupon_view 변경이 실패한 채로 남아 조회 모델이 영원히 갱신되지 않는다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
processed_event 저장과 조회 모델 변경이 함께 Commit되거나 함께 Rollback되어야 처리 기록만 남고 실제 반영이 안 된 상태를 막을 수 있다.
```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```text
Consumer DB 상태:
processed_event와 user_coupon_view가 모두 Commit됨

Consumer Group Offset:
미반영

재시작 후 전달:
같은 Record가 재전달됨

재전달된 이벤트 처리:
processed_event INSERT가 충돌해 RETURNING이 빈 결과가 되므로 중복으로 판단하고 비즈니스 변경 없이 정상 종료 후 Offset을 완료한다.
```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```text
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record
```

```text
enable.auto.commit:
false로 두어 DB 결과와 무관한 시점에 자동 커밋되지 않게 한다.

DB Commit과 Offset Commit 순서:
Consumer DB Transaction Commit 후에 Offset을 완료 처리한다.

Listener 예외 처리:
DB 처리 실패 시 예외를 던져 Offset이 완료되지 않고 재전달되게 한다.

같은 Partition 병렬 처리 시 앞선 미완료 Record:
앞선 미완료 Record를 건너뛰고 더 높은 Offset을 먼저 Commit하지 않도록 해 미완료 이벤트가 유실되지 않게 한다.
```

```text
eventMessageId 기준 멱등 방어가 없어 같은 이벤트가 두 번 전달되면 issued_count가 +2로 이중 집계된다.
```

### **5. `coupon_issue_fact` 기반 집계 구조를 설계한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id 중복 저장 방지
event_message_id 추적
coupon_event_id와 user_id 저장
발급 발생 시각 저장
Fact가 실제 INSERT된 경우에만 집계 +1
Fact INSERT와 집계 변경을 같은 트랜잭션으로 처리
```

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE (event_message_id)
);
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id, event_message_id,
        coupon_event_id, user_id, issued_at
    ) VALUES (
        :couponIssueId, :eventMessageId,
        :couponEventId, :userId, :issuedAt
    )
    ON CONFLICT (coupon_issue_id) DO NOTHING
    RETURNING coupon_event_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId
  AND EXISTS (
      SELECT 1 FROM accepted
  );

COMMIT;
```

## **과제 7. 이벤트 순서와 버전 처리하기**

다음 두 이벤트가 같은 `couponIssueId = 5001`에서 발생했다고 가정한다.

### **1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다**

```text
같은 Topic이어야 하는가?
그렇다. 서로 다른 Topic 사이의 순서는 보장되지 않는다.

같은 Key가 보장하는 범위:
같은 Topic의 같은 Partition에 기록된 순서 (안정적 Partition 전략과 발생 순서 발행 전제)

아니다. 모든 사용자의 전역 순서는 보장하지 않는다.

서로 다른 Topic 사이의 순서를 보장하는가?
아니다.
```

### **2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다**

다음을 포함한다.

```text
여러 Publisher
SKIP LOCKED
```

### **3. `schemaVersion`과 `aggregateVersion`을 비교한다**

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |

### **4. 최신 상태 Projection의 UPSERT를 완성한다**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = EXCLUDED.updated_at
WHERE user_coupon_view.aggregate_version < EXCLUDED.aggregate_version;
```

```text
CouponCancelled(version=2)

CouponIssued(version=1)

CANCELLED (version=2가 유지됨)

최종 aggregate_version:
2

version=1 UPSERT의 affected rows:
```

### **7. Version Gap 처리 정책을 작성한다**

현재 Version이 2인데 Version 4가 먼저 도착했다고 가정한다.

```text
Gap으로 판단하는 조건:
현재 version이 2인데 다음으로 기대하는 3이 아니라 4가 도착 (incomingVersion > currentVersion + 1)

즉시 반영해도 되는 Consumer:
최신 상태만 필요한 MyPage (더 높은 버전이므로 최신값으로 갱신)

모든 전이가 필요한 Consumer의 처리:
incomingVersion == currentVersion + 1만 처리하고 Gap이면 보류(재시도·대기)한다.

복구 방법:
빠진 버전 이벤트가 도착하거나 Replay될 때까지 보류한 뒤 순서대로 처리한다.
```

다음 단계를 안전한 순서로 배치하고 각 단계의 목적을 설명한다.

```text
새 Projection 테이블 생성
```

```text
1. 새 Projection 테이블 생성
   → 기존 조회에 영향 없이 재구축 대상을 준비한다.

2. 원본 DB Snapshot Backfill
   → coupon_issue 원본으로 특정 시점까지의 상태를 채운다.

3. 새 Consumer Group으로 Kafka Replay
   → Snapshot 이후 변경을 이벤트로 따라잡는다.

4. Backfill 경계 이후 이벤트 Catch-up
   → 경계 이후 새 이벤트 유입분까지 v2가 따라잡게 한다.

5. 원본과 v2 정합성 검증
   → 건수·상태 불일치를 비교해 재구축 정확성을 확인한다.

6. 조회 API 전환
   → 검증 통과 후 조회 대상을 v2로 전환한다.

7. 기존 Projection 보관 또는 제거
   → 롤백에 대비해 잠시 보관한 뒤 안전하면 정리한다.
```

## **과제 9. 잘못된 EDA 구현 리뷰하기**

다음 코드는 의도적으로 여러 문제가 포함되어 있다.

```java
@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void notify(CouponIssuedEvent event) {
    smsClient.send(event.userId(), "쿠폰 발급 완료");
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateMyPage(
    CouponIssuedEvent event,
    Acknowledgment acknowledgment
) {
    acknowledgment.acknowledge();

    if (processedEventRepository.existsById(
        event.kafkaOffset()
    )) {
        return;
    }

    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(event.kafkaOffset())
    );
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateAnalytics(CouponIssuedEvent event) {
    statisticsRepository.increaseIssuedCount(
        event.couponEventId()
    );
}
```

각 문제를 다음 표에 작성한다.

| 번호 | 문제 코드 | 발생 가능한 장애 또는 데이터 오류 | 수정 방향 |
| ---: | --- | --- | --- |
| 1 | 세 Listener가 groupId="coupon-result" 공유 | 한 이벤트를 셋 중 하나만 처리해 나머지 작업 누락 | 서비스별 서로 다른 Group ID 사용 |

| 5 | event.kafkaOffset()을 멱등성 Key로 사용 | 재발행 시 다른 Offset이라 중복 반영 | eventMessageId를 Key로 사용 |
| 6 | user_coupon_view save와 processed_event save 분리 | 원자성 없어 부분 성공 시 불일치 | 하나의 트랜잭션으로 묶음 |

## **보너스 2. Projection 재구축 테스트 설계하기**

| 테스트 상황 | 준비 데이터 | 실행 방법 | 검증할 결과 |
| --- | --- | --- | --- |
| 동일 이벤트 2회 Replay | 같은 eventMessageId 2건 | Consumer에 2회 전달 | 조회 모델 1건만 반영, 중복 없음 |
| Version 2 뒤 Version 1 전달 | v2, v1 이벤트 | v2 먼저, v1 나중 전달 | 최종 상태 v2 유지, v1 생략 |
| Backfill 중 새 이벤트 유입 | Snapshot + 경계 이후 이벤트 | Backfill 중 새 이벤트 발생 | 경계 이후만 반영, 이중 반영 없음 |
| Kafka 보관 기간 이전 데이터 존재 | 보관 만료 이벤트 | Snapshot Backfill 후 Replay | Snapshot 기준으로 정확히 재구축 |
| Consumer DB Commit 직후 종료 | 정상 이벤트 | Commit 후 Offset 전 강제 종료 | 재전달 시 중복 반영 없이 정상 완료 |

한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유도 작성한다.

```text
정상 경로에서는 중복·순서 역전·장애 재전달 같은 상황이 드러나지 않는다.
멱등성과 순서 방어는 재전달·역전·중간 장애 상황에서만 검증되므로 그 조건을 재현하는 테스트가 있어야 안전성을 증명할 수 있다.
```

# **8. 핵심 질문**

과제를 마친 뒤 다음 질문에 한 문장씩 답한다.

```text
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
같은 Group이면 이벤트를 나누어 처리해 일부 서비스가 누락되므로 각자 전체 이벤트를 받으려면 Group을 분리해야 한다.

2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
발급이 이미 확정된 사실이므로 Consumer가 재발급이 아니라 후속 처리만 하도록 하기 위해서다.

3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
Coupon Service의 coupon_issue이며 Read Model은 파생 데이터다.

4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
Outbox 재발행이나 재전달로 같은 논리 이벤트가 다른 물리적 위치에 저장되기 때문이다.

5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
처리 기록과 실제 반영이 함께 Commit·Rollback되어야 부분 성공으로 인한 불일치를 막기 때문이다.

6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
조회 모델은 이벤트로 나중에 갱신되는 최종적 일관성 구조라 반영 지연이 있기 때문이다.

7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
순서를 재정렬해 주는 값이 아니라 Consumer가 버전을 비교해 방어해야 하는 값이기 때문이다.

8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
집계·알림처럼 모든 상태 전이가 필요한 Consumer는 낮은 버전도 처리해야 하기 때문이다.

9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
버그로 잘못된 값이 쌓이거나 새 Projection이 필요할 때 원본과 이벤트로 재구축해야 하기 때문이다.

10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
```
