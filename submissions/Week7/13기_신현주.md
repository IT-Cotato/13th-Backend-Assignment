## 과제 1. 직접 호출 구조와 EDA 비교하기

### 1. 직접 호출 구조의 결합을 분석한다

```
| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 호출 시점에 상대 서비스가 반드시 실행 중이어야 한다. 상대가 내려가 있으면 호출이 실패한다 | Kafka가 이벤트를 보관하므로 Consumer가 잠시 내려가 있어도 나중에 소비할 수 있다 |
| 장애 결합 | 후속 서비스의 지연·장애가 Coupon Service 응답으로 전파된다 | 후속 서비스 장애는 해당 Consumer Group에만 국한되고 발급에는 영향을 주지 않는다 |
| 변경 결합 | 후속 서비스를 추가·변경할 때마다 발급 코드에 주소·요청형식·장애처리를 추가해야 한다 | Producer는 이벤트만 발행한다. 새 Consumer는 구독만 추가하면 되고 발급 코드는 바뀌지 않는다 |
| 데이터 결합 | 다른 서비스의 테이블·내부 모델에 직접 의존하기 쉬워진다 | 이벤트 스키마 계약으로만 연결되어 상대 내부 구조에 의존하지 않는다 |
```

### 2. 다음 장애 상황을 분석한다

```
이미 확정된 쿠폰 발급 상태:
coupon_issue에 발급 기록이 저장되고 request가 ISSUED로 Commit된 상태.
쿠폰 발급은 이미 최종 성공이다.

쿠폰 발급을 Rollback하면 안 되는 이유:
발급은 이미 DB에 확정된 사실이다. 알림 호출 실패는 발급 사실을 후속 서비스에
전달하지 못한 것일 뿐 발급이 잘못된 것이 아니다.
Rollback하면 수량 원복, 사용자 쿠폰 회수 등 실제로 성공한 거래를 되돌리게 되고,
클라이언트 재시도 시 같은 사용자에게 중복 발급이나 수량 정합성 문제가 생긴다.

다시 실행해야 하는 작업:
실패한 알림 발송(후속 작업). 재시도 대상은 실패한 Notification 작업이다.

다시 실행하면 안 되는 작업:
쿠폰 발급 자체(issued_count 증가, coupon_issue INSERT, request ISSUED).
이미 성공했으므로 재실행하면 중복 발급이 된다.
```

### 4. 명령과 이벤트의 차이를 작성한다

```
| 이름 | 종류 | 의미 | Consumer가 쿠폰을 다시 발급하는가? |
| --- | --- | --- | --- |
| IssueCoupon | 명령(Command) | 쿠폰을 발급하라는 요청. 받는 쪽이 발급 로직을 실행해야 한다 | 그렇다. 발급을 수행하는 명령이다 |
| CouponIssued | 이벤트(Event) | 쿠폰이 발급되었다는 이미 확정된 과거의 사실 | 아니다. 발급 사실에 대한 후속 처리만 한다 |
```

### 5. EDA를 사용해도 남는 결합을 설명한다

```
직접 API 계약 대신 남는 계약:
이벤트 스키마 계약(CouponIssued의 필드 구성과 의미).
Producer와 Consumer는 이 스키마를 통해 연결된다.

이 계약을 관리해야 하는 이유:
이벤트는 여러 Consumer가 공유하는 공용 계약이다.
필드 의미를 바꾸거나 삭제하면 독립 배포된 Consumer가 깨진다.
따라서 필드는 호환성 있게 추가·관리하고, 호환 불가 변경은 새 schemaVersion이나
새 이벤트 타입으로 다룬다.

EDA가 반드시 MSA를 의미하지 않는 이유:
EDA는 이벤트로 작업을 분리하는 방식이지 서버·배포 단위를 나누는 것이 아니다.
하나의 애플리케이션 안에서도 모듈과 Consumer 책임을 나눠 이벤트로 연결할 수 있고,
필요할 때 실행 프로세스나 저장소를 분리할 수 있다.
```

## 과제 2. Consumer Group과 서비스 책임 설계하기

### 1. 서비스별 Consumer Group을 작성한다

```
| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | notification-coupon-issued | 발급 알림 작업 생성 후 외부 Provider로 발송 |
| MyPage | mypage-coupon-projection | user_coupon_view 조회 모델 갱신 |
| Analytics | analytics-coupon-issued | coupon_issue_fact 저장 및 발급 통계 집계 |
```

### 2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다

```
같은 Group 안의 Consumer 관계:
같은 Group의 Consumer들은 하나의 논리적 구독 단위이며 Partition을 나누어
Record를 분담 처리한다. 같은 Record를 여러 인스턴스가 함께 받지 않는다.

CouponIssued 한 건의 전달 결과:
그 Record는 Group 안에서 해당 Partition을 맡은 하나의 Consumer에게만 전달된다.
Notification/MyPage/Analytics가 한 Group이면 셋 중 하나만 그 이벤트를 받게 된다.

세 서비스 중 일부 작업이 누락될 수 있는 이유:
Group 안에서는 Record가 브로드캐스트되지 않고 한 인스턴스에만 할당되므로,
같은 Group에 넣으면 알림·조회모델·통계 중 일부만 실행되고 나머지는 그 이벤트를
받지 못해 누락된다. 세 작업을 모두 받으려면 서로 다른 Group ID를 써야 한다.
```

### 3. 다음 Partition과 Consumer 배치를 분석한다

```
| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | --- | --- | --- |
| Notification | 2 (Consumer 2 ≤ Partition 6) | 없음. Consumer 2개가 각각 3개 Partition 담당 | 없음. Group마다 Offset 독립 |
| MyPage | 4 (Consumer 4 ≤ Partition 6) | 없음. 다만 6개 중 2개 Partition은 한 Consumer가 2개씩 맡아 부하 불균형 가능 | 없음 |
| Analytics | 1 (Consumer 1) | Consumer가 1개뿐이라 6개 Partition을 혼자 담당. 병렬성 없음(미사용 Partition은 없음) | 없음 |
```

### 4. Consumer Group의 Committed Offset 의미를 설명한다

```
Committed Offset이 나타내는 것:
그 Group이 각 Topic-Partition에서 다음에 읽기 시작할 위치.
즉 그 Offset 이전까지는 완료 처리했다고 표시한 지점이다.

Committed Offset만으로 증명할 수 없는 것:
후속 비즈니스 작업(알림 발송, 외부 API 호출 등)이 실제로 성공했는지는 증명하지 못한다.
Offset은 소비 위치일 뿐이고, 처리 성공 여부는 Consumer의 로컬 DB Commit이 기준이다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
주지 않는다. Group마다 Offset을 독립적으로 관리하므로
Notification 처리가 밀려도 MyPage와 Analytics는 각자 진행할 수 있다.
```

### 5. 서비스별 책임과 데이터 소유권을 완성한다

```
| 서비스 | 소유하는 데이터 | 보장해야 하는 불변식 또는 책임 | 다른 서비스 DB 직접 수정 허용 여부 |
| --- | --- | --- | --- |
| Coupon Service | coupon_event, coupon_issue, coupon_issue_request | 발급 수량 초과 방지, 사용자 중복 발급 방지, 발급 확정 | 허용 안 됨 |
| Notification Service | 알림 작업(notification_job), 발송 상태 | 발급 사실을 사용자에게 전달, 알림 중복 발송 방어 | 허용 안 됨 |
| MyPage Service | 사용자별 쿠폰 조회 모델(user_coupon_view) | 조회 모델을 원본 사실과 최종적으로 일치시킴 | 허용 안 됨 |
| Analytics Service | 발급 사실(coupon_issue_fact), 집계(coupon_issue_stats) | 발급 사실을 한 번만 집계, 통계 재구축 가능 | 허용 안 됨 |
```

### 6. 장애 격리 결과를 작성한다

```
| 장애 | 쿠폰 발급 결과 | 영향받는 기능 | 영향받지 않아야 하는 기능 | 복구 단위 |
| --- | --- | --- | --- | --- |
| Notification Consumer 중단 | ISSUED 유지 | 발급 알림 발송 지연 | 발급, 마이페이지, 통계 | Notification Group에서 재처리 |
| MyPage Consumer 중단 | ISSUED 유지 | 마이페이지 쿠폰함 반영 지연 | 발급, 알림, 통계 | MyPage Group에서 재처리 |
| Analytics Consumer 중단 | ISSUED 유지 | 통계·대시보드 갱신 지연 | 발급, 알림, 마이페이지 | Analytics Group에서 재처리 |
```

## 과제 3. CQRS와 MyPage Read Model 설계하기

### 1. Command Model과 Read Model을 비교한다

```
| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 발급 요청 처리와 불변식 보장 | 화면에 필요한 형태로 빠른 조회 응답 |
| 대표 작업 | 수량 확보, 발급 기록 저장, 상태 전이 | 사용자별 쿠폰 목록 조회 |
| 데이터 구조 | 정확한 쓰기에 맞춘 정규화 구조 | 조회에 맞춘 비정규화 구조(일부 중복 허용) |
| 최종 원장 여부 | 그렇다(Source of Truth) | 아니다(파생 데이터) |
| 장애 후 재구축 가능 여부 | 원본이라 재구축 대상 아님 | 원본 이벤트/Snapshot으로 재구축 가능 |
```

### 2. CQRS에 대해 다음 문장을 판단한다

```
| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 물리적 DB 분리는 구현 선택. 같은 DB에서도 모델·경로 분리로 CQRS 가능 |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | CQRS는 Command/Query 분리이고 Event Sourcing은 상태를 이벤트로 저장하는 별개 기법 |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 하나의 앱 안에서 처리 경로와 모델을 나누면 CQRS 적용 가능 |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 처리 경로와 모델의 책임 분리가 핵심. 이름만 나눈다고 CQRS가 아님 |
```

### 3. `user_coupon_view` DDL을 완성한다

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uk_user_coupon_view_user_event
        UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### 4. 각 제약과 인덱스의 역할을 작성한다

```
| 장치 | 막거나 개선하는 문제 |
| --- | --- |
| PRIMARY KEY (coupon_issue_id) | 같은 발급 건을 두 번 저장하는 것을 막는다(발급 단위 유일성) |
| UNIQUE (user_id, coupon_event_id) | 한 이벤트에 대해 같은 사용자의 쿠폰이 중복 노출되는 것을 추가로 막는다 |
| (user_id, issued_at DESC) Index | 사용자별 최신 쿠폰 목록 조회를 빠르게 한다 |
```

### 5. 다음 조회 API가 Read Model을 사용하는 이유를 설명한다

```
원본 발급 DB를 매번 복잡하게 조회할 때의 문제:
마이페이지 조회마다 여러 테이블 조인이나 다른 서비스 API 호출이 필요해
조회가 복잡하고 느려진다. 조회 트래픽이 발급 원장(Write Model)에 부하를 주고,
데이터 소유권도 흐려진다.

Read Model에 일부 데이터가 중복되어도 되는 이유:
Read Model은 화면에 필요한 값을 미리 모아 둔 비정규화 데이터다.
일부 중복이 있어도 조회가 단순·빠르면 목적에 부합하며, 파생 데이터라
원본으로 언제든 재구축할 수 있다.

쿠폰 발급 성공의 최종 기준 데이터:
Coupon Service의 coupon_issue(그리고 request ISSUED).
user_coupon_view는 파생 조회 모델이지 발급 여부의 원본이 아니다.
```

### 6. 화면 표시용 데이터 전달 방법을 비교한다

```
| 방법 | 장점 | 단점 | 데이터 소유권·장애 결합에 미치는 영향 |
| --- | --- | --- | --- |
| CouponIssued에 Snapshot 포함 | 이벤트 하나로 표시값까지 확보. 추가 조회 불필요 | 이벤트 크기 증가, 메타데이터 변경 시 과거 이벤트에 반영 어려움 | 소유권 유지, 장애 결합 없음(자기 완결적) |
| CouponEventCreated/Updated로 메타데이터 Projection 관리 | 메타데이터를 이벤트로 받아 조회 모델로 유지. 변경 반영 가능 | 메타데이터 Projection을 별도로 관리해야 함 | 소유권 유지, 장애 결합 없음(이벤트 기반) |
| 이벤트 처리 중 Coupon Service API 동기 호출 | 항상 최신 메타데이터 조회 가능 | 처리 지연, 상대 서비스 장애에 다시 의존 | 장애 결합 발생 |
| Coupon Service DB 직접 조회 | 구현이 단순해 보임 | 다른 서비스 테이블에 직접 의존 | 데이터 소유권 위반, 강한 결합 |
```

```
이벤트에 원본 Entity 전체를 넣으면 안 되는 이유:
Consumer가 실제로 필요로 하지 않는 필드까지 실려 이벤트가 커지고,
개인정보나 자주 바뀌는 내부 필드가 노출·전파된다. 내부 모델 변경이
이벤트 계약 변경으로 이어져 결합이 커진다. Consumer가 필요로 하는
안정적인 값만 담아야 한다.
```

## 과제 4. Consumer 멱등 트랜잭션 설계하기

### 1. Offset과 eventMessageId를 비교한다

```
| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka 안의 물리적 저장 위치 | 바뀐다(재발행 시 다른 Offset) | 부적절. 같은 논리 이벤트가 다른 Offset을 가질 수 있음 |
| eventMessageId | 논리 이벤트 메시지 자체 | 안 바뀐다(재발행해도 동일) | 적절. 논리 이벤트를 유일하게 식별 |
```

### 2. `processed_event` DDL을 작성한다

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

```
선택:
mypage-coupon-projection

이유:
pod-a7f9c와 server-10.0.0.12는 실행 중인 프로세스/서버 인스턴스 ID다.
배포, 재시작, 스케일 아웃, IP 변경 때마다 값이 바뀐다.
인스턴스 ID를 subscriber_id로 쓰면 인스턴스 A가 처리한 이벤트를
재배포된 인스턴스 B가 다른 ID로 다시 처리해 조회 모델을 중복 반영한다.
인스턴스와 무관한 안정적인 논리 구독자 이름을 써야 어느 인스턴스가 처리하든
같은 구독자 기준으로 중복을 방어할 수 있다.
```

### 3. MyPage Consumer 트랜잭션을 완성한다

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (
        subscriber_id, event_message_id
    ) VALUES (
        'mypage-coupon-projection', :eventMessageId
    )
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id, user_id, coupon_event_id,
    status, aggregate_version, issued_at, updated_at
)
SELECT
    :couponIssueId, :userId, :couponEventId,
    :status, :aggregateVersion, :issuedAt, CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

```
accepted가 비어 있으면(중복 이벤트) SELECT 결과가 없어 user_coupon_view INSERT가
0행이 되고, 조회 모델은 변경되지 않은 채 정상 종료(Commit)된다.
최초 이벤트일 때만 accepted에 행이 있어 INSERT가 실행된다.
```

### 4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다

```
PostgreSQL은 트랜잭션 안에서 제약 위반(PK 중복)이 발생하면 그 트랜잭션을
abort 상태로 전환한다. 이후의 모든 SQL은
current transaction is aborted, commands ignored until end of transaction block
오류를 반환한다.

따라서 PK 예외를 애플리케이션에서 잡고 그냥 다음 작업(user_coupon_view 변경 등)을
이어서 실행할 수 없다. 예외를 잡아도 트랜잭션이 이미 죽어 있어 후속 SQL이 모두 실패한다.
그래서 예외에 의존하지 않고 ON CONFLICT DO NOTHING RETURNING의
반환 행 유무로 최초/중복을 판단해야 한다.
(부분 처리가 필요하면 SAVEPOINT를 쓸 수 있으나 여기서는 ON CONFLICT가 적절하다)
```

### 5. 다음 잘못된 처리 순서의 결과를 분석한다

```
재전달 시 Consumer 판단:
processed_event에 이미 기록이 있으므로 이미 처리한 이벤트로 판단해 건너뛴다.

최종 조회 모델 상태:
user_coupon_view는 첫 시도에서 변경이 실패했고, 재전달 시에도 중복으로 판단되어
영원히 갱신되지 않는다. 사용자 쿠폰함에 쿠폰이 계속 보이지 않는다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
processed_event 기록과 조회 모델 변경이 함께 Commit되거나 함께 Rollback되어야
"처리했다고 표시됐는데 실제 반영은 안 된" 상태가 생기지 않는다.
분리하면 한쪽만 반영되어 멱등 방어가 오히려 반영 누락을 고착시킨다.
```

### 6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다

```
Consumer DB 상태:
processed_event에 event_message_id 기록 존재, user_coupon_view 갱신 완료(Commit됨).

Consumer Group Offset:
Commit되지 않음 -> 같은 Record가 재전달된다.

재시작 후 전달:
같은 eventMessageId의 이벤트가 다시 전달된다.

재전달된 이벤트 처리:
processed_event INSERT가 ON CONFLICT로 0행이 되어 이미 처리한 이벤트로 판단하고,
조회 모델 변경 없이 정상 종료 후 Offset을 Commit한다.
중복 전달을 허용하되 멱등 처리로 안전하게 흡수한다.
```

### 7. Offset 완료 정책을 작성한다

```
enable.auto.commit:
false. 자동 커밋을 켜면 DB Commit 시점과 어긋나 DB 처리 전 Offset이 커밋되어
메시지가 유실될 수 있다.

DB Commit과 Offset Commit 순서:
반드시 Consumer 로컬 DB 트랜잭션 Commit이 먼저, 그 뒤에 Offset을 수동 Commit한다.
DB Commit과 Offset Commit은 하나의 원자적 트랜잭션이 아니므로,
둘 사이 장애에서는 중복 재전달이 남고 이는 eventMessageId 멱등 처리로 흡수한다.

Listener 예외 처리:
DB Rollback되는 예외가 발생하면 Offset을 Commit하지 않아 재전달되게 한다.
일시적 오류는 재처리로 넘긴다.

같은 Partition 병렬 처리 시 앞선 미완료 Record:
같은 Partition을 병렬 처리한다면 앞선 미완료 Record를 건너뛰고
더 높은 Offset을 먼저 Commit하지 않도록 해야 한다. 그러지 않으면
앞 Record가 유실될 수 있다.
```

## 과제 5. Notification과 Analytics 처리 설계하기

### 1. Notification Consumer의 새로운 Dual Write를 분석한다

```
| 장애 지점 | DB 상태 | 외부 SMS 상태 | 재전달 시 문제 |
| --- | --- | --- | --- |
| SMS 성공 후 processed_event Commit 전 종료 | processed_event 기록 없음 | SMS 이미 발송됨 | 재전달 시 처리 기록이 없어 SMS를 또 발송(중복 전송) |
| processed_event Commit 후 SMS 호출 전 종료 | processed_event 기록 있음 | SMS 미발송 | 재전달 시 이미 처리로 판단해 건너뛰어 SMS 누락 |
```

### 2. Notification 내부 처리 구조를 완성한다

```
Notification Consumer
        |
        v
+------------------------------------------+
| Notification DB Transaction              |
|  processed_event INSERT                  |
|    (ON CONFLICT DO NOTHING)              |
|  notification_job INSERT                 |
|    (notificationId, status = READY)      |
+------------------------------------------+
        |
        | Commit
        v
Consumer Group Offset Commit
        :
+------------------------------------------+
| Notification Sender (별도 프로세스)       |
|  READY notification_job 조회             |
|  notificationId를 Idempotency Key로       |
|  외부 Provider 호출                       |
|  성공 시 job -> SENT                      |
+------------------------------------------+
        |
        v
   외부 Provider (SMS / Email)
```

```
processed_event와 notification_job은 하나의 로컬 DB 트랜잭션으로 함께 저장한다.
그래야 "이벤트를 처리했다고 표시했는데 발송할 작업은 없는" 상태가 생기지 않는다.
외부 발송은 이 트랜잭션 밖에서 별도 Sender가 수행해 외부 호출을 트랜잭션과 분리한다.
```

### 3. 외부 Provider가 Idempotency Key를 지원하지 않는 경우의 보장 수준을 작성한다

```
외부 알림 전송 보장 수준:
At-Least-Once에 가깝다. 발송은 되지만 장애·재시도 상황에서 중복 발송이 발생할 수 있다.

중복 전송 가능성을 완전히 제거할 수 있는가?
완전히 제거할 수 없다. DB 저장과 외부 API 호출을 하나의 원자적 트랜잭션으로
묶을 수 없고, Provider가 멱등 키로 중복을 걸러주지도 않기 때문이다.

운영에서 추가로 필요한 장치:
notificationId 기반 발송 상태 기록으로 재발송 여부 통제,
발송 성공/실패 로그와 재시도 횟수 관리, 짧은 시간 내 동일 사용자 중복 발송 억제,
Provider가 나중에 멱등 키를 지원하면 그 키로 전환.
```

### 4. 다음 Analytics 구현의 문제를 설명한다

```
같은 eventMessageId가 두 번 전달되면 UPDATE가 두 번 실행되어
issued_count가 실제 발급 1건에 대해 2 증가한다(이중 집계).

이 UPDATE는 멱등성 판별 기준(eventMessageId)이 없어서
재전달·재발행된 같은 이벤트를 구분하지 못한다.
발급 사실은 한 건인데 통계는 부풀려져 대시보드 수치가 실제와 어긋난다.
카운터 +1 로직은 UNIQUE 제약만으로 보호되지 않으므로 멱등 처리가 특히 중요하다.
```

### 5. `coupon_issue_fact` 기반 집계 구조를 설계한다

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uk_coupon_issue_fact_event_message
        UNIQUE (event_message_id)
);
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id, event_message_id,
        coupon_event_id, user_id, issued_at
    ) VALUES (
        :couponIssueId, :eventMessageId,
        :couponEventId, :userId, :issuedAt
    )
    ON CONFLICT (coupon_issue_id) DO NOTHING
    RETURNING coupon_event_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId
  AND EXISTS (
      SELECT 1 FROM accepted
  );

COMMIT;
```

```
Fact가 실제 INSERT된 경우(accepted에 행 존재)에만 EXISTS가 참이 되어 집계가 +1된다.
중복 이벤트는 ON CONFLICT로 Fact INSERT가 0행이 되고 accepted가 비어
EXISTS가 거짓이므로 집계가 증가하지 않는다.
Fact INSERT와 집계 변경이 같은 트랜잭션이라 함께 반영되거나 함께 취소된다.
```

### 6. 세 Consumer의 멱등 처리 대상을 비교한다

```
| Consumer | 한 번만 반영해야 하는 비즈니스 결과 | 추가 제약 또는 Idempotency Key | 외부 시스템 포함 여부 |
| --- | --- | --- | --- |
| MyPage | 사용자 쿠폰 조회 모델에 1건 반영 | eventMessageId + user_coupon_view PK/UNIQUE | 없음 |
| Notification | 발급 알림 1회 발송 | eventMessageId + notificationId(Provider 멱등 키) | 있음(외부 Provider) |
| Analytics | 발급 통계 1건 집계 | eventMessageId + coupon_issue_fact PK/UNIQUE | 없음 |
```

```
| 상태 비교 | 같음/다름 | 이유 |
| --- | --- | --- |
| DB ISSUED vs Kafka Record 존재 | 다름 | DB 발급 확정 후에도 Outbox 발행 전이면 Kafka Record가 아직 없을 수 있음 |
| Kafka Record 존재 vs MyPage 반영 완료 | 다름 | Record가 있어도 MyPage Consumer가 소비·Commit하기 전이면 미반영 |
```

```
POST /api/coupon-events/{couponEventId}/issue
→ 발급 요청을 접수하고 202 Accepted와 requestId를 반환한다(비동기 처리 시작).

GET /api/coupon-issue-requests/{requestId}
→ 해당 요청의 최종 처리 상태(PENDING/ISSUED/FAILED)를 반환한다. 발급 결과 확인용.
```

### 4. 발급 직후 사용자 UX를 설계한다

```
상황 A (request = PENDING):
"쿠폰 발급을 처리 중입니다. 잠시만 기다려 주세요." 로딩/대기 상태 표시.

상황 B (request = ISSUED지만 MyPage에 아직 없음):
발급 성공으로 안내하되 쿠폰함은 "쿠폰함에 반영 중입니다. 곧 표시됩니다."로 표시.
요청 상태 API 결과(ISSUED)를 발급 성공의 기준으로 사용한다.

상황 C (request = FAILED):
실패 사유를 안내한다. 예: "쿠폰이 모두 소진되었습니다." 또는
"이미 발급받은 쿠폰입니다." 재시도 가능 여부도 함께 안내.

상황 D (MyPage Projection Delay가 서비스 목표를 초과함):
사용자에게는 발급 성공(ISSUED)을 계속 신뢰해 안내하고,
운영 측에서는 Consumer Lag/Projection Delay 지표로 지연을 감지해 대응한다.
필요 시 "일시적으로 반영이 지연되고 있습니다" 안내.
```

### 5. Projection Delay를 계산한다

```
occurredAt:

user_coupon_view Commit:
10:00:05.200

5.200초 (5초 200밀리초)
```

### 6. 최종적 일관성이 무제한 지연을 의미하지 않는 이유를 설명한다

```
허용할 지연 목표:
서비스가 정한 조회 반영 목표(예: 대부분의 발급이 수 초 이내 마이페이지 반영).
"언젠가는 반영된다"가 아니라 측정 가능한 목표를 정한다.

목표 초과 시 확인할 지표:
Consumer Group Lag, 가장 오래된 미처리 시간(Oldest Unprocessed Age),
Projection Delay(occurredAt부터 조회 모델 Commit까지).

장시간 불일치를 복구할 방법:
Consumer 확장으로 Lag 해소, 처리 병목·핸들러 실패 점검,
필요 시 원본 Snapshot Backfill과 이벤트 Replay로 Read Model 재구축.
```

## 과제 7. 이벤트 순서와 버전 처리하기

### 1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다

```
같은 Topic이어야 하는가?
그렇다. Kafka의 순서 보장은 같은 Topic의 같은 Partition 안에서만 성립한다.
서로 다른 Topic에 있으면 같은 Key여도 순서가 보장되지 않는다.

같은 Key가 보장하는 범위:
같은 Key(couponIssueId)의 Record가 같은 Partition에 기록되므로,
그 Partition에 기록된 순서(같은 Aggregate 내 순서)를 보장할 수 있다.

전역 순서를 보장하는가?
아니다. 모든 사용자/모든 Aggregate에 걸친 전역 순서는 보장하지 않는다.

서로 다른 Topic 사이의 순서를 보장하는가?
아니다. Key가 같아도 두 Topic 사이의 순서는 보장되지 않는다.
```

### 2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다

```
DB 발생 순서:
CouponIssued(version=1) 먼저 Outbox 저장
CouponCancelled(version=2) 나중에 Outbox 저장

Publisher 처리 순서:
Publisher A: version=1(CouponIssued) Claim -> Kafka 발행 실패
             -> PENDING, next_attempt_at 뒤로 밀림(Backoff)
Publisher B: version=2(CouponCancelled) Claim -> 발행 성공
(SKIP LOCKED로 B가 version=1을 건너뛰고 version=2를 먼저 가져감)

Kafka 저장 순서:
Offset 200 : CouponCancelled (version=2)
Offset 201 : CouponIssued    (version=1)
-> DB 발생 순서(발급 -> 취소)와 Kafka 저장 순서(취소 -> 발급)가 역전됨
```

### 3. `schemaVersion`과 `aggregateVersion`을 비교한다

```
| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| schemaVersion | 이벤트 JSON 필드 구조의 버전 | 이벤트 스키마 변경과 Consumer 호환성 | 필드 구조가 호환 불가하게 바뀌어 새 버전 발행 시 |
| aggregateVersion | 한 CouponIssue에서 발생한 비즈니스 변경 순서 | 같은 Aggregate 이벤트의 순서 역전 방어 | 발급(1) 이후 취소(2)처럼 상태 변경이 일어날 때 |
```

### 4. 최신 상태 Projection의 UPSERT를 완성한다

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = CURRENT_TIMESTAMP
WHERE user_coupon_view.aggregate_version < EXCLUDED.aggregate_version;
```

### 5. Version 2가 먼저 도착한 경우를 분석한다

```
최종 MyPage status:
CANCELLED (version=2가 먼저 반영됨)

최종 aggregate_version:
2 (더 높은 버전 유지)

version=1 UPSERT의 affected rows:
0. ON CONFLICT DO UPDATE의 WHERE(aggregate_version < 1)이 거짓(2 < 1 아님)이라
갱신되지 않는다. 이미 더 높은 버전이 반영되어 있어 발급으로 되돌리지 않는다.
```

### 6. 낮은 Version을 생략할 수 있는 범위를 판단한다

```
| Consumer | 낮은 Version 생략 가능 여부 | 필요한 전제 또는 추가 순서 정책 |
| --- | --- | --- |
| 완전한 최신 상태만 저장하는 MyPage | 가능 | 최종 상태만 필요. aggregate_version 비교로 늦은 과거 이벤트 덮어쓰기 방지 |
| 모든 발급·취소를 집계하는 Analytics | 불가능 | 각 상태 전이를 모두 세야 함. eventMessageId 멱등으로 각 이벤트를 한 번씩 반영 |
| 발급·취소 알림을 각각 보내는 Notification | 불가능 | 발급 알림과 취소 알림을 둘 다 보내야 함. 낮은 버전 버리면 발급 알림 누락 |
```

### 7. Version Gap 처리 정책을 작성한다

```
Gap으로 판단하는 조건:
모든 상태 전이가 필요한 Consumer에서 incomingVersion > currentVersion + 1인 경우.
(현재 2인데 4가 오면 3이 아직 안 온 것이므로 Gap)

즉시 반영해도 되는 Consumer:
최신 상태만 저장하는 MyPage. incomingVersion > currentVersion이면 바로 최신값으로 갱신.

모든 전이가 필요한 Consumer의 처리:
incomingVersion == currentVersion + 1인 이벤트만 순서대로 처리하고,
Gap이면 즉시 반영하지 않고 보류한다.

복구 방법:
빠진 버전(3)이 도착할 때까지 보류·재시도하거나, 이벤트 Replay로 순서를 채운다.
Gap이 오래 지속되면 재발행 요청/Replay로 누락 이벤트를 확보한다.
```

### 8. 이벤트 스키마 변경의 호환성을 판단한다

```
| 변경 | 호환 가능성 | 이유와 배포 방법 |
| --- | --- | --- |
| 선택 필드 couponDisplayName 추가 | 호환 가능 | 기존 Consumer는 모르는 선택 필드를 무시. 선택 필드로 추가 배포 |
| 기존 userId 필드 삭제 | 호환 불가 | userId에 의존하는 Consumer가 깨진다. 새 schemaVersion/새 이벤트 타입 필요 |
| userId 의미를 이메일 주소로 변경 | 호환 불가 | 같은 필드의 의미가 바뀌어 조용히 잘못 처리된다. 새 schemaVersion 필요 |
| 호환 안 되는 새 Payload를 같은 schemaVersion=1로 발행 | 호환 불가 | Consumer가 버전 구분 없이 잘못 해석. 반드시 schemaVersion을 올려야 함 |
| 불필요한 전화번호·비밀번호를 이벤트에 추가 | 넣으면 안 됨 | 불필요한 개인정보/민감정보 노출·전파 위험. 이벤트에 포함하지 않는다 |
```

## 과제 8. Read Model 재구축과 운영 지표 설계하기

### 1. 원본 데이터와 파생 데이터를 구분한다

```
| 데이터 | Source of Truth인가? | 삭제 후 재구축 가능한가? | 재구축 근거 |
| --- | --- | --- | --- |
| Coupon Service coupon_issue | 그렇다 | 아니다(원본) | 발급의 최종 원장 |
| MyPage user_coupon_view | 아니다 | 가능 | 원본 Snapshot Backfill 또는 CouponIssued Replay |
| Analytics coupon_issue_fact | 아니다 | 가능 | CouponIssued Replay(발급 사실 재적재) |
| Analytics coupon_issue_stats | 아니다 | 가능 | coupon_issue_fact를 COUNT로 재집계 |
```

### 2. `user_coupon_view_v2` 재구축 순서를 작성한다

```
1. 새 Projection 테이블 생성
   -> user_coupon_view_v2를 만들어 기존 조회에 영향 없이 병렬로 채운다.

2. 원본 DB Snapshot Backfill
   -> Coupon Service coupon_issue의 특정 시점 Snapshot으로 과거분을 일괄 적재한다.

3. Backfill 경계 이후 이벤트 Catch-up
   -> Snapshot 경계 시점 이후의 CouponIssued 이벤트를 이어서 반영해 최신까지 따라잡는다.

4. 새 Consumer Group으로 Kafka Replay
   -> 새 Group으로 보관된 이벤트를 재소비해 v2를 채운다(Backfill과 함께 경계 관리).

5. 원본과 v2 정합성 검증
   -> coupon_issue 기준으로 v2의 건수·상태 일치를 검증한다.

6. 조회 API 전환
   -> 검증 통과 후 GET /api/users/{userId}/coupons가 v2를 바라보게 전환한다.

7. 기존 Projection 보관 또는 제거
   -> 전환 안정화 후 기존 user_coupon_view를 일정 기간 보관하다 제거한다.
```

### 3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다

```
Kafka만으로 전체 Replay가 가능한가?
불가능하다. 보관 기간이 지난 이벤트는 Kafka에서 삭제되어 재소비할 수 없다.

필요한 다른 복구 기준:
Coupon Service의 원본 coupon_issue Snapshot. 과거분은 원본 DB에서 Backfill한다.

Backfill 중 새 이벤트가 들어올 때 필요한 경계:
Snapshot 시점을 경계로 정하고, 그 경계 이후의 이벤트만 이어서 반영한다.
경계 관리를 통해 과거분(Backfill)과 신규분(Replay/Catch-up)이 중복·누락 없이 합쳐지게 한다.
```

### 4. 운영 지표를 완성한다

```
| 지표 | 의미 | 장애 신호 예시 |
| --- | --- | --- |
| Group별 Consumer Lag | Group이 아직 처리하지 못한 메시지 수 | 특정 Group Lag이 계속 증가 |
| Oldest Unprocessed Age | 가장 오래된 미처리 메시지의 대기 시간 | 임계치(수십 초~분) 초과 |
| Projection Delay | occurredAt부터 조회 모델 Commit까지 시간 | 목표치 초과, 지속 상승 |
| Handler Failure Count | 이벤트 처리 실패 횟수 | 특정 Consumer에서 실패 급증 |
| Duplicate Event Count | 중복 이벤트 처리(멱등 흡수) 횟수 | 평소 대비 비정상 급증(재발행 폭증 신호) |
| Read Model Mismatch Count | 원본과 Read Model 불일치 건수 | 0보다 크고 지속 증가 |
```

### 5. 다음 장애 상황에서 확인할 지표를 선택한다

```
가장 먼저 확인할 Consumer Group:
mypage-coupon-projection

확인할 지표:
MyPage Group의 Consumer Lag, Oldest Unprocessed Age, Projection Delay,
Handler Failure Count(해당 이벤트 처리 실패 여부).

로그에서 연결할 식별자:
couponIssueId, eventMessageId, requestId, couponEventId, consumerGroupId로
발급부터 MyPage 처리까지 추적한다.

Coupon Service 발급을 다시 실행해도 되는가?
안 된다. 발급은 이미 ISSUED로 확정된 사실이다. 문제는 MyPage 반영(파생 데이터)이므로
MyPage Consumer 재처리/Projection 재구축으로 해결한다. 발급 재실행은 중복 발급을 만든다.
```

### 6. 로그에 남길 상관관계 ID를 작성한다

```
1. requestId       -> 발급 요청 단위 추적(요청 접수부터 상태 확정까지)
2. eventMessageId  -> 논리 이벤트 단위 추적(발행/재발행/각 Consumer 처리)
3. couponIssueId   -> 발급 건 단위 추적(같은 Aggregate 이벤트 묶음)
4. couponEventId   -> 쿠폰 이벤트(행사) 단위 추적
5. consumerGroupId -> 어느 Consumer Group에서 처리·실패했는지 추적
```

### 3. 수정된 전체 구조를 그린다

```
Kafka coupon.issued
  |
  +--> group: notification-coupon-issued
  |       Notification Consumer
  |         DB Transaction:
  |           processed_event INSERT (ON CONFLICT DO NOTHING)
  |           notification_job INSERT
  |         Commit -> Offset 완료
  |            |
  |            v
  |       Notification Sender (별도)
  |         notificationId를 Idempotency Key로 외부 Provider 호출
  |
  +--> group: mypage-coupon-projection
  |       MyPage Consumer
  |         DB Transaction:
  |           processed_event INSERT (ON CONFLICT DO NOTHING)
  |           user_coupon_view UPSERT (aggregate_version 비교)
  |         Commit -> Offset 완료
  |
  +--> group: analytics-coupon-issued
          Analytics Consumer
            DB Transaction:
              coupon_issue_fact INSERT (ON CONFLICT DO NOTHING)
              실제 INSERT된 경우에만 coupon_issue_stats +1
            Commit -> Offset 완료

공통 원칙:
- 각 Consumer는 자신의 DB만 변경
- eventMessageId로 멱등 처리, 자신의 변경과 같은 트랜잭션
- 자동 Offset Commit 끄고 DB Commit 이후 Offset 완료
- 실패는 자신의 Consumer Group에서 복구
```

### 4. 수정된 구조의 보장 수준을 판단한다

```
| 항목 | 보장/조건부 보장/보장하지 않음 | 이유 |
| --- | --- | --- |
| 쿠폰 발급 DB의 최종 성공 | 보장 | Coupon Service 트랜잭션 Commit으로 확정(원장) |
| 세 Group이 각자 이벤트를 소비할 기회 | 보장 | 서로 다른 Group이라 각 Group이 모든 Record를 독립 소비 |
| Kafka Record의 물리적 Exactly-Once | 보장하지 않음 | 재발행으로 같은 eventMessageId Record가 둘 이상 생길 수 있음 |
| MyPage 중복 반영 방지 | 보장 | eventMessageId 멱등 + PK/UNIQUE로 한 번만 반영 |
| Analytics 중복 집계 방지 | 보장 | Fact ON CONFLICT 후 실제 INSERT 시에만 집계 |
| 외부 SMS Exactly-Once | 보장하지 않음 | 외부 API는 로컬 트랜잭션 밖. Provider 멱등 미지원 시 중복 가능 |
| 발급 직후 MyPage의 즉시 일치 | 보장하지 않음 | 최종적 일관성. 반영까지 Projection Delay 존재 |
```

## 보너스 2. Projection 재구축 테스트 설계하기

```
| 테스트 상황 | 준비 데이터 | 실행 방법 | 검증할 결과 |
| --- | --- | --- | --- |
| 동일 이벤트 2회 Replay | 같은 eventMessageId 이벤트 2건 | 같은 이벤트를 두 번 전달 | user_coupon_view 1건만 반영, processed_event 1건 |
| Version 2 뒤 Version 1 전달 | version=2, version=1 이벤트 | version=2 먼저, version=1 나중 처리 | 최종 status=CANCELLED, version=2 유지, v1 UPSERT 0행 |
| Backfill 중 새 이벤트 유입 | Snapshot + 경계 이후 신규 이벤트 | Backfill 진행 중 신규 이벤트 전달 | 경계 기준으로 중복·누락 없이 합쳐짐 |
| Kafka 보관 기간 이전 데이터 존재 | 보관 기간 지난 과거 발급 + 원본 Snapshot | 원본 Snapshot Backfill 후 최신 Replay | 과거분까지 원본과 일치하게 재구축 |
| Consumer DB Commit 직후 종료 | 처리 후 Offset 미커밋 상태 | DB Commit 후 강제 종료, 재시작 | 재전달돼도 멱등으로 중복 없이 동일 결과 |
```

```
한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유:
정상 경로에서는 중복·순서 역전·부분 실패·재전달 같은 이상 상황이 발생하지 않는다.
Read Model의 안전성은 이런 예외 상황(중복 이벤트, 순서 뒤바뀜, Commit 직후 종료,
보관 기간 초과)에서도 최종 상태가 원본과 일치하는지로 결정되므로,
정상 1회 실행이 아니라 위와 같은 장애·중복 시나리오를 모두 검증해야 한다.
```

## 핵심 질문

```
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
같은 Group은 Record를 나눠 처리하므로, 세 서비스가 각자 모든 이벤트를 받으려면
서로 다른 Group으로 독립 구독해야 한다.

2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
발급은 DB에서 이미 확정된 사실이라, Consumer는 재발급이 아니라 후속 처리만 해야
중복 전달 시에도 재발급 위험이 없다.

3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
Coupon Service의 coupon_issue다. MyPage는 재구축 가능한 파생 조회 모델이다.

4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
Outbox 재발행 등으로 같은 논리 이벤트가 물리적으로 다시 저장되면 다른 Offset을 갖기 때문이다.

5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
"처리했다고 표시됐는데 실제 반영은 안 된" 부분 실패를 막아 멱등과 반영을 함께 보장하기 위해서다.

6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
조회 모델은 이벤트를 통해 나중에 갱신되는 최종적 일관성 구조라 Projection Delay가 있기 때문이다.

7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
aggregateVersion은 순서를 식별하는 값일 뿐이고, 실제 방어는 Consumer가 버전을 비교해
낮은 버전을 무시하도록 구현해야 성립하기 때문이다.

8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
Analytics/Notification처럼 모든 상태 전이가 필요한 Consumer는 낮은 버전을 버리면
집계 누락이나 알림 누락이 생기기 때문이다.

9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
Read Model은 파생 데이터라 버그로 오염될 수 있고, 원본 Snapshot/이벤트 Replay로
언제든 재구축할 수 있어야 신뢰할 수 있기 때문이다.

10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
발급은 이미 성공한 사실이고 실패한 것은 후속 알림이므로, 발급을 재실행하면 중복 발급이 되기 때문이다.
```
