## **1. 과제 목표**

이번 과제의 목표는 쿠폰 발급 이후의 알림, 마이페이지와 통계 작업을 `CouponIssued` 이벤트 기반으로 분리하고, 각 Consumer가 자신의 데이터를 안전하게 만드는 구조를 설계하는 것이다.

## **3. 전제 조건**

```
Coupon Service의 coupon_issue가 발급 여부의 최종 원장이다.

CouponIssued는 DB에서 발급이 확정된 뒤 생성된 과거의 사실이다.

Notification, MyPage와 Analytics는 서로 다른 논리 Subscriber다.

Kafka Record와 동일한 논리 이벤트는 재전달·재발행될 수 있다.

각 Consumer는 자신의 DB만 변경한다.

Consumer 자동 Offset Commit은 사용하지 않는다.

Consumer DB Commit 뒤 Offset을 완료 처리한다.

이번 주차는 Retry Topic과 DLQ의 상세 구현보다
서비스 분리, 조회 모델과 Consumer 멱등성에 집중한다.

```

### **1. 직접 호출 구조의 결합을 분석한다**

| **결합 종류발생하는 문제EDA 적용 후 달라지는 점** |   |   |
| ------------------------------- | - | - |
| 시간 결합                           | 호출 시점에 후속 서비스가 실행 중이어야 함 | Producer는 이벤트만 발행하고 Consumer가 독립 처리 |

| 데이터 결합                          | 다른 서비스의 내부 모델·DB에 의존하기 쉬움 | 각 서비스가 자기 DB만 변경하고 이벤트 계약으로 연결 |

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| **구분Command / Write ModelQuery / Read Model** |   |   |
| --------------------------------------------- | - | - |
| 주요 목적                                         | 정확한 변경·불변식 보장 | 빠른 조회 |
| 대표 작업                                         | 쿠폰 발급 요청 처리 | 마이페이지 목록·운영 통계 조회 |
| 데이터 구조                                        | 쓰기·정합성 중심 모델 | 화면 목적에 맞춘 비정규화 모델 가능 |
| 최종 원장 여부                                      | 예(`coupon_issue`) | 아니오, 파생 데이터 |
| 장애 후 재구축 가능 여부                                | 원본이므로 Read Model처럼 재구축 대상이 아님 | 예, Snapshot/Replay로 재구축 가능 |

### **2. CQRS에 대해 다음 문장을 판단한다**

| **문장맞음/틀림이유**                            |   |   |
| ---------------------------------------- | - | - |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다.            | 틀림 | 논리적 Command·Query 모델 분리가 핵심이다. |
| CQRS는 Event Sourcing과 같은 의미다.            | 틀림 | CQRS에 Event Sourcing은 필수가 아니다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 같은 애플리케이션·DB에서도 처리 경로와 모델을 분리할 수 있다. |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다.            | 틀림 | 책임과 처리 모델의 분리가 필요하다. |

### **3. ****`user_coupon_view`**** DDL을 완성한다**

다음 요구사항을 만족해야 한다.

```
coupon_issue_id Primary Key
user_id와 coupon_event_id 저장
현재 status와 aggregate_version 저장
issued_at과 updated_at 저장
같은 사용자·이벤트의 중복 노출 방지
사용자별 최신 쿠폰 조회 인덱스

```

```
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC)
;

```

### **4. 각 제약과 인덱스의 역할을 작성한다**

| **장치막거나 개선하는 문제**                   |   |
| ----------------------------------- | - |
| `PRIMARY KEY (coupon_issue_id)`     | 같은 발급 건의 중복 생성 방지 |
| `UNIQUE (user_id, coupon_event_id)` | 동일 사용자·이벤트 쿠폰의 중복 노출 방지 |
| `(user_id, issued_at DESC)` Index   | 사용자별 최신 쿠폰 목록 조회 성능 개선 |

### **6. 화면 표시용 데이터 전달 방법을 비교한다**

마이페이지에 `couponDisplayName`과 `discountAmount`가 필요하다고 가정한다.

| **방법장점단점데이터 소유권·장애 결합에 미치는 영향**                   |   |   |   |
| ------------------------------------------------- | - | - | - |
| `CouponIssued`에 Snapshot 포함                       | 한 이벤트만으로 화면 값 구성 가능 | 이벤트 Payload 증가·값 고정 시점 관리 필요 | 필요한 안정적 값만 포함하면 소유권 침범과 동기 장애 결합을 줄임 |
| `CouponEventCreated/Updated`로 메타데이터 Projection 관리 | 메타데이터를 독립 Read Model로 최신화 가능 | Projection 관리가 추가됨 | 이벤트 기반으로 소유권을 지키고 동기 결합을 줄임 |
| 이벤트 처리 중 Coupon Service API 동기 호출                 | 최신 원본 값을 조회 가능 | API 지연·장애에 Consumer가 의존 | 동기 장애 결합이 다시 생김 |
| Coupon Service DB 직접 조회                           | 구현이 단순할 수 있음 | 내부 스키마에 강하게 의존 | 데이터 소유권을 깨뜨림 |

이벤트에 원본 Entity 전체를 넣으면 안 되는 이유도 작성한다.

```
Consumer가 필요한 안정적인 값만 포함해야 하며, 원본 Entity 전체를 넣으면 내부 모델에 결합되고 불필요한 개인정보·변경 가능 필드까지 노출될 수 있다.
```

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001

```

### **3. MyPage Consumer 트랜잭션을 완성한다**

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```
일반 INSERT의 PK 충돌이 예외가 되면 PostgreSQL 트랜잭션이 실패(aborted) 상태가 되어 이후 SQL을 계속 실행할 수 없다. `ON CONFLICT DO NOTHING RETURNING`으로 최초 처리 여부를 원자적으로 판단해야 한다.
```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달

```

```
재전달 시 Consumer 판단:
이미 처리한 eventMessageId로 판단하여 종료

최종 조회 모델 상태:
갱신되지 않은 채 남음

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
processed_event와 비즈니스 변경이 함께 Commit되거나 함께 Rollback되어야 재전달 시 유실이 생기지 않기 때문이다.

```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```
Consumer DB 상태:
processed_event와 비즈니스 변경은 Commit 완료

Consumer Group Offset:
아직 이전 위치

재시작 후 전달:
같은 Record가 다시 전달될 수 있음

재전달된 이벤트 처리:
processed_event가 중복을 감지하여 비즈니스 결과를 다시 반영하지 않고 정상 종료

```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record

```

```
enable.auto.commit=false로 설정한다.
Consumer DB Commit이 성공한 뒤에만 Offset을 완료한다.
Listener 처리 중 예외가 발생하면 Offset을 완료하지 않아 재전달되게 한다.
같은 Partition을 병렬 처리할 때 앞선 Record가 미완료라면 더 높은 Offset을 먼저 Commit하지 않는다.
```

## **과제 7. 이벤트 순서와 버전 처리하기**

다음 두 이벤트가 같은 `couponIssueId = 5001`에서 발생했다고 가정한다.

### **1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다**

```
같은 Topic이어야 하는가?
예. 같은 Topic의 같은 Partition에 기록되어야 순서를 이용할 수 있다.

### **2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다**

다음을 포함한다.

여러 Publisher

### **3. ****`schemaVersion`****과 ****`aggregateVersion`****을 비교한다**

| **필드무엇의 버전인가?어떤 문제를 다루는가?값이 증가하는 예시** |   |   |   |
| ------------------------------------- | - | - | - |
| `schemaVersion`                       | 이벤트 JSON 스키마 | 필드 구조 호환성 | 호환되지 않는 Payload 구조로 변경할 때 |
| `aggregateVersion`                    | 한 CouponIssue의 비즈니스 변경 순서 | 늦게 온 과거 이벤트가 최신 상태를 덮는 문제 | ISSUED v1 -> CANCELLED v2 |

### **4. 최신 상태 Projection의 UPSERT를 완성한다**

```
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    aggregate_version,
    updated_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET
    status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = EXCLUDED.updated_at
WHERE
    EXCLUDED.aggregate_version > user_coupon_view.aggregate_version
;

```

| ------------------------------------------------- | - | - |

### **7. Version Gap 처리 정책을 작성한다**

현재 Version이 2인데 Version 4가 먼저 도착했다고 가정한다.

```
Gap으로 판단하는 조건:
incomingVersion > currentVersion + 1

완전한 최신 상태만 저장하고 이벤트가 전체 현재 상태를 담는 MyPage Projection

복구 방법:
보류·재시도 후 누락 이벤트를 Replay하여 Gap을 메운다.

```

### **2. ****`user_coupon_view_v2`**** 재구축 순서를 작성한다**

다음 단계를 안전한 순서로 배치하고 각 단계의 목적을 설명한다.

```
새 Projection 테이블 생성
원본 DB Snapshot Backfill
새 Consumer Group으로 Kafka Replay
Backfill 경계 이후 이벤트 Catch-up
원본과 v2 정합성 검증
조회 API 전환
기존 Projection 보관 또는 제거

```

```
1. 새 Projection 테이블 생성: 운영 중인 기존 조회를 건드리지 않고 v2를 만든다.

2. 원본 DB Snapshot Backfill: Source of Truth 기준으로 과거 데이터를 채우고 Backfill 경계를 기록한다.

3. 새 Consumer Group으로 Kafka Replay: v2 전용 Group으로 보관 중 이벤트를 멱등하게 재처리한다.

4. Backfill 경계 이후 이벤트 Catch-up: Backfill 중 들어온 새 이벤트까지 따라잡는다.

5. 원본과 v2 정합성 검증: 누락·중복·상태 불일치를 확인한다.

6. 조회 API 전환: 검증된 v2를 조회 대상으로 바꾼다.

7. 기존 Projection 보관 또는 제거: 안정화 후 이전 Projection을 보관하거나 제거한다.

```

# **8. 핵심 질문**

과제를 마친 뒤 다음 질문에 한 문장씩 답한다.

```
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
각 Group이 모든 `CouponIssued`를 독립적으로 소비해야 하며 같은 Group은 Record를 나누어 처리하기 때문이다.


2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
CouponIssued는 Coupon Service DB에서 발급이 확정된 뒤 후속 서비스에 전달되는 과거의 비즈니스 사실이기 때문이다.


3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
발급 여부의 최종 기준은 Coupon Service의 `coupon_issue`다.


4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
같은 논리 이벤트가 재발행되면 Kafka의 새 Record로 저장되어 다른 Offset을 받을 수 있기 때문이다.


5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
처리 기록과 비즈니스 변경이 함께 Commit·Rollback되어 재전달 시 유실이나 중복을 막기 위해서다.


6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
Coupon Service DB Commit과 MyPage Consumer의 Projection Commit 사이에 비동기 처리 지연이 있기 때문이다.


7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
aggregateVersion은 순서를 식별하는 값일 뿐 Consumer가 비교·Gap 정책을 적용하지 않으면 늦은 이벤트가 그대로 처리될 수 있기 때문이다.


8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
Analytics나 Notification처럼 모든 상태 전이가 필요한 Consumer는 낮은 Version의 이벤트도 처리해야 하기 때문이다.


9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
Read Model은 원본이 아닌 파생 데이터이므로 버그·불일치가 생기면 Snapshot이나 Replay로 복구할 수 있어야 하기 때문이다.


10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
쿠폰 발급은 이미 DB에서 최종 확정되었으므로 실패한 Notification 작업만 복구해야 중복 발급을 막을 수 있기 때문이다.
