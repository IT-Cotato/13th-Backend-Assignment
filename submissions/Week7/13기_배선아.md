## **3. 전제 조건**

```text
Coupon Service의 coupon_issue가 발급 여부의 최종 원장이다.

CouponIssued는 DB에서 발급이 확정된 뒤 생성된 과거의 사실이다.

Kafka Record와 동일한 논리 이벤트는 재전달·재발행될 수 있다.

각 Consumer는 자신의 DB만 변경한다.

Consumer 자동 Offset Commit은 사용하지 않는다.

Consumer DB Commit 뒤 Offset을 완료 처리한다.

이번 주차는 Retry Topic과 DLQ의 상세 구현보다
서비스 분리, 조회 모델과 Consumer 멱등성에 집중한다.
```

## **과제 1. 직접 호출 구조와 EDA 비교하기**

Coupon Service가 쿠폰 발급 뒤 세 서비스를 순서대로 호출한다고 가정한다.

```text
Coupon Service
  |
  +--> Notification Service
  |
  +--> MyPage Service
  |
  +--> Analytics Service
```

### **1. 직접 호출 구조의 결합을 분석한다**

| 결합 종류 | 발생하는 문제 | EDA 적용 후 달라지는 점 |
| --- | --- | --- |
| 시간 결합 | 호출 시점에 상대 서비스가 반드시 떠 있어야 함 | Kafka가 버퍼 역할을 해 Consumer가 나중에 처리해도 됨 |
| 장애 결합 | 상대 서비스 장애,지연이 호출자에 전파됨 | Consumer 장애가 Producer로 전파되지 않음 |
| 변경 결합 | 후속 서비스 추가,변경 시 발급 코드도 함께 바뀜 | 이벤트 계약만 지키면 Producer코드는 변경 불필요 |
| 데이터 결합 | 다른 서비스 내부 테이블, 모델에 의존하기 쉬움 | 각 서비스는 이벤트만 참조, 내부 스키마 은닉 |

### **2. 다음 장애 상황을 분석한다**

```text
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```text
이미 확정된 쿠폰 발급 상태: 
DB 트랜잭션 Commit 완료. coupon_issue는 최종 ISSUED 상태


쿠폰 발급을 Rollback하면 안 되는 이유:
발급은 이미 성공한 과거 사실이고, 알림 실패는 발급과 무관한 후속 작업의 실패
이미 완료된 발급을 되돌리면 사용자에게 지급된 혜택을 임의로 취소하는 셈

다시 실행해야 하는 작업:
실패한 Notification 발송(후속 작업)만 재시도

다시 실행하면 안 되는 작업:
쿠폰 발급(coupon_issue 저장, 수량 차감 등) 자체 - 중복 발급 위험

```

### **4. 명령과 이벤트의 차이를 작성한다**

| --- | --- | --- | --- |
| `IssueCoupon` | 명령(Command) | 쿠폰을 발급하라는 지시 | 예 |
| `CouponIssued` | 이벤트(Event) | 쿠폰이 이미 발급되었다는 과거 사실 | 아니요 |

### **5. EDA를 사용해도 남는 결합을 설명한다**

```text
직접 API 계약 대신 남는 계약: 
이벤트 스키마(필드 구성, 의미) 계약


이 계약을 관리해야 하는 이유:
여러 Consumer가 같은 이벤트를 공요으로 구독하므로, 필드를 임의로 바꾸거나 삭제하면 독립적으로 배포된 Consumer들이 깨질 수 있음

EDA가 반드시 MSA를 의미하지 않는 이유:
처음부터 서버,저장소를 물리적으로 분리하지 않아도 하나의 애플리케이션 안에서 모듈과 Consumer 책임만 논리적으로 나눠도 EDA를 적용할 수 있고, 필요할 때만 분리하면 됨
```

## **과제 2. Consumer Group과 서비스 책임 설계하기**

### **1. 서비스별 Consumer Group을 작성한다**

| 서비스 | Group ID | 같은 이벤트를 받아 수행할 작업 |
| --- | --- | --- |
| Notification | `notificaion-coupon-issued` | 발급 결과를 SMS/이메일로 사용자에게 알림 |
| MyPage | `mypage-coupon-projection` | `user_coupon_view` Read Model 갱신 |
| Analytics | `analytics-coupon-issued` | `coupon_issue_fact` 저장 및 발급 통계 집계 |

### **2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다**

```text
같은 Group 안의 Consumer 관계:
Partition을 나눠 처리하는 경쟁(분담) 관계

CouponIssued 한 건의 전달 결과:
Group 내 인스턴스 중 하나에게만 전달됨

세 서비스 중 일부 작업이 누락될 수 있는 이유:
같은 Group에서는 Partition이 인스턴스별로 배타 할당되므로, 특정 서비스 로직을 담당하는 인스턴스가 그 Record를 못 받으면 해당 작업 자체가 수행되지 않는다.
```

### **3. 다음 Partition과 Consumer 배치를 분석한다**

```text
coupon.issued Partition 수: 6

notification-coupon-issued Consumer 수: 2
mypage-coupon-projection Consumer 수: 4
analytics-coupon-issued Consumer 수: 1
```

| Group | 동시에 처리 가능한 최대 Consumer 수 | 사용되지 않는 Partition 또는 Consumer | 다른 Group 지연의 영향 |
| --- | ---: | --- | --- |
| Notification | 2 | 없음 (Consumer 1개당 3개 Partition 담당) | 없음 (Group별 Offset 독립) |
| MyPage | 4 | 없음 (Consumer 2개는 2개, 2개는 1개 Partition 담당) | 없음 |
| Analytics | 1 | 없음, 단 Consumer 1개가 6개 Partition 전부 처리 -> 병목 가능 | 없음 |

### **4. Consumer Group의 Committed Offset 의미를 설명한다**

```text
Committed Offset이 나타내는 것:
해당 Group이 특정 Partition에서 어디까지 성공적으로 처리, 완료 표시했는지 나타내는 위치

Committed Offset만으로 증명할 수 없는 것:
비즈니스 로직이 정확히, 중복 없이 수행되었는지 보장하지 않음 (물리적 위치일 뿐)

Notification Group의 Offset이 MyPage Group에 영향을 주는가?
아니오, 서로 독립적으로 관리됨
```

### **5. 서비스별 책임과 데이터 소유권을 완성한다**

| 서비스 | 소유하는 데이터 | 보장해야 하는 불변식 또는 책임 | 다른 서비스 DB 직접 수정 허용 여부 |
| --- | --- | --- | --- |
| Coupon Service | `coupon_event`, `coupon_issue`, 요청 상태 | 발급 수량, 중복 검사, 발급 확정 | 불가 |
| Notification Service | 알림 작업, 발송 상태 | 발급 결과를 사용자에게 전달 | 불가 |
| MyPage Service | 사용자별 쿠폰 조회 모델 | 빠른 조회용 Read Model 최신화 | 불가 |
| Analytics Service | 발급 사실, 집계 결과 | 정확한 운영 통계 산출 | 불가 |

### **6. 장애 격리 결과를 작성한다**

| 장애 | 쿠폰 발급 결과 | 영향받는 기능 | 영향받지 않아야 하는 기능 | 복구 단위 |

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| 구분 | Command / Write Model | Query / Read Model |
| --- | --- | --- |
| 주요 목적 | 발급 요청 처리, 불변식 보장 | 화면, 없무에 맞는 빠른 조회 |
| 대표 작업 | 발급 확정, 수량 차감 | 마이페이지 목록, 통계 조회 |
| 데이터 구조 | 정규화된 원장 구조 | 비정규화된 조회용 구조 |
| 최종 원장 여부 | 예 | 아니오(파생 데이터) |
| 장애 후 재구축 가능 여부 | 불가(원본) | 가능 |

### **2. CQRS에 대해 다음 문장을 판단한다**

| 문장 | 맞음/틀림 | 이유 |
| --- | --- | --- |
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다. | 틀림 | 논리적으로 Command/Query 모델만 나눠도 적용 가능 |
| CQRS는 Event Sourcing과 같은 의미다. | 틀림 | 서로 다른 개념이며 함께 쓰일 수 있을 뿐 동일하지 않음 |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음 | 같은 DB,앱 안에서도 처리 경로를 분리하면 됨 |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다. | 틀림 | 처리 경로와 모델을 명확히 분리해야 의미가 있음 |

### **3. `user_coupon_view` DDL을 완성한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id Primary Key
user_id와 coupon_event_id 저장
현재 status와 aggregate_version 저장
issued_at과 updated_at 저장
같은 사용자·이벤트의 중복 노출 방지
사용자별 최신 쿠폰 조회 인덱스
```

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### **6. 화면 표시용 데이터 전달 방법을 비교한다**

마이페이지에 `couponDisplayName`과 `discountAmount`가 필요하다고 가정한다.

| 방법 | 장점 | 단점 | 데이터 소유권·장애 결합에 미치는 영향 |
| --- | --- | --- | --- |
| `CouponIssued`에 Snapshot 포함 | 별도 조회 없이 즉시 표시 가능 | 이벤트가 커지고 표시용 데이터 중복 관리 필요 | 소유권 유지, 결합 낮음 |
| `CouponEventCreated/Updated`로 메타데이터 Projection 관리 | 관심사 분리, 메타데이터 변경 추적 용이 | 이벤트/Consumer 종류 증가 | 소유권 유지, 결합 낮음 |
| 이벤트 처리 중 Coupon Service API 동기 호출 | 최신 값 보장 | 상대 서비스 장애에 다시 의존 | 장애 결합 재발생 |
| Coupon Service DB 직접 조회 | 구현 간단 | 데이터 소유권 침해, 강한 결합 | 소유권,장애 결합 모두 악화 |

이벤트에 원본 Entity 전체를 넣으면 안 되는 이유도 작성한다.

```text

안정적으로 필요한 값만 담아야 한다.
```

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```text
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001
```

### **1. Offset과 eventMessageId를 비교한다**

| 값 | 식별 대상 | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| Partition + Offset | Kafka Record의 물리적 위치 | 예 (다른 Offset으로 재기록) | 아니오 |
| eventMessageId | 논리적 이벤트 자체 | 아니오 (동일 값 유지) | 예 |

### **2. `processed_event` DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

다음 세 값 중 올바른 `subscriber_id`를 고르고 이유를 작성한다.

```text
pod-a7f9c
server-10.0.0.12
mypage-coupon-projection
```

```text
선택: my-coupon-projection


이유:
pod-a7f9c나 server-10.0.0.12는 배포,재기동,스케일 시마다 바뀌는 인스턴스 식별자라 멱등성 판별에 부적합하다.

Consumer Group 단위의 논리적 서비스 식별자(mypage-coupon-projection)는 안정적으로 유지되어 같은 이벤트의 중복 여부를 정확히 판별할 수 있다.

```

### **3. MyPage Consumer 트랜잭션을 완성한다**

다음 요구사항을 만족해야 한다.

```text
ON CONFLICT DO NOTHING으로 최초 처리 권한 등록
RETURNING 결과로 최초·중복 판별
최초 이벤트일 때만 user_coupon_view 변경
processed_event와 조회 모델 변경의 원자성
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (
        subscriber_id,
        event_message_id
    ) VALUES (
        'mypage-coupon-projection',
        :eventMessageId
    )
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id, user_id, coupon_event_id,
    status, aggregate_version, issued_at, updated_at
)
SELECT
    :couponIssueId, :userId, :couponEventId,
    'ISSUED', :aggregateVersion, :issuedAt, CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```text
PostgreSQL은 트랜잭션 안에서 오류(PK 위반 등)가 발생하면 해당 트랜잭션 전체가 실패 상태로 전환되고, 이후 같은 트랜잭션의 모든 SQL이 거부된다.

예외를 잡더라도 롤백하지 않는 한 후속 작업은 실행되지 않으므로, 예외를 발생시키지 않는 INSER ... ON CONFLICT DO NOTHING 방식을 써야 한다.
```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```text
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```text
재전달 시 Consumer 판단:
processed_event만 커밋되어 있으므로 이미 처리한 이벤트로 오판하고 아무 것도 하지 않은 채 종료

최종 조회 모델 상태:
user_coupon_view는 영원히 갱신되지 않음(누락)

두 작업을 같은 트랜잭션에 넣어야 하는 이유:
"처리 완료 기록"과 "실제 데이터 반영"이 항상 함께 성공,실패해야 이런 영구 누락을 방지할 수 있다.
```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```text
Consumer DB 상태:
정상적으로 커밋 완료됨 

Consumer Group Offset:
아직 완료 처리되지 않음

재시작 후 전달:
같은 Record가 다시 전달됨

재전달된 이벤트 처리:
processed_event에 이미 기록이 있으므로 중복으로 판별되어 변경 없이 안전하게 종료(멱등 처리로 정상 방어)
```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```text
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record
```

```text
- enable.auto.commit = false로 설정, 자동 Offset Commit 사용 안 함
- DB Commit이 완료된 뒤에만 Offset Commit 수행
- Listener에서 예외 발생 시 Offset을 커밋하지 않아 재전달로 재시도되게 함
- 같은 Partition을 병렬 처리할 때는 앞선 미완료 Record를 건너뛰고 더 높은 Offset을 먼저 커밋하지 않도록 순서를 제어함
```

## **과제 5. Notification과 Analytics 처리 설계하기**

### **1. Notification Consumer의 새로운 Dual Write를 분석한다**

```text
  |
  +--> processed_event DB 저장
  |
```

| 장애 지점 | DB 상태 | 외부 SMS 상태 | 재전달 시 문제 |
| --- | --- | --- | --- |
| SMS 성공 후 `processed_event` Commit 전 종료 | 미기록(롤백) | 이미 발송됨 | 재전달 시 동일 이벤트가 다시 처리되어 SMS 중복 발송 가능 |
| `processed_event` Commit 후 SMS 호출 전 종료 | 기록됨(커밋) | 미발송 | 이미 처리된 것으로 판단되어 스킵 -> 알림 영구 미발송 |

### **2. Notification 내부 처리 구조를 완성한다**

다음 구성 요소를 포함한다.

```text
Notification Consumer
processed_event
notification_job
별도 Notification Sender
외부 Provider
notificationId / Idempotency Key
```

```text
Kafka coupon.issued
        |
        v
Notification Consumer
   (하나의 DB 트랜잭션)
   - processed_event INSERT ... ON CONFLICT DO NOTHING
   - notification_job INSERT (status=PENDING, notificationId 발급)
        |
        v Commit
별도 Notification Sender
        |
        v notificationId를 Idempotency Key로 사용
외부 Provider 호출 → 성공 시 notification_job = SENT
```

`processed_event`와 `notification_job`을 어떤 트랜잭션으로 처리해야 하는지도 작성한다.

```text
processed_event와 notification_job은 같은 로컬 DB 트랜잭션으로 묶어 원자적으로 Commit한다.

외부 SMS 호출은 이 트랜잭션 밖에서 별도 Sender가 notification_job을 읽어 비동기로 수행한다.
```

### **3. 외부 Provider가 Idempotency Key를 지원하지 않는 경우의 보장 수준을 작성한다**

```text
외부 알림 전송 보장 수준:
At-Least-Once (최소 한 번)

중복 전송 가능성을 완전히 제거할 수 있는가?
아니오

운영에서 추가로 필요한 장치:
재시도 횟수 제한, 발송 로그/모니터링, 중복 수신 가능성에 대한 사용자 안내, Provider 자체 dedup 기능 여부 확인
```

### **4. 다음 Analytics 구현의 문제를 설명한다**

```sql
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId;
```

같은 `eventMessageId`가 두 번 전달되었을 때의 결과를 작성한다.

```text
UPDATE ... issued_count + 1은 멱등하지 않은 연산이다.

같은 eventMessageId가 두 번 전달되면 카운트고 두 번 증가해 실제 발급 건수보다 부풀려진다(이중 집계).
```

### **5. `coupon_issue_fact` 기반 집계 구조를 설계한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id 중복 저장 방지
event_message_id 추적
coupon_event_id와 user_id 저장
발급 발생 시각 저장
Fact가 실제 INSERT된 경우에만 집계 +1
Fact INSERT와 집계 변경을 같은 트랜잭션으로 처리
```

```sql
CREATE TABLE coupon_issue_fact (
    coupon_issue_id BIGINT PRIMARY KEY,
    event_message_id UUID NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,

    UNIQUE (event_message_id)
);
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO coupon_issue_fact (
        coupon_issue_id, event_message_id, coupon_event_id, user_id, issued_at
    ) VALUES (
        :couponIssueId, :eventMessageId, :couponEventId, :userId, :issuedAt
    )
    ON CONFLICT DO NOTHING
    RETURNING coupon_issue_id
)
UPDATE coupon_issue_stats
SET issued_count = issued_count + 1
WHERE coupon_event_id = :couponEventId
  AND EXISTS (SELECT 1 FROM accepted);

COMMIT;
```

## **과제 7. 이벤트 순서와 버전 처리하기**

다음 두 이벤트가 같은 `couponIssueId = 5001`에서 발생했다고 가정한다.

```text
CouponIssued
aggregateVersion = 1
status = ISSUED

CouponCancelled
aggregateVersion = 2
status = CANCELLED
```

### **1. 같은 Partition Key가 순서에 도움을 주는 조건을 작성한다**

```text
같은 Topic이어야 하는가?
예 - Kafka는 Topic-Partition 단위로만 순소를 보장한다.

같은 Key가 보장하는 범위:
같은 Partition Key는 ㄴ같은 Partition에 기록되어 그 안에서는 기록 순서가 보장된다.

전역 순서를 보장하는가?
아니오

서로 다른 Topic 사이의 순서를 보장하는가?
아니오
```

### **2. 비즈니스 발생 순서와 Kafka 저장 순서가 달라지는 시나리오를 완성한다**

다음을 포함한다.

```text
여러 Publisher
SKIP LOCKED
version 1 발행 실패
Backoff
version 2 선행 발행
```

```text
DB 발생 순서:
version 1(발급)이 먼저, version 2(취소)가 나중에 발생

Publisher 처리 순서:
여러 Publisher가 SKIP LOCKED로 병렬 처리하는 중
version 1 발행이 실패해 Backoff 재시도 대기에 들어가고, 그 사이 version 2가 먼저 처리되어 발행됨

Kafka 저장 순서:
version 2가 version 1보다 먼저 Kafka에 기록됨(순서 역전)
```

### **3. `schemaVersion`과 `aggregateVersion`을 비교한다**

| 필드 | 무엇의 버전인가? | 어떤 문제를 다루는가? | 값이 증가하는 예시 |
| --- | --- | --- | --- |
| `schemaVersion` | 이벤트 JSON 필드 구조 | 스키마 호환성 | 필드 추가/구조 변경 시 |
| `aggregateVersion` | 한 CouponIssue의 비즈니스 변경 순서 | 이벤트 순서, 최신성 판단 | 발급 -> 취소 상태 전이 시 |

### **4. 최신 상태 Projection의 UPSERT를 완성한다**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id, status, aggregate_version, updated_at
) VALUES (
    :couponIssueId, :status, :aggregateVersion, CURRENT_TIMESTAMP
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET
    status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = EXCLUDED.updated_at
WHERE
    EXCLUDED.aggregate_version > user_coupon_view.aggregate_version;
```

### **5. Version 2가 먼저 도착한 경우를 분석한다**

```text
먼저 처리:
CouponCancelled(version=2)

나중 처리:
CouponIssued(version=1)

최종 MyPage status:
CANCELLED (버전이 낮은 version 1이 이후 도착해도 덮어쓰지 않음)

최종 aggregate_version:
2

version=1 UPSERT의 affected rows:
0 (WHERE 조건 불만족으로 UPDATE 미적용)
```

### **6. 낮은 Version을 생략할 수 있는 범위를 판단한다**

| Consumer | 낮은 Version 생략 가능 여부 | 필요한 전제 또는 추가 순서 정책 |
| --- | --- | --- |
| 완전한 최신 상태만 저장하는 MyPage | 가능 | `incomingVersion > currentVersion` 조건만 있으면 됨 |
| 모든 발급·취소를 집계하는 Analytics | 불가 | 모든 전이가 필요, Version Gap 처리 정책 필요 |
| 발급·취소 알림을 각각 보내는 Notification | 불가 | 각 전이마다 별도 알림 필요, 순서 보장 필요 |

### **7. Version Gap 처리 정책을 작성한다**

현재 Version이 2인데 Version 4가 먼저 도착했다고 가정한다.

```text
Gap으로 판단하는 조건:
incomingVersion > currentVersion + 1

즉시 반영해도 되는 Consumer:
최신 상태만 저장하는 MyPafe

모든 전이가 필요한 Consumer의 처리:
해당 이벤트를 보류하거나 누락 버전을 재조회/재발행 요청을 한 뒤 순서대로 처리

복구 방법:
원본 DB 재조회 또는 이벤트 Replay로 누락된 버전 확보
```

### **8. 이벤트 스키마 변경의 호환성을 판단한다**

| 변경 | 호환 가능성 | 이유와 배포 방법 |
| --- | --- | --- |

## **과제 9. 잘못된 EDA 구현 리뷰하기**

다음 코드는 의도적으로 여러 문제가 포함되어 있다.

```java
@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void notify(CouponIssuedEvent event) {
    smsClient.send(event.userId(), "쿠폰 발급 완료");
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateMyPage(
    CouponIssuedEvent event,
    Acknowledgment acknowledgment
) {
    acknowledgment.acknowledge();

    if (processedEventRepository.existsById(
        event.kafkaOffset()
    )) {
        return;
    }

    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(event.kafkaOffset())
    );
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateAnalytics(CouponIssuedEvent event) {
    statisticsRepository.increaseIssuedCount(
        event.couponEventId()
    );
}
```

### **1. 문제를 최소 10개 찾는다**

각 문제를 다음 표에 작성한다.

| 번호 | 문제 코드 | 발생 가능한 장애 또는 데이터 오류 | 수정 방향 |
| ---: | --- | --- | --- |
| 1 | 세 메서드 모두 `groupId="coupon-result"` | Record가 세 로직 중 하나에만 분배되어 알림/마이페이지/통계 중 일부 누락 | 서비스별로 다른 Group ID 부여 |
| 2 | `notify()`가 로컬 상태 기록 없이 즉시 smsClient.send 호출 | Dual Write — 재전달 시 SMS 중복 발송 | notification_job 저장 + 별도 Sender로 분리 |
| 3 | `updateMyPage()`에서 `acknowledge()`가 DB 저장보다 먼저 호출 | Offset이 먼저 커밋되어 DB 저장 실패 시 이벤트 유실 | DB Commit 이후 acknowledge 호출 |
| 4 | `existsById(event.kafkaOffset())`로 멱등 판별 | Offset은 재발행 시 값이 달라져 논리적 중복을 못 잡음 | `eventMessageId` 기반으로 판별 |
| 5 | `exists` 확인 후 별도 `save` 호출 | 두 단계 사이 Race Condition으로 중복 저장 가능 | `INSERT ... ON CONFLICT DO NOTHING` 원자적 처리 |
| 6 | `userCouponViewRepository.save()`와 `processedEventRepository.save()`가 분리 호출 | 원자성 없음 — 중간 실패 시 데이터 불일치 | 하나의 로컬 트랜잭션으로 묶기 |
| 7 | `updateAnalytics()`가 멱등 처리 없이 무조건 `+1` | 중복 이벤트마다 이중 집계 | fact INSERT 성공 시에만 집계 증가 |
| 8 | 세 메서드 모두 `aggregateVersion` 등 순서·버전 검사 없음 | 순서 역전 시 잘못된 상태로 덮어씀 | 버전 비교(UPSERT WHERE 조건) 추가 |
| 9 | 알림/마이페이지/통계 책임이 한 클래스·같은 Group에 혼재 | 데이터 소유권 불명확, 장애 격리 실패 | Consumer를 서비스별로 분리 |
| 10 | requestId/eventMessageId 등 로그 식별자 전무 | 장애 추적 불가 | 상관관계 ID 로깅 및 지표 수집 추가 |

### **2. 반드시 찾아야 하는 문제를 연결한다**

| 검토 항목 | 문제가 있는 코드 | 수정 방향 |
| --- | --- | --- |

```text
Kafka coupon.issued

processed_event

user_coupon_view
```

```text
Kafka coupon.issued
```

### **4. 수정된 구조의 보장 수준을 판단한다**

| 항목 | 보장/조건부 보장/보장하지 않음 | 이유 |
| --- | --- | --- |
| 쿠폰 발급 DB의 최종 성공 | 보장 | Coupon Service 트랜잭션에서 이미 확정 |
| 세 Group이 각자 이벤트를 소비할 기회 | 보장 | Group 분리로 각각 독립 구독 |
| Kafka Record의 물리적 Exactly-Once | 보장하지 않음 | Kafka는 기본적으로 At-Least-Once |
| MyPage 중복 반영 방지 | 조건부 보장 | processed_event + 원자적 트랜잭션 전제 |

| 외부 SMS Exactly-Once | 보장하지 않음 | Provider가 멱등 키 미지원 시 중복 가능 |
| 발급 직후 MyPage의 즉시 일치 | 보장하지 않음 | 최종적 일관성 — 반영까지 지연 존재 |

## **보너스 2. Projection 재구축 테스트 설계하기**

| 테스트 상황 | 준비 데이터 | 실행 방법 | 검증할 결과 |
| --- | --- | --- | --- |
| 동일 이벤트 2회 Replay | 동일 eventMessageId 이벤트 1건 | 같은 이벤트를 2번 전달	| user_coupon_view/fact가 1건만 생성됨 |  |
| Version 2 뒤 Version 1 전달 | version 1, 2 이벤트 | 	2번 먼저 → 1번 나중 전달	| 최종 상태는 version 2 유지, version 1 UPDATE affected rows=0 |
| Backfill 중 새 이벤트 유입 | Snapshot 이후 발생한 이벤트 | Backfill과 동시에 Catch-up 실행 | 중복·누락 없이 최종 반영 |
| Kafka 보관 기간 이전 데이터 존재 | Kafka에 없는 오래된 발급 건 | Snapshot Backfill만으로 복구 시도 | Snapshot으로 정상 채워짐 |
| Consumer DB Commit 직후 종료 | DB Commit 후 Offset Commit 전 강제 종료 시뮬레이션 | 재시작 | 재전달된 이벤트가 멱등하게 무시됨 |

한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유도 작성한다.

```text
정상 케이스만으로는 중복 전달, 순서 역전, 부분 장애 같은 예외 상황에서의 동작을 검증할 수 없다.

Projection의 안전성은 여러 실패, 재시도 시나리오에서도 최종적으로 정확한 상태에 도달하는지로 판단해야 한다.
```

# **8. 핵심 질문**

과제를 마친 뒤 다음 질문에 한 문장씩 답한다.

```text
1. Notification, MyPage와 Analytics가 서로 다른 Group을 사용해야 하는 이유는 무엇인가?
같은 Group이면 Record가 나뉘어 전달되므로, 서로 다른 Group을 써야 각자 모든 이벤트를 독립적으로 소비할 수 있다.


2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
DB에서 발급이 확정된 뒤 만들어진 과거 사실을 알리는 것이지, 발급을 지시하는 병령어 아니기 때문이다.


3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
Coupon Service DB의 coupon_issue가 최종 원장이고, MyPage는 그로부터 파생된 재구축 가능한 데이터다.


4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
Kafkak Record는 재전달 또는 재발행 될 수 있는데, 이때 물리적 위치인 Offset은 매번 달라지지만 논리적 이벤트 ID는 동일하게 유지되기 때문이다.


5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
두 작업이 항상 함께 성공, 실패해야 "처리했다는 기록"과 "실제 반영"의 불일치(멱등성 붕괴)를 막을 수 있기 때문이다.


6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
DB 반영과 MyPage 반영 사이에는 이벤트 발행 및 Consumer 처리 시간이 걸리는 최종적 일관성 구간이 존재하기 때문이다.


7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
Publisher 순서 역전이나 재시도로 낮은 버전이 나중에 도착할 수 있어, Consumer가 직접 검사해야만 의미가 있기 때문이다.


8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
낮은 버전이라도 아직 처리하지 않은 사실일 수 있어, 버리면 데이터가 영구히 유실되기 때문이다.


9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
Read Model은 파생 데이터이므로 버그 및 장애로 잘못된 값이 쌓였을 때 원본으로부터 다시 만들 수 있어야 서비스 신뢰성을 유지할 수 있기 때문이다.


10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
Notification 장애는 후속 작업의 실패일 뿐이고 쿠폰 발급은 이미 성공한 사실이므로, 발급 로직을 재실행하면 중복 발급 등 원본 데이터 정합성이 깨지기 때문이다.
```
