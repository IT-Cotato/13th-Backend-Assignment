## **과제 1. 직접 호출 구조와 EDA 비교하기**

Coupon Service가 쿠폰 발급 뒤 세 서비스를 순서대로 호출한다고 가정한다.

```text
Coupon Service
  |
  +--> Notification Service
  |
  +--> MyPage Service
  |
  +--> Analytics Service
```

### **1. 직접 호출 구조의 결합을 분석한다**

| 결합 종류  | 발생하는 문제                                     | EDA 적용 후 달라지는 점                                |
|--------|---------------------------------------------|------------------------------------------------|
| 시간 결합  | 호출 시점에 상대 서비스가 반드시 실행 중이어야 한다.              | Consumer가 실행 중이지 않아도 이벤트를 나중에 처리할 수 있다.        |
| 장애 결합  | 후속 서비스의 지연이나 장애가 Coupon Service에 전파된다.      | 각 Consumer가 독립적으로 처리되어 장애가 다른 서비스로 전파되지 않는다.   |
| 변경 결합  | 후속 서비스가 추가되거나 변경되면 Coupon Service도 수정해야 한다. | 새로운 Consumer를 추가해도 Coupon Service를 수정할 필요가 없다. |
| 데이터 결합 | 다른 서비스의 데이터나 내부 구조에 직접 의존할 수 있다.            | 각 서비스가 자신의 데이터를 관리하고 이벤트를 통해 필요한 정보를 전달받는다.    |

### **2. 다음 장애 상황을 분석한다**

```text
1. coupon_issue DB Commit 성공
2. Notification API 호출 실패
3. Coupon Service가 전체 요청 실패 응답
4. 클라이언트가 같은 요청을 다시 전송
```

```text
이미 확정된 쿠폰 발급 상태: coupon_issue는 이미 DB에 Commit되어 발급이 완료된 상태이다.

쿠폰 발급을 Rollback하면 안 되는 이유: 알림 실패는 이미 완료된 쿠폰 발급 자체의 실패가 아니기 때문이다.

다시 실행해야 하는 작업: 실패한 Notification 작업

다시 실행하면 안 되는 작업: 이미 완료된 쿠폰 발급 작업
```

### **2. 세 서비스에 같은 Group ID를 사용하면 어떤 일이 발생하는지 설명한다**

```text
같은 Group 안의 Consumer 관계: 같은 Group의 Consumer들은 Partition을 나누어 메시지를 처리한다.

CouponIssued 한 건의 전달 결과: 하나의 Consumer 인스턴스만 해당 Record를 처리한다.

세 서비스 중 일부 작업이 누락될 수 있는 이유: 같은 Group에서는 하나의 Record가 모든 Consumer에 전달되는 것이 아니므로 알림, 마이페이지, 통계가 모두 같은 이벤트를 처리할 수 없다.
```

|--------------|-------------------------:|-------------------------------|-----------------|
| Notification |                        2 | 사용되지 않는 Partition 없음          | 영향 없음           |

| Analytics    |                        1 | 사용되지 않는 Partition 없음          | 영향 없음           |

### **4. Consumer Group의 Committed Offset 의미를 설명한다**

```text
Committed Offset이 나타내는 것: 해당 Consumer Group이 Partition에서 어디까지 처리를 완료했는지를 나타낸다.

Committed Offset만으로 증명할 수 없는 것: 해당 이벤트의 비즈니스 처리가 정확히 한 번만 수행되었다는 것은 증명할 수 없다.

Notification Group의 Offset이 MyPage Group에 영향을 주는가?: 영향을 주지 않는다. 각 Consumer Group은 Offset을 독립적으로 관리한다.
```

## **과제 3. CQRS와 MyPage Read Model 설계하기**

### **1. Command Model과 Read Model을 비교한다**

| 구분             | Command / Write Model | Query / Read Model    |
|----------------|-----------------------|-----------------------|
| 주요 목적          | 데이터 변경과 비즈니스 불변식 보장   | 빠르고 단순한 조회            |
| 대표 작업          | 쿠폰 발급 및 상태 변경         | 마이페이지 쿠폰 목록 조회        |
| 데이터 구조         | 정확한 쓰기와 정합성에 적합한 구조   | 조회 화면에 맞게 가공된 비정규화 구조 |
| 최종 원장 여부       | O                     | X                     |
| 장애 후 재구축 가능 여부 | 원본 데이터이므로 재구축 대상이 아님  | O                     |

### **2. CQRS에 대해 다음 문장을 판단한다**

| 문장                                       | 맞음/틀림 | 이유                                                    |
|------------------------------------------|-------|-------------------------------------------------------|
| CQRS를 적용하려면 반드시 DB가 두 개여야 한다.            | 틀림    | 같은 DB에서도 Command와 Query의 처리 경로와 모델을 분리할 수 있다.         |
| CQRS는 Event Sourcing과 같은 의미다.            | 틀림    | CQRS는 변경과 조회의 책임을 분리하는 방식이며 Event Sourcing은 별개의 개념이다. |
| 같은 애플리케이션에서도 Command와 Query 모델을 나눌 수 있다. | 맞음    | 물리적인 서비스 분리 없이도 처리 경로와 모델을 분리할 수 있다.                  |
| 테이블 이름만 둘로 나누면 자동으로 CQRS가 된다.            | 틀림    | Command와 Query의 책임과 처리 모델이 실제로 분리되어야 한다.              |

### **3. `user_coupon_view` DDL을 완성한다**

다음 요구사항을 만족해야 한다.

```text
coupon_issue_id Primary Key
user_id와 coupon_event_id 저장
현재 status와 aggregate_version 저장
issued_at과 updated_at 저장
같은 사용자·이벤트의 중복 노출 방지
사용자별 최신 쿠폰 조회 인덱스
```

```sql
CREATE TABLE user_coupon_view (
    coupon_issue_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    coupon_event_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    aggregate_version BIGINT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    UNIQUE (user_id, coupon_event_id)
);

CREATE INDEX idx_user_coupon_view_user_issued
    ON user_coupon_view (user_id, issued_at DESC);
```

### **4. 각 제약과 인덱스의 역할을 작성한다**

| 장치                                  | 막거나 개선하는 문제                     |
|-------------------------------------|---------------------------------|
| `PRIMARY KEY (coupon_issue_id)`     | 같은 쿠폰 발급 건이 중복 저장되는 것을 막는다.     |
| `UNIQUE (user_id, coupon_event_id)` | 같은 사용자의 동일 쿠폰이 중복 노출되는 것을 막는다.  |
| `(user_id, issued_at DESC)` Index   | 사용자별 최신 쿠폰 목록을 빠르게 조회할 수 있게 한다. |

### **5. 다음 조회 API가 Read Model을 사용하는 이유를 설명한다**

```text
GET /api/users/{userId}/coupons
```

```text
원본 발급 DB를 매번 복잡하게 조회할 때의 문제: 여러 테이블을 조인하거나 다른 서비스의 데이터를 조회해야 하므로 조회가 복잡하고 느려질 수 있다.

Read Model에 일부 데이터가 중복되어도 되는 이유: 조회에 필요한 데이터를 미리 저장하여 더 단순하고 빠르게 조회하기 위한 모델이기 때문이다.

```

### **6. 화면 표시용 데이터 전달 방법을 비교한다**

마이페이지에 `couponDisplayName`과 `discountAmount`가 필요하다고 가정한다.

| 방법                                                | 장점                                    | 단점                                 | 데이터 소유권·장애 결합에 미치는 영향                    |
|---------------------------------------------------|---------------------------------------|------------------------------------|------------------------------------------|
| `CouponIssued`에 Snapshot 포함                       | 이벤트만으로 필요한 데이터를 바로 반영할 수 있다.          | 이벤트 크기가 커지고 표시 정보 변경에 영향을 받을 수 있다. | Coupon Service DB에 직접 의존하지 않아 장애 결합이 낮다. |
| `CouponEventCreated/Updated`로 메타데이터 Projection 관리 | 쿠폰 정보 변경을 Read Model에 지속적으로 반영할 수 있다. | 별도의 이벤트와 Projection 관리가 필요하다.      | 데이터 소유권을 유지하면서 서비스 간 결합을 낮출 수 있다.        |
| 이벤트 처리 중 Coupon Service API 동기 호출                 | 필요한 최신 정보를 바로 가져올 수 있다.               | API 장애나 지연 시 Consumer 처리도 영향을 받는다. | Coupon Service와 장애 결합이 생긴다.              |
| Coupon Service DB 직접 조회                           | 구현이 단순하고 데이터를 바로 조회할 수 있다.            | 다른 서비스의 DB 구조에 직접 의존하게 된다.         | 데이터 소유권을 침해하고 강한 결합이 생긴다.                |

이벤트에 원본 Entity 전체를 넣으면 안 되는 이유도 작성한다.

```text
- 이벤트에 원본 Entity 전체를 넣으면 Consumer가 필요하지 않은 내부 데이터까지 이벤트 계약에 포함되어 결합이 커질 수 있다.
- Consumer가 실제로 필요한 안정적인 값만 포함하고 개인정보나 변경 가능성이 큰 내부 필드는 제외해야 한다.
```

## **과제 4. Consumer 멱등 트랜잭션 설계하기**

같은 논리 이벤트가 다음처럼 두 번 저장되었다고 가정한다.

```text
Partition 2 / Offset 100 / eventMessageId = evt-001
Partition 2 / Offset 101 / eventMessageId = evt-001
```

### **1. Offset과 eventMessageId를 비교한다**

| 값                  | 식별 대상                | 재발행 시 변경되는가? | Consumer 멱등성 Key로 적절한가? |
|--------------------|----------------------|--------------|-------------------------|
| Partition + Offset | Kafka Record의 물리적 위치 | O            | X                       |
| eventMessageId     | 논리적인 이벤트             | X            | O                       |

### **2. `processed_event` DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_message_id)
);
```

다음 세 값 중 올바른 `subscriber_id`를 고르고 이유를 작성한다.

```text
pod-a7f9c
server-10.0.0.12
mypage-coupon-projection
```

```text
선택: mypage-coupon-projection

이유: 특정 서버나 Pod가 아니라 하나의 논리적인 Consumer Group을 식별해야 하기 때문이다.
```

### **3. MyPage Consumer 트랜잭션을 완성한다**

다음 요구사항을 만족해야 한다.

```text
ON CONFLICT DO NOTHING으로 최초 처리 권한 등록
RETURNING 결과로 최초·중복 판별
최초 이벤트일 때만 user_coupon_view 변경
processed_event와 조회 모델 변경의 원자성
```

```sql
BEGIN;

WITH accepted AS (
    INSERT INTO processed_event (
        subscriber_id,
        event_message_id
    )
    VALUES (
        'mypage-coupon-projection',
        :eventMessageId
    )
    ON CONFLICT DO NOTHING
    RETURNING event_message_id
)
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    aggregate_version,
    issued_at,
    updated_at
)
SELECT
    :couponIssueId,
    :userId,
    :couponEventId,
    'ISSUED',
    :aggregateVersion,
    :issuedAt,
    CURRENT_TIMESTAMP
FROM accepted;

COMMIT;
```

### **4. 일반 INSERT의 PK 예외를 잡고 계속 진행하면 안 되는 이유를 설명한다**

PostgreSQL 트랜잭션 상태를 포함한다.

```text
- PostgreSQL에서는 INSERT 중 PK 충돌 등의 예외가 발생하면 해당 트랜잭션이 실패 상태가 된다.
- 예외만 잡고 같은 트랜잭션을 계속 진행할 수 없으므로 ON CONFLICT DO NOTHING과 RETURNING을 사용해 중복 여부를 판단해야 한다.
```

### **5. 다음 잘못된 처리 순서의 결과를 분석한다**

```text
1. processed_event만 Commit
2. user_coupon_view 변경 실패
3. Kafka Record 재전달
```

```text
재전달 시 Consumer 판단: processed_event가 이미 존재하므로 처리 완료된 이벤트라고 판단한다.

최종 조회 모델 상태: user_coupon_view에는 이벤트가 반영되지 않은 상태로 남는다.

두 작업을 같은 트랜잭션에 넣어야 하는 이유: processed_event 저장과 조회 모델 변경이 함께 Commit되거나 함께 Rollback되어야 중복 처리와 데이터 누락을 막을 수 있기 때문이다.
```

### **6. Consumer DB Commit 후 Offset Commit 전 종료를 분석한다**

```text
Consumer DB 상태: processed_event와 user_coupon_view 변경이 Commit된 상태

Consumer Group Offset: 아직 Commit되지 않은 상태

재시작 후 전달: 같은 Kafka Record가 다시 전달될 수 있다.

재전달된 이벤트 처리: eventMessageId가 processed_event에 이미 존재하므로 중복 이벤트로 판단하고 변경 없이 정상 종료한다.
```

### **7. Offset 완료 정책을 작성한다**

다음을 반드시 포함한다.

```text
enable.auto.commit
DB Commit과 Offset Commit 순서
Listener 예외 처리
같은 Partition 병렬 처리 시 앞선 미완료 Record
```

```text
enable.auto.commit: false

DB Commit과 Offset Commit 순서: Consumer DB 트랜잭션 Commit이 완료된 뒤 Kafka Offset을 Commit한다.

Listener 예외 처리: 처리 중 예외가 발생하면 Offset을 Commit하지 않아 Record가 다시 전달될 수 있도록 한다.

같은 Partition 병렬 처리 시 앞선 미완료 Record: 앞선 Record가 완료되지 않은 상태에서 더 높은 Offset부터 Commit하지 않아야 한다.
```

```sql
);
```

```sql
    INSERT INTO coupon_issue_fact (
        coupon_issue_id,
        event_message_id,

        :eventMessageId,

        :userId,

    RETURNING coupon_issue_id

WHERE coupon_event_id = :couponEventId
```

```sql
INSERT INTO user_coupon_view (

    status,
    aggregate_version,
    updated_at

    :couponIssueId,
    :status,
    :aggregateVersion,

DO UPDATE
SET
    status = EXCLUDED.status,
    aggregate_version = EXCLUDED.aggregate_version,
    updated_at = CURRENT_TIMESTAMP
```

```text
1. 새 Projection 테이블 생성: 기존 조회 서비스에 영향을 주지 않고 재구축하기 위해 user_coupon_view_v2를 생성한다.

2. 원본 DB Snapshot Backfill: Coupon Service의 원본 데이터를 기준으로 기존 발급 데이터를 v2에 채운다.

3. 새 Consumer Group으로 Kafka Replay: 보관 중인 이벤트를 새로운 Consumer Group으로 다시 소비한다.

4. Backfill 경계 이후 이벤트 Catch-up: Backfill 중 새롭게 발생한 이벤트까지 처리하여 최신 상태를 따라잡는다.

5. 원본과 v2 정합성 검증: 원본 데이터와 새 Projection의 상태 및 건수를 비교한다.

6. 조회 API 전환: 검증이 완료되면 조회 대상을 user_coupon_view_v2로 변경한다.

7. 기존 Projection 보관 또는 제거: 안정적으로 전환된 것을 확인한 뒤 기존 Projection을 보관하거나 제거한다.
```

### **3. Kafka 보관 기간이 지난 경우의 복구 방법을 설명한다**

```text
Kafka만으로 전체 Replay가 가능한가?: X

필요한 다른 복구 기준: Coupon Service의 원본 DB Snapshot

Backfill 중 새 이벤트가 들어올 때 필요한 경계: Snapshot 시점 또는 특정 Offset을 경계로 정하여 그 이후 이벤트를 Catch-up해야 한다.
```

### **4. 운영 지표를 완성한다**

| 지표                        | 의미                                   | 장애 신호 예시                   |
|---------------------------|--------------------------------------|----------------------------|
| Group별 Consumer Lag       | Consumer가 아직 처리하지 못한 Kafka Record의 양 | Lag이 계속 증가함                |
| Oldest Unprocessed Age    | 가장 오래 처리되지 않은 이벤트의 대기 시간             | 오래된 이벤트가 계속 남아 있음          |

| Handler Failure Count     | Consumer 처리 중 발생한 실패 횟수              | 특정 Consumer의 실패가 반복적으로 증가함 |
| Duplicate Event Count     | 중복 이벤트가 감지된 횟수                       | 동일 이벤트의 재전달이 급격히 증가함       |
| Read Model Mismatch Count | 원본과 Read Model이 일치하지 않는 건수           | 원본과 조회 데이터의 불일치가 발생함       |

## **과제 9. 잘못된 EDA 구현 리뷰하기**

다음 코드는 의도적으로 여러 문제가 포함되어 있다.

```java
@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void notify(CouponIssuedEvent event) {
    smsClient.send(event.userId(), "쿠폰 발급 완료");
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateMyPage(
    CouponIssuedEvent event,
    Acknowledgment acknowledgment
) {
    acknowledgment.acknowledge();

    if (processedEventRepository.existsById(
        event.kafkaOffset()
    )) {
        return;
    }

    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(event.kafkaOffset())
    );
}

@KafkaListener(
    topics = "coupon.issued",
    groupId = "coupon-result"
)
public void updateAnalytics(CouponIssuedEvent event) {
    statisticsRepository.increaseIssuedCount(
        event.couponEventId()
    );
}
```

### **1. 문제를 최소 10개 찾는다**

각 문제를 다음 표에 작성한다.

| 번호 | 문제 코드                                                                   | 발생 가능한 장애 또는 데이터 오류                                          | 수정 방향                                                           |
|---:|-------------------------------------------------------------------------|--------------------------------------------------------------|-----------------------------------------------------------------|
|  1 | 세 Listener의 `groupId = "coupon-result"`                                 | 하나의 이벤트를 세 서비스가 모두 처리하지 못해 일부 작업이 누락될 수 있다.                  | Notification, MyPage, Analytics에 서로 다른 Group ID를 사용한다.          |
|  2 | `smsClient.send()` 직접 호출                                                | SMS 발송과 Consumer 처리 상태를 원자적으로 묶을 수 없어 중복 또는 누락 발송이 발생할 수 있다. | `notification_job`을 저장하고 별도 Sender가 외부 Provider를 호출한다.          |
|  3 | DB 처리 전 `acknowledgment.acknowledge()`                                  | DB 저장 실패에도 Offset이 완료되어 이벤트가 유실될 수 있다.                       | DB Commit이 완료된 뒤 Offset을 완료한다.                                  |
|  4 | `existsById()` 후 `save()`                                               | 동시에 같은 이벤트를 처리하면 둘 다 미처리로 판단하는 Race Condition이 발생할 수 있다.     | `INSERT ... ON CONFLICT DO NOTHING`으로 원자적으로 처리 권한을 획득한다.        |
|  5 | `event.kafkaOffset()`을 멱등성 Key로 사용                                      | 같은 논리 이벤트가 다른 Offset으로 재발행되면 중복을 판단하지 못한다.                   | `eventMessageId`를 멱등성 Key로 사용한다.                                |
|  6 | `userCouponViewRepository.save()`와 `processedEventRepository.save()` 분리 | 한쪽만 성공하면 조회 모델과 처리 기록의 상태가 달라질 수 있다.                         | 두 작업을 같은 DB 트랜잭션으로 처리한다.                                        |
|  7 | `increaseIssuedCount()` 직접 실행                                           | 이벤트가 재전달되면 발급 통계가 중복 증가한다.                                   | `coupon_issue_fact`를 멱등하게 저장하고 실제 INSERT된 경우에만 집계를 증가시킨다.       |
|  8 | 이벤트 Version 검사 없음                                                       | 늦게 도착한 과거 이벤트가 최신 상태를 덮어쓸 수 있다.                              | `aggregateVersion`을 비교하여 최신 상태만 반영한다.                           |
|  9 | 서비스별 데이터 소유권 구분 없음                                                      | 다른 서비스의 데이터에 직접 의존하거나 수정하는 구조가 될 수 있다.                       | 각 Consumer가 자신의 DB만 변경하도록 책임을 분리한다.                             |
| 10 | 실패·Lag 관련 관측 정보 없음                                                      | Consumer 지연이나 처리 실패 발생 시 원인을 추적하기 어렵다.                       | Consumer Lag, Projection Delay, 실패 횟수 등을 모니터링하고 관련 ID를 로그에 남긴다. |

### **4. 수정된 구조의 보장 수준을 판단한다**

| 항목                             | 보장/조건부 보장/보장하지 않음 | 이유                                                    |
|--------------------------------|-------------------|-------------------------------------------------------|
| 쿠폰 발급 DB의 최종 성공                | 보장                | Coupon Service의 DB Commit이 발급 성공의 최종 기준이다.            |
| 세 Group이 각자 이벤트를 소비할 기회        | 보장                | 서로 다른 Consumer Group을 사용하므로 각 Group이 이벤트를 독립적으로 소비한다. |
| Kafka Record의 물리적 Exactly-Once | 보장하지 않음           | 동일한 논리 이벤트가 재전달되거나 재발행될 수 있다.                         |

| 외부 SMS Exactly-Once            | 조건부 보장            | Provider가 Idempotency Key를 지원하는 경우 중복 발송을 방지할 수 있다.   |
| 발급 직후 MyPage의 즉시 일치            | 보장하지 않음           | 이벤트 기반 Projection은 최종적 일관성을 가지므로 반영 지연이 발생할 수 있다.     |

## **보너스 2. Projection 재구축 테스트 설계하기**

| 테스트 상황                   | 준비 데이터                                       | 실행 방법                                                   | 검증할 결과                                      |
|--------------------------|----------------------------------------------|---------------------------------------------------------|---------------------------------------------|
| 동일 이벤트 2회 Replay         | 같은 `eventMessageId`를 가진 이벤트                  | 동일 이벤트를 두 번 전달한다.                                       | `user_coupon_view`에는 한 번만 반영된다.             |
| Version 2 뒤 Version 1 전달 | 같은 `couponIssueId`의 version 2와 version 1 이벤트 | version 2를 먼저 처리한 뒤 version 1을 전달한다.                    | 최신 상태인 version 2가 유지되고 version 1은 반영되지 않는다. |
| Backfill 중 새 이벤트 유입      | 기존 원본 데이터와 Backfill 이후 새로 발생할 이벤트            | Snapshot Backfill 중 새로운 이벤트를 발생시킨 뒤 Catch-up한다.         | 기존 데이터와 새 이벤트가 모두 누락 없이 Projection에 반영된다.   |
| Kafka 보관 기간 이전 데이터 존재    | Kafka에서 이미 삭제된 과거 발급 데이터                     | 원본 DB Snapshot으로 Backfill한 뒤 보관 중인 Kafka 이벤트를 Replay한다. | Kafka에 없는 과거 데이터까지 Projection에 복구된다.        |
| Consumer DB Commit 직후 종료 | 아직 Offset Commit되지 않은 이벤트                    | DB Commit 직후 Consumer를 종료하고 다시 시작한다.                    | 이벤트가 재전달되어도 멱등 처리되어 중복 반영되지 않는다.            |

한 번의 정상 실행만으로 Projection 안전성을 증명할 수 없는 이유도 작성한다.

```text
- 한 번의 정상 실행만으로는 이벤트 재전달, 순서 역전, Consumer 장애, Backfill 중 이벤트 유입과 같은 상황에서 Projection이 안전한지 확인할 수 없다.
- 따라서 중복, 순서 변경, 장애와 복구 상황까지 테스트해야 Projection의 멱등성과 정합성을 검증할 수 있다.
```

```text
- 세 서비스가 같은 이벤트를 각각 독립적으로 받아 자신의 작업을 수행해야 하기 때문이다.

2. CouponIssued는 왜 명령이 아니라 이미 발생한 사실이어야 하는가?
- 쿠폰 발급이 DB에서 이미 확정된 이후 생성되는 이벤트이므로 다시 발급하라는 요청이 아니라 발급되었다는 사실을 나타내야 하기 때문이다.

3. Coupon Service DB와 MyPage Read Model 중 발급 여부의 최종 기준은 무엇인가?
- Coupon Service DB의 coupon_issue가 발급 여부의 최종 기준이다.

4. 같은 eventMessageId가 다른 Offset으로 전달될 수 있는 이유는 무엇인가?
- 같은 논리 이벤트가 재발행되면 Kafka에 새로운 Record로 저장되어 다른 Offset을 가질 수 있기 때문이다.

5. processed_event와 Consumer 비즈니스 변경을 같은 트랜잭션에 넣는 이유는 무엇인가?
- 이벤트 처리 기록과 실제 데이터 변경이 함께 Commit되거나 Rollback되어 중복 처리와 데이터 누락을 막기 위해서이다.

6. DB ISSUED인데 마이페이지에 쿠폰이 잠시 보이지 않을 수 있는 이유는 무엇인가?
- 쿠폰 발급 DB Commit 이후 MyPage Consumer가 이벤트를 처리하여 Read Model에 반영하기까지 지연이 발생할 수 있기 때문이다.

7. aggregateVersion이 이벤트 순서 역전을 자동으로 막아 주지 않는 이유는 무엇인가?
- aggregateVersion은 비즈니스 변경 순서를 나타내는 값일 뿐이므로 Consumer가 직접 Version을 비교하여 처리해야 하기 때문이다.

8. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버리면 안 되는 이유는 무엇인가?
- Analytics나 Notification처럼 모든 상태 전이를 집계하거나 각각 처리해야 하는 Consumer는 과거 이벤트도 필요한 작업일 수 있기 때문이다.

9. Read Model을 다시 만들 수 있어야 하는 이유는 무엇인가?
- Read Model은 원본이 아닌 파생 데이터이므로 오류나 불일치가 발생했을 때 원본 데이터나 이벤트를 기반으로 복구할 수 있어야 하기 때문이다.

10. Notification 장애가 발생했을 때 쿠폰 발급 로직을 다시 실행하면 안 되는 이유는 무엇인가?
- 쿠폰 발급은 이미 성공한 상태이므로 다시 실행하면 중복 발급될 수 있으며 실패한 Notification 작업만 다시 처리해야 하기 때문이다.
```
