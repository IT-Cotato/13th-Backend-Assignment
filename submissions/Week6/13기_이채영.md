## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
- PostgreSQL
- Kafka
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
- @Transactional은 PostgreSQL의 DB 트랜잭션만 보장한다.
- PostgreSQL과 Kafka는 서로 다른 시스템이므로 하나의 트랜잭션으로 묶을 수 없다.
- 따라서 한쪽만 성공하는 Dual Write 문제가 발생할 수 있다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[장애 지점] - DB Commit 후 Kafka 발행 전 서버 종료
    ↓
Kafka 발행

최종 DB 상태: coupon_issue 저장 완료, coupon_issue_request = ISSUED, issued_count 증가 완료

최종 Kafka 상태: CouponIssued 이벤트 없음

후속 서비스에 미치는 영향: Notification, MyPage, Analytics가 발급 사실을 알 수 없다.

복구에 필요한 정보: 발행해야 할 CouponIssued 이벤트 정보(Outbox)
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점] - Kafka 발행 후 DB Commit 전 서버 종료
    ↓
DB Commit

최종 DB 상태: 쿠폰 발급 기록 없음

최종 Kafka 상태: CouponIssued 이벤트 존재

후속 서비스에 미치는 영향: 실제 발급되지 않은 쿠폰을 발급된 것으로 처리하여 데이터 정합성이 깨진다.
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료

KafkaTemplate.send() 호출 후
Broker ACK 확인 전 프로세스 종료
```

```
- DB Commit 후 Listener 실행 전에 서버가 종료되면 이벤트가 발행되지 않는다.
- `KafkaTemplate.send()`는 비동기 호출이므로 Broker ACK를 받기 전에 서버가 종료되면 이벤트가 유실될 수 있다.
- 이벤트 정보가 메모리에만 존재하면 장애 발생 후 재발행 기준이 사라진다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간                                      | 이번 Outbox로 해결되는가? | 이유                                       |
|-----------------------------------------|-------------------|------------------------------------------|
| coupon_issue 저장 ↔ CouponIssued 발행 의도 저장 | O                 | 같은 DB 트랜잭션으로 저장한다.                       |
| Redis SUCCESS ↔ 최초 요청 Kafka 발행          | X                 | Redis와 Kafka는 같은 트랜잭션으로 묶을 수 없다.         |
| 원본 Kafka 소비 ↔ 발급 DB Commit              | X                 | Kafka Offset과 DB Commit은 원자적으로 처리되지 않는다. |
| Consumer DB 저장 ↔ 외부 SMS API 호출          | X                 | DB와 외부 API는 같은 트랜잭션으로 묶을 수 없다.           |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것: 쿠폰 발급 결과와 이벤트 발행 의도를 같은 DB 트랜잭션으로 함께 저장하는 것

Transactional Outbox가 직접 보장하지 않는 것: Kafka에 정확히 한 번 발행되는 것, 원본 Kafka 소비와 DB Commit의 원자성, Consumer 처리와 외부 API 호출의 원자성
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

다음 두 이름의 의미 차이를 포함한다.

```
IssueCoupon
- 쿠폰을 발급하라는 명령

CouponIssued
- 쿠폰이 이미 발급되었다는 사실
```

```
- 이벤트는 이미 완료된 비즈니스 결과를 다른 서비스에 전달하기 위한 것이다.
- Consumer는 쿠폰을 다시 발급하지 않고 후속 작업만 수행한다.
```

| 값                        | 식별 대상        | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
|--------------------------|--------------|----------------|-------------------------|
| couponEventId            | 쿠폰 행사        | X              | X                       |

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt: 쿠폰 발급이라는 비즈니스 결과가 발생한 시각

publishedAt: Publisher가 Kafka Broker ACK를 확인한 시각

Publisher 재시도 시 변경하면 안 되는 값: occurredAt, Payload
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
- Outbox 저장 이후 원본 데이터가 변경될 수 있다.
- Publisher는 Outbox에 저장된 Payload를 그대로 발행해야 한다.
- Outbox Payload는 이벤트 발생 시점의 불변 Snapshot이어야 한다.
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    request_id UUID,

    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ
);
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';

-- affected rows가 몇 행이어야 하는가?
-- 1

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;

-- affected rows가 0일 때 가능한 원인은 무엇인가?
-- 쿠폰 소진 또는 존재하지 않는 이벤트

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
)
VALUES (
    :couponEventId,
    :userId,
    'ISSUED',
    CURRENT_TIMESTAMP
)
RETURNING id, issued_at;

-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장
INSERT INTO outbox_event (
    event_id,
    request_id,
    deduplication_key,
    aggregate_type,
    aggregate_id,
    event_type,
    schema_version,
    aggregate_version,
    topic,
    partition_key,
    payload,
    occurred_at
)
VALUES (
    :eventMessageId,
    :requestId,
    :deduplicationKey,
    'COUPON_ISSUE',
    :couponIssueId,
    'COUPON_ISSUED',
    1,
    1,
    'coupon.issued',
    :couponIssueId,
    :payload,
    :issuedAt
);

COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업                   | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리   |
|----------------------|-----------------|---------------|
| PENDING → PROCESSING | 1               | 트랜잭션 종료       |
| issued_count 조건부 증가  | 1               | 트랜잭션 Rollback |
| coupon_issue INSERT  | 1               | 트랜잭션 Rollback |
| PROCESSING → ISSUED  | 1               | 트랜잭션 Rollback |
| outbox_event INSERT  | 1               | 트랜잭션 Rollback |

```
- 쿠폰은 발급되었지만 발행해야 할 이벤트가 남지 않는다.

- 장애 발생 후 어떤 이벤트를 재발행해야 하는지 복구할 수 없다.
```

```
AckMode

```


## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                    Publisher B
------------------------------------------------
PENDING 행 SELECT              PENDING 행 SELECT
같은 event_id 조회             같은 event_id 조회
PROCESSING으로 UPDATE          PROCESSING으로 UPDATE
Kafka 이벤트 발행              Kafka 이벤트 발행
동일 이벤트 중복 발행          동일 이벤트 중복 발행
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY
        next_attempt_at,
        created_at,
        event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until =
        CURRENT_TIMESTAMP
        + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1. DB Connection을 장시간 점유한다.

2. Row Lock이 오래 유지되어 다른 Publisher의 처리가 지연된다.

3. Kafka 응답이 늦으면 트랜잭션 Timeout이 발생할 수 있다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
- 단일 Publisher도 Claim을 Commit한 직후 종료될 수 있다.
- 복구 정책이 없다면 PROCESSING 상태의 이벤트가 영원히 처리되지 않을 수 있으므로 Lease 만료 후 PENDING으로 복구해야 한다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료: Kafka에 발행을 요청하고 CompletableFuture를 반환받은 상태이며, Broker 저장 성공을 의미하지 않는다.

CompletableFuture 정상 완료: Kafka Broker로부터 ACK를 받아 Record 발행 성공을 확인한 상태다.

outbox = PUBLISHED: Kafka ACK 확인 후 Outbox 완료 상태까지 DB에 반영된 상태다.

모든 후속 Consumer 처리 완료: Notification, MyPage, Analytics 등 모든 Consumer가 이벤트 처리를 완료한 상태다.
```

### **2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다**

다음 조건을 반드시 포함한다.

```
event_id 일치

status = PROCESSING

claim_token 일치
```

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,
    lease_until = NULL,
    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
```

### **3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다**

다음 값을 함께 갱신한다.

```
next_attempt_at
```


### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
- 상황 A에서는 Broker에 Record가 저장되지 못한 상태에서 Timeout이 발생한다.
- 상황 B에서는 Broker에 Record가 저장되었지만 네트워크 문제 등으로 Publisher가 ACK를 받지 못해 Timeout이 발생한다.
- Publisher는 두 상황을 구분할 수 없으므로 Timeout 발생 시 미완료 상태로 처리하고 재시도해야 한다.
- 상황 B에서 재시도하면 같은 이벤트가 Kafka에 중복 발행될 수 있다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태: PENDING으로 변경하고 next_attempt_at을 설정한다.

재시도 여부: Exponential Backoff와 Jitter를 적용하여 재시도한다.

Kafka 중복 가능성: Broker에는 이미 저장되었지만 ACK만 받지 못한 경우 중복 발행될 수 있다.

Consumer에게 필요한 방어: eventMessageId를 기준으로 멱등 처리해야 한다.
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff: 재시도 간격을 점차 늘려 Kafka 장애 중 반복 요청으로 인한 부하를 줄인다.

Jitter: 재시도 시각을 무작위로 분산하여 여러 Publisher가 동시에 재시도하는 현상을 방지한다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인                             | Producer Idempotence로 방어 가능한가? | 이유                                                    |
|--------------------------------------|--------------------------------|-------------------------------------------------------|
| Producer 내부 네트워크 재시도                 | O                              | 같은 Producer 세션에서 발생한 내부 재시도의 중복을 방지할 수 있다.            |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | X                              | 새 Publisher가 애플리케이션 수준에서 같은 Outbox 이벤트를 다시 발행하기 때문이다. |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경      | X                              | 별도의 발행 요청으로 처리되므로 Producer Idempotence의 보장 범위를 벗어난다.  |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
- `whenComplete` 콜백은 Kafka Producer의 내부 I/O 스레드에서 실행될 수 있다.
- 콜백에서 DB Connection 획득이나 트랜잭션 처리를 하면 Producer 스레드가 블로킹될 수 있다.
- Producer 스레드가 지연되면 다른 Kafka 발행도 함께 지연되고 Lease 만료와 중복 발행이 증가할 수 있다.
- DB 작업은 `whenCompleteAsync`와 전용 Executor를 사용하여 Producer I/O 스레드와 분리해야 한다.
```

```
DB의 비즈니스 상태
```

| 항목              | 결과                                            |
|-----------------|-----------------------------------------------|
| outbox status   | PROCESSING                                    |
| Kafka Record    | 존재함                                           |

### **5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황**

```
Publisher A가 늦게 성공 UPDATE: token-A가 현재 claim_token과 일치하지 않으므로 상태를 변경하지 못해야 한다.

Publisher A가 늦게 실패 UPDATE: token-A가 현재 claim_token과 일치하지 않으므로 PENDING으로 변경하지 못해야 한다.

두 UPDATE에서 affected rows가 0이어야 하는 조건: event_id는 같지만 status가 PROCESSING이 아니거나 claim_token이 token-A와 일치하지 않는 경우
```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화: 발행되지 못한 이벤트가 계속 쌓이면서 증가한다.

가장 오래된 PENDING 대기 시간: Kafka 장애가 지속되는 동안 계속 증가한다.

attempt_count: Publisher가 이벤트를 다시 Claim할 때마다 증가한다.

Kafka 복구 후 처리: next_attempt_at이 지난 PENDING 이벤트를 다시 Claim하여 순차적으로 발행한다.

운영 알람: PENDING 수, 가장 오래된 PENDING 대기 시간, 높은 attempt_count를 기준으로 알람을 발생시킨다.
```

### **7. 다음 두 재시도 대상을 구분한다**

```
발급 DB 트랜잭션 실패: 원본 coupon.issue.requested 메시지를 재처리하여 쿠폰 발급 트랜잭션 전체를 다시 실행한다.

발급 DB Commit 성공 후 CouponIssued 발행 실패: 쿠폰 발급은 다시 실행하지 않고 Outbox Publisher가 기존 Outbox 이벤트만 재발행한다.
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유도 작성한다.

```
- 결과 이벤트 발행 실패 시에도 DB에는 이미 coupon_issue와 request ISSUED가 저장되어 있다.
- 쿠폰 발급을 다시 실행하면 issued_count가 중복 증가하거나 같은 사용자에게 쿠폰이 중복 발급될 수 있다.
- 따라서 발급 결과는 유지하고 실패한 Outbox 이벤트 발행만 재시도해야 한다.
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001

Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
- 같은 논리 이벤트가 재발행되면 서로 다른 Partition과 Offset을 가질 수 있다.
- Offset은 Kafka 내부의 물리적 위치일 뿐 이벤트 자체를 식별하지 못한다.
- Consumer 멱등성 Key로는 동일하게 유지되는 eventMessageId를 사용해야 한다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_id)
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

다음 중 적절한 값을 선택하고 이유를 작성한다.

```
pod-7f8c9d

server-10.0.0.12

mypage-coupon-projection
```

```
- 적절한 값: mypage-coupon-projection
- Pod 이름이나 서버 주소는 재시작과 확장에 따라 변경될 수 있다.
- 인스턴스마다 subscriber_id가 달라지면 같은 이벤트를 새로운 이벤트로 판단하여 중복 처리할 수 있다.
- subscriber_id는 프로세스가 아닌 안정적인 논리 구독자를 식별해야 한다.
```

### **4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다**

```sql
BEGIN;

-- 1. eventMessageId 중복 확인

    subscriber_id,
    event_id

```

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다**


### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**


### **7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다**

```
1. Notification Service 내부에 알림 Outbox를 두고 별도 Sender가 전송한다.

2. 외부 알림 Provider가 제공하는 Idempotency Key를 사용한다.

3. notificationId를 저장하여 동일 알림의 중복 전송을 방어한다.
```

### **8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다**

```
Kafka Topic 보관 기간

Consumer Offset 되감기

Outbox 지연 재발행

운영자 수동 재발행
```

```
- processed_event를 너무 일찍 삭제하면 Kafka Topic에 남아 있는 이벤트가 다시 전달될 때 중복으로 처리될 수 있다.
- Consumer Offset을 이전 시점으로 되감으면 과거 이벤트가 다시 전달될 수 있다.

- 운영자가 같은 이벤트를 수동으로 재발행할 수 있다.
- 따라서 processed_event 보관 기간은 Kafka Topic 보관 기간과 최대 재전달 지연보다 길게 설정해야 한다.
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateType = COUPON_ISSUE

aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
- 같은 CouponIssue에 속한 이벤트를 같은 Kafka Partition에 전달하기 위해 사용한다.
- Consumer가 같은 Aggregate의 이벤트를 동일한 처리 단위로 다룰 수 있다.
- 여러 Partition에 이벤트를 분산하여 특정 Partition에 부하가 집중되는 것을 줄일 수 있다.
- 향후 Aggregate 단위 순서 보장을 도입할 때 기준으로 사용할 수 있다.
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

다음을 반드시 포함한다.

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
- Kafka Partition의 순서는 Producer가 `send()`를 호출한 순서로 결정되며 DB에서 이벤트가 발생한 순서로 결정되지 않는다.
- 여러 Publisher 인스턴스가 서로 다른 이벤트를 동시에 Claim하고 발행할 수 있다.
- SKIP LOCKED는 잠긴 이전 이벤트를 건너뛰고 다음 이벤트를 가져올 수 있다.
- 먼저 발생한 이벤트가 발행에 실패하여 Backoff 상태가 되면 나중 이벤트가 먼저 발행될 수 있다.
- Producer의 재시도와 관련 설정에 따라 실제 Kafka 저장 순서가 달라질 수 있다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A: CouponIssued(version=1)을 Claim했지만 Kafka 발행에 실패하여 Backoff 재시도 상태로 변경

Publisher B: CouponCancelled(version=2)을 Claim하고 Kafka 발행 성공

Kafka 저장 순서: CouponCancelled(version=2) → CouponIssued(version=1)
```

```
2. 서버와 DB의 시간 정밀도 또는 시계가 서로 다를 수 있다.

3. Publisher 재시도로 실제 Kafka 도착 순서와 occurredAt 순서가 달라질 수 있다.
```

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표                      | 무엇을 의미하는가?                      | 어떤 상태가 장애 신호인가?                   |
|-------------------------|---------------------------------|-----------------------------------|
| PENDING 이벤트 수           | 아직 Kafka에 발행되지 않은 이벤트 수         | 일정 시간 동안 계속 증가하는 경우               |
| 가장 오래된 PENDING 대기 시간    | 가장 오래 기다리고 있는 이벤트의 발행 지연 시간     | 허용한 발행 지연 시간을 초과하는 경우             |
| PROCESSING 이벤트 수        | Publisher가 Claim하여 발행 중인 이벤트 수  | 처리량에 비해 과도하게 많거나 계속 감소하지 않는 경우    |
| 만료된 PROCESSING 수        | Lease가 끝났지만 완료되지 않은 이벤트 수       | 1개 이상 반복적으로 발생하는 경우               |
| attempt_count           | 해당 이벤트가 Publisher에 Claim된 횟수    | 동일 이벤트의 값이 계속 증가하는 경우             |
| Outbox 생성 처리량           | 단위 시간 동안 새로 생성된 Outbox 이벤트 수    | Kafka 발행 처리량보다 계속 높은 경우           |
| Kafka 발행 처리량            | 단위 시간 동안 Kafka 발행에 성공한 이벤트 수    | Outbox 생성 처리량보다 계속 낮거나 급격히 감소한 경우 |
| DB 발생부터 Kafka ACK까지의 시간 | 이벤트 발생부터 Kafka 저장 성공 확인까지 걸린 시간 | 평소보다 지속적으로 증가하거나 허용 시간을 초과하는 경우   |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량: (2,000 - 1,500) × 60 = 30,000건

10분 후 예상 적체 증가량: (2,000 - 1,500) × 600 = 300,000건

가장 먼저 확인할 지표: PENDING 이벤트 수와 가장 오래된 PENDING 대기 시간

가능한 대응: Publisher 인스턴스 또는 처리량을 늘리고, Kafka와 DB 병목을 확인하며 Batch 크기와 Polling 주기를 조정한다.
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. deduplication_key UNIQUE 위반이 발생한 경우

2. Commit된 request = PROCESSING 상태가 관측된 경우

3. 만료된 PROCESSING 이벤트가 반복적으로 발생하는 경우

4. SOLD_OUT 또는 DUPLICATE_USER 확정이 반복적으로 발생하는 경우
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면: 아직 발행되지 않은 이벤트가 유실되어 후속 서비스에 전달되지 않는다.

PROCESSING을 삭제하면: Publisher가 처리 중이거나 Lease 만료 후 복구해야 할 이벤트가 사라진다.

PUBLISHED를 보관하는 목적: 이벤트 발행 이력 확인, 장애 조사, 추적과 감사에 사용한다.
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

다음 항목을 포함한다.

```
긴 트랜잭션

DB 부하

Lock

Table Bloat
```

```
- 대량 삭제는 긴 트랜잭션을 생성하여 DB Connection과 자원을 오래 점유한다.
- 많은 행과 인덱스를 한 번에 변경하여 DB 부하를 증가시킨다.
- 관련 행과 페이지의 Lock 유지 시간이 길어져 다른 쿼리의 처리를 방해할 수 있다.
- 삭제된 공간이 즉시 반환되지 않아 Table Bloat와 인덱스 크기 증가가 발생할 수 있다.
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
보관 기간이 지난 PUBLISHED 행 조회
-> 1,000건 삭제
-> Commit
-> 잠시 대기
-> 삭제 대상이 없어질 때까지 반복
```

### **7. 다음 세 보관 기간의 목적을 비교한다**

| 보관 대상                    | 목적                               | 너무 짧을 때 발생하는 문제                                |
|--------------------------|----------------------------------|------------------------------------------------|
| Outbox PUBLISHED 행       | 발행 이력 확인과 장애 조사                  | 과거 발행 기록을 확인하거나 장애 원인을 추적하기 어려움                |
| Kafka Topic Record       | Consumer가 이벤트를 다시 처리할 수 있는 범위 제공 | Consumer 장애나 Offset 되감기 시 필요한 이벤트가 이미 삭제될 수 있음 |
| Consumer processed_event | 같은 이벤트의 중복 비즈니스 반영 방어            | 과거 이벤트가 재전달되면 최초 이벤트로 판단하여 중복 처리할 수 있음         |

### **8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다**

```
- Stack Trace는 길이가 커서 Outbox 테이블과 인덱스의 크기를 불필요하게 증가시킨다.
- 개인정보, 인증 정보, 요청 데이터 등 민감 정보가 DB에 저장될 수 있다.
- 오류가 반복되면 동일한 대용량 정보가 계속 쌓여 DB 부하가 증가한다.
- `last_error`에는 검색 가능한 짧은 오류 유형과 메시지만 저장하고, 상세 Stack Trace는 Log나 Trace 시스템에 저장해야 한다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

#### 문제 1

```
문제 위치: issueCoupon()의 kafkaTemplate.send()

문제 내용: 쿠폰 발급 DB 트랜잭션 안에서 Kafka를 직접 호출한다.

발생 가능한 장애: DB와 Kafka 중 한쪽만 성공하여 발급 결과와 이벤트 상태가 불일치할 수 있다.

수정 방법: 발급 결과와 CouponIssued Outbox를 같은 DB 트랜잭션에 저장하고 Kafka 발행은 별도 Publisher가 수행한다.
```

#### 문제 2

```
문제 위치: issueCoupon() 전체

문제 내용: coupon_issue 저장과 outbox_event 저장을 같은 트랜잭션으로 처리하지 않는다.

발생 가능한 장애: 쿠폰 발급은 Commit되었지만 재발행할 Outbox 기록이 남지 않을 수 있다.

수정 방법: coupon_issue, request ISSUED, outbox_event INSERT를 하나의 DB 트랜잭션으로 묶는다.
```

#### 문제 3

```
문제 위치: findTop100ByStatus("PENDING")

문제 내용: 여러 Publisher가 같은 PENDING 행을 동시에 조회하는 것을 막지 않는다.

발생 가능한 장애: 여러 Publisher가 동일 이벤트를 동시에 Kafka에 발행할 수 있다.

수정 방법: FOR UPDATE SKIP LOCKED를 사용하여 조회와 PROCESSING 변경을 하나의 Claim 트랜잭션으로 처리한다.
```

#### 문제 4

```
문제 위치: publishOutbox()의 @Transactional

문제 내용: DB 트랜잭션과 Row Lock을 유지한 상태에서 Kafka 발행을 수행한다.

발생 가능한 장애: Kafka 응답 지연 시 DB Connection과 Lock이 장시간 유지되고 트랜잭션 Timeout이 발생할 수 있다.

수정 방법: Claim 트랜잭션을 짧게 Commit한 뒤 DB 트랜잭션 밖에서 Kafka를 호출한다.
```

#### 문제 5

```
문제 위치: kafkaTemplate.send() 직후 event.markPublished()

문제 내용: Kafka Broker ACK를 확인하기 전에 Outbox를 PUBLISHED로 변경한다.

발생 가능한 장애: 실제 Kafka 발행에 실패했는데도 완료된 이벤트로 처리되어 재시도되지 않을 수 있다.

수정 방법: CompletableFuture의 정상 완료로 Broker ACK를 확인한 뒤 PUBLISHED로 변경한다.
```

#### 문제 6

```
문제 위치: publishOutbox() 전체

문제 내용: 이벤트를 처리한 Publisher를 식별하는 Claim Token이 없다.

발생 가능한 장애: Lease가 만료된 뒤 기존 Publisher가 늦게 상태를 변경하여 새로운 Publisher의 처리 결과를 덮어쓸 수 있다.

수정 방법: Claim 시 claim_token을 저장하고 성공과 실패 UPDATE 조건에 event_id, status, claim_token을 포함한다.
```

#### 문제 7

```
문제 위치: recoverProcessing()의 updateAllProcessingToPending()

문제 내용: Lease 만료 여부를 확인하지 않고 모든 PROCESSING 이벤트를 PENDING으로 변경한다.

발생 가능한 장애: 정상적으로 발행 중인 이벤트까지 회수하여 동시에 중복 발행할 수 있다.

수정 방법: status = 'PROCESSING'이고 lease_until <= CURRENT_TIMESTAMP인 행만 복구한다.
```

#### 문제 8

```
문제 위치: createPayloadFromCurrentCouponIssue(event)

문제 내용: Outbox 저장 시점의 Payload가 아니라 현재 비즈니스 테이블을 다시 조회하여 Payload를 생성한다.

발생 가능한 장애: 이벤트 발생 이후 데이터가 변경되면 실제 발생 당시와 다른 내용이 발행될 수 있다.

수정 방법: Outbox INSERT 시 완성된 Payload를 저장하고 Publisher는 저장된 Payload를 그대로 발행한다.
```

#### 문제 9

```
문제 위치: onResult()의 ProcessedEvent 생성

문제 내용: Kafka Partition과 Offset을 Consumer 멱등성 Key로 사용한다.

발생 가능한 장애: 같은 논리 이벤트가 다른 Offset으로 재발행되면 새로운 이벤트로 판단하여 중복 처리할 수 있다.

수정 방법: eventMessageId를 Consumer 멱등성 Key로 사용한다.
```

#### 문제 10

```
문제 위치: onResult()의 userCouponViewRepository.save()와 processedEventRepository.save()

문제 내용: 비즈니스 테이블을 먼저 변경한 뒤 processed_event를 저장한다.

발생 가능한 장애: 조회 모델 저장 후 processed_event 저장 전에 장애가 발생하면 재전달 시 조회 모델이 중복 반영될 수 있다.

수정 방법: processed_event INSERT와 조회 모델 변경을 하나의 DB 트랜잭션으로 묶고, 최초 이벤트인 경우에만 조회 모델을 변경한다.
```

#### 문제 11

```
문제 위치: findTop100ByStatus("PENDING")

문제 내용: next_attempt_at 조건 없이 모든 PENDING 이벤트를 조회한다.

발생 가능한 장애: Backoff 대기 중인 이벤트까지 즉시 재시도되어 불필요한 부하가 발생한다.

수정 방법: next_attempt_at <= CURRENT_TIMESTAMP 조건을 추가한다.
```

#### 문제 12

```
문제 위치: publishOutbox() 전체

문제 내용: 발행 실패 시 PENDING 복구와 Backoff 처리 로직이 없다.

발생 가능한 장애: 실패한 이벤트가 재시도되지 않거나 반복 실패할 수 있다.

수정 방법: 실패 시 next_attempt_at, last_error를 저장하고 PENDING으로 변경한다.
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목                                 | 수준      | 이유                                                                       |
|------------------------------------|---------|--------------------------------------------------------------------------|
| DB 발급 결과와 Outbox 기록의 원자성           | 보장      | 같은 PostgreSQL 트랜잭션에서 함께 Commit하거나 Rollback한다.                            |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | ACK 확인 후 상태 변경 전 장애가 발생하면 같은 이벤트가 재발행될 수 있다.                             |
| Publisher 복구 후 재발행                 | 조건부 보장  | Outbox 행과 Lease 복구 정책이 유지되고 Publisher가 정상 동작해야 한다.                       |
| 비즈니스 발생 순서대로 전달                    | 보장하지 않음 | 여러 Publisher, SKIP LOCKED, Backoff로 발행 순서가 역전될 수 있다.                     |
| Consumer의 중복 비즈니스 반영 방지            | 조건부 보장  | Consumer가 eventMessageId 기반 processed_event를 비즈니스 변경과 같은 트랜잭션으로 처리해야 한다. |
| 모든 Consumer Group의 처리 완료           | 보장하지 않음 | 각 Consumer Group은 독립적으로 이벤트를 처리하고 Offset을 관리한다.                          |
| 외부 SMS의 정확히 한 번 전송                 | 보장하지 않음 | Consumer DB와 외부 SMS API를 하나의 로컬 트랜잭션으로 묶을 수 없다.                          |
