# 6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
PostgreSQL (issued_count 증가, coupon_issue 저장, request ISSUED 변경)
Kafka Broker (coupon.issued 이벤트 발행)
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
@Transactional은 PostgreSQL의 로컬 DB 트랜잭션 경계만 관리한다
Kafka Broker는 이 DB 트랜잭션에 참여하지 않는 별도의 시스템이다

DB 트랜잭션이 Rollback되어도 이미 Broker에 저장된 Record는 되돌아가지 않고
Kafka 발행이 실패해도 DB 변경이 자동으로 취소되지 않는다

두 저장소를 하나로 묶으려면 XA/2PC 같은 분산 트랜잭션이 필요한데
Kafka와 일반 DB 트랜잭션은 그렇게 묶이지 않으므로
한쪽만 성공하는 장애 구간이 항상 존재한다
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

```
DB Commit
    ↓
[장애 지점] DB Commit 성공 후 Kafka 발행 전 프로세스 종료
    ↓
Kafka 발행

최종 DB 상태:
쿠폰 발급 완료 (issued_count 증가, coupon_issue 존재, request ISSUED)

최종 Kafka 상태:
CouponIssued 이벤트 없음

후속 서비스에 미치는 영향:
Notification/MyPage/Analytics가 발급 사실을 알 수 없어 알림·조회·통계 누락

복구에 필요한 정보:
무엇을 발행해야 하는지에 대한 발행 의도가 필요하다
메모리에만 있었다면 재시작 후 복구 기준이 사라진다
쿠폰은 이미 발급되었으므로 재발급은 금지, 누락 이벤트만 재발행해야 한다
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점] Kafka 발행 성공 후 DB 트랜잭션 실패
    ↓
DB Commit

최종 DB 상태:
발급 기록 없음 (issued_count 미증가, coupon_issue 없음)

최종 Kafka 상태:
CouponIssued 이벤트 존재

후속 서비스에 미치는 영향:
실제로 발급되지 않은 쿠폰에 대해 알림·조회 모델·통계를 반영하게 되어
존재하지 않는 발급 결과가 후속 서비스에 전파된다
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

```
AFTER_COMMIT은 DB Commit 전에 이벤트가 발행되는 문제는 막지만
발행 대상이 여전히 메모리에만 존재하므로 다음 장애를 막지 못한다

DB Commit 후 Listener 실행 전 프로세스 종료
→ DB 결과는 확정되었지만 Listener가 실행되지 않아 이벤트가 영구 유실된다
→ 재시작해도 무엇을 발행해야 하는지 알 수 없다

KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료
→ send()는 비동기라 호출 성공이 Broker 저장 완료를 의미하지 않는다
→ ACK 확인 전에 종료되면 이벤트가 저장되지 않았을 수 있는데
   DB는 이미 Commit되어 되돌릴 수 없다

핵심은 발행 대상이 메모리에만 있어 프로세스 종료 시 복구 기준이 사라진다는 것이다
Outbox는 이를 DB에 저장해 해결한다
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | 해결됨 | 같은 PostgreSQL 트랜잭션에 함께 저장되어 원자적으로 Commit/Rollback됨 |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | 해결 안 됨 | Redis는 DB 트랜잭션에 참여하지 않는 외부 저장소로 함께 묶을 수 없음 |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | 해결 안 됨 | Kafka 소비와 DB Commit은 원자화되지 않으며 requestId 멱등성으로 방어함 |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | 해결 안 됨 | 외부 API는 로컬 DB 트랜잭션에 포함되지 않는 별도 Dual Write임 |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것:
DB 발급 결과가 Commit되면 발행할 이벤트 기록도 반드시 같은 DB에 남는다

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record가 물리적으로 정확히 한 번만 생성되는 것,
이벤트가 비즈니스 발생 순서대로 전달되는 것,
모든 Consumer의 처리 완료, 외부 알림의 정확히 한 번 전송
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

```
IssueCoupon은 쿠폰을 발급하라는 명령이고
CouponIssued는 쿠폰이 이미 발급되었다는 과거의 사실이다

CouponIssued는 DB 트랜잭션에서 발급이 확정된 뒤 발행되는 결과 이벤트다
Consumer는 이 이벤트를 받아 쿠폰을 다시 발급하는 것이 아니라
이미 일어난 사실에 대한 후속 처리(알림, 조회 모델 갱신, 통계)만 수행한다

이름을 사실로 두어야 Consumer가 이벤트를 명령으로 오해해
발급 로직을 다시 실행하는 것을 막을 수 있다
```

### **2. CouponIssued 이벤트 JSON을 완성한다**

```json
{
  "eventMessageId": "8a78e94b-5c3d-46a7-a364-538cd1f856c9",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### **3. 다음 ID의 역할을 비교한다**

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 행사 자체 | 바뀌지 않음 | 부적절 (여러 발급이 공유해 이벤트 단위 식별 불가) |
| couponIssueId | 하나의 발급 기록 | 바뀌지 않음 | 부적절 (같은 발급의 여러 이벤트를 구분 못 함) |
| eventMessageId | 결과 이벤트 메시지 자체 | 바뀌지 않음 (Payload에 고정 저장) | 적절 (이벤트 단위 중복 반영 방어의 기준) |
| Kafka Partition + Offset | Kafka 내 물리적 위치 | 바뀜 (재발행 시 다른 Offset) | 부적절 (같은 이벤트가 다른 Offset을 가짐) |

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt:
쿠폰 발급이라는 비즈니스 결과가 발생한 시각 (발급 성공 이벤트에서는 issuedAt과 동일 기준)

publishedAt:
Publisher가 Kafka ACK를 확인한 뒤 DB에 기록하는 발행 완료 시각

Publisher 재시도 시 변경하면 안 되는 값:
occurredAt과 Payload (불변 Snapshot으로 유지하며 재시도로 바뀌지 않는다)
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
Outbox INSERT 시점과 Publisher 발행 시점 사이에 원본 데이터가 변경될 수 있다
예를 들어 발급 후 취소나 상태 변경이 일어나면
발행 시점에 다시 조회한 값은 발생 당시의 사실과 달라진다

Outbox 행은 특정 시점에 발생한 사실의 불변 Snapshot이어야 하므로
Payload는 Outbox INSERT 시점에 확정해 저장하고
Publisher는 저장된 Payload를 그대로 전달해야 한다
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    request_id UUID,

    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),

    CONSTRAINT chk_outbox_schema_version
        CHECK (schema_version >= 1),

    CONSTRAINT chk_outbox_aggregate_version
        CHECK (aggregate_version >= 1),

    CONSTRAINT chk_outbox_attempt_count
        CHECK (attempt_count >= 0),

    CONSTRAINT chk_outbox_state_fields
        CHECK (
            (status = 'PENDING'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NULL)
            OR
            (status = 'PROCESSING'
                AND claim_token IS NOT NULL
                AND lease_until IS NOT NULL
                AND published_at IS NULL)
            OR
            (status = 'PUBLISHED'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NOT NULL)
        )
);

CREATE INDEX idx_outbox_pending
ON outbox_event (next_attempt_at, created_at, event_id)
WHERE status = 'PENDING';

CREATE INDEX idx_outbox_expired_processing
ON outbox_event (lease_until, event_id)
WHERE status = 'PROCESSING';
```

### **7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다**

```
outbox_event.event_id = payload.eventMessageId

Outbox INSERT 시점에 event_id와 Payload의 eventMessageId를 같은 값으로 생성해 저장한다
애플리케이션에서 이벤트 객체를 만들 때 하나의 UUID를 생성해
event_id 컬럼과 payload의 eventMessageId에 동일하게 채운다

추가로 저장 직후 또는 발행 직전에 두 값이 일치하는지 검증하는 방어 로직을 두거나
DB Trigger로 payload->>'eventMessageId'와 event_id가 같은지 CHECK할 수 있다
불일치가 발견되면 이벤트 식별 기준이 어긋난 것이므로 알람 대상으로 둔다
```

### **8. `deduplication_key`를 설계한다**

```
Key 형식:
{eventType}:{aggregateType}:{aggregateId}

예시:
COUPON_ISSUED:COUPON_ISSUE:5001
```

```
같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면
발생 시점이나 시퀀스 같은 추가 구분자가 필요하다
예를 들어 CouponUsed는 같은 couponIssueId에서 반복될 수 있으므로
{eventType}:{aggregateType}:{aggregateId}:{aggregateVersion} 또는 occurredAt 시퀀스를 덧붙인다
CouponIssued는 하나의 couponIssueId에 대해 한 번만 발생하므로 기본 규칙으로 충분하다
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

```
전체 Rollback 후 새 트랜잭션에서 조회:
PostgreSQL은 제약 위반이 발생한 트랜잭션을 계속 사용할 수 없으므로
발급 트랜잭션 전체를 Rollback하고 새 트랜잭션에서 기존 행을 조회해야 한다
이번 설계의 기본 정책이며, 위반은 이상 상황이므로 Rollback 후 알람을 발생시킨다

Savepoint 사용:
INSERT 직전에 Savepoint를 설정하면 위반 시 Savepoint로만 되돌리고
발급 트랜잭션을 살려 이어갈 수 있다. 다만 이상 상황을 트랜잭션 내부에서
조용히 흡수하게 되므로 이번 설계에서는 기본으로 쓰지 않는다

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교:
멱등 INSERT로 만들고 싶을 때 쓴다. 충돌 시 기존 행을 조회해
request_id, aggregate_type/id, event_type, schema_version, aggregate_version, payload가
모두 같은지 확인하고, 동일한 이벤트일 때만 기존 행을 재사용한다
확인 없이 DO NOTHING만 쓰면 서로 다른 충돌을 숨기므로 위험하다

이번 설계에서는 위반을 설계 가정 위반으로 보고 전체 Rollback + 알람을 기본으로 한다
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득 (affected rows = 1이어야 함)
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';

-- 2. 수량이 남아 있을 때만 issued_count 증가
--    affected rows = 0이면 수량 소진 또는 이벤트 미존재(조건에 상태·기간 포함 시 종료·비활성 포함)
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id, user_id, status, issued_at
) VALUES (
    :couponEventId, :userId, 'ISSUED', CURRENT_TIMESTAMP
)
RETURNING id, issued_at;

-- 4. request를 ISSUED로 변경 (affected rows = 1이어야 함)
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장 (ON CONFLICT 사용 안 함)
INSERT INTO outbox_event (
    event_id, request_id, deduplication_key,
    aggregate_type, aggregate_id,
    event_type, schema_version, aggregate_version,
    topic, partition_key, payload, occurred_at
) VALUES (
    :eventMessageId, :requestId, :deduplicationKey,
    'COUPON_ISSUE', CAST(:couponIssueId AS VARCHAR),
    'COUPON_ISSUED', 1, 1,
    'coupon.issued', CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB), :issuedAt
);

COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1행 | 0행이면 기존 상태 확인(ISSUED/FAILED 멱등 종료, PROCESSING 이상 신호, 행 없음 등) |
| issued_count 조건부 증가 | 1행 | 0행이면 SOLD_OUT 확정, request FAILED 변경 후 Commit (성공 이벤트 없음) |
| coupon_issue INSERT | 1행 | UNIQUE 위반이면 전체 Rollback 후 별도 트랜잭션에서 DUPLICATE_USER 확정 |
| PROCESSING → ISSUED | 1행 | 0행이면 상태 불일치이므로 전체 트랜잭션 Rollback |
| outbox_event INSERT | 1행 | 실패 시 전체 트랜잭션 Rollback (발급 결과만 Commit 금지) |

### **3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다**

```
트랜잭션 결과:
전체 Rollback

coupon_event.issued_count:
증가 취소 (원래 값)

coupon_issue:
저장 취소 (발급 행 없음)

coupon_issue_request:
ISSUED 변경 취소 (PENDING으로 되돌아감)

outbox_event:
없음
```

### **4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다**

```
발급 결과만 Commit하면 쿠폰은 발급되었는데 발행할 이벤트 기록이 DB에 없는 상태가 된다
이는 Outbox 패턴이 막으려는 바로 그 상태(발급 확정 + 발행 의도 유실)다

이렇게 되면 후속 서비스가 발급 사실을 영영 알 수 없고
재시작 후에도 무엇을 발행해야 하는지 복구 기준이 사라진다
따라서 Outbox INSERT 실패는 전체 Rollback해 원본 메시지 재처리로 다시 시도해야 한다
```

### **5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다**

```
issued_count를 다시 증가시키는가?
아니다 (첫 UPDATE가 0행이 되어 발급 로직에 도달하지 않음)

coupon_issue를 다시 생성하는가?
아니다

Outbox를 다시 INSERT하는가?
아니다

Consumer 처리는 성공으로 종료할 수 있는가?
그렇다. 이미 완료된 요청의 재전달이므로 새 변경 없이 정상 처리로 종료하고
원본 Kafka Offset을 커밋한다
```

### **6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다**

```
DB 상태:
request ISSUED, coupon_issue 존재, issued_count 반영, outbox_event PENDING 존재

Outbox 상태:
PENDING (Publisher가 아직 발행 전일 수 있음)

Kafka 원본 메시지:
Offset 미반영으로 원본 메시지가 재전달됨

재시작 후 필요한 멱등성 기준:
requestId 기반 멱등성 (재전달 시 request=ISSUED 확인 후 새 발급·새 Outbox 없이 종료)
```

### **7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다**

```
enable.auto.commit:
false로 두어 DB 결과 확정과 무관한 시점에 자동 커밋되지 않게 한다

AckMode:
DB 트랜잭션 Commit 후 수동 Ack로 Offset을 반영하는 모드로 구성한다 (MANUAL/MANUAL_IMMEDIATE 등)

Listener 예외 처리:
DB Rollback 시 예외를 던져 Offset이 커밋되지 않고 재전달되도록 한다

Error Handler가 실패를 정상 처리로 바꾸는지 여부:
Error Handler가 예외를 삼켜 정상 처리로 간주하면 실패한 메시지의 Offset이 커밋되어
유실이 발생할 수 있으므로, 재처리가 필요한 실패는 커밋되지 않도록 구성한다
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                          Publisher B
------------------------------------------------------------
PENDING 행 조회 (evt-001)
                                     PENDING 행 조회 (evt-001)
evt-001 처리 대상으로 판단
                                     evt-001 처리 대상으로 판단
evt-001 PROCESSING UPDATE
                                     evt-001 PROCESSING UPDATE
Kafka 발행 (evt-001)
                                     Kafka 발행 (evt-001)   <- 동일 이벤트 중복 발행
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY next_attempt_at, created_at, event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

```
1. DB Connection을 Kafka ACK를 기다리는 동안 장시간 점유해 커넥션 풀이 고갈된다

2. Claim한 행의 Row Lock을 오래 유지해 다른 Publisher와 정리 작업이 대기한다

3. Kafka 발행이 느리면 DB 트랜잭션이 길어져 트랜잭션 Timeout이나 처리량 저하가 발생한다
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
인스턴스가 하나여도 Claim Commit(PROCESSING 변경) 직후 Kafka 발행 전에
프로세스가 종료될 수 있다

이 경우 해당 행은 PROCESSING으로 남고 복구 장치가 없으면 영원히 발행되지 않는다
Lease 만료 회수나 시작 시 stale PROCESSING을 PENDING으로 되돌리는 복구가 있어야
재시작 후 다시 Claim되어 발행된다
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Claim Token이 없으면 Publisher A가 뒤늦게 상태 UPDATE를 수행할 때
현재 처리 권한을 가진 Publisher B의 상태를 덮어쓸 수 있다

예를 들어 B가 이미 PUBLISHED로 완료했는데
A가 늦게 실패 처리로 PENDING으로 되돌리면 이미 발행된 이벤트가 다시 발행된다
반대로 A가 늦게 PUBLISHED로 덮으면 B의 재시도 상태가 사라질 수 있다

claim_token으로 자신이 획득한 권한일 때만 상태를 변경하게 해야
오래된 처리자가 최신 처리자의 상태를 덮어쓰는 것을 막는다
```

### **7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### **8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다**

```
Lease 시간
>
batchSize × 건당 최대 대기 시간 (send().get()의 timeout)
+
여유 시간 (GC, 스케줄 지연 등 예기치 못한 지연분)
```

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료:
전송 요청을 큐에 넣고 Future를 반환했을 뿐 Broker 저장은 확인되지 않았다

CompletableFuture 정상 완료:
Broker ACK를 받아 Kafka에 Record가 저장되었음이 확인되었다

outbox = PUBLISHED:
ACK 확인 후 완료 상태까지 DB에 반영되어 재발행 대상에서 빠졌다

모든 후속 Consumer 처리 완료:
각 Consumer Group이 독립적으로 처리를 마친 상태로, PUBLISHED와 별개다
```

### **2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,
    lease_until = NULL,
    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### **3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    next_attempt_at = :nextAttemptAt,
    claim_token = NULL,
    lease_until = NULL,
    last_error = :lastError,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

```
상황 A는 Broker에 저장되지 못하고 Timeout이 난 경우이고
상황 B는 Broker에는 저장되었지만 Publisher가 ACK만 확인하지 못하고 Timeout이 난 경우다

Publisher는 둘 다 응답을 받지 못한 Timeout으로만 관측하므로 두 상황을 구분할 수 없다
따라서 Timeout을 저장 실패로 단정하면 안 되고, PUBLISHED로 바꾸지 않고 재시도한다
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태:
PUBLISHED로 바꾸지 않고 PENDING으로 되돌려 미완료로 유지

재시도 여부:
재시도한다 (next_attempt_at 이후 다시 Claim)

Kafka 중복 가능성:
상황 B였다면 재발행으로 동일 이벤트 Record가 두 개 생길 수 있다

Consumer에게 필요한 방어:
eventMessageId 기반 멱등 처리로 중복 반영을 막는다
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff:
실패가 반복될수록 재시도 간격을 지수적으로 늘려 (1초, 2초, 4초, 8초)
장애 중인 Kafka나 DB에 재시도가 몰려 부하가 가중되는 것을 막는다

Jitter:
동일 간격이면 여러 인스턴스가 같은 시각에 동시에 재시도해 부하가 몰린다
작은 무작위 지연을 더해 재시도 시점을 분산시킨다
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | 같은 Producer ID·Sequence로 Broker가 중복 저장을 걸러냄 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능 | 새 Publisher가 애플리케이션 수준에서 다시 발행하는 별개 send임 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능 | 새로운 발행 요청으로 서로 다른 send이며 Sequence도 달라짐 |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

```
whenComplete는 Future를 완료시킨 스레드에서 콜백을 실행하는데
그 스레드는 Kafka Producer의 내부 Sender 스레드다

Sender 스레드에서 DB 작업을 하면 Connection Pool 대기와 Commit 대기로 스레드가 블로킹되고
해당 Producer의 모든 전송이 함께 지연된다
부하 상황에서는 발행 지연 → Lease 만료 → 다른 Publisher 회수 → 중복 발행 → 적체 심화로 이어진다

따라서 whenCompleteAsync에 전용 Executor를 지정해
DB 작업이나 블로킹 I/O를 Producer 콜백 스레드에서 수행하지 않아야 한다
```

## **과제 7. Consumer 멱등 처리 설계하기**

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
같은 논리 이벤트가 재발행되면 서로 다른 Partition/Offset을 갖는다
(Offset 100과 101이 같은 eventMessageId evt-001을 가리킬 수 있다)

Offset을 Key로 삼으면 이 둘을 다른 이벤트로 인식해 중복 반영을 막지 못한다
따라서 재발행에도 값이 바뀌지 않는 eventMessageId를 멱등성 기준으로 써야 한다
```

### **2. processed_event 테이블 DDL을 작성한다**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_id)
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

```
선택: mypage-coupon-projection

pod-7f8c9d나 server-10.0.0.12 같은 값은 배포·재시작·스케일링에 따라 바뀐다
인스턴스 ID를 쓰면 같은 논리 구독자가 재배포된 뒤 다른 subscriber_id로 인식되어
이미 처리한 이벤트를 다시 처리하게 되어 중복 방어가 무너진다

mypage-coupon-projection처럼 안정적인 논리 구독자 이름을 써야
인스턴스가 바뀌어도 같은 구독자로서 중복 처리를 막을 수 있다
```

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다**

### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**

```
processed_event는 Consumer 자신의 로컬 DB 저장과 비즈니스 변경만 원자적으로 묶는다
외부 SMS API 호출은 로컬 DB 트랜잭션에 포함되지 않는 별도 Dual Write다

예를 들어 SMS 전송 후 processed_event Commit 전에 종료되면
재전달 시 이미 보낸 SMS를 다시 보낼 수 있고
processed_event Commit 후 SMS 전송 전에 종료되면 SMS가 누락될 수 있다
따라서 processed_event만으로 외부 전송의 정확히 한 번을 보장할 수 없다
```

```
2. 외부 알림 Provider의 Idempotency Key를 사용해 같은 키의 중복 전송을 Provider가 걸러내게 함

3. notificationId 기반 중복 전송 방어 테이블을 두어 이미 보낸 알림을 재전송하지 않음
```

### **8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다**

```
Kafka Topic 보관 기간: Record가 남아 있는 동안 재소비될 수 있음
Consumer Offset 되감기: 운영자가 Offset을 되돌리면 과거 이벤트가 재전달됨

운영자 수동 재발행: 수동 재처리로 같은 이벤트가 다시 유입됨

processed_event 보관 기간 > Kafka Topic 보관 기간 + 최대 재전달 지연
이보다 짧게 잡으면 기록이 지워진 이벤트가 재등장했을 때 중복 반영을 막지 못한다
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
같은 Aggregate(couponIssueId)의 이벤트를 한 Partition에 모아 Consumer 병렬 처리 단위를 명확히 한다
특정 Partition으로 부하가 몰리지 않도록 분산한다
향후 순서 보장을 도입할 때의 기준 단위를 미리 정한다
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

```
Partition 안의 순서는 Producer가 send()를 호출한 순서로 결정되며 DB 저장 순서가 아니다

여러 Publisher 인스턴스: 서로 다른 속도로 발행해 순서가 섞인다
SKIP LOCKED: 잠긴 행을 건너뛰고 다음 행을 가져와 애초에 순서를 포기한다
발행 실패와 Backoff: 먼저 저장된 이벤트가 실패하면 next_attempt_at 이후로 밀린다
Producer 설정과 재시도: 재시도 과정에서 전송 순서가 뒤바뀔 수 있다

따라서 같은 Key라도 비즈니스 발생 순서대로 저장된다고 보장할 수 없다
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서
CouponIssued    aggregateVersion = 1  (couponIssueId = 5001)
CouponCancelled aggregateVersion = 2  (couponIssueId = 5001)

Publisher 처리
Publisher A: outbox 1(CouponIssued) Claim → Kafka 발행 실패 → PENDING, next_attempt_at 뒤로 밀림
Publisher B: outbox 2(CouponCancelled) Claim → 발행 성공

Kafka 저장 순서:
Offset 200 : CouponCancelled
Offset 201 : CouponIssued
```

### **4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다**

```
1. 서로 다른 이벤트가 같은 Timestamp를 가질 수 있다

2. 서버·DB의 시계나 시간 정밀도가 달라 발생 순서와 Timestamp 순서가 어긋날 수 있다

3. 조회 행이 없는 경우와 오래된 이벤트인 경우를 UPDATE 0행만으로 구분하기 어렵다
```

### **5. MyPage처럼 최신 상태만 필요한 Projection의 순서 역전 방어 SQL을 작성한다**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id, user_id, coupon_event_id,
    status, last_aggregate_version, last_event_at
) VALUES (
    :couponIssueId, :userId, :couponEventId,
    :newStatus, :aggregateVersion, :occurredAt
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    last_aggregate_version = EXCLUDED.last_aggregate_version,
    last_event_at = EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version
      < EXCLUDED.last_aggregate_version;
```

### **6. aggregateVersion이 더 큰 이벤트가 먼저 도착한 경우의 결과를 작성한다**

```
먼저 도착: CouponCancelled(version=2) → 조회 행을 취소 상태(version=2)로 생성

나중 도착: CouponIssued(version=1)

최종 MyPage 상태:
취소 상태 유지 (version=1은 저장된 version=2보다 낮아 반영되지 않음)

version=1 처리 결과:
WHERE 조건(저장 버전 < 들어온 버전)을 만족하지 못해 0행, 상태 변경 생략
```

### **7. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버려도 되는지 판단한다**

| Consumer | 낮은 Version 이벤트 생략 가능 여부 | 이유 또는 추가로 필요한 설계 |
| --- | --- | --- |
| 최신 상태만 저장하는 MyPage Projection | 가능 | 최신 상태만 필요하므로 낮은 버전은 상태를 되돌리지 않게 생략하면 됨 |
| 모든 발급·취소 건수를 집계하는 Analytics | 불가능 | 모든 상태 전이를 세야 하므로 낮은 버전도 처리 필요, eventMessageId 멱등성으로 중복만 방어 |
| 발급과 취소 알림을 각각 보내는 Notification | 불가능 | 발급/취소 알림을 각각 보내야 하므로 낮은 버전 이벤트도 생략 불가, 멱등 전송 방어 필요 |

### **8. `aggregateVersion`의 역할을 정확히 정의한다**

```
aggregateVersion은 이벤트 순서 역전을
자동으로 __재정렬해 주는__ 값이 아니다.

aggregateVersion은 같은 Aggregate에서 발생한 상태 변경의
__순서(몇 번째 변경인지)__ 을 식별하기 위한 값이다.

최신 상태 Projection에서는 낮은 버전이
최신 상태를 __덮어쓰는(되돌리는)__ 것을 방지할 수 있다.

모든 상태 전이를 순서대로 처리해야 하는 Consumer는
추가로 __버퍼링·재정렬 또는 Aggregate 단위 순서 보장 같은 별도 설계__ 이 필요하다.
```

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않은 이벤트 수 | 계속 증가하며 줄지 않을 때 |
| 가장 오래된 PENDING 대기 시간 | 발행되지 못한 채 남은 최장 시간 | 임계치를 넘어 오래 남아 있을 때 |
| PROCESSING 이벤트 수 | 현재 Claim되어 처리 중인 이벤트 수 | 비정상적으로 크거나 줄지 않을 때 |
| 만료된 PROCESSING 수 | Lease가 만료되도록 완료되지 못한 행 수 | 반복적으로 발생할 때 |
| attempt_count | 특정 이벤트의 발행 권한 획득 횟수 | 같은 이벤트가 계속 증가할 때 |
| Outbox 생성 처리량 | 단위 시간당 Outbox INSERT 수 | 발행 처리량보다 지속적으로 클 때 |
| Kafka 발행 처리량 | 단위 시간당 PUBLISHED 수 | 생성 처리량보다 계속 느릴 때 |
| DB 발생부터 Kafka ACK까지의 시간 | 이벤트 발생~발행 지연 | 지연이 지속적으로 커질 때 |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량:
(2000 - 1500) × 60 = 30,000건

10분 후 예상 적체 증가량:
(2000 - 1500) × 600 = 300,000건

가장 먼저 확인할 지표:
PENDING 이벤트 수와 가장 오래된 PENDING 대기 시간

가능한 대응:
Publisher 인스턴스 증설, batchSize 조정, 비동기 발행으로 확장,
Kafka Producer 처리량 튜닝 등으로 발행 속도를 생성 속도 이상으로 끌어올린다
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. deduplication_key UNIQUE 위반 발생

2. Commit된 request = PROCESSING 상태 관측

3. outbox_event.event_id와 payload.eventMessageId 불일치

4. SOLD_OUT 또는 DUPLICATE_USER 확정이 반복적으로 발생 (Redis-DB 비수렴 신호)
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면:
아직 발행되지 않은 이벤트가 사라져 후속 서비스에 영구 유실된다

PROCESSING을 삭제하면:
발행 중이거나 회수 대기 중인 이벤트가 사라져 발행 여부가 불확실한 채로 유실된다

PUBLISHED를 보관하는 목적:
발행 이력 확인과 장애 조사를 위해 일정 기간 유지한다
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

```
긴 트랜잭션: 대량 DELETE가 하나의 긴 트랜잭션이 되어 오래 락과 리소스를 점유한다
DB 부하: 대량 삭제가 I/O와 WAL 부하를 유발해 다른 쿼리에 영향을 준다
Lock: 삭제 대상 행과 인덱스에 락이 걸려 동시 작업이 대기한다
Table Bloat: 한 번에 대량 삭제 시 dead tuple이 급증해 테이블·인덱스 Bloat와 VACUUM 부담이 커진다
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
published_at < :cutoff 이고 status = 'PUBLISHED'인 행을
1,000건 단위로 DELETE
→ Commit
→ 잠시 대기
→ 삭제 대상이 없을 때까지 반복
```

### **7. 다음 세 보관 기간의 목적을 비교한다**

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |


### **4. 수정된 구조의 발행 보장 수준을 작성한다**

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 로컬 DB 트랜잭션으로 함께 Commit/Rollback됨 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | 재시도·재발행으로 동일 이벤트가 중복 생성될 수 있음 |
| Publisher 복구 후 재발행 | 조건부 보장 | Publisher 동작·Kafka 회복·재시도·행 미삭제 등 조건이 충족될 때 재발행됨 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED·Backoff·다중 Publisher로 순서가 역전될 수 있음 |
| Consumer의 중복 비즈니스 반영 방지 | 보장 | eventMessageId 기반 processed_event로 중복 반영을 막음 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | 각 Consumer Group이 Offset과 처리를 독립적으로 관리함 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API는 로컬 트랜잭션 밖의 별도 Dual Write이므로 추가 방어 필요 |
