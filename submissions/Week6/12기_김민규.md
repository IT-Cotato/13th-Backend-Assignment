# **6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성**

이번 과제의 핵심은 쿠폰 발급 결과와 이벤트 발행 의도를 같은 DB 트랜잭션으로 저장하는 것이다.

Outbox는 Kafka에 이벤트가 정확히 한 번만 발행되는 것을 보장하지 않는다.
발행할 이벤트가 유실되지 않게 저장하고 실패한 이벤트를 다시 발행할 수 있게 해준다.
따라서 중복 발행을 허용하고 Consumer에서 멱등하게 처리해야 한다.

---

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

### **1. 위 코드가 사용하는 저장소 두 개**

```
1. 쿠폰 발급 결과를 저장하는 PostgreSQL
2. CouponIssued 이벤트를 저장하는 Kafka
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유**

```
@Transactional은 기본적으로 PostgreSQL의 로컬 트랜잭션만 관리한다.
Kafka는 PostgreSQL과 다른 시스템이므로 DB가 Rollback되어도 Kafka Record는 같이 Rollback되지 않는다.
반대로 Kafka 발행이 실패해도 이미 Commit된 DB 트랜잭션을 되돌릴 수 없다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름**

```
DB Commit
    ↓
[애플리케이션 종료 또는 Kafka 발행 실패]
    ↓
Kafka 발행

최종 DB 상태: 쿠폰 발급 완료

최종 Kafka 상태: CouponIssued가 존재하지 않을 수 있음

후속 서비스에 미치는 영향: 실제 발급은 되었지만 알림, 마이페이지, 통계에 반영되지 않음

복구에 필요한 정보: 어떤 발급 결과의 이벤트가 발행되지 않았는지 확인할 수 있는 영속적인 기록
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름**

```
Kafka 발행
    ↓
[DB 저장 실패 또는 애플리케이션 종료]
    ↓
DB Commit

최종 DB 상태: 쿠폰이 발급되지 않음

최종 Kafka 상태: CouponIssued가 존재함

후속 서비스에 미치는 영향: 실제로 없는 쿠폰을 발급된 것으로 처리함
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유**

```
DB Commit 후 Listener가 실행되기 전에 프로세스가 종료되면 발행할 이벤트 기록이 남지 않는다.

KafkaTemplate.send() 호출은 전송 요청을 넣은 것이지 Broker 저장이 완료된 것이 아니다.
호출 후 Broker ACK를 확인하기 전에 프로세스가 종료되면 성공 여부를 알 수 없다.

AFTER_COMMIT Listener에는 재시도할 대상을 영속적으로 보관하는 기능이 없으므로 이벤트 유실을 막을 수 없다.
```

### **6. Outbox가 해결하는 범위와 해결하지 않는 범위**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | 해결됨 | 두 데이터를 같은 PostgreSQL 트랜잭션으로 저장할 수 있다. |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | 해결되지 않음 | Redis와 Kafka 사이의 별도 Dual Write 문제이다. |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | 직접 해결되지 않음 | DB Commit 후 Offset Commit과 requestId 멱등 처리로 대응해야 한다. |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | 해결되지 않음 | Consumer DB와 외부 API 사이에 다시 Dual Write가 발생한다. |

### **7. 정리**

```
Transactional Outbox가 직접 보장하는 것:
DB 발급 결과가 Commit되면 발행할 이벤트 기록도 반드시 DB에 남는 것

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record의 정확히 한 번 발행, 모든 Consumer의 처리 완료, 외부 API의 정확히 한 번 호출
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 이미 발생한 사실을 나타내야 하는 이유**

```
IssueCoupon은 쿠폰을 발급하라는 명령이므로 아직 성공하지 않았을 수 있다.
CouponIssued는 DB 트랜잭션이 Commit되어 쿠폰이 발급되었다는 사실이다.

결과 Consumer는 다시 발급을 수행하는 것이 아니라 이미 발생한 결과를 알림이나 조회 모델에 반영한다.
따라서 결과 이벤트는 과거형인 CouponIssued가 적절하다.
```

### **2. CouponIssued 이벤트 JSON**

```json
{
  "eventMessageId": "8d17fa42-a88e-4d0d-a809-d28f480ec401",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "61d41287-70bd-44f0-b899-84c585ff3271",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### **3. ID 역할 비교**

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 이벤트 | 바뀌지 않음 | 부적절함. 한 이벤트에서 여러 쿠폰이 발급된다. |
| couponIssueId | 하나의 쿠폰 발급 결과 | 바뀌지 않음 | 특정 업무에서는 가능하지만 이벤트 자체의 식별자는 아니다. |
| eventMessageId | 하나의 논리 이벤트 | 바뀌지 않음 | 적절함 |
| Kafka Partition + Offset | Kafka에 저장된 물리 Record | 재발행하면 바뀜 | 부적절함 |

### **4. `occurredAt`과 `publishedAt`의 차이**

```
occurredAt: 쿠폰 발급이라는 비즈니스 사실이 발생한 시각

publishedAt: Kafka ACK를 확인하고 발행 완료로 기록한 시각

Publisher 재시도 시 변경하면 안 되는 값: occurredAt
```

### **5. 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유**

```
Outbox 저장 후 Publisher가 실행되기 전에 비즈니스 데이터가 변경될 수 있다.
그러면 이벤트 발생 당시의 값이 아니라 현재 값으로 Payload가 만들어진다.

같은 이벤트를 재시도할 때마다 Payload가 달라질 수도 있으므로
발급 트랜잭션에서 이벤트 발생 당시의 Payload를 완성해서 Outbox에 저장해야 한다.
```

### **6. Outbox 테이블 DDL**

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,
    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    event_type VARCHAR(100) NOT NULL,
    schema_version INTEGER NOT NULL,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),
    attempt_count INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    claim_token UUID,
    lease_until TIMESTAMPTZ,
    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CHECK ((payload ->> 'eventMessageId')::UUID = event_id)
);

CREATE INDEX idx_outbox_publish
    ON outbox_event (status, next_attempt_at, occurred_at);
```

### **7. event_id와 payload.eventMessageId 불변조건 검증**

```
애플리케이션에서 UUID를 한 번 생성하고 event_id와 Payload에 같은 값을 넣는다.
추가로 DB CHECK 제약으로 두 값이 같은지 검증한다.
두 값이 다르면 Outbox INSERT를 실패시켜 발급 트랜잭션 전체를 Rollback한다.
```

### **8. `deduplication_key` 설계**

```
Key 형식: COUPON_ISSUED:{couponIssueId}

예시: COUPON_ISSUED:5001
```

같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면 다음과 같이 `aggregateVersion`을 추가한다.

```
COUPON_ISSUED:5001:1
```

### **9. UNIQUE 위반 이후 트랜잭션 처리**

```
일반 INSERT에서 UNIQUE 위반이 발생하면 PostgreSQL 트랜잭션은 aborted 상태가 된다.
따라서 전체 Rollback 후 새 트랜잭션에서 기존 행을 조회해야 한다.

Savepoint를 사용하면 위반이 발생한 구간까지만 Rollback하고 같은 트랜잭션에서 조회할 수 있다.

ON CONFLICT DO NOTHING RETURNING을 사용하면 트랜잭션이 aborted 되지 않는다.
반환된 행이 없으면 기존 행을 조회하고 event_id와 Payload가 같은지 비교한다.
단순히 충돌을 무시하면 잘못된 deduplication_key나 Payload 버그를 숨길 수 있으므로 동일성 확인이 필요하다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

### **1. 전체 SQL 트랜잭션**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows = 1이어야 한다.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
-- affected rows = 0이면 이벤트가 없거나 이미 품절된 경우이다.

-- 3. 발급 결과 저장
INSERT INTO coupon_issue (
    event_id,
    user_id,
    request_id,
    status,
    issued_at
) VALUES (
    :eventId,
    :userId,
    :requestId,
    'ISSUED',
    CURRENT_TIMESTAMP
)
RETURNING id, issued_at;

-- 4. request를 ISSUED로 확정
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- 5. 같은 트랜잭션에서 CouponIssued Outbox 저장
INSERT INTO outbox_event (
    event_id,
    deduplication_key,
    event_type,
    schema_version,
    aggregate_type,
    aggregate_id,
    aggregate_version,
    topic,
    partition_key,
    payload,
    status,
    occurred_at
) VALUES (
    :eventMessageId,
    'COUPON_ISSUED:' || :couponIssueId,
    'COUPON_ISSUED',
    1,
    'COUPON_ISSUE',
    :couponIssueId,
    1,
    'coupon.issued',
    :couponIssueId,
    CAST(:payload AS JSONB),
    'PENDING',
    :issuedAt
);

COMMIT;
```

각 SQL의 영향받은 행 수가 예상과 다르거나 제약 조건 위반이 발생하면 `COMMIT`하지 않고 전체를 `ROLLBACK`한다.

### **2. 단계별 영향받은 행 수**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1 | 이미 처리된 요청인지 조회하고 현재 트랜잭션 종료 |
| issued_count 조건부 증가 | 1 | 기존 발급이면 중복 처리, 아니면 품절 또는 이벤트 없음 처리 |
| coupon_issue INSERT | 1 | 전체 Rollback 후 중복 발급 여부 확인 |
| PROCESSING → ISSUED | 1 | 상태 전이 오류이므로 전체 Rollback |
| outbox_event INSERT | 1 | 전체 Rollback 후 기존 Outbox와 동일성 확인 |

### **3. Outbox INSERT가 실패한 경우**

```
트랜잭션 결과: 전체 Rollback

coupon_event.issued_count: 증가 전 값으로 Rollback

coupon_issue: 생성되지 않음

coupon_issue_request: ISSUED 변경이 Rollback되어 기존 PENDING 상태

outbox_event: 생성되지 않음
```

### **4. Outbox 저장 실패를 무시하면 안 되는 이유**

```
발급 결과만 Commit하면 발급은 되었지만 발행할 이벤트가 없는 상태가 된다.
이 상태에서는 Publisher가 재시도할 대상도 없기 때문에 후속 서비스에 결과가 영구적으로 전달되지 않을 수 있다.
따라서 Outbox INSERT 실패는 발급 트랜잭션 전체 실패로 처리해야 한다.
```

### **5. request가 이미 ISSUED인 경우**

```
issued_count를 다시 증가시키는가? 증가시키지 않는다.

coupon_issue를 다시 생성하는가? 생성하지 않는다.

Outbox를 다시 INSERT하는가? 기존 발급과 함께 Commit된 Outbox가 있으므로 다시 생성하지 않는다.

Consumer 처리는 성공으로 종료할 수 있는가? 기존 request와 coupon_issue가 일치하면 중복 메시지로 보고 성공 처리할 수 있다.
```

이미 ISSUED인데 Outbox가 없다면 정상적인 상태가 아니므로 조용히 새로 만들기보다 알람을 발생시키고 원인을 확인해야 한다.

### **6. DB Commit 후 원본 Kafka Offset Commit 전에 종료되는 경우**

```
DB 상태: 발급 결과와 request ISSUED가 Commit되어 있음

Outbox 상태: PENDING으로 Commit되어 있음

Kafka 원본 메시지: Offset이 Commit되지 않아 다시 전달됨

재시작 후 필요한 멱등성 기준: requestId로 이미 ISSUED인지 확인
```

재전달되어도 발급과 Outbox를 다시 생성하지 않고 정상 처리한 뒤 Offset을 Commit한다.

### **7. 원본 Consumer의 Offset Commit 설정**

```
enable.auto.commit은 false로 설정한다.

AckMode는 DB 트랜잭션 Commit 이후에만 Offset이 반영되는 모드를 사용한다.

Listener에서 예외를 잡고 정상 반환하면 Offset이 Commit될 수 있으므로 실패를 숨기지 않는다.

Error Handler가 재시도할 예외를 정상 처리된 것으로 바꾸거나 recover한 뒤 Offset을 Commit하는지 확인한다.

즉 DB 트랜잭션이 실패한 메시지는 처리 완료로 간주하면 안 된다.
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

### **1. 단순 SELECT 후 UPDATE의 Race Condition**

```
Publisher A                    Publisher B
------------------------------------------------
PENDING evt-001 조회
                               PENDING evt-001 조회
evt-001을 PROCESSING 변경
                               evt-001을 PROCESSING 변경
Kafka 발행
                               Kafka 발행

결과: 두 Publisher가 같은 이벤트를 동시에 발행할 수 있다.
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL**

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY occurred_at, event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP + :leaseDuration,
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit해야 하는 이유**

```
1. Kafka ACK까지 Row Lock을 잡으면 다른 Publisher가 오래 대기하게 된다.

2. 긴 DB 트랜잭션으로 Connection Pool이 고갈되고 DB 처리량이 감소할 수 있다.

3. Kafka 장애가 DB 트랜잭션 지연과 Lock 증가로 전파될 수 있다.

4. 트랜잭션이 길어져 Deadlock이나 Vacuum 지연 가능성도 커진다.
```

따라서 짧은 트랜잭션에서 처리 권한만 Claim하고 Commit한 뒤 Kafka 발행은 트랜잭션 밖에서 수행한다.

### **4. 단일 Publisher에도 Lease가 필요한 이유**

```
Publisher가 PROCESSING으로 변경한 직후 종료될 수 있다.
Lease가 없다면 해당 행은 계속 PROCESSING에 남아 다시 처리되지 않는다.

Publisher가 하나여도 재시작한 Publisher가 만료된 작업을 회수할 수 있도록 Lease가 필요하다.
```

### **5. 만료된 PROCESSING 복구 SQL**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. Claim Token이 없을 때 발생하는 문제**

```
Publisher B가 만료된 작업을 새로 가져갔는데 Publisher A가 뒤늦게 상태를 변경할 수 있다.

A의 늦은 성공 UPDATE가 B의 처리 중 상태를 PUBLISHED로 바꾸거나
A의 늦은 실패 UPDATE가 B가 성공한 상태를 다시 PENDING으로 바꿀 수 있다.

Claim Token을 조건에 넣으면 현재 처리 권한을 가진 Publisher만 상태를 변경할 수 있다.
```

### **7. 성공과 실패 UPDATE의 공통 WHERE 조건**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

영향받은 행 수가 0이면 Lease가 만료되어 처리 권한을 잃은 것이므로 현재 Publisher가 상태를 덮어쓰면 안 된다.

### **8. Lease 시간 계산**

```
Lease 시간
>
Batch 크기 × 이벤트 한 건의 최대 Kafka 발행 및 ACK 대기 시간
+ DB 성공·실패 상태 변경 시간
+ 네트워크 지연과 GC Pause 등의 여유 시간
```

동기 순차 발행이므로 Batch 뒤쪽 이벤트가 실제로 발행되기까지 기다리는 시간도 포함해야 한다.

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 네 상태의 의미 차이**

```
KafkaTemplate.send() 호출 완료:
Producer에게 발행을 요청한 상태이며 Broker 저장 성공을 의미하지 않는다.

CompletableFuture 정상 완료:
설정된 acks 조건에 따라 Broker ACK를 받은 상태이다.

outbox = PUBLISHED:
ACK 성공을 확인한 뒤 Publisher DB에 발행 완료를 기록한 상태이다.

모든 후속 Consumer 처리 완료:
각 Consumer Group이 이벤트 처리를 완료한 상태이며 PUBLISHED와는 별개의 상태이다.
```

### **2. ACK 성공 후 PUBLISHED 변경 SQL**

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,
    lease_until = NULL,
    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### **3. 발행 실패 후 PENDING 변경 SQL**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    next_attempt_at = :nextAttemptAt,
    claim_token = NULL,
    lease_until = NULL,
    last_error = :lastError,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### **4. Timeout 시 Kafka Record가 없다고 단정할 수 없는 이유**

```
상황 A:
Broker에 Record가 저장되지 못한 상태에서 Timeout이 발생할 수 있다.

상황 B:
Broker에는 Record가 저장되었지만 ACK가 유실되거나 늦게 도착해서 Publisher가 Timeout을 받을 수도 있다.

Publisher는 두 상황을 구분할 수 없으므로 Timeout은 발행 결과 불명 상태이다.
```

### **5. Timeout 이후 재시도 정책**

```
Outbox 상태: PENDING으로 변경하고 next_attempt_at을 저장

재시도 여부: Exponential Backoff와 Jitter를 적용하여 재시도

Kafka 중복 가능성: 기존 Record가 저장된 상황 B라면 중복 발행 가능

Consumer에게 필요한 방어: eventMessageId 기반 멱등 처리
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유**

```
Exponential Backoff:
실패가 계속될수록 재시도 간격을 늘려 Kafka와 애플리케이션에 계속 부하를 주는 것을 막는다.

Jitter:
여러 Publisher가 같은 시각에 한번에 재시도하는 현상을 막기 위해 재시도 시각을 무작위로 분산한다.
```

### **7. Producer Idempotence의 범위**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | 같은 Producer 세션의 전송 재시도를 Sequence Number로 제거한다. |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능 | 재시작 후 애플리케이션이 새로운 발행 요청을 수행하는 중복이다. |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능 | 서로 다른 애플리케이션 발행 시도이므로 논리 이벤트 중복은 제거하지 못한다. |

### **8. 비동기 발행의 `whenComplete`에서 DB 작업을 직접 하면 위험한 이유**

```
whenComplete 콜백은 Kafka Producer I/O 스레드에서 실행될 수 있다.
이 스레드에서 DB Connection을 얻고 SQL을 실행하면 Broker 응답 처리와 다음 전송까지 지연될 수 있다.

DB 지연이 Producer I/O 스레드 고갈로 이어지면 전체 Kafka 처리량도 감소한다.
따라서 완료 결과만 받은 뒤 DB 상태 변경 작업은 크기가 제한된 전용 Executor로 넘겨야 한다.
```

## **과제 6. Outbox 장애 시나리오 분석하기**

### **1. 발급 트랜잭션 Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | Rollback되어 존재하지 않음 |
| request | PENDING으로 Rollback |
| outbox_event | Rollback되어 존재하지 않음 |
| 복구 방법 | 원본 Kafka 메시지를 다시 처리 |

Kafka 결과 Record와 중복 발행은 발생하지 않는다.

### **2. 발급 DB Commit 후 원본 Offset Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 발급 결과 존재 |
| request | ISSUED |
| outbox_event | PENDING 존재 |
| 원본 Kafka 메시지 | Offset 미반영으로 재전달 가능 |
| 복구 방법 | requestId로 중복임을 확인하고 발급을 생략한 뒤 정상 처리 |

### **3. Claim Commit 후 Kafka 발행 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING |
| Kafka Record | 존재하지 않음 |
| 복구 조건 | lease_until이 현재 시각보다 이전 |
| 복구 주체 | Outbox 복구 Scheduler 또는 다음 Publisher |

만료 행을 PENDING으로 복구해서 다시 발행한다.

### **4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING |
| Kafka Record | 존재함 |
| 재발행 가능성 | Lease 만료 후 다시 발행될 수 있음 |
| 필요한 Consumer 방어 | 같은 eventMessageId를 한 번만 반영하는 멱등 처리 |

### **5. Publisher A의 Lease 만료 후 B가 회수한 상황**

```
Publisher A가 늦게 성공 UPDATE:
token-A가 현재 claim_token과 다르므로 affected rows = 0

Publisher A가 늦게 실패 UPDATE:
token-A가 현재 claim_token과 다르므로 affected rows = 0

두 UPDATE에서 affected rows가 0이어야 하는 조건:
event_id 일치 AND status = PROCESSING AND claim_token = token-A
```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화: 새 이벤트와 실패 이벤트가 쌓여 계속 증가

가장 오래된 PENDING 대기 시간: 장애 시간만큼 계속 증가

attempt_count: 재시도된 이벤트를 중심으로 증가

Kafka 복구 후 처리: next_attempt_at이 지난 이벤트부터 작은 Batch로 발행

운영 알람: PENDING 수, 가장 오래된 대기 시간, 발행 실패율, 높은 attempt_count 알람
```

Backoff와 Jitter를 이용해 Kafka 장애 중에 재시도가 한꺼번에 몰리지 않게 해야 한다.

### **7. 두 재시도 대상 구분**

```
발급 DB 트랜잭션 실패:
발급 결과와 Outbox가 모두 없으므로 원본 coupon.issue.requested 메시지를 다시 처리한다.

발급 DB Commit 성공 후 CouponIssued 발행 실패:
쿠폰 발급은 이미 완료되었으므로 Outbox 이벤트만 다시 발행한다.
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 issued_count가 다시 증가하거나 사용자에게 쿠폰이 중복 발급될 수 있다.

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음 두 Record로 발행되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001
Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 멱등성 Key로 사용하면 안 되는 이유**

```
Offset은 Kafka에 저장된 물리 Record의 위치이다.
같은 논리 이벤트를 다시 발행하면 eventMessageId는 같지만 Offset은 달라진다.

따라서 Offset을 Key로 사용하면 두 Record를 서로 다른 이벤트로 판단하여 비즈니스 결과를 중복 반영한다.
```

### **2. processed_event 테이블 DDL**

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_id)
);
```

### **3. `subscriber_id`에 사용할 값**

```
mypage-coupon-projection을 사용한다.

pod나 서버 주소는 재시작 또는 Scale Out 시 바뀐다.
인스턴스마다 다른 값을 사용하면 같은 이벤트를 각 인스턴스가 최초 이벤트로 판단한다.

subscriber_id는 실행 중인 서버가 아니라 논리적인 구독 처리기를 식별해야 한다.
```

### **4. processed_event와 MyPage 변경 트랜잭션**

```sql
BEGIN;

-- 1. eventMessageId 중복 확인
INSERT INTO processed_event (
    subscriber_id,
    event_id
) VALUES (
    'mypage-coupon-projection',
    :eventMessageId
)
ON CONFLICT DO NOTHING
RETURNING event_id;

-- 반환된 행이 없으면 이미 처리한 이벤트이므로 조회 모델을 변경하지 않고 COMMIT한다.
-- 반환된 행이 있는 최초 이벤트만 아래 SQL을 실행한다.
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    last_aggregate_version,
    last_event_at
) VALUES (
    :couponIssueId,
    :userId,
    :couponEventId,
    'ISSUED',
    :aggregateVersion,
    :occurredAt
);

COMMIT;
```

조회 모델 변경이 실패하면 `processed_event` INSERT도 같이 Rollback되어야 한다.

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 경우**

```
Consumer DB 상태: processed_event와 조회 모델 변경이 Commit됨

Consumer Group Offset: Commit되지 않음

재시작 후 Kafka 전달: 같은 Record가 재전달됨

재전달된 이벤트 처리: processed_event PK 충돌을 확인하고 조회 모델 변경을 생략한 뒤 Offset Commit
```

### **6. processed_event만으로 외부 SMS를 정확히 한 번 보장할 수 없는 이유**

```
processed_event 저장은 DB 트랜잭션이지만 SMS 전송은 외부 API 호출이다.

SMS 전송 후 DB Commit 전에 장애가 발생하면 SMS는 전송되었지만 processed_event는 Rollback된다.
재처리할 때 SMS가 다시 전송될 수 있다.

반대로 DB를 먼저 Commit하고 SMS 호출 전에 장애가 발생하면 SMS가 전송되지 않는다.
```

### **7. Notification Service에 추가할 방법**

```
1. Notification Service 내부에 별도 Outbox를 저장하고 Sender가 전송한다.

2. 알림 작업 테이블을 만든 뒤 notificationId를 기준으로 중복 작업 생성을 막는다.

3. SMS Provider가 지원한다면 notificationId를 Idempotency Key로 전달한다.
```

### **8. processed_event 보관 기간**

```
Kafka Topic의 Record가 남아 있는 동안 Offset을 되감으면 과거 이벤트가 다시 전달될 수 있다.
Publisher 장애로 Outbox가 오래 지연된 뒤 발행될 수도 있다.
운영자가 Outbox 또는 Kafka Record를 수동 재발행할 수도 있다.

따라서 processed_event 보관 기간은
Kafka Topic 보관 기간 + 최대 Offset 되감기 범위 + Outbox 지연 및 수동 재발행 가능 기간보다 길어야 한다.
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

### **1. 같은 Partition Key를 사용하는 이유**

```
같은 couponIssueId의 이벤트를 같은 Kafka Partition으로 보내기 위해 사용한다.
같은 Partition에 실제로 저장된 Record는 Offset 순서대로 Consumer에게 전달된다.
```

### **2. 같은 Key가 비즈니스 발생 순서까지 보장하지 못하는 이유**

```
여러 Publisher가 SKIP LOCKED로 서로 다른 Outbox 행을 동시에 가져갈 수 있다.
먼저 발생한 이벤트의 발행이 실패해서 Backoff되는 동안 나중 이벤트가 먼저 성공할 수 있다.
Producer의 재시도와 설정에 따라서도 Broker 도착 순서가 달라질 수 있다.

같은 Key는 Kafka에 저장된 이후의 Partition 내 순서를 보장할 뿐
DB에서 이벤트가 발생한 순서대로 Producer가 발행하는 것까지 보장하지 않는다.
```

### **3. 순서 역전 시나리오**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A: version=1 Claim 후 발행 실패, Backoff

Publisher B: version=2 Claim 후 발행 성공

Kafka 저장 순서: CouponCancelled(version=2) → CouponIssued(version=1)
```

### **4. `occurredAt`만으로 순서를 판단하면 안 되는 이유**

```
1. 두 이벤트가 같은 Timestamp 정밀도의 시각을 가질 수 있다.

2. 여러 서버의 시계가 정확히 일치하지 않을 수 있다.

3. occurredAt은 비즈니스 발생 시각일 뿐 Aggregate 상태 변경의 순번이 아니다.
```

### **5. 최신 상태 Projection의 순서 역전 방어 SQL**

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    status,
    last_aggregate_version,
    last_event_at
) VALUES (
    :couponIssueId,
    :status,
    :aggregateVersion,
    :occurredAt
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    last_aggregate_version = EXCLUDED.last_aggregate_version,
    last_event_at = EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version
      < EXCLUDED.last_aggregate_version;
```

### **6. 큰 Version이 먼저 도착한 경우**

```
먼저 도착: CouponCancelled(version=2)

나중 도착: CouponIssued(version=1)

최종 MyPage 상태: CANCELLED, last_aggregate_version = 2

version=1 처리 결과: WHERE 조건을 만족하지 않아 affected rows = 0, 기존 상태 유지
```

### **7. Consumer별 낮은 Version 처리**

| Consumer | 낮은 Version 이벤트 생략 가능 여부 | 이유 또는 추가로 필요한 설계 |
| --- | --- | --- |
| 최신 상태만 저장하는 MyPage Projection | 가능 | 이미 더 최신 상태가 있으므로 낮은 버전이 덮어쓰지 않게 하면 된다. |
| 모든 발급·취소 건수를 집계하는 Analytics | 불가능 | 각각의 사실을 모두 집계해야 하므로 eventMessageId로만 중복을 제거해야 한다. |
| 발급과 취소 알림을 각각 보내는 Notification | 일반적으로 불가능 | 각 알림이 필요하다면 버퍼링, 누락 Version 확인 등 순서 처리 정책이 추가로 필요하다. |

### **8. `aggregateVersion`의 역할**

```
aggregateVersion은 이벤트 순서 역전을
자동으로 바로잡아 주는 값이 아니다.

aggregateVersion은 같은 Aggregate에서 발생한 상태 변경의
논리적인 순서를 식별하기 위한 값이다.

최신 상태 Projection에서는 낮은 버전이
최신 상태를 과거 상태로 덮어쓰는 것을 방지할 수 있다.

모든 상태 전이를 순서대로 처리해야 하는 Consumer는
추가로 Version Gap 감지, 버퍼링 또는 재조회 정책이 필요하다.
```

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 운영 지표**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 발행을 기다리는 이벤트 수 | 생성 속도보다 빠르게 계속 증가할 때 |
| 가장 오래된 PENDING 대기 시간 | 가장 오래 기다린 이벤트의 지연 시간 | 서비스에서 정한 발행 지연 기준을 초과할 때 |
| PROCESSING 이벤트 수 | Publisher가 Claim한 이벤트 수 | Publisher 처리량에 비해 계속 많거나 감소하지 않을 때 |
| 만료된 PROCESSING 수 | 처리 주체를 잃은 이벤트 수 | 1건 이상 반복해서 발생하거나 계속 증가할 때 |
| attempt_count | 이벤트별 발행 시도 횟수 | 같은 이벤트의 값이 계속 증가할 때 |
| Outbox 생성 처리량 | 초당 새로 생성되는 이벤트 수 | 평소보다 급증하거나 0으로 감소할 때 |
| Kafka 발행 처리량 | 초당 ACK 성공한 이벤트 수 | 생성 처리량보다 지속적으로 낮을 때 |
| DB 발생부터 Kafka ACK까지의 시간 | End-to-End 발행 지연 | SLA를 초과하거나 계속 증가할 때 |

### **2. 생성 2,000건/초, 발행 1,500건/초인 상황**

```
1분 후 예상 적체 증가량: (2,000 - 1,500) × 60 = 30,000건

10분 후 예상 적체 증가량: 500 × 600 = 300,000건

가장 먼저 확인할 지표: PENDING 증가 속도와 가장 오래된 PENDING 대기 시간

가능한 대응:
Publisher 인스턴스와 Batch 처리량 확대, Kafka/DB 병목 확인, 발행 속도 제한 또는 입력량 조절
```

현재 상태가 계속되면 초당 500건씩 무한히 적체되므로 반드시 처리량을 늘리거나 유입량을 줄여야 한다.

### **3. 즉시 알람이 필요한 설계 가정 위반**

```
1. deduplication_key UNIQUE 위반이 반복됨

2. request가 PROCESSING 상태로 Commit되어 관측됨

3. Lease가 만료된 PROCESSING 행이 반복적으로 발생함

4. DB의 ISSUED 결과가 있는데 Outbox가 존재하지 않음

5. 발급 처리에서 SOLD_OUT 또는 DUPLICATE_USER가 평소보다 급증함
```

### **4. PUBLISHED 행만 정리해야 하는 이유**

```
PENDING을 삭제하면: 아직 발행하지 않은 이벤트가 영구적으로 유실된다.

PROCESSING을 삭제하면: 발행 중이거나 결과를 확인하지 못한 이벤트가 유실될 수 있다.

PUBLISHED를 보관하는 목적: 발행 이력 확인, 장애 조사, 운영자 재발행에 사용한다.
```

### **5. PUBLISHED 행을 대량 삭제하면 안 되는 이유**

```
한 번에 대량 삭제하면 긴 트랜잭션이 만들어지고 많은 DB I/O가 발생한다.
삭제 중 Lock과 Connection을 오래 사용해서 일반 발급 및 Publisher 처리에 영향을 줄 수 있다.

PostgreSQL은 DELETE 즉시 디스크 공간을 반환하지 않으므로 Dead Tuple이 많아져 Table과 Index Bloat도 커질 수 있다.
```

### **6. 작은 Batch 정리 흐름**

```
1. status = PUBLISHED이고 published_at이 보관 기준보다 오래된 행을 1,000건 조회

2. 조회한 event_id의 행만 DELETE

3. Commit

4. 잠시 대기한 뒤 다음 Batch 반복

5. 삭제 시간과 건수, DB 부하를 모니터링
```

### **7. 보관 기간 비교**

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |
| Outbox PUBLISHED 행 | 발행 이력과 장애 조사 | 과거 발행 여부 확인과 수동 재발행이 어려움 |
| Kafka Topic Record | Consumer의 지연 처리와 재처리 | Offset을 되감아도 필요한 Record가 없음 |
| Consumer processed_event | 중복 비즈니스 반영 방지 | 과거 Record 재전달 시 이미 처리한 이벤트를 다시 반영함 |

processed_event 보관 기간은 Kafka Record 재등장 가능 기간보다 길게 잡아야 한다.

### **8. `last_error` 저장 시 주의점**

```
전체 Stack Trace를 저장하면 행 크기와 DB 용량이 빠르게 증가한다.
Payload, 전화번호, Token 같은 민감 정보가 포함되면 보안 문제가 생길 수 있다.

DB에는 검색 가능한 오류 코드와 제한된 메시지만 저장하고
상세 Stack Trace는 event_id, Trace ID와 함께 로그 시스템에 저장한다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

### **1. 코드에서 찾은 문제**

#### **문제 1**

```
문제 위치: issueCoupon()의 kafkaTemplate.send()

문제 내용: 발급 DB 트랜잭션에서 Kafka를 직접 호출한다.

발생 가능한 장애: DB와 Kafka 중 하나만 성공하는 Dual Write 문제가 발생한다.

수정 방법: 발급 결과와 Outbox를 같은 DB 트랜잭션으로 저장한다.
```

#### **문제 2**

```
문제 위치: issueCoupon() 전체

문제 내용: coupon_issue만 저장하고 Outbox 이벤트를 저장하지 않는다.

발생 가능한 장애: DB Commit 후 프로세스가 종료되면 발행할 이벤트가 영구 유실된다.

수정 방법: 같은 트랜잭션에서 고정된 Payload를 가진 outbox_event를 INSERT한다.
```

#### **문제 3**

```
문제 위치: issueCoupon()의 kafkaTemplate.send()

문제 내용: CompletableFuture의 Broker ACK를 확인하지 않는다.

발생 가능한 장애: 실제 발행 실패인데도 발급 메서드가 성공하고 DB가 Commit될 수 있다.

수정 방법: 발급 트랜잭션에서는 Kafka를 호출하지 않고 Outbox Publisher에서 ACK를 확인한다.
```

#### **문제 4**

```
문제 위치: publishOutbox()의 @Transactional

문제 내용: Outbox 조회부터 Kafka 발행까지 하나의 긴 DB 트랜잭션이다.

발생 가능한 장애: Kafka 지연이 긴 Lock, Connection 점유, DB 처리량 감소로 이어진다.

수정 방법: 짧은 Claim 트랜잭션을 Commit한 뒤 Kafka는 트랜잭션 밖에서 발행한다.
```

#### **문제 5**

```
문제 위치: findTop100ByStatus("PENDING")

문제 내용: 여러 Publisher가 같은 PENDING 행을 조회하지 못하게 하는 Claim이 없다.

발생 가능한 장애: 여러 Publisher가 같은 이벤트를 동시에 발행한다.

수정 방법: FOR UPDATE SKIP LOCKED로 조회하고 PROCESSING으로 원자적으로 변경한다.
```

#### **문제 6**

```
문제 위치: event.markPublished()

문제 내용: send() 호출 직후 ACK 확인 없이 PUBLISHED로 변경한다.

발생 가능한 장애: 실제 Kafka 발행은 실패했지만 완료 상태가 되어 다시 시도하지 않는다.

수정 방법: CompletableFuture가 정상 완료된 뒤에만 PUBLISHED로 변경한다.
```

#### **문제 7**

```
문제 위치: publishOutbox() 전체

문제 내용: Claim Token과 Lease가 없다.

발생 가능한 장애: 종료된 Publisher의 PROCESSING 행을 안전하게 회수할 수 없고 늦은 Publisher가 새 처리 결과를 덮어쓸 수 있다.

수정 방법: Claim 시 UUID Token과 lease_until을 저장하고 상태 UPDATE에도 Token을 조건으로 사용한다.
```

#### **문제 8**

```
문제 위치: recoverProcessing()

문제 내용: Lease 만료 여부와 관계없이 모든 PROCESSING 행을 PENDING으로 변경한다.

발생 가능한 장애: 정상 발행 중인 Publisher의 작업을 다른 Publisher가 중복 발행한다.

수정 방법: status = PROCESSING AND lease_until <= CURRENT_TIMESTAMP인 행만 회수한다.
```

#### **문제 9**

```
문제 위치: createPayloadFromCurrentCouponIssue(event)

문제 내용: 이벤트 발생 시점이 아니라 현재 비즈니스 테이블로 Payload를 다시 만든다.

발생 가능한 장애: 재시도 시 Payload가 달라지고 발생 당시 사실과 다른 이벤트가 발행된다.

수정 방법: 발급 트랜잭션에서 완성한 Payload를 Outbox에 저장하고 그대로 발행한다.
```

#### **문제 10**

```
문제 위치: publishOutbox()의 반복문

문제 내용: 실패 상태, next_attempt_at, attempt_count, Backoff 정책이 없다.

발생 가능한 장애: 일시적인 Kafka 장애를 복구하지 못하거나 재시도가 한꺼번에 몰린다.

수정 방법: 실패 시 Token을 확인하고 PENDING으로 변경한 뒤 Backoff와 Jitter를 적용한다.
```

#### **문제 11**

```
문제 위치: new ProcessedEvent(event.getKafkaPartition(), event.getKafkaOffset())

문제 내용: Kafka Partition과 Offset을 Consumer 멱등성 Key로 사용한다.

발생 가능한 장애: 같은 eventMessageId가 다른 Offset으로 재발행되면 중복 반영된다.

수정 방법: subscriber_id와 eventMessageId를 복합 Primary Key로 사용한다.
```

#### **문제 12**

```
문제 위치: onResult()의 저장 순서

문제 내용: 비즈니스 테이블을 먼저 변경한 뒤 processed_event를 저장한다.

발생 가능한 장애: 중복 확인 전에 조회 모델이 변경되고 processed_event 저장만 실패할 수 있다.

수정 방법: 하나의 DB 트랜잭션에서 processed_event를 먼저 INSERT하고 최초 이벤트일 때만 비즈니스 테이블을 변경한다.
```

#### **문제 13**

```
문제 위치: onResult() 전체

문제 내용: 두 저장 작업을 묶는 @Transactional이 없다.

발생 가능한 장애: 한 작업만 성공하여 처리 기록과 실제 비즈니스 결과가 달라질 수 있다.

수정 방법: processed_event와 user_coupon_view 변경을 같은 로컬 DB 트랜잭션으로 묶는다.
```

#### **문제 14**

```
문제 위치: publishOutbox()의 Batch 반복 처리

문제 내용: 한 이벤트 실패가 발생했을 때 다른 이벤트의 처리 결과와 분리하는 정책이 없다.

발생 가능한 장애: 앞의 Kafka 발행은 성공했지만 DB 트랜잭션 전체가 Rollback되어 Batch 전체가 중복 발행될 수 있다.

수정 방법: Claim 이후 이벤트별 ACK 결과에 따라 짧은 성공·실패 트랜잭션으로 각각 상태를 변경한다.
```

### **2. 필수 검토 항목 연결**

| 검토 항목 | 문제가 발생하는 코드 | 수정 방향 |
| --- | --- | --- |
| 발급 트랜잭션에서 Kafka 직접 호출 | `issueCoupon()`의 `kafkaTemplate.send()` | Outbox INSERT로 변경 |
| 발급 결과와 Outbox의 원자적 저장 없음 | `issueCoupon()` 전체 | coupon_issue와 outbox_event를 같은 트랜잭션에 저장 |
| 여러 Publisher의 동시 Claim 방어 없음 | `findTop100ByStatus()` | `FOR UPDATE SKIP LOCKED`와 PROCESSING 상태 사용 |
| DB 트랜잭션 안에서 Kafka ACK 대기 또는 발행 수행 | `publishOutbox()`의 `@Transactional`과 `send()` | Claim Commit 후 트랜잭션 밖에서 발행 |
| ACK 확인 전에 PUBLISHED 변경 | `send()` 다음의 `markPublished()` | Future 정상 완료 후 PUBLISHED UPDATE |
| Claim Token 없음 | `publishOutbox()` 전체 | Claim과 상태 변경에 UUID Token 사용 |
| Lease 만료 조건 없이 모든 PROCESSING 회수 | `updateAllProcessingToPending()` | 만료된 Lease만 회수 |
| 현재 비즈니스 테이블에서 Payload 재생성 | `createPayloadFromCurrentCouponIssue()` | Outbox에 저장된 Payload 그대로 사용 |
| Kafka Offset을 멱등성 Key로 사용 | `new ProcessedEvent(partition, offset)` | eventMessageId 사용 |
| processed_event와 비즈니스 변경의 트랜잭션 순서·원자성 부족 | `onResult()` 전체 | 중복 확인과 비즈니스 변경을 같은 트랜잭션으로 처리 |

### **4. 수정된 구조의 발행 보장 수준**

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 PostgreSQL 트랜잭션으로 Commit 또는 Rollback된다. |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | ACK 결과 불명과 Publisher 재시도로 같은 이벤트가 여러 Record가 될 수 있다. |
| Publisher 복구 후 재발행 | 조건부 보장 | Outbox가 남고 Poller, Lease 복구, Kafka가 정상 동작해야 한다. |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | 여러 Publisher와 발행 실패 및 Backoff로 순서가 역전될 수 있다. |
| Consumer의 중복 비즈니스 반영 방지 | 조건부 보장 | eventMessageId 중복 기록과 비즈니스 변경을 같은 트랜잭션으로 처리해야 한다. |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | Publisher는 각 Consumer Group의 최종 처리 여부를 알 수 없다. |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | Consumer DB와 외부 API 사이의 Dual Write가 남아 있다. |

결론적으로 이 구조는 **At-Least-Once 발행**을 사용하고 Consumer 멱등 처리로 비즈니스 결과의 중복 반영을 막는 구조이다.
