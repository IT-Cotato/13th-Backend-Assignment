# 6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성

## 과제 1. Dual Write 문제와 Outbox 적용 범위

### 1~2. 저장소와 `@Transactional`

저장소는 PostgreSQL(쿠폰·요청 데이터)과 Kafka Broker(결과 이벤트)다. 일반적인 Spring `@Transactional`은 PostgreSQL의 로컬 트랜잭션만 관리한다. Kafka까지 하나의 원자적 트랜잭션으로 묶으려면 별도 분산 트랜잭션 구성이 필요하며, 이 과제의 구조에는 없다.

### 3. DB First 장애

```text
DB Commit
  ↓
[Kafka send/ACK 전 프로세스 종료]
  ↓
Kafka 발행

최종 DB 상태: coupon_issue 존재, request=ISSUED
최종 Kafka 상태: CouponIssued 없음
영향: 알림·마이페이지·통계가 발급 사실을 모른다.
복구 정보: 무엇을 발행할지 알 수 있는 영속된 Outbox 이벤트
```

### 4. Kafka First 장애

```text
Kafka 발행
  ↓
[DB Commit 전 트랜잭션 실패]
  ↓
DB Commit

최종 DB 상태: 쿠폰 발급 기록 없음
최종 Kafka 상태: CouponIssued 존재 가능
영향: 후속 서비스가 존재하지 않는 쿠폰을 반영할 수 있다.
```

### 5. `AFTER_COMMIT`만으로 부족한 이유

DB Commit 직후 Listener 실행 전에 프로세스가 종료되면, 발행할 이벤트는 메모리에서 사라져 복구 기준이 없다. Listener가 실행되어도 `KafkaTemplate.send()` 호출은 Broker ACK가 아니다. 호출 뒤 ACK 전에 종료·실패할 수 있으며 DB 결과는 이미 되돌릴 수 없다.

### 6. 적용 범위

| 구간 | 해결되는가? | 이유 |
| --- | --- | --- |
| `coupon_issue` 저장 ↔ `CouponIssued` 발행 의도 저장 | 예 | 같은 PostgreSQL 트랜잭션에 저장한다. |
| Redis SUCCESS ↔ 최초 요청 Kafka 발행 | 아니오 | Redis와 Kafka는 로컬 DB 트랜잭션 밖이다. |
| 원본 Kafka 소비 ↔ 발급 DB Commit | 아니오 | Offset Commit과 DB Commit 사이 재전달 가능성이 있다. `requestId` 멱등성으로 방어한다. |
| Consumer DB 저장 ↔ 외부 SMS API 호출 | 아니오 | 외부 API는 Consumer DB 트랜잭션에 포함되지 않는다. |

```text
Transactional Outbox가 직접 보장하는 것:
DB 발급 결과가 Commit되면, 발행할 결과 이벤트 기록도 같은 DB에 남는 것.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record의 물리적 Exactly-Once, 순서 보장, 모든 Consumer 완료, 외부 알림 Exactly-Once.
```

## 과제 2. CouponIssued 이벤트와 Outbox 테이블

### 1. 이벤트는 사실이다

`IssueCoupon`은 “쿠폰을 발급하라”는 명령이고, `CouponIssued`는 “쿠폰이 발급되었다”는 확정된 과거 사실이다. 결과 이벤트 Consumer는 쿠폰을 다시 발급하지 않고 자신의 후속 일을 수행한다.

### 2. 이벤트 Envelope

```json
{
  "eventMessageId": "8a78e94b-5c3d-46a7-a364-538cd1f856c9",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### 3. ID 비교

| 값 | 식별 대상 | 재발행 시 변경? | Consumer 멱등 Key? |
| --- | --- | --- | --- |
| `couponEventId` | 쿠폰 행사 | 아니오 | 아니오. 한 행사에 발급이 많다. |
| `couponIssueId` | 개별 쿠폰 발급 | 아니오 | 이벤트 자체 ID보다 도메인 ID라 부적절하다. |
| `eventMessageId` | 논리 결과 이벤트 | 아니오 | 예 |
| Kafka Partition + Offset | Kafka 내 Record 위치 | 예 | 아니오. 재발행 Record는 다른 Offset이다. |

### 4~5. 시각과 Snapshot

`occurredAt`은 발급 사실이 발생한 시각, `publishedAt`은 Publisher가 Kafka ACK 후 완료를 기록한 시각이다. 재시도해도 `occurredAt`, 이벤트 Payload, `eventMessageId`는 바꾸면 안 된다. Payload는 Outbox INSERT 때 완성된 Snapshot으로 저장한다. 나중에 현재 비즈니스 테이블을 다시 읽으면 변경·삭제된 현재값으로 과거 사실을 왜곡할 수 있다.

### 6. Outbox DDL

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,
    request_id UUID,
    deduplication_key VARCHAR(200) NOT NULL UNIQUE,
    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,
    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),
    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    claim_token UUID,
    lease_until TIMESTAMPTZ,
    last_error VARCHAR(1000),
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 7~9. 불변조건과 중복 키

애플리케이션에서 UUID를 한 번 생성해 `event_id`와 `payload.eventMessageId`에 같은 값을 넣고, INSERT 전 검증한다. 가능하면 DB trigger 또는 JSONB CHECK로도 검증한다.

```text
Key 형식: COUPON_ISSUE:{couponIssueId}:COUPON_ISSUED
예시: COUPON_ISSUE:5001:COUPON_ISSUED
```

같은 Aggregate에서 같은 유형이 여러 번 생기면 `aggregateVersion`을 추가한다. UNIQUE 위반은 정상 중복으로 조용히 넘기지 않는다. 전체 Rollback 후 새 트랜잭션에서 기존 행을 조회해 동일성을 검증하거나, Savepoint로 INSERT 실패만 되돌린다. `ON CONFLICT DO NOTHING RETURNING` 뒤에도 기존 행을 조회하여 Key·Payload가 같은지 비교한다. 다르면 버그/불일치이므로 실패·알람 처리한다.

## 과제 3. 발급 결과와 Outbox의 단일 트랜잭션

### 1. SQL

```sql
BEGIN;

UPDATE coupon_issue_request
SET status = 'PROCESSING', updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId AND status = 'PENDING'; -- 반드시 1행

UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :couponEventId AND issued_count < total_count; -- 1행, 0이면 품절/잘못된 eventId

INSERT INTO coupon_issue (coupon_event_id, user_id, issued_at)
VALUES (:couponEventId, :userId, CURRENT_TIMESTAMP)
RETURNING id, issued_at;

UPDATE coupon_issue_request
SET status = 'ISSUED', coupon_issue_id = :couponIssueId, updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId AND status = 'PROCESSING'; -- 반드시 1행

INSERT INTO outbox_event (event_id, request_id, deduplication_key, aggregate_type,
  aggregate_id, event_type, schema_version, aggregate_version, topic, partition_key,
  payload, occurred_at)
VALUES (:eventId, :requestId, :dedupKey, 'COUPON_ISSUE', :couponIssueId,
  'COUPON_ISSUED', 1, 1, 'coupon.issued', :couponIssueId::text, :payload::jsonb, :occurredAt);

COMMIT;
```

### 2~4. 행 수와 Rollback

| 작업 | 성공 행 수 | 예상과 다를 때 |
| --- | ---: | --- |
| PENDING → PROCESSING | 1 | 이미 최종 처리된 요청인지 조회하고 멱등 종료, 아니면 오류 |
| 조건부 수량 증가 | 1 | `SOLD_OUT` 또는 잘못된 이벤트 확인 후 최종 실패/재시도 분기 |
| `coupon_issue` INSERT | 1 | Rollback |
| PROCESSING → ISSUED | 1 | 설계 위반, Rollback·알람 |
| Outbox INSERT | 1 | Rollback·알람 |

Outbox INSERT가 실패하면 전체 트랜잭션을 Rollback한다. 따라서 `issued_count` 증가, `coupon_issue`, `request=ISSUED`, Outbox 행 모두 남지 않는다. 이를 무시하고 Commit하면 발급됐지만 재발행할 근거가 없는 유실 상태가 된다.

### 5~7. 원본 메시지와 Offset

이미 `ISSUED`인 `requestId`가 재전달되면 수량·발급 기록·Outbox INSERT를 모두 다시 수행하지 않고 성공 처리한다. 발급 DB Commit 뒤 Offset Commit 전에 종료되면 DB와 Outbox는 존재하지만 원본 Kafka 메시지는 재전달될 수 있다. `requestId`와 최종 상태가 멱등 기준이다.

`enable.auto.commit=false`를 확인하고, 실제 `AckMode`, Listener 예외가 정상 처리로 삼켜지지 않는지, Error Handler가 실패 메시지를 성공 처리/Offset Commit으로 바꾸지 않는지를 확인한다. Offset은 DB Commit 뒤에만 커밋한다.

## 과제 4. Claim, Lease, Claim Token

### 1~3. 동시성 및 Claim SQL

단순 SELECT는 A와 B가 같은 PENDING 행을 동시에 읽고 둘 다 발행하는 경쟁 조건이 있다. 다음처럼 DB 잠금으로 Claim한다.

```sql
BEGIN;
WITH candidates AS (
  SELECT event_id FROM outbox_event
  WHERE status = 'PENDING' AND next_attempt_at <= CURRENT_TIMESTAMP
  ORDER BY created_at, event_id
  FOR UPDATE SKIP LOCKED
  LIMIT :batchSize
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING', claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP + :leaseInterval,
    attempt_count = attempt_count + 1, updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;
COMMIT;
```

Claim은 짧게 Commit하고 Kafka는 그 밖에서 호출한다. ACK를 기다리며 Row Lock을 잡으면 다른 Publisher가 대기하고, 장애·느린 네트워크 때 DB 연결/트랜잭션이 오래 점유되며, 처리량과 장애 복구가 나빠진다.

### 4~8. Lease와 Token

단일 Publisher도 Claim 후 프로세스가 죽으면 행이 `PROCESSING`에 남으므로 Lease 만료 회수가 필요하다.

```sql
UPDATE outbox_event
SET status='PENDING', claim_token=NULL, lease_until=NULL,
    next_attempt_at=CURRENT_TIMESTAMP, updated_at=CURRENT_TIMESTAMP
WHERE status='PROCESSING' AND lease_until < CURRENT_TIMESTAMP;
```

A의 Lease가 끝난 뒤 B가 token-B로 재Claim한 경우 A의 늦은 성공/실패 UPDATE는 B의 소유권을 덮으면 안 된다. 성공·실패 UPDATE 모두 다음 조건을 쓴다.

```sql
WHERE event_id = :eventId AND status = 'PROCESSING' AND claim_token = :claimToken
```

Lease 시간은 **한 Batch의 순차 Kafka ACK 최대 대기 시간 + DB 상태 갱신 여유 + GC/네트워크 지연 여유**보다 길어야 한다.

## 과제 5. ACK, Timeout, 재시도

### 1. 상태 차이

`send()` 호출 완료는 요청을 넘겼다는 뜻일 뿐이다. `CompletableFuture` 정상 완료는 Broker ACK 확인이다. `PUBLISHED`는 ACK 뒤 해당 사실을 Outbox DB에도 기록한 상태다. 모든 Consumer 완료는 각 Consumer Group의 별도 처리 완료로, 위 세 상태와 다르다.

```sql
-- ACK 성공
UPDATE outbox_event
SET status='PUBLISHED', published_at=CURRENT_TIMESTAMP,
    claim_token=NULL, lease_until=NULL, updated_at=CURRENT_TIMESTAMP
WHERE event_id=:eventId AND status='PROCESSING' AND claim_token=:claimToken;

-- 실패 또는 Timeout
UPDATE outbox_event
SET status='PENDING', next_attempt_at=:nextAttemptAt,
    claim_token=NULL, lease_until=NULL, last_error=:shortError,
    updated_at=CURRENT_TIMESTAMP
WHERE event_id=:eventId AND status='PROCESSING' AND claim_token=:claimToken;
```

Timeout은 Broker에 저장되지 못한 경우(A)도, 저장됐지만 ACK를 받지 못한 경우(B)도 가능하다. 그래서 미완료로 두고 재시도하며, 중복 Kafka Record를 허용하고 Consumer는 `eventMessageId`로 멱등 처리한다. Backoff는 반복 실패 시 부하를 줄이고, Jitter는 모든 Publisher가 동시에 재시도하는 쏠림을 막는다.

| 중복 원인 | Producer Idempotence 방어 | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | 같은 producer session의 중복 전송을 억제한다. |
| ACK 후 PUBLISHED 전 종료 | 불가 | 재시도는 새 발행 시도/세션일 수 있다. |
| 운영자가 PENDING으로 변경 | 불가 | 애플리케이션 수준 재발행이다. |

비동기 확장 시 `whenComplete`가 Producer I/O 스레드에서 실행될 수 있다. 그 안에서 느린 DB 작업을 하면 I/O를 막을 수 있으므로 전용 Executor로 넘긴다.

## 과제 6. 장애 시나리오

| 상황 | DB/Outbox/Kafka | 복구와 중복 |
| --- | --- | --- |
| 발급 Commit 전 장애 | 발급·Outbox 모두 Rollback, Kafka 없음 | 원본 메시지 재처리, 중복 없음 |
| 발급 Commit 후 원본 Offset 전 장애 | 발급=`ISSUED`, Outbox=`PENDING`, 원본 재전달 가능 | `requestId`로 멱등 종료 |
| Claim Commit 후 발행 전 종료 | Outbox=`PROCESSING`, Kafka 없음 | Lease 만료 후 Publisher가 PENDING 회수 |
| ACK 후 PUBLISHED 전 종료 | Outbox=`PROCESSING`, Kafka 존재 가능 | Lease 후 재발행 가능, Consumer `eventMessageId` 멱등 |

A의 Lease가 만료되어 B가 재Claim하면 A의 늦은 성공·실패 UPDATE는 `event_id + PROCESSING + token-A` 조건에서 0행이어야 한다. Kafka가 30분 장애면 PENDING과 가장 오래된 대기 시간이 증가하고 attempts도 늘어난다. 복구 뒤 Backoff 대상부터 처리하며 PENDING 적체·최장 대기·반복 attempt를 알람한다.

발급 DB 트랜잭션 실패는 **원본 요청**을 재처리한다. DB Commit 성공 후 결과 이벤트 발행 실패는 **Outbox만** 재발행한다. 이미 발급된 쿠폰을 다시 발급하면 수량과 사용자 발급 기록이 중복된다.

## 과제 7. Consumer 멱등 처리

Offset은 물리 Record 위치라 같은 논리 이벤트가 재발행되면 달라진다. 따라서 멱등 Key가 될 수 없다.

```sql
CREATE TABLE processed_event (
  subscriber_id VARCHAR(100) NOT NULL,
  event_id UUID NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (subscriber_id, event_id)
);

BEGIN;
INSERT INTO processed_event (subscriber_id, event_id)
VALUES ('mypage-coupon-projection', :eventMessageId)
ON CONFLICT DO NOTHING
RETURNING event_id;
-- 반환 행이 1개일 때만 user_coupon_view INSERT/UPDATE
COMMIT;
```

`subscriber_id`는 `pod-7f8c9d`나 서버 IP가 아니라 안정적인 논리 구독자 이름 `mypage-coupon-projection`이어야 한다. 인스턴스가 바뀌어도 같은 Handler의 중복을 막아야 하기 때문이다. Consumer DB Commit 뒤 Offset Commit 전에 죽으면 Kafka가 다시 전달하고, `processed_event` 충돌로 비즈니스 변경을 생략한 후 Offset을 커밋한다.

SMS는 DB 저장과 외부 호출 사이에 다시 Dual Write가 생기므로 processed_event만으로 Exactly-Once를 보장하지 않는다. Notification 내부 Outbox/알림 작업 테이블, Provider Idempotency Key, `notificationId` 기반 중복 방어를 함께 고려한다. processed_event 보관은 Kafka Topic 보관 기간 + 최대 Outbox 지연 + Offset 되감기/운영자 수동 재발행 범위보다 길어야 한다.

## 과제 8. Partition Key와 순서

같은 `couponIssueId`를 partitionKey로 쓰면 같은 Aggregate를 같은 Partition에 모아 병렬 처리 단위를 정하고, 향후 순서 보장의 기준을 마련하며 부하 분산에도 도움 된다. 하지만 여러 Publisher, `SKIP LOCKED`, 실패 Backoff, Producer 재시도 때문에 DB 발생 순서와 `send()` 순서가 달라질 수 있다.

```text
DB: CouponIssued(v1) → CouponCancelled(v2)
Publisher A: v1 Claim 후 발행 실패·Backoff
Publisher B: v2 Claim 후 ACK 성공
Kafka: CouponCancelled(v2) → CouponIssued(v1)
```

`occurredAt`만으로는 Timestamp가 같을 수 있고 시계/정밀도가 다르며 도착 순서를 결정하지 못한다.

```sql
INSERT INTO user_coupon_view
  (coupon_issue_id, status, last_aggregate_version, last_event_at)
VALUES (:couponIssueId, :status, :aggregateVersion, :occurredAt)
ON CONFLICT (coupon_issue_id) DO UPDATE
SET status=EXCLUDED.status,
    last_aggregate_version=EXCLUDED.last_aggregate_version,
    last_event_at=EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version < EXCLUDED.last_aggregate_version;
```

v2 취소가 먼저 오면 최종 MyPage는 취소 상태이고, 나중 v1 발급은 0행 UPDATE로 무시한다.

| Consumer | 낮은 Version 생략 | 이유 |
| --- | --- | --- |
| 최신 상태 MyPage | 가능 | 더 큰 버전이 최신 상태를 대표한다. |
| Analytics | 보통 불가 | 각 사실을 집계해야 하므로 event ID 멱등과 이벤트 유형별 설계가 필요하다. |
| Notification | 보통 불가 | 발급·취소 알림은 별도 의미가 있어 순서 조정/업무 규칙이 필요하다. |

```text
aggregateVersion은 이벤트 순서 역전을 자동으로 해결하는 값이 아니다.
aggregateVersion은 같은 Aggregate에서 발생한 상태 변경의 순서를 식별하기 위한 값이다.
최신 상태 Projection에서는 낮은 버전이 최신 상태를 덮어쓰는 것을 방지할 수 있다.
모든 상태 전이를 순서대로 처리해야 하는 Consumer는 추가로 Aggregate 단위 직렬화·버퍼링/재처리 설계가 필요하다.
```

## 과제 9. 운영 지표와 보관

| 지표 | 의미 | 장애 신호 |
| --- | --- | --- |
| PENDING 수 | 미발행 적체 | 지속 증가 |
| 최장 PENDING 대기 | 가장 늦은 발행 지연 | SLO 초과 |
| PROCESSING 수 | 발행 중 작업 | 장시간 유지 |
| 만료 PROCESSING 수 | Publisher/Lease 문제 | 반복 발생 |
| attempt_count | 이벤트별 실패 횟수 | 특정 이벤트 지속 증가 |
| 생성 처리량 | DB가 만드는 속도 | 발행 속도보다 지속 큼 |
| Kafka 발행 처리량 | Publisher 배출 속도 | 급감/0 |
| DB→ACK 시간 | 종단 발행 지연 | 평소 대비 급증 |

초당 생성 2,000건, 발행 1,500건이면 매초 500건, 1분 뒤 30,000건, 10분 뒤 300,000건이 적체된다. 먼저 PENDING 증가율·최장 대기를 보고 Publisher 확장, Batch/처리량 조정, Kafka 장애 점검을 한다.

즉시 알람: `deduplication_key` UNIQUE 위반, Commit된 `request=PROCESSING`, PENDING 지속 증가, Lease 만료 반복, 같은 이벤트 attempts 급증. `PENDING`/`PROCESSING`을 삭제하면 아직 발행되지 않았거나 소유 중인 이벤트를 영구 유실한다. PUBLISHED는 발행 이력·장애 조사 때문에 일정 기간 보관한다.

대량 DELETE는 긴 트랜잭션, DB 부하와 Lock, Table Bloat를 만든다. `PUBLISHED AND published_at < cutoff`을 1,000건씩 삭제하고 Commit·짧은 대기·반복한다.

| 보관 대상 | 목적 | 너무 짧을 때 |
| --- | --- | --- |
| PUBLISHED Outbox | 발행 이력/조사 | 장애 조사·재발행 판단 어려움 |
| Kafka Record | Consumer 재처리 | Offset 되감기 불가 |
| processed_event | 중복 방어 | 오래된 Record 재전달 시 중복 반영 |

`last_error`에는 짧고 검색 가능한 오류 분류만 저장한다. 전체 Stack Trace와 민감정보는 DB 노출·용량 증가·검색 저하 위험이 있으므로 로그/트레이싱 시스템에 둔다.

| 문제 위치 | 문제·장애 | 수정 |
| --- | --- | --- |
| `issueCoupon`의 `kafkaTemplate.send` | DB와 Kafka 직접 Dual Write, Commit 경계에서 유실/거짓 이벤트 | 같은 DB 트랜잭션에 Outbox INSERT |
| `issueCoupon` 전체 | 발급 결과와 Outbox 원자적 저장 자체가 없음 | request·수량·issue·Outbox를 단일 DB 트랜잭션으로 |

| `@Transactional publishOutbox` | DB 트랜잭션 안에서 Kafka 호출, 긴 Lock | Claim Commit 후 트랜잭션 밖에서 ACK 대기 |
| `send` 직후 `markPublished` | ACK 전 PUBLISHED라 실제 미발행 유실 가능 | Future ACK 뒤 token 조건 UPDATE |
| Publisher 구현 | Claim Token·Lease 없음, 느린 옛 작업이 새 소유권 덮음 | token/lease와 조건부 UPDATE |
| `updateAllProcessingToPending` | 아직 정상 처리 중인 행까지 회수 | `lease_until < now()`만 회수 |
| `createPayloadFromCurrentCouponIssue` | 현재 데이터가 과거 이벤트 Snapshot을 변경 | Outbox의 저장된 payload 그대로 발행 |
| `onResult`의 partition/offset | 재발행시 다른 Offset이라 중복 방어 실패 | `eventMessageId` 사용 |
| `onResult` 저장 순서 | view와 processed_event가 원자적이지 않고 view가 먼저 중복 반영 | 같은 DB 트랜잭션에서 processed_event 선삽입 후 최초일 때만 view 변경 |

```text
Coupon Issue Consumer
  → [PostgreSQL Transaction: request·수량·coupon_issue·outbox_event INSERT] → Commit
  → 원본 Offset Commit

Outbox Publisher
  → [Claim Transaction: PENDING → PROCESSING, token·lease]
  → Kafka 발행 및 ACK
  → [성공 PUBLISHED / 실패 PENDING+backoff Transaction]

Kafka Result Consumer
  → [Consumer DB Transaction: processed_event + Consumer Business Table]
  → Consumer Offset Commit
```

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록 원자성 | 보장 | 같은 로컬 DB 트랜잭션이다. |
| Kafka Record 물리적 Exactly-Once | 보장하지 않음 | ACK 후 상태 기록 전 장애 시 재발행된다. |
| Publisher 복구 후 재발행 | 조건부 보장 | Publisher·Kafka 복구와 재시도 운영이 필요하다. |
| 비즈니스 순서대로 전달 | 보장하지 않음 | 병렬 Claim·Backoff로 역전 가능하다. |
| Consumer 중복 반영 방지 | 조건부 보장 | processed_event를 Consumer 변경과 원자적으로 저장해야 한다. |
| 모든 Consumer Group 처리 완료 | 보장하지 않음 | 각 Group이 독립적으로 Offset·장애를 관리한다. |
| 외부 SMS Exactly-Once | 보장하지 않음 | 외부 API에는 별도 Outbox/Idempotency가 필요하다. |

## 문항별 보완 답변

아래 내용은 앞의 압축 답변에서 생략되기 쉬운 **장애 지점, 판단 분기, 복구 기준**을 문항 번호에 맞춰 명시한 것이다.

### 과제 3-1. 요청 처리 권한과 비즈니스 실패 분기

`PENDING → PROCESSING`은 같은 트랜잭션 안의 중간 상태이므로, Commit된 `PROCESSING`이 관측되면 안 된다. 처리 권한 UPDATE가 0행이면 먼저 해당 `requestId`를 조회한다.

```text
ISSUED: 이미 성공한 원본 메시지의 재전달이므로 성공으로 종료한다.
FAILED: 이미 확정된 비즈니스 실패이므로 재발급하지 않고 종료한다.
PENDING: 경합/상태 전이 이상을 재시도 또는 오류로 처리한다.
PROCESSING: 같은 트랜잭션 내부에서만 보여야 한다. Commit된 값이면 알람 대상이다.
```

수량 UPDATE가 0행이면 `coupon_event` 존재 여부를 조회한다. 행이 없으면 `INVALID_EVENT`, 행은 있지만 `issued_count >= total_count`이면 `SOLD_OUT`이다. 사용자별 UNIQUE 제약의 `coupon_issue` INSERT가 충돌하면 `DUPLICATE_USER`로 확정한다. 이들 **최종 비즈니스 실패**는 `request=FAILED`로 저장하고 성공 이벤트 Outbox는 만들지 않는다. DB timeout/deadlock은 최종 실패로 확정하지 않고 Rollback하여 원본 Kafka 메시지 재처리 대상으로 남긴다.

### 과제 4-1. 단순 SELECT의 실제 경쟁 조건

```text
Publisher A                              Publisher B
-----------------------------------------------------------------
SELECT PENDING event-1
                                         SELECT PENDING event-1
UPDATE event-1 → PROCESSING
                                         UPDATE event-1 → PROCESSING
Kafka event-1 발행
                                         Kafka event-1 발행
```

두 인스턴스가 읽기와 상태 변경 사이에 서로를 막지 못하므로, 둘 다 같은 이벤트를 발행한다. `FOR UPDATE SKIP LOCKED`는 후보 행을 잠근 상태에서 Claim 상태 전이를 수행해 이 경합을 막는다. `SKIP LOCKED`는 잠긴 행을 기다리지 않아 처리량은 높이지만, DB 생성 순서대로 발행한다는 보장은 포기한다.

### 과제 5-5. Timeout 이후의 명시적 상태 전이

```text
Outbox 상태: PROCESSING → PENDING
재시도 여부: 예. next_attempt_at에 Backoff + Jitter를 적용해 재시도한다.
Kafka 중복 가능성: 있음. Broker 저장 성공 후 ACK만 유실되었을 수 있다.
Consumer에게 필요한 방어: subscriber_id + eventMessageId 기반 processed_event 멱등 처리.
```

`last_error`에는 예를 들어 `KAFKA_TIMEOUT`처럼 짧은 분류와 안전한 메시지만 저장한다. 재시도 횟수 상한을 넘는 행은 자동 삭제하지 않고, 운영 알람·조사·수동 복구 대상에 둔다.

### 과제 6. 장애 시나리오별 상세 상태

#### 1. 발급 트랜잭션 Commit 전 장애

| 항목 | 결과 |
| --- | --- |
| `coupon_issue` | Rollback되어 없음 |
| `request` | PENDING 유지 또는 트랜잭션 내 변경 Rollback |
| `outbox_event` | 없음 |
| Kafka Record | 없음 |
| 복구 방법 | 원본 `coupon.issue.requested`를 재전달·재처리 |

#### 2. 발급 DB Commit 후 원본 Offset Commit 전 장애

| 항목 | 결과 |
| --- | --- |
| `coupon_issue` | 존재 |
| `request` | `ISSUED` |
| `outbox_event` | `PENDING` 또는 Publisher가 이미 Claim한 상태 |
| 원본 Kafka 메시지 | Offset 미커밋이므로 재전달 가능 |
| 복구 방법 | `requestId`가 ISSUED임을 보고 발급·Outbox INSERT 없이 성공 종료 |

#### 3. Outbox Claim Commit 후 Kafka 발행 전 종료

| 항목 | 결과 |
| --- | --- |
| Outbox status | `PROCESSING`, token과 lease 존재 |
| Kafka Record | 없음 |
| 복구 조건 | `lease_until < now()` |
| 복구 주체 | 다음 Polling Publisher의 stale-lease 회수 작업 |
| 중복 가능성 | 이 지점만 보면 없음 |

#### 4. Kafka 발행 성공 후 PUBLISHED 변경 전 종료

| 항목 | 결과 |
| --- | --- |
| Outbox status | `PROCESSING` |
| Kafka Record | 존재할 수 있음(ACK를 받았거나 Broker 저장 뒤 종료) |
| 재발행 가능성 | Lease 회수 뒤 있음 |
| 필요한 Consumer 방어 | `processed_event`의 `eventMessageId` UNIQUE/PK |

#### 5~7. Lease 경쟁과 장기 Kafka 장애

Publisher A의 늦은 성공 UPDATE와 늦은 실패 UPDATE 모두 0행이어야 한다. 조건은 `event_id` 일치, `status='PROCESSING'`, `claim_token=token-A`다. B가 token-B로 재Claim했다면 이 조건이 성립하지 않는다.

Kafka가 30분 동안 장애면 PENDING 수와 가장 오래된 PENDING의 대기 시간이 계속 증가하고, 발행을 시도한 행의 `attempt_count`도 증가한다. 복구 후에는 각 `next_attempt_at`이 지난 행을 Claim하여 처리한다. PENDING 적체, 최장 대기 시간, 반복 실패, 만료 Lease를 알람한다. 실패 기간에 쿠폰을 재발급하지 않으며 Outbox 이벤트만 재전송한다.

### 과제 7-4. Consumer의 완전한 트랜잭션 예시

```sql
BEGIN;

WITH inserted AS (
  INSERT INTO processed_event (subscriber_id, event_id)
  VALUES ('mypage-coupon-projection', :eventMessageId)
  ON CONFLICT DO NOTHING
  RETURNING event_id
)
INSERT INTO user_coupon_view (
  user_id, coupon_issue_id, coupon_event_id, status,
  last_aggregate_version, last_event_at
)
SELECT :userId, :couponIssueId, :couponEventId, 'ISSUED',
       :aggregateVersion, :occurredAt
FROM inserted
ON CONFLICT (coupon_issue_id) DO UPDATE
SET status = EXCLUDED.status,
    last_aggregate_version = EXCLUDED.last_aggregate_version,
    last_event_at = EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version
      < EXCLUDED.last_aggregate_version;

COMMIT;
```

`inserted`가 비어 있으면 이미 같은 논리 이벤트를 처리한 것이므로 조회 모델을 건드리지 않는다. `processed_event`와 Projection 변경 중 하나라도 실패하면 같은 트랜잭션이 Rollback되므로, 처리 완료 표시만 남거나 조회 모델만 중복 반영되는 상태를 피한다.

### 과제 8-7. Consumer별 낮은 버전 처리의 판단 기준

Analytics가 “현재 발급 상태 수”만 유지하는 Projection이라면 버전 비교로 낮은 이벤트를 생략할 수 있다. 그러나 모든 발급/취소 사실을 각각 집계하는 분석이라면 낮은 버전이라는 이유만으로 버리면 집계가 틀어진다. Notification도 발급과 취소가 각각 반드시 알려져야 한다면 버전만으로 생략하지 말고, 이벤트별 멱등 Key와 업무상 순서/취소 규칙을 별도로 둬야 한다.

### 과제 9-6. PUBLISHED 정리의 Batch SQL 예시

```sql
WITH targets AS (
  SELECT event_id
  FROM outbox_event
  WHERE status = 'PUBLISHED'
    AND published_at < :cutoff
  ORDER BY published_at
  LIMIT 1000
)
DELETE FROM outbox_event
WHERE event_id IN (SELECT event_id FROM targets);
```

이 작업을 짧은 트랜잭션으로 Commit하고 잠시 쉬었다가 반복한다. PENDING·PROCESSING은 성공적으로 Kafka에 저장됐는지 확정되지 않았으므로 정리 대상이 아니다.

### 과제 10-2. 필수 검토 항목 대조표

| 검토 항목 | 문제가 발생하는 코드 | 수정 방향 |
| --- | --- | --- |
| 발급 트랜잭션에서 Kafka 직접 호출 | `issueCoupon()`의 `kafkaTemplate.send()` | DB 트랜잭션에는 Outbox INSERT만 수행 |
| 발급 결과와 Outbox의 원자적 저장 없음 | `issueCoupon()` 전체 | 수량·issue·request·Outbox를 한 로컬 DB 트랜잭션으로 |
| 여러 Publisher의 동시 Claim 방어 없음 | `findTop100ByStatus("PENDING")` | `FOR UPDATE SKIP LOCKED` Claim |
| DB 트랜잭션 안 Kafka 발행 | `@Transactional publishOutbox()` | Claim Commit 후 트랜잭션 밖에서 ACK 대기 |
| ACK 확인 전 PUBLISHED 변경 | `send()` 뒤 `event.markPublished()` | Future ACK 성공 뒤 조건부 PUBLISHED UPDATE |
| Claim Token 없음 | `publishOutbox()` | UUID claim_token을 저장하고 UPDATE 조건에 포함 |
| Lease 만료 조건 없이 PROCESSING 회수 | `updateAllProcessingToPending()` | 만료된 `lease_until` 행만 회수 |
| 현재 테이블에서 Payload 재생성 | `createPayloadFromCurrentCouponIssue(event)` | INSERT 시 저장한 불변 `payload` 사용 |
| Kafka Offset을 멱등 Key로 사용 | `ProcessedEvent(partition, offset)` | `subscriber_id + eventMessageId` PK |
| processed_event와 비즈니스 변경 원자성 부족 | `onResult()`의 두 save | 하나의 Consumer DB 트랜잭션에서 중복표시 후 Projection 변경 |
