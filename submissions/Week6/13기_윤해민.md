# **6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성**

## **1. 과제 목표**

이번 과제의 목표는 **쿠폰 발급 결과를 PostgreSQL에 저장하는 작업과 `CouponIssued` 이벤트를 Kafka에 발행하는 작업 사이의 Dual Write 문제를 분석하고, Transactional Outbox Pattern으로 복구 가능한 이벤트 발행 구조를 설계하는 것**이다.

5주차까지 쿠폰 발급 Consumer는 다음 작업을 하나의 DB 트랜잭션으로 처리했다.

```
coupon_issue_request PENDING → PROCESSING

coupon_event.issued_count 증가

coupon_issue 발급 기록 저장

coupon_issue_request → ISSUED
```

DB 트랜잭션이 Commit된 시점을 최종 쿠폰 발급 성공으로 본다.

하지만 발급 결과를 Notification, MyPage, Analytics 같은 후속 서비스에 전달하려면 별도의 결과 이벤트가 필요하다.

```
PostgreSQL
→ 쿠폰 발급 결과 저장

Kafka
→ CouponIssued 이벤트 발행
```

PostgreSQL과 Kafka는 서로 다른 시스템이다.

하나의 메서드 안에서 두 작업을 호출하거나 DB 메서드에 `@Transactional`을 붙이는 것만으로는 두 시스템이 하나의 원자적 트랜잭션이 되지 않는다.

이번 과제에서는 다음 구조를 설계한다.

```
Coupon Issue Consumer
        ↓
+------------------------------------------+
| PostgreSQL Transaction                   |
|------------------------------------------|
| coupon_issue 저장                        |
| request ISSUED 변경                      |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        ↓ Commit
Outbox Publisher
        ↓
Kafka coupon.issued
        ↓
Result Consumer
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
PostgreSQL과 Kafka 사이의 Dual Write 문제

DB First와 Kafka First가 각각 실패하는 이유

AFTER_COMMIT만으로 이벤트 유실을 막을 수 없는 이유

비즈니스 결과와 Outbox를 같은 트랜잭션에 저장하는 이유

Outbox 이벤트 Envelope와 테이블 설계

PENDING / PROCESSING / PUBLISHED 상태의 의미

FOR UPDATE SKIP LOCKED를 이용한 동시 Claim

Claim Token과 Lease가 필요한 이유

Kafka ACK와 메서드 호출 성공의 차이

Timeout과 재시도에서 발생하는 중복 발행

At-Least-Once Publication과 Consumer 멱등 처리

eventMessageId와 Kafka Offset의 차이

Partition Key와 이벤트 순서 보장의 차이

aggregateVersion의 역할과 적용 범위

Outbox 적체를 감지하기 위한 운영 지표
```

이번 과제의 핵심은 다음과 같다.

```
Outbox는 Kafka Record를 정확히 한 번 생성하는 패턴이 아니다.

Outbox는 DB 결과가 Commit되었을 때
발행할 이벤트 기록도 같은 DB에 반드시 남도록 만드는 패턴이다.

Publisher는 남아 있는 이벤트를 재시도할 수 있다.

재시도로 중복 발행이 발생할 수 있으므로
Consumer도 멱등하게 처리해야 한다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
쿠폰 발급 비즈니스 데이터와 Outbox는
같은 PostgreSQL Database에 저장한다.

coupon_issue_request,
coupon_event,
coupon_issue,
outbox_event는
필요한 경우 하나의 로컬 DB 트랜잭션에 포함할 수 있다.

원본 coupon.issue.requested 메시지는
5주차의 requestId 기반 멱등 처리로 중복을 방어한다.

자동 Offset Commit은 사용하지 않는다.

원본 Consumer는 발급 DB 트랜잭션이 Commit된 뒤에만
처리 완료로 간주한다.

Spring Kafka의 실제 Offset Commit 시점은
설정한 AckMode와 Error Handler 정책에 맞게 구성한다.

Outbox Publisher는 Polling 방식으로 구현한다.

이번 주차의 기본 Publisher는
작은 Batch를 순차 동기 방식으로 발행한다.

Kafka 발행은 Claim 트랜잭션 밖에서 수행한다.

Publisher는 Kafka Broker ACK를 확인한 뒤
Outbox를 PUBLISHED로 변경한다.

Publisher는 같은 Outbox 이벤트를
두 번 이상 Kafka에 발행할 수 있다.

Consumer는 eventMessageId를 기준으로
중복 비즈니스 반영을 방어한다.
```

이번 과제의 Outbox가 직접 해결하는 범위는 다음과 같다.

```
PostgreSQL에 확정되는 쿠폰 발급 성공

+

후속 서비스에 전달할 CouponIssued 발행 의도
```

다음 구간은 이번 Outbox가 자동으로 원자화하지 않는다.

```
Redis 선착순 판정
↔ 최초 coupon.issue.requested Kafka 발행

원본 coupon.issue.requested Kafka 소비
↔ PostgreSQL 발급 트랜잭션

Result Consumer의 로컬 DB 저장
↔ 이메일·SMS 같은 외부 API 호출
```

이번 과제에서는 아래 내용의 상세 구현은 다루지 않는다.

```
Kafka Transaction을 이용한 전체 구조

XA 또는 2PC

Debezium Connector 실제 설치

최대 재시도 이후 DLQ 운영

영구 실패 이벤트의 운영자 재처리 UI

Redis와 PostgreSQL의 보정 배치 상세 구현
```

# **5. 필수 과제**

---

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
PostgreSQL (coupon_event, coupon_issue, coupon_issue_request가 저장되는 관계형 DB)

Kafka Broker (coupon.issued 토픽으로 이벤트가 전달되는 메시지 브로커)
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
@Transactional은 Spring이 관리하는 PlatformTransactionManager, 즉 PostgreSQL과 연결된
DataSourceTransactionManager의 Commit/Rollback 범위 안에서만 원자성을 보장한다.

kafkaTemplate.send()는 이 트랜잭션 매니저가 관리하지 않는 별도의 외부 클라이언트(Kafka
Producer)를 통해 Kafka Broker와 통신하는 호출이다. DB와 Kafka는 서로 다른 커밋 프로토콜을
가진 완전히 독립된 시스템이므로, 하나의 메서드 안에서 순서대로 호출한다고 해서 두 시스템이
하나의 분산 트랜잭션으로 묶이지 않는다.

따라서 다음 두 상황이 모두 가능하다.

DB 트랜잭션이 Rollback되어도
→ 이미 Broker에 전송된 Kafka 메시지는 자동으로 취소되지 않는다.

Kafka 발행이 실패하거나 예외를 던져도
→ 이미 진행된 DB 작업이 자동으로 Rollback되지 않는다.
   (실제로는 코드 순서상 kafkaTemplate.send()가 메서드의 마지막 줄이므로,
    send()가 예외를 던지면 그제서야 @Transactional이 DB 쪽을 Rollback할 수는 있지만,
    이는 "동시에 원자적으로 묶인 것"이 아니라 예외 전파에 의존한 우연한 결과일 뿐이며
    send()가 비동기로 실패를 늦게 통지하면 이마저도 동작하지 않는다.)
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[장애 지점: Kafka 발행 호출 전, 또는 발행 도중 프로세스 종료/네트워크 장애]
    ↓
Kafka 발행

최종 DB 상태:
쿠폰 발급 완료 (issued_count 증가, coupon_issue 저장, request ISSUED로 Commit됨)

최종 Kafka 상태:
CouponIssued 이벤트 없음

후속 서비스에 미치는 영향:
Notification/MyPage/Analytics Consumer가 발급 사실 자체를 알 수 없다.
사용자는 실제로 쿠폰을 받았지만 알림을 받지 못하고, 마이페이지에 쿠폰이 보이지 않으며,
통계에도 반영되지 않는다.

복구에 필요한 정보:
"이미 발급은 확정됐지만 아직 이벤트를 발행하지 못한 건"이 무엇인지 DB에 남아 있는 기록이
필요하다. 이 코드처럼 발행 정보가 메모리(호출 스택)에만 있다면 프로세스가 재시작된 뒤
어떤 발급 건이 이벤트를 놓쳤는지 판단할 근거가 없다. (→ Outbox가 이 근거를 DB에 남겨준다)
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점: Kafka 발행 성공 이후 DB 트랜잭션 Commit 전 실패/Rollback]
    ↓
DB Commit

최종 DB 상태:
쿠폰 발급 기록 없음 (issued_count 증가 안 됨, coupon_issue 없음, request도 ISSUED로
확정되지 않음)

최종 Kafka 상태:
CouponIssued 이벤트가 이미 Broker에 존재함

후속 서비스에 미치는 영향:
후속 Consumer들이 "실제로는 발급되지 않은" 결과를 실제 발급으로 처리한다. 사용자는
쿠폰을 받지 못했는데 발급 알림을 받고, MyPage에는 존재하지 않는 쿠폰이 조회 모델에
반영되는 심각한 정합성 오류가 발생한다. 이 오류는 DB 기준 발급 수량과도 어긋난다.
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료
KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료
```

```
AFTER_COMMIT 방식은 "DB Commit 전에 이벤트가 먼저 발행되는" 문제(4번 시나리오)는
막아준다. 하지만 다음 두 장애 구간은 여전히 남는다.

(1) DB Commit 후 Listener 실행 전 프로세스 종료
    DB Commit은 이미 완료되어 되돌릴 수 없는데, TransactionalEventListener 자체가
    실행되지 못하면 Kafka 발행 시도조차 이루어지지 않는다. 이 이벤트 객체는 JVM
    메모리 안에만 존재했으므로 프로세스가 재시작되면 "무엇을 발행해야 했는지" 정보가
    완전히 사라진다.

(2) send() 호출 후 Broker ACK 확인 전 프로세스 종료
    KafkaTemplate.send()는 CompletableFuture를 즉시 반환하는 비동기 호출이며,
    send() 호출 자체가 Broker에 실제로 저장됐다는 뜻이 아니다. ACK를 기다리는 도중
    프로세스가 종료되면 Kafka에 실제로 전달됐는지 알 수 없고, DB는 이미 Commit된
    상태라 재시도할 근거(발행 대상 목록)도 남지 않는다.

두 장애의 공통 원인은 같다.

발행해야 할 이벤트 정보가 DB가 아니라 메모리에만 존재한다.
→ 프로세스가 종료되면 "무엇을 다시 보내야 하는가"를 판단할 기준 자체가 사라진다.

Outbox Pattern은 이 발행 의도를 메모리가 아니라 비즈니스 데이터와 같은 트랜잭션의
DB 테이블(outbox_event)에 저장함으로써, 프로세스가 언제 죽더라도 "아직 발행 안 된
이벤트 목록"을 DB에서 다시 조회할 수 있게 만든다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | O 해결됨 | 발급 결과(coupon_issue, request ISSUED)와 outbox_event INSERT를 같은 로컬 DB 트랜잭션에 묶으므로, 발급이 Commit되면 발행 의도도 반드시 함께 Commit되고 발급이 Rollback되면 발행 의도도 함께 Rollback된다. |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | X 해결 안 됨 | Redis와 PostgreSQL은 서로 다른 저장소이며, 하나의 PostgreSQL 로컬 트랜잭션에 함께 포함될 수 없다. 이번 과제의 Outbox 적용 범위는 "발급 성공 확정 이후" 구간으로 한정되어 있어 최초 요청 발행 구간은 다루지 않는다. |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | X 해결 안 됨 (다른 메커니즘으로 방어) | Outbox가 원자화하는 대상이 아니다. 이 구간의 재전달 문제는 5주차에서 만든 requestId 기반 멱등 처리(요청 상태 조건부 UPDATE)가 방어한다. |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | X 해결 안 됨 | 외부 API 호출은 로컬 PostgreSQL 트랜잭션에 포함될 수 없는 별도의 Dual Write이다. Notification Service 자체의 내부 Outbox, 외부 Provider의 Idempotency Key 등 별도 설계가 필요하다. |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것:
DB에서 비즈니스 결과(쿠폰 발급)가 Commit되면, 발행해야 할 이벤트 기록도 반드시 같은
트랜잭션 안에서 함께 DB에 남는다. 즉 "발급 결과는 Commit됐는데 발행할 이벤트 기록이
어디에도 존재하지 않는 상태"는 발생하지 않는다.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record가 물리적으로 정확히 한 번만 생성되는 것(At-Least-Once일 뿐), 이벤트가
비즈니스 발생 순서대로 전달되는 것, 모든 후속 Consumer가 처리를 완료하는 것, 외부
알림(SMS 등)이 정확히 한 번 전송되는 것.
```

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt:
쿠폰 발급이라는 비즈니스 결과가 실제로 발생(확정)한 시각. 발급 DB 트랜잭션에서
issued_at과 같은 기준 시각으로 정해지며, Outbox INSERT 시점에 Payload에 고정된다.

publishedAt:
Outbox Publisher가 Kafka Broker의 ACK를 확인한 뒤, 그 결과를 outbox_event.published_at
컬럼에 기록하는 시각. "언제 실제로 Kafka 전송에 성공했는가"를 나타내는 값이다.

Publisher 재시도 시 변경하면 안 되는 값:
occurredAt과 payload 전체(불변 Snapshot). Publisher가 몇 번을 재시도하든 이벤트가
나타내는 사실(무엇이 언제 발생했는가)은 달라지지 않아야 하므로 절대 건드리지 않는다.
바뀌는 것은 published_at, attempt_count, next_attempt_at 같은 발행 진행 상태뿐이다.
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
Outbox INSERT 이후 실제 Kafka 발행까지는 Polling 주기, 재시도 Backoff 등으로 인해
시간 간격이 생길 수 있다. 그 사이에 원본 비즈니스 데이터(coupon_issue 등)가 다른
트랜잭션에 의해 변경되거나 취소될 수 있다.

Publisher가 발행 시점에 현재 테이블을 다시 조회해서 Payload를 만들면, 이벤트가
나타내야 하는 "그 당시 발생한 사실"이 아니라 "현재 시점의 상태"가 섞여 들어가게
된다. 예를 들어 발급 직후 바로 취소된 케이스에서 재조회하면, CouponIssued
이벤트인데 실제로는 취소된 상태의 데이터가 담기는 모순이 생길 수 있다.

따라서 Outbox INSERT 시점에 발행할 Payload를 이미 완성된 형태(불변 Snapshot)로
저장해두고, Publisher는 저장된 값을 그대로 Kafka에 전달하기만 해야 한다. Publisher는
비즈니스 데이터를 다시 조회하거나 재구성하는 책임을 갖지 않는다.
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    -- 도메인 추적용, 필수 아님 (10-2 참고)
    request_id UUID,

    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),

    CONSTRAINT chk_outbox_schema_version
        CHECK (schema_version >= 1),

    CONSTRAINT chk_outbox_aggregate_version
        CHECK (aggregate_version >= 1),

    CONSTRAINT chk_outbox_attempt_count
        CHECK (attempt_count >= 0)
);
```

### **7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다**

```
outbox_event.event_id
=
payload.eventMessageId
```

```
가장 기본적인 보장 방법은 애플리케이션 코드에서 하나의 UUID를 먼저 생성한 뒤, 그
값을 event_id 컬럼과 payload.eventMessageId 필드 양쪽에 동일하게 채워 넣는
것이다. 즉 두 값을 독립적으로 만들지 않고 "하나의 값을 두 곳에 쓰는" 방식으로
애초에 불일치가 발생할 수 없게 만든다.

여기에 더해 DB 차원에서 이중 방어를 걸 수도 있다. PostgreSQL의 JSONB 연산자를
이용해 CHECK 제약으로 강제하는 것이다.

ALTER TABLE outbox_event
ADD CONSTRAINT chk_outbox_event_id_matches_payload
CHECK (payload ->> 'eventMessageId' = event_id::text);

이렇게 하면 애플리케이션 버그로 두 값이 어긋난 채로 INSERT를 시도하더라도 DB가
즉시 거부하므로, 불변조건이 깨진 행이 저장되는 것을 막을 수 있다.
```

### **8. `deduplication_key`를 설계한다**

`CouponIssued`는 하나의 `couponIssueId`에 대해 한 번만 발생한다고 가정한다.

```
Key 형식:
{eventType}:{aggregateType}:{aggregateId}

예시:
COUPON_ISSUED:COUPON_ISSUE:5001
```

같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면 어떤 값을 추가해야 하는지도 작성한다.

```
CouponIssued는 하나의 couponIssueId당 정확히 한 번만 발생하므로 위 형식만으로
충분하다. 하지만 예를 들어 CouponUsed처럼 같은 couponIssueId에서 여러 번 발생할
수 있는 이벤트라면, aggregate 기준만으로는 서로 다른 발생 건을 구분할 수 없다.

이 경우 발생 시점이나 순서를 나타내는 추가 구분자를 Key에 포함해야 한다.

{eventType}:{aggregateType}:{aggregateId}:{aggregateVersion}

예: COUPON_USED:COUPON_ISSUE:5001:3

aggregateVersion처럼 같은 Aggregate 안에서 단조 증가하는 값을 추가하면, "같은
상태 변경"에 대한 중복 Outbox 생성만 막고 서로 다른 시점의 정상적인 재사용
이벤트는 막지 않을 수 있다.
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

다음 선택지를 비교한다.

```
전체 Rollback 후 새 트랜잭션에서 조회

Savepoint 사용

ON CONFLICT DO NOTHING RETURNING 후
기존 행 조회·동일성 비교
```

```
전체 Rollback 후 새 트랜잭션에서 조회
→ 가장 단순하고 안전하다. UNIQUE 위반이 발생하면 발급 트랜잭션 전체(수량 증가,
  coupon_issue 저장, request ISSUED 변경 포함)를 Rollback하고, 별도의 새 트랜잭션을
  열어 원인을 조사한다. 이번 과제 설계에서는 이 위반 자체가 "정상 경로에서 발생하면
  안 되는 이상 상황"(10-4)이라고 전제하므로, 조용히 넘기지 않고 전체를 Rollback한
  뒤 경고 로그와 알람을 발생시키는 이 방식을 기본으로 채택한다.

Savepoint 사용
→ SAVEPOINT를 잡고 Outbox INSERT를 시도한 뒤, 실패하면 그 지점까지만
  ROLLBACK TO SAVEPOINT로 되돌리고 나머지 트랜잭션(발급 결과)은 그대로 Commit할
  수 있다. 하지만 이는 "왜 충돌했는지 모른 채로 발급만 확정하고 이벤트 발행은
  포기"하는 것과 같아서, 요청 상태 관리 결함이나 Key 생성 버그를 숨긴 채 발급
  결과와 Outbox 기록이 어긋나는 상태(발급은 됐는데 발행 의도가 없는 상태)를 만들
  수 있다. 이번 설계의 "발급 결과와 Outbox는 항상 함께 Commit/Rollback되어야
  한다"는 원칙과 충돌하므로 채택하지 않는다.

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교
→ 충돌 시 예외 없이 조용히 넘어가고, RETURNING된 행이 없으면 기존 행을 다시
  조회해 request_id, aggregate_id, event_type, schema_version, aggregate_version,
  payload가 모두 같은지 비교한다. 모두 같으면 같은 이벤트의 재시도로 판단해 기존
  행을 재사용하는 멱등 INSERT로 설계할 수 있다. 다만 이번 과제에서는 이 위반이
  "동일 이벤트의 정상적인 재시도"가 아니라 설계 가정이 깨진 신호로 다루기로
  했으므로, ON CONFLICT DO NOTHING으로 조용히 넘기지 않고 위의 Rollback+알람
  방식을 기본으로 사용한다. 멱등 INSERT가 필요한 별도 상황이 생긴다면 이 방식을
  채택할 수 있다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';

-- affected rows가 몇 행이어야 하는가? -> 반드시 1행. 0행이면 아래 5번 문항의
-- 분기(이미 ISSUED/FAILED/PROCESSING/요청 없음)로 판단하고 계속 진행하지 않는다.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;

-- affected rows가 0일 때 가능한 원인은 무엇인가? -> 실제로 수량이 소진되었거나
-- (SOLD_OUT), 조건에 이벤트 상태·기간까지 포함했다면 이벤트가 종료/비활성화된
-- 경우도 포함될 수 있다. 이 경우 발급을 중단하고 request를 FAILED로 확정한다.

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
) VALUES (
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1행 | 0행이면 기존 request 상태를 재조회한다. ISSUED/FAILED면 재전달로 판단해 새 발급·새 Outbox 없이 정상 종료하고, PROCESSING이면 설계 가정 위반으로 알람 후 재처리 대상으로 남긴다. 요청 자체가 없으면 등록 불일치로 분류한다. |
| issued_count 조건부 증가 | 1행 | 0행이면 수량 소진(SOLD_OUT) 또는 이벤트 비활성/종료로 판단. request를 FAILED/SOLD_OUT으로 확정하고 CouponIssued Outbox는 저장하지 않는다. |
| coupon_issue INSERT | 1행 | UNIQUE(event_id, user_id) 위반이면 전체 트랜잭션 Rollback 후, 별도 트랜잭션에서 기존 발급 기록을 확인해 request를 FAILED/DUPLICATE_USER로 확정한다(11-3). |
| PROCESSING → ISSUED | 1행 | 0행이면 앞 단계들과 상태가 어긋난 것이므로 예상한 결과가 아니라고 보고 전체 트랜잭션을 Rollback한다. |
| outbox_event INSERT | 1행 | 0행/UNIQUE 위반이면 전체 트랜잭션을 Rollback하고 경고 로그와 알람을 발생시킨다(정상 경로에서는 발생하면 안 되는 위반이므로 ON CONFLICT DO NOTHING으로 조용히 넘기지 않는다). |

### **3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다**

장애 직전 상황은 다음과 같다.

```
issued_count 증가 성공

coupon_issue INSERT 성공

request ISSUED 변경 성공

outbox_event INSERT 실패
```

```
트랜잭션 결과:
전체 Rollback

coupon_event.issued_count:
증가하지 않은 원래 값으로 되돌아감

coupon_issue:
저장되지 않음 (Insert 취소)

coupon_issue_request:
ISSUED로 변경되지 않고 PENDING으로 되돌아감 (트랜잭션 시작 전 상태)

outbox_event:
존재하지 않음

→ 원본 coupon.issue.requested 메시지는 아직 Offset Commit 전이므로 재전달되고,
  재전달된 Consumer가 위 5단계 트랜잭션을 처음부터 다시 시도한다.
```

### **4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다**

```
Outbox 저장 실패를 무시하고 발급 결과(issued_count, coupon_issue, request ISSUED)만
Commit해버리면, "DB에는 쿠폰 발급이 확정되었는데 발행할 이벤트 기록은 어디에도
남지 않은 상태"가 만들어진다. 이는 이번 과제 전체가 없애려는 바로 그 상태다
(과제 1-7 참고).

이 상태가 되면 requestId 기반 멱등 처리가 오히려 복구를 막는다. request가 이미
ISSUED이므로 원본 메시지가 재전달되어도 5번 문항처럼 "새 발급과 새 Outbox 없이
정상 종료"되어 버린다. 즉 발급은 됐지만 CouponIssued 이벤트를 영원히 발행할 기회를
잃게 되고, Notification/MyPage/Analytics는 이 발급 사실을 끝까지 알 수 없다.

따라서 5개 작업(권한 획득, 수량 확보, 발급 저장, 요청 확정, Outbox 저장)은
"모두 성공하거나 모두 실패"해야 하며, 그중 하나라도 실패하면 전체를 Rollback해서
원본 메시지가 재전달될 때 처음부터 다시 시도할 수 있게 만들어야 한다.
```

### **5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다**

```
issued_count를 다시 증가시키는가?
아니오. 이미 확정된 발급 건을 다시 카운트하면 실제 발급 수량보다 issued_count가
더 커져서 수량 초과가 발생한다.

coupon_issue를 다시 생성하는가?
아니오. UNIQUE(event_id, user_id) 제약이 이를 막아주지만, 그 이전에 애플리케이션
로직 자체가 request = ISSUED를 확인한 시점에서 발급 로직을 실행하지 않아야 한다.

Outbox를 다시 INSERT하는가?
아니오. 이미 첫 처리에서 CouponIssued Outbox가 저장되었으므로 다시 INSERT하면
deduplication_key UNIQUE 위반이 발생한다(정상적으로는 이 지점에 도달하지 않아야
한다 — 아래 참고).

Consumer 처리는 성공으로 종료할 수 있는가?
예. request = ISSUED를 관측하면 "이미 완료된 요청의 재전달"로 판단하고, 새로운
DB 변경이나 Outbox INSERT 없이 그대로 정상 처리로 종료한 뒤 원본 Kafka Offset을
Commit한다. 즉 첫 번째 UPDATE(PENDING → PROCESSING)가 0행이 되는 시점에서 이미
분기되어 2~5번 SQL 자체가 실행되지 않으므로, Outbox 재INSERT 시도까지 가지 않는
것이 정상 경로다.
```

### **6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다**

```
DB 상태:
request = ISSUED, coupon_issue 존재, issued_count 반영 완료 (모두 정상 Commit됨)

Outbox 상태:
outbox_event가 PENDING 상태로 존재 (아직 Publisher가 발행하지 않음)

Kafka 원본 메시지:
Offset이 아직 반영되지 않았으므로 coupon.issue.requested 원본 메시지가 재전달될
수 있다.

재시작 후 필요한 멱등성 기준:
재전달된 Consumer는 Kafka Partition/Offset이 아니라 메시지에 담긴 requestId를
기준으로 기존 request 상태를 조회해야 한다. request = ISSUED를 확인하면 5번
문항과 동일하게 새로운 발급·Outbox 처리 없이 정상 종료 후 Offset을 Commit한다.
이 재전달 자체는 Outbox가 막아주는 구간이 아니라, 5주차에서 만든 requestId 기반
멱등 처리가 방어하는 구간이다.
```

### **7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit

AckMode

Listener 예외 처리

Error Handler가 실패를 정상 처리로 바꾸는지 여부
```

```
enable.auto.commit
반드시 false로 설정해야 한다. true면 Kafka Consumer가 poll() 주기마다 자동으로
Offset을 Commit해버려서, 발급 DB 트랜잭션이 아직 Commit되지 않았거나 실패했는데도
Offset이 먼저 반영되어 메시지가 유실될 수 있다.

AckMode
Spring Kafka라면 AckMode.MANUAL 또는 MANUAL_IMMEDIATE로 설정해, 발급 DB
트랜잭션이 성공적으로 Commit된 뒤 Listener 코드에서 명시적으로 acknowledge()를
호출하도록 구성해야 한다. RECORD나 BATCH 같은 자동 커밋 계열 AckMode를 쓰면
DB 처리와 Offset Commit의 순서를 보장할 수 없다.

Listener 예외 처리
발급 트랜잭션 중 발생한 예외(DB Deadlock, Lock Timeout 등 일시적 기술 실패)는
Listener 밖으로 다시 던져서 Kafka의 재시도/에러 핸들링 정책으로 넘겨야 한다.
예외를 Listener 안에서 삼켜버리면 실제로는 발급이 실패했는데도 Offset이
Commit되어 메시지가 유실된다.

Error Handler가 실패를 정상 처리로 바꾸는지 여부
DefaultErrorHandler 등에 설정된 재시도 횟수를 넘긴 뒤 SeekToCurrentErrorHandler
류가 실패 레코드를 건너뛰고 Offset을 진행시키는 정책(DLQ로 이동 등)을 쓰는지
반드시 확인해야 한다. 이런 정책이 켜져 있으면 일시적 실패였던 메시지가 최종
실패로 취급되어 Offset이 넘어가버리고, 발급이 되지 않은 요청이 조용히 누락될
수 있다.
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                              Publisher B
------------------------------------------------------------------------
SELECT * FROM outbox_event
WHERE status = 'PENDING'
LIMIT 50
→ 이벤트 X 포함(아직 PENDING)

                                          SELECT * FROM outbox_event
                                          WHERE status = 'PENDING'
                                          LIMIT 50
                                          → 이벤트 X도 포함
                                            (A가 아직 UPDATE 전이라 여전히 PENDING)

UPDATE outbox_event
SET status='PROCESSING'
WHERE event_id = X
→ 성공 (1행)

                                          UPDATE outbox_event
                                          SET status='PROCESSING'
                                          WHERE event_id = X
                                          → WHERE에 status 조건이 없다면
                                            이미 PROCESSING인 행도 그대로
                                            다시 UPDATE되어 "성공"으로 보임

Kafka 발행 시도                            Kafka 발행 시도
→ 이벤트 X가 두 Publisher에서            → 이벤트 X가 두 Publisher에서
  동시에 발행됨                              동시에 발행됨
------------------------------------------------------------------------
```

SELECT로 PENDING 행을 조회하는 시점과 UPDATE로 PROCESSING으로 바꾸는 시점 사이에
원자성이 없기 때문에, 두 Publisher가 같은 시점에 같은 이벤트를 "아직 아무도
가져가지 않은 PENDING 행"으로 동시에 인식하고 각자 Claim했다고 착각하는 경쟁이
발생한다.

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY
        next_attempt_at,
        created_at,
        event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until =
        CURRENT_TIMESTAMP
        + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id

RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1. DB Connection Pool 고갈
   Kafka ACK를 기다리는 동안 DB Connection을 계속 점유하게 되어, Connection Pool의
   가용 커넥션이 줄어든다. 다른 요청/트랜잭션이 커넥션을 얻지 못해 대기하거나
   타임아웃될 수 있다.

2. Row Lock 장시간 유지로 인한 대기 증가
   FOR UPDATE로 잠근 행의 Lock을 Kafka 응답이 올 때까지 계속 들고 있으면, 그
   행을 회수하려는 다른 Publisher나 관련 쿼리가 Lock 해제까지 대기해야 한다.
   Kafka가 느려질수록 대기 시간이 함께 늘어난다.

3. 트랜잭션 Timeout
   Kafka Broker 장애나 네트워크 지연으로 ACK 대기가 길어지면 DB 트랜잭션 자체가
   설정된 Timeout을 넘겨 강제로 종료될 수 있다. 이 경우 Claim 상태 변경까지
   함께 Rollback되어 오히려 처리가 더 꼬인다.

→ 따라서 "PENDING → PROCESSING" Claim은 짧은 트랜잭션으로 즉시 Commit하고, Kafka
  호출은 DB Lock/Connection을 전혀 점유하지 않는 상태에서 별도로 수행한 뒤,
  성공/실패 결과만 다시 짧은 트랜잭션으로 반영해야 한다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
Publisher 인스턴스가 하나뿐이어도, Claim 트랜잭션이 Commit된 직후 Kafka 발행을
시도하기 전에 그 프로세스가 재시작되거나 종료될 수 있다(배포, OOM, 서버 재부팅
등). 이 순간 해당 이벤트는 PROCESSING 상태로 DB에 Commit되어 남는다.

만약 Lease나 stale 복구 정책이 전혀 없다면, 재시작된 Publisher(같은 인스턴스든
새 인스턴스든)가 다음 Polling에서 PENDING 행만 조회하므로 이 PROCESSING 행은
누구의 Claim 대상도 되지 못하고 영원히 방치된다. 즉 인스턴스 개수와 무관하게
"Claim은 됐지만 발행은 안 된 채로 멈춘 행"을 다시 PENDING으로 되돌릴 방법이
반드시 있어야 한다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Publisher A
→ token-A로 Claim
→ 처리 지연
→ Lease 만료

Publisher B
→ 만료 행 회수
→ token-B로 Claim

Publisher A
→ 뒤늦게 성공 또는 실패 상태 UPDATE
```

```
Claim Token이 없으면 상태 UPDATE의 WHERE 조건이 event_id와 status만으로
구성된다. 이 경우 Publisher A가 Lease가 이미 만료된 뒤에도 살아있다가 뒤늦게
Kafka 결과를 받아 "자신이 여전히 처리 권한을 가지고 있다"고 착각한 채 상태를
변경할 수 있다.

- Publisher A가 뒤늦게 실패로 판단해 PENDING으로 되돌리면
  → 이미 Publisher B가 성공시켜 PUBLISHED로 만든 최신 상태를 되돌려버려
    다시 발행 대상이 되고, 불필요한 중복 발행이 유발된다.

- Publisher A가 뒤늦게 성공으로 판단해 PUBLISHED로 변경하면
  → Publisher B가 아직 진행 중인 처리(또는 이미 완료한 다른 결과)를
    A가 임의로 덮어써서 실제 발행 상태와 DB 상태가 어긋나게 된다.

즉 Claim Token이 없으면 "지금 이 행에 대한 최신 처리 권한을 가진 Publisher가
누구인지"를 DB가 구분할 방법이 없어, 오래되어 이미 권한을 잃은 Publisher가
최신 상태를 덮어쓰는 사고가 발생한다.
```

### **7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### **8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다**

```
Lease 시간
>
batchSize × 건당 최대 대기 시간(Kafka send().get()의 timeout)
+
여유 시간(margin)
```

건당 최대 대기 시간은 Publisher가 `get()`에 지정한 timeout이며, Kafka Producer의
`delivery.timeout.ms`와 정합성 있게 설계해야 한다. Lease가 이 값보다 짧으면
Kafka 발행이 아직 진행 중인데도 Lease가 먼저 만료되어 다른 Publisher가 같은
행을 회수해버리고, 두 Publisher가 동시에 같은 이벤트를 중복 발행할 위험이
커진다. Batch 크기를 작게 유지할수록 Lease 산정이 단순해지고 여유 시간을
확보하기 쉬워진다.

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료:
send() 메서드가 반환된 시점일 뿐이다. 이 시점은 단지 CompletableFuture(전송
요청)를 즉시 돌려받은 것이며, 메시지가 Broker에 실제로 전달되거나 저장됐다는
것을 전혀 의미하지 않는다.

CompletableFuture 정상 완료:
Broker로부터 성공 응답(RecordMetadata)을 수신하여 Future가 정상 완료된 상태.
이 시점에서야 비로소 Broker에 실제로 기록됐다고 신뢰할 수 있다(신뢰 수준은
acks 설정에 따라 달라진다).

outbox = PUBLISHED:
Publisher가 Future 완료(Broker ACK 성공)를 확인한 뒤, 그 사실을 DB의
outbox_event.status에 반영해 별도 트랜잭션으로 Commit까지 마친 상태. "Kafka에
전송됐다"는 사실이 DB에도 안전하게 기록되어 남은 상태다.

모든 후속 Consumer 처리 완료:
Notification/MyPage/Analytics 등 모든 Consumer Group이 이 이벤트를 소비해 각자의
비즈니스 로직 반영과 Offset Commit까지 마친 상태. outbox = PUBLISHED와는 완전히
독립적인 개념이며, PUBLISHED가 됐다고 이 상태가 자동으로 보장되지 않는다
(25절 "다음 상태는 같은 의미가 아니다" 참고).
```

### **2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다**

다음 조건을 반드시 포함한다.

```
event_id 일치

status = PROCESSING

claim_token 일치
```

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,
    lease_until = NULL,
    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

affected rows가 0이면 Lease가 이미 만료되어 다른 Publisher가 권한을 회수했거나
이미 완료 처리된 것이므로, 현재 Publisher는 상태를 더 이상 덮어쓰지 않는다.

### **3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다**

다음 값을 함께 갱신한다.

```
next_attempt_at

claim_token

lease_until

last_error

updated_at
```

```sql
UPDATE outbox_event
SET status = 'PENDING',
    next_attempt_at = :nextAttemptAt,
    claim_token = NULL,
    lease_until = NULL,
    last_error = :lastError,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

성공 UPDATE와 마찬가지로 `claim_token` 조건이 반드시 필요하다. 오래된 Publisher가
뒤늦게 실패로 판단해 이미 다른 Publisher가 처리 중이거나 완료한 최신 상태를
덮어쓰는 것을 막기 위해서다.

### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
Publisher가 받는 Timeout 예외는 "Broker에 요청이 도달했는지, 도달했다면 실제로
저장에 성공했는지"에 대한 정보를 구분해서 알려주지 않는다. 네트워크 왕복 중
어느 지점에서 응답이 늦어졌는지에 따라 다음 두 상황이 모두 같은 Timeout으로
관측될 수 있다.

상황 A: 요청 자체가 Broker에 도달하지 못했거나 Broker에서 저장이 실패한 경우
→ Kafka Topic에 Record가 존재하지 않는다.

상황 B: Broker에는 이미 정상적으로 저장됐지만, 그 성공 응답(ACK)이 네트워크
지연 등으로 Publisher에게 돌아오는 도중 Timeout이 먼저 발생한 경우
→ Kafka Topic에는 이미 Record가 존재한다.

Publisher는 이 둘을 구분할 방법이 없으므로, Timeout을 "Record가 없다"고
단정하고 안전하게 재시도했다가는 상황 B에서 같은 이벤트가 Kafka에 중복
저장되는 결과를 받아들여야 한다. 그래서 Outbox 설계는 Timeout을 실패로 간주해
재시도하되, 이로 인한 Kafka 레벨의 중복 가능성은 Consumer 멱등 처리로
방어한다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태:
PUBLISHED로 변경하지 않는다. 발행 실패와 동일하게 처리해 PENDING으로 되돌리고
next_attempt_at을 채워 재시도 대상으로 남긴다.

재시도 여부:
예. Backoff 지연 후 다시 Claim되어 재발행을 시도한다.

Kafka 중복 가능성:
있다. 상황 B(4번 문항)였다면 이미 Broker에 정상 저장된 Record가 존재하는
채로 같은 이벤트가 다시 발행되어, 같은 eventMessageId를 가진 Record가 서로
다른 Offset으로 두 번 이상 쌓일 수 있다.

Consumer에게 필요한 방어:
eventMessageId를 Key로 하는 processed_event 기반 멱등 처리. Kafka Offset이
아니라 이벤트 메시지 자체의 논리적 식별자로 중복 반영을 걸러야 한다.
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff:
연속으로 발행이 실패할수록 재시도 간격을 1초, 2초, 4초, 8초처럼 지수적으로
늘리는 방식이다. Kafka Broker 장애나 네트워크 문제가 지속되는 상황에서 곧바로
재시도를 반복하면 이미 불안정한 Broker에 더 많은 부하를 얹어 복구를 지연시킬
수 있다. 간격을 점점 늘리면 장애 지속 동안의 재시도 압력을 줄이고 Broker가
회복할 시간을 벌어준다.

Jitter:
여러 Publisher 인스턴스가 거의 동시에 실패했다면, Backoff만으로는 모든
인스턴스가 정확히 같은 시각에 재시도를 재개하게 된다(Thundering Herd). 여기에
작은 무작위 지연(Jitter)을 더하면 재시도 시점이 흩어져서 Kafka Broker나 DB에
순간적으로 요청이 몰리는 것을 방지할 수 있다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | Kafka Producer가 내부적으로 같은 배치를 재전송하더라도, Producer ID와 시퀀스 번호를 이용해 Broker가 이미 저장한 시퀀스인지 판단해 중복 저장을 막아준다. |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능 | Producer Idempotence는 같은 Producer 세션 내부의 재시도로 인한 물리적 중복만 방지한다. Publisher 프로세스가 성공을 DB에 기록하지 못해 새 Producer 세션에서 send()를 다시 호출하는 것은 애플리케이션 계층의 새로운 논리적 발행 요청이라 방어 대상이 아니다. |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능 | 이 역시 Producer 입장에서는 완전히 새로운 send() 호출이며, 애플리케이션/운영 계층에서 발생한 재발행이므로 Producer 내부 재시도 방지 메커니즘이 관여할 수 없다. |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
CompletableFuture.whenComplete()는 Future를 완료시킨 스레드에서 콜백을
실행한다. 이 스레드는 애플리케이션이 관리하는 스레드가 아니라 Kafka Producer
내부의 Sender 스레드다.

이 Sender 스레드 안에서 markPublished() 같은 DB 작업(Connection Pool 획득,
트랜잭션 Commit 대기)을 직접 수행하면, DB 응답이 느려지는 순간 Sender
스레드 자체가 블로킹된다. Sender 스레드는 해당 Kafka Producer의 모든 전송을
처리하는 공유 자원이므로, 이 스레드가 막히면 같은 Producer를 쓰는 다른
모든 발행 요청까지 함께 지연된다.

부하 상황에서는 다음과 같은 연쇄 장애로 이어질 수 있다.

Sender 스레드 블로킹 → 발행 지연 증가 → Lease 만료 → 다른 Publisher가
같은 행을 회수 → 중복 발행 증가 → 적체 심화

따라서 반드시 whenCompleteAsync(callback, executor)처럼 전용 Executor를
지정해, DB 작업이나 블로킹 I/O가 Kafka Producer의 Sender 스레드가 아니라
별도로 관리되는 스레드 풀에서 실행되도록 분리해야 한다.
```

## **과제 6. Outbox 장애 시나리오 분석하기**

각 장애 시나리오에 대해 다음을 작성한다.

```
DB의 비즈니스 상태

Outbox 상태

Kafka Record 존재 가능성

복구 주체

중복 가능성
```

### **1. 발급 트랜잭션 Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 저장되지 않음 (트랜잭션 Rollback) |
| request | PENDING 상태 그대로 유지 (또는 PROCESSING까지 진행됐어도 Rollback되어 PENDING으로 되돌아감) |
| outbox_event | 저장되지 않음 |
| 복구 방법 | Offset이 아직 Commit되지 않았으므로 원본 coupon.issue.requested 메시지가 재전달되고, Consumer가 5단계 발급 트랜잭션을 처음부터 다시 시도한다. |

### **2. 발급 DB Commit 후 원본 Offset Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 정상 저장됨 (Commit 완료) |
| request | ISSUED로 확정됨 |
| outbox_event | PENDING으로 정상 존재함 |
| 원본 Kafka 메시지 | Offset이 아직 반영되지 않아 재전달될 수 있음 |
| 복구 방법 | 재전달된 Consumer가 requestId로 request = ISSUED를 확인하고, 새 발급·새 Outbox 없이 정상 종료 후 Offset을 Commit한다. Outbox는 이후 Publisher가 별도로 발행을 진행한다. |

### **3. Outbox Claim Commit 후 Kafka 발행 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING (claim_token, lease_until이 설정된 채로 멈춰 있음) |
| Kafka Record | 존재하지 않음 (발행 시도 자체가 이루어지지 못함) |
| 복구 조건 | lease_until이 경과(만료)해야 함 |
| 복구 주체 | 동일 또는 다른 Publisher 인스턴스의 stale PROCESSING 복구 로직(스케줄러)이 만료된 행을 PENDING으로 되돌려 다시 Claim 대상이 되게 한다. |

### **4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING으로 남아 있다가 Lease 만료 후 PENDING으로 복구됨 |
| Kafka Record | 이미 존재함 (Broker에는 정상 저장 완료) |
| 재발행 가능성 | 있음 — 복구된 행이 다시 Claim되어 같은 이벤트를 재발행할 수 있음(같은 eventMessageId를 가진 Record가 서로 다른 Offset으로 중복 저장) |
| 필요한 Consumer 방어 | eventMessageId 기준 processed_event 멱등 처리로 중복 비즈니스 반영을 차단해야 함 |

### **5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황**

```
Publisher A가 늦게 성공 UPDATE:
UPDATE ... WHERE event_id=X AND status='PROCESSING' AND claim_token='token-A'
를 시도하지만, 이미 Publisher B가 회수하며 claim_token이 'token-B'로 바뀌었거나
그사이 성공적으로 PUBLISHED(claim_token=NULL)로 변경되었으므로 조건에 맞는 행이
없어 affected rows = 0이 되고 A의 UPDATE는 아무 효과 없이 무시된다.

Publisher A가 늦게 실패 UPDATE:
마찬가지로 claim_token='token-A' 조건이 더 이상 현재 행의 claim_token과
일치하지 않으므로 affected rows = 0이 되어, A가 뒤늦게 "실패"로 판단해도
Publisher B가 진행 중이거나 이미 완료한 최신 상태를 되돌리지 못한다.

두 UPDATE에서 affected rows가 0이어야 하는 조건:
Publisher B가 만료된 행을 회수하며 claim_token을 token-B로 바꾸었거나, 이미
발행에 성공해 status를 PUBLISHED로 바꾸고 claim_token을 NULL로 초기화한
경우. 즉 "현재 DB에 남아 있는 claim_token이 더 이상 token-A가 아닌" 모든
경우에 A의 뒤늦은 UPDATE는 반드시 0행이 되어야 한다.
```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화:
Outbox 생성(발급 성공)은 계속 일어나는데 발행은 전혀 성공하지 못하므로,
PENDING(및 재시도 대기 중인) 행이 시간이 지날수록 계속 누적되어 증가한다.

가장 오래된 PENDING 대기 시간:
장애가 지속되는 30분 내내 함께 늘어난다. 장애 초반에 생성된 이벤트일수록
대기 시간이 가장 길어진다.

attempt_count:
매 재시도마다 계속 증가한다. Exponential Backoff로 인해 재시도할 때마다
next_attempt_at 간격도 점점 벌어진다.

Kafka 복구 후 처리:
Kafka가 복구되면 누적된 PENDING 행들이 Polling 주기마다 Batch 크기만큼
순차적으로 Claim되어 재발행을 시도한다. 한 번에 모두 몰아 처리하지 않고
Batch 단위로 나눠서 서서히 적체를 해소한다.

운영 알람:
PENDING 이벤트 수가 계속 증가하는 추세, 가장 오래된 PENDING 대기 시간이
임계치를 초과, attempt_count가 계속 늘어나는 이벤트가 다수 관측되는 시점에
알람이 발생해야 한다(23절 운영 지표 참고).
```

### **7. 다음 두 재시도 대상을 구분한다**

```
발급 DB 트랜잭션 실패:
쿠폰 발급 자체가 확정되지 않았으므로, 원본 coupon.issue.requested 메시지를
재처리 대상으로 남겨 처음부터(권한 획득 → 수량 확보 → 발급 → Outbox 저장)
다시 시도해야 한다.

발급 DB Commit 성공 후 CouponIssued 발행 실패:
쿠폰 발급 자체는 이미 DB에서 확정된 사실이다. 이 경우 원본 메시지를 재처리
하는 것이 아니라, 이미 저장되어 있는 Outbox 이벤트만 Publisher가 재발행하면
된다.
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유도 작성한다.

```
발급 성공 여부는 이미 PostgreSQL 트랜잭션 Commit 시점에 확정된 사실이며,
CouponIssued 이벤트 발행은 그 확정된 사실을 후속 서비스에 "알리는" 부수적인
작업일 뿐 발급 자체의 성공/실패를 좌우하지 않는다.

만약 발행 실패를 이유로 발급 로직을 다시 실행하면 다음 문제가 생긴다.

- coupon_issue에 UNIQUE(event_id, user_id) 위반이 발생해 정상적으로 이미
  완료된 발급 건과 충돌하거나, 이를 회피하도록 잘못 구현하면 issued_count가
  또 증가해 실제 발급 수량보다 카운트가 부풀려질 수 있다.
- 사용자에게 쿠폰이 중복으로 발급되거나, 발급 기록이 꼬여 후속 조회·환불·
  통계 처리에서 정합성 오류가 발생한다.

따라서 "발급 확정"과 "결과 이벤트 발행"은 서로 다른 재시도 대상으로 명확히
분리해서 다뤄야 하며, 발행 실패는 오직 Outbox 재발행으로만 복구한다.
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001

Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
Partition과 Offset은 Kafka 안에서 메시지가 저장된 물리적 위치일 뿐, 이벤트가
나타내는 논리적인 사실을 식별하는 값이 아니다. 같은 논리 이벤트(eventMessageId
= evt-001)가 Publisher의 재시도로 인해 재발행되면, Kafka에는 서로 다른
Offset(예: Offset 100, Offset 101)을 가진 두 개의 Record로 각각 저장된다.

만약 Consumer가 (Partition, Offset)을 멱등성 Key로 사용한다면, 이 두 Record를
서로 다른 이벤트로 인식하고 각각 비즈니스 로직을 반영해버려 중복 처리를 전혀
막지 못한다. 또한 Consumer Group의 Rebalance나 Offset 되감기 등으로 같은
Offset의 메시지가 다시 전달되는 경우와, 진짜 새로운 이벤트가 도착한 경우를
구분하는 목적에도 적합하지 않다. 따라서 이벤트 자체에 고정된 논리적 식별자인
eventMessageId를 멱등성 Key로 사용해야 한다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (
        subscriber_id,
        event_id
    )
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

다음 중 적절한 값을 선택하고 이유를 작성한다.

```
pod-7f8c9d

server-10.0.0.12

mypage-coupon-projection
```

```
적절한 값: mypage-coupon-projection

pod-7f8c9d나 server-10.0.0.12 같은 프로세스 인스턴스 ID는 배포·재시작·오토
스케일링이 일어날 때마다 바뀐다. 만약 subscriber_id로 이런 값을 쓰면, 같은
"논리적인 구독자"(MyPage 조회 모델을 갱신하는 로직)임에도 재배포 이후에는
전혀 다른 subscriber_id로 취급되어 이전에 처리했던 eventMessageId 기록을
다시 조회할 수 없게 된다. 그 결과 재배포 직후 재전달된 이벤트를 "처음 보는
이벤트"로 오인해 중복 반영이 발생한다.

mypage-coupon-projection처럼 인스턴스와 무관하게 안정적으로 유지되는 논리적
구독자 이름을 써야, 어떤 인스턴스가 처리하든 같은 이름으로 중복 여부를 정확히
판단할 수 있다. 같은 이벤트를 서로 다른 목적으로 각자 처리하는 여러 Handler
(예: Notification, MyPage, Analytics)가 같은 DB를 공유하는 상황에서는 이
subscriber_id가 Handler 간 처리 여부를 구분하는 역할도 한다.
```

### **4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다**

```sql
BEGIN;

-- 1. eventMessageId 중복 확인
INSERT INTO processed_event (
    subscriber_id,
    event_id
) VALUES (
    'mypage-coupon-projection',
    :eventMessageId
)
ON CONFLICT DO NOTHING
RETURNING event_id;

-- 반환된 행이 없으면 이미 처리한 이벤트이므로
-- 아래 2번을 실행하지 않고 트랜잭션을 그대로 COMMIT한다(정상 종료).

-- 2. 최초 이벤트인 경우에만 조회 모델 변경
INSERT INTO user_coupon_view (
    user_id,
    coupon_issue_id,
    coupon_event_id,
    issued_at
) VALUES (
    :userId,
    :couponIssueId,
    :couponEventId,
    :issuedAt
);

COMMIT;
```

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다**

```
Consumer DB 상태:
processed_event에 해당 eventMessageId가 이미 기록되어 있고, user_coupon_view
조회 모델 변경도 정상적으로 Commit되어 있다.

Consumer Group Offset:
아직 반영되지 않았다.

재시작 후 Kafka 전달:
같은 Kafka Record가 재전달된다.

재전달된 이벤트 처리:
processed_event에 eventMessageId가 이미 존재하므로 4번 문항의 INSERT ...
ON CONFLICT DO NOTHING이 0행을 반환한다. 이 경우 조회 모델을 다시 변경하지
않고 그대로 정상 처리로 종료한 뒤 Offset을 Commit한다. 즉 이 중복은 예외로
취급하지 않고 조용히 건너뛰는 것이 올바른 처리다(10-4의 Outbox INSERT UNIQUE
위반과는 성격이 다르다).
```

### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**

```
processed_event는 Notification Consumer 자신의 로컬 DB 트랜잭션 안에서만
원자성을 보장한다. 하지만 실제 SMS 전송은 외부 SMS Provider API 호출이며,
이는 로컬 DB 트랜잭션에 포함될 수 없는 별도의 Dual Write다.

예를 들어 다음과 같은 순서로 처리한다고 가정하면,

1. processed_event INSERT (트랜잭션 A, Commit)
2. 외부 SMS API 호출

1번 Commit 후 2번을 호출하기 전에 프로세스가 종료되면, DB에는 "이미 처리
완료"로 기록되어 있지만 실제 SMS는 전송되지 않은 상태가 된다. 재전달되는
같은 이벤트는 processed_event 중복 검사에 걸려 "이미 처리한 이벤트"로 조용히
건너뛰어지므로, SMS가 영원히 전송되지 않을 수 있다.

반대로 SMS API를 먼저 호출하고 processed_event를 나중에 저장하면, SMS는
전송됐지만 DB Commit 전에 프로세스가 죽는 경우 재전달된 이벤트가 다시 SMS를
중복 전송하게 된다.

즉 processed_event는 "로컬 DB 반영"의 중복만 막아줄 뿐, 로컬 DB와 외부 API
호출 사이의 Dual Write 문제 자체를 해결해주지 않는다.
```

### **7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다**

```
1. Notification Service 내부 Outbox
   SMS 발송 "의도"를 processed_event 반영과 같은 로컬 트랜잭션에 별도의
   notification_outbox 테이블로 저장하고, 별도의 Sender가 이 테이블을 Polling
   하며 실제 SMS API를 호출하도록 분리한다. Coupon Issue 쪽 Outbox 패턴을
   Notification Service 내부에도 한 단계 더 적용하는 것이다.

2. notificationId 기반 멱등 발송과 외부 Provider의 Idempotency Key 활용
   SMS 발송 요청마다 고유한 notificationId를 생성해 저장하고, SMS Provider가
   Idempotency Key를 지원한다면 이 값을 그대로 전달한다. Provider 쪽에서
   같은 Key로 재요청이 오면 중복 발송하지 않도록 처리해주므로, 애플리케이션이
   재시도하더라도 실제 전송은 한 번만 이루어지게 만들 수 있다.

3. 발송 작업 상태 테이블(알림 작업 테이블)과 별도 Sender
   notification_task 같은 별도 상태 테이블(PENDING/SENT/FAILED)을 두고,
   Sender가 PENDING 건을 Claim해 발송한 뒤 Provider 응답을 확인하고 나서야
   SENT로 확정한다. Coupon Outbox Publisher의 Claim/Lease 구조를 그대로
   재사용할 수 있다.
```

### **8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다**

다음을 포함한다.

```
Kafka Topic 보관 기간

Consumer Offset 되감기

Outbox 지연 재발행

운영자 수동 재발행
```

```
processed_event는 처리한 이벤트마다 한 행씩 계속 쌓이므로 무한정 보관할 수
없고, 오래된 행은 주기적으로 삭제해야 한다. 하지만 보관 기간을 너무 짧게
잡으면 중복 방어 자체가 뚫릴 수 있다. 삭제 이후에 같은 이벤트가 다시
전달되면, processed_event에 기록이 없으므로 "최초 이벤트"로 오인해 조회
모델을 중복 반영하게 된다.

따라서 다음과 같이 실제로 같은 이벤트가 다시 등장할 수 있는 모든 경로의
최대 지연 시간보다 보관 기간이 길어야 한다.

Kafka Topic 보관 기간
→ Topic에 Record가 남아 있는 동안은 언제든 재전달될 가능성이 있다.

Consumer Offset 되감기
→ 운영자가 장애 조사·재처리를 위해 Consumer Group Offset을 과거로 되돌리면,
  이미 처리했던 오래된 이벤트가 다시 전달될 수 있다.

Outbox 지연 재발행
→ Outbox Publisher가 Lease 만료·재시도 등으로 한참 지난 뒤에야 같은
  eventMessageId를 재발행할 수 있다(Backoff가 누적되면 지연이 길어질 수 있음).

운영자 수동 재발행
→ 운영자가 특정 Outbox 행이나 특정 기간의 이벤트를 수동으로 다시 발행시키는
  복구 작업을 수행할 수 있다.

결론적으로 processed_event 보관 기간은 "Kafka Topic 보관 기간 + 최대 재전달
지연(Consumer 장애 복구 시간, Offset 되감기 운영 가능 범위, Outbox 재발행
지연 최대치 등을 모두 포함)"보다 길게 설정해야 한다.
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateType = COUPON_ISSUE

aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
1. 같은 Aggregate(같은 couponIssueId)에서 발생하는 이벤트들을 하나의 Partition에
   모아, Consumer가 병렬 처리하는 단위를 명확히 하기 위해서다. 같은 Aggregate의
   이벤트가 서로 다른 Partition에 흩어지면 어느 Consumer 인스턴스가 처리할지가
   섞여 관리가 더 복잡해진다.

2. 특정 Partition에 부하가 몰리지 않도록 이벤트를 여러 Partition에 고르게
   분산시키기 위해서다. couponIssueId처럼 값이 다양하게 분포하는 키를 쓰면
   자연스럽게 부하가 분산된다.

3. 지금 당장 순서를 보장하지 않더라도, 향후 순서 보장이 필요해질 때 "어떤
   단위로 직렬화할 것인가"의 기준을 미리 정해두기 위해서다(같은 Aggregate
   단위 직렬화 등을 나중에 도입할 때의 출발점이 된다).
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

다음을 반드시 포함한다.

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
같은 Partition Key를 쓰면 "같은 Record들이 같은 Partition으로 전달된다"는
것만 보장될 뿐이다. 그 Partition 안에서의 실제 저장 순서는 Producer가
send()를 호출한 순서로 결정되며, 이는 Outbox의 DB 저장 순서와 다음 이유로
달라질 수 있다.

여러 Publisher 인스턴스
→ 서로 다른 Publisher 인스턴스가 서로 다른 속도로 각자 Claim한 이벤트를
  독립적으로 발행하므로, 먼저 DB에 저장된 이벤트가 나중에 send()될 수 있다.

SKIP LOCKED
→ Claim 쿼리 자체가 "잠긴 행은 건너뛰고 다음 행을 먼저 가져오는" 방식이라,
  애초에 DB 저장 순서를 지키기 위한 장치가 아니라 처리량을 위해 순서를
  포기한 장치다.

발행 실패와 Backoff
→ 먼저 저장된 이벤트의 발행이 실패하면 next_attempt_at이 뒤로 밀려 대기
  상태가 되고, 그 사이 나중에 저장된 이벤트가 먼저 성공적으로 발행되어
  순서가 역전될 수 있다.

Producer 설정과 재시도
→ Producer 내부의 재시도, 여러 요청을 동시에 전송하는 설정
  (max.in.flight.requests.per.connection 등)에 따라 애플리케이션이
  send()를 호출한 순서와 실제로 Broker에 도착하는 순서가 정확히 일치하지
  않을 수 있다.

따라서 이번 주차의 설계는 Partition Key를 정해두더라도 발행 순서를
"At-Least-Once, 순서 보장 없음"으로 명시적으로 선언한다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A:
outbox 1(CouponIssued, version=1)을 Claim했지만 Kafka 발행에 실패한다.
PENDING 상태로 되돌아가고 next_attempt_at이 +4초 뒤로 밀린다.

Publisher B:
outbox 2(CouponCancelled, version=2)를 Claim해 곧바로 발행에 성공한다.

Kafka 저장 순서:
Offset 200 : CouponCancelled (version=2)
Offset 201 : CouponIssued    (version=1)

→ 비즈니스 발생 순서와 정반대로 Kafka에 저장되는 순서 역전이 발생한다.
```

### **4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다**

```
1. 서로 다른 이벤트가 같은 Timestamp 값을 가질 수 있다. 서버나 DB의 시간
   정밀도(밀리초 단위 등)에 따라 짧은 시간 안에 연속으로 발생한 서로 다른
   이벤트가 우연히 같은 occurredAt을 갖게 될 수 있어, 이 값만으로는 어느
   쪽이 먼저인지 구분할 수 없다.

2. 이벤트를 발생시키는 여러 컴포넌트(서버, DB)의 시계가 완전히 일치하지
   않을 수 있다(Clock Skew). 서로 다른 서버에서 생성된 occurredAt을 단순
   비교하면 실제 발생 순서와 다르게 판단될 위험이 있다.

3. occurredAt 비교만으로 로직을 짜면, "조회 행이 아직 없어서 최초로 반영하는
   경우"와 "이미 더 최신 이벤트가 반영되어 있어 지금 온 이벤트가 오래된
   경우"를 affected rows처럼 명확한 신호로 구분하기 어렵다. 반면
   aggregateVersion은 정수 비교이므로 이 두 상황을 항상 명확하게 구분할 수
   있다.
```

### **5. MyPage처럼 최신 상태만 필요한 Projection의 순서 역전 방어 SQL을 작성한다**

다음 컬럼을 사용한다.

```
coupon_issue_id

status

last_aggregate_version

last_event_at
```

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    last_aggregate_version,
    last_event_at
) VALUES (
    :couponIssueId,
    :userId,
    :couponEventId,
    :newStatus,
    :aggregateVersion,
    :occurredAt
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    last_aggregate_version = EXCLUDED.last_aggregate_version,
    last_event_at = EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version
      < EXCLUDED.last_aggregate_version;
```

affected rows = 1이면 최초 반영이거나 더 최신 버전을 정상 반영한 것이고,
affected rows = 0이면 같거나 더 높은 버전이 이미 반영돼 있어 현재 이벤트의
상태 변경을 생략한 것이다.

### **6. aggregateVersion이 더 큰 이벤트가 먼저 도착한 경우의 결과를 작성한다**

```
먼저 도착:
CouponCancelled(version=2)

나중 도착:
CouponIssued(version=1)

최종 MyPage 상태:
CouponCancelled(version=2)가 먼저 반영되어 취소 상태로 저장된다.

version=1 처리 결과:
5번 SQL의 WHERE 조건(last_aggregate_version < EXCLUDED.last_aggregate_version)에
의해 1 < 2가 거짓이 되어 affected rows = 0이 된다. 즉 나중에 도착한
CouponIssued(version=1)는 상태를 되돌리지 못하고 생략되며, MyPage에는 계속
취소 상태가 정확하게 유지된다.
```

### **7. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버려도 되는지 판단한다**

다음 Consumer별로 답한다.

| Consumer | 낮은 Version 이벤트 생략 가능 여부 | 이유 또는 추가로 필요한 설계 |
| --- | --- | --- |
| 최신 상태만 저장하는 MyPage Projection | 가능 | 사용자에게 보여줄 것은 "지금 이 쿠폰이 어떤 상태인가"라는 최신 상태 하나뿐이므로, 더 낮은 버전의 이벤트는 최신 상태를 덮어쓰지만 않으면 되고 생략해도 최종 결과에 영향이 없다. |
| 모든 발급·취소 건수를 집계하는 Analytics | 불가능 — 추가 설계 필요 | 통계는 발생한 모든 이벤트를 빠짐없이 반영해야 정확하다. version이 낮다고 생략하면 실제 발생한 건수(예: 취소 건수)가 누락된다. 순서와 무관하게 각 이벤트를 개별적으로 집계하되, eventMessageId 기준 processed_event로 "같은 이벤트의 중복 집계"만 방지하는 설계가 필요하다. |
| 발급과 취소 알림을 각각 보내는 Notification | 불가능 — 추가 설계 필요 | 발급 알림과 취소 알림은 각각 독립적으로 사용자에게 전달해야 하는 별개의 사실이다. version이 낮다고 생략하면 사용자가 발급 알림 자체를 받지 못하게 된다. 역시 모든 이벤트를 각각 처리하되 eventMessageId 기준 중복 발송만 방지해야 한다. |

### **8. `aggregateVersion`의 역할을 정확히 정의한다**

다음 문장을 완성한다.


## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않고 대기 중인 Outbox 행의 수 | 시간이 지날수록 계속 증가하는 추세를 보이면 Publisher 처리량이 생성량을 못 따라가거나 Kafka 발행이 실패하고 있다는 신호 |
| 가장 오래된 PENDING 대기 시간 | 가장 먼저 생성됐지만 아직 발행되지 못한 이벤트가 얼마나 오래 기다리고 있는지 | 이 값이 SLA(예: 후속 알림이 몇 분 내로 도착해야 함)를 넘어서면 사용자 체감 지연으로 이어지는 장애 신호 |
| PROCESSING 이벤트 수 | 현재 어떤 Publisher가 발행 권한을 갖고 처리 중인 행의 수 | 정상적으로는 Batch 크기 수준에서 오르내려야 하며, 지속적으로 비정상적으로 많이 쌓이면 Publisher가 멈췄거나 Kafka 호출이 걸려 있다는 신호 |
| 만료된 PROCESSING 수 | lease_until이 지났는데도 아직 PENDING으로 복구되지 않은 행의 수 | 0에 가까워야 정상이며, 반복적으로 관측되면 Publisher가 Claim 후 자주 죽거나 Lease 계산이 잘못됐다는 신호 |
| attempt_count | 특정 이벤트가 발행 권한을 얻은(재시도한) 횟수 | 특정 이벤트의 attempt_count가 계속 증가하면 그 이벤트만 반복 실패하고 있다는 신호(영구 실패 후보) |
| Outbox 생성 처리량 | 초당/분당 새로 INSERT되는 Outbox 행의 수(비즈니스 발급 속도와 연동) | 급격한 스파이크 자체는 정상일 수 있지만, 이후 발행 처리량이 이를 못 따라가면 적체로 이어짐 |
| Kafka 발행 처리량 | 초당/분당 실제로 PUBLISHED로 전환되는 행의 수 | Outbox 생성 처리량보다 지속적으로 낮으면 적체가 계속 쌓이고 있다는 신호 |
| DB 발생부터 Kafka ACK까지의 시간 | occurred_at(또는 created_at)부터 published_at까지 걸린 시간(발행 지연) | 이 지연이 점점 길어지는 추세면 Publisher 처리 능력 저하 또는 Kafka 장애의 신호 |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량:
(2,000 - 1,500)건/초 × 60초 = 30,000건

10분 후 예상 적체 증가량:
(2,000 - 1,500)건/초 × 600초 = 300,000건

가장 먼저 확인할 지표:
PENDING 이벤트 수의 증가 추세와 가장 오래된 PENDING 대기 시간. 그리고 처리
속도가 낮은 원인이 "Kafka 발행 자체의 실패/재시도로 인한 것"인지 "정상
발행이지만 처리량 자체가 부족한 것"인지 구분하기 위해 발행 성공/실패
비율(attempt_count 분포)도 함께 확인한다.

가능한 대응:
Publisher 인스턴스 수를 늘리거나 Batch 크기를 조정해 처리량을 끌어올린다.
병목이 Kafka Broker/Partition 자체의 처리 한계라면 Partition 증설이나 Broker
스케일업을 검토한다. 처리량이 근본적으로 부족하다면 동기 순차 발행에서
비동기 발행 모델(16-3)로 전환을 검토한다. 동시에 운영 알람을 발생시켜
사람이 상황을 인지하고 개입할 수 있게 한다.
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. outbox_event.deduplication_key UNIQUE 위반
   정상 경로에서는 절대 발생하면 안 되는 위반이며, 요청 상태 관리 결함이나
   Key 생성 로직 버그를 의미한다.

2. Commit된 request = PROCESSING 상태의 관측
   이번 설계에서 PROCESSING은 하나의 트랜잭션 내부에서만 존재해야 하며
   외부에 Commit되지 않는다. 이 상태가 관측되면 설계 가정 자체가 깨진 것이다.

3. SOLD_OUT 또는 DUPLICATE_USER 확정이 반복적으로 발생
   Redis 선착순 판정과 DB 최종 상태가 수렴하지 않고 있다는 신호이며, 저장소
   간 divergence를 의미할 수 있다.

4. Lease가 만료된 PROCESSING 행이 반복적으로 발생
   특정 Publisher가 자주 죽거나, Lease 시간이 실제 발행 소요 시간보다
   짧게 설정되어 있다는 신호다.
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면:
아직 한 번도 Kafka에 발행되지 않은 이벤트 기록을 지워버리는 것이므로, 해당
발급 결과에 대한 CouponIssued 이벤트가 영원히 발행되지 못하는 이벤트
유실이 발생한다.

PROCESSING을 삭제하면:
현재 어떤 Publisher가 처리 중이거나(또는 Lease 만료로 회수 대기 중인) 행을
지워버리는 것이므로, 이미 진행 중이던 발행 시도의 결과를 알 수 없게 되고
PENDING 삭제와 마찬가지로 이벤트가 발행되지 못한 채 유실될 수 있다.

PUBLISHED를 보관하는 목적:
이미 Kafka ACK까지 확인되어 발행 책임이 끝난 행이지만, 일정 기간은 발행
이력 확인과 장애 조사(언제, 어떤 Payload로, 몇 번 시도 끝에 발행됐는지)를
위해 남겨둔다. 이 이력이 없으면 사후 감사나 문제 재현이 어려워진다.
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

다음 항목을 포함한다.

```
긴 트랜잭션

DB 부하

Lock

Table Bloat
```

```
긴 트랜잭션
한 번에 수십만~수백만 건을 DELETE하면 하나의 트랜잭션이 매우 오래 실행되어,
그동안 다른 트랜잭션과의 충돌 가능성과 WAL(Write-Ahead Log) 적체가 함께
커진다.

DB 부하
대량 삭제는 순간적으로 많은 I/O와 CPU를 소모해 같은 DB를 쓰는 다른 서비스
(발급 트랜잭션, Claim 쿼리 등)의 응답 시간에 영향을 줄 수 있다.

Lock
대량 DELETE 동안 관련 행/인덱스에 Lock이 오래 유지되면, 그 사이 다른
Publisher의 Claim 쿼리나 INSERT가 대기하게 되어 전체 처리량이 순간적으로
떨어진다.

Table Bloat
PostgreSQL은 삭제된 행을 즉시 물리적으로 회수하지 않고 Dead Tuple로
남기므로, 대량 삭제 직후 VACUUM 부담이 커지고 테이블/인덱스가 불필요하게
비대해지는 Table Bloat가 발생하기 쉽다.
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
1. status = 'PUBLISHED' AND published_at < :cutoff 조건으로 삭제 대상 조회
2. 예: 1,000건 단위로 LIMIT을 걸어 DELETE
3. 각 Batch마다 즉시 COMMIT
4. 짧게 대기(Sleep)해 DB에 다른 요청이 끼어들 여유를 준다
5. 삭제 대상이 남아 있으면 2번부터 반복
6. 전체 삭제가 끝나면 스케줄을 종료하고 다음 배치 실행 시각까지 대기
```

### **7. 다음 세 보관 기간의 목적을 비교한다**

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |
| Outbox PUBLISHED 행 | 발행 이력 확인과 장애 조사(언제, 몇 번 시도 끝에 발행됐는지)를 위한 보관 | 과거 발행 이력을 추적할 수 없어 장애 원인 분석이 어려워지지만, 발행 자체는 이미 끝났으므로 데이터 유실로 직결되지는 않는다 |
| Kafka Topic Record | Consumer가 아직 처리하지 못한 메시지를 재처리(재구독, Offset 되감기)할 수 있는 범위를 결정 | Consumer 장애 복구나 재처리가 필요한 시점에 이미 Record가 삭제되어 있으면 해당 이벤트를 영영 다시 읽을 수 없어 실제 데이터 유실로 이어진다 |

### **8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다**

```
last_error 컬럼은 운영자가 대시보드나 쿼리로 자주 조회·검색하는 필드이며,
접근 권한이 상세 로그·트레이싱 시스템만큼 엄격하게 통제되지 않는 경우가
많다. 여기에 전체 Stack Trace나 개인정보·인증 정보 같은 민감 정보를 그대로
저장하면 다음 문제가 생긴다.

- Stack Trace는 매우 길어 컬럼 크기를 불필요하게 키우고, 같은 원인의 실패가
  반복될 때마다 유사하지만 미세하게 다른 텍스트가 계속 쌓여 검색·집계를
  어렵게 만든다.
- 민감 정보(사용자 식별 정보, 내부 시스템 경로, 인증 토큰 등)가 상세 로그
  시스템보다 접근 통제가 느슨한 DB 컬럼에 그대로 노출되어 보안 사고로
  이어질 수 있다.

따라서 DB의 last_error에는 검색 가능한 짧은 오류 분류와 요약 메시지만
남기고, 전체 Stack Trace와 상세 진단 정보는 별도의 Log/Trace 시스템에
저장해 필요할 때 상관관계 ID(event_id 등)로 연결해 조회하도록 분리해야
한다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

```
문제 위치:

문제 내용:

발생 가능한 장애:

수정 방법:
```

```
문제 1
문제 위치: issueCoupon() 내부의 kafkaTemplate.send() 호출
문제 내용: 발급 DB 트랜잭션 안에서 Kafka를 직접 호출한다. Outbox 테이블에
  전혀 저장하지 않고 곧바로 send()를 호출해, 이번 주차가 없애려는 Dual
  Write 문제를 그대로 재현한다.
발생 가능한 장애: DB Commit은 성공했지만 Kafka 발행이 실패하거나 그 반대의
  경우 모두 발생할 수 있으며, 발행 실패 시 재시도할 근거(Outbox 기록)가
  전혀 남지 않아 이벤트가 영구히 유실될 수 있다.
수정 방법: kafkaTemplate.send() 호출을 제거하고, 같은 트랜잭션 안에서
  outboxRepository.save()로 CouponIssuedEvent에 대한 outbox_event 행만
  저장한다.

문제 2
문제 위치: issueCoupon() 전체
문제 내용: outbox_event가 전혀 생성되지 않으므로, 아래 publishOutbox()가
  이 이벤트를 처리할 방법이 없다. 즉 Outbox 패턴이 이름만 있고 실제로는
  적용되지 않았다.
발생 가능한 장애: 문제 1과 결합해 "메모리에서만 발행 시도 → 실패 시 완전
  유실"되는 상황이 발생한다.
수정 방법: 문제 1과 동일하게 Outbox INSERT로 대체한다.

문제 3
문제 위치: publishOutbox() 메서드 전체의 @Transactional
문제 내용: PENDING 조회부터 Kafka 발행, markPublished()까지 전체 반복문이
  하나의 DB 트랜잭션 안에서 실행된다. Kafka 발행처럼 네트워크 왕복이 필요한
  작업을 DB 트랜잭션(Lock, Connection) 안에 넣고 있다.
발생 가능한 장애: DB Connection과 Row Lock을 오래 점유해 Connection Pool
  고갈, 다른 Publisher/트랜잭션의 대기 증가, 트랜잭션 Timeout이 발생할 수
  있다(과제4-3).
수정 방법: Claim(PENDING→PROCESSING) 단계만 짧은 트랜잭션으로 Commit하고,
  Kafka 발행은 트랜잭션 밖에서 수행한 뒤 성공/실패 결과만 별도의 짧은
  트랜잭션으로 반영한다.

문제 4
문제 위치: publishOutbox()의 outboxRepository.findTop100ByStatus("PENDING")
문제 내용: 단순 SELECT(조회)만 수행하고 즉시 PROCESSING으로 바꾸는 원자적
  Claim이 없다. FOR UPDATE SKIP LOCKED 같은 동시성 제어가 전혀 없다.
발생 가능한 장애: 스케줄러가 겹쳐 실행되거나 Publisher 인스턴스가 여러 개면,
  같은 PENDING 행을 동시에 여러 Publisher가 가져가 중복 발행하는 경쟁 상태가
  발생한다(과제4-1의 Race Condition과 동일).
수정 방법: WITH candidates ... FOR UPDATE SKIP LOCKED로 조회와 동시에
  PROCESSING으로 변경하는 원자적 Claim 쿼리를 사용한다.

문제 5
문제 위치: publishOutbox() 안의 event.markPublished() 호출
문제 내용: Kafka send()가 반환하는 결과(Future)를 기다리거나 확인하지
  않고 곧바로 PUBLISHED로 표시한다. send() 호출 완료와 Broker ACK 확인은
  다른 것인데(과제5-1) 이를 구분하지 않는다.
발생 가능한 장애: 실제로는 Kafka 발행이 실패했는데도 DB에는 PUBLISHED로
  잘못 기록되어, 후속 재시도 대상에서 영구히 제외되고 이벤트가 조용히
  유실된다.
수정 방법: send().get(timeoutMs, ...)로 Broker ACK를 명시적으로 확인한
  뒤에만 markPublished를 호출하고, 실패/Timeout이면 재시도(PENDING +
  next_attempt_at)로 분기한다.

문제 6
문제 위치: publishOutbox()의 for 루프 전체
문제 내용: 개별 이벤트의 발행 실패에 대한 예외 처리(try-catch)가 전혀 없다.
  한 건이라도 send()에서 예외가 발생하면 반복문 전체가 중단될 수 있고,
  실패에 대한 재시도 정책(Backoff, next_attempt_at 갱신)도 없다.
발생 가능한 장애: 하나의 이벤트 발행 실패가 나머지 Batch 전체의 처리를
  막아 정상 이벤트까지 지연시키고, 실패한 이벤트는 재시도되지 않아 발행이
  누락될 수 있다.
수정 방법: 각 이벤트 발행을 개별 try-catch로 감싸 한 건의 실패가 나머지
  처리를 막지 않게 하고, 실패 시 Exponential Backoff + Jitter로
  next_attempt_at을 설정해 PENDING으로 되돌린다.

문제 7
문제 위치: publishOutbox()의 createPayloadFromCurrentCouponIssue(event)
문제 내용: 발행 시점에 현재 CouponIssue 테이블을 다시 조회해 Payload를
  새로 만든다. Outbox INSERT 시점에 완성된 불변 Payload를 저장하지 않는다.
발생 가능한 장애: Outbox 저장과 실제 발행 사이에 원본 데이터가 변경되면
  (예: 발급 직후 취소), 실제 발생 시점과 다른 내용의 Payload가 발행되어
  이벤트의 사실성이 깨진다(과제2-5).
수정 방법: Outbox INSERT 시점에 Payload를 완성해 outbox_event.payload에
  저장하고, Publisher는 저장된 값을 그대로 전달하기만 한다.

문제 8
문제 위치: recoverProcessing()의 updateAllProcessingToPending()
문제 내용: lease_until 만료 여부를 확인하지 않고 PROCESSING 상태의 모든
  행을 무조건 PENDING으로 되돌린다.
발생 가능한 장애: 다른 Publisher가 정상적으로 Lease 안에서 처리 중인
  행까지 강제로 회수당해, 두 Publisher가 같은 이벤트를 동시에 발행하는
  중복 발행이 발생한다(과제4-4, 과제4-6).
수정 방법: WHERE status='PROCESSING' AND lease_until <= CURRENT_TIMESTAMP
  조건을 추가해 실제로 Lease가 만료된 행만 회수한다.

문제 9
문제 위치: 테이블 전반 (claim_token 컬럼 사용 없음), markPublished()와
  recoverProcessing()
문제 내용: Claim Token 자체를 전혀 사용하지 않는다. 어떤 Publisher가 현재
  처리 권한을 가지고 있는지 구분할 방법이 없다.
발생 가능한 장애: Lease가 만료된 뒤 다른 Publisher가 이미 행을 회수해
  처리했는데도, 원래 Publisher가 뒤늦게 자신의 결과로 상태를 덮어써서
  최신 처리 결과를 잘못된 값으로 되돌릴 수 있다(과제4-6).
수정 방법: Claim 시 claim_token(UUID)을 생성해 저장하고, 성공/실패 상태
  변경 UPDATE의 WHERE 절에 claim_token 일치 조건을 반드시 포함시킨다.

문제 10
문제 위치: onResult()의 new ProcessedEvent(event.getKafkaPartition(),
  event.getKafkaOffset())
문제 내용: Kafka Partition + Offset을 멱등성 Key로 사용한다.
발생 가능한 장애: 같은 논리 이벤트(같은 eventMessageId)가 재발행되면 서로
  다른 Offset을 가지므로 같은 이벤트를 서로 다른 이벤트로 오인해 중복
  비즈니스 반영(조회 모델 중복 갱신 등)이 발생한다(과제7-1).
수정 방법: event.getEventMessageId()를 Key로 사용하도록 ProcessedEvent
  스키마와 저장 로직을 변경한다.

문제 11
문제 위치: onResult() 메서드 전체 (@Transactional 어노테이션 없음)
문제 내용: userCouponViewRepository.save()와 processedEventRepository.save()
  가 하나의 트랜잭션으로 묶여 있다는 보장이 코드상 없다(메서드에
  @Transactional이 붙어 있지 않다).
발생 가능한 장애: 둘 중 하나만 성공하고 나머지가 실패하면(예: 조회 모델은
  갱신됐는데 processed_event는 저장 안 됨), 재전달 시 같은 이벤트를 다시
  반영해 중복 처리가 발생하거나 반대로 반영 자체가 누락될 수 있다
  (과제7-4).
수정 방법: onResult()에 @Transactional을 붙이고, processed_event
  중복 확인(INSERT ... ON CONFLICT DO NOTHING) 이후 반환된 행이 있을
  때만 조회 모델을 갱신하도록 순서를 바꾼다.

문제 12
문제 위치: onResult()에서 사용하는 ProcessedEvent 저장 구조 전체
문제 내용: subscriber_id 같은 논리 구독자 식별자가 전혀 없다.
발생 가능한 장애: Notification/MyPage/Analytics처럼 같은 이벤트를 각자
  다른 목적으로 처리하는 여러 Handler가 있다면, 이 스키마로는 "어떤
  Handler가 이미 처리했는지"를 구분할 수 없어 한 Handler의 처리 여부가
  다른 Handler의 중복 방어에 잘못 영향을 준다.
수정 방법: processed_event 테이블에 subscriber_id 컬럼을 추가하고
  (subscriber_id, event_id)를 복합 Primary Key로 구성한다(과제7-2).
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | coupon_issue 저장과 outbox_event 저장을 같은 로컬 DB 트랜잭션에 묶었으므로 항상 함께 Commit되거나 함께 Rollback된다 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | Lease 만료 후 재Claim, Timeout 후 재시도 등으로 같은 이벤트가 Kafka에 두 번 이상 저장될 수 있다(At-Least-Once) |
| Publisher 복구 후 재발행 | 조건부 보장 | Publisher가 계속 살아 있고, Lease/Claim Token 기반 복구 로직이 올바르게 동작하며, Kafka 장애가 결국 회복된다는 전제하에서만 보장된다 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED, 발행 실패 Backoff, 여러 Publisher 인스턴스의 병렬 처리로 인해 DB 저장 순서와 실제 발행 순서가 달라질 수 있다 |
| Consumer의 중복 비즈니스 반영 방지 | 조건부 보장 | Consumer가 eventMessageId 기준 processed_event 확인과 비즈니스 변경을 하나의 트랜잭션으로 올바르게 구현했을 때만 보장되며, 구현이 틀리면(수정 전 코드처럼) 깨진다 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | outbox = PUBLISHED는 Kafka Broker에 저장됐다는 뜻일 뿐이며, 각 Consumer Group의 실제 처리 여부는 서로 독립적으로 관리되어 이 상태만으로는 알 수 없다 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API 호출은 로컬 DB 트랜잭션에 포함될 수 없는 별도의 Dual Write이며, Notification Service 내부 Outbox나 Provider Idempotency Key 같은 별도 메커니즘이 추가로 필요하다 |
