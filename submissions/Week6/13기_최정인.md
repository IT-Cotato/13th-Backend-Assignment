# **6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성**


## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
관계형 DB(RDBMS) - coupon_event, coupon_issue, coupon_issue_request 저장
Kafka - coupon.issued 토픽 Broker
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
Spring의 @Transactional은 PlatformTransactionManager가 관리하는 하나의 리소스(여기서는 RDBMS 커넥션)에 대해서만
Commit/Rollback을 보장한다.

kafkaTemplate.send()는 이 트랜잭션 매니저가 관리하지 않는 별도의 외부 시스템(Kafka Broker) 호출이다.
DB 트랜잭션이 Rollback되어도 이미 Kafka Broker에 전달된 레코드는 자동으로 취소되지 않고,
반대로 Kafka 전송이 실패해도 이미 실행된 DB INSERT/UPDATE는 자동으로 Rollback되지 않는다.

2PC/XA 같은 분산 트랜잭션을 사용하지 않는 한, 어노테이션 하나로는 서로 다른 두 시스템이
하나의 원자적 단위로 묶이지 않는다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[장애 지점: Commit 후 kafkaTemplate.send() 호출 전(또는 호출 도중) 프로세스 종료/네트워크 장애]
    ↓
Kafka 발행

최종 DB 상태: 쿠폰 발급 완료 (coupon_issue 존재, coupon_issue_request = ISSUED)

최종 Kafka 상태: CouponIssued 이벤트 없음

후속 서비스에 미치는 영향: Notification / MyPage / Analytics Consumer 모두 발급 사실을 알 수 없음

복구에 필요한 정보: 쿠폰은 이미 발급되었으므로 재발급하면 안 되고, "발행되지 않은 이벤트가 있다"는 사실을
                    영속 저장소(DB)에서 식별할 수 있어야 한다. 메모리에만 있던 발행 의도는 프로세스 종료와 함께
                    사라지므로 복구 기준이 없어진다.
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점: Kafka 발행 성공 후 DB 트랜잭션 Commit 전 예외/타임아웃 발생]
    ↓
DB Commit

최종 DB 상태: 쿠폰 발급 기록 없음 (Rollback됨)

최종 Kafka 상태: CouponIssued 이벤트 존재

후속 서비스에 미치는 영향: 존재하지 않는 발급 건에 대해 알림 발송, 마이페이지 반영, 통계 집계 등
                        후속 Consumer가 잘못된 결과를 처리하게 됨
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료

KafkaTemplate.send() 호출 후
Broker ACK 확인 전 프로세스 종료
```

```
@TransactionalEventListener(phase = AFTER_COMMIT)는 DB Commit이 끝난 뒤에만 Kafka를 호출하도록 만들어
"Commit 전에 이벤트가 먼저 나가는" 문제는 막아준다. 하지만 다음 두 장애 구간은 여전히 남는다.

1) DB Commit 후 Listener 실행 전 프로세스 종료
   → Commit은 성공했지만 Listener 자체가 실행되지 못해 kafkaTemplate.send() 호출조차 되지 않는다.
     이벤트가 아예 발행되지 않는다.

2) KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료
   → send()는 CompletableFuture를 즉시 반환하는 비동기 호출이며, send() 호출 ≠ Broker ACK 확인이다.
     ACK를 기다리는 도중 프로세스가 종료되면 실제로 Kafka에 전달되었는지 알 수 없고,
     DB는 이미 Commit되어 되돌릴 수 없다.

두 장애의 공통 원인은 "발행할 이벤트 정보가 메모리에만 존재한다"는 것이다.
프로세스가 종료되면 무엇을 재발행해야 하는지 판단할 근거 자체가 사라진다.
Outbox Pattern은 이 발행 의도를 메모리가 아니라 DB(Commit 대상)에 저장해 이 문제를 없앤다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | O | 같은 RDBMS, 같은 트랜잭션에 outbox_event INSERT를 포함시켜 원자적으로 묶을 수 있음 |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | X | Redis와 RDBMS는 서로 다른 저장소라 하나의 로컬 DB 트랜잭션으로 묶이지 않음. 별도의 보정(reconciliation) 메커니즘이 필요 |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | X | 이 구간은 Outbox가 아니라 requestId 기반 멱등 처리로 방어하는 영역. 원본 메시지 재전달 자체는 막지 못하고 중복 실행만 막음 |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | X | 외부 API 호출은 로컬 DB 트랜잭션에 포함되지 않는 별도의 Dual Write이며, Notification Service 자체의 Outbox/멱등 키 설계가 별도로 필요 |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것:
DB에서 비즈니스 결과가 Commit되면, 발행해야 할 이벤트 기록도 반드시 같은 DB에 함께 남는다는 것.
즉 "결과는 Commit됐는데 발행 의도가 사라진 상태"가 발생하지 않는다는 것.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record가 물리적으로 정확히 한 번만 생성되는 것, 이벤트가 비즈니스 발생 순서대로 전달되는 것,
모든 Consumer가 반드시 처리를 완료하는 것, 외부 알림(SMS/이메일 등)이 정확히 한 번 전송되는 것.
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

다음 두 이름의 의미 차이를 포함한다.

```
IssueCoupon

CouponIssued
```

```
IssueCoupon → "쿠폰을 발급하라"는 명령(Command). 아직 실행되지 않은 미래의 요청을 뜻한다.
CouponIssued → "쿠폰이 발급되었다"는 이미 발생한 사실(Fact/Event). DB 트랜잭션에서 발급이 확정된 과거의 결과다.

Outbox에 저장되고 Kafka로 전달되는 대상은 "이미 DB에 Commit된 결과"이지, 앞으로 처리해야 할 요청이 아니다.
Consumer가 CouponIssued를 명령으로 오해하면 이벤트를 받고 쿠폰을 다시 발급하려는 시도를 하게 되고,
이는 이미 확정된 결과를 중복 처리하는 문제로 이어진다. 이벤트 이름을 과거형(사실)으로 두면
Consumer는 "이미 일어난 일을 반영만 하면 된다"는 계약을 코드 레벨에서 분명히 알 수 있다.
```

### **3. 다음 ID의 역할을 비교한다**

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 행사(이벤트) 자체 | 바뀌지 않음(같은 행사) | 부적절 — 여러 발급 건이 같은 값을 공유해 구분 불가 |
| couponIssueId | 개별 발급 기록(Aggregate) | 바뀌지 않음 | 부적절 단독 사용 시 위험 — 같은 발급 건에 대해 여러 이벤트(발급/취소 등)가 발생할 수 있어 이벤트 자체를 구분 못함 |
| eventMessageId | 결과 이벤트 메시지 자체 | 재발행해도 동일 값 유지(Outbox 생성 시 확정) | 적절 — Consumer 멱등 처리의 기준 키로 사용 |
| Kafka Partition + Offset | 메시지의 Kafka 내 물리적 위치 | 재발행되면 새로운 Offset을 가짐(값이 바뀜) | 부적절 — 같은 논리 이벤트도 재발행 시 Offset이 달라져 중복 판단 불가 |

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt: 쿠폰 발급이라는 비즈니스 결과가 실제로 발생한 시각. 발급 트랜잭션에서 확정되어 Outbox Payload에
            저장되는, 변하지 않는 값.

publishedAt: Publisher가 Kafka Broker의 ACK를 확인한 뒤 그 사실을 DB에 기록한 시각. Publisher가 언제 발행에
             성공했는지를 나타내는 값으로, 재시도 횟수/타이밍에 따라 매번 달라질 수 있다.

Publisher 재시도 시 변경하면 안 되는 값: occurredAt (그리고 Payload 전체). 재시도는 "같은 사실을 다시
전달하는 것"이므로 이미 발생한 사실의 시각과 내용은 고정되어야 한다. 바뀌는 것은 발행 시도/성공 시각
(publishedAt, attempt_count) 뿐이다.
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
Outbox INSERT 시점과 실제 Kafka 발행 시점 사이에는 시간차가 있다(Polling 주기, 재시도 Backoff 등).
그 사이 원본 데이터(coupon_issue 등)가 다른 트랜잭션에 의해 변경될 수 있다.

Publisher가 발행 시점에 현재 테이블을 다시 조회해서 Payload를 만들면, "이벤트가 발생한 시점의 사실"이
아니라 "발행하는 시점의 최신 상태"가 이벤트에 담기게 되어 이벤트의 의미(불변 Snapshot)가 깨진다.
재시도할 때마다 Payload 내용이 달라질 수도 있다.

따라서 Outbox INSERT 시점에 발행할 Payload를 완전히 확정하여 저장하고, Publisher는 그 값을 그대로
전달만 해야 한다.
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    request_id UUID,

    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),

    CONSTRAINT chk_outbox_schema_version
        CHECK (schema_version >= 1),

    CONSTRAINT chk_outbox_aggregate_version
        CHECK (aggregate_version >= 1),

    CONSTRAINT chk_outbox_attempt_count
        CHECK (attempt_count >= 0)
);
```

### **7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다**

```
outbox_event.event_id
=
payload.eventMessageId
```

```
애플리케이션에서 Outbox 저장용 도메인 객체를 만들 때 event_id로 사용할 UUID를 먼저 생성한 뒤,
그 값을 그대로 payload.eventMessageId에 채워 넣는 방식으로 "한 곳에서 생성해 두 곳에 동시에 씀"으로써
값이 어긋날 여지를 원천적으로 없앤다(서로 다른 두 값을 각각 생성하지 않는다).

DB 레벨에서 더 강하게 강제하고 싶다면 다음과 같은 CHECK 제약을 추가할 수 있다.

CHECK (payload->>'eventMessageId' = event_id::text)

다만 이 방식은 JSONB 파싱 비용이 들기 때문에, 실무에서는 애플리케이션/Repository 테스트로 두 값이
항상 같은 소스에서 나오는지 검증하는 편이 더 실용적이다.
```

### **8. `deduplication_key`를 설계한다**

`CouponIssued`는 하나의 `couponIssueId`에 대해 한 번만 발생한다고 가정한다.

```
Key 형식: {eventType}:{aggregateType}:{aggregateId}

예시: COUPON_ISSUED:COUPON_ISSUE:5001
```

같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면 어떤 값을 추가해야 하는지도 작성한다.

```
같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면(예: CouponUsed가 같은 couponIssueId에서
반복될 수 있는 경우), {eventType}:{aggregateType}:{aggregateId} 형식만으로는 매번 같은 Key가 생성되어
두 번째 발생부터 UNIQUE 위반이 난다.

이 경우 발생 시점(occurredAt)이나 애그리거트 내 시퀀스 번호 같은 추가 구분자를 Key에 포함시켜야 한다.
예: COUPON_USED:COUPON_ISSUE:5001:2026-08-01T10:00:00Z
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

다음 선택지를 비교한다.

```
전체 Rollback 후 새 트랜잭션에서 조회

Savepoint 사용

ON CONFLICT DO NOTHING RETURNING 후
기존 행 조회·동일성 비교
```

```
전체 Rollback 후 새 트랜잭션에서 조회 (이번 설계에서 채택)
→ UNIQUE 위반은 정상 경로에서는 발생하면 안 되는 이상 상황이므로, 전체 트랜잭션을 Rollback하고
  알람을 발생시킨 뒤 별도 트랜잭션에서 원인(요청 상태 관리 결함, Key 생성 버그 등)을 조사한다.
  발급 결과와 Outbox가 반쪽만 반영되는 상태를 만들지 않는다.

Savepoint 사용
→ INSERT 직전에 Savepoint를 두고 위반 시 그 지점까지만 Rollback해 트랜잭션을 이어갈 수 있다.
  다만 "왜 충돌이 났는지" 검증 없이 조용히 넘어가면 설계 결함을 숨길 위험이 있어,
  이번 설계 기조(무조건 알람)와는 맞지 않는다.

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교
→ 멱등 INSERT를 원한다면, 충돌 후 기존 행을 조회해 request_id / aggregate_type / aggregate_id /
  event_type / schema_version / aggregate_version / payload가 모두 같은지 확인하고,
  동일함이 확인된 경우에만 기존 행을 재사용하는 별도 정책을 둘 수 있다.
  이번 설계에서는 기본값으로 채택하지 않고 Rollback + 알람을 기본으로 한다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';

-- affected rows가 몇 행이어야 하는가? → 1행. 0행이면 기존 요청 상태를 재확인해 분기한다.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;

-- affected rows가 0일 때 가능한 원인은 무엇인가? → 수량 소진(SOLD_OUT)이 대표적이며,
-- 이벤트 행이 없거나 이벤트 조건(기간·활성화 상태 등)까지 조건에 넣었다면 그로 인한 0행도 있을 수 있다.

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
) VALUES (
    :couponEventId,
    :userId,
    'ISSUED',
    CURRENT_TIMESTAMP
)
RETURNING id, issued_at;

-- 반환된 값을 couponIssueId, issuedAt으로 사용한다.

-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- affected rows = 1이어야 한다.

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장 (ON CONFLICT 사용하지 않음)
INSERT INTO outbox_event (
    event_id,
    request_id,
    deduplication_key,
    aggregate_type,
    aggregate_id,
    event_type,
    schema_version,
    aggregate_version,
    topic,
    partition_key,
    payload,
    occurred_at
) VALUES (
    :eventMessageId,
    :requestId,
    :deduplicationKey,
    'COUPON_ISSUE',
    CAST(:couponIssueId AS VARCHAR),
    'COUPON_ISSUED',
    1,
    1,
    'coupon.issued',
    CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB),
    :issuedAt
);

COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1행 | 0행이면 즉시 실패로 보지 않고 기존 요청 상태(ISSUED/FAILED/PROCESSING/없음)를 재확인해 분기 처리한다 |
| issued_count 조건부 증가 | 1행(성공 경로) | 0행이면 수량 소진(SOLD_OUT) 등 최종 실패로 판단, coupon_issue INSERT를 진행하지 않고 request FAILED로 트랜잭션을 진행한다 |
| coupon_issue INSERT | 1행 | UNIQUE(event_id, user_id) 위반 시 전체 트랜잭션 실패(Rollback) → 별도 트랜잭션에서 원인 조사 |
| PROCESSING → ISSUED | 1행 | 0행이면 예상 상태와 실제 상태가 어긋난 것이므로 전체 트랜잭션 Rollback |
| outbox_event INSERT | 1행 | 실패(제약 위반 등) 시 전체 트랜잭션 Rollback, 발급 결과만 남기지 않는다 |

### **3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다**

장애 직전 상황은 다음과 같다.

```
issued_count 증가 성공

coupon_issue INSERT 성공

request ISSUED 변경 성공

outbox_event INSERT 실패
```

```
트랜잭션 결과: 전체 Rollback

coupon_event.issued_count: 증가 취소 (원래 값으로 되돌아감)

coupon_issue: 저장 취소 (INSERT 자체가 없었던 것처럼 됨)

coupon_issue_request: ISSUED 변경 취소, PENDING으로 되돌아감 (재처리 대상)

outbox_event: 저장되지 않음
```

### **4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다**

```
발급 결과만 Commit하고 Outbox 저장 실패를 무시하면, "DB에는 쿠폰 발급이 확정되어 있는데 발행할 이벤트
기록은 어디에도 없는" 상태가 만들어진다. 이 상태는 메모리에 이벤트를 들고 있다가 유실하는 것과 본질적으로
같은 문제로, Outbox Pattern이 없애려던 바로 그 장애 상황을 다시 만드는 것이다.

이후 이 발급 건은 어떤 방법으로도 재발행 대상이라는 사실을 찾아낼 수 없다(Outbox 행 자체가 없으므로
Publisher가 조회할 대상도 없음). 후속 서비스(Notification/MyPage/Analytics)는 영구적으로 이 발급 사실을
알 수 없게 된다. 따라서 Outbox INSERT 실패는 반드시 전체 트랜잭션 Rollback으로 이어져야 한다.
```

### **5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다**

```
issued_count를 다시 증가시키는가? → 아니오

coupon_issue를 다시 생성하는가? → 아니오

Outbox를 다시 INSERT하는가? → 아니오

Consumer 처리는 성공으로 종료할 수 있는가? → 예. 첫 번째 UPDATE(PENDING → PROCESSING)가 0행이면
바로 실패로 보지 않고 request 상태를 재조회한다. request = ISSUED라면 이미 완료된 요청의 재전달이므로
아무 작업도 새로 수행하지 않고 정상 처리(성공)로 종료한 뒤 원본 Kafka Offset을 Commit한다.
```

### **6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다**

```
DB 상태: request = ISSUED, coupon_issue 존재 (모두 정상 Commit됨)

Outbox 상태: PENDING (발행 대기 중, 정상 저장됨)

Kafka 원본 메시지: Offset 미반영 상태이므로 재전달될 수 있음

재시작 후 필요한 멱등성 기준: 재전달된 requestId로 request 상태를 재조회했을 때 이미 ISSUED임을 확인하고,
발급 로직과 Outbox INSERT를 다시 실행하지 않은 채 정상 처리로 종료 → Offset Commit.
즉 5주차에서 만든 requestId 기반 멱등 처리가 이 구간의 안전망 역할을 한다.
```

### **7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit

AckMode

Listener 예외 처리

Error Handler가 실패를 정상 처리로 바꾸는지 여부
```

```
enable.auto.commit
→ false로 설정해야 한다. true면 poll() 이후 처리 완료 여부와 무관하게 자동으로 Offset이 앞서 나가
  DB Commit 전에 Offset이 반영되는 유실 위험이 생긴다.

AckMode
→ MANUAL 또는 MANUAL_IMMEDIATE로 설정해, 발급 DB 트랜잭션이 Commit된 뒤에만 명시적으로
  acknowledge()를 호출하도록 한다.

Listener 예외 처리
→ 발급 트랜잭션에서 예외(일시적 DB 오류 등)가 발생하면 Listener가 예외를 다시 던져 Offset을
  Commit하지 않고 원본 메시지가 재전달되도록 해야 한다.

Error Handler가 실패를 정상 처리로 바꾸는지 여부
→ Spring Kafka의 Error Handler(예: DefaultErrorHandler)가 예외를 삼키고 조용히 Offset을 넘겨버리는
  설정이 아닌지 확인해야 한다. 재시도 정책과 최종 실패(DLQ 등) 처리 기준을 명확히 구분해야, 일시적 오류가
  "처리 완료"로 잘못 커밋되는 일을 막을 수 있다.
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                    Publisher B
------------------------------------------------
SELECT event_id
FROM outbox_event
WHERE status = 'PENDING'
LIMIT 50
→ event-1, event-2, ... 조회
                                SELECT event_id
                                FROM outbox_event
                                WHERE status = 'PENDING'
                                LIMIT 50
                                → 동일한 event-1, event-2, ... 조회
                                  (A가 아직 UPDATE하지 않았으므로 같은 PENDING 행이 그대로 보임)

UPDATE outbox_event
SET status = 'PROCESSING'
WHERE event_id IN (event-1, ...)
→ 커밋 전까지는 다른 세션에서
  이 SELECT를 막지 못함

                                UPDATE outbox_event
                                SET status = 'PROCESSING'
                                WHERE event_id IN (event-1, ...)
                                → A, B 둘 다 같은 행을 Claim했다고 믿음

결과: A와 B가 event-1을 동시에 Kafka로 발행 시도 → 같은 이벤트가 중복 발행됨
      (단순 SELECT는 잠금을 걸지 않으므로 두 세션이 같은 PENDING 행을 동시에 후보로 인식한다)
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY
        next_attempt_at,
        created_at,
        event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until =
        CURRENT_TIMESTAMP
        + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id

RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1. DB Connection 장시간 점유 → Connection Pool이 고갈되어 다른 요청/트랜잭션이 커넥션을 얻지 못한다.

2. Row Lock 장시간 유지 → 같은 행에 접근하려는 다른 Publisher나 관리 쿼리가 Kafka 응답 시간만큼
   대기해야 하므로 시스템 전체의 대기 시간이 늘어난다.

3. 트랜잭션 Timeout / Publisher 간 대기 증가 → Kafka ACK 대기 시간이 DB 트랜잭션 Timeout보다 길어지면
   트랜잭션 자체가 실패할 수 있고, 여러 Publisher 인스턴스가 서로 잠금을 기다리며 처리량이 급격히 떨어진다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
인스턴스 수가 하나뿐이더라도, Claim Commit 직후 배포/재시작/장애 등으로 해당 프로세스가 종료될 수 있다.
이 경우 방금 PROCESSING으로 바뀐 행은 Kafka 발행이 시작되기도 전에 "권한을 가진 Publisher가 없는" 상태로
영원히 멈춰버린다. Lease가 없다면 이 행은 status = PROCESSING인 채로 다음 Polling에서도 계속 대상에서
제외되므로(PENDING 조회 조건에 걸리지 않음), 새 Publisher(재시작된 같은 인스턴스 포함)가 다시 시도할
방법이 없어진다. 따라서 Publisher 인스턴스 수와 무관하게 "Claim한 프로세스가 죽을 수 있다"는 전제 아래
Lease 또는 시작 시 stale PROCESSING 복구 로직이 반드시 필요하다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Publisher A
→ token-A로 Claim
→ 처리 지연
→ Lease 만료

Publisher B
→ 만료 행 회수
→ token-B로 Claim

Publisher A
→ 뒤늦게 성공 또는 실패 상태 UPDATE
```

```
Claim Token이 없다면 Publisher A는 자신이 여전히 처리 권한을 가지고 있다고 믿고 event_id만으로
상태 UPDATE를 시도한다. 하지만 이미 Publisher B가 같은 행을 회수해 새로 처리(또는 완료)한 뒤이므로,
A의 뒤늦은 UPDATE가 B의 최신 상태를 그대로 덮어쓸 수 있다.

예를 들어 B가 성공적으로 PUBLISHED로 바꾼 직후 A의 지연된 "성공 UPDATE"가 실행되면 문제는 없어 보이지만,
A의 지연된 "실패(PENDING으로 되돌림) UPDATE"가 나중에 실행되면 이미 PUBLISHED된 행이 다시 PENDING으로
바뀌어 또 다른 Publisher가 이미 발행된 이벤트를 재발행하게 된다. 즉 claim_token 없이는 "지금 이 상태
변경을 시도하는 내가 최신 처리 권한을 가진 Publisher가 맞는지"를 검증할 방법이 없어, 최신 처리자의
결과가 오래된 처리자에 의해 덮어써지는 경쟁 상태가 발생한다.
```

### **7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### **8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다**

```
Lease 시간
>

batchSize × 건당 최대 대기 시간(Publisher get() timeout)

+

여유 시간(Buffer)

Lease가 너무 짧으면 Kafka 발행이 아직 진행 중인데 Lease가 만료되어 다른 Publisher가 같은 행을 회수해
동시에 중복 발행할 수 있으므로, Batch 전체를 순차 동기 처리하는 데 걸리는 최대 시간보다 충분히 길게
Lease를 잡아야 한다.
```

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료: send() 메서드 호출 자체가 끝나 CompletableFuture를 반환받은 상태.
  Kafka Broker에 실제로 전달되었는지는 아직 알 수 없다.

CompletableFuture 정상 완료: Producer가 Broker로부터 ACK(acks 설정에 따른 확인)를 받아 Future가
  성공적으로 완료된 상태. Kafka에 Record가 저장되었다고 신뢰할 수 있는 시점.

outbox = PUBLISHED: Broker ACK 확인 후, 그 사실을 Outbox 테이블에도 반영해 DB에 영속적으로 기록한 상태.
  ACK 확인과 DB 기록 사이에도 시간차가 있어 이 상태로 바뀌기 전에 장애가 날 수 있다.

모든 후속 Consumer 처리 완료: Notification/MyPage/Analytics 등 모든 Consumer Group이 각자의 비즈니스
  로직까지 반영을 끝낸 상태. outbox = PUBLISHED와는 전혀 다른 차원의 완료이며 Outbox가 보장하지 않는 영역이다.
```

### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
상황 A: 실제로 Record가 없음 (Broker 장애, 네트워크 단절 등으로 전송 자체가 실패)
상황 B: 실제로는 Record가 존재함 (Broker 응답이 네트워크 지연으로 늦게 도착하거나 유실된 경우)

Publisher 입장에서는 자신이 받은 것이 "Timeout"이라는 사실뿐이며, 그 원인이 A인지 B인지 구분할 방법이
없다. 만약 Timeout을 곧바로 "발행 실패"로 단정해 PUBLISHED로 표시하지 않고 재시도한다면, 상황 B에서는
이미 Broker에 저장된 Record와 재시도로 만들어진 새 Record가 함께 존재하는 중복이 발생한다.
그렇다고 Timeout을 성공으로 간주할 수도 없으므로(상황 A일 수 있으므로), 안전한 선택은 "미완료로 남기고
재시도하되 중복 가능성은 Consumer가 방어한다"는 것이다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태: PROCESSING → (재시도 로직에 의해) PENDING, next_attempt_at을 미래 시각으로 설정

재시도 여부: 재시도한다. Timeout만으로 최종 실패로 확정하지 않는다.

Kafka 중복 가능성: 있음 (상황 B처럼 이미 Broker에 저장된 뒤 재시도로 같은 논리 이벤트가 다시 발행될 수 있음)

Consumer에게 필요한 방어: eventMessageId 기반 멱등 처리(processed_event 등)로 같은 이벤트가 여러 번
전달되어도 비즈니스 반영은 한 번만 되도록 방어해야 한다.
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff: 재시도할 때마다 대기 시간을 지수적으로 늘려(1초 → 2초 → 4초 → 8초 …), Kafka나
네트워크에 일시적 장애가 발생했을 때 실패한 요청들이 즉시 반복 재시도하며 장애 중인 Broker에 부하를
추가로 몰아주는 것을 막는다. 장애가 지속되는 동안 재시도 빈도를 자연스럽게 줄여준다.

Jitter: 여러 Publisher 인스턴스(또는 여러 이벤트)가 동시에 같은 Backoff 스케줄을 따르면 정확히 같은
시각에 한꺼번에 재시도가 몰리는 "Thundering Herd" 현상이 생길 수 있다. 계산된 대기 시간에 작은
무작위값을 더해 재시도 시각을 분산시켜 이를 완화한다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | O | Producer가 PID + Sequence Number로 같은 배치의 중복 전송을 Broker 레벨에서 걸러내도록 설계된 기능이므로 해당 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | X | 이미 Broker에 정상적으로 한 번 저장된 뒤 벌어지는 애플리케이션 레벨 재발행(새로운 send() 호출)이므로 Producer 내부 재시도가 아니라 Idempotence 범위 밖 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | X | 애플리케이션(운영자) 주도로 새로운 발행 요청을 만드는 것이므로 Producer 입장에서는 완전히 새로운 전송이며, Idempotence가 막을 수 있는 "Producer 내부 재시도"가 아님 |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
future.whenComplete(...)의 콜백은 Future를 완료시킨 스레드에서 실행되는데, 이 스레드는 Kafka Producer의
내부 Sender 스레드다. 이 콜백 안에서 DB Connection Pool 대기, 트랜잭션 Commit 대기 같은 블로킹 I/O를
수행하면 Sender 스레드 자체가 블로킹되고, 그 Producer의 모든 전송이 함께 지연된다.

부하 상황에서는 다음 연쇄 장애로 이어질 수 있다: Sender 스레드 블로킹 → 발행 지연 증가 → Lease 만료 →
다른 Publisher가 회수 → 중복 발행 증가 → 적체 심화.

따라서 콜백에서는 절대 블로킹 작업을 하지 않아야 하며, whenCompleteAsync(...)와 전용 Executor를 지정해
DB 작업(markPublished/scheduleRetry)을 Producer의 I/O 스레드가 아닌 별도 스레드 풀에서 수행해야 한다.
```

## **과제 6. Outbox 장애 시나리오 분석하기**

각 장애 시나리오에 대해 다음을 작성한다.

```
DB의 비즈니스 상태

Outbox 상태

Kafka Record 존재 가능성

복구 주체

중복 가능성
```

### **1. 발급 트랜잭션 Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 저장되지 않음 (Rollback) |
| request | PENDING 그대로 (또는 Rollback되어 PENDING으로 복귀) |
| outbox_event | 저장되지 않음 |
| 복구 방법 | 원본 `coupon.issue.requested` 메시지 재처리 (Offset이 Commit되지 않았으므로 자연스럽게 재전달됨) |

### **2. 발급 DB Commit 후 원본 Offset Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 존재함 (정상 Commit) |
| request | ISSUED (정상 Commit) |
| outbox_event | PENDING으로 존재함 (정상 Commit) |
| 원본 Kafka 메시지 | Offset 미반영 → 재전달 가능 |
| 복구 방법 | requestId 기반 멱등 처리 — 재전달된 메시지에서 request가 이미 ISSUED임을 확인하고 새 발급/새 Outbox 없이 정상 종료 후 Offset Commit |

### **3. Outbox Claim Commit 후 Kafka 발행 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING (Claim Commit까지는 성공했으므로) |
| Kafka Record | 없음 (발행 자체가 시작되지 못함) |
| 복구 조건 | lease_until 만료 |
| 복구 주체 | 다른 Publisher(또는 재시작된 동일 인스턴스)가 만료된 PROCESSING을 PENDING으로 회수해 재발행 |

### **4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING (그대로 남거나, Lease 만료 후 PENDING으로 복구됨) |
| Kafka Record | 존재함 (Broker ACK까지 받은 뒤 종료된 것이므로) |
| 재발행 가능성 | 있음 — Lease 만료 후 다른 Publisher가 같은 이벤트를 다시 발행할 수 있음 |
| 필요한 Consumer 방어 | eventMessageId 기반 멱등 처리(processed_event)로 중복 비즈니스 반영 방지 |

### **5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황**

```
Publisher A가 늦게 성공 UPDATE: WHERE 조건에 claim_token = token-A가 포함되어 있으므로,
이미 B가 claim_token을 token-B로 바꿔놓은 상태에서는 조건이 맞지 않아 affected rows = 0 →
A의 UPDATE는 아무 효과도 내지 못하고 조용히 무시된다.

Publisher A가 늦게 실패 UPDATE: 마찬가지로 claim_token = token-A 조건이 더 이상 일치하지 않으므로
affected rows = 0 → B가 이미 만들어 놓은 최신 상태(PUBLISHED 또는 새로운 PROCESSING)를 A가 덮어쓰지 못한다.

두 UPDATE에서 affected rows가 0이어야 하는 조건: event_id는 같지만 claim_token이 더 이상 A의 token과
일치하지 않는 경우(B가 이미 회수해 claim_token을 교체했거나, B의 처리가 끝나 PUBLISHED로 바뀌어
status 자체가 PROCESSING이 아니게 된 경우).
```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화: Outbox 생성 속도만큼 계속 증가한다. 발행이 전혀 성공하지 못하므로 순수하게 누적된다.

가장 오래된 PENDING 대기 시간: 장애 시작 시점부터 계속 늘어나 최대 30분 이상까지 증가한다.

attempt_count: 재시도가 반복될 때마다 계속 증가한다. Backoff로 인해 재시도 간격은 점점 벌어지지만
30분이면 여러 차례 재시도가 누적된다.

Kafka 복구 후 처리: 쌓여 있던 PENDING 행들이 다음 Polling 주기부터 순차적으로(단, SKIP LOCKED/재시도
지연으로 인해 저장 순서와 다르게) Claim되어 발행되기 시작한다. 적체된 물량 때문에 정상 상태로 돌아오기까지
추가 시간이 걸릴 수 있다.

운영 알람: PENDING 수 급증, 가장 오래된 PENDING 대기 시간 임계치 초과, attempt_count 급증 등의 지표를
기준으로 장애 발생 시점에 이미 알람이 울렸어야 한다.
```

### **7. 다음 두 재시도 대상을 구분한다**

```
발급 DB 트랜잭션 실패: coupon_issue/request/outbox_event 모두 저장되지 않은 상태이므로,
원본 coupon.issue.requested 메시지 자체를 재처리해야 한다 (발급 로직을 처음부터 다시 실행).

발급 DB Commit 성공 후 CouponIssued 발행 실패: 쿠폰은 이미 정상적으로 발급되어 DB에 확정된 상태이므로
발급 로직을 다시 실행하면 안 된다. Outbox에 남아 있는 이벤트만 재발행하면 된다.
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유도 작성한다.

```
발급 성공 여부는 오직 DB 트랜잭션의 Commit 여부로만 판단한다. 이 트랜잭션은 이미 Commit되어
coupon_event.issued_count, coupon_issue, request가 모두 확정된 상태다. 여기서 재발급을 시도하면
issued_count가 다시 증가하거나 coupon_issue가 중복 생성되어(UNIQUE 제약 위반 또는 수량 초과 발급)
비즈니스 정합성이 깨진다. 결과 이벤트 발행은 "이미 확정된 사실을 후속 서비스에 알리는" 부수 작업일 뿐,
발급 자체의 성공/실패를 결정하는 기준이 아니다.
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001

Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
Kafka의 Partition/Offset은 메시지의 물리적 위치일 뿐, 논리적 이벤트의 정체성을 나타내지 않는다.
같은 논리 이벤트(eventMessageId = evt-001)가 Publisher 재시도로 재발행되면 서로 다른 Offset
(예: Offset 100, Offset 101)을 갖게 된다.

Offset을 멱등성 Key로 사용하면 Consumer는 이 두 레코드를 "서로 다른 이벤트"로 인식해 각각 처리하게
되고, 결국 같은 비즈니스 결과가 두 번 반영된다. 멱등성 Key는 "메시지가 어디에 있는지"가 아니라
"어떤 사실을 나타내는지"를 기준으로 삼아야 하므로, 재발행되어도 값이 바뀌지 않는 eventMessageId를
사용해야 한다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (
        subscriber_id,
        event_id
    )
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

다음 중 적절한 값을 선택하고 이유를 작성한다.

```
pod-7f8c9d

server-10.0.0.12

mypage-coupon-projection
```

```
적절한 값: mypage-coupon-projection

pod-7f8c9d나 server-10.0.0.12 같은 값은 재배포·스케일링·재시작마다 바뀌는 "실행 중인 프로세스"의
식별자다. 이 값을 subscriber_id로 쓰면, 인스턴스가 재시작되어 새 pod ID를 받는 순간 이전 pod가
처리했던 이벤트 기록과 완전히 단절된 새로운 subscriber로 취급되어, 이미 처리한 이벤트도 처음 보는
이벤트처럼 다시 처리하게 된다.

mypage-coupon-projection처럼 "이 로직을 수행하는 논리적 구독자가 누구인지"를 나타내는 안정적인
이름을 사용해야, 어떤 인스턴스가 처리하든 같은 subscriber_id로 processed_event가 누적되어
중복 방어가 인스턴스 교체와 무관하게 계속 유지된다.
```

### **4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다**

```sql
BEGIN;

-- 1. eventMessageId 중복 확인
INSERT INTO processed_event (
    subscriber_id,
    event_id
) VALUES (
    'mypage-coupon-projection',
    :eventMessageId
)
ON CONFLICT DO NOTHING
RETURNING event_id;

-- 반환된 행이 없으면 이미 처리한 이벤트이므로 아래 2번을 건너뛰고 커밋 후 종료한다.

-- 2. 최초 이벤트인 경우에만 조회 모델 변경
INSERT INTO user_coupon_view (
    user_id,
    coupon_issue_id,
    coupon_event_id,
    issued_at
) VALUES (
    :userId,
    :couponIssueId,
    :couponEventId,
    :issuedAt
);

COMMIT;
```

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다**

```
Consumer DB 상태: processed_event 저장 완료, user_coupon_view 변경 완료 (모두 정상 Commit됨)

Consumer Group Offset: 아직 반영되지 않음

재시작 후 Kafka 전달: 같은 Kafka Record(같은 eventMessageId)가 재전달될 수 있음

재전달된 이벤트 처리: processed_event INSERT가 ON CONFLICT DO NOTHING으로 중복 판정되어(반환 행 없음)
조회 모델 변경(2번)을 다시 수행하지 않고 정상 처리로 종료 → Offset Commit
```

### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**

```
processed_event는 Consumer 자신의 로컬 DB 트랜잭션 안에서만 원자성을 보장한다. 외부 SMS API 호출은
이 로컬 트랜잭션에 포함되지 않는 별도의 Dual Write이므로, "processed_event는 저장됐지만 SMS는
전송되지 않은 상태"나 "SMS는 전송됐지만 processed_event Commit 전에 프로세스가 죽는 상태"가
똑같이 발생할 수 있다. processed_event는 어디까지나 "Consumer 내부 비즈니스 반영"의 중복을 막을 뿐,
외부 시스템 호출까지 원자적으로 묶어주지는 않는다.
```

### **7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다**

```
1. Notification Service 내부에도 별도의 Outbox를 두어 "SMS를 보내야 한다"는 의도를 로컬 DB 트랜잭션에
   커밋한 뒤, 별도의 Sender가 그 Outbox를 읽어 SMS Provider를 호출하도록 한다 (이번 주차 패턴을 한 단계
   더 내부에 적용).

2. 알림 발송 작업을 나타내는 별도의 작업 테이블(notification_task)과 Sender를 분리해, 발송 시도/성공/
   실패 상태를 추적하고 재시도 가능하게 만든다.

3. 외부 SMS Provider가 지원하는 Idempotency Key(예: notificationId)를 발급 요청에 함께 실어 보내,
   같은 notificationId로 여러 번 요청해도 Provider 쪽에서 중복 발송을 걸러내도록 한다.
```

### **8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다**

다음을 포함한다.

```
Kafka Topic 보관 기간

Consumer Offset 되감기

Outbox 지연 재발행

운영자 수동 재발행
```

```
Kafka Topic 보관 기간: Topic에 Record가 남아 있는 한 언제든 재전달될 수 있으므로,
processed_event 보관 기간은 최소 Kafka Topic 보관 기간보다 길어야 한다.

Consumer Offset 되감기: 운영자가 장애 복구나 재처리 목적으로 Consumer Group Offset을 과거로
되돌리면, 이미 처리했던 이벤트가 다시 전달될 수 있다.

Outbox 지연 재발행: Publisher의 Lease 만료·재시도 등으로 Outbox 이벤트가 정상 발행 시점보다
한참 뒤에 재발행될 수 있으므로, 그 최대 지연 시간만큼 여유를 둬야 한다.

운영자 수동 재발행: 장애 조사나 복구 과정에서 운영자가 특정 Outbox 행이나 Kafka Record를
수동으로 다시 발행시키는 경우도 재전달 경로에 포함해야 한다.

따라서 processed_event 보관 기간 > Kafka Topic 보관 기간 + 위 요인들을 모두 포함한 최대 재전달 지연
이어야 중복 방어가 뚫리지 않는다.
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateType = COUPON_ISSUE

aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
1. 같은 Aggregate(CouponIssue)의 이벤트를 한 Partition에 모아, Consumer의 병렬 처리 단위를
   명확히 하기 위함이다.

2. 특정 Partition으로 부하가 몰리지 않도록 여러 Aggregate의 이벤트를 여러 Partition에 고르게
   분산시키기 위함이다.

3. 향후 순서 보장이 필요해질 때(예: Aggregate 단위 직렬화) 기준이 될 단위를 미리 정해두기 위함이다.
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

다음을 반드시 포함한다.

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
Kafka에서 같은 Partition Key를 가진 Record는 같은 Partition으로 전달되지만, Partition 안의 순서는
"비즈니스 발생 순서"가 아니라 "Producer가 send()를 호출한 순서"로 결정된다. Polling Outbox Publisher
구조에서는 이 호출 순서가 DB 저장 순서와 달라질 수 있는 원인이 여러 가지 있다.

여러 Publisher 인스턴스: 서로 다른 인스턴스가 서로 다른 속도로 이벤트를 처리하므로, 먼저 저장된
이벤트를 담당한 인스턴스가 느리면 나중에 저장된 이벤트가 먼저 발행될 수 있다.

SKIP LOCKED: 잠긴 행을 건너뛰고 다음 행을 Claim하는 장치이므로, 애초에 저장 순서를 지키지 않고
가져갈 수 있는 행부터 처리하도록 설계되어 있다.

발행 실패와 Backoff: 먼저 저장된 이벤트가 발행에 실패하면 next_attempt_at이 뒤로 밀려, 나중에
저장된 이벤트가 먼저 재시도되어 발행될 수 있다.

Producer 설정과 재시도: Producer 내부 재시도나 네트워크 지연으로 인해 실제로 Broker에 도달하는
순서가 send() 호출 순서와도 어긋날 수 있다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A: outbox 1(CouponIssued) Claim → Kafka 발행 실패 → PENDING, next_attempt_at = +4초

Publisher B: outbox 2(CouponCancelled) Claim → 발행 성공

Kafka 저장 순서:
Offset 200: CouponCancelled
Offset 201: CouponIssued
```

### **4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다**

```
1. 서로 다른 이벤트가 우연히 같은 Timestamp를 가질 수 있다 (동시 처리, 초 단위 정밀도 등).

2. 서버나 DB의 시간 정밀도, 그리고 여러 컴포넌트의 시계가 완전히 일치하지 않을 수 있어
   실제 발생 순서와 Timestamp 대소 관계가 어긋날 수 있다.

3. 조회 행이 아예 없는 경우(최초 이벤트)와 이미 더 최신 이벤트가 반영되어 있어 무시해야 하는 경우를
   occurredAt 비교만으로는 하나의 UPDATE 조건으로 명확히 구분하기 어렵다. (aggregateVersion처럼
   단조 증가하는 정수가 아니므로 "더 크다/같다/없다"를 안정적으로 판별하기 힘들다.)
```

### **5. MyPage처럼 최신 상태만 필요한 Projection의 순서 역전 방어 SQL을 작성한다**

다음 컬럼을 사용한다.

```
coupon_issue_id

status

last_aggregate_version

last_event_at
```

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id,
    user_id,
    coupon_event_id,
    status,
    last_aggregate_version,
    last_event_at
) VALUES (
    :couponIssueId,
    :userId,
    :couponEventId,
    :newStatus,
    :aggregateVersion,

    last_aggregate_version = EXCLUDED.last_aggregate_version,

      < EXCLUDED.last_aggregate_version;

### **6. aggregateVersion이 더 큰 이벤트가 먼저 도착한 경우의 결과를 작성한다**

```
먼저 도착:
CouponCancelled(version=2)

나중 도착:
CouponIssued(version=1)

최종 MyPage 상태: CouponCancelled(version=2)가 먼저 반영되어 취소 상태로 저장되고,
last_aggregate_version = 2로 기록된다.

version=1 처리 결과: 나중에 도착한 CouponIssued(version=1)는 UPDATE 조건
(last_aggregate_version < EXCLUDED.last_aggregate_version, 즉 2 < 1)을 만족하지 못해
affected rows = 0이 되고, 상태 변경 없이 생략된다. 즉 오래된 이벤트가 최신 상태(취소됨)를
발급 상태로 되돌리지 못한다.

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않고 대기 중인 이벤트 수 | 계속 증가 추세를 보이며 줄어들지 않는 상태 |
| 가장 오래된 PENDING 대기 시간 | 가장 오래 발행을 기다리고 있는 이벤트의 나이 | 임계치(예: 수 분~수십 분) 이상 계속 늘어나는 상태 |
| PROCESSING 이벤트 수 | 현재 어떤 Publisher가 발행 권한을 가지고 처리 중인 이벤트 수 | 정상 처리량 대비 비정상적으로 많이 쌓여 있는 상태 |
| 만료된 PROCESSING 수 | Lease가 지났는데도 아직 회수되지 않은 이벤트 수 | 0이 아니거나 반복적으로 발생하는 상태 (Publisher가 죽고 회수가 지연되고 있다는 신호) |
| attempt_count | 하나의 이벤트가 발행 권한을 얻은(Claim된) 횟수 | 특정 이벤트의 attempt_count가 계속 증가하며 줄지 않는 상태 (반복 실패 신호) |
| Outbox 생성 처리량 | 시간당 새로 저장되는 Outbox 행 수 | 발급 트래픽 대비 비정상적으로 급증/급감하는 상태 |
| Kafka 발행 처리량 | 시간당 PUBLISHED로 전환되는 Outbox 행 수 | 생성 처리량보다 지속적으로 낮은 상태 (적체가 계속 쌓이고 있다는 신호) |
| DB 발생부터 Kafka ACK까지의 시간 | 이벤트가 DB에 확정된 시점부터 실제 Kafka에 전달 완료되기까지 걸린 지연 시간 | 이 지연이 SLA 기준치를 넘어서거나 계속 늘어나는 상태 |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량: (2,000 - 1,500) × 60초 = 30,000건

10분 후 예상 적체 증가량: (2,000 - 1,500) × 600초 = 300,000건

가장 먼저 확인할 지표: PENDING 이벤트 수 증가 추세와 가장 오래된 PENDING 대기 시간

가능한 대응: Publisher 인스턴스 수 또는 batchSize를 늘려 처리량을 확보, Kafka Producer/Broker 쪽
병목(네트워크, Broker 부하 등) 확인, 필요 시 발급 요청 자체의 유입 속도를 제한(Rate Limit)하는 것도
검토. 처리량 격차가 계속되면 적체가 선형으로 계속 쌓이므로 조기에 알람이 필요하다.
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. deduplication_key UNIQUE 위반 발생 (정상 경로에서는 절대 발생하면 안 되는 이상 상황)

2. Commit된 request = PROCESSING 상태가 관측됨 (설계상 PROCESSING은 트랜잭션 내부에서만 존재해야 함)

3. Lease가 만료된 PROCESSING 행이 반복적으로 발생 (Publisher가 비정상 종료를 반복하고 있다는 신호)

4. SOLD_OUT 또는 DUPLICATE_USER 확정이 반복적으로 발생 (Redis와 DB 상태가 수렴하지 않는다는 신호)
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면: 아직 한 번도 발행되지 않은 이벤트를 영구히 잃는다. 후속 서비스는 해당 발급 사실을
영원히 알 수 없게 되어 Outbox Pattern이 보장하려던 것 자체가 깨진다.

PROCESSING을 삭제하면: 어떤 Publisher가 지금 처리하고 있을 수도 있는(혹은 처리하다 죽었을 수도 있는)
이벤트를 삭제하는 것이므로, 발행되었는지 여부를 확인할 방법 자체가 사라진다.

PUBLISHED를 보관하는 목적: 이미 Kafka ACK까지 확인되어 전달 책임이 Kafka/Consumer Group으로 넘어간
행이므로 삭제해도 발행 자체에는 문제가 없다. 다만 일정 기간은 발행 이력 확인, 장애 조사, 감사 목적으로
보관해 둔다.
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

다음 항목을 포함한다.

```
긴 트랜잭션

DB 부하

Lock

Table Bloat
```

```
긴 트랜잭션: 한 번에 수십만~수백만 건을 삭제하면 트랜잭션이 오래 걸려 다른 작업과 충돌하거나 Timeout이
날 수 있다.

DB 부하: 대량 DELETE는 순간적으로 큰 I/O와 CPU 부하를 유발해 다른 쿼리(Claim, INSERT 등)의 응답 속도에
영향을 준다.

Lock: 삭제 대상 범위에 걸쳐 있는 인덱스/행 Lock이 오래 유지되면 동시에 진행 중인 Publisher의 Claim이나
새로운 Outbox INSERT가 지연될 수 있다.

Table Bloat: PostgreSQL은 삭제된 행을 즉시 물리적으로 회수하지 않고 Dead Tuple로 남기므로, 대량 삭제가
한 번에 몰리면 테이블/인덱스가 부풀고 VACUUM 부담이 커진다.
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
1. PUBLISHED이면서 published_at < :cutoff(보관 기간 경과)인 행을 대상으로 선정
2. 예: 1,000건 단위로 DELETE
3. 그 Batch를 Commit
4. 짧게 대기(다른 트랜잭션이 진행할 시간을 확보)
5. 남은 대상이 없을 때까지 2~4를 반복
```

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |

### **8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다**

```
last_error 컬럼은 검색·조회가 쉬운 DB 테이블에 저장되며, 운영자뿐 아니라 여러 도구·대시보드에서
직접 조회될 수 있다. 전체 Stack Trace를 그대로 저장하면 컬럼 크기가 과도하게 커지고, 내부 클래스
구조나 쿼리 파라미터, 사용자 개인정보 같은 민감 정보가 노출될 위험이 있다.

따라서 DB에는 검색 가능한 짧은 오류 분류와 요약 메시지만 저장하고, 상세 Stack Trace와 진단 정보는
접근이 통제된 로그·트레이싱 시스템에 남기는 것이 안전하다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

```
문제 위치:

문제 내용:

발생 가능한 장애:

수정 방법:
```

```
문제 1
문제 위치: issueCoupon() 내부 kafkaTemplate.send()
문제 내용: 발급 DB 트랜잭션 안에서 Kafka를 직접 호출한다.
발생 가능한 장애: DB Commit과 Kafka 발행이 원자적으로 묶이지 않아, Commit 후 발행 전 종료 시
                 이벤트가 유실되거나, 발행 후 Commit 실패 시 존재하지 않는 발급 건의 이벤트가 남는다.
수정 방법: Kafka 호출을 제거하고, 같은 트랜잭션에 outbox_event INSERT만 추가한다.

문제 2
문제 위치: issueCoupon() 전체
문제 내용: outbox_event를 저장하는 코드 자체가 없다. 발급 결과와 발행 의도가 같은 트랜잭션에 저장되지 않는다.
발생 가능한 장애: Kafka 발행이 실패해도 재발행할 근거가 DB 어디에도 없어 이벤트가 영구 유실된다.
수정 방법: coupon_issue 저장과 같은 트랜잭션 안에서 outbox_event를 INSERT한다.

문제 3
문제 위치: publishOutbox() 내 outboxRepository.findTop100ByStatus("PENDING")
문제 내용: 단순 SELECT로 PENDING 행을 조회할 뿐, FOR UPDATE SKIP LOCKED 같은 잠금 장치가 없다.
발생 가능한 장애: 여러 Publisher 인스턴스가 동시에 같은 PENDING 행을 가져가 동일 이벤트를 중복 발행한다.
수정 방법: FOR UPDATE SKIP LOCKED로 후보를 잠그고 PROCESSING으로 변경하는 Claim 쿼리로 교체한다.

문제 4
문제 위치: publishOutbox() 메서드 전체에 걸린 @Transactional
문제 내용: 100건의 Kafka 발행(네트워크 I/O)이 하나의 DB 트랜잭션 안에서 순차적으로 일어난다.
발생 가능한 장애: DB Connection과 Row Lock을 오래 점유해 Connection Pool 고갈, 다른 Publisher의
                 대기 증가, 트랜잭션 Timeout이 발생할 수 있다.
수정 방법: Claim 트랜잭션(짧게 Commit) → 트랜잭션 밖에서 Kafka 발행 → 완료 상태 트랜잭션(짧게 Commit)
          으로 단계를 분리한다.

문제 5
문제 위치: publishOutbox() 내 kafkaTemplate.send(...) 직후 event.markPublished()
문제 내용: send()의 결과(ACK)를 확인하지 않고 즉시 PUBLISHED로 표시한다.
발생 가능한 장애: 실제로는 Broker에 저장되지 못했는데 PUBLISHED로 기록되어, 실패한 이벤트가 영구히
                 재시도 대상에서 빠진다(이벤트 유실).
수정 방법: send(...).get(timeout)으로 ACK를 확인한 뒤에만 PUBLISHED로 변경하고, 실패/Timeout 시
          PENDING으로 되돌려 재시도한다.

문제 6
문제 위치: OutboxEvent 엔티티/publishOutbox() 전체
문제 내용: claim_token 개념 자체가 없다.
발생 가능한 장애: Lease가 만료되어 다른 Publisher가 같은 행을 회수한 뒤, 원래 Publisher의 뒤늦은
                 상태 변경이 최신 처리자의 결과를 덮어쓸 수 있다(예: 이미 PUBLISHED된 행이 다시
                 PENDING으로 되돌아가 재발행됨).
수정 방법: Claim 시 claim_token을 발급해 저장하고, 이후 모든 상태 변경 UPDATE의 WHERE 절에
          claim_token 일치 조건을 포함시킨다.

문제 7
문제 위치: recoverProcessing()의 outboxRepository.updateAllProcessingToPending()
문제 내용: lease_until 만료 여부와 무관하게 모든 PROCESSING 행을 무조건 PENDING으로 되돌린다.
발생 가능한 장애: 다른 Publisher가 지금 정상적으로 처리 중인(Lease가 아직 유효한) 이벤트까지 회수되어,
                 두 Publisher가 같은 이벤트를 동시에 발행하는 중복이 발생한다.
수정 방법: WHERE status = 'PROCESSING' AND lease_until <= CURRENT_TIMESTAMP 조건으로 만료된
          행만 회수하도록 제한한다.

문제 8
문제 위치: publishOutbox() 내 createPayloadFromCurrentCouponIssue(event)
문제 내용: 발행 시점에 현재 coupon_issue 테이블을 다시 조회해 Payload를 새로 만든다.
발생 가능한 장애: Outbox 저장 시점과 발행 시점 사이에 원본 데이터가 바뀌면 이벤트 내용이 실제 발생
                 시점의 사실과 달라진다. 재시도할 때마다 Payload가 달라질 수도 있다.
수정 방법: Outbox INSERT 시점에 Payload를 완전히 확정해 저장하고, Publisher는 저장된 값을 그대로
          전달만 한다.

문제 9
문제 위치: onResult()의 new ProcessedEvent(event.getKafkaPartition(), event.getKafkaOffset())
문제 내용: Kafka Partition + Offset을 멱등성 Key로 사용한다.
발생 가능한 장애: 같은 논리 이벤트가 재발행되면 서로 다른 Offset을 가지므로, Consumer가 같은 이벤트를
                 서로 다른 이벤트로 착각해 비즈니스 반영을 중복 수행한다.
수정 방법: eventMessageId를 멱등성 Key로 사용하도록 ProcessedEvent를 (subscriber_id, event_id)
          기준으로 저장한다.

문제 10
문제 위치: onResult() 메서드 전체
문제 내용: @Transactional이 없고, processed_event 저장(중복 확인)보다 비즈니스 변경(userCouponViewRepository.save())을
          먼저 무조건 수행한 뒤 처리 기록을 남긴다. 중복 여부를 먼저 확인하는 로직도 없다.
발생 가능한 장애: 두 저장이 원자적으로 묶이지 않아 하나만 반영되고 다른 하나는 실패하는 반쪽짜리 상태가
                 생길 수 있고, 애초에 중복 체크가 없으므로 같은 이벤트가 재전달될 때마다 조회 모델이
                 계속 중복 반영된다.
수정 방법: 하나의 트랜잭션 안에서 먼저 processed_event를 INSERT ... ON CONFLICT DO NOTHING으로
          시도하고, 반환된 행이 있을 때(최초 처리)만 비즈니스 변경을 수행하도록 순서를 바꾼다.
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 로컬 DB 트랜잭션에 coupon_issue와 outbox_event INSERT를 함께 커밋하므로 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | Timeout·Lease 만료 등으로 같은 이벤트가 물리적으로 여러 Record로 재발행될 수 있음 |
| Publisher 복구 후 재발행 | 보장 | PENDING 행과 Lease 만료 복구 로직이 있는 한, Publisher가 살아있고 Kafka가 복구되면 언젠가 발행됨 (At-Least-Once) |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED, Backoff 재시도, 여러 Publisher 인스턴스로 인해 저장 순서와 발행 순서가 달라질 수 있음 |
| Consumer의 중복 비즈니스 반영 방지 | 보장 | eventMessageId 기준 processed_event 멱등 체크로 같은 이벤트의 중복 반영을 막음 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | Outbox/Publisher는 Kafka까지 전달할 뿐, 각 Consumer Group의 실제 처리 완료 여부는 별도로 관리해야 함 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | processed_event는 로컬 DB 반영의 중복만 막을 뿐 외부 API 호출은 별도의 Dual Write이며, Notification Service 자체의 추가 설계(내부 Outbox, Idempotency Key 등)가 필요함 |
