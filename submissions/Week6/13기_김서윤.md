# **6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성**

## **1. 과제 목표**

이번 과제의 목표는 **쿠폰 발급 결과를 PostgreSQL에 저장하는 작업과 `CouponIssued` 이벤트를 Kafka에 발행하는 작업 사이의 Dual Write 문제를 분석하고, Transactional Outbox Pattern으로 복구 가능한 이벤트 발행 구조를 설계하는 것**이다.

5주차까지 쿠폰 발급 Consumer는 다음 작업을 하나의 DB 트랜잭션으로 처리했다.

```
coupon_issue_request PENDING → PROCESSING

coupon_event.issued_count 증가

coupon_issue 발급 기록 저장

coupon_issue_request → ISSUED
```

DB 트랜잭션이 Commit된 시점을 최종 쿠폰 발급 성공으로 본다.

하지만 발급 결과를 Notification, MyPage, Analytics 같은 후속 서비스에 전달하려면 별도의 결과 이벤트가 필요하다.

```
PostgreSQL
→ 쿠폰 발급 결과 저장

Kafka
→ CouponIssued 이벤트 발행
```

PostgreSQL과 Kafka는 서로 다른 시스템이다.

하나의 메서드 안에서 두 작업을 호출하거나 DB 메서드에 `@Transactional`을 붙이는 것만으로는 두 시스템이 하나의 원자적 트랜잭션이 되지 않는다.

이번 과제에서는 다음 구조를 설계한다.

```
Coupon Issue Consumer
        ↓
+------------------------------------------+
| PostgreSQL Transaction                   |
|------------------------------------------|
| coupon_issue 저장                        |
| request ISSUED 변경                      |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        ↓ Commit
Outbox Publisher
        ↓
Kafka coupon.issued
        ↓
Result Consumer
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
PostgreSQL과 Kafka 사이의 Dual Write 문제

DB First와 Kafka First가 각각 실패하는 이유

AFTER_COMMIT만으로 이벤트 유실을 막을 수 없는 이유

비즈니스 결과와 Outbox를 같은 트랜잭션에 저장하는 이유

Outbox 이벤트 Envelope와 테이블 설계

PENDING / PROCESSING / PUBLISHED 상태의 의미

FOR UPDATE SKIP LOCKED를 이용한 동시 Claim

Claim Token과 Lease가 필요한 이유

Kafka ACK와 메서드 호출 성공의 차이

Timeout과 재시도에서 발생하는 중복 발행

At-Least-Once Publication과 Consumer 멱등 처리

eventMessageId와 Kafka Offset의 차이

Partition Key와 이벤트 순서 보장의 차이

aggregateVersion의 역할과 적용 범위

Outbox 적체를 감지하기 위한 운영 지표
```

이번 과제의 핵심은 다음과 같다.

```
Outbox는 Kafka Record를 정확히 한 번 생성하는 패턴이 아니다.

Outbox는 DB 결과가 Commit되었을 때
발행할 이벤트 기록도 같은 DB에 반드시 남도록 만드는 패턴이다.

Publisher는 남아 있는 이벤트를 재시도할 수 있다.

재시도로 중복 발행이 발생할 수 있으므로
Consumer도 멱등하게 처리해야 한다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
쿠폰 발급 비즈니스 데이터와 Outbox는
같은 PostgreSQL Database에 저장한다.

coupon_issue_request,
coupon_event,
coupon_issue,
outbox_event는
필요한 경우 하나의 로컬 DB 트랜잭션에 포함할 수 있다.

원본 coupon.issue.requested 메시지는
5주차의 requestId 기반 멱등 처리로 중복을 방어한다.

자동 Offset Commit은 사용하지 않는다.

원본 Consumer는 발급 DB 트랜잭션이 Commit된 뒤에만
처리 완료로 간주한다.

Spring Kafka의 실제 Offset Commit 시점은
설정한 AckMode와 Error Handler 정책에 맞게 구성한다.

Outbox Publisher는 Polling 방식으로 구현한다.

이번 주차의 기본 Publisher는
작은 Batch를 순차 동기 방식으로 발행한다.

Kafka 발행은 Claim 트랜잭션 밖에서 수행한다.

Publisher는 Kafka Broker ACK를 확인한 뒤
Outbox를 PUBLISHED로 변경한다.

Publisher는 같은 Outbox 이벤트를
두 번 이상 Kafka에 발행할 수 있다.

Consumer는 eventMessageId를 기준으로
중복 비즈니스 반영을 방어한다.
```

이번 과제의 Outbox가 직접 해결하는 범위는 다음과 같다.

```
PostgreSQL에 확정되는 쿠폰 발급 성공

+

후속 서비스에 전달할 CouponIssued 발행 의도
```

다음 구간은 이번 Outbox가 자동으로 원자화하지 않는다.

```
Redis 선착순 판정
↔ 최초 coupon.issue.requested Kafka 발행

원본 coupon.issue.requested Kafka 소비
↔ PostgreSQL 발급 트랜잭션

Result Consumer의 로컬 DB 저장
↔ 이메일·SMS 같은 외부 API 호출
```

이번 과제에서는 아래 내용의 상세 구현은 다루지 않는다.

```
Kafka Transaction을 이용한 전체 구조

XA 또는 2PC

Debezium Connector 실제 설치

최대 재시도 이후 DLQ 운영

영구 실패 이벤트의 운영자 재처리 UI

Redis와 PostgreSQL의 보정 배치 상세 구현
```

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
PostgreSQL
Kafka Broker
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
DB 트랜잭션은 PostgreSQL만 제어하며 Kafka Broker는 별도 시스템이다.
따라서 한쪽 성공 후 장애가 나도 다른 쪽을 함께 Rollback할 수 없다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[Kafka 발행 전 프로세스 종료]
    ↓
Kafka 발행

최종 DB 상태: 쿠폰 발급 완료

최종 Kafka 상태: CouponIssued 없음

후속 서비스에 미치는 영향: 발급 사실을 알 수 없음

복구에 필요한 정보: 발행해야 할 CouponIssued의 영속화된 정보(Outbox)
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[Kafka 발행 후 DB 트랜잭션 실패]
    ↓
DB Commit

최종 DB 상태: 쿠폰 발급 기록 없음

최종 Kafka 상태: CouponIssued 존재

후속 서비스에 미치는 영향: 실제로 발급되지 않은 쿠폰을 발급된 것으로 처리할 수 있음
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료

KafkaTemplate.send() 호출 후
Broker ACK 확인 전 프로세스 종료
```

```
두 경우 모두 DB는 이미 Commit되어 되돌릴 수 있지만 이벤트 발행 성공은 보장되지 않는다.
발행 정보가 메모리에만 있으면 종료 후 복구 기준도 사라지므로, Outbox에 발행 의도를 영속화해야 한다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | O | 같은 PostgreSQL 트랜잭션으로 원자적으로 저장 가능 |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | X | Redis와 Kafka/PostgreSQL은 별도 시스템 |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | X | Kafka Offset과 PostgreSQL Commit은 하나의 로컬 트랜잭션이 아님 |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | X | 외부 API는 Consumer의 로컬 DB 트랜잭션에 포함되지 않음 |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것: DB 결과와 이벤트 발행 의도가 같은 DB 트랜잭션에 함께 남는 것

Transactional Outbox가 직접 보장하지 않는 것: Kafka Exactly-Once, 이벤트 순서, Consumer 처리 완료, 외부 API의 정확히 한 번 실행
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

다음 두 이름의 의미 차이를 포함한다.

```
IssueCoupon

CouponIssued
```

```
IssueCoupon은 쿠폰을 발급하라는 명령이고, CouponIssued는 DB에서 발급이 확정되었다는 사실이다.
후속 Consumer는 CouponIssued를 받아 쿠폰을 다시 발급하지 않고 알림·조회 모델·통계만 처리한다.
```

### **2. CouponIssued 이벤트 JSON을 완성한다**

반드시 다음 필드를 포함한다.

```
eventMessageId
eventType
schemaVersion
aggregateVersion
occurredAt
requestId
couponIssueId
couponEventId
userId
issuedAt
```

```json
{
  "eventMessageId": "8a78e94b-5c3d-46a7-a364-538cd1f856c9",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### **3. 다음 ID의 역할을 비교한다**

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 행사 | 아니오 | 아니오 |
| couponIssueId | 발급된 쿠폰 Aggregate | 아니오 | 일반적으로 아니오 |
| eventMessageId | 논리 결과 이벤트 | 아니오 | 예 |
| Kafka Partition + Offset | Kafka의 물리 Record 위치 | 예 | 아니오 |

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt: 쿠폰 발급이라는 비즈니스 결과가 발생한 시각

publishedAt: Kafka ACK 확인 후 Outbox를 PUBLISHED로 반영한 시각

Publisher 재시도 시 변경하면 안 되는 값: eventMessageId, occurredAt, Payload
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
발행 대기 중 원본 데이터가 변경될 수 있어 당시 발생한 사실과 다른 이벤트가 만들어질 수 있다.
따라서 Outbox INSERT 시 Payload를 불변 Snapshot으로 확정하고 Publisher는 그대로 발행한다.
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,
    request_id UUID,
    deduplication_key VARCHAR(200) NOT NULL UNIQUE,
    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,
    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    claim_token UUID,
    lease_until TIMESTAMPTZ,
    last_error VARCHAR(1000),
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),
    CHECK (schema_version >= 1),
    CHECK (aggregate_version >= 1),
    CHECK (attempt_count >= 0)
);
```

### **7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다**

```
outbox_event.event_id
=
payload.eventMessageId
```

```
이벤트 생성 시 하나의 UUID를 event_id와 payload.eventMessageId에 동시에 사용한다.
필요하면 CHECK ((payload->>'eventMessageId')::uuid = event_id)로 DB에서도 검증한다.
```

### **8. `deduplication_key`를 설계한다**

`CouponIssued`는 하나의 `couponIssueId`에 대해 한 번만 발생한다고 가정한다.

```
Key 형식: {eventType}:{aggregateType}:{aggregateId}

예시: COUPON_ISSUED:COUPON_ISSUE:5001
```

같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면 어떤 값을 추가해야 하는지도 작성한다.

```
aggregateVersion 또는 별도 sequence/발생 식별자를 추가한다.
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

다음 선택지를 비교한다.

```
전체 Rollback 후 새 트랜잭션에서 조회

Savepoint 사용

ON CONFLICT DO NOTHING RETURNING 후
기존 행 조회·동일성 비교
```

```
일반 INSERT의 UNIQUE 위반 후에는 같은 트랜잭션을 그대로 사용할 수 없다.
기본은 전체 Rollback 후 새 트랜잭션 조회이며, Savepoint가 있으면 그 지점까지 Rollback 후 조회한다.
ON CONFLICT DO NOTHING RETURNING은 실패시키지 않으므로 미반환 시 기존 행을 조회해 주요 필드와 Payload가 같은지 비교한다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';

-- affected rows가 몇 행이어야 하는가?
-- 1행

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;

-- affected rows가 0일 때 가능한 원인은 무엇인가?
-- 품절 또는 coupon_event 행 없음

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id, user_id, status, issued_at
) VALUES (
    :couponEventId, :userId, 'ISSUED', CURRENT_TIMESTAMP
)
RETURNING id, issued_at;

-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장
INSERT INTO outbox_event (
    event_id, request_id, deduplication_key,
    aggregate_type, aggregate_id,
    event_type, schema_version, aggregate_version,
    topic, partition_key, payload, occurred_at
) VALUES (
    :eventMessageId, :requestId, :deduplicationKey,
    'COUPON_ISSUE', CAST(:couponIssueId AS VARCHAR),
    'COUPON_ISSUED', 1, 1,
    'coupon.issued', CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB), :issuedAt
);

COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| --- | --- | --- |

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                    Publisher B
------------------------------------------------
PENDING 조회(evt-001)          PENDING 조회(evt-001)
PROCESSING 변경                PROCESSING 변경
Kafka 발행                     Kafka 발행
→ 같은 이벤트 중복 발행 가능
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY next_attempt_at, created_at, event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP
        + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1. DB Connection을 오래 점유한다.

2. Row Lock이 오래 유지되어 다른 Publisher 대기가 증가한다.

3. Kafka 지연이 DB 트랜잭션 Timeout으로 이어질 수 있다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
Claim Commit 직후 Publisher가 종료되면 PROCESSING 행이 영원히 남을 수 있다.
Lease 만료 후 PENDING으로 회수해야 재발행할 수 있다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Publisher A
→ token-A로 Claim
→ 처리 지연
→ Lease 만료

Publisher B
→ 만료 행 회수
→ token-B로 Claim

Publisher A
→ 뒤늦게 성공 또는 실패 상태 UPDATE
```

```
A의 오래된 결과가 B가 가진 최신 처리 권한의 상태를 덮어쓸 수 있다.
claim_token을 WHERE 조건에 넣어 A의 늦은 UPDATE가 0행이 되게 해야 한다.
```

### **7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### **8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다**

```
Lease 시간
>
batchSize × 건당 최대 Kafka 대기 시간
+
여유 시간
```

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료: 발행 요청을 넘기고 Future를 받은 상태, Broker 저장 성공은 아직 미확정

모든 후속 Consumer 처리 완료: 각 Consumer Group이 별도로 처리까지 마친 상태
```

### **2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다**

다음 조건을 반드시 포함한다.

```
event_id 일치

status = PROCESSING

claim_token 일치
```

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    claim_token = NULL,
```

### **3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다**

다음 값을 함께 갱신한다.

```
next_attempt_at

claim_token

lease_until

last_error

updated_at
```

```sql
UPDATE outbox_event
```

### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
Publisher는 A와 B를 완전히 구분할 수 없다.
따라서 Timeout이면 PUBLISHED로 확정하지 않고 재시도하며, B였다면 중복 Record가 생길 수 있다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태: PENDING으로 복귀, 또는 장애 시 Lease 만료 전까지 PROCESSING

재시도 여부: 예

Kafka 중복 가능성: 있음

Consumer에게 필요한 방어: eventMessageId 기반 멱등 처리
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff: 반복 실패 시 재시도 간격을 늘려 Kafka와 DB 부하를 줄인다.

Jitter: 여러 Publisher가 동시에 재시도하는 Thundering Herd를 줄인다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 예 | 동일 Producer 세션의 재시도 중복을 줄임 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 아니오 | 애플리케이션이 Outbox를 다시 발행하는 별도 send이기 때문 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 아니오 | 새로운 애플리케이션 수준 재발행이기 때문 |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
콜백이 Producer I/O 스레드에서 실행되면 느린 DB 작업이 Kafka I/O를 막아 처리량과 안정성을 떨어뜨릴 수 있다.
DB 상태 변경은 전용 Executor로 넘기고 짧은 별도 트랜잭션으로 처리한다.
```

```
가장 오래된 PENDING 대기 시간: 최대 30분 이상 증가
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
Offset은 Kafka Record의 물리 위치라 같은 논리 이벤트가 재발행되면 다른 Offset을 가진다.
따라서 논리 이벤트 ID인 eventMessageId를 멱등성 Key로 사용해야 한다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (subscriber_id, event_id)
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

```
subscriber_id는 안정적인 논리 구독자 이름이어야 한다.
```

### **4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다**

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
같은 CouponIssue Aggregate의 이벤트를 같은 Partition에 모아 Consumer 처리 단위를 명확히 하고,
부하를 분산하며 향후 Aggregate 단위 순서 보장의 기준으로 사용하기 위해서다.
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
Kafka Partition 순서는 Producer의 실제 send 순서이지 DB 발생 순서가 아니다.

Producer 설정과 재시도에 따라서도 실제 send 완료 순서가 달라질 수 있다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A: CouponIssued(version=1) Claim → 발행 실패 → Backoff

Publisher B: CouponCancelled(version=2) Claim → 발행 성공

Kafka 저장 순서: CouponCancelled(version=2) → 재시도된 CouponIssued(version=1)
```

```
3. Publisher 재시도로 전달 시각과 비즈니스 발생 순서가 달라질 수 있다.
```

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않은 이벤트 수 | 지속 증가하거나 임계치 초과 |
| 가장 오래된 PENDING 대기 시간 | 최장 발행 지연 | 발행 SLO를 계속 초과 |
| PROCESSING 이벤트 수 | Publisher가 Claim해 처리 중인 수 | 장시간 높게 유지됨 |
| 만료된 PROCESSING 수 | Lease가 끝났지만 완료되지 않은 수 | 반복적으로 1건 이상 발생 |
| attempt_count | 이벤트별 Claim·발행 시도 횟수 | 특정 이벤트에서 계속 증가 |
| Outbox 생성 처리량 | 단위 시간당 새 Outbox 생성량 | 발행 처리량보다 지속적으로 큼 |
| Kafka 발행 처리량 | 단위 시간당 ACK 성공 발행량 | 생성량보다 낮거나 급감 |
| DB 발생부터 Kafka ACK까지의 시간 | 이벤트 발생→발행 완료 지연 | 지속 증가하거나 SLO 초과 |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량: (2,000 - 1,500) × 60 = 30,000건

10분 후 예상 적체 증가량: 300,000건

가장 먼저 확인할 지표: Outbox 생성·Kafka 발행 처리량, PENDING 수, 가장 오래된 PENDING 시간

가능한 대응: Publisher 확장, 병목 확인, Batch·비동기 발행 조정
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. deduplication_key UNIQUE 위반

2. Commit된 request = PROCESSING 관측

3. outbox.event_id와 payload.eventMessageId 불일치

4. 같은 Aggregate에서 동일 aggregateVersion 충돌
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면: 아직 발행되지 않은 이벤트가 유실된다.

PROCESSING을 삭제하면: 발행 성공 여부가 확정되지 않은 작업이 유실될 수 있다.

PUBLISHED를 보관하는 목적: 발행 이력 확인과 장애 조사
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

```
Lock

Table Bloat
```

```
대량 DELETE는 긴 트랜잭션과 많은 I/O·WAL을 만들고 Lock 유지 시간을 늘린다.
삭제된 행 공간도 즉시 반환되지 않아 Table Bloat와 Vacuum 부담이 커질 수 있다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

```
문제 1
문제 위치: issueCoupon()의 kafkaTemplate.send()

문제 내용: DB 발급 트랜잭션에서 Kafka를 직접 호출한다.

발생 가능한 장애: DB와 Kafka 중 한쪽만 성공하는 Dual Write가 발생한다.

수정 방법: 발급 결과와 CouponIssued Outbox를 같은 DB 트랜잭션에 저장한다.

문제 2
문제 위치: issueCoupon() 전체

문제 내용: 발급 결과와 outbox_event의 원자적 저장이 없다.

발생 가능한 장애: DB 발급은 Commit됐지만 재발행할 이벤트 기록이 남지 않을 수 있다.

수정 방법: coupon_issue·request ISSUED·outbox_event INSERT를 하나의 트랜잭션으로 묶는다.

문제 3
문제 위치: findTop100ByStatus("PENDING")

문제 내용: 여러 Publisher의 동시 Claim 방어가 없다.

발생 가능한 장애: 여러 인스턴스가 같은 PENDING 행을 동시에 발행할 수 있다.

수정 방법: FOR UPDATE SKIP LOCKED로 조회와 PROCESSING Claim을 같은 짧은 트랜잭션에서 처리한다.

문제 4
문제 위치: @Transactional publishOutbox() 내부 kafkaTemplate.send()

문제 내용: DB 트랜잭션 경계 안에서 외부 Kafka 발행을 수행한다.

발생 가능한 장애: Kafka 지연이 DB Connection·Lock 점유와 트랜잭션 지연으로 이어진다.

수정 방법: Claim Transaction을 먼저 Commit하고 Kafka 발행은 트랜잭션 밖에서 수행한다.

문제 5
문제 위치: kafkaTemplate.send() 직후 event.markPublished()

문제 내용: Broker ACK 확인 전에 PUBLISHED로 변경한다.

발생 가능한 장애: 실제 Kafka 발행 실패인데 Outbox만 PUBLISHED가 되어 이벤트가 유실된다.

수정 방법: CompletableFuture의 ACK 성공을 확인한 뒤 별도 트랜잭션에서 PUBLISHED로 변경한다.

문제 6
문제 위치: publishOutbox()의 Claim·상태 변경

문제 내용: claim_token이 없다.

발생 가능한 장애: Lease 회수 후 이전 Publisher의 늦은 UPDATE가 최신 처리 상태를 덮어쓸 수 있다.

수정 방법: Claim Token을 저장하고 성공·실패 UPDATE의 WHERE에서 검증한다.

문제 7
문제 위치: recoverProcessing()

문제 내용: Lease 만료 조건 없이 모든 PROCESSING을 PENDING으로 되돌린다.

발생 가능한 장애: 정상 처리 중인 이벤트까지 회수되어 동시 중복 발행될 수 있다.

수정 방법: lease_until <= CURRENT_TIMESTAMP인 stale PROCESSING만 회수한다.

문제 8
문제 위치: createPayloadFromCurrentCouponIssue(event)

문제 내용: 발행 시점의 현재 비즈니스 데이터로 Payload를 다시 만든다.

발생 가능한 장애: Outbox 생성 이후 데이터가 바뀌면 당시 발생한 사실과 다른 이벤트가 발행된다.

수정 방법: Outbox INSERT 시 Payload Snapshot을 저장하고 그대로 발행한다.

문제 9
문제 위치: new ProcessedEvent(event.getKafkaPartition(), event.getKafkaOffset())

문제 내용: Kafka Partition+Offset을 Consumer 멱등성 Key로 사용한다.

발생 가능한 장애: 같은 eventMessageId가 다른 Offset으로 재발행되면 중복 반영된다.

수정 방법: subscriber_id + eventMessageId를 멱등성 Key로 사용한다.

문제 10
문제 위치: onResult()

문제 내용: 비즈니스 저장 후 processed_event를 저장하고 두 작업의 원자성이 보장되지 않는다.

발생 가능한 장애: 비즈니스 저장 후 장애가 나면 재전달 때 같은 변경이 다시 반영될 수 있다.

수정 방법: processed_event 중복 확인과 비즈니스 변경을 하나의 Consumer DB 트랜잭션으로 묶는다.

문제 11
문제 위치: publishOutbox() 전체

문제 내용: 발행 실패 시 PENDING 복귀·next_attempt_at·last_error 처리와 Backoff가 없다.

발생 가능한 장애: 실패 이벤트가 정상 재시도되지 않거나 반복 즉시 재시도로 장애를 키울 수 있다.

수정 방법: 실패 시 PENDING으로 돌리고 Exponential Backoff + Jitter로 재시도한다.

문제 12
문제 위치: onResult()

문제 내용: aggregateVersion을 이용한 순서 역전 방어가 없다.

발생 가능한 장애: Cancelled(version=2) 뒤 Issued(version=1)이 도착하면 최신 상태가 과거 상태로 덮일 수 있다.

수정 방법: 조회 모델의 last_aggregate_version보다 큰 이벤트만 상태에 반영한다.
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 PostgreSQL Transaction에서 함께 Commit/Rollback |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | ACK 후 PUBLISHED 전 장애 시 같은 Outbox가 재발행될 수 있음 |
| Publisher 복구 후 재발행 | 조건부 보장 | Lease·재시도와 Publisher/Kafka 복구, Outbox 보존이 필요 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED·다중 Publisher·Backoff로 순서 역전 가능 |
| Consumer의 중복 비즈니스 반영 방지 | 조건부 보장 | eventMessageId 기반 processed_event와 동일 DB Transaction이 필요 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | 각 Consumer Group은 독립적으로 처리·Offset 관리 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API는 로컬 DB Transaction에 포함되지 않음 |
