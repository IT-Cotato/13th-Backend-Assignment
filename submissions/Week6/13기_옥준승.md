# **6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성**

## **1. 과제 목표**

이번 과제의 목표는 **쿠폰 발급 결과를 PostgreSQL에 저장하는 작업과 `CouponIssued` 이벤트를 Kafka에 발행하는 작업 사이의 Dual Write 문제를 분석하고, Transactional Outbox Pattern으로 복구 가능한 이벤트 발행 구조를 설계하는 것**이다.

5주차까지 쿠폰 발급 Consumer는 다음 작업을 하나의 DB 트랜잭션으로 처리했다.

```
coupon_issue_request PENDING → PROCESSING

coupon_event.issued_count 증가

coupon_issue 발급 기록 저장

coupon_issue_request → ISSUED
```

DB 트랜잭션이 Commit된 시점을 최종 쿠폰 발급 성공으로 본다.

하지만 발급 결과를 Notification, MyPage, Analytics 같은 후속 서비스에 전달하려면 별도의 결과 이벤트가 필요하다.

```
PostgreSQL
→ 쿠폰 발급 결과 저장

Kafka
→ CouponIssued 이벤트 발행
```

PostgreSQL과 Kafka는 서로 다른 시스템이다.

하나의 메서드 안에서 두 작업을 호출하거나 DB 메서드에 `@Transactional`을 붙이는 것만으로는 두 시스템이 하나의 원자적 트랜잭션이 되지 않는다.

이번 과제에서는 다음 구조를 설계한다.

```
Coupon Issue Consumer
        ↓
+------------------------------------------+
| PostgreSQL Transaction                   |
|------------------------------------------|
| coupon_issue 저장                        |
| request ISSUED 변경                      |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        ↓ Commit
Outbox Publisher
        ↓
Kafka coupon.issued
        ↓
Result Consumer
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
PostgreSQL과 Kafka 사이의 Dual Write 문제

DB First와 Kafka First가 각각 실패하는 이유

AFTER_COMMIT만으로 이벤트 유실을 막을 수 없는 이유

비즈니스 결과와 Outbox를 같은 트랜잭션에 저장하는 이유

Outbox 이벤트 Envelope와 테이블 설계

PENDING / PROCESSING / PUBLISHED 상태의 의미

FOR UPDATE SKIP LOCKED를 이용한 동시 Claim

Claim Token과 Lease가 필요한 이유

Kafka ACK와 메서드 호출 성공의 차이

Timeout과 재시도에서 발생하는 중복 발행

At-Least-Once Publication과 Consumer 멱등 처리

eventMessageId와 Kafka Offset의 차이

Partition Key와 이벤트 순서 보장의 차이

aggregateVersion의 역할과 적용 범위

Outbox 적체를 감지하기 위한 운영 지표
```

이번 과제의 핵심은 다음과 같다.

```
Outbox는 Kafka Record를 정확히 한 번 생성하는 패턴이 아니다.

Outbox는 DB 결과가 Commit되었을 때
발행할 이벤트 기록도 같은 DB에 반드시 남도록 만드는 패턴이다.

Publisher는 남아 있는 이벤트를 재시도할 수 있다.

재시도로 중복 발행이 발생할 수 있으므로
Consumer도 멱등하게 처리해야 한다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
쿠폰 발급 비즈니스 데이터와 Outbox는
같은 PostgreSQL Database에 저장한다.

coupon_issue_request,
coupon_event,
coupon_issue,
outbox_event는
필요한 경우 하나의 로컬 DB 트랜잭션에 포함할 수 있다.

원본 coupon.issue.requested 메시지는
5주차의 requestId 기반 멱등 처리로 중복을 방어한다.

자동 Offset Commit은 사용하지 않는다.

원본 Consumer는 발급 DB 트랜잭션이 Commit된 뒤에만
처리 완료로 간주한다.

Spring Kafka의 실제 Offset Commit 시점은
설정한 AckMode와 Error Handler 정책에 맞게 구성한다.

Outbox Publisher는 Polling 방식으로 구현한다.

이번 주차의 기본 Publisher는
작은 Batch를 순차 동기 방식으로 발행한다.

Kafka 발행은 Claim 트랜잭션 밖에서 수행한다.

Publisher는 Kafka Broker ACK를 확인한 뒤
Outbox를 PUBLISHED로 변경한다.

Publisher는 같은 Outbox 이벤트를
두 번 이상 Kafka에 발행할 수 있다.

Consumer는 eventMessageId를 기준으로
중복 비즈니스 반영을 방어한다.
```

이번 과제의 Outbox가 직접 해결하는 범위는 다음과 같다.

```
PostgreSQL에 확정되는 쿠폰 발급 성공

+

후속 서비스에 전달할 CouponIssued 발행 의도
```

다음 구간은 이번 Outbox가 자동으로 원자화하지 않는다.

```
Redis 선착순 판정
↔ 최초 coupon.issue.requested Kafka 발행

원본 coupon.issue.requested Kafka 소비
↔ PostgreSQL 발급 트랜잭션

Result Consumer의 로컬 DB 저장
↔ 이메일·SMS 같은 외부 API 호출
```

이번 과제에서는 아래 내용의 상세 구현은 다루지 않는다.

```
Kafka Transaction을 이용한 전체 구조

XA 또는 2PC

Debezium Connector 실제 설치

최대 재시도 이후 DLQ 운영

영구 실패 이벤트의 운영자 재처리 UI

Redis와 PostgreSQL의 보정 배치 상세 구현
```

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
            message.requestId(),
            issue.getId()
    );

    kafkaTemplate.send(
            "coupon.issued",
            issue.getId().toString(),
            CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
PostgreSQL, Kafka
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
@Transactional의 관리 대상은 DataSource 커넥션 하나로, PostgreSQL 하나만 원자적으로 만든다. Kafka 발행은 그 경계 밖에서 발생하므로, DB Commit 성공과 Kafka 저장 성공은 서로를 보장하지 않는다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[장애 지점]
    ↓
Kafka 발행

최종 DB 상태:
coupon_event.issued_count 증가 확정
coupon_issue 발급 기록 존재
coupon_issue_request = ISSUED
→ 쿠폰 발급 완료

최종 Kafka 상태:
coupon.issued Topic에 CouponIssued Record 없음

후속 서비스에 미치는 영향:
Notification  → 발급 성공 알림 미발송
MyPage        → 사용자 쿠폰 조회 모델에 반영 안 됨
Analytics     → 발급 통계 누락
사용자 입장에서는 DB에 쿠폰이 있으나 어디에도 보이지 않는다
이벤트가 오지 않았으므로 후속 서비스는 누락 사실 자체를 인지할 수 없다

복구에 필요한 정보:
발행되어야 했으나 발행되지 않은 이벤트의 목록
→ 어떤 couponIssueId, requestId에 대해 어떤 payload를 어느 Topic에 보내야 하는지
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점]
    ↓
DB Commit

최종 DB 상태:
전체 Rollback
coupon_event.issued_count 증가 없음
coupon_issue 발급 기록 없음
coupon_issue_request = PENDING (또는 최종 확정되지 않음)
→ 쿠폰은 발급되지 않았다

최종 Kafka 상태:
coupon.issued Topic에 CouponIssued Record 존재

후속 서비스에 미치는 영향:
Notification  → 발급되지 않은 쿠폰의 성공 알림 발송
MyPage        → 존재하지 않는 쿠폰이 조회 모델에 노출
                사용자가 쿠폰을 사용하려 하면 DB에 없어 실패
Analytics     → 실제 발급 수량보다 큰 통계, issued_count와 불일치
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료

KafkaTemplate.send() 호출 후
Broker ACK 확인 전 프로세스 종료
```

```
AFTER_COMMIT은 발급되지 않은 쿠폰의 이벤트 발행 문제를 해결하지만, DB Commit 후 Listener 실행 전 프로세스가 종료 되거나 KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료되어 발생하는 발행 의도의 유실 문제는 해결하지 못한다.

필요한 것은 실행 시점 조정이 아니라 발행할 이벤트를 메모리가 아닌 DB에 비즈니스 결과와 같은 트랜잭션으로 저장하는 구조다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | o | 두 작업 모두 같은 PostgreSQL Database의 테이블에 대한 쓰기이므로 하나의 로컬 트랜잭션에 포함된다. 함께 Commit되거나 함께 Rollback되므로 "발급은 확정되었는데 발행할 이벤트 기록이 없는 상태"가 발생하지 않는다. |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | x | Redis와 PostgreSQL은 서로 다른 저장소이므로 하나의 로컬 트랜잭션에 포함되지 않는다. Redis Lua Script가 SUCCESS를 반환한 뒤 요청 저장이나 Kafka 발행 전에 장애가 나면 Redis 자리만 소진되고 요청은 유실된다. |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | x | Kafka Offset Commit과 PostgreSQL 트랜잭션은 서로 다른 시스템의 확정 행위다. 발급 DB Commit 후 Offset Commit 전에 종료되면 원본 메시지가 재전달된다. |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | x | 외부 API 호출은 로컬 DB 트랜잭션에 포함되지 않는 또 다른 Dual Write다. processed_event는 로컬 DB의 중복 반영만 막을 뿐, SMS가 물리적으로 정확히 한 번 전송되는 것은 보장하지 못한다. |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것:
쿠폰 발급 결과가 PostgreSQL에 Commit되면
그 결과를 알리기 위해 발행해야 할 이벤트 기록도
반드시 같은 DB에 함께 남는다.

Transactional Outbox가 직접 보장하지 않는 것:
1. Kafka Record가 물리적으로 정확히 한 번 생성되는 것
2. 이벤트가 비즈니스 발생 순서대로 전달되는 것
3. 모든 Consumer가 반드시 처리를 완료하는 것
4. 외부 알림(SMS·이메일)이 정확히 한 번 전송되는 것
5. Redis 선착순 판정과 PostgreSQL 상태의 일치
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

다음 두 이름의 의미 차이를 포함한다.

```
IssueCoupon

CouponIssued
```

```
1. 이벤트가 만들어지는 시점이 이미 확정 이후다

   Outbox INSERT는 다음 작업들과 같은 트랜잭션 안에서 일어난다.
     issued_count 증가
     coupon_issue INSERT
     request → ISSUED

   이 트랜잭션이 Commit된 시점에 발급은 최종 확정된다.
   따라서 Outbox 행이 존재한다는 것은
   "발급해달라"가 아니라 "이미 발급되었다"를 의미한다.
   확정된 사실에 명령형 이름을 붙이면 의미가 어긋난다.

2. Consumer가 발급 로직을 다시 실행하면 안 된다

   IssueCoupon으로 이해하면 Consumer는 자신이 발급을 수행해야 한다고
   판단할 수 있다. 그 경우 다음 문제가 생긴다.
     issued_count 이중 증가
     coupon_issue UNIQUE(event_id, user_id) 위반
     이미 소진된 수량의 추가 차감

   CouponIssued를 받은 Consumer가 하는 일은 반응뿐이다.
     Notification → 발급 성공 알림 생성
     MyPage       → 사용자 쿠폰 조회 모델 갱신
     Analytics    → 발급 성공 통계 반영
```

### **2. CouponIssued 이벤트 JSON을 완성한다**

반드시 다음 필드를 포함한다.

```
eventMessageId
eventType
schemaVersion
aggregateVersion
occurredAt
requestId
couponIssueId
couponEventId
userId
issuedAt
```

```
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
```

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt:
쿠폰 발급이 DB 트랜잭션에서 확정된 시각

publishedAt:
Publisher가 Kafka Broker의 ACK를 확인한 뒤 DB에 기록한 시각이다. (Kafka 발행 작업이 완료된 시점)

Publisher 재시도 시 변경하면 안 되는 값:
occurredAt과 payload 전체.

Outbox 행은 특정 시점에 발생한 사실의 불변 Snapshot이다.
재시도로 발행 시각이 바뀌더라도 발생 시각과 내용은 바뀌지 않는다.

```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
1. 발행을 기다리는 사이 원본 데이터가 변경될 수 있다

   Outbox INSERT와 실제 Kafka 발행 사이에는 시간 간격이 존재한다.
     Polling 주기만큼의 지연
     발행 실패 후 Backoff 재시도로 인한 지연 (1초 → 2초 → 4초 → 8초)
     Kafka 장애 시 수십 분 이상의 지연

   그 사이에 coupon_issue 행이 변경되면
   발행되는 내용이 발생 시점의 사실과 달라진다.

   10:00:00  발급 확정 → outbox_event INSERT (CouponIssued)
   10:00:03  Kafka 장애로 발행 실패 → next_attempt_at = +4초
   10:00:10  사용자가 쿠폰 취소 → coupon_issue.status = CANCELLED
   10:00:15  Publisher 재시도 → 현재 행을 조회해 payload 생성
             → eventType은 COUPON_ISSUED인데 내용은 CANCELLED 상태

   이벤트 타입과 payload 내용이 모순되는 메시지가 전달된다.

2. 이벤트의 정의 자체를 위반한다

   CouponIssued는 "쿠폰이 발급되었다"는 과거의 사실이다.
   과거의 사실은 나중에 조회한 현재 상태로 재구성될 수 없다.

   현재 상태를 조회해 만든 payload는
   "발급 시점의 사실"이 아니라 "발행 시점의 상태"이며,
   이것은 Event가 아니라 State Snapshot이다.

   Outbox 행은 특정 시점에 발생한 사실의 불변 Snapshot으로 다뤄야 한다.

3. 재발행 시 동일성이 깨진다

   At-Least-Once 구조에서 같은 eventMessageId가 여러 번 전달될 수 있다.
   Consumer는 같은 eventMessageId면 같은 내용이라고 가정한다.

   그런데 발행할 때마다 payload를 다시 만들면
   같은 eventMessageId를 가진 서로 다른 내용의 메시지가 나갈 수 있다.

   Record 1 : eventMessageId = evt-001, status = ISSUED
   Record 2 : eventMessageId = evt-001, status = CANCELLED

   processed_event 기반 멱등 처리는 두 번째를 건너뛰므로
   어느 쪽이 반영되는지가 도착 순서에 좌우된다.
   멱등성의 전제(같은 ID = 같은 결과)가 무너진다.

4. 원본 행이 삭제되었거나 조회할 수 없을 수 있다

   보관 정책이나 아카이빙으로 원본이 없으면
   Publisher는 payload를 만들지 못하고 발행 자체가 불가능해진다.
   Outbox 행은 남아 있는데 발행할 수 없는 상태가 된다.

   실패 이벤트처럼 애초에 대응하는 비즈니스 행이 없는 경우도 있다.
   (SOLD_OUT은 coupon_issue가 생성되지 않는다)
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    request_id UUID,

    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_outbox_status
        CHECK (
            status IN (
                'PENDING',
                'PROCESSING',
                'PUBLISHED'
            )
        ),

    CONSTRAINT chk_outbox_schema_version
        CHECK (schema_version >= 1),

    CONSTRAINT chk_outbox_aggregate_version
        CHECK (aggregate_version >= 1),

    CONSTRAINT chk_outbox_attempt_count
        CHECK (attempt_count >= 0),

    CONSTRAINT chk_outbox_state_fields
        CHECK (
            (
                status = 'PENDING'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NULL
            )
            OR
            (
                status = 'PROCESSING'
                AND claim_token IS NOT NULL
                AND lease_until IS NOT NULL
                AND published_at IS NULL
            )
            OR
            (
                status = 'PUBLISHED'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NOT NULL
            )
        )
);
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

다음 선택지를 비교한다.

```
전체 Rollback 후 새 트랜잭션에서 조회

Savepoint 사용

ON CONFLICT DO NOTHING RETURNING 후
기존 행 조회·동일성 비교
```

```
전체 Rollback 후 새 트랜잭션에서 조회
→ 발급 결과와 Outbox가 함께 취소되므로 불일치가 없다.
   설계 가정 위반을 확실히 드러내고 알람으로 처리할 수 있다.
   단, 조회를 위해 별도 트랜잭션이 필요하다.

Savepoint 사용
→ 위반 직전에 SAVEPOINT를 잡고 ROLLBACK TO SAVEPOINT로 복구하면
   같은 트랜잭션 안에서 기존 행을 조회하고 계속 진행할 수 있다.
   다만 Savepoint는 발급 경로마다 관리 비용이 들고,
   위반을 트랜잭션 안에서 흡수하므로 이상 상황이 묻히기 쉽다.

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교
→ 트랜잭션이 abort되지 않아 가장 매끄럽다.
   반환 행이 없으면 기존 행을 조회해 request_id, aggregate_type/id,
   event_type, schema_version, aggregate_version, payload가 모두 같은지
   확인한 뒤에만 재사용한다.
   비교 없이 조용히 넘기면 Key 생성 버그나 요청 상태 관리 결함을 숨긴다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows가 몇 행이어야 하는가? 
-- 1행

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;
-- affected rows가 0일 때 가능한 원인은 무엇인가? 
-- 수량 소진, 해당 이벤트 없음, 잘못된 메시지 

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
) VALUES (
    :couponEventId,
    :userId,
    'ISSUED',
    CURRENT_TIMESTAMP
)
RETURNING id, issued_at;
-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';
-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장
INSERT INTO outbox_event (
    event_id,
    request_id,
    deduplication_key,
    aggregate_type,
    aggregate_id,
    event_type,
    schema_version,
    aggregate_version,
    topic,
    partition_key,
    payload,
    occurred_at
) VALUES (
    :eventMessageId,
    :requestId,
    :deduplicationKey,
    'COUPON_ISSUE',
    CAST(:couponIssueId AS VARCHAR),
    'COUPON_ISSUED',
    1,
    1,
    'coupon.issued',
    CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB),
    :issuedAt
);

COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1 | 0행이면 즉시 실패로 단정하지 않고 기존 요청 상태를 조회한다. ISSUED/FAILED면 이미 처리된 요청의 재전달이므로 새 발급·Outbox 없이 정상 종료. PROCESSING이면 설계 가정 위반이므로 알람 후 재처리 대상으로 남긴다. 요청 행이 없거나 메시지 내용이 불일치하면 잘못된 메시지로 분류한다 |
| issued_count 조건부 증가 | 1 | 0행이면 원인을 구분한다. 수량 소진이면 request = FAILED / SOLD_OUT으로 확정하고 CouponIssued Outbox는 저장하지 않는다. 이벤트 행이 없거나 종료된 경우는 잘못된 메시지로 별도 분류한다. SOLD_OUT 확정은 Redis-DB divergence 신호이므로 알람 대상이다 |
| coupon_issue INSERT | 1 | UNIQUE(event_id, user_id) 위반이면 전체 Rollback된다. 별도 트랜잭션에서 기존 발급 기록과 요청 상태를 확인하고, 다른 요청에서 발급된 것이 확인되면 FAILED / DUPLICATE_USER로 확정한다. CouponIssued Outbox는 만들지 않는다 |
| PROCESSING → ISSUED | 1 | 전체 Rollback한다. 이 UPDATE가 0행인데 발급 결과와 Outbox를 Commit하면 요청 상태와 실제 결과가 어긋난다 |
| outbox_event INSERT | 1 | 실패 시 전체 Rollback한다. deduplication_key UNIQUE 위반은 설계 가정 위반이므로 ON CONFLICT로 넘기지 않고 Rollback + 알람 |

### **3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다**

장애 직전 상황은 다음과 같다.

```
issued_count 증가 성공

coupon_issue INSERT 성공

request ISSUED 변경 성공

outbox_event INSERT 실패
```

```
트랜잭션 결과: 전체 Rollback

coupon_event.issued_count: 증가 취소

coupon_issue: 발급 기록 없음

coupon_issue_request: ISSUED 변경 취소

outbox_event: 행 없음
```

### **4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다**

```
발급 결과만 Commit되고 Outbox가 없으면 쿠폰은 발급되었는데 발행할 이벤트 기록이 없는 상태가 된다. 그 결과 쿠폰은 이미 발급되어 되돌릴 수 없으므로 재발급하면 안 되고, 발행해야 할 이벤트를 식별할 근거가 DB에 남아 있지 않아 재발행도 할 수 없게 된다.
```

### **5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다**

```
issued_count를 다시 증가시키는가?
첫 번째 UPDATE(PENDING → PROCESSING)가 0행이 되어 수량 증가 단계까지 도달하지 않는다.
coupon_issue를 다시 생성하는가?
같은 이유로 실행되지 않으며, 시도하더라도 UNIQUE(event_id, user_id) 제약에 걸린다.
Outbox를 다시 INSERT하는가?
INSERT 하지 않는다.
Consumer 처리는 성공으로 종료할 수 있는가?
쿠폰 발급이 확정되었고, 발행 의도도 DB에 저장되어 있으므로 Consumer 처리는 성공적으로 종료될 수 있다.
```

### **6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다**

```
DB 상태:
발급 트랜잭션이 이미 Commit되어 확정된 상태다.
coupon_event.issued_count 증가 완료
coupon_issue 발급 기록 존재
coupon_issue_request = ISSUED

Outbox 상태:
outbox_event 행 존재, status = PENDING
발행할 이벤트가 DB에 안전하게 기록되어 있으므로
Publisher가 복구되면 정상적으로 발행된다.

Kafka 원본 메시지:
coupon.issue.requested의 Offset이 Commit되지 않았으므로
Consumer 재시작이나 리밸런싱 후 같은 메시지가 재전달된다.

재시작 후 필요한 멱등성 기준:
requestId를 기준으로 요청의 최종 상태를 확인한다.
PENDING → PROCESSING UPDATE가 0행이 되므로 기존 상태를 조회하고, request = ISSUED이면 이미 완료된 요청의 재전달로 판단해 수량 증가·발급 기록·Outbox를 다시 만들지 않고 정상 종료 후 Offset을 Commit한다.
```

### **7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit

AckMode

Listener 예외 처리

Error Handler가 실패를 정상 처리로 바꾸는지 여부
```

```
enable.auto.commit
false여야 한다. true이면 Kafka Consumer가 주기적으로 Offset을 자동 Commit하므로 DB 트랜잭션 성공 여부와 무관하게 처리 완료로 기록되어 메시지가 유실될 수 있다.

AckMode
Offset 반영 시점을 결정한다.
RECORD 또는 BATCH를 사용해 Listener가 정상 종료한 뒤에 Commit되도록 한다.
MANUAL / MANUAL_IMMEDIATE를 사용한다면 발급 DB Commit 이후에만
acknowledge()를 호출해야 한다.
TIME이나 COUNT처럼 처리 결과와 무관하게 시간·건수 기준으로 Commit하는 모드는 DB Commit 전에 Offset이 반영될 수 있으므로 사용하지 않는다.

Listener 예외 처리
발급 트랜잭션이 실패하면 예외를 반드시 던져야 한다.
Listener 안에서 try-catch로 로깅만 하고 정상 종료하면 Offset이 Commit되어 재처리 기회가 사라진다.
반대로 이미 처리된 요청의 재전달은 정상 종료시켜야 무한 재전달을 막을 수 있다.

Error Handler가 실패를 정상 처리로 바꾸는지 여부
DefaultErrorHandler는 재시도 소진 후 recoverer로 넘기고 Offset을 진행시킨다. DLQ나 별도 저장 없이 이 경로를 사용하면 실패한 메시지가 조용히 사라진다. 재시도 정책, recoverer 동작, 실패 메시지의 최종 도착지를 확인해야 하며, 일시적 DB 오류처럼 재처리해야 하는 예외가 recoverer로 넘어가지 않도록 재시도 대상 예외를 분류해야 한다.
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                              Publisher B
------------------------------------------------------------------
SELECT * FROM outbox_event
WHERE status = 'PENDING'
  AND next_attempt_at <= now()
LIMIT 100
→ evt-001 조회
                                         SELECT * FROM outbox_event
                                         WHERE status = 'PENDING'
                                           AND next_attempt_at <= now()
                                         LIMIT 100
                                         → evt-001 조회 (동일 행)

UPDATE outbox_event
SET status = 'PROCESSING'
WHERE event_id = 'evt-001'
→ 1행
                                         UPDATE outbox_event
                                         SET status = 'PROCESSING'
                                         WHERE event_id = 'evt-001'
                                         → 1행 (조건 없이 덮어씀)

kafkaTemplate.send(evt-001)
                                         kafkaTemplate.send(evt-001)

```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY
        next_attempt_at,
        created_at,
        event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until =
        CURRENT_TIMESTAMP
        + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1.
DB Connection을 장시간 점유한다.
Kafka ACK 대기는 네트워크 왕복이며 수백 ms에서 수 초까지 걸릴 수 있다.
그동안 Connection Pool의 커넥션이 반환되지 않아 풀이 고갈되고,
발급 트랜잭션까지 커넥션을 얻지 못해 쿠폰 발급 자체가 지연되는
연쇄 장애로 번진다.

2.
Row Lock을 장시간 유지한다.
Claim한 행에 대한 잠금이 Kafka 왕복 내내 유지되므로
다른 Publisher가 SKIP LOCKED로 건너뛰어야 하는 행이 계속 늘어나고,
Claim 쿼리의 스캔 효율이 떨어진다.

3.
트랜잭션 Timeout이 발생한다.
Kafka가 느려지거나 장애가 나면 DB 트랜잭션이 먼저 Timeout되어
Rollback되고, Claim 자체가 무효화된다.
발행은 이미 시도했는데 상태는 PENDING으로 되돌아가
같은 이벤트를 계속 다시 집어가는 루프가 생긴다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
인스턴스 수가 하나여도 Claim Commit 직후 프로세스가 종료될 수 있기 때문이다.

Claim 트랜잭션이 Commit되면 그 행은 PROCESSING 상태로 확정된다.
이 직후 Publisher가 종료되면 다음 상태가 남는다.

  status = PROCESSING
  claim_token = 죽은 인스턴스의 토큰
  lease_until = 과거 시각

Publisher를 재시작해도 Claim 쿼리는 status = 'PENDING'인 행만 조회하므로
이 행은 다시 집히지 않는다.
소유자는 이미 사라졌는데 상태는 "처리 중"으로 남아
아무도 발행하지 않는 행이 영구히 방치된다.

경쟁 방어는 여러 인스턴스가 있을 때만 필요하지만,
stale PROCESSING 복구는 인스턴스가 하나여도 필요하다.
Lease 만료 회수 또는 시작 시 stale PROCESSING 일괄 복구 중
최소 하나는 반드시 있어야 한다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Publisher A
→ token-A로 Claim
→ 처리 지연
→ Lease 만료

Publisher B
→ 만료 행 회수
→ token-B로 Claim

Publisher A
→ 뒤늦게 성공 또는 실패 상태 UPDATE
```

```
Lease가 만료되어 처리 권한을 잃은 Publisher A가
뒤늦게 상태를 변경하면 최신 소유자인 B의 상태를 덮어쓴다.

A가 성공으로 덮어쓰면 실제 발행 여부가 불확실한데 PUBLISHED로 확정되어
B의 실패가 기록되지 않고 재시도 대상에서 빠진다.
A가 실패로 덮어쓰면 B가 처리 중인데 행은 PENDING이 되어
제3의 Publisher가 다시 Claim해 중복 발행이 늘어난다.

성공·실패 UPDATE 모두 claim_token 조건을 두면
권한을 잃은 A의 UPDATE는 affected rows = 0이 되어 덮어쓰지 못한다.
```

## **과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기**

### **1. 다음 네 상태의 의미 차이를 설명한다**

```
KafkaTemplate.send() 호출 완료:
Record가 Producer 내부 버퍼에 적재

CompletableFuture 정상 완료:
Broker가 Record를 저장하고 ACK를 응답

outbox = PUBLISHED:
ACK 확인 후 claim_token이 일치하는 상태에서 DB UPDATE가 1행 성공해 발행 완료가 DB에 기록된 상태

모든 후속 Consumer 처리 완료:
각 Consumer Group이 Record를 소비해 자신의 DB 트랜잭션을 Commit하고 Offset을 반영한 상태
```

### **2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다**

다음 조건을 반드시 포함한다.

```
event_id 일치

status = PROCESSING

claim_token 일치
```

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,

    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### **3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다**


### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
상황 A
Producer가 Broker에 전송하지 못했거나, Broker가 저장에 실패한 뒤 응답이 오지 않아 Timeout이 발생했다.
→ Kafka에 Record 없음

상황 B
Broker는 Record를 정상적으로 저장했으나 ACK 응답이 네트워크에서 유실되었거나, 응답이 늦게 도착해 Publisher가 먼저 Timeout으로 판정했다.
→ Kafka에 Record 존재

Publisher가 관측할 수 있는 것은 "응답이 오지 않았다"는 사실뿐이며, 응답이 없는 이유가 저장 실패인지 응답 유실인지 구분할 수단이 없다. 저장과 응답 사이에 네트워크 경계가 있고, 그 경계 너머의 결과는 응답을 통해서만 알 수 있기 때문이다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태:
PUBLISHED로 변경하지 않고 미완료 상태로 유지한다.
claim_token 조건을 만족하면 PENDING으로 되돌리고
next_attempt_at을 Backoff + Jitter로 계산해 저장한다.
last_error에는 짧은 오류 분류와 메시지를 기록한다.
Publisher가 이 UPDATE 전에 종료되면 PROCESSING으로 남고
lease_until 만료 후 회수되어 PENDING으로 복구된다.

재시도 여부:
재시도한다. Timeout만으로는 Broker 저장 여부를 확정할 수 없으므로 발행되지 않았을 가능성을 전제로 처리한다.
PUBLISHED로 확정하면 실제로 저장되지 않았을 때 영구 유실되며, 유실은 복구할 수 없고 중복은 흡수할 수 있기 때문이다.

Kafka 중복 가능성:
Broker에는 저장되었으나 ACK만 유실된 경우(상황 B),
재시도로 같은 eventMessageId를 가진 Record가 한 번 더 저장된다.

Consumer에게 필요한 방어:
eventMessageId 기준의 멱등 처리가 필요하다.
processed_event에 (subscriber_id, event_id)를 Primary Key로 저장하고, 비즈니스 데이터 변경과 같은 트랜잭션으로 묶는다.
중복 도착 시 ON CONFLICT DO NOTHING으로 반환 행이 없으면 비즈니스 변경을 생략하고 정상 처리로 종료한다.
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff:
재시도 간격을 지수적으로 늘려 실패가 반복될 때 부하를 줄인다.

Jitter:
재시도 시각에 작은 무작위 지연을 더해 여러 요청이 같은 시각에 몰리는 것을 막는다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | o | Broker가 저장에 성공했으나 ACK가 유실되어 Producer가 자동 재시도하는 경우다. enable.idempotence = true이면 Producer가 각 Record에 producer id와 시퀀스 번호를 부여하고, Broker가 이미 수신한 시퀀스를 식별해 중복 저장을 제거한다. 같은 Producer 세션 안에서 일어나는 중복이므로 방어된다 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | x | Producer Idempotence는 하나의 Producer 세션 내부에서만 유효하다. 프로세스가 종료되면 그 Producer도 함께 사라지고, 회수한 Publisher는 새 Producer 세션에서 새 producer id로 발행하므로 Broker 입장에서는 처음 보는 요청이 된다. Outbox 행은 미완료로 남아 Lease 만료 후 회수되어 재발행되며, 이는 애플리케이션 수준의 재발행이라 Producer 계층에서 막을 수 없다 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | x | 완전히 새로운 Claim과 새로운 send() 호출이다. 이전 발행과 동일한 시퀀스 컨텍스트를 공유하지 않으므로 Broker는 별개의 Record로 저장한다. Producer Idempotence의 범위 밖이며, 의도적인 재발행이므로 애초에 방어 대상도 아니다 |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
whenComplete는 Future를 완료시킨 스레드에서 콜백을 실행한다.
Kafka 발행 결과로 Future를 완료시키는 것은 Producer 내부의 Sender 스레드이므로,
콜백 안의 DB 작업이 Producer I/O 스레드에서 수행된다.

Sender 스레드는 Producer당 하나이며, 버퍼에서 배치를 꺼내 전송하고
응답을 처리하는 루프를 담당한다.
이 스레드에서 다음 작업이 발생하면 루프 전체가 멈춘다.

  Connection Pool 대기
  트랜잭션 Commit 대기
  → Sender 스레드 블로킹
  → 해당 Producer의 모든 전송이 함께 지연

부하 상황에서는 연쇄 장애로 이어진다.

  Sender 스레드 블로킹
  → 발행 지연 증가
  → Lease 만료
  → 다른 Publisher가 회수
  → 중복 발행 증가
  → 적체 심화

따라서 콜백을 전용 Executor로 넘겨 Sender 스레드가 즉시 루프로 복귀하게 한다.
```

## **과제 6. Outbox 장애 시나리오 분석하기**

각 장애 시나리오에 대해 다음을 작성한다.

```
DB의 비즈니스 상태

Outbox 상태

Kafka Record 존재 가능성

복구 주체

중복 가능성
```

### **1. 발급 트랜잭션 Commit 전 장애**

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 없음 |
| request | PENDING |
| outbox_event | 없음 |
| 복구 방법 | 원본 coupon.issue.requested 메시지 재처리. DB Commit이 없었으므로 Offset도 Commit되지 않아 메시지가 재전달되고, request = PENDING이므로 첫 UPDATE가 1행이 되어 정상적으로 처음부터 재처리된다 |

| --- | --- |

| request | ISSUED |
| outbox_event | 존재 |

| 복구 방법 | requestId 기반 멱등 처리. 재전달 시 PENDING → PROCESSING UPDATE가 0행이 되므로 기존 상태를 조회하고, request = ISSUED이면 이미 완료된 요청의 재전달로 판단해 수량 증가·발급 기록·Outbox를 다시 만들지 않고 정상 종료 후 Offset을 Commit한다 |

### **3. Outbox Claim Commit 후 Kafka 발행 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING |
| Kafka Record | 없음 |
| 복구 조건 | lease_until <= CURRENT_TIMESTAMP 도달. 만료 전에는 다른 Publisher가 처리 중이라고 판단해 회수하지 않는다 |
| 복구 주체 | 다른 Publisher 인스턴스, 또는 재시작한 같은 인스턴스의 만료 회수 로직. Lease 만료 UPDATE로 PENDING으로 되돌린 뒤 다음 Polling에서 새 claim_token으로 다시 Claim한다 |

### **4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료**

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING |
| Kafka Record | 존재 |
| 재발행 가능성 | 있다. 회수 후 다른 Publisher가 새 claim_token으로 Claim해 같은 payload를 다시 발행한다. 같은 eventMessageId를 가진 Record가 서로 다른 Offset으로 두 번 저장된다 |
| 필요한 Consumer 방어 | eventMessageId 기준 멱등 처리. processed_event에 (subscriber_id, event_id)를 Primary Key로 저장하고 비즈니스 변경과 같은 트랜잭션으로 묶어, 중복 도착 시 비즈니스 반영을 생략하고 정상 종료한다 |

### **5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황**

```
Publisher A가 늦게 성공 UPDATE:
B가 회수하면서 claim_token이 token-B로 변경되었으므로 조건이 불일치한다.
A는 상태를 덮어쓰지 못하고 그대로 종료한다.

Publisher A가 늦게 실패 UPDATE:
B가 회수하면서 claim_token이 token-B로 변경되었으므로 조건이 불일치한다.
A는 상태를 덮어쓰지 못하고 그대로 종료한다.

두 UPDATE에서 affected rows가 0이어야 하는 조건:

claim_token이 현재 행의 값과 다를 때.
Lease 만료 후 다른 Publisher가 회수하면서 새 토큰으로 교체했기 때문이다.

status가 PROCESSING이 아닐 때.
회수 직후 PENDING이거나 B가 이미 PUBLISHED로 확정한 경우가 해당한다.

```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화:
발급은 정상적으로 계속되므로 Outbox 행은 계속 INSERT된다.
발행은 전부 실패해 PENDING으로 되돌아간다.

가장 오래된 PENDING 대기 시간:
장애 시작 직전에 저장된 행이 그대로 남아 계속 증가한다.
30분 시점에는 약 30분에 도달한다.

attempt_count:
Claim할 때마다 증가하므로 같은 이벤트에서 계속 올라간다.

Kafka 복구 후 처리:
next_attempt_at이 도래한 행부터 순차적으로 Claim되어 발행된다.
Outbox 행이 모두 DB에 남아 있으므로 유실 없이 처리된다.

운영 알람:
  PENDING 이벤트 수가 지속적으로 증가
  가장 오래된 PENDING 대기 시간이 임계치 초과
  같은 이벤트의 attempt_count가 계속 증가
  Outbox 생성 속도 대비 발행 속도가 계속 느림
  Kafka 발행 실패율 급증, last_error에 동일 오류 분류 집중

이 지표들은 Outbox 자체의 결함이 아니라 외부 의존성 장애를 가리킨다.
발급은 정상 동작 중이므로 발급 API를 중단할 필요는 없고, 후속 서비스로의 전달만 지연되고 있다는 점을 함께 판단해야 한다.
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001

Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
Partition과 Offset은 Kafka 안의 물리적 저장 위치일 뿐이며
논리 이벤트의 정체성을 나타내지 않는다.

같은 논리 이벤트가 재발행되면 서로 다른 Offset을 갖는다. 이때 Offset을 Key로 사용하면 Consumer는 두 Record를 서로 다른 이벤트로 판단해 비즈니스 데이터를 두 번 반영한다. 그 결과, 멱등 처리가 동작하지 않는다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (
        subscriber_id,
        event_id
    )
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

다음 중 적절한 값을 선택하고 이유를 작성한다.

```
pod-7f8c9d

server-10.0.0.12

mypage-coupon-projection
```

```
적절한 값 : mypage-coupon-projection

인스턴스 ID를 Key에 포함하면 새 인스턴스가 뜰 때마다 subscriber_id가 달라져 이전 처리 기록과 연결되지 않는다.

mypage-coupon-projection의 경우 인스턴스가 몇 개든, 몇 번 재배포되든 값이 변하지 않기 때문에 적절하다.
```

### **4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다**

### **5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다**

```
Consumer DB 상태:
processed_event 저장과 user_coupon_view 변경이 모두 Commit된 상태

Consumer Group Offset:
Commit되지 않아 이전 위치에 머물러 있음

재시작 후 Kafka 전달:
해당 Offset부터 다시 읽으므로 같은 Record가 재전달

재전달된 이벤트 처리:
processed_event INSERT가 Primary Key 충돌로 반환 행이 없으므로 이미 처리한 이벤트로 판단하고 조회 모델 변경을 생략한다.
예외를 던지지 않고 정상 처리로 종료한 뒤 Offset을 Commit한다. 
중복 도착은 At-Least-Once 구조에서 예상되는 상황이므로 조용히 건너뛰는 것이 올바른 처리이며, 예외로 처리하면 Offset이 진행되지 않아 무한 재전달 루프가 된다.
```

### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**

```
processed_event는 Consumer 자신의 로컬 DB에 대한 중복 반영만 막는다.
외부 SMS 발송은 로컬 DB 트랜잭션에 포함되지 않는 별도 시스템 호출이므로
processed_event 저장과 원자적으로 묶이지 않는다. 또 하나의 Dual Write다.

SMS API를 먼저 호출하고 processed_event를 저장하면,
발송 성공 후 Commit 전에 종료될 때 기록이 남지 않아 재전달 시 중복 발송된다.
반대로 processed_event를 먼저 Commit하고 API를 호출하면,
발송 실패 시 이미 처리한 것으로 판단해 알림이 영구 누락된다.

Timeout도 문제가 된다. Provider가 실제로 발송했는데 응답만 유실된 경우와
발송 자체가 실패한 경우를 구분할 수 없어, 재시도하면 중복 발송이 되고
포기하면 누락이 된다. 이미 발송된 SMS는 회수할 수도 없다.

따라서 processed_event는 조회 모델 갱신 같은 로컬 상태 변경에는 유효하지만,
외부 알림이 물리적으로 정확히 한 번 전송되는 것은 보장하지 못한다.
```

### **7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다**

```
1. Notification Service 내부 Outbox
   알림 발송 의도를 processed_event와 같은 로컬 트랜잭션에 저장하고,
   별도 Sender가 그 행을 읽어 외부 API를 호출한다.
   Coupon Service의 Outbox와 같은 구조이며,
   발송 실패 시 재시도 대상이 DB에 남아 유실되지 않는다.

2. 외부 Provider의 Idempotency Key 사용
   발송 요청에 notificationId 같은 고유 Key를 함께 전달하면
   Provider가 같은 Key의 중복 요청을 걸러낸다.
   Timeout 후 재시도해도 실제 발송은 한 번만 이뤄진다.
   Key는 eventMessageId에서 결정적으로 파생시켜
   재시도할 때마다 같은 값이 나오도록 한다.

3. 발송 상태 테이블로 결과 추적
   알림 작업 테이블에 PENDING / SENT / FAILED와 Provider 응답 ID를 기록해
   발송 여부를 확인 가능한 상태로 남긴다.
   Timeout처럼 결과가 불확실한 경우 Provider에 조회 API가 있다면
   발송 여부를 확인한 뒤 재시도를 결정한다.
```

### **8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다**

다음을 포함한다.

```
Kafka Topic 보관 기간

Consumer Offset 되감기

Outbox 지연 재발행

운영자 수동 재발행
```

```
processed_event 보관 기간은 다음 조건을 만족해야 한다.

  processed_event 보관 기간 > Kafka Topic 보관 기간 + 최대 재전달 지연

기록이 삭제된 뒤에도 같은 이벤트가 다시 도착할 수 있는 경로가 있기 때문이다.
evt-001을 처리하고 기록을 지웠는데 Topic에 Record가 남아 있고
Offset이 되감기면, Consumer는 처음 보는 이벤트로 판단해 중복 반영한다.

중복이 재등장하는 경로는 다음과 같다.

Kafka Topic 보관 기간
Record가 남아 있는 동안은 언제든 다시 읽힐 수 있으므로
보관 기간이 짧으면 그 사이 삭제된 기록의 방어가 뚫린다.

Consumer Offset 되감기
장애 복구나 데이터 재구축을 위해 Offset을 과거로 되돌리거나
Consumer Group을 초기화하면 이미 처리한 Record가 전량 재전달된다.

Outbox 지연 재발행
Kafka 장애나 Backoff로 발행이 오래 밀린 이벤트가
한참 뒤에 도착할 수 있다.

운영자 수동 재발행
영구 실패로 분류된 Outbox 행을 다시 PENDING으로 바꿔 재발행하면
원래 발생 시점보다 훨씬 늦게 전달된다.

따라서 Kafka 보관 기간에 Consumer 장애 복구 시간, Offset 되감기 운영 범위,
Outbox 재발행 지연 최대치를 더한 값보다 길게 잡는다.
삭제는 Outbox와 마찬가지로 작은 Batch로 나누어 수행한다.
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateType = COUPON_ISSUE

aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
1. Consumer의 병렬 처리 단위를 명확히 하기 위해
Kafka는 Partition 단위로 Consumer에게 할당되므로,
같은 couponIssueId의 이벤트는 항상 같은 Consumer 인스턴스가 처리한다.
서로 다른 인스턴스가 같은 Aggregate를 동시에 다루는 상황이 생기지 않아
조회 모델 갱신 시 경합을 줄일 수 있다.

2. 특정 Partition으로 부하가 몰리지 않도록 분산하기 위해
couponIssueId는 발급마다 고유하므로 Key가 고르게 흩어진다.
couponEventId를 Key로 쓰면 하나의 행사에서 발생한 수천 건이
전부 한 Partition에 몰려 처리량이 그 Partition에 묶인다.

3. 향후 순서 보장을 도입할 때의 기준 단위를 미리 정해두기 위해
Kafka에서 순서는 Partition 안에서만 의미가 있으므로,
Aggregate 단위 순서를 보장하려면 그 Aggregate의 이벤트가
같은 Partition에 모여 있어야 한다.
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

다음을 반드시 포함한다.

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
Kafka에서 Partition 안의 순서는 Producer가 send()를 호출한 순서로 결정된다. Outbox에 저장된 순서가 아니다. 

여러 Publisher 인스턴스
서로 다른 인스턴스가 서로 다른 배치를 서로 다른 속도로 처리한다.
나중에 저장된 이벤트를 맡은 인스턴스가 먼저 발행을 끝낼 수 있다.

SKIP LOCKED
다른 세션이 잠근 행을 기다리지 않고 건너뛰어 다음 행을 가져온다.
애초에 순서를 포기하고 처리량을 얻는 장치다.
ORDER BY가 있어도 잠긴 행이 제외되므로 전체 발행 순서는 보장되지 않는다.

발행 실패와 Backoff
먼저 저장된 이벤트가 발행에 실패하면 next_attempt_at이 미래로 밀린다.
그 사이 나중에 저장된 이벤트가 먼저 발행된다.
단일 Publisher 인스턴스만 사용해도 이 원인만으로 역전이 발생한다.

Producer 설정과 재시도
max.in.flight.requests.per.connection이 1보다 크고 재시도가 발생하면
Producer 내부에서도 배치 순서가 뒤바뀔 수 있다.
enable.idempotence = true이면 Producer가 시퀀스로 순서를 유지하지만,
이는 한 Producer 세션 안의 보장일 뿐 서로 다른 Publisher가
각자의 Producer로 발행하는 순서까지 맞춰주지는 않는다.

따라서 이번 주차의 발행 보장 수준은 At-Least-Once Publication이며
순서는 보장하지 않는다. Consumer가 aggregateVersion으로 방어한다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A:
outbox 1번(CouponIssued)을 token-A로 Claim했으나 Kafka 발행에 실패한다.
claim_token 조건을 확인한 뒤 PENDING으로 되돌리고
next_attempt_at을 현재 시각 + 4초로 저장한다.

Publisher B:
outbox 2번(CouponCancelled)을 token-B로 Claim해 발행에 성공한다.
Broker ACK를 확인하고 PUBLISHED로 변경한다.

이후 next_attempt_at이 도래하면 CouponIssued가 다시 Claim되어 발행된다.

Kafka 저장 순서:
Offset 200 : CouponCancelled  (aggregateVersion = 2)
Offset 201 : CouponIssued     (aggregateVersion = 1)
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면:
아직 Kafka에 발행되지 않은 이벤트가 사라진다.
발급 결과는 DB에 확정되어 있는데 발행할 근거만 없어지므로
후속 서비스는 발급 사실을 영영 알 수 없고, 무엇을 다시 보내야 하는지도
알 수 없어 복구가 불가능하다.

PROCESSING을 삭제하면:
발행 성공 여부가 확정되지 않은 이벤트가 사라진다.
Kafka에 저장되었는지 아닌지 알 수 없는 상태이므로,
저장되지 않았다면 그대로 유실되고 Lease 만료 회수 기회도 사라진다.

PUBLISHED를 보관하는 목적:
운영과 조사 목적이다.
특정 이벤트가 실제로 발행되었는지, 언제 발행되었는지(published_at),
몇 번 재시도했는지(attempt_count), 어떤 오류가 있었는지(last_error)를 확인해
발행 지연을 분석하고 장애를 추적한다.
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

다음 항목을 포함한다.

```
긴 트랜잭션

DB 부하

Lock

Table Bloat
```

```
긴 트랜잭션
수십만 행을 한 번에 삭제하면 트랜잭션이 오래 열려 있게 된다.
PostgreSQL은 열린 트랜잭션보다 오래된 dead tuple을 정리하지 못하므로
VACUUM이 지연되고, 트랜잭션 Timeout에 걸려 전체가 Rollback되면
그동안의 작업이 전부 무효가 된다.

DB 부하
대량 DELETE는 디스크 I/O와 WAL 생성량을 급격히 늘린다.
Outbox 테이블은 발급 트랜잭션의 INSERT와 Publisher의 Claim·완료 UPDATE가
동시에 몰리는 테이블이므로, 정리 작업이 발급 처리량과 발행 처리량을
동시에 떨어뜨린다.

Lock
삭제 대상 행에 잠금이 유지되어 같은 페이지의 다른 행에 접근하는
Claim 쿼리와 경합한다. Connection Pool 점유도 길어져
발급 트랜잭션이 커넥션을 얻지 못하는 상황으로 번질 수 있다.

Table Bloat
PostgreSQL의 DELETE는 행을 즉시 제거하지 않고 dead tuple로 표시한다.
대량 삭제로 dead tuple이 한꺼번에 생기면 autovacuum이 따라가지 못해
테이블과 인덱스가 커진 채로 남고, Claim 쿼리의 인덱스 스캔 효율이 떨어진다.
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
각 배치를 Commit한 뒤 짧게 대기했다가 다음 배치를 수행하고,
삭제 대상이 없으면 종료한다. 대기 구간은 autovacuum이 dead tuple을
정리하고 발급·발행 트랜잭션이 커넥션과 잠금을 확보할 여유를 만든다.

status = 'PUBLISHED' 조건은 반드시 유지한다.
PENDING이나 PROCESSING이 삭제되면 아직 발행이 확정되지 않은 이벤트가
유실되기 때문이다. cutoff는 발행 이력 조사에 필요한 기간을 기준으로 정하며,
Kafka Topic이나 processed_event 보관 기간과는 별개의 정책이다.

정리 진행 상황도 함께 관측한다. 배치 소요 시간, 삭제 건수,
남아 있는 PUBLISHED 행 수를 기록해 생성 속도보다 정리 속도가 느려
테이블이 계속 커지고 있지는 않은지 확인한다.
필요하다면 삭제 대신 별도 아카이브 테이블로 이동시켜 이력을 보존한다.
```

### **7. 다음 세 보관 기간의 목적을 비교한다**

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

```
1.
문제 위치: issueCoupon() — kafkaTemplate.send() 호출
문제 내용: 발급 DB 트랜잭션 안에서 Kafka를 직접 호출한다.
          서로 다른 시스템이므로 @Transactional로 묶이지 않는다.
발생 가능한 장애: DB Commit 후 발행 전 종료 시 이벤트 유실,
          발행 후 DB Rollback 시 존재하지 않는 발급의 이벤트 전파.
수정 방법: Kafka 호출을 제거하고 발급 트랜잭션에서는 DB 작업만 수행한다.

2.
문제 위치: issueCoupon() — outbox_event INSERT 없음
문제 내용: 발행 의도를 DB에 남기지 않아 발행 대상이 메모리에만 존재한다.
발생 가능한 장애: 프로세스 종료 시 무엇을 발행해야 하는지 알 수 없어
          복구가 불가능하다.
수정 방법: 발급 결과 확정과 같은 트랜잭션에서 Outbox 행을 저장한다.

3.
문제 위치: issueCoupon() — issued_count 증가와 request 상태 전이 누락
문제 내용: 수량 조건부 UPDATE와 requestId 기반 멱등 처리가 없다.
발생 가능한 장애: 수량 초과 발급, 원본 메시지 재전달 시 중복 발급.
수정 방법: PENDING → PROCESSING 획득, 조건부 issued_count 증가,
          request → ISSUED 확정을 수행하고 영향받은 행 수를 검증한다.

4.
문제 위치: publishOutbox() — @Transactional로 배치 전체를 감쌈
문제 내용: Kafka 발행과 ACK 대기가 DB 트랜잭션 안에서 수행된다.
발생 가능한 장애: Connection Pool 고갈, Row Lock 장기 점유,
          트랜잭션 Timeout, Table Bloat, 발급 트랜잭션까지 영향받는 연쇄 장애.
수정 방법: Claim 트랜잭션을 짧게 Commit하고 Kafka 호출은 트랜잭션 밖에서 수행한다.

5.
문제 위치: publishOutbox() — findTop100ByStatus("PENDING")
문제 내용: 단순 조회로 행을 가져와 동시 Claim 방어가 없고
          next_attempt_at 조건이 없어 Backoff가 무시된다.
발생 가능한 장애: 여러 Publisher가 같은 행을 동시에 발행해
          중복이 인스턴스 수에 비례하고, 장애 시 재시도 부하가 증폭된다.
수정 방법: FOR UPDATE SKIP LOCKED로 Claim하고
          next_attempt_at <= now() 조건을 추가한다.

6.
문제 위치: publishOutbox() — claim_token, lease_until 부재
문제 내용: 처리 권한을 식별하고 만료를 판단할 수단이 없다.
발생 가능한 장애: 권한을 잃은 Publisher가 최신 소유자의 상태를 덮어써
          발행되지 않은 이벤트가 PUBLISHED로 확정되거나 중복이 증폭된다.
수정 방법: Claim 시 두 값을 저장하고 모든 상태 변경 UPDATE의 WHERE에
          claim_token 조건을 둔다.

7.
문제 위치: publishOutbox() — createPayloadFromCurrentCouponIssue(event)
문제 내용: 발행 시점에 현재 비즈니스 테이블을 조회해 Payload를 재생성한다.
발생 가능한 장애: 발행 대기 중 원본이 변경되면 COUPON_ISSUED인데
          취소된 내용이 전달되고, 같은 eventMessageId가 서로 다른 내용으로
          발행되어 멱등성 전제가 깨진다.
수정 방법: Outbox INSERT 시점에 확정한 payload를 그대로 전달한다.

8.
문제 위치: publishOutbox() — event.markPublished()와 실패 처리 부재
문제 내용: ACK 확인 없이 send() 직후 PUBLISHED로 변경하고,
          발행 실패 시 재시도 정책과 attempt_count, last_error 기록이 없다.
          한 건의 예외가 배치 전체를 Rollback시킨다.
발생 가능한 장애: 발행 실패나 Timeout에도 완료로 기록되어
          재시도 대상에서 빠지고 이벤트가 영구 유실된다.
수정 방법: timeout으로 ACK를 확인한 뒤 PUBLISHED로 변경하고,
          건별 try-catch로 실패 시 Backoff + Jitter 기반
          next_attempt_at과 last_error를 기록한다.

9.
문제 위치: recoverProcessing() — updateAllProcessingToPending()
문제 내용: lease_until 만료 조건 없이 모든 PROCESSING 행을 회수한다.
발생 가능한 장애: 정상 발행 중인 이벤트까지 PENDING으로 되돌려
          다른 Publisher가 동시에 발행하면서 중복이 대량 발생한다.
수정 방법: lease_until <= CURRENT_TIMESTAMP 조건을 추가한다.

10.
문제 위치: onResult() — Offset 기반 멱등 Key와 저장 순서
문제 내용: Kafka Partition/Offset을 멱등성 Key로 사용하고,
          비즈니스 데이터를 먼저 저장하며 두 작업이 트랜잭션으로 묶여 있지 않다.
          aggregateVersion 검증도 없다.
발생 가능한 장애: 재발행된 이벤트가 다른 Offset을 가져 중복 반영되고,
          한쪽만 Commit되면 중복 또는 영구 누락이 발생한다.
          순서 역전 시 낮은 버전이 최신 상태를 덮어쓴다.
수정 방법: 하나의 트랜잭션에서 (subscriber_id, eventMessageId) 기준으로
          ON CONFLICT DO NOTHING RETURNING INSERT를 먼저 수행하고,
          반환 행이 있을 때만 last_aggregate_version 비교와 함께
          조회 모델을 변경한다. Offset은 Commit 이후 반영한다.
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 두 작업 모두 같은 PostgreSQL Database에 대한 쓰기이므로 하나의 로컬 트랜잭션에 포함된다. 함께 Commit되거나 함께 Rollback되므로 발급이 확정되었는데 발행할 이벤트 기록이 없는 상태는 발생하지 않는다 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | ACK 확인 후 PUBLISHED 변경 전 종료, Timeout 후 재시도, Lease 만료 후 회수로 같은 eventMessageId가 여러 번 저장될 수 있다. Kafka 저장과 Outbox 상태 변경은 서로 다른 시스템에 대한 쓰기라 또 하나의 Dual Write이며, Producer Idempotence도 세션 범위라 이를 막지 못한다. 보장 수준은 At-Least-Once Publication이다 |
| Publisher 복구 후 재발행 | 조건부 보장 | 발행할 이벤트가 DB에 남아 있으므로 근거는 유실되지 않는다. 다만 실제 발행되려면 Publisher가 계속 동작하고, Kafka 장애가 회복되며, 실패를 재시도하고, 발행 전에 Outbox 행을 삭제하지 않고, 영구 실패를 운영에서 확인해 복구해야 한다 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED가 잠긴 행을 건너뛰고, 실패 후 Backoff로 next_attempt_at이 밀리며, 여러 Publisher 인스턴스가 서로 다른 속도로 처리한다. Partition Key를 고정해도 Partition 안의 순서는 send() 호출 순서로 결정되므로 DB 저장 순서와 달라진다. 단일 인스턴스여도 Backoff만으로 역전이 발생한다 |
| Consumer의 중복 비즈니스 반영 방지 | 조건부 보장 | processed_event와 비즈니스 변경을 같은 트랜잭션으로 묶고 eventMessageId를 Key로 사용하면 로컬 DB에 대한 중복 반영은 막을 수 있다. 다만 보관 기간이 Kafka Topic 보관 기간 + 최대 재전달 지연보다 짧으면 기록이 삭제된 뒤 재전달될 때 방어가 뚫린다 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | outbox = PUBLISHED는 Broker ACK 확인까지만 의미한다. 각 Consumer Group은 자신의 Offset과 처리 결과를 독립적으로 관리하므로, 한 그룹이 처리했다고 다른 그룹의 처리를 알 수 없다. Consumer Group Lag으로 별도 관측해야 한다 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API 호출은 로컬 DB 트랜잭션에 포함되지 않는 또 다른 Dual Write다. processed_event는 로컬 상태 변경의 중복만 막으며, Timeout 시 실제 발송 여부를 구분할 수 없어 재시도하면 중복, 포기하면 누락이 된다. Notification 내부 Outbox와 Provider의 Idempotency Key가 추가로 필요하다 |
