## 과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기

### 1. 위 코드가 사용하는 저장소 두 개를 작성한다

```
1. PostgreSQL (Transaction: increaseIssuedCount, saveCouponIssue, markRequestIssued)
2. Kafka Broker (kafkaTemplate.send로 coupon.issued 발행)
```

### 2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다

```
@Transactional은 하나의 PostgreSQL 로컬 트랜잭션의 경계만 관리한다.
Kafka Broker는 PostgreSQL 트랜잭션에 참여하지 않는 별개의 시스템이다.

- DB 트랜잭션이 Rollback되어도 이미 Broker에 저장된 Kafka Record는 되돌아가지 않는다.
- Kafka 발행이 실패해도 DB 트랜잭션은 이미 Commit되었을 수 있다.

두 시스템을 하나의 원자적 단위로 묶으려면 XA/2PC 같은 분산 트랜잭션이 필요하지만
Kafka는 그런 방식으로 참여하지 않는다.
따라서 @Transactional을 붙여도 DB Commit과 Kafka 저장 사이에는
한쪽만 성공할 수 있는 장애 구간이 남는다.
```

### 3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다

```
DB Commit
    ↓
[장애 지점] DB Commit 성공 후 Kafka 발행 전 프로세스 종료 (또는 발행 실패)
    ↓
Kafka 발행

최종 DB 상태:
쿠폰 발급 완료 (issued_count 증가, coupon_issue 존재, request ISSUED)

최종 Kafka 상태:
CouponIssued 이벤트 없음

후속 서비스에 미치는 영향:
Notification/MyPage/Analytics가 발급 사실을 알 수 없다. 알림 누락, 쿠폰함 미갱신,
통계 누락이 발생한다.

복구에 필요한 정보:
어떤 발급 결과에 대해 어떤 이벤트를 발행해야 하는지에 대한 기록.
이 정보가 메모리에만 있었다면 재시작 후 무엇을 재발행할지 알 수 없다.
(쿠폰은 이미 발급됐으므로 재발급이 아니라 누락 이벤트 재발행만 필요하다)
```

### 4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다

```
Kafka 발행
    ↓
[장애 지점] Kafka 발행 성공 후 DB Commit 전 트랜잭션 실패/프로세스 종료
    ↓
DB Commit

최종 DB 상태:
쿠폰 발급 기록 없음 (Rollback되어 issued_count 증가 없음, coupon_issue 없음)

최종 Kafka 상태:
CouponIssued 이벤트 존재

후속 서비스에 미치는 영향:
실제로는 발급되지 않은 쿠폰에 대해 후속 서비스가 처리한다.
존재하지 않는 발급에 대한 알림 발송, 쿠폰함에 유령 쿠폰 표시,
잘못된 통계 반영이 발생한다.
```

### 5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다

```
AFTER_COMMIT은 DB Commit 전에 이벤트가 발행되는 문제(4번 상황)는 막지만,
발행할 이벤트가 여전히 메모리에만 존재하므로 다음 두 장애에서 유실이 발생한다.

DB Commit 후 Listener 실행 전 프로세스 종료:
DB는 이미 발급을 Commit했는데 Listener가 실행되기 전에 프로세스가 죽으면,
발행해야 할 이벤트 정보가 메모리와 함께 사라진다. 재시작 후 무엇을 발행할지 알 수 없다.

KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료:
send()는 비동기라서 호출이 끝났다고 Broker 저장이 확정된 것이 아니다.
ACK를 확인하기 전에 프로세스가 죽으면 실제로 발행됐는지 알 수 없고,
DB 결과는 이미 Commit되어 되돌릴 수 없다.

핵심: 발행할 이벤트가 메모리에만 있으면 프로세스 종료 시 복구 기준이 사라진다.
Outbox는 발행할 이벤트를 메모리가 아니라 DB에 저장해 이 문제를 해결한다.
```

### 6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다

```
| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔ CouponIssued 발행 의도 저장 | 해결됨 | 둘 다 같은 PostgreSQL 트랜잭션에 저장되어 함께 Commit/Rollback되므로 |
| Redis SUCCESS ↔ 최초 요청 Kafka 발행 | 해결 안 됨 | Redis와 PostgreSQL은 별개 저장소라 하나의 로컬 트랜잭션에 묶이지 않음 |
| 원본 Kafka 소비 ↔ 발급 DB Commit | 해결 안 됨 | Outbox의 범위가 아님. requestId 기반 멱등 처리로 방어 |
| Consumer DB 저장 ↔ 외부 SMS API 호출 | 해결 안 됨 | 외부 API는 로컬 DB 트랜잭션에 포함되지 않는 또 다른 Dual Write |
```

### 7. 다음 문장을 완성한다

```
Transactional Outbox가 직접 보장하는 것:
DB 발급 결과가 Commit되면 발행할 이벤트 기록(Outbox 행)도 반드시 같은 DB에 남는다.
즉 "발급 결과는 Commit됐는데 발행할 이벤트 기록이 없는 상태"가 발생하지 않는다.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record가 물리적으로 정확히 한 번만 생성되는 것,
이벤트가 비즈니스 발생 순서대로 전달되는 것,
모든 Consumer가 반드시 처리 완료하는 것,
외부 알림이 정확히 한 번 전송되는 것.
(재시도로 중복 발행이 발생할 수 있으므로 Consumer 멱등 처리가 필요하다)
```

## 과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기

### 1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다

```
IssueCoupon:
"쿠폰을 발급하라"는 명령(Command). 받는 쪽이 발급 로직을 실행해야 한다는 의미다.

CouponIssued:
"쿠폰이 발급되었다"는 이미 확정된 과거의 사실(Event).

이 이벤트는 DB 트랜잭션에서 발급이 이미 확정된 뒤에 발행된다.
따라서 Consumer는 이 이벤트를 받아 쿠폰을 다시 발급하면 안 되고,
이미 발생한 사실에 대한 후속 처리(알림, 조회 모델 갱신, 통계 반영)만 해야 한다.

이름을 사실로 두면 이벤트가 재전달·중복 발행되어도 Consumer가
발급 로직을 재실행하지 않으므로 멱등 처리가 자연스럽다.
명령으로 두면 중복 전달 시 재발급 위험이 생긴다.
```

### 2. CouponIssued 이벤트 JSON을 완성한다

```json
{
  "eventMessageId": "8a78e94b-5c3d-46a7-a364-538cd1f856c9",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### 3. 다음 ID의 역할을 비교한다

```
| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 행사(이벤트) | 안 바뀜 | 부적절. 한 행사에 수많은 발급이 있어 이벤트 단위 식별 불가 |
| couponIssueId | 하나의 발급 기록 | 안 바뀜 | 조건부 사용 가능하나 이벤트 유형이 여럿이면 부족(발급/취소 구분 불가) |
| eventMessageId | 결과 이벤트 메시지 자체 | 안 바뀜(재발행해도 동일 유지) | 적절. 논리 이벤트 하나를 유일하게 식별 |
| Kafka Partition + Offset | Kafka 안의 물리적 위치 | 바뀜(재발행 시 다른 Offset) | 부적절. 같은 논리 이벤트가 다른 Offset을 가질 수 있음 |
```

### 4. `occurredAt`과 `publishedAt`의 차이를 설명한다

```
occurredAt:
쿠폰 발급이라는 비즈니스 결과가 실제로 발생한 시각.
발급 이벤트에서는 issuedAt과 같은 기준 시각을 사용할 수 있다.

publishedAt:
Publisher가 Kafka Broker ACK를 확인한 뒤 Outbox 행에 기록하는 발행 완료 시각.

Publisher 재시도 시 변경하면 안 되는 값:
occurredAt (그리고 payload 전체). occurredAt은 비즈니스 발생 사실이므로 불변이다.
재발행으로 실제 Kafka 전송 시각(publishedAt)은 바뀌지만 occurredAt은 그대로 유지한다.
```

### 5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다

```
Outbox INSERT 시점과 실제 발행 시점 사이에 원본 비즈니스 데이터가 변경될 수 있기 때문이다.

예: CouponIssued를 발행하기 전에 해당 쿠폰이 취소되어 상태가 바뀌었다면,
발행 시점에 조회하면 "발급됨"이 아닌 최신 상태를 담게 되어
이벤트가 나타내야 할 과거 사실과 달라진다.

Outbox 행은 특정 시점에 발생한 사실의 불변 Snapshot이어야 한다.
따라서 발행할 Payload를 Outbox INSERT 시점에 완성해 저장하고,
Publisher는 저장된 Payload를 그대로 전달만 한다.
```

### 6. 다음 Outbox 테이블 DDL을 완성한다

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,

    -- 도메인 추적용. 필수가 아니다(선택).
    request_id UUID,

    -- 같은 비즈니스 결과의 중복 Outbox 생성 방지
    deduplication_key VARCHAR(200) NOT NULL UNIQUE,

    -- Aggregate 식별 정보 (필수)
    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,

    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,

    -- Topic, Partition Key, Payload
    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,

    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',

    -- 재시도 횟수와 다음 재시도 시각
    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- Claim Token과 Lease
    claim_token UUID,
    lease_until TIMESTAMPTZ,

    last_error VARCHAR(1000),

    -- 발생 시각과 발행 완료 시각
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),

    CONSTRAINT chk_outbox_schema_version
        CHECK (schema_version >= 1),

    CONSTRAINT chk_outbox_aggregate_version
        CHECK (aggregate_version >= 1),

    CONSTRAINT chk_outbox_attempt_count
        CHECK (attempt_count >= 0),

    -- 상태별로 claim_token/lease_until/published_at 조합을 강제
    CONSTRAINT chk_outbox_state_fields
        CHECK (
            (status = 'PENDING'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NULL)
            OR
            (status = 'PROCESSING'
                AND claim_token IS NOT NULL
                AND lease_until IS NOT NULL
                AND published_at IS NULL)
            OR
            (status = 'PUBLISHED'
                AND claim_token IS NULL
                AND lease_until IS NULL
                AND published_at IS NOT NULL)
        )
);

-- 발행 가능한 PENDING 조회용 Partial Index
CREATE INDEX idx_outbox_pending
ON outbox_event (next_attempt_at, created_at, event_id)
WHERE status = 'PENDING';

-- 만료된 PROCESSING 조회용 Index
CREATE INDEX idx_outbox_expired_processing
ON outbox_event (lease_until, event_id)
WHERE status = 'PROCESSING';
```

### 7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다

```
outbox_event.event_id = payload.eventMessageId

검증 방법:
1. 애플리케이션 레벨:
   Outbox 행을 만들 때 event_id와 payload의 eventMessageId를 같은 UUID 변수 하나로
   설정한다. CouponIssuedEvent를 만들 때 생성한 eventMessageId를
   그대로 outbox_event.event_id에 사용한다.

2. DB 레벨(보조):
   JSONB에서 값을 추출해 CHECK 제약으로 검증할 수 있다.
   CHECK (event_id = (payload->>'eventMessageId')::uuid)
   다만 payload 형식 의존성이 커지므로 애플리케이션 검증을 기본으로 하고,
   테스트나 정합성 배치로 event_id = payload->>'eventMessageId'를 확인한다.

이 불변조건이 지켜져야 Consumer가 eventMessageId로 멱등 처리한 것과
Outbox의 event_id 기준 관리가 일치한다.
```

### 8. `deduplication_key`를 설계한다

```
Key 형식:
{eventType}:{aggregateType}:{aggregateId}

예시:
COUPON_ISSUED:COUPON_ISSUE:5001
```

```
같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면
추가 구분자가 필요하다.

예: CouponUsed는 같은 couponIssueId에서 반복될 수 있으므로
    발생 시점이나 시퀀스(aggregateVersion 등)를 Key에 추가해야 한다.
    COUPON_USED:COUPON_ISSUE:5001:{aggregateVersion}

CouponIssued는 하나의 couponIssueId에 대해 한 번만 발생하므로
위 기본 형식(추가 구분자 없이)으로 충분하다.
```

### 9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다

```
| 선택지 | 설명 및 판단 |

전체 Rollback 후 새 트랜잭션에서 조회:
PostgreSQL은 제약 위반 후 같은 트랜잭션을 계속 쓸 수 없으므로,
Rollback한 뒤 새 트랜잭션에서 기존 행을 조회해야 한다.
이번 설계에서는 정상 경로라면 이 위반이 발생하지 않으므로(11절 첫 UPDATE가 차단),
위반 발생 시 전체 Rollback하고 알람을 발생시킨다. (기본 정책)

Savepoint 사용:
INSERT 전에 SAVEPOINT를 두면 위반 시 그 지점까지만 롤백해
트랜잭션을 이어갈 수 있다. 발급 트랜잭션 전체를 살리고 싶을 때 쓸 수 있으나,
이번 설계에서는 위반 자체가 이상 신호이므로 전체 Rollback + 알람이 더 적절하다.

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교:
멱등 INSERT 방식으로 설계하고 싶을 때 사용한다. 충돌 시 조용히 넘기지 않고
기존 행의 request_id, aggregate_type/id, event_type, schema_version,
aggregate_version, payload가 모두 같은지 확인해야 한다.
모두 같으면 동일 이벤트로 보고 기존 행 재사용, 다르면 알람.

이번 과제 기본 선택:
ON CONFLICT를 쓰지 않고 위반 시 전체 Rollback + 알람.
조용히 넘기면 요청 상태 관리 결함이나 Key 생성 버그를 숨길 수 있기 때문이다.
```

## 과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기

### 1. 전체 SQL 트랜잭션을 완성한다

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득 (반드시 1행)
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows = 1인 경우에만 계속 진행. 0이면 기존 상태 조회로 분기.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;
-- affected rows = 0이면 가능한 원인: 이벤트 없음, 또는 수량 소진(SOLD_OUT).
-- (상태/기간 조건을 넣었다면 종료/비활성 이벤트도 0행이 될 수 있음)
-- 이 경우 INSERT하지 않고 request를 FAILED/SOLD_OUT으로 확정 후 Commit.

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (
    event_id, user_id, status, issued_at
) VALUES (
    :couponEventId, :userId, 'ISSUED', CURRENT_TIMESTAMP
)
RETURNING id, issued_at;
-- 반환값을 couponIssueId, issuedAt으로 사용.
-- UNIQUE(event_id, user_id) 위반 시 전체 Rollback → 별도 트랜잭션에서 확정.

-- 4. request를 ISSUED로 변경 (반드시 1행)
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장 (ON CONFLICT 미사용)
INSERT INTO outbox_event (
    event_id, request_id, deduplication_key,
    aggregate_type, aggregate_id,
    event_type, schema_version, aggregate_version,
    topic, partition_key, payload, occurred_at
) VALUES (
    :eventMessageId, :requestId, :deduplicationKey,
    'COUPON_ISSUE', CAST(:couponIssueId AS VARCHAR),
    'COUPON_ISSUED', 1, 1,
    'coupon.issued', CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB), :issuedAt
);

COMMIT;
```

### 2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다

```
| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1 | 0이면 기존 상태 조회: ISSUED/FAILED는 멱등 종료, PROCESSING은 이상 신호(11-5), 행 없음/불일치는 별도 분류 |
| issued_count 조건부 증가 | 1 | 0이면 수량 소진 또는 이벤트 없음. INSERT 생략하고 FAILED/SOLD_OUT 확정 후 Commit |
| coupon_issue INSERT | 1 | UNIQUE 위반 시 전체 Rollback 후 별도 트랜잭션에서 DUPLICATE_USER 확정 |
| PROCESSING → ISSUED | 1 | 0이면 상태 불일치. 발급 결과와 어긋나므로 전체 Rollback |
| outbox_event INSERT | 1 | 실패 시 전체 Rollback (dedup UNIQUE 위반은 이상 신호 → Rollback + 알람) |
```

### 3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다

```
트랜잭션 결과:
전체 Rollback

coupon_event.issued_count:
증가가 취소되어 원래 값으로 복구

coupon_issue:
INSERT가 취소되어 발급 기록 없음

coupon_issue_request:
ISSUED 변경이 취소되어 PENDING으로 복구

outbox_event:
없음 (INSERT 실패로 저장되지 않음)
```

### 4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다

```
발급 결과만 Commit하고 Outbox INSERT 실패를 무시하면,
"쿠폰은 발급됐는데 발행할 이벤트 기록이 DB에 없는" 상태가 된다.

이는 정확히 Dual Write 문제이자 AFTER_COMMIT 방식의 유실 상황과 같다.
Outbox 행이 없으므로 Publisher가 발행할 대상 자체가 없고,
후속 서비스는 발급 사실을 영원히 알 수 없다(알림/쿠폰함/통계 누락).

Outbox 패턴의 핵심 보장은 "DB 발급 결과가 Commit되면 발행할 이벤트 기록도 반드시 남는다"이다.
Outbox INSERT 실패를 무시하면 이 보장이 깨지므로 전체 트랜잭션을 Rollback해야 한다.
```

### 5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다

```
issued_count를 다시 증가시키는가?
아니다. 첫 번째 UPDATE(PENDING → PROCESSING)가 0행이 되어
수량 증가 단계까지 진행하지 않는다.

coupon_issue를 다시 생성하는가?
아니다. 이미 발급 기록이 존재하고, 이 흐름에서는 INSERT 단계에 도달하지 않는다.

Outbox를 다시 INSERT하는가?
아니다. 새 Outbox를 만들지 않는다. (설령 도달해도 deduplication_key UNIQUE가 방어)

Consumer 처리는 성공으로 종료할 수 있는가?
그렇다. request가 이미 ISSUED임을 확인하면 최종 상태에 도달한 것이므로
새 발급/새 Outbox 없이 정상 처리로 종료하고 원본 Kafka Offset을 Commit한다.
```

### 6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다

```
DB 상태:
request = ISSUED, coupon_issue 존재, issued_count 증가 반영, outbox_event PENDING 존재
(모두 Commit됨)

Outbox 상태:
PENDING (아직 Publisher가 발행하지 않음)

Kafka 원본 메시지:
Offset이 Commit되지 않아 coupon.issue.requested 메시지가 재전달될 수 있음

재시작 후 필요한 멱등성 기준:
requestId 기반 멱등 처리. 재전달된 메시지의 requestId로 요청 상태를 조회해
이미 ISSUED임을 확인하고 발급 로직과 Outbox INSERT를 다시 실행하지 않는다.
Outbox(발행 의도 유실 방어)와 requestId 멱등(원본 중복 처리 방어)은 역할이 다르므로
함께 사용해야 한다.
```

### 7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다

```
enable.auto.commit:
false로 둔다. 자동 커밋을 켜면 DB 트랜잭션 Commit 시점과 어긋나
DB 처리 전에 Offset이 커밋되어 메시지가 유실될 수 있다.

AckMode:
DB 결과가 확정된 뒤 수동으로 Ack하도록 구성한다(예: MANUAL/MANUAL_IMMEDIATE).
발급 DB 트랜잭션 Commit 후에만 처리 완료로 간주한다.

Listener 예외 처리:
DB 트랜잭션이 Rollback되는 예외가 발생하면 Offset을 Commit하지 않아
메시지가 재전달되게 한다. 일시적 오류는 재처리로 넘긴다.

Error Handler가 실패를 정상 처리로 바꾸는지 여부:
Error Handler가 예외를 삼켜 실패를 성공(Ack)으로 바꾸면 메시지가 유실된다.
재시도가 필요한 실패는 Offset을 커밋하지 않도록 Error Handler 정책을 확인한다.
```

## 과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기

### 1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다

```
Publisher A                          Publisher B
------------------------------------------------------------
SELECT PENDING → evt-001 조회
                                     SELECT PENDING → evt-001 조회
evt-001을 PROCESSING으로 UPDATE
                                     evt-001을 PROCESSING으로 UPDATE
evt-001 Kafka 발행
                                     evt-001 Kafka 발행 (중복 발행)
------------------------------------------------------------

두 Publisher가 모두 UPDATE 전에 같은 PENDING 행을 조회했기 때문에
동일 이벤트를 각자 Claim해 동시에 발행한다. (불필요한 중복 발행)
```

### 2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY
        next_attempt_at,
        created_at,
        event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### 3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다

```
1. DB Connection 장시간 점유: Kafka ACK를 기다리는 동안 트랜잭션이 열려 있으면
   Connection Pool의 커넥션을 오래 잡아 다른 작업이 커넥션을 얻지 못한다.

2. Row Lock 장시간 유지: 잠긴 행 때문에 다른 Publisher나 정리 배치가 대기하고,
   전체 처리량이 떨어진다.

3. 트랜잭션 Timeout / 장애 전파: Kafka가 느리거나 장애가 나면
   DB 트랜잭션이 Timeout에 걸리거나, Kafka 지연이 DB 자원 고갈로 번져
   발급 트랜잭션 등 다른 DB 작업까지 영향을 받는다.
```

### 4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다

```
인스턴스가 하나뿐이어도 Claim을 Commit한 직후(PROCESSING 상태 저장 직후)
Kafka 발행 전에 프로세스가 종료될 수 있다.

이 경우 그 행은 PROCESSING으로 남고, 재시작한 같은 Publisher도
PENDING만 조회하므로 그 행을 영원히 다시 가져가지 못한다.

따라서 lease_until 만료로 회수하거나, 시작 시 stale PROCESSING을
PENDING으로 복구하는 정책이 없으면 이벤트가 발행되지 않고 고착된다.
```

### 5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### 6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다

```
Claim Token이 없으면 Publisher A가 뒤늦게 성공/실패 UPDATE를 실행할 때
"현재 처리 권한이 누구에게 있는지" 확인할 수단이 없다.

Publisher A(만료된 처리자)가 조건 없이 상태를 UPDATE하면,
- 이미 Publisher B가 새로 Claim(token-B)해 처리 중인 행을 A가 PUBLISHED나 PENDING으로
  덮어써 버린다.
- B의 최신 처리 결과가 A의 오래된 결과로 무효화되어 상태가 뒤엉킨다.
- 예: B가 PUBLISHED로 만든 행을 A가 PENDING으로 되돌려 불필요한 재발행을 유발한다.

Claim Token을 두고 성공/실패 UPDATE의 WHERE에 claim_token = :myToken을 넣으면,
A의 토큰(token-A)과 현재 행의 토큰(token-B)이 달라 affected rows = 0이 되어
오래된 처리자가 최신 상태를 덮어쓰지 못한다.
```

### 7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### 8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다

```
Lease 시간
>
(batchSize × 건당 최대 대기 시간)
+
여유 시간(여러 상태 UPDATE·GC·스케줄 지터 등을 위한 버퍼)

- 건당 최대 대기 시간은 Publisher가 get()에 지정한 timeout이며,
  Producer의 delivery.timeout.ms와 함께 설계해야 한다.
- Lease가 너무 짧으면 아직 발행 중인데 만료되어 다른 Publisher가 회수하고
  동시에 중복 발행이 늘어난다.
- 그래서 이번 주차 기본 전략은 batchSize를 작게(50~100) 두어
  Lease 산정을 단순하게 만드는 것이다.
```

## 과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기

### 1. 다음 네 상태의 의미 차이를 설명한다

```
KafkaTemplate.send() 호출 완료:
send()가 CompletableFuture를 반환하며 돌아왔을 뿐이다. 비동기이므로
Broker 저장이 확정된 것이 아니다.

CompletableFuture 정상 완료:
Broker로부터 ACK를 받아 발행이 성공했음을 확인한 상태. (get()이 정상 반환)

outbox = PUBLISHED:
ACK 확인 후 DB에 완료 상태까지 반영한 상태. 이제 재발행 대상이 아니다.

모든 후속 Consumer 처리 완료:
Notification/MyPage/Analytics 등 각 Consumer Group이 이벤트를 소비·반영한 상태.
Outbox가 PUBLISHED여도 이것이 완료됐다는 뜻은 아니다. (별개)
```

### 2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다

```sql
UPDATE outbox_event
SET status = 'PUBLISHED',
    published_at = CURRENT_TIMESTAMP,
    claim_token = NULL,
    lease_until = NULL,
    last_error = NULL,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### 3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다

```sql
UPDATE outbox_event
SET status = 'PENDING',
    next_attempt_at = :nextAttemptAt,
    claim_token = NULL,
    lease_until = NULL,
    last_error = :lastError,
    updated_at = CURRENT_TIMESTAMP
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken;
```

### 4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다

```
상황 A: Broker에 저장되지 못하고 Timeout → 실제로 Record 없음
상황 B: Broker에는 저장되었지만 Publisher가 ACK를 확인하지 못하고 Timeout → 실제로 Record 있음

Publisher가 받은 것은 "정해진 시간 안에 ACK가 오지 않았다"는 사실뿐이다.
저장 실패로 응답이 없는 것인지, 저장은 됐는데 ACK 응답만 유실/지연된 것인지
Publisher 입장에서는 동일하게 Timeout으로 보이므로 구분할 수 없다.

따라서 Timeout이면 PUBLISHED로 확정하지 않고 재시도한다.
상황 B였다면 재시도로 같은 이벤트가 두 번 저장될 수 있으므로 Consumer 멱등 처리가 필요하다.
```

### 5. Timeout 이후 재시도 정책을 작성한다

```
Outbox 상태:
PENDING으로 되돌린다 (PUBLISHED로 확정하지 않음). next_attempt_at을 미래로 설정.

재시도 여부:
재시도한다.

Kafka 중복 가능성:
있다. 상황 B였다면 원본 + 재발행으로 같은 eventMessageId의 Record가 둘 생길 수 있다.

Consumer에게 필요한 방어:
eventMessageId 기반 멱등 처리(processed_event). 중복 전달돼도 비즈니스 반영은 한 번만.
```

### 6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다

```
Exponential Backoff:
실패가 반복될 때 재시도 간격을 1초, 2초, 4초, 8초처럼 지수적으로 늘린다.
Kafka 장애가 지속되는 동안 즉시 반복 재시도로 DB와 Kafka에 부하를 주지 않고,
회복 여유를 준다.

Jitter:
재시도 간격에 작은 무작위 지연을 더한다.
여러 Publisher 인스턴스가 정확히 같은 시각에 몰려 재시도(thundering herd)하는 것을 막아
부하를 시간축으로 분산시킨다.
```

### 7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다

```
| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | 같은 send()의 내부 재시도를 Producer ID + Sequence Number로 식별해 중복 저장 방지 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능 | 재시작한 다른 Publisher가 새로운 send()로 재발행하므로 Sequence가 달라 별개 저장 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능 | 애플리케이션 수준의 재발행이라 Producer 내부 재시도가 아님. 새 send()로 저장됨 |
```

### 8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다

```
whenComplete는 Future를 완료시킨 스레드에서 콜백을 실행하는데,
그 스레드는 Kafka Producer의 내부 Sender(I/O) 스레드다.

이 Sender 스레드에서 markPublished 같은 DB 작업(Connection Pool 대기, 트랜잭션 Commit 대기)을
수행하면 Sender 스레드가 블로킹된다. 그러면 해당 Producer의 모든 전송이 함께 지연되고,
발행 지연 → Lease 만료 → 다른 Publisher 회수 → 중복 발행 증가 → 적체 심화라는
연쇄 장애로 이어진다.

따라서 전용 Executor를 지정해야 한다(whenCompleteAsync(callback, outboxCallbackExecutor)).
원칙: Kafka Producer 콜백 스레드에서 DB 작업이나 블로킹 I/O를 수행하지 않는다.
```

## 과제 6. Outbox 장애 시나리오 분석하기

### 1. 발급 트랜잭션 Commit 전 장애

```
| 항목 | 결과 |
| coupon_issue | 없음 (Rollback) |
| request | PENDING (PROCESSING 전이도 Rollback) |
| outbox_event | 없음 (Rollback) |
| 복구 방법 | 원본 coupon.issue.requested 메시지 재전달 → 재처리 |
```

### 2. 발급 DB Commit 후 원본 Offset Commit 전 장애

```
| 항목 | 결과 |
| coupon_issue | 존재 (Commit됨) |
| request | ISSUED |
| outbox_event | PENDING 존재 |
| 원본 Kafka 메시지 | Offset 미커밋 → 재전달 가능 |
| 복구 방법 | requestId 멱등 처리. 재전달 시 request=ISSUED 확인 후 새 발급/Outbox 없이 정상 종료. Outbox는 Publisher가 발행 |
```

### 3. Outbox Claim Commit 후 Kafka 발행 전 Publisher 종료

```
| 항목 | 결과 |
| outbox status | PROCESSING (claim_token, lease_until 존재) |
| Kafka Record | 없음 (발행 전 종료) |
| 복구 조건 | lease_until 만료 |
| 복구 주체 | 다른(또는 재시작한) Publisher가 만료 PROCESSING을 PENDING으로 회수 후 재Claim·발행 |
```

### 4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료

```
| 항목 | 결과 |
| outbox status | PROCESSING (또는 Lease 만료 후 PENDING) |
| Kafka Record | 존재 (ACK까지 받은 상태) |
| 재발행 가능성 | 있음. Lease 만료 후 다른 Publisher가 회수해 같은 eventMessageId를 재발행 |
| 필요한 Consumer 방어 | eventMessageId 기반 멱등 처리(processed_event)로 중복 비즈니스 반영 방지 |
```

### 5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황

```
Publisher A가 늦게 성공 UPDATE:
affected rows = 0. claim_token = token-A 조건이 현재 행의 token-B와 달라 갱신되지 않음.
A는 PUBLISHED로 덮어쓰지 못한다.

Publisher A가 늦게 실패 UPDATE:
affected rows = 0. 마찬가지로 claim_token 불일치로 PENDING으로 되돌리지 못한다.
B의 처리 상태를 훼손하지 않는다.

두 UPDATE에서 affected rows가 0이어야 하는 조건:
WHERE에 status = 'PROCESSING' AND claim_token = :myToken이 포함되어 있고,
현재 행의 claim_token이 이미 token-B로 바뀌었기 때문.
(A의 token-A ≠ 행의 token-B → 매칭 실패 → 0행)
```

### 6. Kafka 장애가 30분 동안 지속되는 상황

```
PENDING 수의 변화:
계속 증가한다. 발급은 되지만 발행이 실패해 PENDING으로 되돌아가고 새 발급도 쌓인다.

가장 오래된 PENDING 대기 시간:
장애 지속 시간만큼 커진다(최대 약 30분+). 이 지표가 임계치를 넘으면 적체 신호.

attempt_count:
같은 이벤트에 대해 재시도할 때마다 증가한다(Backoff로 시도 간격은 벌어짐).

Kafka 복구 후 처리:
회복되면 PENDING/만료 PROCESSING 행들을 다시 Claim해 순차 발행한다.
쌓인 물량을 처리하는 동안 발행 지연이 한동안 지속될 수 있다.

운영 알람:
가장 오래된 PENDING 대기 시간 초과, PENDING 급증, 발행 실패율 상승,
attempt_count 지속 증가에 대해 알람.
```

### 7. 다음 두 재시도 대상을 구분한다

```
발급 DB 트랜잭션 실패:
coupon.issue.requested 원본 메시지를 재처리한다. (발급 자체가 안 됐으므로)

발급 DB Commit 성공 후 CouponIssued 발행 실패:
쿠폰은 이미 발급됐으므로 재발급하지 않는다. Outbox 이벤트만 재발행한다.
```

```
결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유:
발급은 이미 DB에 확정된 사실이다. CouponIssued 발행 실패는
"발급 사실을 후속 서비스에 아직 전달하지 못한 것"일 뿐, 발급이 안 된 것이 아니다.

재발급하면 같은 사용자에게 쿠폰이 두 개 생기거나 issued_count가 중복 증가해
UNIQUE(event_id, user_id) 위반이나 수량 초과가 발생한다.
발행 실패는 발급을 되돌릴 이유가 아니라 Outbox 재발행으로 해결할 문제다.
```

## 과제 7. Consumer 멱등 처리 설계하기

### 1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다

```
같은 논리 이벤트(eventMessageId = evt-001)가 재발행되면
Partition 1 / Offset 100과 Partition 1 / Offset 101처럼 서로 다른 Offset을 가진다.

Offset을 멱등성 Key로 쓰면 이 둘을 서로 다른 이벤트로 인식해
같은 비즈니스 결과를 두 번 반영한다.
또 Topic 이동(Retry Topic)이나 재발행으로 Offset이 얼마든지 달라진다.

따라서 물리적 위치인 Offset이 아니라, 논리 이벤트를 유일하게 식별하는
eventMessageId를 멱등성 Key로 사용해야 한다.
```

### 2. processed_event 테이블 DDL을 작성한다

```sql
CREATE TABLE processed_event (
    -- 논리 Subscriber 식별자
    subscriber_id VARCHAR(100) NOT NULL,
    -- 이벤트 메시지 식별자
    event_id UUID NOT NULL,
    -- 처리 완료 시각
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- 같은 Subscriber가 같은 이벤트를 두 번 처리하지 못하도록 복합 PK
    PRIMARY KEY (subscriber_id, event_id)
);
```

### 3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다

```
선택: mypage-coupon-projection

이유:
pod-7f8c9d나 server-10.0.0.12는 실행 중인 프로세스/서버 인스턴스 ID다.
이 값은 배포, 재시작, 스케일 아웃, IP 변경 때마다 바뀐다.

인스턴스 ID를 subscriber_id로 쓰면 같은 이벤트를 인스턴스 A가 처리한 뒤
재배포된 인스턴스 B(다른 ID)가 다시 받았을 때 중복 기록으로 인식하지 못해
조회 모델을 두 번 반영한다.

mypage-coupon-projection처럼 인스턴스와 무관한 안정적인 "논리 구독자" 이름을 써야
어느 인스턴스가 처리하든 같은 구독자 기준으로 중복을 방어할 수 있다.
```

### 4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다

```sql
BEGIN;

-- 1. eventMessageId 중복 확인 (이미 처리했으면 RETURNING 없음)
INSERT INTO processed_event (
    subscriber_id, event_id
) VALUES (
    'mypage-coupon-projection', :eventMessageId
)
ON CONFLICT DO NOTHING
RETURNING event_id;
-- 반환 행이 없으면 이미 처리한 이벤트 → 조회 모델 변경 생략하고 정상 종료(Commit)

-- 2. 최초 이벤트인 경우에만 조회 모델 변경
INSERT INTO user_coupon_view (
    user_id, coupon_issue_id, coupon_event_id, issued_at
) VALUES (
    :userId, :couponIssueId, :couponEventId, :issuedAt
);

COMMIT;
```

### 5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다

```
Consumer DB 상태:
processed_event에 evt-001 기록 존재, user_coupon_view 갱신 완료 (Commit됨)

Consumer Group Offset:
Commit되지 않음 → 같은 Kafka Record가 재전달됨

재시작 후 Kafka 전달:
같은 eventMessageId의 이벤트가 다시 전달된다.

재전달된 이벤트 처리:
processed_event INSERT가 ON CONFLICT로 0행 → 이미 처리한 이벤트로 판단 →
조회 모델 변경을 생략하고 정상 처리로 종료 → Offset Commit.
중복 전달을 허용하되 processed_event로 안전하게 흡수한다.
```

### 6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다

```
processed_event는 Consumer의 로컬 DB 트랜잭션에만 참여한다.
외부 SMS API 호출은 그 로컬 DB 트랜잭션에 포함되지 않는 또 다른 시스템이다.

예: SMS를 먼저 보내고 processed_event를 Commit하기 전에 프로세스가 죽으면
재전달 시 processed_event에 기록이 없어 SMS를 또 보낸다(중복 전송).
반대로 processed_event를 먼저 Commit하고 SMS 전 종료되면 SMS가 누락된다.

즉 DB 저장과 외부 API 호출 사이에 또 다른 Dual Write가 생기므로,
processed_event만으로는 외부 전송의 정확히 한 번을 보장할 수 없다.
```

### 7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다

```
1. Notification Service 내부 Outbox: 알림 발송 의도를 로컬 DB에 저장하고
   별도 Sender가 발송한다. DB 저장과 발송 의도를 원자적으로 묶는다.

2. 외부 Provider의 Idempotency Key 사용: SMS/이메일 Provider에 멱등 키를 함께 보내
   같은 키의 재요청을 Provider가 한 번만 처리하게 한다.

3. notificationId 기반 중복 전송 방어: 발송 단위마다 고유 ID를 부여해
   이미 전송한 notificationId는 다시 보내지 않도록 기록·확인한다.
```

### 8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다

```
Kafka Topic 보관 기간: Topic에 Record가 남아 있는 동안 재소비될 수 있음
Consumer Offset 되감기: 운영자가 Offset을 과거로 되감아 재처리할 수 있음
Outbox 지연 재발행: Publisher가 뒤늦게 같은 이벤트를 재발행할 수 있음
운영자 수동 재발행: 장애 복구 시 같은 이벤트를 수동으로 다시 발행할 수 있음

결론:
processed_event 보관 기간 > (Kafka Topic 보관 기간 + 최대 재전달 지연)
이어야 한다. 너무 짧게 잡으면 아직 재등장 가능한 이벤트를 방어하지 못해
조회 모델을 중복 반영한다.
```

## 과제 8. Partition Key와 이벤트 순서 문제 분석하기

### 1. 같은 Partition Key를 사용하는 이유를 작성한다

```
partitionKey = couponIssueId를 쓰면 같은 CouponIssue(같은 Aggregate)의 이벤트가
같은 Partition으로 모인다.

이유:
1. 같은 Aggregate의 이벤트를 한 Partition에 모아 Consumer 병렬 처리 단위를 명확히 한다.
2. couponIssueId로 분산되므로 특정 Partition으로 부하가 쏠리지 않는다.
3. 향후 순서 보장을 도입할 때의 기준 단위(Aggregate 단위)를 미리 정해둔다.
```

### 2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다

```
같은 Partition 안의 순서는 Producer가 send()를 호출한 순서로 정해지며,
Outbox의 DB 저장 순서가 아니다. Polling Publisher에서는 발행 순서가 저장 순서와 어긋난다.

여러 Publisher 인스턴스:
서로 다른 인스턴스가 서로 다른 속도로 발행해 저장 순서와 다르게 send()될 수 있다.

SKIP LOCKED:
잠긴 행을 건너뛰고 다음 행을 가져가므로 애초에 순서를 포기하는 장치다.

발행 실패와 Backoff:
먼저 저장된 이벤트가 발행에 실패하면 next_attempt_at 뒤로 밀려
나중에 저장된 이벤트보다 늦게 발행된다.

Producer 설정과 재시도:
Producer 내부 재시도/배치 처리에 따라 전송 순서가 달라질 수 있다.
(max.in.flight 설정에 따라서도 영향을 받는다)

결론: 이번 주차 발행 보장은 At-Least-Once, 순서 보장 없음이다.
```

### 3. 다음 순서 역전 시나리오를 완성한다

```
DB 발생 순서

CouponIssued
aggregateVersion = 1  (outbox 1, couponIssueId = 5001)

CouponCancelled
aggregateVersion = 2  (outbox 2, couponIssueId = 5001)

Publisher 처리

Publisher A: outbox 1(CouponIssued) Claim → Kafka 발행 실패
             → PENDING, next_attempt_at = +4초

Publisher B: outbox 2(CouponCancelled) Claim → 발행 성공

Kafka 저장 순서:
Offset 200 : CouponCancelled (version 2)
Offset 201 : CouponIssued    (version 1)

→ DB 발생 순서(발급 → 취소)와 Kafka 저장 순서(취소 → 발급)가 역전됨
```

### 4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다

```
1. 서로 다른 이벤트가 같은 시각(occurredAt)을 가질 수 있다. 시간 정밀도 한계로
   동시에 가까운 두 이벤트가 같은 Timestamp가 되면 순서를 구분할 수 없다.

2. 여러 컴포넌트(서버, DB)의 시계가 완전히 일치하지 않는다. 시계 오차(clock skew)로
   실제로 나중에 발생한 이벤트가 더 이른 occurredAt을 가질 수 있다.

3. UPDATE 0행이 "더 오래된 이벤트라 무시"인지 "대상 행이 없어서"인지
   occurredAt 비교만으로는 구분하기 어렵다. 명시적 버전 컬럼이 필요하다.
```

### 5. MyPage처럼 최신 상태만 필요한 Projection의 순서 역전 방어 SQL을 작성한다

```sql
INSERT INTO user_coupon_view (
    coupon_issue_id, user_id, coupon_event_id,
    status, last_aggregate_version, last_event_at
) VALUES (
    :couponIssueId, :userId, :couponEventId,
    :newStatus, :aggregateVersion, :occurredAt
)
ON CONFLICT (coupon_issue_id)
DO UPDATE
SET status = EXCLUDED.status,
    last_aggregate_version = EXCLUDED.last_aggregate_version,
    last_event_at = EXCLUDED.last_event_at
WHERE user_coupon_view.last_aggregate_version
      < EXCLUDED.last_aggregate_version;
```

### 6. aggregateVersion이 더 큰 이벤트가 먼저 도착한 경우의 결과를 작성한다

```
먼저 도착: CouponCancelled(version=2)
→ user_coupon_view가 없으면 취소 상태로 INSERT(last_aggregate_version = 2)

나중 도착: CouponIssued(version=1)
→ ON CONFLICT DO UPDATE의 WHERE(last_aggregate_version < 1)이 거짓(2 < 1 아님)
→ affected rows = 0, 상태를 되돌리지 않음

최종 MyPage 상태:
취소됨(Cancelled), last_aggregate_version = 2 유지

version=1 처리 결과:
상태 변경 생략(무시). 이미 더 높은 버전이 반영되어 있으므로 발급으로 되돌리지 않는다.
```

### 7. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버려도 되는지 판단한다

```
| Consumer | 낮은 Version 이벤트 생략 가능 여부 | 이유 또는 추가로 필요한 설계 |
| --- | --- | --- |
| 최신 상태만 저장하는 MyPage Projection | 가능 | 최종 상태만 필요하므로 더 낮은 버전은 무시해도 됨. last_aggregate_version 비교로 방어 |
| 모든 발급·취소 건수를 집계하는 Analytics | 불가능 | 각 상태 전이 건수를 모두 세야 함. 버려서는 안 되고 eventMessageId 멱등 처리로 각 이벤트를 한 번씩 반영 |
| 발급과 취소 알림을 각각 보내는 Notification | 불가능 | 발급 알림과 취소 알림을 둘 다 보내야 함. 낮은 버전(발급)을 버리면 발급 알림 누락. 각 이벤트를 개별 처리 |
```

### 8. `aggregateVersion`의 역할을 정확히 정의한다

```
aggregateVersion은 이벤트 순서 역전을
자동으로 [교정(방지)해 주는] 값이 아니다.

aggregateVersion은 같은 Aggregate에서 발생한 상태 변경의
[순서(몇 번째 상태 변경인지)] 을 식별하기 위한 값이다.

최신 상태 Projection에서는 낮은 버전이
최신 상태를 [덮어쓰는(되돌리는)] 것을 방지할 수 있다.

모든 상태 전이를 순서대로 처리해야 하는 Consumer는
추가로 [순서 보장(예: Aggregate 단위 직렬화 또는 버퍼링/재정렬, CDC 등)] 이 필요하다.
```

## 과제 9. Outbox 운영 지표와 보관 정책 설계하기

### 1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다

```
| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않은 이벤트 수 | 지속적으로 증가하면 발행 병목/Kafka 장애 신호 |
| 가장 오래된 PENDING 대기 시간 | 가장 늦게 발행되는 이벤트의 지연 | 임계치(예: 수십 초~분) 초과 시 적체 |
| PROCESSING 이벤트 수 | 현재 발행 권한을 잡고 처리 중인 수 | 발행량 대비 비정상적으로 크면 처리 지연 |
| 만료된 PROCESSING 수 | Lease 만료 후 회수 대기 중인 수 | 반복 발생하면 Publisher 종료/Lease 과소 설정 신호 |
| attempt_count | 특정 이벤트의 발행 시도 횟수 | 특정 이벤트에서 계속 증가하면 영구 실패 후보 |
| Outbox 생성 처리량 | 시간당 생성되는 이벤트 수 | 발행 처리량보다 지속적으로 크면 적체 |
| Kafka 발행 처리량 | 시간당 발행 성공 수 | 생성량보다 계속 낮으면 적체 심화 |
| DB 발생부터 Kafka ACK까지의 시간 | 종단 발행 지연 | 지속 상승 시 후속 서비스 반영 지연 |
```

### 2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다

```
1분 후 예상 적체 증가량:
(2000 - 1500) × 60 = 30,000건 증가

10분 후 예상 적체 증가량:
500 × 600 = 300,000건 증가

가장 먼저 확인할 지표:
가장 오래된 PENDING 대기 시간(과 PENDING 이벤트 수 증가 추세).

가능한 대응:
- Publisher 인스턴스 수 확대(수평 확장)
- batchSize 조정 / 동기 → 비동기 발행으로 처리량 향상
- Producer 설정(배치, linger) 튜닝
- 근본적으로 발행 처리량이 생성 처리량 이상이 되도록 확장
```

### 3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다

```
1. deduplication_key UNIQUE 위반 발생 (정상 경로에서는 없어야 하는 이상 신호)
2. Commit된 request = PROCESSING 관측 (단일 트랜잭션 설계에서는 발생 불가)
3. 같은 Aggregate의 서로 다른 이벤트가 동일 aggregateVersion을 가짐 (버전 충돌)
4. SOLD_OUT 또는 DUPLICATE_USER 확정이 반복 발생 (Redis-DB divergence 신호)
5. 만료된 PROCESSING 행이 반복적으로 대량 발생 (Publisher 종료/Lease 오설정)
```

### 4. PUBLISHED 행만 정리해야 하는 이유를 설명한다

```
PENDING을 삭제하면:
아직 발행되지 않은 이벤트가 사라진다 → 이벤트 유실. 후속 서비스가 영원히 못 받음.

PROCESSING을 삭제하면:
발행 중이거나 발행 성공 후 완료 표시 전인 이벤트가 사라진다 →
복구·재발행 기준이 사라지고, 발행 여부를 확인할 수 없게 된다.

PUBLISHED를 보관하는 목적:
발행 이력 확인과 장애 조사(언제 무엇을 발행했는지)를 위해 일정 기간 남긴다.
발행이 확정된 행이므로 유실 위험 없이 정리 대상이 된다.
```

### 5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다

```
긴 트랜잭션:
대량 DELETE는 하나의 긴 트랜잭션이 되어 오래 실행되고, 실패 시 전체가 롤백된다.

DB 부하:
한 번에 많은 행을 지우면 I/O와 CPU 부하가 급증해 다른 쿼리 응답이 느려진다.

Lock:
삭제 대상 행과 인덱스에 Lock이 오래 유지되어 다른 트랜잭션이 대기한다.

Table Bloat:
PostgreSQL은 삭제 시 즉시 공간을 회수하지 않고 dead tuple을 남긴다.
대량 삭제는 bloat를 키우고 VACUUM 부담을 늘린다.
```

### 6. 작은 Batch로 정리하는 운영 흐름을 작성한다

```
1. cutoff 시각 계산 (published_at < cutoff 이고 status = 'PUBLISHED'인 행 대상)
2. 한 번에 1,000건씩 DELETE
3. Commit
4. 잠시 대기 (다른 트랜잭션에 자원 양보, autovacuum 여유)
5. 대상 행이 없을 때까지 2~4 반복

주의: PENDING/PROCESSING은 절대 삭제하지 않고, PUBLISHED만 대상으로 한다.
```

### 7. 다음 세 보관 기간의 목적을 비교한다

```
| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |
| Outbox PUBLISHED 행 | 발행 이력 확인과 장애 조사 | 조사 근거가 사라져 장애 원인 추적이 어려움 |
| Kafka Topic Record | Consumer 재처리 가능 범위 제공 | Consumer가 지연/장애 복구 시 재소비할 메시지가 이미 삭제되어 유실 |
| Consumer processed_event | 중복 방어 가능 범위 제공 | Kafka 재전달/재발행 시 이미 처리한 이벤트를 방어 못해 조회 모델 중복 반영 |
```

### 8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다

```
- Stack Trace를 통째로 저장하면 last_error 컬럼과 테이블 크기가 급격히 커져
  DB 부하와 인덱스 비대화를 유발한다.
- 자유 텍스트라 검색·집계가 어렵다. 짧은 오류 분류 코드가 있어야 장애 유형별 통계가 가능하다.
- Payload나 예외 메시지에 사용자 개인정보·토큰 같은 민감 정보가 섞여
  DB에 그대로 남으면 유출·컴플라이언스 위험이 된다.

권장: DB에는 검색 가능한 짧은 오류 분류와 메시지만 저장하고,
상세 Stack Trace와 진단 정보는 Log/Trace 시스템에 남긴다.
```

| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 PostgreSQL 트랜잭션에 저장되어 함께 Commit/Rollback |

| Publisher 복구 후 재발행 | 조건부 보장 | Publisher 동작, Kafka 회복, 재시도, Outbox 미삭제 등 조건이 충족될 때만 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED, Backoff, 다중 Publisher로 발행 순서가 저장 순서와 달라짐 |
| Consumer의 중복 비즈니스 반영 방지 | 보장 | eventMessageId 기반 processed_event로 한 번만 반영 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | 각 Consumer Group은 독립적. Outbox PUBLISHED ≠ 전체 소비 완료 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API는 로컬 트랜잭션 밖의 또 다른 Dual Write. 별도 멱등/Outbox 필요 |
