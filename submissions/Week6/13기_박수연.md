# 6주차 과제: Transactional Outbox Pattern과 이벤트 발행 정합성

---

## 과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기

### 1. 위 코드가 사용하는 저장소 두 개를 작성한다

```
1. PostgreSQL: coupon_issue 저장, coupon_issue_request ISSUED 변경 등 비즈니스 데이터 저장
2. Kafka: CouponIssued 이벤트 발행 (kafkaTemplate.send 호출)
```

### 2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다

```
@Transactional은 Spring이 관리하는 JDBC 트랜잭션 범위를 나타낸다.
PostgreSQL 트랜잭션은 JDBC 연결을 통해 관리되지만, Kafka 발행은 완전히 별개의 시스템이다.
Kafka는 트랜잭션 참여자로 등록되지 않으므로 Spring의 @Transactional이 Commit·Rollback할 때
Kafka 발행이 함께 롤백되거나 원자적으로 처리되지 않는다.
결과적으로 DB는 성공하고 Kafka는 실패하거나, 반대로 Kafka는 성공했지만 DB는 Rollback되는 상황이 발생한다.
```

### 3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다

```
DB Commit
    ↓
[장애 지점: 프로세스 종료 / 네트워크 단절 / Kafka Broker 장애]
    ↓
Kafka 발행

최종 DB 상태:
쿠폰 발급 기록(coupon_issue), request ISSUED 상태가 영속적으로 저장됨.
DB 기준으로는 발급이 완료된 상태.

최종 Kafka 상태:
CouponIssued 이벤트가 발행되지 않음.
Kafka Topic에 Record가 없음.

후속 서비스에 미치는 영향:
Notification, MyPage, Analytics 등 후속 Consumer가 이벤트를 받지 못한다.
사용자는 쿠폰 발급 알림을 받지 못하고 마이페이지에도 반영되지 않는다.
DB에는 발급 기록이 있지만 후속 서비스는 이 사실을 모른다.

복구에 필요한 정보:
발행되지 않은 이벤트를 식별할 수단이 없다. DB에 "발행 의도"가 저장되어 있지 않으므로
어떤 이벤트를 다시 발행해야 하는지 알 수 없다. 수동 조회 및 재발행이 필요하다.
```

### 4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다

```
Kafka 발행
    ↓
[장애 지점: 프로세스 종료 / DB 연결 실패 / 트랜잭션 Rollback]
    ↓
DB Commit

최종 DB 상태:
coupon_issue 저장, request ISSUED 변경이 이루어지지 않음.
DB 기준으로는 쿠폰이 발급되지 않은 상태.

최종 Kafka 상태:
CouponIssued 이벤트가 이미 Topic에 저장됨.
Record는 존재하지만 실제 발급 기록이 없음.

후속 서비스에 미치는 영향:
Notification, MyPage, Analytics가 이벤트를 받아 처리하지만 실제 발급은 이루어지지 않은 상태다.
마이페이지에 쿠폰이 표시되지만 DB에는 기록이 없는 유령 쿠폰이 된다.
데이터 불일치가 발생하고 쿠폰이 실제로 유효하지 않을 수 있다.
```

### 5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다

```
AFTER_COMMIT Listener는 DB 트랜잭션이 Commit된 직후 호출되는 콜백이다.
하지만 다음 두 상황에서 이벤트 유실이 발생한다.

장애 1. DB Commit 후 Listener 실행 전 프로세스 종료:
DB는 Commit됐지만 JVM이 종료되거나 OOM이 발생하면 AFTER_COMMIT 콜백 자체가 실행되지 않는다.
이 경우 Kafka 발행이 아예 시도되지 않아 이벤트가 유실된다.
재시작 후에는 어떤 이벤트를 발행해야 하는지 알 수 없다.

장애 2. KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료:
send() 호출은 Producer 내부 버퍼에 넣는 것이며 ACK를 즉시 받는 것이 아니다.
ACK를 확인하기 전에 프로세스가 종료되면 Broker가 메시지를 저장했는지 알 수 없다.
두 경우 모두 "발행 의도"를 DB에 저장하지 않았으므로 재시작 후 복구할 근거가 없다.
Outbox는 발행 의도를 DB에 먼저 저장해 재시작 후 재발행이 가능하게 한다.
```

### 6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔ CouponIssued 발행 의도 저장 | 해결된다 | 같은 DB 트랜잭션으로 묶어 둘 다 Commit되거나 둘 다 Rollback된다 |
| Redis SUCCESS ↔ 최초 요청 Kafka 발행 | 해결되지 않는다 | Redis와 DB는 별개 시스템이므로 이번 Outbox 범위 밖이다 |
| 원본 Kafka 소비 ↔ 발급 DB Commit | 해결되지 않는다 | 원본 Consumer의 at-least-once 처리와 requestId 멱등성으로 별도 관리 |
| Consumer DB 저장 ↔ 외부 SMS API 호출 | 해결되지 않는다 | Result Consumer 내부의 외부 API 호출은 이번 Outbox 범위 밖이다. 별도 Outbox나 Saga 패턴 필요 |

### 7. 다음 문장을 완성한다

```
Transactional Outbox가 직접 보장하는 것:
DB 발급 결과가 Commit됐을 때 CouponIssued 발행 의도(Outbox 행)도 반드시 같은 DB에 저장된다는 것.
Publisher가 Outbox를 읽어 Kafka에 발행하므로 DB Commit된 이벤트는 재시도를 통해 결국 발행된다.
즉, DB 결과와 Kafka 발행 의도의 원자성을 보장한다.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record의 물리적 Exactly-Once 생성. Publisher 재시도로 중복 발행이 발생할 수 있다.
비즈니스 발생 순서대로의 Kafka 전달. 순서 역전이 생길 수 있다.
Result Consumer의 중복 비즈니스 반영 방지. Consumer가 별도로 멱등 처리해야 한다.
```

## 과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기

### 1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다

```
IssueCoupon: 쿠폰을 발급하라는 명령(Command)이다. 미래에 수행할 행위를 나타낸다.
이 명령은 실패할 수 있고, 처리 여부가 아직 결정되지 않은 상태다.

CouponIssued: 쿠폰 발급이 이미 완료됐다는 사실(Fact/Event)이다.
이 이벤트는 DB 트랜잭션이 Commit된 이후에 생성되므로 되돌릴 수 없는 확정된 사실이다.

이벤트를 과거형으로 표현해야 하는 이유:
후속 서비스(Notification, MyPage, Analytics)는 이 이벤트를 받고 자신의 반응만 결정하면 된다.
"발급됐으니 알림을 보내라", "발급됐으니 조회 모델을 갱신하라"처럼 이미 발생한 사실에 반응한다.
명령형 이벤트는 수신 서비스가 처리 여부를 결정해야 하지만, 사실형 이벤트는 단순히 반응하면 된다.
```

### 2. CouponIssued 이벤트 JSON을 완성한다

```json
{
  "eventMessageId": "7a1c3e92-f4d2-4b8e-9a0f-2d3c1e5f7b99",
  "eventType": "COUPON_ISSUED",
  "schemaVersion": 1,
  "aggregateVersion": 1,
  "occurredAt": "2026-07-26T03:00:01Z",
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "data": {
    "couponIssueId": 5001,
    "couponEventId": 100,
    "userId": 10,
    "issuedAt": "2026-07-26T03:00:01Z"
  }
}
```

### 3. 다음 ID의 역할을 비교한다

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 이벤트(선착순 행사) | 아니다 | 아니다. 하나의 이벤트에서 1,000개 쿠폰이 발급되면 couponEventId가 동일하다 |
| couponIssueId | 개별 쿠폰 발급 건 | 아니다 | 부분적으로. 같은 couponIssueId에 대해 재발행이 발생할 수 있으므로 단독 사용 불충분 |
| eventMessageId | 이 Outbox 메시지 자체(논리 이벤트 식별) | 아니다. 재발행해도 동일한 eventMessageId 유지 | 그렇다. 같은 논리 이벤트의 중복 처리를 식별하는 기준 |
| Kafka Partition + Offset | Kafka Record의 물리적 위치 | 그렇다. 재발행하면 Offset이 달라진다 | 아니다. 재발행 시 Offset이 달라지므로 같은 논리 이벤트를 다른 이벤트로 인식하게 된다 |

### 4. `occurredAt`과 `publishedAt`의 차이를 설명한다

```
occurredAt:
비즈니스 이벤트가 실제로 발생한 시각이다. 쿠폰 발급 트랜잭션이 Commit된 시점을 기록한다.
이 값은 Outbox가 처음 생성될 때 결정되며, 재발행해도 변경되지 않는다.

publishedAt:
Outbox Publisher가 Kafka에 발행을 완료하고 ACK를 받은 시각이다.
처음 발행 시, 또는 재발행 시마다 갱신될 수 있다.

Publisher 재시도 시 변경하면 안 되는 값:
occurredAt, eventMessageId, requestId, 이벤트 payload 내 issuedAt.
이 값들은 비즈니스 사실이 발생한 시점의 정보이므로 재발행해도 동일해야 한다.
```

### 5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다

```
비즈니스 테이블의 데이터는 시간이 지나면서 변경될 수 있다.
예를 들어 쿠폰이 취소된 후 Outbox가 재발행되면, 현재 테이블을 조회할 때 이미 취소 상태의 데이터를 가져오게 된다.
이렇게 되면 "쿠폰이 발급됐다"는 CouponIssued 이벤트에 취소 이후의 상태가 담겨 잘못된 정보가 전달된다.
또한 조회 시점과 이벤트 발생 시점 사이에 다른 트랜잭션이 데이터를 변경하면 이벤트의 정확성이 보장되지 않는다.
Outbox에는 이벤트 발생 시점의 Payload를 스냅샷으로 저장해야 재발행해도 동일한 사실이 전달된다.
```

### 6. 다음 Outbox 테이블 DDL을 완성한다

```sql
CREATE TABLE outbox_event (
    event_id            UUID          NOT NULL,
    deduplication_key   VARCHAR(255)  NOT NULL,
    aggregate_type      VARCHAR(100)  NOT NULL,
    aggregate_id        VARCHAR(100)  NOT NULL,
    aggregate_version   BIGINT        NOT NULL DEFAULT 1,
    event_type          VARCHAR(100)  NOT NULL,
    topic               VARCHAR(255)  NOT NULL,
    partition_key       VARCHAR(255)  NOT NULL,
    payload             JSONB         NOT NULL,
    status              VARCHAR(20)   NOT NULL DEFAULT 'PENDING',
    attempt_count       INT           NOT NULL DEFAULT 0,
    next_attempt_at     TIMESTAMP     NOT NULL DEFAULT NOW(),
    claim_token         UUID          NULL,
    lease_until         TIMESTAMP     NULL,
    last_error          TEXT          NULL,
    occurred_at         TIMESTAMP     NOT NULL,
    published_at        TIMESTAMP     NULL,
    created_at          TIMESTAMP     NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_outbox_event
        PRIMARY KEY (event_id),

    CONSTRAINT uq_outbox_deduplication_key
        UNIQUE (deduplication_key),

    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED'))
);

CREATE INDEX idx_outbox_status_next_attempt
    ON outbox_event (status, next_attempt_at)
    WHERE status IN ('PENDING', 'PROCESSING');
```

### 7. 다음 불변조건을 애플리케이션 또는 DB에서 어떻게 검증할지 작성한다

```
outbox_event.event_id = payload.eventMessageId

애플리케이션 레벨에서 검증:
Outbox 행을 INSERT하기 전에 미리 UUID를 생성하고,
event_id와 payload.eventMessageId에 동일한 값을 넣어 저장한다.
별도 검증 메서드를 통해 event_id == JSON.parse(payload).eventMessageId를 확인한 후 INSERT한다.

DB 레벨에서 검증 (PostgreSQL 예시):
CHECK 제약으로 JSON 값과 컬럼 값이 일치하는지 확인할 수 있다.
예: CHECK ((payload->>'eventMessageId')::UUID = event_id)
또는 Generated Column으로 payload에서 eventMessageId를 추출해 event_id와 비교하는 컬럼을 추가한다.
```

### 8. `deduplication_key`를 설계한다

```
Key 형식: {aggregate_type}:{aggregate_id}:{event_type}

예시: COUPON_ISSUE:5001:COUPON_ISSUED
(couponIssueId=5001에 대한 CouponIssued 이벤트)
```

같은 Aggregate에서 같은 이벤트 유형이 여러 번 발생할 수 있다면 어떤 값을 추가해야 하는지도 작성한다.

```
aggregateVersion을 추가한다.
Key 형식: {aggregate_type}:{aggregate_id}:{event_type}:{aggregate_version}
예시: COUPON_ISSUE:5001:COUPON_ISSUED:1

이렇게 하면 같은 쿠폰 발급 건에서 발급(version=1), 취소(version=2) 등 같은 유형의 이벤트가
여러 번 발생해도 각각 고유한 deduplication_key를 가진다.
```

### 9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다

```
전체 Rollback 후 새 트랜잭션에서 조회:
PostgreSQL에서 UNIQUE 위반이 발생하면 트랜잭션이 aborted 상태가 된다.
이후 어떤 SQL도 실행할 수 없으므로 ROLLBACK 후 새 트랜잭션에서 기존 행을 SELECT해야 한다.
안전하지만 두 번의 트랜잭션이 필요하다.

Savepoint 사용:
INSERT 전에 SAVEPOINT를 생성하고, UNIQUE 위반 시 SAVEPOINT로 복구한 뒤 같은 트랜잭션에서 기존 행을 조회한다.
트랜잭션 전체를 Rollback하지 않아도 되므로 이미 수행한 다른 작업을 유지할 수 있다.

ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교:
INSERT ... ON CONFLICT (deduplication_key) DO NOTHING RETURNING event_id
RETURNING 절은 실제로 INSERT된 행만 반환하므로, 충돌 시 RETURNING이 빈 결과를 반환한다.
빈 결과면 기존 행을 SELECT해 동일한 이벤트인지 확인한다.
같은 트랜잭션 안에서 처리할 수 있어 가장 깔끔하다.
```

## 과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기

### 1. 전체 SQL 트랜잭션을 완성한다

```sql
BEGIN;

-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET    status                = 'PROCESSING',
       processing_started_at = NOW(),
       updated_at            = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PENDING';

-- affected rows가 몇 행이어야 하는가?
-- 1행. 0행이면 이미 다른 Consumer가 처리 중이거나 최종 상태이므로 ROLLBACK 후 상태 확인.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET    issued_count = issued_count + 1
WHERE  id           = :eventId
  AND  issued_count < total_quantity;

-- affected rows가 0일 때 가능한 원인은 무엇인가?
-- 수량 소진(issued_count >= total_quantity) 또는 해당 eventId가 존재하지 않음.
-- 이 경우 request를 FAILED/SOLD_OUT으로 변경 후 COMMIT.

-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:eventId, :userId, 'ISSUED', NOW())
RETURNING id, issued_at;

-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET    status          = 'ISSUED',
       coupon_issue_id = :couponIssueId,
       completed_at    = NOW(),
       updated_at      = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PROCESSING';

-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장
INSERT INTO outbox_event (
    event_id,
    deduplication_key,
    aggregate_type,
    aggregate_id,
    aggregate_version,
    event_type,
    topic,
    partition_key,
    payload,
    status,
    next_attempt_at,
    occurred_at,
    created_at,
    updated_at
)
VALUES (
    :eventMessageId,
    CONCAT('COUPON_ISSUE:', :couponIssueId, ':COUPON_ISSUED'),
    'COUPON_ISSUE',
    :couponIssueId::VARCHAR,
    1,
    'COUPON_ISSUED',
    'coupon.issued',
    :couponIssueId::VARCHAR,
    :payloadJson,
    'PENDING',
    NOW(),
    :issuedAt,
    NOW(),
    NOW()
);

COMMIT;
```

### 2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1 | ROLLBACK. 현재 상태 조회 후 ISSUED/FAILED면 멱등 성공, 그 외 재시도 또는 DLQ |
| issued_count 조건부 증가 | 1 | SOLD_OUT 처리. request FAILED/SOLD_OUT 변경 후 COMMIT |
| coupon_issue INSERT | 1 | UNIQUE 위반이면 ROLLBACK. 별도 트랜잭션에서 FAILED/DUPLICATE_USER 변경 |
| PROCESSING → ISSUED | 1 | 0이면 ROLLBACK. 발급 결과만 남으면 정합성이 깨지므로 전체 취소 |
| outbox_event INSERT | 1 | 0이면(UNIQUE 위반 등) ROLLBACK. Outbox 없이 발급 결과만 Commit하면 후속 서비스에 이벤트가 전달되지 않음 |

### 3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다

```
트랜잭션 결과: ROLLBACK. 트랜잭션에 포함된 모든 변경이 취소된다.

coupon_event.issued_count: 증가 전 값으로 복구됨.

coupon_issue: INSERT되지 않음. 발급 기록 없음.

coupon_issue_request: PROCESSING 변경이 취소되어 PENDING으로 복구됨.

outbox_event: INSERT되지 않음.
```

### 4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다

```
Outbox가 없으면 CouponIssued 이벤트를 Kafka에 발행할 근거가 사라진다.
Publisher는 outbox_event 테이블을 Polling해 발행하므로 Outbox 행이 없으면 이벤트가 영원히 발행되지 않는다.
Notification, MyPage, Analytics 등 후속 서비스는 쿠폰이 발급됐음을 알 수 없게 된다.
Outbox는 "발행 의도"의 영속적 기록이므로 비즈니스 결과와 반드시 함께 Commit되어야 한다.
```

### 5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다

```
issued_count를 다시 증가시키는가?
아니다. Consumer가 PENDING → PROCESSING 조건부 UPDATE를 시도하면 status='ISSUED'이므로 0행이 된다.
상태 조회 결과 ISSUED이므로 이미 처리된 요청으로 판단한다.

coupon_issue를 다시 생성하는가?
아니다. 처리 권한 획득에 실패했으므로 coupon_issue INSERT까지 도달하지 않는다.

Outbox를 다시 INSERT하는가?
아니다. 이미 ISSUED 처리됐으므로 Outbox도 이미 존재한다. 중복 INSERT를 시도하면 deduplication_key UNIQUE 위반이 발생한다.

Consumer 처리는 성공으로 종료할 수 있는가?
그렇다. 멱등 처리로 ISSUED 상태를 확인하고 추가 처리 없이 Offset을 커밋해 정상 종료한다.
```

### 6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다

```
DB 상태:
coupon_issue, request ISSUED, outbox_event PENDING이 모두 Commit됨. 발급 완료 상태.

Outbox 상태:
PENDING 상태로 저장됨. Publisher가 아직 처리하지 않았음.

Kafka 원본 메시지:
Offset이 Commit되지 않았으므로 Consumer 재시작 후 같은 메시지를 다시 읽는다.

재시작 후 필요한 멱등성 기준:
Consumer가 같은 requestId의 메시지를 처리할 때 request 상태가 ISSUED임을 확인한다.
이미 처리된 메시지로 판단해 추가 발급 없이 Offset을 커밋한다.
Outbox는 이미 PENDING으로 저장되어 있으므로 Publisher가 별도로 처리한다.
```

### 7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다

```
enable.auto.commit:
반드시 false로 설정한다. DB Commit 이후에 수동으로 Offset을 커밋해야 한다.
자동 커밋이 활성화되면 DB 처리 완료 전에 Offset이 커밋되어 처리 실패 시 메시지가 유실된다.

AckMode:
MANUAL 또는 MANUAL_IMMEDIATE를 사용한다. DB Commit이 확인된 후에 명시적으로 acknowledgment.acknowledge()를 호출한다.

Listener 예외 처리:
일시적 DB 오류(Deadlock, 연결 실패)는 예외를 던져 Listener가 재처리할 수 있도록 한다.
비즈니스 최종 실패(SOLD_OUT, DUPLICATE_USER)는 예외 없이 정상 종료하고 Offset을 커밋한다.
메시지 내용 불일치는 DLQ로 이동시키고 Offset을 커밋한다.

Error Handler가 실패를 정상 처리로 바꾸는지 여부:
DefaultErrorHandler가 재시도 소진 후 DLQ로 보내는 과정에서 Offset을 커밋하는지 확인한다.
일시적 오류를 정상 처리로 바꿔 Offset을 커밋하면 메시지가 유실된다.
Error Handler 설정이 실패 유형에 따라 올바르게 분기하는지 검토해야 한다.
```

## 과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기

### 1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다

```
Publisher A                           Publisher B
------------------------------------------------
SELECT PENDING rows → [evt-001, evt-002]
                                      SELECT PENDING rows → [evt-001, evt-002]
UPDATE evt-001 PROCESSING
UPDATE evt-002 PROCESSING
                                      UPDATE evt-001 PROCESSING (중복 Claim!)
                                      UPDATE evt-002 PROCESSING (중복 Claim!)
Kafka 발행 evt-001
Kafka 발행 evt-002
                                      Kafka 발행 evt-001 (중복 발행!)
                                      Kafka 발행 evt-002 (중복 발행!)
```

### 2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다

```sql
BEGIN;

WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= NOW()
    ORDER BY occurred_at ASC
    LIMIT 100
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET
    status        = 'PROCESSING',
    claim_token   = gen_random_uuid(),
    lease_until   = NOW() + INTERVAL '60 seconds',
    attempt_count = attempt_count + 1,
    updated_at    = NOW()
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;

COMMIT;
```

### 3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다

```
1. DB Row Lock 보유 시간 최소화:
   FOR UPDATE로 잠긴 row는 다른 Publisher가 접근하지 못한다.
   Kafka ACK를 기다리는 동안(수십 ms ~ 수 초) 락을 보유하면 다른 Publisher가 해당 row를 처리할 수 없어 처리량이 급감한다.

2. DB 연결 점유:
   Kafka 발행을 기다리는 동안 DB 연결이 계속 점유된다. 커넥션 풀이 고갈되면 다른 DB 작업도 지연된다.

3. Deadlock 위험 증가:
   Lock 보유 시간이 길수록 다른 트랜잭션과 교착 상태가 발생할 확률이 높아진다.
   Kafka Broker 응답 지연이 DB Deadlock으로 이어질 수 있다.
```

### 4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다

```
Publisher가 Claim 후 PROCESSING으로 변경했지만 Kafka 발행 도중 프로세스가 종료되면
outbox_event가 PROCESSING 상태로 영구히 남는다.
단일 Publisher라도 재시작 후에는 PROCESSING 행을 다시 Claim하지 못한다.
(이미 PROCESSING이므로 PENDING 조건에 걸리지 않음)
Lease가 없다면 이 행은 영원히 발행되지 않는다.
Lease 만료 후 PENDING으로 복구하는 로직이 있어야 재시작 후 재발행이 가능하다.
```

### 5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다

```sql
UPDATE outbox_event
SET    status        = 'PENDING',
       claim_token   = NULL,
       lease_until   = NULL,
       next_attempt_at = NOW() + (INTERVAL '1 second' * POWER(2, LEAST(attempt_count, 10))),
       updated_at    = NOW()
WHERE  status      = 'PROCESSING'
  AND  lease_until < NOW();
```

### 6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다

```
Publisher A가 token-A로 Claim → 처리 지연 → Lease 만료
Publisher B가 만료된 행을 token-B로 Claim → Kafka 발행 성공 → PUBLISHED로 변경

Publisher A가 뒤늦게 성공 UPDATE를 시도:
Claim Token이 없으면 WHERE event_id = :eventId 조건만으로 UPDATE한다.
이미 PUBLISHED된 행이 다시 상태가 변경될 수 있다.
또는 이미 B가 처리 중인 행을 A가 다시 PROCESSING으로 덮어쓸 수 있다.
결과적으로 Outbox 상태가 올바르지 않게 변경되어 재발행이 발생한다.

Claim Token이 있으면:
WHERE claim_token = :tokenA 조건을 함께 사용한다.
token-B로 Claim된 행에 token-A UPDATE를 시도하면 조건이 맞지 않아 0행이 된다.
Publisher A는 자신이 이미 소유권을 잃었음을 알고 UPDATE를 포기한다.
```

### 7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다

```sql
WHERE  event_id    = :eventId
  AND  status      = 'PROCESSING'
  AND  claim_token = :claimToken
```

### 8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다

```
Lease 시간
>
(Batch 크기 × 개별 Kafka 발행 최대 응답 시간)
+
처리 완료 후 PUBLISHED 상태 UPDATE 시간
+
안전 마진 (예: 20%)

예시: Batch 100건 × 최대 100ms + UPDATE 50ms + 20% 마진 ≈ 12초 이상
```

## 과제 5. Kafka ACK, Timeout, 재시도 상태 전이 설계하기

### 1. 다음 네 상태의 의미 차이를 설명한다

```
KafkaTemplate.send() 호출 완료:
Producer 내부 버퍼에 메시지가 들어간 상태다. Broker에 전달됐는지, ACK를 받았는지 아직 모른다.
비동기로 동작하므로 이 시점은 발행 성공을 의미하지 않는다.

CompletableFuture 정상 완료:
Kafka Broker가 메시지를 수신하고 ACK를 반환한 상태다. Broker의 지정된 복제 수만큼 저장이 완료됐다.
이 시점부터 Kafka Record가 실제로 존재한다고 확신할 수 있다.

outbox = PUBLISHED:
Publisher가 ACK를 확인한 뒤 outbox_event 상태를 PUBLISHED로 변경한 시점이다.
DB에 "발행 완료"가 기록된 상태로, 이 이벤트는 더 이상 재발행 대상이 아니다.

모든 후속 Consumer 처리 완료:
Notification, MyPage, Analytics 등 모든 후속 서비스가 이벤트를 소비하고 자신의 비즈니스 로직을 완료한 상태다.
Publisher 입장에서는 이 상태를 직접 알 수 없다. 각 Consumer Group의 Offset 추적이 필요하다.
```

### 2. Kafka ACK 성공 후 PUBLISHED로 변경하는 SQL을 작성한다

```sql
UPDATE outbox_event
SET    status       = 'PUBLISHED',
       published_at = NOW(),
       claim_token  = NULL,
       lease_until  = NULL,
       updated_at   = NOW()
WHERE  event_id    = :eventId
  AND  status      = 'PROCESSING'
  AND  claim_token = :claimToken;
```

### 3. 발행 실패 후 PENDING으로 되돌리는 SQL을 작성한다

```sql
UPDATE outbox_event
SET    status           = 'PENDING',
       next_attempt_at  = NOW() + (INTERVAL '1 second' * POWER(2, LEAST(attempt_count, 10)) * (0.5 + random() * 0.5)),
       claim_token      = NULL,
       lease_until      = NULL,
       last_error       = LEFT(:errorMessage, 500),
       updated_at       = NOW()
WHERE  event_id    = :eventId
  AND  status      = 'PROCESSING'
  AND  claim_token = :claimToken;
```

### 4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다

```
상황 A: Broker에 저장되지 못하고 Timeout
네트워크 단절이나 Broker 장애로 메시지가 Broker에 도달하지 못한 경우다.
Kafka Topic에 Record가 없다. 재발행하면 처음으로 Record가 생성된다.

상황 B: Broker에는 저장됐지만 Publisher가 ACK를 확인하지 못하고 Timeout
Broker는 메시지를 받아 저장하고 ACK를 보냈지만 네트워크 단절로 Publisher가 ACK를 받지 못한 경우다.
Kafka Topic에 이미 Record가 존재한다. 재발행하면 같은 eventMessageId의 Record가 두 개 생긴다.

Publisher 입장에서 두 상황을 구분하기 어렵다. 모두 Timeout으로 보이기 때문이다.
따라서 Timeout 후에는 보수적으로 재발행을 시도하고 Consumer가 멱등하게 처리하도록 설계한다.
```

### 5. Timeout 이후 재시도 정책을 작성한다

```
Outbox 상태:
PENDING으로 되돌린다. claim_token을 초기화하고 next_attempt_at을 Backoff 이후로 설정한다.

재시도 여부:
한다. Timeout이 상황 A인지 B인지 알 수 없으므로 재시도해야 한다.

Kafka 중복 가능성:
있다. 상황 B라면 Broker에 이미 Record가 있고 재발행으로 두 번째 Record가 생긴다.

Consumer에게 필요한 방어:
eventMessageId 기준 멱등 처리. processed_event 테이블에 eventMessageId를 저장해 두 번째 Record는 처리를 건너뛴다.
```

### 6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다

```
Exponential Backoff:
발행 실패가 반복될수록 재시도 간격을 지수적으로 늘린다. (1초 → 2초 → 4초 → 8초...)
Kafka Broker가 일시적으로 과부하 상태라면 즉시 재시도하면 더 큰 부하를 주게 된다.
간격을 늘려 Broker가 회복할 시간을 주고 시스템 전체 부하를 줄인다.

Jitter:
여러 Outbox가 동시에 재시도를 시도하면 특정 시점에 Broker에 요청이 몰린다(Thundering Herd).
각 Outbox의 next_attempt_at에 무작위 분산값을 더해 재시도 시점을 분산시킨다.
동시 재시도 폭발을 방지하고 부하를 시간적으로 고르게 분산한다.
```

### 7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능하다 | 같은 PID + Sequence Number로 재시도한 메시지를 Broker가 감지해 한 번만 저장 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능하다 | 애플리케이션 레벨 재시도로 send()를 다시 호출하면 새 Sequence Number가 부여되어 Broker가 별개 메시지로 처리 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능하다 | 새로운 send() 호출로 새 Sequence Number가 부여되어 중복 Record가 생성됨 |

### 8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다

```
Kafka Producer의 whenComplete 콜백은 기본적으로 Producer의 I/O 스레드에서 실행된다.
I/O 스레드는 모든 발행 결과를 처리하는 공유 스레드이므로 이 스레드에서 DB 연결을 획득하고
오래 걸리는 작업을 수행하면 다른 발행 작업의 콜백 처리가 지연된다.
DB 연결 획득이 지연되면 Producer I/O 스레드 전체가 블로킹되어 발행 처리량이 급감한다.
또한 DB 예외가 발생해도 I/O 스레드에서 올바르게 처리하기 어렵다.
따라서 whenComplete 콜백에서는 결과를 별도 큐에 넣고, 전용 Executor 스레드 풀에서 DB 작업을 수행해야 한다.
```

## 과제 6. Outbox 장애 시나리오 분석하기

### 1. 발급 트랜잭션 Commit 전 장애

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 저장되지 않음. ROLLBACK으로 취소됨 |
| request | PROCESSING 전이 취소. PENDING 상태로 복구됨 |
| outbox_event | 저장되지 않음. ROLLBACK으로 취소됨 |
| 복구 방법 | 원본 Kafka 메시지의 Offset이 커밋되지 않았으므로 Consumer 재시작 후 같은 메시지를 다시 처리한다. PENDING 상태이므로 정상 재처리 가능 |

### 2. 발급 DB Commit 후 원본 Offset Commit 전 장애

| 항목 | 결과 |
| --- | --- |
| coupon_issue | 저장됨. 발급 기록 존재 |
| request | ISSUED 상태로 저장됨 |
| outbox_event | PENDING 상태로 저장됨. Publisher가 처리 대기 중 |
| 원본 Kafka 메시지 | Offset 미커밋으로 Consumer 재시작 시 재전달됨 |
| 복구 방법 | Consumer 재시작 후 같은 requestId 메시지 재처리. request ISSUED 확인 → 멱등 성공 처리 → Offset 커밋. outbox_event는 Publisher가 독립적으로 발행 |

### 3. Outbox Claim Commit 후 Kafka 발행 전 Publisher 종료

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING 상태로 남음. claim_token 설정됨 |
| Kafka Record | 없음. 발행이 시도되지 않았음 |
| 복구 조건 | Lease 만료 시각(lease_until) 이후 복구 가능 |
| 복구 주체 | 복구 배치 또는 다른 Publisher 인스턴스가 만료된 PROCESSING 행을 감지해 PENDING으로 복구 |

### 4. Kafka 발행 성공 후 PUBLISHED 변경 전 Publisher 종료

| 항목 | 결과 |
| --- | --- |
| outbox status | PROCESSING 상태로 남음. Lease 만료 후 PENDING으로 복구됨 |
| Kafka Record | 존재함. 이미 발행 성공 |
| 재발행 가능성 | 있음. PENDING 복구 후 Publisher가 다시 발행하면 같은 eventMessageId의 Record가 두 개 생김 |
| 필요한 Consumer 방어 | eventMessageId 기준 멱등 처리. processed_event에 eventMessageId가 이미 있으면 처리 건너뜀 |

### 5. Publisher A의 Lease 만료 후 Publisher B가 회수한 상황

```
Publisher A가 늦게 성공 UPDATE:
WHERE claim_token = tokenA 조건이 맞지 않아 (현재 claim_token = tokenB) affected = 0.
A의 UPDATE는 무시된다. Publisher B가 이미 처리 중이므로 문제없다.

Publisher A가 늦게 실패 UPDATE:
마찬가지로 WHERE claim_token = tokenA 조건이 실패해 0행. A의 실패 처리가 B의 작업에 영향을 주지 않는다.

두 UPDATE에서 affected rows가 0이어야 하는 조건:
WHERE event_id = :eventId AND status = 'PROCESSING' AND claim_token = :claimToken
A의 claimToken과 현재 저장된 tokenB가 다르므로 항상 0행이 된다.
```

### 6. Kafka 장애가 30분 동안 지속되는 상황

```
PENDING 수의 변화:
Outbox는 계속 생성(coupon 발급이 계속될 경우)되지만 Publisher가 발행하지 못하므로 PENDING이 계속 증가한다.
30분 × 60초 × 초당 생성 건수만큼 적체된다.

가장 오래된 PENDING 대기 시간:
30분. 장애 시작 시점에 생성된 Outbox가 가장 오래 대기한다.

attempt_count:
Exponential Backoff가 적용되더라도 30분 동안 여러 번 재시도했을 것이다.
예: 1s, 2s, 4s, 8s, 16s, 32s, 64s... 최대 attempt_count 제한에 따라 다름.

Kafka 복구 후 처리:
PENDING 상태의 모든 Outbox를 순차적으로 발행한다.
Backoff가 적용되어 next_attempt_at이 미래인 경우, 복구 즉시 일괄 처리하려면 next_attempt_at을 리셋하는 조치가 필요하다.

운영 알람:
PENDING 수 임계치 초과 알람, 가장 오래된 PENDING 대기 시간 임계치 초과 알람 발생.
즉각적인 Kafka Broker 상태 확인과 대응이 필요하다.
```

### 7. 다음 두 재시도 대상을 구분한다

```
발급 DB 트랜잭션 실패:
원본 coupon.issue.requested 메시지를 재처리한다.
Consumer가 Offset을 커밋하지 않아 Kafka가 메시지를 재전달하거나, 재시도 정책에 따라 재처리한다.
coupon_issue 발급 기록이 생성되지 않았으므로 재처리해야 한다.

발급 DB Commit 성공 후 CouponIssued 발행 실패:
원본 메시지를 재처리하지 않는다. 쿠폰은 이미 발급됐다.
outbox_event를 재발행하는 것이 목적이다. Publisher가 PENDING Outbox를 읽어 Kafka에 재발행한다.
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유:

```
쿠폰 발급은 이미 DB Commit으로 완료됐다. coupon_issue 기록이 존재하고 issued_count도 증가했다.
다시 발급을 시도하면 UNIQUE(event_id, user_id) 위반이 발생하거나 issued_count가 추가로 증가해 수량 정합성이 깨진다.
결과 이벤트 발행 실패는 후속 서비스 전달의 문제이지 발급 자체의 문제가 아니다.
Outbox 재발행으로 해결해야 한다.
```

## 과제 7. Consumer 멱등 처리 설계하기

### 1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다

```
Partition 1 / Offset 100 / eventMessageId = evt-001
Partition 1 / Offset 101 / eventMessageId = evt-001

두 Record는 같은 논리 이벤트(evt-001)지만 Offset이 다르다.
Offset을 멱등성 Key로 사용하면 Offset 100은 처리하고 Offset 101을 같은 이벤트로 인식하지 못한다.
결과적으로 같은 이벤트(evt-001)에 대한 비즈니스 반영이 두 번 이루어진다.
eventMessageId는 재발행해도 동일하므로 논리 이벤트의 중복을 올바르게 식별할 수 있다.
```

### 2. processed_event 테이블 DDL을 작성한다

```sql
CREATE TABLE processed_event (
    subscriber_id    VARCHAR(100)  NOT NULL,
    event_message_id UUID          NOT NULL,
    processed_at     TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_processed_event
        PRIMARY KEY (subscriber_id, event_message_id)
);
```

### 3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다

```
pod-7f8c9d, server-10.0.0.12는 프로세스 인스턴스 식별자다.
인스턴스가 재시작되거나 새 인스턴스로 교체되면 subscriber_id가 달라진다.
이전 인스턴스가 처리한 evt-001 기록이 있어도 새 인스턴스는 다른 subscriber_id로 처리하므로 중복을 감지하지 못한다.

mypage-coupon-projection처럼 논리적 서비스/Consumer 역할 이름을 사용해야 한다.
인스턴스가 교체되어도 subscriber_id가 동일하므로 이전에 처리한 이벤트를 올바르게 중복 감지할 수 있다.
같은 Consumer Group 내 여러 인스턴스가 모두 동일한 subscriber_id를 사용하므로 어느 인스턴스가 처리해도 멱등성이 보장된다.
```

### 4. processed_event 저장과 MyPage 조회 모델 변경을 하나의 트랜잭션으로 작성한다

```sql
BEGIN;

-- 1. eventMessageId 중복 확인 (INSERT 시도)
INSERT INTO processed_event (subscriber_id, event_message_id, processed_at)
VALUES ('mypage-coupon-projection', :eventMessageId, NOW())
ON CONFLICT (subscriber_id, event_message_id) DO NOTHING;

-- INSERT 영향받은 행 수 확인:
-- 1행: 최초 이벤트, 조회 모델 변경 진행
-- 0행: 중복 이벤트, 조회 모델 변경 건너뜀 (COMMIT 후 Offset 커밋)

-- 2. 최초 이벤트인 경우에만 조회 모델 변경
INSERT INTO user_coupon_view (user_id, coupon_event_id, coupon_issue_id, status, issued_at)
VALUES (:userId, :couponEventId, :couponIssueId, 'ISSUED', :issuedAt)
ON CONFLICT (user_id, coupon_event_id) DO UPDATE
    SET coupon_issue_id = EXCLUDED.coupon_issue_id,
        status          = EXCLUDED.status,
        issued_at       = EXCLUDED.issued_at;

COMMIT;
```

### 5. Consumer DB Commit 후 Offset Commit 전에 종료되는 상황을 분석한다

```
Consumer DB 상태:
processed_event에 eventMessageId 기록됨. user_coupon_view 조회 모델 갱신됨.

Consumer Group Offset:
Commit되지 않음. Kafka는 이 이벤트가 아직 처리되지 않은 것으로 인식.

재시작 후 Kafka 전달:
Consumer 재시작 후 같은 Offset(또는 Retry Topic의 같은 eventMessageId)을 다시 읽는다.

재전달된 이벤트 처리:
processed_event에 이미 eventMessageId 기록이 있으므로 INSERT ON CONFLICT DO NOTHING으로 0행.
조회 모델 변경을 건너뛰고 Commit 후 Offset을 커밋한다. 중복 비즈니스 반영 없이 정상 완료.
```

### 6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다

```
processed_event INSERT와 SMS API 호출은 원자적으로 묶을 수 없다.
processed_event를 INSERT하고 Commit한 후 SMS API 호출 전에 프로세스가 종료되면,
재시작 후 processed_event가 있으므로 중복 처리를 건너뛰어 SMS가 전송되지 않는다.
반대로 SMS API 호출 후 processed_event INSERT 전에 종료되면 중복 전송이 발생한다.
외부 SMS API는 DB 트랜잭션 참여자가 아니므로 완전한 Exactly-Once는 불가능하다.
```

### 7. Notification Service에서 추가로 적용할 수 있는 방법을 두 가지 이상 작성한다

```
1. SMS Provider의 멱등 API 사용:
   외부 SMS 서비스가 idempotency-key를 지원하면 동일한 키로 재시도해도 한 번만 전송된다.
   예: Twilio, AWS SNS의 DeduplicationId 활용.

2. 발송 상태 테이블 별도 관리:
   notification_log 테이블에 (eventMessageId, channel) 조합의 발송 기록을 저장한다.
   발송 전 기록이 있으면 건너뛰고, 없으면 발송 후 기록한다.
   처리 결과와 발송 기록을 하나의 트랜잭션으로 묶어 at-most-once 발송을 목표로 한다.

3. 지연 수용(At-Least-Once + 사용자 경험 설계):
   중복 SMS 발송을 완전히 막기 어려우므로 "쿠폰이 발급됐습니다" 알림이 두 번 오는 것을 수용 가능한 수준으로 설계한다.
   중복 발송 빈도를 모니터링하고 임계치 초과 시 알람을 설정한다.
```

### 8. processed_event 보관 기간을 정할 때 고려할 중복 재등장 경로를 작성한다

```
Kafka Topic 보관 기간:
Topic의 retention 기간 내에 Consumer Offset이 되감기면 오래된 이벤트가 재전달된다.
processed_event 보관 기간은 Topic retention 기간보다 길어야 한다.

Consumer Offset 되감기:
운영 중 의도적으로 Offset을 과거로 되감으면 이미 처리한 이벤트가 재전달된다.
되감기 시점 이전의 eventMessageId가 다시 전달될 수 있으므로 해당 기간의 기록이 남아 있어야 한다.

Outbox 지연 재발행:
오랫동안 PROCESSING에 머물다 복구된 Outbox가 뒤늦게 발행되면 오래된 eventMessageId가 전달된다.
최대 Outbox 지연 허용 시간을 고려해 보관 기간을 설정한다.

운영자 수동 재발행:
장애 복구 목적으로 운영자가 과거 Outbox를 다시 PENDING으로 변경해 재발행하면
오래된 eventMessageId가 다시 Consumer에 전달된다.
재발행 가능한 가장 오래된 Outbox 기간을 고려해야 한다.

→ 보관 기간 = max(Topic retention, Outbox 최대 지연, 운영자 재발행 가능 기간) + 여유 기간
```

## 과제 8. Partition Key와 이벤트 순서 문제 분석하기

### 1. 같은 Partition Key를 사용하는 이유를 작성한다

```
Kafka는 같은 Partition Key를 가진 메시지를 항상 같은 Partition에 저장한다.
같은 Partition 내에서는 메시지가 저장된 순서대로 Consumer에게 전달된다.
couponIssueId를 Partition Key로 사용하면 같은 쿠폰 발급 건에 관한 이벤트(CouponIssued, CouponCancelled 등)가
모두 같은 Partition에 배치되어 같은 Consumer 인스턴스가 순서대로 처리할 수 있다.
```

### 2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다

```
여러 Publisher 인스턴스:
Publisher A가 CouponIssued(version=1)를 처리하고 Publisher B가 CouponCancelled(version=2)를 처리할 때
B가 먼저 Kafka에 발행하면 순서가 역전된다.

SKIP LOCKED:
FOR UPDATE SKIP LOCKED는 잠긴 행을 건너뛰므로 생성 순서와 다른 순서로 Claim될 수 있다.
오래된 이벤트가 잠겨 있으면 최신 이벤트가 먼저 발행된다.

발행 실패와 Backoff:
CouponIssued(version=1) 발행에 실패해 Backoff 중일 때 CouponCancelled(version=2)가 먼저 발행될 수 있다.
같은 Partition Key라도 발행 시점의 차이로 순서가 역전된다.

Producer 설정과 재시도:
Producer 내부 재시도와 max.in.flight.requests.per.connection 설정에 따라 순서가 달라질 수 있다.
Idempotent Producer를 사용해도 애플리케이션 레벨 재시도에서 순서가 달라질 수 있다.
```

### 3. 다음 순서 역전 시나리오를 완성한다

```
DB 발생 순서

CouponIssued
aggregateVersion = 1

CouponCancelled
aggregateVersion = 2

Publisher 처리

Publisher A:
CouponIssued(version=1) Claim → 발행 실패 → Backoff 중

Publisher B:
CouponCancelled(version=2) Claim → 발행 성공 → PUBLISHED

Publisher A 재시도:
CouponIssued(version=1) 발행 성공 → PUBLISHED

Kafka 저장 순서:
CouponCancelled(version=2) → CouponIssued(version=1)
(비즈니스 발생 순서와 반대)
```

### 4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다

```
1. 시스템 시계 오차(Clock Skew):
   여러 서버 인스턴스의 시계가 정확히 일치하지 않는다.
   서버 A에서 발생한 이벤트의 occurredAt이 서버 B의 이벤트보다 앞서도 실제 발생 순서는 다를 수 있다.

2. 같은 트랜잭션의 동시성:
   NOW()는 트랜잭션 시작 시각을 반환하므로 같은 밀리초 안에 여러 이벤트가 발생하면 occurredAt이 동일하다.
   동일한 occurredAt으로는 순서를 판단할 수 없다.

3. 재발행 시 occurredAt이 변경될 수 있음:
   구현이 잘못된 경우 재발행 시 현재 시각으로 occurredAt이 갱신되면 원래 발생 순서와 달라진다.
   이 경우 나중에 재발행된 오래된 이벤트의 occurredAt이 최신 이벤트보다 뒤에 찍힐 수 있다.
```

### 5. MyPage처럼 최신 상태만 필요한 Projection의 순서 역전 방어 SQL을 작성한다

```sql
UPDATE user_coupon_view
SET    status                  = :newStatus,
       last_aggregate_version  = :aggregateVersion,
       last_event_at           = :occurredAt,
       updated_at              = NOW()
WHERE  coupon_issue_id         = :couponIssueId
  AND  last_aggregate_version  < :aggregateVersion;
```

### 6. aggregateVersion이 더 큰 이벤트가 먼저 도착한 경우의 결과를 작성한다

```
먼저 도착: CouponCancelled(version=2)
→ user_coupon_view 업데이트됨. status=CANCELLED, last_aggregate_version=2

나중 도착: CouponIssued(version=1)
→ WHERE last_aggregate_version < 1 조건이 false (현재 2 >= 1)
→ UPDATE 0행. 조회 모델이 변경되지 않음

최종 MyPage 상태:
status = CANCELLED (CouponCancelled 기준으로 유지됨)

version=1 처리 결과:
UPDATE 0행. 낮은 버전의 이벤트가 최신 상태를 덮어쓰지 않음. 올바른 동작.
```

### 7. 모든 Consumer가 낮은 aggregateVersion 이벤트를 버려도 되는지 판단한다

| Consumer | 낮은 Version 이벤트 생략 가능 여부 | 이유 또는 추가로 필요한 설계 |
| --- | --- | --- |
| 최신 상태만 저장하는 MyPage Projection | 가능하다 | 최신 aggregateVersion보다 낮은 이벤트는 이미 더 최신 상태로 덮어씌워진 상태이므로 처리해도 결과가 동일하거나 잘못된 상태로 역전된다 |
| 모든 발급·취소 건수를 집계하는 Analytics | 불가능하다 | 발급 건수와 취소 건수를 정확히 집계하려면 모든 이벤트를 처리해야 한다. 낮은 버전의 이벤트도 실제 발생한 사실이므로 집계에 포함해야 한다 |
| 발급과 취소 알림을 각각 보내는 Notification | 불가능하다 | 발급 알림과 취소 알림을 각각 보내야 한다. 순서 역전이 발생해도 각 이벤트에 대한 알림은 모두 전송해야 한다. 단, 중복 알림 방지를 위해 processed_event 기반 멱등 처리가 추가로 필요하다 |

### 8. `aggregateVersion`의 역할을 정확히 정의한다

```
aggregateVersion은 이벤트 순서 역전을
자동으로 방지하는 값이 아니다.

aggregateVersion은 같은 Aggregate에서 발생한 상태 변경의
논리적 순서(발생 순번) 을 식별하기 위한 값이다.

최신 상태 Projection에서는 낮은 버전이
최신 상태를 덮어쓰는 것을 방지할 수 있다.

모든 상태 전이를 순서대로 처리해야 하는 Consumer는
추가로 이벤트 순서 재조립(버퍼링) 또는 sequencer 설계 이 필요하다.
```

## 과제 9. Outbox 운영 지표와 보관 정책 설계하기

### 1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않은 이벤트 수. Publisher가 처리해야 할 대기 건수 | 지속적으로 증가하거나 임계치 초과 시 → Publisher 처리 지연 또는 Kafka 장애 |
| 가장 오래된 PENDING 대기 시간 | 미발행 이벤트 중 가장 오래 대기한 이벤트의 경과 시간 | 수 분 이상 → Publisher가 해당 이벤트를 처리하지 못하고 있음 |
| PROCESSING 이벤트 수 | 현재 Publisher가 Claim해 발행 시도 중인 이벤트 수 | 급격히 증가하고 줄지 않으면 Publisher 장애 또는 Lease 만료 복구 문제 |
| 만료된 PROCESSING 수 | Lease가 지났지만 아직 PENDING으로 복구되지 않은 이벤트 수 | 0 이상 → 복구 배치가 동작하지 않거나 Lease 설정이 잘못됨 |
| attempt_count | 특정 이벤트의 재시도 횟수 | 최대 재시도 임계치에 가까우면 → 영구 실패 가능성. DLQ 처리 준비 필요 |
| Outbox 생성 처리량 | 초당 새로 생성되는 Outbox 이벤트 수 | 급증 → 쿠폰 발급 요청 폭주. 발행 속도와 비교해 적체 여부 판단 |
| Kafka 발행 처리량 | 초당 Publisher가 Kafka에 발행 완료하는 이벤트 수 | 생성 처리량보다 낮으면 → 적체 증가. Kafka Broker 또는 Publisher 병목 |
| DB 발생부터 Kafka ACK까지의 시간 | Outbox 생성 시각부터 PUBLISHED 상태로 변경될 때까지의 지연 시간 | SLA 초과 → 후속 서비스 지연 발생. Publisher Polling 주기나 배치 크기 조정 필요 |

### 2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다

```
1분 후 예상 적체 증가량:
(2,000 - 1,500) × 60 = 30,000건

10분 후 예상 적체 증가량:
(2,000 - 1,500) × 600 = 300,000건

가장 먼저 확인할 지표:
Publisher 처리 속도 병목 원인 → Kafka Broker 처리 지연, Publisher 인스턴스 수, Batch 크기, DB 쿼리 성능

가능한 대응:
1. Publisher 인스턴스 수 증가 (수평 확장)
2. Batch 크기 증가 (Claim당 처리 건수 늘림)
3. Kafka Producer 설정 최적화 (linger.ms, batch.size)
4. 근본 원인이 Kafka Broker 성능이면 Broker 스케일 아웃
```

### 3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다

```
1. 가장 오래된 PENDING 이벤트 대기 시간이 SLA(예: 5분)를 초과한 경우
   → 특정 이벤트가 영구적으로 처리되지 않을 위험. 수동 확인 필요.

2. 동일 이벤트의 attempt_count가 최대 재시도 임계치(예: 10회)에 도달한 경우
   → 영구 실패 이벤트 가능성. DLQ 처리 또는 운영자 개입 필요.

3. 만료된 PROCESSING 이벤트가 복구 배치 주기를 지나도 PENDING으로 돌아오지 않는 경우
   → 복구 배치 자체가 동작하지 않는 장애 상황.

4. Outbox 생성 처리량과 Kafka 발행 처리량의 격차가 지속적으로 벌어지는 경우
   → 적체가 선형적으로 증가해 결국 서비스 전체에 영향을 미칠 수 있음.
```

### 4. PUBLISHED 행만 정리해야 하는 이유를 설명한다

```
PENDING을 삭제하면:
아직 발행되지 않은 이벤트가 사라진다. CouponIssued 이벤트가 영원히 발행되지 않아 후속 서비스가 이를 알 수 없게 된다.
데이터 유실이 발생한다.

PROCESSING을 삭제하면:
현재 Publisher가 처리 중인 이벤트가 삭제된다. Publisher가 ACK 후 PUBLISHED로 변경하려 해도 행이 없어 실패한다.
발행이 완료됐지만 DB에 기록이 없어 재발행 여부를 판단할 수 없다.

PUBLISHED를 보관하는 목적:
운영 감사(Audit): 발행된 이벤트의 이력 확인.
Consumer 디버깅: 특정 이벤트가 발행됐는지 확인.
재발행 요청: 운영자가 과거 이벤트를 다시 PENDING으로 변경해 재발행하는 근거.
duplicate 탐지: 최근 PUBLISHED 이력과 비교해 중복 발행 여부 확인.
일정 기간 이후에는 삭제해도 무방하다.
```

### 5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다

```
긴 트랜잭션:
수십만 건의 DELETE를 하나의 트랜잭션으로 처리하면 트랜잭션이 오래 열려 있다.
이 동안 다른 쿼리의 MVCC 스냅샷이 오래된 버전을 참조해야 하므로 DB 부하가 증가한다.

DB 부하:
대량 DELETE는 CPU, I/O, 메모리를 집중적으로 사용해 다른 Outbox 처리와 쿠폰 발급 처리에 영향을 준다.

Lock:
DELETE는 대상 행에 배타 락을 잡는다. 대량 삭제 중 다른 트랜잭션이 같은 행에 접근하면 대기가 발생한다.
Publisher Claim이나 Outbox INSERT가 지연될 수 있다.

Table Bloat:
대량 DELETE 후 PostgreSQL에서 dead tuple이 많이 남아 테이블 크기가 줄지 않는다.
VACUUM 또는 AUTOVACUUM이 실행되기 전까지 Table Bloat이 지속되어 인덱스 성능이 저하된다.
```

### 6. 작은 Batch로 정리하는 운영 흐름을 작성한다

```
1. 정리 배치가 주기적으로 실행된다 (예: 매 1분마다).

2. 보관 기간이 지난 PUBLISHED 행을 occurred_at 기준으로 소량(예: 1,000건씩) 조회한다.
   SELECT event_id FROM outbox_event
   WHERE status = 'PUBLISHED' AND published_at < NOW() - INTERVAL '7 days'
   ORDER BY published_at ASC LIMIT 1000;

3. 조회된 event_id 목록을 삭제한다.
   DELETE FROM outbox_event WHERE event_id = ANY(:ids);

4. 삭제 건수를 로그에 기록한다.

5. 삭제 건수가 Batch 크기와 같으면(더 삭제할 것이 있음) 짧은 간격 후 반복한다.
   삭제 건수가 Batch 크기보다 작으면 다음 주기까지 대기한다.
```

### 7. 다음 세 보관 기간의 목적을 비교한다

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |
| Outbox PUBLISHED 행 | 발행 이력 감사, 재발행 근거, 중복 발행 탐지 | 보관 기간 내 재발행 요청 시 근거 행이 없어 재발행 불가. 이력 조회 불가 |
| Kafka Topic Record | Consumer가 이벤트를 소비할 수 있는 시간 보장, Offset 되감기 복구 | 보관 기간 내 Consumer가 처리하지 못한 이벤트가 사라짐. 복구 불가 |
| Consumer processed_event | 중복 이벤트 처리 방지 | 보관 기간 이후 동일한 eventMessageId가 재전달되면 중복 처리 발생. 오래된 이벤트 재발행 시 processed_event가 없어 중복 비즈니스 반영 |

### 8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다

```
Stack Trace 전체 저장 문제:
Stack Trace는 내부 패키지 구조, 메서드명, 라인 번호 등 시스템 내부 정보를 담고 있다.
outbox_event 테이블에 접근 권한이 있는 내부 사용자가 이 정보를 통해 시스템 구조를 파악하거나 보안 취약점을 찾을 수 있다.
또한 Stack Trace는 매우 길어 컬럼 크기를 초과하거나 DB 공간을 낭비한다.

민감 정보 저장 문제:
오류 메시지에 userId, 개인 식별 정보, 쿠폰 코드 등이 포함될 수 있다.
outbox_event는 운영 목적 테이블이므로 여러 담당자가 접근할 수 있어 개인정보 노출 위험이 있다.
규정(GDPR, 개인정보 보호법)에 따라 DB에 개인정보를 불필요하게 저장하는 것은 위반이 될 수 있다.

대안: 오류 유형과 간단한 메시지(예: "Kafka connection timeout after 5s")만 저장하고,
상세 오류는 별도 로그 시스템(ELK, CloudWatch)에서 관리한다.
```

```
발생 가능한 장애: processed_event는 저장됐지만 조회 모델이 갱신되지 않거나, 반대로 조회 모델만 갱신되고 processed_event가 없어 중복 처리가 발생한다.

수정 방법: 두 저장 작업을 하나의 @Transactional 메서드에서 처리한다.
```

### 2. 반드시 찾아야 하는 문제

| 검토 항목 | 문제가 발생하는 코드 | 수정 방향 |
| --- | --- | --- |
| 발급 트랜잭션에서 Kafka 직접 호출 | issueCoupon()의 kafkaTemplate.send() | Outbox INSERT로 대체. Kafka 발행은 Publisher가 담당 |
| 발급 결과와 Outbox의 원자적 저장 없음 | issueCoupon()에 outbox_event INSERT 없음 | 발급 트랜잭션 마지막에 outbox_event INSERT 추가 |

| DB 트랜잭션 안에서 Kafka ACK 대기 또는 발행 수행 | publishOutbox()의 @Transactional + kafkaTemplate.send() | Claim 트랜잭션 Commit 후 트랜잭션 밖에서 Kafka 발행 |

| processed_event와 비즈니스 변경의 트랜잭션 순서·원자성 부족 | onResult()에서 두 저장소 별도 호출 | 하나의 트랜잭션으로 묶어 원자적으로 처리 |

### 3. 수정된 전체 구조를 다이어그램으로 작성한다

```
Coupon Issue Consumer
  │ 원본 메시지 소비 (coupon.issue.requested)
  │
  ├─ 발급 DB Transaction (BEGIN)
  │    ├─ PENDING → PROCESSING (처리 권한 획득)
  │    ├─ coupon_event issued_count 증가
  │    ├─ coupon_issue INSERT
  │    ├─ coupon_issue_request ISSUED 변경
  │    └─ outbox_event INSERT (status=PENDING, payload=스냅샷)
  │    COMMIT
  │
  │ Kafka 원본 Offset 커밋
  │
  ▼
outbox_event (PENDING)
  │
  ▼
Outbox Publisher (Polling)
  │
  ├─ Claim Transaction (BEGIN)
  │    └─ PENDING → PROCESSING (FOR UPDATE SKIP LOCKED, claim_token 생성)
  │    COMMIT
  │
  ├─ Kafka 발행 (트랜잭션 밖에서)
  │    kafkaTemplate.send("coupon.issued", partitionKey, payload)
  │
  ├─ ACK 성공 → 성공 Transaction
  │    UPDATE outbox_event SET status='PUBLISHED'
  │    WHERE event_id=:id AND status='PROCESSING' AND claim_token=:token
  │    COMMIT
  │
  └─ ACK 실패 / Timeout → 실패 Transaction
       UPDATE outbox_event SET status='PENDING', next_attempt_at=backoff
       WHERE event_id=:id AND status='PROCESSING' AND claim_token=:token
       COMMIT
  │
  ▼
Kafka coupon.issued Topic
  │
  ▼
Result Consumers (Notification / MyPage / Analytics)
  │
  ├─ Consumer Business Transaction (BEGIN)
  │    ├─ processed_event INSERT ON CONFLICT DO NOTHING
  │    │    0행 → 중복 이벤트 → COMMIT → Offset 커밋 (멱등 성공)
  │    │    1행 → 최초 이벤트 → 비즈니스 처리 진행
  │    └─ Consumer Business Table 변경 (조회 모델, 통계, 알림 기록 등)
  │    COMMIT
  │
  └─ Kafka Offset 커밋
```

### 4. 수정된 구조의 발행 보장 수준을 작성한다

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 DB 트랜잭션으로 묶어 둘 다 Commit되거나 둘 다 Rollback된다 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | Publisher 재시도로 같은 eventMessageId의 Record가 두 개 생길 수 있다 |
| Publisher 복구 후 재발행 | 보장 | Lease 만료 복구와 PENDING 상태 유지로 재시작 후 재발행이 가능하다 |
| 비즈니스 발생 순서대로 전달 | 조건부 보장 | 같은 Partition Key 사용 시 단일 Publisher에서는 순서가 보존되나, 여러 Publisher나 재시도로 순서 역전이 발생할 수 있다 |
| Consumer의 중복 비즈니스 반영 방지 | 보장 | eventMessageId 기반 processed_event와 원자적 트랜잭션으로 중복 반영을 방지한다 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | Publisher는 Kafka에 발행만 하며 각 Consumer Group의 처리 완료는 별도로 추적해야 한다 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | 외부 API는 DB 트랜잭션 참여자가 아니므로 완전한 Exactly-Once는 불가능하다. Provider의 멱등 API 활용이 최선 |
