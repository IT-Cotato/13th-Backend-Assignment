# 13기_배선아 5주차 과제

# **Transactional Outbox Pattern과 이벤트 발행 정합성**

## **1. 과제 목표**

이번 과제의 목표는 **쿠폰 발급 결과를 PostgreSQL에 저장하는 작업과 `CouponIssued` 이벤트를 Kafka에 발행하는 작업 사이의 Dual Write 문제를 분석하고, Transactional Outbox Pattern으로 복구 가능한 이벤트 발행 구조를 설계하는 것**이다.

5주차까지 쿠폰 발급 Consumer는 다음 작업을 하나의 DB 트랜잭션으로 처리했다.

```
coupon_issue_request PENDING → PROCESSING

coupon_event.issued_count 증가

coupon_issue 발급 기록 저장

coupon_issue_request → ISSUED
```

DB 트랜잭션이 Commit된 시점을 최종 쿠폰 발급 성공으로 본다.

하지만 발급 결과를 Notification, MyPage, Analytics 같은 후속 서비스에 전달하려면 별도의 결과 이벤트가 필요하다.

```
PostgreSQL
→ 쿠폰 발급 결과 저장

Kafka
→ CouponIssued 이벤트 발행
```

PostgreSQL과 Kafka는 서로 다른 시스템이다.

하나의 메서드 안에서 두 작업을 호출하거나 DB 메서드에 `@Transactional`을 붙이는 것만으로는 두 시스템이 하나의 원자적 트랜잭션이 되지 않는다.

이번 과제에서는 다음 구조를 설계한다.

```
Coupon Issue Consumer
        ↓
+------------------------------------------+
| PostgreSQL Transaction                   |
|------------------------------------------|
| coupon_issue 저장                        |
| request ISSUED 변경                      |
| CouponIssued Outbox 저장                 |
+------------------------------------------+
        ↓ Commit
Outbox Publisher
        ↓
Kafka coupon.issued
        ↓
Result Consumer
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
PostgreSQL과 Kafka 사이의 Dual Write 문제

DB First와 Kafka First가 각각 실패하는 이유

AFTER_COMMIT만으로 이벤트 유실을 막을 수 없는 이유

비즈니스 결과와 Outbox를 같은 트랜잭션에 저장하는 이유

Outbox 이벤트 Envelope와 테이블 설계

PENDING / PROCESSING / PUBLISHED 상태의 의미

FOR UPDATE SKIP LOCKED를 이용한 동시 Claim

Claim Token과 Lease가 필요한 이유

Kafka ACK와 메서드 호출 성공의 차이

Timeout과 재시도에서 발생하는 중복 발행

At-Least-Once Publication과 Consumer 멱등 처리

eventMessageId와 Kafka Offset의 차이

Partition Key와 이벤트 순서 보장의 차이

aggregateVersion의 역할과 적용 범위

Outbox 적체를 감지하기 위한 운영 지표
```

이번 과제의 핵심은 다음과 같다.

```
Outbox는 Kafka Record를 정확히 한 번 생성하는 패턴이 아니다.

Outbox는 DB 결과가 Commit되었을 때
발행할 이벤트 기록도 같은 DB에 반드시 남도록 만드는 패턴이다.

Publisher는 남아 있는 이벤트를 재시도할 수 있다.

재시도로 중복 발행이 발생할 수 있으므로
Consumer도 멱등하게 처리해야 한다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
쿠폰 발급 비즈니스 데이터와 Outbox는
같은 PostgreSQL Database에 저장한다.

coupon_issue_request,
coupon_event,
coupon_issue,
outbox_event는
필요한 경우 하나의 로컬 DB 트랜잭션에 포함할 수 있다.

원본 coupon.issue.requested 메시지는
5주차의 requestId 기반 멱등 처리로 중복을 방어한다.

자동 Offset Commit은 사용하지 않는다.

원본 Consumer는 발급 DB 트랜잭션이 Commit된 뒤에만
처리 완료로 간주한다.

Spring Kafka의 실제 Offset Commit 시점은
설정한 AckMode와 Error Handler 정책에 맞게 구성한다.

Outbox Publisher는 Polling 방식으로 구현한다.

이번 주차의 기본 Publisher는
작은 Batch를 순차 동기 방식으로 발행한다.

Kafka 발행은 Claim 트랜잭션 밖에서 수행한다.

Publisher는 Kafka Broker ACK를 확인한 뒤
Outbox를 PUBLISHED로 변경한다.

Publisher는 같은 Outbox 이벤트를
두 번 이상 Kafka에 발행할 수 있다.

Consumer는 eventMessageId를 기준으로
중복 비즈니스 반영을 방어한다.
```

이번 과제의 Outbox가 직접 해결하는 범위는 다음과 같다.

```
PostgreSQL에 확정되는 쿠폰 발급 성공

+

후속 서비스에 전달할 CouponIssued 발행 의도
```

다음 구간은 이번 Outbox가 자동으로 원자화하지 않는다.

```
Redis 선착순 판정
↔ 최초 coupon.issue.requested Kafka 발행

원본 coupon.issue.requested Kafka 소비
↔ PostgreSQL 발급 트랜잭션

Result Consumer의 로컬 DB 저장
↔ 이메일·SMS 같은 외부 API 호출
```

## **과제 1. Dual Write 문제와 Outbox 적용 범위 분석하기**

쿠폰 발급 결과를 DB에 저장하는 작업과 Kafka에 결과 이벤트를 발행하는 작업을 하나의 메서드에서 직접 수행한다고 가정한다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    increaseIssuedCount(message.eventId());

    CouponIssue issue = saveCouponIssue(message);

    markRequestIssued(
        message.requestId(),
        issue.getId()
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}
```

### **1. 위 코드가 사용하는 저장소 두 개를 작성한다**

```
PostgreSQL (coupon_event, coupon_issue, coupon_issue_request)
Kafka Borker (coupon.issued 토픽)
```

### **2. `@Transactional`만으로 두 저장소가 원자적으로 묶이지 않는 이유를 설명한다**

```
@Transactional은 Spring이 관리하는 하나의 PlatformTransactionManager에 대해서만 Commit/Rollback을 제어한다. 

따라서 DB 내부 상태만 제어할 뿐 Kafka 네트워크 전송까지 제어할 수 없으므로, 두 저장소 간의 원자성을 보장할 수 없다.
```

### **3. DB를 먼저 Commit한 뒤 Kafka에 발행하는 흐름의 장애 구간을 작성한다**

다음 형식을 완성한다.

```
DB Commit
    ↓
[장애 지점]
    ↓
Kafka 발행

최종 DB 상태: coupon_issue 저장 완료, request = ISSUED (쿠폰은 실제로 발급됨)

최종 Kafka 상태: CouponIssued 레코드 없음

후속 서비스에 미치는 영향: Notification/MyPage/Analytics 모두 발급 사실을 전달받지 못함

복구에 필요한 정보: "무엇을 다시 발행해야 하는가"에 대한 영속적인 기록. 메모리에만 발행 대상이 있었다면 재시작 후 이를 알 방법이 없다 -> Outbox 필요
```

### **4. Kafka를 먼저 발행한 뒤 DB에 저장하는 흐름의 장애 구간을 작성한다**

```
Kafka 발행
    ↓
[장애 지점]
    ↓
DB Commit

최종 DB 상태: coupon_issue 없음, request는 ISSUED로 확정되지 않음 (Rollback)

최종 Kafka 상태: CouponIssued 레코드 존재
 
후속 서비스에 미치는 영향: Notification/MyPafe/Analytics가 "존재하지 않는" 발급 결과를 실제 발급인 것처럼 처리함. 사용자는 실제로 쿠폰을 받지 못했는데 발급 알림을 받거나 마이페이지에 쿠폰이 노출되는 정합성 오류가 발생
```

### **5. `AFTER_COMMIT` Listener만으로 이벤트 유실을 해결할 수 없는 이유를 설명한다**

다음 두 장애를 반드시 포함한다.

```
DB Commit 후 Listener 실행 전 프로세스 종료

KafkaTemplate.send() 호출 후
Broker ACK 확인 전 프로세스 종료
```

```
AFTER_COMMIT은 이벤트를 DB에 저장하지 않고 메모리(JVM)에서만 다루기 때문에 다음 두 상황에서 이벤트 유실을 막을 수 없다.

    - DB Commit 후 Listener 실행 전 프로세스 종료: 이베트가 메모리에서 휘발되어 Kafka 발행 시도조차 못하고 소멸한다.

    - KafkaTemplate.send() 호출 후 Broker ACK 확인 전 프로세스 종료: 비동기 전송 특성상 ACK를 받기 전에 죽으면 실제 전송 여부를 알 수 없어 재발행이 불가능하다.

결국 이벤트 상태가 기록되지 않아 장애 시 재시도할 근거가 없다는 것이 핵심 이유이다.
```

### **6. 이번 과제에서 Outbox가 해결하는 범위와 해결하지 않는 범위를 구분한다**

| 구간 | 이번 Outbox로 해결되는가? | 이유 |
| --- | --- | --- |
| coupon_issue 저장 ↔︎ CouponIssued 발행 의도 저장 | O | 같은 PostgreSQL DB, 같은 로컬 트랜잭션으로 묶어 원자적으로 Commit/Rollback 되도록 설계했기 때문 |
| Redis SUCCESS ↔︎ 최초 요청 Kafka 발행 | X | Redis와 PostgreSQL은 서로 다른 저장소이며, 이번 과제의 Outbox는 PostgreSQL 내부 트랜잭션 범위만 다룸. API Server 쪽에 별도 Outbox를 둘 수는 있지만 그래도 Redis ↔ PostgreSQL 구간 자체는 원자화되지 않음 |
| 원본 Kafka 소비 ↔︎ 발급 DB Commit | X | Outbox가 원자화하는 것이 아니라, requestId 기반 멱등 처리로 중복 소비를 방어함. 원본 Consumer가 재시도될 수 있다는 전제 위에서 동작 |
| Consumer DB 저장 ↔︎ 외부 SMS API 호출 | X | 외부 API 호출은 로컬 DB 트랜잭션에 포함될 수 없는 별도의 Dual Write 문제이며, Notification Service 내부에 별도 Outbox나 Idempotency Key같은 추가 설계가 필요함 |

### **7. 다음 문장을 완성한다**

```
Transactional Outbox가 직접 보장하는 것:
DB에서 쿠폰 발급 결과가 Commit되면, 그 결과에 대해 발행해야 함.
이벤트 기록(outbox_event 행)도 반드시 같은 트랜잭션 안에서 함께 DB에 남는다는 것.

Transactional Outbox가 직접 보장하지 않는 것:
Kafka Record가 물리적으로 정확히 한 번만 생성되는 것, 이벤트가 비즈니스 발생 순서대로 전달되는 것, 모든 Consumer가 반드시 처리를 완료하는 것, 그리고 외부 알림(SMS/이메일)이 정확히 한 번 전송되는 것
```

## **과제 2. CouponIssued 이벤트와 Outbox 테이블 설계하기**

### **1. `CouponIssued`가 명령이 아니라 이미 발생한 사실을 나타내야 하는 이유를 설명한다**

다음 두 이름의 의미 차이를 포함한다.

```
IssueCoupon -> "쿠폰을 발급하라"는 명령

CouponIssued -> "쿠폰이 이미 발급되었다"는 사실
```

```
결과 이벤트를 명령형으로 이름 붙이면 Consumer가 "내가 다시 발급을 수행해야 하나?"라고 오해할 위험이 생긴다.
CouponIssued처럼 과거 사실로 표현하면 Consumer는 이 이벤트를 발급 로직의 트리거가 아니면 이미 끝난 일의 결과 반영(알림 생성, 조회 모델 갱신, 통계 반영)으로만 다루게 된다. 
```

### **2. CouponIssued 이벤트 JSON을 완성한다**

반드시 다음 필드를 포함한다.

```
eventMessageId
eventType
schemaVersion
aggregateVersion
occurredAt
requestId
couponIssueId
couponEventId
userId
issuedAt
```

```json
{
    "eventMessageId": "8a78e94b-5c3d-46a7-a364-538cd1f856c9",
    "eventType": "COUPON_ISSUED",
    "schemaVersion": 11,
    "aggregateVersion": 1,
    "occurredAt": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
    "data": {
        "couponIssueId": 5001,
        "couponEventId": 100,
        "userId": 10,
        "issuedAt": "2026-07-26T03:00:01Z"
    }
}
```

### **3. 다음 ID의 역할을 비교한다**

| 값 | 식별 대상 | 재발행 시 값이 바뀌는가? | Consumer 멱등성 Key로 적절한가? |
| --- | --- | --- | --- |
| couponEventId | 쿠폰 행사 자체 | X | 부적절 (여러 발급 건이 같은 값을 공유) |
| couponIssueId | 하나의 발급 기록 | X | 부적절 (단독으로 X. 같은 발급에 대해 여러 이벤트 타입이 생길 수 있음) |
| eventMessageId | 이 결과 이벤트 메시지 자체 | X | 적절 (Cosumer의 proccessed_event 멱등 키로 사용) |
| Kafka Partition + Offset | 물리적 저장 위치 | O | 부적절 (같은 논리 이벤트가 다른 Offset을 가질 수 있음) |

### **4. `occurredAt`과 `publishedAt`의 차이를 설명한다**

```
occurredAt: 쿠폰 발급이라는 비즈니스 결과가 "실제로 발생한" 시각. DB 트랜잭션에서 발급이 확정된 시점 기준이며, CouponIssued의 경우 issuedAt과 같은 기준 시각을 사용할 수 있다.
 
publishedAt: Publisher가 Kafka Broker의 ACK를 확인한 뒤, 그 사실을 DB(outbox_event.published_at)데 기록한 시각. 재시도가 발생하면 매번 달라질 수 있다.

Publisher 재시도 시 변경하면 안 되는 값: occurredAt과 payload 전체. 이 값들은 "발생한 사실의 불변 스냅샷"이므로 재시도 여부와 무관하게 고정되어야 한다.
```

### **5. Publisher가 발행 시점에 현재 비즈니스 테이블을 다시 조회해 Payload를 만들면 안 되는 이유를 설명한다**

```
Outbox 행히 INSERT된 후 실제 Kafka 발행까지는 시간차가 있다.

그 사이에 원본 지스니스 데이터(coupon_issue 등)가 다른 트랜잭션에 의해 변경되거나 취소될 수 있다.

Publisher가 발행 시점에 다시 조회해서 Payload를 만들면, "그 이벤트가 발생했던 시점의 사실"이 아니라 "지금 이 순간의 최신 상태"를 발행하게 되어 이벤트의 의미가 왜곡된다.

예를 들어 발급 직후 바로 취소된 쿠폰이라면 뒤늦게 발행되는 CouponIssued 이벤트의 Payload에 취소된 상태가 섞여 들어갈 수 있다.

따라서 Payload는 INSERT 시점에 완성된 불변 Sanpshot으로 저장하고, Publisher는 그것을 그대로 전달만 해야 한다.
```

### **6. 다음 Outbox 테이블 DDL을 완성한다**

아래 요구사항을 만족해야 한다.

```
event_id는 UUID Primary Key

같은 비즈니스 결과의 중복 Outbox 생성을 막는
deduplication_key UNIQUE

Aggregate 식별 정보 저장

Topic, Partition Key, Payload 저장

PENDING / PROCESSING / PUBLISHED 상태만 허용

재시도 횟수와 다음 재시도 시각 저장

Claim Token과 Lease 저장

발생 시각과 발행 완료 시각 저장
```

```sql
CREATE TABLE outbox_event (
    event_id UUID PRIMARY KEY,
 
    request_id UUID,
 
    deduplication_key VARCHAR(200) NOT NULL UNIQUE,
 
    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
 
    event_type VARCHAR(100) NOT NULL,
    schema_version INT NOT NULL DEFAULT 1,
    aggregate_version BIGINT NOT NULL,
 
    topic VARCHAR(200) NOT NULL,
    partition_key VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,
 
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
 
    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
 
    claim_token UUID,
    lease_until TIMESTAMPTZ,
 
    last_error VARCHAR(1000),
 
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,
 
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
 
    CONSTRAINT chk_outbox_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'PUBLISHED')),
 
    CONSTRAINT chk_outbox_schema_version CHECK (schema_version >= 1),
    CONSTRAINT chk_outbox_aggregate_version CHECK (aggregate_version >= 1),
    CONSTRAINT chk_outbox_attempt_count CHECK (attempt_count >= 0)
);
 
CREATE INDEX idx_outbox_pending
ON outbox_event (next_attempt_at, created_at, event_id)
WHERE status = 'PENDING';
 
CREATE INDEX idx_outbox_expired_processing
ON outbox_event (lease_until, event_id)
WHERE status = 'PROCESSING';
```

### **9. 일반 INSERT에서 `deduplication_key` UNIQUE 위반이 발생한 뒤 기존 행을 확인하려면 어떤 트랜잭션 처리가 필요한지 설명한다**

다음 선택지를 비교한다.

```
전체 Rollback 후 새 트랜잭션에서 조회

Savepoint 사용

ON CONFLICT DO NOTHING RETURNING 후
기존 행 조회·동일성 비교
```

```
전체 Rollback 후 새 트랜잭션에서 조회
→ UNIQUE 위반은 "정상 경로에서는 발생하면 안 되는" 설계 가정 위반 신호이므로, 조용히 넘기지 않고 트랜잭션 전체를 Rollback한 뒤 알람을 발생시키고 별도 트랜잭션에서 원인을 조사한다. 가장 안전하지만 매 충돌마다 전체 재시도 비용이 든다.
 
Savepoint 사용
→ INSERT 직전에 Savepoint를 찍고 위반 시 Savepoint까지만 되돌려 트랜잭션의 나머지 부분(request ISSUED 등)은 유지한 채 계속 진행할 수 있다. 다만 "발급은 확정됐는데 Outbox 저장 실패는 무시"하는 구조가 될 위험이 있다.
 
ON CONFLICT DO NOTHING RETURNING 후 기존 행 조회·동일성 비교
→ 멱등 INSERT를 원한다면 충돌 후 기존 행의 request_id, aggregate_id, event_type, schema_version, aggregate_version, payload가 모두 같은지 확인하고, 같으면 기존 행을 재사용해 정상 흐름으로 진행할 수 있다.
다만 이 방식은 서로 다른 원인의 충돌(진짜 버그)을 조용히 숨길 위험이 있으므로, 비교 로직과 불일치 시 알람 로직을 반드시 함께 구현해야 한다.
```

## **과제 3. 발급 결과와 Outbox를 하나의 트랜잭션으로 저장하기**

쿠폰 발급 성공 시 다음 작업을 하나의 DB 트랜잭션으로 수행한다.

```
1. 요청 처리 권한 획득

2. 수량 확보

3. coupon_issue 저장

4. request ISSUED 확정

5. CouponIssued Outbox 저장
```

### **1. 전체 SQL 트랜잭션을 완성한다**

```sql
BEGIN;
 
-- 1. PENDING 요청에 대한 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows는 반드시 1행이어야 한다. 0이면 이미 처리된(ISSUED/FAILED) 요청이거나
-- 잘못된 요청이므로 발급 로직을 새로 실행하지 않는다.
 
-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :couponEventId
  AND issued_count < total_quantity;
-- affected rows가 0이면: 수량 소진(SOLD_OUT) 또는 대상 이벤트 행 자체가
-- 없거나 이미 종료/비활성화된 경우일 수 있다. 원인을 구분해서 FAILED 처리해야 한다.
 
-- 3. coupon_issue 저장 후 id와 issued_at 획득
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:couponEventId, :userId, 'ISSUED', CURRENT_TIMESTAMP)
RETURNING id, issued_at;
 
-- 4. request를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = :issuedAt,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';
 
-- 5. 동일한 트랜잭션에서 CouponIssued Outbox 저장 (ON CONFLICT 사용하지 않음)
INSERT INTO outbox_event (
    event_id, request_id, deduplication_key,
    aggregate_type, aggregate_id, event_type,
    schema_version, aggregate_version,
    topic, partition_key, payload, occurred_at
) VALUES (
    :eventMessageId, :requestId, :deduplicationKey,
    'COUPON_ISSUE', CAST(:couponIssueId AS VARCHAR), 'COUPON_ISSUED',
    1, 1,
    'coupon.issued', CAST(:couponIssueId AS VARCHAR),
    CAST(:payload AS JSONB), :issuedAt
);
 
COMMIT;
```

### **2. 각 단계에서 확인해야 하는 영향받은 행 수를 작성한다**

| 작업 | 성공 경로의 영향받은 행 수 | 예상과 다를 때 처리 |
| --- | --- | --- |
| PENDING → PROCESSING | 1행 | 0행이면 즉시 실패로 단정하지 않고 기존 request 상태를 재확인 |
| issued_count 조건부 증가 | 1행 | 0행이면 SOLD_OUT 또는 대상 이벤트 부재/비활성 -> request FAILED로 확정, 트랜잭션은 Commit |
| coupon_issue INSERT | 1행 | UNIQUE(event_id, user_id) 위반 시 전체 Rollback → DUPLICATE_USER 처리 |
| PROCESSING → ISSUED | 1행 | 0행이면 상태 불일치이므로 전체 트랜잭션 Rollback |
| outbox_event INSERT | 1행 | UNIQUE 위반 등 실패 시 전체 Rollback + 알람 |

### **3. Outbox INSERT가 실패한 경우 최종 상태를 작성한다**

장애 직전 상황은 다음과 같다.

```
issued_count 증가 성공

coupon_issue INSERT 성공

request ISSUED 변경 성공

outbox_event INSERT 실패
```

```
트랜잭션 결과: 전체 Rollback
 
coupon_event.issued_count: 증가 취소 (원래 값으로 되돌아감)
 
coupon_issue: 저장 취소 (행 자체가 존재하지 않음)
 
coupon_issue_request: ISSUED로의 변경 취소, PENDING 상태로 되돌아감
(재전달 시 처음부터 다시 처리 가능)
 
outbox_event: 저장되지 않음 (행 없음)
```

### **4. Outbox 저장 실패를 무시하고 발급 결과만 Commit하면 안 되는 이유를 설명한다**

```
만약 Outbox INSERT 실패를 무시하고 나머지만 Commit한다면, "DB에는 쿠폰이 발급되었는데 발행해야 할 이벤트 기록은 어디에도 남지 않는"상태가 발생한다.

이는 정확히 Dual Write문제를 그대로 재현하는 것이며, Outbox Pattern이 애초에 없애려던 상태다.

메모리에도, DB에도 "이 발급 건에 대해 이벤트를 발행해야 한다"는 기록이 없으므로 어떤 Publisher도 이 이벤트를 발행할 수 없고, 영구적으로 후속 서비스에 통지되지 않는 쿠폰 발급 건이 생긴다.

따라서 발급 결과와 Outbox 저장은 반드시 all-or-nothing으로 묶여야 한다.
```

### **5. 원본 메시지가 재전달되었지만 request가 이미 ISSUED인 경우의 처리를 작성한다**

```
issued_count를 다시 증가시키는가? 아니오. 이미 확정된 수량 증가를 다시 하면 안 되므로 issued_count UPDATE를 실행하지 않는다.
 
coupon_issue를 다시 생성하는가? 아니오. 이미 존재하는 발급 기록을 중복 생성하면 UNIQUE(event_id, user_id) 위반이 발생하므로 애초에 시도하지 않는다.
 
Outbox를 다시 INSERT하는가? 아니오. deduplication_key UNIQUE 제약으로도 막히지만, 그 이전에 request = ISSUED 확인 단계에서 새 Outbox 생성 로직 자체를 건너뛴다.
 
Consumer 처리는 성공으로 종료할 수 있는가? 예. request = ISSUED를 확인한 즉시 "이미 완료된 요청의 재전달"로 판단하고 새로운 발급/Outbox 없이 정상 처리(성공)로 종료한 뒤 원본 Kafka Offset을 Commit한다.
```

### **6. 발급 DB Commit 후 원본 Kafka Offset Commit 전에 Consumer가 종료되는 상황을 분석한다**

```
DB 상태: request = ISSUED, coupon_issue 존재, 모두 Commit 완료
 
Outbox 상태: PENDING 
 
Kafka 원본 메시지: Offset이 아직 Commit되지 않았으므로, Consumer Group 리밸런싱 또는 재시작 시 같은 메시지가 다시 전달될 수 있음
 
재시작 후 필요한 멱등성 기준: requestId를 기준으로 coupon_issue_request의 현재 상태를 조회. status = ISSUED이면 새로운 발급/Outbox 생성 없이 정상 처리로 종료하고 원본 Offset만 Commit한다. Outbox 자체는 이미 Commit되어 있으므로 Publisher가 별도로 발행을 이어서 처리한다.
```

### **7. 원본 Consumer의 Offset Commit 설정에서 확인해야 할 항목을 작성한다**

다음을 반드시 포함한다.

```
enable.auto.commit

AckMode

Listener 예외 처리

Error Handler가 실패를 정상 처리로 바꾸는지 여부
```

```
enable.auto.commit: false로 설정해야 한다. 자동 커밋을 사용하면 DB 트랜잭션 Commit 여부와 무관하게 Kafka가 임의 주기로 Offset을 앞당겨 커밋할 수 있어 메시지 유실 위험이 생긴다.
 
AckMode: Spring Kafka에서는 MANUAL 또는 MANUAL_IMMEDIATE로 설정해 발급 DB 트랜잭션이 Commit된 이후에만 명시적으로 Acknowledgment.acknowledge()를 호출하도록 한다.
 
Listener 예외 처리: 발급 트랜잭션 중 예외(일시적 DB 오류 등)가 발생하면 Listener가 예외를 삼키지 않고 다시 던져(rethrow) 컨테이너가 재시도/재처리 정책을 타도록 해야 한다. 예외를 삼키면 실패했는데도 Offset이 커밋되어
버릴 수 있다.
 
Error Handler가 실패를 정상 처리로 바꾸는지 여부: CommonErrorHandler/DefaultErrorHandler 설정을 확인해 특정 예외를 "처리 성공"으로 간주하고 Offset을 넘겨버리지는 않는지 반드시 점검해야 한다. 특히 재시도 횟수 초과 시 DLQ로 보내는 정책이 있다면, 그 시점에도 원본 메시지가 유실 없이 별도 채널로 보존되는지 확인해야 한다.
```

## **과제 4. Polling Publisher의 Claim, Lease, Claim Token 설계하기**

여러 Publisher 인스턴스가 같은 Outbox 테이블을 Polling한다고 가정한다.

### **1. 단순 SELECT 후 UPDATE 방식의 Race Condition을 작성한다**

```
Publisher A                              Publisher B
------------------------------------------------------------------
SELECT ... WHERE status='PENDING'
  → event_id = evt-001 획득
                                          SELECT ... WHERE status='PENDING'
                                            → 아직 A가 UPDATE 안 했으므로
                                              동일하게 event_id = evt-001 획득
UPDATE ... SET status='PROCESSING'
  WHERE event_id = evt-001
  → 성공
                                          UPDATE ... SET status='PROCESSING'
                                            WHERE event_id = evt-001
                                            → 이미 PROCESSING이지만 WHERE 조건에
                                              상태 체크가 없다면 이 UPDATE도 성공
Kafka 발행                                Kafka 발행
  → 중복 발행 발생
```

### **2. `FOR UPDATE SKIP LOCKED`를 이용한 Claim SQL을 완성한다**

다음 요구사항을 만족해야 한다.

```
status = PENDING

next_attempt_at이 현재 시각 이하

오래된 이벤트부터 조회

Batch 크기 제한

잠긴 행은 대기하지 않고 건너뜀

PROCESSING 상태로 변경

claim_token과 lease_until 저장

attempt_count 증가

Claim한 행 반환
```

```sql
BEGIN;
 
WITH candidates AS (
    SELECT event_id
    FROM outbox_event
    WHERE status = 'PENDING'
      AND next_attempt_at <= CURRENT_TIMESTAMP
    ORDER BY next_attempt_at, created_at, event_id
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event AS outbox
SET status = 'PROCESSING',
    claim_token = :claimToken,
    lease_until = CURRENT_TIMESTAMP + (:leaseSeconds * INTERVAL '1 second'),
    attempt_count = attempt_count + 1,
    updated_at = CURRENT_TIMESTAMP
FROM candidates
WHERE outbox.event_id = candidates.event_id
RETURNING outbox.*;
 
COMMIT;
```

### **3. Claim 트랜잭션을 짧게 Commit한 뒤 Kafka를 호출해야 하는 이유를 설명한다**

DB Row Lock을 잡은 채 Kafka ACK를 기다릴 때의 문제를 최소 세 가지 작성한다.

```
1. DB Connection Pool 고갈: Kfaka ACK를 기다리는 동안 커넥션을 계속 점유하면 다른 요청/Publisher가 사용할 커넥션이 부족해져 전체 시스템 처리량이 급증한다.

2. Row Lock 장시간 유지: Claim된 행에 대한 Lock을 오래 들고 있으면 다른 Publisher 인스턴스의 SKIP LOCKED 대상 후보가 줄어들거나, 관련 인덱스에 대한 경합이 늘어나 전체 Claim 처리량이 저하된다.

3. 트랜잭션 Timeout: Kafka 네트워크 지연이나 Broker 장애가 길어지면 DB 트랜잭션 자체가 Timeout에 걸려 예기치 않은 Rollback이 발생하고, Publisher간 대기가 연쇄적으로 늘어나는 병목이 생긴다.
```

### **4. 단일 Publisher만 있어도 Lease 또는 stale PROCESSING 복구가 필요한 이유를 설명한다**

```
Claim 트랜잭션이 Commit된 직후, 즉 행이 이미 `PROCESSING`으로 확정된 뒤에도 Kafka 발행 전에 프로세스가 종료될 수 있다. 

이 경우 인스턴스가 하나뿐이더라도 그 하나가 없어지면 `PROCESSING`으로 멈춘 행을 되돌릴 주체가 사라진다. 

Lease가 없다면 이 행은 영원히 발행되지 않고 방치되므로, 인스턴스 수와 무관하게 만료 시간 기반의 자기 로직이 반드시 필요하다.
```

### **5. 만료된 PROCESSING 행을 PENDING으로 복구하는 SQL을 작성한다**

```sql
UPDATE outbox_event
SET status = 'PENDING',
    claim_token = NULL,
    lease_until = NULL,
    next_attempt_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE status = 'PROCESSING'
  AND lease_until <= CURRENT_TIMESTAMP;
```

### **6. 다음 경쟁 상황에서 Claim Token이 없을 때 발생하는 문제를 설명한다**

```
Publisher A
→ token-A로 Claim
→ 처리 지연
→ Lease 만료

Publisher B
→ 만료 행 회수
→ token-B로 Claim

Publisher A
→ 뒤늦게 성공 또는 실패 상태 UPDATE
```

```
Claim Token이 없다면 Publisher A는 자신이 여전히 처리 권한을 가지고 있다고 착각한 채, 뒤늦게 받은 Kafka 결과(성공 또는 실패)를 조건 없이 DB에 반영하려 한다. 

그런데 이미 Lease가 만료되어 Publisher B가 그 행을 새로 Claim해 처리하고 있거나 이미 처리를 끝낸 상태일 수 있다. 

이때 Publisher A의 뒤늦은 UPDATE가 `event_id`만으로 실행되면, Publisher B가 만든 최신 상태(`PROCESSING`, 새 `lease_until`, 혹은 이미 `PUBLISHED`)를 A가 덮어써버려 상태가 꼬인다. 

예를 들어 B가 성공적으로 `PUBLISHED`로 만든 직후 A가 `PENDING`으로 되돌려버리면 불필요한 재발행이 일어나고, 최악의 경우 두 Publisher가 서로의 상태를 번갈아 덮어쓰는 경합이 반복될 수 있다.
```

### **7. 성공과 실패 UPDATE에 들어가야 하는 공통 WHERE 조건을 작성한다**

```sql
WHERE event_id = :eventId
  AND status = 'PROCESSING'
  AND claim_token = :claimToken
```

### **8. 동기 순차 발행 모델에서 Lease 시간을 계산할 때 고려할 항목을 작성한다**

```
Lease 시간
>
batchSize × 건당 최대 대기 시간(Kafka send timeout)
+
여유 시간(Buffer, 네트워크 지연·GC Pause 등을 감안한 마진)
```

### **4. Timeout을 받았다고 Kafka에 Record가 없다고 단정할 수 없는 이유를 설명한다**

다음 두 상황을 구분한다.

```
상황 A:
Broker에 저장되지 못하고 Timeout

상황 B:
Broker에는 저장되었지만
Publisher가 ACK를 확인하지 못하고 Timeout
```

```
상황 A: Broker에 저장되지 못하고 Timeout
→ 실제로 Kafka에 아무것도 남지 않았을 수 있음
 
상황 B: Broker에는 저장되었지만 ACK 응답을 Publisher가 받지 못하고 Timeout
→ 네트워크 왕복 중 응답 패킷만 유실된 경우로, Kafka에는 이미 Record가
  존재할 수 있음

Publisher는 Timeout 예외만으로는 A와 B를 구분할 방법이 없다. 따라서 두 상황을 모두 "미확정"으로 간주하고 안전한 쪽을 선택해야 하며, 이는 곧 B의 경우 중복 발행 가능성을 감수한다는 뜻이다.
```

### **5. Timeout 이후 재시도 정책을 작성한다**

```
Outbox 상태: 미완료로 유지 → 재시도 대상으로 남김 (PUBLISHED로 바꾸지 않음)
 
재시도 여부: 수행함 (Exponential Backoff + Jitter 적용)
 
Kafka 중복 가능성: 있음 (상황 B였다면 같은 이벤트가 Kafka에 두 번 이상 남을 수 있음)
 
Consumer에게 필요한 방어: eventMessageId 기준의 processed_event 멱등 처리
```

### **6. Exponential Backoff와 Jitter를 사용하는 이유를 설명한다**

```
Exponential Backoff:
연속 실패 시 재시도 간격을 지수적으로 늘려 Broker나 네트워크에 장애가 있는 동안 불필요한 재시도 폭주로 상황을 악화시키지 않고, 회복할 시간을 벌어준다.

Jitter:
모든 Publisher 인스턴스가 정확히 동일한 시각에 재시도를 시도하면 그 순간에 부하가 몰려(Thundering Herd) 오히려 Broker나 DB에 순간적인 과부하를 유발할 수 있다. 작은 무작위 지연을 더해 재시도 시점을 분산시킨다.
```

### **7. Producer Idempotence가 해결하는 중복과 해결하지 못하는 중복을 구분한다**

| 중복 발생 원인 | Producer Idempotence로 방어 가능한가? | 이유 |
| --- | --- | --- |
| Producer 내부 네트워크 재시도 | 가능 | Producer가 내부적으로 재전송할 때 Sequence Number로 같은 배치의 중복 저장을 Broker가 걸러낸다 |
| Kafka 발행 성공 후 PUBLISHED 변경 전 프로세스 종료 | 불가능 | 이는 애플리케이션 레벨에서 발생하는 논리적 중복이며, 각각 별도의 Producer 세션/요청으로 인식되어 Idempotence 범위 밖 |
| 운영자가 같은 Outbox를 다시 PENDING으로 변경 | 불가능 | 사람이 의도적으로 재발행을 트리거한 것으로, Producer 입장에서는 완전히 새로운 정상 발행 요청과 구분할 수 없음 |

### **8. 비동기 발행으로 확장할 때 `whenComplete` 안에서 DB 작업을 직접 수행하는 것이 위험한 이유를 설명한다**

콜백이 Producer I/O 스레드에서 실행될 수 있다는 점과 전용 Executor의 필요성을 포함한다.

```
`whenComplete`/`whenCompleteAsync`의 콜백은 Future를 완료시킨 스레드, 즉 Kafka Producer의 내부 Sender 스레드에서 실행될 수 있다. 

이 스레드에서 DB Connection Pool 획득을 기다리거나 트랜잭션 Commit 같은 블로킹 I/O를 수행하면, Sender 스레드 자체가 블로킹되어 해당 Producer의 모든 전송이 함께 지연된다. 

부하 상황에서는 "Sender 블로킹 → 발행 지연 증가 → Lease 만료 → 다른 Publisher가 회수 → 중복 발행 증가 → 적체 심화"로 이어지는 연쇄 장애가 발생할 수 있다. 

따라서 반드시 `whenCompleteAsync`처럼 전용 Executor를 지정해 Kafka Producer 내부 스레드와 DB 작업 스레드를 분리해야 한다.
```

```
Publisher A가 늦게 실패 UPDATE:
동일하게 claim_token='token-A' 조건이 더 이상 맞지 않으므로 0행 갱신되어 B가 진행 중인 처리를 A가 되돌리지 못함
 
두 UPDATE에서 affected rows가 0이어야 하는 조건:
현재 시점의 claim_token이 A가 가진 token-A와 다르거나(B가 이미 새로 Claim했음), status가 더 이상 PROCESSING이 아닌 경우
```

### **6. Kafka 장애가 30분 동안 지속되는 상황**

```
PENDING 수의 변화: 
Outbox 생성 속도만큼 계속 증가. 재시도 실패한 행들도 next_attempt_at 이후 다시 PENDING으로 쌓임
 
가장 오래된 PENDING 대기 시간: 
30분 이상으로 계속 늘어남 
 
attempt_count: 
Claim될 때마다 증가하므로, Backoff 간격에 따라 여러 차례 증가함 
 
Kafka 복구 후 처리: 
누적된 PENDING/next_attempt_at 도래 행들이 다음 Polling 주기부터 순차적으로 Claim되어 발행됨. 이 시점에는 이미 재시도로 인해 "DB 저장 순서 ≠ 실제 발행 순서"가 크게 벌어져 있을 수 있음
 
운영 알람: 
PENDING 이벤트 수 급증, 가장 오래된 PENDING 대기 시간 임계치 초과, attempt_count 임계치 초과 등을 기준으로 즉시 알람 발생
```

```
발급 DB Commit 성공 후 CouponIssued 발행 실패:
```

결과 이벤트 발행 실패를 이유로 쿠폰을 다시 발급하면 안 되는 이유도 작성한다.

```
발급 DB 트랜잭션 실패: 
coupon.issue.requested 원본 메시지를 재처리 대상으로 남긴다. 아직 쿠폰이 발급되지 않았으므로 처음부터 다시 시도하는 것이 맞다.
 
발급 DB Commit 성공 후 CouponIssued 발행 실패: 
쿠폰은 이미 정상적으로 발급되어 확정된 상태이므로, 재시도 대상은 오직 "Outbox 이벤트 재발행"뿐이다.

결과 이벤트 발행 실패를 이유로 이미 발급된 쿠폰을 취소하거나 다시 발급하면 안 되는 이유는, 발급 자체는 이미 별도 DB 트랜잭션에서 확정된 사실이기 때문이다.

이벤트 발행은 어디까지나 "이미 일어난 사실을 후속 서비스에 알리는" 부수 작업일 뿐 발급 로직의 일부가 아니다. 

발행 실패를 이유로 재발급하면 동일 사용자에게 쿠폰이 중복 지급되고, 취소하면 정당하게 발급받은 쿠폰을 임의로 빼앗는 오류가 발생한다. 

Outbox와 Publisher의 역할은 "이미 확정된 이벤트를 전달"하는 것으로 한정되며 발급 수량이나 발급 기록을 다시 만들지 않는다.
```

## **과제 7. Consumer 멱등 처리 설계하기**

같은 논리 이벤트가 다음처럼 두 번 Kafka에 저장되었다고 가정한다.

```
Partition 1 / Offset 100 / eventMessageId = evt-001

Partition 1 / Offset 101 / eventMessageId = evt-001
```

### **1. Kafka Offset을 Consumer 멱등성 Key로 사용하면 안 되는 이유를 설명한다**

```
같은 논리 이벤트라도 Publisher가 재시도하면 서로 다른 Partition/Offset에 여러 번 저장될 수 있다. 

Offset은 물리적 저장 위치일 뿐 비즈니스 이벤트의 정체성과는 무관하다. 

Offset을 멱등 키로 사용하면 같은 논리 이벤트가 다른 Offset으로 재전달될 때마다 "새로운 이벤트"로 오인해 중복 반영이 그대로 발생한다. 

따라서 이벤트 자체의 고유 식별자인 `eventMessageId`를 멱등 키로 사용해야 한다.
```

### **2. processed_event 테이블 DDL을 작성한다**

다음 요구사항을 만족해야 한다.

```
논리 Subscriber 식별자 저장

eventMessageId 저장

처리 완료 시각 저장

같은 Subscriber가 같은 이벤트를
두 번 처리하지 못하도록 Primary Key 구성
```

```sql
CREATE TABLE processed_event (
    subscriber_id VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
 
    PRIMARY KEY (subscriber_id, event_id)
);
```

### **3. `subscriber_id`에 프로세스 인스턴스 ID를 사용하면 안 되는 이유를 설명한다**

다음 중 적절한 값을 선택하고 이유를 작성한다.

```
pod-7f8c9d

server-10.0.0.12

mypage-coupon-projection
```

```
pod-7f8c9d       
 → 부적절. Pod는 재배포/스케일링/재시작마다 바뀌는 일시적식별자이므로, 이 값을 기준으로 멱등성을 관리하면 재배포 이후 이전 Pod가 처리했던 이벤트를 새 Pod가 "처음 보는 이벤트"로 착각해 중복 반영할 위험이 있다.
 
server-10.0.0.12  
→ 마찬가지로 부적절. IP는 인프라 환경에 따라 재할당되거나 여러 인스턴스가 로드밸런싱되며 바뀔 수 있는 물리적 위치 정보일 뿐, 논리적 처리 주체를 나타내지 않는다.
 
mypage-coupon-projection
```

### **6. `processed_event`만으로 외부 SMS가 정확히 한 번 전송된다고 보장할 수 없는 이유를 설명한다**

```
그런데 SMS 발송 같은 외부 API 호출은 이 로컬 DB 트랜잭션에 포함될 수 없는 별도의 네트워크 호출이다.

```

```
3. notificationId 기반의 자체 발송 이력 테이블을 두어, 발송 시도 전에 이미 성공적으로 발송된 이력이 있는지 확인한 뒤에만 실제 호출을 수행한다.
```

```
Kafka Topic 보관 기간

Consumer Offset 되감기

Outbox 지연 재발행

운영자 수동 재발행
```

```

운영자 수동 재발행:
```

## **과제 8. Partition Key와 이벤트 순서 문제 분석하기**

이번 과제에서는 다음 값을 사용한다고 가정한다.

```
aggregateType = COUPON_ISSUE

aggregateId = couponIssueId

partitionKey = couponIssueId
```

### **1. 같은 Partition Key를 사용하는 이유를 작성한다**

```
1. 같은 Aggregate의 이벤트를 한 Partition에 모아 Consumer의 병렬 처리 단위를 명확히 하기 위해서다.

2. 특정 Partition으로 부하가 쏠리지 않도록 여러 couponIssueId를 넓게 분산시키기 위해서다.

3. 향후 순서 보장이 필요해질 때 기준이 될 수 있는 단위를 미리 정해두기 위해서다.
```

### **2. 같은 Key를 사용한다고 비즈니스 발생 순서까지 보장되는 것은 아닌 이유를 설명한다**

다음을 반드시 포함한다.

```
여러 Publisher 인스턴스

SKIP LOCKED

발행 실패와 Backoff

Producer 설정과 재시도
```

```
Kafka는 같은 Partition Key를 가진 Record를 같은 Partition에 저장하지만, Partition안의 저장 순서는 "Producer가 send()를 호출한 순서"로 결정될 뿐 "DB에 저장된 순서"가 아니다.

Polling Outbox Publisher 구조에서는 다음 요소들 때문에 이 두 순서가 어긋날 수 있다.
여러 Publisher 인스턴스: 
서로 다른 인스턴스가 서로 다른 속도로 Claim하고 발행하기 때문에 먼저 저장된 이벤트가 나중에 발행될 수 있다.
 
SKIP LOCKED: 
잠긴 행을 건너뛰고 다음 행을 가져오는 방식 자체가 순서를 포기하는 장치다. ORDER BY가 있어도 실제로는 순서대로 Claim되지 않을 수 있다.
 
발행 실패와 Backoff: 
먼저 저장된 이벤트가 발행에 실패하면 next_attempt_at이 뒤로 밀리는 동안, 나중에 저장된 이벤트가 먼저 성공적으로 발행될 수 있다.
 
Producer 설정과 재시도: 
Producer 내부 재시도, 네트워크 지연 등도 실제 Broker 저장 순서에 영향을 줄 수 있다.
```

### **3. 다음 순서 역전 시나리오를 완성한다**

```
DB 발생 순서
CouponIssued (aggregateVersion = 1)
CouponCancelled (aggregateVersion = 2)
 
Publisher 처리
Publisher A: outbox 1(CouponIssued) Claim → Kafka 발행 실패
             → PENDING, next_attempt_at = +4초
Publisher B: outbox 2(CouponCancelled) Claim → 발행 성공
 
Kafka 저장 순서:
Offset 200: CouponCancelled
Offset 201: CouponIssued
```

### **4. `occurredAt`만으로 이벤트 순서를 판단하면 안 되는 이유를 두 가지 이상 작성한다**

```
1. 서로 다른 이벤트가 우연히 같은 Timestamp를 가질 수 있다.
 
2. 여러 서버/DB의 시계가 완전히 일치하지 않을 수 있어, 실제로는 나중에 발생한 이벤트가 더 이른 occurredAt을 가질 수도 있다.
 
3. 조회 대상 행이 아예 없는 경우와, 이미 더 최신 이벤트가 반영되어 있어 갱신을 생략해야 하는 경우를 occurredAt 비교만으로는 명확히 구분하기 어렵다.
```

## **과제 9. Outbox 운영 지표와 보관 정책 설계하기**

### **1. 다음 운영 지표의 의미와 장애 판단 기준을 작성한다**

| 지표 | 무엇을 의미하는가? | 어떤 상태가 장애 신호인가? |
| --- | --- | --- |
| PENDING 이벤트 수 | 아직 발행되지 않고 대기 중인 이벤트 수 | 지속적으로 증가하는 추세를 보일 때 (생성 속도 > 발행 속도) |
| 가장 오래된 PENDING 대기 시간 | 가장 오래 기다린 이벤트의 지연 시간 | SLA로 정한 임계치(예: 수 분 이상)를 넘길 때 |
| PROCESSING 이벤트 수 | 현재 어떤 Publisher가 처리 권한을 쥐고 있는 이벤트 수 | 비정상적으로 계속 쌓이거나 Batch 크기 대비 과도하게 클 때 |
| 만료된 PROCESSING 수 | Lease가 지났는데 아직 회수되지 않은 행 수 | 0보다 커서는 안 되며, 지속 발생 시 Publisher 장애/느려짐 신호 |
| attempt_count | 해당 이벤트가 Claim(발행 시도)된 횟수 | 특정 이벤트가 반복적으로 높은 값을 가질 때 (Kafka 또는 Payload 자체 문제 의심) |
| Outbox 생성 처리량 | 시간당/초당 새로 INSERT되는 Outbox 행 수 | 급격한 증가/감소 자체가 상류 시스템 이상을 나타낼 수 있음 |
| Kafka 발행 처리량 | 시간당/초당 PUBLISHED로 전환되는 행 수 | 생성 처리량 대비 지속적으로 낮을 때 |
| DB 발생부터 Kafka ACK까지의 시간 | occurred_at부터 published_at까지의 지연(End-to-End Latency) | 목표 SLA를 초과해 지속적으로 증가할 때 |

### **2. Outbox 생성 속도가 초당 2,000건이고 Publisher 처리 속도가 초당 1,500건인 상황을 분석한다**

```
1분 후 예상 적체 증가량: 
(2,000 - 1,500) × 60초 = 30,000건
 
10분 후 예상 적체 증가량: 
(2,000 - 1,500) × 600초 = 300,000건
 
가장 먼저 확인할 지표: 
PENDING 이벤트 수의 증가 추세와 가장 오래된 PENDING 대기 시간
 
가능한 대응: 
Publisher 인스턴스 수 또는 Batch Size 확장, Kafka/DB 병목 여부 점검, 필요 시 일시적으로 Polling 주기 단축, 근본 원인 해결 전까지는 적체가 있어도 Consumer 멱등 처리가 되어 있으므로 데이터 정합성 자체는 깨지지
않는다는 점을 확인하고 순차적으로 대응
```

### **3. 즉시 알람이 필요한 설계 가정 위반을 세 가지 이상 작성한다**

```
1. deduplication_key UNIQUE 위반 발생 
 
2. request = PROCESSING 상태가 다른 세션에서 관측됨
 
3. Lease가 만료된 PROCESSING 행이 반복적으로 발생
 
4. SOLD_OUT 또는 DUPLICATE_USER 확정이 비정상적으로 반복 발생
```

### **4. PUBLISHED 행만 정리해야 하는 이유를 설명한다**

```
PENDING을 삭제하면: 
아직 한 번도 Kafka에 발행되지 않은 이벤트를 영구히 잃어버리게 되어, 해당 발급 건에 대한 후속 서비스 통지가 영원히 누락된다.
 
PROCESSING을 삭제하면: 
지금 이 순간 어떤 Publisher가 실제로 처리 중이거나 Lease 복구 대기 중인 행을 지워버려, 정상적으로 진행 중이던 발행 흐름이 끊기고 추적 불가능한 상태가 된다.
 
PUBLISHED를 보관하는 목적: 
이미 Kafka ACK까지 확인되어 발행 책임이 Kafka/Consumer 쪽으로 넘어간 상태이므로, 일정 기간은 발행 이력 확인과 장애 조사(감사, 재현) 용도로만 보관한 뒤 안전하게 정리할 수 있다.
```

### **5. PUBLISHED 행을 한 번에 대량 삭제하면 안 되는 이유를 설명한다**

다음 항목을 포함한다.

```
긴 트랜잭션

DB 부하

Lock

Table Bloat
```

```
긴 트랜잭션: 
대량 DELETE는 하나의 트랜잭션 안에서 오래 실행되며, 그 동안 관련 인덱스와 테이블에 대한 다른 작업(INSERT, Claim 쿼리 등)과 경합한다.
 
DB 부하: 
한 번에 수십만~수백만 행을 지우면 WAL 생성량과 I/O 부하가 급증해 운영 중인 서비스의 다른 쿼리 성능에 영향을 줄 수 있다.
 
Lock: 
대량 삭제 중 관련 행/인덱스에 대한 Lock이 오래 유지되면 Claim 쿼리나 INSERT가 지연되거나 대기하게 된다.
 
Table Bloat: 
PostgreSQL은 삭제된 행을 즉시 물리적으로 회수하지 않고 dead tuple로 남기므로, 대량 삭제 후 VACUUM 부하가 커지고 테이블/인덱스 크기가 예상보다 크게 유지될 수 있다.
```

### **6. 작은 Batch로 정리하는 운영 흐름을 작성한다**

```
1. published_at < :cutoff 조건으로 최대 N건(예: 1,000건)만 DELETE
2. Commit
3. 짧게 대기하여 DB 부하를 분산
4. 삭제 대상이 남아있으면 1번부터 반복
5. 스케줄러로 주기적으로 실행하며, 트래픽이 낮은 시간대에 더 큰 Batch로 실행하도록 조정 가능
```

### **7. 다음 세 보관 기간의 목적을 비교한다**

| 보관 대상 | 목적 | 너무 짧을 때 발생하는 문제 |
| --- | --- | --- |
| Outbox PUBLISHED 행 | 발행 이력 확인과 장애 조사 | 발행 완료 여부/시점을 추적할 수 없어 사후 원인 분석이 어려워짐 |
| Kafka Topic Record | Consumer가 장애 후 재처리할 수 있는 범위 확보 | Consumer가 오래 다운되었거나 Offset을 되감아야 할 때 이미 삭제된 메시지를 다시 소비할 수 없어 영구 유실 발생 |
| Consumer processed_event | 중복 방어(멱등성) 가능 범위 확보 | Kafka Topic 보관 기간보다 짧으면, 재전달된 오래된 이벤트를 "새 이벤트"로 오인해 중복 반영이 발생 |

### **8. `last_error`에 전체 Stack Trace나 민감 정보를 저장하면 안 되는 이유를 설명한다**

```
Outbox 테이블은 애플리케이션 다수가 조회·검색할 수 있는 운영 데이터이며, DB 백업이나 조회 권한을 가진 사람이 폭넓게 접근할 수 있다. 

여기에 Stack Trace 전체나 민감 정보를 그대로 저장하면 정보 노출 위험이 커지고, 각 행마다 대용량 텍스트가 쌓여 테이블 크기와 인덱스 성능에도 부담을 준다. 

따라서 DB에는 검색 가능한 짧은 오류 분류와 요약 메시지만 저장하고, 상세 Stack Trace와 진단 정보는 별도의 로그/트레이싱 시스템에 남겨 필요할 때 상관 ID로 연결해 조회하는 것이 안전하다.
```

## **과제 10. 잘못된 Outbox 구현 리뷰하기**

다음은 의도적으로 문제가 포함된 구현이다.

```java
@Transactional
public void issueCoupon(IssueMessage message) {
    CouponIssue issue = issueRepository.save(
        CouponIssue.from(message)
    );

    kafkaTemplate.send(
        "coupon.issued",
        issue.getId().toString(),
        CouponIssuedEvent.from(message, issue)
    );
}

@Scheduled(fixedDelay = 1000)
@Transactional
public void publishOutbox() {
    List<OutboxEvent> events =
        outboxRepository.findTop100ByStatus("PENDING");

    for (OutboxEvent event : events) {
        kafkaTemplate.send(
            event.getTopic(),
            event.getPartitionKey(),
            createPayloadFromCurrentCouponIssue(event)
        );

        event.markPublished();
    }
}

public void recoverProcessing() {
    outboxRepository.updateAllProcessingToPending();
}

public void onResult(CouponIssuedEvent event) {
    userCouponViewRepository.save(
        UserCouponView.from(event)
    );

    processedEventRepository.save(
        new ProcessedEvent(
            event.getKafkaPartition(),
            event.getKafkaOffset()
        )
    );
}
```

### **1. 위 코드에서 문제를 최소 10개 찾는다**

각 문제마다 다음 형식으로 작성한다.

```
문제 1
문제 위치: issueCoupon() 안의 kafkaTemplate.send() 직접 호출
문제 내용: 발급 DB 트랜잭션 내부에서 Kafka를 직접 호출하고 있어
Dual Write 문제(과제 1)가 그대로 재현된다.
발생 가능한 장애: DB Commit 전/후로 Kafka 발행이 어긋나 이벤트 유실 또는
발급 없는 이벤트 존재 상태가 발생할 수 있다.
수정 방법: Kafka 호출을 제거하고, 같은 트랜잭션에 outbox_event INSERT를
추가한다.
 
문제 2
문제 위치: issueCoupon() 전체
문제 내용: Outbox 저장 자체가 아예 없다. issueRepository.save()만 하고
바로 Kafka를 호출한다.
발생 가능한 장애: DB Commit과 발행 사이에 발행 대상 기록이 전혀 남지 않아
장애 시 복구 불가능한 이벤트 유실이 발생한다.
수정 방법: 비즈니스 데이터 저장과 outbox_event INSERT를 하나의 트랜잭션으로
묶는다.
 
문제 3
문제 위치: publishOutbox()의 @Scheduled + @Transactional 메서드 전체
문제 내용: Claim(findTop100ByStatus)과 Kafka 발행, markPublished()가 모두
하나의 긴 DB 트랜잭션 안에서 일어난다. Kafka ACK 대기 중에도 DB 트랜잭션과
Row Lock을 계속 들고 있게 된다.
발생 가능한 장애: DB Connection 고갈, Lock 장기 점유, 트랜잭션 Timeout,
Publisher 간 대기 증가.
수정 방법: Claim 트랜잭션(짧게 Commit) → Kafka 호출(트랜잭션 밖) →
성공/실패 상태 반영 트랜잭션(짧게 Commit)으로 3단계 분리한다.
 
문제 4
문제 위치: publishOutbox()에서 여러 Publisher 동시 실행을 가정한 코드가
없음 (findTop100ByStatus만 사용)
문제 내용: FOR UPDATE SKIP LOCKED 같은 동시성 제어가 없어 여러 인스턴스가
같은 PENDING 행을 동시에 읽고 동시에 발행할 수 있다.
발생 가능한 장애: 동일 이벤트의 불필요한 대량 중복 발행.
수정 방법: SKIP LOCKED 기반 Claim 쿼리와 PROCESSING 상태 전환을 도입한다.
 
문제 5
문제 위치: for 루프 안 kafkaTemplate.send(...) 뒤 바로 event.markPublished()
문제 내용: send()는 비동기 호출인데 결과(ACK)를 확인하지 않고 즉시
PUBLISHED로 표시한다.
발생 가능한 장애: 실제로는 발행이 실패했는데도 DB에는 성공으로 기록되어,
영구적인 이벤트 유실이 발생할 수 있다.
수정 방법: get(timeout) 또는 콜백으로 Broker ACK를 확인한 뒤에만
PUBLISHED로 변경한다.
 
문제 6
문제 위치: publishOutbox() 전체
문제 내용: claim_token 개념이 전혀 없다.
발생 가능한 장애: Lease 만료로 다른 Publisher가 같은 행을 재Claim했을 때,
원래 Publisher가 뒤늦게 상태를 덮어써 최신 처리자의 상태를 훼손할 수 있다.
수정 방법: Claim 시 고유 claim_token을 발급하고, 이후 모든 상태 변경
UPDATE의 WHERE 절에 claim_token 일치 조건을 포함한다.
 
문제 7
문제 위치: recoverProcessing() → outboxRepository.updateAllProcessingToPending()
문제 내용: Lease 만료 여부와 무관하게 PROCESSING인 모든 행을 무조건
PENDING으로 되돌린다.
발생 가능한 장애: 다른 Publisher가 지금 막 정상적으로 처리 중인 행까지
강제로 되돌려버려, 진행 중인 정상 발행과 경합·중복 발행을 유발한다.
수정 방법: WHERE status='PROCESSING' AND lease_until <= now()처럼 만료된
행만 대상으로 복구한다.
 
문제 8
문제 위치: publishOutbox() 안의 createPayloadFromCurrentCouponIssue(event)
문제 내용: 발행 시점에 현재 coupon_issue 테이블을 다시 조회해 Payload를
새로 만든다.
발생 가능한 장애: Outbox INSERT 이후 원본 데이터가 변경/취소되었다면,
실제 발생했던 사실과 다른 최신 상태가 이벤트로 발행되어 이벤트의 의미가
왜곡된다.
수정 방법: Outbox INSERT 시점에 Payload를 완성된 불변 Snapshot으로
저장하고, Publisher는 저장된 Payload를 그대로 전달만 한다.
 
문제 9
문제 위치: onResult()의 new ProcessedEvent(event.getKafkaPartition(),
event.getKafkaOffset())
문제 내용: Kafka Partition+Offset을 멱등성 Key로 사용하고 있다.
발생 가능한 장애: 같은 논리 이벤트가 재발행되면 다른 Offset을 가지므로
멱등 확인이 무력화되어 조회 모델에 중복 반영이 발생한다.
수정 방법: eventMessageId(이벤트 자체의 고유 ID)를 processed_event의
Key로 사용한다.
 
문제 10
문제 위치: onResult() 전체
문제 내용: userCouponViewRepository.save()와 processedEventRepository.save()가
같은 트랜잭션으로 묶여있는지 코드상 보장이 없고(트랜잭션 어노테이션 부재),
순서·원자성이 불명확하다.
발생 가능한 장애: 조회 모델은 반영되었는데 processed_event 기록이
실패(혹은 그 반대)하면, 재전달 시 중복 반영되거나 반영이 누락될 수 있다.
수정 방법: 두 작업을 @Transactional로 하나의 로컬 DB 트랜잭션으로 묶고,
Consumer Offset은 그 트랜잭션 Commit 이후에만 커밋한다.
```

### **4. 수정된 구조의 발행 보장 수준을 작성한다**

다음 항목별로 `보장`, `조건부 보장`, `보장하지 않음` 중 하나를 선택하고 이유를 작성한다.

| 항목 | 수준 | 이유 |
| --- | --- | --- |
| DB 발급 결과와 Outbox 기록의 원자성 | 보장 | 같은 로컬 DB 트랜잭션 안에서 함께 Commit/Rollback되도록 수정했기 때문 |
| Kafka Record의 물리적인 Exactly-Once 생성 | 보장하지 않음 | Timeout/Lease 만료 후 재Claim 등으로 같은 이벤트가 물리적으로 여러 번 발행될 수 있음 |
| Publisher 복구 후 재발행 | 조건부 보장 | Lease 만료 회수, Backoff 재시도가 정상 동작하고 Publisher가 결국 다시 살아난다는 전제 하에 보장됨 |
| 비즈니스 발생 순서대로 전달 | 보장하지 않음 | SKIP LOCKED, Backoff 재시도, 다중 Publisher로 인해 DB 저장 순서와 발행 순서가 달라질 수 있음 |
| Consumer의 중복 비즈니스 반영 방지 | 보장 | eventMessageId 기반 processed_event 멱등 처리를 Consumer 트랜잭션에 포함했기 때문 |
| 모든 Consumer Group의 처리 완료 | 보장하지 않음 | 각 Consumer Group은 독립적으로 자신의 Offset과 처리 속도를 관리하며 Publisher/Outbox가 이를 알 수 없음 |
| 외부 SMS의 정확히 한 번 전송 | 보장하지 않음 | processed_event는 로컬 DB 반영의 중복만 막을 뿐, 외부 API 호출은 별도의 Dual Write 문제로 남아있어 Notification 내부에 별도 설계가 필요함 |
