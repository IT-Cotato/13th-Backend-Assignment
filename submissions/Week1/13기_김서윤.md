## 과제 2. 구조 A와 구조 B 중 더 적합한 구조 선택하기

아래 두 구조를 비교한다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/d98dc724-8951-4080-aff8-af74ff6485cd" />

다음 질문에 답한다.

```
1. 두 구조 중 선착순 쿠폰 이벤트에 더 적합한 구조는 무엇인가?
구조 B

2. 구조 A는 Queue를 사용했는데도 왜 비동기 처리의 장점이 줄어드는가?
큐를 사용해 DB 작업은 Worker로 넘겼지만, API 서버가 그 결과를 기다리는 동안 현재 실행 흐름이 멈춰있는 블로킹(Blocking) 상태가 되기 때문입니다. 즉, API 서버가 제어권을 즉시 돌려받지 못해 다른 요청을 처리할 수 없으므로 실질적인 병목 해소 효과가 사라집니다.

3. API Server가 Worker 결과를 기다리면 어떤 문제가 생기는가?
API Serverd에 많은 요청이 몰리는 동안 Worker 결과를 기다리기 위해 대기 상태에 머무른다면 스레드 풀이 고갈되기 때문에 타임아웃이 발생해 새로운 요청을 받을 수 없는 셧다운 상태에 빠질 수 있다. 

4. 구조 B를 선택한다면 사용자는 최종 발급 결과를 어떻게 확인해야 하는가?
클라이언트가 PENDING 응답을 받은 후에는 주기적으로 확인 API를 호출하게 한다. 
```

## 과제 4. API Server가 직접 처리할 일과 비동기 처리 영역으로 넘길 일을 나누기

쿠폰 발급 요청이 들어왔을 때 API Server가 직접 처리해야 하는 일과, 비동기 처리 영역으로 넘겨야 하는 일을 구분한다.

아래 작업들을 기준으로 나누고 이유를 작성한다.

```
- 로그인 여부 확인
- 이벤트 시간 확인
- 쿠폰 수량 최종 차감
- DB 발급 기록 저장
- 사용자에게 요청 접수 응답
- 발급 성공/실패 최종 결정
```

아래 표 형식으로 작성한다.

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유                                                                  |
| --- |-----------------|----------------|---------------------------------------------------------------------|
| 로그인 여부 확인 | o               |                | DB 조회 없이 세션이나 JWT 토큰을 통해 바로 처리할 수 있기 때문이다.                          |
| 이벤트 시간 확인 | o               |                | 마찬가지로 DB 조회 없이 처리 가능하기 때문에 서버 부담이 많지 않다.                            |
| 쿠폰 수량 최종 차감 |                 | o              | 신뢰성이 중요한 부분이므로 분리해서 데이터 정합성을 확보해 순차적으로 안전하게 처리해야 한다.                |
| DB 발급 기록 저장 |                 | o              | DB I/O 작업은 API 서버에서 하게 되면 병목현상이 발생하므로 비동기 구역에서 처리한다.                |
| 사용자에게 요청 접수 응답 | o               |                | 사용자에게 PENDING 응답을 바로 주면 UX가 개선된다.                                   |
| 발급 성공/실패 최종 결정 |                 | o              | 쿠폰 수량 최종 차감 등을 비동기 영역에서 하고 있으므로 최종 성공 판단 또한 비동기영역에서 해서 주는 것이 효과적이다. |

## 과제 5. 요청 접수 성공 응답을 언제 반환할 수 있는지 설계하기

비동기 처리 구조에서는 API Server가 사용자에게 다음과 같은 응답을 반환할 수 있다.

```
쿠폰 발급 요청이 접수되었습니다.
```

하지만 이 응답을 아무 때나 반환하면 안 된다.

예를 들어 요청이 메모리에만 있는 상태에서 응답했는데 API Server가 장애로 종료되면 요청이 유실될 수 있다.

따라서 API Server가 언제 사용자에게 요청 접수 성공 응답을 반환할 수 있는지 설계해야 한다.

다음 질문에 답한다.

```
1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?
메시지 큐에 요청이 성공적으로 적재되었을 때 반환해야 한다. 

2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?
큐에 요청이 적재되지 않으면 대기상태가 지속될 쁀 작업이 진행되지 않는 문제가 발생할 수 있다. 
- 예시) 서버 전원이 꺼지거나 재시작할 경우, 데이터 증발로 인한 문제가 생길 수 있다. 

3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    - 장점: 더 확실히 신뢰성을 보장할 수 있다. 
    - 단점: DB I/O 작업으로 인해 응답이 느려져 UX에 악영향을 줄 수 있으며, 대규모 트래픽 발생 시 병목 현상이 발생할 수 있다. 
    
4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    - 장점: 데이터 유실을 방지하고 최소한의 신뢰성을 보장한다. 
    - 단점: 메시지 큐에 장애가 발생할 경우 서버 응답에 영향을 줄 수 있고, 브로커 응답을 기다리는 지연이 발생한다. 


5. 내가 선택한 방식과 그 이유를 설명하라.
    비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식
    - 이유: 큐에 적재된 이후에는 요청이 유실될 확률이 적고, 병목 현상을 피할 수 있어 균형 잡힌 구성을 할 수 있다. 
    
```

참고로 요청 접수 성공의 기준은 다음 중 하나로 생각해볼 수 있다.

```
1. 요청을 메모리에 올린 순간
2. 요청 검증이 끝난 순간
3. 요청 상태가 DB에 PENDING으로 저장된 순간
4. Queue 또는 Kafka에 안전하게 전달된 순간
```

단순히 빠르게 응답하는 것만 생각하지 말고, 사용자가 접수 응답을 받은 뒤 요청이 유실되지 않도록 하려면 어떤 기준이 필요한지 고민한다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각해보기

비동기 처리는 대규모 트래픽 상황에서 유리할 수 있다.

하지만 항상 비동기가 더 좋은 것은 아니다.

다음 질문에 답한다.

```
1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?
대규모 트래픽이 몰리며,DB I/O 작업, 외부 API 호출 등 응답 지연을 유발하는 코스트가 큰 작업이 있을 때 유리하다. 

2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?
작업의 코스트가 크지 않거나 사용자에게 즉각적 & 확실한 결과를 보여줘야 하는 작업의 경우 적합하다. 
또한, 단시간에 대규모 트래픽이 몰리지 않을 경우 비동기 처리는 별도의 인프라가 필요하므로 비용 부담이 증가할 수 있다. 

3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?
메시지 큐를 사용하고 Worker서버를 따로 관리해야 하므로 시스템 아키텍처가 복잡하다. 
바로 처리에 대한 응답이 아닌 PENDING 상태를 줘 백그라운드 작업 후, 다시 작업 성공 여부에 대한 응답을 줘야 하므로 이 부분의 API 호출이 번거로울 수 있다.
+) 아랫부분은 제가 생각해내지 못한 부분인데 추가적으로 알게 되어 넣었습니다.
    메시지 처리 실패 시 재시도 로직 등 에러 핸들링이 까다롭다. 

4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?
사용자가 최종 결과를 바로 알아야 한다면 비동기 처리가 아닌 동기 처리가 적합할 수 있다. 
비동기 처리는 PENDING 응답 이후에 다른 페이지로 이동하거나 추가적인 요청을 통해 사용자가 결과를 알 수 있기 대문에 UX가 훼손된다.

5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?
결과 확인이 늦어지더라도 이벤트 참여 자체가 막히는 서비스 가용성 문제를 방지하는 게 더 중요한 케이스이기 때문이다.  
```

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석하기

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 기준이 다르다.

동기/비동기는 요청한 작업의 결과를 **같은 요청 흐름에서 직접 받아 처리하는가**, 아니면 요청 흐름과 실제 처리 흐름을 분리하는가에 대한 개념이다.

블로킹/논블로킹은 **작업이 끝날 때까지** 현재 실행 흐름이 멈추는가, 아니면 바로 제어권을 돌려받는가?에 대한 개념이다.

다음 4가지 조합을 분석한다.

```
1. 동기 / 블로킹

2. 동기 / 논블로킹

3. 비동기 / 블로킹

4. 비동기 / 논블로킹
```

다음 질문에 답한다.


1. 아래 4가지 조합 각각이 무엇인지, 일반적인 작업 흐름(예: 함수 호출, DB 호출, 소켓 IO 등) 기준으로 다이어그램과 함께 설명하라. (쿠폰 발급 시나리오에 한정하지 않아도 된다.)
    - 동기/블로킹: API 서버가 DB에 작업을 요청한 뒤 DB에서 제어권을 가져가 API 서버는 결과가 나올 때까지 대기한다.
    <img width="2116" height="562" alt="Image" src="https://github.com/user-attachments/assets/53b15080-41c7-4f49-99a4-840876051d71" /> 
    - 동기/논블로킹: API 서버가 DB에 작업을 요청한 뒤 제어권을 즉시 돌려 받아 해당 작업의 결과가 나올 때까지 다른 작업을 병행 처리할 수 있다.
    <img width="2075" height="825" alt="Image" src="https://github.com/user-attachments/assets/468440e0-06b5-4c30-8d3d-be30780d3f53" />
    - 비동기/블로킹 (보통 잘못된 상태): API에서 비동기적으로 처리해 병목현상을 없애려고 했으나 제어권이 없어 다른 작업 없이 대기하고 있다.
    <img width="2072" height="669" alt="Image" src="https://github.com/user-attachments/assets/1be756c1-3bfb-40c6-b1a0-d6b3273a0dfe" />
    - 비동기/논블로킹: API에서 비동기적으로 처리해 Client에 즉각적으로 답을 보낼 수 있으며, 제어권을 돌려받아 다른 작업을 실행할 수 있다. 결과는 따로 마이페이지나 조회 API를 호출해 확인한다.
    <img width="1810" height="783" alt="Image" src="https://github.com/user-attachments/assets/244d9c60-1c69-4826-b594-1428c9538b3e" />
    
2. 이 4가지 중 이번 선착순 쿠폰 발급 구조에 실제로 등장하는 조합은 무엇인지 고르고, 어디에서 등장하는지 근거를 들어 설명하라. (4개가 다 등장하지 않을 수 있다.)
    - 동기 / 블로킹: 클라이언트가 처음 API를 호출했을 때 API서버에서 로그인 유효성 등을 체크하는 로직은 해당 방식을 사용해 처리될 것이다. 위에서 설명했듯 이는 바로 즉각적인 결과를 보여줘야 하며, 처리가 빠르기 때문에 제어권을 넘겨주고 기다려도 서버에 무리가 가지 않는다.
    - 비동기 / 논블로킹: API 서버가 쿠폰 발급 요청을 메시지 큐에 적재하고 사용자에게 PENDING을 응답하는 핵심 로직에 사용되었을 것이다. API 서버가 작업 완료를 기다리지 않고 백그라운드에서 Worker가 스스로 처리하기 때문에 비동기 흐름이며, 그 사이에 API는 추가적인 클라이언트의 요청을 받아오고 다시 PENDING을 보내기도 하므로 제어권 또한 즉각적으로 돌려받았다고 판단했다.
