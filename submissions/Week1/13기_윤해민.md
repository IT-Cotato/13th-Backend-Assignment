### 두 구조의 차이

| 항목 | 동기 처리 | 비동기 처리 |
|---|---|---|
| **응답 시점** | 쿠폰 발급이 완전히 끝난 후 응답 | 요청 접수 직후 즉시 응답 (202 Accepted) |
| **API Server 점유 시간** | DB 조회 + 저장이 완료될 때까지 스레드 점유 | 검증 + 접수 저장 직후 스레드 해제 |
| **사용자 경험** | 발급 성공/실패를 즉시 확인 가능 | 최종 결과는 별도 조회 필요 (PENDING → SUCCESS/FAILED) |
| **장애 격리** | DB 부하 증가 시 API Server도 함께 지연 | Worker 장애가 API Server 응답에 직접 영향을 주지 않음 |
| **구조 복잡도** | 단순 (흐름이 하나) | Queue, Worker, 상태 관리 등 추가 구성 필요 |
| **적합한 트래픽** | 요청이 적고 안정적인 서비스 | 순간 트래픽이 급증하는 이벤트성 서비스 |

**핵심 차이**: 동기 처리는 "요청 처리"와 "응답"이 하나의 흐름 안에서 완결된다. 비동기 처리는 "요청 접수"와 "실제 발급"을 서로 다른 흐름으로 분리하여, API Server는 접수 사실만 보장하고 발급 처리는 Worker에게 위임한다. 선착순 쿠폰처럼 순간 트래픽이 집중되는 상황에서는 API Server의 스레드 점유를 최소화할 수 있는 비동기 구조가 유리하다.

### Q1. 두 구조 중 선착순 쿠폰 이벤트에 더 적합한 구조는 무엇인가?

**구조 B**가 더 적합하다.

선착순 쿠폰 이벤트는 짧은 시간에 수만 건의 요청이 집중되는 트래픽 구조를 가진다. 이 상황에서 API Server의 스레드를 얼마나 빠르게 해제하느냐가 서비스 안정성의 핵심이다.

구조 B는 API Server가 요청 검증과 접수 저장만 완료한 뒤 즉시 202 응답을 반환한다. 스레드가 Worker의 처리 결과를 기다리지 않으므로, 같은 스레드 수로 훨씬 많은 요청을 처리할 수 있다. 실제 쿠폰 발급은 Worker가 Queue에서 메시지를 소비하며 처리하므로, DB에 순간적으로 몰리는 부하를 완충해 처리 속도를 제어할 수 있다.

> 다만 Queue(또는 Kafka)의 역할은 요청을 **완충하고 Worker가 감당 가능한 속도로 소비**하게 하는 데 있다. 정확한 수량 차감과 중복 발급 방지 자체는 Queue가 보장하지 않으며, Redis 원자 연산·DB Lock/Transaction·조건부 UPDATE·Unique 제약 같은 정합성 장치가 함께 있어야 성립한다. (3·4주차에서 상세히 다룬다.)

---

### Q2. 구조 A는 Queue를 사용했는데도 왜 비동기 처리의 장점이 줄어드는가?

비동기 처리의 핵심 장점은 **요청 접수 흐름과 실제 처리 흐름을 분리**하여 API Server의 스레드를 빠르게 해제하는 것이다.

구조 A는 Queue를 사이에 두었지만, API Server가 Worker의 처리 결과가 돌아올 때까지 스레드를 점유한 채 대기한다. 즉, Queue는 메시지를 전달하는 경로로만 사용될 뿐, API Server 입장에서는 결과를 기다리는 **동기적 흐름**이 그대로 유지된다.

결국 아래 두 구조는 API Server의 스레드 점유 시간 측면에서 사실상 동일하다.

```
구조 A:  Client → API Server → (Queue → Worker → DB) → API Server 대기 → Client 응답
동기:    Client → API Server → DB → Client 응답
```

Queue를 도입했다는 사실 자체가 비동기를 의미하지 않는다. **API Server가 결과를 기다리지 않는 구조**여야 비동기의 장점이 실현된다.

---

### Q3. API Server가 Worker 결과를 기다리면 어떤 문제가 생기는가?

**① 스레드 고갈 (Thread Exhaustion)**

API Server는 일반적으로 스레드 풀을 사용해 요청을 처리한다. Worker 결과를 기다리는 동안 해당 스레드는 블로킹 상태로 점유된다. 순간 트래픽이 몰리면 모든 스레드가 대기 중인 상태가 되어 신규 요청을 받지 못하게 된다.

**② 응답 지연 누적**

Worker의 처리 속도가 느리거나 DB에 부하가 발생하면, 그 지연이 그대로 API Server의 응답 시간으로 전파된다. 사용자는 쿠폰 발급 버튼을 누른 후 오랜 시간 동안 응답을 받지 못한다.

**③ Timeout 장애 전파**

Worker 또는 DB에서 Timeout이 발생하면 API Server도 함께 오류 응답을 반환하게 된다. 발급 처리 레이어의 장애가 API Server 전체의 장애로 전파되는 구조다.

**④ 확장성 한계**

API Server를 수평 확장해도 Worker 결과를 기다리는 구조 자체가 병목이기 때문에, 인스턴스 수를 늘려도 처리량이 선형으로 증가하지 않는다.

### Q4. 구조 B를 선택한다면 사용자는 최종 발급 결과를 어떻게 확인해야 하는가?

구조 B에서 API Server는 요청 접수 시점에 `202 Accepted`와 함께 `PENDING` 상태만 보장한다. 사용자는 아래 방식 중 하나로 최종 결과를 확인한다.

**방식 1. 클라이언트 폴링 (Short Polling)**

클라이언트가 일정 주기(예: 2~3초)로 발급 결과 조회 API를 반복 호출한다. 상태가 `PENDING`이면 재시도, `SUCCESS` 또는 `FAILED`이면 결과를 표시한다.

```
GET /coupons/status/{requestId}
→ { "status": "PENDING" }   # 처리 중
→ { "status": "SUCCESS" }   # 발급 성공
→ { "status": "FAILED", "reason": "쿠폰 소진" }  # 발급 실패
```

**방식 2. 서버 푸시 (SSE / WebSocket)**

Worker가 발급을 완료하는 시점에 서버가 클라이언트에 결과를 능동적으로 전송한다. 폴링보다 응답이 빠르고 불필요한 API 호출이 없다는 장점이 있지만, 커넥션 유지를 위한 추가 인프라가 필요하다.

**방식 3. 앱 푸시 알림**

Worker가 발급 완료 후 알림 서비스를 통해 사용자 기기에 결과를 전송한다. 사용자가 화면을 이탈한 경우에도 결과를 전달할 수 있다.

이벤트 특성과 구현 비용을 고려하면 **클라이언트 폴링**이 가장 현실적인 첫 번째 선택이며, 서비스 성숙도에 따라 SSE나 푸시 알림으로 개선할 수 있다.

### 위의 설계 구조

```
Client
  → API Server
      → 로그인 확인
      → 이벤트 시간 확인
      → DB: 쿠폰 수량 조회
      → DB: 쿠폰 발급 기록 저장 + 수량 차감
      → 외부 알림 서비스: 발급 알림 발송 (SMS / 이메일)
      → DB: 마이페이지 데이터 갱신
  → Client에게 최종 성공/실패 응답
```

이 구조는 하나의 요청이 DB 처리, 외부 서비스 호출, 데이터 갱신을 모두 순차적으로 완료해야 응답이 반환된다.

### Q1. 이 설계에서 문제가 될 수 있는 부분을 5개 이상 찾아라.

**① 응답 시간 누적 지연**

DB 수량 조회 → DB 발급 저장 → 외부 알림 API 호출 → 마이페이지 DB 갱신 순서로 각 단계의 처리 시간이 순차적으로 합산된다. 외부 알림 서비스 응답이 200ms만 늦어도 그 지연이 그대로 사용자 응답 시간에 반영된다.

**② 외부 서비스 장애가 쿠폰 발급 실패로 전파**

알림 발송 단계에서 외부 서비스(SMS, 이메일 Provider 등)가 다운되거나 Timeout이 발생하면 API Server도 오류 응답을 반환한다. 쿠폰은 이미 DB에 저장되었는데 알림 실패 때문에 사용자에게는 발급 실패로 표시되는 데이터 불일치가 발생할 수 있다.

**③ 트랜잭션 범위 과대 설정으로 인한 Lock 증가**

DB 쿠폰 수량 차감과 발급 기록 저장을 하나의 트랜잭션으로 처리하는 동안, 이후의 마이페이지 갱신이나 알림 호출 시간만큼 트랜잭션이 길게 유지된다. 트랜잭션이 길어지면 해당 Row에 Lock이 오래 걸려 다른 요청들이 대기해야 한다.

**④ DB Connection Pool 고갈**

각 요청이 모든 처리 단계를 완료할 때까지 DB Connection을 점유한다. 선착순 이벤트처럼 순간적으로 수천 건의 요청이 들어오면 Connection Pool이 고갈되어 신규 요청이 DB에 접근조차 하지 못하는 상황이 발생한다.

**⑤ API Server 스레드 고갈**

외부 알림 API 호출처럼 응답이 느린 작업을 기다리는 동안 해당 요청을 처리하는 스레드가 블로킹 상태로 점유된다. 순간 트래픽에서 모든 스레드가 대기 상태가 되면 새로운 요청을 처리할 수 없게 된다.

**⑥ 단일 책임 원칙(SRP) 위반으로 인한 유지보수 어려움**

알림 발송 방식이 변경되거나 마이페이지 스키마가 바뀔 때마다 쿠폰 발급 로직이 담긴 코드를 함께 수정해야 한다. 각 기능이 하나의 흐름에 강하게 결합되어 있어 독립적인 배포와 테스트가 어렵다.

**⑦ 부분 실패 시 복구 전략 부재**

DB에 발급 기록을 저장한 뒤 알림 발송이 실패했을 때, 발급을 롤백해야 하는지 알림만 재시도해야 하는지에 대한 처리 로직이 없다. 중간 실패 상태에서 데이터 정합성을 보장하기 어렵다.

### Q2. API Server가 너무 많은 일을 하면 어떤 문제가 생기는가?

**처리량(Throughput) 저하**

하나의 요청이 API Server를 오래 점유할수록 동시에 처리할 수 있는 요청 수가 줄어든다. 작업이 많아질수록 스레드 점유 시간이 길어지고, 결국 같은 인프라로 처리 가능한 TPS(Transaction Per Second)가 낮아진다.

**장애 전파 범위 확대**

관련 없는 기능들이 하나의 처리 흐름에 묶이면 하나의 기능 장애가 전체 요청 실패로 이어진다. 알림 서비스가 느려지면 쿠폰 발급 자체도 느려지는 식으로 장애가 연쇄적으로 전파된다.

**확장의 어려움**

알림 발송 부하가 크다고 해서 알림 처리만 독립적으로 확장할 수 없다. API Server 전체를 확장해야 하므로 비용 효율이 낮고, 병목이 되는 지점만 선택적으로 개선하기 어렵다.

### Q3. 알림 발송이나 마이페이지 데이터 갱신이 실패하면 쿠폰 발급 응답에 어떤 영향을 줄 수 있는가?

두 가지 시나리오로 나눌 수 있다.

**시나리오 1 — 예외를 그대로 전파하는 경우**

알림 발송 또는 마이페이지 갱신에서 예외가 발생하면 API Server가 오류 응답을 반환한다. 이미 DB에 쿠폰 발급 기록이 저장된 상태라면, 사용자에게는 발급 실패로 보이지만 실제로는 발급된 상태가 된다. 이중 발급 방지 로직을 재실행하면 중복 발급 오류가 발생할 수 있다.

**시나리오 2 — 예외를 무시하는 경우**

알림 실패를 catch로 무시하고 쿠폰 발급은 성공으로 응답한다면, 발급은 완료되었지만 사용자가 알림을 받지 못하는 상황이 생긴다. 이 경우 발급 성공과 알림 발송의 정합성이 보장되지 않는다.

두 경우 모두 문제가 발생한다. 근본적인 원인은 **비즈니스 중요도가 다른 작업들이 같은 트랜잭션 흐름에 묶여 있기 때문**이다. 쿠폰 발급은 핵심 트랜잭션이지만, 알림 발송과 마이페이지 갱신은 부가적인 작업이다. 부가 작업의 실패가 핵심 작업의 결과에 영향을 주어서는 안 된다.

| 항목 | 나쁜 설계 | 개선된 설계 |
|---|---|---|
| **API Server 역할** | 발급 + 알림 + 마이페이지 갱신 전부 처리 | 요청 검증 + 접수 저장 + 202 응답만 처리 |
| **알림 발송 실패 영향** | 쿠폰 발급 자체가 실패로 처리될 수 있음 | Notification Worker가 독립적으로 재시도, 쿠폰 발급에 영향 없음 |
| **트랜잭션 범위** | 알림 + 마이페이지 갱신 완료까지 포함 | 쿠폰 발급 기록 저장까지만 트랜잭션 |
| **장애 격리** | 부가 기능 장애 → 전체 요청 실패 | 각 Worker가 독립적으로 처리, 장애가 격리됨 |
| **확장성** | API Server 전체를 확장해야 함 | 병목이 되는 Worker만 선택적으로 수평 확장 가능 |

## 과제 4. API Server가 직접 처리할 일과 비동기 처리 영역으로 넘길 일을 나누기

쿠폰 발급 요청이 들어왔을 때 API Server가 직접 처리해야 하는 일과, 비동기 처리 영역으로 넘겨야 하는 일을 구분한다.

아래 작업들을 기준으로 나누고 이유를 작성한다.

```
- 로그인 여부 확인
- 이벤트 시간 확인
- 쿠폰 수량 최종 차감
- DB 발급 기록 저장
- 사용자에게 요청 접수 응답
- 발급 성공/실패 최종 결정
```

아래 표 형식으로 작성한다.

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유 |
| --- | --- | --- | --- |
| 로그인 여부 확인 | O |  | 인증되지 않은 요청은 Queue에 넣기 전에 즉시 거부해야 한다. 비인가 요청이 Worker까지 전달되면 불필요한 처리가 발생하고, 보안 검증은 항상 요청 흐름의 가장 앞단에서 이루어져야 한다. |
| 이벤트 시간 확인 | O |  | 이벤트 시간이 아닌 요청은 빠르게 거절해야 한다. 유효하지 않은 요청을 Queue에 적재하면 Worker 처리 비용이 낭비되고, Queue가 불필요하게 채워진다. |
| 쿠폰 수량 최종 차감 |  | O | 수량 차감은 원자적으로 처리되어야 하며, 순간 트래픽에서 모든 요청이 동시에 DB에 차감을 시도하면 Lock 경합이 심해진다. Worker가 Queue에서 소비하며 처리하면 DB에 몰리는 부하를 완충·분산할 수 있다. 다만 정확한 수량 차감 자체는 Queue가 아니라 Redis 원자 연산·DB Lock/Transaction·조건부 UPDATE·Unique 제약이 보장한다. |
| DB 발급 기록 저장 |  | O | 발급 기록 저장은 수량 차감과 같은 트랜잭션 안에서 원자적으로 처리되어야 한다. Worker가 수량 차감과 함께 처리하는 것이 데이터 정합성 측면에서 안전하다. (단, 요청 접수 상태를 PENDING으로 저장하는 것은 API Server에서 처리한다.) |
| 사용자에게 요청 접수 응답 | O |  | 응답은 API Server가 Client에게 직접 반환한다. PENDING 상태 저장 완료 후 202 Accepted를 반환하며, 이 시점부터 요청의 내구성이 보장된다. |
| 발급 성공/실패 최종 결정 |  | O | 실제 수량 차감 결과에 따라 성공/실패가 결정되므로 Worker에서 판단한다. Worker는 처리 결과에 따라 요청 상태를 SUCCESS 또는 FAILED로 업데이트한다. |

### 처리 흐름 요약

```
[API Server 처리 영역]
  1. 로그인 여부 확인          → 미인증 시 401 반환
  2. 이벤트 시간 확인          → 유효하지 않으면 400 반환
  3. 요청 상태 PENDING 저장    → DB에 내구성 있는 기록 생성
  4. Queue에 메시지 발행       → Worker에게 처리 위임
  5. 202 Accepted 응답 반환    → 스레드 즉시 해제

[비동기 처리 영역 — Worker]
  6. 쿠폰 수량 원자적 차감
  7. DB 발급 기록 저장
  8. 요청 상태 SUCCESS / FAILED 업데이트
```

**분류 기준**: API Server는 요청의 **유효성 검증**과 **접수 보장**만 담당하고, 실제 발급에 관련된 데이터 변경과 최종 결과 결정은 모두 Worker에게 위임한다. 이렇게 분리해야 순간 트래픽에서 API Server의 스레드 점유 시간을 최소화하고, DB에 가해지는 부하를 제어할 수 있다.

## 과제 5. 요청 접수 성공 응답을 언제 반환할 수 있는지 설계하기

비동기 처리 구조에서는 API Server가 사용자에게 다음과 같은 응답을 반환할 수 있다.

```
쿠폰 발급 요청이 접수되었습니다.
```

하지만 이 응답을 아무 때나 반환하면 안 된다.

예를 들어 요청이 메모리에만 있는 상태에서 응답했는데 API Server가 장애로 종료되면 요청이 유실될 수 있다.

따라서 API Server가 언제 사용자에게 요청 접수 성공 응답을 반환할 수 있는지 설계해야 한다.

다음 질문에 답한다.

```
1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?

2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?

3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?

4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?

5. 내가 선택한 방식과 그 이유를 설명하라.
```

참고로 요청 접수 성공의 기준은 다음 중 하나로 생각해볼 수 있다.

```
1. 요청을 메모리에 올린 순간
2. 요청 검증이 끝난 순간
3. 요청 상태가 DB에 PENDING으로 저장된 순간
4. Queue 또는 Kafka에 안전하게 전달된 순간
```

단순히 빠르게 응답하는 것만 생각하지 말고, 사용자가 접수 응답을 받은 뒤 요청이 유실되지 않도록 하려면 어떤 기준이 필요한지 고민한다.

---

### 4가지 기준 비교

| 기준 | 응답 속도 | 요청 내구성 | 장애 시 동작 |
|---|---|---|---|
| ① 메모리에 올린 순간 | 가장 빠름 | 없음 | API Server 재시작 시 요청 유실 |
| ② 검증이 끝난 순간 | 빠름 | 없음 | 저장되지 않아 장애 시 유실 |
| ③ DB에 PENDING 저장 완료 | 보통 | DB 수준 보장 | 서버 재시작 후 PENDING 상태로 복구 가능 |
| ④ Queue에 안전하게 전달 완료 | 약간 느림 | Queue 수준 보장 | Queue 장애 시 응답 자체가 불가 |

---

### Q1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?

**요청 상태가 DB에 PENDING으로 저장된 이후**에 응답을 반환해야 한다.

"요청 접수 성공"이라는 응답은 서버가 해당 요청을 안전하게 기록했고, 이후 처리를 보장할 수 있다는 의미를 내포한다. 요청이 메모리나 검증 단계에만 존재하는 상태에서 응답하면 이 보장을 지킬 수 없다. DB에 저장된 시점부터 서버가 재시작되더라도 요청을 복구할 수 있으며, 사용자는 나중에 상태를 조회해 결과를 확인할 수 있다.

---

### Q2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?

사용자는 요청이 접수되었다는 응답을 받았지만, 서버 입장에서는 아무것도 저장되지 않은 상태다. 이 시점에 API Server가 프로세스 재시작, OOM, 배포 등으로 종료되면 요청은 흔적 없이 사라진다.

```
사용자 → "요청 접수 완료 응답 받음"
서버   → (재시작) → 요청 데이터 없음
사용자 → 결과 조회 → 요청 기록 없음
```

사용자는 요청이 처리 중이라고 믿고 기다리지만, 서버에는 해당 요청 자체가 존재하지 않는다. 사용자는 재요청을 해야 하는지조차 알 수 없고, 재요청 시 중복 발급 가능성도 생긴다.

---

### Q3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?

**장점**

- **내구성 보장**: DB에 저장된 순간부터 서버 장애가 발생해도 PENDING 상태로 요청이 남아 복구할 수 있다.
- **상태 추적 가능**: 사용자가 `GET /coupons/status/{requestId}`로 PENDING 상태를 확인할 수 있다. 요청이 처리 중임을 알 수 있어 UX 측면에서도 적절하다.
- **Queue 독립성**: DB 저장 후 Queue 발행이 실패하더라도, Scheduler나 Batch로 PENDING 상태 요청을 재발행하는 복구 전략을 적용할 수 있다.

**단점**

- **DB 쓰기 지연**: 응답 전에 반드시 DB 쓰기가 완료되어야 한다. 순간 트래픽에서 DB에 부하가 집중되면 이 단계에서 응답 지연이 발생할 수 있다.
- **DB 단일 장애점**: DB가 다운되면 요청 접수 자체가 불가능하다.

---

### Q4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?

**장점**

- **처리 흐름 보장**: Queue에 메시지가 안전하게 적재된 것을 확인했으므로, Worker가 해당 요청을 소비할 준비가 완료된 상태다.
- **DB + Queue 이중 보장**: DB 저장에 더해 Queue까지 전달을 확인하면 요청 유실 가능성이 더 낮아진다.

**단점**

- **Queue 장애 시 응답 불가**: Kafka나 RabbitMQ 등 Queue 브로커에 장애가 발생하면 ack를 받을 수 없어 응답 자체를 반환하지 못한다. Queue 장애가 API Server 응답 장애로 전파된다.
- **응답 시간 증가**: DB 저장 + Queue 발행 + ack 수신까지 기다려야 하므로 메모리 응답이나 DB 저장 방식보다 응답 시간이 길다.
- **불필요한 커플링**: API Server의 응답 가능 여부가 Queue 브로커의 상태에 종속된다.

---

### Q5. 내가 선택한 방식과 그 이유

**선택: 요청 상태를 DB에 PENDING으로 저장한 뒤 응답하고, Queue 발행은 별도로 진행한다.**

```
[선택한 처리 흐름]

Client
  → API Server
      → 요청 검증 (로그인, 이벤트 시간, 중복 확인)
      → DB: 요청 상태 PENDING 저장          ← 내구성 확보
      → 202 Accepted 응답 반환              ← 스레드 해제
      → Queue: 발급 요청 메시지 발행 (비동기)  ← 응답 이후 진행
```

**이유**

첫째, DB에 저장된 순간 요청의 내구성이 보장된다. 응답 이후 API Server가 재시작되더라도 PENDING 상태로 기록이 남아있기 때문에 요청이 유실되지 않는다.

둘째, Queue ack를 응답 조건으로 포함하지 않기 때문에 Queue 브로커 장애가 API Server의 응답 가능 여부에 영향을 주지 않는다. Queue 장애가 접수 단계까지 전파되는 것을 막을 수 있다.

셋째, Queue 발행이 실패하더라도 DB에 PENDING 상태가 남아있으므로, Scheduler가 주기적으로 PENDING 상태 요청을 스캔하여 Queue에 재발행하는 복구 전략(Outbox Pattern과 유사)을 적용할 수 있다.

```
[Queue 발행 실패 시 복구 흐름]

DB: PENDING 상태 요청 존재
  → Scheduler 주기적 스캔
  → Queue 재발행
  → Worker 처리 재개
```

단, 이 방식에서는 DB 쓰기가 응답 경로에 포함되므로 순간 트래픽에서 DB 부하 관리가 중요하다. Redis를 활용한 요청 중복 체크나 DB Connection Pool 크기 조정 등을 함께 고려해야 한다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각해보기

비동기 처리는 대규모 트래픽 상황에서 유리할 수 있다.

하지만 항상 비동기가 더 좋은 것은 아니다.

다음 질문에 답한다.

```
1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?

2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?

3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?

4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?

5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?
```

---

### Q1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?

**① 순간 트래픽이 급격히 몰리는 경우**

이벤트 시작, 티켓 오픈처럼 특정 시간에 요청이 집중되는 상황에서 동기 처리는 API Server와 DB에 동시에 부하가 집중된다. 비동기 처리는 요청을 Queue에 쌓아 처리 속도를 일정하게 유지할 수 있어, 순간 트래픽을 완충하는 버퍼 역할을 한다.

**② 처리 시간이 길거나 불확실한 작업이 포함된 경우**

외부 API 호출, 대용량 파일 처리, 이메일/SMS 발송처럼 처리 완료 시간이 길거나 예측하기 어려운 작업이 포함된 경우, 동기 처리는 그 작업이 완료될 때까지 스레드를 점유한다. 비동기 처리는 이런 작업을 Worker에게 위임하고 스레드를 즉시 해제할 수 있다.

**③ 처리 결과를 사용자가 즉시 알 필요가 없는 경우**

주문 처리 완료 알림, 정산 처리, 리포트 생성처럼 백그라운드에서 처리되어도 되는 작업은 비동기가 적합하다. 사용자는 요청 접수 응답만 받고, 완료 시 알림으로 결과를 확인하면 된다.

**④ 작업 흐름 중 일부가 독립적으로 처리 가능한 경우**

쿠폰 발급 후 알림 발송, 마이페이지 갱신처럼 핵심 처리와 부가 처리가 분리 가능한 경우, 핵심 처리만 동기로 완료하고 부가 처리를 비동기로 넘기면 응답 속도를 높이면서도 부가 기능을 보장할 수 있다.

---

### Q2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?

**① 사용자가 결과를 즉시 알아야 하는 경우**

로그인 인증, 결제 승인, 재고 확인처럼 사용자가 응답을 받아야 다음 행동을 결정할 수 있는 기능은 동기 처리가 적합하다. 비동기로 처리하면 사용자는 결과를 기다리는 추가 단계가 생겨 UX가 저하된다.

**② 요청 빈도가 낮고 트래픽이 안정적인 경우**

관리자 페이지, 내부 도구, 일반적인 CRUD API처럼 초당 수십 건 이내의 안정적인 트래픽이 예상되는 기능은 동기 처리로도 충분히 처리 가능하다. 굳이 Queue와 Worker를 도입할 필요가 없다.

**③ 작업의 원자성과 즉각적인 정합성이 중요한 경우**

계좌 이체처럼 요청과 결과가 하나의 트랜잭션으로 완결되어야 하고, 중간 상태(PENDING)가 허용되지 않는 비즈니스 요구사항이 있을 때는 동기 처리가 더 안전하다.

**④ 시스템이 아직 소규모이거나 초기 단계인 경우**

비동기 구조는 Queue, Worker, 상태 테이블, 재시도 로직 등 추가 인프라와 코드가 필요하다. 트래픽이 적은 초기 단계에서는 동기 처리로 빠르게 출시하고, 트래픽이 증가하는 시점에 비동기 구조로 전환하는 전략이 합리적이다.

---

### Q3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?

**① 인프라 추가**

Kafka, RabbitMQ 같은 Message Broker와 Worker 서버가 필요하다. 이 시스템들은 각각 별도의 운영, 모니터링, 장애 대응이 필요하다.

**② 상태 관리 필요**

동기 처리는 응답 자체가 최종 결과다. 비동기 처리는 PENDING → SUCCESS / FAILED 상태 전이를 추적해야 하므로 요청 상태 테이블과 상태 조회 API가 추가로 필요하다.

**③ 실패 복구 전략 설계 필요**

Worker가 처리 도중 실패하면 재시도(Retry) 로직이 필요하다. 재시도가 반복될 경우 Dead Letter Queue(DLQ)나 알림 처리가 필요하고, 멱등성(Idempotency) 보장도 설계해야 한다.

**④ 디버깅과 추적 어려움**

요청 흐름이 API Server → Queue → Worker로 분산되어 있어, 특정 요청이 어느 단계에서 실패했는지 추적하기 어렵다. 분산 트레이싱(Distributed Tracing)이나 상세한 로깅 전략이 필요하다.

**⑤ 데이터 정합성 관리 부담**

Worker가 메시지를 중복 소비하거나 순서가 바뀌어 처리될 수 있다. 이를 방지하기 위한 멱등성 키 관리와 순서 보장 설계가 필요하다.

---

### Q4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?

**아니다.** 사용자가 결과를 즉시 확인해야 하는 기능이라면 비동기 처리가 오히려 UX를 저하시킬 수 있다.

예를 들어, 결제 승인 화면에서 사용자가 "결제 완료" 또는 "결제 실패"를 즉시 확인해야 하는 경우, 비동기로 처리하면 사용자가 결과를 알기 위해 폴링하거나 별도 알림을 기다려야 한다. 이는 "지금 결제가 된 건지 안 된 건지 모르는" 불안한 상태를 만든다.

비동기 처리는 **"결과를 나중에 알아도 되는" 기능에 적합**하다. 결과를 즉시 알아야 하는 기능에서도 비동기를 적용하려면, SSE나 WebSocket을 통해 결과를 실시간으로 Push하는 구조가 추가로 필요하며, 이는 더 큰 복잡도를 요구한다.

결론적으로 비동기 처리는 성능 향상을 위한 도구일 뿐, 모든 기능에 무조건 적용하는 것이 아니라 **비즈니스 요구사항과 UX를 함께 고려해서 선택해야 한다.**

---

### Q5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?

선착순 쿠폰 이벤트는 아래의 특성을 가진다.

```
쿠폰 수량:       1,000개
예상 요청:       이벤트 시작 직후 1분 내 최대 10만 건
평균 RPS:        약 1,667 RPS
초반 0~5초 RPS:  수만 RPS 가능
```

이 조건에서 비동기 처리가 적합한 이유는 세 가지다.

**① 1,000개만 발급하면 되므로 나머지 요청은 빠르게 거절하거나 대기시킬 수 있다**

10만 건 중 실제 쿠폰을 받는 사람은 1,000명이다. 나머지 99,000건은 어차피 발급이 거절될 요청이다. 이 요청들을 모두 DB 처리까지 완료하고 응답하는 것은 불필요한 자원 낭비다. 비동기 구조에서는 API Server가 접수만 하고, Worker가 순서대로 처리하면서 수량이 소진되면 이후 요청은 FAILED로 처리할 수 있다.

**② 사용자는 즉시 결과를 알지 않아도 된다**

선착순 이벤트 특성상 사용자는 "내 요청이 접수되었는지"가 먼저 중요하다. 최종 발급 여부는 잠시 후 확인해도 UX상 허용된다. 따라서 API Server가 즉시 202 응답을 반환하고, 결과를 나중에 조회하는 흐름이 자연스럽다.

**③ 순간 트래픽 완충이 필수적이다**

이벤트 시작 직후 수만 RPS가 몰리는 상황에서 모든 요청을 즉시 DB까지 처리하면 DB Connection Pool 고갈, Lock 경합, 응답 Timeout이 연쇄적으로 발생한다. 비동기 구조는 Queue가 트래픽을 받아내는 버퍼 역할을 하고, Worker가 DB를 일정한 속도로 처리하므로 DB 부하를 제어할 수 있다.

```
동기 처리:   10만 RPS → DB 직격 → Connection Pool 고갈 → 서비스 장애
비동기 처리: 10만 RPS → Queue 적재 → Worker가 순차 처리 → DB 부하 분산
```

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석하기

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 기준이 다르다.

동기/비동기는 요청한 작업의 결과를 **같은 요청 흐름에서 직접 받아 처리하는가**, 아니면 요청 흐름과 실제 처리 흐름을 분리하는가에 대한 개념이다.

블로킹/논블로킹은 **작업이 끝날 때까지** 현재 실행 흐름이 멈추는가, 아니면 바로 제어권을 돌려받는가?에 대한 개념이다.

다음 4가지 조합을 분석한다.

```
1. 동기 / 블로킹

2. 동기 / 논블로킹

3. 비동기 / 블로킹

4. 비동기 / 논블로킹
```

다음 질문에 답한다.

```
1. 아래 4가지 조합 각각이 무엇인지, 일반적인 작업 흐름(예: 함수 호출, DB 호출, 소켓 IO 등) 기준으로 다이어그램과 함께 설명하라. (쿠폰 발급 시나리오에 한정하지 않아도 된다.)

2. 이 4가지 중 이번 선착순 쿠폰 발급 구조에 실제로 등장하는 조합은 무엇인지 고르고, 어디에서 등장하는지 근거를 들어 설명하라. (4개가 다 등장하지 않을 수 있다.)
```

---

### 개념 기준 정리

먼저 두 축의 기준을 명확히 한다.

```
동기 (Sync):
  요청한 작업의 결과를 호출한 흐름 안에서 직접 확인한다.
  호출자가 결과를 기다리거나, 결과가 없으면 즉시 "없음"을 받아 직접 재확인한다.

비동기 (Async):
  요청 흐름과 실제 처리 흐름을 분리한다.
  호출자는 결과를 기다리지 않고, 결과는 나중에 콜백 / 이벤트 / 폴링으로 받는다.

블로킹 (Blocking):
  작업이 완료될 때까지 현재 실행 흐름(스레드)이 멈춘다. 제어권을 반환하지 않는다.

논블로킹 (Non-blocking):
  작업 완료 여부와 관계없이 호출 즉시 제어권을 반환한다.
  결과가 없으면 "결과 없음(EAGAIN 등)"을 즉시 반환한다.
```

---

### Q1. 4가지 조합 각각에 대한 설명과 다이어그램

---

#### 조합 1. 동기 / 블로킹 (Sync + Blocking)

호출자가 작업 결과를 직접 기다리며(동기), 작업이 완료될 때까지 실행 흐름도 멈춘다(블로킹). 가장 일반적인 패턴으로, 대부분의 전통적인 서버 코드에서 사용된다.

**예시**: JDBC를 통한 DB 쿼리

```
Application Thread
  │
  ├─▶ stmt.executeQuery(sql)   ← DB 응답이 올 때까지 스레드 정지
  │        │
  │    (DB 처리 중 — 스레드 블로킹)
  │        │
  │◀───────┘  ResultSet 반환
  │
  └─▶ 결과 처리 (다음 로직 실행)
```

- 구현이 단순하고 코드 흐름이 직관적이다.
- 작업이 오래 걸릴수록 스레드가 오래 점유되어, 동시 요청이 많아지면 스레드 풀이 빠르게 소진될 수 있다.

---

#### 조합 2. 동기 / 논블로킹 (Sync + Non-blocking)

호출자가 결과를 직접 확인(동기)하지만, 즉시 제어권을 반환받는다(논블로킹). 결과가 준비되지 않았으면 "결과 없음"을 즉시 반환하고, 호출자가 직접 루프를 돌며 재확인한다.

**예시**: Non-blocking 소켓에서 데이터 수신 폴링

```
Application Thread
  │
  ├─▶ socket.read()    ← 즉시 반환 (데이터 없으면 EAGAIN)
  │◀── EAGAIN
  │
  ├─▶ (짧은 대기 후 재시도)
  │
  ├─▶ socket.read()    ← 재시도
  │◀── EAGAIN
  │
  ├─▶ socket.read()    ← 재시도
  │◀── 데이터 반환
  │
  └─▶ 결과 처리
```

- 스레드가 멈추지 않아 블로킹 I/O보다 스레드 낭비가 없다.
- 결과가 준비될 때까지 반복 호출(Busy-waiting)이 발생해 CPU를 낭비할 수 있다.
- 4가지 조합 중 실용성이 가장 낮은 패턴이다.

---

#### 조합 3. 비동기 / 블로킹 (Async + Blocking)

처리 흐름은 분리되어 있지만(비동기), 호출자가 결과를 기다리기 위해 다시 블로킹한다. 비동기로 작업을 시작했지만 결과를 받기 위해 스레드가 멈추는 패턴이다.

**예시**: Java `Future.get()`

```
Application Thread                  Worker Thread
  │
  ├─▶ Future<Result> f = executor.submit(task)
  │                                    ├─▶ task 실행 시작
  │
  ├─▶ f.get()   ← 결과 올 때까지 스레드 블로킹
  │                                    │  (task 처리 중...)
  │                                    │
  │◀───────────────────────────────────┘  결과 반환
  │
  └─▶ 결과 처리
```

- 작업을 별도 흐름으로 분리했지만(비동기), 결과를 받기 위해 다시 블로킹하므로 실제 성능 이점이 제한적이다.
- 과제 2의 **구조 A**가 이 패턴에 해당한다. Queue에 메시지를 넣었지만(처리 흐름 분리), API Server가 Worker 결과를 기다린다(블로킹).

---

#### 조합 4. 비동기 / 논블로킹 (Async + Non-blocking)

처리 흐름이 완전히 분리되고(비동기), 호출자는 작업을 요청한 뒤 즉시 제어권을 반환받는다(논블로킹). 결과는 나중에 콜백, 이벤트, Promise로 처리된다.

**예시**: Java `CompletableFuture.thenApply()` / JavaScript `Promise`

```
Application Thread                  Worker Thread
  │
  ├─▶ CompletableFuture
  │     .supplyAsync(task)           ├─▶ task 실행 시작 (별도 스레드)
  │     .thenApply(result -> ...)    │
  │◀── 즉시 반환 (논블로킹)           │  (처리 중...)
  │                                  │
  ├─▶ 다른 작업 A 처리               │
  ├─▶ 다른 작업 B 처리               │
  │                                  │  (task 완료)
  │◀─────────────────────────────────┘
  │
  └─▶ thenApply 콜백에서 결과 처리
```

- 스레드를 최소한으로 점유하면서 높은 처리량을 달성할 수 있다.
- Node.js 이벤트 루프, Java WebFlux(Reactor), Spring WebClient가 이 모델을 기반으로 한다.
- 4가지 조합 중 대규모 트래픽 처리에서 가장 효율적인 패턴이다.

---

### Q2. 선착순 쿠폰 발급 구조에서 실제로 등장하는 조합

과제 5에서 선택한 **구조 B (DB PENDING 저장 후 202 응답, Queue 발행은 응답 이후 별도 진행)** 를 기준으로 분석한다.

```
[API Server 처리 흐름]
  1. 요청 검증
  2. DB: 요청 상태 PENDING 저장    ← ① 동기/블로킹
  3. 202 Accepted 응답 반환
  4. Queue: 발급 요청 메시지 발행  (응답 이후 독립 진행)

[Worker 처리 흐름 — API Server와 분리된 흐름]  ← ② 비동기/논블로킹
  5. Queue: 메시지 소비
  6. DB: 쿠폰 수량 차감 + 발급 기록 저장     ← ① 동기/블로킹
  7. DB: 요청 상태 SUCCESS / FAILED 업데이트
```

---

#### 등장하는 조합 ①: 동기 / 블로킹

**등장 위치**: API Server에서 요청 상태를 DB에 PENDING으로 저장하는 단계, Worker에서 쿠폰 수량 차감과 발급 기록을 저장하는 단계.

Spring Boot + JPA 환경에서 `repository.save(couponRequest)` 호출은 DB 응답이 올 때까지 해당 스레드가 블로킹 상태로 대기한다. 호출한 흐름 안에서 결과를 직접 받아 처리하므로 동기이고, 완료까지 스레드가 멈추므로 블로킹이다.

```
API Server Thread
  ├─▶ repository.save(couponRequest)  ← 동기/블로킹
  │        (DB 저장 완료까지 스레드 정지)
  │◀─────── 저장 완료
  └─▶ 202 응답 반환
```

---

#### 등장하는 조합 ②: 비동기 / 논블로킹

**등장 위치**: API Server가 202 응답을 반환한 이후, Worker가 Queue를 소비해 독립적인 흐름에서 처리하는 전체 구조.

API Server는 202 응답을 반환하는 즉시 스레드를 해제한다. Worker가 메시지를 소비해 처리하는 것은 API Server의 요청 흐름과 완전히 분리된 별도 흐름에서 진행된다. API Server가 Worker의 결과를 기다리지 않으므로 논블로킹이고, 처리 흐름이 분리되어 있으므로 비동기다.

```
API Server Thread                    Worker Thread (독립 흐름)
  ├─▶ 202 응답 반환
  └─▶ 스레드 즉시 해제 (논블로킹)
                                       ├─▶ Queue 메시지 소비
                                       ├─▶ 쿠폰 수량 차감
                                       └─▶ 상태 SUCCESS / FAILED 업데이트
```

---

#### 등장하지 않는 조합

| 조합 | 등장 여부 | 이유 |
|---|---|---|
| 동기 / 논블로킹 | 등장하지 않음 | DB 저장은 결과가 올 때까지 스레드가 멈추는 블로킹 방식이다. 결과가 없으면 즉시 "없음"을 반환하고 직접 재확인하는 Busy-waiting 패턴은 이 구조에서 사용되지 않는다. |
| 비동기 / 블로킹 | 등장하지 않음 | 구조 A에서 등장하는 패턴이다. 구조 B에서는 API Server가 Worker 결과를 기다리지 않으므로 이 조합은 나타나지 않는다. |

**결론**: 선착순 쿠폰 발급 구조(구조 B)에서는 **동기/블로킹**과 **비동기/논블로킹** 두 가지 조합이 등장한다. DB 접근처럼 결과가 즉시 필요한 지점에서는 동기/블로킹이, API Server와 Worker의 처리 흐름이 분리되는 지점에서는 비동기/논블로킹이 나타난다.
