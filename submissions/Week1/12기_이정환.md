# Week1 필수 과제

## 과제 1. 동기 처리와 비동기 처리 구조

### 동기 처리 구조

```text
Client
  -> API Server
    -> 로그인 여부 확인
    -> 이벤트 시간 확인
    -> DB에서 쿠폰 수량 조회
    -> DB에 쿠폰 발급 기록 저장
    -> 쿠폰 수량 차감
  <- Client에게 최종 성공/실패 응답
```

동기 처리는 사용자의 쿠폰 발급 요청이 들어왔을 때 API Server가 실제 쿠폰 발급까지 모두 처리한 뒤 최종 결과를 응답하는 방식이다.

구조가 단순하고 사용자가 성공/실패 결과를 바로 알 수 있다는 장점이 있다. 하지만 이벤트 시작 직후처럼 요청이 한꺼번에 몰리는 상황에서는 API Server와 DB에 부하가 집중된다. DB 조회, DB 저장, 수량 차감, Lock 대기, Connection Pool 부족 등이 동시에 발생할 수 있다.

### 비동기 처리 구조

```text
Client
  -> API Server
    -> 로그인 여부 확인
    -> 이벤트 시간 확인
    -> 요청 상태를 PENDING으로 저장
  <- Client에게 요청 접수 응답

Worker
  -> PENDING 요청 조회 또는 Queue 메시지 소비
  -> 쿠폰 수량 확인 및 차감
  -> 발급 기록 저장
  -> 요청 상태를 SUCCESS 또는 FAILED로 변경

Client
  -> 결과 조회 API 호출
  <- 최종 발급 결과 확인
```

비동기 처리는 API Server가 최종 발급 결과까지 기다리지 않고 요청을 먼저 접수한 뒤 빠르게 응답하는 방식이다. 실제 쿠폰 발급은 Worker가 뒤에서 처리한다.

이 구조에서는 요청 접수와 발급 성공이 다르다. 사용자가 `PENDING` 응답을 받았다는 것은 요청이 접수되었다는 의미이지, 쿠폰 발급이 성공했다는 의미는 아니다. 최종 발급 결과는 이후 결과 조회 API를 통해 확인해야 한다.

## 과제 2. 구조 A와 구조 B 중 더 적합한 구조

### 1. 더 적합한 구조

선착순 쿠폰 이벤트에는 구조 B가 더 적합하다.

구조 B는 API Server가 요청을 접수한 뒤 Worker의 최종 처리 결과를 기다리지 않고 사용자에게 요청 접수 응답을 반환한다. 따라서 API Server의 요청 처리 시간이 짧아지고, 대량 요청 상황에서도 API Server가 오래 점유되지 않는다.

반면 구조 A는 Queue를 사용하더라도 API Server가 Worker 결과를 기다린다. 사용자는 최종 결과가 나올 때까지 응답을 받지 못하고, API Server도 그동안 요청 흐름을 붙잡고 있어야 한다.

### 2. 구조 A에서 비동기 처리의 장점이 줄어드는 이유

구조 A는 Queue를 사용하지만 API Server가 Worker 결과를 기다리기 때문에 비동기 처리의 장점이 줄어든다.

비동기 처리의 핵심은 API Server의 요청 처리 흐름과 실제 발급 처리 흐름을 분리하는 것이다. 하지만 구조 A에서는 Worker 처리가 끝날 때까지 API Server가 대기한다. 즉, 처리 위치만 Worker로 옮겨졌을 뿐 사용자의 HTTP 요청 흐름은 여전히 최종 결과에 묶여 있다.

### 3. API Server가 Worker 결과를 기다릴 때 생기는 문제

API Server가 Worker 결과를 기다리면 다음 문제가 생길 수 있다.

```text
- API Server 스레드가 오래 점유된다.
- 요청 대기 시간이 길어진다.
- 대량 트래픽 상황에서 Timeout이 증가한다.
- Worker 처리 지연이 API 응답 지연으로 바로 전파된다.
- Queue를 사용해도 부하 완화 효과가 줄어든다.
- Worker나 Queue 장애가 사용자 응답 지연 또는 실패로 이어진다.
```

결국 구조 A는 Queue를 도입했지만 API Server가 최종 결과를 기다리기 때문에 동기 처리와 비슷한 문제가 남는다.

### 4. 구조 B에서 사용자가 최종 결과를 확인하는 방법

구조 B를 선택한다면 사용자는 최초 요청 시 최종 발급 결과가 아니라 요청 접수 결과를 받는다.

예시 응답은 다음과 같다.

```json
{
  "requestId": 1,
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다."
}
```

이후 사용자는 별도의 결과 조회 API를 호출해 최종 상태를 확인한다.

```text
GET /coupon-requests/{requestId}
```

성공한 경우:

```json
{
  "requestId": 1,
  "status": "SUCCESS",
  "message": "쿠폰이 발급되었습니다."
}
```

실패한 경우:

```json
{
  "requestId": 1,
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

## 과제 3. 나쁜 설계의 문제점과 개선

### 1. 문제가 될 수 있는 부분

나쁜 설계에서 문제가 될 수 있는 부분은 다음과 같다.

```text
- API Server가 쿠폰 발급 전체 과정을 직접 처리한다.
- DB 수량 조회와 발급 기록 저장이 요청마다 즉시 발생한다.
- 쿠폰 수량 차감이 대량 요청 상황에서 Lock 경합을 만들 수 있다.
- 알림 발송까지 API 요청 흐름에 포함되어 있다.
- 마이페이지 데이터 갱신까지 API 요청 흐름에 포함되어 있다.
- 외부 알림 시스템 장애가 쿠폰 발급 응답에 영향을 줄 수 있다.
- 마이페이지 갱신 실패가 전체 요청 실패처럼 보일 수 있다.
- API Server의 응답 시간이 길어진다.
- DB Connection Pool이 부족해질 수 있다.
- 쿠폰 발급과 직접 관련 없는 부가 작업 때문에 사용자의 응답이 늦어진다.
```

### 2. API Server가 너무 많은 일을 할 때의 문제

API Server가 너무 많은 일을 하면 요청 하나를 처리하는 시간이 길어진다. 요청 처리 시간이 길어지면 동시에 처리할 수 있는 요청 수가 줄어든다. 이벤트 시작 직후처럼 요청이 몰리는 상황에서는 API Server 스레드, DB Connection, 외부 시스템 호출 대기 등이 빠르게 쌓일 수 있다.

또한 알림 발송, 마이페이지 갱신 같은 부가 작업의 장애가 핵심 기능인 쿠폰 발급 응답에 영향을 줄 수 있다. 쿠폰 발급 자체는 성공했는데 알림 발송 실패 때문에 전체 요청이 실패한 것처럼 보이는 문제가 생길 수 있다.

### 3. 알림 발송이나 마이페이지 갱신 실패가 응답에 주는 영향

알림 발송이나 마이페이지 데이터 갱신이 API 요청 흐름 안에 포함되어 있다면, 해당 작업의 실패가 쿠폰 발급 응답에 영향을 줄 수 있다.

예를 들어 쿠폰 발급 기록 저장은 성공했지만 알림 발송이 실패하면 사용자에게 실패 응답이 내려갈 수 있다. 또는 외부 알림 시스템 응답이 늦어져 API 요청 자체가 Timeout될 수 있다. 이 경우 사용자는 쿠폰이 발급되었는지 알기 어렵고, 중복 요청을 다시 보낼 가능성이 있다.

따라서 알림 발송과 마이페이지 갱신은 쿠폰 발급의 핵심 트랜잭션과 분리하는 것이 좋다.

### 4. 개선 구조

요청 접수와 실제 발급 처리를 분리한 개선 구조는 다음과 같다.

```text
Client
  -> API Server
    -> 로그인 여부 확인
    -> 이벤트 시간 확인
    -> 중복 요청 여부 기본 확인
    -> 요청 상태를 PENDING으로 저장
  <- 요청 접수 응답

Coupon Worker
  -> PENDING 요청 처리
  -> 쿠폰 수량 확인 및 차감
  -> 발급 기록 저장
  -> 요청 상태 SUCCESS 또는 FAILED 변경

Notification Worker
  -> 발급 성공 이벤트 처리
  -> 알림 발송

MyPage Worker
  -> 발급 성공 이벤트 처리
  -> 마이페이지 데이터 갱신
```

이 구조에서는 API Server가 요청을 안전하게 접수한 뒤 빠르게 응답한다. 실제 쿠폰 발급은 Worker가 처리하고, 알림 발송이나 마이페이지 갱신은 별도 비동기 작업으로 분리한다. 따라서 부가 작업이 실패해도 쿠폰 발급 자체가 실패하지 않도록 설계할 수 있다.

## 과제 4. API Server와 비동기 처리 영역 구분

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유 |
| --- | --- | --- | --- |
| 로그인 여부 확인 | O | X | 인증되지 않은 요청은 접수할 필요가 없으므로 API Server에서 빠르게 차단한다. |
| 이벤트 시간 확인 | O | O | API Server에서 기본적으로 이벤트 시간이 맞는지 확인하고, Worker에서도 실제 처리 시점 기준으로 한 번 더 검증할 수 있다. |
| 쿠폰 수량 최종 차감 | X | O | 수량 차감은 선착순 성공/실패를 결정하는 핵심 처리이므로 Worker에서 순서와 동시성을 고려해 처리한다. |
| DB 발급 기록 저장 | X | O | 실제 발급 성공이 확정된 뒤 저장해야 하므로 비동기 처리 영역에서 수행한다. |
| 사용자에게 요청 접수 응답 | O | X | 사용자의 HTTP 요청에 응답하는 주체는 API Server이다. |
| 발급 성공/실패 최종 결정 | X | O | 최종 성공 여부는 쿠폰 잔여 수량, 중복 발급 여부, 처리 순서에 따라 결정되므로 Worker가 처리한다. |

## 과제 5. 요청 접수 성공 응답 반환 시점

### 1. 요청 접수 성공 응답을 반환해야 하는 시점

API Server는 요청이 유실되지 않을 정도로 안전하게 저장되거나 전달된 뒤 사용자에게 요청 접수 성공 응답을 반환해야 한다.

즉, 단순히 요청을 메모리에 올린 순간이나 요청 검증이 끝난 순간은 부족하다. 최소한 요청 상태가 DB에 `PENDING`으로 저장되었거나, Queue 또는 Kafka에 안전하게 전달된 뒤 응답해야 한다.

### 2. 요청이 메모리에만 있는 상태에서 응답할 때의 문제

요청이 메모리에만 있는 상태에서 사용자에게 접수 성공 응답을 반환하면 API Server 장애 시 요청이 유실될 수 있다.

사용자는 "쿠폰 발급 요청이 접수되었습니다."라는 응답을 받았지만, 서버가 종료되면 해당 요청을 복구할 방법이 없다. 이후 사용자가 결과를 조회해도 요청 기록이 존재하지 않을 수 있다. 이는 시스템 신뢰성을 크게 떨어뜨린다.

### 3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식

장점은 다음과 같다.

```text
- 요청이 DB에 남기 때문에 서버 장애가 발생해도 복구할 수 있다.
- 사용자가 requestId로 처리 상태를 조회할 수 있다.
- 요청 접수와 최종 발급 상태를 명확히 구분할 수 있다.
- Worker가 PENDING 상태의 요청을 기준으로 후속 처리를 진행할 수 있다.
```

단점은 다음과 같다.

```text
- 요청마다 DB 쓰기가 발생한다.
- 트래픽이 매우 많으면 PENDING 저장 테이블도 부하 지점이 될 수 있다.
- Worker가 PENDING 요청을 안정적으로 가져가 처리하는 구조가 필요하다.
```

### 4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식

장점은 다음과 같다.

```text
- Worker가 처리할 수 있는 흐름에 들어갔다는 것을 보장할 수 있다.
- Queue나 Kafka가 내구성을 제공한다면 요청 유실 가능성을 줄일 수 있다.
- API Server와 Worker의 책임 분리가 명확하다.
```

단점은 다음과 같다.

```text
- Queue 또는 Kafka 전달 실패를 처리해야 한다.
- 메시지 전달 성공 여부 확인 때문에 응답이 약간 늦어질 수 있다.
- 메시지 중복 소비, 재시도, 순서 보장 같은 추가 설계가 필요하다.
- Queue에 전달되었지만 상태 조회용 데이터가 없다면 사용자가 결과를 확인하기 어렵다.
```

### 5. 선택한 방식과 이유

내가 선택한 방식은 요청 상태를 DB에 `PENDING`으로 저장한 뒤 응답하는 방식이다.

이유는 사용자가 요청 접수 응답을 받은 뒤 상태 조회를 할 수 있어야 하기 때문이다. DB에 `PENDING` 상태가 저장되어 있으면 API Server가 장애로 종료되어도 요청 기록이 남는다. 이후 Worker가 해당 요청을 처리하면서 상태를 `SUCCESS` 또는 `FAILED`로 변경할 수 있다.

추가로 Queue를 사용한다면 DB에 `PENDING`으로 저장한 뒤 Queue에 전달하고 Worker가 처리하는 구조가 더 안정적이다. 다만 이번 과제의 핵심은 세부 기술보다 전체 요청 처리 구조이므로, 최소 기준은 "메모리가 아니라 영속 저장소에 접수 기록을 남긴 뒤 응답한다"로 잡는 것이 적절하다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각하기

### 1. 비동기 처리가 유리한 상황

비동기 처리는 다음 상황에서 동기 처리보다 유리할 수 있다.

```text
- 요청량이 짧은 시간에 급격히 몰리는 경우
- 최종 결과를 즉시 응답하지 않아도 되는 경우
- 처리 시간이 오래 걸리는 작업이 포함된 경우
- 외부 시스템 호출이나 부가 작업이 많은 경우
- API Server의 응답 시간을 짧게 유지해야 하는 경우
```

### 2. 동기 처리가 더 적합한 상황

동기 처리는 다음 상황에서 더 단순하고 적합할 수 있다.

```text
- 요청량이 많지 않은 경우
- 사용자가 즉시 최종 결과를 알아야 하는 경우
- 처리 로직이 짧고 단순한 경우
- 실패 여부를 즉시 알려줘야 하는 경우
- 별도의 Worker, Queue, 상태 관리가 과한 경우
```

### 3. 비동기 처리 구조의 추가 복잡도

비동기 처리 구조를 사용하면 다음과 같은 복잡도가 생긴다.

```text
- 요청 상태 관리가 필요하다.
- 사용자가 결과를 조회할 API가 필요하다.
- Worker 장애와 재시도 처리가 필요하다.
- 중복 처리 방지가 필요하다.
- 메시지 유실 방지 설계가 필요하다.
- 최종 일관성을 고려해야 한다.
- 운영 모니터링 포인트가 늘어난다.
```

### 4. 최종 결과를 바로 알아야 하는 기능에서의 비동기 처리

사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합하지는 않다.

예를 들어 결제 승인, 로그인, 비밀번호 변경처럼 즉시 성공/실패를 알아야 하는 기능은 동기 처리가 더 적합할 수 있다. 이런 기능을 비동기로 처리하면 사용자가 현재 상태를 알기 어렵고 사용자 경험이 나빠질 수 있다.

### 5. 이번 선착순 쿠폰 이벤트에서 비동기가 더 적합한 이유

이번 선착순 쿠폰 이벤트에서는 비동기 처리가 더 적합하다.

이유는 이벤트 시작 직후 요청이 매우 짧은 시간에 몰리고, 쿠폰 수량은 제한되어 있으며, 모든 요청을 API Server와 DB가 즉시 처리하면 병목이 발생하기 쉽기 때문이다.

사용자는 최종 결과를 즉시 받는 대신 요청 접수 응답을 먼저 받고, 이후 결과 조회를 통해 발급 성공 여부를 확인할 수 있다. 이렇게 하면 API Server는 요청 접수 역할에 집중하고, 실제 발급 처리는 Worker가 순차성, 중복 여부, 수량 차감을 고려해 안정적으로 처리할 수 있다.

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석

### 1. 동기 / 블로킹

```text
Caller
  -> 작업 요청
  -> 작업이 끝날 때까지 대기
  <- 결과 반환
  -> 다음 로직 실행
```

동기/블로킹은 작업 결과를 같은 흐름에서 받고, 결과가 올 때까지 현재 실행 흐름도 멈추는 방식이다.

예를 들어 API Server가 DB에 조회 요청을 보내고 DB 응답이 올 때까지 기다리는 경우가 이에 해당한다.

```text
API Server
  -> DB 조회 요청
  -> DB 응답이 올 때까지 대기
  <- DB 결과 수신
  -> 결과 처리
```

가장 일반적인 동기 DB 호출 방식이다.

### 2. 동기 / 논블로킹

```text
Caller
  -> 작업 요청
  <- 아직 완료되지 않음
  -> 다른 작업 수행
  -> 완료 여부 반복 확인
  <- 결과 확인
```

동기/논블로킹은 결과를 같은 흐름에서 직접 확인하지만, 기다리는 동안 실행 흐름이 완전히 멈추지는 않는 방식이다. 대신 호출자가 작업 완료 여부를 직접 확인해야 한다.

예를 들어 non-blocking 소켓을 사용하는 경우 데이터가 아직 준비되지 않았다면 즉시 반환되고, 호출자가 나중에 다시 읽기를 시도한다. 결과를 직접 확인한다는 점에서는 동기적이지만, 데이터가 준비될 때까지 멈춰 있지 않는다는 점에서는 논블로킹이다.

### 3. 비동기 / 블로킹

```text
Caller
  -> 작업을 다른 흐름에 맡김
  -> 결과를 기다리며 대기
  <- 결과 수신
```

비동기/블로킹은 작업 자체는 다른 흐름에서 처리되지만, 호출자가 그 결과를 기다리며 멈춰 있는 방식이다.

쿠폰 발급 구조에서는 다음과 같은 흐름이 예시가 될 수 있다.

```text
API Server
  -> Queue에 요청 전달
  -> Worker가 처리
  -> API Server가 Worker 결과를 기다림
  <- 최종 결과 응답
```

Queue를 사용하더라도 API Server가 Worker 결과를 기다리면 비동기 처리의 장점이 줄어든다. 이는 과제 2의 구조 A에서 피해야 하는 형태이다.

### 4. 비동기 / 논블로킹

```text
Caller
  -> 작업을 다른 흐름에 맡김
  <- 즉시 반환
  -> Caller는 다른 작업 수행

Worker
  -> 실제 작업 처리
  -> 결과 저장 또는 이벤트 발행
```

비동기/논블로킹은 작업 흐름과 결과 처리 흐름이 분리되고, 호출자는 작업 완료를 기다리지 않는 방식이다.

이번 쿠폰 발급 구조에서는 다음 흐름이 이에 해당한다.

```text
Client
  -> API Server
  -> 요청 접수
  <- PENDING 응답

Worker
  -> 뒤에서 쿠폰 발급 처리
  -> 상태를 SUCCESS 또는 FAILED로 변경
```

선착순 쿠폰 발급처럼 요청이 짧은 시간에 몰리는 상황에서는 이 구조가 가장 적합하다.

### 5. 이번 선착순 쿠폰 발급 구조에 등장하는 조합

이번 쿠폰 발급 구조에 등장하는 조합은 다음과 같다.

```text
동기 / 블로킹:
API Server가 로그인 여부 확인, 이벤트 시간 확인, PENDING 상태 저장 등을 DB나 인증 시스템에 요청하고 응답을 기다리는 구간에서 등장할 수 있다.

비동기 / 논블로킹:
API Server가 요청을 접수한 뒤 최종 발급 결과를 기다리지 않고 사용자에게 PENDING 응답을 반환하는 구간에서 등장한다.

비동기 / 블로킹:
구조 A처럼 Queue에 요청을 넣고도 API Server가 Worker 결과를 기다리는 잘못된 구조에서 등장한다. 이번 설계에서는 피해야 할 조합이다.

동기 / 논블로킹:
일반적인 쿠폰 발급 설계의 핵심 흐름에는 반드시 등장하지 않는다. 다만 non-blocking IO를 사용하면서 호출자가 완료 여부를 직접 확인하는 낮은 수준의 구현에서는 등장할 수 있다.
```

정리하면 이번 과제에서 선택해야 하는 핵심 구조는 API Server가 요청을 안전하게 접수한 뒤 빠르게 `PENDING` 응답을 반환하고, Worker가 뒤에서 실제 쿠폰 발급 성공/실패를 결정하는 구조이다. 사용자는 결과 조회 API를 통해 최종 상태를 확인한다.
