# 1주차 과제: 요청 처리 구조 설계

---

## 과제 1. 동기/비동기 처리 구조를 전체 요청 처리 순서에 맞게 다이어그램으로 그리기

### 동기 처리 구조

```
Client
  │
  ▼
API Server
  │ (1) DB에서 쿠폰 수량 조회       → 완료될 때까지 대기
  │ (2) 중복 발급 여부 확인         → 완료될 때까지 대기
  │ (3) DB에 쿠폰 발급 기록 저장    → 완료될 때까지 대기
  │ (4) 알림 발송                   → 완료될 때까지 대기
  │ (5) 마이페이지 데이터 갱신      → 완료될 때까지 대기
  ▼
Client에게 최종 성공/실패 응답 반환
```

모든 처리가 하나의 요청 흐름 안에서 순서대로 실행된다.  
각 단계가 완료될 때까지 다음 단계로 넘어가지 않으며, 클라이언트는 최종 결과가 나올 때까지 기다려야 한다.

---

### 비동기 처리 구조

```
Client
  │
  ▼
API Server
  │ (1) 로그인 여부 확인
  │ (2) 이벤트 시간 확인
  │ (3) 요청 상태를 DB에 PENDING으로 저장
  │ (4) Queue(Kafka)에 메시지 발행
  ▼
Client에게 요청 접수 응답 반환  ← 여기서 API Server의 역할 종료

              ↓ (비동기 영역)

        ┌─────────────────────────┐
        │ Worker                  │
        │  ├ 쿠폰 수량 차감        │
        │  ├ DB 발급 기록 저장     │
        │  ├ 알림 발송             │
        │  └ 마이페이지 데이터 갱신 │
        └─────────────────────────┘

Client는 나중에 조회 API 또는 마이페이지에서 발급 결과 확인
```

---

### 두 구조의 차이

동기는 요청 흐름에서 최종 결과까지 직접 처리하므로 구조가 단순하고 사용자가 결과를 즉시 알 수 있다.  
반면 요청이 몰릴 때 API Server와 DB에 부하가 집중되고 스레드가 오래 점유된다.

비동기는 요청 접수와 실제 발급 처리를 분리해 API Server가 빠르게 응답할 수 있다.  
단, 사용자가 결과를 즉시 알 수 없어 별도의 결과 조회 구조가 필요하고, 상태 관리 등 추가적인 복잡도가 생긴다.

## 과제 2. 구조 A와 구조 B 중 더 적합한 구조 선택하기

**선택: 구조 B**

- **구조 A**: Queue를 사용하지만 API Server가 Worker 처리 결과를 기다린 뒤 Client에 최종 응답하는 구조
- **구조 B**: API Server가 요청을 접수한 직후 Client에 응답하고, Worker가 독립적으로 뒤에서 처리하는 구조

---

**1. 선착순 쿠폰 이벤트에 더 적합한 구조는 무엇인가?**

구조 B.  
이벤트 시작 직후 초당 수천 건의 요청이 몰리는 상황에서 API Server가 빠르게 요청을 접수하고 응답하는 것이 중요하다.  
구조 B는 Worker 처리 결과를 기다리지 않으므로 스레드가 빠르게 반환되어 다음 요청을 처리할 수 있다.

**2. 구조 A는 Queue를 사용했는데도 왜 비동기 처리의 장점이 줄어드는가?**

API Server가 Worker의 결과를 기다리는 동안 해당 스레드는 계속 점유된다.  
Queue를 사이에 뒀지만 결국 요청 흐름이 Worker 완료 시점까지 묶여 있으므로, 동기 처리와 동일하게 스레드 고갈과 응답 지연이 발생할 수 있다.

**3. API Server가 Worker 결과를 기다리면 어떤 문제가 생기는가?**

- API Server 스레드가 Worker 처리 시간만큼 계속 점유된다.
- 요청이 몰릴 때 스레드 풀이 빠르게 소진된다.
- Worker에 장애가 생기면 API Server 응답도 타임아웃된다.
- Queue를 사용해도 결국 동기 처리와 동일한 병목이 발생한다.

**4. 구조 B를 선택한다면 사용자는 최종 발급 결과를 어떻게 확인해야 하는가?**

API Server로부터 `{ "status": "PENDING", "message": "쿠폰 발급 요청이 접수되었습니다." }` 응답을 받은 뒤,  
발급 상태 조회 API를 폴링하거나 마이페이지에서 ISSUED/FAILED 여부를 직접 확인한다.

## 과제 3. 나쁜 설계의 문제점을 찾고 개선하기

**나쁜 설계 (현재 구조):**

```
Client (다수의 동시 요청)
  → API Server
      → DB에서 쿠폰 수량 조회 (남은 수량 확인)
      → DB에 쿠폰 발급 기록 저장 (발급 처리)
      → 알림 발송
      → 마이페이지 데이터 갱신
  → Client에게 성공 응답
```

---

**1. 이 설계에서 문제가 될 수 있는 부분 5개 이상**

1. **API Server가 너무 많은 책임을 진다.**  
   발급 처리, 알림, 마이페이지 갱신까지 한 곳에서 동기로 처리하므로 코드 복잡도와 장애 영향 범위가 커진다.

2. **요청이 몰리면 DB에 부하가 집중된다.**  
   다수의 요청이 동시에 DB 조회와 저장을 수행하므로 커넥션 풀 고갈과 Lock 경합이 발생할 수 있다.

3. **서비스 간 강한 결합이 발생한다.**  
   API Server가 알림 서비스, 마이페이지 서비스를 직접 호출하므로 한 서비스 장애가 전체 흐름을 멈출 수 있다.

4. **알림 발송 실패가 쿠폰 발급 응답에 영향을 준다.**  
   알림 서비스가 느리거나 장애가 나면 쿠폰 발급 응답 자체가 지연되거나 실패로 처리될 수 있다.

5. **동시 요청에서 중복 발급이 발생할 수 있다.**  
   수량 조회와 저장 사이에 다른 요청이 끼어들 수 있어, 같은 시점에 여러 요청이 모두 "수량 있음"으로 판단하고 발급에 성공할 수 있다.

6. **요청 접수와 실제 발급 처리가 분리되지 않는다.**  
   API Server가 모든 처리를 끝낼 때까지 스레드를 점유하므로, 트래픽이 몰리면 스레드 풀이 빠르게 고갈된다.

---

**2. API Server가 너무 많은 일을 하면 어떤 문제가 생기는가?**

단일 장애 지점이 되어 하나의 처리 실패가 전체 응답 실패로 이어진다.  
또한 알림 서비스 지연처럼 부수적인 작업 하나가 전체 응답 시간을 늘리고, 서비스별 독립 배포와 확장이 어려워진다.

---

**3. 알림 발송이나 마이페이지 데이터 갱신이 실패하면 쿠폰 발급 응답에 어떤 영향을 줄 수 있는가?**

같은 흐름 안에 묶여 있으므로, 알림 발송이 실패하면 이미 DB에 쿠폰 발급이 저장되었더라도 오류 응답을 반환하거나 트랜잭션 롤백이 발생할 수 있다.  
비즈니스 핵심인 쿠폰 발급이 부수적인 작업 때문에 실패하는 구조다.

---

**4. 요청 접수와 실제 발급 처리를 분리하는 구조로 개선하라.**

```
Client (다수의 동시 요청)
  → API Server
      → 요청 검증 (로그인 여부, 이벤트 시간 확인)
      → 요청 상태를 DB에 PENDING으로 저장
      → Queue(Kafka)에 메시지 발행
  → Client에게 요청 접수 응답 반환

Queue
  → Worker (비동기)
      → 쿠폰 수량 차감 및 발급 처리
      → DB 발급 기록 저장
      → 알림 발송 (Worker 내부에서 비동기 처리)
      → 마이페이지 데이터 갱신 (Worker 내부에서 비동기 처리)

Client는 나중에 조회 API 또는 마이페이지에서 최종 결과 확인
```

API Server는 요청 검증과 접수만 담당하고, 무거운 DB 작업과 후속 처리는 Worker가 비동기로 처리한다.  
알림이나 마이페이지 갱신 실패가 쿠폰 발급 자체에 영향을 주지 않는다.

## 과제 4. API Server가 직접 처리할 일과 비동기 처리 영역으로 넘길 일 나누기

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유 |
| --- | :---: | :---: | --- |
| 로그인 여부 확인 | ✓ | | 인증되지 않은 요청은 즉시 거절해야 한다. 비동기로 넘기면 불필요한 메시지가 Queue에 쌓인다. |
| 이벤트 시간 확인 | ✓ | | 이벤트 시간이 아니면 요청 자체가 무효다. 빠르게 거절할수록 불필요한 처리를 줄일 수 있다. |
| 쿠폰 수량 최종 차감 | | ✓ | 동시성 제어가 필요한 작업으로, Worker에서 원자적으로 처리해야 한다. API Server가 직접 처리하면 Race Condition이 발생한다. |
| DB 발급 기록 저장 | | ✓ | 무거운 DB 쓰기 작업이므로 API Server가 직접 처리하면 트래픽 집중 시 병목이 생긴다. |
| 사용자에게 요청 접수 응답 | ✓ | | 요청 접수 응답은 API Server가 빠르게 반환해야 한다. 비동기로 넘길 수 없다. |
| 발급 성공/실패 최종 결정 | | ✓ | 실제 DB 저장 결과에 따라 결정되므로 Worker가 처리 후 상태를 업데이트해야 한다. |

## 과제 5. 요청 접수 성공 응답을 언제 반환할 수 있는지 설계하기

**선택: 요청 상태가 DB에 PENDING으로 저장된 순간**

---

**1. API Server는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?**

요청 상태가 DB에 PENDING으로 저장된 것을 확인한 직후.  
이 시점에서는 API Server가 재시작되거나 장애가 발생해도 DB에 요청 기록이 남아 있으므로 유실 없이 재처리가 가능하다.

**2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?**

API Server가 응답 직후 장애로 종료되면 메모리에 있던 요청 데이터가 사라진다.  
사용자는 접수 응답을 받았지만 실제로 요청이 처리되지 않는 상황이 발생하고, 이를 추적하거나 복구할 방법이 없다.

**3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식의 장단점**

- **장점**: 서버 재시작 후에도 PENDING 상태로 재처리 가능하다. 요청 상태 추적이 쉽고 유실 위험이 없다.
- **단점**: 응답 전에 DB 쓰기가 발생하므로 응답 시간이 약간 늘어난다. 트래픽 집중 시 DB에 추가 쓰기 부하가 생긴다.

**4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식의 장단점**

- **장점**: Kafka 브로커에 저장됐으므로 요청 유실 없이 처리 보장이 가능하다.
- **단점**: Kafka 장애 시 응답 자체가 지연된다. DB에 PENDING 상태가 없으면 요청을 추적하기 어렵다.

**5. 내가 선택한 방식과 이유**

DB에 PENDING 저장 후 응답을 선택한다.  
Kafka에만 의존할 경우 Kafka 장애 시 요청 추적이 불가능하다. DB에 PENDING을 저장해두면 서버 장애나 Kafka 장애 상황에서도 어떤 요청이 접수됐는지 파악하고 재처리할 수 있다.  
응답 시간이 약간 늘어나는 단점이 있지만, 요청 유실 없는 안전한 접수 보장이 더 중요하다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각해보기

**1. 비동기 처리가 동기 처리보다 유리한 상황**

- 대규모 트래픽이 짧은 시간에 집중되는 경우 (예: 선착순 이벤트)
- 처리 시간이 길어서 사용자가 기다리기 어려운 경우 (예: 이메일 발송, 보고서 생성)
- 처리 결과를 즉시 알지 않아도 되는 경우
- 여러 서비스가 같은 이벤트를 독립적으로 소비해야 하는 경우

**2. 동기 처리가 더 단순하고 적합한 상황**

- 사용자가 처리 결과를 즉시 알아야 하는 경우 (예: 로그인, 결제 성공/실패 확인)
- 트래픽이 적고 처리 속도가 빠른 경우
- 트랜잭션 일관성이 중요하고 복잡한 보상 처리를 피하고 싶은 경우
- 팀 규모가 작아 메시지 인프라 운영 부담을 최소화해야 하는 경우

**3. 비동기 처리 구조를 사용하면 생기는 추가 복잡도**

- 요청 상태 관리 필요 (PENDING / PROCESSING / ISSUED / FAILED)
- 결과 조회 API 또는 마이페이지 조회 구조 추가 필요
- Kafka, Consumer 등 메시지 인프라 운영 부담
- 메시지 중복 처리, 실패 메시지 재처리 설계 필요

**4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기가 항상 적합한가?**

아니다.  
결제 완료 여부, 로그인 성공 여부처럼 즉각적인 결과가 UX의 핵심인 경우에는 비동기 구조가 오히려 사용자 경험을 해친다.  
비동기는 "결과를 나중에 확인해도 되는 흐름"에서 의미가 있다.

**5. 이번 선착순 쿠폰 이벤트에서 비동기 처리가 더 적합한 이유**

이벤트 시작 직후 1분 내 최대 10만 건(약 1,667 RPS, 실제 피크는 수 배)의 요청이 몰린다.  
이 상황에서 모든 요청을 동기로 DB까지 처리하면 커넥션 풀 고갈, Lock 경합, 응답 지연이 발생한다.  
또한 이번 시스템은 쿠폰 발급 결과를 즉시 받지 않아도 마이페이지에서 확인 가능하다는 전제가 있으므로, 비동기 구조가 적합하다.

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석하기

### 개념 정의

```
동기/비동기: 요청한 작업의 결과를 같은 요청 흐름에서 직접 받아 처리하는가?
블로킹/논블로킹: 작업이 끝날 때까지 현재 실행 흐름이 멈추는가?
```

---

### 1. 4가지 조합 설명

**① 동기 / 블로킹**

```
Thread A
  │── DB 저장 요청 ──▶ DB
  │   (완료될 때까지 멈춤)
  │◀─────────────────── DB 응답
  │── 다음 로직 실행
```

Thread A가 DB 응답이 올 때까지 아무것도 하지 못하고 멈춰 있다.  
요청 흐름에서 결과를 직접 받고(동기), 기다리는 동안 흐름이 멈춘다(블로킹).  
가장 일반적인 방식으로, 전통적인 JDBC 기반 DB 호출이 이에 해당한다.

---

**② 동기 / 논블로킹**

```
Thread A
  │── 작업 요청 ──▶ (즉시 제어권 반환)
  │── 완료됐나? 확인 (폴링 또는 I/O 멀티플렉싱)
  │── 완료됐나? 확인
  │◀── 완료 신호
  │── 결과 처리 (같은 흐름에서 직접 처리)
```

Thread A가 멈추지 않고 완료 여부를 확인하며, 결과는 같은 흐름에서 직접 처리한다(동기).  
기다리는 동안 흐름이 멈추지 않는다(논블로킹).  
바쁜 폴링(busy polling) 방식에서는 CPU를 낭비할 수 있지만, epoll/select 같은 I/O 멀티플렉싱으로 구현하면 효율적으로 동작한다.

---

**③ 비동기 / 블로킹**

```
Thread A                        Thread B (Worker)
  │── 작업 요청 ─────────────▶ │── 실제 작업 수행
  │   (Thread A 멈춤, 대기)     │
  │                             │── 완료
  │◀──────────────────────────  │
  │── 결과 처리
```

작업은 다른 흐름(Thread B)에서 처리되지만(비동기), Thread A는 그 결과가 올 때까지 멈춰서 기다린다(블로킹).  
Java에서 `Future.get()`을 즉시 호출하는 경우가 대표적인 예다.  
과제 2의 구조 A가 이 패턴에 해당한다. Queue를 사용해도 결과를 기다리면 이 조합이 된다.

---

**④ 비동기 / 논블로킹**

```
Thread A                        Worker (별도 처리)
  │── Kafka 메시지 발행 ───────▶ │── 쿠폰 발급 처리
  │── 즉시 응답 반환             │── DB 저장
  │   (흐름 멈추지 않음)         │── 상태 업데이트
  ▼
Client에게 접수 응답

(나중에 Client가 조회 API로 결과 확인)
```

요청 흐름과 처리 흐름이 완전히 분리되고(비동기), Thread A도 멈추지 않는다(논블로킹).  
현대 대규모 트래픽 시스템에서 가장 많이 사용하는 패턴이다.

---

### 2. 선착순 쿠폰 발급 구조에 실제로 등장하는 조합

| 조합 | 등장 여부 | 등장 위치 |
| --- | :---: | --- |
| 동기 / 블로킹 | ✓ | API Server에서 요청 검증(로그인 확인, 이벤트 시간 확인) 시. 검증 결과를 즉시 받아야 하고, 그 동안 흐름이 멈춘다. |
| 동기 / 논블로킹 | ✗ | 이번 구조에는 등장하지 않는다. |
| 비동기 / 블로킹 | ✗ | 설계상 API Server가 Worker 결과를 기다리지 않으므로 등장하지 않는다. (구조 A를 선택하지 않은 이유다.) |
| 비동기 / 논블로킹 | ✓ | API Server가 Kafka에 메시지를 발행한 뒤 즉시 접수 응답을 반환하고, Worker가 독립적으로 쿠폰 발급을 처리하는 전체 흐름. 이번 시스템의 핵심 패턴이다. |

실제 쿠폰 발급 시스템에서 주로 등장하는 조합은 **동기/블로킹** (API Server 내부 검증 단계)과 **비동기/논블로킹** (Kafka 기반 발급 처리) 두 가지다.  
요청 흐름 앞단은 동기/블로킹으로 빠르게 검증하고, 실제 발급 처리는 비동기/논블로킹으로 분리하는 것이 이번 설계의 핵심이다.
