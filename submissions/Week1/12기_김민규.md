## 과제 1. 동기 처리와 비동기 처리 구조를 전체 요청 처리 순서에 맞게 다이어그램으로 그리기

쿠폰 발급 요청이 들어왔을 때 동기 처리 방식과 비동기 처리 방식이 각각 어떤 순서로 동작하는지 다이어그램으로 작성한다.

그림 아래에는 두 구조의 차이를 간단히 설명한다.

<img width="1077" height="715" alt="Image" src="https://github.com/user-attachments/assets/5241a376-7f48-4ea4-a807-40530ed4493b" />

### 동기 처리
동기 처리 방식은 Client에서 쿠폰 발급 요청을 받으면 쿠폰 발급 결과가 나올 때 까지 결과를 기다렸다가 쿠폰 발급에 대한 결과를 사용자에게 반환해준다.
### 비동기 처리
비동기 처리 방식은 Client에서 쿠폰 발급 요청을 받으면 해당 요청에 대한 접수 결과만 바로 반환한다.
그 후 실제 쿠폰 발급 과정은 서버에서 처리하고 결과는 사용자가 나중에 마이페이지나 조회 API를 이용하여 조회한다.

    이후 조회 요청을 따로 구현해 쿠폰이 성공적으로 발급되었는지 확인한다.
```

## 과제 4. API Server가 직접 처리할 일과 비동기 처리 영역으로 넘길 일을 나누기

쿠폰 발급 요청이 들어왔을 때 API Server가 직접 처리해야 하는 일과, 비동기 처리 영역으로 넘겨야 하는 일을 구분한다.

아래 작업들을 기준으로 나누고 이유를 작성한다.

```
- 로그인 여부 확인
- 이벤트 시간 확인
- 쿠폰 수량 최종 차감
- DB 발급 기록 저장
- 사용자에게 요청 접수 응답
- 발급 성공/실패 최종 결정
```

아래 표 형식으로 작성한다.

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유                                                                                 |
| --- |-----------------|----------------|------------------------------------------------------------------------------------|
| 로그인 여부 확인 | O               |                | 요청이 인증된 사용자게에서 온 것인지 확인하기 위해 매 요청마다 API 서버에서 확인해야 한다.                              |
| 이벤트 시간 확인 | O               |                | API 서버단에서 요청을 유효한 시간에만 받으면 서버에 부하를 줄이고 큐에 불필요한 요청이 쌓이지 않게된다.                   |
| 쿠폰 수량 최종 차감 |                 | O              | 쿠폰 발급 요청에 대해서 비동기로 넘겨 큐에 저장하고 차례대로 쿠폰 발급 절차를 밟아 쿠폰의 최종 수량을 차감하기 때문에 비동기 영역에서 처리해야한다. |
| DB 발급 기록 저장 |                 | O              | 비동기 영역에서 쿠폰을 성공적으로 발행하고 이를 DB에 저장하는 것 역시 비동기 영역에서 처리한다.                            |
| 사용자에게 요청 접수 응답 | O               |                | 사용자가 쿠폰 발급 요청을 한 경우 응답만 바로 API 서버에서 반환하고 발급 절차는 비동기 영역에서 처리하기 때문이다.                |
| 발급 성공/실패 최종 결정 |                 | O              | 비동기 영역에서도 여러 워커가 동시에 처리할 가능성이 존재하기 때문에 원자적 연산을 추가로 비동기 영역에서 실행하여 처리한다.             |

## 과제 5. 요청 접수 성공 응답을 언제 반환할 수 있는지 설계하기

비동기 처리 구조에서는 API Server가 사용자에게 다음과 같은 응답을 반환할 수 있다.

```
쿠폰 발급 요청이 접수되었습니다.
```

하지만 이 응답을 아무 때나 반환하면 안 된다.

예를 들어 요청이 메모리에만 있는 상태에서 응답했는데 API Server가 장애로 종료되면 요청이 유실될 수 있다.

따라서 API Server가 언제 사용자에게 요청 접수 성공 응답을 반환할 수 있는지 설계해야 한다.

다음 질문에 답한다.

```
1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?
    -> Queue 또는 Kafka에 안전하게 전달된 순간이다.
    
2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?
    -> 요청이 메모리에 올린 순간에 바로 사용자에게 응답을 반환하면 메모리가 오류난 상황에서 요청이 유실될 가능성이 존재하기 때문이다.
    
3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    -> 요청이 DB에 영구적으로 저장되어서 유실될 가능성이 없고 요청 상태 추적이 쉬워진다.
    하지만 모든 요청마다 DB 쓰기 작업이 발생하여 DB에 부하가 늘어나고 PENDING 상태 요청에 대한 구현이 복잡해진다.
    
4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    -> 요청이 비동기 처리 영역에 저장되어서 유실되지 않는다.
    하지만 큐나 카프카가 다운되면 요청을 받을 수 없고 응답 시간이 Kafka 전달까지 기다려야 해서 증가한다.
    
    
5. 내가 선택한 방식과 그 이유를 설명하라.
    -> Kafka에 성공적으로 요청을 접수한 후에 성공 요청을 반환할 것이다.
    왜냐하면 kafka에 성공적으로 들어간 순간으로 요청을 반환하면 비동기 처리 전에 들어가기 전에 오류가 발생한 경우에 대해
    빠르게 실패 응답을 반환할 수 있고 Kafka에서 실패한 경우에 대해서는 재시도 로직을 작성하여 사용자 요청에 대한 처리를 보장할 수 있기 때문이다.
```

참고로 요청 접수 성공의 기준은 다음 중 하나로 생각해볼 수 있다.

```
1. 요청을 메모리에 올린 순간
2. 요청 검증이 끝난 순간
3. 요청 상태가 DB에 PENDING으로 저장된 순간
4. Queue 또는 Kafka에 안전하게 전달된 순간
```

단순히 빠르게 응답하는 것만 생각하지 말고, 사용자가 접수 응답을 받은 뒤 요청이 유실되지 않도록 하려면 어떤 기준이 필요한지 고민한다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각해보기

비동기 처리는 대규모 트래픽 상황에서 유리할 수 있다.

하지만 항상 비동기가 더 좋은 것은 아니다.

다음 질문에 답한다.

```
1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?
    -> 비동기 처리가 유리한 상황은 요청이 쓰레드를 오래 잡고 있는 상황이나 
    트래픽이 몰릴 것으로 예상되는 상황에서 DB작업이 동반되는 경우 등이 존재한다.

2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?
    -> 요청에 대한 작업이 비교적 간단하고 사용자에게 바로 응답을 줄 수 있는 경우
    굳이 비동기 처리 방식을 선택할 필요가 없다.
    
3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?
    -> 비동기 처리 구조를 사용하면 요청 처리에 대한 결과만 바로 반환하기 때문에 
    요청 결과를 조회하는 API를 따로 제작해야한다.
    또한 메시지 큐/워커 관리 로직을 추가적으로 구현해야 한다.
    
4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?
    -> 그렇지 않다.
    비동기 처리를 하게 되면 구조적으로 더 복잡해지고 사용자 측면에서도 결과를 바로 반환하는 구조가 
    아니기 때문에 불편함을 줄 수 있다.
    따라서 트래픽이 몰리는 상황이 아니거나 굳이 비동기 처리를 할 필요가 없는 상황이면 동기 처리 방식이
    깔끔하고 단순하다.
    
5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?
    -> 그렇다.
    트래픽이 몰릴 것이라고 예상되는 상황에서 DB 작업이 동반되는데 이 때 매 요청마다 DB작업을 수행하면 
    DB 커넥션 풀이 고갈될 가능성이 존재하고 또한 요청에 대한 안정적인 처리를 하기 위해 부하를 분산하고 순차적으로
    처리하는 것이 적합하다.

```

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석하기

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 기준이 다르다.

동기/비동기는 요청한 작업의 결과를 **같은 요청 흐름에서 직접 받아 처리하는가**, 아니면 요청 흐름과 실제 처리 흐름을 분리하는가에 대한 개념이다.

블로킹/논블로킹은 **작업이 끝날 때까지** 현재 실행 흐름이 멈추는가, 아니면 바로 제어권을 돌려받는가?에 대한 개념이다.

다음 4가지 조합을 분석한다.

```
1. 동기 / 블로킹

2. 동기 / 논블로킹

3. 비동기 / 블로킹

4. 비동기 / 논블로킹
```

다음 질문에 답한다.

```
1. 아래 4가지 조합 각각이 무엇인지, 일반적인 작업 흐름(예: 함수 호출, DB 호출, 소켓 IO 등) 기준으로 다이어그램과 함께 설명하라. (쿠폰 발급 시나리오에 한정하지 않아도 된다.)
2. 이 4가지 중 이번 선착순 쿠폰 발급 구조에 실제로 등장하는 조합은 무엇인지 고르고, 어디에서 등장하는지 근거를 들어 설명하라. (4개가 다 등장하지 않을 수 있다.)

### 동기 / 블로킹 방식
동기 블로킹 방식은 요청이 같은 흐름에서 처리되고 요청을 받을 때 까지 기다리는 방식이다.
일반적으로 한 요청에 대해서 동일한 메서드 내부에서 요청을 처리하고 결과를 반환하는 방식이다.
- 쿠폰 발급에서 처음 제시된 동기 구조이다. 사용자는 쿠폰 발급을 요청하고 요청이 처리될 때까지 기다리며, 이 요청들이 한 작업 흐름에서 순차적으로 처리된다.

### 동기 / 논블로킹 방식
동기 논블로킹 방식은 요청이 같은 흐름에서 처리되지만 요청 결과를 받을 때까지 기다리지 않는 방식이다.
일반적으로 요청에 대해서 접수 결과만 바로 반환하고 같은 쓰레드에서 while 루프를 통해 계속해서 확인하는 방식이다.

### 비동기 / 블로킹 방식
비동기 블로킹 방식은 요청이 다른 흐름에서 처리되지만 요청을 받을 때 까지 기다리는 방식이다.
일반적으로 요청에 대해서 워커를 통해 처리하거나 외부 함수 호출을 통해 처리할 때처럼 다른 흐름에서 처리되지만 
그 요청 결과를 받기 위해서 기다린다.
- 구조 A에서 API 서버가 워커의 결과를 기다리는 방식이 이에 해당한다.

### 비동기 / 논블로킹 방식
비동기 논블로킹 방식은 요청이 다른 흐름에서 처리되고 그 요청을 받을 때 까지 기다리지 않는 방식이다.
일반적으로 한 요청에 대해서 요청 결과를 바로 반환하고 접수된 요청은 다른 작업 흐름에서 처리되어서 반환한다.
그리고 이 요청이 완료되었는지 확인하기 위해서는 따로 조회를 통해 결과를 확인해야 한다.
- 이번 과제에서 제시된 구조이다. 쿠폰 발급 요청을 접수하고 바로 요청에 대한 결과를 바로 반환하고 그 요청에 대한 처리는 Kafka에 적재하고 consumer를 통해 소비하여 결과를 다른 조회 API를 통해 조회하는 방식에 해당한다.
