# 선착순 쿠폰 이벤트 시스템 설계 과제

---
## 과제 1

### 동기 처리

```
Client
→ API Server
→ DB 쿠폰 수량 조회 (응답 대기)
→ DB 발급 기록 저장 (응답 대기)
→ Client에게 최종 성공/실패 응답
```

요청 하나가 발급 완료까지 한 흐름으로 끝난다. API 서버 스레드는 DB 처리가 끝날 때까지 기다린다.

### 비동기 처리

```
Client
→ API Server
→ 요청 검증 (로그인 / 이벤트 시간)
→ 요청 상태 저장 (PENDING) 또는 Kafka 전달
→ Client에게 "요청 접수됨(PENDING)" 응답   ← 여기서 API 서버 역할 끝
|
└→ Worker가 뒤에서 실제 쿠폰 발급 처리 (수량 차감, 발급 기록 저장)
└→ 사용자는 나중에 결과 조회 / 알림으로 확인
```

요청 접수와 실제 발급을 분리한다. API 서버는 발급 완료를 기다리지 않고 빠르게 응답한다.

## 과제 2

<img width="1536" height="1024" alt="과제 2" src="https://github.com/user-attachments/assets/6e1db77e-7644-4e23-94c8-2d4cc0ac105f" />

1. 두 구조 중 선착순 쿠폰 이벤트에 더 적합한 구조는 무엇인가?
    ```
   구조 A의 경우 API 서버가 Worker의 결과를 기다리는 구조이므로 요청 스레드가 오래 점유되어 동시 처리량이 떨어지게 된다. 
   반면에 구조 B의 경우 API 서버가 요청만 접수하고 바로 응답한 뒤 발급은 Worker가 뒤에서 하므로 API 서버에 병목이 발생하지 않아 선착순 쿠폰 이벤트에 더 적합하다.
    ```
2. 구조 A는 Queue를 사용했는데도 왜 비동기 처리의 장점이 줄어드는가?
    ```
   Queue를 사용하는 목적은 요청을 접수하는 속도와 쿠폰을 발급하는 속도를 분리하는 것이다. 
   하지만 구조 A는 요청을 Queue에 넣고 Worker 결과를 기다리는 구조로, Queue를 사용하여 요청과 발급의 처리 속도를 분리하는 결과를 내지 못한다. 
   따라서 비동기 처리의 장점이 줄어들게 된다.
    ```
3. API Server가 Worker 결과를 기다리면 어떤 문제가 생기는가?
    ```
   요청 스레드가 Worker 처리가 끝날 때까지 점유되어 동시 처리량이 감소하게 되고, Worker가 느려지거나 장애가 발생하면 사용자에게 지연이 전파된다.
    ```
4. 구조 B를 선택한다면 사용자는 최종 발급 결과를 어떻게 확인해야 하는가?
    ```
   구조 B를 사용하는 경우 API 서버가 최종 응답을 기다리지 않으므로 Worker가 쿠폰 발급 처리를 완료한 뒤 그 결과를 상태로 저장한다. 
   사용자는 이를 별도로 확인해야 하며 발급 완료 시 알림을 받거나, 발급 요청 ID로 쿠폰 발급 처리에 대한 상태를 직접 조회해야 한다.
    ```

1. 이 설계에서 문제가 될 수 있는 부분을 5개 이상 찾아라.
    ```
    - API 서버가 요청을 직접 처리해 요청 스레드 점유 시간이 늘어나고 이로 인해 동시 처리량이 떨어진다.
    - 알림 발송과 마이페이지 갱신 같은 부가 작업이 동기로 묶여 응답이 지연된다.
    - 모든 요청이 동기로 DB에 몰려 Lock 경합과 Connection Pool 고갈이 발생하고 이로 인해 Timeout이 발생한다.
    - 부가 기능의 장애가 핵심 기능의 장애로 이어진다.
    - 실패 시 재시도나 복구 전략이 없다.
   ```
2. API Server가 너무 많은 일을 하면 어떤 문제가 생기는가?
    ```
   API 서버가 많은 일을 하게 되면 요청 스레드 점유 시간이 늘어나게 되고, 그 결과 동시 처리량이 떨어지게 된다.

   또한 부가 기능이 쿠폰 발급과 같은 흐름에 동기로 묶여 있어, 부가 기능의 장애가 핵심 기능의 장애로 이어진다.
    ```
3. 알림 발송이나 마이페이지 데이터 갱신이 실패하면 쿠폰 발급 응답에 어떤 영향을 줄 수 있는가?
    ```
   알림 발송이나 마이페이지 데이터 갱신이 쿠폰 발급과 같은 흐름에 묶여 있으므로 쿠폰이 정상 발급되어도 부가 작업에 실패하여 사용자에게 실패로 응답될 수 있다.
    ```
4. 요청 접수와 실제 발급 처리를 분리하는 구조로 개선하라.

    ```
    Client
    → API Server
    → 요청 검증 (로그인 / 이벤트 시간 / 중복 발급)
    → 요청 상태 저장(PENDING) 또는 Kafka 전달
    → Client에게 "요청 접수됨" 응답
            |
            └→ Worker: 쿠폰 수량 차감 + 발급 기록 저장 (핵심)
                    └→ (별도) 알림 발송 / 마이페이지 갱신 → 실패해도 발급엔 영향 없음, 재시도 가능
    
    ```


핵심 발급과 부가 작업을 분리하고, 부가 작업은 실패해도 발급에 영향 주지 않도록 별도 처리 + 재시도로 뺀다.

## 과제 5

1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?
    ```
   요청에 대한 정보가 DB에 저장된 경우에 접수 성공 응답을 반환해야 한다.
    ```
2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?
    ```
   API 서버가 장애로 인해 종료되어 요청이 사라지게 되면 사용자에게는 발급이 완료되었다는 응답이 갔지만 실제 발급은 되지 않는 상황이 발생한다.
    ```
3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    ```
   장점으로는 요청 유실을 방지하며 상태 추적 및 조회가 가능해져 멱등성 처리 기반을 마련할 수 있다는 점이 있다.

   단점으로는 DB 쓰기 부하가 증가하며 발급 상태 관리 복잡성이 증가한다는 점이 있다.
    ```
4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?
    ```
   장점으로는 DB 부하가 감소하며, DB에 저장하기 전에 응답을 하므로 빠른 응답이 가능하다는 점이 있다.

   단점으로는 비동기 처리 영역에 있는 동안 서버 장애나 큐 장애가 발생하면 요청이 유실될 수 있으며, 상태 조회와 멱등성 관리가 어렵다는 점이 있다.
    ```
5. 내가 선택한 방식과 그 이유를 설명하라.
    ```
   비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식을 선택한다.

   1분에 10만 건의 요청이 들어오는 경우 빠르게 응답과 요청의 유실 가능성 두 가지를 모두 고려해야 한다. 
   메모리 영역에 있는 경우 요청 유실 가능성이 높기 때문에 적절하지 않고, 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 DB에서 병목이 발생하여 응답이 늦어질 수 있어 적절하지 않다. 
   따라서 요청 상태를 저장하는 방식보다 빠른 응답 시간을 가지며 메모리 영역에 있는 경우보다 유실 가능성이 낮은 비동기 처리 영역에 전달된 것을 확인한 후 응답하는 방식을 선택한다.
    ```

## 과제 6

1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?
    ```
   순간 트래픽이 폭증하는 상황이나, 처리량을 평준화해 부하를 조절해야 하는 경우, 사용자에게 즉시 응답할 필요가 없을 때 비동기 처리가 유리하다.
    ```
2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?
    ```
   트래픽이 많지 않고, 결과를 즉시 알려야 하는 단순한 작업의 경우 동기 처리가 더 유리하다.
    ```
3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?
    ```
   비동기 처리 구조를 사용하는 경우 요청 상태를 관리해야 하고, 결과 조회 및 알림 구조도 추가하여야 한다. 
   또한, 실패 시 재시도 및 복구 로직도 추가되어야 하고 메세지 큐와 같은 인프라 운영에 대한 복잡도도 발생한다.
    ```
4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?
    ```
   최종 결과를 바로 알아야 하는 경우, 비동기 처리 구조를 사용하면 결과 조회 및 알림 구조가 추가로 필요하므로 복잡도가 올라간다. 
   따라서 이런 경우 동기 처리가 더 적합하다.
    ```
5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?
    ```
   선착순 쿠폰 이벤트의 경우 트래픽이 폭증할 가능성이 높고, 동기적으로 처리할 경우 사용자에게 응답을 주기까지 시간이 오래걸릴 뿐만 아니라 요청 스레드 점유 시간도 길어져 동시 처리량이 떨어지게 되므로 요청과 발급을 분리하여 처리하는 비동기 처리가 더 적합하다.

   또한, 쿠폰이 1000개이고 요청이 10만 건이 넘는 경우 대부분이 쿠폰을 받지 못하게 되므로 모든 요청을 동기로 끝까지 처리할 필요가 없다.
    ```

## 과제 7

1. 아래 4가지 조합 각각이 무엇인지, 일반적인 작업 흐름(예: 함수 호출, DB 호출, 소켓 IO 등) 기준으로 다이어그램과 함께 설명하라. (쿠폰 발급 시나리오에 한정하지 않아도 된다.)
    ```
    1. 동기 / 블로킹

       최종 결과를 직접 기다리고, 기다리는 동안 실행 흐름 멈춤

       호출자 → 작업 요청
       → [결과 올 때까지 멈춰서 대기 ----]
       → 결과 받음
       → 다음 작업 수행

    2. 동기 / 논블로킹

       최종 결과를 직접 기다리지만, 실행 흐름은 멈추지 않음 (폴링 방식 사용)

       호출자 → 작업 요청
       → "아직 안 됨" 즉시 반환 → 다른 일 잠깐
       → 다시 확인 후 완료 안된 경우 → 다른 일
       → 다시 확인 후 완료된 경우 → 결과 받음

    3. 비동기 / 블로킹

       요청과 처리를 분리하였지만, 실행 흐름을 멈추고 결과를 기다림

       호출자 → 작업 등록 (결과는 Future/콜백으로 받기로 함 = 비동기)
       → 그런데 바로 future.get() 호출
       → [결과 올 때까지 멈춰서 대기 ----]   ← 분리한 의미가 사라짐
       → 결과 받음

    4. 비동기 / 논블로킹

       요청과 처리를 분리하고, 실행 흐름을 멈추지 않음

       호출자 → 작업 등록 (처리는 다른 흐름에 맡김 = 비동기)
       → 즉시 제어권 반환 → 멈추지 않고 다른 일 계속 수행
       ↓
       (작업 완료 시) 콜백/이벤트로 결과 통지받음 (논블로킹)
   ```

2. 이 4가지 중 이번 선착순 쿠폰 발급 구조에 실제로 등장하는 조합은 무엇인지 고르고, 어디에서 등장하는지 근거를 들어 설명하라. (4개가 다 등장하지 않을 수 있다.)
    ```
   - 동기 / 블로킹 조합

     API Server가 요청을 접수하기까지의 내부 단계(로그인·이벤트 시간 검증, 큐/Kafka로 메시지를 보낸 뒤 ack 확인)

     이 구간은 요청 스레드가 결과를 같은 흐름에서 직접 받고, 그 결과가 올 때까지 멈춰서 기다린다. 그래야 안전하게 처리됐음을 확인하고 응답할 수 있기 때문이다.

   - 비동기 / 논블로킹 조합

     요청을 접수하는 흐름과 실제 발급을 처리하는 흐름이 분리되어 있고, Worker가 메시지를 받아 처리하는 부분

     API Server는 발급 완료를 기다리지 않고 접수 응답만 주고 빠진다. 이후 Worker는 큐에서 메시지를 꺼내 처리하는 이벤트 기반 구조로, 하나의 작업 결과를 기다리며 멈춰 있지 않는다.
    ```
