## 과제 1. 동기 처리와 비동기 처리 구조를 전체 요청 처리 순서에 맞게 다이어그램으로 그리기
<img width="873" height="306" alt="image" src="https://github.com/user-attachments/assets/6312fc71-129e-47f3-b7e8-d72c33c7a798" />

동기 처리 구조에서는 API 서버가 쿠폰 발급 결과가 나올 때까지 모든 과정을 직접 처리한다. 그래서 사용자는 즉시 결과를 알 수 있지만, 대량 요청이 들어오면 API 서버와 DB에 부하가 집중된다.

반면 비동기 처리 구조에서는 API 서버가 요청 접수까지만 담당하고, 실제 발급은 Worker가 뒤에서 처리한다. 사용자는 먼저 요청 접수 응답을 받고, 이후 발급 결과를 조회한다.

선착순 쿠폰 이벤트처럼 짧은 시간에 많은 요청이 몰리는 상황에서는 API 서버가 최종 발급 결과까지 기다리는 동기 처리보다, 요청 접수와 발급 처리를 분리하는 비동기 처리 구조가 더 적합하다.

## 과제 2. 구조 A와 구조 B 중 더 적합한 구조 선택하기

아래 두 구조를 비교한다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/d98dc724-8951-4080-aff8-af74ff6485cd" />

#### 1. 두 구조 중 선착순 쿠폰 이벤트에 더 적합한 구조는 무엇인가?

구조 B가 더 적합하다. API 서버는 요청만 접수하고 바로 응답하며, 실제 쿠폰 발급은 Worker가 뒤에서 처리하므로 많은 요청이 몰려도 안정적으로 처리할 수 있다.

#### 2. 구조 A는 Queue를 사용했는데도 왜 비동기 처리의 장점이 줄어드는가?

API 서버가 Worker의 처리 결과를 기다리기 때문이다. Queue는 사용하지만 사용자는 여전히 최종 결과를 기다려야 하므로 응답이 늦어지고 API 서버도 오래 점유된다.

#### 3. API Server가 Worker 결과를 기다리면 어떤 문제가 생기는가?

- API 서버 스레드가 오래 점유된다.
- 응답 시간이 길어진다.
- 많은 요청이 들어오면 성능이 저하되고 Timeout이 발생할 수 있다.

#### 4. 구조 B를 선택한다면 사용자는 최종 발급 결과를 어떻게 확인해야 하는가?

API 서버는 먼저 PENDING(요청 접수) 상태를 응답하고, 사용자는 이후 조회 API 또는 마이페이지에서 SUCCESS 또는 FAILED 결과를 확인한다.

## 과제 3. 나쁜 설계의 문제점을 찾고 개선하기

다음 설계를 보고 문제가 될 수 있는 부분을 찾는다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/d501748f-4dbe-4a5c-9b5e-5ac6dde13de1" />

#### 1. 이 설계에서 문제가 될 수 있는 부분을 5개 이상 찾아라.

- API 서버가 쿠폰 발급을 끝까지 직접 처리한다.
- 모든 요청이 DB 조회와 저장을 수행해 DB 부하가 커질 수 있다.
- 알림 발송까지 끝나야 응답을 보낸다.
- 마이페이지 데이터 갱신까지 기다려야 한다.
- 요청이 많아지면 응답 시간이 길어진다.
- API 서버가 여러 작업을 처리해 장애가 발생하기 쉽다.

#### 2. API Server가 너무 많은 일을 하면 어떤 문제가 생기는가?

API 서버의 처리 시간이 길어지고 스레드가 오래 점유된다. 그 결과 응답이 느려지고, 많은 요청이 몰리면 성능 저하나 Timeout이 발생할 수 있다.

#### 3. 알림 발송이나 마이페이지 데이터 갱신이 실패하면 쿠폰 발급 응답에 어떤 영향을 줄 수 있는가?

쿠폰 발급은 성공했더라도 후속 작업이 실패하면 사용자에게 성공 응답이 늦어지거나 실패 응답이 전달될 수 있다.

#### 4. 요청 접수와 실제 발급 처리를 분리하는 구조로 개선하라.

```
Client
→ API Server (요청 검증 및 접수)
→ Queue
→ Client (PENDING 응답)

Worker
→ 쿠폰 발급 처리
→ DB 저장
→ 알림 발송
→ 마이페이지 갱신

Client
→ 조회 API 또는 마이페이지에서 최종 결과 확인
```

API 서버는 요청만 접수하고 바로 응답하며, 실제 쿠폰 발급과 후속 작업은 Worker가 처리하도록 분리한다.

## 과제 4. API Server가 직접 처리할 일과 비동기 처리 영역으로 넘길 일을 나누기

쿠폰 발급 요청이 들어왔을 때 API Server가 직접 처리해야 하는 일과, 비동기 처리 영역으로 넘겨야 하는 일을 구분한다.

아래 작업들을 기준으로 나누고 이유를 작성한다.

```
- 로그인 여부 확인
- 이벤트 시간 확인
- 쿠폰 수량 최종 차감
- DB 발급 기록 저장
- 사용자에게 요청 접수 응답
- 발급 성공/실패 최종 결정
```

아래 표 형식으로 작성한다.

| 작업 | API Server에서 처리 | 비동기 처리 영역에서 처리 | 이유 |
| --- | --- | --- | --- |
| 로그인 여부 확인 | O |  | 요청한 사용자가 누구인지 먼저 확인해야 하기 때문이다. |
| 이벤트 시간 확인 | O |  | 이벤트 시간이 아니면 요청을 접수하지 않아야 하기 때문이다. |
| 쿠폰 수량 최종 차감 |  | O | 실제 발급 성공 여부와 관련된 핵심 처리이므로 Worker가 처리한다. |
| DB 발급 기록 저장 |  | O | 실제 쿠폰 발급 결과를 저장하는 작업이므로 비동기로 처리한다. |
| 사용자에게 요청 접수 응답 | O |  | API 서버가 요청을 접수했다는 응답을 빠르게 반환해야 하기 때문이다. |
| 발급 성공/실패 최종 결정 |  | O | 쿠폰 수량, 중복 발급 여부 등을 확인한 뒤 Worker가 최종 결정해야 하기 때문이다. |

## 과제 5. 요청 접수 성공 응답을 언제 반환할 수 있는지 설계하기

비동기 처리 구조에서는 API Server가 사용자에게 다음과 같은 응답을 반환할 수 있다.

```
쿠폰 발급 요청이 접수되었습니다.
```

하지만 이 응답을 아무 때나 반환하면 안 된다.

예를 들어 요청이 메모리에만 있는 상태에서 응답했는데 API Server가 장애로 종료되면 요청이 유실될 수 있다.

따라서 API Server가 언제 사용자에게 요청 접수 성공 응답을 반환할 수 있는지 설계해야 한다.


#### 1. API 서버는 언제 사용자에게 요청 접수 성공 응답을 반환해야 하는가?

API 서버는 요청이 유실되지 않도록 DB에 PENDING 상태로 저장되거나 Queue에 안전하게 전달된 뒤 요청 접수 성공 응답을 반환해야 한다.

#### 2. 요청이 메모리에만 있는 상태에서 응답하면 어떤 문제가 생기는가?

API 서버가 장애로 종료되면 메모리에 있던 요청이 사라질 수 있다. 사용자는 접수 성공 응답을 받았지만 실제로는 쿠폰 발급 처리가 진행되지 않는 문제가 생긴다.

#### 3. 요청 상태를 PENDING으로 저장한 뒤 응답하는 방식은 어떤 장단점이 있는가?
장점: 요청이 DB에 남기 때문에 서버가 장애 나도 유실을 줄일 수 있고, 사용자가 이후 상태를 조회할 수 있다는 점이다.

단점: 모든 요청이 DB에 저장되므로 트래픽이 몰릴 때 DB 부하가 커질 수 있다.

#### 4. 비동기 처리 영역에 전달된 것을 확인한 뒤 응답하는 방식은 어떤 장단점이 있는가?

장점: Worker가 처리할 수 있는 영역까지 요청이 전달된 뒤 응답하므로 요청 유실 가능성이 낮다.

단점: Queue나 Kafka 전달 결과를 확인해야 하므로 메모리에만 올리는 방식보다는 응답이 느려질 수 있다.

#### 5. 내가 선택한 방식과 그 이유를 설명하라.

Queue 또는 Kafka에 안전하게 전달된 순간 요청 접수 성공 응답을 반환하는 방식을 선택한다.


선착순 쿠폰 이벤트는 순간적으로 요청이 많이 몰리기 때문에 API 서버가 모든 요청을 DB에 먼저 저장하면 DB 부하가 커질 수 있다. 반면 Queue나 Kafka에 안전하게 전달된 뒤 응답하면 요청 유실 가능성을 줄이면서도 실제 발급 처리는 Worker가 뒤에서 처리할 수 있다.


따라서 API 서버는 로그인 여부와 이벤트 시간 등 기본 검증만 수행하고, 요청을 비동기 처리 영역에 안전하게 전달한 뒤 사용자에게 PENDING 응답을 반환하는 것이 적합하다.


*참고로 요청 접수 성공의 기준은 다음 중 하나로 생각해볼 수 있다.

```
1. 요청을 메모리에 올린 순간
2. 요청 검증이 끝난 순간
3. 요청 상태가 DB에 PENDING으로 저장된 순간
4. Queue 또는 Kafka에 안전하게 전달된 순간
```

단순히 빠르게 응답하는 것만 생각하지 말고, 사용자가 접수 응답을 받은 뒤 요청이 유실되지 않도록 하려면 어떤 기준이 필요한지 고민한다.

## 과제 6. 항상 비동기가 성능이 좋은지 생각해보기

비동기 처리는 대규모 트래픽 상황에서 유리할 수 있다.

하지만 항상 비동기가 더 좋은 것은 아니다.

#### 1. 비동기 처리가 동기 처리보다 유리한 상황은 언제인가?

짧은 시간에 많은 요청이 몰리거나, 오래 걸리는 작업을 분리해야 하는 상황에서 유리하다.

#### 2. 동기 처리가 더 단순하고 적합한 상황은 언제인가?

요청이 많지 않고, 사용자가 최종 결과를 즉시 확인해야 하는 기능에서는 동기 처리가 더 적합하다.

#### 3. 비동기 처리 구조를 사용하면 어떤 추가 복잡도가 생기는가?

Queue 관리, Worker 운영, 요청 상태(PENDING/SUCCESS/FAILED) 관리, 실패 재처리, 결과 조회 API 등을 추가로 구현해야 한다.

#### 4. 사용자가 최종 결과를 바로 알아야 하는 기능이라면 비동기 처리가 항상 적합한가?

아니다. 결제나 로그인처럼 즉시 결과가 필요한 기능은 동기 처리가 더 적합할 수 있다.

#### 5. 이번 선착순 쿠폰 이벤트에서는 왜 비동기 처리가 더 적합하다고 볼 수 있는가?

이벤트 시작 직후 많은 요청이 동시에 발생하므로, API 서버는 요청만 접수하고 실제 발급은 Worker가 처리하는 것이 서버와 DB의 부하를 줄이고 안정적으로 요청을 처리할 수 있기 때문이다.

## 과제 7. 동기/비동기와 블로킹/논블로킹 조합 분석하기

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 기준이 다르다.

동기/비동기는 요청한 작업의 결과를 **같은 요청 흐름에서 직접 받아 처리하는가**, 아니면 요청 흐름과 실제 처리 흐름을 분리하는가에 대한 개념이다.

블로킹/논블로킹은 **작업이 끝날 때까지** 현재 실행 흐름이 멈추는가, 아니면 바로 제어권을 돌려받는가?에 대한 개념이다.

다음 4가지 조합을 분석한다.

```
1. 동기 / 블로킹

2. 동기 / 논블로킹

3. 비동기 / 블로킹

4. 비동기 / 논블로킹
```

#### 1. 위 4가지 조합 각각이 무엇인지, 일반적인 작업 흐름(예: 함수 호출, DB 호출, 소켓 IO 등) 기준으로 다이어그램과 함께 설명하라. (쿠폰 발급 시나리오에 한정하지 않아도 된다.)
1) 동기 / 블로킹
```
Client → 함수 호출 → DB 요청 → DB 응답을 기다림 → 결과 반환 → 다음 작업 수행
```

호출한 작업이 끝날 때까지 현재 실행 흐름이 멈춘다. 가장 일반적인 방식이다.

2) 동기 / 논블로킹
```
Client → 함수 호출 → 작업 요청 → 바로 제어권 반환 → 완료 여부를 계속 확인(Polling) → 결과 확인 후 다음 작업 수행
```

실행 흐름은 멈추지 않지만, 결과는 같은 흐름에서 직접 확인한다.

3) 비동기 / 블로킹
```
Client → 작업 요청 → 다른 스레드에서 처리 → 현재 흐름은 결과를 기다림 → 결과 반환
```

작업은 다른 곳에서 처리하지만 현재 실행 흐름은 결과가 올 때까지 기다린다.

4) 비동기 / 논블로킹
```
Client → 작업 요청 → 즉시 제어권 반환 → 다른 작업 수행 → 작업 완료 후 Callback/Event로 결과 전달
```

작업과 결과 처리가 분리되어 있으며 현재 실행 흐름도 멈추지 않는다.


#### 2. 이 4가지 중 이번 선착순 쿠폰 발급 구조에 실제로 등장하는 조합은 무엇인지 고르고, 어디에서 등장하는지 근거를 들어 설명하라. (4개가 다 등장하지 않을 수 있다.)
- 동기 / 블로킹 : API 서버가 로그인 확인이나 이벤트 시간 확인을 위해 DB를 조회하는 과정에서 사용된다. DB 응답이 올 때까지 현재 요청이 기다린다.
- 비동기 / 논블로킹 : API 서버가 요청을 Queue에 전달한 뒤 바로 PENDING 응답을 반환하는 구조이다. 이후 Worker가 쿠폰 발급을 처리하고 사용자는 나중에 결과를 조회한다.
- 비동기 / 블로킹 : Queue를 사용하지만 API 서버가 Worker의 처리 결과를 기다린 뒤 사용자에게 응답하는 구조에서 나타난다. 과제에서 구조 A가 이에 해당하며, 비동기의 장점을 충분히 활용하지 못하는 방식이다.
- 동기 / 논블로킹 : 이번 선착순 쿠폰 발급 구조에서는 사용되지 않는다. 일반적으로 이벤트 기반 I/O나 Polling 방식에서 사용될 수 있다.
