## 과제 1. Kafka 기반 비동기 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  │ ① 쿠폰 발급 요청 
  ▼
API Server
  │ ② 요청값 검증 
  │ ③ requestId 생성 + 요청 상태 PENDING 저장
  ▼
Kafka Producer
  │ ④ 쿠폰 발급 요청 메시지 발행
  ▼
coupon.issue.requested Topic (Partition 0 ~ N)
  │ ⑤ 메시지 저장 (Consumer가 읽을 때까지 보관)
  ▼
Coupon Issue Consumer (coupon-issue-group)
  │ ⑥ 메시지 읽기 → 쿠폰 발급 처리 수행
  ▼
DB
  │ ⑦ 최종 쿠폰 발급 기록 저장 (상태 ISSUED / FAILED 갱신)


```

### 2. API Server의 역할

```
1. 사용자의 쿠폰 발급 요청을 받는다.
2. 기본적인 요청값(eventId, userId 등)을 검증한다.
3. 요청을 식별할 requestId를 생성한다.
4. Kafka에 쿠폰 발급 요청 메시지를 발행한다.
5. Kafka 발행 성공 여부에 따라 사용자에게 요청 접수 성공/실패 응답을 빠르게 반환한다.

즉, API Server는 실제 쿠폰 발급 처리를 끝까지 수행하지 않고 요청 접수까지만 담당한다.
```

### 3. Kafka의 역할

```
API Server(요청 접수)와 Consumer(실제 처리) 사이에서
쿠폰 발급 요청 메시지를 안전하게 전달하고 잠시 쌓아두는 역할을 한다.

- 요청이 한 번에 몰려도 메시지를 Topic에 저장해두고
  Consumer가 자신의 처리 속도에 맞춰 꺼내 처리할 수 있게 해준다.
- 이를 통해 API Server와 실제 발급 처리 로직을 분리한다.
```

### 4. Consumer의 역할

```
1. coupon.issue.requested Topic에서 쿠폰 발급 요청 메시지를 읽는다.
2. 메시지의 eventId, userId, requestId 등을 확인한다.
3. 실제 쿠폰 발급 로직을 수행한다.
4. 최종 발급 결과를 DB에 저장한다 (요청 상태를 ISSUED/FAILED로 갱신).
5. 처리가 끝난 메시지의 Offset을 Commit한다.
```

### 5. DB의 역할

```
최종 쿠폰 발급 기록을 저장하는 저장소.
발급 요청의 상태를 보관하여
사용자가 나중에 상태 조회 API나 마이페이지에서 결과를 확인할 수 있게 한다.
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 몰릴 수 있다.
모든 요청을 API Server가 동기적으로 DB까지 처리해서 최종 결과를 응답하면
- API Server의 요청 처리 시간이 길어지고
- DB에 동시에 부하가 몰리며
- 사용자는 응답을 오래 기다리게 된다.

그래서 요청 접수와 실제 발급 처리를 분리해,
사용자에게는 요청이 접수되었다는 응답만 빠르게 주고
실제 발급 결과는 Consumer가 뒤에서 처리한 뒤
상태 조회 API/마이페이지에서 확인하게 한다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공:
API Server가 요청을 정상적으로 받아 Kafka에 메시지 발행까지 성공한 상태
요청이 처리 대기열에 안전하게 들어갔다는 의미일 뿐이다

쿠폰 발급 성공:
Consumer가 메시지를 읽어 실제 발급 처리를 수행하고,
발급 기록이 DB에 저장된 상태

접수에 성공했더라도 수량 소진 등으로 최종 발급은 실패할 수 있으므로
두 개념을 분리해서 생각해야 한다
```

## 과제 2. Topic 설계하기

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```
쿠폰 발급 요청이 들어왔다는 사실을 나타내는 메시지
- coupon: 쿠폰 도메인
- issue: 발급
- requested: 발급 요청이 들어온 단계 
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
Producer는 API Server다.
사용자의 쿠폰 발급 요청을 받아 기본 검증을 마친 직후
사용자에게 응답을 반환하기 전에 이 Topic으로 발급 요청 메시지를 발행한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Consumer는 Coupon Issue Consumer다.
이 Topic에서 발급 요청 메시지를 읽어
실제 쿠폰 발급 처리를 수행하고 최종 발급 결과를 DB에 저장한다.
```

### 5. 이 Topic이 필요한 이유

```
요청 접수와 실제 발급 처리를 분리하기 위해서다.
이 Topic이 두 컴포넌트 사이의 완충 지대 역할을 하여
- 요청이 폭증해도 메시지를 쌓아두고 뒤에서 처리할 수 있고
- API Server는 발급 처리 완료를 기다리지 않고 빠르게 응답할 수 있으며
- API Server와 발급 처리 로직이 서로의 장애/부하에 직접 영향받지 않게 된다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
쿠폰 발급 요청이 시스템에 접수되었고,
이 요청을 나중에 Consumer가 읽어서 처리해야 한다는 의미다.
-> 요청이 처리 대기열에 들어간 상태
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
메시지가 Topic에 들어간 것은 아직 요청 단계일 뿐이며
실제 발급 처리는 Consumer가 나중에 수행한다.

- Consumer가 아직 메시지를 읽지 않았을 수 있고 
- 처리 과정에서 수량 소진, 중복 발급 등으로 발급이 실패할 수도 있다.

따라서 발급 완료 여부는 Consumer가 처리를 끝내고
DB에 결과를 저장한 후에야 확정된다.
```

## 과제 3. Kafka Message 구조 설계하기

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-123",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-06-26T12:00:00"
}
```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| requestId | 쿠폰 발급 요청 하나를 식별하는 ID | 요청 식별과 발급 상태 조회에 사용. 같은 요청이 여러 번 들어왔는지 판단하거나 장애/중복 요청을 추적할 때 필요 |
| eventId | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 쿠폰을 발급해야 하는지 알아야 하므로 필요 |
| userId | 어떤 사용자가 요청했는지 나타내는 ID | 누구에게 쿠폰을 발급할지, 그리고 1인 1매 조건 확인을 위해 필요 |
| requestedAt | 사용자가 요청한 시각 | 요청 시점 기록, 장애 상황 추적 및 선착순 관련 분석에 활용 가능 |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
- eventId로 어떤 이벤트의 쿠폰 발급 요청인지 확인하고
- userId로 어떤 사용자에게 발급할지 확인하여
  실제 쿠폰 발급 처리를 수행하고 발급 기록을 DB에 저장할 수 있다.
- requestId로 해당 요청의 상태를 갱신할 수 있고
  나중에 문제 발생 시 요청 단위 추적이 가능하다.

즉, 이 메시지만 보고도 Consumer가 필요한 처리를 수행할 수 있다
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
- 메시지 크기가 커지면 네트워크 전송량과 Kafka 저장 공간 부담이 커지고
  대량 트래픽 상황에서 발행/소비 처리량에 불리하다.
- 사용자 이름, 등급 같은 부가 정보를 메시지에 넣으면
  메시지 발행 시점과 처리 시점 사이에 값이 바뀌었을 때
  정합성이 깨진 데이터로 처리할 위험이 있다.
- 필드가 많아질수록 메시지 스키마 변경/관리가 어려워진다.

따라서 Consumer가 처리에 꼭 필요한 식별자 중심의 최소 정보만 담고,
나머지는 Consumer가 처리 시점에 조회하는 것이 안전하다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
requestId는 요청 하나를 구분하기 위한 식별자이며 발급 상태 조회에 필요한 값 정도로 이해하면 된다.
같은 요청이 여러 번 들어왔는지 판단할 때 사용할 수 있다는 것까지만 알면 된다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

### 상황 A. Kafka 발행 성공

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 발급 결과는 마이페이지에서 확인해주세요.",
  "requestId": "req-123"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
Kafka 발행 성공은 요청 메시지가 처리 대기열에 안전하게 들어갔다는 뜻일 뿐이다
실제 발급 처리는 Consumer가 나중에 수행하며
처리 과정에서 쿠폰 수량 소진이나 중복 발급 등으로 최종 발급이 실패할 수 있다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공: Kafka에 발급 요청 메시지가 정상 발행되어 요청이 시스템에 접수된 상태. 

쿠폰 발급 성공: Consumer가 실제 발급 처리를 완료하고 발급 기록이 DB에 저장된 상태. 
```

#### 4. requestId를 응답에 포함하는 이유

```
사용자가 나중에 발급 상태 조회 API를 호출할 때
자신의 요청을 식별할 수 있는 키가 필요하기 때문이다.
클라이언트는 이 requestId로 PENDING → ISSUED/FAILED 상태 변화를 조회할 수 있다.
또한 문의나 장애 상황에서 특정 요청을 추적하는 데도 사용된다.
```

### 상황 B. Kafka 발행 실패

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": null
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
Kafka에 메시지가 들어가지 않았으므로
Consumer가 이 요청을 처리할 방법이 없다.

그런데 접수 성공 응답을 주면 사용자는 요청이 접수되었다고 믿고
결과를 기다리지만 시스템 내부에는 처리할 요청 자체가 존재하지 않는다.
→ 요청이 조용히 유실되고 사용자는 영원히 PENDING 상태만 보게 된다.

Kafka 발행이 실패했다는 것은 요청이 시스템에
안전하게 접수된 것이 아니므로, 접수 성공 응답을 주면 안 된다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
- 반드시 Producer가 Kafka Broker로부터 발행 성공 응답을 받은 것을 확인한 뒤에 접수 성공 응답을 반환해야 한다. 
- 발행 실패 시 명확한 실패 응답을 주어 사용자가 재시도할 수 있게 안내한다.
- 실패 로그를 남겨 운영자가 Kafka 장애 여부를 파악할 수 있게 한다.
- 요청 상태 저장소에 PENDING을 먼저 기록했다면 발행 실패 시 해당 상태가 처리 불가능한 유령 요청으로 남지 않도록 정리해야 한다.
```

## 과제 5. Partition Key 선택하기

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자의 요청이 같은 Partition으로 들어가 사용자 기준 순서 관리에 유리, 중복 요청 흐름 추적에 좋음, 사용자 수가 많으면 분산도 비교적 고름 | 특정 사용자가 비정상적으로 많은 요청을 보내면 일부 Partition에 부하가 몰릴 수 있음 |
| eventId | 같은 이벤트의 요청을 묶어서 보기 쉬움 | 선착순 이벤트 특성상 요청 대부분이 하나의 eventId에 몰려 특정 Partition에 쏠림 발생, Partition을 여러 개 둬도 병렬 처리 효과가 사라짐 |
| requestId | 요청마다 Key가 달라 메시지가 고르게 분산됨, 특정 이벤트에 요청이 몰려도 분산 가능 | 같은 사용자의 요청이 서로 다른 Partition으로 흩어져 사용자 기준 순서 보장이 어렵고, 사용자 단위 중복 요청 추적이 어려움 |

### 2. 내가 선택한 Partition Key

```
userId
```

### 3. 선택한 이유

```
1) 분산: 선착순 쿠폰 이벤트는 참여 사용자가 매우 많고 각 사용자의 요청 수는 상대적으로 제한적이다.
   따라서 userId 기준으로 해싱하면 메시지가 여러 Partition에 비교적 고르게 분산되어 Consumer 병렬 처리가 가능하다.

2) 순서: 같은 사용자의 요청은 항상 같은 Partition으로 들어가므로 사용자 기준 요청 순서를 관리하기 쉽다.
   한 사용자가 버튼을 여러 번 눌러 중복 요청이 발생해도 같은 Partition에서 순서대로 처리되어 흐름 추적이 용이하다.

즉, userId는 분산과 사용자 기준 순서 보장의 균형이 가장 좋은 선택이다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
사용자가 매우 많으므로 userId 해싱 결과가 여러 Partition에 고르게 퍼진다.
10만 건의 요청이 서로 다른 수많은 사용자로부터 오기 때문에
특정 Partition 하나에만 메시지가 집중되지 않고
Partition 수만큼 병렬 처리 효과를 살릴 수 있다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
Kafka는 같은 Partition 안에서만 순서를 보장한다.
userId를 Key로 쓰면 같은 사용자의 요청이 항상 같은 Partition에 들어가므로 같은 사용자 기준의 요청 순서는 보장된다.
반면 서로 다른 사용자의 요청은 다른 Partition에 들어갈 수 있어
사용자 간 전체 순서는 보장되지 않는다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
가능성이 아예 없지는 않다.
특정 사용자가 비정상적으로 많은 요청을 보내면 그 사용자의 요청이 모두 같은 Partition으로 들어가 부하가 몰릴 수 있다.
다만 일반적인 쿠폰 이벤트에서는 사용자당 요청 수가 제한적이므로 eventId 대비 쏠림 위험이 훨씬 낮다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
- 비정상 사용자의 대량 요청 시 특정 Partition 부하 가능
- 사용자 분포가 균등하지 않으면 Partition간 처리량 차이가 발생할 수 있음
- 전체 요청의 글로벌 순서는 보장하지 못함
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
선착순 이벤트에서는 이벤트 시작 직후 대부분의 요청이
eventId = 1 하나에 몰린다.
같은 Key는 같은 Partition으로 가므로 10만 건의 메시지가
모두 하나의 Partition에 쌓일 수 있다.

그 결과:
- Partition을 여러 개 만들어도 실제로는 하나만 바쁘게 일하고
- Consumer Group을 구성해도 그 Partition을 담당하는
  Consumer 하나만 일하게 되어 병렬 처리 효과가 사라지며
- Consumer Lag이 해당 Partition에 집중된다.

하나의 이벤트에 요청이 몰리는 것이 이 시스템의 핵심 문제인데,
eventId를 Key로 쓰면 그 문제를 Partition 쏠림으로 그대로 옮기는 셈이다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다.

서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되지 않는다.

이유:
- 각 Partition은 독립적인 메시지 저장 공간이며 Offset도 Partition 단위로 따로 관리된다.
- 서로 다른 Partition은 서로 다른 Consumer가 병렬로 각자의 속도로 읽어 처리한다.
- 따라서 Partition 내부에서는 Offset 순서대로 읽히지만 Partition 사이에는 어느 메시지가 먼저 처리될지 정해주는 공통 기준이 존재하지 않는다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
6개 (Partition 0 ~ 5)
```

### 3. Consumer Group 이름

```
coupon-issue-group
```

### 4. Consumer 수

```
3개 (Consumer 1 ~ 3)
```

### 5. Partition과 Consumer 매핑

```
Partition 0 → Consumer 1
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Partition 3 → Consumer 2
Partition 4 → Consumer 3
Partition 5 → Consumer 3
```

### 6. 이 구조를 선택한 이유

```
1) 처리량 관점:
   이벤트 시작 직후 1분 안에 최대 10만 건 → 평균 약 1,700건/초 수준의
   순간 트래픽을 하나의 Consumer가 감당하기 어려우므로
   여러 Consumer가 Partition을 나누어 병렬 처리해야 한다.

2) Partition 수(6) > Consumer 수(3)로 여유를 둔 이유:
   Partition 수는 병렬 처리의 상한이고, 운영 중에 늘리기 번거롭다.
   평소에는 Consumer 3개가 각각 2개 Partition을 담당하다가
   Consumer Lag이 증가하면 Consumer를 최대 6개까지 늘려 처리량을 확장할 수 있다.

3) Consumer Group 사용 이유:
   같은 Group 안의 Consumer들이 Partition을 나눠 맡아
   같은 메시지를 중복해서 읽지 않고 분담 처리할 수 있으며
   특정 Consumer 장애 시 나머지 Consumer에게 Partition이
   재할당되어 처리가 이어질 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
최대 3개.
같은 Consumer Group 안에서 하나의 Partition은
하나의 Consumer만 처리할 수 있으므로
동시에 일하는 Consumer 수는 Partition 수(3)를 넘을 수 없다.
나머지 Consumer 2개는 할당받을 Partition이 없어 논다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
Partition 수만큼의 Consumer만 Partition을 할당받고,
초과분 Consumer는 할당받을 Partition이 없어 대기 상태가 된다.
즉, Consumer를 늘려도 처리량은 늘지 않고 자원만 낭비된다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
한 Consumer가 여러 Partition을 담당하게 된다.
모든 Partition이 처리되기는 하지만
Consumer 하나당 처리 부담이 커져서
처리 속도가 느려지고 Consumer Lag이 커질 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
1) 병렬 처리의 상한은 Partition 수다.
   같은 Group에서 하나의 Partition은 하나의 Consumer만 처리할 수 있으므로
   Consumer 수가 Partition 수를 넘으면 초과 Consumer는 놀기만 한다.

2) Consumer를 늘려 Kafka 소비 속도를 높여도
   실제 처리의 병목이 DB라면 DB에 동시 요청이 몰려
   오히려 DB 부하 문제가 다시 발생할 수 있다.

따라서 Consumer 수는 Partition 수와 DB 처리 능력을
함께 고려해서 정해야 한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
마지막으로 Commit된 Offset 이후의 메시지부터 다시 읽는다.
따라서 장애 직전에 DB 저장까지 성공했지만 Offset Commit은 하지 못한
그 메시지를 다시 읽게 된다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Kafka는 Consumer가 실제로 어떤 처리를 했는지를 알지 못한다.
Kafka가 처리 완료 여부를 판단하는 유일한 기준은 Offset Commit 기록이다.

이 상황에서는 DB 저장은 성공했지만 Offset Commit 전에 Consumer가 죽었으므로
Kafka에는 해당 Offset까지 처리했다는 Commit 기록이 남아 있지 않다.
따라서 Kafka는 그 메시지가 아직 처리되지 않았다고 판단한다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
있다.
재시작한 Consumer는 마지막 Commit 지점부터 다시 읽기 때문에
이미 DB 저장까지 끝난 메시지를 다시 읽어 다시 처리하게 된다.
이것이 Kafka의 at-least-once 처리 특성이며,
Kafka를 쓰는 시스템은 같은 메시지가 한 번 이상 처리될 수 있다고 가정하고 설계해야 한다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
- 같은 사용자에게 같은 쿠폰이 두 번 발급될 수 있다.
- 중복 발급이 누적되면 전체 발급 수량이 제한을 초과할 수 있다.
- DB에 중복 발급 기록이 쌓여 데이터 정합성이 깨지고,
  마이페이지/통계 등 후속 데이터도 잘못될 수 있다.
- 사용자 1명당 1개라는 이벤트 규칙이 깨진다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

```
1) DB Unique Key:
   coupon_issue 테이블의 (eventId + userId)에 Unique 제약을 걸어
   같은 메시지가 다시 처리되어도 두 번째 INSERT는 실패하게 만든다
   → 중복 발급을 막는 방어선 

2) requestId 기반 멱등성:
   requestId로 이미 처리한 요청인지 확인하고
   같은 requestId가 다시 들어오면 새로 처리하지 않고
   기존 처리 결과를 그대로 반환한다. 

3) 처리 상태 저장:
   요청 상태(PENDING / PROCESSING / ISSUED / FAILED)를 저장해두고
   메시지 처리 전에 상태를 확인하여 이미 완료된 요청은 건너뛴다.

4) 중복 메시지 방어:
   Consumer가 같은 메시지는 언제든 다시 올 수 있다는 전제로
   처리 로직 자체를 멱등하게 작성한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

### 1. Consumer Lag이란 무엇인가?

```
Consumer Lag
= log-end-offset − committed offset

Producer는 계속 메시지를 발행하는데 Consumer 처리 속도가 그보다 느려서
아직 처리하지 못하고 밀려 있는 메시지 수를 의미한다.

```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
1. 요청 접수 응답은 빨리 받지만, 최종 발급 결과 확인이 늦어진다.
2. 마이페이지에 쿠폰이 늦게 반영된다.
3. 발급 알림 발송이 늦어질 수 있다.
4. 사용자는 불안을 느끼고 문의가 늘거나 재요청을 시도할 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 발급 결과는 잠시 후 확인해주세요.",
  "requestId": "req-123"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다. 잠시 후 다시 확인해주세요.",
  "requestId": "req-123"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다. 마이페이지에서 확인해주세요.",
  "requestId": "req-123"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되어 발급에 실패했습니다.",
  "requestId": "req-123"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
- Lag이 일정 수준에서 유지되거나 감소 중이면:
  트래픽 대비 Consumer가 따라잡고 있으므로 정상 처리 중이라고 판단할 수 있다.

- Lag이 계속 증가하면:
  Consumer 처리량이 Producer 발행량을 따라가지 못한다는 신호다.
  → Consumer 수를 늘리거나
    Consumer 처리 로직/DB 병목을 점검하거나
    Partition 수 확장을 검토해야 한다

- 특정 Partition에만 Lag이 몰려 있으면:
  Partition Key 쏠림이나 특정 Consumer 장애를 의심할 수 있다.

```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
Kafka는 요청을 잠시 쌓아두고 뒤에서 처리할 수 있게 해줄 뿐,
전체 시스템의 처리량을 무한히 늘려주는 것이 아니다.

Kafka 도입으로 API 응답은 빨라지지만
실제 발급 처리는 여전히 Consumer가 수행해야 한다.
Consumer 처리 속도가 Producer 발행 속도보다 느리면
메시지가 Topic에 계속 쌓이고 사용자의 요청이 처리 순서를 기다리는 시간이 길어진다.

즉, 병목이 사라지는 것이 아니라
API Server/DB 앞단에서 Consumer 쪽으로 이동하는 것이며
그만큼 최종 발급 결과 확정도 늦어질 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| 1. Partition이 1개뿐이다 | 병렬 처리의 상한은 Partition 수인데, Partition이 1개면 Consumer를 아무리 늘려도 동시에 처리할 수 있는 Consumer는 1개뿐이다. 1분에 10만 건의 트래픽을 단일 Partition/단일 처리 흐름으로 감당할 수 없어 Consumer Lag이 급격히 증가한다 | Partition을 여러 개로 늘려 병렬 처리가 가능하게 하고, 트래픽과 Consumer 처리량을 고려해 Partition 수를 산정한다 |
| 2. Consumer가 1개뿐이다 | 10만 건의 메시지를 Consumer 하나가 순차 처리해야 하므로 처리 속도가 발행 속도를 못 따라가 Lag이 계속 쌓이고, 그 Consumer에 장애가 나면 처리가 완전히 중단된다(단일 장애점) | Consumer Group을 구성하고 Partition 수에 맞춰 Consumer를 여러 개 배치해 병렬 처리와 장애 시 재할당이 가능하게 한다 |
| 3. Partition Key를 eventId로 설정했다 | 대부분의 요청이 eventId = 1이므로 모든 메시지가 같은 Partition으로 쏠린다. Partition을 여러 개로 늘려도 실제로는 하나만 일하게 되어 병렬 처리 효과가 사라지고, 해당 Partition에 Lag이 집중된다 | Partition Key를 userId로 변경해 메시지를 여러 Partition에 고르게 분산시킨다 |
| 4. Kafka 발행 실패 시에도 요청 접수 성공 응답을 준다 | Kafka에 메시지가 없으므로 Consumer가 처리할 수 없는데, 사용자는 접수되었다고 믿고 기다린다. 요청이 조용히 유실되고 사용자는 영원히 결과를 받지 못한다 | Producer가 Broker의 발행 성공 응답을 확인한 뒤에만 접수 성공 응답을 반환하고, 발행 실패 시에는 FAILED 응답으로 재시도를 안내한다 |
| 5. Offset Commit 전 Consumer 장애 상황을 고려하지 않았다 | DB 저장 후 Offset Commit 전에 Consumer가 죽으면, 재시작 시 같은 메시지를 다시 읽어 다시 처리한다. 대비가 없으면 같은 사용자에게 쿠폰이 중복 발급되고 수량 제한도 깨질 수 있다 |at-least-once를 전제로 설계한다. DB Unique Key(eventId + userId), requestId 기반 멱등성, 처리 상태 확인 등으로 중복 처리를 방어한다 |
| 6. Consumer Lag이 증가해도 사용자가 처리 상태를 확인할 수 없다 | 사용자는 요청 접수 응답만 받고 이후 발급 결과를 알 방법이 없다. 처리가 밀리는 상황에서 발급 여부를 확인하지 못해 불안해하고, 재요청을 반복해 트래픽이 오히려 늘어날 수 있다 | 요청 상태(PENDING / ISSUED / FAILED)를 저장하고, requestId 기반 발급 상태 조회 API와 마이페이지 조회를 제공해 사용자가 결과를 확인할 수 있게 한다 |
| 7. Consumer Lag 모니터링/대응 체계가 없다 | Lag이 계속 증가해도 운영자가 인지하지 못하면 처리 지연이 방치되고, 이벤트 종료 후에도 발급이 확정되지 않는 상황이 발생할 수 있다 | Consumer Lag을 모니터링 지표로 두고, Lag 증가 시 Consumer 확장이나 병목 점검을 수행할 수 있는 운영 기준을 마련한다 |
