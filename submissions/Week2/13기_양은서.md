### 2. API Server의 역할

```text
1. API Server는 사용자의 쿠폰 발급 요청을 받고 기본 요청값을 검증한다.
2. 이후 requestId를 생성하고 쿠폰 발급 요청 메시지를 Kafka에 발행한다.
3. Kafka 발행에 성공하면 사용자에게 요청 접수 응답을 반환한다.
```

### 3. Kafka의 역할

```text
Kafka는 API Server와 Consumer 사이에서 쿠폰 발급 요청 메시지를 안전하게 전달하는 역할을 한다.
API Server가 직접 모든 발급 처리를 수행하지 않도록 요청을 Topic에 저장하고, Consumer가 나중에 읽어 처리할 수 있게 한다.
```

### 4. Consumer의 역할

```text
Consumer는 coupon.issue.requested Topic에서 메시지를 읽고 실제 쿠폰 발급 처리를 수행한다.
메시지에 포함된 eventId, userId, requestId를 바탕으로 발급 가능 여부를 확인하고 DB에 발급 결과를 저장한다.
```

### 5. DB의 역할

```text
DB는 최종 쿠폰 발급 결과를 저장한다.
또한 사용자가 발급 상태를 조회할 수 있도록 PENDING, ISSUED, FAILED와 같은 요청 상태를 저장하는 역할도 한다.
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```text
이벤트 시작 직후 짧은 시간에 많은 요청이 몰리기 때문에 API Server가 모든 DB 처리를 직접 수행하면 응답 지연과 DB 부하가 커질 수 있다.
따라서 요청 접수와 실제 발급 처리를 분리하여 API Server는 빠르게 요청 접수 응답을 반환하고, 실제 발급은 Consumer가 비동기적으로 처리한다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```text
요청 접수 성공은 API Server가 사용자의 요청을 받아 Kafka에 메시지를 정상적으로 발행했다는 의미이다.
쿠폰 발급 성공은 Consumer가 실제 발급 로직을 수행하고 DB에 쿠폰 발급 결과를 저장했다는 의미이다.
따라서 Kafka 발행 성공은 발급 완료가 아니라 처리 대기 상태를 의미한다.
```

## 과제 2. Topic 설계하기

### 1. Topic 이름

```text
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```text
쿠폰 발급 요청이 접수되었고, Consumer가 이후 실제 발급 처리를 수행해야 한다는 의미의 메시지가 담긴다.
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```text
Producer는 API Server이다.
사용자가 쿠폰 발급 버튼을 눌러 요청을 보내면 API Server가 요청값을 검증한 뒤 Kafka Topic에 메시지를 발행한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```text
Consumer는 Coupon Issue Consumer이다.
coupon.issue.requested Topic에서 메시지를 읽고, 해당 사용자가 해당 이벤트의 쿠폰을 발급받을 수 있는지 확인한 뒤 발급 결과를 DB에 저장한다.
```

### 5. 이 Topic이 필요한 이유

```text
API Server와 실제 쿠폰 발급 처리를 분리하기 위해 필요하다.
요청이 몰리는 상황에서 API Server가 모든 처리를 직접 수행하지 않고 Kafka에 요청을 저장하면, Consumer가 처리 가능한 속도에 맞춰 비동기적으로 발급을 수행할 수 있다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```text
쿠폰 발급 요청이 시스템에 접수되어 처리 대기열에 들어갔다는 의미이다.
즉, Consumer가 나중에 이 메시지를 읽어 실제 발급 처리를 수행해야 한다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```text
Topic에 메시지가 들어간 시점에는 Consumer가 아직 DB 저장이나 발급 가능 여부 판단을 수행하지 않았기 때문이다.
따라서 이 상태는 발급 완료가 아니라 요청 접수 또는 처리 대기 상태로 봐야 한다.
```

## 과제 3. Kafka Message 구조 설계하기

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-20260702-000001",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-07-02T12:00:00"
}
```

### 2. 각 필드의 의미

| 필드          | 의미                         | 필요한 이유                                             |
| ----------- | -------------------------- | -------------------------------------------------- |
| requestId   | 쿠폰 발급 요청 하나를 식별하는 ID       | 상태 조회와 요청 추적에 필요하다. 이후 멱등성 처리에도 활용할 수 있다.          |
| eventId     | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 쿠폰 수량과 조건을 기준으로 처리해야 하는지 알 수 있다. |
| userId      | 쿠폰 발급을 요청한 사용자 ID          | 사용자당 1개 발급 조건을 확인하고 발급 결과를 사용자와 연결하기 위해 필요하다.      |
| requestedAt | 사용자가 쿠폰 발급을 요청한 시간         | 요청 순서, 로그 추적, 장애 분석에 활용할 수 있다.                     |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```text
Consumer는 eventId를 보고 어떤 쿠폰 이벤트인지 확인하고, userId를 통해 요청 사용자를 식별한다.
이후 해당 사용자가 이미 쿠폰을 발급받았는지, 쿠폰 수량이 남아 있는지 확인한 뒤 발급 결과를 DB에 저장할 수 있다.
requestId를 이용해 요청 상태를 갱신하거나 로그를 추적할 수도 있다.
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```text
메시지에 너무 많은 정보를 넣으면 메시지 크기가 커지고, 데이터 변경 시 Producer와 Consumer가 강하게 결합될 수 있다.
또한 오래된 메시지에 담긴 정보와 DB의 최신 정보가 달라질 수 있어 정합성 문제가 생길 수 있다.
따라서 Consumer가 처리에 필요한 최소한의 식별자 중심으로 메시지를 설계하는 것이 좋다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```text
이번 주차에서는 requestId를 하나의 쿠폰 발급 요청을 식별하고, 사용자가 발급 상태를 조회할 때 사용할 수 있는 값으로 이해하면 된다.
requestId 기반 멱등성 처리와 중복 요청 방지는 이후 주차에서 더 자세히 다룬다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

### 상황 A. Kafka 발행 성공

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-20260702-000001"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```text
Kafka 발행 성공은 쿠폰 발급 요청 메시지가 Topic에 정상적으로 들어갔다는 의미일 뿐이다.
아직 Consumer가 실제 발급 가능 여부를 확인하거나 DB에 발급 결과를 저장한 상태가 아니므로 쿠폰 발급 성공을 의미하지 않는다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```text
요청 접수 성공은 API Server가 Kafka에 메시지를 정상적으로 발행했다는 뜻이다.
쿠폰 발급 성공은 Consumer가 메시지를 처리하고 DB에 발급 성공 결과를 저장했다는 뜻이다.
```

#### 4. requestId를 응답에 포함하는 이유

```text
사용자가 이후 발급 상태 조회 API나 마이페이지에서 자신의 요청 처리 상태를 확인할 수 있도록 하기 위해서이다.
또한 장애나 지연이 발생했을 때 특정 요청을 추적하는 데 사용할 수 있다.
```

### 상황 B. Kafka 발행 실패

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": "req-20260702-000001"
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```text
Kafka에 메시지가 발행되지 않으면 Consumer가 해당 요청을 읽을 수 없다.
그런데 사용자에게 요청 접수 성공 응답을 주면 사용자는 처리 중이라고 생각하지만, 실제 시스템 내부에는 처리할 메시지가 없는 상태가 된다.
즉, 요청이 유실될 수 있으므로 성공 응답을 주면 안 된다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```text
Kafka 발행 성공 여부를 확인한 뒤 응답해야 한다.
발행 실패 시에는 요청 접수 실패로 응답하고, 필요하다면 재시도 전략이나 장애 로그 기록을 고려해야 한다.
```

## 과제 5. Partition Key 선택하기

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점                                                                            | 단점                                                               |
| ---------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| userId           | 같은 사용자의 요청이 같은 Partition으로 들어가므로 사용자 기준 순서 관리에 유리하다. 사용자 수가 많다면 비교적 분산도 가능하다. | 특정 사용자가 비정상적으로 많은 요청을 보내면 일부 Partition에 부하가 몰릴 수 있다.             |
| eventId          | 같은 이벤트 요청을 묶어서 처리 흐름을 보기 쉽다.                                                  | 인기 이벤트 하나에 요청이 몰리면 동일한 eventId가 사용되어 특정 Partition에 메시지가 몰릴 수 있다. |
| requestId        | 요청마다 값이 달라 비교적 고르게 분산될 수 있다.                                                  | 같은 사용자의 여러 요청이 서로 다른 Partition으로 갈 수 있어 사용자 기준 순서 보장이 어렵다.       |

### 2. 내가 선택한 Partition Key

```text
userId
```

### 3. 선택한 이유

```text
쿠폰 발급 조건이 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능하다는 것이기 때문에 사용자 기준의 요청 흐름이 중요하다고 판단했다.
userId를 Key로 사용하면 같은 사용자의 요청이 같은 Partition에 들어가므로 동일 사용자 요청의 순서를 관리하기 쉽다.
또한 일반적으로 이벤트에는 많은 사용자가 참여하므로 eventId보다 Partition 분산에 유리하다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```text
사용자 수가 많다면 userId 값도 다양해지므로 여러 Partition으로 메시지가 분산될 수 있다.
반면 eventId를 Key로 사용하면 인기 이벤트 하나에 요청이 몰릴 때 특정 Partition으로 쏠릴 가능성이 크다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```text
Kafka는 같은 Partition 안에서만 순서를 보장한다.
userId를 Partition Key로 사용하면 같은 사용자의 요청은 같은 Partition으로 들어가므로 사용자 단위의 요청 순서를 보장하기 쉽다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```text
완전히 없지는 않다.
특정 사용자가 비정상적으로 많은 요청을 보내거나 userId 해시 결과가 고르게 분산되지 않으면 일부 Partition에 부하가 몰릴 수 있다.
하지만 대부분의 요청이 하나의 eventId에 몰리는 선착순 이벤트 상황에서는 eventId보다 userId가 쏠림 위험이 낮다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```text
전체 이벤트 기준의 완전한 요청 순서는 보장되지 않는다.
또한 특정 사용자 요청이 과도하게 많으면 해당 사용자가 매핑된 Partition에 부하가 집중될 수 있다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```text
선착순 쿠폰 이벤트에서는 대부분의 요청이 하나의 이벤트에 몰릴 수 있다.
이때 eventId = 1이 Partition Key가 되면 모든 메시지가 같은 Partition으로 들어갈 수 있다.
그러면 Partition을 여러 개 만들어도 병렬 처리 효과가 떨어지고 Consumer Lag이 특정 Partition에 집중될 수 있다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```text
Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다.
서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되지 않는다.
각 Partition은 서로 독립적으로 Consumer에게 처리되므로 Partition 간 전체 순서를 Kafka가 보장하지 않기 때문이다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

### 1. Topic 이름

```text
coupon.issue.requested
```

### 2. Partition 수

```text
6개
```

### 3. Consumer Group 이름

```text
coupon-issue-group
```

### 4. Consumer 수

```text
3개
```

### 5. Partition과 Consumer 매핑

```text
Partition 0 → Consumer 1
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Partition 3 → Consumer 2
Partition 4 → Consumer 3
Partition 5 → Consumer 3
```

### 6. 이 구조를 선택한 이유

```text
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있으므로 Consumer 병렬 처리가 필요하다.
Partition을 6개로 두면 Consumer를 최대 6개까지 확장할 수 있는 여지가 생긴다.
초기에는 Consumer 3개가 각각 2개 Partition을 담당하게 하고, Lag이 증가하면 Consumer 수를 늘려 처리량을 높일 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```text
최대 3개이다.
같은 Consumer Group 안에서는 하나의 Partition을 동시에 여러 Consumer가 처리할 수 없기 때문이다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```text
일부 Consumer는 할당받을 Partition이 없어 대기 상태가 된다.
즉, Consumer 수를 늘려도 Partition 수보다 더 많은 병렬 처리는 불가능하다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```text
하나의 Consumer가 여러 Partition을 담당하게 된다.
모든 Partition은 처리될 수 있지만 Consumer 하나당 처리 부담이 커질 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```text
병렬 처리의 최대 단위는 Partition 수에 의해 제한되기 때문이다.
Partition 수보다 많은 Consumer를 두면 일부 Consumer는 실제 처리를 하지 못한다.
또한 Consumer를 무작정 늘리면 운영 복잡도와 리밸런싱 비용이 증가할 수 있다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```text
DB 저장은 성공했지만 Offset Commit이 되지 않은 메시지를 다시 읽을 수 있다.
Kafka 입장에서는 마지막으로 Commit된 Offset 이후의 메시지가 아직 처리 완료되지 않은 것으로 보일 수 있기 때문이다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```text
Consumer가 DB 저장까지는 성공했지만 Offset Commit 전에 장애로 종료되었기 때문이다.
Kafka는 Consumer의 DB 저장 성공 여부를 알 수 없고, Commit된 Offset을 기준으로 처리 완료 여부를 판단한다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```text
그렇다.
Offset Commit이 실패했기 때문에 Consumer가 재시작되면 같은 메시지를 다시 읽고 처리할 수 있다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```text
같은 사용자에게 같은 이벤트의 쿠폰이 중복 발급될 수 있다.
또한 쿠폰 수량이 실제보다 더 많이 차감되거나 발급 결과가 중복 저장되는 문제가 생길 수 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

```text
DB Unique Key를 사용해 같은 eventId와 userId 조합이 중복 저장되지 않도록 막을 수 있다.
또한 requestId 기반 멱등성 처리를 통해 이미 처리된 요청인지 확인해야 한다.
처리 상태를 저장해 같은 메시지가 다시 들어와도 이미 ISSUED 또는 FAILED로 처리된 요청이면 중복 처리하지 않도록 방어해야 한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

### 1. Consumer Lag이란 무엇인가?

```text
Consumer Lag은 Kafka에 쌓인 메시지 중 Consumer가 아직 처리하지 못한 메시지의 양을 의미한다.
즉, 최신 메시지 위치와 Consumer Group이 처리 완료했다고 Commit한 Offset 사이의 차이다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```text
사용자는 요청 직후 접수 응답은 빠르게 받을 수 있지만, 실제 쿠폰 발급 결과는 늦게 확인할 수 있다.
마이페이지에 쿠폰이 늦게 반영되거나 발급 상태 조회 API에서 PENDING 상태가 오래 유지될 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다.",
  "requestId": "req-20260702-000001"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패했습니다. 쿠폰이 모두 소진되었거나 발급 조건을 만족하지 않습니다.",
  "requestId": "req-20260702-000001"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```text
Consumer Lag이 계속 증가하면 Producer가 메시지를 발행하는 속도보다 Consumer 처리 속도가 느리다는 의미이다.
운영자는 Consumer 수를 늘리거나, Partition 수를 조정하거나, Consumer 처리 로직과 DB 병목을 확인해야 한다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```text
Kafka는 API Server가 요청을 빠르게 접수하고 메시지를 저장할 수 있게 해주지만, 실제 쿠폰 발급 처리는 Consumer가 수행한다.
따라서 Consumer 처리 속도가 느리거나 DB 저장이 병목이 되면 Kafka에 메시지가 쌓이고 최종 발급 결과는 늦어질 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

### 문제점과 개선 방향

| 문제점                                   | 왜 문제인가?                                                                       | 개선 방향                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Partition이 1개이다.                      | Partition이 1개이면 같은 Consumer Group 안에서 하나의 Consumer만 처리할 수 있어 병렬 처리에 한계가 있다.   | 예상 트래픽을 고려해 Partition 수를 여러 개로 늘린다.                               |
| Consumer가 1개이다.                       | 이벤트 시작 직후 10만 건의 요청을 Consumer 1개가 모두 처리하면 Consumer Lag이 크게 증가할 수 있다.          | Consumer Group을 구성하고 여러 Consumer가 Partition을 나누어 처리하도록 한다.        |
| Partition Key가 eventId이다.             | 대부분의 요청이 eventId = 1이면 특정 Partition에 메시지가 몰릴 수 있다.                            | userId 또는 requestId처럼 더 분산에 유리한 Key를 고려한다.                        |
| Kafka 발행 실패에도 요청 접수 성공 응답을 준다.        | Kafka에 메시지가 없으면 Consumer가 처리할 수 없는데, 사용자는 요청이 접수되었다고 오해하게 된다. 요청 유실 문제가 발생한다. | Kafka Broker로부터 발행 성공 응답을 받은 경우에만 접수 성공을 반환한다.                    |
| Offset Commit 전 장애 상황을 고려하지 않았다.      | DB 저장 후 Commit 전에 Consumer가 죽으면 같은 메시지가 다시 처리되어 중복 발급이 발생할 수 있다.              | DB Unique Key, requestId 기반 멱등성, 처리 상태 저장으로 중복 처리를 방어한다.          |
| Consumer Lag이 증가해도 사용자가 상태를 확인할 수 없다. | 사용자는 쿠폰 발급이 진행 중인지 실패했는지 알 수 없어 혼란을 겪는다.                                      | requestId 기반 발급 상태 조회 API를 제공하고 PENDING, ISSUED, FAILED 상태를 보여준다. |
| Kafka를 사용하면 모든 문제가 해결된다고 가정했다.        | Kafka는 요청을 비동기로 전달할 뿐, Consumer 처리 속도나 DB 병목, 중복 처리 문제를 자동으로 해결하지 않는다.        | Consumer 처리량, Lag 모니터링, 중복 방어, 실패 대응 전략을 함께 설계한다.                 |
