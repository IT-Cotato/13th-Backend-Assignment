## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  │
  │ 쿠폰 발급 요청
  ↓
API Server
  │
  │ 요청 검증
  ↓
Kafka Producer
  │
  │ 메시지 발행
  ↓
coupon.issue.requested Topic
  │
  │ 메시지 소비
  ↓
Coupon Issue Consumer
  │
  │ 실제 쿠폰 발급 처리
  ↓
DB
  │
  ├── PENDING
  ├── ISSUED
  └── FAILED
```

### 2. API Server의 역할

```
- 사용자의 쿠폰 발급 요청을 받는다.
- 요청 데이터의 기본적인 유효성을 검증한다.
- Kafka Producer를 통해 coupon.issue.requested Topic에 메시지를 발행한다.
- Kafka 발행이 성공하면 사용자에게 요청 접수 응답을 반환한다.
```

### 3. Kafka의 역할

```
- API Server와 Coupon Issue Consumer를 분리한다.
- 쿠폰 발급 요청 메시지를 안전하게 저장하고 전달한다.
- Consumer가 순차적으로 메시지를 읽어 실제 쿠폰 발급을 수행할 수 있도록 한다.
```

### 4. Consumer의 역할

```
- coupon.issue.requested Topic에서 메시지를 읽는다.
- 메시지의 eventId, userId, requestId를 확인한다.
- 실제 쿠폰 발급 로직을 수행한다.
- 처리 결과를 DB에 저장한다.
```

### 5. DB의 역할

```
- 쿠폰 발급 요청의 상태를 저장한다.
- 최종 발급 결과를 관리한다.
- 상태는 다음과 같이 관리할 수 있다.
  - PENDING : 요청 접수 완료, 아직 처리 전
  - ISSUED : 쿠폰 발급 성공
  - FAILED : 쿠폰 발급 실패
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
- 이벤트 시작 직후 최대 10만 건의 요청이 동시에 발생할 수 있기 때문이다.
- API Server가 모든 요청을 직접 처리하면 응답 시간이 길어지고 DB에도 큰 부하가 발생한다.
- 따라서 Kafka를 이용해 요청 접수와 실제 쿠폰 발급을 분리하여 API Server는 빠르게 요청 접수만 처리하고, 실제 발급은 Consumer가 비동기로 수행한다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
- 요청 접수 성공은 Kafka에 쿠폰 발급 요청 메시지가 정상적으로 저장되었다는 의미이다.
- 반면 쿠폰 발급 성공은 Consumer가 해당 메시지를 읽고 실제 쿠폰 발급을 완료한 후 DB에 성공 상태를 저장했다는 의미이다.
- 따라서 Kafka 발행 성공은 쿠폰 발급 성공을 의미하지 않는다.
```

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```
- 쿠폰 발급 요청이 정상적으로 접수되었으며, Coupon Issue Consumer가 이후 실제 쿠폰 발급 처리를 수행해야 한다는 의미의 메시지이다.
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
- Producer는 API Server이다.
- 사용자가 쿠폰 발급을 요청하면 API Server가 요청을 검증한 후 Kafka의 coupon.issue.requested Topic에 쿠폰 발급 요청 메시지를 발행한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
- Consumer는 Coupon Issue Consumer이다.
- coupon.issue.requested Topic에서 메시지를 읽은 후, eventId와 userId를 확인하여 실제 쿠폰 발급을 수행하고 처리 결과를 DB에 저장한다.
```

### 5. 이 Topic이 필요한 이유

```
- API Server와 실제 쿠폰 발급 처리를 분리하기 위해 필요하다.
- API Server는 요청을 빠르게 접수하고, Consumer는 Kafka에 저장된 메시지를 읽어 실제 쿠폰 발급을 처리할 수 있다.
- 대량의 요청이 발생해도 안정적으로 처리할 수 있다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
- 쿠폰 발급 요청이 Kafka에 정상적으로 저장되었다는 뜻이다.
- Consumer가 해당 요청을 처리할 수 있는 상태가 되었음을 의미한다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
- Topic에 메시지가 저장된 것은 요청이 접수되었다는 의미일 뿐이다.
- 실제 쿠폰 발급은 Consumer가 메시지를 읽어 처리한 후 완료된다.
- 따라서 Topic에 메시지가 들어갔다고 해서 쿠폰 발급이 완료된 것은 아니다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-20260702-0001",
  "eventId": 1,
  "userId": 1,
  "requestedAt": "2026-07-02T14:00:00"
}
```

### 2. 각 필드의 의미

| 필드          | 의미                         | 필요한 이유                                       |
|-------------|----------------------------|----------------------------------------------|
| requestId   | 쿠폰 발급 요청 하나를 식별하기 위한 ID    | 요청 상태 조회와 로그 추적에 필요하다                        |
| eventId     | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 쿠폰을 발급해야 하는지 판단하기 위해 필요하다  |
| userId      | 쿠폰 발급을 요청한 사용자 ID          | Consumer가 어떤 사용자에게 쿠폰을 발급해야 하는지 판단하기 위해 필요하다 |
| requestedAt | 사용자가 쿠폰 발급을 요청한 시간         | 요청 시점 기록과 장애 상황 추적에 필요하다                     |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
- eventId를 보고 어떤 쿠폰 이벤트인지 확인할 수 있다.
- userId를 보고 어떤 사용자에게 쿠폰을 발급해야 하는지 확인할 수 있다.
- requestId를 이용해 요청 상태를 조회하거나 로그를 추적할 수 있다.
- requestedAt을 통해 사용자가 요청한 시점을 확인할 수 있다.
- 이후 실제 쿠폰 발급 처리를 수행하고 결과를 DB에 저장할 수 있다.
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
- 메시지 크기가 커져 Kafka에 부담이 될 수 있다.
- 불필요한 정보가 많아지면 Producer와 Consumer 간 의존성이 커질 수 있다.
- 데이터 구조가 변경될 때 Producer와 Consumer를 함께 수정해야 할 가능성이 높아진다.
- 개인정보나 민감한 정보가 포함될 위험이 커질 수 있다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
- requestId는 쿠폰 발급 요청 하나를 구분하기 위한 식별자이다.
- 요청 상태 조회와 로그 추적에 사용할 수 있는 값 정도로 이해하면 된다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 결과는 잠시 후 확인해주세요.",
  "requestId": "req-20260702-0001"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
- Kafka 발행 성공은 요청 메시지가 Topic에 정상적으로 저장되었다는 의미이다.
- 아직 Consumer가 메시지를 읽어 실제 쿠폰 발급을 수행하지 않았다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
- 요청 접수 성공은 Kafka에 메시지가 정상적으로 저장된 상태이다.
- 쿠폰 발급 성공은 Consumer가 메시지를 처리하고 DB에 발급 결과를 저장한 상태이다.
```

#### 4. requestId를 응답에 포함하는 이유

```
- 사용자가 자신의 쿠폰 발급 요청을 식별할 수 있도록 하기 위해서이다.
- 이후 발급 상태 조회 API에서 requestId를 이용해 처리 상태를 확인할 수 있다.
- 장애 발생 시 요청을 추적하는 데에도 사용할 수 있다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": "req-20260702-0001"
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
- Kafka에 메시지가 저장되지 않았기 때문에 Consumer가 해당 요청을 처리할 수 없다.
- 그런데 요청 접수 성공을 응답하면 사용자는 정상적으로 접수된 것으로 오해할 수 있다.
- 실제 시스템에는 처리할 요청이 존재하지 않으므로 요청 접수 성공 응답을 주면 안 된다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
- Kafka 발행 성공 여부를 확인한 후 사용자에게 응답해야 한다.
- Kafka 발행에 실패했다면 요청 접수 성공 응답을 반환하면 안 된다.
- 사용자에게 실패 원인을 안내하고 다시 시도할 수 있도록 적절한 실패 응답을 반환해야 한다.
```

## 과제 5. Partition Key 선택하기

`coupon.issue.requested` Topic의 Partition Key를 무엇으로 정할지 선택한다.

아래 후보 중 하나를 선택하거나, 직접 다른 Key를 제안해도 된다.

```
1. userId

2. eventId

3. requestId

4. 그 외 직접 선택
```

특히 `eventId`를 Partition Key로 선택한 경우에는 아래 상황을 반드시 고려한다.

```
이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰린다.
```

이때 모든 메시지가 특정 Partition에 몰릴 수 있는지 설명한다.

이번 과제에서는 정답 Partition Key를 하나로 고정하지 않는다.

중요한 것은 자신이 선택한 Partition Key가 아래 항목에 어떤 영향을 주는지 설명하는 것이다.

```
메시지 분산

순서 보장

특정 Partition 쏠림 가능성

Consumer 병렬 처리
```

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점                                                   | 단점                                                      |
|------------------|------------------------------------------------------|---------------------------------------------------------|
| userId           | 같은 사용자의 요청이 같은 Partition으로 들어가므로 사용자 기준 순서 관리에 유리하다. | 특정 사용자가 비정상적으로 많은 요청을 보내면 일부 Partition에 부하가 생길 수 있다.    |
| eventId          | 같은 이벤트 요청을 묶어서 관리하기 쉽다.                              | 이벤트 하나에 요청이 몰리면 특정 Partition에 메시지가 집중될 수 있다.            |
| requestId        | 요청마다 다른 값이므로 메시지 분산에 유리하다.                           | 같은 사용자의 요청이 서로 다른 Partition으로 갈 수 있어 사용자 기준 순서 보장이 어렵다. |

### 2. 내가 선택한 Partition Key

```
userId
```

### 3. 선택한 이유

```
- 쿠폰 발급 조건이 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능하기 때문이다.
- userId를 Partition Key로 사용하면 같은 사용자의 요청이 같은 Partition으로 들어간다.
- 같은 사용자 기준의 요청 순서를 관리하기 쉽고 중복 요청 흐름을 추적하기에도 유리하다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
- 이벤트에는 많은 사용자가 참여하므로 userId를 기준으로 하면 여러 Partition에 비교적 고르게 분산될 수 있다.
- eventId를 Key로 사용할 때보다 특정 이벤트 하나에 모든 메시지가 몰리는 문제를 줄일 수 있다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
- Kafka는 같은 Partition 안에서 메시지 순서를 보장한다.
- userId를 Key로 사용하면 같은 사용자의 요청이 같은 Partition으로 들어간다.
- 같은 사용자 기준의 요청 순서를 보장하기 쉽다고 할 수 있다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
- 완전히 없지는 않다.
- 특정 사용자가 비정상적으로 많은 요청을 보내면 해당 userId가 매핑된 Partition에 메시지가 몰릴 수 있다.
- 하지만 일반적인 쿠폰 이벤트에서는 많은 사용자가 요청을 보내므로 eventId를 사용하는 것보다는 쏠림 가능성이 낮다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
- 이벤트 전체 기준의 요청 순서를 보장하기 어렵다.
- 같은 이벤트에 대한 요청이라도 사용자별로 여러 Partition에 나뉘어 들어갈 수 있다.
- 전체 요청의 순서를 하나의 흐름으로 관리하기는 어렵다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
- 이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰릴 수 있다.
- 이 경우 모든 메시지가 같은 Partition으로 들어갈 수 있다.
- Partition을 여러 개 만들어도 실제로는 하나의 Partition만 바쁘게 처리될 수 있다.
- Consumer 병렬 처리 효과가 줄어들고 Consumer Lag이 특정 Partition에 집중될 수 있다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
- Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다.
- 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되지 않는다.
- 각 Partition은 독립적으로 처리되고 서로 다른 Consumer가 병렬로 처리할 수 있기 때문이다.
- Kafka에서는 Topic 전체의 전역 순서가 아니라 Partition 내부의 순서만 보장된다고 이해해야 한다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

쿠폰 발급 요청을 처리하는 Consumer Group을 설계한다.

기본 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.

Consumer는 coupon.issue.requested Topic을 읽는다.

Consumer는 실제 쿠폰 발급 처리를 수행한다.
```

이번 과제에서 정확한 처리량 계산이 목적은 아니다.

중요한 것은 아래 내용을 이해하고 설명하는 것이다.

```
Partition 수가 Consumer 병렬 처리에 어떤 영향을 주는가?

Consumer Group은 왜 필요한가?

Consumer 수와 Partition 수의 관계는 무엇인가?

Consumer 수만 무작정 늘리면 왜 안 되는가?
```

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
6개
```

### 3. Consumer Group 이름

```
coupon-issue-consumer-group
```

### 4. Consumer 수

```
3개
```

### 5. Partition과 Consumer 매핑

```
Partition 0 → Consumer 1
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Partition 3 → Consumer 2
Partition 4 → Consumer 3
Partition 5 → Consumer 3
```

### 6. 이 구조를 선택한 이유

```
- 이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있기 때문이다.
- Partition이 1개라면 Consumer를 여러 개 두어도 병렬 처리에 한계가 있다.
- Partition을 6개로 설정하면 여러 Consumer가 Partition을 나누어 처리할 수 있다.
- 초기에는 Consumer 3개가 각각 2개 Partition을 담당하도록 구성한다.
- 이후 Consumer Lag이 계속 증가하면 Consumer 수를 최대 6개까지 늘려 병렬 처리량을 높일 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
- 최대 3개
- 같은 Consumer Group 안에서는 하나의 Partition을 동시에 하나의 Consumer만 처리할 수 있기 때문이다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
- 일부 Consumer는 할당받을 Partition이 없어서 대기 상태가 된다.
- ex. Partition이 3개이고 Consumer가 5개라면 최대 3개의 Consumer만 실제로 메시지를 처리한다. (나머지 2개의 Consumer는 메시지를 처리하지 못하고 놀게 된다.)
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
- 한 Consumer가 여러 Partition을 담당하게 된다.
- 모든 Partition은 처리될 수 있지만, Consumer 하나가 처리해야 하는 메시지 양이 많아진다.
- 이 경우 Consumer 처리 속도가 부족하면 Consumer Lag이 증가할 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
- Consumer 병렬 처리의 최대 단위는 Partition 수에 의해 제한된다.
- Partition 수보다 Consumer 수가 많으면 추가된 Consumer는 Partition을 할당받지 못한다.
- Consumer 수만 늘린다고 처리량이 무조건 증가하는 것은 아니다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

Kafka Consumer가 메시지를 처리하는 도중 장애가 발생하는 상황을 분석한다.

아래 상황을 읽고 질문에 답한다.

```
1. Consumer가 Kafka 메시지를 읽었다.

2. Consumer가 DB 저장까지 성공했다.

3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.

4. Consumer가 다시 실행되었다.
```

이번 과제에서는 이 문제를 완전히 해결하는 것이 목적이 아니다.

중요한 것은 Kafka Consumer에서 아래 상황이 발생할 수 있음을 이해하는 것이다.

```
DB 처리는 성공했지만 Offset Commit은 실패할 수 있다.

Offset Commit이 실패하면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못할 수 있다.

그 결과 같은 메시지가 다시 읽히고 다시 처리될 수 있다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
- Offset Commit 전에 처리했던 같은 메시지를 다시 읽을 수 있다.
- Consumer가 DB 저장까지 성공했더라도 Offset Commit을 하지 못했다면, Kafka 입장에서는 해당 메시지가 처리 완료된 것으로 기록되지 않는다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
- Kafka는 Consumer가 Commit한 Offset을 기준으로 메시지 처리 완료 여부를 판단한다.
- DB 저장이 성공했는지는 Kafka가 직접 알 수 없다.
- Offset Commit 전에 Consumer가 종료되면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못한다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
- 가능하다.
- Consumer가 다시 실행되면 마지막으로 Commit된 Offset 이후의 메시지를 다시 읽을 수 있다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
- 같은 사용자에게 같은 이벤트의 쿠폰이 중복 발급될 수 있다.
- 쿠폰 수량이 실제보다 더 많이 차감될 수 있다.
- 이미 처리된 요청인데 다시 처리되면서 데이터 정합성 문제가 발생할 수 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

아래 키워드를 참고해서 작성한다.

```
DB Unique Key

requestId 기반 멱등성

처리 상태 저장

중복 메시지 방어
```

답변:

```
- DB Unique Key를 사용해 같은 사용자와 같은 이벤트에 대해 쿠폰이 중복 발급되지 않도록 막을 수 있다.
- requestId 기반 멱등성 처리를 통해 이미 처리된 요청인지 확인할 수 있다.
- 요청 처리 상태를 저장하여 PENDING, ISSUED, FAILED 상태를 관리할 수 있다.
- Consumer는 같은 메시지를 다시 읽더라도 이미 처리된 요청인지 확인하고 중복 처리를 방어해야 한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

Kafka를 사용하면 API Server는 사용자에게 빠르게 요청 접수 응답을 줄 수 있다.

하지만 Consumer 처리 속도가 느리면 Kafka에 메시지가 쌓일 수 있다.

아래 상황을 읽고 답한다.

```
이벤트 시작 직후 요청이 급격히 증가했다.

API Server는 Kafka에 메시지를 빠르게 발행하고 있다.

하지만 Consumer 처리 속도가 Producer 발행 속도보다 느리다.

Kafka에 아직 처리되지 않은 메시지가 계속 쌓이고 있다.
```

이번 과제에서는 사용자가 발급 상태를 조회할 수 있도록 요청 상태가 저장되어 있다고 가정한다.

상태는 아래와 같이 단순화해서 사용한다.

```
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태

ISSUED: 쿠폰 발급이 성공한 상태

FAILED: 쿠폰 발급이 실패한 상태
```

### 1. Consumer Lag이란 무엇인가?

```
- Consumer가 아직 처리하지 못한 메시지가 Kafka에 쌓여 있는 상태를 의미한다.
- Kafka에 저장된 최신 메시지 위치와 Consumer가 처리 완료했다고 Commit한 Offset 사이의 차이를 말한다.
- Consumer 처리 속도가 Producer의 메시지 발행 속도를 따라가지 못하면 Consumer Lag이 증가한다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
```text
- 사용자는 요청 접수 응답은 빠르게 받을 수 있지만, 실제 쿠폰 발급 결과를 확인하기까지 시간이 오래 걸릴 수 있다.
- 결과 조회 API에서 PENDING 상태가 오래 유지될 수 있다.
- 마이페이지에 쿠폰 발급 결과가 늦게 반영될 수 있다.
- 사용자는 시스템이 느리거나 오류가 발생했다고 느낄 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 결과는 잠시 후 확인해주세요.",
  "requestId": "req-20260702-0001"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다. 잠시 후 다시 확인해주세요.",
  "requestId": "req-20260702-0001"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 정상적으로 발급되었습니다.",
  "requestId": "req-20260702-0001"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패했습니다. 쿠폰이 모두 소진되었거나 발급 조건을 만족하지 않습니다.",
  "requestId": "req-20260702-0001"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
- Consumer의 처리 속도가 충분한지 확인할 수 있다.
- Consumer Lag이 계속 증가하면 Consumer 처리량이 부족하다고 판단할 수 있다.
- Consumer 수를 늘리거나 Partition 수를 조정해야 하는지 검토할 수 있다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
- Kafka는 요청을 빠르게 접수하도록 도와줄 뿐, 실제 쿠폰 발급은 Consumer가 수행한다.
- Consumer 처리 속도가 Producer보다 느리면 Kafka에 메시지가 계속 쌓이게 된다.
- Consumer Lag이 증가하면 최종 쿠폰 발급 결과도 늦어질 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

아래 Kafka 설계를 읽고 문제점을 찾는다.

```
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.

Partition Key는 eventId로 설정했다.

대부분의 요청은 eventId = 1이다.

Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.

Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.

Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

위 설계의 문제점을 5가지 이상 작성하고, 각각의 개선 방향을 작성한다.

### 문제점과 개선 방향

| 문제점                                      | 왜 문제인가?                                                                      | 개선 방향                                                                         |
|------------------------------------------|------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| Partition이 1개이고 Consumer가 1개이다.          | 모든 요청을 하나의 Consumer가 처리해야 하므로 병렬 처리가 불가능하고, 대량 요청 시 Consumer Lag이 크게 증가한다.   | Partition을 여러 개로 늘리고 Consumer Group을 구성하여 여러 Consumer가 병렬 처리하도록 한다.           |
| Partition Key를 eventId로 사용한다.            | 대부분의 요청이 같은 이벤트(eventId=1)에 몰리면 모든 메시지가 하나의 Partition으로 집중되어 병렬 처리 효과가 사라진다. | userId 또는 requestId처럼 메시지를 분산시키기 쉬운 Key를 사용한다.                                |
| Kafka 발행 실패에도 요청 접수 성공을 응답한다.            | Kafka에 메시지가 저장되지 않았는데도 사용자는 정상 접수된 것으로 오해할 수 있으며, 실제로는 요청이 처리되지 않는다.         | Kafka 발행이 성공한 경우에만 요청 접수 성공을 응답하고, 실패 시에는 실패 응답을 반환한다.                        |
| Offset Commit 실패 상황을 고려하지 않았다.           | DB 저장 후 Offset Commit 전에 Consumer가 종료되면 같은 메시지가 다시 처리되어 중복 발급이 발생할 수 있다.     | DB Unique Key, requestId 기반 멱등성 처리, 처리 상태 저장 등을 통해 중복 처리를 방어한다.               |
| Consumer Lag이 증가해도 사용자가 처리 상태를 확인할 수 없다. | 사용자는 요청이 처리 중인지, 실패했는지 알 수 없어 혼란을 겪을 수 있다.                                   | 상태 조회 API 또는 마이페이지에서 PENDING, ISSUED, FAILED 상태를 제공하고 요청 접수와 발급 완료를 명확히 구분한다. |
