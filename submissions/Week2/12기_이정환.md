# 2주차 과제 풀이

# Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```text
Client
  ↓
API Server
  ↓
Kafka Producer
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

사용자가 쿠폰 발급 요청을 보내면 API Server는 요청을 받은 뒤 Kafka Producer를 통해 `coupon.issue.requested` Topic에 메시지를 발행한다.

이후 Coupon Issue Consumer가 해당 Topic의 메시지를 읽어 실제 쿠폰 발급 로직을 수행하고, 최종 결과를 DB에 저장한다.

### 2. API Server의 역할

```text
1. 사용자의 쿠폰 발급 요청을 받는다.
2. eventId, userId 등 기본 요청값을 검증한다.
3. requestId를 생성하거나 전달받는다.
4. Kafka Producer를 통해 coupon.issue.requested Topic에 메시지를 발행한다.
5. Kafka 발행 성공 여부에 따라 사용자에게 요청 접수 결과를 응답한다.
```

API Server는 실제 쿠폰 발급을 끝까지 처리하지 않고 요청 접수와 Kafka 발행만 담당한다고 설명한다.

### 3. Kafka의 역할

```text
Kafka는 API Server와 Consumer 사이에서 쿠폰 발급 요청 메시지를 안전하게 전달하고 저장하는 역할을 한다.
```

Kafka는 단순 Queue처럼 메시지를 읽으면 바로 삭제하는 구조가 아니다. 메시지는 Topic의 Partition에 일정 기간 저장되고, Consumer는 Offset을 기준으로 어디까지 처리했는지 관리한다.

### 4. Consumer의 역할

```text
1. coupon.issue.requested Topic에서 메시지를 읽는다.
2. 메시지의 requestId, eventId, userId, requestedAt을 확인한다.
3. 쿠폰 발급 가능 여부를 판단한다.
4. 실제 쿠폰 발급 처리를 수행한다.
5. 발급 결과를 DB에 저장한다.
6. 처리가 끝난 뒤 Offset을 Commit한다.
```

Consumer는 비동기 구조에서 실제 쿠폰 발급 처리를 담당하는 컴포넌트다.

### 5. DB의 역할

```text
DB는 최종 쿠폰 발급 결과와 발급 상태를 저장한다.
```

이번 과제에서는 상태 저장소가 있다고 가정한다.

```text
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태
ISSUED: 쿠폰 발급이 성공한 상태
FAILED: 쿠폰 발급이 실패한 상태
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```text
선착순 쿠폰 이벤트는 이벤트 시작 직후 짧은 시간에 요청이 몰릴 수 있다.
API Server가 모든 요청에 대해 DB 조회와 DB 저장까지 직접 처리하면 API Server와 DB에 부하가 집중되고, 사용자는 응답을 오래 기다릴 수 있다.
그래서 API Server는 요청을 Kafka에 넣고 빠르게 요청 접수 응답을 반환한다. 실제 발급 처리는 Consumer가 뒤에서 처리한다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```text
요청 접수 성공
→ API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행한 상태

쿠폰 발급 성공
→ Consumer가 메시지를 읽고 실제 쿠폰 발급 처리와 DB 저장까지 완료한 상태
```

즉, Kafka 발행 성공은 쿠폰 발급 성공이 아니라 발급 요청이 처리 대기열에 들어간 상태를 의미한다.

## 과제 2. Topic 설계하기

### 1. Topic 이름

```text
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```text
쿠폰 발급 요청이 들어왔다.
```

이 Topic은 발급 완료 이벤트가 아니라 발급 요청 이벤트를 담는다.

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```text
Producer는 API Server이다.
```

사용자가 쿠폰 발급 API를 호출하고 API Server가 기본 요청값을 검증한 뒤, 실제 발급 처리를 Consumer에게 넘기기 위해 Kafka 메시지를 발행한다.

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```text
Consumer는 Coupon Issue Consumer이다.
```
`coupon.issue.requested` Topic을 구독하고 메시지를 읽어 쿠폰 발급 가능 여부를 판단한 뒤, 발급 성공 또는 실패 결과를 DB에 저장한다.

### 5. 이 Topic이 필요한 이유

```text
API Server와 실제 쿠폰 발급 처리 로직을 분리하기 위해 필요하다.
```
Kafka Topic을 사이에 두면 API Server는 빠르게 요청 접수 응답을 줄 수 있고, Consumer는 쌓인 메시지를 순차적 또는 병렬로 처리할 수 있다.

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```text
쿠폰 발급 요청이 Kafka에 정상적으로 접수되었고, Consumer가 나중에 처리할 수 있는 상태가 되었다는 의미다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```text
Topic에 메시지가 들어간 시점에는 Consumer가 아직 메시지를 읽지 않았을 수 있다.
또한 Consumer가 메시지를 읽더라도 쿠폰 수량 부족, 중복 요청, DB 저장 실패 같은 이유로 발급이 실패할 수 있다.
따라서 Topic 적재는 발급 요청 접수이지 발급 완료가 아니다.
```

## 과제 3. Kafka Message 구조 설계하기

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-20260702-000001",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-07-02T10:00:00+09:00"
}
```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| requestId | 하나의 쿠폰 발급 요청을 식별하는 ID | 상태 조회, 장애 추적, 나중의 멱등성 처리 기준으로 사용할 수 있다. |
| eventId | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 쿠폰 수량과 발급 조건을 확인해야 하는지 알 수 있다. |
| userId | 어떤 사용자가 요청했는지 나타내는 ID | 사용자별 1회 발급 조건을 확인하고 발급 기록을 저장하는 데 필요하다. |
| requestedAt | 사용자가 요청한 시간 | 요청 순서와 지연 상황을 추적하고 운영 로그로 활용할 수 있다. |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```text
Consumer는 eventId로 대상 쿠폰 이벤트를 찾고, userId로 발급 대상 사용자를 확인한다.
그 뒤 쿠폰 발급 가능 여부를 판단하고, 발급 성공 시 DB에 발급 기록을 저장한다. 실패 시에는 요청 상태를 FAILED로 저장할 수 있다.
requestId는 사용자가 결과 조회 API로 발급 상태를 확인할 때 사용할 수 있다.
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```text
Kafka 메시지는 Consumer가 처리에 필요한 최소 정보 중심으로 설계하는 것이 좋다.
메시지에 쿠폰 이름, 할인 금액, 사용자 상세 정보 같은 부가 정보를 과도하게 넣으면 메시지 크기가 커지고, 데이터 변경 시 메시지 스키마 변경 영향도 커진다.
또한 메시지에 담긴 부가 정보와 DB의 최신 정보가 달라질 수 있어 정합성 판단이 어려워질 수 있다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```text
이번 주차에서는 requestId를 요청 하나를 식별하고 상태를 조회하기 위한 값 정도로 이해하면 된다.
requestId 기반 멱등성 처리와 중복 요청 방지는 5주차에서 자세히 다룬다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

### 상황 A. Kafka 발행 성공

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-20260702-000001"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```text
API Server는 Kafka에 메시지를 발행했을 뿐, 실제 쿠폰 발급 처리를 수행하지 않았다.
실제 발급은 Coupon Issue Consumer가 메시지를 읽은 뒤 DB 저장까지 완료해야 성공으로 볼 수 있다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```text
요청 접수 성공
→ Kafka에 발급 요청 메시지가 정상적으로 들어간 상태

쿠폰 발급 성공
→ Consumer가 발급 로직을 수행하고 DB에 최종 발급 기록을 저장한 상태
```

#### 4. requestId를 응답에 포함하는 이유

```text
사용자가 이후 결과 조회 API나 마이페이지에서 자신의 요청 상태를 확인할 수 있게 하기 위해서다.
```
예를 들어 `requestId`로 `PENDING`, `ISSUED`, `FAILED` 상태를 조회할 수 있다.

### 상황 B. Kafka 발행 실패

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": "req-20260702-000001"
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```text
Kafka에 메시지가 들어가지 않았다면 Consumer가 처리할 요청이 존재하지 않는다.
그런데 사용자에게 요청 접수 성공 응답을 주면 사용자는 처리 중이라고 생각하지만, 실제 시스템에는 처리할 메시지가 없는 상태가 된다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```text
API Server는 Producer가 Kafka Broker로부터 발행 성공 응답을 받았는지 확인한 뒤 성공 응답을 줘야 한다.
발행 실패 시에는 요청 접수 실패로 응답하거나, 별도의 재시도 전략을 사용해야 한다. 이번 과제에서는 재시도 전략은 깊게 다루지 않는다.
```

## 과제 5. Partition Key 선택하기

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자의 요청이 같은 Partition으로 들어가므로 사용자 기준 순서 관리와 중복 요청 흐름 추적에 유리하다. | 특정 사용자가 비정상적으로 많은 요청을 보내면 일부 Partition에 부하가 몰릴 수 있다. |
| eventId | 같은 이벤트의 요청을 묶어서 보기 쉽다. | 인기 이벤트 하나에 요청이 몰리면 같은 Key가 반복되어 특정 Partition에 메시지가 쏠릴 수 있다. |
| requestId | 요청마다 값이 달라질 가능성이 높아 메시지 분산에 유리하다. | 같은 사용자의 여러 요청이 서로 다른 Partition으로 갈 수 있어 사용자 기준 순서 보장이 어렵다. |

### 2. 내가 선택한 Partition Key

```text
userId
```

### 3. 선택한 이유

```text
선착순 쿠폰 발급에서는 사용자 1명이 하나의 이벤트에서 쿠폰 1개만 받을 수 있다는 조건이 중요하다.
userId를 Partition Key로 사용하면 같은 사용자의 요청이 같은 Partition에 들어가므로, 같은 사용자 기준의 요청 순서를 다루기 쉽고 중복 요청 흐름을 추적하기 좋다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```text
사용자가 많고 각 사용자의 요청 수가 상대적으로 제한적이라면 userId는 여러 Partition에 비교적 고르게 분산될 수 있다.
반면 특정 사용자가 비정상적으로 많은 요청을 보내면 그 사용자의 Key가 매번 같은 Partition으로 가므로 특정 Partition에 부하가 생길 수 있다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```text
Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다.
```
`userId`를 Key로 사용하면 같은 사용자의 요청이 같은 Partition에 들어가므로 같은 사용자 기준의 요청 순서를 보장받기 쉽다.

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```text
가능성은 있다.
예를 들어 특정 사용자가 비정상적으로 반복 요청을 보내면 해당 사용자의 메시지는 같은 Partition으로 몰릴 수 있다.
하지만 이벤트 전체로 보면 사용자가 많고 각 사용자별 요청 수가 제한적이라는 전제가 있으므로 eventId를 Key로 사용하는 것보다 쏠림 위험이 작다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```text
userId 기준으로 분산되기 때문에 특정 이벤트의 전체 요청 순서를 보장하지는 못한다.
또한 악성 사용자나 자동화 요청이 특정 userId로 집중되면 해당 Partition에 부하가 생길 수 있다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```text
이벤트 시작 직후 대부분의 요청이 eventId가 1일 때로 몰릴 수 있다.
이 경우 모든 메시지가 같은 Key를 가지므로 특정 Partition에 몰릴 가능성이 크다.
Partition을 여러 개 만들어도 실제로는 하나의 Partition만 바쁘게 일하게 되어 Consumer 병렬 처리 효과가 줄어들고 Consumer Lag이 특정 Partition에 집중될 수 있다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가?

```text
Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다.
서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되지 않는다.
이유는 각 Partition이 독립적으로 처리되고, Consumer Group 안에서 서로 다른 Consumer가 각 Partition을 병렬로 처리할 수 있기 때문이다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

### 1. Topic 이름

```text
coupon.issue.requested
```

### 2. Partition 수

```text
6개
```

### 3. Consumer Group 이름

```text
coupon-issue-group
```

### 4. Consumer 수

```text
3개
```

### 5. Partition과 Consumer 매핑

```text
Partition 0 → Consumer 1
Partition 1 → Consumer 1
Partition 2 → Consumer 2
Partition 3 → Consumer 2
Partition 4 → Consumer 3
Partition 5 → Consumer 3
```

### 6. 이 구조를 선택한 이유

```text
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있으므로 Partition을 1개만 두면 병렬 처리에 한계가 크다.
Partition을 6개로 두면 Consumer를 늘렸을 때 최대 6개까지 병렬 처리할 수 있는 여지를 확보할 수 있다.
초기 Consumer는 3개로 시작하여 각 Consumer가 2개 Partition을 담당하게 하고, Consumer Lag이 지속적으로 증가하면 Consumer 수를 6개까지 늘리는 방식으로 확장할 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```text
최대 3개
```

같은 Consumer Group 안에서는 하나의 Partition을 동시에 여러 Consumer가 처리할 수 없기 때문이다.

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```text
일부 Consumer는 할당받을 Partition이 없어 대기하게 된다.
예를 들어 Partition이 3개인데 Consumer가 5개라면 최대 3개 Consumer만 메시지를 처리하고 나머지 2개 Consumer는 놀게 된다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```text
한 Consumer가 여러 Partition을 담당한다.
모든 Partition은 처리되지만, Consumer 하나당 처리해야 할 Partition이 늘어나므로 개별 Consumer의 부담이 커질 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```text
Consumer 병렬 처리의 최대 단위는 Partition 수에 의해 제한된다.
Partition 수보다 Consumer 수가 많으면 추가 Consumer는 메시지를 처리하지 못하므로 처리량 증가 효과가 없다.
따라서 Consumer 수는 Partition 수와 Consumer Lag, 실제 처리량을 함께 보고 조정해야 한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

상황은 다음과 같다.

```text
1. Consumer가 Kafka 메시지를 읽었다.
2. Consumer가 DB 저장까지 성공했다.
3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.
4. Consumer가 다시 실행되었다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```text
DB 저장까지 성공했지만 Offset Commit이 완료되지 않은 메시지를 다시 읽을 수 있다.
Kafka 입장에서는 해당 Offset이 처리 완료되었다는 기록을 받지 못했기 때문이다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```text
Kafka Consumer는 Offset Commit을 통해 어디까지 처리했는지 기록한다.
DB 저장이 성공했더라도 Offset Commit 전에 Consumer가 죽으면 Kafka에는 처리 완료 Offset이 남지 않는다.
따라서 Kafka는 해당 메시지를 아직 처리되지 않은 메시지로 판단할 수 있다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```text
가능하다.
Kafka를 사용한다고 해서 메시지가 반드시 정확히 한 번만 처리되는 것은 아니다. 장애 상황에서는 같은 메시지가 다시 읽히고 다시 처리될 수 있다고 가정해야 한다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```text
같은 사용자에게 같은 이벤트 쿠폰이 중복 발급될 수 있다.
또는 이미 처리된 요청의 상태가 다시 변경되거나, 쿠폰 수량이 중복 차감되는 문제가 발생할 수 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

```text
- DB Unique Key:
    eventId와 userId 조합에 Unique Key를 걸어 같은 사용자가 같은 이벤트 쿠폰을 중복 발급받지 못하게 한다.

- requestId 기반 멱등성:
    같은 requestId로 이미 처리된 요청이면 다시 처리하지 않고 기존 처리 결과를 반환하거나 무시한다.

- 처리 상태 저장:
    requestId별 상태를 PENDING, ISSUED, FAILED 등으로 저장해 이미 완료된 요청인지 확인한다.

- 중복 메시지 방어:
    Consumer는 Kafka 메시지가 중복으로 들어올 수 있다고 가정하고, DB 저장 전에 중복 여부를 확인한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

### 1. Consumer Lag이란 무엇인가?

Consumer Lag은 Consumer가 아직 처리하지 못하고 밀려 있는 메시지 수를 의미한다.

개념적으로는 다음과 같다.

```text
Consumer Lag
= log-end-offset - committed offset
```

즉, Partition에 쌓인 최신 메시지 위치와 Consumer Group이 처리 완료했다고 Commit한 Offset 사이의 차이다.

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```text
API Server는 Kafka에 메시지를 발행하고 빠르게 요청 접수 응답을 줄 수 있다.
하지만 Consumer가 느리면 실제 쿠폰 발급 처리는 늦어진다.
그 결과 사용자는 요청 직후에는 PENDING 상태를 보게 되고, 마이페이지나 결과 조회 API에 쿠폰이 늦게 반영될 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다.",
  "requestId": "req-20260702-000001"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패했습니다.",
  "requestId": "req-20260702-000001"
}
```

쿠폰 수량이 소진된 경우에는 메시지를 더 구체화할 수 있다.

```json
{
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```text
Consumer Lag이 일시적으로 증가했다가 줄어든다면 요청 폭증을 Consumer가 따라잡고 있다고 볼 수 있다.
반대로 Lag이 계속 증가하면 Consumer 처리량이 Producer 발행 속도를 따라가지 못한다는 신호다.
이 경우 운영자는 Consumer 수 증가, Partition 수 조정, Consumer 처리 로직 최적화, DB 병목 확인 등을 검토할 수 있다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```text
Kafka는 API Server와 Consumer 사이에 메시지를 쌓아두고 비동기 처리를 가능하게 해준다.
하지만 Consumer가 메시지를 처리하는 속도보다 Producer가 메시지를 발행하는 속도가 빠르면 Kafka에 메시지가 계속 쌓인다.
따라서 API 응답은 빨라질 수 있지만 최종 발급 처리는 Consumer 처리 속도에 따라 늦어질 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

나쁜 설계는 다음과 같다.

```text
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```text
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.
Partition Key는 eventId로 설정했다.
대부분의 요청은 eventId = 1이다.
Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.
Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.
Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| Partition이 1개뿐이다. | 같은 Consumer Group 안에서는 하나의 Partition을 하나의 Consumer만 처리할 수 있으므로 병렬 처리에 한계가 크다. | 요청량을 고려해 Partition을 여러 개로 늘린다. 예를 들어 6개 이상으로 시작해 처리량을 관찰한다. |
| Consumer가 1개뿐이다. | 이벤트 시작 직후 10만 건의 요청을 단일 Consumer가 처리하면 Consumer Lag이 크게 증가할 수 있다. | Consumer Group을 구성하고 여러 Consumer가 Partition을 나누어 처리하게 한다. |
| Partition Key가 eventId다. | 대부분의 요청이 `eventId = 1`이면 같은 Key가 반복되어 특정 Partition에 메시지가 몰릴 수 있다. | `userId` 또는 분산성이 좋은 Key를 검토한다. 사용자 기준 순서가 중요하다면 `userId`를 선택할 수 있다. |
| Kafka 발행 실패에도 요청 접수 성공 응답을 준다. | Kafka에 메시지가 없으면 Consumer가 처리할 요청도 없는데 사용자는 접수된 것으로 오해한다. | Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우에만 `PENDING` 또는 `ACCEPTED` 응답을 준다. |
| Offset Commit 실패 상황을 고려하지 않았다. | DB 저장 후 Commit 전에 Consumer가 죽으면 같은 메시지가 다시 처리되어 중복 발급될 수 있다. | DB Unique Key, requestId 기반 멱등성, 처리 상태 저장 등 중복 메시지 방어 장치를 둔다. |
| Consumer Lag이 증가해도 사용자가 상태를 확인할 수 없다. | 사용자는 요청이 처리 중인지, 성공했는지, 실패했는지 알 수 없어 사용자 경험이 나빠진다. | requestId 기반 결과 조회 API를 제공하고 `PENDING`, `ISSUED`, `FAILED` 상태를 저장한다. |
| 요청 접수 성공과 쿠폰 발급 성공을 구분하지 않는다. | API Server가 Kafka에 넣은 것만으로 발급 성공처럼 보이면 실제 처리 결과와 사용자 인식이 어긋난다. | 요청 API는 접수 상태만 응답하고, 실제 발급 결과는 결과 조회 API나 마이페이지에서 확인하게 한다. |
| Consumer 처리량과 DB 병목을 관찰할 수 있는 기준이 부족하다. | Lag이 커져도 병목이 Kafka, Consumer, DB 중 어디에 있는지 판단하기 어렵다. | Consumer Lag, 처리 성공/실패 수, DB 저장 지연 등을 모니터링한다. |
