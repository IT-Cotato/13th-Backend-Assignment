# 2주차 과제

# Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 1. 과제 목표

이번 2주차 과제의 목표는 **Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 처리하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

이번 주차에서는 그 비동기 구조를 Kafka 기반으로 구체화한다.

이번 과제에서 설계해야 하는 기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Kafka Producer
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Topic 설계

Message 구조 설계

Partition Key 선택

Consumer Group 설계

Offset Commit과 중복 처리 가능성 이해

Consumer Lag이 사용자 경험에 미치는 영향 이해

Kafka 발행 실패 시 API 응답 설계
```

이번 과제의 핵심은 Kafka를 구현하는 것이 아니라, **Kafka를 시스템 구조 안에서 어떻게 사용할지 설계하는 것**이다.

---

## 2. 기본 상황

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 쿠폰 발급 처리를 수행하는 구조를 설계한다.

단, 이번 주차에서는 Redis 선착순 판정, DB Unique Key, requestId 멱등성, Outbox Pattern, Retry Topic, DLQ는 깊게 다루지 않는다.

## 3. 이번 과제의 전제 조건

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행한다.

Kafka 발행이 성공했다는 것은 Producer가 Kafka Broker로부터 발행 성공 응답을 받은 상황을 의미한다.

Kafka 발행이 실패했다면 아직 쿠폰 발급 요청이 시스템에 안전하게 접수된 것이 아니다.

따라서 Kafka 발행에 실패한 경우에는 사용자에게 요청 접수 성공 응답을 주면 안 된다.
```

또한 발급 상태 조회를 위해 요청을 식별할 수 있는 값이 필요하다.

```
requestId는 쿠폰 발급 요청을 식별하기 위한 값이다.

이번 주차에서는 requestId를 요청 식별자와 상태 조회에 필요한 값 정도로만 이해한다.

requestId를 이용한 멱등성 처리와 중복 요청 방지는 5주차에서 자세히 다룬다.
```

Consumer Lag 상황에서 사용자가 발급 상태를 조회할 수 있어야 하므로, 이번 과제에서는 발급 요청 상태를 저장할 수 있는 저장소가 있다고 가정한다.

```
상태 예시:
PENDING
ISSUED
FAILED
```

단, 상태 저장 테이블의 상세 설계는 이번 주차의 핵심이 아니다.

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

1주차에서 선택한 **구조 B(요청 접수와 실제 발급 처리 분리)** 를 Kafka로 구체화한 흐름이다.
전체 흐름은 **세 구간**으로 나뉜다.

<img width="726" height="497" alt="Image" src="https://github.com/user-attachments/assets/9fa2f978-f2d6-461f-9d42-04316906eaff" />

- **[1] 요청 접수 구간**: 사용자가 기다리는 동기 응답 흐름. API Server는 `검증 → 상태 저장 → Kafka 발행`까지만 하고 즉시 응답한다.
- **[2] 실제 발급 구간**: 사용자 요청 흐름과 완전히 분리되어, Consumer가 자신의 속도로 처리한다.
- **[3] 결과 확인 구간**: 사용자는 나중에 `requestId`로 최종 결과를 조회한다.

이렇게 분리하면 이벤트 직후 요청이 몰려도 API Server는 무거운 발급 로직에 묶이지 않고, 요청을 Kafka에 안전하게 쌓아둔 뒤 빠르게 응답할 수 있다.

### 2. API Server의 역할

API Server는 **"요청 접수 담당자"** 다. 실제 발급은 하지 않는다.

```
1. 쿠폰 발급 요청을 받는다.
2. 로그인 여부, 이벤트 진행 시간 등 즉시 판단 가능한 값을 검증한다.
3. 요청 상태를 PENDING으로 저장하고 requestId를 부여한다.
   (사용자가 나중에 결과를 조회할 수 있도록)
4. Kafka(coupon.issue.requested)에 쿠폰 발급 요청 메시지를 발행한다.
5. Broker로부터 발행 성공 ack를 받으면, 사용자에게 요청 접수 응답(ACCEPTED)을 반환한다.
```

즉, API Server는 "발급을 끝냈다"가 아니라 **"요청을 안전하게 접수했다"까지만** 책임진다.
발급 결과를 기다리지 않으므로 스레드가 오래 점유되지 않고, 요청이 몰려도 응답이 빠르다.

### 3. Kafka의 역할

Kafka는 API Server와 Consumer 사이에서 요청 메시지를 **안전하게 전달하고 완충(buffering)** 하는 역할을 한다.

```
1. 완충 지대(Buffer)
   - 요청이 순간적으로 몰려도 메시지를 Topic에 쌓아두고,
     Consumer가 감당 가능한 속도로 꺼내 처리하게 한다. (트래픽 급증 흡수)

2. 컴포넌트 분리(Decoupling)
   - API Server는 Consumer의 처리 속도/장애와 무관하게 응답할 수 있다.
   - Consumer가 잠시 죽어도 메시지는 Topic에 그대로 남아있다.

3. 재처리 가능성(Durability)
   - 메시지를 읽었다고 바로 삭제하지 않고 일정 기간 보관하며, Offset으로 위치를 관리한다.
   - Consumer가 재시작되면 마지막 Commit 지점부터 다시 처리할 수 있다.
```

일반 Queue와 달리 Kafka는 "소비해도 삭제하지 않고 Offset으로 위치를 관리"하기 때문에, 장애 복구와 재처리에 강하다.

### 4. Consumer의 역할

Consumer(Coupon Issue Consumer)는 **"실제 발급 처리 담당자"** 다.

```
1. coupon.issue.requested Topic에서 쿠폰 발급 요청 메시지를 읽는다.
2. 메시지의 eventId, userId, requestId를 확인한다.
3. 실제 쿠폰 발급 처리를 수행한다. (수량 차감, 발급 성공/실패 최종 결정)
4. 발급 기록을 DB에 저장하고, 요청 상태를 ISSUED 또는 FAILED로 갱신한다.
5. 처리가 끝난 메시지의 Offset을 Commit한다.
```

Consumer는 여러 개를 두어 병렬 처리할 수 있고(Consumer Group), 처리 속도가 부족하면 Consumer/Partition을 늘려 처리량을 확장할 수 있다.

### 5. DB의 역할

DB는 두 가지 역할을 한다.

```
1. 요청 상태 저장소
   - API Server가 접수 시점에 PENDING을 기록한다.
   - Consumer가 처리 후 ISSUED / FAILED로 갱신한다.
   - 사용자는 requestId로 이 상태를 조회해 최종 결과를 확인한다.

2. 발급 기록 저장소
   - Consumer가 실제 쿠폰 발급 결과(누가 어떤 쿠폰을 받았는지)를 최종 저장한다.
```

즉, DB는 "지금 이 요청이 어디까지 왔는가(상태)"와 "실제로 무엇이 발급되었는가(기록)"에 대한 단일 진실 공급원(Single Source of Truth) 역할을 한다.

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
선착순 이벤트는 시작 직후 1분에 최대 10만 건이 몰린다.
이 요청을 모두 "발급 완료까지" 동기로 처리하면 API Server 스레드와 DB Connection이
발급 로직에 묶여 고갈되고, 응답 지연·Timeout·장애 전파가 발생한다.

따라서 API Server는 "요청을 안전하게 접수했다"는 사실만 빠르게 확정해 응답하고,
실제 발급(수량 차감, 성공/실패 결정)은 Consumer가 뒤에서 처리한다.

이렇게 하면
- 사용자는 요청 즉시 "접수됨" 응답을 받아 무한 대기하지 않고,
- 시스템은 순간 폭주를 Kafka로 흡수해 안정적으로 처리량을 유지할 수 있다.
```

대신 최종 결과는 요청 흐름과 분리되었으므로, 사용자는 상태 조회 API나 마이페이지에서 나중에 확인한다.
요청 직후의 응답은 **"발급 완료"가 아니라 "접수됨"** 이다.

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공
  - API Server가 요청을 정상적으로 받아, 이후 처리될 수 있도록 안전하게 기록한 상태.
  - 이 시스템에서는 "Kafka 발행 성공(Broker ack 수신)"을 접수 성공의 기준으로 삼는다.
  - 응답 예: { "status": "PENDING", "message": "쿠폰 발급 요청이 접수되었습니다." }
  - 아직 쿠폰이 발급된 것은 아니다. 처리 대기열에 안전하게 들어갔다는 뜻일 뿐이다.

쿠폰 발급 성공
  - Consumer가 실제로 발급 처리를 완료하고 DB에 기록한 상태.
  - 이때 비로소 상태가 ISSUED로 바뀐다.
  - 응답 예: { "status": "ISSUED", "message": "쿠폰이 발급되었습니다." }
```

**핵심**: 접수 성공은 "요청을 받았다", 발급 성공은 "쿠폰을 줬다"이다.
둘은 시점도 다르고 실패 원인도 다르다. (접수는 성공했어도 수량 소진으로 발급은 FAILED가 될 수 있다.)
그래서 **요청 API(접수 여부)** 와 **결과 조회 API(발급 결과)** 를 분리해서 설계한다.

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested
```

`<도메인>.<행위>.<상태>` 규칙으로 네이밍했다.

```
coupon    → 쿠폰 도메인
issue     → 발급
requested → "발급 요청이 들어왔다"는 상태(과거형)
```

`requested`(요청됨)를 쓴 이유는, 이 Topic이 담는 것이 **"발급 완료"가 아니라 "발급 요청"** 이라는 사실을
이름만 봐도 알 수 있게 하기 위해서다. 나중에 `coupon.issue.succeeded` 같은 완료 이벤트 Topic이
추가되더라도 이름 규칙이 일관되게 확장된다.

### 2. Topic에 담기는 메시지의 의미

```
"어떤 사용자가, 어떤 이벤트의 쿠폰 발급을 요청했다."

- 아직 발급된 것이 아니라, "발급 요청이 접수되었으니 뒤에서 처리해달라"는 작업 지시(command)에 가깝다.
- 메시지 하나 = 처리해야 할 쿠폰 발급 요청 1건.
- 이 메시지를 Consumer가 읽어 실제 발급 처리를 수행한다.
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
Producer: API Server

발행 시점:
1. 사용자의 쿠폰 발급 요청을 받는다.
2. 로그인 여부, 이벤트 진행 시간 등 기본 검증을 통과한다.
3. 요청 상태를 PENDING으로 저장한다.
4. → 이 시점에 coupon.issue.requested Topic으로 발급 요청 메시지를 발행한다.

즉, "검증을 통과해 접수할 가치가 있는 요청"에 대해서만 발행한다.
검증에서 걸러진 요청(비로그인, 이벤트 종료 등)은 Kafka에 발행하지 않고 즉시 실패 응답한다.
(불필요한 메시지로 Consumer 부하를 늘리지 않기 위해서)
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Consumer: Coupon Issue Consumer

수행 처리:
1. coupon.issue.requested Topic에서 메시지를 읽는다.
2. 메시지의 eventId, userId, requestId를 확인한다.
3. 실제 쿠폰 발급 처리를 수행한다. (수량 차감, 발급 성공/실패 최종 결정)
4. 발급 기록을 DB에 저장하고, 요청 상태를 ISSUED 또는 FAILED로 갱신한다.
5. 처리 완료 후 Offset을 Commit한다.
```

### 5. 이 Topic이 필요한 이유

```
1. 요청 접수와 실제 발급 처리를 분리하기 위해서다.
   - API Server는 이 Topic에 메시지만 넣고 빠르게 응답할 수 있다.
   - 실제 무거운 발급 처리는 Consumer가 뒤에서 수행한다.

2. 트래픽 급증을 흡수하기 위해서다.
   - 이벤트 직후 10만 건이 몰려도, Topic이 완충 지대가 되어 요청을 쌓아둔다.
   - Consumer는 감당 가능한 속도로 꺼내 처리하므로 DB가 순간 폭주에 무너지지 않는다.

3. 안정적인 전달과 재처리를 위해서다.
   - 메시지가 Topic에 안전하게 보관되므로, Consumer가 잠시 죽어도 요청이 유실되지 않는다.
   - Consumer 재시작 시 마지막 Commit 이후부터 다시 처리할 수 있다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
"쿠폰 발급 요청이 시스템에 안전하게 접수되었고, 이 요청을 나중에 Consumer가 처리해야 한다."

- API Server가 Broker로부터 발행 성공 ack를 받은 상태다.
- 이 시점에 비로소 사용자에게 "요청 접수 성공(PENDING)" 응답을 줄 수 있다.
- 반대로 발행에 실패했다면 메시지가 Topic에 없으므로, 접수 성공으로 봐서는 안 된다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
Topic에 메시지가 들어간 것은 "처리해야 할 요청이 대기열에 쌓였다"는 뜻일 뿐,
아직 Consumer가 그 메시지를 읽어 발급 처리를 하지 않았기 때문이다.

- Consumer 처리 전이라면 아직 수량 차감도, 발급 기록 저장도 일어나지 않았다.
- Consumer Lag이 크면 메시지는 Topic에 있지만 발급은 한참 뒤에 일어날 수 있다.
- 또한 접수는 되었어도 수량 소진으로 최종 결과가 FAILED가 될 수도 있다.

따라서 이 Topic의 메시지는 "발급 완료"가 아니라 "발급 요청 접수"를 의미하며,
사용자에게도 "발급 완료"가 아니라 "요청 접수/처리 중" 응답을 주는 것이 정확하다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-06-26T12:00:00Z"
}
```

- `requestId`는 요청마다 고유해야 하므로 UUID 형태를 사용했다.
- `requestedAt`은 타임존 혼동을 막기 위해 UTC 기준(ISO-8601, `Z`)으로 표기했다.

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| requestId | 쿠폰 발급 요청 1건을 식별하는 고유 ID | 사용자가 결과를 조회할 키이자, 로그 추적·중복 판단(멱등성, 5주차)의 기준이 됨 |
| eventId | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 수량을 차감할지 판단하려면 반드시 필요함 |
| userId | 요청을 보낸 사용자 ID | "1인 1매" 조건 검증과 누구에게 발급할지 결정하는 데 필요함 |
| requestedAt | 사용자가 요청한 시각 | 요청 시각 추적, 처리 지연(Lag) 분석, 장애 추적 시 시간 기준이 됨 (선착순 판정 자체의 근거로는 쓰지 않는다 — 아래 주석 참고) |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
Consumer는 이 4개 필드만으로 발급 처리에 필요한 판단을 모두 할 수 있다.

- eventId → 어떤 이벤트의 쿠폰 수량을 차감할지 결정한다.
- userId  → 이 사용자가 이미 발급받았는지 확인하고(1인 1매), 누구에게 발급할지 정한다.
- requestId → 처리 결과(ISSUED/FAILED)를 어떤 요청 상태에 반영할지 식별한다.
              (같은 메시지가 재처리될 때 중복 판단의 기준으로도 쓸 수 있다 - 5주차)
- requestedAt → 요청 시각 추적, 처리 지연(Lag) 분석, 장애 추적 시 시간 기준으로 활용한다.

즉, "어떤 이벤트(eventId)의 쿠폰을, 어떤 사용자(userId)에게, 어떤 요청(requestId)으로 발급하는가"
라는 처리에 필요한 최소 정보가 모두 담겨 있다.

> 주의: `requestedAt`(사용자가 누른 시각)을 선착순 판정의 근거로 삼지 않는다. 실제 선착순은 보통
> Redis/DB에 도착해 **원자적으로 처리된 순서**를 기준으로 하고, Kafka도 Partition이 여러 개면 전체
> 요청의 전역 순서를 보장하지 않기 때문이다. 그래서 `requestedAt`은 추적·지연·장애 분석용 시간 값으로만
> 쓰고, 전역 선착순 판정은 3주차 Redis 계층에서 별도로 다룬다.
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
1. 데이터 정합성(stale data) 문제
   - 사용자 이름, 등급, 쿠폰 상세 같은 값을 메시지에 넣으면, 메시지가 Topic에 쌓여
     처리가 지연되는 동안 원본 데이터가 바뀔 수 있다. → 발행 시점의 옛 값으로 처리되는 위험.
   - 자주 바뀌는 값은 메시지에 넣지 말고, Consumer가 처리 시점에 식별자(ID)로 DB를 조회해야 한다.

2. 결합도 증가
   - 메시지에 특정 컬럼을 많이 담을수록 Producer와 Consumer가 그 스키마에 강하게 묶인다.
   - 필드 하나 바뀔 때마다 양쪽을 함께 배포해야 하는 부담이 생긴다.

3. 성능·비용 문제
   - 10만 건 규모에서 메시지 크기가 커지면 네트워크 대역폭, Broker 저장 공간,
     직렬화/역직렬화 비용이 모두 증가한다.

4. 보안·개인정보 노출
   - Kafka 메시지는 일정 기간 보관되므로, 이름·전화번호 같은 민감정보를 넣으면
     불필요하게 보관·노출되는 위험이 커진다.

결론: 메시지에는 "Consumer가 처리에 필요한 최소한의 식별자"만 담고,
      나머지 상세 정보는 처리 시점에 DB에서 조회하는 것이 안전하다. (Claim Check 관점)
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
이번 2주차에서는 requestId를 "요청 하나를 구분하는 식별자" 정도로만 이해한다.

- 사용자가 발급 결과를 조회할 때 쓰는 조회 키.
- 로그/모니터링에서 특정 요청의 처리 흐름을 추적하는 값.
- "같은 요청이 여러 번 들어왔는지" 판단할 때 기준이 될 수 있는 값.

다만, requestId를 이용해 실제로 중복 처리를 막는 "멱등성 처리"는 5주차에서 다룬다.
(예: requestId에 Unique 제약을 걸어 같은 요청이 두 번 발급되지 않게 하는 것 등)
이번 주차에서는 "중복 처리가 발생할 수 있다"는 사실과, 그때 requestId가 열쇠가 된다는 정도만 인지한다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 결과는 잠시 후 확인해 주세요.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

- HTTP 상태 코드는 **202 Accepted**를 사용한다. "요청은 받아 처리를 시작했지만 아직 완료되지 않았다"는
  의미를 정확히 표현하기 때문이다. (200 OK는 "완료"로 오해될 수 있어 부적절)
- `status`는 `ACCEPTED` 대신 `PENDING`을 썼다. 결과 조회 API의 상태값(PENDING/ISSUED/FAILED)과
  용어를 통일해, 사용자가 조회 시 상태 변화를 자연스럽게 이해할 수 있도록 하기 위해서다.

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
이 시점에 완료된 것은 "Kafka에 요청 메시지를 안전하게 발행했다"는 것뿐이다.

- 아직 Consumer가 메시지를 읽지 않았고, 수량 차감도 발급 기록 저장도 일어나지 않았다.
- 접수는 성공했어도 실제 처리 시점에 수량이 소진되어 있으면 결과는 FAILED가 될 수 있다.
- Consumer Lag이 크면 실제 발급은 한참 뒤에 일어난다.

따라서 이 응답은 "발급 완료"가 아니라 "요청을 접수해 처리 대기열에 안전하게 넣었다"는 뜻이며,
status를 PENDING(처리 중)으로 표현하는 것이 정확하다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공
  - 기준: Kafka 발행 성공(Producer가 Broker로부터 발행 성공 ack 수신).
  - 의미: 요청이 유실되지 않고 처리 대기열에 안전하게 들어갔다.
  - 응답: 202 Accepted, status = PENDING.

쿠폰 발급 성공
  - 기준: Consumer가 실제 발급 처리를 완료하고 DB에 기록.
  - 의미: 수량 차감이 끝나고 해당 사용자에게 쿠폰이 실제로 지급됨.
  - 상태: ISSUED.

접수는 "요청 API"의 책임이고, 발급은 "Consumer + 결과 조회 API"의 영역이다.
두 시점 사이에는 Kafka 대기 시간(Lag)이 존재하며, 결과가 뒤집힐(FAILED) 수도 있다.
```

#### 4. requestId를 응답에 포함하는 이유

```
1. 결과 조회의 키
   - 사용자는 요청 직후 최종 결과를 받지 못하므로, 나중에 이 requestId로 상태 조회 API를 호출해
     PENDING / ISSUED / FAILED를 확인한다. requestId가 없으면 "내 요청"을 특정할 수 없다.

2. 장애 추적(Observability)
   - 문제가 생겼을 때 requestId 하나로 API 로그 → Kafka 메시지 → Consumer 처리 로그까지
     하나의 요청 흐름을 추적할 수 있다.

3. 중복 요청 문의 대응
   - 사용자가 "발급됐나요?"라고 문의할 때 requestId 기준으로 상태를 조회해 답할 수 있고,
     5주차의 멱등성 처리에서도 이 값이 기준이 된다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "ACCEPT_FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해 주세요.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

- HTTP 상태 코드는 **503 Service Unavailable**(또는 500)을 사용한다. 서버 측 사정으로 요청을
  접수하지 못했음을 나타내고, 클라이언트가 재시도해도 되는 상황임을 표현한다.
- 메시지에 "다시 시도해 주세요"를 넣어, 사용자가 재요청하면 정상 접수될 수 있음을 안내한다.
- `status`는 `FAILED`가 아니라 **`ACCEPT_FAILED`**로 표기했다. Consumer가 발급을 처리한 뒤의
  "쿠폰 발급 실패(FAILED, 예: 수량 소진)"와 지금의 "요청 접수 실패(Kafka 발행 자체가 안 됨)"는
  시점도 원인도 다르기 때문이다. 접수 단계 실패임을 이름으로 분명히 드러내 상태 의미가 섞이지 않게 한다.
- `requestId`에 대한 주의: 구조 B는 발행 전에 요청 상태를 DB에 먼저 저장하므로 requestId가 이미
  생성돼 있을 수 있다. 다만 Kafka에 메시지가 들어가지 않았다면 Consumer가 처리할 요청은 없으므로,
  이 requestId를 "정상 발급 진행 중인 요청 조회용"으로 오해하게 두면 안 된다.
  따라서 두 선택지 중 하나를 택한다.
  - (a) 해당 DB 레코드를 `ACCEPT_FAILED` 상태로 확정 저장하고, requestId를 **"조회 시 접수 실패로
    응답되는" 레코드의 식별자**로 내려준다. (재시도·추적 근거로 활용)
  - (b) 접수 실패 레코드를 남기지 않는다면 `requestId: null`로 내려, 조회 가능한 요청이 없음을 명확히 한다.

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
Kafka 발행에 실패하면 Topic에 메시지가 없다. 즉, Consumer가 처리할 요청이 시스템에 존재하지 않는다.

이때 사용자에게 "접수되었습니다(PENDING)"라고 응답하면 심각한 불일치가 생긴다.

- 사용자: "요청이 접수됐으니 곧 발급되겠지" 하고 기다린다.
- 시스템: 처리할 메시지가 없으므로 영원히 발급되지 않는다. (유실된 요청)

결과적으로 사용자는 조회 API에서 계속 PENDING만 보거나, 아예 상태 자체가 없는 상태가 되어
"접수는 됐다는데 왜 발급이 안 되냐"는 신뢰 붕괴로 이어진다.

접수 성공의 기준은 "요청이 유실되지 않고 처리 대기열에 안전하게 들어갔는가"이다.
Kafka 발행 실패는 이 기준을 충족하지 못하므로, 접수 성공 응답을 주면 안 된다.
(→ 이것이 과제 9 나쁜 설계의 대표적 문제이기도 하다.)
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
1. 상태 불일치를 남기지 않기
   - 발행 전에 DB에 PENDING을 미리 저장했다면, 발행 실패 시 그 상태를 FAILED로 정리하거나
     롤백해야 한다. "PENDING인데 Kafka엔 메시지가 없는" 유령 요청을 남기면 안 된다.
   - 이 순서 문제(DB 저장과 Kafka 발행의 원자성)를 근본적으로 푸는 것이 6주차 Outbox Pattern이다.

2. 실패를 성공처럼 숨기지 않기
   - 발행 실패를 삼키고 PENDING을 응답하는 것이 가장 위험하다. 실패는 실패로 정직하게 응답한다.

3. 재시도는 신중하게
   - 일시적 오류(네트워크, 리더 선출 등)라면 Producer 레벨의 짧은 재시도로 흡수할 수 있다.
   - 다만 무한 대기·과도한 재시도는 API 응답 지연으로 이어지므로, 재시도 횟수/타임아웃을 제한하고
     그래도 실패하면 즉시 FAILED로 응답한다. (본격적인 재처리·DLQ는 8주차)

4. 사용자에게 명확한 안내
   - "일시적 오류로 접수 실패, 재시도 요망"임을 알려, 사용자가 안전하게 다시 요청하도록 유도한다.
```

## 과제 5. Partition Key 선택하기

`coupon.issue.requested` Topic의 Partition Key를 무엇으로 정할지 선택한다.

아래 후보 중 하나를 선택하거나, 직접 다른 Key를 제안해도 된다.

```
1. userId

2. eventId

3. requestId

4. 그 외 직접 선택
```

특히 `eventId`를 Partition Key로 선택한 경우에는 아래 상황을 반드시 고려한다.

```
이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰린다.
```

이때 모든 메시지가 특정 Partition에 몰릴 수 있는지 설명한다.

이번 과제에서는 정답 Partition Key를 하나로 고정하지 않는다.

중요한 것은 자신이 선택한 Partition Key가 아래 항목에 어떤 영향을 주는지 설명하는 것이다.

```
메시지 분산

순서 보장

특정 Partition 쏠림 가능성

Consumer 병렬 처리
```

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자 요청이 같은 Partition으로 감 → 사용자 기준 순서 관리·"1인 1매" 중복 판단에 유리. 사용자가 매우 많으므로 분산도 고르게 이뤄짐 | 특정 사용자가 비정상적으로 많은 요청을 보내면 해당 Partition에 일시적 부하(Hot Key)가 생길 수 있음 |
| eventId | 같은 이벤트 요청을 한 곳에 묶어 보기 쉬움 | **선착순 이벤트에서는 대부분 eventId=1 하나에 몰림 → 특정 Partition 쏠림, Partition을 늘려도 병렬 처리 효과가 사라짐** |
| requestId | 요청마다 Key가 달라 가장 고르게 분산됨 | 같은 사용자 요청이 서로 다른 Partition으로 흩어져 사용자 기준 순서 보장·중복 추적이 어려움 |

### 2. 내가 선택한 Partition Key

```
userId
```

### 3. 선택한 이유

```
선착순 쿠폰 이벤트의 두 가지 특성을 동시에 만족하기 때문이다.

1. 분산이 고르다 (가장 중요)
   - 이 시스템의 핵심 위험은 "하나의 인기 이벤트에 요청이 몰리는 것"이다.
   - eventId를 Key로 쓰면 eventId=1 요청 10만 건이 전부 한 Partition에 몰려 병렬 처리가 무력화된다.
   - 반면 userId는 요청 주체가 수많은 사용자로 흩어져 있어 여러 Partition에 자연스럽게 분산된다.
     (게다가 "1인 1매" 조건 덕분에 한 사용자의 정상 요청 수가 제한적이다.)

2. 같은 사용자 순서/중복 판단에 유리하다
   - 사용자가 버튼을 여러 번 눌러도 같은 userId 요청은 같은 Partition으로 들어가 순서대로 처리된다.
   - "1인 1매"를 지켜야 하는 이 시스템에서, 같은 사용자의 중복 요청이 같은 Partition에서
     순차 처리되면 중복 발급 판단(5주차 멱등성)을 다루기 훨씬 수월하다.

즉, "분산은 확보하면서 사용자 단위 정합성도 챙길 수 있다"는 점에서 userId가 가장 균형 잡힌 선택이다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
Kafka는 Key의 해시값을 Partition 수로 나눠 배치하므로, Key 종류가 다양할수록 고르게 분산된다.

- userId는 값의 가짓수가 매우 많다(사용자 수만큼). → 메시지가 여러 Partition에 골고루 퍼진다.
- 특정 이벤트 하나에 요청이 집중되는 상황에서도, 요청을 보낸 사용자는 제각각이므로
  Partition 쏠림 없이 분산된다. → Consumer들이 병렬로 처리하기 좋은 구조가 된다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
Kafka는 "같은 Partition 안에서만" 순서를 보장한다. userId를 Key로 쓰면
같은 사용자의 요청은 항상 같은 Partition으로 들어가므로, 사용자 기준 순서가 보장된다.

- 같은 사용자가 연속으로 두 번 눌러도 먼저 온 요청이 먼저 처리된다.
- 반대로 "서로 다른 사용자 간의 전체 순서"는 보장되지 않는다. 하지만 선착순은
  "먼저 접수된 요청부터 발급"이 Partition 하나 안의 미시적 순서까지 엄밀히 맞아야 하는 것은 아니고,
  전역 선착순 판정은 3주차 Redis에서 별도로 다루므로 userId 기준 순서 보장으로 충분하다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
일반적인 상황에서는 몰릴 가능성이 낮다. 사용자 수가 많고 "1인 1매"라 한 사용자의 요청 수가 제한적이라,
userId 기준으로 자연스럽게 분산되기 때문이다.

다만 예외적으로 Hot Key 위험은 있다.
- 특정 userId가 봇/스크립트로 비정상적으로 많은 요청을 보내면 해당 Partition에 일시적 부하가 생길 수 있다.
- 이는 요청 속도 제한(Rate Limiting), 중복 요청 차단으로 완화할 수 있다.
- 그래도 eventId처럼 "구조적으로 모든 요청이 한 Partition에 몰리는" 문제와는 성격이 다르다.
  (eventId 쏠림은 정상 트래픽에서도 항상 발생하지만, userId Hot Key는 비정상 요청에서만 예외적으로 발생)
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
1. Hot Key 가능성: 특정 사용자의 비정상적 대량 요청 시 일부 Partition에 부하가 몰릴 수 있다.
2. 전역 순서 미보장: 서로 다른 사용자 간의 전체 처리 순서는 보장되지 않는다.
   (단, 이 시스템에서 전역 선착순 판정은 Redis 등 별도 계층에서 처리하므로 큰 제약은 아니다.)
3. Partition 수 변경 시 재배치: 나중에 Partition 수를 바꾸면 같은 userId가 다른 Partition으로
   갈 수 있어, "같은 사용자는 항상 같은 Partition" 전제가 재배치 이후 요청부터는 달라질 수 있다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
선착순 이벤트에서 eventId를 Key로 쓰는 것은 이 시스템의 핵심 문제와 정면충돌한다.

- 이벤트 시작 직후 대부분의 요청이 eventId=1 하나에 몰린다.
- 같은 Key는 같은 Partition으로 가므로, 10만 건이 전부 한 Partition에 쌓인다.
- 그 결과 Partition을 3개, 5개로 늘리고 Consumer를 여러 개 띄워도, 실제로는 하나의 Consumer만
  일하고 나머지는 논다. → 병렬 처리 효과가 사라지고 Consumer Lag이 그 Partition에 집중된다.

정리하면, eventId는 "묶어 보기 좋다"는 장점보다 "쏠림으로 병렬성이 무너진다"는 단점이 훨씬 크다.
동시에 진행되는 이벤트가 Partition 수만큼 충분히 많고 트래픽이 고르게 분산되는 경우가 아니라면,
선착순 시스템에서 eventId 단독 Key는 피해야 한다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
Kafka는 "Partition 단위"로만 순서를 보장한다.
같은 Partition 안에서는 Offset이 순차적으로 증가하고 Consumer도 그 순서대로 읽으므로,
먼저 들어간 메시지가 먼저 처리된다.

하지만 서로 다른 Partition에 들어간 메시지 A, B의 전체 순서는 보장되지 않는다.

이유:
- Partition은 서로 독립적인 로그이며, 각 Partition을 처리하는 Consumer(또는 처리 속도)가 다르다.
- A가 Partition 0, B가 Partition 1에 있다면, 두 Partition은 병렬로 소비되므로
  B가 A보다 먼저 처리될 수도 있다. Kafka는 Partition 간의 전역 순서를 조율하지 않는다.

따라서 "어떤 기준의 순서"가 중요하다면 그 기준을 Partition Key로 삼아 같은 Partition에 모아야 한다.
이 시스템에서는 userId를 Key로 삼아 "같은 사용자 기준의 순서"를 보장하도록 설계했다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

쿠폰 발급 요청을 처리하는 Consumer Group을 설계한다.

기본 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.

Consumer는 coupon.issue.requested Topic을 읽는다.

Consumer는 실제 쿠폰 발급 처리를 수행한다.
```

이번 과제에서 정확한 처리량 계산이 목적은 아니다.

중요한 것은 아래 내용을 이해하고 설명하는 것이다.

```
Partition 수가 Consumer 병렬 처리에 어떤 영향을 주는가?

Consumer Group은 왜 필요한가?

Consumer 수와 Partition 수의 관계는 무엇인가?

Consumer 수만 무작정 늘리면 왜 안 되는가?
```

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
10개

간단한 처리량 감각:
- 10만 건 / 60초 ≈ 평균 1,667 msg/s. 실제로는 시작 0~5초에 몰려 순간 RPS는 이보다 몇 배 높다.
- Consumer 하나가 발급 처리(DB 쓰기 포함)에 약 5ms가 걸린다고 보면 단일 Consumer는 초당 약 200건 처리.
- 평균 1,667 msg/s를 감당하려면 약 8~9개의 병렬 처리가 필요하고, 순간 폭주까지 고려해 여유를 둔다.

→ 병렬 처리의 상한은 Partition 수이므로, Partition을 10개로 두어 최대 10개 Consumer까지
   병렬 확장할 수 있게 한다. (약간의 헤드룸 포함)
```

### 3. Consumer Group 이름

```
coupon-issue-group
```

같은 Topic을 나눠 처리하는 발급 Consumer들을 하나의 Group으로 묶는다. Group 하나 안에서는
Partition이 Consumer들에게 겹치지 않게 나뉘어, 같은 메시지를 여러 Consumer가 중복 처리하지 않는다.

### 4. Consumer 수

```
평상시 3개, 이벤트 피크 시 최대 10개까지 오토스케일

- 평소에는 트래픽이 적으므로 3개로 충분하다(자원 낭비 방지).
- 이벤트 시작 직후 Lag이 늘면 Partition 수(10)까지 Consumer를 늘려 병렬 처리량을 끌어올린다.
```

### 5. Partition과 Consumer 매핑

```
[피크 시] Partition 10개, Consumer 10개 → 1:1 매핑

Partition 0 → Consumer 1
Partition 1 → Consumer 2
Partition 2 → Consumer 3
Partition 3 → Consumer 4
Partition 4 → Consumer 5
Partition 5 → Consumer 6
Partition 6 → Consumer 7
Partition 7 → Consumer 8
Partition 8 → Consumer 9
Partition 9 → Consumer 10

[평상시] Partition 10개, Consumer 3개 → 한 Consumer가 여러 Partition 담당
Consumer 1 → Partition 0,1,2,3
Consumer 2 → Partition 4,5,6
Consumer 3 → Partition 7,8,9
```

### 6. 이 구조를 선택한 이유

```
1. 병렬 처리 상한을 미리 확보
   - 병렬 처리의 최대 단위는 Partition 수다. Partition을 넉넉히(10) 잡아두면,
     Consumer만 늘려서 최대 10배 병렬까지 확장할 수 있다.
   - Partition 수는 나중에 늘릴 수는 있어도 줄이기 어렵고, 늘리면 기존 Key→Partition 매핑이
     바뀌므로, 처음에 예상 피크를 고려해 여유 있게 잡는 편이 안전하다.

2. Consumer는 탄력적으로
   - Partition은 고정(10)해두고, Consumer 수를 Lag에 따라 3~10개로 오토스케일한다.
   - 평상시엔 적게(비용 절감), 피크엔 최대치로(처리량 확보) 운용한다.

3. Consumer 수 ≤ Partition 수 원칙 준수
   - Consumer를 Partition 수(10)보다 많이 띄우지 않는다. 넘겨도 노는 Consumer만 생기기 때문이다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
최대 3개.

같은 Consumer Group 안에서 하나의 Partition은 하나의 Consumer에만 할당된다.
Partition이 3개뿐이므로 3개의 Consumer만 Partition을 배정받아 처리하고,
나머지 2개는 할당받을 Partition이 없어 논다(대기 상태).
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
남는 Consumer가 놀게 된다.

- Partition 수만큼만 Consumer가 배정되고, 초과된 Consumer는 아무 Partition도 받지 못한다.
- 이들은 대기 상태로 자원(메모리, 스레드, 인스턴스 비용)만 차지하고 처리량에는 기여하지 못한다.
- 다만 완전히 무의미하진 않다. 처리 중이던 Consumer가 죽으면 리밸런싱을 통해
  대기하던 Consumer가 그 Partition을 넘겨받는 "예비(standby)" 역할은 할 수 있다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
한 Consumer가 여러 Partition을 담당한다.

- 모든 Partition은 빠짐없이 처리되지만, Consumer 하나가 여러 Partition을 맡으므로
  Consumer당 처리 부담이 커진다.
- 처리 속도가 발행 속도를 못 따라가면 Consumer Lag이 쌓인다.
- 이때는 Consumer를 늘려(Partition 수 한도 내에서) 부담을 나눠주면 처리량이 개선된다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
1. Partition 수가 병렬 처리의 상한이다
   - Consumer를 Partition 수보다 많이 늘려도 초과분은 놀기만 한다. 처리량은 늘지 않고 비용만 는다.

2. 진짜 병목이 Consumer 개수가 아닐 수 있다
   - 발급 처리의 최종 병목은 대개 DB(Connection Pool, Lock, 수량 차감 경합)다.
   - Consumer만 늘리면 DB로 동시 요청이 몰려 오히려 DB가 병목/장애 지점이 된다.
     (Kafka를 넣어 병목을 뒤로 미뤘는데, Consumer를 과하게 늘리면 병목이 다시 DB로 돌아온다.)

3. 리밸런싱 비용
   - Consumer가 늘거나 줄 때마다 Partition 재배정(리밸런싱)이 일어나며,
     그동안 잠시 처리가 멈출 수 있다. 잦은 스케일 변경은 오히려 처리 안정성을 해친다.

결론: 처리량을 늘리려면 "Consumer 수"만이 아니라 Partition 수, Consumer 처리 로직 최적화,
      DB 처리 능력을 함께 고려해야 한다. Consumer 수는 Partition 수를 상한으로 두고 조절한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

Kafka Consumer가 메시지를 처리하는 도중 장애가 발생하는 상황을 분석한다.

아래 상황을 읽고 질문에 답한다.

```
1. Consumer가 Kafka 메시지를 읽었다.

2. Consumer가 DB 저장까지 성공했다.

3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.

4. Consumer가 다시 실행되었다.
```

이번 과제에서는 이 문제를 완전히 해결하는 것이 목적이 아니다.

중요한 것은 Kafka Consumer에서 아래 상황이 발생할 수 있음을 이해하는 것이다.

```
DB 처리는 성공했지만 Offset Commit은 실패할 수 있다.

Offset Commit이 실패하면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못할 수 있다.

그 결과 같은 메시지가 다시 읽히고 다시 처리될 수 있다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
"DB 저장까지 성공했지만 Offset Commit은 못한" 바로 그 메시지를 다시 읽는다.

Consumer는 재시작 시 "마지막으로 Commit된 Offset의 다음"부터 읽기 시작한다.
그런데 이 메시지는 처리(DB 저장)는 끝났지만 Commit 전에 죽었으므로,
Kafka에 기록된 마지막 Commit Offset은 이 메시지 "이전"을 가리킨다.
따라서 재시작하면 이미 DB에 저장까지 마친 이 메시지를 처음부터 다시 읽게 된다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Kafka는 Consumer 내부에서 DB 저장이 끝났는지 전혀 알지 못하기 때문이다.

- Kafka가 "여기까지 처리됐다"고 인정하는 유일한 신호는 Offset Commit이다.
- "메시지를 읽었다" ≠ "처리가 끝났다"이며, Kafka는 오직 Commit 기록만 본다.
- DB 저장은 성공했어도 Commit이 안 됐으므로, Kafka 입장에서 이 메시지는 여전히 "미처리" 상태다.

즉, 실제 처리 완료 여부(DB 저장)와 Kafka가 아는 완료 여부(Commit)가 어긋난 것이 원인이다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
그렇다. 다시 처리될 수 있다.

재시작한 Consumer는 이 메시지를 미처리로 보고 다시 읽어, 발급 로직을 한 번 더 실행한다.
이것이 Kafka의 기본 전달 보장인 at-least-once(최소 한 번 이상)의 전형적인 결과다.
Kafka를 쓴다고 해서 "정확히 한 번" 처리가 보장되는 것은 아니며,
장애 상황에서는 같은 메시지가 두 번 이상 처리될 수 있다고 가정해야 한다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
아무런 방어 장치가 없다면 중복 발급이 발생한다.

- 같은 요청(requestId)이 두 번 처리되어, 같은 사용자에게 같은 쿠폰이 두 번 발급될 수 있다.
  → "1인 1매" 조건 위반.
- 쿠폰 수량이 실제보다 더 많이 차감되어, 준비한 1,000개보다 많이 나가는 초과 발급이 생길 수 있다.
  → 재고/정산 불일치, 비즈니스 손실.
- 발급 완료 알림이 두 번 나가는 등 사용자 경험도 나빠진다.

선착순·수량 제한 시스템에서 중복 처리는 곧바로 정합성 사고로 이어지므로 반드시 방어해야 한다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

답변:

```
핵심 아이디어: "같은 메시지가 다시 와도(재처리돼도) 결과가 한 번 처리한 것과 같도록" 만든다. (멱등성)

1. DB Unique Key로 최종 방어 (4주차)
   - (eventId, userId)에 Unique 제약을 걸어, 같은 사용자가 같은 이벤트에서 두 번 저장되지 못하게 한다.
   - 재처리로 INSERT가 또 시도돼도 Unique 위반으로 실패시켜 중복 발급을 물리적으로 차단한다.
     (DB가 마지막 안전망 역할)

2. requestId 기반 멱등성 (5주차)
   - requestId를 유일 키로 삼아, "이미 처리한 requestId면 다시 처리하지 않고 기존 결과를 반환"한다.
   - 애플리케이션 레벨에서 재처리를 걸러내는 방어선.

3. 처리 상태 저장
   - 요청 상태(PENDING/ISSUED/FAILED)를 저장해두고, Consumer가 처리 전에 상태를 확인한다.
   - 이미 ISSUED/FAILED로 확정된 요청이면 발급 로직을 건너뛴다.

4. 중복 메시지 방어(운영 관점)
   - at-least-once를 전제로, 재처리가 발생해도 안전하도록 위 장치들을 조합한다.
   - 반복 실패하는 메시지는 8주차의 재처리/DLQ로 격리해 무한 재처리를 막는다.

이번 2주차에서는 "이 문제가 존재한다(중복 처리 가능성)"는 사실을 인식하는 것까지가 목표이고,
구체적 해결은 4·5·8주차에서 다룬다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

Kafka를 사용하면 API Server는 사용자에게 빠르게 요청 접수 응답을 줄 수 있다.

하지만 Consumer 처리 속도가 느리면 Kafka에 메시지가 쌓일 수 있다.

아래 상황을 읽고 답한다.

```
이벤트 시작 직후 요청이 급격히 증가했다.

API Server는 Kafka에 메시지를 빠르게 발행하고 있다.

하지만 Consumer 처리 속도가 Producer 발행 속도보다 느리다.

Kafka에 아직 처리되지 않은 메시지가 계속 쌓이고 있다.
```

이번 과제에서는 사용자가 발급 상태를 조회할 수 있도록 요청 상태가 저장되어 있다고 가정한다.

상태는 아래와 같이 단순화해서 사용한다.

```
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태

ISSUED: 쿠폰 발급이 성공한 상태

FAILED: 쿠폰 발급이 실패한 상태
```

### 1. Consumer Lag이란 무엇인가?

```
Consumer Lag = log-end-offset − committed offset
             = (Partition에 쌓인 최신 메시지 위치) − (Consumer Group이 처리 완료로 Commit한 위치)

즉, "아직 처리하지 못하고 밀려 있는 메시지 수"다.

- Producer 발행 속도 > Consumer 처리 속도이면 Lag이 계속 증가한다.
  (예: 초당 1,000건 발행, 초당 300건 처리 → 초당 700건씩 쌓임)
- Lag은 "지금 시스템이 얼마나 밀려 있는가"를 보여주는 핵심 지표다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
API 응답(요청 접수)은 여전히 빠르지만, 실제 발급 결과가 나오기까지의 시간이 길어진다.

- 사용자는 요청 직후 "접수됨(PENDING)"은 즉시 받지만,
  결과 조회 API에서 한참 동안 계속 PENDING만 보게 된다.
- 마이페이지에 쿠폰이 늦게 반영되고, 발급 완료 알림도 지연된다.
- 대기가 길어지면 "발급된 건지 아닌지" 불안해하고, 새로고침/재요청을 반복해
  오히려 부하를 키울 수 있다.

핵심: Kafka로 API는 빨라졌지만, Lag이 크면 "체감 발급 완료 시간"은 여전히 느릴 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 결과는 잠시 후 확인해 주세요.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급을 처리 중입니다. 잠시 후 다시 확인해 주세요.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되어 발급에 실패했습니다.",
  "requestId": "req-9f1c2a7b-3e2d-4a1b-8c6d-1f2e3a4b5c6d"
}
```

> 참고: 요청 직후(과제 4 상황 A)와 조회 중 PENDING은 같은 `status: "PENDING"`이지만 문구를 구분했다.
> 접수 직후는 "요청이 접수되었습니다", 조회 시점은 "처리 중입니다"로, 사용자가 지금 어느 단계인지
> 자연스럽게 인지하도록 했다. 결과 조회 API는 이 네 상태(PENDING/ISSUED/FAILED)를 그대로 노출한다.

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
Lag은 운영자에게 "시스템이 얼마나, 어디서 밀려 있는가"를 알려주는 신호다.

1. 처리량 부족 감지
   - Lag이 계속 증가하면 Consumer 처리 속도가 발행 속도를 못 따라간다는 뜻이다.
     → Consumer 증설(Partition 수 한도 내), 처리 로직/DB 튜닝을 검토한다.

2. 특정 Partition 쏠림 감지
   - 특정 Partition에만 Lag이 몰려 있으면 Partition Key 설계 문제(예: eventId 쏠림)를 의심할 수 있다.

3. 장애/정체 감지
   - Lag이 줄지 않고 정체되면 Consumer가 죽었거나 특정 메시지에서 계속 실패(무한 재처리)하는지 본다.
     → 8주차의 재처리/DLQ 대상 판단.

4. 스케일 판단과 사용자 안내
   - Lag 추이로 "예상 처리 완료 시각"을 가늠하고, 필요 시 사용자에게 지연 안내를 노출할 수 있다.

즉, Lag은 처리량 조절(Consumer 스케일)과 장애 탐지의 핵심 모니터링 지표다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
Kafka는 병목을 "없애는" 것이 아니라 "위치를 옮기고 완충"하는 도구이기 때문이다.

- Kafka 도입 전: API Server와 DB에 부하가 집중 → 응답 지연/Timeout.
- Kafka 도입 후: API 응답은 빨라진다. 하지만 요청은 Topic에 쌓이고, 실제 발급은
  Consumer 처리 속도에 달려 있다.
- Consumer 처리 속도(그리고 그 뒤의 DB 처리 능력)가 발행 속도를 못 따라가면
  Lag이 쌓이고, 최종 발급 결과는 그만큼 늦어진다.

정리: "API 응답이 빠르다" ≠ "발급이 빠르다".
      Kafka는 순간 폭주를 버티게 해주지만, 전체 처리량은 결국 Consumer/DB 처리 능력이 결정한다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

아래 Kafka 설계를 읽고 문제점을 찾는다.

```
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.

Partition Key는 eventId로 설정했다.

대부분의 요청은 eventId = 1이다.

Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.

Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.

Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

위 설계의 문제점을 5가지 이상 작성하고, 각각의 개선 방향을 작성한다.

### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| **Partition이 1개** | 병렬 처리의 상한이 Partition 수이므로, Partition 1개면 Consumer를 아무리 늘려도 동시에 1개만 처리한다. 10만 건 폭주를 단일 흐름으로 처리하니 Lag이 폭증한다. | 예상 피크를 고려해 Partition을 여러 개(예: 10개)로 늘려 병렬 처리 상한을 확보한다. (과제 6) |
| **Consumer가 1개** | 단일 Consumer가 모든 메시지를 혼자 처리해 처리량이 부족하고, 이 Consumer가 죽으면 발급 처리가 전면 중단되는 단일 장애점(SPOF)이 된다. | Consumer Group으로 묶어 여러 Consumer를 두고, Lag에 따라 Partition 수 한도 내에서 오토스케일한다. |
| **Partition Key = eventId (대부분 eventId=1)** | 같은 Key는 같은 Partition으로 가므로 모든 요청이 한 Partition에 쏠린다. 나중에 Partition을 늘려도 eventId=1 요청은 여전히 한 곳에 몰려 병렬 처리가 무력화된다. | Partition Key를 userId 등 카디널리티가 높은 값으로 바꿔 메시지를 고르게 분산시킨다. (과제 5) |
| **Kafka 발행 실패해도 접수 성공 응답** | Topic에 메시지가 없어 Consumer가 처리할 요청이 존재하지 않는데, 사용자는 "접수됨"으로 알고 기다린다. → 요청 유실 + 영원한 PENDING → 신뢰 붕괴. | 발행 성공(Broker ack) 시에만 접수 성공(PENDING)을 응답하고, 발행 실패 시 ACCEPT_FAILED로 정직하게 응답한다. 근본적으로는 Outbox Pattern(6주차)으로 저장·발행의 원자성을 확보한다. (과제 4) |
| **Offset Commit 전 장애 미고려** | DB 저장 후 Commit 전에 죽으면 재시작 시 같은 메시지를 다시 읽어 재처리한다(at-least-once). 방어가 없으면 같은 사용자 중복 발급·수량 초과 발급이 발생한다. | (eventId, userId) DB Unique Key(4주차), requestId 기반 멱등성(5주차), 처리 상태 확인으로 재처리에 안전하게 만든다. (과제 7) |
| **Consumer Lag이 커도 사용자가 상태를 확인할 수 없음** | 발급이 지연되는데 사용자는 결과를 알 수 없어 새로고침·재요청을 반복하고, 이는 부하를 더 키운다. | 요청 상태(PENDING/ISSUED/FAILED)를 저장하고 requestId로 조회하는 결과 조회 API를 제공한다. (과제 8) |
| **Lag/장애를 감지할 모니터링 부재** | Consumer Lag이 쌓이거나 Consumer가 죽어도 운영자가 알 수 없어 대응이 늦어지고 장애가 장기화된다. | Consumer Lag·처리량·Consumer 상태를 모니터링/알람으로 관측하고, 반복 실패 메시지는 재처리/DLQ(8주차)로 격리한다. |

**종합**: 이 설계는 "Kafka만 붙이면 비동기 처리가 된다"는 오해에서 나온 구조다.
Kafka는 병목을 없애는 것이 아니라 옮기고 완충하는 도구이므로, **Partition·Consumer로 병렬성을 확보하고,
Partition Key로 분산을 설계하고, 발행 실패·중복 처리·Lag을 각각 방어**해야 비로소 안정적인 비동기 발급 구조가 된다.
