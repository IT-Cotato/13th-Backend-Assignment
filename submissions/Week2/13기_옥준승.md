# Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

```
												 Client
												 | ^
				                                                   쿠폰 발급 요청 | |    
												 | | 요청 접수 성공/실패 환
												 v |
											     API Server
												  |
												  | 쿠폰 발급 요청 생성 
												  |
												  v
										          Kafka Producer
												  |
												  | 쿠폰 발급 요청 전달
												  |
												  v
							                           coupon.issue.requested Topic
												  |
												  | kafka 내부의 파티션에서 
												  | consumer group으로 요청 이동
												  v
									                Coupon Issue Consumer
												  |
												  | consumer에서 요청 처리 후 
												  | 결과 DB에 저장
												  v
												  DB
```

### 2. API Server의 역할

```
- Client의 요청을 검증한다. 
- 발급 요청 메시지를 Producer에게 전달한다. 
- Client에게 즉시 접수 응답을 반환한다.
```

### 3. Kafka의 역할

```
- 쿠폰 요청 접수와 쿠폰 발급의 흐름을 나누어 트래픽이 몰리는 상황에서 안정적인 처리가 가능하도록 한다. 
- API Server가 생성한 요청을 Topic에 전달한다.
```

### 4. Consumer의 역할

```
- Topic 내부의 partition에 있는 메시지를 읽어 처리한다.
- 처리가 끝난 메시지의 offset을 commit한다.
```

### 5. DB의 역할

```
- Consumer에서 처리한 결과를 DB에 저장하고 발급 상태를 관리한다.
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
API Server는 요청 직후 "접수 성공" 여부만 즉시 반환한다. 
실제 발급 결과는 Kafka 메시지가 Consumer에서 처리되어 DB에 반영된 뒤에야 확정되기 때문이다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공은 쿠폰 발급 성공을 의미하지 않고, 발급에 대한 요청이 성공한 것을 의미한다.
쿠폰 발급 성공은 요청이 접수되어 최종적으로 쿠폰이 발급되었음을 의미한다.
```

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested

coupon -> 쿠폰 도메인

issue -> 발급

requested -> 발급 요청이 들어옴

coupon.issue.requested -> 쿠폰 발급 요청이 들어왔음
```

### 2. Topic에 담기는 메시지의 의미

```
requestId -> 요청 ID (멱등성 보장)
eventId -> 쿠폰 이벤트 ID
userId -> 요청한 사용자 ID
requestedAt -> 사용자가 요청한 시간

EX)

{
  "requestId": "req-123",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-06-26T12:00:00"
}
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
Producer는 Kafka에 메시지를 보내는 컴포넌트이다. 
Producer는 API Server가 요청을 받아 검증을 한 후 Kafka Topic에 쿠폰 발급 요청 메시지를 발행한다.
이후 쿠폰 발급 요청이 성공했다는 응답을 즉시 반환한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Producer에서 발행하여 Topic에 전달된 메시지를 가져와 처리하는 컴포넌트이다. 
Topic에 있는 메시지를 가져오고 관련 로직을 수행한 후 DB에 결과를 저장한다.
이후 offset을 커밋하여 처리 완료 지점을 기록한다.
```

### 5. 이 Topic이 필요한 이유

```
Producer와 Consumer를 분리하여 각각의 속도를 독립시키기 위해서 필요하다. 
트래픽이 몰리는 순간에 Topic에 메시지를 쌓아두고 Consumer가 감당 가능한 속도로 처리하여 DB 부하를 분산하고 시스템 안정성을 확보한다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
Topic에 메시지가 들어갔다는 것은 "쿠폰 발급 요청이 유효하게 접수되었고, 브로커에 내구성 있게 기록되어 유실 없이 처리될 것이 보장된다"는 의미이다. 
사용자 관점에서는 이 시점에 요청 상태가 PENDING이 된다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
메시지가 Topic에 들어간 후 Consumer에서 읽고 처리가 완료되어야 쿠폰 발급 완료가 되므로 Topic에 메시지가 들어갔다는 것은 쿠폰 발급 완료를 의미하지 않는다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-123",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-06-30T12:00:00Z"
}
```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유                          |
| --- | --- |---------------------------------|
| requestId | 요청 ID | 요청을 식별하여 멱등성을 유지하기 위해           |
| eventId | 쿠폰 이벤트 ID | 어떤 쿠폰을 발급할지 특정하기 위해             |
| userId | 요청한 사용자 ID | 누구에게 발급할지 식별하고, 중복 발급 제한 검사를 위해 |
| requestedAt | 사용자가 요청한 시간 | 요청 시점 기록(로그/디버깅 추적을 위해)         |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
- requestId로 이미 처리한 요청인지 확인 
- eventId로 해당 쿠폰 이벤트의 재고/발급 기간 등 조건 확인
- userId로 중복 발급 검사
- 조건 통과 시 재고 차감 후 쿠폰 발급
- 결과를 DB에 저장 (성공/실패)
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
- 메시지 크기가 증가하여 전송 비용 및 저장 부담이 증가
- 재고와 같이 변하는 값을 넣을 경우 정합성 문제 발생
- Producer와 Consumer 간의 결합도 증가로 변화에 취약해짐
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
요청을 구분하기 위한 식별자로, 같은 요청이 여러 번 들어왔는지 판단할 때 사용할 수 있다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-123"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
쿠폰 발급 요청에 대한 성공으로, 쿠폰 발급 성공은 쿠폰 발급 요청 메시지를 Consumer가 처리한 후 확인할 수 있기 때문이다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공 -> 메시지가 kafka에 안전하게 기록되어 처리될 것이 보장된 상태
쿠폰 발급 성공 -> 재고 확인 및 차감이 이루어져 발급이 마무리 된 상태 
```

#### 4. requestId를 응답에 포함하는 이유

```
쿠폰 발급 요청이 성공한 이후에 쿠폰 발급 성공 여부에 대한 조회가 필요할 때 이 결과를 추적/조회하기 위해서 포함한다.

서버 입장에서는 requestId를 활용해 중복 처리를 방지한다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청이 실패하였습니다. 잠시 후 다시 시도해주세요.",
  "requestId": "req-123"
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
Kafka 발행에 실패한 경우 요청이 존재하지 않아 쿠폰 발급이 이루어질 수 없지만, 사용자가 요청 접수 성공 응답을 받게 되면 사용자는 발급될 수 없는 쿠폰을 기다리게 되므로 실패 응답을 주어야 한다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
- 거짓 성공 응답 금지
	발행 실패를 성공으로 위장하면 안된다.
- 재시도 고려
	일시적인 실패일 수 있으므로 일정 횟수 재시도가 필요하다.
- 부분 실패 상태 주의
	메시지 발행은 되었지만 응답만 유실된 경우 재시도로 인해 같은 요청이 Topic에 들어오면 중복 발급 위험이 있다.
```

## 과제 5. Partition Key 선택하기

`coupon.issue.requested` Topic의 Partition Key를 무엇으로 정할지 선택한다.

아래 후보 중 하나를 선택하거나, 직접 다른 Key를 제안해도 된다.

```
1. userId

2. eventId

3. requestId

4. 그 외 직접 선택
```

특히 `eventId`를 Partition Key로 선택한 경우에는 아래 상황을 반드시 고려한다.

```
이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰린다.
```

이때 모든 메시지가 특정 Partition에 몰릴 수 있는지 설명한다.

이번 과제에서는 정답 Partition Key를 하나로 고정하지 않는다.

중요한 것은 자신이 선택한 Partition Key가 아래 항목에 어떤 영향을 주는지 설명하는 것이다.

```
메시지 분산

순서 보장

특정 Partition 쏠림 가능성

Consumer 병렬 처리
```

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자 요청 순서 관리에 유리 | 한 사용자가 요청을 많이 보내면 파티션 쏠림 현상 발생 |
| eventId | 같은 이벤트 요청을 묶어서 보기 쉬움 | 이벤트 하나에 요청이 몰리면 파티션 쏠림 현상 발생 |
| requestId | 메시지 분산에 유리 | 같은 사용자 요청 순서 보장 안됨 |

### 2. 내가 선택한 Partition Key

```
requestId
```

### 3. 선택한 이유

```
1분 안에 최대 10만 건이 들어오기 때문에 메시지를 고르게 분산할 수 있어야 하고, 1인 1매 쿠폰 발급의 요청 순서를 보장할 필요가 없기 때문에 requestId를 선택하였다.   
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
요청마다 requestId는 다르기 때문에 다른 Key들에 비해 메시지가 고르게 분산된다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
같은 사용자가 요청을 보내더라도 requestId에 따라 분산되기 때문에 요청이 서로 다른 Partition에 들어갈 수 있고, 그렇기 때문에 순서를 보장하기 어렵다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
requestId는 요청마다 고유한 값을 가지므로 해시 결과가 균등하게 분포된다.
따라서 userId나 eventId를 사용하는 경우에 비해 특정 Partition에 메시지가 몰릴 가능성이 낮다. 
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
같은 사용자의 요청에 대한 순서를 보장하기 어렵다.

또한, 같은 사용자의 요청이 다른 Partition에서 처리되는 경우 동일 사용자의 중복 요청이 서로 다른 Consumer에서 동시에 처리될 수 있다. 
이 경우 같은 사용자의 같은 요청이 다른 requestId로 생성되어 멱등성 보장을 하지 못한다.
그러므로 user_id와 event_id를 활용한 DB 유니크 제약이 필요하다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
1분에 최대 10만 건의 요청이 들어오는데 eventId를 Partition Key로 사용하는 경우, 모든 요청이 하나의 Partition으로 몰리게 되어 병렬 처리가 이루어지지 않아 처리량이 떨어질 수 있다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
Kafka는 같은 Partition 단위에서 메시지 순서가 보장된다. 이는, Partition에 들어온 순서대로 offset이 부여되고, Consumer가 그 순서대로 소비하기 때문이다. 

서로 다른 Partition에 들어간 메시지의 경우 순서가 보장되지 않는다. Kafka는 Partition간 순서를 조정하는 메커니즘이 없고, 각 Partition이 서로 다른 Consumer에 의해 병렬적으로 처리되기 때문이다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

쿠폰 발급 요청을 처리하는 Consumer Group을 설계한다.

기본 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.

Consumer는 coupon.issue.requested Topic을 읽는다.

Consumer는 실제 쿠폰 발급 처리를 수행한다.
```

이번 과제에서 정확한 처리량 계산이 목적은 아니다.

중요한 것은 아래 내용을 이해하고 설명하는 것이다.

```
Partition 수가 Consumer 병렬 처리에 어떤 영향을 주는가?

Consumer Group은 왜 필요한가?

Consumer 수와 Partition 수의 관계는 무엇인가?

Consumer 수만 무작정 늘리면 왜 안 되는가?
```

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
20개
1분에 10만 건 → 약 1,667건/초 처리 필요.
Consumer 1개가 약 100건/초 처리(DB 트랜잭션 ~10ms 가정)한다고 보면 최소 17개의 병렬 처리가 필요하므로, 여유를 두어 Partition을 20개로 설정.
```

### 3. Consumer Group 이름

```
coupon-issue-group
```

### 4. Consumer 수

```
20개
Consumer 1개당 약 100건/초 × 20개 = 약 2,000건/초로,
목표치 1,667건/초를 처리할 수 있다.
```

### 5. Partition과 Consumer 매핑

```
Partition 0 → Consumer 1
Partition 1 → Consumer 2
...
Partition 19 → Consumer 20
```

### 6. 이 구조를 선택한 이유

```
1. 처리량 기준 산정
	 1분 10만 건(약 1,667건/초) 처리를 목표로, Consumer 1개의 처리 속도(DB 트랜잭션 ~10ms 기준 약 100건/초)를 고려해 최소 17개의 병렬 처리가 필요하다고 보았다. 여유를 두어 Partition과 Consumer를 각각 20개로 설정했다.

2. 1:1 매핑으로 자원 낭비 최소화
   Partition 수와 Consumer 수를 동일하게 맞춰, 모든 Consumer가 정확히 파티션 하나씩 담당하도록 했다. 노는 Consumer가 없어 자원을 낭비하지 않으면서, 동시에 20개 병렬 처리라는 최대 처리량을 확보한다.

3. Partition이 병렬 처리의 상한이므로, Partition에 맞춰 Consumer를 산정
   Consumer는 Partition 수를 초과해 동시 처리할 수 없다. 따라서 필요한 병렬 처리량(Partition 20)을 먼저 정하고 거기에 Consumer 수를 맞췄다. 만약 Consumer를 21개 이상으로 늘리면 21번째부터는 할당받을 Partition이 없어 놀게 되므로, Partition 수가 곧 처리량 확장의 한계임을 고려했다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
Partition은 하나의 Consumer와 연결되기 때문에 동시에 처리할 수 있는 Consumer는 3개이다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
Partition은 하나의 Consumer와 연결되기 때문에 놀게 되는 Consumer가 생긴다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
하나의 Consumer에 여러 Partition이 연결되어 Consumer에 처리 부담이 발생할 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
Partition 수가 충분하지 않다면 놀게 되는 Consumer가 발생하기 때문이다.

병목이 Consumer가 아닌 DB에 있는 경우 Consumer를 늘려도 처리량은 늘지 않고 DB 병목이 더 심해질 수 있기 때문이다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

Kafka Consumer가 메시지를 처리하는 도중 장애가 발생하는 상황을 분석한다.

아래 상황을 읽고 질문에 답한다.

```
1. Consumer가 Kafka 메시지를 읽었다.

2. Consumer가 DB 저장까지 성공했다.

3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.

4. Consumer가 다시 실행되었다.
```

이번 과제에서는 이 문제를 완전히 해결하는 것이 목적이 아니다.

중요한 것은 Kafka Consumer에서 아래 상황이 발생할 수 있음을 이해하는 것이다.

```
DB 처리는 성공했지만 Offset Commit은 실패할 수 있다.

Offset Commit이 실패하면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못할 수 있다.

그 결과 같은 메시지가 다시 읽히고 다시 처리될 수 있다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
이전에 offset commit이 실패한 메시지 이후의 모든 메시지를 다시 읽을 수 있다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Kafka는 처리 완료 commit을 받아야 메시지 처리가 완료되었다고 판단하는데, offset commit이 실패하였기 때문에 처리가 완료되었다고 판단하지 못한다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
Kafka 입장에서 해당 메시지는 미처리 상태이므로 Consumer를 재시작하면 메시지가 다시 전달되고 이를 다시 처리하게 된다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
같은 발급 요청이 두 번 처리되어 한 사용자에게 쿠폰이 중복 발급될 수 있다. 
이 경우 멱등성을 보장하는 장치가 없다면 1인 1매 제약이 깨지게 된다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

아래 키워드를 참고해서 작성한다.

```
DB Unique Key

requestId 기반 멱등성

처리 상태 저장

중복 메시지 방어
```

답변:

```
- (eventId + userId)를 DB Unique Key로 사용하여 같은 메시지가 여러번 와도 DB에는 한 번만 저장되도록 한다.
- requestId를 기반으로 중복 요청을 판단하여 동일한 메시지가 와도 한 번만 처리하도록 한다.
- 별도 테이블이나 redis에 처리 상태를 저장해 재처리 시 중복 여부 판단에 사용한다.
- 위에서 언급한 방법을 조합해 중복 메시지를 방어해 메시지가 여러번 오더라도 쿠폰은 한 번만 발급되도록 한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

Kafka를 사용하면 API Server는 사용자에게 빠르게 요청 접수 응답을 줄 수 있다.

하지만 Consumer 처리 속도가 느리면 Kafka에 메시지가 쌓일 수 있다.

아래 상황을 읽고 답한다.

```
이벤트 시작 직후 요청이 급격히 증가했다.

API Server는 Kafka에 메시지를 빠르게 발행하고 있다.

하지만 Consumer 처리 속도가 Producer 발행 속도보다 느리다.

Kafka에 아직 처리되지 않은 메시지가 계속 쌓이고 있다.
```

이번 과제에서는 사용자가 발급 상태를 조회할 수 있도록 요청 상태가 저장되어 있다고 가정한다.

상태는 아래와 같이 단순화해서 사용한다.

```
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태

ISSUED: 쿠폰 발급이 성공한 상태

FAILED: 쿠폰 발급이 실패한 상태
```

### 1. Consumer Lag이란 무엇인가?

```
현재 Partition에 쌓인 최신 메시지 위치와 Consumer Group이 처리 완료했다고 기록한 Offset 사이 의 차이 
Consumer가 처리하지 못하고 밀린 메시지 수를 의미한다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
요청 직후 요청이 접수되었다는 응답은 바로 받지만, Consumer의 처리가 늦어져 최종 결과 확인이 늦어진다. 
이는 마이페이지 반영, 알림 발송의 지연으로도 이어지며, 사용자의 재요청으로도 이어질 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-123"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다.",
  "requestId": "req-123"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-123"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패하였습니다",
  "requestId": "req-123"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
Consumer Lag가 높은 경우, Consumer 처리량이 떨어져 병목이 발생하고 있다는 판단을 할 수 있다. 이에 따라 Consumer나 Partition을 늘려 처리량을 높이는 판단을 할 수 있다.

Consumer Lag가 낮은 경우에는 현재 리소스가 충분하다고 판단할 수 있다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
Kafka를 사용하여 API Server에서의 병목을 해결하여도 Consumer의 처리량이 낮은 경우 이 병목이 Consumer로 이동해 최종 발급 결과가 늦어질 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

아래 Kafka 설계를 읽고 문제점을 찾는다.

```
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.

Partition Key는 eventId로 설정했다.

대부분의 요청은 eventId = 1이다.

Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.

Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.

Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

위 설계의 문제점을 5가지 이상 작성하고, 각각의 개선 방향을 작성한다.

### 문제점과 개선 방향

| 문제점 | 왜 문제인가?                                                                          | 개선 방향                                                                           |
| --- |----------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| Partition Key를 eventId로 설정했다.| 1분 안에 최대 10만 건의 요청이 들어와 해당 이벤트를 담당하는 Partition에 몰려 Partition을 늘려도 처리량이 늘어나지 않는다. | Partition Key를 requestId로 설정한다.                                                 |
| Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.| 발행에 실패한 경우 쿠폰 발급은 이루어지지 않는데 사용자가 성공 응답을 받게 되면 사용자는 발급되지 못하는 쿠폰을 기다리게 된다.         | 발행에 실패한 경우 요청 접수 실패 응답을 반환한다.                                                   |
| Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다. | offset commit 전에 죽으면 재시작 시 같은 메시지를 다시 읽어 중복 처리한다. 이는 쿠폰 중복 발급으로 이어질 수 있다.        | requestId를 멱등성 키로 활용해 Consumer가 이미 처리한 요청인지 확인하고, DB unique 제약을 사용해 중복 저장을 막는다. |
| Partition 1개, Consumer 1개 | 요청에 비해 Partition과 Consumer의 수가 적어 병렬 처리가 불가능해 처리량이 떨어진다.                         | Partition과 Consumer의 개수를 요청 크기에 맞게 늘린다.                                         |
| Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다. | 처리가 밀려 쿠폰 발급이 지연되는 경우 사용자가 자신의 요청 처리 상황을 확인하지 못해 오래 기다리게 되거나 중복 요청을 보내게 된다.      | 요청 상태를 따로 저장하고 requestId로 상태를 조회하는 API를 제공한다.                                   |
| Consumer Lag을 모니터링하는 장치가 없다. | Lag가 쌓여 처리가 지연되어도 운영자가 이를 빠르게 감지하기 어렵다.                                          | Grafana 등을 활용해 Lag를 모니터링하여 빠른 대응을 할 수 있도록 한다.                                   |
