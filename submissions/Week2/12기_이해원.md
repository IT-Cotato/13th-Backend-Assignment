# 과제 설명

# 2주차 과제: Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 1. 과제 목표

이번 2주차 과제의 목표는 **Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 처리하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

이번 주차에서는 그 비동기 구조를 Kafka 기반으로 구체화한다.

이번 과제에서 설계해야 하는 기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Kafka Producer
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Topic 설계

Message 구조 설계

Partition Key 선택

Consumer Group 설계

Offset Commit과 중복 처리 가능성 이해

Consumer Lag이 사용자 경험에 미치는 영향 이해

Kafka 발행 실패 시 API 응답 설계
```

이번 과제의 핵심은 Kafka를 구현하는 것이 아니라, **Kafka를 시스템 구조 안에서 어떻게 사용할지 설계하는 것**이다.

---

## 2. 기본 상황

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 쿠폰 발급 처리를 수행하는 구조를 설계한다.

단, 이번 주차에서는 Redis 선착순 판정, DB Unique Key, requestId 멱등성, Outbox Pattern, Retry Topic, DLQ는 깊게 다루지 않는다.

## 3. 이번 과제의 전제 조건

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행한다.

Kafka 발행이 성공했다는 것은 Producer가 Kafka Broker로부터 발행 성공 응답을 받은 상황을 의미한다.

Kafka 발행이 실패했다면 아직 쿠폰 발급 요청이 시스템에 안전하게 접수된 것이 아니다.

따라서 Kafka 발행에 실패한 경우에는 사용자에게 요청 접수 성공 응답을 주면 안 된다.
```

또한 발급 상태 조회를 위해 요청을 식별할 수 있는 값이 필요하다.

```
requestId는 쿠폰 발급 요청을 식별하기 위한 값이다.

이번 주차에서는 requestId를 요청 식별자와 상태 조회에 필요한 값 정도로만 이해한다.

requestId를 이용한 멱등성 처리와 중복 요청 방지는 5주차에서 자세히 다룬다.
```

Consumer Lag 상황에서 사용자가 발급 상태를 조회할 수 있어야 하므로, 이번 과제에서는 발급 요청 상태를 저장할 수 있는 저장소가 있다고 가정한다.

```
상태 예시:
PENDING
ISSUED
FAILED
```

단, 상태 저장 테이블의 상세 설계는 이번 주차의 핵심이 아니다.

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  |
  | 1. 쿠폰 발급 요청
  v
API Server
  |
  | 2. requestId 생성, 기본 검증
  v
Kafka Producer
  |
  | 3. 메시지 발행
  v
coupon.issue.requested Topic
  |
  | 4. Consumer가 메시지 읽기
  v
Coupon Issue Consumer
  |
  | 5. 실제 쿠폰 발급 처리
  v
DB
```

### 2. API Server의 역할

```
API Server는 사용자의 쿠폰 발급 요청을 직접 처리하지 않고, 요청을 Kafka에 안전하게 전달한다.

- Client로부터 쿠폰 발급 요청을 받는다.
- eventId, userId 등 기본 요청 값을 검증한다.
- requestId를 생성한다.
- coupon.issue.requested Topic에 메시지를 발행한다.
- Kafka 발행 성공 시 요청 접수 성공 응답을 반환한다.
- Kafka 발행 실패 시 요청 접수 실패 응답을 반환한다.

API Server는 쿠폰 수량 차감, 실제 발급, 발급 성공 여부 판단을 직접 수행하지 않는다.
해당 작업은 Consumer가 비동기적으로 처리한다.
```

### 3. Kafka의 역할

```
Kafka는 API Server와 Coupon Issue Consumer 사이에서 쿠폰 발급 요청을 안전하게 전달하는 메시지 큐 역할을 한다.

- 쿠폰 발급 요청 메시지를 Topic에 저장한다.
- API Server와 Consumer의 처리 속도 차이를 완충한다.
- 요청이 순간적으로 몰려도 Consumer가 순차적으로 처리할 수 있게 한다.
- Consumer 장애가 발생하더라도 아직 처리되지 않은 메시지를 보관한다.
- Consumer Group과 Partition을 통해 병렬 처리를 가능하게 한다.
```

### 4. Consumer의 역할

```
Coupon Issue Consumer는 Kafka Topic에서 메시지를 읽어 실제 쿠폰 발급 처리를 수행한다.

- coupon.issue.requested Topic에서 메시지를 읽는다.
- 메시지에 포함된 eventId, userId, requestId를 확인한다.
- DB를 이용해 쿠폰 발급 가능 여부를 판단한다.
- 발급 가능하면 쿠폰을 발급하고 상태를 ISSUED로 저장한다.
- 발급 불가능하면 상태를 FAILED로 저장한다.
- DB 처리가 성공한 뒤 Kafka Offset을 Commit한다.
```

### 5. DB의 역할

```
DB는 쿠폰 발급 결과와 요청 상태를 저장하는 역할을 한다.

- 쿠폰 이벤트 정보 저장
- 쿠폰 발급 내역 저장
- 사용자별 쿠폰 발급 결과 저장
- requestId 기준 발급 요청 상태 저장
- 상태 조회 API에서 사용할 PENDING, ISSUED, FAILED 상태 저장

PENDING: 요청은 접수되었지만 아직 Consumer가 처리하지 않음
ISSUED: 쿠폰 발급 성공
FAILED: 쿠폰 발급 실패
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.
API Server가 모든 쿠폰 발급 처리를 즉시 수행하면 DB 부하가 급격히 증가하고, API 응답 지연이나 장애가 발생할 수 있다.

따라서 API Server는 요청을 Kafka에 넣는 역할까지만 수행하고, 실제 쿠폰 발급 처리는 Consumer가 비동기적으로 수행한다.

사용자는 요청 직후에 최종 발급 결과가 아니라 요청이 접수되었다는 응답만 받는다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공과 쿠폰 발급 성공은 서로 다르다.

요청 접수 성공:
- API Server가 Kafka에 쿠폰 발급 요청 메시지를 성공적으로 발행한 상태
- 아직 쿠폰이 발급된 것은 아님
- 상태는 PENDING

쿠폰 발급 성공:
- Consumer가 Kafka 메시지를 읽음
- DB에서 실제 쿠폰 발급 처리를 완료함
- 상태는 ISSUED

예를 들어 사용자가 쿠폰 발급 요청을 했고 Kafka 발행에 성공하면 API는 202 Accepted를 반환할 수 있다. 하지만 이후 Consumer가 처리할 때 쿠폰 수량이 이미 소진되었다면 최종 상태는 FAILED가 될 수 있다.
```

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```
특정 사용자가 특정 쿠폰 이벤트에 대해 쿠폰 발급을 요청했다는 의미이다.
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
Producer는 API Server이다.

Client가 쿠폰 발급 요청 API를 호출하면 API Server는 기본적인 요청 검증을 수행한 뒤,
쿠폰 발급 요청 메시지를 coupon.issue.requested Topic에 발행한다.

사용자의 요청을 받은 직후 실제 쿠폰 발급 처리를 직접 수행하지 않고
Kafka에 요청 메시지를 넣는 역할을 한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Consumer는 Coupon Issue Consumer이다.

Coupon Issue Consumer는 coupon.issue.requested Topic에서 메시지를 읽고, 
메시지에 포함된 requestId, eventId, userId, requestedAt 정보를 바탕으로 실제 쿠폰 발급 처리를 수행한다. 
처리 결과에 따라 발급 상태를 ISSUED 또는 FAILED로 저장한다.
```

### 5. 이 Topic이 필요한 이유

```
쿠폰 이벤트 시작 직후 짧은 시간 동안 많은 요청이 몰릴 수 있다. 
API Server가 모든 쿠폰 발급 처리를 직접 수행하면 API 응답 지연, DB 부하 증가, 서버 장애가 발생할 수 있다. 

coupon.issue.requested Topic을 사용하면 API Server는 요청을 빠르게 접수하고, Consumer가 나중에 비동기적으로 쿠폰 발급 처리를 수행할 수 있다. 

이 Topic은 API Server와 실제 쿠폰 발급 처리 로직을 분리하고, 대량 요청을 안정적으로 처리하기 위해 필요하다.
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
이 Topic에 메시지가 들어갔다는 것은 쿠폰 발급 요청이 Kafka에 정상적으로 접수되었다는 의미이다. 

API Server가 Kafka Broker로부터 메시지 발행 성공 응답을 받았고, 이후 Consumer가 해당 메시지를 읽어 쿠폰 발급 처리를 수행할 수 있는 상태라는 뜻이다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
coupon.issue.requested Topic은 쿠폰 발급 요청 메시지를 담는 Topic이다. 

이 Topic에 메시지가 들어간 시점에는 아직 Consumer가 메시지를 읽지 않았을 수 있고, DB에 실제 쿠폰 발급 처리가 완료되지 않았을 수 있다. 

또한 Consumer가 처리하는 시점에 쿠폰 수량이 이미 소진되었거나, 발급 조건을 만족하지 못하면 최종 발급 결과는 실패가 될 수도 있다. 

따라서 이 Topic에 메시지가 들어갔다는 것은 요청 접수 성공을 의미할 뿐 쿠폰 발급 완료를 의미하지 않는다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-20260702-000001",
  "eventId": "summer-5000-off-2026",
  "userId": "user-12345",
  "requestedAt": "2026-07-02T10:00:00+09:00"
}
```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| requestId | 쿠폰 발급 요청을 식별하는 고유 ID | 사용자가 발급 상태를 조회하거나, 특정 요청의 처리 흐름을 추적하기 위해 필요하다. |
| requestId | 쿠폰 발급 요청을 식별하는 고유 ID | 사용자가 발급 상태를 조회하거나, 특정 요청의 처리 흐름을 추적하기 위해 필요하다. |
| requestId | 쿠폰 발급 요청을 식별하는 고유 ID | 사용자가 발급 상태를 조회하거나, 특정 요청의 처리 흐름을 추적하기 위해 필요하다. |
| requestId | 쿠폰 발급 요청을 식별하는 고유 ID | 사용자가 발급 상태를 조회하거나, 특정 요청의 처리 흐름을 추적하기 위해 필요하다. |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
Consumer는 메시지에 포함된 정보를 바탕으로 다음 처리를 수행할 수 있다. 

1. requestId -> 어떤 요청인지 식별
2. eventId -> 어떤 쿠폰 이벤트에 대한 요청인지 확인
3. userId -> 어떤 사용자가 요청했는지 확인
4. 해당 이벤트의 쿠폰 발급 가능 여부 확인
5. 발급 가능하면 쿠폰 발급 내역을 DB에 저장, 상태를 ISSUED로 변경
6. 발급 불가능하면 요청 상태를 FAILED로 변경
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
Kafka 메시지에 너무 많은 정보를 넣으면 메시지 크기가 커지고,
네트워크 전송 비용과 Kafka 저장 비용이 증가할 수 있다.

또한 메시지 구조가 복잡해지면 Producer와 Consumer가 강하게 결합된다.
예를 들어 메시지 필드가 자주 변경되면 Producer와 Consumer를 함께 수정해야 하는 문제가 생길 수 있다.

그리고 쿠폰 이름, 할인 금액, 사용자 상세 정보처럼 DB에서 조회할 수 있는 정보를 모두 메시지에 넣으면
데이터 정합성 문제가 발생할 수 있다.

=> Kafka 메시지에는 Consumer가 처리를 시작하기 위해 필요한 최소한의 식별 정보만 담는 것이 좋다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
requestId는 요청 하나를 구분하기 위한 식별자다.
같은 요청이 여러 번 들어왔는지 판단할 때 사용할 수 있다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 발급 결과는 상태 조회 API 또는 마이페이지에서 확인할 수 있습니다.",
  "requestId": "req-20260702-000001"
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
Kafka 발행 성공은 쿠폰 발급 요청 메시지가 Kafka에 정상적으로 저장되었다는 의미이다. 

하지만 이 시점에는 아직 Consumer가 메시지를 읽어 실제 쿠폰 발급 처리를 수행하지 않았을 수 있다. 

또한 Consumer가 처리하는 시점에 쿠폰 수량이 이미 소진되었거나, 사용자가 발급 조건을 만족하지 못하면 최종 발급 결과는 실패가 될 수 있다. 

따라서 Kafka 발행 성공 응답은 요청 접수 성공을 의미할 뿐 쿠폰 발급 성공을 의미하지 않는다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공은 API Server가 쿠폰 발급 요청을 Kafka에 정상적으로 발행한 상태이다. 

이때 요청 상태는 PENDING이며, 아직 최종 결과가 확정되지 않았다. 
쿠폰 발급 성공은 Consumer가 Kafka 메시지를 읽고, DB에 실제 쿠폰 발급 처리를 완료한 상태이다. 
이때 요청 상태는 ISSUED가 된다. 

요청 접수 성공은 비동기 처리를 시작할 수 있는 상태이고, 쿠폰 발급 성공은 실제 발급 처리가 끝난 최종 상태이다.
```

#### 4. requestId를 응답에 포함하는 이유

```
requestId는 쿠폰 발급 요청을 식별하기 위한 고유 값이다. 
이 값을 응답에 포함하면 이후 장애 상황이나 중복 요청이 발생했을 때 특정 요청을 기준으로 로그를 추적하고 문제를 분석할 수 있다. 

또한 동일한 요청이 여러 번 들어왔는지 여부를 확인하거나, 특정 요청이 정상적으로 처리되었는지 확인하는 데에도 활용할 수 있다. 

따라서 requestId는 단순 조회 용도를 넘어, 장애 대응과 중복 요청 추적을 위해 반드시 필요한 값이다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청을 접수하지 못했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": null
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
Kafka 발행에 실패했다는 것은 쿠폰 발급 요청 메시지가 Kafka에 안전하게 저장되지 않았다는 의미이다.
Consumer가 나중에 읽어서 처리할 메시지가 없을 수 있다. 

그런데 API Server가 사용자에게 요청 접수 성공 응답을 주면, 사용자는 자신의 쿠폰 발급 요청이 정상적으로 접수되었다고 생각하게 된다. 

하지만 실제로는 Kafka Topic에 메시지가 없기 때문에 Consumer가 해당 요청을 처리할 수 없다. 이 경우 사용자는 상태 조회를 해도 결과를 확인할 수 없거나, 계속 처리되지 않는 요청처럼 보이는 문제가 발생할 수 있다. 

따라서 Kafka 발행에 실패한 경우에는 요청 접수 성공 응답을 주면 안 된다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
API Server는 Kafka 발행 성공 여부를 확인한 뒤 응답을 결정해야 한다. 

Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우에만 요청 접수 성공 응답을 반환해야 한다. 
반대로 Kafka 발행에 실패했다면 해당 요청은 시스템에 안전하게 접수된 것이 아니므로, 사용자에게 실패 응답을 반환해야 한다. 

또한 실패 응답에서는 사용자가 상태 조회를 할 수 있는 것처럼 requestId를 제공하면 안 된다. 
requestId를 이미 생성했더라도 Kafka에 메시지가 저장되지 않았다면, 그 requestId는 정상 접수된 요청을 의미하지 않기 때문이다. 

따라서 이 상황에서는 사용자가 다시 요청할 수 있도록 안내해야 한다.
```

## 과제 5. Partition Key 선택하기

`coupon.issue.requested` Topic의 Partition Key를 무엇으로 정할지 선택한다.

아래 후보 중 하나를 선택하거나, 직접 다른 Key를 제안해도 된다.

```
1. userId

2. eventId

3. requestId

4. 그 외 직접 선택
```

특히 `eventId`를 Partition Key로 선택한 경우에는 아래 상황을 반드시 고려한다.

```
이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰린다.
```

이때 모든 메시지가 특정 Partition에 몰릴 수 있는지 설명한다.

이번 과제에서는 정답 Partition Key를 하나로 고정하지 않는다.

중요한 것은 자신이 선택한 Partition Key가 아래 항목에 어떤 영향을 주는지 설명하는 것이다.

```
메시지 분산

순서 보장

특정 Partition 쏠림 가능성

Consumer 병렬 처리
```

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자 요청이 같은 Partition으로 들어감, 사용자 기준 순서 관리에 유리 | 특정 사용자의 요청이 과도하게 많으면 일부 Partition에 부하 가능 |
| eventId | 같은 이벤트 요청을 묶어서 보기 쉬움 | 인기 이벤트 하나에 요청이 몰리면 특정 Partition에 쏠릴 가능성이 큼 |
| requestId | 요청 단위로 분산되기 쉬움 | 같은 사용자 기준 순서 보장이 어려움 |

### 2. 내가 선택한 Partition Key

```
eventId:userId

예시: summer-5000-off-2026:user-12345
```

### 3. 선택한 이유

```
쿠폰 발급 조건은 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능하다는 것이다. 
따라서 같은 사용자가 같은 이벤트에 대해 여러 번 쿠폰 발급 요청을 보낸 경우, 그 요청들은 같은 Partition에 들어가는 것이 좋다. 

Kafka는 같은 Partition 안에서 메시지 순서를 보장하므로, eventId:userId를 Key로 사용하면 같은 이벤트의 같은 사용자 요청 순서를 유지할 수 있다. 

또한 eventId만 Key로 사용하는 것보다 userId가 함께 포함되기 때문에 여러 사용자 요청이 여러 Partition으로 분산될 수 있다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
eventId:userId를 Partition Key로 사용하면 사용자별로 Key가 달라진다. 

예를 들어 같은 이벤트에 10만 명이 요청하더라도 userId가 다르기 때문에 메시지가 여러 Partition에 분산될 가능성이 높다. 

따라서 eventId만 Key로 사용할 때보다 특정 Partition에 요청이 몰릴 가능성이 낮다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
Kafka는 같은 Partition 안에서만 메시지 순서를 보장한다. 

eventId:userId를 Partition Key로 사용하면 같은 이벤트에 대한 같은 사용자의 요청은 같은 Partition에 들어간다. 

따라서 같은 사용자가 같은 이벤트에 대해 여러 번 요청한 경우, 그 요청들 사이의 순서를 같은 Partition 안에서 보장할 수 있다. 다만 서로 다른 사용자 요청의 전체 순서는 보장되지 않는다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
eventId:userId를 Key로 사용하면 eventId만 Key로 사용하는 경우보다 몰릴 가능성이 낮다. 

하지만 완전히 몰림이 없다고 볼 수는 없다. Kafka의 Partition 배정은 Key의 해시값을 기준으로 이루어지므로, 특정 Key 패턴이나 사용자 요청 분포에 따라 일부 Partition에 더 많은 메시지가 들어갈 수 있다. 

그래도 이벤트 하나에 모든 요청이 몰리는 상황에서는 eventId만 사용하는 것보다 eventId:userId를 사용하는 것이 분산 측면에서 더 유리하다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
eventId:userId를 Key로 사용하면 같은 이벤트의 전체 요청 순서는 보장되지 않는다. 

예를 들어 user-1의 요청과 user-2의 요청은 서로 다른 Partition에 들어갈 수 있으므로, 두 요청 사이의 전체 처리 순서는 보장되지 않는다. 

또한 선착순 쿠폰처럼 전체 요청 순서가 매우 중요한 요구사항이 있다면 Kafka Partition 분산 처리만으로 정확한 전체 순서를 보장하기 어렵다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
eventId를 Partition Key로 사용하면 같은 이벤트의 모든 요청이 같은 Key를 갖게 된다.

- 인기 이벤트 하나에 요청이 몰리면 특정 Partition으로 쏠릴 수 있다.
- Partition을 여러 개 둬도 병렬 처리 효과가 줄어들 수 있다.
- Consumer Lag이 특정 Partition에 집중될 수 있다.

따라서 이벤트 하나에 트래픽이 집중되는 쿠폰 발급 시스템에서는 eventId만 Partition Key로 사용하는 것은 주의해야 한다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
Kafka는 Partition 단위로 메시지 순서를 보장한다. 
즉, 같은 Topic 안에서도 같은 Partition에 들어간 메시지들은 저장된 순서대로 읽을 수 있다. 

하지만 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되지 않는다. 

그 이유는 각 Partition이 서로 독립적으로 처리되기 때문이다. 
서로 다른 Partition은 서로 다른 Consumer가 병렬로 처리할 수 있고, 각 Consumer의 처리 속도나 DB 처리 시간도 다를 수 있다. 

따라서 A가 B보다 먼저 Kafka에 들어갔다고 하더라도, A와 B가 서로 다른 Partition에 있다면 실제 처리 완료 순서는 달라질 수 있다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기

쿠폰 발급 요청을 처리하는 Consumer Group을 설계한다.

기본 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.

Consumer는 coupon.issue.requested Topic을 읽는다.

Consumer는 실제 쿠폰 발급 처리를 수행한다.
```

이번 과제에서 정확한 처리량 계산이 목적은 아니다.

중요한 것은 아래 내용을 이해하고 설명하는 것이다.

```
Partition 수가 Consumer 병렬 처리에 어떤 영향을 주는가?

Consumer Group은 왜 필요한가?

Consumer 수와 Partition 수의 관계는 무엇인가?

Consumer 수만 무작정 늘리면 왜 안 되는가?
```

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
12개
```

### 3. Consumer Group 이름

```
coupon-issue-consumer-group
```

### 4. Consumer 수

```
초기 Consumer 수는 6개로 설정한다. 트래픽이 증가하면 최대 12개까지 확장할 수 있다.
```

### 5. Partition과 Consumer 매핑

```
(매핑 예시: Partition 0 → Consumer 1)

Partition 0 → Consumer 1 
Partition 1 → Consumer 1

Partition 2 → Consumer 2 
Partition 3 → Consumer 2 

Partition 4 → Consumer 3 
Partition 5 → Consumer 3 

Partition 6 → Consumer 4 
Partition 7 → Consumer 4 

Partition 8 → Consumer 5 
Partition 9 → Consumer 5 

Partition 10 → Consumer 6 
Partition 11 → Consumer 6
```

### 6. 이 구조를 선택한 이유

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있으므로, 단일 Consumer로 모든 요청을 처리하기에는 부담이 크다. 

Partition을 12개로 설정하면 하나의 Topic을 여러 Partition으로 나눌 수 있고, Consumer Group 안의 여러 Consumer가 Partition을 나누어 처리할 수 있다. 

초기에는 Consumer 6개가 각각 2개 Partition을 담당하도록 구성한다. 이후 Consumer Lag이 증가하거나 처리량이 부족하면 Consumer 수를 늘려 최대 12개까지 병렬 처리 수준을 높일 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
최대 3개이다. 
같은 Consumer Group 안에서는 하나의 Partition이 동시에 여러 Consumer에게 할당되지 않는다. 
따라서 Partition이 3개라면 실제로 메시지를 처리할 수 있는 Consumer도 최대 3개이다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
Consumer 수가 Partition 수보다 많으면 일부 Consumer는 Partition을 할당받지 못한다. 

예를 들어 Partition이 3개이고 Consumer가 5개라면, 3개의 Consumer만 Partition을 하나씩 할당받아 메시지를 처리하고, 나머지 2개의 Consumer는 대기 상태가 된다.

따라서 Consumer 수를 Partition 수보다 많이 늘려도 처리량이 계속 증가하지 않는다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
Consumer 수가 Partition 수보다 적으면 하나의 Consumer가 여러 Partition을 담당한다. 

예를 들어 Partition이 12개이고 Consumer가 6개라면, 각 Consumer는 평균적으로 2개 Partition을 처리한다. 
이 방식은 정상적으로 동작하지만, Consumer 하나가 담당해야 하는 메시지 양이 많아지면 처리 속도가 느려지고 Consumer Lag이 증가할 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
Consumer 수만 무작정 늘려도 Partition 수보다 많은 Consumer는 메시지를 처리할 수 없다. 

Kafka의 Consumer 병렬 처리 한계는 같은 Consumer Group 안에서는 Partition 수에 의해 결정된다. 
또한 Consumer 수가 많아지면 Rebalancing 비용이 증가하고, 운영해야 할 인스턴스 수가 늘어나며, DB에 동시에 접근하는 처리량도 증가할 수 있다. 

Consumer 수를 늘리면 Kafka 메시지 처리량은 증가할 수 있지만, DB 부하나 외부 시스템 부하도 함께 증가할 수 있다. 
따라서 Consumer 수는 Partition 수, DB 처리 성능, Consumer Lag을 함께 고려해서 조정해야 한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

Kafka Consumer가 메시지를 처리하는 도중 장애가 발생하는 상황을 분석한다.

아래 상황을 읽고 질문에 답한다.

```
1. Consumer가 Kafka 메시지를 읽었다.

2. Consumer가 DB 저장까지 성공했다.

3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.

4. Consumer가 다시 실행되었다.
```

이번 과제에서는 이 문제를 완전히 해결하는 것이 목적이 아니다.

중요한 것은 Kafka Consumer에서 아래 상황이 발생할 수 있음을 이해하는 것이다.

```
DB 처리는 성공했지만 Offset Commit은 실패할 수 있다.

Offset Commit이 실패하면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못할 수 있다.

그 결과 같은 메시지가 다시 읽히고 다시 처리될 수 있다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
Consumer는 DB 저장까지 성공했지만 Offset Commit에 실패한 메시지를 다시 읽을 수 있다. 

Kafka 입장에서는 해당 메시지의 Offset이 Commit되지 않았기 때문에, Consumer Group이 그 메시지를 처리 완료했다고 판단할 수 없다. 

따라서 Consumer가 다시 실행되면 마지막으로 Commit된 Offset 이후의 메시지를 다시 읽게 되고, 그 안에는 이미 DB 처리가 성공한 메시지가 포함될 수 있다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Kafka는 Consumer의 DB 처리 성공 여부를 직접 알지 못한다. 

Kafka가 아는 것은 Consumer Group이 어느 Offset까지 Commit했는지이다. 

Consumer가 DB 저장까지 성공했더라도 Offset Commit 전에 장애로 종료되었다면, Kafka에는 해당 메시지를 처리했다는 기록이 남지 않는다. 

따라서 Kafka 입장에서는 이 메시지가 아직 처리 완료되지 않은 메시지로 보일 수 있다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
그렇다. 같은 메시지가 다시 처리될 수 있다. 

DB 처리는 이미 성공했지만 Offset Commit이 실패했기 때문에, Consumer가 재시작되면 같은 메시지를 다시 읽을 수 있다. 

이처럼 Kafka Consumer는 메시지를 최소 한 번 이상 처리할 수 있다. 메시지가 유실되지 않도록 설계하면 중복 처리가 발생할 수 있다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
같은 메시지가 다시 처리되면 쿠폰이 중복 발급될 수 있다. 

예를 들어 user-12345가 summer-5000-off-2026 이벤트에 대해 쿠폰 발급 요청을 했고, Consumer가 DB에 쿠폰 발급 내역을 저장한 뒤 장애가 발생했다고 가정한다. 

이후 Consumer가 다시 실행되어 같은 메시지를 다시 읽으면, 이미 발급된 쿠폰을 다시 발급하려고 할 수 있다. 이 경우 다음과 같은 문제가 생길 수 있다. 

1. 한 사용자가 같은 이벤트에서 쿠폰을 2개 이상 받을 수 있다. 
2. 쿠폰 수량이 실제보다 더 많이 차감될 수 있다. 
3. 선착순 1,000개 제한이 깨질 수 있다. 
4. 발급 상태가 중복으로 저장될 수 있다. 
5. 사용자별 발급 조건을 위반할 수 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

아래 키워드를 참고해서 작성한다.

```
DB Unique Key

requestId 기반 멱등성

처리 상태 저장

중복 메시지 방어
```

답변:

```
Consumer가 같은 메시지를 다시 읽더라도 쿠폰이 중복 발급되지 않도록 방어하는 장치가 필요하다. 

1. DB Unique Key 사용
예를 들어 eventId와 userId 조합에 Unique Key를 설정하면, 같은 사용자가 같은 이벤트에서 쿠폰을 두 번 발급받는 것을 DB 차원에서 막을 수 있다. 

2. requestId 기반 멱등성 처리
Consumer가 메시지를 처리하기 전에 requestId로 이미 처리된 요청인지 확인하면, 같은 요청이 다시 들어와도 중복 처리를 막을 수 있다. 

3. 처리 상태 저장 
요청 상태를 PENDING, ISSUED, FAILED와 같이 저장해두면, Consumer가 같은 메시지를 다시 읽었을 때 이미 ISSUED 상태인 요청은 다시 발급하지 않고 넘어갈 수 있다. 

4. Consumer 로직에서 중복 메시지를 방어해야 한다. 
Kafka 메시지는 장애 상황에서 다시 읽힐 수 있다는 전제로, Consumer는 같은 메시지가 여러 번 들어와도 결과가 한 번만 반영되도록 설계해야 한다. 
Kafka Consumer에서는 Offset Commit 실패로 인해 중복 처리가 발생할 수 있으므로, DB Unique Key, requestId 기반 멱등성, 처리 상태 저장 등을 이용해 중복 발급을 방지해야 한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

Kafka를 사용하면 API Server는 사용자에게 빠르게 요청 접수 응답을 줄 수 있다.

하지만 Consumer 처리 속도가 느리면 Kafka에 메시지가 쌓일 수 있다.

아래 상황을 읽고 답한다.

```
이벤트 시작 직후 요청이 급격히 증가했다.

API Server는 Kafka에 메시지를 빠르게 발행하고 있다.

하지만 Consumer 처리 속도가 Producer 발행 속도보다 느리다.

Kafka에 아직 처리되지 않은 메시지가 계속 쌓이고 있다.
```

이번 과제에서는 사용자가 발급 상태를 조회할 수 있도록 요청 상태가 저장되어 있다고 가정한다.

상태는 아래와 같이 단순화해서 사용한다.

```
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태

ISSUED: 쿠폰 발급이 성공한 상태

FAILED: 쿠폰 발급이 실패한 상태
```

### 1. Consumer Lag이란 무엇인가?

```
Consumer Lag은 Kafka Topic에 쌓인 메시지 중 Consumer가 아직 처리하지 못한 메시지의 양을 의미한다.

Producer는 계속 메시지를 발행하고 있는데 Consumer의 처리 속도가 그보다 느리면,
Kafka Topic에는 아직 읽히지 않았거나 처리되지 않은 메시지가 쌓이게 된다.

Producer가 발행한 메시지의 위치와 Consumer가 처리 완료한 Offset 사이의 차이를 Consumer Lag이라고 볼 수 있다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
Consumer Lag이 증가하면 사용자는 쿠폰 발급 요청 후 최종 결과를 늦게 확인하게 된다.

API Server는 Kafka 발행에 성공하면 빠르게 요청 접수 응답을 줄 수 있지만,
실제 쿠폰 발급 처리는 Consumer가 메시지를 읽고 DB 처리를 완료해야 끝난다.

따라서 Consumer Lag이 커지면 사용자의 요청 상태가 오랫동안 PENDING으로 남을 수 있다.

사용자 입장에서는 다음과 같은 경험을 하게 된다.
- 요청은 성공한 것 같은데 쿠폰이 바로 보이지 않는다.
- 마이페이지에서 발급 결과가 늦게 반영된다.
- 상태 조회 API를 호출해도 계속 PENDING이 나온다.
- 처리가 실패한 것인지, 아직 대기 중인 것인지 헷갈릴 수 있다.

따라서 Consumer Lag이 발생할 수 있는 구조에서는 사용자에게 현재 상태가 처리 중임을 명확히 안내해야 한다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 현재 처리 대기 중이며, 결과는 상태 조회 API 또는 마이페이지에서 확인할 수 있습니다.",
  "requestId": "req-20260702-000001"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었으며 아직 처리 중입니다. 잠시 후 다시 확인해주세요.",
  "requestId": "req-20260702-000001"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 정상적으로 발급되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패했습니다. 쿠폰이 모두 소진되었거나 발급 조건을 만족하지 못했습니다.",
  "requestId": "req-20260702-000001"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
운영자는 Consumer Lag을 보고 현재 쿠폰 발급 처리 시스템이 요청량을 따라가고 있는지 판단할 수 있다.

Consumer Lag이 일시적으로 증가했다가 빠르게 줄어든다면,
순간적으로 트래픽이 몰렸지만 Consumer가 정상적으로 따라잡고 있다고 볼 수 있다.

반대로 Consumer Lag이 계속 증가하거나 줄어들지 않는다면,
Consumer 처리 속도가 Producer 발행 속도보다 부족하다는 의미일 수 있다.

이 경우 운영자는 다음과 같은 판단을 할 수 있다.
- Consumer 인스턴스를 추가해야 하는지 확인한다.
- Partition 수가 충분한지 확인한다.
- DB 저장 속도가 병목인지 확인한다.
- 특정 Partition에 메시지가 몰리고 있는지 확인한다.
- Consumer 장애나 처리 실패가 발생하고 있는지 확인한다.
- 사용자에게 처리 지연 안내가 필요한지 판단한다.

Consumer Lag은 비동기 처리 시스템의 처리 지연 상태를 확인하는 중요한 운영 지표이다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
Kafka를 사용하면 API Server는 요청을 빠르게 접수할 수 있다. 
하지만 Kafka에 메시지를 넣는 것과 실제 쿠폰 발급 처리가 완료되는 것은 다르다. 

최종 발급 결과가 나오려면 Consumer가 Kafka 메시지를 읽고, 쿠폰 수량과 발급 조건을 확인한 뒤, DB에 쿠폰 발급 결과를 저장해야 한다. 

이때 요청량이 Consumer 처리량보다 많으면 Kafka에 메시지가 쌓이고, 뒤에 들어온 요청은 Consumer가 읽을 때까지 기다려야 한다. 

따라서 Kafka를 사용하더라도 Consumer 처리 속도, Partition 수, Consumer 수, DB 처리 성능에 따라 최종 발급 결과는 늦어질 수 있다. 

Kafka는 API Server의 즉시 부하를 줄이고 요청을 안전하게 쌓아두는 역할을 하지만, 실제 처리 속도 자체를 무한히 빠르게 만들어주는 것은 아니다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

아래 Kafka 설계를 읽고 문제점을 찾는다.

```
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.

Partition Key는 eventId로 설정했다.

대부분의 요청은 eventId = 1이다.

Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.

Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.

Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

위 설계의 문제점을 5가지 이상 작성하고, 각각의 개선 방향을 작성한다.

### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| Partition이 1개이다. | Partition이 1개이면 같은 Consumer Group 안에서 동시에 처리할 수 있는 Consumer도 최대 1개이다. 이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어오면 처리량이 부족해 Consumer Lag이 크게 증가할 수 있다. | Partition 수를 여러 개로 늘린다. 예를 들어 12개 Partition으로 설계해 여러 Consumer가 병렬로 처리할 수 있게 한다. |
| Consumer가 1개뿐이다. | Consumer가 1개이면 모든 쿠폰 발급 요청을 단일 Consumer가 처리해야 한다. 처리 속도가 부족하면 Kafka에 메시지가 계속 쌓이고, Consumer 장애 시 처리도 중단된다. | Consumer Group을 구성하고 여러 Consumer 인스턴스를 실행한다. 초기에는 6개 Consumer로 시작하고 Lag에 따라 확장할 수 있다. |
| Partition Key를 eventId로만 사용한다. | 대부분의 요청이 eventId = 1이면 같은 Key를 가진 메시지가 하나의 Partition에 몰릴 수 있다. 이 경우 Partition을 여러 개로 늘려도 특정 Partition만 바빠지고 병렬 처리 효과가 떨어진다. | eventId와 같이 이벤트와 사용자를 함께 포함한 Key를 사용한다. 이렇게 하면 같은 이벤트의 같은 사용자 요청 순서는 유지하면서 여러 사용자 요청을 분산할 수 있다. |
| Kafka 발행 실패에도 요청 접수 성공 응답을 준다. | Kafka 발행에 실패했다면 메시지가 Topic에 저장되지 않았을 수 있다. 그런데 성공 응답을 주면 사용자는 요청이 접수되었다고 믿지만, 실제로는 Consumer가 처리할 메시지가 없을 수 있다. | Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우에만 요청 접수 성공 응답을 준다. 발행 실패 시에는 요청 접수 실패 응답을 반환한다. |
| 요청 접수 성공과 쿠폰 발급 성공을 구분하지 않는다. | Kafka에 메시지가 들어간 것은 요청이 접수되었다는 뜻이지 쿠폰 발급이 완료되었다는 뜻이 아니다. 이를 구분하지 않으면 사용자에게 잘못된 결과를 안내할 수 있다. | API 응답은 PENDING 상태로 반환하고, 최종 결과는 Consumer 처리 후 ISSUED 또는 FAILED로 상태 조회 API에서 확인하게 한다. |
| DB 저장 후 Offset Commit 전에 Consumer가 죽는 상황을 고려하지 않았다. | DB 저장은 성공했지만 Offset Commit이 실패하면 Kafka는 해당 메시지를 처리 완료로 판단하지 못할 수 있다. Consumer가 재시작되면 같은 메시지를 다시 읽고 중복 처리할 수 있다. | DB 처리 후 Offset Commit을 수행하되, 중복 메시지가 다시 들어와도 문제가 없도록 DB Unique Key, requestId 기반 멱등성, 처리 상태 저장 등을 도입한다. |
| Consumer Lag이 증가해도 사용자가 처리 상태를 확인할 수 없다. | 사용자는 요청이 접수되었는지, 처리 중인지, 성공했는지, 실패했는지 알 수 없다. 결과가 늦어지면 사용자는 장애로 오해하거나 반복 요청을 보낼 수 있다. | requestId를 반환하고 상태 조회 API 또는 마이페이지에서 PENDING, ISSUED, FAILED 상태를 확인할 수 있게 한다. |
| 상태 저장 구조가 없다. | 비동기 구조에서는 요청 직후 최종 결과를 알 수 없기 때문에 현재 요청 상태를 저장해야 한다. 상태 저장이 없으면 PENDING 상태를 표현하거나 결과 조회를 제공하기 어렵다. | requestId 기준으로 요청 상태를 저장하는 저장소를 둔다. 상태는 PENDING, ISSUED, FAILED로 관리한다. |
| Consumer 처리 병목이 DB인지 Kafka인지 판단하기 어렵다. | Consumer Lag이 증가했을 때 원인이 Partition 부족인지, Consumer 수 부족인지, DB 저장 지연인지 알기 어렵다. 운영자가 적절한 조치를 하기 힘들다. | Consumer Lag, 처리 성공/실패 수, DB 저장 시간, Partition별 메시지 쏠림 등을 모니터링한다. |
| 단일 Consumer 장애에 취약하다. | Consumer가 1개뿐이면 해당 Consumer가 장애로 종료되었을 때 쿠폰 발급 처리가 멈춘다. Kafka에는 메시지가 쌓이지만 실제 발급은 진행되지 않는다. | 여러 Consumer 인스턴스를 같은 Consumer Group으로 운영한다. 하나의 Consumer가 장애 나더라도 다른 Consumer가 Partition을 재할당받아 처리할 수 있게 한다. |
