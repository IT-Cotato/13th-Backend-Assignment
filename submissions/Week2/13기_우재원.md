## 과제 1. Kafka 기반 비동기 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

![alt text](image.png)

### 2. API Server의 역할

API Server는 사용자의 요청을 받아 로그인 여부, 이벤트 기간 등 최소한의 유효성을 검증한 뒤, 실제 발급 처리를 직접 수행하지 않고 Kafka에 발급 요청 메시지를 Produce 합니다. 이후 Kafka로부터 ack를 정상적으로 수신하면, 클라이언트에게 요청이 접수되었음을 알리는 응답을 반환하여 스레드 제어권을 빠르게 회수합니다.

### 3. Kafka의 역할

Kafka는 API Server와 Consumer 사이에서 요청 메시지를 안전하게 전달하고 보관하는 버퍼 역할을 합니다. 이벤트 시작 순간 발생하는 대규모 트래픽 스파이크를 Topic과 Partition에 나누어 적재함으로써 DB로 향하는 부하를 물리적으로 격리합니다.

### 4. Consumer의 역할

Consumer는 Kafka Topic에 적재된 메시지를 자신이 처리 가능한 속도로 Consume, 실제 쿠폰 수량 차감 및 중복 발급 방지 로직을 수행하고 최종 결과를 DB에 저장합니다. 작업이 완료되면 Kafka에 Offset을 Commit하여 메시지 처리가 끝났음을 알립니다.

### 5. DB의 역할

Consumer의 비즈니스 로직 수행 결과를 바탕으로 최종 쿠폰 발급 기록을 영구적으로 저장합니다. 또한 `UNIQUE(coupon_id, user_id)`와 같은 제약 조건을 통해 분산 환경에서 발생할 수 있는 중복 발급을 막는 정합성 보장 역할을 담당합니다.

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

1분 안에 10만 건(약 1,667 RPS 이상)의 요청이 몰리는 상황에서 최종 발급 결과(DB 저장)까지 기다리는 동기 처리 방식을 사용하면, API Server의 스레드가 장시간 점유되고 DB Connection Pool이 고갈됩니다. 이는 시스템 전체의 타임아웃과 장애로 이어지므로, 비동기 구조를 통해 요청 접수와 처리 흐름을 분리해야 합니다.

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

* 요청 접수 성공: API Server가 클라이언트의 요청을 유실되지 않는 Kafka에 정상적으로 적재했다는 의미입니다.
* 쿠폰 발급 성공: Consumer가 대기열에서 메시지를 꺼내어 수량 차감 조건을 통과하고 DB에 최종적으로 발급 기록 저장을 완료했다는 의미입니다.

## 과제 2. Topic 설계하기

### 1. Topic 이름

`coupon.issue.requested`

### 2. Topic에 담기는 메시지의 의미

사용자로부터 쿠폰 발급 요청이 인입되었으며, 처리를 기다리고 있다는 상태를 의미합니다. 이는 발급 완료 이벤트가 아니며, 후속 처리가 필요함을 나타냅니다.

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

Producer는 API Server입니다. 클라이언트로부터 쿠폰 발급 API 호출이 들어왔을 때, 기본적인 요청값 검증을 통과한 직후 메시지를 발행합니다.

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

Consumer는 Coupon Issue Consumer(Worker)입니다. 큐에서 메시지를 폴링하여 이벤트 잔여 수량을 확인하고, 발급이 가능한 경우 DB에 발급 내역을 `INSERT` 하는 비즈니스 로직을 수행합니다.

### 5. 이 Topic이 필요한 이유

웹 요청을 처리하는 동기적 흐름과 무거운 디스크 I/O가 동반되는 DB 저장 흐름을 Decoupling하기 위함입니다. 이를 통해 트래픽 병목을 완충하고 API 서버의 가용성을 확보할 수 있습니다.

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

요청 데이터가 Kafka의 브로커 노드에 안전하게 기록되었으며, 서버 장애가 발생하더라도 해당 요청이 유실되지 않고 추후 Consumer에 의해 처리될 수 있음을 의미합니다.

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

메시지 적재는 단순히 처리 대기열에 진입했음을 뜻합니다. 향후 Consumer가 메시지를 처리하는 과정에서 쿠폰 수량이 이미 소진되었거나, 동일 사용자의 중복 요청으로 판별될 경우 발급이 FAILED될 수 있기 때문입니다.

## 과제 3. Kafka Message 구조 설계하기

### 1. Kafka Message JSON 예시

```json
{
  "requestId": "req-12345",
  "eventId": 1,
  "userId": 100,
  "requestedAt": "2026-06-26T12:00:00Z"
}

```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| `requestId` | 단일 요청을 식별하기 위한 고유 ID | 클라이언트의 상태 조회 API 호출 시 매핑 키로 사용되며, Consumer 재시도 시 멱등성을 보장하기 위한 식별자로 필요합니다. |
| `eventId` | 쿠폰 이벤트의 고유 식별자 | Consumer가 어떤 이벤트의 잔여 수량을 조회하고 차감해야 하는지 판단하기 위해 필요합니다. |
| `userId` | 요청을 보낸 사용자의 식별자 | DB 저장 시 발급 대상자를 특정하고, 동일 유저의 중복 참여 여부를 검증하기 위해 필요합니다. |
| `requestedAt` | API Server에 요청이 도달한 시각 | 선착순 판정의 논리적 기준 시간으로 활용되거나, Consumer Lag 모니터링 시 메시지 지연 시간을 측정하기 위해 필요합니다. |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

`eventId`로 이벤트 유효성을 확인하고, `userId`로 기발급 여부를 체크한 뒤 DB에 발급 레코드를 생성할 수 있습니다.

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

메시지 페이로드 크기가 증가하면 Kafka 브로커의 디스크 I/O 및 네트워크 대역폭 사용량이 늘어나 전체적인 시스템 처리량이 감소합니다. 또한, 발급 로직과 무관한 데이터가 포함되면 컴포넌트 간 결합도가 상승합니다.

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

네트워크 재전송이나 큐 내부 로직에 의한 중복 처리를 방어하는 멱등성 키의 역할보다는, 사용자가 본인의 요청 상태(PENDING, ISSUED 등)를 추적하고 조회하기 위한 유일한 식별값 정도로 이해하면 됩니다.

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

### 상황 A. Kafka 발행 성공

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-12345"
}

```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

해당 응답은 Kafka Broker로부터 메시지가 안전하게 기록되었다는 ack를 받은 직후 생성됩니다. 즉, 대기열 진입만 확인된 상태이며 Consumer의 실제 발급 로직은 아직 수행되지 않았습니다.

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

요청 접수 성공은 비동기 큐에 작업 지시서가 전달되었음을 뜻하고, 발급 성공은 Worker가 그 지시서를 수행하여 최종 데이터베이스 커밋까지 완료했음을 뜻합니다.

#### 4. requestId를 응답에 포함하는 이유

최종 발급 결과를 즉시 반환하지 않으므로, 클라이언트가 이후 폴링 방식 등으로 결과 조회 API를 호출할 때 자신의 요청 상태를 특정하기 위한 키 값이 필요하기 때문입니다.

---

### 상황 B. Kafka 발행 실패

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": "req-12345"
}

```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

Kafka 발행에 실패했다면 시스템 내부에 해당 요청에 대한 어떠한 기록도 존재하지 않습니다. 이때 성공 응답을 주면 사용자는 발급을 대기하게 되지만 실제 처리는 이루어지지 않는  데이터 유실 및 CS 이슈가 발생합니다.

#### 3. 이 상황에서 API Server가 주의해야 할 점

단순히 `producer.send()`를 호출한 시점이 아니라, 브로커로부터 확실한 실패 예외(Timeout 등)를 전달받은 상태를 의미합니다. API 서버는 내부 장애를 클라이언트에게 투명하게 인지시키고 재시도를 유도해야 합니다.

## 과제 5. Partition Key 선택하기

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| `userId` | 동일 사용자의 다중 요청이 항상 동일 파티션에 인입되므로, 사용자 단위의 메시지 처리 순서 보장과 중복 요청 필터링에 유리합니다. | 극소수의 악성 봇이 특정 계정으로 트래픽을 과도하게 발생시킬 경우 특정 파티션에 부하가 Skew될 수 있습니다. |
| `eventId` | 특정 이벤트 관련 로직이나 데이터를 하나의 파티션에서 모아서 관리하기 수월합니다. | 단일 선착순 이벤트 진행 시 모든 트래픽이 1개의 파티션으로 몰려 병렬 처리 이점을 완전히 상실합니다. |
| `requestId` | 모든 요청이 고르게 분산되므로 파티션 쏠림 현상을 완벽하게 방지하고 최대의 병렬 처리 효율을 낼 수 있습니다. | 동일 사용자의 중복 요청이 서로 다른 파티션에 배정되므로, 처리 순서 보장이 불가능하여 중복 제어 로직이 복잡해집니다. |

### 2. 내가 선택한 Partition Key

`userId`

### 3. 선택한 이유

선착순 시스템에서는 클라이언트의 재시도(버튼 연타 등)로 인한 중복 요청이 빈번하게 발생합니다. `userId`를 키로 지정하면 동일 유저의 요청 흐름이 단일 파티션에 순차적으로 적재되므로, Consumer가 중복 발급 시도를 추적하고 제어하는 데 구조적으로 가장 안정적이기 때문입니다.

### 4. 메시지 분산에 어떤 영향을 주는가?

사용자 ID의 해시 값을 기준으로 파티션을 결정하므로, 이벤트 참여자가 다수일 경우 트래픽은 설정된 여러 파티션에 균등하게 분산됩니다.

### 5. 순서 보장에 어떤 영향을 주는가?

Kafka의 파티션 내부 순서 보장 특성에 따라, 특정 `userId`가 보낸 요청 A, B, C는 반드시 파티션에 A, B, C 순서로 적재되고 Consumer 역시 그 순서대로 처리하게 됩니다.

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

일반적인 트래픽에서는 균등 분산되지만, 매크로를 사용하는 특정 유저(userId)가 초당 수천 건의 요청을 발생시킬 경우 해당 해시값이 배정된 단일 파티션의 Consumer Lag만 급증하는 쏠림 현상이 발생할 수 있습니다.

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

위에서 언급한 핫 키 문제로 인해, 동일 파티션에 묶여 있는 선량한 다른 사용자들의 요청 처리까지 연쇄적으로 지연될 위험이 존재합니다.

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

여름맞이 쿠폰 이벤트(`eventId = 1`) 하나만 진행 중일 때, 10만 건의 트래픽이 모두 파티션 0번으로 해싱됩니다. Consumer를 여러 대 구성하더라도 1대만 작동하고 나머지는 유휴 상태가 되어 시스템 확장이 무의미해집니다.

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가?

Kafka는 오직 동일한 Partition 내부에 적재된 메시지들에 대해서만 순서를 보장합니다. 서로 다른 파티션에 들어간 메시지는 각 파티션을 담당하는 독립적인 Consumer 스레드에 의해 비동기 병렬 처리되므로 전체 전역 순서는 보장되지 않습니다.

## 과제 6. Consumer Group과 Partition 수 설계하기

### 1. Topic 이름

`coupon.issue.requested`

### 2. Partition 수

`3`

### 3. Consumer Group 이름

`coupon-issue-group`

### 4. Consumer 수

`3`

### 5. Partition과 Consumer 매핑

```text
Partition 0 → Consumer 1
Partition 1 → Consumer 2
Partition 2 → Consumer 3

```

### 6. 이 구조를 선택한 이유

파티션 개수와 컨슈머 개수를 1:1로 맞춤으로써, 어떠한 컨슈머도 Idle로 낭비되지 않고 동시에 3개의 스레드가 10만 건의 트래픽을 나누어 처리하는 최대의 병렬 처리량을 확보하기 위함입니다.

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

최대 3개입니다.

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

초과된 2개의 Consumer는 할당받을 파티션이 없어 메시지를 전혀 소비하지 못한 채 대기 상태로 머무르게 되며, 불필요한 컴퓨팅 리소스가 낭비됩니다.

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

일부 Consumer가 2개 이상의 파티션을 동시에 담당하게 됩니다. 1대의 Consumer가 처리해야 할 메시지 양이 증가하므로, 단일 인스턴스의 병목이 발생하여 전체 Consumer Lag이 빠르게 상승할 수 있습니다.

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

Consumer Group의 병렬 처리 단위는 파티션 수에 의해 제한되기 때문입니다. 시스템 처리량을 높이기 위해 Consumer 인스턴스를 스케일 아웃하려면, 반드시 Topic의 파티션 수도 함께 스케일 아웃해야 유효한 성능 향상을 얻을 수 있습니다.

## 과제 7. Offset Commit 실패 상황 분석하기

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

Consumer가 정상적으로 로직 처리를 완료하고 DB에 저장까지 마쳤으나, 미처 Offset을 Commit하지 못한 채 종료되었던 동일한 메시지를 재시작 시 다시 읽어오게 됩니다.

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

Kafka 브로커는 Consumer로부터 명시적인 Offset Commit 요청을 수신해야만 해당 메시지가 처리되었음을 내부적으로 기록(Log)합니다. Commit 기록이 수신되지 않았다면 해당 오프셋은 미처리 상태로 간주됩니다.

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

네. Consumer Group은 재시작 시 Kafka에 기록된 마지막 Committed Offset 위치부터 메시지를 폴링하므로, 처리되었으나 커밋되지 않은 메시지는 중복 소비됩니다. (At-least-once 특성)

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

이미 발급 처리가 완료된 메시지가 다시 DB에 `INSERT`를 시도하게 됩니다. 이로 인해 동일 사용자에게 2장의 쿠폰이 초과 발급되거나, 한정된 쿠폰 수량이 이중 차감되는 등의 비즈니스 로직 훼손이 발생합니다.

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

메시지가 중복으로 인입되더라도 시스템 상태가 변경되지 않도록 멱등성,Idempotency 를 보장하는 장치가 필요합니다.

* `DB Unique Key`: `eventId`와 `userId` 컬럼 조합에 Unique 제약조건을 설정하여, 중복 INSERT 시 DB 레벨에서 무결성 위반 에러를 발생시키고 막습니다.
* `requestId 기반 멱등성`: 처리 상태를 저장하는 테이블에 `requestId`를 기록해 두고, 컨슈머 로직 진입 전 이미 처리된 `requestId`인지 검증하여 중복 시 로직을 Skip 합니다.

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

### 1. Consumer Lag이란 무엇인가?

Kafka 파티션에 새롭게 적재된 최신 메시지의 위치(Log-End-Offset)와 Consumer가 마지막으로 처리 완료를 보고한 위치(Committed Offset)의 차이입니다. 즉, 현재 처리되지 못하고 큐에 밀려 대기 중인 메시지의 총량을 뜻합니다.

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

API Server로부터 접수 완료 응답은 매우 빠르게 받았으나, 실제 Consumer의 처리가 지연되어 최종 발급 결과가 도출되기까지 오랜 시간이 소요됩니다. 사용자는 긴 시간 동안 처리 중 상태만 보게 되어 서비스 지연을 체감하게 됩니다.

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-12345"
}

```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "현재 요청량이 많아 순차적으로 발급 처리 중입니다.",
  "requestId": "req-12345"
}

```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰 발급이 성공적으로 완료되었습니다.",
  "requestId": "req-12345"
}

```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "준비된 쿠폰 수량이 모두 소진되었습니다.",
  "requestId": "req-12345"
}

```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?
현재 Consumer의 메시지 처리 속도가 Producer의 메시지 발행 속도를 따라가지 못하여 병목이 발생하고 있다고 판단할 수 있습니다. 이에 따라 Consumer 인스턴스 스케일 아웃을 검토하거나, DB 쿼리 등 컨슈머 내부 지연 요인을 분석해야 합니다.

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

Kafka는 API Server가 사용자에게 빠른 응답을 주기 위해 요청을 잠시 쌓아두는 완충일 뿐, 실질적인 비즈니스 연산 속도를 물리적으로 단축시키지 않기 때문입니다. 병목 지점이 API Server에서 Consumer 영역으로 이동한 것입니다.

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| **Partition 1개, Consumer 1개 구성** | 10만 건의 트래픽을 단일 스레드가 순차 처리해야 하므로, 병렬 처리가 원천적으로 불가능하여 시스템 처리량이 심각하게 저하됩니다. | Partition 개수를 늘리고(예: 3~5개), 동일한 Consumer Group 내에 Consumer 인스턴스를 늘려 병렬 처리 구조를 확보합니다. |
| **Partition Key를 `eventId`로 설정** | 선착순 10만 건의 요청이 모두 `eventId=1`이므로, 파티션이 여러 개여도 단일 파티션에만 트래픽이 쏠리는 Skew 현상이 발생합니다. | 트래픽을 균등하게 분산시키거나 사용자별 순서를 보장할 수 있도록, Partition Key를 `userId` 또는 `requestId`로 변경합니다. |
| **발행 실패 시에도 '접수 성공' 응답 반환** | 브로커 전송에 실패한 요청은 대기열에 존재하지 않아 영구 유실되나, 사용자는 접수된 것으로 오인지하여 치명적인 시스템 신뢰도 하락을 초래합니다. | API Server는 Kafka `ack` 수신 실패(Timeout 등) 시, 클라이언트에게 즉각적으로 `FAILED` (또는 500 Error)를 응답하여 재시도를 유도해야 합니다. |
| **Offset Commit 실패 상황 고려 누락** | Consumer 재시작 시 미커밋된 오프셋 구간이 재처리(At-least-once)되어, 동일 유저에게 쿠폰이 중복 발급되는 정합성 훼손이 발생합니다. | DB 레벨에 `UNIQUE(coupon_id, user_id)` 제약을 추가하거나, `requestId`를 활용한 멱등성 검증 로직을 구현하여 중복 삽입을 방어합니다. |
| **Consumer Lag 증가 시 처리 상태 확인 불가** | 지연 시간이 길어질 때 사용자가 상태를 확인할 수 없으면, 무분별한 새로고침과 재요청이 발생하여 API Server에 2차 장애(DDoS성 부하)를 유발합니다. | Redis 또는 DB에 요청의 초기 상태 PENDING 을  기록하고, 클라이언트가 식별자(`requestId`)로 폴링할 수 있는 조회 API를 제공해야 합니다. |
