# 2주차 과제

# Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 1. 과제 목표

이번 2주차 과제의 목표는 **Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 처리하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

이번 주차에서는 그 비동기 구조를 Kafka 기반으로 구체화한다.

이번 과제에서 설계해야 하는 기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Kafka Producer
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Topic 설계

Message 구조 설계

Partition Key 선택

Consumer Group 설계

Offset Commit과 중복 처리 가능성 이해

Consumer Lag이 사용자 경험에 미치는 영향 이해

Kafka 발행 실패 시 API 응답 설계
```

이번 과제의 핵심은 Kafka를 구현하는 것이 아니라, **Kafka를 시스템 구조 안에서 어떻게 사용할지 설계하는 것**이다.

---

## 2. 기본 상황

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 쿠폰 발급 처리를 수행하는 구조를 설계한다.

단, 이번 주차에서는 Redis 선착순 판정, DB Unique Key, requestId 멱등성, Outbox Pattern, Retry Topic, DLQ는 깊게 다루지 않는다.

---

## 3. 이번 과제의 전제 조건

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행한다.

Kafka 발행이 성공했다는 것은 Producer가 Kafka Broker로부터 발행 성공 응답을 받은 상황을 의미한다.

Kafka 발행이 실패했다면 아직 쿠폰 발급 요청이 시스템에 안전하게 접수된 것이 아니다.

따라서 Kafka 발행에 실패한 경우에는 사용자에게 요청 접수 성공 응답을 주면 안 된다.
```

또한 발급 상태 조회를 위해 요청을 식별할 수 있는 값이 필요하다.

```
requestId는 쿠폰 발급 요청을 식별하기 위한 값이다.

이번 주차에서는 requestId를 요청 식별자와 상태 조회에 필요한 값 정도로만 이해한다.

requestId를 이용한 멱등성 처리와 중복 요청 방지는 5주차에서 자세히 다룬다.
```

Consumer Lag 상황에서 사용자가 발급 상태를 조회할 수 있어야 하므로, 이번 과제에서는 발급 요청 상태를 저장할 수 있는 저장소가 있다고 가정한다.

```
상태 예시:
PENDING
ISSUED
FAILED
```

단, 상태 저장 테이블의 상세 설계는 이번 주차의 핵심이 아니다.

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

```
[Client]
  │
  │ 1. 쿠폰 발급 요청
  ▼
[API Server]
  │
  │ 2. 요청값 검증
  │ 3. requestId 생성
  │ 4. Kafka 메시지 생성
  ▼
[Kafka Producer]
  │
  │ 5. coupon.issue.requested Topic에 메시지 발행
  ▼
[Kafka Topic: coupon.issue.requested]
  │
  │ 6. 쿠폰 발급 요청 메시지 저장
  ▼
[Coupon Issue Consumer]
  │
  │ 7. 메시지 소비
  │ 8. 쿠폰 발급 로직 수행
  ▼
[DB]
  │
  │ 9. 발급 결과 저장
  ▼
[발급 상태 조회 API 또는 마이페이지]
```

### 2. API Server의 역할

```
사용자에게 쿠폰 발급 요청을 받아 쿠폰 발급 요청 메시지를 생성한다. 
Kafka Producer를 통해 Topic에 메시지를 발행하고, 발행 성공 여부에 따라 사용자에게 요청 접수 성공 또는 실패 응답을 반환한다. 
```

### 3. Kafka의 역할

```
API Server가 발행한 쿠폰 발급 요청 메시지를 Topic에 저장하고, Consumer가 처리할 수 있을 때까지 메시지를 보관한다.
Consumer 그룹을 통해 메시지를 Partition 단위로 나누어 처리할 수 있게 한다. 
Offset을 통해 Consumer가 어디까지 메시지를 읽었는지 관리할 수 있게 한다.
API 서버와 실제 쿠폰 발급 처리 로직을 분리한다. 
```

### 4. Consumer의 역할

```
Topic에서 메시지를 읽고 요청값을 확인한다. 
실제 쿠폰 발급 로직의 실행 가능성을 확인 후, 발급 로직을 수행한다. 
로직 수행 결과를 DB에 저장한 뒤 Offset을 커밋한다.
```

### 5. DB의 역할

```
쿠폰 발급 로직의 수행 결과를 저장한다. 
현재 발급 상태를 조회할 수 있게 데이터를 제공한다. 
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
대규모 트래픽이 몰릴 경우, 다음과 같은 문제가 발생할 수 있기 때문이다. 
1. API Server의 응답 시간이 길어진다.
2. DB에 동시에 많은 요청이 몰린다.
3. 사용자는 응답을 오래 기다리게 된다.
4. API Server나 DB 장애가 전체 사용자 경험에 직접 영향을 준다.
5. 대량 트래픽 상황에서 시스템 전체가 불안정해질 수 있다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
Kafka 발행 성공은 쿠폰 발급 완료가 아니라 처리 대기열에 요청이 들어갔다는 의미이다.

요청 접수 성공:
- API Server가 요청을 받음
- Kafka에 메시지 발행 성공
- 상태는 PENDING 또는 ACCEPTED

쿠폰 발급 성공:
- Consumer가 메시지를 처리함
- 실제 쿠폰 발급 로직 성공
- DB에 발급 결과 저장
- 상태는 ISSUED
```

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```
coupon
→ 도메인

issue
→ 발급

requested
→ 발급 요청이 들어왔음

```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
API Server가 Producer이다. 사용자가 쿠폰 발급 버튼을 눌러 API Server에 접수된 직후에 메시지를 발행한다.  
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Coupin Issue Consumer가 Consumer 역할을 하고 있다. 
Kafka에서 쿠폰 발급 요청 메시지를 읽고 그 메시지 안의 값들을 바탕으로 실제 쿠폰 발급 처리를 수행한다.

```

### 5. 이 Topic이 필요한 이유

```
API 서버와 실제 쿠폰 발급 처리 로직을 분리하기 위해 필요하다. 
Topic을 이용하면 API 서버는 요청을 카프카에 빠르게 전달하고 Consumer가 뒤에서 순차적 or 병렬적으로 실제 발급 처리를 수행하는 비동기화를 구현할 수 있다. 
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
쿠폰 발급 요청이 시스템에 접수되었고, 이 요청이 나중에 Consumer에 의해 처리될 수 있는 대기 상태가 되었다는 의미이다.
```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
실제 쿠폰 발급 로직은 Consumer에서 수행되고 있다. 
Topic에 메세지가 들어갔다는 것은 요청 접수와 처리 대기 상태를 의미할 뿐이다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": ,
  "eventId": ,
  "userId": ,
  "requestedAt":
}
```

### 2. 각 필드의 의미

| 필드 | 의미                    | 필요한 이유                                           |
| --- |-----------------------|--------------------------------------------------|
| requestId | 요청 식별 ID              | 사용자가 발급 상태를 조회하는 상황 등에서 각 요청을 식별하기 위해 사용하는 필드이다. |
| eventId | 쿠폰 이벤트 식별 ID          | 어떤 쿠폰 이벤트에 대한 발급 요청인지 Consumer가 알 수 있도록 기록       |
| userId | 요청 사용자 식별 ID          | 요청을 한 사용자를 식별하고 발급 조건과 발급 결과를 확인할 수 있도록 기록       |
| requestedAt | 사용자가 쿠폰 발급을 요청한 시간 기록 | 요청 발생 시점을 기록해 장애, 로그 분석, 처리 지연 확인 등 가능           |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
requestId를 기준으로 어떤 요청인지 식별 후,
eventId를 기준으로 어떤 쿠폰 이벤트에 대한 요청인지 확인.
userId를 기준으로 어떤 사용자의 요청인지 확인해 발급 받을 수 있는지 확인.
쿠폰 수량이 남아 있다면 쿠폰 발급 처리를 수행하고, 발급 결과를 저장한다.
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
메시지 크기가 커지면 Kafka 저장 공간과 네트워크 비용이 증가한다. 
인프라 전체가 불필요하게 많은 데이터 구조에 의존하게 된다. 
민감한 정보가 메시지에 포함될 위험이 커진다.
메시지 스키마 변경이 어려워 유지보수성이 떨어진다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
사용자의 요청을 구분하고, 발급 상태를 조회하거나 장애나 로그를 추적할 때 요청 단위로 확인할 수 있다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": ,
  "message": ,
  "requestId":
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
위의 다른 과제에서 설명했듯, Kafka에 쿠폰 발급 요청 메시지가 정상적으로 발행되었다고 해서 Consumer가 실제 쿠폰 발급 로직을 수행했다는 의미가 되진 않는다. 
다만 이 응답은 요청 접수 성공을 의미할 수 있다. 
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공은 사용자의 요청이 Kafka Topic에 정상적으로 들어갔다는 뜻이다.
쿠폰 발급 성공은 Consumer가 Kafka 메시지를 읽고 실제 발급 로직을 수행한 뒤, DB에 발급 성공 결과를 저장했다는 뜻이다.
```

#### 4. requestId를 응답에 포함하는 이유

```
사용자가 나중에 발급 상태를 조회할 때 필요하기 때문이다.
비동기 구조에서는 요청 직후 최종 결과를 바로 응답하지 않으므로 따로 조회할 필요가 있다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": ,
  "message": ,
  "requestId":
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
Kafka 발행 실패 시, Consumer가 해당 요청을 전달받을 수 있는 경로가 없기 때문이다.
실제 로직이 수행되지 않는 상황에서 성공 응답을 준다면, 사용자는 자신의 요청이 접수되었다고 오해한 상태로 대기하게 되어 UX가 망가진다. 
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
API 서버는 Kafka 발행 성공 여부 확인 전에 즉각적으로 요청 접수 성공 응답을 클라이언트에게 전송하지 않도록 주의해야 한다. 
발행 실패 시 사용자에게 재시도 가능한 실패 응답을 반환해야 하고 실패한 요청을 성공 상태로 저장하지 않는다. 
```

## 과제 5. Partition Key 선택하기

`coupon.issue.requested` Topic의 Partition Key를 무엇으로 정할지 선택한다.

아래 후보 중 하나를 선택하거나, 직접 다른 Key를 제안해도 된다.

```
1. userId

2. eventId

3. requestId

4. 그 외 직접 선택
```

특히 `eventId`를 Partition Key로 선택한 경우에는 아래 상황을 반드시 고려한다.

```
이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰린다.
```

이때 모든 메시지가 특정 Partition에 몰릴 수 있는지 설명한다.

이번 과제에서는 정답 Partition Key를 하나로 고정하지 않는다.

중요한 것은 자신이 선택한 Partition Key가 아래 항목에 어떤 영향을 주는지 설명하는 것이다.

```
메시지 분산

순서 보장

특정 Partition 쏠림 가능성

Consumer 병렬 처리
```

### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점                                                                      | 단점                                                                                  |
| --- |-------------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| userId | 같은 사용자의 요청이 같은 Partition에 들어가 사용자 기준 요청 순서를 괄니할 수 있고, 중복 클릭 흐름을 추적하기 좋다. | 특정 사용자의 비정상적인 요청량을 처리해야 할 경우 특정 Partiotion에 부하가 몰릴 수 있다. 이벤트 전체 기준의 순서를 보장하지 않는다.   |
| eventId | 같은 이벤트에 대한 요청을 한 기준으로 묶어 이벤트 단위 처리 흐름을 파악하기 쉽다.                         | 선착순 이벤트에서는 대부분의 요청이 하나의 Partition에 집중되어 병렬 처리 효과가 떨어질 수 있다.                         |
| requestId | 요청마다 고유한 값이므로 메시지가 비교적 고르게 분산된다.                                        | 같은 사용자의 여러 요청이 서로 다른 Partition으로 가면 사용자 기준 순서 보장이 어렵다. 중복 클릭 흐름을 사용자 단위로 추적하기 불리하다. |

### 2. 내가 선택한 Partition Key

```
userId
```

### 3. 선택한 이유

```
선착순 쿠폰 발급 시스템에서는 다양한 상황으로 인해 한 사용자의 중복요청이 발생할 수 있다. 
이 경우, 한 사용자의 요청을 같은 Partiotion으로 넣어야 그 내부에서 메시지 순서를 보장할 수 있어 요청 순서를 관리하기 쉽다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
일반적인 이벤트에서는 요청자가 매우 많고 사용자의 요청 수는 상대적으로 제한적이라 메시지 분산 효과도 기대할 수 있다. 
다만, 한 사용자의 악의적인 활용이나 비정상적인 수의 요청이 발생할 경우 해당 Partiotion에 메시지가 몰릴 수 있다. 
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
같은 파티션 내에서는 메시지 순서가 보장되므로 같은 사용자 기준으로 요청 순서를 유지하기 쉽다. 
서로 다른 사용자 간의 전체 요청 순서는 보장되지 않는다. 
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
가능성은 있다. 
특정 사용자가 비정상적으로 많은 요청을 보내면 몰릴 가능성이 있다.

하지만 선착순 쿠폰 이벤트에서는 일반적으로 많은 사용자가 각각 소수의 요청을 보낸다.
따라서 eventId를 Key로 사용하는 것보다 Partition 부하 위험이 낮다고 판단했다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
- 특정 사용자의 악의적 과다 요청으로 인한 부하.
- 이벤트 전체 기준의 요청 순서 보장 불가
- 같은 이벤트의 전체 요청을 하나의 순서로 처리해야 하는 요구사항이 있을 경우 부적합
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
특정 이벤트에 요청이 몰리는 상황을 반드시 고려해야 한다.
eventId만 파티션 키로 사용할 경우, 이벤트 시작 직후 대부분의 요청이 eventId = 1 하나에 몰릴 수 있으며, 그 결과 병렬 처리 효과가 크게 떨어진다. 
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
서로 다른 Partition의 메시지 순서는 보장하지 않으며 같은 Partition에 들어간 메시지의 처리 순서는 보장된다.
이는 각 파티션마다 독립적으로 메시지가 저장된고 Consumer Group 안의 서로 다른 Consumer가 각 파티션을 병렬로 처리할 수 있기 때문이다.
같은 파티션에 들어간 메시지는 Offset 순서대로 저장되어 Consumer에 의해 읽혀진다. 
```

## 과제 6. Consumer Group과 Partition 수 설계하기

쿠폰 발급 요청을 처리하는 Consumer Group을 설계한다.

기본 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있다.

Consumer는 coupon.issue.requested Topic을 읽는다.

Consumer는 실제 쿠폰 발급 처리를 수행한다.
```

이번 과제에서 정확한 처리량 계산이 목적은 아니다.

중요한 것은 아래 내용을 이해하고 설명하는 것이다.

```
Partition 수가 Consumer 병렬 처리에 어떤 영향을 주는가?

Consumer Group은 왜 필요한가?

Consumer 수와 Partition 수의 관계는 무엇인가?

Consumer 수만 무작정 늘리면 왜 안 되는가?
```

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
6개
```

### 3. Consumer Group 이름

```
coupon-issue-group
```

### 4. Consumer 수

```
6개
```

### 5. Partition과 Consumer 매핑

```
(매핑 예시: Partition 0 → Consumer 1)

Partition 0 → Consumer 1
Partition 1 → Consumer 2
Partition 2 → Consumer 3
Partition 3 → Consumer 4
Partition 4 → Consumer 5
Partition 5 → Consumer 6
```

### 6. 이 구조를 선택한 이유

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어올 수 있어 Consumer가 하나만 처리하는 구조는 적절하지 않다.
카프카에서는 같은 Consumer Group 안에서 파티션 단위로 메시지를 나누어 처리할 수 있다. 
따라서 Partiotion 수를 6개로 두고 Consumer도 6개로 두면, 각 consumer가 하나의 Partiotion을 담당해 병렬 처리를 수행할 수 있다. 
그러면 처리량을 높일 수 있고, 놀고 있는 Consumer가 발생하지 않는다.

```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
최대 3개이다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
Consumer 수가 Partiotion 수보다 많으면 일부 Consumersms Partition을 할당받지 못하고 대기한다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
Consumer 수가 Partition 수보다 적으면 하나의 Consumer가 여러 Partition을 담당하게 된다. 
이 경우 모든 Partition은 처리되지만, 각 Consumer가 여러 Partition은 처리되지만 Consumer 하나당 처리 부담이 커질 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
Consumer 수만 늘린다고 처리량이 무한히 증가하지 않기 때문이다. 
그리고 불필요한 서버 리소스 낭비, Consumer Group 리밸런싱 비용이 증가한다. DB에 동시에 많은 쓰기 요청이 들어가 DB 부하가 증가하고 장애 상황에서 운영 복잡도가 증가한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

Kafka Consumer가 메시지를 처리하는 도중 장애가 발생하는 상황을 분석한다.

아래 상황을 읽고 질문에 답한다.

```
1. Consumer가 Kafka 메시지를 읽었다.

2. Consumer가 DB 저장까지 성공했다.

3. 하지만 Offset Commit 전에 Consumer가 장애로 종료되었다.

4. Consumer가 다시 실행되었다.
```

이번 과제에서는 이 문제를 완전히 해결하는 것이 목적이 아니다.

중요한 것은 Kafka Consumer에서 아래 상황이 발생할 수 있음을 이해하는 것이다.

```
DB 처리는 성공했지만 Offset Commit은 실패할 수 있다.

Offset Commit이 실패하면 Kafka는 해당 메시지가 처리 완료되었다고 판단하지 못할 수 있다.

그 결과 같은 메시지가 다시 읽히고 다시 처리될 수 있다.
```

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
Consumer는 Offset 커밋이 완료되지 않은 메시지를 다시 읽을 수 있다. 

현 상황에서는 Offset Commit 전에 장애로 종료되었다.
따라서 Consumer가 다시 실행되면 마지막으로 Commit된 Offset 이후의 메시지부터 다시 읽게 된다.
그 결과 DB 저장까지 성공했던 동일한 메시지를 다시 읽을 수 있다.
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Offset Commit 전에 장애가 발생했기 때문에 해당 메시지가 처리 완료되었는지 기록이 남지 않아서 그렇다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
그렇다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능이라는 조건을 위반할 수 있다. 
또한, 쿠폰 수량이 실제보다 빠르게 차감되어 다른 사용자가 피해를 볼 수 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

아래 키워드를 참고해서 작성한다.

```
DB Unique Key

requestId 기반 멱등성

처리 상태 저장

중복 메시지 방어
```

답변:

```
이 문제를 해결하려면 다음과 같은 장치가 필요할 수 있다.

1. DB Unique Key

같은 이벤트에서 같은 사용자가 쿠폰을 2번 발급받지 못하도록 DB에 eventId + userId 조합의 Unique Key를 설정할 수 있다.

2. requestId 기반 멱등성

requestId를 기준으로 이미 처리한 요청인지 확인할 수 있다. 
처리 상태를 확인하고, 이미 ISSUED 또는 FAILED 상태로 처리된 요청이라면 다시 처리하지 않도록 할 수 있다. 

3. 처리 상태 저장

요청 상태를 PENDING, ISSUED, FAILED 등으로 저장해두고, Consumer가 같은 메시지를 다시 읽었을 때 현재 상태를 확인할 수 있게 한다.
이미 처리 완료된 요청이라면 중복 처리를 하지 않고 Skip할 수 있다.

4. 중복 메시지 방어

Kafka Consumer는 같은 메시지를 한 번 이상 처리할 수 있다고 가정해야 한다.
따라서 Consumer 로직은 중복 메시지가 들어와도 시스템 정합성이 깨지지 않도록 설계해야 한다.
즉, Kafka를 사용한다고 해서 정확히 한 번만 처리된다고 가정하면 안 되고, DB 제약 조건과 멱등성 처리를 함께 고려해야 한다.
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

Kafka를 사용하면 API Server는 사용자에게 빠르게 요청 접수 응답을 줄 수 있다.

하지만 Consumer 처리 속도가 느리면 Kafka에 메시지가 쌓일 수 있다.

아래 상황을 읽고 답한다.

```
이벤트 시작 직후 요청이 급격히 증가했다.

API Server는 Kafka에 메시지를 빠르게 발행하고 있다.

하지만 Consumer 처리 속도가 Producer 발행 속도보다 느리다.

Kafka에 아직 처리되지 않은 메시지가 계속 쌓이고 있다.
```

이번 과제에서는 사용자가 발급 상태를 조회할 수 있도록 요청 상태가 저장되어 있다고 가정한다.

상태는 아래와 같이 단순화해서 사용한다.

```
PENDING: 요청은 접수되었지만 아직 처리되지 않은 상태

ISSUED: 쿠폰 발급이 성공한 상태

FAILED: 쿠폰 발급이 실패한 상태
```

### 1. Consumer Lag이란 무엇인가?

```
카프카에 쌓인 메시지 중 Consumer가 아직 처리하지 못한 메시지 수를 의미한다.
파티션의 최신 오프셋과 Consumer 그룹이 마지막으로 커밋한 오프셋 차이를 의미한다. 
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
사용자는 요청 접수 응답은 빠르게 받을 수 있지만, 대기 상태가 길어져 최종 쿠폰 발급 결과는 늦게 확인하게 된다. 
따라서 UX가 나빠진다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "request-20260702-000001"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다.",
  "requestId": "req-20260702-000001"
}}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-20260702-000001"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급에 실패했습니다.",
  "requestId": "req-20260702-000001"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
운영자는 Consumer Lag을 보고 현재 Consumer 처리량이 Producer 발행량을 따라가고 있는지 판단할 수 있다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
실제 쿠폰 발급은 Consumer가 Kafka 메시지를 읽고 처리해야 완료된다.
Producer가 메시지를 발행하는 속도보다 Consumer가 처리하는 속도가 느리면, Kafka Topic에 처리되지 않은 메시지가 계속 쌓인다.
이 경우 요청 접수에 비해 최종 결과는 늦게 나올 수 있다. 
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기

아래 Kafka 설계를 읽고 문제점을 찾는다.

```
Client
  ↓
API Server
  ↓
Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Partition 1개
  ↓
Consumer 1개
  ↓
DB 저장
```

추가 조건은 다음과 같다.

```
이벤트 시작 직후 1분 안에 최대 10만 건의 요청이 들어온다.

Partition Key는 eventId로 설정했다.

대부분의 요청은 eventId = 1이다.

Kafka 발행에 실패해도 API Server는 사용자에게 요청 접수 성공 응답을 준다.

Consumer가 DB 저장 후 Offset Commit 전에 죽는 상황은 고려하지 않았다.

Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다.
```

위 설계의 문제점을 5가지 이상 작성하고, 각각의 개선 방향을 작성한다.

### 문제점과 개선 방향

| 문제점                                                 | 왜 문제인가?                                                                                       | 개선 방향                                                                                     |
|-----------------------------------------------------|-----------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------|
| Partition이 하나이다.                                    | 병렬 처리 단위인 파티션이 1개이면 같은 컨슈머 그룹 안에서 하나의 컨슈머만 메시지를 처리할 수 있다.                                     | 예상 요청량과 Consumer 처리량을 고려해 파티션 수를 늘린다.                                                     |
| Consumer가 하나이다.                                     | 모든 쿠폰 발급 요청이 하나의 Consumer에 의해 처리되기 때문에 Consumer Lag이 증가할 수 있으며, 장애가 발생할 경우 처리 전체가 중단될 위험이 있다. | 컨슈머 그룹을 구성하고 여러 컨슈머를 실행해 파티션 단위로 병렬 처리한다.                                                 |
| 파티션 키가 eventId이다.                                   | 대부분의 요청이 특정 파티션에 몰릴 수 있어 병렬 처리 효과가 떨어진다.                                                      | 더 분산에 유리한 키를 고려한다.                                                                        |
| Kafka 발행에 실패해도 요청 접수 성공 응답을 준다.                     | Consumer에 전달되 메시지가 없음에도 사용자는 요청이 접수되덨다고 생각해 데이터 유실 문제가 발생한다.                                  | Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우에만 성공 응답을 준다. 실패할 경우 실패 응답을 반환하고 재시도를 안내한다.      |
| DB 저장 후 Offset Commit 전에 Consumer가 죽는 상황을 고려하지 않았다. | 컨슈머 재시작 후 같은 메시지를 다시 읽고 중복 발급될 확률이 있다.                                                        | requestId 기반 멱동성, 처리 상태 저장 등을 통해 같은 메시지가 다시 처리되어도 중복 발급이 발생하지 않도록 방어한다.                   |
| Consumer Lag이 증가해도 사용자가 처리 상태를 확인할 수 있다.            | PENDING 상태가 길어지는 상황에서 UX가 나빠진다.                                                               | requestId 기반 발급 조회 API를 제공해 상태를 PENDING, ISSUED, FAILED 등으로 명시한다.                         |
| 요청 접수 성공과 쿠폰 발급 성공을 구분하지 않는다.                       | 메시지를 넣은 시점은 실제 발급 완료가 아니다. 이를 구분하지 않으면, 실제 상태와 다른 상황을 사용자에게 안내하게 될 수 있다.                      | 요청 API는 PENDING 또는 ACCEPTED를 반환하고 실제 발급 결과는 상태 조회 API나 마이페이지에서 ISSUED 또는 FAILED로 확인하게 한다. |
