# Kafka 기반 비동기 쿠폰 발급 요청 처리 구조 설계

## 과제 1. Kafka 기반 비동기 처리 구조 그리기

쿠폰 발급 요청이 들어왔을 때 Kafka를 이용해 비동기적으로 처리하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### 1. 전체 요청 처리 흐름 다이어그램

Client
  │  쿠폰 발급 요청 (POST /coupons/issue)
  ▼
API Server
  │  요청값 검증
  │  Kafka 발행 시도
  ▼
Kafka Producer
  │  발행 성공 응답 수신
  ▼
coupon.issue.requested Topic (Partition 0 / 1 / 2 ...)
  │
  ▼
Coupon Issue Consumer (Consumer Group: coupon-issue-group)
  │  eventId, userId 확인
  │  실제 발급 처리 로직 수행
  ▼
DB
  │  발급 결과 저장 (ISSUED / FAILED)
  ▼
(사용자는 마이페이지 조회 API로 결과 확인)

### 2. API Server의 역할

```
API Server는 쿠폰 발급을 끝까지 처리하지 않는다. 요청을 받아서 기본적인 값 검증(로그인 여부, eventId 유효성 등)을 하고, Kafka에 메시지를 발행한 뒤, 발행 성공 여부만 확인해서 사용자에게 빠르게 응답을 돌려주는 역할까지만 담당한다. 즉 API Server의 책임은 "요청 접수"이지 "발급 처리"는 아니다.

```

### 3. Kafka의 역할

```
Kafka는 API Server와 Consumer 사이에서 요청을 안전하게 전달하고 잠시 쌓아두는 중간 버퍼 역할을 한다. 요청이 순간적으로 몰려도 API Server가 이를 즉시 다 처리할 필요 없이 Kafka에 밀어넣기만 하면 되므로, 순간 트래픽과 실제 처리 속도를 분리해주는 역할을 한다.
```

### 4. Consumer의 역할

```
Consumer는 Kafka에 쌓인 메시지를 자신의 처리 속도에 맞춰 꺼내 읽고, 메시지 안의 eventId·userId를 바탕으로 실제 쿠폰 발급 가능 여부를 판단해 DB에 반영하는 역할을 한다. API Server가 받지 않은 "실제 비즈니스 로직 수행 + 정합성 처리"의 책임을 여기서 진다.
```

### 5. DB의 역할

```
DB는 최종적으로 쿠폰이 발급되었는지, 실패했는지에 대한 사실을 영구적으로 기록한다.
1. 발급 요청 상태를 담는 테이블
  Kafka 메시지가 들어와서 Consumer가 처리한 결과를 기록하는 테이블.
2. 실제 발급된 쿠폰을 담는 테이블 
```

### 6. 사용자가 요청 직후 최종 발급 결과를 바로 받지 않는 이유

```
1분 안에 10만 건이 몰리는 상황에서 API Server가 요청마다 DB까지 동기적으로 처리하면 응답 시간이 길어지고 DB 부하가 커진다. 그래서 요청을 받았다는 사실과 실제로 처리했다는 사실을 분리해서, 접수는 즉시 응답하고 실제 처리는 뒤에서 비동기로 진행하도록 설계한 것이다. 이렇게 하면 API Server는 Kafka에 메시지를 넣는 짧은 작업만 하면 되므로 응답 속도가 트래픽 규모와 거의 무관해진다.
```

### 7. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공은 API Server가 Kafka에 메시지를 정상적으로 발행했다는 뜻이다. 아직 쿠폰이 실제로 발급됐는지는 알 수 없다.
쿠폰 발급 성공은 Consumer가 메시지를 읽어 실제 발급 로직을 수행하고 DB에 ISSUED로 기록까지 끝난 상태이다.
```

## 과제 2. Topic 설계하기

쿠폰 발급 요청 메시지를 담을 Kafka Topic을 설계한다.

### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Topic에 담기는 메시지의 의미

```
사용자가 어떤 이벤트에 대해 쿠폰 발급을 요청했다는 의미이다. 발급이 완료됐다는 의미는 포함하지 않는다.
```

### 3. Producer는 어떤 컴포넌트이며 언제 메시지를 발행하는가?

```
Producer는 API Server다. 
사용자의 쿠폰 발급 요청이 들어오고, 기본적인 요청값 검증(로그인 여부, eventId 존재 여부 등)을 통과한 직후 이 Topic에 메시지를 발행한다.
```

### 4. Consumer는 어떤 컴포넌트이며 어떤 처리를 수행하는가?

```
Consumer는 Coupon Issue Consumer다. 이 Topic에서 메시지를 읽어 실제 쿠폰 발급 가능 여부를 판단하고, 발급 처리 후 결과를 DB에 저장한다.
```

### 5. 이 Topic이 필요한 이유

```
 Topic이 없으면 API Server가 요청을 받는 즉시 DB까지 직접 다뤄야 하고, 이는 트래픽이 몰릴 때 초과분은 갈 곳이 없어서 응답 지연, 타임아웃, 커넥션 풀 고갈, DB 락 경합 같은 문제로 이어질 수 있다.
 Topic은 API Server와 실제 발급 처리 로직을 물리적으로 분리하기 위해 필요하다. 
Topic이 하는 일은 세 가지로 나눠서 볼 수 있다.
- 순간 트래픽을 흡수하는 버퍼 역할
-  API Server와 DB를 트래픽 폭주로부터 보호
- 두 컴포넌트의 확장을 독립적으로 가져갈 수 있음
```

### 6. 이 Topic에 메시지가 들어갔다는 것은 어떤 의미인가?

```
"쿠폰 발급 요청이 시스템에 안전하게 접수되어, 나중에 반드시 Consumer가 읽어서 처리할 대상이 되었다"는 의미다.
1) API Server(Producer)가 Kafka Broker로부터 발행 성공 응답(ack)을 받았다
2)  메시지가 특정 Partition에 물리적으로 기록되었다
3) 이 메시지는 Consumer가 반드시 읽어갈 대상으로 등록된다
 정리하자면, Topic에 메시지가 들어갔다는 건 "이 요청은 이제 API Server의 메모리나 네트워크 요청 안에만 존재하는 게 아니라, Kafka라는 영속적인 로그에 Offset이라는 확정된 위치를 가지고 저장되어, Consumer가 장애 여부와 무관하게 언젠가는 반드시 읽어갈 수 있는 상태가 되었다"는 의미이다.

```

### 7. 이 Topic에 메시지가 들어갔다는 것이 쿠폰 발급 완료를 의미하지 않는 이유

```
Topic은 "요청됨" 상태를 나타낼 뿐이다. 
실제 발급 여부는 재고 소진, 중복 발급 여부 등 Consumer가 메시지를 읽은 뒤 비즈니스 로직을 수행해야만 결정된다.
메시지가 Topic에 쌓여 있어도 Consumer가 아직 읽지 않았거나, 읽었지만 처리에 실패(재고 소진 등)했을 수 있으므로 Topic 적재 자체는 완료를 보장하지 않는다.
```

## 과제 3. Kafka Message 구조 설계하기

`coupon.issue.requested` Topic에 발행할 메시지 구조를 JSON 형태로 설계한다.

### 1. Kafka Message JSON 예시

```json
{
  "requestId": ,
  "eventId": ,
  "userId": ,
  "requestedAt":
}
```

### 2. 각 필드의 의미

| 필드 | 의미 | 필요한 이유 |
| --- | --- | --- |
| requestId | 하나의 발급 요청을 식별하는 고유 문자열 | 상태 조회 API에서 이 요청의 처리 상태를 찾는 키가 되고, 이후 중복 처리 여부를 추적/방어하는 기준이 된다 |
| eventId | 어떤 쿠폰 이벤트에 대한 요청인지 나타내는 ID | Consumer가 어떤 이벤트의 재고·조건을 확인해야 하는지 알기 위해 필수 |
| userId | 요청한 사용자 ID | Consumer가 "이 사용자가 이미 발급받았는지"를 판단하고 발급 대상을 특정하기 위해 필수 |
| requestedAt | 사용자가 요청을 보낸 시각 | 처리 지연 시간(Consumer Lag) 측정, 장애 추적, 선착순 판단의 참고 자료로 사용 |

### 3. Consumer가 이 메시지를 보고 어떤 처리를 할 수 있는가?

```
1) eventId로 "무엇에 대한 요청인지" 컨텍스트를 확보
  - 이벤트가 아직 진행 중인가 (시작 전/종료 후 요청 방어)
  - 총 발급 가능 수량이 몇 개고, 지금까지 몇 개가 나갔는가 (남은 재고)
  메시지는 요청 시점의 스냅샷일 뿐이고, 재고는 그 사이 다른 메시지들이 처리되면서 계속 바뀌는 값이라 Consumer가 처리하는 그 순간에 DB(혹은 Redis 같은 카운터)를 직접 조회해야만 정확하다.

2) userId로 "누구에게" 발급할지, 그리고 "이미 받았는지"를 판단
  userId와 eventId를 조합해서 "이 사용자가 이 이벤트에서 이미 발급받은 이력이 있는가"를 확인한다.

3) requestId로 "이 요청 자체"를 상태 저장소에 매핑
  처리 결과가 나오면(성공이든 실패든) requestId를 키로 상태 테이블에 반영한다.

4) requestedAt으로 지연 상황을 파악
  직접적인 발급 판단에는 안 쓰이지만, "이 메시지가 발행된 지 얼마나 지나서 처리됐는가"를 계산하는 데 쓸 수 있다
```

### 4. 메시지에 너무 많은 정보를 넣는 것이 왜 좋지 않을 수 있는가?

```
1) 처리량/성능 문제
  Kafka는 초당 대량의 메시지를 처리하도록 설계됐지만, 메시지 하나의 크기가 커지면 그만큼 네트워크 전송량, 디스크 쓰기량, 브로커 메모리 사용량이 늘어난다.

2) 데이터 정합성 문제
  메시지는 "발행되는 시점"의 스냅샷이다.
  만약 메시지 안에 "할인 금액: 5000원"처럼 정책성 데이터를 박아뒀는데, 처리되는 시점에 정책이 바뀌었다면 Consumer는 오래된 데이터를 기준으로 발급하게 되는 문제가 생긴다.
```

### 5. requestId는 이번 주차에서 어떤 정도로만 이해하면 되는가?

```
이번 주차에서는 requestId를 식별 + 조회용정도로 이해하면 된다.
```

## 과제 4. Kafka 발행 성공 / 실패에 따른 API 응답 설계하기

API Server는 사용자의 쿠폰 발급 요청을 받은 뒤 Kafka에 메시지를 발행한다.

이때 Kafka 발행이 성공한 경우와 실패한 경우의 API 응답을 각각 설계한다.

이번 과제에서는 Kafka 발행 성공을 아래와 같이 정의한다.

```
Kafka 발행 성공:
Producer가 Kafka Broker로부터 발행 성공 응답을 받은 경우

Kafka 발행 실패:
Producer가 Kafka Broker에 메시지를 정상적으로 발행하지 못한 경우
```

---

### 상황 A. Kafka 발행 성공

API Server가 Kafka에 쿠폰 발급 요청 메시지를 정상적으로 발행했다.

이때 사용자에게 어떤 응답을 줄 것인지 작성한다.

#### 1. Kafka 발행 성공 시 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 잠시 후 결과를 확인해주세요.",
  "requestId" "req-20260702-abc123":
}
```

#### 2. 이 응답이 쿠폰 발급 성공을 의미하지 않는 이유

```
이 응답 시점에 실제로 확정된 사실은 "Producer가 Kafka Broker로부터 발행 성공 응답을 받았다" 하나 뿐이다. 
Consumer가 아직 이 메시지를 읽지도 않았을 수 있고, 읽었다 해도 재고 소진·중복 발급 등으로 실패할 수 있다. "발행 성공"이라는 사실 하나로는 "발급 성공"이라는 결과를 전혀 추론할 수 없다. 
따라서 이 시점에는 실제 발급 여부를 전혀 알 수 없다.
```

#### 3. 요청 접수 성공과 쿠폰 발급 성공의 차이

```
요청 접수 성공은 시스템이 요청을 잃어버리지 않고 안전하게 받아들였다는 뜻,
 쿠폰 발급 성공은 실제로 재고가 차감되고 DB에 발급 기록이 남았다는 뜻이다.
 전자는 Producer~Broker 사이의 계약이고, 후자는 Consumer~DB 사이의 계약이라 서로 다른 컴포넌트, 다른 시점에 결정된다.
```

#### 4. requestId를 응답에 포함하는 이유

```
 1) 1:1 매핑 보장 - 요청 하나(버튼 클릭 한 번)와 상태 조회 결과 하나가 정확히 대응된다.
 2) 중복 요청 구분 -  사용자가 실수로 버튼을 두 번 눌렀다면 requestId가 두 개 생기고, 두 요청은 서로 독립적으로 상태를 조회할 수 있다.
```

---

### 상황 B. Kafka 발행 실패

API Server가 Kafka에 메시지를 발행하려고 했지만 실패했다.

이때 사용자에게 요청 접수 성공 응답을 줘도 되는지 판단하고, 적절한 응답을 설계한다.

#### 1. Kafka 발행 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요.",
  "requestId": null
}
```

#### 2. Kafka 발행에 실패했는데 요청 접수 성공 응답을 주면 안 되는 이유

```
1) "유실"이 아니라 "존재한 적 없는 것처럼" 사라진다는 점
  일반적인 장애는 "처리하다가 실패해서 FAILED로 남는 것"이지만, 이 경우는 시스템 어디에도 이 요청이 기록되지 않는다.
2) 비동기 구조의 기본 전제를 깨뜨린다는 점
  이 시스템 전체는 "일단 접수만 되면, 처리에 시간이 걸릴 뿐 결과는 반드시 나온다(ISSUED든 FAILED든)"는 전제 위에서 설계되었다. 그런데 접수 응답과 실제 시스템 상태가 어긋나는 케이스가 하나라도 생기면, 이 비동기 구조 자체의 신뢰성이 무너진다.
```

#### 3. 이 상황에서 API Server가 주의해야 할 점

```
1) 발행 실패를 사용자에게 명확히 알려서 재시도를 유도해야 한다
2) requestId 처리 
  requestId는 Kafka에 정상적으로 실린 요청에 대해서만 의미가 있으므로, 발행 실패 시에는 상태 조회의 대상이 되는 requestId를 발급하지 않거나, 발급하더라도 "이 requestId는 유효하지 않다"는 점을 명확히 해야 한다.
```

## 과제 5. Partition Key 선택하기


### 1. Partition Key 후보별 장단점 비교

| Partition Key 후보 | 장점 | 단점 |
| --- | --- | --- |
| userId | 같은 사용자의 요청이 항상 같은 Partition에 들어가 순서 관리와 중복 요청 추적에 유리하다 | 특정 사용자가 비정상적으로 많은 요청을 보내면 일부 Partition에 쏠릴 수 있지만, 일반적인 이벤트에서는 사용자 수가 많아 상대적으로 위험이 낮다 |
| eventId | 같은 이벤트의 요청을 논리적으로 묶어서 보기 쉽다 | 선착순 이벤트 특성상 대부분의 요청이 eventId 하나에 몰리므로 사실상 단일 Partition에 쏠려 병렬 처리 이점이 거의 사라진다 |
| requestId | 요청마다 값이 달라 메시지가 Partition 전반에 고르게 분산된다 | 같은 사용자의 요청도 서로 다른 Partition에 흩어져 사용자 기준 순서 보장이 어렵고, 사용자 단위 중복 추적이 힘들어진다 |

### 2. 내가 선택한 Partition Key

```
userId
```

### 3. 선택한 이유

```
이 시스템의 비즈니스 규칙은 "사용자 1명당 쿠폰 1개"이다.
즉, 사용자 단위로 상태(발급 여부)를 추적하고 판단해야 하는 규칙이라는 뜻이다. 같은 사용자의 요청(정상 요청이든 실수로 여러 번 누른 중복 클릭이든)을 같은 Partition, 같은 Consumer가 순서대로 처리하게 만들면 향후 동시성 문제를 다룰 때 훨씬 유리한 출발점이 된다.
requestId를 Key로 쓰면, Race Condition의 위험성이 있어서 배제하였다.
```

### 4. 메시지 분산에 어떤 영향을 주는가?

```
이벤트에 참여하는 사용자 수가 충분히 많다면(예: 10만 건의 요청이 서로 다른 다수의 사용자에게서 온다면) userId 기준으로도 메시지가 여러 Partition에 비교적 고르게 퍼진다. 
eventId처럼 값이 하나로 고정되는 것과 달리 userId는 값 자체가 다양하므로 분산 효과를 기대할 수 있다.
```

### 5. 순서 보장에 어떤 영향을 주는가?

```
Kafka가 보장하는 순서는 항상 Partition 내부 순서이다.
같은 userId를 가진 메시지는 항상 같은 Partition에 들어가므로, 같은 사용자가 보낸 요청들 사이의 순서는 Kafka가 보장한다. 즉 "이 사용자의 요청 A가 먼저 왔고 B가 나중에 왔다"는 순서를 신뢰할 수 있다.
```

### 6. 특정 Partition에 메시지가 몰릴 가능성은 없는가?

```
이론적으로는 가능하다.
매크로나 어뷰징으로 특정 소수 사용자가 요청을 대량으로 반복 발송하면 해당 userId들이 매핑된 Partition에 부하가 집중될 수 있다. 
다만 일반적인 선착순 이벤트에서는 참여자 수 자체가 매우 많고 각 사용자의 요청 수는 제한적이므로, eventId를 Key로 쓸 때(정상적인 트래픽 패턴 자체)만큼 쏠림이 구조적으로 확정적이지는 않다.
```

### 7. 이 Key를 선택했을 때 발생할 수 있는 단점

```
같은 이벤트 전체를 하나의 흐름으로 순서대로 보고 싶은 경우(예: "이 이벤트에 대한 전체 요청을 시간순으로 처리하고 싶다")에는 userId Key로는 그 순서를 보장할 수 없다. 이벤트 전체 순서가 아니라 사용자별 부분 순서만 보장되기 때문이다.
```

### 8. eventId를 Partition Key로 사용할 때 주의해야 할 점

```
지금 진행 중인 이벤트가 사실상 하나(eventId=1)뿐이라면, Partition을 아무리 여러 개 만들어도 거의 모든 메시지가 같은 Key를 가지므로 실제로는 하나의 Partition만 바쁘게 일하게 된다. 결과적으로 Consumer를 여러 대 띄워도 대부분이 유휴 상태가 되어 병렬 처리 효과를 거의 얻지 못하고, Consumer Lag이 그 Partition 하나에 집중되는 문제가 생긴다.
```

### 9. Kafka는 어떤 단위에서 메시지 순서를 보장하는가? 서로 다른 Partition에 들어간 메시지 A, B의 전체 처리 순서는 보장되는가? 그 이유는?

```
Kafka에서 Partition은 각각이 완전히 독립된 로그 파일(append-only log)이다.
Kafka는 같은 Partition 내부에서만 메시지 순서를 보장한다. 서로 다른 Partition에 들어간 메시지 A, B 사이의 전체 순서는 보장되지 않는다. 각 Partition은 독립적으로 Offset이 관리되고, 서로 다른 Consumer가 서로 다른 속도로 각 Partition을 읽어가기 때문에, Partition을 넘나드는 전역적인 시간 순서를 Kafka가 강제할 방법이 없다. 순서 보장이 필요한 범위는 반드시 같은 Partition Key를 통해 같은 Partition으로 모아야 한다.
"전역 순서"라는 개념 자체를 지키려면 모든 메시지를 하나의 단일한 로그(Partition 1개)로만 관리해야 하는데, 그러면 애초에 병렬 처리라는 Kafka의 핵심 이점 자체가 사라진다.
```

## 과제 6. Consumer Group과 Partition 수 설계하기


### 1. Topic 이름

```
coupon.issue.requested
```

### 2. Partition 수

```
6개
```

### 3. Consumer Group 이름

```
coupon-issue-group
```

### 4. Consumer 수

```
6개 (초기), 트래픽에 따라 최대 6개까지 스케일 아웃
```

### 5. Partition과 Consumer 매핑

```
Partition 0 → Consumer 1
Partition 1 → Consumer 2
Partition 2 → Consumer 3
Partition 3 → Consumer 4
Partition 4 → Consumer 5
Partition 5 → Consumer 6
```

### 6. 이 구조를 선택한 이유

```
"Partition 수만큼 Consumer를 1:1로 매핑해 병렬 처리 효율을 최대로 끌어올린다"는 원칙에 맞춰 6개로 설정했다. Partition 수를 처음부터 여유 있게 잡아두면(예: 6개), 이후 트래픽이 늘어 Consumer를 추가로 늘리고 싶을 때 Partition 수 자체를 다시 늘리는 운영 부담 없이 Consumer 수만 최대 Partition 수까지 유연하게 조정할 수 있다.
```

### 7. Partition이 3개이고 Consumer가 5개라면 실제로 동시에 처리할 수 있는 Consumer는 최대 몇 개인가?

```
3개. 
같은 Consumer Group 안에서는 하나의 Partition을 동시에 두 개 이상의 Consumer가 처리할 수 없으므로, Partition 수가 병렬 처리의 상한선이 된다. 나머지 2개의 Consumer는 할당받을 Partition이 없어 유휴 상태로 대기한다.
```

### 8. Consumer 수가 Partition 수보다 많으면 어떤 일이 발생하는가?

```
Partition 수를 초과하는 Consumer는 어떤 Partition도 할당받지 못해 아무 일도 하지 않고 대기 상태가 된다. 리소스(서버, 스레드)만 낭비하고 실제 처리량 향상에는 기여하지 못한다.
```

### 9. Consumer 수가 Partition 수보다 적으면 어떤 일이 발생하는가?

```
한 Consumer가 여러 Partition을 동시에 담당하게 된다. 이 경우 해당 Consumer의 처리 부담이 커지고, 여러 Partition을 순회하며 처리해야 하므로 특정 Partition의 메시지 처리가 상대적으로 지연될 수 있다.
```

### 10. Consumer 수만 무작정 늘리면 안 되는 이유는 무엇인가?

```
병렬 처리의 실제 상한은 Partition 수이기 때문이다. Partition 수를 늘리지 않은 채 Consumer만 늘리면 초과분은 그냥 놀게 되어 처리량 개선 효과가 없고, 인프라 비용만 늘어난다. 처리량을 늘리려면 Consumer 수와 함께 Partition 수도 같이 재설계해야 한다.
```

## 과제 7. Offset Commit 실패 상황 분석하기

### 1. Consumer가 다시 실행되면 어떤 메시지를 다시 읽을 수 있는가?

```
  DB 저장까지는 성공했지만 Offset Commit이 되지 않은 바로 그 메시지를, 마지막으로 성공적으로 Commit된 Offset 이후부터 다시 읽게 된다.
 핵심은 Consumer가 "무엇을 처리했는지"와 "무엇을 Commit했는지"가 서로 다른 정보라는 점이다. Consumer 입장(애플리케이션 로직)에서는 이미 t2에서 DB 저장까지 끝냈으니 "이 메시지는 처리 완료됐다"고 알고 있다. 하지만 재시작된 새 Consumer 프로세스는 이전 프로세스의 메모리 상태(어디까지 처리했는지)를 전혀 알지 못한다. 
```

### 2. Kafka 입장에서는 왜 이 메시지가 처리 완료되었다고 판단하지 못하는가?

```
Kafka는 Consumer가 DB에 무엇을 저장했는지는 알지 못한다. Kafka가 "처리 완료"를 판단하는 유일한 근거는 Offset Commit 여부다. Commit이 기록되지 않았다면 Kafka 입장에서는 해당 메시지가 아직 안전하게 처리되지 않은 것으로 간주할 수밖에 없다.
```

### 3. 이 상황에서 같은 메시지가 다시 처리될 수 있는가?

```
가능하다. Consumer가 재시작되면서 마지막 Commit 지점부터 다시 읽기 때문에, 이미 DB 저장까지 끝났던 메시지를 다시 읽어 다시 처리 로직을 수행하게 된다.
Kafka의 at-least-once 전달 모델에서 구조적으로 항상 발생 가능한 상황이기 때문에 그 이후 대응(멱등성 처리)을 설계하는 것이 중요하다.
```

### 4. 같은 메시지가 다시 처리되면 쿠폰 발급 시스템에서는 어떤 문제가 생길 수 있는가?

```
같은 사용자에게 같은 쿠폰이 중복으로 발급되거나, 이미 차감된 재고 수량이 한 번 더 차감되는 문제가 생길 수 있다. "사용자 1명당 쿠폰 1개"라는 발급 조건이 깨지고, 실제 발급 수량이 이벤트에서 정한 1,000개를 초과할 수도 있다.
```

### 5. 이 문제를 해결하려면 나중에 어떤 장치가 필요할 수 있는가?

아래 키워드를 참고해서 작성한다.

```
DB Unique Key

requestId 기반 멱등성

처리 상태 저장

중복 메시지 방어
```

답변:

```
같은 메시지가 다시 처리되더라도 결과가 달라지지 않도록 만드는 멱등성 장치가 필요하다. 예를 들어 (eventId, userId) 조합에 DB Unique Key를 걸어 두 번째 INSERT 시도가 DB 레벨에서 거부되도록 하거나, requestId를 기준으로 "이미 처리된 요청인지"를 먼저 확인하는 requestId 기반 멱등성 처리를 둘 수 있다. 또한 요청 처리 상태를 별도로 저장해두고 재처리 전에 상태를 먼저 조회해서 이미 ISSUED라면 중복 처리를 건너뛰는 방식(처리 상태 저장 + 중복 메시지 방어)도 함께 고려할 수 있다. 
```

## 과제 8. Consumer Lag이 생겼을 때 사용자 경험 설계하기

### 1. Consumer Lag이란 무엇인가?

```
Consumer Lag은 특정 Partition에 최신까지 쌓인 메시지 위치(log-end-offset)와 Consumer Group이 실제로 처리 완료했다고 커밋한 Offset 사이의 차이다. 즉 Consumer가 아직 처리하지 못하고 밀려 있는 메시지의 개수를 의미한다.
```

### 2. Consumer Lag이 증가하면 사용자 경험에 어떤 영향이 있는가?

```
사용자는 요청 접수 응답은 빠르게 받지만, 실제 발급 여부(ISSUED/FAILED)를 확인할 수 있기까지의 시간이 점점 길어진다. 마이페이지에 쿠폰이 늦게 뜨고, 결과 조회 API를 여러 번 호출해도 계속 PENDING 상태로 남아 사용자가 "요청이 실패한 게 아닌가" 하는 불안을 느낄 수 있다.
```

### 3. 요청 직후 사용자에게 줄 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 결과는 잠시 후 확인해주세요.",
  "requestId":"req-20260702-abc123"
}
```

### 4. 결과 조회 API에서 PENDING 상태일 때 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 처리 중입니다. 조금만 더 기다려주세요.",
  "requestId": "req-20260702-abc123"
}
```

### 5. 발급 성공 시 응답 JSON

```json
{
  "status": "ISSUED",
  "message": "쿠폰이 발급되었습니다.",
  "requestId": "req-20260702-abc123"
}
```

### 6. 발급 실패 시 응답 JSON

```json
{
  "status": "FAILED",
  "message": "쿠폰이 모두 소진되어 발급에 실패했습니다.",
  "requestId": "req-20260702-abc123"
}
```

### 7. 운영자가 Consumer Lag을 보고 어떤 판단을 할 수 있는가?

```
Lag이 계속 늘어나기만 하고 줄어들지 않는다면 Consumer의 처리량이 유입되는 메시지 양을 따라가지 못하고 있다는 신호로 판단할 수 있다. 이 경우 운영자는 Consumer 인스턴스를 추가로 늘리거나(단, Partition 수 한도 내에서), Consumer 로직 자체의 처리 속도(DB 쿼리 최적화 등)를 점검해야 한다는 결론을 내릴 수 있다. 반대로 Lag이 특정 Partition에만 몰려 있다면 Partition Key 설계(쏠림) 문제일 가능성을 의심할 수 있다.
```

### 8. Kafka를 사용해도 최종 발급 결과가 늦어질 수 있는 이유

```
Kafka는 API Server의 응답 속도를 빠르게 만들어줄 뿐, 시스템 전체의 처리 용량을 무한히 늘려주지는 않는다. Producer가 메시지를 발행하는 속도가 Consumer가 실제로 처리하는 속도보다 빠르면 메시지는 Kafka에 계속 쌓이기만 하고, Consumer가 이를 소진하는 데 시간이 걸린다. 즉 병목이 API Server/DB에서 Consumer 쪽으로 옮겨갈 뿐, 병목 자체가 사라지는 것은 아니기 때문에 최종 결과 확인은 여전히 지연될 수 있다.
```

## 과제 9. 나쁜 Kafka 설계의 문제점 찾기


### 문제점과 개선 방향

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| Partition이 1개뿐이다 | Consumer를 아무리 여러 대 띄워도 같은 Partition을 동시에 처리할 수 있는 Consumer는 1개뿐이라 병렬 처리가 전혀 되지 않는다. 10만 건 트래픽을 사실상 Consumer 1대가 순차로 처리해야 한다 | Partition 수를 늘려(예: 6~10개) Consumer가 여러 개 붙어 병렬로 처리할 수 있도록 설계한다 |
| Consumer가 1개뿐이다 | 위와 맞물려서, 단일 Consumer가 모든 메시지를 처리해야 하므로 처리량이 매우 낮고 Consumer 장애 시 전체 처리가 완전히 멈춘다 | Partition 수를 늘린 뒤 Consumer Group 안에 여러 Consumer를 두어 병렬 처리 및 장애 시 다른 Consumer가 이어받도록 한다 |
| Partition Key로 eventId를 사용하고 대부분 요청이 eventId=1이다 | 거의 모든 메시지가 같은 Key를 가지므로 Partition을 여러 개 만들어도 사실상 하나의 Partition에만 몰린다. 병렬 처리 이점이 사라지고 Consumer Lag이 특정 Partition에 집중된다 | userId처럼 값이 다양하게 분산되는 Key로 변경하거나, eventId를 쓰더라도 사용자 단위 서브 파티셔닝(예: eventId+userId 해시)을 함께 고려한다 |
| Kafka 발행 실패해도 요청 접수 성공 응답을 준다 | 실제로는 메시지가 Topic에 들어가지 않았는데 사용자는 접수됐다고 믿는다. Consumer가 읽을 메시지 자체가 없으므로 이 요청은 영원히 처리되지 않고 조용히 유실된다 | 발행 성공을 확인한 뒤에만 접수 성공 응답을 주고, 실패 시에는 FAILED 응답과 재시도 안내를 준다 |
| DB 저장 후 Offset Commit 전에 죽는 상황을 고려하지 않았다 | 이 경우 Consumer 재시작 시 같은 메시지를 다시 읽어 중복 처리하게 되고, 같은 사용자에게 쿠폰이 두 번 발급되거나 재고가 이중 차감될 수 있다 | DB Unique Key(예: eventId+userId 조합)나 requestId 기반 멱등성 처리를 두어 같은 메시지가 재처리되어도 결과가 달라지지 않도록 만든다 |
| Consumer Lag이 증가해도 사용자는 처리 상태를 확인할 수 없다 | 사용자는 요청이 실패했는지, 처리 중인지 전혀 알 수 없어 불안해하거나 중복으로 재요청을 시도할 수 있다. 이는 시스템 부하를 더 키우는 악순환으로 이어진다 | PENDING/ISSUED/FAILED 상태를 저장하는 조회 API(또는 마이페이지)를 제공해 사용자가 언제든 자신의 요청 상태를 확인할 수 있게 한다 |
| Consumer 처리 실패 시 재시도/DLQ 처리가 없다 | 일시적 오류(DB 커넥션 문제 등)로 처리에 실패한 메시지가 그냥 유실되거나 무한 재시도로 다른 메시지 처리를 막을 수 있다 | 재시도 Topic이나 DLQ(Dead Letter Queue)를 두어 실패한 메시지를 별도로 격리하고 추후 재처리하거나 운영자가 확인할 수 있도록 한다 |
