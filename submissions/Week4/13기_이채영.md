## **과제 1. DB 최종 발급 처리 구조 그리기**

Redis 판정을 통과한 요청이 Kafka를 거쳐 DB에 최종 저장되는 전체 구조를 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka

Coupon Issue Consumer

coupon_event

coupon_issue
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | 1. 쿠폰 발급 요청
  v
API Server
  |
  | 2. 사용자 인증 및 쿠폰 이벤트 기본 검증
  v
Redis
  |
  | 3. 사용자 중복 요청과 잔여 수량을 원자적으로 판정
  |
  | Redis ACCEPTED
  v
API Server
  |
  | 4. Redis 판정을 통과한 요청만 Kafka에 발행
  v
Kafka
  |
  | Topic: coupon.issue.requested
  | 5. 쿠폰 발급 요청 메시지 전달
  v
Coupon Issue Consumer
  |
  | 6. Kafka 메시지 소비
  v
DB Transaction 시작
  |
  | 7. 수량이 남아 있을 때
  |    coupon_event.issued_count를 1 증가
  v
coupon_event
  |
  | 8. UPDATE에 성공한 경우
  |    coupon_issue에 발급 기록 저장
  v
coupon_issue
  |
  | 9. 두 작업이 모두 성공하면 Commit
  v
DB ISSUED
  |
  | 10. Consumer Group Offset Commit
  v
최종 발급 처리 완료
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
- Redis 판정 통과 후 Kafka 메시지 발행이 실패할 수 있다.
- Kafka에 메시지가 발행되었지만 Consumer가 메시지를 처리하지 못할 수 있다.
- Consumer가 메시지를 처리하는 도중 DB 오류가 발생할 수 있다.
- coupon_event의 수량 증가 또는 coupon_issue의 발급 기록 저장이 실패할 수 있다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
- Consumer가 메시지를 아직 읽지 않았을 수 있다.
- Consumer가 메시지를 읽은 후 처리 중 장애가 발생할 수 있다.
- DB의 쿠폰 수량이 이미 모두 소진되었을 수 있다.
- 동일한 사용자의 발급 기록이 이미 존재할 수 있다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
- coupon_event.issued_count 증가 성공
- coupon_issue 발급 기록 INSERT 성공
- DB Transaction Commit 성공
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계**          | **의미**                                                         | **최종 발급 성공 여부** |
|-----------------|----------------------------------------------------------------|-----------------|
| Redis ACCEPTED  | Redis를 기준으로 사용자 중복 요청과 남은 수량 검사를 통과한 상태이다.                     | 아니요             |
| Kafka PUBLISHED | 쿠폰 발급 요청 메시지가 Kafka Topic에 정상적으로 발행된 상태이다.                     | 아니요             |
| DB ISSUED       | `issued_count` 증가와 `coupon_issue` 저장이 하나의 트랜잭션으로 Commit된 상태이다. | 예               |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

쿠폰 발급 시스템이 장애와 동시 요청 상황에서도 지켜야 하는 조건을 불변식으로 정의한다.

이번 과제에서는 다음 세 가지 불변식을 기준으로 작성한다.

```
불변식 1.

한 사용자는 하나의 이벤트에서
쿠폰을 최대 한 번만 발급받는다.

불변식 2.

발급 수량은 0보다 작거나
전체 수량보다 많을 수 없다.

불변식 3.

issued_count 증가와 coupon_issue 저장은
함께 성공하거나 함께 실패한다.
```

### **1. 불변식이 필요한 이유**

```
- 장애나 동시 요청이 발생해도 쿠폰 발급 데이터의 일관성을 유지하기 위해 필요하다.
- 사용자 중복 발급과 전체 수량 초과를 방지하기 위해 필요하다.
- 발급 수량과 발급 기록이 항상 일치하도록 보장하기 위해 필요하다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식**             | **깨졌을 때 발생하는 문제**                       |
|---------------------|-----------------------------------------|
| 사용자별 최대 1회 발급       | 같은 사용자가 하나의 이벤트에서 쿠폰을 여러 번 발급받을 수 있다.   |
| 전체 수량 이하 발급         | 발급 수량이 전체 쿠폰 수량을 초과하여 쿠폰이 과발급될 수 있다.    |
| 수량과 발급 기록의 동시 성공·실패 | 발급 수량과 발급 기록이 서로 일치하지 않는 데이터 불일치가 발생한다. |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식**      | **DB 방어 장치**                |
|--------------|-----------------------------|
| 사용자 중복 발급 방지 | `UNIQUE(event_id, user_id)` |
| 전체 수량 초과 방지  | 조건부 `UPDATE`, `CHECK` 제약    |
| 두 테이블의 일관성   | DB Transaction              |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
- 두 요청이 동시에 발급 기록을 조회하면 모두 기존 기록이 없다고 판단할 수 있다.
- 두 요청이 동시에 INSERT를 수행하면 중복 발급이 발생할 수 있다.
- 따라서 최종 중복 방지는 DB의 UNIQUE 제약이 담당해야 한다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

쿠폰 이벤트와 최종 발급 기록을 저장할 테이블을 설계한다.

완전한 운영용 스키마를 만드는 것이 목적은 아니다. 이번 주차에서 필요한 불변식을 지킬 수 있도록 핵심 컬럼과 제약 조건을 작성한다.

### **1. coupon_event 테이블의 역할**

```
- 쿠폰 이벤트 정보를 저장한다.
- 이벤트별 전체 발급 가능 수량을 저장한다.
- DB 기준 최종 발급 수량(issued_count)을 저장한다.
- 이벤트 기간과 상태를 관리한다.
```

### **2. coupon_issue 테이블의 역할**

```
- 최종 발급에 성공한 사용자별 쿠폰 발급 기록을 저장한다.
- 어떤 사용자가 어떤 이벤트의 쿠폰을 발급받았는지 관리한다.
- 동일 사용자의 중복 발급을 방지한다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
+----------------------+
| coupon_event         |
|----------------------|
| id                   |
| name                 |
| total_quantity       |
| issued_count         |
| start_at             |
| end_at               |
| status               |
| version              |
+----------------------+
          |
          | 1 : N
          |
          v
+----------------------+
| coupon_issue         |
|----------------------|
| id                   |
| event_id             |
| user_id              |
| status               |
| issued_at            |
+----------------------+
```

### **4. coupon_event 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

name

total_quantity

issued_count

start_at

end_at

status

version (낙관적 락을 선택할 경우)

수량 CHECK 제약

이벤트 기간 CHECK 제약
```

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count INT NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

### **5. coupon_issue 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

event_id

user_id

status

issued_at

coupon_event를 참조하는 Foreign Key

동일 이벤트의 사용자 중복 발급을 막는 UNIQUE 제약
```

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
- 남은 쿠폰 수량을 빠르게 확인할 수 있다.
- DB 기준 발급 현황을 빠르게 조회할 수 있다.
- Redis와 DB의 발급 수량을 비교할 수 있다.
- DB에서 전체 수량 초과를 다시 방어할 수 있다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

`UNIQUE(event_id, user_id)`가 어떤 문제를 막고, 어떤 문제는 막지 못하는지 분석한다.

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
- 같은 사용자는 하나의 쿠폰 이벤트에서 쿠폰을 한 번만 발급받을 수 있다.
- 동일한 event_id와 user_id 조합은 coupon_issue 테이블에 중복 저장될 수 없다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 다음과 같다.

```
event_id = 100
user_id = 10
```

| **새로운 INSERT**           | **성공 또는 실패** | **이유**                                                  |
|--------------------------|--------------|---------------------------------------------------------|
| event_id=100, user_id=10 | 실패           | 동일한 `(event_id, user_id)` 조합이 이미 존재하므로 UNIQUE 제약을 위반한다. |
| event_id=100, user_id=11 | 성공           | event_id는 같지만 user_id가 다르므로 중복 조합이 아니다.                 |
| event_id=101, user_id=10 | 성공           | user_id는 같지만 event_id가 다르므로 중복 조합이 아니다.                 |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

아래 상황을 시간 순서로 표현한다.

```
Transaction A가 user:10의 발급 기록을 조회한다.

Transaction B도 user:10의 발급 기록을 조회한다.

두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

두 트랜잭션이 동시에 INSERT를 시도한다.
```

답변:

```
- Transaction A가 user:10의 발급 기록을 조회한다.
- Transaction B도 user:10의 발급 기록을 조회한다.
- 두 트랜잭션 모두 기존 발급 기록이 없다고 판단한다.
- Transaction A가 발급 기록을 INSERT한다.
- Transaction B도 같은 발급 기록을 INSERT한다.
- UNIQUE 제약이 없다면 같은 사용자의 중복 발급 기록이 저장될 수 있다.
- 따라서 사전 SELECT만으로는 중복 발급을 안전하게 방지할 수 없다.
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

아래 상황을 기준으로 설명한다.

```
전체 수량: 1,000개

서로 다른 사용자: 1,001명

모든 (event_id, user_id) 조합은 서로 다름
```

```
- UNIQUE 제약은 동일한 event_id와 user_id 조합의 중복만 방지한다.
- 서로 다른 사용자 1,001명이 요청하면 모든 `(event_id, user_id)` 조합이 다르다.
- 전체 쿠폰 수량이 1,000개여도 1,001개의 INSERT가 UNIQUE 제약을 모두 통과할 수 있다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제**                 | **DB 방어 장치**                |
|------------------------|-----------------------------|
| 같은 사용자의 중복 발급          | `UNIQUE(event_id, user_id)` |
| 서로 다른 사용자에 의한 전체 수량 초과 | `issued_count` 조건부 `UPDATE` |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

쿠폰 수량이 남아 있을 때만 `issued_count`를 증가시키는 조건부 UPDATE를 설계한다.

### **1. 조건부 UPDATE SQL 작성하기**

다음 조건을 만족해야 한다.

```
event_id가 일치해야 한다.

issued_count가 total_quantity보다 작을 때만 증가해야 한다.

issued_count는 1 증가해야 한다.
```

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :event_id
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
- 영향받은 row 수는 조건부 UPDATE의 조건을 만족하여 실제로 수정된 행의 개수를 의미한다.
- 영향받은 row 수가 1이면 수량 증가에 성공한 것이다.
- 영향받은 row 수가 0이면 조건을 만족하는 이벤트가 없어 수량 증가에 실패한 것이다.
```

### **3. 영향받은 row 수가 1인 경우**

```
- event_id에 해당하는 이벤트가 존재한다.
- issued_count가 total_quantity보다 작다.
- issued_count가 1 증가했다.
- 해당 요청은 발급 기록 INSERT를 진행할 수 있다.
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

과제 5-1의 SQL은 `event_id`와 수량 조건만 사용한다. 중복 메시지 여부는 UPDATE 결과가 0인 직접 원인이 아니라, 이후 기존 발급 기록을 조회해 구분한다.

```
1. event_id에 해당하는 이벤트가 존재하지 않는다.

2. issued_count가 total_quantity와 같아 쿠폰 수량이 모두 소진되었다.
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

과제 5-1에서 작성한 조건부 UPDATE를 사용한다고 가정한다.

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과**                        |
|--------|------------------|--------------------|---------------|----------------|-------------------------------|
| A      | 999              | 1,000              | 존재            | 1              | `issued_count`가 1,000으로 증가한다. |
| B      | 1,000            | 1,000              | 존재            | 0              | 수량이 모두 소진되어 증가하지 않는다.         |
| C      | -                | -                  | 존재하지 않음       | 0              | 해당 이벤트가 없어 증가하지 않는다.          |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전체 수량: 1,000개

현재 issued_count: 999

Transaction A와 Transaction B가
동시에 조건부 UPDATE 실행
```

두 트랜잭션의 실행 결과를 시간 순서 다이어그램으로 작성한다.

```
초기 상태
coupon_event.issued_count = 999
coupon_event.total_quantity = 1,000

Transaction A                         Transaction B
      |                                     |
      | 조건부 UPDATE 실행                   | 조건부 UPDATE 실행
      v                                     v
이벤트 row의 락 획득                     이벤트 row의 락 대기
      |
issued_count: 999 → 1,000
영향받은 row 수: 1
      |
    Commit
                                            |
                                            | 락 획득 후 조건 재확인
                                            v
                                 issued_count = total_quantity
                                 조건 불충족
                                 영향받은 row 수: 0
                                            |
                                          Commit

최종 issued_count = 1,000
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
- 조건부 UPDATE는 issued_count가 total_quantity보다 작은 경우에만 수량을 증가시킨다.
- 동시에 여러 트랜잭션이 요청하더라도 같은 이벤트 row의 UPDATE는 순차적으로 처리된다.
- 먼저 실행된 트랜잭션이 마지막 수량을 증가시키면 이후 트랜잭션은 변경된 값을 기준으로 조건을 다시 검사한다.
- issued_count와 total_quantity가 같아지면 조건을 만족하지 않으므로 이후 UPDATE의 영향받은 row 수는 0이 된다.
- 따라서 issued_count는 total_quantity를 초과할 수 없다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

다음 두 작업을 하나의 DB 트랜잭션으로 묶는 이유를 설명한다.

```
1. coupon_event.issued_count 증가

2. coupon_issue 발급 기록 INSERT
```

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황**                                     | **발생하는 데이터 불일치**                                 |
|--------------------------------------------|--------------------------------------------------|
| issued_count 증가 성공, coupon_issue INSERT 실패 | 실제 발급 기록은 없지만 발급 수량만 증가하여 수량이 더 많이 차감된다.         |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 실제 발급 기록은 존재하지만 발급 수량에는 반영되지 않아 전체 수량을 초과할 수 있다. |


### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
- DB Transaction 시작
- 조건부 UPDATE로 coupon_event.issued_count 증가 시도
- 영향받은 row 수가 1인지 확인
- 영향받은 row 수가 1이면 coupon_issue 발급 기록 INSERT
- UPDATE와 INSERT가 모두 성공하면 Commit
- UPDATE 또는 INSERT 중 하나라도 실패하면 Rollback
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :event_id
  AND issued_count < total_quantity;

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
) VALUES (
    :event_id,
    :user_id,
    'ISSUED',
    CURRENT_TIMESTAMP
);

-- 두 작업이 모두 성공하면 Commit
COMMIT;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

아래 항목을 모두 설명한다.

```
현재 트랜잭션은 어떻게 되는가?

앞에서 증가한 issued_count는 어떻게 되는가?

기존 발급 기록은 언제 조회해야 하는가?
```

답변:

```
- coupon_issue INSERT에서 UNIQUE 제약 위반이 발생하면 현재 트랜잭션은 실패 상태가 된다.
- 트랜잭션 전체를 Rollback해야 한다.
- 앞에서 증가한 issued_count도 Rollback되어 증가 이전 값으로 돌아간다.
- Rollback이 완료된 후 별도의 조회를 통해 기존 coupon_issue 발급 기록을 확인해야 한다.
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
- PostgreSQL에서는 트랜잭션 내부에서 제약 조건 위반이 발생하면 해당 트랜잭션이 실패 상태가 된다.
- 실패 상태가 된 트랜잭션에서는 일반 SQL을 계속 실행할 수 없다.
- 이후 명령은 현재 트랜잭션이 중단되었다는 오류가 발생한다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
- issued_count 증가와 coupon_issue INSERT의 원자성을 항상 보장하기 위해 필요하다.
- 일부 발급 경로에서 두 작업을 따로 처리하면 수량과 발급 기록이 불일치할 수 있다.
- API, Kafka Consumer, 관리자 발급 등 모든 발급 경로가 동일한 트랜잭션 규칙을 사용해야 한다.
- 이를 통해 발급 수량과 실제 발급 기록이 항상 함께 성공하거나 함께 실패하도록 보장할 수 있다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

Kafka Consumer는 같은 메시지를 다시 처리할 수 있다.

아래 상황을 기준으로 분석한다.

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.
```

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
Consumer가 Kafka 메시지 읽기
        |
        v
DB 발급 트랜잭션 실행
        |
        v
issued_count 증가
        |
        v
coupon_issue 발급 기록 INSERT
        |
        v
DB Transaction Commit
        |
        v
Consumer Group Offset 커밋 전 Consumer 종료
        |
        v
Consumer 재시작
        |
        v
커밋되지 않은 Offset부터 메시지 다시 읽기
        |
        v
같은 발급 요청 메시지 재처리
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
- 같은 메시지가 다시 처리될 때 동일한 사용자의 발급 기록이 중복 저장될 수 있다.
- coupon_event의 issued_count가 다시 증가할 수 있다.
- 하나의 사용자가 같은 이벤트에서 쿠폰을 여러 번 발급받을 수 있다.
- 발급 수량과 실제 사용자 수가 일치하지 않을 수 있다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
- 첫 번째 처리에서 coupon_issue에 발급 기록이 저장된다.
- 같은 Kafka 메시지가 다시 소비된다.
- 조건부 UPDATE로 issued_count가 증가한다.
- 동일한 event_id와 user_id로 coupon_issue INSERT를 시도한다.
- UNIQUE 제약 위반이 발생한다.
- 발급 트랜잭션 전체가 Rollback된다.
- 앞에서 증가한 issued_count도 원래 값으로 돌아간다.
- 따라서 중복 발급 기록과 수량 증가를 모두 방지할 수 있다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
- UNIQUE 위반의 원인이 coupon_issue의 UNIQUE(event_id, user_id) 제약이어야 한다.
- Rollback 후 동일한 event_id와 user_id의 발급 기록이 실제로 존재해야 한다.
- 기존 발급 기록이 정상적으로 최종 발급된 기록이어야 한다.
- 다른 제약 조건 위반이나 DB 장애는 이미 처리된 메시지로 판단하면 안 된다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. UNIQUE 제약 위반이 발생한 현재 트랜잭션을 Rollback한다.

2. 새로운 트랜잭션에서 동일한 event_id와 user_id의 기존 발급 기록을 조회한다.

3. 기존 발급 기록이 존재하면 이미 처리된 메시지로 판단하여 처리를 완료한다.

4. 메시지 처리가 완료된 후 Consumer Group Offset을 커밋한다.
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
- Offset을 먼저 커밋한 뒤 DB 저장에 실패하면 Kafka에서는 해당 메시지를 처리한 것으로 기록된다.
- Consumer가 재시작되어도 해당 메시지를 다시 읽지 않는다.
- Redis와 Kafka에는 요청이 통과했지만 DB에는 최종 발급 기록이 저장되지 않을 수 있다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
- UNIQUE(event_id, user_id)는 동일한 사용자가 같은 이벤트의 쿠폰을 중복 발급받는 것을 방지한다.
- requestId 기반 멱등성은 동일한 요청이 여러 번 전달되더라도 한 번만 처리되도록 보장한다.
- 서로 다른 requestId를 사용한 동일 사용자의 중복 발급은 UNIQUE(event_id, user_id)가 방지한다.
- 같은 requestId가 다시 전달되는 중복 요청은 requestId 기반 멱등성이 식별한다.
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

조건부 UPDATE를 먼저 실행하는 구조에서는 중복 메시지가 항상 INSERT까지 도달하는 것은 아니다.

아래 상황을 기준으로 분석한다.

```
이벤트 ID: 100

전체 수량: 1개

현재 issued_count: 1

coupon_issue에
(event_id=100, user_id=10) 기록이 이미 존재

user:10의 Kafka 메시지가 다시 전달됨
```

### **1. 조건부 UPDATE 결과와 그 이유**

```
- 영향받은 row 수는 0이다.
- 현재 issued_count와 total_quantity가 모두 1이므로 issued_count < total_quantity 조건을 만족하지 않는다.
```

### **2. coupon_issue INSERT까지 실행되는가?**

```
- 실행되지 않는다.
- 조건부 UPDATE의 영향받은 row 수가 0이므로 발급 기록 INSERT 단계로 진행하지 않는다.
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```
- 발생하지 않는다.
- coupon_issue INSERT 자체가 실행되지 않기 때문에 UNIQUE 제약을 검사하지 않는다.
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```
- 동일한 사용자의 메시지가 이미 처리된 후 다시 전달된 경우에도 UPDATE 결과가 0이 될 수 있다.
- 따라서 UPDATE 결과가 0이라는 사실만으로 신규 요청의 품절 실패인지 중복 메시지 재처리인지 구분할 수 없다.
```

```
- 기존 발급 기록이 없다면 실제 품절로 인해 처리되지 못한 요청으로 판단할 수 있다.
```

## **과제 9. DB 동시성 제어 방식 비교하기**

다음 세 가지 방식으로 쿠폰 수량을 제어할 수 있다.

```
조건부 UPDATE

비관적 락

낙관적 락
```

### **1. 조건부 UPDATE 방식 설명**

```
- 수량이 남아 있는 경우에만 issued_count를 증가시키도록 UPDATE 조건을 설정한다.
- UPDATE 한 번으로 수량 확인과 증가를 처리한다.
- 영향받은 row 수를 통해 성공 여부를 판단한다.
- 동시에 요청이 들어와도 DB가 같은 row의 UPDATE를 순차적으로 처리하므로 수량 초과를 방지할 수 있다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
BEGIN;

SELECT issued_count, total_quantity
FROM coupon_event
WHERE id = :event_id
FOR UPDATE;

UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :event_id;

COMMIT;
```

설명:

```
- SELECT FOR UPDATE로 이벤트 row에 배타적 락을 획득한다.
- 먼저 락을 획득한 트랜잭션이 끝날 때까지 다른 트랜잭션은 대기한다.
- 락을 획득한 상태에서 잔여 수량을 확인하고 issued_count를 증가시킨다.
- 동시 요청을 안전하게 처리할 수 있지만 대기 시간이 길어질 수 있다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :event_id
  AND issued_count < total_quantity
  AND version = :current_version;
```

설명:

```
- 데이터를 조회할 때 version 값을 함께 확인한다.
- UPDATE 시 조회했던 version과 현재 version이 같은 경우에만 수정한다.
- 다른 트랜잭션이 먼저 수정하면 version이 변경되어 UPDATE의 영향받은 row 수가 0이 된다.
- 충돌이 발생한 요청은 최신 데이터를 다시 조회한 뒤 재시도해야 한다.
```

### **4. 세 방식 비교표**

| **구분**      | **조건부 UPDATE**                       | **비관적 락**              | **낙관적 락**              |
|-------------|--------------------------------------|------------------------|------------------------|
| 수량을 보호하는 방법 | 수량 조건을 포함한 UPDATE를 원자적으로 실행          | row를 잠근 후 수량 확인 및 증가   | version이 일치할 때만 UPDATE |
| 충돌 시 동작     | 한 요청만 조건을 통과하고 나머지는 영향받은 row 수가 0이 됨 | 다른 트랜잭션이 락 해제까지 대기     | version 불일치로 UPDATE 실패 |
| 재시도 필요 여부   | 일반적으로 필요 없음                          | 일반적으로 필요 없음            | 충돌 시 필요함               |
| 장점          | SQL이 단순하고 처리 과정이 짧음                  | 처리 흐름이 명확하고 데이터 보호가 강함 | 충돌이 적을 때 락 대기가 없음      |
| 단점          | 하나의 row에 요청이 집중되면 경합 발생              | 락 대기와 교착 상태가 발생할 수 있음  | 충돌이 많으면 재시도가 반복됨       |
| 선착순 이벤트 적합성 | 높음                                   | 가능하지만 처리량이 낮아질 수 있음    | 충돌이 많아 적합성이 낮음         |


### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
- 모든 요청이 동일한 coupon_event row를 수정하려고 한다.
- 해당 row에 락 경합이 발생하여 요청이 순차적으로 처리된다.
- 요청 수가 많아지면 대기 시간이 증가하고 DB 처리량이 감소할 수 있다.
- 특정 이벤트 row가 전체 발급 처리의 병목 지점이 될 수 있다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
- 수량 확인과 증가를 하나의 SQL로 처리할 수 있다.
- 별도의 SELECT나 명시적인 락 획득 과정이 필요하지 않다.
- 영향받은 row 수로 발급 가능 여부를 바로 판단할 수 있다.
- 낙관적 락처럼 충돌할 때 애플리케이션에서 반복 재시도할 필요가 적다.
- 선착순 이벤트처럼 충돌이 많은 환경에서 비교적 단순하게 수량 초과를 방지할 수 있다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```
- 조건부 UPDATE, 비관적 락, 낙관적 락은 전체 쿠폰 수량이 초과되지 않도록 보호한다.
- UNIQUE(event_id, user_id)는 동일한 사용자가 같은 이벤트에서 중복 발급받는 것을 방지한다.
- 수량 제어 방식만으로는 사용자 중복 발급을 막을 수 없다.
- UNIQUE 제약만으로는 서로 다른 사용자에 의한 전체 수량 초과를 막을 수 없다.
- 따라서 전체 수량 제어 방식과 UNIQUE 제약을 함께 사용해야 한다.
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

Redis, Kafka, DB는 서로 다른 시스템이므로 상태가 일시적으로 달라질 수 있다.

Kafka 상태는 발행된 레코드의 존재 여부와 Consumer Group Offset 커밋 여부를 구분해서 작성한다. Kafka 레코드가 존재한다는 사실만으로 처리 대기 상태라고 판단하지 않는다.

### **1. Redis 통과 후 Kafka 발행 실패 상황**

아래 세 시스템에 남는 상태를 작성한다.

| **시스템** | **남아 있는 상태**           |
|---------|------------------------|
| Redis   | 발급 가능으로 판정한 상태가 남아 있다. |
| Kafka   | 발급 요청 메시지가 존재하지 않는다.   |
| DB      | 최종 발급 기록이 존재하지 않는다.    |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태**                                                           |
|---------|------------------------------------------------------------------------|
| Redis   | 발급 가능으로 판정한 상태가 남아 있다.                                                 |
| Kafka   | 발급 요청 레코드는 존재하지만 DB 저장은 완료되지 않았으며 Consumer Group Offset도 커밋되지 않을 수 있다. |
| DB      | 최종 발급 기록이 존재하지 않는다.                                                    |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태**             |
|---------|--------------------------|
| Redis   | 발급 가능 판정 데이터가 유실될 수 있다.  |
| DB      | 최종 발급 기록이 정상적으로 저장되어 있다. |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
- Redis는 발급 가능 여부를 빠르게 판단하기 위한 시스템이다.
- Kafka는 발급 요청을 전달하기 위한 메시지 시스템이다.
- 두 시스템은 일시적으로 DB와 상태가 달라질 수 있다.
- DB에 발급 기록이 저장되고 Commit된 상태만 최종 발급 성공으로 판단해야 한다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분**     | **Redis**      | **Kafka**      | **DB**            |
|------------|----------------|----------------|-------------------|
| 주 역할       | 발급 가능 여부 판단    | 발급 요청 전달       | 최종 발급 기록 저장       |
| 저장하는 상태    | 임시 판정 정보       | 발급 요청 메시지      | 최종 발급 결과          |
| 성공이 의미하는 것 | 발급 가능 판정 성공    | 메시지 전달 성공      | 최종 발급 성공          |
| 강점         | 매우 빠른 조회와 처리   | 안정적인 메시지 전달    | 최종 데이터의 정합성 보장    |
| 한계         | 최종 발급을 보장하지 않음 | 최종 발급을 보장하지 않음 | 처리 속도가 Redis보다 느림 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
- 동일한 요청이 여러 번 전달되어도 한 번만 처리되도록 보장한다.
- 재시도나 네트워크 오류로 인한 중복 요청을 안전하게 처리한다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
- DB 저장과 Kafka 메시지 발행 사이의 불일치 문제를 해결한다.
- DB에는 저장되었지만 Kafka 발행이 실패하는 상황을 안전하게 처리한다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
- Redis와 DB는 서로 다른 시스템이다.
- Outbox Pattern은 DB 트랜잭션과 Outbox 저장을 함께 처리할 뿐이다.
- Redis 판정과 최초 Kafka 발행을 하나의 트랜잭션으로 묶어 주지는 않는다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
- 일시적인 장애로 실패한 메시지를 자동으로 재시도한다.
- 여러 번 재시도해도 처리되지 않는 메시지는 DLQ로 이동하여 별도로 관리한다.
```
