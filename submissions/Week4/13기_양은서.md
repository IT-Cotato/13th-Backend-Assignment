# **4주차 과제: DB 테이블과 최종 발급 정합성 보장**

## **1. 과제 목표**

이번 과제의 목표는 **Redis와 Kafka를 통과한 쿠폰 발급 요청을 DB에 정확하게 저장하고, 사용자 중복 발급과 전체 수량 초과를 방지하는 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

이번 4주차에서는 Consumer가 Kafka 메시지를 읽은 뒤 DB에 최종 발급 기록을 저장하는 단계를 설계한다.

기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
ACCEPTED인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB Transaction
  ├─ coupon_event.issued_count 증가
  └─ coupon_issue 발급 기록 저장
```

`Redis ACCEPTED`는 3주차의 `Redis SUCCESS`와 같은 단계다. 최종 발급 성공과 구분하기 위해 이번 주차에서는 `ACCEPTED`로 표기한다.

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Redis 판정 통과와 DB 최종 발급 성공의 차이

DB가 보장해야 하는 불변식

coupon_event와 coupon_issue 테이블 설계

UNIQUE(event_id, user_id)의 역할과 한계

조건부 UPDATE를 이용한 수량 초과 방지

영향받은 row 수의 의미와 실패 원인 구분

issued_count 증가와 coupon_issue INSERT를
하나의 트랜잭션으로 묶는 이유

Kafka 중복 소비와 DB 중복 발급 방지

품절 후 중복 메시지가 재처리되는 경우

조건부 UPDATE, 비관적 락, 낙관적 락 비교

Redis, Kafka, DB의 역할과 데이터 불일치 상황
```

이번 과제의 핵심은 다음과 같다.

```
Redis는 빠른 선착순 판정을 담당한다.

Kafka는 발급 요청 메시지를 전달한다.

DB는 최종 발급 기록을 저장하고 수량 정합성을 보장한다.
```

## **2. 기본 상황**

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 ID: 100

이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트

전체 쿠폰 수량: 1,000개

발급 조건:
사용자 1명당 해당 이벤트 쿠폰 1개만 발급 가능

DBMS: PostgreSQL

최종 발급 성공 기준:
coupon_issue 저장 트랜잭션 Commit
```

Redis는 정상 상황에서 최대 1,000명의 사용자만 통과시킨다.

하지만 다음과 같은 상황이 발생할 수 있다.

```
Redis 데이터 유실 또는 초기화

Redis Replica Failover 과정에서 일부 통과 기록 유실

Kafka 메시지 재처리

DB Commit 이후 Consumer Group Offset 커밋 전 Consumer 장애

애플리케이션 버그로 같은 발급 요청이 여러 번 DB에 도달
```

따라서 Redis가 앞단에서 요청을 차단하더라도 DB에는 다음 방어 장치가 필요하다.

```
사용자 중복 발급 방지
→ UNIQUE(event_id, user_id)

전체 수량 초과 방지
→ issued_count 조건부 UPDATE

두 작업의 일관성
→ DB Transaction
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
coupon_issue에는 최종 발급에 성공한 기록만 저장한다.

coupon_issue의 status는 ISSUED만 사용한다.

쿠폰 발급 취소와 재발급은 다루지 않는다.

이벤트별 전체 수량은
coupon_event.total_quantity에 저장한다.

DB에서 최종 발급된 수량은
coupon_event.issued_count에 저장한다.

모든 발급 처리는 issued_count 증가와
coupon_issue INSERT를 같은 트랜잭션에서 수행한다.

이벤트 발급 자격은 Redis 판정 시점을 기준으로 한다.
Consumer는 이벤트 상태와 기간을 다시 판정하지 않고
DB의 최종 수량과 사용자 중복 발급을 방어한다.

PostgreSQL의 기본 격리 수준인
READ COMMITTED를 기준으로 설명한다.

자동 Offset 커밋은 사용하지 않는다.
Consumer가 DB 처리 결과를 확정한 후에
Consumer Group Offset을 커밋한다고 가정한다.
```

이번 주차에서는 아래 내용의 상세 구현은 다루지 않는다.

```
requestId 기반 요청 상태 관리

Outbox Pattern

Retry Topic과 DLQ

쿠폰 발급 취소와 재발급 정책

Redis와 Kafka 사이의 원자성 보장
```

다만 이번 주차의 설계가 이후 주차의 내용과 어떻게 연결되는지는 설명해야 한다.

## **과제 1. DB 최종 발급 처리 구조 그리기**

Redis 판정을 통과한 요청이 Kafka를 거쳐 DB에 최종 저장되는 전체 구조를 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka

Coupon Issue Consumer

coupon_event

coupon_issue
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  ↓
API Server
  ↓
Redis 선착순·중복 판정
  ↓ ACCEPTED
Kafka coupon.issue.requested
  ↓
Coupon Issue Consumer
  ↓
DB Transaction
  ├─ coupon_event.issued_count 증가
  └─ coupon_issue 발급 기록 INSERT
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
Redis는 요청의 선착순·중복 여부만 빠르게 판정한다.
이후 Kafka 발행이나 DB 저장이 실패할 수 있으므로 최종 발급 성공은 아니다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
Kafka 발행 성공은 요청 메시지가 저장되었다는 의미다.
Consumer의 DB 트랜잭션이 실패할 수 있으므로 최종 발급 성공은 아니다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
issued_count 증가와 coupon_issue INSERT가 하나의 DB 트랜잭션으로 Commit된 시점이다.
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준 선착순·중복 판정 통과 | 아니오 |
| Kafka PUBLISHED | Kafka에 발급 요청 레코드 저장 | 아니오 |
| DB ISSUED | DB 발급 트랜잭션 Commit 완료 | 예 |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

쿠폰 발급 시스템이 장애와 동시 요청 상황에서도 지켜야 하는 조건을 불변식으로 정의한다.

이번 과제에서는 다음 세 가지 불변식을 기준으로 작성한다.

```
불변식 1.

한 사용자는 하나의 이벤트에서
쿠폰을 최대 한 번만 발급받는다.

불변식 2.

발급 수량은 0보다 작거나
전체 수량보다 많을 수 없다.

불변식 3.

issued_count 증가와 coupon_issue 저장은
함께 성공하거나 함께 실패한다.
```

### **1. 불변식이 필요한 이유**

```
동시 요청, 중복 메시지, 장애가 발생해도 중복 발급과 수량 초과 없이
항상 일관된 최종 결과를 유지하기 위해 필요하다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 같은 사용자가 같은 이벤트에서 여러 쿠폰을 발급받는다. |
| 전체 수량 이하 발급 | 정해진 수량보다 많은 쿠폰이 발급된다. |
| 수량과 발급 기록의 동시 성공·실패 | issued_count와 실제 발급 기록 수가 달라진다. |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | `UNIQUE(event_id, user_id)` |
| 전체 수량 초과 방지 | 조건부 UPDATE와 수량 CHECK 제약 |
| 두 테이블의 일관성 | DB Transaction |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
두 트랜잭션이 동시에 조회하면 모두 발급 기록이 없다고 판단할 수 있다.
따라서 최종 중복 방지는 DB의 UNIQUE 제약으로 보장해야 한다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

쿠폰 이벤트와 최종 발급 기록을 저장할 테이블을 설계한다.

완전한 운영용 스키마를 만드는 것이 목적은 아니다. 이번 주차에서 필요한 불변식을 지킬 수 있도록 핵심 컬럼과 제약 조건을 작성한다.

### **1. coupon_event 테이블의 역할**

```
이벤트 정보, 전체 수량, DB 기준 최종 발급 수량을 저장한다.
```

### **2. coupon_issue 테이블의 역할**

```
최종 발급에 성공한 사용자별 쿠폰 발급 기록을 저장한다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
+----------------------+
| coupon_event         |
|----------------------|
| id                   |
| name                 |
| total_quantity       |
| issued_count         |
| start_at             |
| end_at               |
| status               |
| version              |
+----------------------+
          |
          | 1 : N
          |
          v
+----------------------+
| coupon_issue         |
|----------------------|
| id                   |
| event_id             |
| user_id              |
| status               |
| issued_at            |
+----------------------+
```

### **4. coupon_event 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

name

total_quantity

issued_count

start_at

end_at

status

version (낙관적 락을 선택할 경우)

수량 CHECK 제약

이벤트 기간 CHECK 제약
```

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INTEGER NOT NULL,
    issued_count INTEGER NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),
    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at)
);
```

### **5. coupon_issue 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

event_id

user_id

status

issued_at

coupon_event를 참조하는 Foreign Key

동일 이벤트의 사용자 중복 발급을 막는 UNIQUE 제약
```

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),
    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
발급 수량을 빠르게 조회하고 조건부 UPDATE로 수량 초과를 막을 수 있다.
다만 coupon_issue 기록과 값이 어긋날 수 있으므로 반드시 같은 트랜잭션에서 변경해야 한다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

`UNIQUE(event_id, user_id)`가 어떤 문제를 막고, 어떤 문제는 막지 못하는지 분석한다.

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
UNIQUE(event_id, user_id)는 동일한 사용자가 같은 이벤트에서
두 번 이상 쿠폰을 발급받는 것을 막는다.

Kafka 메시지가 다시 소비되어도 동일한 발급 기록을 INSERT하면
UNIQUE 제약 위반이 발생하므로 최종적으로 하나의 발급 기록만 저장된다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 다음과 같다.

```
event_id = 100
user_id = 10
```

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | 기존 조합과 동일하여 UNIQUE 제약을 위반한다. |
| event_id=100, user_id=11 | 성공 | 사용자 ID가 달라 새로운 조합이다. |
| event_id=101, user_id=10 | 성공 | 이벤트 ID가 달라 새로운 조합이다. |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

아래 상황을 시간 순서로 표현한다.

```
Transaction A가 user:10의 발급 기록을 조회한다.

Transaction B도 user:10의 발급 기록을 조회한다.

두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

두 트랜잭션이 동시에 INSERT를 시도한다.
```

답변:

```
Transaction A와 B가 동시에 SELECT하면 둘 다 기록이 없다고 볼 수 있다.
이후 두 트랜잭션이 모두 INSERT를 시도하므로 SELECT만으로는 중복을 막을 수 없다.
UNIQUE 제약이 있으면 한 INSERT만 성공하고 나머지는 실패한다.
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

아래 상황을 기준으로 설명한다.

```
전체 수량: 1,000개

서로 다른 사용자: 1,001명

모든 (event_id, user_id) 조합은 서로 다름
```

```
모든 사용자 조합이 다르면 UNIQUE 제약을 위반하지 않는다.
따라서 1,001명 모두 INSERT될 수 있으므로 전체 수량은 조건부 UPDATE로 별도 보호해야 한다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | `UNIQUE(event_id, user_id)` |
| 서로 다른 사용자에 의한 전체 수량 초과 | `issued_count < total_quantity` 조건부 UPDATE |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

쿠폰 수량이 남아 있을 때만 `issued_count`를 증가시키는 조건부 UPDATE를 설계한다.

### **1. 조건부 UPDATE SQL 작성하기**

다음 조건을 만족해야 한다.

```
event_id가 일치해야 한다.

issued_count가 total_quantity보다 작을 때만 증가해야 한다.

issued_count는 1 증가해야 한다.
```

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
조건을 만족해 실제로 수정된 행의 수다.
1이면 수량 확보 성공, 0이면 수량 확보 실패다.
```

### **3. 영향받은 row 수가 1인 경우**

```
이벤트가 존재하고 수량이 남아 있어 issued_count가 1 증가한 경우다.
이후 coupon_issue INSERT를 진행한다.
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

과제 5-1의 SQL은 `event_id`와 수량 조건만 사용한다. 중복 메시지 여부는 UPDATE 결과가 0인 직접 원인이 아니라, 이후 기존 발급 기록을 조회해 구분한다.

```
1. 해당 event_id의 이벤트가 존재하지 않는다.

2. issued_count가 total_quantity와 같아 수량이 소진되었다.
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

과제 5-1에서 작성한 조건부 UPDATE를 사용한다고 가정한다.

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | issued_count가 1,000으로 증가한다. |
| B | 1,000 | 1,000 | 존재 | 0 | 수량 조건을 만족하지 않는다. |
| C | - | - | 존재하지 않음 | 0 | 수정할 이벤트가 없다. |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전체 수량: 1,000개

현재 issued_count: 999

Transaction A와 Transaction B가
동시에 조건부 UPDATE 실행
```

두 트랜잭션의 실행 결과를 시간 순서 다이어그램으로 작성한다.

```
초기 issued_count = 999

Transaction A: row 갱신 락 획득
Transaction B: 같은 row의 락 대기
Transaction A: 999 < 1000 확인 후 1000으로 증가, Commit
Transaction B: 최신 값 1000으로 조건 재확인
Transaction B: 1000 < 1000이 거짓이므로 UPDATE 결과 0
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
동일 row의 UPDATE는 순차 처리되고, 대기한 트랜잭션은 최신 값으로 WHERE 조건을 다시 확인한다.
따라서 수량이 모두 소진된 뒤에는 UPDATE 결과가 0이 된다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

다음 두 작업을 하나의 DB 트랜잭션으로 묶는 이유를 설명한다.

```
1. coupon_event.issued_count 증가

2. coupon_issue 발급 기록 INSERT
```

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량만 증가하고 실제 발급 기록은 없어 두 값이 달라진다. |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급 기록만 남아 이후 전체 수량을 초과할 수 있다. |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
Transaction 시작
  ↓
조건부 UPDATE
  ↓
UPDATE 결과가 1이면 coupon_issue INSERT
  ↓
모두 성공하면 Commit
하나라도 실패하면 Rollback
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
BEGIN;

UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;

-- UPDATE 결과가 1일 때만 실행
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:eventId, :userId, 'ISSUED', CURRENT_TIMESTAMP);

COMMIT;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

아래 항목을 모두 설명한다.

```
현재 트랜잭션은 어떻게 되는가?

앞에서 증가한 issued_count는 어떻게 되는가?

기존 발급 기록은 언제 조회해야 하는가?
```

답변:

```
UNIQUE 위반이 발생하면 현재 트랜잭션은 실패 상태가 되어 Rollback해야 한다.

Rollback하면 같은 트랜잭션에서 증가한 issued_count도 함께 취소된다.

기존 발급 기록은 Rollback 후 새로운 트랜잭션에서 조회해야 한다.
``` 

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
PostgreSQL은 제약 위반이 발생한 트랜잭션을 실패 상태로 전환한다.
이후 SQL은 실행할 수 없으므로 Rollback 후 새 트랜잭션을 사용해야 한다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
Consumer, 관리자 발급, 재처리 배치 등 모든 경로가 같은 규칙을 사용해야
issued_count와 coupon_issue의 정합성이 항상 유지된다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

Kafka Consumer는 같은 메시지를 다시 처리할 수 있다.

아래 상황을 기준으로 분석한다.

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.
```

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
메시지 소비
  ↓
DB 발급 Transaction Commit
  ↓
Offset 커밋 전 Consumer 종료
  ↓
Consumer 재시작
  ↓
같은 메시지 재소비
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
같은 사용자의 발급 기록이 중복 INSERT되고 issued_count도 다시 증가할 수 있다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
중복 메시지가 같은 발급 기록을 INSERT하면 UNIQUE 위반이 발생한다.
트랜잭션을 Rollback하므로 앞서 증가한 issued_count도 취소된다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
위반한 제약이 UNIQUE(event_id, user_id)이고,
Rollback 후 조회했을 때 동일한 ISSUED 기록이 실제로 존재해야 한다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. 현재 트랜잭션을 Rollback한다.

2. 새 트랜잭션에서 동일한 발급 기록을 조회한다.

3. 기록이 있으면 이미 처리된 메시지로 판단한다.

4. 처리 완료 후 Consumer Group Offset을 커밋한다.
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
Offset을 먼저 커밋한 뒤 DB 저장이 실패하면 Kafka는 메시지를 처리 완료로 판단한다.
그 결과 메시지가 재전달되지 않아 최종 발급 요청이 유실될 수 있다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
UNIQUE는 같은 사용자의 중복 발급 결과를 막는다.
requestId는 동일 요청의 중복 접수·처리를 식별하고 이전 결과를 재사용한다.
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

조건부 UPDATE를 먼저 실행하는 구조에서는 중복 메시지가 항상 INSERT까지 도달하는 것은 아니다.

아래 상황을 기준으로 분석한다.

```
이벤트 ID: 100

전체 수량: 1개

현재 issued_count: 1

coupon_issue에
(event_id=100, user_id=10) 기록이 이미 존재

user:10의 Kafka 메시지가 다시 전달됨
```

### **1. 조건부 UPDATE 결과와 그 이유**

```
결과는 0이다. issued_count와 total_quantity가 모두 1이므로
issued_count < total_quantity 조건을 만족하지 않는다.
```

### **2. coupon_issue INSERT까지 실행되는가?**

```
실행되지 않는다. UPDATE 결과가 1일 때만 INSERT하기 때문이다.
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```
발생하지 않는다. INSERT 단계까지 도달하지 않기 때문이다.
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```
이미 발급에 성공한 사용자의 중복 메시지가 재처리된 경우도 UPDATE 결과가 0일 수 있다.
```

### **5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유**

```
이미 처리된 중복 메시지인지, 실제로 발급받지 못한 품절 요청인지 구분하기 위해서다.
```

### **6. 다음 두 상황을 구분하는 처리 흐름 작성하기**

각 상황에서 메시지 처리 완료 여부와 Consumer Group Offset 커밋 여부도 함께 작성한다.

```
상황 A

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 존재

상황 B

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 없음
```

답변:

```
상황 A
기존 기록이 있으므로 이미 처리된 중복 메시지로 판단한다.
메시지 처리를 완료하고 Offset을 커밋한다.

상황 B
기존 기록이 없으므로 이벤트 없음 또는 실제 품절로 판단한다.
비즈니스 실패 결과를 기록하고 Offset을 커밋한다.
단, DB 조회 자체가 실패한 경우에는 Offset을 커밋하지 않는다.
```

### **7. 전체 Consumer 처리 흐름 완성하기**

아래 두 경로를 모두 포함해야 한다.

```
조건부 UPDATE 결과 = 0인 경로

조건부 UPDATE 결과 = 1인 경로
```

```
Kafka 메시지 소비
  ↓
DB Transaction 시작
  ↓
조건부 UPDATE
  ├─ 결과 0
  │    └─ 기존 coupon_issue 조회
  │         ├─ 존재: 중복 메시지 처리 완료 → Offset 커밋
  │         └─ 없음: 품절·이벤트 없음 처리 → Offset 커밋
  │
  └─ 결과 1
       └─ coupon_issue INSERT
            ├─ 성공: Commit → Offset 커밋
            └─ 실패: Rollback
                 ├─ 기존 기록 존재: 중복 처리 → Offset 커밋
                 └─ 기록 없음: 오류 처리 → Offset 미커밋
```

## **과제 9. DB 동시성 제어 방식 비교하기**

다음 세 가지 방식으로 쿠폰 수량을 제어할 수 있다.

```
조건부 UPDATE

비관적 락

낙관적 락
```

### **1. 조건부 UPDATE 방식 설명**

```
수량 확인과 증가를 하나의 UPDATE로 처리한다.
영향받은 row 수가 1이면 성공, 0이면 실패다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
BEGIN;

SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;

COMMIT;
```

설명:

```
먼저 이벤트 row를 잠그고 수량을 확인·수정한다.
다른 트랜잭션은 락이 해제될 때까지 대기한다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
조회한 version과 현재 version이 같을 때만 수정한다.
충돌로 UPDATE가 실패하면 최신 값을 다시 조회해 재시도해야 한다.
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | 조건과 증가를 한 SQL로 처리 | row를 먼저 잠금 | version 비교 |
| 충돌 시 동작 | 순차 처리 후 조건 재확인 | 락 해제까지 대기 | UPDATE 실패 |
| 재시도 필요 여부 | 일반적으로 불필요 | 일반적으로 불필요 | 필요 |
| 장점 | 단순하고 효율적 | 이해하기 쉽고 안전함 | 충돌이 적을 때 효율적 |
| 단점 | 특정 row에 대기 발생 | 락 대기 증가 | 충돌 시 재시도 증가 |
| 선착순 이벤트 적합성 | 높음 | 보통 | 낮음 |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
같은 row의 갱신 락을 기다리는 요청이 늘어 처리 지연과 Consumer Lag이 발생할 수 있다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
별도 SELECT 없이 한 SQL로 수량 확인과 증가를 처리하며,
row 수로 성공 여부를 쉽게 판단할 수 있기 때문이다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```
세 동시성 제어 방식은 전체 수량 초과를 막고,
UNIQUE 제약은 동일 사용자의 중복 발급을 막는다.
보호하는 불변식이 다르므로 함께 사용해야 한다.
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

Redis, Kafka, DB는 서로 다른 시스템이므로 상태가 일시적으로 달라질 수 있다.

Kafka 상태는 발행된 레코드의 존재 여부와 Consumer Group Offset 커밋 여부를 구분해서 작성한다. Kafka 레코드가 존재한다는 사실만으로 처리 대기 상태라고 판단하지 않는다.

### **1. Redis 통과 후 Kafka 발행 실패 상황**

아래 세 시스템에 남는 상태를 작성한다.

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 요청 통과 기록과 Redis 기준 수량 차감이 남을 수 있다. |
| Kafka | 발행 실패로 레코드가 없고 Offset 변화도 없다. |
| DB | Consumer가 처리하지 못해 최종 발급 기록이 없다. |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 요청 통과 기록과 Redis 기준 수량 차감이 남아 있다. |
| Kafka | 레코드는 존재한다. DB 실패 후 Offset이 미커밋이면 재전달 대상이다. |
| DB | 트랜잭션이 Rollback되어 최종 발급 기록이 없다. |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 장애나 초기화로 판정 기록과 수량 정보가 유실될 수 있다. |
| DB | Commit된 issued_count와 coupon_issue 기록은 유지된다. |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
Redis는 임시 판정, Kafka는 메시지 전달을 담당한다.
최종 발급 기록과 트랜잭션 결과는 DB에 저장되므로 DB를 기준으로 판단해야 한다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 선착순·중복 판정 | 요청 전달·재처리 | 최종 발급 저장·정합성 보장 |
| 저장하는 상태 | 임시 수량·통과 기록 | 메시지 레코드·Offset | 발급 수량·사용자 발급 기록 |
| 성공이 의미하는 것 | Redis 판정 통과 | 레코드 저장 또는 Offset 처리 완료 | 발급 Transaction Commit |
| 강점 | 빠른 처리 | 비동기 처리와 완충 | 트랜잭션과 제약 조건 |
| 한계 | 데이터 유실 가능 | 중복 전달 가능 | row lock 병목 가능 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
동일 requestId의 중복 요청을 식별하고 기존 처리 결과를 재사용하는 문제를 해결한다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
DB 변경은 성공했지만 후속 Kafka 이벤트 발행이 실패해 메시지가 유실되는 문제를 줄인다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
Outbox는 관계형 DB 내부의 데이터 변경과 Outbox 저장을 같은 트랜잭션으로 묶는다.
Redis와 Kafka는 별도 시스템이므로 Redis 판정과 최초 Kafka 발행은 원자적으로 묶이지 않는다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
일시적 장애는 Retry로 재처리하고,
반복 실패 메시지는 DLQ로 격리해 무한 재시도와 Consumer 중단을 방지한다.
```
