# **DB 테이블과 최종 발급 정합성 보장**

## **과제 1. DB 최종 발급 처리 구조 그리기**

Redis 판정을 통과한 요청이 Kafka를 거쳐 DB에 최종 저장되는 전체 구조를 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka

Coupon Issue Consumer

coupon_event

coupon_issue
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | POST /coupon-events/{eventId}/issue
  v
API Server
  |
  | 1) 로그인 여부 확인
  | 2) 이벤트 시간 확인
  v
Redis 선착순 / 중복 판정
  |
  +---> DUPLICATE / SOLD_OUT → 즉시 실패 응답 반환
  |
  | ACCEPTED인 경우에만
  v
Kafka Producer
  |
  | publish
  v
coupon.issue.requested (Topic)
  |
  | consume
  v
Coupon Issue Consumer
  |
  | DB Transaction 시작
  |
  | 1) 조건부 UPDATE
  |    UPDATE coupon_event
  |    SET issued_count = issued_count + 1
  |    WHERE id = :eventId
  |      AND issued_count < total_quantity
  |
  +---> 결과 = 0
  |       |
  |       | coupon_issue 기록 조회
  |       +---> 기록 있음 → 중복 메시지 → 처리 완료 → Offset 커밋
  |       +---> 기록 없음 → 수량 소진 / 이벤트 없음 → 처리 완료 → Offset 커밋
  |
  | 결과 = 1
  |
  | 2) coupon_issue INSERT
  |    INSERT INTO coupon_issue (event_id, user_id, status)
  |    VALUES (:eventId, :userId, 'ISSUED')
  |    UNIQUE(event_id, user_id) 적용
  |
  +---> UNIQUE 위반 → Rollback
  |       |
  |       | 새 트랜잭션에서 기록 조회
  |       +---> 기록 있음 → 중복 메시지 → 처리 완료 → Offset 커밋
  |       +---> 기록 없음 → 예상치 못한 오류 → 재시도 / DLQ
  |
  | INSERT 성공
  v
Commit
  |
  v
DB (coupon_event.issued_count 증가 + coupon_issue 발급 기록 저장)
  |
  v
Consumer Group Offset 커밋
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
Redis는 인메모리 저장소이므로 Redis 통과 이후에도 Kafka 발생 실패, Consumer 장애, DB 저장 실패가 발생할 수 있다.

Redis는 빠른 선착순 판정만 담당하고 실제 발급 기록은 DB에만 존재한다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
Kafka는 메시지를 전달하는 역할만 한다.

Consumer가 메시지를 읽어 수량 확인, 중복 검사, DB 저장까지 성공해야 발급이 완료된다.

Kafk에 메시지가 있더라고 Consumer가 처리 중 실패하면 발급 기록은 존재하지 않는다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
'coupon_issue' INSERT와 'coupon_event.issued_count' 증가가 포함된 DB 트랜잭션이 커밋된 시점이다.
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준 선착순 판정 통과, 중복 사용자 아님 | X |
| Kafka PUBLISHED | 발급 요청 메시지가 Kafka Broker에 안전하게 저장됨 | X |
| DB ISSUED | coupon_issue 저장 트랜잭션이 커밋 완료됨 | O |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

쿠폰 발급 시스템이 장애와 동시 요청 상황에서도 지켜야 하는 조건을 불변식으로 정의한다.

이번 과제에서는 다음 세 가지 불변식을 기준으로 작성한다.

```
불변식 1.

한 사용자는 하나의 이벤트에서
쿠폰을 최대 한 번만 발급받는다.

불변식 2.

발급 수량은 0보다 작거나
전체 수량보다 많을 수 없다.

불변식 3.

issued_count 증가와 coupon_issue 저장은
함께 성공하거나 함께 실패한다.
```

### **1. 불변식이 필요한 이유**

```
Redis는 데이터가 유실될 수 있고, Kafka는 메시지를 중복 소비할 수 있으며, 애플리케이션 버그로 같은 요청이 여러 번 도달할 수 있다.

이런 상황에서도 쿠폰이 의도한 수량 이상으로 발급되거나 한 사용자가 여러 번 발급받는 일이 없어야 한다.

불변식은 시스템 장애 상황에서도 반드시 지켜야 할 최후의 조건이므로 DB 레벨에서 보장해야 한다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 같은 사용자가 동일 일벤트 쿠폰을 여러 개 보유하게 되어 비즈니스 손실 발생 |
| 전체 수량 이하 발급 | 1,000개 이벤트에서 1,001개 이상 발급되어 서비스 신뢰 손상 및 추가 비용 발생 |
| 수량과 발급 기록의 동시 성공·실패 | issued_count와 coupon_issue 수가 어긋나 현황 파악 불가, 재발급 기준 혼란 |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | UNIQUE(event_id, user_id) |
| 전체 수량 초과 방지 | issued_count < total_quantity 조건부 UPDATE |
| 두 테이블의 일관성 | DB Transaction (두 작업을 하나의 트랜잭션으로 묶음) |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
두 요청이 동시에 "발급 기록 없음"을 조회한 뒤 둘 다 INSERT를 시도할 수 있다.

조회 시점과 INSERT 시점 사이에 다른 트랜잭션이 끼어들 수 있기 때문에 SELECT 후 INSERT 방식은 Race Condition에 취약하다.

DB의 UNIQUE 제약은 INSERT 시점에 원자적으로 검사하므로 이 문제를 해결한다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

쿠폰 이벤트와 최종 발급 기록을 저장할 테이블을 설계한다.

완전한 운영용 스키마를 만드는 것이 목적은 아니다. 이번 주차에서 필요한 불변식을 지킬 수 있도록 핵심 컬럼과 제약 조건을 작성한다.

### **1. coupon_event 테이블의 역할**

```
쿠폰 이벤트의 기본 정보(이름, 전체 수량, 기간, 상태)와 DB 기준 발금 수량(issued_count)을 저장한다.

조건부 UPDATE의 대상 테이블로, 전체 수량 초과를 DB레벨에서 방어한다.
```

### **2. coupon_issue 테이블의 역할**

```
최종 발급에 성공한 사용자별 기록을 저장한다.

UNIQUE(event_id, user_id)제약으로 사용자 중복 발급을 방어하는 마지막 방어선이다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
coupon_event (1)
    │
    │ 1 : N
    ▼
coupon_issue (N)

coupon_event.id ← coupon_issue.event_id (FK)
```

### **4. coupon_event 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

name

total_quantity

issued_count

start_at

end_at

status

version (낙관적 락을 선택할 경우)

수량 CHECK 제약

이벤트 기간 CHECK 제약
```

```sql
CREATE TABLE coupon_event (
    id             BIGSERIAL PRIMARY KEY,
    name           VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count   INT NOT NULL DEFAULT 0,
    start_at       TIMESTAMPTZ NOT NULL,
    end_at         TIMESTAMPTZ NOT NULL,
    status         VARCHAR(20) NOT NULL,
    version        BIGINT NOT NULL DEFAULT 0,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

### **5. coupon_issue 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

event_id

user_id

status

issued_at

coupon_event를 참조하는 Foreign Key

동일 이벤트의 사용자 중복 발급을 막는 UNIQUE 제약
```

```sql
CREATE TABLE coupon_issue (
    id         BIGSERIAL PRIMARY KEY,
    event_id   BIGINT NOT NULL,
    user_id    BIGINT NOT NULL,
    status     VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
이유: coupon_issue를 집계하지 않고 남은 수량을 빠르게 판단할 수 있습니다. 조건부 UPDATE에서 issued_count < total_quantity조건을 한 row에서 원자적으로 검사할 수 있다. Redis와 DB 수량을 비교해 불일치를 감지하는 데도 유용하다.

단점: issued_count와 coupon_issue행 수가 반드시 일치해야 하므로 반드시 같은 트랜잭션으로 묶어야 한다. 실수로 트랜잭션 없이 한 쪽만 변경하면 데이터가 어긋난다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

`UNIQUE(event_id, user_id)`가 어떤 문제를 막고, 어떤 문제는 막지 못하는지 분석한다.

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
같은 이벤트에서 같은 사용자의 발급 기록은 DB에 단 하나만 존재할 수 있다.

(event_id, user_id)조합이 동일한 두 번째 INSERT는 제약 위반으로 실패한다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 다음과 같다.

```
event_id = 100
user_id = 10
```

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | (100,10)조합이 이미 존재하므로 UNIQUE 위반 |
| event_id=100, user_id=11 | 성공 | (100,11)은 존재하지 않는 새로운 조합 |
| event_id=101, user_id=10 | 성공 | (100,11)은 존재하지 않는 새로운 조합 |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

아래 상황을 시간 순서로 표현한다.

```
Transaction A가 user:10의 발급 기록을 조회한다.

Transaction B도 user:10의 발급 기록을 조회한다.

두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

두 트랜잭션이 동시에 INSERT를 시도한다.
```

답변: 조회 시점에는 둘 다 "없음"으로 보이기 때문에 애플리케이션 레벨 체크만으로는 중복을 막을 수 없다. UNIQUE 제약이 INSERT 시점에 원자적으로 검사하기 때문에 중복을 차단할 수 없다.

```
Transaction A: user:10 발급 기록 조회 → 없음
Transaction B: user:10 발급 기록 조회 → 없음

Transaction A: INSERT (event_id=100, user_id=10) 시도
Transaction B: INSERT (event_id=100, user_id=10) 시도

→ A 먼저 커밋 성공
→ B INSERT 시 UNIQUE 위반 발생
  (UNIQUE 제약이 없다면 B도 성공 → 중복 발급)
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

아래 상황을 기준으로 설명한다.

```
전체 수량: 1,000개

서로 다른 사용자: 1,001명

모든 (event_id, user_id) 조합은 서로 다름
```

```
전체 수량이 1,000개일 때 서로 다른 1,001명의 사용가자 각각 INSERT를 시도하면 모든 (event_id, user_id)조합이 다르다.

UINQUE 제약은 동일 조합의 중복만 차단하므로 1,001번 째 서로 다른 사용자의 INSERT도 통과한다.

전체 수량 초과는 issued_count 조건 UPDATE로 별도 방어해야 한다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | 	UNIQUE(event_id, user_id) |
| 서로 다른 사용자에 의한 전체 수량 초과 | issued_count < total_quantity 조건부 UPDATE |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

쿠폰 수량이 남아 있을 때만 `issued_count`를 증가시키는 조건부 UPDATE를 설계한다.

### **1. 조건부 UPDATE SQL 작성하기**

다음 조건을 만족해야 한다.

```
event_id가 일치해야 한다.

issued_count가 total_quantity보다 작을 때만 증가해야 한다.

issued_count는 1 증가해야 한다.
```

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at   = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
WHERE조건을 만족해서 실제로 수정된 행의 수다.

조건을 만족하지 않으면 0, 조건을 만족하면 1이 반환된다.
```

### **3. 영향받은 row 수가 1인 경우**

```
issued_count < total_quantity조건을 만족했으므로 수량을 정상적으로 확보했다.

이후 coupon_issue INSERT를 진행한다.
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

과제 5-1의 SQL은 `event_id`와 수량 조건만 사용한다. 중복 메시지 여부는 UPDATE 결과가 0인 직접 원인이 아니라, 이후 기존 발급 기록을 조회해 구분한다.

```
1. 해당 eventId의 이벤트가 존재하지 않음

2. issued_count가 이미 total_quantity에 도달하여 수량이 모두 소진함
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

과제 5-1에서 작성한 조건부 UPDATE를 사용한다고 가정한다.

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | 수량 확보 성공 -> INSERT 진행 |
| B | 1,000 | 1,000 | 존재 | 0 | 수량 소진 -> INSERT 생략, 기존 기록 조회 |
| C | - | - | 존재하지 않음 | 0 | 이벤트 없음 -> 기존 기록 조회 |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전체 수량: 1,000개

현재 issued_count: 999

Transaction A와 Transaction B가
동시에 조건부 UPDATE 실행
```

두 트랜잭션의 실행 결과를 시간 순서 다이어그램으로 작성한다.

```
전체 수량: 1,000개 / 현재 issued_count: 999

Transaction A: UPDATE WHERE issued_count < 1000
               → DB row lock 획득
               → issued_count = 1000 으로 변경
               → 영향받은 row 수 = 1

Transaction B: UPDATE WHERE issued_count < 1000
               → A가 row lock 보유 중이므로 대기
               → A 커밋 후 lock 해제
               → 현재 issued_count = 1000 확인
               → 1000 < 1000 조건 불만족
               → 영향받은 row 수 = 0
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
DB는 같은 row에 대한 UPDATE를 직렬화한다.

Transaction B는 A가 커밋된 후의 최신 issued_count값을 기준으로 조건을 재평가하므로 이미 한계에 도달한 경우 조건을 만족하지 못해 UPDATE가 실행되지 않는다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

다음 두 작업을 하나의 DB 트랜잭션으로 묶는 이유를 설명한다.

```
1. coupon_event.issued_count 증가

2. coupon_issue 발급 기록 INSERT
```

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 1 줄었지만 발급받은 사용자 기록이 없음. 해당 수량은 영구 소실 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 사용자는 쿠폰을 받았지만 issued_count에 반영되지 않아 수량 현황 부정확 |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
Transaction 시작
  ↓
조건부 UPDATE (issued_count + 1)
  ↓
  ├─ 결과 = 0 → 기존 coupon_issue 기록 조회
  │              ├─ 기록 있음 → 중복 메시지, 정상 처리 후 Rollback 불필요
  │              └─ 기록 없음 → 수량 소진 또는 이벤트 없음, 처리 완료
  │
  └─ 결과 = 1 → coupon_issue INSERT
                  ├─ 성공 → Commit
                  └─ UNIQUE 위반 → Rollback → 새 트랜잭션에서 기록 조회
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
-- Transaction 시작

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at   = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (event_id, user_id, status)
VALUES (:eventId, :userId, 'ISSUED');

-- 두 작업이 모두 성공하면 Commit
COMMIT;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

아래 항목을 모두 설명한다.

```
현재 트랜잭션은 어떻게 되는가?

앞에서 증가한 issued_count는 어떻게 되는가?

기존 발급 기록은 언제 조회해야 하는가?
```

답변:

```
- 현재 트랜잭션: PostgreSQL에서 제약 위반이 발생한 트랜잭션은 더 이상 사용할 수 없고 반드시 Rollback해야 한다.

- 앞에서 증가한 issued_count: 트랜잭션 자체가 Rollback되므로 issued_count증가도 함께 취소되어 원래 값으로 돌아간다.

- 기존 발급 기록 조회 시점: Rollback 후 새로운 트랜잭션을 시작하여 해당(event_id, user_id)의 기존 기록을 조회한다.
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
PostgreSQL은 트랜잭션 내에서 오류가 발생하면 해당 트랜잭션을 aborted상태로 표시한다.

aborted상태에서는 ROLLBACK외의 모든 SQL명령이 ERROR: current transaction is aborted오류를 반환한다. 

따라서 반드시 Rollback 후 새 트랜잭션을 시작해야 한다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
issued_count증가와 coupon_issue INSERT가 서로 다른 트랜잭션에 속하면 한 쪽만 성공하고 한 쪽이 실패하는 부분 성공 상태가 발생할 수 있다.

같은 트랜잭션으로 묶으면 둘 다 성공하거나 둘 다 실패하는 원자성이 보장된다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

Kafka Consumer는 같은 메시지를 다시 처리할 수 있다.

아래 상황을 기준으로 분석한다.

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.
```

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
Consumer → 메시지 수신
         → DB 트랜잭션 Commit 성공
         → Offset Commit 전 Consumer 장애 종료
         → Consumer 재시작
         → 같은 메시지 재수신
         → DB 처리 재시도
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
재처리된 메시지가 동일한 (event_id, user_id)로 INSERT를 시도할 때 막는 장치가 없다.

같은 사용자에게 쿠폰이 두 번 발급되고 issued_count도 두 번 증가하여 수량 데이터가 오염된다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
재처리 메시지가 조건부 UPDATE를 통과하더라도 coupon_issue INSERT단계에서 이미 동일한 (event_id, user_id)기록이 존재하므로 UNIQUE 위반이 발생한다.

트랜잭션 전체가 Rollback되어 issued_count증가도 취소된다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
Rollback 후 새 트랜잭션에서 해당 (event_id, user_id)기록을 조회했을 때 기록이 존재하면 이미 처리된 중복 메시지로 판단한다.

기록이 없다면 예상치 못한 오류로 처리해야 한다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. UNIQUE 위반 감지 -> 현재 트랜잭션 Rollback
 
2. 새 트랜잭션 시작 -> (event_id, user_id) 기존 기록 조회

3. 기록이 존재하면 -> 이미 처리된 중복 메시지로 판단, 정상 완료 처리

4. Consumer Group Offset 커밋
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
Offset이 먼저 커밋되면 Kafka는 해당 메시지가 처리 완료된 것으로 판단한다.

이후 DB 저장이 실패해도 메시지를 다시 받을 수 없어 발급 요청이 영구 유실된다.

DB 처리 성공을 확인한 뒤 Offset을 커밋해야 at-least-once 처리가 보장된다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
UNIQUE(event_id, user_id)는 동일 사용자가 동일 이벤드에서 쿠폰을 두 번 받지 못하도록 막는 비즈니스 규칙이다.

requestId 기반 멱등성은 동일한 요청(requestId)이 여러 번 처리되더라도 한 번만 처리된 것과 같은 결과를 보장하는 기술적 장치다.

전자는 사용자 중복 발급 방지, 후자는 재처리 요청의 중복 처리 방지를 목적으로 한다.
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

조건부 UPDATE를 먼저 실행하는 구조에서는 중복 메시지가 항상 INSERT까지 도달하는 것은 아니다.

아래 상황을 기준으로 분석한다.

```
이벤트 ID: 100

전체 수량: 1개

현재 issued_count: 1

coupon_issue에
(event_id=100, user_id=10) 기록이 이미 존재

user:10의 Kafka 메시지가 다시 전달됨
```

### **1. 조건부 UPDATE 결과와 그 이유**

```
영향받은 row 수 = 0. 현재 issued_count = 1이고 total_quantity = 1이므로 issued_count < total_quantity 조건(1 < 1)을 만족하지 않아 UPDATE가 실행되지 않는다.
```

### **2. coupon_issue INSERT까지 실행되는가?**

```
아니다.

조건부 UPDATE결과가 0이면 INSERT 단계로 진입하지 않는다.
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```
아니다.

INSERT 자체가 실행되지 않으므로 UNIQUE 제약 검사도 발생하지 않는다.
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```
결과가 0인 원인이 두 가지이기 때문이다.

이벤트 자체가 존재하지 않는 경우도 0이 반환된다.

또한 이미 처리된 중복 메시지인지 확인하려면 추가 조회가 필요하다.

품저로 잘못 판단하면 이미 발급받은 사용자에게 잘못된 실패 응답을 줄 수 있다.
```

### **5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유**

```
조건부 UPDATE가 0을 반환한 상황에서 해당 사용자의 발급 기록이 이미 있다면 이 메시지는 중복 소비된 것이므로 정상 처리로 완료해야 한다.

기록이 없다면 진짜 수량 소진이므로 실패 처리한다.

이 구분 없이 무조건 실패 처리하면 중복 메시지를 오류로 잘못처리하게 된다.
```

### **6. 다음 두 상황을 구분하는 처리 흐름 작성하기**

각 상황에서 메시지 처리 완료 여부와 Consumer Group Offset 커밋 여부도 함께 작성한다.

```
상황 A

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 존재

상황 B

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 없음
```

답변:

```
상황 A: 조건부 UPDATE 결과 = 0, coupon_issue 기록 존재
  → 이미 처리된 중복 메시지로 판단
  → 별도 처리 없이 메시지 처리 완료
  → Consumer Group Offset 커밋

상황 B: 조건부 UPDATE 결과 = 0, coupon_issue 기록 없음
  → 실제 수량 소진 또는 이벤트 없음으로 판단
  → 발급 실패 상태 기록 (필요 시)
  → 메시지 처리 완료 (재시도해도 결과가 달라지지 않음)
  → Consumer Group Offset 커밋
```

### **7. 전체 Consumer 처리 흐름 완성하기**

아래 두 경로를 모두 포함해야 한다.

```
조건부 UPDATE 결과 = 0인 경로

조건부 UPDATE 결과 = 1인 경로
```

```
메시지 수신
  ↓
조건부 UPDATE
  ├─ 결과 = 0
  │    ↓
  │   coupon_issue 기록 조회
  │    ├─ 기록 있음 → 중복 메시지 → 처리 완료 → Offset 커밋
  │    └─ 기록 없음 → 수량 소진 / 이벤트 없음 → 처리 완료 → Offset 커밋
  │
  └─ 결과 = 1
       ↓
      coupon_issue INSERT
       ├─ 성공 → Commit → 처리 완료 → Offset 커밋
       └─ UNIQUE 위반 → Rollback
                          ↓
                         새 트랜잭션에서 기록 조회
                          ├─ 기록 있음 → 중복 메시지 → 처리 완료 → Offset 커밋
                          └─ 기록 없음 → 예상치 못한 오류 → 재시도 또는 DLQ
```

## **과제 9. DB 동시성 제어 방식 비교하기**

다음 세 가지 방식으로 쿠폰 수량을 제어할 수 있다.

```
조건부 UPDATE

비관적 락

낙관적 락
```

### **1. 조건부 UPDATE 방식 설명**

```
수량 확인과 증가를 하나의 SQL로 원자적으로 처리한다.

WHERE issued_count < total_quantity 조건이 만족될 때만 UPDATE가 실행되므로 별도의 조회나 애플리케이션 재시도 없이 수량 초과를 막을 수 있다.

영향받은 row 수로 성공 여부를 판단한다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;
```

설명:

```
트랜잭션 시작 시 이벤트 row에 배타 락을 걸어 다른 트랜잭션이 접근하지 못하도록 한다.

락을 얻은 뒤 수량을 확인하고 안전하게 변경할 수 있다.

하지만 요청이 몰리면 락 대기 줄이 길어져 처리량이 크게 떨어진다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version      = version + 1,
    updated_at   = CURRENT_TIMESTAMP
WHERE id      = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
처음부터 락을 잡지 않고, UPDATE시 읽었던 version과 현재 version이 같은지 확인한다.

version이 달라진 경우(다른 트랜잭션이 먼저 변경) 영향받은 row수가 0이 되어 애플리케이션에서 재시도해야 한다.

충돌이 잦은 환경(선착순 이벤트)에서는 재시도가 폭발적으로 증가할 수 있다.
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | WHERE조건으로 원자적 수량 확인 + 증가 | 명시적 row lock후 수량 확인 | version 불일치 시 UPDATE실패 |
| 충돌 시 동작 | DB가 직렬화하여 나중 요청은 조건 불만족 | 락 대기 후 순서대로 처리 | UPDATE실패 -> 애플리케이션 재시도 |
| 재시도 필요 여부 | 불필요 | 불필요 | 필요 |
| 장점 | 구현 단순, 재시도 없음 | 처리 순서 직관적, 정합성 이해 쉬움 | 락 대기 없음, 충돌 적은 환경에서 효율적 |
| 단점 | row lock 대기 발생 가능 | 동시 요청 시 락 대기 증가, 처리량 감소 | 충돌 많으면 재시도 폭증, 선착순에 부적합 |
| 선착순 이벤트 적합성 | 적합 | 락 대기 문제 | 재시도 폭증 |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
세 방식 모두 같은 row를 동시에 변경하려는 요청들이 DB내부에서 직렬화된다.

요청이 많을수록 대기 시간이 길어지고 처리량이 감소한다.

이 때문에 Redis에서 대부분의 요청을 먼저 걸러내어 DB에 도달하는 요청 수 자체를 줄이는 구조가 필요하다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
Redis가 앞단에서 대부분의 요청을 차단하므로 DB에는 최대 1,000건 내외의 요청만 도달한다. 

이 규모에서는 조건부 UPDATE의 row lock 대기가 문제가 될 만큼 심하지 않다. 반면 구현이 단순하고 재시도 로직이 필요 없어 Consumer 코드가 간결하다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```

```
세 방식은 모두 전체 수량 초과를 막는 장치다. 

UNIQUE(event_id, user_id)는 수량과 무관하게 동일 사용자의 중복 발급을 막는 장치다. 

서로 다른 문제를 각각 방어하므로 역할이 다르다.
---

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

Redis, Kafka, DB는 서로 다른 시스템이므로 상태가 일시적으로 달라질 수 있다.

Kafka 상태는 발행된 레코드의 존재 여부와 Consumer Group Offset 커밋 여부를 구분해서 작성한다. Kafka 레코드가 존재한다는 사실만으로 처리 대기 상태라고 판단하지 않는다.

### **1. Redis 통과 후 Kafka 발행 실패 상황**

아래 세 시스템에 남는 상태를 작성한다.

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 사용자가 통과 Set에 등록되어 있음, Redis 기준 수량 1 차감 |
| Kafka | 레코드 없음(발행 실패) |
| DB | 발급 기록 없음 |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 사용자가 통과 Set에 등록되어 있음 |
| Kafka | 레코드 존재, 해당 Consumer Group Offset 미커밋 (재처리 대상) |
| DB | 발급 기록 없음 |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 없음(유실) |
| DB | coupon_issue발급 기록 존재 |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
Redis는 인메모리 저장소로 데이터가 유실될 수 있고, Kafka는 메시지 브로커로 처리 완료 여부는 Offset 커밋으로만 판단된다. 

DB만이 트랜잭션으로 커밋된 영구 기록을 보장한다. coupon_issue 테이블에 기록이 있다는 것이 실제 발급 완료의 유일한 기준이다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순 판정과 중복 차단 | 발급 요청 메시지 전달 및 버퍼링 | 최종 발급 기록 저장 및 정합성 보장 |
| 저장하는 상태 | 통과 사용자 Set, 잔여 수량 카운터 | 발급 요청 레코드와 Consumer Group Offset | coupon_event(수량), coupon_issuer(발급 기록) |
| 성공이 의미하는 것 | 선착순 통과, 중복 아님 (최종 발급 아님) | 메시지가 Broker에 안전하게 저장됨 | 발급 트랜잭션 커밋 완료 (최종 발급 성공) |
| 강점 | 매우 빠른 응답, 원자적 연산(Lua Script) | 대량 메시지 버퍼링, 재처리 보장 | 영구 저장, ACID 트랜잭션, 제약 조건 |
| 한계 | 데이터 유실 가능, 재시작 시 초기화 위험 | 중복 소비 발생 가능 | 동시 요청 집중 시 lock 경합, 처리 속도 제한 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
같은 requestId를 가진 요청이 여러 번 도달했을 때 단 한 번만 처리된 것으로 보장하는 구조를 만든다. 

UNIQUE(event_id, user_id)가 사용자 중복을 막는다면, requestId 멱등성은 동일 요청의 재처리를 막는다. 

요청 상태(PENDING, ISSUED, FAILED)를 requestId 기준으로 관리하는 테이블도 이 주차에서 설계한다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
DB에 발급 기록을 저장한 뒤 CouponIssued 이벤트를 Kafka에 발행할 때, DB 저장은 성공했지만 Kafka 발행이 실패하는 정합성 문제를 해결한다. 

발급 기록 저장과 이벤트 데이터를 Outbox Table에 같은 트랜잭션으로 저장하고, 별도의 Publisher가 Outbox를 읽어 Kafka에 발행한다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
Outbox Pattern은 DB 트랜잭션 내부에서 발급 기록과 이벤트를 함께 저장하는 패턴이다. 

Redis는 별도의 인메모리 저장소이므로 DB 트랜잭션 범위에 포함되지 않는다. 

Redis 판정과 최초 Kafka 발행 사이의 원자성은 Outbox Pattern으로 보장할 수 없고, 이 불일치는 8주차의 보상 트랜잭션에서 별도로 다룬다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
Consumer 처리 실패 메시지를 유실 없이 관리하는 구조를 설계한다. 

일시적 DB 오류처럼 재시도로 해결 가능한 실패는 Retry Topic에서 재처리하고, 잘못된 메시지 형식처럼 재시도해도 해결되지 않는 영구 실패는 DLQ에 보관한다. 

Redis 통과 후 DB 저장이 실패하여 Redis와 DB 사이에 불일치가 생긴 경우 보상 트랜잭션으로 Redis 상태를 복구하는 절차도 이 주차에서 다룬다.
```
