# 4주차 과제: DB 테이블과 최종 발급 정합성 보장

## **과제 1. DB 최종 발급 처리 구조 그리기**

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | 1. 쿠폰 발급 요청
  v
API Server
  |
  | 2. 인증 및 이벤트 기본 검증
  v
Redis
  |
  | 3. 중복 사용자 및 잔여 수량을 원자적으로 판정
  |    (ACCEPTED / REJECTED)
  v
API Server
  |
  | 4. ACCEPTED 요청만 Kafka에 발행
  v
Kafka (coupon.issue.requested Topic)
  |
  | 5. 발급 요청 메시지 전달
  v
Coupon Issue Consumer
  |
  | 6. DB 트랜잭션 시작
  v
DB Transaction
  |
  +--> coupon_event : issued_count 조건부 UPDATE
  |
  +--> coupon_issue : 발급 기록 INSERT (UNIQUE 제약)
  |
  v
Commit -> DB ISSUED
  |
  v
Consumer Group Offset 커밋
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
Redis ACCEPTED는 Redis 기준으로 선착순 판정을 통과했다는 의미일 뿐이다

판정 이후 Kafka 발행이 실패할 수 있다
Consumer가 처리 도중 장애로 종료될 수 있다
Redis 데이터가 유실되거나 초기화되어 통과 기록이 사라질 수 있다
Redis Replica Failover 과정에서 일부 통과 기록이 유실될 수 있다

즉 Redis는 최종 발급 기록을 저장하는 저장소가 아니라
빠른 선착순 판정을 위한 상태 저장소다
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
Kafka PUBLISHED는 발급 요청 메시지가 브로커에 저장되었다는 의미다

메시지가 저장되었을 뿐 Consumer가 아직 처리하지 않았을 수 있다
Consumer가 처리 중 실패해 DB 트랜잭션이 Rollback될 수 있다
이미 수량이 소진되어 조건부 UPDATE가 0을 반환할 수 있다

Kafka는 메시지를 전달하는 역할을 하며 별도의 요청 상태 저장소가 없다면 PENDING이라는 도메인 상태를 관리하지 않는다
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
coupon_event.issued_count 증가와 coupon_issue INSERT를 포함한
DB 트랜잭션이 Commit된 시점이다

이 시점부터 coupon_issue에 (event_id, user_id) 기록이 남으며
이 기록이 최종 발급 여부를 판단하는 기준 데이터가 된다
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준으로 선착순 판정과 사용자 중복 검사를 통과함 | 아님 |
| Kafka PUBLISHED | 발급 요청 메시지가 Kafka에 저장됨 | 아님 |
| DB ISSUED | 수량 증가와 발급 기록 저장 트랜잭션이 Commit됨 | 맞음 |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

### **1. 불변식이 필요한 이유**

```
Redis와 Kafka는 장애, 유실, 재처리 가능성이 있는 구성 요소다
따라서 앞단의 판정만으로는 어떤 상황에서도 지켜져야 할 조건을 보장할 수 없다

불변식은 장애와 동시 요청 상황에서도 시스템이 반드시 지켜야 하는 조건이다
DB는 요청 흐름의 마지막 단계이자 최종 기준 데이터를 저장하므로
불변식을 강제하는 마지막 방어선이 되어야 한다

애플리케이션 로직은 배포 버전마다 달라지고 버그가 생길 수 있지만
DB 제약 조건은 모든 경로에 동일하게 적용된다
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 한 사용자가 같은 이벤트 쿠폰을 여러 장 보유하게 되어 이벤트 정책이 무너지고, 다른 사용자의 발급 기회가 줄어들며 할인 비용이 예상보다 증가함 |
| 전체 수량 이하 발급 | 준비한 수량보다 많은 쿠폰이 발급되어 정산 손실이 발생하고, 발급 후 회수하거나 사용을 거부해야 하는 사용자 신뢰 문제가 생김 |
| 수량과 발급 기록의 동시 성공·실패 | issued_count와 실제 발급 기록 수가 어긋나 남은 수량 계산이 틀리고, 유령 수량 차감이나 미반영 발급이 발생해 어느 값도 신뢰할 수 없게 됨 |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | `UNIQUE (event_id, user_id)` |
| 전체 수량 초과 방지 | `issued_count < total_quantity` 조건부 `UPDATE`, 수량 `CHECK` 제약 |
| 두 테이블의 일관성 | DB Transaction (Commit / Rollback 원자성) |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
조회와 INSERT 사이에는 시간 간격이 존재한다

READ COMMITTED 격리 수준에서 두 트랜잭션이 동시에 조회하면
아직 커밋되지 않은 상대 트랜잭션의 INSERT를 볼 수 없다
따라서 두 트랜잭션 모두 기존 기록 없음으로 판단하고 INSERT를 시도한다

Consumer가 여러 인스턴스로 확장되면 애플리케이션 메모리 기반 검사도 무의미하다

중복 검사와 삽입을 원자적으로 처리할 수 있는 것은 DB 제약 조건뿐이다
사전 조회는 불필요한 예외를 줄이는 최적화이며 정합성의 근거가 될 수 없다
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

### **1. coupon_event 테이블의 역할**

```
쿠폰 이벤트 자체의 정의와 DB 기준 발급 수량을 저장한다

이벤트 이름, 전체 발급 가능 수량, 진행 기간, 이벤트 상태를 관리한다
issued_count로 DB 트랜잭션이 완료된 발급 수량을 관리한다
전체 수량 초과 방지를 위한 조건부 UPDATE의 대상 row가 된다
```

### **2. coupon_issue 테이블의 역할**

```
어떤 사용자가 어떤 이벤트의 쿠폰을 발급받았는지 최종 기록을 저장한다

이번 주차에서는 최종 발급에 성공한 기록만 저장하며 status는 ISSUED만 사용한다
UNIQUE (event_id, user_id)로 사용자 중복 발급을 차단한다
최종 발급 여부를 판단할 때 기준이 되는 데이터다
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
+--------------------------+
| coupon_event             |
|--------------------------|
| id            (PK)       |
| name                     |
| total_quantity           |
| issued_count             |
| start_at                 |
| end_at                   |
| status                   |
| version                  |
| created_at               |
| updated_at               |
+--------------------------+
            |
            | 1 : N  (event_id FK)
            v
+--------------------------+
| coupon_issue             |
|--------------------------|
| id            (PK)       |
| event_id      (FK)       |
| user_id                  |
| status                   |
| issued_at                |
| created_at               |
| updated_at               |
|--------------------------|
| UNIQUE (event_id,        |
|         user_id)         |
+--------------------------+
```

### **4. coupon_event 테이블 DDL 작성하기**

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,

    name VARCHAR(100) NOT NULL,

    -- 전체 발급 가능 수량
    total_quantity INT NOT NULL,

    -- DB 트랜잭션이 완료된 발급 수량
    issued_count INT NOT NULL DEFAULT 0,

    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,

    -- READY, OPEN, CLOSED
    status VARCHAR(20) NOT NULL,

    -- 낙관적 락을 선택할 경우 사용한다
    version BIGINT NOT NULL DEFAULT 0,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

```
TIMESTAMPTZ는 서버와 DB의 시간대가 달라도 동일한 시점을 안전하게 다루기 위해 사용한다
updated_at의 DEFAULT는 INSERT 시점에만 적용되므로
값을 갱신하려면 애플리케이션 코드나 DB 트리거가 별도로 필요하다
```

### **5. coupon_issue 테이블 DDL 작성하기**

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,

    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,

    -- 이번 주차에서는 ISSUED만 저장한다
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',

    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
이유

1. 남은 수량을 COUNT 집계 없이 빠르게 판단할 수 있다
2. DB 기준 발급 현황을 단일 row 조회로 확인할 수 있다
3. Redis 수량과 DB 수량의 차이를 비교해 불일치를 감지할 수 있다
4. 조건부 UPDATE의 대상이 되어 DB에서 전체 수량 초과를 다시 방어할 수 있다

단점

1. coupon_issue의 실제 기록 수와 어긋날 수 있는 중복 데이터다
2. 반드시 같은 트랜잭션에서 변경해야 하므로 트랜잭션 설계 제약이 생긴다
3. 모든 발급 요청이 동일한 이벤트 row를 갱신하므로 row lock 경합 지점이 된다
4. 발급 취소나 재발급 정책이 추가되면 동기화 규칙을 다시 정의해야 한다
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
coupon_issue 테이블에서 (event_id, user_id) 조합은 단 하나만 존재할 수 있다

한 사용자는 하나의 이벤트에서 쿠폰을 최대 한 번만 발급받는다
서로 다른 이벤트에서는 같은 사용자가 각각 발급받을 수 있다
같은 이벤트에서는 서로 다른 사용자가 각각 발급받을 수 있다
```

### **2. 다음 INSERT의 성공 여부와 이유**

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | 기존 행과 (event_id, user_id) 조합이 동일해 UNIQUE 제약을 위반함 |
| event_id=100, user_id=11 | 성공 | 이벤트는 같지만 user_id가 달라 조합이 중복되지 않음 |
| event_id=101, user_id=10 | 성공 | 사용자는 같지만 event_id가 달라 조합이 중복되지 않음 |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

```
시간 순서

t1  Transaction A : SELECT * FROM coupon_issue
                    WHERE event_id=100 AND user_id=10
                    -> 결과 없음

t2  Transaction B : SELECT * FROM coupon_issue
                    WHERE event_id=100 AND user_id=10
                    -> 결과 없음
                    (A가 아직 INSERT하지 않았으므로 볼 수 없음)

t3  Transaction A : INSERT (100, 10) 실행

t4  Transaction B : INSERT (100, 10) 실행
                    (A가 미커밋이면 UNIQUE 인덱스에서 대기)

t5  Transaction A : Commit

t6  Transaction B : 대기 해제 후 UNIQUE 위반 발생

두 트랜잭션 모두 조회 시점에는 기록 없음을 확인한다
READ COMMITTED에서는 다른 트랜잭션의 미커밋 INSERT가 보이지 않으므로
사전 조회만으로는 중복을 막을 수 없다
최종적으로 중복을 차단하는 것은 UNIQUE 제약이다
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

```
UNIQUE (event_id, user_id)는 조합의 중복만 검사한다

1,001명의 서로 다른 사용자가 INSERT를 시도하면
모든 (event_id, user_id) 조합이 서로 다르다

user_id=1     -> UNIQUE 통과
user_id=2     -> UNIQUE 통과
...
user_id=1000  -> UNIQUE 통과
user_id=1001  -> UNIQUE 통과 가능

UNIQUE 제약은 전체 행의 개수를 세거나 total_quantity와 비교하지 않는다
따라서 전체 수량이라는 집계 조건은 별도의 장치로 방어해야 한다
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | `UNIQUE (event_id, user_id)` |
| 서로 다른 사용자에 의한 전체 수량 초과 | `issued_count < total_quantity` 조건부 `UPDATE`와 수량 `CHECK` 제약 |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

### **1. 조건부 UPDATE SQL 작성하기**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
WHERE 조건을 만족해 실제로 갱신된 이벤트 row의 개수를 의미한다

이벤트 row는 id 기준으로 최대 1개이므로 결과는 0 또는 1이다
값을 다시 SELECT하지 않고도 수량 확보 성공 여부를 판단할 수 있다
```

### **3. 영향받은 row 수가 1인 경우**

```
이벤트가 존재하고 갱신 시점에 issued_count < total_quantity를 만족했다는 의미다

이 요청이 남은 쿠폰 수량 1개를 확보했다
issued_count는 1 증가한 상태로 트랜잭션 안에 반영되어 있다
따라서 이어서 coupon_issue INSERT를 실행할 수 있다
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

```
1. 해당 id의 이벤트 row가 존재하지 않는다

2. issued_count가 이미 total_quantity에 도달해 수량이 모두 소진되었다
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | 999 < 1,000을 만족해 issued_count가 1,000으로 증가하고 수량 확보에 성공함 |
| B | 1,000 | 1,000 | 존재 | 0 | 수량 조건을 만족하지 않아 갱신되지 않고 수량 소진으로 판단함 |
| C | - | - | 존재하지 않음 | 0 | id 조건에 해당하는 row가 없어 갱신 대상이 없음 |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전제 : total_quantity = 1,000, issued_count = 999

t1  Transaction A : 조건부 UPDATE 실행
                    coupon_event id=100 row에 대한 row lock 획득
                    999 < 1,000 만족
                    issued_count = 1,000 으로 갱신 (미커밋)

t2  Transaction B : 조건부 UPDATE 실행
                    같은 row가 A에 의해 잠겨 있어 대기

t3  Transaction A : coupon_issue INSERT 성공
                    Commit -> row lock 해제

t4  Transaction B : 대기 해제
                    READ COMMITTED에서 갱신 대상 row를 최신 버전으로 재확인
                    (EvalPlanQual : issued_count = 1,000)
                    1,000 < 1,000 조건 불만족

t5  Transaction B : 영향받은 row 수 = 0
                    INSERT 실행하지 않음
                    수량 소진으로 처리

최종 상태 : issued_count = 1,000, coupon_issue 기록 1건 추가
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
DB는 같은 row에 대한 UPDATE를 row lock으로 직렬화한다

동시에 조건을 평가하는 것이 아니라 락을 획득한 트랜잭션이 순서대로 실행된다
READ COMMITTED에서 대기하던 트랜잭션은 락 해제 후 갱신된 최신 값을 다시 읽어
WHERE 조건을 재평가한다

즉 조건 확인과 값 증가가 하나의 SQL 안에서 원자적으로 수행되며
갱신 시점의 최신 issued_count를 기준으로 판단하므로
total_quantity를 넘는 갱신은 발생하지 않는다

추가로 CHECK (issued_count <= total_quantity) 제약이
어떤 경로로도 초과 값이 저장되지 않도록 최종적으로 보장한다
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 차감되었지만 실제 발급받은 사용자가 없어 유령 수량이 발생하고, 실제보다 적은 수량만 발급된 채 이벤트가 조기 종료됨 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급받은 사용자는 존재하지만 수량에 반영되지 않아 total_quantity를 초과한 발급이 발생하고, 남은 수량 계산이 실제보다 많게 나타남 |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
Transaction 시작
  |
  v
조건부 UPDATE로 수량 확보
  |
  +-- 영향받은 row 수 = 0
  |     |
  |     v
  |   동일한 (event_id, user_id) coupon_issue 기록 조회
  |     |
  |     +-- 기록 존재 -> 이미 처리된 중복 메시지로 판단
  |     |                 트랜잭션 종료 후 메시지 처리 완료
  |     |
  |     +-- 기록 없음   -> 수량 소진 또는 이벤트 없음
  |                       실패 기록 후 메시지 처리 완료
  |
  +-- 영향받은 row 수 = 1
        |
        v
      coupon_issue INSERT
        |
        +-- 성공         -> Commit -> DB ISSUED
        |
        +-- UNIQUE 위반  -> 트랜잭션 전체 Rollback
                            (issued_count 증가도 함께 취소)
                            새 트랜잭션에서 기존 기록 조회
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 영향받은 row 수가 0이면
--   동일한 발급 기록을 조회해 중복 메시지와 수량 소진을 구분한 뒤
--   INSERT를 실행하지 않고 트랜잭션을 종료한다
SELECT id
FROM coupon_issue
WHERE event_id = :eventId
  AND user_id = :userId;

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status
) VALUES (
    :eventId,
    :userId,
    'ISSUED'
);

-- 두 작업이 모두 성공하면 Commit
COMMIT;

-- INSERT에서 UNIQUE 위반이 발생하면 전체 Rollback
-- ROLLBACK;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

```
현재 트랜잭션은 어떻게 되는가

제약 조건 위반으로 트랜잭션이 오류 상태가 되며 전체를 Rollback해야 한다
PostgreSQL에서는 오류 발생 이후 해당 트랜잭션에서 추가 SQL을 실행할 수 없다

앞에서 증가한 issued_count는 어떻게 되는가

같은 트랜잭션 안에서 수행된 변경이므로 Rollback과 함께 원래 값으로 복구된다
따라서 중복 메시지 때문에 수량이 잘못 차감되는 일은 발생하지 않는다

기존 발급 기록은 언제 조회해야 하는가

Rollback을 완료해 트랜잭션을 종료한 뒤 새로운 트랜잭션에서 조회해야 한다
조회 결과 동일한 (event_id, user_id) 기록이 존재하면
이미 처리된 중복 메시지로 판단해 정상 처리한다
기록이 없다면 예상하지 못한 오류로 처리한다
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
PostgreSQL은 트랜잭션 내에서 오류가 발생하면
해당 트랜잭션을 aborted 상태로 전환한다

이 상태에서는 이후의 모든 명령이
current transaction is aborted 오류로 거부되며
ROLLBACK 또는 SAVEPOINT 복귀만 허용된다

이는 오류가 발생한 트랜잭션이 부분적으로 성공한 것처럼 계속 진행되어
원자성이 깨지는 것을 막기 위한 설계다

따라서 UNIQUE 위반 이후 기존 기록을 조회하려면
반드시 Rollback을 먼저 수행하고 새 트랜잭션을 시작해야 한다
SAVEPOINT를 미리 설정했다면 해당 지점으로 되돌려 이어갈 수도 있다
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
Consumer 정상 처리, 재처리, 관리자 수동 발급, 배치 보정 등
어떤 경로로 발급이 이루어지든 불변식 3은 동일하게 지켜져야 한다

일부 경로만 트랜잭션 밖에서 issued_count를 변경하거나
coupon_issue만 단독으로 INSERT하면
그 경로 하나 때문에 전체 데이터의 정합성이 깨진다

불변식은 가장 약한 경로의 수준까지만 보장되므로
발급 처리 로직을 단일 지점으로 모으고
모든 경로가 동일한 트랜잭션 경계를 사용하도록 설계해야 한다
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
Consumer가 메시지 수신 (offset = N)
  |
  v
DB 발급 트랜잭션 시작
  |
  v
issued_count 증가 + coupon_issue INSERT
  |
  v
Commit -> DB ISSUED (발급 기록 존재)
  |
  v
Consumer Group Offset 커밋 전 Consumer 장애 발생
  |
  v
Consumer Group Rebalance / Consumer 재시작
  |
  v
마지막 커밋된 Offset(N)부터 다시 읽음
  |
  v
동일한 메시지 재처리 시작
  |
  v
같은 (event_id, user_id)로 발급 시도
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
같은 사용자에 대한 coupon_issue 행이 여러 건 INSERT된다

한 사용자가 동일 이벤트 쿠폰을 여러 장 보유하게 되어 불변식 1이 깨진다
재처리마다 issued_count도 함께 증가하므로 수량이 실제보다 빠르게 소진된다
결과적으로 다른 사용자가 받을 수 있었던 쿠폰 기회를 잃는다

애플리케이션이 사전 조회를 하더라도 동시 재처리 상황에서는 막을 수 없으므로
DB 제약이 없으면 중복 발급을 구조적으로 차단할 방법이 없다
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
재처리된 메시지가 동일한 (event_id, user_id)로 INSERT를 시도한다
  |
  v
DB가 UNIQUE 인덱스에서 동일 키의 존재를 확인한다
  |
  v
제약 위반 오류를 발생시켜 INSERT를 거부한다
  |
  v
트랜잭션 전체가 Rollback되어 issued_count 증가도 함께 취소된다
  |
  v
최종적으로 발급 기록은 최초 1건만 남는다

다만 이미 수량이 소진된 상태라면
조건부 UPDATE가 먼저 0을 반환해 INSERT까지 도달하지 않으므로
두 경로를 모두 처리해야 한다
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
1. 위반된 제약이 uk_coupon_issue_event_user임을 확인할 수 있어야 한다
   (PostgreSQL SQLSTATE 23505와 제약 조건 이름으로 식별한다)

2. Rollback 이후 새 트랜잭션에서 동일한 (event_id, user_id) 기록이
   실제로 존재하는지 조회해 확인해야 한다

3. 기존 기록의 event_id와 user_id가 현재 메시지의 값과 일치해야 한다

4. coupon_issue가 최종 발급 성공 기록만 저장한다는 전제가 유지되어야 한다
   (취소나 재발급으로 상태가 바뀌는 정책이 없어야 한다)

위 조건을 모두 만족하면 이미 원하는 결과가 DB에 반영된 상태이므로
오류가 아니라 성공으로 간주하고 메시지 처리를 완료한다
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. 현재 트랜잭션을 Rollback해 aborted 상태를 해제한다
   (issued_count 증가도 함께 취소된다)

2. 새 트랜잭션에서 동일한 (event_id, user_id)의 coupon_issue 기록을 조회한다

3. 기록이 존재하면 이미 처리된 중복 메시지로 판단해 정상 처리로 종료하고
   기록이 없으면 예상하지 못한 오류로 판단해 실패 처리한다

4. 정상 처리로 판단한 경우에만 Consumer Group Offset을 커밋한다
   재시도가 필요한 오류라면 Offset을 커밋하지 않는다
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
Offset을 먼저 커밋하면 해당 메시지는 다시 읽히지 않는다

DB 트랜잭션이 실패하거나 Consumer가 그 사이에 종료되면
발급 요청이 영구적으로 유실된다
Redis는 ACCEPTED로 판정했는데 DB에는 기록이 없는 불일치가 남고
사용자는 성공 안내를 받았지만 쿠폰을 사용할 수 없게 된다

이 유실은 재처리로 복구할 수 없으므로 별도 보정 절차가 필요하다

반대로 DB 처리 후 Offset 커밋 전에 장애가 나면
같은 메시지를 다시 읽게 되지만
UNIQUE 제약과 기존 기록 조회로 안전하게 처리할 수 있다

즉 유실보다 중복이 복구 가능한 실패이므로
at-least-once 전달과 DB 멱등성을 조합하는 것이 안전하다
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
UNIQUE (event_id, user_id)

- 비즈니스 규칙 수준의 멱등성을 제공한다
- 한 사용자가 한 이벤트에서 한 번만 발급받는다는 결과를 보장한다
- 서로 다른 요청이라도 같은 사용자면 동일하게 차단된다
- 요청 단위의 처리 결과나 실패 이유는 알 수 없다
- 사용자당 1회 제약이 없는 도메인에는 적용할 수 없다

requestId 기반 멱등성

- 요청 단위의 멱등성을 제공한다
- 동일한 요청이 몇 번 도달해도 한 번만 처리되고 같은 결과를 반환한다
- 처리 상태와 결과를 저장하므로 재조회 시 이전 응답을 그대로 돌려줄 수 있다
- 사용자당 여러 번 발급 가능한 정책에서도 중복 처리를 막을 수 있다
- 별도의 요청 상태 저장소와 만료 정책이 필요하다

이번 주차는 결과 수준의 멱등성까지 다루고
요청 단위 식별과 결과 관리는 5주차에서 다룬다
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

### **1. 조건부 UPDATE 결과와 그 이유**

```
영향받은 row 수 = 0 이다

WHERE 조건의 issued_count < total_quantity가
1 < 1 이 되어 만족하지 않기 때문이다

이미 수량이 모두 소진된 상태이므로 갱신 대상 row가 없다
```

### **2. coupon_issue INSERT까지 실행되는가?**

```
실행되지 않는다

INSERT는 조건부 UPDATE의 영향받은 row 수가 1일 때만 실행하도록 설계했다
결과가 0이므로 수량을 확보하지 못했고 발급 기록을 남길 수 없다
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```
발생하지 않는다

INSERT 자체가 실행되지 않으므로 UNIQUE 제약을 검사할 기회가 없다

수량이 남아 있었다면 UPDATE가 1을 반환하고 INSERT에서 UNIQUE 위반이 발생했겠지만
품절 상태에서는 그 이전 단계에서 흐름이 멈춘다
따라서 중복 메시지가 항상 UNIQUE 위반으로 드러나는 것은 아니다
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```
결과 0은 조건을 만족하는 row가 없다는 사실만 알려준다

이미 발급을 완료한 사용자의 중복 메시지가 재처리된 경우에도 0이 반환된다
이때 실제 결과는 실패가 아니라 이미 성공이다

이를 품절 실패로 처리하면
사용자에게 잘못된 실패 결과를 안내하게 되고
실패 메트릭과 Redis-DB 불일치 지표가 왜곡된다
불필요한 재시도나 보정 작업을 유발할 수도 있다
```

### **5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유**

```
UPDATE 결과 0만으로는 다음 두 상황을 구분할 수 없다

- 이미 발급이 완료된 사용자의 중복 메시지
- 실제로 수량이 소진되었거나 이벤트가 존재하지 않는 경우

coupon_issue는 최종 발급 결과의 기준 데이터이므로
동일한 (event_id, user_id) 기록의 존재 여부가 두 상황을 구분하는 근거가 된다

기록이 있으면 이미 원하는 결과가 반영된 상태이므로 성공으로 처리하고
기록이 없으면 비즈니스 실패로 처리한다
```

### **6. 다음 두 상황을 구분하는 처리 흐름 작성하기**

```
상황 A : 조건부 UPDATE 결과 = 0, 동일한 coupon_issue 기록 존재

  판단 : 이미 처리된 중복 메시지
  처리 : 추가 DB 변경 없이 트랜잭션 종료
         이미 성공한 요청이므로 성공으로 간주
  메시지 처리 완료 여부 : 완료
  Offset 커밋 여부 : 커밋
  비고 : 중복 소비 메트릭만 기록하고 오류 로그는 남기지 않음

상황 B : 조건부 UPDATE 결과 = 0, 동일한 coupon_issue 기록 없음

  판단 : 실제 수량 소진 또는 이벤트 미존재
  처리 : 발급 실패로 확정
         재시도해도 결과가 달라지지 않는 비즈니스 실패이므로 재처리하지 않음
  메시지 처리 완료 여부 : 완료
  Offset 커밋 여부 : 커밋
  비고 : 실패 사유 로그와 Redis-DB 불일치 메트릭을 남기고
         복구는 8주차의 별도 절차로 위임

공통 원칙

일시적 DB 오류나 네트워크 오류처럼 재시도로 해결 가능한 실패에서는
Offset을 커밋하지 않고 재처리 대상으로 남긴다
```

### **7. 전체 Consumer 처리 흐름 완성하기**

```
Kafka 메시지 수신 (event_id, user_id)
  |
  v
Transaction 시작
  |
  v
조건부 UPDATE
  UPDATE coupon_event
  SET issued_count = issued_count + 1
  WHERE id = :eventId AND issued_count < total_quantity
  |
  +-- 영향받은 row 수 = 0
  |     |
  |     v
  |   동일한 (event_id, user_id) coupon_issue 조회
  |     |
  |     +-- 기록 존재
  |     |     -> 이미 처리된 중복 메시지
  |     |     -> 트랜잭션 종료, 성공 처리
  |     |     -> Offset 커밋
  |     |
  |     +-- 기록 없음
  |           -> 수량 소진 또는 이벤트 없음
  |           -> 비즈니스 실패로 확정
  |           -> 로그 및 메트릭 기록
  |           -> Offset 커밋 (불일치 복구는 별도 절차)
  |
  +-- 영향받은 row 수 = 1
        |
        v
      coupon_issue INSERT (event_id, user_id, 'ISSUED')
        |
        +-- 성공
        |     -> Commit -> DB ISSUED
        |     -> Offset 커밋
        |
        +-- UNIQUE 위반 (SQLSTATE 23505)
        |     -> 트랜잭션 전체 Rollback
        |     -> issued_count 증가도 취소
        |     -> 새 트랜잭션에서 기존 기록 조회
        |         +-- 기록 존재 -> 중복 메시지로 성공 처리 -> Offset 커밋
        |         +-- 기록 없음 -> 예상하지 못한 오류로 처리
        |
        +-- 일시적 DB 오류
              -> Rollback
              -> Offset 커밋하지 않음
              -> 재처리 대상으로 남김
```

## **과제 9. DB 동시성 제어 방식 비교하기**

### **1. 조건부 UPDATE 방식 설명**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;
```

```
수량 확인과 증가를 하나의 SQL로 원자적으로 수행한다

별도의 SELECT나 명시적 락 없이 WHERE 절이 수량 조건을 검사하고
같은 문장에서 값을 증가시킨다
DB가 같은 row의 갱신을 직렬화하고 대기 후 최신 값으로 조건을 재평가하므로
동시 요청에서도 total_quantity를 초과하지 않는다

성공 여부는 영향받은 row 수로 판단하며 애플리케이션 재시도가 필요 없다
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
SELECT id, issued_count, total_quantity
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

-- 애플리케이션에서 issued_count < total_quantity 확인 후

UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId;
```

설명:

```
이벤트 row를 먼저 명시적으로 잠근 뒤 수량을 확인하고 갱신한다

락을 획득한 트랜잭션만 해당 row를 읽고 변경할 수 있으므로
확인과 변경 사이에 다른 트랜잭션이 끼어들 수 없다
처리 순서와 정합성을 이해하기 쉽다

다만 락 유지 구간이 조회부터 Commit까지로 길어지고
요청이 몰리면 대기가 누적되어 처리량이 크게 감소한다
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
-- 1. 현재 상태와 version 조회
SELECT issued_count, total_quantity, version
FROM coupon_event
WHERE id = :eventId;

-- 2. 읽은 version이 그대로일 때만 갱신
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
처음부터 명시적인 락을 잡지 않고 충돌을 사후에 감지한다

읽은 시점의 version과 갱신 시점의 version이 같은지 확인해
그 사이에 다른 트랜잭션이 row를 수정했는지 판단한다
version이 달라졌다면 영향받은 row 수가 0이 되고 갱신은 실패한다

충돌이 감지되면 애플리케이션이 다시 조회한 뒤 재시도해야 한다
충돌이 드문 환경에서는 락 대기 없이 처리량을 확보할 수 있지만
선착순 이벤트처럼 하나의 row에 요청이 집중되면 재시도가 폭증한다
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | WHERE 절의 수량 조건과 증가를 하나의 SQL로 원자 실행함 | SELECT FOR UPDATE로 row를 선점한 뒤 확인하고 갱신함 | 읽은 version과 현재 version이 같을 때만 갱신함 |
| 충돌 시 동작 | 락 해제 후 최신 값으로 조건을 재평가해 영향받은 row 수 0을 반환함 | 락을 획득할 때까지 대기한 뒤 순차적으로 처리함 | 갱신이 실패하고 영향받은 row 수 0을 반환함 |
| 재시도 필요 여부 | 필요 없음 (0이면 수량 소진으로 확정 처리) | 필요 없음 (대기 후 처리되나 타임아웃 시 재시도) | 필요함 (재조회 후 재시도 루프 구현) |
| 장점 | 구현이 단순하고 SQL 한 번으로 끝나며 왕복이 적음 | 처리 순서와 정합성을 직관적으로 이해할 수 있음 | 충돌이 적은 환경에서 락 대기 없이 처리량을 확보함 |
| 단점 | 같은 row에 row lock 대기가 집중되고 실패 원인이 세분화되지 않음 | 락 유지 구간이 길어 처리량이 크게 감소하고 데드락 위험이 있음 | 경합이 심하면 재시도가 폭증하고 처리 지연과 기아 현상이 발생함 |
| 선착순 이벤트 적합성 | 가장 적합함 | 보통 (수량이 적거나 요청이 완만할 때 고려 가능) | 부적합함 (단일 row 경합 구조와 상성이 나쁨) |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
모든 발급 요청이 동일한 coupon_event row를 갱신하므로 hot row가 된다

DB 내부에서 해당 row의 갱신이 직렬화되어 동시 처리량의 상한이 생긴다
트랜잭션이 길수록 락 유지 시간이 늘어 대기 트랜잭션이 누적된다
커넥션 풀이 대기 트랜잭션으로 소진되면 다른 API 요청까지 영향을 받는다
낙관적 락에서는 대기 대신 실패와 재시도가 반복되어 부하가 증폭된다
PostgreSQL에서는 반복 갱신으로 dead tuple이 쌓여 VACUUM 부담도 커진다

따라서 Redis로 대부분의 요청을 앞단에서 걸러내
DB에 도달하는 요청 수 자체를 줄이는 것이 중요하다
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
1. Redis가 이미 대부분의 초과 요청을 차단해 DB에는 소수의 요청만 도달한다

2. SELECT 없이 SQL 한 번으로 수량 확인과 증가를 끝내므로
   트랜잭션 길이와 락 유지 시간이 가장 짧다

3. 영향받은 row 수만으로 성공 여부를 판단할 수 있어 처리 분기가 단순하다

4. 애플리케이션 재시도 루프가 필요 없어 Consumer 로직이 단순해진다

5. UNIQUE 제약, Transaction과 조합해 최소한의 장치로
   세 가지 불변식을 모두 보장할 수 있다
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```
조건부 UPDATE, 비관적 락, 낙관적 락은
동일한 row에 대한 동시 수정을 제어하는 동시성 제어 수단이다
보호 대상은 issued_count라는 집계 값이며 전체 수량 초과를 막는다

UNIQUE 제약은 동시성 제어 수단이 아니라 데이터 무결성 제약이다
보호 대상은 (event_id, user_id) 조합의 유일성이며 사용자 중복 발급을 막는다

| 방식 | 역할 |
| --- | --- |
| 조건부 UPDATE | 남은 수량 확인과 증가를 원자적으로 수행함 |
| 비관적 락 | 같은 row를 수정하는 트랜잭션을 명시적으로 대기시킴 |
| 낙관적 락 | version 변화를 확인해 동시 수정 충돌을 감지함 |
| UNIQUE 제약 | 같은 사용자의 중복 발급을 막음 |

즉 서로 대체 관계가 아니라 보완 관계이므로
이번 구조에서는 조건부 UPDATE + UNIQUE 제약 + Transaction을 함께 사용한다
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

### **1. Redis 통과 후 Kafka 발행 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 사용자 Set에 user_id가 존재하고 잔여 수량도 차감된 상태 |
| Kafka | 발행 실패로 해당 요청의 레코드가 존재하지 않음 |
| DB | issued_count 미증가, coupon_issue 발급 기록 없음 |

```
Redis만 소비되고 요청이 사라진 상태로
수량은 차감되었으나 아무도 발급받지 못한 유실이다
Redis 판정 시점의 보상 처리나 복구 절차가 필요하다
```

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 존재, 잔여 수량 차감됨 |
| Kafka | 발행된 레코드 존재, 해당 Consumer Group Offset 미커밋 |
| DB | issued_count 미증가, coupon_issue 발급 기록 없음 |

```
Offset이 커밋되지 않았으므로 Consumer 재시작 시 같은 메시지를 다시 읽는다
재시도로 복구 가능한 상태이며 at-least-once 전달의 정상적인 동작이다
```

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 없음, 잔여 수량이 초기 상태로 되돌아갈 수 있음 |
| DB | coupon_issue 발급 기록 존재, issued_count 반영 완료 |

```
Kafka는 발행된 레코드가 보존 정책에 따라 유지되며
Offset은 DB 처리 시점에 따라 커밋 또는 미커밋 상태다

Redis만 보면 미발급으로 보이지만 실제로는 발급이 완료된 상태다
Redis를 재구성할 때 DB의 coupon_issue를 기준으로 복구해야 한다
```

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
Redis는 인메모리 저장소로 유실과 초기화, Failover 유실 가능성이 있다
Kafka 레코드는 소비 후 즉시 삭제되지 않고 보존 정책에 따라 유지되므로
레코드 존재 여부가 처리 완료를 의미하지 않는다

반면 DB의 coupon_issue는 트랜잭션 Commit으로 확정된 영속 데이터이며
UNIQUE 제약으로 중복 없이 정확히 한 건만 존재함이 보장된다

따라서 발급 여부 조회, 사용자 안내, 정산, 복구 작업의 기준은
항상 coupon_issue 기록이어야 한다
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순 판정과 사용자 중복 요청 사전 차단 | 발급 요청 메시지의 비동기 전달과 버퍼링 | 최종 발급 기록 저장과 수량 정합성 보장 |
| 저장하는 상태 | 통과 사용자 Set과 잔여 수량 카운터 | 발급 요청 레코드와 Consumer Group Offset | coupon_event.issued_count와 coupon_issue 발급 기록 |
| 성공이 의미하는 것 | Redis 기준 선착순 판정 통과 (ACCEPTED) | 요청 메시지가 브로커에 저장됨 (PUBLISHED) | 발급 트랜잭션 Commit 완료로 최종 발급 성공 (ISSUED) |
| 강점 | 원자적 연산으로 대량 트래픽을 낮은 지연으로 처리함 | 트래픽 급증을 흡수하고 재처리와 확장이 가능함 | 제약 조건과 트랜잭션으로 불변식을 강제함 |
| 한계 | 데이터 유실과 초기화 가능성이 있고 최종 기준이 될 수 없음 | 전달만 보장하며 도메인 처리 결과와 상태를 알지 못함 | 처리량 한계가 있어 단일 row 경합에 취약함 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
4주차의 UNIQUE 제약은 결과 수준의 멱등성만 제공한다
동일 사용자의 중복 발급은 막지만 다음 문제는 해결하지 못한다

- 동일한 요청 자체를 식별할 수 없다
- 이미 처리된 요청의 처리 결과와 실패 사유를 다시 응답할 수 없다
- 사용자가 자신의 요청이 어느 단계까지 진행되었는지 조회할 수 없다
- 사용자당 여러 번 발급 가능한 정책에서는 중복 처리를 막을 수 없다

5주차에서는 requestId로 요청을 식별하고
요청 상태와 결과를 저장해 요청 단위 멱등성을 확보한다
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
DB 저장과 후속 이벤트 발행 사이의 정합성 문제를 해결한다

발급 트랜잭션 Commit 후 CouponIssued 이벤트를 별도로 발행하면
발행 직전 장애 시 발급은 되었으나 알림과 통계 서비스가 이를 알지 못한다
반대로 먼저 발행하고 Commit이 실패하면 발급되지 않은 이벤트가 전파된다

Outbox Pattern은 발급 기록과 발행할 이벤트를
같은 트랜잭션에서 outbox 테이블에 함께 저장하고
별도 프로세스가 outbox를 읽어 Kafka에 발행함으로써
DB 상태와 발행 이벤트가 어긋나지 않도록 보장한다
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
Outbox Pattern은 DB 트랜잭션을 기준으로 동작한다
같은 트랜잭션 안에서 저장된 데이터와 outbox 레코드의 원자성을 보장하는 방식이다

Redis 판정과 최초 Kafka 발행은 DB 트랜잭션 이전 단계에서 일어난다
Redis는 DB 트랜잭션에 참여하지 않는 외부 저장소이므로
Redis 연산을 DB Commit과 함께 롤백하거나 커밋할 수 없다

따라서 Redis 통과 후 Kafka 발행이 실패하는 상황은
Outbox Pattern의 보장 범위 밖이며
API 단계의 보상 트랜잭션, 재시도, 별도 정합성 검증 절차로 해결해야 한다
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
Consumer 처리 실패의 유형별 대응과 복구를 다룬다

- 일시적 DB 오류와 네트워크 오류를 Retry Topic으로 분리해
  정상 메시지 처리를 막지 않으면서 재시도한다
- 반복 실패하거나 재시도로 해결되지 않는 메시지를 DLQ로 격리해
  Consumer 전체가 멈추거나 특정 파티션이 지연되는 상황을 방지한다
- DLQ에 쌓인 메시지를 분석하고 수동 또는 배치로 재처리한다
- 4주차에서 로그와 메트릭으로만 남겨둔 Redis-DB 불일치를
  탐지하고 보정하는 복구 절차를 설계한다
```
