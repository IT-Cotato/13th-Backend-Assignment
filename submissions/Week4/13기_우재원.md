2. Redis 판정 통과가 최종 발급 성공이 아닌 이유
Redis 판정 통과 이후에 Kafka 발행이 실패할 수 있습니다.

4. coupon_event 테이블 DDL 작성하기

CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count INT NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),
    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),
    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);

5. coupon_issue 테이블 DDL 작성하기

CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),
    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),
    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);

과제 6. 발급 트랜잭션과 Rollback 설계하기
1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제

상황,발생하는 데이터 불일치
"issued_count 증가 성공, coupon_issue INSERT 실패",수량은 차감되었으나 이를 수령한 발급 사용자 기록이 누락됩니다.
"coupon_issue INSERT 성공, issued_count 증가 실패","사용자에게 쿠폰이 정상 지급되었으나, 전체 집계 수량에 반영되지 않아 초과 발급의 원인이 됩니다."

2. 하나의 트랜잭션으로 처리하는 전체 흐름
Transaction 시작 ➔ 조건부 UPDATE로 수량 확보 시도 ➔ 결과가 1일 때만 coupon_issue에 INSERT 수행 ➔ 두 과정이 모두 에러 없이 완료되면 DB Commit, 예외 발생 시 Rollback 처리합니다.

3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기

BEGIN;

UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- UPDATE 결과가 1일 때만 실행한다.
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status
) VALUES (
    :eventId,
    :userId,
    'ISSUED'
);

COMMIT;

4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우
현재 트랜잭션은 어떻게 되는가? 에러가 발생하여 트랜잭션 전체가 롤백(Rollback) 됩니다.

앞에서 증가한 issued_count는 어떻게 되는가? 롤백에 의해 함께 취소되어 원상 복구됩니다.

기존 발급 기록은 언제 조회해야 하는가? 롤백 처리를 마친 뒤, 새로운 트랜잭션을 열어서 기존 기록 존재 여부를 조회해야 합니다.

5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유
PostgreSQL의 특성상 트랜잭션 내에서 한 번 제약 조건 위반 등의 에러가 발생하면, 해당 트랜잭션은 즉시 Aborted 상태가 되어 추가 쿼리를 수행할 수 없으므로 무조건 롤백 후 새 트랜잭션을 시작해야 하기 때문입니다.

6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유
카운터 증가와 기록 삽입 중 하나라도 실패했을 때 두 작업을 동시에 무효화하여 시스템 내에 반쪽짜리 불일치 데이터가 남는 것을 원천 방어하기 위해서입니다.

![alt text](image-5.png)

2. DB에 UNIQUE 제약이 없다면 발생하는 문제
재처리된 메시지가 별도의 필터링 없이 그대로 INSERT 되어, 동일한 사용자가 같은 이벤트의 쿠폰을 여러 장 소유하게 되는 치명적 중복 발급 사태가 벌어집니다.

3. UNIQUE(event_id, user_id)가 중복 소비를 방어하는 과정
중복 전달된 메시지가 coupon_issue 테이블에 다시 삽입을 시도할 때, 데이터베이스가 고유 키 위반 에러를 발생시켜 두 번째 저장을 물리적으로 차단합니다.

4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건
에러 발생 후 롤백을 수행한 뒤, 독립된 트랜잭션으로 다시 조회해 보았을 때 해당 (event_id, user_id)로 커밋된 발급 기록이 명확히 존재할 때입니다.

5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서
현재 진행 중이던 트랜잭션을 Rollback 처리합니다.

새로운 트랜잭션 영역에서 기존 발급 기록을 조회합니다.

기록이 존재하면 이를 단순 중복 메시지로 판단하여 에러 없이 정상 처리, 즉 skip으로 간주합니다.

정상 처리된 것으로 간주한 후 Consumer Group Offset을 커밋하여 메시지를 비웁니다.

6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유
메시지 오프셋이 먼저 커밋된 직후 DB 쓰기 도중 에러가 발생해 롤백될 경우, Kafka 큐에서는 이미 읽은 것으로 표기되어 해당 요청은 영영 유실(Loss)되기 때문입니다.

7. UNIQUE(event_id, user_id)와 requestId 기반 멱등성의 차이
UNIQUE 제약조건은 특정 사용자가 2개 이상의 쿠폰을 가지지 못하게 막는 도메인 비즈니스 규칙 방어 수단입니다. 반면, requestId는 어떤 클라이언트의 통신 요청 자체를 유일하게 식별하고 재시도에 동일한 응답을 주기 위한 시스템 멱등성 보장 수단으로 역할이 분리됩니다.

과제 8. 품절 후 중복 메시지 재처리 분석하기
1. 조건부 UPDATE 결과와 그 이유
결과는 0입니다. 이미 전체 허용 수량 1개 중 1개가 모두 발급되어 issued_count < total_quantity 조건에 부합하지 않아 업데이트되는 행이 없기 때문입니다.

2. coupon_issue INSERT까지 실행되는가?
실행되지 않습니다. 선행 조건부 UPDATE 쿼리의 반환 결과가 0이므로, 애플리케이션 로직 상 다음 삽입 단계로 진입하지 않습니다.

3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?
발생하지 않습니다. INSERT 쿼리 자체가 시도되지 않았으므로 제약 조건 검증 단계에 도달하지 않습니다.

4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유
순수한 품절 혹은 이벤트 미존재로 인해 실패했을 수도 있지만, Kafka의 재전송으로 인한 이미 처리 완료된 중복 메시지여서 조건에 걸렸을 가능성도 배제할 수 없기 때문입니다.

5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유
조건부 업데이트 결과가 0으로 나타났을 때, 이것이 "내가 이전에 받아간 중복 메시지라 막힌 것"인지 아니면 "정말 수량이 꽉 차서 실패한 것"인지를 명확히 구분해야 올바른 예외 또는 Offset 처리를 할 수 있기 때문입니다.

6. 다음 두 상황을 구분하는 처리 흐름 작성하기
상황 A (조건부 UPDATE 0, 기존 기록 존재): 이미 정상적으로 완료된 메시지가 중복 인입된 것으로 간주합니다. 메시지 처리가 무사히 끝난 것으로 표기하고 Consumer Group Offset을 커밋합니다.

상황 B (조건부 UPDATE 0, 기존 기록 없음): 실제로 이벤트 수량이 소진되었거나, 이벤트 자체가 없어서 발급에 실패한 비즈니스 예외 상황입니다. 별도의 실패 로그와 메트릭을 남긴 뒤 Offset을 커밋하여 큐를 비웁니다.

7. 전체 Consumer 처리 흐름 완성하기
조건부 UPDATE 실행 ➔ 결과가 1인 경우 INSERT 실행 (여기서 UNIQUE 위반 시 트랜잭션 롤백 후 조회 과정을 거쳐 중복 판단) ➔ 결과가 0인 경우 기존 발급 이력을 SELECT 하여 이력이 존재하면 중복 스킵, 없으면 영구 품절 예외로 처리합니다.

과제 9. DB 동시성 제어 방식 비교하기
1. 조건부 UPDATE 방식 설명
별도의 명시적인 데이터베이스 락을 설정하지 않고, 단일 UPDATE 쿼리 내의 WHERE 조건절로 검증과 수량 차감을 원자적으로 묶어서 해결하는 방식입니다.

2. 비관적 락 방식 설명과 SQL 예시

SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

설명: 데이터 정합성을 강하게 보장하기 위해 트랜잭션 시작과 동시에 해당 데이터 행에 베타 락을 선점하여 다른 트랜잭션의 접근과 수정을 강제로 대기시키는 방식입니다.

3. 낙관적 락 방식 설명과 SQL 예시

UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;

  설명: 데이터를 읽을 당시의 version 값을 기억해두고, 업데이트 시점에 버전이 변경되었는지 대조하여 동시 수정을 감지해 내는 어플리케이션 레벨의 방식입니다.

4. 세 방식 비교표

구분,조건부 UPDATE,비관적 락,낙관적 락
수량을 보호하는 방법,WHERE 절 조건 필터링,행 단위 물리적 DB 잠금,데이터 version 컬럼 대조
충돌 시 동작,DB 내부 직렬화 후 0 반환,이전 트랜잭션 종료 시까지 무한 대기,어플리케이션 충돌 에러 반환
재시도 필요 여부,불필요,불필요 (자동 대기),필수적으로 재시도 로직 필요
장점,구현이 단순하고 별도 락 대기가 없음,일관성을 파악하기 매우 직관적임,충돌이 적을 땐 락 성능 오버헤드가 없음
단점,갱신 집중 시 DB 내부 병목 유발,요청 폭주시 대기열 적체 및 처리량 하락,잦은 충돌 발생 시 재시도로 인한 오버헤드 큼
선착순 이벤트 적합성,적합,부적합,부적합

5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제
단일 레코드에 동시 접근이 과도하게 쏠리면 비관적 락의 대기열 큐가 길어져 타임아웃이 나거나, 낙관적 락의 경우 계속된 충돌과 재시도 루프로 인해 컴퓨팅 리소스가 폭발하는 문제(Thundering Herd)가 발생합니다.

6. 이번 구조에서 조건부 UPDATE를 선택하는 이유
어플리케이션 단의 조회나 지루한 락 대기, 복잡한 재시도 로직을 작성할 필요 없이, 가장 단순한 쿼리 하나로 데이터베이스 벤더가 보장하는 원자적 직렬화를 활용해 깔끔하게 방어할 수 있기 때문입니다.

7. 세 방식과 UNIQUE 제약의 역할이 다른 이유
위 세 가지 방식은 한정된 자원인 전체 파이(수량)를 공통으로 깎아나갈 때 원자성을 보장하기 위함이고, UNIQUE 제약은 개인 유저가 동일한 파이를 2번 이상 중복으로 가져가지 못하게 개별 권한을 검증하기 위함입니다.

과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기
1. Redis 통과 후 Kafka 발행 실패 상황

시스템,남아 있는 상태
Redis,통과 기록이 세트에 그대로 존재함
Kafka,발행 실패로 해당 레코드 없음
DB,큐에 없으므로 발급 기록 없음

2. Kafka 발행 후 DB 저장 실패 상황

시스템,남아 있는 상태
Redis,통과 기록 존재함
Kafka,"발행된 레코드가 존재하며, Consumer Group Offset은 미커밋 상태"
DB,에러 롤백으로 인해 발급 기록 없음

3. DB 저장 후 Redis 데이터 유실 상황

시스템,남아 있는 상태
Redis,재시작 등 유실로 통과 기록이 없음
DB,이미 정상 처리되어 발급 기록이 확정 존재함

4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유
Redis나 Kafka는 비동기 처리의 유속을 조절하기 위한 상태 및 버퍼 저장소이므로 부분 실패와 초기화의 위험이 상존합니다. 따라서 영구 속성을 지닌 DB의 레코드를 유일한 원천 데이터(SSOT) 기준으로 보아야 합니다.

5. Redis, Kafka, DB의 역할 비교표

구분,Redis,Kafka,DB

6. 5주차 requestId 기반 멱등성에서 해결할 문제
순수한 네트워크 지연이나 재시도로 인해 파생된, 동일한 requestId를 지닌 반복 요청들을 식별하고 이미 확정된 기존 응답 상태를 안전하게 돌려주는 시스템 멱등성 제어를 구현합니다.

7. 6주차 Outbox Pattern에서 해결할 문제
DB에 쿠폰이 저장되는 트랜잭션과 그 이후 파생 이벤트를 브로커에 쏘아 올리는 행위 사이에서 발생하는 정합성 훼손을, 단일 로컬 트랜잭션 테이블 기법으로 완벽히 묶어서 보장합니다.

8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유
Outbox Pattern은 발급이 확정된 DB 저장 시점과 그 이후의 후속 이벤트 전파 사이의 트랜잭션을 일치시키는 아키텍처이지, 단순 인메모리 필터망(Redis)과 브로커(Kafka)의 네트워크 갭을 묶어주는 용도가 아니기 때문입니다.

9. 8주차 Retry와 DLQ에서 해결할 문제
네트워크 순단이나 일시적 데이터베이스 락 등의 오류로 실패한 메시지를 안전하게 재시도하고, 영구적 에러 메시지는 별도의 DLQ로 빼서 큐 막힘 현상을 복구 및 수동 처리하는 방안을 배웁니다.
