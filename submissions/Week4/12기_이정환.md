# **4주차 과제: DB 테이블과 최종 발급 정합성 보장**

## **1. 과제 목표**

이번 과제의 목표는 **Redis와 Kafka를 통과한 쿠폰 발급 요청을 DB에 정확하게 저장하고, 사용자 중복 발급과 전체 수량 초과를 방지하는 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

이번 4주차에서는 Consumer가 Kafka 메시지를 읽은 뒤 DB에 최종 발급 기록을 저장하는 단계를 설계한다.

기본 흐름은 다음과 같다.

```text
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
ACCEPTED인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB Transaction
  ├─ coupon_event.issued_count 증가
  └─ coupon_issue 발급 기록 저장
```

`Redis ACCEPTED`는 3주차의 `Redis SUCCESS`와 같은 단계다. 최종 발급 성공과 구분하기 위해 이번 주차에서는 `ACCEPTED`로 표기한다.

이번 과제의 핵심은 다음과 같다.

```text
Redis는 빠른 선착순 판정을 담당한다.

Kafka는 발급 요청 메시지를 전달한다.

DB는 최종 발급 기록을 저장하고 수량 정합성을 보장한다.
```

## **과제 1. DB 최종 발급 처리 구조 그리기**

### **1. 전체 요청 처리 흐름 다이어그램**

```text
┌──────────────┐
│    Client    │
└──────┬───────┘
       │ ① 쿠폰 발급 요청
       ▼
┌──────────────┐
│  API Server  │
└──────┬───────┘
       │ ② 인증·이벤트 기본 검증
       ▼
┌──────────────┐
│    Redis     │  ③ 사용자 중복·잔여 수량 원자적 판정
└──────┬───────┘
       │ ACCEPTED 요청만 통과
       ▼
┌──────────────┐
│  API Server  │  ④ coupon.issue.requested 발행
└──────┬───────┘
       ▼
┌──────────────┐
│    Kafka     │  ⑤ 발급 요청 메시지 전달
└──────┬───────┘
       ▼
┌────────────────────────┐
│ Coupon Issue Consumer  │
└───────────┬────────────┘
            │ ⑥ DB Transaction
            ▼
┌──────────────────────────────────────┐
│ coupon_event 조건부 UPDATE           │
│              +                       │
│ coupon_issue INSERT                  │
└──────────────────┬───────────────────┘
                   │ Commit 성공
                   ▼
            ┌─────────────┐
            │  DB ISSUED  │
            └──────┬──────┘
                   │
                   ▼
              Offset Commit
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```text
Redis ACCEPTED는 Redis가 가진 데이터 기준으로 중복과 수량 검사를 통과했다는
뜻일 뿐이다. 이후 Kafka 발행 실패, Consumer 장애, DB 오류 또는 DB 제약 위반이
발생할 수 있으므로 coupon_issue 트랜잭션이 커밋되기 전에는 최종 발급이 아니다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```text
Kafka PUBLISHED는 발급 요청 레코드가 브로커에 저장되었다는 뜻이다.
Consumer가 아직 읽지 않았거나, 읽은 뒤 DB 트랜잭션을 실패할 수 있으므로
메시지 발행 성공 자체는 쿠폰 발급 성공을 의미하지 않는다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```text
coupon_event.issued_count 증가와 coupon_issue INSERT가 포함된 하나의
DB 트랜잭션이 Commit된 시점이다. 이때의 상태를 DB ISSUED로 판단한다.
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준 선착순·중복 판정 통과 | 아니오 |
| Kafka PUBLISHED | 발급 요청 레코드가 Kafka에 저장됨 | 아니오 |
| DB ISSUED | 발급 기록 저장 트랜잭션이 Commit됨 | 예 |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

### **1. 불변식이 필요한 이유**

```text
동시 요청, 메시지 중복 소비, Redis 데이터 유실 및 애플리케이션 장애가
발생하더라도 쿠폰 발급 데이터가 항상 유효한 상태를 유지해야 하기 때문이다.
애플리케이션의 검사만으로는 동시 실행을 완전히 통제할 수 없으므로 최종
저장소인 DB가 제약과 트랜잭션으로 불변식을 보장해야 한다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 같은 사용자가 같은 이벤트 쿠폰을 여러 장 받음 |
| 전체 수량 이하 발급 | 약속한 수량보다 많은 쿠폰이 발급됨 |
| 수량과 발급 기록의 동시 성공·실패 | issued_count와 실제 발급 사용자 수가 달라짐 |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | `UNIQUE(event_id, user_id)` |
| 전체 수량 초과 방지 | 조건부 `UPDATE`와 수량 `CHECK` |
| 두 테이블의 일관성 | 하나의 DB Transaction |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```text
Transaction A와 B가 동시에 조회하면 둘 다 아직 발급 기록이 없다고 볼 수 있다.
그 뒤 두 트랜잭션이 INSERT하면 애플리케이션의 사전 검사는 모두 통과한다.
이러한 check-then-act Race Condition의 최종 방어는 DB UNIQUE 제약이어야 한다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

### **1. coupon_event 테이블의 역할**

```text
쿠폰 이벤트의 이름, 전체 수량, DB에서 최종 발급된 수량, 운영 기간과 상태를
저장한다. 조건부 UPDATE의 대상이 되어 전체 발급 수량 초과를 방어한다.
```

### **2. coupon_issue 테이블의 역할**

```text
어떤 사용자가 어떤 이벤트의 쿠폰을 최종 발급받았는지 저장하는 기준 데이터다.
이번 과제에서는 발급에 성공해 상태가 ISSUED인 기록만 저장한다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```text
┌─────────────────────────┐             ┌─────────────────────────┐
│      coupon_event       │             │      coupon_issue       │
├─────────────────────────┤             ├─────────────────────────┤
│ PK  id                  │  1       N  │ PK  id                  │
│     name                │────────────<│ FK  event_id            │
│     total_quantity      │             │ UK  (event_id, user_id) │
│     issued_count        │             │     status              │
│     start_at / end_at   │             │     issued_at           │
│     status / version    │             └─────────────────────────┘
└─────────────────────────┘

관계:
coupon_event 하나에는 coupon_issue가 0개 이상 연결될 수 있다.
coupon_issue 하나는 반드시 하나의 coupon_event를 참조한다.
```

### **4. coupon_event 테이블 DDL 작성하기**

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count INT NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),
    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),
    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

### **5. coupon_issue 테이블 DDL 작성하기**

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),
    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),
    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```text
이유:
- coupon_issue를 매번 COUNT하지 않고 잔여 수량과 발급 현황을 빠르게 조회한다.
- 하나의 조건부 UPDATE로 DB에서도 전체 수량 초과를 방어한다.
- Redis의 통과 수와 DB의 최종 발급 수를 비교할 수 있다.

단점:
- coupon_issue로부터 계산할 수 있는 값을 중복 저장한다.
- 두 값이 어긋날 위험이 있으므로 수량 증가와 INSERT를 반드시 같은
  트랜잭션에서 처리하고 필요하면 정합성 점검·복구 절차를 운영해야 한다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```text
동일한 이벤트에서 동일한 사용자의 발급 기록은 최대 한 행만 존재할 수 있다.
한 사용자가 서로 다른 이벤트에 참여하거나 서로 다른 사용자가 같은 이벤트에
참여하는 것은 허용한다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 `event_id=100, user_id=10`이다.

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | 기존 행과 두 컬럼의 조합이 같아 UNIQUE 위반 |
| event_id=100, user_id=11 | 성공 | user_id가 달라 조합이 다름 |
| event_id=101, user_id=10 | 성공 | event_id가 달라 조합이 다름 |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

```text
시간      Transaction A                       Transaction B
──────────────────────────────────────────────────────────────────
T1        SELECT (100, 10)
          └─ 결과: 없음

T2                                            SELECT (100, 10)
                                              └─ 결과: 없음

T3        INSERT (100, 10)
          └─ 성공

T4                                            INSERT (100, 10)
                                              ├─ UNIQUE 없음: 성공
                                              └─ UNIQUE 있음: 실패
──────────────────────────────────────────────────────────────────
결론      두 트랜잭션이 모두 "없음"을 읽을 수 있으므로 SELECT만으로는
          중복을 막을 수 없다. 최종 방어는 DB UNIQUE 제약이 담당한다.
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

```text
서로 다른 사용자 1,001명의 (event_id, user_id) 조합은 전부 다르므로
UNIQUE 검사를 모두 통과할 수 있다. UNIQUE는 조합의 중복만 검사하며
이벤트 전체 행 개수나 total_quantity와의 관계는 검사하지 않는다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | `UNIQUE(event_id, user_id)` |
| 서로 다른 사용자에 의한 전체 수량 초과 | `issued_count < total_quantity` 조건부 UPDATE |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

### **1. 조건부 UPDATE SQL 작성하기**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```text
WHERE 조건을 만족해 실제 갱신된 coupon_event 행의 수다.
id가 PK이므로 이 SQL의 결과는 0 또는 1이며, Consumer는 이 값으로
DB 수량을 확보했는지 판단한다.
```

### **3. 영향받은 row 수가 1인 경우**

```text
이벤트가 존재하고 실행 시점에 issued_count가 total_quantity보다 작아서
수량 하나를 확보했다는 뜻이다. 같은 트랜잭션에서 coupon_issue INSERT를
계속 수행한다.
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

```text
1. 해당 event_id의 coupon_event가 존재하지 않는다.
2. 이벤트는 존재하지만 issued_count가 total_quantity와 같아 소진되었다.

중복 메시지는 이 UPDATE가 0이 되는 직접 원인이 아니다. UPDATE 이후 동일한
coupon_issue를 조회해 이미 처리된 메시지인지 별도로 구분한다.
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | issued_count가 1,000으로 증가 |
| B | 1,000 | 1,000 | 존재 | 0 | 수량 조건 불충족, 변경 없음 |
| C | - | - | 존재하지 않음 | 0 | id 조건에 맞는 행 없음 |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```text
초기 issued_count = 999, total_quantity = 1,000

시간      Transaction A                       Transaction B
──────────────────────────────────────────────────────────────────
T1        조건부 UPDATE 실행                  조건부 UPDATE 실행

T2        이벤트 row lock 획득                같은 row lock 대기
          999 < 1,000 → TRUE                  ··· WAIT ···

T3        issued_count = 1,000
          영향받은 row 수 = 1
          COMMIT 후 lock 해제

T4                                            row lock 획득
                                              최신 값으로 조건 재평가
                                              1,000 < 1,000 → FALSE
                                              영향받은 row 수 = 0
──────────────────────────────────────────────────────────────────
결과      A: 마지막 수량 확보 성공            B: 수량 확보 실패

※ 실행 순서는 바뀔 수 있지만 둘 중 한 트랜잭션만 성공한다.
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```text
PostgreSQL은 같은 행의 UPDATE를 직렬화한다. 대기한 트랜잭션은 앞선 변경이
확정된 최신 행을 기준으로 WHERE 조건을 다시 평가하므로 마지막 한 개를 두
트랜잭션이 동시에 차지할 수 없다. CHECK 제약도 잘못된 값의 저장을 방어한다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 차감되었지만 실제 발급 사용자가 없음 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급 기록은 있지만 발급 수량에 반영되지 않음 |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```text
┌────────────────────┐
│ Transaction 시작   │
└─────────┬──────────┘
          ▼
┌────────────────────┐
│ 조건부 UPDATE      │
└─────────┬──────────┘
          │
     ┌────┴────┐
     │         │
 결과 = 0   결과 = 1
     │         │
     ▼         ▼
┌──────────┐  ┌────────────────────┐
│ 기존 발급│  │ coupon_issue       │
│ 기록 조회│  │ INSERT             │
└────┬─────┘  └─────────┬──────────┘
     │              ┌───┴────┐
     │              │        │
     ▼            성공      실패
중복 메시지/         │        │
실제 실패 구분       ▼        ▼
                  COMMIT   ROLLBACK
                           (수량 증가도 취소)
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
BEGIN;

UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 애플리케이션이 영향받은 row 수가 1인지 확인한 경우에만 실행
INSERT INTO coupon_issue (event_id, user_id, status)
VALUES (:eventId, :userId, 'ISSUED');

COMMIT;

-- 중간 오류 또는 제약 위반 시 COMMIT 대신 ROLLBACK
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

```text
PostgreSQL의 현재 트랜잭션은 오류 상태가 되어 Commit할 수 없다.
반드시 Rollback해야 하며, 같은 트랜잭션에서 먼저 증가시킨 issued_count도
원래 값으로 복구된다. Rollback이 완료된 뒤 새 트랜잭션에서 동일한
(event_id, user_id) 발급 기록을 조회해 중복 메시지인지 확인해야 한다.
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```text
PostgreSQL은 한 문장에서 오류가 발생하면 해당 트랜잭션을 aborted 상태로
표시한다. 이후 SQL은 current transaction is aborted 오류가 발생하므로
ROLLBACK 또는 savepoint를 이용한 복구 전에는 정상 SQL을 실행할 수 없다.
이번 흐름에서는 전체 원자성을 위해 트랜잭션을 Rollback한 뒤 다시 조회한다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```text
어떤 경로라도 수량 증가와 발급 기록 저장을 따로 수행하면 두 데이터가
불일치할 수 있고, 그 경로를 통해 수량 제한이나 중복 방어를 우회할 수 있다.
API, Consumer, 운영 도구 등 모든 발급 진입점이 같은 서비스 규칙과
트랜잭션 경계를 사용해야 불변식이 항상 유지된다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```text
┌───────────────────────────────┐
│ ① Kafka 메시지 수신          │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ ② DB 발급 Transaction Commit │
└───────────────┬───────────────┘
                ▼
        ┌──────────────────┐
        │ ③ 장애 발생      │
        │ Offset 미커밋    │
        └────────┬─────────┘
                 ▼
┌───────────────────────────────┐
│ ④ Consumer 재시작            │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ ⑤ 마지막 Commit Offset부터   │
│    메시지 다시 소비           │
└───────────────┬───────────────┘
                ▼
┌───────────────────────────────┐
│ 동일한 (event_id, user_id)    │
│ 메시지 재처리                 │
└───────────────────────────────┘

DB에는 이미 발급 기록이 있으므로 UNIQUE 제약과 기존 기록 조회를 통해
"새 발급"이 아니라 "이미 처리된 메시지"로 판정한다.
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```text
재처리된 메시지가 coupon_issue에 다시 INSERT되어 같은 사용자가 같은
이벤트 쿠폰을 여러 번 발급받을 수 있다. issued_count도 중복으로 증가하여
정상 사용자가 받을 수 있는 수량까지 잘못 소모된다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```text
재처리 시 수량이 남아 있으면 조건부 UPDATE 이후 INSERT가 실행된다.
기존 발급 행과 같은 키이므로 UNIQUE 위반이 발생하고 트랜잭션 전체가
Rollback되어 임시로 증가한 issued_count도 복구된다. 수량이 이미 소진된
경우에는 UPDATE가 0이므로 기존 발급 기록을 조회해 중복임을 확인한다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```text
Rollback 후 새 트랜잭션에서 동일한 event_id와 user_id의 ISSUED 기록이
실제로 존재하는지 확인해야 한다. 해당 기록이 확인될 때만 이미 성공한
발급의 재처리로 판단한다. 기록이 없다면 예상하지 못한 데이터 또는 제약
오류이므로 정상 중복으로 삼키지 않고 오류로 처리한다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```text
1. 제약 위반이 발생한 현재 DB 트랜잭션을 Rollback한다.
2. 새 트랜잭션에서 동일한 coupon_issue 기록을 조회한다.
3. 기록이 있으면 이미 처리된 메시지로 정상 완료하고 Offset을 커밋한다.
4. 기록이 없으면 예상하지 못한 오류로 분류하고 Offset을 커밋하지 않아
   재시도 또는 이후 Retry/DLQ 정책으로 처리한다.
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```text
Offset을 먼저 커밋한 뒤 DB 처리가 실패하면 Consumer가 재시작되어도 해당
메시지를 다시 읽지 않는다. 발급 요청이 영구적으로 유실될 수 있으므로
DB Commit 또는 이미 처리됨이 확인된 후에만 Offset을 커밋해야 한다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```text
UNIQUE(event_id, user_id)는 같은 사용자에게 같은 이벤트 쿠폰을 한 번만
발급하는 비즈니스 불변식을 보장한다. requestId는 동일한 요청 메시지 자체를
식별하여 처리 상태와 이전 결과를 재사용하는 요청 단위 멱등성이다.
서로 다른 requestId라도 같은 사용자·이벤트이면 UNIQUE에 의해 하나만
발급되며, 같은 requestId의 재처리 결과 관리는 5주차 범위다.
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

### **1. 조건부 UPDATE 결과와 그 이유**

```text
영향받은 row 수는 0이다. 현재 issued_count와 total_quantity가 모두 1이라
issued_count < total_quantity 조건이 거짓이기 때문이다.
```

### **2. coupon_issue INSERT까지 실행되는가?**

```text
실행되지 않는다. 설계상 조건부 UPDATE 결과가 1일 때만 INSERT를 수행한다.
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```text
발생하지 않는다. INSERT 문 자체가 실행되지 않으므로 UNIQUE 제약을
검사하는 단계까지 도달하지 않는다.
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```text
이번 메시지는 실제 품절 때문에 처음 실패한 요청일 수도 있지만, 이미 발급에
성공한 user:10의 메시지가 다시 전달된 것일 수도 있다. UPDATE 결과만으로는
두 상황을 구분할 수 없다.
```

### **5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유**

```text
동일한 (event_id, user_id)의 ISSUED 기록이 있으면 현재 요청은 이미 성공한
처리의 중복이므로 성공과 동등하게 완료할 수 있다. 기록이 없으면 이벤트
없음 또는 실제 수량 소진이라는 비즈니스 실패로 분류해야 한다.
```

### **6. 다음 두 상황을 구분하는 처리 흐름 작성하기**

```text
상황 A: UPDATE = 0, 동일 coupon_issue 존재
  → 이미 최종 발급된 메시지의 재처리
  → 메시지를 정상 처리 완료
  → Consumer Group Offset 커밋

상황 B: UPDATE = 0, 동일 coupon_issue 없음
  → 이벤트 없음 또는 실제 수량 소진
  → 비즈니스 실패 로그·메트릭 및 필요한 실패 기록 생성
  → 같은 메시지의 재시도로 해결되지 않으므로 처리 완료
  → Consumer Group Offset 커밋
  → Redis-DB 불일치는 별도 복구 절차의 대상으로 남김

단, 조회 자체의 DB 장애처럼 결과가 확정되지 않은 기술적 실패에서는
Offset을 커밋하지 않고 재시도한다.
```

### **7. 전체 Consumer 처리 흐름 완성하기**

```text
┌───────────────────┐
│ Kafka 메시지 수신 │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Transaction 시작  │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 조건부 UPDATE     │
└─────────┬─────────┘
          │
   ┌──────┴──────┐
   │             │
결과 = 0      결과 = 1
   │             │
```

## **과제 9. DB 동시성 제어 방식 비교하기**

### **1. 조건부 UPDATE 방식 설명**

```text
수량 확인과 증가를 하나의 UPDATE로 원자적으로 실행한다. 영향받은 row 수가
1이면 확보 성공, 0이면 확보 실패다. 별도 SELECT가 없어 구현이 단순하지만
같은 이벤트 행에 요청이 집중되면 내부 row lock 대기가 발생한다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

-- 락을 획득한 뒤 수량을 확인하고 UPDATE와 INSERT 수행
```

설명:

```text
이벤트 행을 먼저 배타적으로 잠근 뒤 애플리케이션이 수량을 검사하고 갱신한다.
동시에 접근한 다른 트랜잭션은 락이 해제될 때까지 기다리므로 흐름이 명확하다.
그러나 트랜잭션이 길거나 요청이 집중되면 대기 시간과 처리량 저하가 커진다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```text
조회 시 얻은 version과 UPDATE 시점의 version이 같은 경우에만 갱신한다.
다른 트랜잭션이 먼저 수정하면 영향받은 행이 0이 되어 충돌을 감지하며,
호출자는 최신 값을 다시 읽어 재시도해야 한다. 충돌이 적으면 유리하지만
선착순 이벤트처럼 하나의 행에 쓰기가 몰리면 재시도가 급증한다.
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | WHERE 조건과 증가를 한 SQL로 수행 | `FOR UPDATE`로 행을 먼저 잠금 | version 일치 여부로 충돌 감지 |
| 충돌 시 동작 | row lock 대기 후 최신 조건 재평가 | 락 해제까지 대기 | UPDATE 0건으로 실패 |
| 재시도 필요 여부 | 일반적으로 불필요 | 일반적으로 불필요 | 충돌 시 필요 |
| 장점 | 단순하고 왕복이 적음 | 처리 순서와 정합성이 명확함 | 충돌이 적을 때 긴 락 대기를 줄임 |
| 단점 | 인기 행의 락 대기 | 긴 트랜잭션에서 처리량 저하 | 충돌 시 재조회·재시도 비용 |
| 선착순 이벤트 적합성 | 높음 | 정합성은 높으나 대기 부담 | 충돌이 많아 상대적으로 낮음 |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```text
모든 트랜잭션이 동일한 coupon_event 행을 변경하므로 해당 행이 직렬화 지점,
즉 hot row가 된다. row lock 대기, 응답 지연, DB 연결 점유와 처리량 저하가
발생할 수 있다. Redis가 앞단에서 대부분의 요청을 제한하여 DB 경쟁을
줄이지만 DB의 마지막 정합성 검사는 제거할 수 없다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```text
수량 확인과 증가를 단일 SQL로 처리해 애플리케이션 재시도 로직이 단순하고,
영향받은 row 수로 성공 여부를 바로 알 수 있다. Redis가 대부분의 초과
요청을 먼저 거르므로 DB에서는 조건부 UPDATE를 최종 방어선으로 사용하는
구성이 구현 복잡도와 정합성 사이에서 적절하다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```text
세 동시성 제어 방식은 여러 트랜잭션이 같은 이벤트의 수량 행을 수정할 때
전체 수량을 보호한다. UNIQUE 제약은 수량 경쟁과 별개로 같은 사용자와
이벤트 조합의 중복 발급을 막는다. 따라서 한 방식을 선택해도 UNIQUE는
대체되지 않으며 두 종류의 방어를 함께 사용해야 한다.
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

### **1. Redis 통과 후 Kafka 발행 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 사용자 통과 Set 및 수량 차감 기록 존재 |
| Kafka | 발행된 레코드 없음 |
| DB | 발급 기록 없음 |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 존재 |
| Kafka | 발행 레코드 존재, 처리 미확정이면 Consumer Group Offset 미커밋 |
| DB | 커밋된 발급 기록 없음 |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록이 유실되어 없음 |
| DB | 최종 발급된 coupon_issue와 증가한 issued_count 존재 |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```text
Redis는 빠른 판정을 위한 임시 상태이고 Kafka는 요청 레코드와 소비 위치를
관리하는 전달 시스템이다. 실제 발급 불변식과 최종 발급 기록은 DB 제약 및
트랜잭션으로 확정되므로 coupon_issue의 커밋 여부가 최종 기준이어야 한다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순·중복 판정 | 발급 요청 전달과 재처리 | 최종 발급 및 정합성 보장 |
| 저장하는 상태 | 통과 사용자와 임시 수량 | 요청 레코드와 Group Offset | 이벤트 수량과 발급 기록 |
| 성공이 의미하는 것 | 판정 통과 | 레코드 발행 성공 | 발급 트랜잭션 Commit |
| 강점 | 낮은 지연, 원자적 빠른 연산 | 비동기 처리, 내구성과 확장성 | 제약·트랜잭션 기반 정합성 |
| 한계 | 유실·초기화 및 타 시스템과 불일치 | 중복 전달 가능, 발급 자체를 확정하지 않음 | 인기 행의 경합과 상대적으로 높은 비용 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```text
동일 requestId의 요청이 반복되었는지 식별하고, 요청의 처리 상태와 이전
결과를 저장·재사용하는 요청 단위 멱등성을 해결한다. 이는 사용자별 1회
발급만 보장하는 UNIQUE의 비즈니스 멱등성보다 구체적인 요청 추적이다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```text
DB의 비즈니스 데이터 저장과 CouponIssued 같은 후속 이벤트 발행을 하나의
로컬 DB 트랜잭션에 기록해, DB Commit 후 이벤트 발행이 누락되는 문제를
해결한다. Outbox relay가 저장된 이벤트를 Kafka에 재발행할 수 있게 한다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```text
Outbox는 동일한 DB 트랜잭션에 비즈니스 변경과 outbox 행을 함께 저장하는
패턴이다. Redis 판정은 별도 저장소에서 일어나며 최초 coupon.issue.requested
발행 전에는 함께 커밋할 로컬 DB 트랜잭션이 없으므로 Redis 연산과 Kafka
발행을 Outbox만으로 원자화할 수 없다. 해당 구간에는 별도의 보상·재처리
또는 다른 일관성 설계가 필요하다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```text
일시적인 DB 장애처럼 재시도로 회복 가능한 메시지를 지연 재처리하고,
정해진 횟수 후에도 실패하는 메시지를 DLQ로 격리해 정상 메시지 처리를
방해하지 않도록 한다. 실패 원인, 재시도 횟수, 모니터링과 수동·자동 복구,
Redis-DB 불일치 보정 절차도 함께 다룬다.
```
