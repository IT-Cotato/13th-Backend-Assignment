# **4주차 과제: DB 테이블과 최종 발급 정합성 보장**

## **1. 과제 목표**

이번 과제의 목표는 **Redis와 Kafka를 통과한 쿠폰 발급 요청을 DB에 정확하게 저장하고, 사용자 중복 발급과 전체 수량 초과를 방지하는 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

이번 4주차에서는 Consumer가 Kafka 메시지를 읽은 뒤 DB에 최종 발급 기록을 저장하는 단계를 설계한다.

기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
ACCEPTED인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB Transaction
  ├─ coupon_event.issued_count 증가
  └─ coupon_issue 발급 기록 저장
```

`Redis ACCEPTED`는 3주차의 `Redis SUCCESS`와 같은 단계다. 최종 발급 성공과 구분하기 위해 이번 주차에서는 `ACCEPTED`로 표기한다.

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Redis 판정 통과와 DB 최종 발급 성공의 차이

DB가 보장해야 하는 불변식

coupon_event와 coupon_issue 테이블 설계

UNIQUE(event_id, user_id)의 역할과 한계

조건부 UPDATE를 이용한 수량 초과 방지

영향받은 row 수의 의미와 실패 원인 구분

issued_count 증가와 coupon_issue INSERT를
하나의 트랜잭션으로 묶는 이유

Kafka 중복 소비와 DB 중복 발급 방지

품절 후 중복 메시지가 재처리되는 경우

조건부 UPDATE, 비관적 락, 낙관적 락 비교

Redis, Kafka, DB의 역할과 데이터 불일치 상황
```

이번 과제의 핵심은 다음과 같다.

```
Redis는 빠른 선착순 판정을 담당한다.

Kafka는 발급 요청 메시지를 전달한다.

DB는 최종 발급 기록을 저장하고 수량 정합성을 보장한다.
```

## **2. 기본 상황**

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 ID: 100

이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트

전체 쿠폰 수량: 1,000개

발급 조건:
사용자 1명당 해당 이벤트 쿠폰 1개만 발급 가능

DBMS: PostgreSQL

최종 발급 성공 기준:
coupon_issue 저장 트랜잭션 Commit
```

Redis는 정상 상황에서 최대 1,000명의 사용자만 통과시킨다.

하지만 다음과 같은 상황이 발생할 수 있다.

```
Redis 데이터 유실 또는 초기화

Redis Replica Failover 과정에서 일부 통과 기록 유실

Kafka 메시지 재처리

DB Commit 이후 Consumer Group Offset 커밋 전 Consumer 장애

애플리케이션 버그로 같은 발급 요청이 여러 번 DB에 도달
```

따라서 Redis가 앞단에서 요청을 차단하더라도 DB에는 다음 방어 장치가 필요하다.

```
사용자 중복 발급 방지
→ UNIQUE(event_id, user_id)

전체 수량 초과 방지
→ issued_count 조건부 UPDATE

두 작업의 일관성
→ DB Transaction
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
coupon_issue에는 최종 발급에 성공한 기록만 저장한다.

coupon_issue의 status는 ISSUED만 사용한다.

쿠폰 발급 취소와 재발급은 다루지 않는다.

이벤트별 전체 수량은
coupon_event.total_quantity에 저장한다.

DB에서 최종 발급된 수량은
coupon_event.issued_count에 저장한다.

모든 발급 처리는 issued_count 증가와
coupon_issue INSERT를 같은 트랜잭션에서 수행한다.

이벤트 발급 자격은 Redis 판정 시점을 기준으로 한다.
Consumer는 이벤트 상태와 기간을 다시 판정하지 않고
DB의 최종 수량과 사용자 중복 발급을 방어한다.

PostgreSQL의 기본 격리 수준인
READ COMMITTED를 기준으로 설명한다.

자동 Offset 커밋은 사용하지 않는다.
Consumer가 DB 처리 결과를 확정한 후에
Consumer Group Offset을 커밋한다고 가정한다.
```

이번 주차에서는 아래 내용의 상세 구현은 다루지 않는다.

```
requestId 기반 요청 상태 관리

Outbox Pattern

Retry Topic과 DLQ

쿠폰 발급 취소와 재발급 정책

Redis와 Kafka 사이의 원자성 보장
```

다만 이번 주차의 설계가 이후 주차의 내용과 어떻게 연결되는지는 설명해야 한다.

## **과제 1. DB 최종 발급 처리 구조 그리기**

Redis 판정을 통과한 요청이 Kafka를 거쳐 DB에 최종 저장되는 전체 구조를 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka

Coupon Issue Consumer

coupon_event

coupon_issue
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  ↓ (쿠폰 발급 요청)
API Server
  ↓ (선착순 판별 요청)
Redis
  ↓ (쿠폰 발급 비동기 요청)
Kafka
  ↓ (쿠폰 발급 메시지 발행)
Coupon Issue Consumer
  ↓ (쿠폰 발행)
coupon_event
  ↓ (DB 저장)
coupon_issue
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
Redis 판정 통과는 선착순 안에 들어온 것을 의미한다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
카프카 메시지 발행은 쿠폰 발급 요청을 비동기로 요청한 시점을 의미한다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
최종 발급 성공은 카프카에 성공적으로 요청이 적재된 후 컨슈머를 통해 소비되고
그 결과가 DB에 성공적으로 저장된 것(ISSUED)을 의미한다.
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- |--------|-----------------|
| Redis ACCEPTED | 선착순 통과 | X               |
| Kafka PUBLISHED | 비동기 요청 | X               |
| DB ISSUED | 쿠폰 발급  | O               |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

쿠폰 발급 시스템이 장애와 동시 요청 상황에서도 지켜야 하는 조건을 불변식으로 정의한다.

이번 과제에서는 다음 세 가지 불변식을 기준으로 작성한다.

```
불변식 1.

한 사용자는 하나의 이벤트에서
쿠폰을 최대 한 번만 발급받는다.

불변식 2.

발급 수량은 0보다 작거나
전체 수량보다 많을 수 없다.

불변식 3.

issued_count 증가와 coupon_issue 저장은
함께 성공하거나 함께 실패한다.
```

### **1. 불변식이 필요한 이유**

```
시스템 설계 시 필요한 제약들을 사전에 정의하여 설계의 기반을 마련하기 위해서 필요하다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제**                                    |
| --- |------------------------------------------------------|
| 사용자별 최대 1회 발급 | 사용자가 쿠폰을 중복으로 발급받을 수 있다.                             |
| 전체 수량 이하 발급 | 수량보다 많은 쿠폰이 사용자에게 발급될 수 있다.                          |
| 수량과 발급 기록의 동시 성공·실패 | 발급된 쿠폰 수와 차이가 발생하면 의도한 수량보다 쿠폰이 더 많거나 더 적게 발급될 수 있다. |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치**                                   |
| --- |------------------------------------------------|
| 사용자 중복 발급 방지 | Unique 제약조건(userId, eventId)                   |
| 전체 수량 초과 방지 | DB제약조건 선언(CHECK `totalCoupon` >= `couponCnt`), issued_count 조건부 UPDATE |
| 두 테이블의 일관성 | 쿠폰 수량과 발급 기록 저장을 한 트랜잭션 안에서 처리한다.(원자성)         |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
DB 저장 전 사용자 요청이 동일하게 2번 들어온 경우
첫번째 요청이 카프카에서 소비되고 있고 DB 트랜잭션을 커밋하기 전에
두번째 중복된 요청이 들어와 DB를 확인하지만 아직 저장된 데이터가 없어 또 발행요청이 처리될 수 있다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

쿠폰 이벤트와 최종 발급 기록을 저장할 테이블을 설계한다.

완전한 운영용 스키마를 만드는 것이 목적은 아니다. 이번 주차에서 필요한 불변식을 지킬 수 있도록 핵심 컬럼과 제약 조건을 작성한다.

### **1. coupon_event 테이블의 역할**

```
쿠폰 이벤트의 메타데이터를 저장한다.
event_id(어떤 이벤트인지)
total_coupon(발급할 쿠폰의 수)
issued_count(발급한 쿠폰의 수)
등이 있다.
```

### **2. coupon_issue 테이블의 역할**

```
발급된 쿠폰들을 저장한다.
user_id(어떤 사용자인지)
event_id(foreignKey, 어떤 이벤트인지)
등을 저장한다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
coupon_event (1)
     ↓        :
coupon_issue (N)
```

### **4. coupon_event 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

name

total_quantity

issued_count

start_at

end_at

status

version (낙관적 락을 선택할 경우)

수량 CHECK 제약

이벤트 기간 CHECK 제약
```

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count INT NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    CONSTRAINT chk_quantity
        CHECK (total_quantity >= 0 AND issued_count >= 0 AND issued_count <= total_quantity),
    CONSTRAINT chk_period
        CHECK (start_at < end_at)
```

### **5. coupon_issue 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

event_id

user_id

status

issued_at

coupon_event를 참조하는 Foreign Key

동일 이벤트의 사용자 중복 발급을 막는 UNIQUE 제약
```

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),
    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
쿠폰 발행을 coupon_event안에 쿠폰 수량과 CHECK하기 위해서(DB레벨에서의 최종 방어선) 쿠폰 이벤트에 별도로 저장한다.
이에 대한 데이터 정합성을 지키기 위해 별도의 트랜잭션 처리가 필요하다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

`UNIQUE(event_id, user_id)`가 어떤 문제를 막고, 어떤 문제는 막지 못하는지 분석한다.

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
사용자는 쿠폰을 1개만 발급받을 수 있다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 다음과 같다.

```
event_id = 100
user_id = 10
```

| **새로운 INSERT** | **성공 또는 실패** | **이유**                                             |
| --- |--------------|----------------------------------------------------|
| event_id=100, user_id=10 | 실패           | DB에 이미 100번 이벤트에대한 userId10번이 존재함(Unique 제약 조건 위반) |
| event_id=100, user_id=11 | 성공           | 100번 이벤트의 11번 사용자는 기존 DB에 존재 X                     |
| event_id=101, user_id=10 | 성공           | 101번 이벤트의 10번 사용자는 기존 DB에 존재 X                     |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

아래 상황을 시간 순서로 표현한다.

```
Transaction A가 user:10의 발급 기록을 조회한다.

Transaction B도 user:10의 발급 기록을 조회한다.

두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

두 트랜잭션이 동시에 INSERT를 시도한다.
```

답변:

```
유니크 제약조건이 있는 경우:
트랜잭션 A가 먼저 처리되어 커밋된다고 가정했을 때 
트랜잭션 B는 DB에 저장된 데이터로 유니크 제약조건을 위해하게 되어 저장되지 않는다.
유니크 제약조건이 없는 경우:
트랜잭션 A가 먼저 처리되어 커밋된다고 가정했을 때
트랜잭션 B도 마찬가지로 처리되어 커밋된다.
따라서 사용자는 쿠폰을 2번 발급할 수 있게된다.
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

아래 상황을 기준으로 설명한다.

```
전체 수량: 1,000개

서로 다른 사용자: 1,001명

모든 (event_id, user_id) 조합은 서로 다름
```

```
유니크 제약조건은 중복 데이터 저장을 막는 기능이다.
따라서 전체 수량과는 관련이 없다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치**                                     |
| --- |--------------------------------------------------|
| 같은 사용자의 중복 발급 | UNIQUE(userId, eventId)                          |
| 서로 다른 사용자에 의한 전체 수량 초과 | CHECK(total_coupon >= issued_coupon), 조건부 update |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

쿠폰 수량이 남아 있을 때만 `issued_count`를 증가시키는 조건부 UPDATE를 설계한다.

### **1. 조건부 UPDATE SQL 작성하기**

다음 조건을 만족해야 한다.

```
event_id가 일치해야 한다.

issued_count가 total_quantity보다 작을 때만 증가해야 한다.

issued_count는 1 증가해야 한다.
```

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
  updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
1인 경우 1개의 행이 영향을 받았다는 의미인데 이는 쿠폰이 성공적으로 발급되어 처리된 경우를 의미한다.
0인 경우 0개의 행이 영향을 받았다는 의미이므로 쿠폰이 발급되지 않아 DB에 변경이 없음을 의미한다.
```

### **3. 영향받은 row 수가 1인 경우**

```
쿠폰이 성공적으로 발급된 것을 의미한다
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

과제 5-1의 SQL은 `event_id`와 수량 조건만 사용한다. 중복 메시지 여부는 UPDATE 결과가 0인 직접 원인이 아니라, 이후 기존 발급 기록을 조회해 구분한다.

```
1. 쿠폰이 모두 소진되어 발급되지 않았다

2. 이벤트가 끝나서 발급되지 않았다.
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

과제 5-1에서 작성한 조건부 UPDATE를 사용한다고 가정한다.

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과**  |
| --- | --- | --- | --- |----------------|---------|
| A | 999 | 1,000 | 존재 | 1              | 쿠폰 발급   |
| B | 1,000 | 1,000 | 존재 | 0              | 쿠폰 발급 X |
| C | - | - | 존재하지 않음 | 0              | 쿠폰 발급 X |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전체 수량: 1,000개

현재 issued_count: 999

Transaction A와 Transaction B가
동시에 조건부 UPDATE 실행
```

두 트랜잭션의 실행 결과를 시간 순서 다이어그램으로 작성한다.

```
  Transaction A, B 동시에 조건부 UPDATE 시도
    |
    DB가 같은 row 갱신을 직렬화 (row lock)
    |
    +-- Transaction A가 lock 먼저 획득
    |     issued_count: 999 < 1000 → 조건 충족
    |     issued_count = 1000으로 UPDATE 성공 (row 수 = 1)
    |     lock 해제
    |
    +-- Transaction B가 lock 획득
          issued_count: 1000 < 1000 → 조건 불충족
          UPDATE 실패 (row 수 = 0)
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
DB는 같은 row의 갱신을 직렬화한다.
따라서 각 트랜잭션은 갱신 시점의 최신 issued_count를 기준으로
AND issued_count < total_quantity 조건을 다시 평가한다.
마지막 수량을 A가 가져가면 B의 UPDATE는 조건 불충족으로 0을 반환한다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

다음 두 작업을 하나의 DB 트랜잭션으로 묶는 이유를 설명한다.

```
1. coupon_event.issued_count 증가

2. coupon_issue 발급 기록 INSERT
```

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치**         |
| --- |--------------------------|
| issued_count 증가 성공, coupon_issue INSERT 실패 | 쿠폰 수량보다 적게 쿠폰이 발급될 수 있다. |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 쿠폰 수량보다 많게 쿠폰이 발급될 수 있다. |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
조건부 UPDATE로 수량 확보 (issued_count 증가)
  ↓ 결과 = 1
coupon_issue INSERT
  ↓ 성공
Commit
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (event_id, user_id, status)
VALUES (:eventId, :userId, 'ISSUED');

-- 두 작업이 모두 성공하면 Commit
COMMIT;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

아래 항목을 모두 설명한다.

```
현재 트랜잭션은 어떻게 되는가?

앞에서 증가한 issued_count는 어떻게 되는가?

기존 발급 기록은 언제 조회해야 하는가?
```

답변:

```
현재 트랜잭션은 어떻게 되는가?
- 롤백된다.
앞에서 증가한 issued_count는 어떻게 되는가?
- 롤백된다.
기존 발급 기록은 언제 조회해야 하는가?
UNIQUE 위반 발생
    → 현재 트랜잭션 Rollback (PostgreSQL에서 aborted 상태)
    → 새 트랜잭션 시작
    → 새 트랜잭션에서 기존 coupon_issue 기록 조회
Rollback 후 새 트랜잭션에서 조회한다.
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
PostgreSQL에서 에러가 발생하면 트랜잭션이 aborted 상태가 된다.
aborted 상태에서는 ROLLBACK 이외의 모든 명령이
"ERROR: current transaction is aborted" 에러를 반환한다.
따라서 UNIQUE 위반 후 같은 트랜잭션에서 SELECT를 할 수 없고,
반드시 ROLLBACK한 뒤 새 트랜잭션에서 조회해야 한다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
데이터의 정합성을 유지하기 위해 같은 트랜잭션을 이용해야 한다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

Kafka Consumer는 같은 메시지를 다시 처리할 수 있다.

아래 상황을 기준으로 분석한다.

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.
```

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.

6. DB 발급 트랜잭션을 커밋하지만 UNIQUE 제약조건을 위배하여 커밋되지 않는다.
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
카프카 오류나 어플리케이션 장애 등으로 인해 쿠폰이 중복으로 저장될 가능성이 존재한다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
DB 커밋 시점에 동일한 데이터가 있다면 트랜잭션을 롤백한다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
DB에 동일 데이터가 존재한다면 이는 이미 쿠폰을 성공적으로 발행한 상태이기 떄문에
DB에 동일한 데이터가 있는지로 판단한다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. UNIQUE 위반으로 트랜잭션 전체 Rollback

2. 새 트랜잭션에서 동일 (event_id, user_id) 발급 기록 조회

3. 기록 존재 → 이미 처리된 중복 메시지로 판단 → 정상 처리

4. Consumer Group Offset 커밋
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
Consumer Group Offset이 먼저 처리되고 장애가 발생한 경우
이를 재시도 할 수 있는 방법이 없기 때문에 DB처리를 먼저 수행해야 한다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
UNIQUE(event_id, user_id)은 쿠폰 최종 발급 성공의 제약조건 즉 최후의 방어선과 같은 개념이다.
requestId 기반 멱등성은 요청을 중복으로 처리하지 않기 위한 것이다.
```

## **과제 9. DB 동시성 제어 방식 비교하기**

다음 세 가지 방식으로 쿠폰 수량을 제어할 수 있다.

```
조건부 UPDATE

비관적 락

낙관적 락
```

### **1. 조건부 UPDATE 방식 설명**

```
UPDATE에 제약조건을 걸어 해당 조건을 만족하는 경우만 UPDATE를 한다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;
-- 이후 수량 확인 후 UPDATE + INSERT
```

설명:

```
데이터는 무조건 충돌한다는 가정하에 
데이터 조회, 업데이트를 트랜잭션 별로 순차적으로 실행한다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
  version = version + 1,
  updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
AND version = :oldVersion
AND issued_count < total_quantity;
-- 결과 = 0이면 버전 충돌 → 재시도
```

설명:

```
데이터는 충돌하지 않는다는 가정하에 
데이터 조회 시점의 version과 업데이트 시점의 version을 비교한다.
version이 다른 경우에 재시도하거나 롤백한다.
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE**               | **비관적 락**                     | **낙관적 락**         |
| --- |------------------------------|-------------------------------|-------------------|
| 수량을 보호하는 방법 | WHERE 조건으로 수량 확인, 증가를 원자적 수행 | FOR UPDATE로 row 잠금 후 수량 확인·변경 | version 비교로 충돌 감지 |
| 충돌 시 동작 | 갱신 후 최신 값으로 조건 재평가           | 이전 트랜잭션 완료까지 대기               | UPDATE 실패         |
| 재시도 필요 여부 | 불필요                          | 불필요(대기 후 처리)                  | 필요                |
| 장점 | 구현 단순, 재시도 X                 | 순서와 정합성 이해가 쉽다.               | 락 없이 처리 시도        |
| 단점 | 같은 row 집중 시 lock 대기          | 락 대기 길어짐, 처리량 감소              | 선착순에서 재시도가 많아짐    |
| 선착순 이벤트 적합성 | 적합                           | 보통                            | 부적합               |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
같은 event row 하나에 수천 건이 몰리면
비관적 락: 트랜잭션이 길어질수록 처리량 급감, 락 대기 증가
낙관적 락: 충돌이 많아 재시도가 폭발적으로 증가
조건부 UPDATE도 lock 대기가 생기지만 SELECT 없이 바로 UPDATE하므로 트랜잭션이 짧아 상대적으로 유리하다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
수량 확인과 증가를 하나의 SQL로 원자적으로 처리한다.
별도 SELECT와 재시도 없이 영향받은 row 수로 성공 여부를 판단할 수 있다.
낙관적 락은 선착순처럼 집중되는 환경에서 재시도가 너무 많아진다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```
조건부 UPDATE / 비관적 락 / 낙관적 락 → 전체 수량 초과 방지
UNIQUE(event_id, user_id) → 같은 사용자의 중복 발급 방지
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

Redis, Kafka, DB는 서로 다른 시스템이므로 상태가 일시적으로 달라질 수 있다.

Kafka 상태는 발행된 레코드의 존재 여부와 Consumer Group Offset 커밋 여부를 구분해서 작성한다. Kafka 레코드가 존재한다는 사실만으로 처리 대기 상태라고 판단하지 않는다.

### **1. Redis 통과 후 Kafka 발행 실패 상황**

아래 세 시스템에 남는 상태를 작성한다.

| **시스템** | **남아 있는 상태** |
| --- |--------------|
| Redis | 통과 기록 존재     |
| Kafka | 메시지 없음       |
| DB | 발급 기록 없음     |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태**       |
| --- |--------------------|
| Redis | 통과 기록 존재           |
| Kafka | 메시지 존재(offset 미커밋) |
| DB | 발급 기록 없음           |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- |--------------|
| Redis | 통과 기록 없음     |
| DB | 발급 기록 존재     |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
Redis는 휘발성 메모리로 유실될 가능성이 존재한다.
카프카는 단순히 요청이 비동기로 요청되었음을 의미한다.
DB만 영속적으로 저장되는 최종 발급 기록이다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis**          | **Kafka**    | **DB**                  |
| --- |--------------------|--------------|-------------------------|
| 주 역할 | 선착순 판정             | 비동기 처리       | 발급 기록 영구 저징             |
| 저장하는 상태 | 통과한 사용자 set, 잔여 수량 | 발급 요청 메시지    | 이벤트 정보, 발급 기록           |
| 성공이 의미하는 것 | 선착순 통과             | 비동기 처리 요청 성공 | 쿠폰 발급 성공                |
| 강점 | 빠른 속도, 원자적 연산      | 고가용성, 재처리보장  | 영속성, 제약조건을 통한 최종 정합성 보장 |
| 한계 | 유실 가능성 존재          | 최종 발급 보장 X   | 직접 트래픽 집중 시 병목          |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
동일 requestId를 가진 중복 요청을 식별해 처리 결과를 재사용한다.
requestId로 "이 요청을 이미 처리했는가"를 판단한다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
DB 발급 기록 커밋과 후속 이벤트 Kafka 발행 사이의 원자성 문제를 해결한다
DB에 커밋했지만 Kafka 발행이 실패하면 알림/마이페이지/통계 서비스가
발급 사실을 알 수 없게 된다. Outbox는 두 작업을 원자적으로 묶는다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
Outbox Pattern은 DB 트랜잭션 내에 메시지를 함께 저장하고
별도 프로세스가 DB에서 읽어 Kafka로 발행하는 패턴이다.
즉, DB 저장 ↔ Kafka 발행 사이의 원자성을 해결한다.
Redis 판정과 최초 Kafka 발행은 DB 트랜잭션 범위 밖의 일이므로
Outbox로 해결되지 않는다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
일시적 DB 오류 등으로 Consumer 처리가 실패했을 때 재시도 정책을 정의한다.
재시도 횟수를 초과한 메시지는 DLQ에 보관해 나중에 수동 처리하거나 분석한다.
Redis-DB 불일치 복구도 이 범위에서 다룬다.
```
