# 4주차 과제: DB 테이블과 최종 발급 정합성 보장

---

## 과제 1. DB 최종 발급 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  │ 쿠폰 발급 요청
  ▼
API Server
  │ (1) 인증 확인
  │ (2) Redis Lua Script 실행
  ▼
Redis
  ├── DUPLICATE → 즉시 중복 응답 반환 → Client
  ├── SOLD_OUT  → 즉시 품절 응답 반환 → Client
  └── ACCEPTED
        │ Kafka 메시지 발행
        ▼
      Kafka (coupon.issue.requested Topic)
        │
        ▼
      Coupon Issue Consumer
        │
        ├─ BEGIN TRANSACTION
        │    │
        │    ├─ 1. coupon_event.issued_count 조건부 UPDATE
        │    │      (issued_count < total_quantity 인 경우만 +1)
        │    │      영향받은 row = 0 → ROLLBACK → 실패 처리
        │    │
        │    └─ 2. coupon_issue INSERT
        │           UNIQUE 위반 → ROLLBACK → 중복 소비 처리
        │
        └─ COMMIT → 발급 완료
              │
              ▼
        coupon_event (issued_count 증가)
        coupon_issue (발급 기록 저장)

        Consumer Group Offset 커밋 (DB Commit 이후)

Client ← PENDING 응답 (ACCEPTED + Kafka 발행 성공 시)
이후 조회 API에서 최종 상태(ISSUED) 확인
```

### 2. Redis 판정 통과가 최종 발급 성공이 아닌 이유

Redis ACCEPTED는 선착순 판정 통과를 의미할 뿐이다. 이후 Kafka 발행, Consumer 메시지 소비, DB 트랜잭션 Commit이 모두 완료되어야 실제로 쿠폰이 발급된다. Redis 장애로 데이터가 유실되거나, Kafka 발행이 실패하거나, Consumer가 DB 처리에 실패하면 최종 발급은 이루어지지 않는다.

### 3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유

Kafka 발행 성공은 메시지가 Kafka Topic에 안전하게 저장됐다는 의미다. Consumer가 메시지를 읽고 DB 트랜잭션(issued_count 증가 + coupon_issue INSERT)을 Commit하기 전까지는 발급이 완료되지 않는다. Consumer 장애, DB 장애, 수량 초과, UNIQUE 위반 등으로 이후 단계가 실패할 수 있다.

### 4. 최종 발급 성공으로 판단할 수 있는 시점

`coupon_issue` INSERT와 `coupon_event.issued_count` 증가를 묶은 DB 트랜잭션이 Commit된 시점이다. 이 시점에 coupon_issue 테이블에 발급 기록이 영속적으로 저장된 것을 최종 발급 성공 기준으로 삼는다.

### 5. Redis, Kafka, DB 단계의 상태 차이

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | 선착순 중복 판정 통과. 쿠폰 수량 내에서 처음 요청한 사용자임이 확인됨 | 아니다. 이후 단계가 실패하면 발급되지 않는다 |
| Kafka PUBLISHED | 발급 요청 메시지가 Kafka Topic에 저장됨. Consumer가 처리 대기 중 | 아니다. Consumer 처리와 DB Commit이 완료되어야 한다 |
| DB ISSUED | coupon_issue 발급 기록 저장 트랜잭션 Commit 완료 | 그렇다. 이 시점이 최종 발급 성공 기준이다 |

## 과제 2. DB가 보장해야 하는 불변식 정의하기

### 1. 불변식이 필요한 이유

Redis와 Kafka는 빠른 처리를 위해 설계됐지만 완전한 정합성을 보장하지 않는다. Redis 장애로 통과 기록이 유실될 수 있고, Kafka Consumer는 같은 메시지를 두 번 처리할 수 있으며, 애플리케이션 버그로 중복 요청이 DB에 도달할 수도 있다. 이런 상황에서도 쿠폰 중복 발급과 수량 초과가 발생하지 않도록 DB 레벨에서 최종 방어선을 구축해야 한다.

### 2. 각 불변식이 깨졌을 때 발생하는 문제

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 같은 사용자가 동일 이벤트에서 쿠폰을 여러 개 발급받아 불공정한 혜택을 누린다. 쿠폰 남용으로 서비스 손실이 발생한다 |
| 전체 수량 이하 발급 | 총 1,000개 쿠폰 이벤트에서 1,001개 이상이 발급되어 약속한 수량을 초과한다. 쿠폰 비용 손실과 사용자 신뢰 저하가 발생한다 |
| 수량과 발급 기록의 동시 성공·실패 | issued_count는 증가했으나 coupon_issue 기록이 없는 경우 실제로 받은 사람을 추적할 수 없다. 반대로 기록은 있는데 issued_count가 증가하지 않으면 수량 정합성이 깨진다 |

### 3. 각 불변식을 보호하는 DB 장치

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | `coupon_issue` 테이블의 `UNIQUE(event_id, user_id)` 제약 |
| 전체 수량 초과 방지 | `coupon_event.issued_count < total_quantity` 조건을 포함한 조건부 UPDATE |
| 두 테이블의 일관성 | issued_count 증가와 coupon_issue INSERT를 하나의 DB 트랜잭션으로 묶음 |

### 4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유

SELECT 조회와 INSERT 사이에 다른 트랜잭션이 같은 사용자의 INSERT를 완료할 수 있다. Transaction A가 "발급 기록 없음"을 확인한 뒤 INSERT하기 전에 Transaction B도 같은 확인을 하고 INSERT를 먼저 완료하면, Transaction A도 INSERT에 성공해 중복 발급이 발생한다. SELECT + INSERT 패턴은 원자적이지 않으므로 DB 레벨의 UNIQUE 제약이 반드시 필요하다.

## 과제 3. coupon_event와 coupon_issue 테이블 설계하기

### 1. coupon_event 테이블의 역할

이벤트 정보와 수량 관리를 담당한다. 이벤트별 전체 수량(total_quantity)과 현재까지 발급된 수량(issued_count)을 저장해 수량 초과 여부를 판단하는 기준이 된다. 조건부 UPDATE의 대상 테이블이다.

### 2. coupon_issue 테이블의 역할

실제로 쿠폰을 발급받은 사용자 기록을 저장한다. UNIQUE(event_id, user_id) 제약으로 같은 사용자의 중복 발급을 DB 레벨에서 차단한다. 발급 완료된 최종 기록의 기준이 되며, 조회 API에서 사용자의 쿠폰 발급 여부를 확인하는 데 사용된다.

### 3. 두 테이블의 관계를 다이어그램으로 표현하기

```
coupon_event
┌──────────────────────────────────┐
│ id (PK)                          │
│ name                             │
│ total_quantity                   │
│ issued_count  ← 조건부 UPDATE    │
│ start_at                         │
│ end_at                           │
│ status                           │
└──────────────┬───────────────────┘
               │ 1
               │
               │ N
coupon_issue   │
┌──────────────▼───────────────────┐
│ id (PK)                          │
│ event_id (FK → coupon_event.id)  │
│ user_id                          │
│ status                           │
│ issued_at                        │
│ UNIQUE(event_id, user_id)        │
└──────────────────────────────────┘
```

### 4. coupon_event 테이블 DDL 작성하기

```sql
CREATE TABLE coupon_event (
    id             BIGSERIAL       PRIMARY KEY,
    name           VARCHAR(255)    NOT NULL,
    total_quantity INT             NOT NULL,
    issued_count   INT             NOT NULL DEFAULT 0,
    start_at       TIMESTAMP       NOT NULL,
    end_at         TIMESTAMP       NOT NULL,
    status         VARCHAR(20)     NOT NULL DEFAULT 'ACTIVE',
    version        BIGINT          NOT NULL DEFAULT 0,  -- 낙관적 락 선택 시 사용

    CONSTRAINT chk_quantity_range
        CHECK (issued_count >= 0 AND issued_count <= total_quantity),

    CONSTRAINT chk_event_period
        CHECK (end_at > start_at)
);
```

### 5. coupon_issue 테이블 DDL 작성하기

```sql
CREATE TABLE coupon_issue (
    id         BIGSERIAL    PRIMARY KEY,
    event_id   BIGINT       NOT NULL,
    user_id    BIGINT       NOT NULL,
    status     VARCHAR(20)  NOT NULL DEFAULT 'ISSUED',
    issued_at  TIMESTAMP    NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),

    CONSTRAINT uq_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### 6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점

**이유**: coupon_issue 테이블의 COUNT(*)로 매번 현재 발급 수량을 집계하면 행이 많아질수록 쿼리 비용이 증가한다. issued_count를 별도로 관리하면 O(1)으로 현재 수량을 확인할 수 있고, 조건부 UPDATE로 수량 초과를 원자적으로 방어할 수 있다.

**단점**: issued_count와 coupon_issue 실제 행 수가 일치하지 않을 수 있다. 트랜잭션 실패나 버그로 두 값이 어긋나면 별도의 정합성 검증 배치가 필요하다. 두 값을 항상 동기화하는 부담이 생긴다.

## 과제 4. UNIQUE 제약의 역할과 한계 분석하기

### 1. `UNIQUE(event_id, user_id)`가 의미하는 규칙

동일한 (event_id, user_id) 조합이 coupon_issue 테이블에 두 번 이상 존재할 수 없다. 즉, 같은 사용자가 같은 이벤트에서 쿠폰을 여러 번 발급받는 것을 DB 레벨에서 차단한다.

### 2. 다음 INSERT의 성공 여부와 이유

기존 데이터: event_id = 100, user_id = 10

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | (100, 10) 조합이 이미 존재하므로 UNIQUE 위반 |
| event_id=100, user_id=11 | 성공 | (100, 11) 조합은 존재하지 않음 |
| event_id=101, user_id=10 | 성공 | (101, 10) 조합은 존재하지 않음. 다른 이벤트의 발급이므로 제약 적용 안 됨 |

### 3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition

```
시간 →

Transaction A                          Transaction B
  │                                        │
  ├─ SELECT: (100,10) 발급 기록 없음       │
  │                                        ├─ SELECT: (100,10) 발급 기록 없음
  │                                        │
  │                                        ├─ INSERT (event_id=100, user_id=10) → 성공
  │                                        ├─ COMMIT
  │
  ├─ INSERT (event_id=100, user_id=10)
  │    → UNIQUE 위반 에러 발생
  │    (Transaction B가 먼저 Commit했으므로)
  │
  └─ ROLLBACK
```

SELECT 시점에는 두 트랜잭션 모두 "발급 기록 없음"을 확인했지만, Transaction B가 먼저 INSERT·Commit하면 Transaction A의 INSERT는 UNIQUE 위반으로 실패한다. SELECT + INSERT 사이의 간격이 Race Condition의 원인이다. UNIQUE 제약이 없다면 두 트랜잭션 모두 INSERT에 성공해 중복 발급이 발생한다.

### 4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유

전체 수량이 1,000개이고 서로 다른 1,001명이 요청하는 경우, 각 (event_id, user_id) 조합은 모두 고유하다. UNIQUE(event_id, user_id)는 같은 사용자의 중복 발급만 막기 때문에 1,001번째 서로 다른 사용자의 INSERT도 제약 위반 없이 성공한다. 수량 초과를 막으려면 issued_count를 조건으로 하는 별도의 수량 제어 장치가 필요하다.

### 5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | `UNIQUE(event_id, user_id)` 제약 |
| 서로 다른 사용자에 의한 전체 수량 초과 | `issued_count < total_quantity` 조건의 조건부 UPDATE |

## 과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기

### 1. 조건부 UPDATE SQL 작성하기

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### 2. 영향받은 row 수가 의미하는 것

UPDATE 문이 실제로 조건을 만족해 값을 변경한 행의 수다. 조건부 UPDATE에서 이 값은 수량 증가가 실제로 이루어졌는지를 나타내는 핵심 판단 기준이다.

### 3. 영향받은 row 수가 1인 경우

`issued_count < total_quantity` 조건을 만족해 issued_count가 1 증가했다. 쿠폰 수량이 남아 있었으므로 이후 coupon_issue INSERT를 진행한다.

### 4. 영향받은 row 수가 0인 경우 가능한 원인

```
1. issued_count >= total_quantity: 쿠폰 수량이 이미 소진됐다.

2. 해당 event_id가 coupon_event 테이블에 존재하지 않는다.
```

### 5. 다음 상황에서 UPDATE 결과를 작성하기

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | issued_count가 1,000이 됨. coupon_issue INSERT 진행 |
| B | 1,000 | 1,000 | 존재 | 0 | 조건 불만족(1,000 < 1,000 = false). SOLD_OUT 처리 |
| C | - | - | 존재하지 않음 | 0 | 해당 event_id row 없음. 이벤트 없음으로 실패 처리 |

### 6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석

```
전체 수량: 1,000개 / 현재 issued_count: 999

시간 →

Transaction A                             Transaction B
  │                                           │
  ├─ UPDATE ... WHERE issued_count < 1000     │
  │   → DB 내부적으로 해당 row에 락 획득      │
  │                                           ├─ UPDATE ... WHERE issued_count < 1000
  │                                           │   → Transaction A가 락을 가지고 있으므로
  │                                           │     Transaction B는 대기 (blocking)
  │
  ├─ issued_count: 999 → 1000 (성공)
  ├─ 영향받은 row = 1
  ├─ coupon_issue INSERT
  ├─ COMMIT
  │
  │                                           │ Transaction A Commit 확인
  │                                           │ UPDATE 재시도
  │                                           │ 현재 issued_count = 1000
  │                                           │ 조건: 1000 < 1000 = false
  │                                           ├─ 영향받은 row = 0
  │                                           ├─ SOLD_OUT 처리
  │                                           └─ ROLLBACK
```

### 7. issued_count가 total_quantity를 초과하지 않는 이유

UPDATE 문 자체가 `issued_count < total_quantity` 조건을 만족할 때만 실행된다. PostgreSQL의 행 수준 락(row-level lock)이 UPDATE 실행 중 다른 트랜잭션의 동일 행 UPDATE를 직렬화한다. Transaction A가 업데이트를 완료하고 Commit하면 Transaction B는 갱신된 issued_count로 조건을 재평가하게 되어 이미 1,000개가 된 시점에서 조건이 false가 된다.

## 과제 6. 발급 트랜잭션과 Rollback 설계하기

### 1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | issued_count는 1 증가했지만 실제 발급 기록이 없다. 수량은 줄었으나 쿠폰을 받은 사람이 없는 유령 발급이 발생한다 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급 기록은 있지만 issued_count가 반영되지 않았다. 실제 발급 수량과 issued_count가 불일치해 이후 수량 초과 방지 로직이 오작동할 수 있다 |

### 2. 하나의 트랜잭션으로 처리하는 전체 흐름

```
BEGIN TRANSACTION

  1. coupon_event UPDATE (조건부)
     → 영향받은 row = 0 이면 ROLLBACK (수량 초과 또는 이벤트 없음)

  2. coupon_issue INSERT
     → UNIQUE 위반이면 ROLLBACK (중복 소비)
       (rolled back issued_count도 함께 복구됨)

COMMIT
(두 작업 모두 성공한 경우에만)
```

### 3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;

-- UPDATE 결과 확인: 영향받은 row 수가 0이면 수량 초과
-- (애플리케이션에서 affected rows 확인 후 0이면 ROLLBACK)

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:eventId, :userId, 'ISSUED', NOW());

-- 두 작업이 모두 성공하면 Commit
COMMIT;

-- 어느 한 단계라도 실패하면 전체 취소
-- ROLLBACK;
```

### 4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우

현재 트랜잭션은 ROLLBACK된다. PostgreSQL에서 제약 조건 위반이 발생하면 해당 트랜잭션은 더 이상 진행할 수 없는 오류 상태(aborted)가 되며 ROLLBACK만 가능하다. 앞에서 증가한 issued_count도 ROLLBACK으로 함께 원래 값으로 되돌아간다. 따라서 수량 불일치가 발생하지 않는다. 기존 발급 기록 조회는 ROLLBACK 이후 새 트랜잭션에서 수행해야 한다. 이 조회 결과로 "이미 처리된 중복 소비"인지 "진짜 오류"인지 구분한다.

### 5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유

PostgreSQL은 오류가 발생한 트랜잭션을 자동으로 aborted 상태로 전환한다. aborted 상태에서는 ROLLBACK 명령 외에 다른 SQL 명령을 실행할 수 없다. 이는 오류가 발생한 상태에서 이후 쿼리가 실행돼 잘못된 부분 커밋이 일어나는 것을 방지하기 위한 PostgreSQL의 설계다.

### 6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유

여러 Consumer 스레드나 인스턴스가 같은 메시지를 처리하는 경우에도 DB 트랜잭션의 원자성이 보장되어야 중복 발급이 발생하지 않는다. 각 처리 경로가 독립적인 트랜잭션을 사용해야 ROLLBACK 시 부분 변경이 남지 않으며, UNIQUE 제약과 조건부 UPDATE의 방어 효과가 온전히 작동한다.

## 과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기

### 1. 중복 소비가 발생하는 전체 흐름 다이어그램

```
Consumer
  │ 1. Kafka Topic에서 메시지 읽음 (user:10, event:100)
  │ 2. DB 발급 트랜잭션 실행
  │    - issued_count UPDATE (999 → 1000)
  │    - coupon_issue INSERT (event_id=100, user_id=10)
  │ 3. COMMIT 성공
  │
  │ 4. Consumer Group Offset 커밋 시도
  │    → Consumer 장애 발생 (Offset 커밋 실패)
  │
Consumer 재시작
  │ 5. 마지막으로 커밋된 Offset부터 다시 읽음
  │    → 동일한 메시지 (user:10, event:100) 재처리
  │ 6. DB 발급 트랜잭션 재시도
  │    - issued_count UPDATE → 1000 = 1000, 조건 불만족 → 0 rows
  │
  ├─ 영향받은 row = 0
  │  └─ coupon_issue에서 (event_id=100, user_id=10) 조회
  │      → 기록 존재 → 이미 처리된 메시지로 판단
  │      → Offset 커밋 후 정상 완료
```

### 2. DB에 UNIQUE 제약이 없다면 발생하는 문제

중복 소비된 메시지가 DB에 그대로 INSERT되어 같은 사용자(user:10)의 발급 기록이 두 개 생긴다. 쿠폰을 두 개 발급받는 중복 발급이 발생하고, 수량 관리도 어긋난다. UNIQUE 제약이 없으면 DB가 중복 소비를 걸러낼 수단이 없다.

### 3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정

중복 소비된 메시지로 coupon_issue INSERT를 시도하면 이미 (event_id=100, user_id=10) 기록이 존재하므로 UNIQUE 위반이 발생한다. 트랜잭션이 ROLLBACK되어 issued_count도 함께 복구된다. 중복으로 인한 데이터 변경이 전혀 남지 않는다.

### 4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건

ROLLBACK 후 새 트랜잭션에서 `SELECT * FROM coupon_issue WHERE event_id = :eventId AND user_id = :userId`를 조회해 기록이 존재하는지 확인한다. 기록이 존재하면 이전에 정상 처리된 중복 소비다. 기록이 없으면 다른 원인의 INSERT 실패이므로 별도 처리(재시도 또는 DLQ)가 필요하다.

### 5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서

```
1. UNIQUE 위반 감지 → 트랜잭션 ROLLBACK

2. 새 트랜잭션 시작 → coupon_issue에서 (event_id, user_id) 기록 조회

3. 기록이 존재하면 → 이미 처리된 메시지로 판단, 정상 완료로 처리

4. Consumer Group Offset 커밋 → 다음 메시지 처리로 이동
```

### 6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유

Offset을 먼저 커밋하면 Consumer가 장애로 재시작될 때 해당 메시지를 다시 읽지 않는다. DB 처리가 실패했음에도 메시지가 영구적으로 유실되어 쿠폰 발급이 되지 않는다. DB Commit 이후에 Offset을 커밋해야 적어도 한 번(at-least-once) 처리가 보장된다.

### 7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이

`UNIQUE(event_id, user_id)`는 사용자 단위 중복 방지다. 같은 사용자가 같은 이벤트에서 쿠폰을 두 번 발급받는 것을 막는다. requestId 기반 멱등성은 요청 단위 중복 방지다. 완전히 동일한 요청(같은 requestId)이 네트워크 재전송이나 Consumer 재처리로 여러 번 처리되더라도 결과가 한 번만 반영되도록 보장한다. UNIQUE 제약은 결과 기준 중복 방지이고, requestId 멱등성은 요청 처리 과정의 중복 방지다.

## 과제 8. 품절 후 중복 메시지 재처리 분석하기

상황: event_id=100, total_quantity=1, issued_count=1, coupon_issue에 (100, 10) 기록 존재, user:10의 메시지가 다시 전달됨.

### 1. 조건부 UPDATE 결과와 그 이유

영향받은 row = 0. issued_count(1) >= total_quantity(1)이므로 `issued_count < total_quantity` 조건이 false가 되어 UPDATE가 실행되지 않는다.

### 2. coupon_issue INSERT까지 실행되는가?

실행되지 않는다. 애플리케이션에서 UPDATE 결과가 0이면 INSERT를 진행하지 않고 0인 원인을 판단하는 분기로 이동하도록 설계해야 한다.

### 3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?

발생하지 않는다. UPDATE 결과가 0이므로 INSERT 자체가 실행되지 않아 UNIQUE 제약 위반이 발생할 기회가 없다.

### 4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유

UPDATE 결과 0에는 두 가지 원인이 있다. 수량이 소진된 품절(SOLD_OUT)과 해당 event_id가 존재하지 않는 경우다. 이 상황처럼 user:10의 중복 소비도 UPDATE 결과 0으로 나타난다(이미 issued_count = total_quantity). 무조건 품절로 판단하면 중복 소비된 메시지를 Offset 커밋해야 할지 오류로 처리해야 할지 판단할 수 없다. 기존 coupon_issue 기록을 조회해 원인을 구분해야 한다.

### 5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유

UPDATE 결과 0만으로는 "수량 소진으로 새 사용자가 실패한 것"인지 "이미 발급받은 사용자의 중복 소비인 것"인지 구분이 안 된다. coupon_issue에 (event_id=100, user_id=10) 기록이 있으면 이미 처리된 중복 소비이므로 성공적으로 Offset을 커밋하면 된다. 기록이 없으면 수량 소진으로 처리 불가한 상황이다.

### 6. 다음 두 상황을 구분하는 처리 흐름 작성하기

```
조건부 UPDATE 실행 → 영향받은 row = 0
  │
  └─ coupon_issue WHERE event_id=:eventId AND user_id=:userId 조회
        │
        ├─ 상황 A: 기록 존재
        │    → 이미 정상 처리된 중복 소비
        │    → 메시지 처리 완료로 간주
        │    → Consumer Group Offset 커밋
        │
        └─ 상황 B: 기록 없음
             → 수량 초과 (SOLD_OUT) 또는 이벤트 없음
             → 처리 불가 메시지
             → Consumer Group Offset 커밋
               (재처리해도 결과가 달라지지 않으므로 Offset은 커밋해 유실 방지)
               이후 DLQ 또는 별도 실패 로그로 기록
```

### 7. 전체 Consumer 처리 흐름 완성하기

```
Kafka 메시지 수신 (event_id, user_id)
  │
  ├─ BEGIN TRANSACTION
  │
  ├─ [조건부 UPDATE]
  │   WHERE id = :eventId AND issued_count < total_quantity
  │
  ├─ 영향받은 row = 1 경로
  │    ├─ coupon_issue INSERT
  │    │    ├─ 성공 → COMMIT → Offset 커밋 → 처리 완료
  │    │    └─ UNIQUE 위반 → ROLLBACK
  │    │         └─ coupon_issue 기록 조회
  │    │              ├─ 있음 → 중복 소비 → Offset 커밋 → 처리 완료
  │    │              └─ 없음 → 예상치 못한 오류 → DLQ 처리
  │
  └─ 영향받은 row = 0 경로
       ├─ ROLLBACK (트랜잭션 종료)
       ├─ coupon_issue 기록 조회
       │    ├─ 있음 → 중복 소비 → Offset 커밋 → 처리 완료
       │    └─ 없음 → 수량 소진 또는 이벤트 없음 → Offset 커밋 (재처리 불필요) → 실패 로그
```

## 과제 9. DB 동시성 제어 방식 비교하기

### 1. 조건부 UPDATE 방식 설명

UPDATE 문에 `issued_count < total_quantity` 조건을 포함해 조건을 만족할 때만 증가시킨다. DB가 UPDATE 실행 중 해당 row에 락을 획득해 다른 트랜잭션의 동일 row UPDATE를 직렬화한다. 결과가 1이면 성공, 0이면 실패로 처리한다. 별도로 SELECT 없이 단일 UPDATE 문으로 수량 확인과 증가를 원자적으로 처리한다.

### 2. 비관적 락 방식 설명과 SQL 예시

```sql
-- 조회 시점에 row 락 획득
SELECT id, issued_count, total_quantity
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

-- 애플리케이션에서 수량 확인 후
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId;
```

설명: 조회 시점에 `FOR UPDATE`로 row 수준 배타 락을 획득한다. 락을 보유한 트랜잭션이 Commit 또는 ROLLBACK할 때까지 다른 트랜잭션은 같은 row를 읽을 때(SELECT FOR UPDATE) 대기한다. 충돌 가능성을 비관적으로 가정해 미리 락을 잡는 방식이다.

### 3. 낙관적 락 방식 설명과 SQL 예시

```sql
-- version을 함께 조회
SELECT id, issued_count, total_quantity, version
FROM coupon_event
WHERE id = :eventId;

-- UPDATE 시 version 조건 포함
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND issued_count < total_quantity
  AND version = :readVersion;

-- 영향받은 row = 0이면 다른 트랜잭션이 먼저 변경 → 재시도
```

설명: 충돌이 드물다고 낙관적으로 가정해 조회 시 락을 잡지 않는다. UPDATE 시 읽은 시점의 version이 일치할 때만 변경한다. 다른 트랜잭션이 먼저 변경해 version이 달라지면 UPDATE 결과가 0이 되고 애플리케이션에서 재시도한다.

### 4. 세 방식 비교표

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | UPDATE 조건문으로 수량 확인과 증가를 동시에 처리 | SELECT FOR UPDATE로 먼저 row 락 획득 후 UPDATE | version 컬럼으로 변경 충돌 감지 후 재시도 |
| 충돌 시 동작 | UPDATE 조건 불만족으로 row = 0 반환, 즉시 실패 처리 | 락 획득까지 대기 | version 불일치로 UPDATE row = 0, 재시도 |
| 재시도 필요 여부 | 불필요 | 불필요 (대기 후 처리) | 필요 |
| 장점 | 단순하고 락 대기 없음. SELECT 없이 단일 UPDATE로 처리 | 충돌이 많을 때 재시도 없이 처리 가능 | 락이 없어 읽기가 많은 환경에서 유리 |
| 단점 | UPDATE 실패 원인을 애플리케이션에서 별도 구분해야 함 | 동시 요청이 많으면 락 경합으로 처리 지연 발생 | 충돌이 많으면 재시도가 반복되어 성능 저하 |
| 선착순 이벤트 적합성 | 높음. 동시 요청이 많고 쿠폰은 선착순이라 실패가 자연스러움 | 보통. 락 대기로 인한 지연이 선착순 형평성에 영향 가능 | 낮음. 충돌이 많은 선착순에서 재시도 폭발 가능 |

### 5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제

비관적 락 방식에서는 하나의 row에 락이 집중되어 모든 요청이 이전 트랜잭션의 Commit을 기다려야 한다. 요청이 폭증하면 락 대기 시간이 급증하고 처리 지연이 발생한다. 락 타임아웃이 발생할 수도 있다. 낙관적 락 방식에서는 충돌이 빈번해 재시도가 반복되면서 시스템 부하가 오히려 증가할 수 있다.

### 6. 이번 구조에서 조건부 UPDATE를 선택하는 이유

선착순 이벤트에서는 수량 초과 요청이 실패하는 것이 자연스러운 결과다. 조건부 UPDATE는 별도 SELECT 없이 단일 UPDATE로 수량 확인과 증가를 원자적으로 처리해 단순하다. 락 대기 없이 즉시 성공·실패를 판단할 수 있어 대량 동시 요청 환경에서 처리 지연을 최소화한다.

### 7. 세 방식과 UNIQUE 제약의 역할이 다른 이유

조건부 UPDATE, 비관적 락, 낙관적 락은 모두 전체 수량 초과를 방지하는 수량 제어 장치다. 반면 `UNIQUE(event_id, user_id)`는 같은 사용자가 중복 발급받는 것을 방지한다. 수량 초과 방지와 중복 발급 방지는 서로 다른 문제이므로, 두 방어 장치가 함께 필요하다.

## 과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기

### 1. Redis 통과 후 Kafka 발행 실패 상황

### 2. Kafka 발행 후 DB 저장 실패 상황

| **시스템** | **남아 있는 상태** |

| Redis | `coupon:{eventId}:issued-users` Set에 userId가 추가된 상태 |
| Kafka | 메시지가 Topic에 존재한다. Consumer Group Offset이 커밋되지 않았으면 재처리 대상이다 |
| DB | 아무 변경 없음. 트랜잭션 ROLLBACK으로 issued_count와 coupon_issue 모두 이전 상태다 |

### 3. DB 저장 후 Redis 데이터 유실 상황

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | userId가 Set에서 사라진 상태. 이 사용자의 재요청이 ACCEPTED로 판정될 수 있다 |
| DB | coupon_issue에 발급 기록이 존재한다. issued_count도 증가된 상태다 |

### 4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유

Redis는 인메모리 저장소로 장애 시 데이터가 유실될 수 있고 영속성을 보장하지 않는다. Kafka는 메시지의 전달과 소비 상태를 관리하지만 최종 발급 결과를 직접 저장하지 않는다. DB만이 트랜잭션과 영속 저장을 통해 최종 발급 기록을 신뢰성 있게 보관한다. 따라서 실제로 쿠폰이 발급됐는지는 coupon_issue 테이블의 기록으로만 확인할 수 있다.

### 5. Redis, Kafka, DB의 역할 비교표

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순/중복 판정 | 비동기 메시지 전달 및 버퍼링 | 최종 발급 기록 영속 저장 및 정합성 보장 |
| 저장하는 상태 | 통과 사용자 Set (임시) | 쿠폰 발급 요청 메시지 | coupon_event issued_count, coupon_issue 발급 기록 |
| 성공이 의미하는 것 | ACCEPTED: 선착순 판정 통과 | PUBLISHED: 메시지 Topic 저장 완료 | ISSUED: 쿠폰 발급 기록 Commit 완료 |
| 강점 | 인메모리로 초고속 처리, 원자적 Lua Script | 대용량 메시지 내구성 저장, 처리 속도 완충 | 트랜잭션, 제약 조건으로 강력한 정합성 보장 |
| 한계 | 영속성 없음, 장애 시 데이터 유실 가능 | 발급 결과를 직접 저장하지 않음 | 고동시성 집중 시 Lock 경합과 병목 가능 |

### 6. 5주차 requestId 기반 멱등성에서 해결할 문제

Redis SUCCESS 후 Kafka 발행에 실패하면 Redis에 userId가 남아 있어 사용자가 재시도할 때 DUPLICATE로 차단된다. requestId를 이용해 동일한 요청을 재전송해도 이미 처리된 요청인지 새로운 재시도인지 구분할 수 있게 한다. 또한 Consumer가 같은 메시지를 중복 소비할 때 requestId로 이미 처리된 요청임을 확인해 DB 처리를 건너뛸 수 있다.

### 7. 6주차 Outbox Pattern에서 해결할 문제

DB 저장과 Kafka 발행이 별개의 작업이므로 DB Commit 후 Kafka 발행에 실패하면 DB에는 기록이 있지만 이후 서비스(알림, 마이페이지 갱신 등)에 이벤트가 전달되지 않는다. Outbox Pattern은 DB 트랜잭션 안에 이벤트 발행 기록도 함께 저장해 DB Commit과 이벤트 발행의 원자성을 보장한다. 발행 실패 시 Outbox 레코드가 남아 있어 재발행이 가능하다.

### 8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유

Outbox Pattern은 DB 트랜잭션 내에서 비즈니스 로직 저장과 Outbox 이벤트 저장을 원자적으로 묶는 패턴이다. 그러나 Redis 판정과 최초 Kafka 발행은 DB 트랜잭션 바깥에서 이루어진다. Redis는 인메모리 저장소로 DB 트랜잭션에 참여할 수 없으므로, Redis 판정 → Kafka 발행 사이의 원자성은 Outbox Pattern으로도 해결되지 않는다. 이 구간의 불일치는 보상 트랜잭션(Redis SREM)이나 requestId 기반 재시도로 별도 처리해야 한다.

### 9. 8주차 Retry와 DLQ에서 해결할 문제

Consumer가 DB 처리에 실패한 경우 일시적 장애라면 Retry Topic에서 재시도하고, 영구적으로 처리 불가한 메시지는 DLQ에 격리해 운영자가 수동으로 처리한다. 무한 재시도를 방지하고 처리 불가 메시지를 유실 없이 관리하는 구조를 다룬다. 또한 DB 처리 실패 후 Redis 상태를 복구하는 보상 트랜잭션 설계도 이 단계에서 구체화된다.
