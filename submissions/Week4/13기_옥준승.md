## **과제 1. DB 최종 발급 처리 구조 그리기**

Redis 판정을 통과한 요청이 Kafka를 거쳐 DB에 최종 저장되는 전체 구조를 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka

Coupon Issue Consumer

coupon_event

coupon_issue
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
	↓ 쿠폰 발급 요청
API Server
	↓ 인증 및 이벤트 기본 검증
Redis
	↓ 중복 사용자 및 잔여 수량 원자적으로 판정
API Server
	↓ 판정을 통과한 요청을 Kafka에 발행
Kafka
	↓ 발급한 요청 메시지 전달
Coupon Issue Consumer
	↓ DB 트랜잭션으로 최종 발급 처리
DB Transaction
	├─coupon_event -> issued_count 조건부 UPDATE (수량 확보)
  └─coupon_issue INSERT (발급 기록 저장)
```

### **2. Redis 판정 통과가 최종 발급 성공이 아닌 이유**

```
Redis 통과 후에도 Kafka 발행 실패, Consumer 장애, DB 저장 실패가 발생할 수 있고, Redis 데이터 자체가 유실될 수도 있다.
```

### **3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유**

```
Kafka 발행 후에도 Consumer 처리 실패나 DB 트랜잭션 Rollback으로 발급이 안 될 수 있다. Kafka는 메시지 전달만 담당하고 발급 상태를 확정하지 않는다.
```

### **4. 최종 발급 성공으로 판단할 수 있는 시점**

```
발급 기록 저장 트랜잭션이 Commit된 시점, 즉 DB ISSUED 상태가 되었을 때 최종 발급 성공으로 판단할 수 있다.

Commit 이전에는 Rollback 가능성이 남아 있다.
조건부 UPDATE가 성공했더라도 이어지는 coupon_issue INSERT가
UNIQUE 제약에 걸리면 issued_count 증가까지 함께 취소된다.

Commit 이후부터 coupon_issue의 발급 기록이 DB에 확정되고
issued_count 증가도 함께 반영된 상태로 유지된다.
따라서 Redis ACCEPTED나 Kafka PUBLISHED가 아니라
DB 트랜잭션 Commit이 최종 발급 성공의 기준 시점이다.
```

### **5. Redis, Kafka, DB 단계의 상태 차이**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준으로 선착순 판정 통과 | x |
| Kafka PUBLISHED | 발급 요청 메시지가 Kafka에 저장 | x |
| DB ISSUED | 발급 기록 저장 트랜잭션이 커밋 | o |

## **과제 2. DB가 보장해야 하는 불변식 정의하기**

쿠폰 발급 시스템이 장애와 동시 요청 상황에서도 지켜야 하는 조건을 불변식으로 정의한다.

이번 과제에서는 다음 세 가지 불변식을 기준으로 작성한다.

```
불변식 1.

한 사용자는 하나의 이벤트에서
쿠폰을 최대 한 번만 발급받는다.

불변식 2.

발급 수량은 0보다 작거나
전체 수량보다 많을 수 없다.

불변식 3.

issued_count 증가와 coupon_issue 저장은
함께 성공하거나 함께 실패한다.
```

### **1. 불변식이 필요한 이유**

```
쿠폰 발급 시스템에는 정상 상황이 아니라 장애와 동시 요청 상황에서
데이터가 깨진다. Redis 유실, Kafka 중복 소비, Consumer 장애처럼
언제든 발생할 수 있는 예외 상황에서도 절대 깨지면 안 되는 조건을
먼저 명시해야 한다.

불변식을 정의하면 다음이 가능해진다.

1. 어떤 상태를 깨진 데이터로 볼지 판단 기준이 생긴다.
2. 각 불변식마다 어떤 장치로 방어할지 설계 근거가 생긴다.
   (중복 발급 → UNIQUE, 수량 초과 → 조건부 UPDATE,
    두 테이블 일관성 → Transaction)
3. 애플리케이션 로직만으로는 보장할 수 없는 조건을 구분해
   DB 제약을 마지막 방어선으로 둘 수 있다.

정상 흐름만 기준으로 설계하면 예외 상황에서 어떤 조건이 깨졌는지
판단할 수 없으므로, 방어 장치를 선택하기 전에 불변식부터 정의해야 한다.
```

### **2. 각 불변식이 깨졌을 때 발생하는 문제**

| **불변식** | **깨졌을 때 발생하는 문제** |
| --- | --- |
| 사용자별 최대 1회 발급 | 중복 발급 발생 |
| 전체 수량 이하 발급 | 전체 수량보다 많은 쿠폰 발급 |
| 수량과 발급 기록의 동시 성공·실패 | 수량과 기록의 불일치 발생 → 유령 발급, 전체 수량보다 많은 쿠폰 발급 |

### **3. 각 불변식을 보호하는 DB 장치**

| **불변식** | **DB 방어 장치** |
| --- | --- |
| 사용자 중복 발급 방지 | UNIQUE(event_id, user_id) |
| 전체 수량 초과 방지 | 조건부 UPDATE, 수량 CHECK |
| 두 테이블의 일관성 | DB Transaction |

### **4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유**

```
조회와 INSERT 사이에 다른 트랜잭션이 끼어들 수 있어, 요청 두개가 동시에 들어오면 둘 다 기존 기록이 없다고 확인을 받아 중복 발급이 발생할 수 있다. 이로 인해 전체 수량을 초과하는 발급이 발생할 수 있다.
```

## **과제 3. coupon_event와 coupon_issue 테이블 설계하기**

쿠폰 이벤트와 최종 발급 기록을 저장할 테이블을 설계한다.

완전한 운영용 스키마를 만드는 것이 목적은 아니다. 이번 주차에서 필요한 불변식을 지킬 수 있도록 핵심 컬럼과 제약 조건을 작성한다.

### **1. coupon_event 테이블의 역할**

```
쿠폰 이벤트의 id와 start_at, end_at 정보를 저장하고, 전체 발급 가능 수량, 완료된 발급 수량 정보를 저장한다.

낙관적 락을 사용하는 경우 version 정보를 저장한다.
```

### **2. coupon_issue 테이블의 역할**

```
event_id와 user_id를 저장하여 최종 발급에 성공한 사용자별 기록을 저장한다.
```

### **3. 두 테이블의 관계를 다이어그램으로 표현하기**

```
+----------------------+
| coupon_event         |
|----------------------|
| id                   |
| name                 |
| total_quantity       |
| issued_count         |
| start_at             |
| end_at               |
| status               |
| version              |
+----------------------+
          |
          | 1 : N
          v
+----------------------+
| coupon_issue         |
|----------------------|
| id                   |
| event_id             |
| user_id              |
| status               |
| issued_at            |
+----------------------+
```

### **4. coupon_event 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

name

total_quantity

issued_count

start_at

end_at

status

version (낙관적 락을 선택할 경우)

수량 CHECK 제약

이벤트 기간 CHECK 제약
```

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,

    name VARCHAR(100) NOT NULL,

    -- 전체 발급 가능 수량
    total_quantity INT NOT NULL,

    -- DB 트랜잭션이 완료된 발급 수량
    issued_count INT NOT NULL DEFAULT 0,

    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,

    -- READY, OPEN, CLOSED
    status VARCHAR(20) NOT NULL,

    -- 낙관적 락을 선택할 경우 사용한다.
    version BIGINT NOT NULL DEFAULT 0,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

### **5. coupon_issue 테이블 DDL 작성하기**

아래 컬럼과 제약 조건을 포함한다.

```
id

event_id

user_id

status

issued_at

coupon_event를 참조하는 Foreign Key

동일 이벤트의 사용자 중복 발급을 막는 UNIQUE 제약
```

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,

    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,

    -- 이번 주차에서는 ISSUED만 저장한다.
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',

    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### **6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점**

```
issued_count를 coupon_event에 별도로 저장하는 이유는 다음과 같다
- 남은 수량을 빠르게 판단할 수 있음
- DB 기준 발급 현황을 빠르게 조회할 수 있음
- Redis와 DB의 수량 차이를 비교할 수 있음
- DB 전체 수량 초과를 다시 방어할 수 있음

단점으로는 동시성 제어가 필요하고, 트랜잭션으로 묶어서 issued_count와 발급 기록이 어긋나지 않도록 해줘야한다는 점이 있다.
```

## **과제 4. UNIQUE 제약의 역할과 한계 분석하기**

`UNIQUE(event_id, user_id)`가 어떤 문제를 막고, 어떤 문제는 막지 못하는지 분석한다.

### **1. `UNIQUE(event_id, user_id)`가 의미하는 규칙**

```
event_id, user_id 쌍이 중복될 수 없게 하여 같은 사용자의 중복 발급을 방지한다.
```

### **2. 다음 INSERT의 성공 여부와 이유**

기존 데이터는 다음과 같다.

```
event_id = 100
user_id = 10
```

| **새로운 INSERT** | **성공 또는 실패** | **이유** |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | 중복 발급 요청이기 때문에 DB UNIQUE 방어 장치에 의해 실패 |
| event_id=100, user_id=11 | 성공 | DB UNIQUE 제약 조건에 걸리지 않으므로 성공 |
| event_id=101, user_id=10 | 실패 | event_id에 해당하는 이벤트가 없기 때문에(진행 중인 다른 이벤트가 있고, 그 이벤트의 id가 101인 경우 중복 요청이 아니라면 성공) |

### **3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition**

아래 상황을 시간 순서로 표현한다.

```
Transaction A가 user:10의 발급 기록을 조회한다.

Transaction B도 user:10의 발급 기록을 조회한다.

두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

두 트랜잭션이 동시에 INSERT를 시도한다.
```

답변:

```
1. Transaction A가 user:10의 발급 기록을 조회한다.

2. Transaction B도 user:10의 발급 기록을 조회한다.

3. 두 트랜잭션 모두 아직 발급 기록이 없다고 판단한다.

4. 두 트랜잭션이 동시에 INSERT를 시도한다.

Transaction A가 조회하고 INSERT 하기 전에 Transaction B가 조회하여 둘 모두 user:10의 발급 기록이 없다고 판단

이후 두 트랜잭션이 INSERT를 실행하여 한 사용자에 대한 중복된 발급 기록이 남게됨
```

### **4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유**

아래 상황을 기준으로 설명한다.

```
전체 수량: 1,000개

서로 다른 사용자: 1,001명

모든 (event_id, user_id) 조합은 서로 다름
```

```
UNIQUE 제약은 전체 수량과 발급 완료된 수량을 모르기 때문에 수량 초과를 막을 수 없다.
```

### **5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?**

| **문제** | **DB 방어 장치** |
| --- | --- |
| 같은 사용자의 중복 발급 | UNIQUE 제약 |
| 서로 다른 사용자에 의한 전체 수량 초과 | 조건부 UPDATE, 수량 CHECK |

## **과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기**

쿠폰 수량이 남아 있을 때만 `issued_count`를 증가시키는 조건부 UPDATE를 설계한다.

### **1. 조건부 UPDATE SQL 작성하기**

다음 조건을 만족해야 한다.

```
event_id가 일치해야 한다.

issued_count가 total_quantity보다 작을 때만 증가해야 한다.

issued_count는 1 증가해야 한다.
```

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### **2. 영향받은 row 수가 의미하는 것**

```
조건부 UPDATE의 WHERE 조건을 만족해 issued_count가 실제로 증가한 coupon_event 행의 개수

id가 PK이므로 조건을 만족해도 최대 1개이며, 결과는 0 또는 1이다.
별도의 SELECT 없이 이 값 하나로 수량 확보 성공 여부를 판단할 수 있다.
```

### **3. 영향받은 row 수가 1인 경우**

```
WHERE 조건(이벤트 존재 + issued_count < total_quantity)을 만족해 해당 이벤트의 issued_count가 1 증가한 경우다.
이 트랜잭션이 남은 수량 한 개를 확보했으므로 coupon_issue INSERT로 진행한다.

다만 이 시점은 수량 확보에 성공한 것일 뿐 발급 확정은 아니다.
이어지는 INSERT가 UNIQUE 제약을 위반하면 트랜잭션 전체가 Rollback되어 증가한 issued_count도 취소된다.
```

### **4. 영향받은 row 수가 0인 경우 가능한 원인**

과제 5-1의 SQL은 `event_id`와 수량 조건만 사용한다. 중복 메시지 여부는 UPDATE 결과가 0인 직접 원인이 아니라, 이후 기존 발급 기록을 조회해 구분한다.

```
1. event_id에 해당하는 이벤트가 없는 경우

2. 쿠폰 수량이 소진된 경우
```

### **5. 다음 상황에서 UPDATE 결과를 작성하기**

과제 5-1에서 작성한 조건부 UPDATE를 사용한다고 가정한다.

| **상황** | **issued_count** | **total_quantity** | **이벤트 존재 여부** | **영향받은 row 수** | **결과** |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | 성공 |
| B | 1,000 | 1,000 | 존재 | 0 | 실패 |
| C | - | - | 존재하지 않음 | 0 | 실패 |

### **6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석**

```
전체 수량: 1,000개

현재 issued_count: 999

Transaction A와 Transaction B가
동시에 조건부 UPDATE 실행
```

두 트랜잭션의 실행 결과를 시간 순서 다이어그램으로 작성한다.

```
Transaction A에서 조건부 UPDATE 실행
↓
id = :eventId AND issued_count < total_quantity를 검증
↓
999<1000 이므로 issued_count = issued_count + 1
↓
Transaction B에서 조건부 UPDATE 실행
↓
id = :eventId AND issued_count < total_quantity를 검증
↓
issued_count == total_quantity 이므로 발급 실패
```

### **7. issued_count가 total_quantity를 초과하지 않는 이유**

```
DB는 같은 row에 대한 UPDATE를 직렬화한다.
먼저 진입한 트랜잭션이 해당 coupon_event row의 lock을 획득하고,
뒤이은 트랜잭션은 그 lock이 해제될 때까지 대기한다.

대기하던 트랜잭션은 lock 해제 후 갱신된 최신 값으로 WHERE 조건을 다시 평가한다.
따라서 각 트랜잭션은 항상 그 시점의 최신 issued_count를 기준으로 판단한다.

issued_count == total_quantity가 되면 issued_count < total_quantity 조건을 만족하는 row가 없어 영향받은 row 수가 0이 되고 issued_count + 1은 실행되지 않는다.

즉, 확인과 증가가 하나의 SQL에서 원자적으로 수행되고, 동일 row 갱신이 직렬화되어 항상 최신 값을 기준으로 조건을 평가하므로 issued_count는 total_quantity를 초과할 수 없다.
```

## **과제 6. 발급 트랜잭션과 Rollback 설계하기**

다음 두 작업을 하나의 DB 트랜잭션으로 묶는 이유를 설명한다.

```
1. coupon_event.issued_count 증가

2. coupon_issue 발급 기록 INSERT
```

### **1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제**

| **상황** | **발생하는 데이터 불일치** |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 줄었지만 발급 받은 사용자가 없음 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급 받은 사용자는 있지만 수량이 줄어들지 않음 |

### **2. 하나의 트랜잭션으로 처리하는 전체 흐름**

```
Transaction 시작
  |
  v
조건부 UPDATE로 수량 확보
  |
  +-- 결과 = 0
  |     → 기존 coupon_issue 기록 조회
  |     → 중복 메시지와 실제 발급 실패 구분
  |
  +-- 결과 = 1
        |
        v
      coupon_issue INSERT
        |
        +-- 성공 → Commit
        |
        +-- 실패 → Rollback
```

### **3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기**

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 영향받은 row 수가 0이면 INSERT를 실행하지 않고 트랜잭션을 종료한다.
-- 이후 기존 coupon_issue 기록을 조회해
-- 이미 처리된 중복 메시지와 실제 발급 실패를 구분한다.

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status
) VALUES (
    :eventId,
    :userId,
    'ISSUED'
);

-- 두 작업이 모두 성공하면 Commit
COMMIT;

-- INSERT가 UNIQUE 제약을 위반하면 트랜잭션 전체를 Rollback한다.
-- 앞에서 증가한 issued_count도 함께 취소된다.
-- ROLLBACK;
```

### **4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우**

아래 항목을 모두 설명한다.

```
현재 트랜잭션은 어떻게 되는가?

앞에서 증가한 issued_count는 어떻게 되는가?

기존 발급 기록은 언제 조회해야 하는가?
```

답변:

```
현재 트랜잭션은 어떻게 되는가?

INSERT가 UNIQUE 제약을 위반하면 PostgreSQL은 해당 트랜잭션을
aborted 상태로 전환한다. 이후 모든 명령은 실행되지 않고 거부되므로 애플리케이션이 ROLLBACK을 실행해 트랜잭션을 종료해야 한다.
결과적으로 트랜잭션 전체가 취소된다.

앞에서 증가한 issued_count는 어떻게 되는가?

UPDATE와 INSERT가 하나의 트랜잭션이므로 Rollback 시 증가한 것도 함께 취소되어 원래 값으로 복구된다.
따라서 실제로 발급되지 않은 요청 때문에 수량이 소모되는 일은 없다.

기존 발급 기록은 언제 조회해야 하는가?

aborted 상태에서는 조회를 실행할 수 없으므로, 반드시 Rollback으로 현재 트랜잭션을 종료한 뒤 새 트랜잭션에서 조회한다.
동일한 (event_id, user_id) 기록이 존재하면 이미 처리된 중복 메시지로 정상 처리하고, 기록이 없으면 예상하지 못한 오류로 처리한다.
```

### **5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유**

```
PostgreSQL에는 statement-level undo가 없어서 에러가 나면 서버는 트랜잭션을 ABORT 상태로 전환하고, 이후 모든 명령은 실행 없이 거부하기 때문에 같은 트랜잭션을 계속 사용할 수 없다.
```

### **6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유**

```
한 경로의 누락이 그 경로만의 문제로 끝나지 않고 정상 경로의 방어 장치까지 무력화한다. 따라서 발급 처리는 하나의 서비스 메서드로 통합해 모든 경로가 동일한 트랜잭션 흐름을 거치도록 해야 한다.
```

## **과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기**

Kafka Consumer는 같은 메시지를 다시 처리할 수 있다.

아래 상황을 기준으로 분석한다.

```
1. Consumer가 발급 요청 메시지를 읽는다.

2. DB 발급 트랜잭션을 Commit한다.

3. Consumer Group Offset 커밋 전에 Consumer가 종료된다.

4. Consumer가 재시작된다.

5. 같은 메시지를 다시 읽는다.
```

### **1. 중복 소비가 발생하는 전체 흐름 다이어그램**

```
Kafka 메시지 수신
↓
DB 발급 트랜잭션 commit
↓
Offset 반영 전 Consumer 종료 (장애 발생)
↓
재시작 후 Kafka에서 같은 메시지 재소비
```

### **2. DB에 UNIQUE 제약이 없다면 발생하는 문제**

```
Kafka에서 중복 소비가 발생하는 경우 이를 DB에서 제어하지 못해 한 사용자에 대해서 중복 발급문제가 발생한다.
```

### **3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정**

```
DB 발급 트랜잭션이 Commit되면 (event_id, user_id) 행이 coupon_issue에 저장된다.
이후 Offset 커밋 전 장애로 Consumer가 종료되고, 재시작 후 같은 메시지를 재소비한다.

수량이 남아 있는 경우
조건부 UPDATE는 1을 반환하지만 이어지는 INSERT에서 UNIQUE 제약을 위반한다.
트랜잭션 전체가 Rollback되어 증가한 issued_count도 함께 취소된다.

수량이 이미 소진된 경우
조건부 UPDATE가 0을 반환하므로 INSERT까지 도달하지 않는다.

수량이 남아 있는 경우 Rollback 후 새 트랜잭션에서 기존 기록을 조회하고 수량이 이미 소진된 경우 같은 트랜잭션에서 기존 기록을 조회한다. 기록이 존재하면 이미 처리된 메시지로 정상 처리하고 Offset을 커밋한다.

따라서 중복 소비 자체는 발생하지만 UNIQUE 제약이 최종 방어선 역할을 해 DB에 중복 발급 기록이 남지 않는다.
```

### **4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건**

```
Rollback 후 새 트랜잭션에서 조회했을 때 현재 메시지와 동일한 (event_id, user_id) 기록이 존재해야 한다.
```

### **5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서**

```
1. 현재 트랜잭션을 Rollback한다.

2. 새 트랜잭션에서 동일한 (event_id, user_id) 발급 기록을 조회한다.

3. 기록이 존재하면 이미 처리된 중복 메시지로 정상 처리하고 Consumer Group Offset을 커밋한다.

4. 기록이 없으면 예상하지 못한 오류로 처리한다. Offset을 커밋하지 않고 재시도 대상으로 넘긴다.
```

### **6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유**

```
Offset을 먼저 커밋한 뒤 DB 처리 전에 Consumer가 종료되면,
재시작 후 해당 메시지를 다시 읽지 않으므로 발급 요청이 유실된다.

중복 소비는 UNIQUE 제약으로 DB에서 방어할 수 있지만, 메시지 유실은 DB에 도달 자체를 못 하므로 복구 수단이 없다. 따라서 DB 처리 결과가 확정된 후에 Offset을 커밋해야 한다.
```

### **7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이**

```
UNIQUE(event_id, user_id)는 같은 사용자는 같은 이벤트에서 한 번만 발급 받는다는 비즈니스 규칙 수준의 멱등성이다. 이는 결과의 중복만 막는다.

requestId 기반 멱등성은 요청 자체를 식별한다. 동일 requestId의 처리 상태(처리 중/성공/실패)와 결과를 저장해두고, 재요청이 오면 다시 처리하지 않고 저장된 결과를 반환할 수 있다.

즉 UNIQUE는 중복 결과 차단만 하고, requestId는 동일 요청의 상태·결과 관리까지 한다. 
```

## **과제 8. 품절 후 중복 메시지 재처리 분석하기**

조건부 UPDATE를 먼저 실행하는 구조에서는 중복 메시지가 항상 INSERT까지 도달하는 것은 아니다.

아래 상황을 기준으로 분석한다.

```
이벤트 ID: 100

전체 수량: 1개

현재 issued_count: 1

coupon_issue에
(event_id=100, user_id=10) 기록이 이미 존재

user:10의 Kafka 메시지가 다시 전달됨
```

### **1. 조건부 UPDATE 결과와 그 이유**

```
조건부 UPDATE 결과 0이 나온다.
전체 수량이 1개이고 issued_count도 1이므로 issued_count == total_quantity가 되어 영향 받는 row 수가 0이 되기 때문이다.
```

### **2. coupon_issue INSERT까지 실행되는가?**

```
조건부 UPDATE가 실패하여 INSERT가 실행되지 않는다.
```

### **3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?**

```
INSERT가 실행되지 않기 때문에 UNIQUE 제약 위반은 발생하지 않는다.
```

### **4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유**

```
row가 0인 경우 해당 요청이 수량을 확보하지 못했다는 것을 의미하는데 이는 이밴트가 존재하지 않는 경우와 품절 두가지 경우가 존재한다. 또한, 수량 소진 상태에서 이미 발급 받은 사용자의 중복 메시지가 재처리되는 경우 row가 0임을 보고 품절로 판단하면 실제로 발급에 성공한 사용자를 실패로 잘못 기록하게 된다.  
```

### **5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유**

```
위에선 언급한 수량 소진 상태에서 이미 발급 받은 사용자의 중복 메시지가 재처리되는 경우 row가 0임을 보고 품절로 판단하면 실제로 발급에 성공한 사용자를 실패로 잘못 기록하게 된다. 이러한 경우를 방지하며 처리된 중복 메시지인지 여부를 확인하기 위해서 coupon_issue 기록을 확인해야 한다.
```

### **6. 다음 두 상황을 구분하는 처리 흐름 작성하기**

각 상황에서 메시지 처리 완료 여부와 Consumer Group Offset 커밋 여부도 함께 작성한다.

```
상황 A

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 존재

상황 B

조건부 UPDATE 결과 = 0
동일한 coupon_issue 기록 없음
```

답변:

```
Transaction 시작
↓
조건부 UPDATE로 수량 확보
↓
결과 = 0 (예외 없음 → 트랜잭션 정상 상태)
↓
같은 트랜잭션에서 동일한 (event_id, user_id) 기록 조회
↓                              ↓
기록 존재 (상황 A)              기록 없음 (상황 B)
↓                              ↓
이미 처리된 중복 메시지          실제 수량 소진 또는 이벤트 없음

INSERT 없이 트랜잭션 종료        실패 로그·메트릭 기록
↓                              ↓
메시지 처리 완료                 트랜잭션 종료
↓                              ↓
Offset 커밋                     메시지 처리 완료

```

## **과제 9. DB 동시성 제어 방식 비교하기**

다음 세 가지 방식으로 쿠폰 수량을 제어할 수 있다.

```
조건부 UPDATE

비관적 락

낙관적 락
```

### **1. 조건부 UPDATE 방식 설명**

```
수량 확인과 증가를 하나의 SQL로 수행한다.

장점
- 구현이 단순하다.
- 별도의 조회와 애플리케이션 재시도 없이 수량 초과를 막을 수 있다.
- 영향받은 row 수로 성공 여부를 판단할 수 있다.
주의점
- 같은 이벤트 row에 갱신이 집중되므로 DB 내부의 row lock 대기가 발생할 수 있다.
- INSERT와 반드시 같은 트랜잭션으로 묶어야 한다.
```

### **2. 비관적 락 방식 설명과 SQL 예시**

```sql
SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;
```

설명:

```
이벤트 row를 먼저 잠근 뒤 수량을 확인하고 발급한다.

장점
- 처리 순서와 정합성을 이해하기 쉽다.
- 락을 얻은 트랜잭션이 안전하게 수량을 확인하고 변경할 수 있다.
단점
- 요청이 몰리면 락 대기가 길어진다.
- 트랜잭션이 길어지면 DB 처리량이 크게 감소할 수 있다.
```

### **3. 낙관적 락 방식 설명과 SQL 예시**

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
처음부터 명시적인 락을 잡지 않고, UPDATE 시 읽었던 version과 현재 version이 같은지 확인한다.

장점
- 충돌이 적은 환경에서는 긴 락 대기를 줄일 수 있다.
단점
- 충돌하면 UPDATE가 실패하므로 재시도가 필요하다.
- 선착순 이벤트처럼 하나의 row에 요청이 집중되면 충돌과 재시도가 많아질 수 있다.
```

### **4. 세 방식 비교표**

| **구분** | **조건부 UPDATE** | **비관적 락** | **낙관적 락** |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | WHERE 조건으로 확인과 증가를 하나의 SQL에서 원자적으로 수행 | FOR UPDATE로 row를 먼저 잠근 뒤 확인·변경 | version 비교로 동시 수정 충돌을 감지 |
| 충돌 시 동작 | row lock 대기 후 최신 값으로 조건 재평가 | 락 해제까지 대기 | UPDATE 실패 (영향받은 row 0) |
| 재시도 필요 여부 | 	불필요 | 	불필요 | 필요 |
| 장점 | 구현 단순, 짧은 트랜잭션, row 수로 성공 판단 | 흐름 이해 쉬움, 정합성 명확 | 충돌 적으면 락 대기 없음 |
| 단점 | 동일 row 갱신 집중 시 lock 대기 | 락 대기 길어지면 처리량 급감 | 충돌 많으면 재시도 폭증 |
| 선착순 이벤트 적합성 | 상대적으로 유리 (락 구간 최소) | 불리 (락 구간이 길어 대기 누적) | 불리 (충돌, 재시도 폭증) |

### **5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제**

```
선착순 이벤트는 모든 요청이 coupon_event의 동일한 row를 갱신하므로 DB 내부에서 해당 row lock을 두고 경쟁이 발생한다. 이때 갱신이 직렬화되어 대기 시간이 길어지고, 트랜잭션이 길어질수록 커넥션 점유 시간이 늘어나 전체 처리량이 감소한다. 낙관적 락이라면 대기 대신 충돌·재시도가 폭증한다.
```

### **6. 이번 구조에서 조건부 UPDATE를 선택하는 이유**

```
1. Redis가 앞단에서 대부분의 요청을 걸러내므로
   DB에 도달하는 요청 수 자체가 적다.
2. 확인과 증가가 하나의 SQL이라 트랜잭션이 짧고,
   비관적 락처럼 별도 SELECT ... FOR UPDATE 단계가 없다.
3. 낙관적 락과 달리 애플리케이션 재시도가 필요 없다.
4. 영향받은 row 수만으로 수량 확보 성공 여부를 판단할 수 있어
   Consumer 처리 흐름이 단순해진다.
```

### **7. 세 방식과 UNIQUE 제약의 역할이 다른 이유**

```
세 방식은 모두 coupon_event.issued_count라는 하나의 값에 대한
동시 갱신을 제어해 전체 수량 초과(불변식 2)를 막는 장치다.

UNIQUE 제약은 coupon_issue에 같은 (event_id, user_id) 행이
두 번 들어가는 것을 막아 사용자 중복 발급(불변식 1)을 방어한다.

서로 다른 불변식을 담당하므로 어느 한쪽으로 대체할 수 없고,
이번 구조에서는 조건부 UPDATE + UNIQUE + Transaction을 함께 사용한다.
```

## **과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기**

Redis, Kafka, DB는 서로 다른 시스템이므로 상태가 일시적으로 달라질 수 있다.

Kafka 상태는 발행된 레코드의 존재 여부와 Consumer Group Offset 커밋 여부를 구분해서 작성한다. Kafka 레코드가 존재한다는 사실만으로 처리 대기 상태라고 판단하지 않는다.

### **1. Redis 통과 후 Kafka 발행 실패 상황**

아래 세 시스템에 남는 상태를 작성한다.

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 사용자가 통과 사용자 set에 존재 |
| Kafka | 발행 실패로 레코드 없음 |
| DB | 발급 기록 없음 |

### **2. Kafka 발행 후 DB 저장 실패 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 존재 |
| Kafka | 발행된 레코드 존재, Consumer Group Offset 미커밋 |
| DB | 발급 기록 없음 |

### **3. DB 저장 후 Redis 데이터 유실 상황**

| **시스템** | **남아 있는 상태** |
| --- | --- |
| Redis | 통과 기록 없음 |
| DB | 발급 기록 존재 |

### **4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유**

```
최종 발급 성공의 정의 자체가 coupon_issue 저장 트랜잭션의 Commit이다.

Redis는 유실·초기화될 수 있어 통과 기록이 사라질 수 있고, Kafka는 레코드가 존재해도 그것이 처리 완료를 의미하지 않는다 (레코드는 보존 정책에 따라 소비 후에도 남는다).

DB만이 제약 조건과 트랜잭션으로 불변식을 보장하며 최종 발급 결과를 내구성 있게 보존하므로, 발급 여부 판단의 기준 데이터는 DB의 coupon_issue다.
```

### **5. Redis, Kafka, DB의 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순 판정을 위한 상태 | 발급 요청 레코드와 Consumer Group Offset을 관리하는 메시지 브로커 | 최종 발급 결과의 기준 데이터 |
| 저장하는 상태 | 통과 사용자 set, 잔여 수량 카운터 | 발급 요청 레코드, Consumer Group Offset | coupon_event 수량, coupon_issue 발급 기록 |
| 성공이 의미하는 것 | ACCEPTED(선착순 판정 통과) | PUBLISHED(메시지가 브로커에 저장됨) | ISSUED(최종 발급 확정) |
| 강점 | 원자적 판정으로 대량 트래픽을 빠르게 차단 | 발급 요청 버퍼링, 재처리 가능, API와 Consumer 분리 | 제약 조건과 트랜잭션으로 정합성, 내구성 보장 |
| 한계 | 데이터 유실 가능, 최종 상태 아님 | 중복 전달 가능, 도메인 상태를 관리하지 않음 | 처리량이 낮아 대량 트래픽을 직접 감당하기 어려움 |

### **6. 5주차 requestId 기반 멱등성에서 해결할 문제**

```
동일 요청의 상태와 결과 관리

4주차의 UNIQUE(event_id, user_id)는 "같은 사용자에게 두 번 발급되지 않는다"는
결과 중복만 막는다. 요청 자체를 식별하지 않으므로 다음을 알 수 없다.

- 이 요청이 처리 중인지, 성공했는지, 실패했는지
- 실패했다면 어떤 이유로 실패했는지
- 재조회 시 사용자에게 무엇을 응답해야 하는지

8-5에서 본 것처럼 조건부 UPDATE 결과 0을 실패로 기록하면
실제로 발급받은 사용자에게 실패 응답이 나갈 수 있다.
requestId로 요청 단위의 상태와 결과를 저장하면
재요청 시 재처리 없이 저장된 결과를 그대로 반환할 수 있다.
```

### **7. 6주차 Outbox Pattern에서 해결할 문제**

```
DB 저장과 후속 이벤트 발행 사이의 정합성

4주차는 coupon_issue INSERT가 Commit되는 지점까지만 다룬다.
그런데 발급 이후에는 알림, 마이페이지, 통계 서비스에
CouponIssued 이벤트를 전달해야 한다. (7주차)

이때 DB Commit과 Kafka 발행이 별개 작업이라
Commit 후 발행 실패 시 발급은 됐는데 알림은 안 가는 불일치가 생긴다.
Outbox Pattern은 이벤트 발행 사실을 같은 DB 트랜잭션 안에
outbox 테이블로 함께 기록해 이 구간을 원자적으로 묶는다.
```

### **8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유**

```
Outbox Pattern은 DB 트랜잭션 안에서 이벤트 발행 사실까지 함께 기록해 DB 저장과 그 이후의 이벤트 발행 사이를 원자적으로 묶는 방식이다.

반면 Redis 판정과 최초 Kafka 발행은 API 서버에서 일어나며
DB 트랜잭션 밖의 구간이므로 Outbox가 적용될 대상이 아니다.

따라서 이 구간의 원자성과 실패 보상은 별도의 설계가 필요하다.
```

### **9. 8주차 Retry와 DLQ에서 해결할 문제**

```
실패 메시지 및 Redis-DB 불일치 복구

4주차에서는 재시도가 필요한 실패에서 Offset을 커밋하지 않는 것까지만 정한다.
하지만 다음이 남는다.

- 몇 번까지 재시도할 것인가
- 계속 실패하는 메시지를 언제 DLQ로 보낼 것인가
- 8-6 상황 B처럼 "Redis는 통과시켰지만 DB에는 기록이 없는" 요청을
  어떻게 탐지하고 보정할 것인가

Retry Topic과 DLQ는 재시도 정책을 분리하고,
실패 메시지를 유실 없이 보관해 이후 복구할 수 있게 한다.
```
