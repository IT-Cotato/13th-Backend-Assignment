# 4주차 과제: DB 테이블과 최종 발급 정합성 보장

## 과제 1. DB 최종 발급 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  ↓ 발급 요청
API Server
  ↓ 중복·수량 판정
Redis
  ↓ ACCEPTED 요청 발행
Kafka
  ↓ 메시지 소비
Coupon Issue Consumer
  ↓ DB 트랜잭션 시작
coupon_event 조건부 UPDATE
  ↓ 성공 시
coupon_issue INSERT
  ↓
트랜잭션 커밋
  ↓
컨슈머 그룹 오프셋 커밋
```

### 2. Redis 판정 통과가 최종 발급 성공이 아닌 이유

```
Redis는 요청의 중복과 잔여 수량을 빠르게 판정할 뿐이다.
이후 Kafka 발행이나 DB 저장이 실패할 수 있으므로 최종 발급 성공이 아니다.
```

### 3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유

```
Kafka 발행 성공은 메시지가 저장되었다는 의미다.
컨슈머 처리와 DB 트랜잭션이 실패할 수 있으므로 최종 발급 성공이 아니다.
```

### 4. 최종 발급 성공으로 판단할 수 있는 시점

```
coupon_event의 수량 증가와 coupon_issue 저장이 모두 성공하여
DB 트랜잭션이 커밋된 시점이다.
```

### 5. Redis, Kafka, DB 단계의 상태 차이

| 단계              | 의미            | 최종 발급 성공 여부 |
| --------------- | ------------- | ----------- |
| Redis ACCEPTED  | 선착순·중복 판정 통과  | 아니요         |
| Kafka PUBLISHED | 발급 요청 메시지 저장  | 아니요         |
| DB ISSUED       | DB 발급 트랜잭션 커밋 | 예           |

## 과제 2. DB가 보장해야 하는 불변식 정의하기

### 1. 불변식이 필요한 이유

```
동시 요청, 메시지 중복 처리, 장애가 발생해도
중복 발급과 수량 초과 없이 데이터 정합성을 유지하기 위해 필요하다.
```

### 2. 각 불변식이 깨졌을 때 발생하는 문제

| 불변식                 | 깨졌을 때 발생하는 문제           |
| ------------------- | ----------------------- |
| 사용자별 최대 1회 발급       | 한 사용자가 같은 쿠폰을 여러 번 받는다. |
| 전체 수량 이하 발급         | 준비된 수량보다 많은 쿠폰이 발급된다.   |
| 수량과 발급 기록의 동시 성공·실패 | 발급 수량과 실제 발급 기록이 달라진다.  |

### 3. 각 불변식을 보호하는 DB 장치

| 불변식          | DB 방어 장치                    |
| ------------ | --------------------------- |
| 사용자 중복 발급 방지 | `UNIQUE(event_id, user_id)` |
| 전체 수량 초과 방지  | 조건부 `UPDATE`, 수량 `CHECK`    |
| 두 테이블의 일관성   | DB 트랜잭션                     |

### 4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유

```
두 요청이 동시에 조회하면 모두 기존 기록이 없다고 판단할 수 있다.
따라서 최종 중복 방지는 DB의 UNIQUE 제약이 담당해야 한다.
```

## 과제 3. coupon_event와 coupon_issue 테이블 설계하기

### 1. coupon_event 테이블의 역할

```
쿠폰 이벤트 정보, 전체 수량, DB 기준 발급 수량을 저장한다.
```

### 2. coupon_issue 테이블의 역할

```
어떤 사용자가 어떤 이벤트의 쿠폰을 최종 발급받았는지 저장한다.
```

### 3. 두 테이블의 관계를 다이어그램으로 표현하기

```
coupon_event 1
     │
     │ 1:N
     ▼
coupon_issue N
```

### 4. coupon_event 테이블 DDL 작성하기

```
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    total_quantity INT NOT NULL,
    issued_count INT NOT NULL DEFAULT 0,
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

### 5. coupon_issue 테이블 DDL 작성하기

```
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',
    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### 6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점

```
남은 수량과 발급 현황을 빠르게 확인하고,
DB에서 수량 초과를 방지하기 위해 저장한다.

단점은 coupon_issue 기록 수와 값이 달라질 수 있다는 것이다.
따라서 발급 기록 저장과 같은 트랜잭션에서 변경해야 한다.
```

## 과제 4. UNIQUE 제약의 역할과 한계 분석하기

### 1. `UNIQUE(event_id, user_id)`가 의미하는 규칙

```
같은 사용자는 같은 쿠폰 이벤트에서 한 번만 발급받을 수 있다.
```

### 2. 다음 INSERT의 성공 여부와 이유

| 새로운 INSERT               | 성공 또는 실패 | 이유                  |
| ------------------------ | -------- | ------------------- |
| event_id=100, user_id=10 | 실패       | 기존 조합과 같아 UNIQUE 위반 |
| event_id=100, user_id=11 | 성공       | 사용자가 다름             |
| event_id=101, user_id=10 | 성공       | 이벤트가 다름             |

### 3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition

```
A: 발급 기록 조회 → 없음
B: 발급 기록 조회 → 없음
A: INSERT 시도
B: INSERT 시도

UNIQUE 제약이 없다면 두 INSERT가 모두 성공하여 중복 발급된다.
UNIQUE 제약이 있으면 하나만 성공하고 나머지는 실패한다.
```

### 4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유

```
1,001명의 사용자는 모두 서로 다른 event_id와 user_id 조합을 가진다.
따라서 UNIQUE 제약을 모두 통과할 수 있어 전체 수량 초과를 막지 못한다.
```

### 5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?

| 문제                     | DB 방어 장치                    |
| ---------------------- | --------------------------- |
| 같은 사용자의 중복 발급          | `UNIQUE(event_id, user_id)` |
| 서로 다른 사용자에 의한 전체 수량 초과 | issued_count 조건부 `UPDATE`   |

## 과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기

### 1. 조건부 UPDATE SQL 작성하기

```
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### 2. 영향받은 row 수가 의미하는 것

```
조건을 만족하여 실제로 변경된 이벤트 행의 수를 의미한다.
```

### 3. 영향받은 row 수가 1인 경우

```
이벤트가 존재하고 수량이 남아 있어 발급 수량 확보에 성공한 경우다.
```

### 4. 영향받은 row 수가 0인 경우 가능한 원인

```
1. event_id에 해당하는 이벤트가 존재하지 않는다.

2. issued_count가 total_quantity에 도달하여 수량이 소진되었다.
```

### 5. 다음 상황에서 UPDATE 결과를 작성하기

| 상황 | issued_count | total_quantity | 이벤트 존재 여부 | 영향받은 row 수 | 결과         |
| -- | ------------ | -------------- | --------- | ---------- | ---------- |
| A  | 999          | 1,000          | 존재        | 1          | 1,000으로 증가 |
| B  | 1,000        | 1,000          | 존재        | 0          | 수량 소진      |
| C  | -            | -              | 존재하지 않음   | 0          | 이벤트 없음     |

### 6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석

```
초기값: issued_count = 999

트랜잭션 A
  ↓ 조건부 UPDATE 실행
행 잠금 획득
  ↓
999 → 1,000
  ↓
커밋

트랜잭션 B
  ↓ 같은 UPDATE 실행
A의 행 잠금이 풀릴 때까지 대기
  ↓
최신 값 1,000으로 조건 재확인
  ↓
1,000 < 1,000 조건 불충족
  ↓
영향받은 row 수 = 0
```

### 7. issued_count가 total_quantity를 초과하지 않는 이유

```
DB가 같은 행의 갱신을 직렬화하고,
각 트랜잭션이 최신 값을 기준으로 WHERE 조건을 다시 판단하기 때문이다.
```

## 과제 6. 발급 트랜잭션과 Rollback 설계하기

### 1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제

| 상황                                         | 발생하는 데이터 불일치             |
| ------------------------------------------ | ------------------------ |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 증가했지만 발급 사용자가 없다.    |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급 기록은 있지만 수량에 반영되지 않는다. |

### 2. 하나의 트랜잭션으로 처리하는 전체 흐름

```
트랜잭션 시작
  ↓
조건부 UPDATE
  ├─ 결과 0 → 기존 발급 기록 확인
  └─ 결과 1
       ↓
     coupon_issue INSERT
       ├─ 성공 → 커밋
       └─ 실패 → 전체 롤백
```

### 3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기

```
BEGIN;

UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 영향받은 row 수가 1일 때 실행
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status
) VALUES (
    :eventId,
    :userId,
    'ISSUED'
);

COMMIT;
```

영향받은 row 수가 0이거나 INSERT가 실패하면 다음을 실행한다.

```
ROLLBACK;
```

### 4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우

```
현재 트랜잭션은 실패 상태가 되어 롤백해야 한다.

롤백하면 앞에서 증가한 issued_count도 원래 값으로 복구된다.

기존 발급 기록은 롤백을 완료한 뒤
새 트랜잭션에서 조회해야 한다.
```

### 5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유

```
제약 위반이 발생하면 해당 트랜잭션이 실패 상태가 된다.
롤백하기 전에는 추가 SQL을 정상적으로 실행할 수 없다.
```

### 6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유

```
일부 경로가 수량 증가나 발급 기록 저장만 수행하면
issued_count와 실제 발급 기록이 달라질 수 있기 때문이다.
```

## 과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기

### 1. 중복 소비가 발생하는 전체 흐름 다이어그램

```
메시지 수신
  ↓
DB 발급 트랜잭션 커밋
  ↓
오프셋 커밋 전 컨슈머 장애
  ↓
컨슈머 재시작
  ↓
마지막 미커밋 메시지 재수신
  ↓
같은 발급 요청 재처리
```

### 2. DB에 UNIQUE 제약이 없다면 발생하는 문제

```
같은 사용자의 coupon_issue가 다시 저장되어 중복 발급된다.
issued_count도 중복으로 증가할 수 있다.
```

### 3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정

```
같은 이벤트와 사용자로 INSERT를 다시 시도하면
DB가 UNIQUE 위반을 발생시켜 중복 발급을 차단한다.

앞선 수량 증가도 같은 트랜잭션에서 롤백된다.
```

### 4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건

```
롤백 후 동일한 event_id와 user_id의
ISSUED 발급 기록이 실제로 존재해야 한다.
```

### 5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서

```
1. UNIQUE 위반이 발생한 트랜잭션을 롤백한다.

2. 새 트랜잭션을 시작한다.

3. 동일한 coupon_issue 기록을 조회한다.

4. 기록이 있으면 중복 메시지로 정상 처리하고 오프셋을 커밋한다.
```

기록이 없다면 예상하지 못한 오류로 처리한다.

### 6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유

```
오프셋을 먼저 커밋한 뒤 DB 저장이 실패하면
해당 메시지가 다시 전달되지 않아 발급 요청이 유실된다.
```

### 7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이

```
UNIQUE는 같은 사용자의 같은 이벤트 중복 발급을 막는다.

requestId는 동일한 요청 자체를 식별하고
요청 상태와 처리 결과를 관리한다.
```

## 과제 8. 품절 후 중복 메시지 재처리 분석하기

### 1. 조건부 UPDATE 결과와 그 이유

```
영향받은 row 수는 0이다.

issued_count와 total_quantity가 모두 1이므로
issued_count < total_quantity 조건을 만족하지 않는다.
```

### 2. coupon_issue INSERT까지 실행되는가?

```
실행되지 않는다.
조건부 UPDATE 결과가 0이므로 INSERT 단계로 진행하지 않는다.
```

### 3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?

```
발생하지 않는다.
INSERT 자체가 실행되지 않기 때문이다.
```

### 4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유

```
이미 정상 처리된 사용자의 중복 메시지가
품절 이후 다시 전달된 상황일 수도 있기 때문이다.
```

### 5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유

```
이미 처리된 중복 메시지인지,
실제로 발급받지 못한 품절 요청인지 구분하기 위해서다.
```

### 6. 다음 두 상황을 구분하는 처리 흐름 작성하기

```
상황 A: 동일한 coupon_issue 기록 존재

조건부 UPDATE 결과 0
  ↓
기존 발급 기록 조회
  ↓
기록 존재
  ↓
이미 처리된 중복 메시지로 판단
  ↓
메시지 처리 완료
  ↓
컨슈머 그룹 오프셋 커밋


상황 B: 동일한 coupon_issue 기록 없음

조건부 UPDATE 결과 0
  ↓
기존 발급 기록 조회
  ↓
기록 없음
  ↓
이벤트 없음 또는 수량 소진으로 판단
  ↓
로그·지표에 실패 기록
  ↓
메시지 처리 완료
  ↓
컨슈머 그룹 오프셋 커밋
```

상황 B의 Redis와 DB 불일치는 별도 복구 대상으로 관리한다.

### 7. 전체 Consumer 처리 흐름 완성하기

```
메시지 수신
  ↓
DB 트랜잭션 시작
  ↓
조건부 UPDATE
  │
  ├─ 결과 = 0
  │    ↓
  │  동일한 coupon_issue 조회
  │    ├─ 기록 있음
  │    │    → 중복 메시지로 정상 처리
  │    │    → 오프셋 커밋
  │    │
  │    └─ 기록 없음
  │         → 이벤트 없음 또는 수량 소진
  │         → 실패 기록 후 처리 완료
  │         → 오프셋 커밋
  │
  └─ 결과 = 1
       ↓
     coupon_issue INSERT
       ├─ 성공
       │    → DB 커밋
       │    → 오프셋 커밋
       │
       └─ UNIQUE 위반
            → DB 롤백
            → 새 트랜잭션에서 기존 기록 조회
            ├─ 기록 있음 → 중복 처리 후 오프셋 커밋
            └─ 기록 없음 → 오류 처리, 오프셋 미커밋
```

일시적인 DB 오류도 오프셋을 커밋하지 않고 재시도한다.

## 과제 9. DB 동시성 제어 방식 비교하기

### 1. 조건부 UPDATE 방식 설명

```
수량 확인과 증가를 하나의 UPDATE로 처리한다.
영향받은 row 수로 수량 확보 성공 여부를 판단한다.
```

### 2. 비관적 락 방식 설명과 SQL 예시

```
SELECT *
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;
```

설명:

```
이벤트 행을 먼저 잠근 뒤 수량을 확인하고 증가시킨다.
다른 트랜잭션은 잠금이 해제될 때까지 대기한다.
```

### 3. 낙관적 락 방식 설명과 SQL 예시

```
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
조회 당시 버전과 현재 버전이 같은 경우에만 수정한다.
버전이 달라졌다면 충돌로 판단하고 다시 시도해야 한다.
```

### 4. 세 방식 비교표

| 구분          | 조건부 UPDATE           | 비관적 락       | 낙관적 락        |
| ----------- | -------------------- | ----------- | ------------ |
| 수량을 보호하는 방법 | 조건 확인과 증가를 한 SQL로 실행 | 행을 먼저 잠금    | 버전 일치 여부 확인  |
| 충돌 시 동작     | 잠금 대기 후 조건 재확인       | 잠금 해제까지 대기  | UPDATE 실패    |
| 재시도 필요 여부   | 일반적으로 불필요            | 일반적으로 불필요   | 필요           |
| 장점          | 단순하고 원자적임            | 흐름을 이해하기 쉬움 | 충돌이 적으면 효율적임 |
| 단점          | 특정 행에 잠금 대기 집중       | 긴 잠금 대기 발생  | 충돌 시 재시도 증가  |
| 선착순 이벤트 적합성 | 높음                   | 보통          | 낮음           |

### 5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제

```
같은 coupon_event 행에 갱신이 몰려
행 잠금 대기와 DB 병목이 발생할 수 있다.
```

### 6. 이번 구조에서 조건부 UPDATE를 선택하는 이유

```
수량 확인과 증가를 한 SQL로 처리할 수 있고,
별도의 조회나 애플리케이션 재시도 없이 수량 초과를 막을 수 있기 때문이다.
```

### 7. 세 방식과 UNIQUE 제약의 역할이 다른 이유

```
세 동시성 제어 방식은 전체 발급 수량을 보호한다.

UNIQUE 제약은 같은 사용자의 중복 발급을 막는다.
서로 보호하는 불변식이 다르다.
```

## 과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기

### 1. Redis 통과 후 Kafka 발행 실패 상황

| 시스템   | 남아 있는 상태               |
| ----- | ---------------------- |
| Redis | 사용자 통과 기록과 수량 차감 상태 존재 |
| Kafka | 발급 요청 레코드 없음           |
| DB    | 발급 기록 없음               |

### 2. Kafka 발행 후 DB 저장 실패 상황

| 시스템   | 남아 있는 상태                  |
| ----- | ------------------------- |
| Redis | 사용자 통과 기록 존재              |
| Kafka | 발급 레코드 존재, 컨슈머 그룹 오프셋 미커밋 |
| DB    | 발급 기록 없음                  |

### 3. DB 저장 후 Redis 데이터 유실 상황

| 시스템   | 남아 있는 상태              |
| ----- | --------------------- |
| Redis | 사용자 통과 기록 없음          |
| DB    | coupon_issue 발급 기록 존재 |

### 4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유

```
DB 트랜잭션이 커밋되어야 최종 발급 기록과 수량이 확정된다.
Redis와 Kafka는 판정과 전달을 담당하므로 최종 결과의 기준이 아니다.
```

### 5. Redis, Kafka, DB의 역할 비교표

| 구분         | Redis         | Kafka          | DB               |
| ---------- | ------------- | -------------- | ---------------- |
| 주 역할       | 빠른 선착순·중복 판정  | 발급 요청 전달       | 최종 발급 저장과 정합성 보장 |
| 저장하는 상태    | 통과 사용자와 임시 수량 | 발급 요청 레코드와 오프셋 | 이벤트 수량과 발급 기록    |
| 성공이 의미하는 것 | 판정 통과         | 메시지 저장         | 발급 트랜잭션 커밋       |
| 강점         | 빠른 처리         | 비동기 전달과 재처리    | 제약과 트랜잭션 제공      |
| 한계         | 유실·초기화 가능     | 중복 소비 가능       | 높은 동시 요청 시 병목 가능 |

### 6. 5주차 requestId 기반 멱등성에서 해결할 문제

```
동일한 요청을 requestId로 식별하고,
요청의 처리 상태와 결과를 중복 없이 관리한다.
```

### 7. 6주차 Outbox Pattern에서 해결할 문제

```
DB 저장과 후속 이벤트 발행을 같은 DB 트랜잭션에 기록하여
DB만 저장되고 이벤트는 발행되지 않는 문제를 줄인다.
```

### 8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유

```
아웃박스 패턴은 DB 트랜잭션과 후속 이벤트 발행을 연결하는 방식이다.

Redis 판정은 별도 저장소에서 먼저 수행되므로
Redis 변경과 최초 Kafka 발행을 같은 DB 트랜잭션으로 묶을 수 없다.
```

### 9. 8주차 Retry와 DLQ에서 해결할 문제

```
일시적 오류 메시지를 재시도하고,
계속 실패하는 메시지를 DLQ로 분리하여 분석·복구한다.

Redis와 DB의 수량 불일치도 별도 복구 절차로 처리한다.
```
