## 과제 1. DB 최종 발급 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
 Client
   |
   | ① 쿠폰 발급 요청
   v
API Server
   |
   | ② 인증 / 이벤트 상태·기간 검증
   | ③ Redis Lua Script 실행
   v
 Redis
   |
   | ④ ACCEPTED / DUPLICATE / SOLD_OUT 반환
   v
API Server
   |
   |-- DUPLICATE / SOLD_OUT → Kafka 발행 안 함 → 즉시 응답
   |
   |-- ACCEPTED → ⑤ Kafka 발행
                    v
                  Kafka
                  coupon.issue.requested
                    |
                    | ⑥ 메시지 소비
                    v
                Coupon Issue Consumer
                    |
                    | ⑦ DB Transaction 시작
                    v
       ------------------------------------------
        1. coupon_event 조건부 UPDATE
           issued_count < total_quantity 일 때만 +1
              |
              |-- 결과 0 → 기존 coupon_issue 기록 조회
              |            → 중복 메시지 / 수량 소진 구분
              |
              |-- 결과 1 → 2. coupon_issue INSERT
                              |
                              |-- 성공        → Commit (ISSUED)
                              |-- UNIQUE 위반 → Rollback
       ------------------------------------------
                    |
                    | ⑧ DB 처리 결과 확정 후
                    v
        Consumer Group Offset 커밋
```

### 2. Redis 판정 통과가 최종 발급 성공이 아닌 이유

```
Redis ACCEPTED는 Redis 기준으로 선착순 판정을 통과했다는 뜻일 뿐이다.
이후 아래 단계에서 실패할 수 있다.

- Kafka 발행이 실패할 수 있다. 이 경우 Consumer가 처리할 메시지 자체가 없다.
- Consumer가 메시지를 처리하는 도중 장애가 날 수 있다.
- DB 트랜잭션이 Rollback되어 발급 기록이 남지 않을 수 있다.

또한 Redis 데이터가 유실되거나 Replica Failover 과정에서 통과 기록이 사라지면
Redis 기준 통과 수량 자체가 실제와 달라질 수 있다.
Redis는 인메모리 임시 판정 상태이고 최종 원본이 아니다.
```

### 3. Kafka 메시지 발행 성공이 최종 발급 성공이 아닌 이유

```
Kafka PUBLISHED는 발급 요청 메시지가 Kafka에 저장되었다는 뜻이다.
메시지가 저장된 것과 그 요청이 처리된 것은 다르다.

- Consumer가 아직 메시지를 소비하지 않았을 수 있다.
- 소비했더라도 DB 조건부 UPDATE에서 수량 소진으로 실패할 수 있다.
- INSERT에서 UNIQUE 위반이 발생해 트랜잭션이 Rollback될 수 있다.

Kafka는 메시지를 전달하는 역할만 한다.
별도의 요청 상태 저장소가 없다면 Kafka가 PENDING이라는 도메인 상태를 관리하는 것은 아니다.
```

### 4. 최종 발급 성공으로 판단할 수 있는 시점

```
coupon_event.issued_count 증가와 coupon_issue INSERT를 포함한
DB 트랜잭션이 Commit된 시점이다.

이 시점 이후에만 coupon_issue에 (event_id, user_id) 기록이 존재하며
이 기록이 최종 발급 여부를 판단하는 유일한 기준 데이터다.
```

### 5. Redis, Kafka, DB 단계의 상태 차이

| 단계 | 의미 | 최종 발급 성공 여부 |
| --- | --- | --- |
| Redis ACCEPTED | Redis 기준으로 중복 사용자가 아니고 잔여 수량이 있어 선착순 판정을 통과했다 | 아니다. Kafka 발행과 DB 저장이 남아 있다 |
| Kafka PUBLISHED | 발급 요청 메시지가 Kafka에 저장되었다 | 아니다. Consumer 처리와 DB 트랜잭션 Commit이 남아 있다 |
| DB ISSUED | issued_count 증가와 coupon_issue INSERT를 묶은 트랜잭션이 Commit되었다 | 그렇다. 최종 발급 성공이다 |

## 과제 2. DB가 보장해야 하는 불변식 정의하기

### 1. 불변식이 필요한 이유

```
Redis 판정은 정상 상황에서만 정확하다.
다음 상황에서는 Redis 앞단 방어가 뚫릴 수 있다.

- Redis 데이터 유실 또는 초기화
- Redis Replica Failover 과정에서 일부 통과 기록 유실
- Kafka 메시지 재처리
- DB Commit 이후 Consumer Group Offset 커밋 전 Consumer 장애
- 애플리케이션 버그로 같은 발급 요청이 여러 번 DB에 도달

불변식은 어떤 장애나 동시 요청 상황에서도 데이터가 반드시 지켜야 하는 조건이다.
이것을 DB 제약 조건과 트랜잭션으로 강제해두면
앞단의 방어가 모두 실패하더라도 데이터 자체는 깨지지 않는다.
DB가 마지막 방어선이 되는 이유가 여기에 있다.
```

### 2. 각 불변식이 깨졌을 때 발생하는 문제

| 불변식 | 깨졌을 때 발생하는 문제 |
| --- | --- |
| 사용자별 최대 1회 발급 | 한 사용자가 같은 이벤트 쿠폰을 두 개 이상 보유한다. 사용자 1명당 1개라는 이벤트 규칙이 깨지고, 어뷰징 사용자가 여러 장을 확보해 정상 사용자가 밀려난다. 마이페이지에 같은 쿠폰이 중복 표시된다 |
| 전체 수량 이하 발급 | 준비한 1,000개보다 많은 쿠폰이 발급되어 예산 초과와 실제 금전 손실이 발생한다. 정산과 통계 수치가 어긋나고, 초과 발급분을 회수하려면 이미 발급된 사용자에게 취소를 통보해야 하는 운영 사고가 된다 |
| 수량과 발급 기록의 동시 성공·실패 | issued_count와 coupon_issue 건수가 어긋난다. 수량은 줄었는데 발급받은 사용자가 없으면 쿠폰이 아무에게도 가지 않고 사라지고, 반대면 수량 집계에 잡히지 않는 발급이 생겨 수량 초과 방어 자체가 무의미해진다 |

### 3. 각 불변식을 보호하는 DB 장치

| 불변식 | DB 방어 장치 |
| --- | --- |
| 사용자 중복 발급 방지 | UNIQUE (event_id, user_id) |
| 전체 수량 초과 방지 | issued_count 조건부 UPDATE, CHECK (issued_count <= total_quantity) |
| 두 테이블의 일관성 | DB Transaction (두 작업을 하나의 트랜잭션으로 묶어 Commit 또는 Rollback) |

### 4. 애플리케이션에서 중복 여부를 먼저 조회하는 것만으로 불변식을 보장할 수 없는 이유

```
조회와 INSERT가 별개의 명령이므로 그 사이에 다른 트랜잭션이 끼어들 수 있다.

Transaction A: SELECT → 기록 없음 확인
Transaction B: SELECT → 기록 없음 확인
Transaction A: INSERT → 성공
Transaction B: INSERT → 성공

두 트랜잭션 모두 조회 시점에는 기록이 없었으므로 각자 발급 가능으로 판단한다.
READ COMMITTED에서는 커밋되지 않은 다른 트랜잭션의 INSERT가 보이지 않고,
커밋된 뒤에도 이미 판단이 끝난 뒤이므로 소용이 없다.

3주차 Redis의 SCARD 후 SADD와 동일한 Check-Then-Act 문제다.
검사 시점과 실제 변경 시점이 어긋나기 때문에,
중복 방지는 데이터가 실제로 기록되는 지점인 DB 제약 조건이 담당해야 한다.
```

## 과제 3. coupon_event와 coupon_issue 테이블 설계하기

### 1. coupon_event 테이블의 역할

```
쿠폰 이벤트 자체의 정보와 DB 기준 발급 수량을 저장한다.

- 이벤트 이름, 기간, 상태를 관리한다.
- total_quantity로 전체 발급 가능 수량을 정의한다.
- issued_count로 DB 트랜잭션이 완료된 실제 발급 수량을 관리한다.
- 조건부 UPDATE의 대상이 되어 전체 수량 초과를 DB에서 방어한다.
```

### 2. coupon_issue 테이블의 역할

```
어떤 사용자가 어떤 이벤트의 쿠폰을 발급받았는지 최종 기록을 저장한다.

- 최종 발급에 성공한 기록만 저장하며 이번 주차에서는 status가 ISSUED만 존재한다.
- UNIQUE(event_id, user_id)로 사용자 중복 발급을 막는다.
- 이 테이블의 기록이 최종 발급 여부를 판단하는 기준 데이터다.
- 사용자는 상태 조회 API나 마이페이지에서 이 기록을 확인한다.
```

### 3. 두 테이블의 관계를 다이어그램으로 표현하기

```
 coupon_event
----------------------
 id (PK)
 name
 total_quantity
 issued_count
 start_at
 end_at
 status
 version
----------------------
        |
        | 1 : N   (coupon_issue.event_id → coupon_event.id)
        v
 coupon_issue
----------------------
 id (PK)
 event_id (FK)
 user_id
 status
 issued_at
----------------------
 UNIQUE (event_id, user_id)
```

### 4. coupon_event 테이블 DDL 작성하기

```sql
CREATE TABLE coupon_event (
    id BIGSERIAL PRIMARY KEY,

    name VARCHAR(100) NOT NULL,

    -- 전체 발급 가능 수량
    total_quantity INT NOT NULL,

    -- DB 트랜잭션이 완료된 발급 수량
    issued_count INT NOT NULL DEFAULT 0,

    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,

    -- READY, OPEN, CLOSED
    status VARCHAR(20) NOT NULL,

    -- 낙관적 락을 선택할 경우 사용한다.
    version BIGINT NOT NULL DEFAULT 0,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_coupon_event_quantity
        CHECK (
            total_quantity >= 0
            AND issued_count >= 0
            AND issued_count <= total_quantity
        ),

    CONSTRAINT chk_coupon_event_period
        CHECK (start_at < end_at),

    CONSTRAINT chk_coupon_event_status
        CHECK (status IN ('READY', 'OPEN', 'CLOSED'))
);
```

```
TIMESTAMPTZ는 시간대가 다른 서버와 DB 사이에서 동일한 시점을 안전하게 다루기 위해 사용한다.
updated_at의 DEFAULT는 INSERT 시점에만 적용되므로
값을 계속 갱신하려면 애플리케이션 코드나 DB 트리거가 별도로 필요하다.

수량 CHECK는 조건부 UPDATE가 실패하더라도
issued_count가 음수가 되거나 total_quantity를 넘는 상태 자체를 DB가 거부하게 만드는
최후의 안전장치다.
```

### 5. coupon_issue 테이블 DDL 작성하기

```sql
CREATE TABLE coupon_issue (
    id BIGSERIAL PRIMARY KEY,

    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,

    -- 이번 주차에서는 ISSUED만 저장한다.
    status VARCHAR(20) NOT NULL DEFAULT 'ISSUED',

    issued_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_event
        FOREIGN KEY (event_id)
        REFERENCES coupon_event(id),

    CONSTRAINT chk_coupon_issue_status
        CHECK (status = 'ISSUED'),

    CONSTRAINT uk_coupon_issue_event_user
        UNIQUE (event_id, user_id)
);
```

### 6. issued_count를 coupon_event에 별도로 저장하는 이유와 단점

```
이유:
1. 남은 수량을 빠르게 판단할 수 있다. coupon_issue를 매번 COUNT하지 않아도 된다.
2. DB 기준 발급 현황을 조회 한 번으로 확인할 수 있다.
3. Redis 통과 수량과 DB 발급 수량의 차이를 비교해 불일치를 감지할 수 있다.
4. 조건부 UPDATE의 대상 컬럼이 되어 DB에서 전체 수량 초과를 다시 방어할 수 있다.
   coupon_issue를 COUNT해서 비교하는 방식은 조회와 INSERT 사이에
   다른 트랜잭션이 끼어들 수 있어 수량 초과를 막지 못한다.

단점:
1. 같은 정보가 두 곳에 존재하는 비정규화이므로 두 값이 어긋날 수 있다.
   반드시 같은 트랜잭션에서 변경해야 한다.
2. 모든 발급 요청이 coupon_event의 같은 row 하나를 갱신하므로
   해당 row에 갱신이 집중되어 row lock 대기가 발생한다. 처리량의 병목 지점이 된다.
3. 발급 취소나 재발급을 지원하게 되면 issued_count 감소 정책까지 함께 설계해야 한다.
```

## 과제 4. UNIQUE 제약의 역할과 한계 분석하기

### 1. `UNIQUE(event_id, user_id)`가 의미하는 규칙

```
coupon_issue 테이블에서 (event_id, user_id) 조합은 단 하나의 행으로만 존재할 수 있다.

즉 한 사용자는 하나의 이벤트에서 쿠폰을 최대 한 번만 발급받는다는 규칙을
애플리케이션 코드가 아니라 DB가 물리적으로 강제한다.
어떤 경로로 INSERT가 들어오든 두 번째 시도는 반드시 실패한다.
```

### 2. 다음 INSERT의 성공 여부와 이유

기존 데이터: `event_id = 100, user_id = 10`

| 새로운 INSERT | 성공 또는 실패 | 이유 |
| --- | --- | --- |
| event_id=100, user_id=10 | 실패 | (100, 10) 조합이 이미 존재하므로 UNIQUE 제약 위반이 발생한다. 같은 사용자의 같은 이벤트 중복 발급이다 |
| event_id=100, user_id=11 | 성공 | user_id가 다르므로 (100, 11)은 새로운 조합이다. 같은 이벤트라도 다른 사용자이므로 허용된다 |
| event_id=101, user_id=10 | 성공 | event_id가 다르므로 (101, 10)은 새로운 조합이다. 같은 사용자라도 다른 이벤트이므로 허용된다 |

### 3. 중복 여부를 SELECT한 뒤 INSERT하는 방식의 Race Condition

```
  시간        Transaction A                    Transaction B
  ------------------------------------------------------------------
   t1    SELECT ... WHERE event_id=100
         AND user_id=10 → 기록 없음
   t2                                  SELECT ... WHERE event_id=100
                                       AND user_id=10 → 기록 없음
   t3    발급 가능으로 판단
   t4                                  발급 가능으로 판단
   t5    INSERT (100, 10)
   t6                                  INSERT (100, 10)
   t7    Commit
   t8                                  Commit
  ------------------------------------------------------------------

결과:
UNIQUE 제약이 없다면 (100, 10) 기록이 두 개 생기고 user:10이 쿠폰을 두 장 받는다.

원인:
조회와 INSERT가 별개의 명령이라 그 사이에 다른 트랜잭션이 끼어들 수 있다.
READ COMMITTED에서는 아직 커밋되지 않은 A의 INSERT가 B의 SELECT에 보이지 않으므로
B는 기록이 없다고 판단한다.

UNIQUE 제약이 있다면 t6의 INSERT는 t5의 A가 커밋될 때까지 대기하다가
A 커밋 후 제약 위반으로 실패한다. 결국 하나만 성공한다.
```

### 4. UNIQUE 제약이 전체 수량 초과를 막을 수 없는 이유

```
UNIQUE(event_id, user_id)는 조합의 유일성만 검사한다.
행이 몇 개인지는 검사하지 않는다.

전체 수량 1,000개인데 서로 다른 사용자 1,001명이 INSERT를 시도하면

  (100, 1)    → 새로운 조합 → 통과
  (100, 2)    → 새로운 조합 → 통과
  ...
  (100, 1000) → 새로운 조합 → 통과
  (100, 1001) → 새로운 조합 → 통과

모든 조합이 서로 다르므로 UNIQUE 제약은 단 한 번도 걸리지 않는다.
결과적으로 1,001개의 발급 기록이 생겨 전체 수량을 초과한다.

UNIQUE는 같은 사용자의 두 번째 발급만 막을 뿐,
서로 다른 사용자가 몰려서 발생하는 수량 초과는 막지 못한다.
```

### 5. 사용자 중복과 전체 수량 초과를 각각 어떤 장치로 막아야 하는가?

| 문제 | DB 방어 장치 |
| --- | --- |
| 같은 사용자의 중복 발급 | UNIQUE (event_id, user_id) |
| 서로 다른 사용자에 의한 전체 수량 초과 | coupon_event.issued_count 조건부 UPDATE, 보조 장치로 CHECK (issued_count <= total_quantity) |

## 과제 5. 조건부 UPDATE로 전체 수량 초과 방지하기

### 1. 조건부 UPDATE SQL 작성하기

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
```

### 2. 영향받은 row 수가 의미하는 것

```
WHERE 조건을 만족해 실제로 갱신된 행의 개수를 의미한다.

이 SQL에서는 수량 확인과 증가가 하나의 명령 안에서 이루어지므로,
영향받은 row 수가 곧 이 요청이 쿠폰 한 장의 자리를 확보했는지 여부를 나타낸다.
별도의 SELECT로 남은 수량을 조회할 필요가 없다.
```

### 3. 영향받은 row 수가 1인 경우

```
해당 eventId의 행이 존재했고, 갱신 시점에 issued_count < total_quantity가 참이었다.
issued_count가 1 증가했으며 이 요청이 쿠폰 한 장의 자리를 확보했다.

이 경우에만 coupon_issue INSERT로 진행한다.
```

### 4. 영향받은 row 수가 0인 경우 가능한 원인

```
1. 해당 id의 coupon_event 행이 존재하지 않는다.

2. issued_count가 이미 total_quantity에 도달해 수량이 모두 소진되었다.
```

```
이 SQL은 event_id와 수량 조건만 사용하므로 중복 메시지 여부는 0의 직접 원인이 아니다.
결과가 0인 뒤에 기존 coupon_issue 기록을 조회해 중복 메시지인지 구분한다.

이벤트 상태나 기간까지 WHERE 절에 추가한다면
READY, CLOSED, 기간 밖인 경우에도 0이 반환될 수 있다.
이번 구조에서는 Redis 판정 시점을 발급 자격 판단 시점으로 정하고
Consumer는 상태와 기간을 다시 판정하지 않는다.
```

### 5. 다음 상황에서 UPDATE 결과를 작성하기

| 상황 | issued_count | total_quantity | 이벤트 존재 여부 | 영향받은 row 수 | 결과 |
| --- | --- | --- | --- | --- | --- |
| A | 999 | 1,000 | 존재 | 1 | 999 < 1000이 참이므로 issued_count가 1000으로 증가한다. 수량 확보 성공, coupon_issue INSERT로 진행 |
| B | 1,000 | 1,000 | 존재 | 0 | 1000 < 1000이 거짓이므로 갱신되지 않는다. 수량 소진, INSERT까지 도달하지 않음. 기존 발급 기록을 조회해 중복 메시지인지 구분 |
| C | - | - | 존재하지 않음 | 0 | id = :eventId 조건을 만족하는 행이 없어 갱신 대상이 없다. 이벤트 없음으로 처리 |

### 6. 두 트랜잭션이 동시에 마지막 수량을 증가시키는 상황 분석

```
전체 수량 1,000개, 현재 issued_count = 999

  시간        Transaction A                       Transaction B
  --------------------------------------------------------------------
   t1    UPDATE 실행
         해당 row에 lock 획득
         999 < 1000 → 참
         issued_count = 1000
   t2                                    UPDATE 실행
                                         같은 row에 lock 요청 → 대기
   t3    Commit
         lock 해제
   t4                                    lock 획득
                                         갱신된 최신 값으로 조건 재평가
                                         1000 < 1000 → 거짓
                                         영향받은 row 수 = 0
   t5                                    수량 소진으로 처리
  --------------------------------------------------------------------

결과:
Transaction A만 수량을 확보하고 issued_count는 1000에서 멈춘다.
Transaction B는 INSERT까지 진행하지 않는다.
```

### 7. issued_count가 total_quantity를 초과하지 않는 이유

```
같은 row를 갱신하는 UPDATE는 DB가 row lock으로 직렬화한다.
따라서 두 트랜잭션이 동시에 같은 값을 읽고 각자 증가시키는 상황이 발생하지 않는다.

또한 대기하던 트랜잭션은 lock을 획득한 뒤
자신이 처음 읽었던 값이 아니라 갱신 후의 최신 값을 기준으로 WHERE 조건을 다시 평가한다.
수량이 이미 찼다면 조건이 거짓이 되어 아무 행도 갱신하지 않는다.

수량 확인과 증가가 하나의 SQL 안에서 이루어지므로
확인과 변경 사이에 다른 요청이 끼어들 틈 자체가 없다.
3주차의 Lua Script가 Redis에서 했던 역할을 여기서는 조건부 UPDATE가 수행한다.

추가로 CHECK (issued_count <= total_quantity) 제약이 있어
어떤 경로로든 초과 값이 저장되려 하면 DB가 거부한다.
```

## 과제 6. 발급 트랜잭션과 Rollback 설계하기

### 1. 두 작업을 서로 다른 트랜잭션으로 처리했을 때 발생할 수 있는 문제

| 상황 | 발생하는 데이터 불일치 |
| --- | --- |
| issued_count 증가 성공, coupon_issue INSERT 실패 | 수량은 차감되었는데 발급받은 사용자가 없다. 쿠폰 한 장이 아무에게도 가지 않고 사라져 실제 발급은 999개인데 시스템은 품절로 판단한다. 정당한 사용자가 SOLD_OUT을 받는 기회 손실이 발생한다 |
| coupon_issue INSERT 성공, issued_count 증가 실패 | 발급받은 사용자는 있는데 수량 집계에 반영되지 않는다. 이런 요청이 반복되면 issued_count가 실제보다 작게 유지되어 조건부 UPDATE가 계속 통과하고, 결국 total_quantity를 초과한 발급이 발생한다 |

### 2. 하나의 트랜잭션으로 처리하는 전체 흐름

```
Transaction 시작
   |
   v
조건부 UPDATE로 수량 확보
   |
   |-- 영향받은 row 수 = 0
   |     |
   |     v
   |   기존 coupon_issue 기록 조회
   |     |
   |     |-- 기록 존재 → 이미 처리된 중복 메시지로 정상 처리 후 종료
   |     |-- 기록 없음 → 수량 소진 또는 이벤트 없음으로 처리 후 종료
   |
   |-- 영향받은 row 수 = 1
         |
         v
       coupon_issue INSERT
         |
         |-- 성공        → Commit (최종 발급 성공, ISSUED)
         |
         |-- UNIQUE 위반 → Rollback
                            → issued_count 증가도 함께 취소
                            → 새 트랜잭션에서 기존 기록 조회
```

### 3. 다음 SQL을 하나의 트랜잭션 흐름으로 완성하기

```sql
-- Transaction 시작
BEGIN;

-- 1. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 영향받은 row 수가 0이면 INSERT를 실행하지 않고
-- 기존 발급 기록을 조회한 뒤 트랜잭션을 종료한다.
SELECT id
FROM coupon_issue
WHERE event_id = :eventId
  AND user_id = :userId;

-- 2. UPDATE 결과가 1이면 발급 기록 INSERT
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status
) VALUES (
    :eventId,
    :userId,
    'ISSUED'
);

-- 두 작업이 모두 성공하면 Commit
COMMIT;

-- INSERT에서 UNIQUE 위반이 발생하면 Rollback
-- ROLLBACK;
```

### 4. UPDATE 성공 후 INSERT에서 UNIQUE 위반이 발생한 경우

```
현재 트랜잭션은 어떻게 되는가?
PostgreSQL에서는 제약 조건 위반이 발생하면 트랜잭션이 abort 상태가 된다.
이후 어떤 명령을 보내도 오류만 반환되므로 반드시 Rollback해야 한다.
Commit을 시도해도 Rollback으로 처리된다.

앞에서 증가한 issued_count는 어떻게 되는가?
같은 트랜잭션 안에서 수행된 UPDATE이므로 Rollback과 함께 원래 값으로 되돌아간다.
쿠폰 자리가 잘못 소모되지 않는다.
이것이 두 작업을 하나의 트랜잭션으로 묶는 이유다.

기존 발급 기록은 언제 조회해야 하는가?
Rollback을 완료한 뒤 새로운 트랜잭션에서 조회해야 한다.
abort된 트랜잭션에서는 SELECT조차 실행할 수 없다.
조회 결과 (event_id, user_id) 기록이 존재하면 이미 처리된 중복 메시지로 보고
정상 처리로 간주해 Offset을 커밋한다.
```

### 5. PostgreSQL에서 제약 조건 위반 후 같은 트랜잭션을 계속 사용할 수 없는 이유

```
PostgreSQL은 트랜잭션 안에서 오류가 발생하면 해당 트랜잭션을 abort 상태로 전환한다.
이 상태에서는 이후의 모든 명령이
current transaction is aborted, commands ignored until end of transaction block
오류를 반환한다.

이는 오류 발생 시점 이후의 작업이 일관되지 않은 상태에서 수행되는 것을 막기 위한 설계다.
따라서 제약 위반을 감지했다면 먼저 Rollback으로 트랜잭션을 종료하고
새 트랜잭션을 시작해 후속 조회를 수행해야 한다.

일부만 되돌리고 싶다면 INSERT 전에 SAVEPOINT를 설정해
해당 지점까지만 롤백하는 방법도 있다.
다만 이번 구조에서는 중복이면 발급 자체가 성립하지 않으므로
트랜잭션 전체를 Rollback하는 것이 맞다.
```

### 6. 모든 발급 경로가 같은 트랜잭션을 사용해야 하는 이유

```
Kafka Consumer 외에도 운영자 수동 발급, 복구 배치, 관리자 API 등
발급 기록을 만드는 경로가 여러 개 생길 수 있다.

어느 한 경로라도 issued_count 증가 없이 coupon_issue만 INSERT하거나
두 작업을 별도 트랜잭션으로 처리하면
그 경로 하나 때문에 전체 수량 정합성이 깨진다.

issued_count는 조건부 UPDATE의 판단 근거이므로
값이 실제보다 작게 유지되면 이후의 모든 요청이 잘못 통과한다.
불변식은 모든 경로가 함께 지켜야 유지되며 하나만 예외를 두어도 무너진다.

따라서 발급 처리 로직을 하나의 서비스 메서드로 통합하고
모든 경로가 그 메서드를 통해서만 발급하도록 강제하는 것이 안전하다.
```

## 과제 7. Kafka 중복 소비와 DB 중복 발급 방지 설계하기

### 1. 중복 소비가 발생하는 전체 흐름 다이어그램

```
Consumer
   |
   | ① coupon.issue.requested에서 메시지 읽기 (offset = 50)
   v
DB Transaction
   |
   | ② 조건부 UPDATE 성공 (결과 1)
   | ③ coupon_issue INSERT 성공
   | ④ Commit  → DB에 (100, 10) 기록 저장됨
   v
Consumer
   |
   | ⑤ Consumer Group Offset 커밋 시도
   |
   ✕ 커밋 전 Consumer 장애로 종료
   |
   v
Consumer 재시작
   |
   | ⑥ 마지막 커밋된 Offset(=50) 부터 다시 읽음
   v
같은 메시지 재처리
   |
   | DB에는 이미 (100, 10) 기록이 존재하는 상태
   v
중복 발급 위험 발생
```

### 2. DB에 UNIQUE 제약이 없다면 발생하는 문제

```
재처리된 메시지가 그대로 INSERT에 성공한다.

coupon_issue
  (event_id=100, user_id=10)  ← 최초 처리
  (event_id=100, user_id=10)  ← 재처리로 추가 생성

- 같은 사용자가 같은 이벤트 쿠폰을 두 장 보유한다.
- issued_count도 두 번 증가해 실제 사용자 수보다 수량이 더 많이 소모된다.
- 결과적으로 다른 정상 사용자가 받을 쿠폰이 줄어든다.
- 마이페이지에 같은 쿠폰이 중복 표시되고 정산 수치가 어긋난다.

Kafka는 at-least-once 전달을 보장하므로 중복 소비는 예외 상황이 아니라 전제다.
애플리케이션이 중복을 완벽히 막을 수 있다는 가정 자체가 위험하다.
```

### 3. `UNIQUE(event_id, user_id)`가 중복 소비를 방어하는 과정

```
재처리 메시지 도착
   |
   v
조건부 UPDATE
   |
   |-- 수량이 남아 있으면 결과 1 → issued_count 증가
   |        |
   |        v
   |     coupon_issue INSERT (100, 10)
   |        |
   |        v
   |     이미 같은 조합이 존재 → UNIQUE 제약 위반 발생
   |        |
   |        v
   |     트랜잭션 전체 Rollback
   |     → 중복 발급 차단
   |     → 앞에서 증가한 issued_count도 원래 값으로 복구
   |
   |-- 수량이 이미 소진되었으면 결과 0
            |
            v
          INSERT까지 도달하지 않음
          → UNIQUE 위반도 발생하지 않음
          → 기존 기록 조회로 중복 메시지 판별

DB가 어떤 경로로 들어온 요청이든 (event_id, user_id) 조합을 단 하나로 유지하므로
애플리케이션 로직의 결함이나 Kafka 재전송과 무관하게 중복 발급이 차단된다.
```

### 4. UNIQUE 위반을 단순 장애가 아니라 이미 처리된 메시지로 판단하기 위한 조건

```
1. 위반한 제약이 uk_coupon_issue_event_user인지 확인해야 한다.
   다른 제약이나 다른 종류의 오류를 중복으로 오인하면 실제 장애를 놓친다.
   PostgreSQL의 SQLSTATE 23505와 제약 조건 이름을 함께 확인한다.

2. Rollback 후 새 트랜잭션에서 (event_id, user_id) 기록이 실제로 존재하는지
   조회해 확인해야 한다.

3. 조회된 기록이 지금 처리 중인 메시지와 같은 요청에서 비롯된 것이어야 한다.
   UNIQUE(event_id, user_id)는 사용자 단위 중복만 식별하므로
   같은 사용자의 다른 요청과 완전히 동일한 요청을 구분하지는 못한다.
   요청 단위 식별은 5주차 requestId 기반 멱등성에서 다룬다.

이 조건이 확인되면 최종 상태가 이미 원하는 상태이므로
오류가 아니라 정상 완료로 처리한다.
```

### 5. 제약 위반 후 Consumer가 수행해야 하는 처리 순서

```
1. 현재 트랜잭션을 Rollback한다.
   PostgreSQL에서는 abort된 트랜잭션으로 아무 작업도 할 수 없고,
   앞에서 증가시킨 issued_count도 함께 되돌려야 한다.

2. 새 트랜잭션에서 (event_id, user_id)의 기존 coupon_issue 기록을 조회한다.

3. 기록이 존재하면 이미 처리된 메시지로 판단하고 정상 처리로 간주한다.
   기록이 없으면 예상하지 못한 오류이므로 로그와 메트릭을 남기고 실패로 처리한다.

4. 정상 처리로 판단한 경우에만 Consumer Group Offset을 커밋한다.
   재시도가 필요한 일시적 실패라면 커밋하지 않는다.
```

### 6. DB 처리보다 Consumer Group Offset이 먼저 커밋되면 안 되는 이유

```
Offset이 먼저 커밋되면 Kafka는 그 메시지를 처리 완료로 간주한다.
그런데 이후 DB 트랜잭션이 실패하거나 Consumer가 종료되면
해당 요청은 다시 읽히지 않아 영원히 유실된다.

Redis는 통과 기록을 가지고 있어 사용자는 재시도해도 DUPLICATE로 차단되고,
Kafka는 처리 완료로 알고 있으며, DB에는 발급 기록이 없다.
누구도 이 요청을 복구할 수 없는 상태가 된다.

DB 처리를 먼저 확정한 뒤 Offset을 커밋하면
최악의 경우 중복 처리가 발생하지만 이것은 UNIQUE 제약이 방어해준다.
유실보다 중복이 훨씬 다루기 쉬운 실패다.
그래서 자동 커밋을 사용하지 않고 DB 결과 확정 후 수동으로 커밋한다.
```

### 7. `UNIQUE(event_id, user_id)`와 requestId 기반 멱등성의 차이

```
UNIQUE(event_id, user_id)
- 기준: 사용자 단위
- 질문: 이 사용자가 이 이벤트의 쿠폰을 이미 받았는가?
- 성격: 비즈니스 규칙 자체를 DB 제약으로 강제하는 비즈니스 멱등성
- 범위: 어떤 경로로 들어온 INSERT든 무조건 차단한다
- 한계: 요청 자체를 식별하지 못한다.
        같은 사용자의 서로 다른 요청인지, 완전히 동일한 요청의 재전송인지 구분할 수 없다.
        실패 원인을 위반 예외로만 알 수 있어 정상 재처리와 오류 구분에 추가 조회가 필요하다.

requestId 기반 멱등성
- 기준: 요청 단위
- 질문: 이 요청이 이미 처리되었는가?
- 성격: 요청 상태를 저장해 같은 요청의 결과를 한 번만 반영하는 요청 멱등성
- 범위: 처리 상태(PENDING, PROCESSING, ISSUED, FAILED)를 관리해
        재요청 시 기존 결과를 그대로 반환할 수 있다
- 이점: 발급 성공뿐 아니라 실패한 요청의 결과도 일관되게 재현할 수 있다

두 장치는 대체 관계가 아니다.
requestId는 요청 흐름의 멱등성을 만들고, UNIQUE는 최종 데이터의 불변식을 지킨다.
requestId 상태 관리가 실패하거나 우회되더라도 UNIQUE가 마지막에 데이터를 지킨다.
```

## 과제 8. 품절 후 중복 메시지 재처리 분석하기

기준 상황

```
이벤트 ID: 100
전체 수량: 1개
현재 issued_count: 1
coupon_issue에 (event_id=100, user_id=10) 기록 존재
user:10의 Kafka 메시지가 다시 전달됨
```

### 1. 조건부 UPDATE 결과와 그 이유

```
영향받은 row 수 = 0

WHERE 절의 issued_count < total_quantity 조건이 1 < 1이 되어 거짓이다.
따라서 갱신 대상 행이 없고 issued_count는 1로 유지된다.
```

### 2. coupon_issue INSERT까지 실행되는가?

```
실행되지 않는다.

조건부 UPDATE 결과가 1일 때만 INSERT로 진행하는 흐름이므로,
결과가 0인 이 상황에서는 INSERT 단계에 도달하지 않는다.
수량을 확보하지 못한 요청은 발급 기록을 만들 수 없다.
```

### 3. 이 상황에서 UNIQUE 제약 위반이 발생하는가?

```
발생하지 않는다.

INSERT 자체가 실행되지 않으므로 제약 조건을 검사할 기회도 없다.

주의할 점은 중복 메시지가 항상 UNIQUE 위반으로 걸러진다고 생각하면 안 된다는 것이다.
수량이 남아 있는 상태에서 중복 메시지가 오면 UPDATE가 성공한 뒤 INSERT에서 위반이 발생하고,
수량이 소진된 상태에서 오면 UPDATE 단계에서 0으로 끝난다.
중복 메시지는 수량 상황에 따라 서로 다른 경로로 처리되므로 두 경로를 모두 다뤄야 한다.
```

### 4. 영향받은 row 수가 0이라고 무조건 품절로 판단하면 안 되는 이유

```
결과가 0이라는 사실만으로는 다음 세 가지가 구분되지 않는다.

1. 이벤트가 존재하지 않는다.
2. 실제로 수량이 모두 소진되어 이 요청이 발급받지 못했다.
3. 이 사용자는 이미 발급을 받았고, 그 뒤 수량이 소진된 상태에서 중복 메시지가 재처리되었다.

3번을 품절로 처리하면 이미 정상 발급된 요청을 실패로 기록하게 된다.
사용자는 쿠폰을 가지고 있는데 시스템은 발급 실패로 알고 있는 상태가 되어
상태 조회 결과와 실제 보유 쿠폰이 어긋나고, 불필요한 실패 알림이나 재처리가 발생한다.
```

### 5. 기존 coupon_issue 기록을 추가로 확인해야 하는 이유

```
coupon_issue의 (event_id, user_id) 기록은 최종 발급 성공 여부를 판단하는 기준 데이터다.

조건부 UPDATE 결과 0은 이번 시도가 수량을 확보하지 못했다는 사실만 알려줄 뿐
이 사용자가 과거에 발급을 받았는지는 알려주지 않는다.

기록이 존재하면 이미 처리가 완료된 요청이므로 정상 처리로 종료해야 하고,
기록이 없어야 비로소 실제 발급 실패로 판단할 수 있다.

즉 UPDATE 결과는 이번 시도의 결과이고,
coupon_issue 조회는 최종 상태의 확인이다. 둘을 함께 봐야 올바르게 판단할 수 있다.
```

### 6. 다음 두 상황을 구분하는 처리 흐름 작성하기

```
상황 A. 조건부 UPDATE 결과 = 0, 동일한 coupon_issue 기록 존재

  판단: 이미 처리된 중복 메시지
  처리: 새로 발급하지 않고 기존 발급 결과를 그대로 유지한다.
        중복 소비 메트릭과 로그를 남긴다.
  메시지 처리 완료 여부: 완료로 처리한다.
        DB의 최종 상태가 이미 원하는 상태이므로 다시 처리할 필요가 없다.
  Offset 커밋 여부: 커밋한다.
        커밋하지 않으면 같은 메시지를 무한히 다시 읽게 된다.


상황 B. 조건부 UPDATE 결과 = 0, 동일한 coupon_issue 기록 없음

  판단: 실제 수량 소진 또는 이벤트 없음. 이 사용자는 발급받지 못했다.
  처리: 발급 실패로 확정하고 실패 로그와 메트릭을 남긴다.
        Redis에는 통과 기록이 남아 있을 수 있으므로 Redis-DB 불일치 복구 대상으로 기록한다.
  메시지 처리 완료 여부: 완료로 처리한다.
        재시도해도 수량이 늘어나지 않으므로 재시도로 해결되지 않는 비즈니스 실패다.
  Offset 커밋 여부: 커밋한다.
        커밋하지 않고 재시도하면 같은 메시지에서 무한 반복되어 Consumer Lag만 커진다.


참고: 일시적인 DB 연결 오류나 타임아웃처럼 재시도로 해결될 수 있는 실패는
      위 두 경우와 달리 Offset을 커밋하지 않고 재처리되게 둔다.
```

## 과제 9. DB 동시성 제어 방식 비교하기

### 1. 조건부 UPDATE 방식 설명

```sql
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId
  AND issued_count < total_quantity;
```

```
수량 확인과 증가를 하나의 SQL로 수행한다.

명시적인 락을 잡거나 값을 미리 읽지 않고, WHERE 절의 조건을 갱신 시점에 평가한다.
같은 row를 갱신하는 트랜잭션은 DB가 직렬화하고,
대기하던 트랜잭션은 갱신된 최신 값으로 조건을 다시 평가한다.
따라서 확인과 변경 사이에 다른 요청이 끼어들 틈이 없다.

성공 여부는 영향받은 row 수로 판단한다. 1이면 수량 확보 성공, 0이면 실패다.
```

### 2. 비관적 락 방식 설명과 SQL 예시

```sql
-- 1. 이벤트 row를 잠그고 현재 수량을 읽는다.
SELECT id, issued_count, total_quantity
FROM coupon_event
WHERE id = :eventId
FOR UPDATE;

-- 2. 애플리케이션에서 issued_count < total_quantity 를 확인한 뒤 실행한다.
UPDATE coupon_event
SET issued_count = issued_count + 1
WHERE id = :eventId;
```

설명:

```
FOR UPDATE로 이벤트 row에 배타 락을 걸어 다른 트랜잭션의 접근을 막은 뒤
수량을 확인하고 증가시킨다.

락을 획득한 트랜잭션이 커밋 또는 롤백할 때까지 다른 트랜잭션은 대기하므로
읽은 값이 판단하는 동안 변하지 않는다는 것을 보장할 수 있다.

처리 순서가 직관적이고 복잡한 검증 로직을 락 안에서 안전하게 수행할 수 있지만,
락 구간이 트랜잭션 커밋까지 유지되므로 요청이 몰리면 대기 시간이 길어진다.
```

### 3. 낙관적 락 방식 설명과 SQL 예시

```sql
-- 1. 현재 상태와 version을 읽는다.
SELECT issued_count, total_quantity, version
FROM coupon_event
WHERE id = :eventId;

-- 2. 읽었던 version이 그대로일 때만 갱신한다.
UPDATE coupon_event
SET issued_count = issued_count + 1,
    version = version + 1
WHERE id = :eventId
  AND version = :oldVersion
  AND issued_count < total_quantity;
```

설명:

```
처음부터 락을 잡지 않고, 갱신 시점에 읽었던 version과 현재 version이 같은지 확인한다.

다른 트랜잭션이 먼저 갱신해 version이 증가했다면 WHERE 조건이 거짓이 되어
영향받은 row 수가 0이 된다. 이때 충돌이 발생했다고 판단하고 애플리케이션이 재시도한다.

충돌이 드문 환경에서는 락 대기 없이 처리량을 높일 수 있지만,
선착순 이벤트처럼 하나의 row에 요청이 집중되면 대부분의 요청이 충돌해
재시도가 반복되고 오히려 비효율적이다.
```

### 4. 세 방식 비교표

| 구분 | 조건부 UPDATE | 비관적 락 | 낙관적 락 |
| --- | --- | --- | --- |
| 수량을 보호하는 방법 | WHERE 절의 수량 조건을 갱신 시점에 평가해 확인과 증가를 하나의 SQL로 수행한다 | FOR UPDATE로 row에 배타 락을 걸어 다른 트랜잭션을 대기시킨 뒤 확인하고 증가시킨다 | 읽은 version과 현재 version이 같을 때만 갱신해 그사이 다른 변경이 없었음을 확인한다 |
| 충돌 시 동작 | 대기 후 최신 값으로 조건을 재평가한다. 수량이 찼으면 영향받은 row 수가 0이 된다 | 락을 획득할 때까지 대기한다. 획득 후 갱신된 값을 읽어 판단한다 | UPDATE가 아무 행도 갱신하지 못하고 영향받은 row 수가 0이 된다 |
| 재시도 필요 여부 | 필요 없다. 0은 충돌이 아니라 수량 소진이라는 확정된 결과다 | 필요 없다. 대기 후 정상 처리된다. 단 락 타임아웃이나 데드락 시에는 필요하다 | 필요하다. 0이 충돌을 의미하므로 다시 읽고 다시 시도해야 한다 |
| 장점 | 구현이 단순하고 왕복이 한 번이다. 별도 조회와 재시도 없이 수량 초과를 막는다 | 처리 순서와 정합성을 이해하기 쉽다. 락 안에서 복잡한 검증 로직을 안전하게 수행할 수 있다 | 명시적 락을 잡지 않아 충돌이 적은 환경에서는 락 대기를 줄일 수 있다 |
| 단점 | 같은 이벤트 row에 갱신이 집중되어 row lock 대기가 발생한다. INSERT와 반드시 같은 트랜잭션으로 묶어야 한다 | 락 구간이 트랜잭션 커밋까지 유지되어 요청이 몰리면 대기가 길어지고 처리량이 크게 떨어진다 | 충돌이 잦으면 재시도가 반복되어 오히려 비효율적이다. version 컬럼과 재시도 로직이 추가로 필요하다 |
| 선착순 이벤트 적합성 | 적합하다. 단일 SQL로 짧게 끝나 락 점유 시간이 가장 짧다 | 부적합하다. 하나의 row에 요청이 집중되는 상황에서 대기 시간이 급격히 늘어난다 | 부적합하다. 충돌이 사실상 항상 발생해 재시도 폭증으로 이어진다 |

### 5. 하나의 이벤트 row에 요청이 집중될 때 발생하는 문제

```
모든 발급 요청이 coupon_event의 같은 row 하나를 갱신하므로
그 row가 전체 시스템의 직렬화 지점이 된다.

- 어떤 방식을 쓰든 해당 row의 갱신은 순차적으로만 처리되므로
  Consumer를 여러 개 띄워도 이 지점에서 처리량이 제한된다.
- 비관적 락은 락 대기 큐가 길어지고, 낙관적 락은 재시도가 폭증한다.
- 트랜잭션이 길어지면 락 점유 시간이 늘어 대기가 연쇄적으로 악화된다.
- 커넥션 풀이 대기 중인 트랜잭션으로 가득 차면 다른 API까지 영향을 받는다.

이것이 Redis를 앞단에 두는 이유다.
Redis가 10만 건 중 1,000건만 통과시키므로 이 row에 도달하는 요청 자체가 크게 줄어든다.
DB는 통과한 요청에 대해서만 최종 방어선 역할을 수행한다.
```

### 6. 이번 구조에서 조건부 UPDATE를 선택하는 이유

```
1. 락 점유 시간이 가장 짧다.
   단일 SQL로 확인과 증가가 끝나므로 row lock을 잡고 있는 시간이 최소화된다.
   요청이 하나의 row에 집중되는 선착순 구조에서 가장 중요한 요소다.

2. 재시도 로직이 필요 없다.
   영향받은 row 수 0은 충돌이 아니라 수량 소진이라는 확정된 비즈니스 결과이므로
   그대로 실패 처리하면 된다. 낙관적 락처럼 재시도를 반복하지 않는다.

3. 왕복이 한 번이다.
   비관적 락은 SELECT FOR UPDATE와 UPDATE로 두 번 왕복하지만
   조건부 UPDATE는 한 번으로 끝나 네트워크 왕복과 트랜잭션 길이를 줄인다.

4. 구현이 단순해 실수 여지가 적다.
   애플리케이션에서 수량을 비교하는 코드가 없으므로
   Check-Then-Act 실수가 원천적으로 발생하지 않는다.

5. 이번 구조에서 Consumer가 하는 일은 수량 확보와 기록 저장뿐이다.
   락 안에서 복잡한 검증을 해야 하는 상황이 아니므로
   비관적 락의 장점이 필요하지 않다.
```

### 7. 세 방식과 UNIQUE 제약의 역할이 다른 이유

```
세 방식은 모두 하나의 이벤트 row에 대한 동시 수정을 제어하는 장치다.
목적은 전체 수량 초과 방지이며 대상은 coupon_event다.

  조건부 UPDATE : 남은 수량 확인과 증가를 원자적으로 수행한다.
  비관적 락      : 같은 row를 수정하는 트랜잭션을 명시적으로 대기시킨다.
  낙관적 락      : version 변화를 확인해 동시 수정 충돌을 감지한다.

UNIQUE 제약은 동시성 제어 장치가 아니라 데이터 자체의 무결성 제약이다.
목적은 사용자 중복 발급 방지이며 대상은 coupon_issue다.
동시 요청뿐 아니라 시간 간격을 두고 들어온 중복 요청, Kafka 재처리,
Redis 유실 후 재통과, 수동 배치까지 어떤 경로든 무조건 차단한다.

두 문제는 서로 독립적이다.
동시성 제어만으로는 같은 사용자의 중복 발급을 막지 못하고,
UNIQUE만으로는 서로 다른 사용자에 의한 수량 초과를 막지 못한다.

따라서 최종 방어선은 다음 조합으로 구성한다.

  조건부 UPDATE + UNIQUE 제약 + Transaction
```

## 과제 10. Redis, Kafka, DB 불일치 상황과 이후 주차 연결하기

### 1. Redis 통과 후 Kafka 발행 실패 상황

| 시스템 | 남아 있는 상태 |
| --- | --- |
| Redis | 통과 사용자 Set에 userId가 존재한다. 선착순 자리 하나를 점유한 상태 |
| Kafka | 발행에 실패했으므로 해당 요청의 레코드가 존재하지 않는다 |
| DB | 처리할 메시지 자체가 없으므로 coupon_issue 발급 기록이 없다 |

```
사용자는 Redis 자리만 차지한 채 아무것도 받지 못한다.
재요청해도 Redis에서 DUPLICATE로 차단되며,
점유된 자리 때문에 실제 발급 수량이 total_quantity보다 적어질 수 있다.
```

### 2. Kafka 발행 후 DB 저장 실패 상황

| 시스템 | 남아 있는 상태 |
| --- | --- |
| Redis | 통과 기록 존재 |
| Kafka | 발행된 레코드가 존재하고 해당 Consumer Group의 Offset은 커밋되지 않은 상태 |
| DB | 트랜잭션이 Rollback되어 coupon_issue 발급 기록이 없다 |

```
Offset이 커밋되지 않았으므로 Consumer가 메시지를 다시 읽어 재처리할 수 있다.
일시적 DB 오류라면 재처리로 복구되지만,
수량 소진처럼 재시도로 해결되지 않는 실패라면 실패로 확정하고
Redis 통과 기록과의 불일치는 별도 복구 대상으로 남긴다.
```

### 3. DB 저장 후 Redis 데이터 유실 상황

| 시스템 | 남아 있는 상태 |
| --- | --- |
| Redis | 유실로 통과 기록이 없다. 해당 사용자가 다시 요청하면 판정을 통과할 수 있다 |
| DB | coupon_issue에 발급 기록이 존재한다. 최종 발급은 이미 성공한 상태 |

```
Kafka에는 발행된 레코드가 남아 있으며
Consumer Group Offset은 처리 시점에 따라 커밋되었을 수도, 커밋되지 않았을 수도 있다.

Redis 방어가 사라졌으므로 같은 사용자가 다시 요청하면 Redis를 통과하고
Kafka를 거쳐 DB까지 도달한다. 이때 UNIQUE(event_id, user_id)가
중복 INSERT를 차단해 최종 데이터는 지켜진다.
이 상황이 바로 Redis만 믿으면 안 되는 이유이며 DB가 마지막 방어선인 이유다.
```

### 4. 최종 발급 여부를 판단할 때 DB를 기준으로 해야 하는 이유

```
1. Redis는 인메모리 임시 판정 상태다.
   유실, 초기화, Failover로 사라질 수 있고 TTL로도 삭제된다.
   통과 기록이 있다고 발급된 것도 아니고, 없다고 발급되지 않은 것도 아니다.

2. Kafka는 메시지 전달 계층이다.
   레코드가 존재한다는 사실은 요청이 전달되었다는 뜻일 뿐 처리 결과를 의미하지 않는다.
   레코드는 소비 후에도 보존 정책에 따라 남아 있으므로
   처리 여부는 레코드 존재가 아니라 해당 Consumer Group의 Offset 커밋 여부로 봐야 한다.
   그마저도 Offset 커밋은 처리를 시도했다는 사실이지 발급 성공을 뜻하지 않는다.

3. DB는 트랜잭션과 제약 조건으로 정합성을 보장하는 영구 저장소다.
   coupon_issue의 기록은 issued_count 증가와 함께 Commit된 결과이며
   불변식이 지켜진 상태에서만 존재한다.

따라서 세 시스템의 상태가 어긋났을 때는 언제나 DB의 coupon_issue를 정답으로 삼고
나머지를 DB에 맞춰 복구한다.
```

### 5. Redis, Kafka, DB의 역할 비교표

| 구분 | Redis | Kafka | DB |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순 판정과 중복 요청 사전 차단 | 발급 요청 메시지 전달과 완충 | 최종 발급 기록 저장과 정합성 보장 |
| 저장하는 상태 | 통과 사용자 Set 등 임시 판정 상태 | 발급 요청 레코드와 Consumer Group Offset | coupon_event 수량, coupon_issue 최종 발급 기록 |
| 성공이 의미하는 것 | ACCEPTED. Redis 기준으로 판정을 통과했다 | PUBLISHED. 요청 메시지가 Kafka에 저장되었다 | ISSUED. 발급 트랜잭션이 Commit되어 최종 발급이 확정되었다 |
| 강점 | 인메모리 연산으로 매우 빠르고 Lua Script로 복합 연산을 원자적으로 처리한다 | 요청 폭주를 완충하고 Consumer 병렬 처리와 Offset 기반 재처리를 지원한다 | 트랜잭션과 제약 조건으로 불변식을 강제하고 영구 보존한다 |
| 한계 | 유실과 초기화 가능성이 있고 최종 원본 저장소로 부적합하다 | 수량 초과와 중복 발급을 막지 못하고 at-least-once라 중복 소비가 발생한다 | 하나의 이벤트 row에 갱신이 집중되어 처리량 병목이 된다 |

### 6. 5주차 requestId 기반 멱등성에서 해결할 문제

```
이번 주차의 UNIQUE(event_id, user_id)는 사용자 단위 중복만 막는다.
따라서 다음 문제가 남는다.

1. 요청 자체를 식별하지 못한다.
   같은 사용자의 서로 다른 요청인지, 동일한 요청의 재전송인지 구분할 수 없다.

2. 실패한 요청의 결과를 재현할 수 없다.
   수량 소진으로 실패한 요청이 재전송되면 다시 처음부터 처리한다.
   중복 여부와 무관하게 매번 조건부 UPDATE를 실행하게 된다.

3. 사용자에게 처리 상태를 보여줄 수단이 없다.
   PENDING인지 ISSUED인지 FAILED인지 조회할 기준 값이 필요하다.

5주차에서는 requestId와 요청 상태 테이블을 도입해
같은 요청이 여러 번 들어와도 결과가 한 번만 반영되고
기존 처리 결과를 그대로 반환할 수 있게 만든다.
UNIQUE는 그대로 유지하며 최종 데이터를 지키는 역할을 계속 담당한다.
```

### 7. 6주차 Outbox Pattern에서 해결할 문제

```
이번 주차는 발급 기록이 DB에 커밋되는 지점까지만 다룬다.
그런데 발급이 완료되면 알림, 마이페이지, 통계 서비스에 결과를 알려야 한다.

Consumer
  |
  | coupon_issue 저장 트랜잭션 Commit 성공
  v
DB (발급 기록 있음)
  |
  | CouponIssued 이벤트 발행 시도
  v
Kafka 장애 → 발행 실패

DB에는 발급 기록이 있는데 후속 서비스는 그 사실을 모르는 불일치가 발생한다.

6주차에서는 발행할 이벤트를 coupon_issue와 같은 트랜잭션에서 outbox_event에 저장하고,
별도 Publisher가 outbox_event를 읽어 Kafka에 발행한다.
두 작업이 같은 트랜잭션이므로 함께 성공하거나 함께 실패하고,
발행에 실패해도 outbox_event가 남아 있어 다시 발행할 수 있다.
```

### 8. Outbox Pattern이 Redis 판정과 최초 Kafka 발행 사이를 원자적으로 묶어주는 것은 아닌 이유

```
Outbox Pattern이 성립하는 전제는
상태 변경과 이벤트 기록이 같은 DB 트랜잭션 안에서 일어난다는 것이다.
DB 트랜잭션이라는 공통의 원자적 단위가 있어야 두 작업을 묶을 수 있다.

그런데 Redis 판정과 최초 Kafka 발행 구간에는 그 전제가 없다.

1. Redis 상태 변경은 DB 트랜잭션에 참여할 수 없다.
   Redis와 DB는 서로 다른 시스템이고 하나의 트랜잭션으로 묶을 수단이 없다.
   SADD를 롤백해주는 DB 트랜잭션은 존재하지 않는다.

2. 이 시점의 API Server에는 트랜잭션으로 묶을 DB 쓰기 작업 자체가 없다.
   Redis 판정 후 바로 Kafka에 발행하는 구조이므로
   outbox_event를 함께 저장할 트랜잭션이 애초에 없다.

Outbox가 해결하는 것은 DB 상태 변경 이후의 이벤트 발행 정합성이다.
Redis 판정과 Kafka 발행 사이의 정합성은 다른 문제다.

이 구간을 다루려면 API Server가 요청을 먼저 DB 요청 상태 테이블에 저장하고
그 트랜잭션 안에서 outbox_event까지 기록하는 구조로 바꿔야 한다.
이는 5주차 requestId 기반 상태 관리가 전제되어야 가능하며,
DB 쓰기가 추가되므로 Redis를 앞단에 둔 성능 이점과의 트레이드오프도 함께 고려해야 한다.

이번 주차 범위에서는 이 구간의 불일치를 보상 처리와 복구 배치로 다루고,
DB 도달 이후의 중복 없는 저장에 집중한다.
```

### 9. 8주차 Retry와 DLQ에서 해결할 문제

```
이번 주차에서는 실패를 두 종류로만 구분했다.

- 재처리로 해결되는 일시적 실패 → Offset 미커밋
- 재시도해도 해결되지 않는 비즈니스 실패 → 로그를 남기고 Offset 커밋

이 방식에는 한계가 있다.

1. 일시적 실패를 Offset 미커밋으로만 처리하면
   같은 메시지에서 무한 반복되어 뒤의 정상 메시지까지 막힌다. Poison Message 문제다.
2. 재시도 횟수와 간격을 제어할 수단이 없다.
3. 끝내 처리하지 못한 메시지를 보관하고 추적할 곳이 없다.
4. 실패로 확정한 요청 때문에 생긴 Redis-DB 불일치를 복구할 절차가 없다.

8주차에서는 다음을 다룬다.

- Retry Topic으로 일시적 실패를 메인 Topic과 분리해 백오프를 두고 제한된 횟수만 재시도
- DLQ로 처리 불가능한 메시지를 격리 보관하고 운영자가 분석과 수동 재처리 수행
- 실패 유형 분류에 따른 처리 정책 정립
- Redis 통과 기록은 있는데 DB 발급 기록이 없는 경우의 보상 트랜잭션과 정합성 검증 배치
```
