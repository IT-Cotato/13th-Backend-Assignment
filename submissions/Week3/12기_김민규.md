# **3주차 과제**

# **Redis 기반 선착순 쿠폰 판정 구조 설계**

## **1. 과제 목표**

이번 3주차 과제의 목표는 **Redis를 이용해 선착순 쿠폰 발급 요청을 빠르게 판정하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달하고, Consumer가 뒤에서 실제 쿠폰 발급 처리를 수행하는 구조를 설계했다.

이번 3주차에서는 Kafka 앞단에 Redis를 도입한다.

기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
SUCCESS인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Redis가 필요한 이유

Redis Key 설계

Redis 자료구조 선택

Set 기반 중복 요청 방지

SCARD / SADD를 분리했을 때 생기는 Race Condition

Lua Script를 이용한 원자적 처리

INCR 기반 방식의 장점과 한계

Redis SUCCESS / DUPLICATE / SOLD_OUT 결과에 따른 API 응답 설계

Redis SUCCESS 이후 Kafka 발행 실패 상황 분석

Redis SUCCESS가 최종 쿠폰 발급 성공을 의미하지 않는 이유

Redis, Kafka, DB의 역할 구분

앞으로 4~8주차에서 해결할 문제 연결하기
```

이번 과제의 핵심은 Redis 명령어를 외우는 것이 아니라, **Redis를 시스템 구조 안에서 어떤 역할로 사용할지 설계하는 것**이다.

특히 아래 내용을 반드시 구분해야 한다.

```
Redis SUCCESS
= 선착순 판정 통과

Kafka PENDING
= 발급 요청 메시지가 Kafka에 접수됨

DB ISSUED
= DB에 쿠폰 발급 기록이 최종 저장됨
```

즉, Redis에서 `SUCCESS`가 나왔다고 해서 쿠폰 발급이 최종 완료된 것은 아니다.

## **2. 기본 상황**

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

2주차까지의 구조에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 발급 처리를 수행했다.

하지만 이 구조에서는 모든 요청이 Kafka와 Consumer까지 도달할 수 있다.

예를 들어 쿠폰 수량은 1,000개인데 요청이 100,000건 들어온다면, 실제로는 99,000건은 실패할 가능성이 높은 요청이다.

이번 주차에서는 이 실패할 요청을 DB까지 보내지 않도록 Redis에서 먼저 판정한다.

```
요청 100,000건
  ↓
Redis 선착순 / 중복 판정
  ↓
성공 1,000건만 Kafka 발행
  ↓
실패 99,000건은 SOLD_OUT 또는 DUPLICATE 응답
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Redis에서 다음을 먼저 확인한다고 가정한다.

```
1. 이미 통과한 사용자인가?

2. 쿠폰 수량이 아직 남아 있는가?

3. 선착순 안에 들어온 요청인가?
```

Redis 판정 결과가 `SUCCESS`인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 `DUPLICATE` 또는 `SOLD_OUT`인 경우에는 Kafka에 메시지를 발행하지 않는다.

## **3. 이번 과제의 전제 조건**

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 먼저 로그인 여부와 이벤트 시간을 확인한다.

그 다음 Redis를 이용해 선착순 / 중복 여부를 판정한다.

Redis 판정 결과가 SUCCESS인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 DUPLICATE 또는 SOLD_OUT이면 Kafka에 메시지를 발행하지 않는다.

Redis SUCCESS는 최종 쿠폰 발급 성공이 아니다.

최종 쿠폰 발급 성공은 Consumer가 DB에 쿠폰 발급 기록을 저장한 뒤 결정된다.
```

이번 주차에서 사용할 Redis 결과는 아래 세 가지로 단순화한다.

```
SUCCESS:
Redis 선착순 판정 통과

DUPLICATE:
이미 Redis에서 통과한 사용자

SOLD_OUT:
쿠폰 수량 소진
```

이번 주차에서는 Redis를 사용해 선착순 판정을 수행하지만, 아래 내용은 깊게 다루지 않는다.

```
DB Unique Key 상세 설계

requestId 기반 멱등성 상세 설계

Outbox Pattern 상세 설계

Retry Topic / DLQ 상세 설계

보상 트랜잭션 상세 설계
```

다만 이 문제들이 왜 이후 주차에서 필요한지는 간단히 연결해서 설명해야 한다.

## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client

↓ 쿠폰 발급 요청

API Server

↓ 로그인 / 이벤트 시간 검증

Redis

↓ SUCCESS / DUPLICATE / SOLD_OUT 반환

API Server

↓ SUCCESS인 경우에만 Kafka 발행

Kafka Producer

↓ 메시지 발행

coupon.issue.requested Topic

↓ 발행된 메시지를 Consumer에서 소비

Coupon Issue Consumer

↓ 성공적으로 소비한 경우 DB 저장

DB
```

### **2. Redis의 역할**

```
1. 쿠폰 요청을 정해진 수량만큼만 빠르게 받는다.(정해진 수량이 넘었다면 Redis 단에서 반려)
2. 중복 요청한 사용자를 Redis Set을 이용하여 Redis 단에서 거절한다.
```

### **3. Kafka의 역할**

```
1. API서버에 몰린 요청을 Kafka를 통해 요청을 적재하고 순서대로 Consumer를 통해 소비한다.
이를 통해 API 서버의 요청을 비동기로 넘겨 부하를 줄일 수 있다.
```

### **4. DB의 역할**

```
쿠폰 요청상태를 저장한다. 이때 Unique키를 이용하여 최종적인 데이터 정합성을 보장한ㄷ.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
Redis에 통과하지 않은 요청을 Kafka에 발행하는 경우 중복된 사용자나 이미 소진된 쿠폰도 Kafka로 발행하기 때문이다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
1. 1000개만 발급 가능한 쿠폰에 대해서 1000000개의 요청을 모두 카프카로 적재하기 때문에 비효율적이다.
2. 중복된 사용자나 구현이 어려울 수 있다.
3. 카프카에서 요청을 소비할 때 DB의 발급된 쿠폰 개수를 계속해서 읽고 써야한다.
4. DB조회 시 동시성 문제가 발생할 수 있다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
1000개만 발급 가능하지만 남은 요청도 모두 카프카에 발급하고 남은 쿠폰이 있는지 계속 DB를 조회하며 처리하기 떄문에 비효율적이다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
필요없는 요청을 카프카로 발행하여 계속 처리하기 비동기 부분, DB 레벨에서 비효율적이다.
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
중복 요청이 카프카로 접수되어 처리될 수 있다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
1. 이미 소진된 쿠폰에 대해서 빠르게 소진 응답을 반환할 수 있다.
2. Redis Set을 통해 중복된 사용자를 빠르게 거절할 수 있다.
3. Redis Lua Script를 통해 원자적 연산을 하여 동시성을 보장할 수 있다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| **Redis Key** | **자료구조** | **저장하는 값**              | **필요한 이유**             |
| --- |----------|-------------------------|------------------------|
| coupon:{eventId}:issued-users | Set      | 선착순 통과한 userId          | 중복 요청 방지, 통과한 사용자 수 확인 |
| coupon:{eventId}:request-count | String   | 요청 순번                   | INCR 방식에서 몇 번째 요청인지 판단 |
| coupon:{eventId}:metadata | Hash     | limit, startAt, endAt 등 | 이벤트 메타정보 빠른 조회         |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users

coupon:100:request-count

coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
발급한 유저의 id값이 저장된다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
요청된 응답의 개수를 저장한다.
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
캐시 메모리를 효율적으로 관리하기 위해서 필요하다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
이벤트가 끝난 후 1일을 Redis Key의 TTL로 설정하여 정리할 수 있다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
중복된 사용자의 요청을 막기 위해서 사용한다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
SADD 1은 Set에 사용자를 추가한 경우(신규 사용자의 요청), 
0은 Set에 사용자를 추가하지 못한 경우(중복 사용자의 요청)이다.
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청: Redis Set에 신규 사용자 Id가 저장된다.

user:1 두 번째 요청: 아무 변화도 일어나지 않는다. SADD가 0을 반환하고 API 서버는 DUPLICATE로 처리한다.
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
coupon:{eventId}:issued-users
-----------------------------
userId: 1
userId: 2
userId: 3
.
.
.
userId: 999
userId: 1000
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
그렇지 않다. Redis Set은 중복 사용자만 막는 역할이기 때문이다.
수량 제한을 확인하려면 SCARD로 현재 set의 크기를 확인하고 제한 수량과 비교하는 로직이 별도로 필요하다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD coupon:{eventId}:issued-users
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
1. SCARD coupon:100:issued-users로 현재 통과한 사용자의 수를 확인한다.
2. 현재 수량이 limit보다 작은지 확인한다.
3. 발급 가능하다면 SADD coupon:100:issued-users userId로 사용자를 추가한다.
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
요청 A-----SCARD로 확인-----limit보다 작다면 발급(999)----SADD userA 성공----> 
요청 B-----SCARD로 확인-----limit보다 작다면 발급(999)----SADD userB 성공----> 
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
조회 명령어와 증가 명령어가 원자적으로 동작하지 않기 때문이다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
SCARD를 통해 지금까지 발급된 쿠폰 개수를 확인하고 limit보다 작다면 쿠폰을 발급(SADD)하는데
조회와 증가 명령어가 원자적으로 동작하지 않기 때문에 동시성 문제가 발생한다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
조회와 수정이 원자적으로 동작하지 않아 동시성 문제가 발생한다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
SISMEMBER(중복 사용자 확인), SCARD, limit과 비교, SADD 연산은 Lua Script로 묶어 원자적으로 처리해야 한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1.SISMEMBER

2.SCARD

3.SADD
```

### **2. Lua Script 처리 흐름 다이어그램**

```
SISMEMBER(중복 사용자 확인)----> DUPLICATE(이미 존재)
↓ 
SCARD(쿠폰 발급 요청한 사용자 수 확인)---->SOLD_OUT(모두 소진)
↓ 
SADD(요청 사용자 Id 저장)
↓ 
SUCCESS
```

### **3. Lua Script 반환값 설계**

| **반환값** | **의미**        | **API Server 처리**      |
| --- |---------------|------------------------|
| SUCCESS | 선착순 판정 통과     | 카프카 발생 시도 후 PENDING 응답 |
| DUPLICATE | 중복된 사용자의 요청   | 이미 접수된 요청입니다 반환        |
| SOLD_OUT | 쿠폰이 이미 모두 소진됨 | 쿠폰이 모두 소진되었습니다 반환      |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
3개의 연산이 원자적으로 동작하기 때문에 조회한 값이 변하지 않는다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
Redis에서 SUCCESS의 의미는 선착순 판정 통과를 의미한다.
이는 아직 카프카 발행 단계 이전이므로 최종 쿠폰 발급 완료가 아니다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
요청이 들어오면 INCR coupon:{eventId}:request-count를 실행한다.
↓
limit의 값이 1000 이하이면 SADD coupon:{eventId}:issued-uesrs {uesrId}로 중복 사용자를 관리한다.
limit의 값이 1001 이상이라면 SOLD_OUT을 반환한다.
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
원자적 증가를 보장한다.(동시성 보장)
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
중복 사용자를 막지 못한다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
user1이 중복 요청으로 쿠폰 수량의 3개를 모두 가져가서 다른 유저들은 쿠폰을 발급받지 못한다.
INCR 연산만으로는 동일한 사용자에 대해서 중복 요청을 막지 못한다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
user1 ----> INCR ----> 1 ----> 1 <= 3 -----> SUCCESS
user1 ----> INCR ----> 2 ----> 2 <= 3 -----> SUCCESS
user1 ----> INCR ----> 3 ----> 3 <= 3 -----> SUCCESS
user2 ----> INCR ----> 4 ----> 4 > 3 -----> SOLD_OUT
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
request-count는 단순히 요청이 들어온 횟수를 의미한다.
이는 최종 쿠폰 발급을 의미하는 것이 아니다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
Redis Set에 들어있는 사용자 수로 보는 것이 더 적절하다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식**                  | **Set + Lua Script 방식**                   |
| --- |---------------------------------|-------------------------------------------|
| 수량 판단 기준 | request-count의 값이 limit 이하인지 확인 | SCARD로 issued-users Set의 사용자 수 확인         |
| 중복 사용자 방지 | 불가능                             | SISMEMBER로 원자적으로 방지 가능                    |
| 장점 | 구현이 단순하고, 순서 보장이 가능하다.          | 중복 사용자에 대한 요청을 방지하고 원자적 연산을 통해 동시성을 제어한다. |
| 단점 | 중복 사용자 방지가 불가능하다.               | 구현 복잡도가 INCR 방식에 비해 증가한다.                 |
| 최종 권장 여부 | 중복 방지가 필요없는 경우에 사용한다.           | 선착순 + 중복방지인 경우 사용한다.                      |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "1"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
202 ACCEPTED
쿠폰 발급 요청이 성공(200) 처리된 것이 아니라 요청이 접수되었기 때문에 202를 반환한다.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
요청 접수 처리 응답은 단순히 요청이 선착순 인원 내에 접수되었다는 것을 의미한다.
접수된 요청이 카프카에 적재되고 컨슈머를 통해 소비되어 최종적으로 DB에 저장되어야 쿠폰 발급 요청이 성공한 것이다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
coupon.issue.requested 토픽에서 메시지를 소비한다.
그 후 DB에 쿠폰 발급 기록을 저장하고 저장 성공 시 해당 사용자의 쿠폰 상태를 ISSUED로 변경한다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 접수된 요청입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409 Conflict
Redis Set에 이미 존재하는 사용자라 DUPLICATE 응답을 받았다.
이는 중복 요청을 의미하기 때문에 409 Conflict를 반환한다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
중복 사용자가 쿠폰을 중복으로 발급 받을 가능성이 생기므로 kafka에 에초에 중복 요청을 메시지를 발행하지 않는다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
이미 발급된 요청이므로 마이페이지와 같이 쿠폰 발급 상태를 확인할 수 있는 페이지로 이동시킬 수 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
410 Gone
요청한 리소스가 더 이상 존재하지 않기 때문에 410 Gone을 반환한다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
이미 모두 소진된 쿠폰이기 때문에 더 이상 카프카에 발행해서 쿠폰 발급 절차를 진핸하면 안된다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
이미 소진된 쿠폰 발급 요청을 빠르게 SOLD_OUT 반환함으로써 서버 자원(kafka, db 조회 등 불필요한 부하)을 아낄 수 있다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client

↓ 쿠폰 발급 요청

API Server

↓ Redis Lua Script 실행

Redis

↓ SUCCESS 반환 (issued-users Set에 userId 추가됨)

API Server

↓ Kafka 발행 시도

Kafka(장애) -> 발행 실패
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
Redis Set에 사용자 Id가 남아있다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
카프카 장애로 인해 메시지가 발행되지 않았기 때문에 발급 요청이 카프카에 기록되지 않는다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
카프카에 적재된 요청이 존재하지 않기 때문에 컨슈머가 소비할 수 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
카프카에 적재되지 않아 쿠폰 발급 요청이 처리되지 않기 때문에 PENDING응답을 주면 안된다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
카프카 발행을 재시도 한다.(N회 제한)
재시도 후에도 실패 시 실패 로그를 저장한다.
Redis Set에서 userId를 제거한다.
복구 배치를 통해 실패 로그를 읽고 카프카를 재발행한다.
사용자에게 발급 실패 안내 후 재요청을 유도한다.
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
Redis도 마찬가지로 네트워크 오류로 인해 userId 제거가 실패할 가능성이 존재하기 때문이다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
6주차의 DB저장과 Kafka 발행을 원자적으로 처리하는 패턴
8주차의 Retry Topic, DLQ, 보상 트랜잭션
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis**                      | **Kafka**                 | **DB**                     |
| --- |--------------------------------|---------------------------|----------------------------|
| 주 역할 | 중복 사용자 처리, 선착순 판단              | 요청 비동기 처리 및 병렬 처리         | 쿠폰 발급 상태 저장                |
| 저장하는 데이터 | userId, 요청 카운트                 | 쿠폰 발급 요청 메시지              | 쿠폰 발급 기록                   |
| 강점 | 메모리 기반 빠른 처리, 원자적 연산           | 대용량 트래픽 비동기 처리            | 발급 상태 영구 저장                |
| 한계 | 데이터 유실 가능성이 존재                 | 발행 - 소비 간 정합성 보장이 어렵다     | 트래픽이 몰리는 상황에서 성능 한계가 존재한다. |
| 실패 시 문제 | 데이터가 유실될 수 있고, 중복 발급 처리될 수 있다. | 메시지가 유실되어 컨슈머가 처리할 수 없다.  | 최종 발급 기록 저장 실패             |
| 이번 주차에서 보는 핵심 | Lua Script로 원자적 선착순을 판정한다.     | SUCCESS요청만 발행하여 부하가 감소한다. | Redis/Kafka 이후 값을 저장한다.    |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
Redis SUCCESS: 선착순 이내 요청 접수를 의미한다.
Kafka PENDING: 발급 요청 메시지가 카프카에 정상적으로 접수된 상태를 의미한다.
DB ISSUED: 카프카에 적재된 요청이 성공적으로 처리되어 쿠폰 최종 발급 상태를 의미한다.
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Client 요청
↓
Redis Lua Script 실행
↓
[Redis SUCCESS]
↓
Kafka 발행
↓
[Kafka PENDING]
↓
Consumer 소비
↓
[DB ISSUED]
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
Redis에 장애가 발생한 경우 이미 발급된 사용자가 다시 Redis를 통과할 수 있다.
그러면 중복된 사용자가 쿠폰을 중복으로 받을 수 있기 때문에 Unique 키를 통해서 최종적으로 방어해야 한다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
카프카는 메시지를 순서대로 전달하는 역할을 하지만
남은 쿠폰 발급 개수나 중복 사용자 판단의 기능을 제공하지 않는다.
이렇게 되면 DB를 조회하며 쿠폰 개수와 중복 사용자를 판단해야 하는데 이는
여러 컨슈머로 인해 동시성 문제가 발생할 수 있고 
또한 DB를 계속 조회하므로 DB에서 병목현상이 발생할 수 있다. 
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis가 장애가 발생한 경우 DB Unique Key를 통해 중복 사용자 요청을 최종적으로 방어해야 한다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
동일한 이벤트에 대해 중복된 사용자의 쿠폰 발급을 막아준다.
```

---

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
1. 네트워크 오류로 인해 사용자가 응답을 받지 못해 재시도 하는 경우
2. 카프카 컨슈머가 요청을 소비하여 쿠폰을 발급했지만 저장하는 과정에서 실패해 재시도 하는 경우
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis의 중복 체크는 Redis Set을 통해 중복된 사용자의 요청을 막는다.
requestId는 동일한 요청 자체의 중복처리를 막는다.

=> 같은 사용자가 정상적으로 두 번 요청한 것은 Redis Set을 통해 막고
   같은 요청이 네트워크 재시도 등으로 여러 번 처리 되는 것은 requestId로 막는다.
```

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
DB저장과 카프카 발행은 하나의 트랜잭션으로 묶을 수 없기 때문이다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
DB 저장과 동시에 같은 트랜잭션 안에서 Outbox 테이블에 이벤트를 기록한다.
별도 프로세스가 Outbox 테이블을 읽어 카프카에 발행한다.
이렇게 하면 DB 저장 성공 = 이벤트 발행 보장되어 정합성이 유지된다.
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
쿠폰 발급 Consumer가 알림 서비스, 마이페이지 서비스, 통계 서비스를 직접 다 호출하면
하나의 서비스 장애가 다른 서비스 전체에 영향을 준다.
서비스 간 결합도가 높아져 확장이 어려워 진다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
쿠폰 발급 컨슈머는 DB 저장 후 이벤트만 발행하면 된다.
알림, 마이페이지, 통계 서비스는 각자 이벤트를 구독해서 독립적으로 처리한다.
서비스 간 결합도가 낮아져 장애 격리, 독립 배포, 독립 확장이 가능해진다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis에는 userId가 통과 처리된 상태로 남아 있지만
DB에는 쿠폰 발급 기록이 없는 불일치 상태가 된다.
사용자는 선착순에 통과했지만 실제 쿠폰을 받지 못하고,
재요청 시 Redis DUPLICATE로 막혀 다시 시도할 수도 없다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
Consumer 처리 실패 시 즉시 재시도하면 같은 오류가 반복될 수 있다.
Retry Topic에 실패 메시지를 보내 일정 시간 후 재처리를 시도한다.
N회 재시도 후에도 실패하면 DLQ(Dead Letter Queue)에 적재해
수동 확인 및 보정 처리를 할 수 있도록 한다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
SUCCESS → Kafka 발행 성공 → Consumer 처리 → DB 저장 실패

DB 저장이 최종 실패한 경우 이미 통과된 Redis 상태를 원복해야 한다.
1. Redis Set에서 userId 제거 (선착순 자리 반납)
2. 실패 이벤트를 발행하여 사용자에게 발급 실패 안내
3. 해당 자리를 다른 사용자에게 재발급 기회로 줄 수 있도록 처리
```
