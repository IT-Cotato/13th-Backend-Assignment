## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client 
    ↓  쿠폰 발급 요청	         
API Server
    ↓  로그인 여부/이벤트 시간 확인 -> 선착순/중복 판별
Redis
    ↓  결과가 SUCCESS인 경우 Kafka로 전달 (SOLD_OUT, DUPLICATE인 경우 Kafka로 발행 x)
Kafka Producer
    ↓  Redis를 판별 통과한 경우 메시지 발급
coupon.issue.requested Topic
    ↓  발급된 메시지 처리
Coupon Issue Consumer
    ↓  최종 unique 제약 통과하면 DB에 저장
   DB
```

### **2. Redis의 역할**

```
Redis는 서버에서 온 요청을 모두 DB로 보내지 않고, 선착순/중복을 빠르게 판별한 뒤 성공한 요청만 Kafka를 거쳐 DB로 갈 수 있도록 하여 불필요한 DB 접근을 줄여준다.
```

### **3. Kafka의 역할**

```
Redis에서 선착순/중복 판별을 통과한 요청에 대한 메시지를 Producer가 발급하고, Consumer가 소비하여 처리하도록 한다.
```

### **4. DB의 역할**

```
Redis에서 선착순/중복 판별을 통과하고 Kafka를 통해 메시지를 발행하고 Consumer에서 이 메시지에 대한 요청을 보내면 DB에서 최종적으로 Unique 제약으로 정합성을 보장하여 저장한다.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
Redis에서 선착순/중복을 빠르게 판별해줘 Kafka에서 발행되어 DB에 도달하는 요청의 수를 줄여주기 때문이다. 이는 DB 부하 증가를 방지해준다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
Redis가 없는 경우 모든 요청이 Kafka에서 발행되어 DB에 도달하게 된다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
DB에 모든 요청이 도달하면 DB 부하가 증가하고 동시 요청 시 DB LOCK 경합이 증가한다. 
Consumer가 선착순에 실패할 요청까지 처리하게되어 Consumer Lag가 증가한다. 
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
품절된 이후의 요청은 실패할 요청인데 이를 Kafka에 적재하고 Consumer에서 소비하여 DB 조회 및 저장 시도를 하게 되어 자원이 낭비되고 실패 응답까지 지연이 길어진다. 
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
같은 사용자의 중복 요청이 전부 Kafka에 적재되고 Consumer가 소비해 DB까지 도달한다.
이로 인해 불필요한 Kafka/Consumer/DB 처리가 반복되어 부하가 증가하고, DB Unique 제약 같은 방어가 없다면 1인 1매 조건이 깨져 중복 발급이 발생할 수 있다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
Redis 도입을 통해 선착순을 통과하지 못한 요청과 중복 요청을 빠르게 판별하여 이러한 요청이 DB에 도달하는 차단 할 수 있다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| **Redis Key** | **자료구조** | **저장하는 값** | **필요한 이유** |
| --- | --- | --- | --- |
| coupon:{eventId}:issued-users | Set | 선착순 판정에 성공한 사용자 ID | 같은 사용자의 중복된 요청을 막기 위해 |
| coupon:{eventId}:metadata | Hash | 이벤트 메타 정보 | 정보를 활용한 요청 유효성 검증을 위해 |


### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
해당 이벤트의 선착순 판정에 성공한 사용자들의 ID가 저장된다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
해당 이벤트에 대한 몇번째 쿠폰 발급 요청인지 알려주는 역할
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
선착순 쿠폰 발급 과정에서 사용되고 일정 시간이 지나면 필요가 없어지는데, 이를 자동으로 폐기하기 위해 필요하다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
TTL을 지정해 두고, 이 기간이 지나면 Redis에서 자동으로 삭제되도록 한다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
Set에 선착순/중복 판별을 통과한 userId를 저장하여, Set에 있는 userId로 요청이 들어오는 경우 이를 막기 위해 사용한다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
SADD는 userId를 Set에 넣는 명렁어로, Set에 userId가 이미 존재하는 경우 결과는 0이 되고, userId가 존재하지 않는 경우 Set에 userId를 넣고 결과는 1이 된다.
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청: Set에 1을 넣고 1을 반환한다.

user:1 두 번째 요청: Set에 1이 존재하므로 0을 반환한다.
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
coupon:100:issued-users (Set)
+------------------+
| user:1           |
| user:5           |
| user:20          |
| ...              |
+------------------+

SADD coupon:100:issued-users user:99  → 1 (새로 추가, 통과)
SADD coupon:100:issued-users user:1   → 0 (이미 존재, 중복 차단)
SCARD coupon:100:issued-users         → 현재 통과 사용자 수
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
Redis Set을 사용하더라도 SCARD와 SADD는 개별적으로 실행되므로 제한된 수량을 넘는 경우가 발생한다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD 명령어를 통해 Set에 저장된 사용자 수를 확인할 수 있다.
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
SCARD로 현재 통과 사용자 수를 확인하고, 쿠폰 제한 수량보다 작은 경우 SADD로 사용자를 추가한다.
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
			[현재 상태]
	   coupon:100:issued-users size = 999
	   
             요청 A                         요청 B
               |                              |
               | SCARD = 999                  |
               |                              | SCARD = 999
               |                              |
               | 발급 가능 판단                | 발급 가능 판단
               |                              |
               | SADD user:A                  |
               |                              | SADD user:B
               v                              v
														
			  [결과]
		coupon:100:issued-users size = 1001
			   문제
	       쿠폰은 1000개인데 1001명이 통과했다.
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
SCARD와 SADD가 원자적으로 실행되지 않아 요청이 동시에 들어온 경우 재고가 1개 남은 상황에서 두 요청 모두 SCARD 결과가 999가 되어 통과되기 때문이다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
두 요청이 모두 SCARD를 통과하여 SADD를 하게 되어 최종적으로 1001개가 통과하게 된다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
작업이 원자적으로 이루어지지 않아 작업 사이에 다른 요청이 들어오게 되면 수량을 넘는 경우가 발생한다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
SCARD와 SADD를 하나로 묶어 작업 중에 다른 요청이 들어오지 못하도록 해야한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER

2. SCARD

3. SADD
```

### **2. Lua Script 처리 흐름 다이어그램**

```
SISMEMBER -> 같은 사용자의 중복 요청인지 확인
	↓ 중복 요청이 아닌 경우
SCARD -> 남아 있는 수량 확인
	↓ 수량이 남은 경우
SADD -> 사용자 추가
```

### **3. Lua Script 반환값 설계**

| **반환값** | **의미** | **API Server 처리** |
| --- | --- | --- |
| SUCCESS | Redis 판정 통과 | Kafka 메시지 발행 시도 |
| DUPLICATE | 이미 통과한 사용자 | 중복 요청 응답 |
| SOLD_OUT | 재고 소진 | 품절 응답 |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
중복 확인, 수량 확인, 사용자 추가를 원자적으로 처리하여 요청이 동시에 들어오더라도, 하나의 작업이 끝나기 전에는 다른 작업을 처리하지 못한다. 이에 따라 Race Condition을 줄일 수 있게 된다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
여기서의 성공은 Redis 선착순 판정을 통과하여 Kafka 메시지 발행을 시도하는 것이므로 최종 쿠폰 발급이 완료된 것이 아니다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
요청이 들어올 때마다 Redis Counter를 증가시키고, 그 결과가 쿠폰 수량 안에 들어온 요청만 다음 단계로 통과시킨다.
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
INCR은 원자적으로 동작하기 때문에, 동시에 많은 요청이 들어와도
각 요청이 중복 없이 서로 다른 고유한 순번을 부여받는 것을 보장한다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
같은 사용자가 여러번 요청을 보내는 중복 방지를 보장하지 못한다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
같은 사용자의 중복 요청에 대해 request-count를 증가시켜 실제 쿠폰 발급 수량과 달라지게 된다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
request-count 기준 선착순 자리

+---------+---------+---------+---------+
| 순번 1  | 순번 2   | 순번 3  | 순번 4  | 
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
   통과      중복      중복      품절
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
같은 사용자의 중복 요청에 대해서 request-count가 증가하여 실제 발급 수량과 차이가 발생하기 때문이다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
같은 사용자의 중복 요청을 걸러야 하기 때문에 Set에 userId를 저장하고 Set에 있는 userId 개수를 실제 통과 사용자 수로 사용하는 것이 적절하다. 
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식** | **Set + Lua Script 방식**               |
| --- | --- |---------------------------------------|
| 수량 판단 기준 | Redis Counter | SCARD                                 |
| 중복 사용자 방지 | 불가능 | 가능                                    |
| 장점 | 단순하고 빠름 | 중복 방지 가능, Race Condition 문제 해결        |
| 단점 | 중복 요청 문제  발생 | 최종 DB 저장 실패나 Kafka 발행 실패에 대한 별도 처리 필요 |
| 최종 권장 여부 | 한계가 있음 | 권장                                    |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
	  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
202
요청은 성공적으로 수신했지만, 처리가 아직 끝나지 않았고 이후에 다른 작업이 이어질 것이라는 의미로 쿠폰 발급 요청은 접수 되었지만, 이후에 실제 발급 과정이 남아있음을 나타내기 때문에.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
Redis에서 선착순/중복 판별을 통과해 Kafka 메시지 발급 준비가 되었다는 의미이므로, 최종 쿠폰 발급 성공을 의미하지 않는다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
Producer에서 발급한 메시지를 처리하여 성공한 경우 DB에서 한번 더 검증을 거친 후 저장한다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409
현재 리소스 상태와 요청이 충돌한다는 의미로 이미 처리된 요청과 충돌한다는 것을 나타내기 때문에.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
DUPLICATE는 해당 사용자가 이미 Redis 판정을 통과한 상태라는 의미다. 여기서 다시 Kafka에 메시지를 발행하면 같은 사용자의 발급 요청 메시지가 두 번 이상 Kafka로 흘러가고, Consumer가 이를 중복 처리하게 된다. 
DB Unique 제약 같은 방어가 없다면 1인 1매 조건이 깨져 중복 발급으로 이어질 수 있고, 방어가 있더라도 결국 실패할 요청 때문에
Kafka/Consumer/DB 자원이 불필요하게 낭비된다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
"이미 쿠폰 발급 요청이 접수되었습니다"라는 안내 메시지를 보여주고, 현재 발급 진행 상태를 확인할 수 있도록 발급 상태 조회 API 결과나 마이페이지(쿠폰함)로 이동할 수 있는 경로를 함께 제공한다.
추가로 클라이언트에서 발급 버튼을 비활성화하거나 요청 중 상태로 바꿔 반복 클릭 자체를 줄일 수도 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409
요청이 리소스의 현재 상태(수량 소진)와 충돌함을 나타내기 때문에 409를 선택했다.
다만 품절은 클라이언트의 잘못이 아닌 정상적인 비즈니스 결과이므로,
200 OK를 반환하고 body의 status 필드(SOLD_OUT)로 구분하는 설계도 가능하다.
이 경우 HTTP 계층은 "요청 정상 처리", 비즈니스 계층은 "품절"로 관심사를 분리할 수 있다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
쿠폰이 모두 소진되어 선착순 판별에 실패한 경우이다.
이때 Kafka에 메시지를 발행하면 남은 재고가 없는 상황에서 불필요한 DB 부하가 발생한다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
Redis에서 빠르게 차단하지 않으면 모든 요청이 DB로 전달되어 DB 부하가 발생하기 때문에 이를 방지하기 위해서 빠르게 차단하는 것이 중요하다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client
  |
  v
API Server
  |
  | Redis SUCCESS
  v
Redis
  |
  v
API Server
  |
  | Kafka 발행 시도
  v
Kafka 장애
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
Redis의 issued-users Set에는 해당 userId가 선착순 판정을 통과한 것으로 남아 있다.
하지만 Kafka에는 메시지가 없으므로 실제 발급 처리는 진행되지 않고, 이 상태에서 사용자가 재시도하면 Redis가 DUPLICATE로 차단하기 때문에 보상 처리가 없다면 사용자는 쿠폰을 발급받지 못하는 상태가 된다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
Kafka 장애로 인해 발급되었어야 할 메시지가 발급되지 않는 문제가 발생한다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
Producer에서 메시지가 발급되지 않아 Consumer가 이 요청을 처리할 수 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
PENDING을 주면 안된다.
Kafka 메시지 발행이 실패한 경우 Consumer로 요청이 전달되지 않아 처리될 수 없게 된다.
이때 PENDING을 주게 되면, 사용자는 완료되지 못하는 요청을 기다리게 된다.
따라서 사용자에게 FAILED 응답을 주어 요청이 실패했음을 알려야한다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
1. Redis issued-users Set에서 해당 userId 제거 시도 (SREM) → 사용자가 다시 요청할 수 있도록 자리 반환
2. Kafka 발행 재시도 (일시적 장애일 수 있으므로 제한된 횟수 내 재시도)
3. 실패 로그 저장 → 어떤 요청이 어느 단계에서 실패했는지 추적 가능하게 함
4. 복구 배치에서 실패 건 재처리
5. 사용자에게는 PENDING이 아닌 "요청 접수 실패, 다시 시도해주세요" 응답 반환
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
보상 처리(SREM) 자체도 Redis에 대한 네트워크 요청이기 때문에, Redis 네트워크 오류나 장애로 실패할 수 있다. 이 경우 Redis에는 여전히 사용자가 통과한 것으로 남아 있지만 Kafka에는 메시지가 없어, Redis와 Kafka 상태가 다시 불일치하게 된다. 따라서 보상 처리에만 의존할 수 없고 실패 로그 저장, 복구 배치, 상태 테이블, 운영자 재처리 도구 같은 추가 장치가 필요하다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
5주차 requestId 기반 멱등성
접수 실패 후 사용자가 재시도할 때 같은 requestId로 들어오면 중복 처리 없이 기존 상태를 조회해 응답할 수 있다.

8주차 Retry / DLQ / 보상 트랜잭션
Kafka 발행 실패의 재시도 구조, 보상 처리 실패로 생긴 Redis-DB(Kafka) 불일치 복구, 운영자 재처리 도구와 연결된다.
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 판정 | 비동기 메시지 전달 | 최종 발급 기록 저장 |
| 저장하는 데이터 | 임시 상태, 통과 사용자 목록, 카운터 | 쿠폰 발급 요청 메시지 | 최종 발급 기록 |
| 강점 | 빠른 조회, 원자 연산, Set/Lua/INCR | 요청 완충, Consumer 병렬 처리 | 트랜잭션, unique key로 정합성 최종 보장 |
| 한계 | 최종 발급 기록 저장소로 쓰기에는 부적합 | 수량 초과와 중복 발급을 자동을 막지 못함 | 모든 요청을 직접 판정하면 Lock 경합과 병목이 발생 |
| 실패 시 문제 | 판정 데이터 유실 → 중복/초과 통과 위험 | 메시지 발행/전달 실패 → Redis와 상태 불일치 | 저장 실패 → Redis와 상태 불일치, 보상 필요 |
| 이번 주차에서 보는 핵심 | Lua Script 기반 원자적 선착순/중복 판정 | Redis SUCCESS인 요청만 발행 | 최종 방어선 (UNIQUE(event_id, user_id)) |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
Redis SUCCESS
= 선착순 판정 통과
Kafka PENDING
= 발급 요청 메시지가 Kafka에 접수됨
DB ISSUED
= DB에 쿠폰 발급 기록이 최종 저장됨
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Client
  |
  v
Redis 판정 통과 ──────────── Redis SUCCESS  (선착순 통과, 발급 아님)
  |
  | Kafka 발행 성공
  v
Kafka 메시지 접수 ─────────── PENDING       (요청 접수 완료, 발급 아님)
  |
  | Consumer 소비 → DB 저장 성공
  v
DB 발급 기록 저장 ─────────── ISSUED        (최종 발급 성공)
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
Redis에 장애가 발생하여 데이터가 유실되거나 버그로 Redis를 우회하는 경우, Kakfa에서 메시지가 중복 소비되는 경우에 1인 1매 발급이 위반될 수 있다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
Kafka는 메시지를 전달하고 저장하는 역할을 하는데 이는 수량 초과와 중복 발급을 막아주지 않는다.
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis 오류가 발생하거나 Redis를 우회하여 요청이 들어올 수 있기 때문에 필요하다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
같은 유저에 대한 중복 요청을 막아준다.
```

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
네트워크 문제나 브라우저 재시도로 인해 같은 요청이 반복되어 들어올 수 있다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis 중복 체크는 사용자가 쿠폰을 1개 이상 발급 받지 못하게 하는 것이고,
requestId 멱등성은 네트워크 문제나 재시도 시 동일한 응답을 보내는 것이다.
```

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
coupon_issue 테이블 저장 성공한 후 CouponIssued 이벤트 발행을 시도할 때 Kafka 장애로 이벤트 발행이 실패할 수 있다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
쿠폰 발급 기록을 DB에 저장할 때, 발행해야 할 이벤트도 Outbox Table에 함께 저장한다.
이를 통해 DB 저장은 성공했지만 Kafka 이벤트 발행이 실패하는 경우를 방지한다. ****
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
쿠폰 발급 서비스가 이 서비스들을 직접 호출하면 서비스 간 결합도가 높아진다.
또한 알림 서비스에 장애가 생겼을 때 쿠폰 발급 처리까지 영향을 받을 수 있다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
쿠폰 발급 서비스는 “쿠폰이 발급되었다”는 이벤트만 발행하고, 이후 작업은 각 서비스가 독립적으로 처리하여 서비스 간 결합도를 낮출 수 있다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis와 DB의 상태가 불일치하는 정합성 실패 문제다. Redis에는 해당 사용자가 선착순을 통과한 것으로 남아 있지만 DB에는 발급 기록이 저장되지 않아, 사용자는 선착순 자리를 차지하고도 실제 쿠폰은 받지 못한 상태가 된다. 이때 재시도를 해도 Redis가 DUPLICATE로 차단하여 스스로 복구되지 않으므로, Redis 상태를 되돌리거나 실패를 기록해 재처리하는 보상 트랜잭션 검토가 필요하다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
예외가 발생했을 때 메시지를 안전하게 처리하기 위해서 필요하다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
1. Redis SUCCESS 이후 Kafka 발행 실패
Redis Set에서 userId를 제거해 선착순 자리를 되돌려야 한다.

2. Redis 통과 후 Consumer의 DB 저장이 재시도까지 모두 최종 실패한 경우
Redis에는 통과로 남아 있지만 실제 발급은 안 된 상태이므로, Redis 상태를 되돌리거나 실패 상태를 기록하고 운영자가 재처리해야 한다.

```

### 보너스 과제. 나쁜 Redis 설계의 문제점 찾기

이번 과제를 진행하며 여러 Redis 설계 방식을 검토했다. 그중 나쁜 설계들을 세 가지 관점으로 묶어 정리하고, 최종적으로 왜 Set + Lua Script 방식을 선택했는지 설명한다.

---

#### 1. 원자성 관점의 나쁜 설계

#### 1-1. SCARD 후 SADD 분리 실행 (과제 5)

```
current = SCARD coupon:100:issued-users
if current < limit:
    SADD coupon:100:issued-users userId
```

**문제점**

```
수량 확인과 사용자 추가가 원자적으로 묶여 있지 않다.남은 수량이 1개일 때 두 요청이 동시에 SCARD로 999를 확인하면둘 다 발급 가능으로 판단해 SADD까지 성공하고,제한 수량 1,000개를 초과한 1,001명이 통과하는 Race Condition이 발생한다.
```

#### 1-2. INCR + Set 명령을 애플리케이션에서 분리 실행 (과제 7)

```
1. INCR request-count
2. requestOrder <= limit 확인
3. SISMEMBER로 중복 확인
4. SADD로 사용자 추가
```

**문제점**

```
INCR과 SADD 각각은 원자적이지만, 네 단계가 하나의 흐름으로묶여 있지 않아 단계 사이에 다른 요청이 끼어들 수 있다.
```

**공통 원인과 개선 방향**

```
공통 원인은 "확인"과 "추가"가 분리되어 있다는 것이다.중복 확인(SISMEMBER), 수량 확인(SCARD), 사용자 추가(SADD)를Lua Script 하나로 묶어 원자적으로 처리해야 한다.
```

---

#### 2. 판정 기준 관점의 나쁜 설계

#### 2-1. INCR 단독 사용 (과제 7)

```
current = INCR coupon:100:request-count
if current <= limit:
    SUCCESS
```

**문제점**

```
INCR은 고유 순번 부여만 보장할 뿐 사용자 중복을 알지 못한다.쿠폰 수량이 3개일 때 user:1이 버튼을 세 번 누르면순번 1, 2, 3을 모두 user:1이 차지하고,user:2의 첫 요청이 순번 4를 받아 부당하게 SOLD_OUT 처리된다.
```

#### 2-2. request-count를 최종 발급 수량으로 해석

**문제점**

```
request-count는 같은 사용자의 중복 요청과 품절 이후 요청도 카운터를 증가시키므로 실제 발급 수량과 차이가 발생한다.최종 발급 수량은 DB의 coupon_issue 저장 건수로 판단해야 한다.
```

**공통 원인과 개선 방향**

```
공통 원인은 중복 제거가 안 된 요청 순번을 판정 기준으로 삼았다는 것이다.중복 제거된 실제 통과 사용자 수, 즉 issued-users Set의 크기(SCARD)를기준으로 판단해야 한다.
```

---

#### 3. 역할 오해 관점의 나쁜 설계

#### 3-1. Redis SUCCESS를 최종 발급 성공으로 응답 (과제 8, 9)

```
if (result == RedisResult.SUCCESS) {
    return IssueResponse.success("쿠폰이 발급되었습니다!");
}
```

**문제점**

```
Redis SUCCESS는 선착순 판정 통과이다.
이후 Kafka 발행이나 DB 저장이 실패하면 사용자는 성공 응답을 받았지만실제 쿠폰은 없는 상태가 되어 시스템 상태와 사용자 인식이 불일치한다.
Kafka 발행 성공까지 확인한 뒤 PENDING 응답을 줘야 하고,발행 실패 시에는 Redis 보상 처리 후 접수 실패 응답을 줘야 한다.
```

#### 3-2. Redis만 믿고 DB Unique Key 생략 (과제 10)

**문제점**

```
Redis는 장애나 데이터 유실이 가능한 임시 판정 계층이다.
Redis 데이터 유실, Kafka 메시지 중복 소비, 애플리케이션 버그나 배치 작업으로 Redis를 우회하는 요청이 발생하면1인 1매 조건이 깨질 수 있다.
따라서 DB에 UNIQUE(event_id, user_id) 제약을 두어마지막 방어선을 반드시 유지해야 한다.
```

#### 3-3. TTL 없는 Key 설계 (과제 3)

**문제점**

```
이벤트가 끝나도 issued-users Set 등이 삭제되지 않아 이벤트가 반복될수록 Redis 메모리 사용량이 계속 증가한다.
이벤트 종료 후 일정 시간이 지나면 자동 삭제되도록 TTL과 Key 정리 전략을 함께 설계해야 한다.
```

**공통 원인과 개선 방향**

```
공통 원인은 임시 판정 계층인 Redis를 최종 저장소나 최종 결과처럼 취급했다는 것이다.
Redis는 빠른 판정, Kafka는 비동기 전달, DB는 최종 정합성 보장으로역할을 명확히 분리해야 한다.
```

```
위 나쁜 설계들을 검토한 결과, 3주차의 최종 선택은 다음과 같다.

1. 중복 확인 / 수량 확인 / 사용자 추가를 Lua Script로 원자적으로 처리한다.

2. 판정 기준은 중복 제거된 Set의 크기(SCARD)로 삼는다.

3. Redis SUCCESS는 선착순 통과일 뿐이므로 사용자에게는 PENDING을 응답하고, 최종 발급은 DB 저장(ISSUED)으로 확정하며, DB Unique Key와 TTL 정리 전략으로 Redis의 한계를 보완한다.
```
