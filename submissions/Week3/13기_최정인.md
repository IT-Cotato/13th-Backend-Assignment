## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  │  POST /coupons/{eventId}/issue
  ▼
API Server
  │  1) 로그인 여부 / 이벤트 시간 검증
  │  2) Redis Lua Script 실행 (SISMEMBER + SCARD + SADD)
  ▼
Redis (issued-users Set, metadata)
  │
  ├─ SUCCESS ───────────────┐
  ├─ DUPLICATE → 즉시 응답    │  (Kafka 발행 없이 바로 API Server가 응답)
  └─ SOLD_OUT  → 즉시 응답    │
                             ▼
                     API Server가 Kafka Producer 호출
                             ▼
                  coupon.issue.requested Topic
                             ▼
                   Coupon Issue Consumer
                             ▼
                             DB (쿠폰 발급 기록 INSERT)
```

### **2. Redis의 역할**

```
요청 폭주 상황에서 1차 필터 역할을 한다. 실제로 발급 가능한 요청인지(중복 여부, 남은 수량)를 인메모리에서 빠르게 판정해서, 실패할 요청이 Kafka·Consumer·DB까지 내려가지 않도록 앞단에서 걸러낸다.
```

### **3. Kafka의 역할**

```
Redis에서 통과한 요청만 비동기로 전달하는 버퍼 역할을 한다. API Server가 DB 저장까지 동기로 기다리지 않고 즉시 응답할 수 있게 해주고, Consumer가 처리 속도에 맞춰 순차적으로 소비할 수 있게 트래픽을 완충한다.
```

### **4. DB의 역할**

```
최종 정합성을 보장한다. Redis와 Kafka는 판정/전달 단계일 뿐이고, 실제로 이 사용자에게 쿠폰이 발급되었다는 사실은 DB에 기록이 저장된 순간 확정된다. 
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
쿠폰 수량은 1,000개인데 요청이 100,000건이라면, 그 중 99,000건은 처리해봤자 실패할 요청이다. 이걸 그대로 Kafka에 발행하면 Consumer와 DB까지 불필요한 트래픽이 전파되어 시스템 전체 부하가 커진다. Redis에서 미리 걸러내면 Kafka 이후 구간은 실제로 성공 가능성이 있는 요청만 처리하면 된다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
Redis 없이 Kafka와 DB만 사용하는 구조에서는, 실패할 수밖에 없는 요청까지 전부 Kafka와 Consumer, DB까지 도달하게 된다. 예를 들어 100,000건의 요청이 들어오면 그중 성공 가능한 건 1,000건뿐인데도, 실패할 99,000건이 DB 커넥션·Consumer 처리량 같은 자원을 성공할 1,000건과 함께 놓고 경쟁하게 된다. 그 결과 정작 성공해야 할 요청들의 처리 속도까지 함께 느려지는 문제가 발생한다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
Kafka 단계에서는 Redis가 없다면 성공/실패 요청 구분이 없이 전부 Topic에 쌓인다. 

Consumer에서 이 메시지들을 온 순서대로 하나씩 처리해야 하는데, 실패할 99,000건도 일단 DB에 저장을 시도해봐야 실패 여부를 알 수 있다. 그래서 실제로 성공할 1,000건도 이 99,000건과 섞여서 처리되느라 전체 처리 시간이 늘어난다.

마지막으로 DB에서는 DB커넥션 풀이 실패할 요청들의 INSERT 시도에도 계속 점유되면서, 성공할 요청의 처리속도까지 함께 느려진다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
품절 이후에도 계속 요청이 DB까지 도달하면, 이미 결론이 난 요청 때문에 DB와 Consumer 자원이 계속 소모된다.
사용자 입장에서도 즉시 품절임을 알 수 없어, DB까지 다 거친 뒤에야 결과를 받게 되므로 그동안 로딩 화면을 계속 보게 되는 문제도 생긴다.
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
Redis가 없다면 응답 속도가 느려지고, 사용자는 성공/실패 여부과 상관없이 답답함에 버튼을 여러 번 누르게 된다. 이렇게 발생한 중복 요청이 전부 Kafka로 발행되면, 결국 처리 속도 저하를 야기하게 된다. 
이는 앞서 살펴본 문제와 마찬가지로 불필요한 자원소모이다. 
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
Redis를 도입하면 크게 두 가지 유형의 요청을 Kafka 이전 단계에서 차단 가능하다.
- 이미 발급에 성공한 사용자가 다시 보내는 중복 요청
- 쿠폰 수량이 이미 소진된 뒤에 들어오는 품절 이후 요청

이 두 경우 모두 Redis 단계에서 처리할 수 있어서, 빠르게 응답을 줄 수 있다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| **Redis Key** | **자료구조** | **저장하는 값** | **필요한 이유** |
| --- | --- | --- | --- |
| coupon:{eventId}:issued-users | Set | 통과 처리된 유저 목록 | 중복 체크 + 수량 체크 |
| coupon:{eventId}:metadata | Hash | 쿠폰 총 수량, 이벤트 시작/종료 시각 | 판정 기준값 제공 |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
Redis 판정을 통과한(SUCCESS로 처리된) 유저의 userId가 중복 없이 저장된다. 
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
중복 요청까지 포함하여 이벤트에 대한 총 요청 건수를 세는 용도로 쓸 수 있다. 다만 이 값은 중복이 섞여있기 때문에 발급 가능 여부를 판단하는 기준으로 쓰기엔 부적절하다. 전체 트래픽 규모를 파악하는 모니터링용 지표로 활용될 수 있다.
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
Redis는 인메모리 저장소이기 때문에, 이벤트가 끝난 뒤에도 Key가 계속 남아있으면 불필요하게 메모리를 차지해 다른 데이터가 저장될 공간이 줄어든다.
또한, 나중에 같은 eventId가 재사용될 경우, 예전 이벤트의 issued-users 기록이 그대로 남아있으면, 새 이벤트에는 처음으로 요청한 사용자임에도 예전 기록 때문에 DUPLICATE로 잘못 판정되어 쿠폰을 받지 못하는 문제가 생길 수 있다.

```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
기본적으로는 이벤트 종료 시점에 맞춰 설정해둔 TTL이 만료되면서 자동으로 삭제되도록 한다. 다만 정상적인 흐름이라면 Redis Success이후 Kafka 발행 실패 등으로 Redis와 DB의 상태가 어긋나는 경우가 생길 수 있다. 이런 불일치를 나중에 장애 원인 분석에 활용하려면, TTL로 삭제되기 전에 issued-users를 DB나 별도 로그로 백업해두는 게 안전하다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
Redis Set은 같은 값을 자동으로 중복 저장하지 않는 자료구조다. 그래서 이미 통과한 유저가 다시 요청해도 Set에 새로 추가되지 않기 때문에, 중복 요청을 걸러낼 수 있다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
- 반환값 1: 값이 Set에 없어서 새로 추가됨
- 반환값 0: 이미 Set에 존재해서 추가되지 않았음
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청: SADD coupon:100:issued-users "1" → 1

user:1 두 번째 요청: SADD coupon:100:issued-users "1" → 0  
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
그림 추가
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
아니다. Set 자체는 "중복인가 아닌가"만 판단해준다. 예를 들어 쿠폰이 한 자리 남은 시점에서 두 유저가 동시에 SCARD를 호출하면, 둘 다 "1자리 남았다"는 동일한 결과를 받게 된다.
SCARD와 SADD는 독립된 별개의 명령어라서 정원이 찼는지 스스로 판단하지 않기 때문에, 두 유저가 각자 받은 정원 정보를 믿고 SADD를 실행하면 둘 다 성공해버리기 때문에 정원을 초과하게 된다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD coupon:{eventId}:issued-users
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
1. SCARD로 현재 통과 인원 수를 확인한다.
2. 그 값이 제한 수량보다 적으면 SADD로 사용자를 추가한다.
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
시각    user:A                          user:B
t1      SCARD → 999 (1자리 남음)
t2                                      SCARD → 999 (동일하게 판단)
t3      SADD → 성공 (1000명)
t4                                      SADD → 성공 (1001명, 초과!)
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
user:A가 SCARD를 실행해 "1자리 남음"을 확인한 뒤, 아직 SADD를 실행하기 전에 user:B도 SCARD를 실행해 똑같이 "1자리 남음"이라는 결과를 받는다. 이 시점에는 아직 아무도 SADD를 하지 않았기 때문에, 두 사용자 모두 자신이 발급 가능하다고 판단하게 된다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
SADD는 스스로 정원이 찼는지를 확인하지 않는다.
 user:A가 먼저 SADD로 1,000번째 자리를 채운 뒤에도, user:B는 Set에 없던 새로운 값이기 때문에 user:B의 SADD 역시 그대로 성공해버린다. 결국 "정원 확인"은 오직 SCARD 시점에서만 이뤄지는데, 그 SCARD가 이미 낡은 정보(999명)를 기준으로 판단했기 때문에 SADD 단계에서는 정원 초과를 막을 방법이 없다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
확인(SCARD)과 반영(SADD)이 하나의 원자적인 작업으로 묶여있지 않다는 것이다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
SISMEMBER(중복 체크), SCARD(수량 체크), SADD(추가) 이 세 작업이 하나의 원자적인 실행 단위로 묶여야 한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER coupon:{eventId}:issued-users {userId}

2. SCARD coupon:{eventId}:issued-users

3. SADD coupon:{eventId}:issued-users {userId}
```

### **2. Lua Script 처리 흐름 다이어그램**

```
EVALSHA(script) 실행
      │
      ▼
  SISMEMBER 확인
      │
  ┌───┴───┐
 있음      없음
  │         │
DUPLICATE   SCARD 확인
            │
        ┌───┴───┐
      가득참    남음
        │         │
     SOLD_OUT   SADD 실행 → SUCCESS
```

### **3. Lua Script 반환값 설계**

| **반환값** | **의미** | **API Server 처리** |
| --- | --- | --- |
| SUCCESS | 신규 사용자이고, 아직 제한 수량 미만일 때 | Kafka에 발급 요청 메시지 발행 후, 발행 성공까지 확인되면 PENDING 응답 |
| DUPLICATE | SISMEMBER에서 이미 존재하는 사용자로 확인됨 | Kafka 발행 없이 즉시 DUPLICATE 응답 |
| SOLD_OUT | 신규 사용자이지만 SCARD가 제한 수량에 도달함 | Kafka 발행 없이 즉시 SOLD_OUT 응답 |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
Redis는 기본적으로 명령어를 싱글스레드로 순차 처리한다.
Lua Script는 Redis 서버 안에서 통째로 실행되는데, 이 실행이 끝날 때까지는 다른 클라이언트의 어떤 명령어도 끼어들 수 없다. 그래서 SISMEMBER·SCARD·SADD를 Lua Script로 묶으면 "SCARD와 SADD 사이에 다른 요청이 끼어드는" 상황 자체가 구조적으로 발생하지 않는다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
Redis Lua Script의 SUCCESS는 어디까지나 Redis 안에서의 1차 판정 통과일 뿐이다. 이후 Kafka에 메시지를 발행하는 과정에서 장애로 발행이 실패할 수도 있고, 발행에 성공하더라도 Consumer가 그 메시지를 소비해 DB에 저장하는 과정에서 또 실패할 수 있다. 
최종적으로 쿠폰 발급이 완료되었다고 확정할 수 있는 시점은, Consumer가 DB에 발급 기록을 실제로 저장한 순간뿐이다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
요청이 도착할 때마다 INCR coupon:{eventId}:request-count를 실행해 카운터 값을 하나씩 증가시킨다. 반환된 값이 제한 수량 이하이면 통과 후보로 간주한다.
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
INCR 자체는 원자적인 연산이다. 여러 클라이언트가 동시에 호출해도 Redis가 순서대로 하나씩 처리하기 때문에, 두 사람이 똑같은 카운터 값을 받는 일은 절대 생기지 않는다. 즉 카운터 값 자체의 정합성은 보장된다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
INCR은 "누가" 요청했는지는 전혀 알지 못하고 그냥 횟수만 센다. 그래서 같은 사용자가 여러 번 요청해도 이를 구분하지 못하고, 중복 요청 방지는 INCR만으로는 전혀 해결되지 않는다. 중복 방지를 하려면 반드시 별도의 Set 같은 자료구조가 함께 필요하다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
user1의 중복요청 때문에, 처음으로 요청한 user2는 카운터가 4가 되어 제한 수량을 초과했다는 이유로 SOLD_OUT 처리된다. 진짜 신규 사용자인 user2는 실제로는 발급받을 수 있었음에도 불구하고, 손해를 보는 불공평한 결과가 발생한다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
쿠폰 수량 3개 (제한)

INCR 순번:  1        2        3        4
요청자:    user:1   user:1   user:1   user:2
판정:      통과     통과     통과     SOLD_OUT (제한초과)

→ 유니크 통과 인원(unique): 1명 (user:1)
→ 카운터 상 통과 처리: 3건 (모두 user:1)
→ 자리가 있었음에도 처음 요청한 user:2는 부당하게 탈락
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
request-count는 요청 건수를 셀 뿐, 중복 요청을 걸러내지 못한다. 그래서 이 값에는 같은 사용자의 여러 번 요청도 그대로 포함된다.
 따라서 이 카운터 값을 최종 발급 수량으로 보면, 실제 발급 대상자 수와 어긋나게 된다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
Set에 저장된 고유 userId의 개수, 즉 SCARD로 확인하는 값이 더 적절하다. 이 값은 유일한 사용자 수만 정확하게 반영한다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식** | **Set + Lua Script 방식** |
| --- | --- | --- |
| 수량 판단 기준 | request-count 카운터 값 | SCARD |
| 중복 사용자 방지 | X | SISMEMBER + Set  |
| 장점 | 단일 명령어라 구현이 단순하고 연산이 빠름 | 중복 방지와 수량 제한을 동시에, 원자적으로 처리 |
| 단점 | 중복 요청이 실제 통과 인원을 왜곡시킴 | 구현 복잡도 |
| 최종 권장 여부 | 단독 사용은 비권장 | O |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 발급 결과는 마이페이지에서 확인해주세요.",
  "requestId": "9f1c2e2a-..."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
202 Accepted
- 200 OK는 "요청이 완전히 처리 완료됐다"는 오해를 줄 수 있음.
- 202 Accepted는 "요청은 정상적으로 접수됐지만, 아직 처리가 끝나지 않았다"는 걸 정확히 표현하는 상태 코드.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
Redis SUCCESS + Kafka 발행 성공까지만 확인된 거고, Consumer가 DB에 저장하는 단계가 아직 남아있기 때문이다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
Kafka Topic의 메시지를 소비해서 DB에 (event_id, user_id) 기준으로 발급 기록을 INSERT한다. 성공하면 상태를 ISSUED로 갱신.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 발급을 요청하신 쿠폰입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409 Conflict
- 409: 사용자의 요청이 서버의 현재 상태(이미 발급 이력이 있음)와 충돌한다는 의미
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
 이미 결론이 난 요청이라, 그대로 발행하면 Consumer가 DB Unique 제약에 걸려 실패하거나 중복 처리 로직을 추가로 짜야 한다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
"이미 발급을 요청하셨어요"라는 안내와 함께 마이페이지·발급 상태 조회 화면으로 이동할 수 있는 버튼을 제공한다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "죄송합니다. 쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
410 Gone
- 쿠폰이라는 자원이 더 이상 유효하게 존재하지 않는다는 의미
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
어차피 DB에서도 수량 초과로 실패할 요청이라, 미리 걸러서 Kafka·Consumer·DB의 자원 낭비를 막기 위해서 발행하지 않아야 한다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
품절 직후에도 대량 트래픽이 몇 분간 계속 몰릴 수 있는데, 이를 Redis 단계에서 즉시 끊어주지 않으면 Kafka·Consumer·DB 이 흐름에서 의미 없는 트래픽에 과부하가 걸린다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client → API Server
            │ Lua Script 실행
            ▼
       Redis: SUCCESS (issued-users에 userId 추가됨)
            │
            ▼
   API Server → Kafka Producer.send()
            │
            ▼
        Kafka 장애 발생 → 발행 실패
            │
            ▼
   Consumer는 이 요청 자체를 전혀 알지 못함
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
issued-users Set에는 이미 해당 userId가 추가되어 있다. 즉 Redis 입장에서는 "이 사용자는 이미 통과했다"는 기록이 남아있는 상태다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
발행 자체가 실패했으므로 coupon.issue.requested Topic에는 이 요청에 대한 메시지가 전혀 남지 않는다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
Consumer는 Kafka Topic에 쌓인 메시지만 읽을 수 있는데, 애초에 메시지가 발행되지 않았으므로 이 요청이 존재했다는 사실 자체를 알 방법이 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
사용자에게 `PENDING` 응답을 주면 안 된다. 
PENDING은 "정상적으로 접수되어 처리 중"이라는 의미인데, 실제로는 Kafka 발행에 실패해 아무 처리도 진행되지 않는 상태이기 때문이다. 이 경우는 실패로 처리하고, Redis에 남은 SUCCESS 상태를 되돌리는 보상 처리가 필요하다.

```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
- Redis issued-users에서 해당 userId 제거(SREM)해서 재요청 가능하게 되돌림
- 발행 실패 로그를 별도로 저장
- Kafka 발행 재시도 (Producer 자체 재시도 정책 활용)
- 재시도까지 실패하면 복구 배치 프로세스가 실패 로그를 읽어 나중에 재처리
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
보상 처리도 결국 네트워크를 통해 Redis에 보내는 별개의 연산이라, 그 시점에 Redis 자체가 장애 상태이거나 네트워크가 끊겨 있으면 이 보상 요청도 실패할 수 있다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
8주차의 Retry / DLQ / 장애 처리와 보상 트랜잭션과 직접 연결된다.
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 선착순/중복 1차 판정 | 요청을 비동기로 전달하는 버퍼 | 최종 정합성 보장 및 영구 저장 |
| 저장하는 데이터 | 통과 사용자 목록, 이벤트 메타데이터 | 발급 요청 이벤트 메시지 | 쿠폰 발급 기록 |
| 강점 | 인메모리 기반 빠른 응답 | 순서 보장, 재처리 가능, 부하 완충 | 트랜잭션, Unique 제약 등 강한 정합성 |
| 한계 | 휘발성 | 발행 실패 시 메시지 유실 가능 | 쓰기 속도가 상대적으로 느림 |
| 실패 시 문제 | 판정 결과가 실제 처리와 어긋날 수 있음 | Consumer가 요청 존재 자체를 모름 | INSERT 실패 시 재처리 필요 |
| 이번 주차에서 보는 핵심 | 중복·수량 판정을 어떻게 원자적으로 처리할지 | "Redis를 통과한 요청만 발행"하는 필터링 이후의 전달 역할 | 최종 정합성을 보장 |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
- Redis SUCCESS: 인메모리에서의 1차 판정 통과, 임시 상태
- Kafka PENDING: 메시지가 정상 접수됨, 여전히 처리 중
- DB ISSUED: 실제로 저장 완료된, 최종 확정 상태

```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
[임시/휘발성] Redis SUCCESS  →  [전달 중] Kafka PENDING  →  [영구/확정] DB ISSUED
      빠름, 불확실                순서보장, 여전히 처리중        느림, 확정됨
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
Redis 장애, 보상 처리 실패, Consumer 재시도 로직 오류 등 여러 원인으로 같은 사용자에 대한 발급 요청이 두 번 DB에 INSERT될 수 있다. DB에 UNIQUE(event_id, user_id) 제약이 없으면 이 중복 삽입을 막을 안전장치가 사라진다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
Kafka는 메시지를 순서대로 전달하는 역할만 할 뿐, 수량이나 중복 여부를 스스로 판단하지 않는다. 
이 판단을 Consumer·DB 단계에서만 하면, 이미 100,000건이 다 Kafka와 Consumer를 거쳐간 뒤에야 실패가 확정되므로 자원 낭비가 크다.
```

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis의 판정은 장애 상황까지 완벽히 막아주지는 못한다. DB Unique Key는 어떤 경로로 중복 요청이 들어오든 최종적으로 막아주는 마지막 방어선이다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
같은 이벤트에 대해 같은 사용자가 두 번 이상 쿠폰을 발급받는 것을 DB 레벨에서 원천 차단한다.
```

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
네트워크 타임아웃으로 인한 클라이언트의 자동 재전송, 사용자의 중복 클릭, Kafka Consumer의 재시도 로직(at-least-once 처리) 등 다양한 경로로 동일한 요청이 여러 번 도달할 수 있다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis 중복 체크는 "이 사용자가 이미 발급받았는가"를 기준으로 판단한다. requestId 멱등성은 "이 특정 요청 자체가 이미 처리된 적이 있는가"를 기준으로 판단한다. 후자는 재시도로 인해 완전히 동일한 요청이 중복 처리되는 것을 막는 데 특화되어 있다.
```

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
DB 트랜잭션과 Kafka 메시지 발행은 서로 별개의 시스템에 대한 별개의 작업이라, 하나의 트랜잭션으로 묶이지 않는다. DB commit은 성공했는데 그 직후 네트워크 장애 등으로 Kafka 발행이 실패하는 상황이 생길 수 있다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
DB 저장과 이벤트 발행이 원자적으로 함께 성공하거나 함께 실패하도록 보장하기 위해서다. 실제 데이터 저장과 같은 트랜잭션 안에서 "발행할 이벤트"를 Outbox 테이블에 함께 기록해두고, 별도 프로세스가 이 테이블을 읽어 안전하게 이벤트를 발행함으로써 정합성을 확보한다.
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
발급 서비스가 알림·통계 서비스를 동기로 직접 호출하면 서로 강하게 결합된다. 알림 서비스에 장애가 나면 발급 자체가 지연되거나 실패할 수 있고, 서비스가 늘어날수록 발급 로직이 점점 복잡해진다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
발급 서비스는 "발급 완료" 이벤트만 발행하고, 알림·마이페이지·통계는 각자 그 이벤트를 구독해서 독립적으로 처리한다. 서비스 간 결합도가 낮아지고, 한쪽에 장애가 나도 다른 서비스에 영향을 주지 않으며, 각 서비스를 독립적으로 확장할 수 있다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis에는 "통과했다"는 기록이 남아있는데 실제로는 DB에 발급 기록이 없는, 상태 불일치가 발생한다. 이 사용자는 다시 요청해도 Redis가 DUPLICATE로 막아버려 영구히 발급받지 못하는 상황에 빠질 수 있다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
일시적인 장애는 재시도하면 해결될 수 있으므로 Retry Topic으로 다시 시도한다. 반복해서 계속 실패하는 메시지를 무한정 재시도하면 자원을 낭비하므로, 일정 횟수 이상 실패한 메시지는 DLQ로 격리해 별도로 분석·수동 처리할 수 있게 한다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
Redis에서는 SUCCESS로 처리되었지만 DB 저장이 재시도까지 모두 실패로 확정된 경우, issued-users에서 해당 userId를 제거해 Redis 상태를 DB 상태와 다시 일치시키는 처리가 필요하다.
```
