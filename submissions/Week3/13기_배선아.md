## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | POST /coupon-events/{eventId}/issue
  v
API Server
  |
  | 1) 로그인 여부 확인
  | 2) 이벤트 시간 확인
  | 3) Redis Lua Script 실행 (SISMEMBER -> SCARD -> SADD 원자 처리)
  v
Redis ----------------------------------> SUCCESS / DUPLICATE / SOLD_OUT
  |
  | SUCCESS인 경우에만
  v
Kafka Producer
  |
  | publish
  v
coupon.issue.requested (Topic)
  |
  | consume
  v
Coupon Issue Consumer
  |
  | INSERT ... UNIQUE(event_id, user_id)
  v
DB (coupon_issue)


- DUPLICATE / SOLD_OUT은 Kafka Producer 단계로 넘어가지 않고 API Server에서 즉시 응답을 반환한다.

- SUCCESS인 요청만 Kafka->Consumer->DB 경로를 거친다.
```

### **2. Redis의 역할**

```
Redis는 DB에 도달하기 전 단계에서 "이 요청을 다음 단계로 넘겨도 되는가"를 빠르게 판정하는 1차 필터 역할을 한다.

중복 사용자 여부와 쿠폰 잔여 수량 여부를 원자적으로 확인해서, 성공 가능성이 없는 요청을 가능한 한 앞단에서 걸러낸다.
```

### **3. Kafka의 역할**

```
Kafka는 Redis를 통과한 요청(성공 후보)을 Consumer에게 안정적으로, 비동기로 전달하는 역할을 한다.

요청이 순간적으로 몰려도 Consumer가 처리 가능한 속도로 소비할 수 있게 완충 역할을 하며, 판정 로직 자체를 갖고 있지는 않다.
```

### **4. DB의 역할**

```
DB는 최종 발급 기록을 저장하는 원본 저장소이자 마지막 방어선이다.

`UNIQUE(event_id, user_id)`제약을 통해 Redis나 Kafka 단계에서 놓친 중복 발급을 최종적으로 차단하고, 실제로 발급이 완료되었다는 사실을 영속적으로 보장한다.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
쿠폰 수량보다 훨씬 많은 요청이 들어오는 상황에서, 실패가 확정적인 요청까지 Kafka에 발행하면 Kafka와 Consumer, DB가 처리할 필요가 없는 메시지를 떠안게 된다.

이는 불필요한 처리량 증가, Consumer 지연, DB Lock 경합으로 이어딘다.

Redis에서 먼저 걸러내면 Kafka 이후 구간은 "성공 가능성이 있는 요청"만 다루게 되어 시스템 전체의 효율이 크게 올라간다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
Kafka는 메시지를 순서대로 안정적으로 전달할 뿐, 수량 제한이나 중복 요청을 스스로 판단하지 못한다.

결국 판정 책임이 전부 DB로 넘어가는데, DB는 상대적으로 느리고 Lock경합에 취약하기 때문에 대량 트래픽의 판정 계층으로는 부적합하다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
100,000건 중 실제로 성공 가능한 요청은 1,000건뿐인데, 나머지 99,000건도 동일하게 Kafka에 적재되고 Consumer가 소비하며 DB 조회/저장 시도를 하게 된다.

이는 실패가 뻔한 요청 때문에 Kafka 처리량, Consumer 처리 지연, DB Connection/Lock 경합이 불필요하게 커지는 것을 의미한다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
품절 이후 요청들도 매번 DB까지 가서 "이미 소진됨"을 확인해야 하므로, 의미 없는 DB조회 부하가 계속 쌓인다.

특히 이벤트 초반 트래픽 피크와 겹치면 정작 처리되어야 할 다른 요청(조회 API등)까지 지연시킬 수 있다.
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
각 클릭이 별도의 요청으로 Kfaka에 발행되고 Consumer가 각각 처리를 시도하면, DB Unique제약이 없다면 중복 발급이 발생할 수 있고, 있다 하더라도 불필요한 저장 시도와 실패 처리 비용이 반복적으로 발생한다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
- 이미 통과 판정을 받은 사용자의 재요청(DUPLICATE)

- 쿠폰 수량이 이미 소진된 이후의 모든 요청(SOLD_OUT)

이 두 유형을 Redis단계에서 밀리초 단위로 차단함으로써, Kafka/Consumer/DB는 성공 가능성이 있는 최소한의 요청만 처리하면 된다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| **Redis Key** | **자료구조** | **저장하는 값** | **필요한 이유** |
| --- | --- | --- | --- |
| coupon:{eventId}:issued-users | Set | Redis 선착순 판정을 통과한 사용자 ID 목록 | 중복 사용자 확인(SISMEMBER)과 통과 인원 수 확인(SCARD)을 동시에 처리 |
| coupon:{eventId}:metadata | Hash | limit(발급 수량), startAt, endAt | 이벤트별 설정값을 Redis에 캐시해 빠르게 조회, 원본은 DB에 유지 |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
Redis선착순 판정(Lua Script)을 통과한 사용자의 식별자(user:1, user:2...)가 Set원소로 저장된다.

Set이므로 같은 값은 한 번만 존재할 수 있다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
전체 요청이 몇 번째로 들어왔는지(요청 순번)를 계산하는 용도로 쓰인다.

이 값은 중복 제거가 되어 있지 않으므로 최종 발급 수량과 동일시하면 안된다.
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
이벤트는 특정 기간 동안만 유효하고, 이벤트가 끝난 뒤에도 Key가 영구히 남아 있으면 Redis메모리가 불필요하게 낭비된다.

TTL을 설정해두면 별도의 정리 배치가 없어도 자동으로 메모리에서 해제된다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
이벤트 종료 시각을 기준으로 일정 유예 기간(예:1일)이 지나면 만료되도록 `EXPIRE`를 이벤트 생성 시점에 설정한다. 

또는 별도의 정리 배치가 이벤트 종료 여부를 확인해 관련 Key(`issued-users`, `metadata`)를 명시적으로 삭제하도록 구성할 수도 있다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
Set은 동일한 값을 중복 저장하지 않는 자료구조이기 때문에, 같은 사용자 ID를 여러 번 추가 시도해도 실제로는 한 번만 저장된다.

이 성질을 이용하면 별도의 로직 없이도 "이미 통과한 사용자인지"판단과 "중복 저장 방지"를 동시에 해결할 수 있다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
- 1: 새로운 값이 Set에 추가됨 (기존에 없던 값)

- 0: 이미 Set에 존재하는 값이라 추가되지 않음
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청: SADD 결과 1 -> 새로 추가됨 -> 선착순 통과

user:1 두 번째 요청: SADD 결과 0 -> 이미 존재함 -> 중복 요청으로 차단
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
coupon:100:issued-users (Set)
+----------+----------+----------+----------+
|  user:1  |  user:5  |  user:20 |  user:77 |
+----------+----------+----------+----------+
        SCARD = 4 (현재 통과 인원)
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
아니다.

Set은 "중복 저장 방지"만 자동으로 보장할 뿐, 몇 명까지 넣을 수 있는지는 애플리케이션이 `SCARD`값을 확인해서 별도로 판단해야 한다.

이때 확인(SCARD)과 추가(SADD)가 분리되어 실행되면 Race Condition이 발생할 수 있다.

그래서 Lua Script로 하나의 원자적 흐름으로 묶어야 한다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD coupon:{eventId}:issued-users

- Set에 저장된 고유 원소 개수를 반환한다.
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
current = SCARD coupon:100:issued-users

if current < limit:
    SADD coupon:100:issued-users userId
    return SUCCESS

else:
    return SOLD_OUT
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
시간     요청A                          요청B
 t1     SCARD → 999                    
 t2                                    SCARD → 999
 t3     999 < 1000 → 발급 가능 판단
 t4                                    999 < 1000 → 발급 가능 판단
 t5     SADD user:A (성공)
 t6                                    SADD user:B (성공)

최종 issued-users size = 1001
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
요청 A가 `SCARD`결과(999)를 확인한 시점과 요청 B가 `SCARD`결과(999)를 확인한 시점이 모두 SADD가 실행되기 이전이기 때문이다.

두 요청 모두 "아직 999명"이라는 동일한 스냅샷을 보고 판단하므로, 서로의 진행 상황을 모른 채 둘 다 "발급 가능"으로 결론 내린다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
수량 확인(SCARD)과 사용차 추가(SADD)라는 두 개의 독립적인 Redis명령 사이에 "확인 시점"과 "반영 시점"의 간격이 존재하고, 그 간격 동안 다른 요청이 끼어들어 같은 확인 결과를 근거로 각자 SADD를 수행하기 때문이다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
확인(Read)과 반영(Write)이 하나의 원자적 연산으로 묶여 있지 않다는 것이다.

두 명령 사이에 다른 클라이언트의 명령이 끼어들 수 있는 여지(비원자성)가 Race Condition의 근본 원인이다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
- 중복 사용자 확인(SISMEMBER)

- 현재 통과 인원 수 확인(SCARD)

- 조건을 만족할 때 사용자 추가(SADD)

이 세 작업이 Redis 서버 내부에서 하나의 단일 실행 단위로 처리되어야 하며, 이를 위해 Lua Script를 사용한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER - 이미 통과한 사용자인지 확인

2. SCARD - 현재 통과 인원 수 확인
 
3. SADD - 조건을 만족하면 사용자 추가
```

### **2. Lua Script 처리 흐름 다이어그램**

```
API Server
  |
  | EVAL script KEYS[1]=issued-users ARGV[1]=userId ARGV[2]-limit
  v
Redis (단일 스레드 내에서 원자적으로 실행)
  | 1) SISMEMBER issued-users userId -> 1이면 DUPLICATE 반환
  | 2) SCARD issued-users            -> currentCount
  | 3) currentCount >= limit         -> SOLD_OUT 반환
  | 4) SADD issued-users userId      -> SUCCESS 반환
  |
  v
API Server (결과 수진)
```

### **3. Lua Script 반환값 설계**

| **반환값** | **의미** | **API Server 처리** |
| --- | --- | --- |
| SUCCESS | Redis선착순 판정 통과(Set에 추가 완료) | Kfaka에 발급 요청 메시지 발행 시도 |
| DUPLICATE | 이미 Set에 존재하는 사용자 | 중복 요청 응답, Kafka발행 안 함 |
| SOLD_OUT | 현재 통과 인원이 제한 수량 이상 | 품절 응답, Kfaka발행 안 함 |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
Redis는 단일 스레드로 명령을 처리하며, Lua Script는 실행되는 동안 다른 명령이 중간에 끼어들 수 없다.

따라서 "중복 확인 -> 수량 확인 -> 사용자 추가"라는 세 단계가 다른 요청의 개입 없이 하나의 원자적 트랜잭션처럼 처리되어, 확인-반영 사이의 간격이 사라진다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
Lua Script의 SUCCESS는 "Redis안에서의 선착순 판정 통과"만을 의미할 뿐, 이후 Kfaka발행이 실패할 수도 있고, Kafka발행이 성공하더라도 Consumer의 DB저장이 실패할 수도 있다.

최종 발급 성공 여부는 DB에 발급 기록이 실제로 저장되었는지로만 판단할 수 있다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
API Server
  | 
  | INCR coupon:{eventId}:request-count
  v
Redus -> requestOrder 반환
  |
  | requestOrder <= limit ?
  | issued-users Set으로 중복 사용자 확인
  v
통과 시 Kafka 발생
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
동시에 여러 요청이 들어와도 각 요청이 서로 다른, 겹치지 않는 순변을 원자적으로 부여받는다는 것을 보장한다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
같은 사용자가 여러 번 요청했을 때 그 요청들이 서로 다른 사용자의 요청인지, 동일 사용자의 중복 요청인지는 구분하지 못한다.

즉 사용자 단위의 중복 제거를 보장하지 않는다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변: user:1 혼자서 순번 1,2,3을 모두 차지해버려 실제로는 3개의 자리 모두 user:1 한 명의 중복 요청으로 채워진다.

정작 처음 요청한 user:2는 순번 4를 받아 SOLD_OUT처리된다.

즉 실제 발급되어야 할 사용자 3명이 아니라, 중복 요청 때문에 진짜 선착순 대상자가 밀려나는 문제가 생긴다.

```

```

### **5. 위 상황을 다이어그램으로 표현하기**

```
request-count 기준 선착순 자리
+---------+---------+---------+---------+
| 순번 1  | 순번 2  | 순번 3  | 순번 4  |
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
   통과      중복      중복      품절(부당)
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
`request-count`는 중복 제거가 되지 않은 "전체 요청 순번"에 불과하다.

동일 사용자의 반복 요청도 그대로 카운트되기 때문에, 이 값이 limit에 도달했다고 해서 실제로 서로 다른 limit명의 사용자가 통과했다는 것을 의미하지 않는다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
중복이 제거된 `issued-users` Set의 크기(SCARD)를 기준으로 판단하는 것이 적절하다.

Set은 구조적으로 동일 사용자를 한 번만 담기 때문에 실제 고유 통과 인원 수를 정확히 반영한다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식** | **Set + Lua Script 방식** |
| --- | --- | --- |
| 수량 판단 기준 | 전체 요청 순번(request-count) | 중복 제거된 통과 사용자 수(SCARD) |
| 중복 사용자 방지 | 자동 보장 안 됨, Set을 별도 결합해야함 | Set구조 자체로 자동 보장 |
| 장점 | 구현이 단순하고 순번 계산이 빠름 | 수량 제한과 중복 방지를 하나의 원자적 흐름으로 동시에 해결 |
| 단점 | 중복 요청이 선착순 자리를 부당하게 차지할 수 있음 | Lua Script 작성/운영 난이도가 다소 있음 |
| 최종 권장 여부 | 참고용(단독 채택 비권장) | 최종 채택 |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
'202 Accepted'를 사용한다.

요청은 정상적으로 접수되어 처리 대기 상태로 들어갔지만, 아직 최종 처리(DB 저장)가 완료되지 않았다는 의미를 가장 잘 나타내는 코드이기 때문이다.

'200 OK'를 사용하면 "이미 완료된 처리"라는 오해를 줄 수 있다.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
이 시점에는 Redis 선착순 판정과 Kafka발행까지만 성공한 것이고, Consumer가 실제로 메시지를 소비해 DB에 발급 기록을 저장하는 단계는 아직 진행되지 않았다.

DB 저장이 실패하면 이 요청은 최종적으로 실패로 종료될 수도 있다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
'coupon.issue.requested'토픽의 메시지를 소비하여, 'coupon_issue'테이블에 'UNIQUE(event_id, user_id)'제약과 함께 발급 기록 저장을 시도한다.

저장에 성공하면 최종 'ISSUED' 상태가 되고, 실패하면 재시도나 실패 처리 로직으로 이어진다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
'409 Conflict'를 사용한다.

요청 자체는 문법적으로 문제가 없지만, 현재 서버의 상태(이미 발급 이력이 있음)와 충돌하기 때문에 이 요청을 처리할 수 없다는 의미를 가장 정확히 전달한다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
이미 발급받은 사용자에 대해 또 메시지를 발행하면 Consumer와 DB까지 불필요한 처리 부하가 전달되고, 만약 DB Unique 제약이 없었다면 중복 발급으로 이어질 수도 있다.

Redis단계에서 이미 이동할 수 있는 버튼을 제공하면, 사용자가 혼란 없이 자신의 발급 상태를 확인할 수 있다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
"이미 발급받으신 쿠폰이 있어요"라는 안내와 함께 마이페이지의 발급 내역이나 쿠폰함으로 바로 이동할 수 있는 버튼을 제공하면, 사용자가 혼란 없이 자신의 발급 상태를 확인할 수 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
`409 Conflict'(또는 팀 컨벤션에 따라 '401 Gone'도 고려 가능)를 사용한다.

요청 자체는 유효하지만 "쿠폰 재고가 소진된 상태"와 충돌하여 처리할 수 없다는 의미를 전달하기 위함이다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
이미 수량이 소진되었다는 것이 Redis에서 확정되었기 때문에, Kafka에 발행해봤자 Consumer가 DB에서 다시 한 번 실패를 확인하는 불필요한 작업만 늘어난다.

실패가 확정된 요청은 가능한 한 앞단에서 종결시키는 것이 효율적이다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
이벤트 인기가 높을수록 품절 이후에도 대량의 요청이 계속 들어올 가능성이 크다.

이 요청들을 Redis단계에서 즉시 차단하지 못하면 Kafka-Consumer-DB까지 불필요한 부하가 누적되어, 정작 처리되어야 할 다른 정상 트래픽(조회, 로그인 등)까지 영향을 받을 수 있다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client            API Server                Redis                 Kafka
   |                    |                       |                     |
   | 쿠폰 발급 요청       |                       |                     |
   |------------------->|                       |                     |
   |                    | 로그인 / 이벤트시간 검증 |                     |
   |                    |                       |                     |
   |                    | EVAL Lua Script       |                     |
   |                    |---------------------->|                     |
   |                    |                       | SISMEMBER → 0       |
   |                    |                       | SCARD → 999 (<1000) |
   |                    |                       | SADD user:1 → 성공   |
   |                    |     SUCCESS           |                     |
   |                    |<----------------------|                     |
   |                    |                       |                     |
   |                    |  [Redis 상태 변경 완료: issued-users에 user:1 포함]
   |                    |                       |                     |
   |                    | publish                                     |
   |                    | coupon.issue.requested                      |
   |                    |-------------------------------------------->|
   |                    |                       |                     |
   |                    |                       |        X  Kafka 브로커 장애
   |                    |                       |        X  (네트워크 단절 /
   |                    |                       |        X   리더 선출 지연 등)
   |                    |                       |                     |
   |                    |   발행 실패(Exception)                       |
   |                    |<--------------------------------------------|
   |                    |                       |                     |
   |                    | [보상 처리 시도]        |                     |
   |                    | SREM issued-users     |                     |
   |                    | user:1                |                     |
   |                    |---------------------->|                     |
   |                    |     REM 결과           |                     |
   |                    |<----------------------|                     |
   |                    |                       |                     |
   |   접수 실패 응답     |                       |                     |
   |<-------------------|                       |                     |
   |                    |                       |                     |


결과적으로 남는 상태:
  Redis   : 보상 처리가 성공했다면 issued-users에 user:1 없음 (정상 복구)
            보상 처리까지 실패했다면 issued-users에 user:1 남아있음 (불일치 발생)
  Kafka   : coupon.issue.requested 토픽에 해당 메시지 없음
  Consumer: 처리할 메시지 자체가 없으므로 아무 동작도 하지 않음
  DB      : 발급 기록 없음 (ISSUED 되지 않음)
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
'issued-users' Set에 해당 사용자가 이미 추가된 상태로 남아 있다.

즉 Redis관점에서는 이 사용자가 "선착순 통과 완료"로 기록되어 있다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
'coupon.issue.requested'토픽에 해당 요청에 대한 메시지가 존재하지 않는다.

즉 Consumer입장에서는 이 요청이 발생했다는 사실 자체를 알 수 없다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
Consumer는 Kafka토픽에 쌓인 메시지를 소비하는 방식으로만 동작하기 때문에, 애초에 메시지가 발생되지 않았다면 처리할 대상 자체가 없다.

Redis상태만으로는 Consuemr가 이 요청의 존재를 알 방법이 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
안 된다.

'PENDING'은 "Kafka에 정상적으로 접수되어 Consumer가 처리할 예정"이라는 의미인데, 이 시나리오에서는 Kafka발행 자체가 실패했으므로 실제로 아무 처리도 예정되어 있지 않다.

이 경우에는 접수 실패임을 알리고 재시도를 유도하는 응답을 줘야 한다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
- Redis issued-users Set에서 해당 userId제거 (Redis 상태를 요청 이전으로 되돌림)

- 실패 로그 저장 (장애 분석 및 사후 추적용)

- Kafka 발행 재시도 (일시적 장애라면 즉시 또는 짧은 backoff 후 재시도)

- 위 재시도까지 실패하면 사용자에게 "접수 실패, 다시 시도해주세요" 응답

- 복구 배치를 통해 실패 로그 기반으로 후속 재처리
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
보상 처리(Set에서 userId 제거) 역시 하나의 Redis 명령이므로, 그 시점에 Redis 네트워크 오류나 장애가 발생하면 제거 자체가 실패할 수 있다.

이 경우 Redis에는 "통과 완료"로 남아 있지만 실제로는 아무 메시지도 발행되지 않은 상태로 영구히 불일치가 남을 위험이 있다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
5주차의 requestId 기반 멱등성(같은 요청 재시도 시 안전하게 처리), 6주차의 Outbox Pattern(저장과 발행의 정합성), 8주차의 Retry/DLQ/보상 트랜잭션(실패 유형별 복구 전략)과 직접 연결된다.
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순/중복 판정 | 요청의 안정적 비동기 전달 | 최종 발급 기록의 영속 저장 |
| 저장하는 데이터 | 통과 사용자 목록(임시 상태) | 발급 요청 메시지 | 발급 기록(coupon_issue) |
| 강점 | 원자 연산, 매우 빠른 조회/쓰기 | 트래픽 완충, Consumer 병렬 처리 | 트랜잭션, Unique제약을 통한 정합성 보장 |
| 한계 | 최종 저장소로 부적합, 장애/유실 가능 | 수량 초과,중복 발급을 스스로 막지 못함 | 대량 동시 조회/갱신 시 병목 가능 |
| 실패 시 문제 | 상태 유실 시 판정 무효화 가능 | 메시지 유실/중복 소비 가능 | 저장 실패 시 최종 발급 미완료 |
| 이번 주차에서 보는 핵심 | 선착순 판정을 원자적으로 처리하는 방법 | 성공 후보만 전달받아 처리하는 구조 | 아직 상세히 다루지 않음 |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
Redis SUCCESS = 선착순 판정 통과 (Redis 내부 상태)

Kafka PENDING = 발급 요청 메시지가 Kafka에 정상 접수됨 (전달 완료, 처리 전)

DB ISSUED     = DB에 발급 기록이 최종 저장됨 (진짜 완료)
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Redis                  Kafka              Consumer                 DB
   |                     |                    |                     |
   | issued-users        |                    |                     |
   | 에 user:1 추가       |                    |                     |
   | (SUCCESS)           |                    |                     |
   |                     |                    |                     |
   |         coupon.issue.requested           |                     |
   |         메시지 발행 성공                   |                     |
   |-------------------->|                    |                     |
   |                     |                    |                     |
   |                     | consume            |                     |
   |                     |------------------->|                     |
   |                     |                    | INSERT coupon_issue |
   |                     |                    | (event_id, user_id) |
   |                     |                    |-------------------->|
   |                     |                    |                     |
   |                     |                    |     X DB 순간 장애 / |
   |                     |                    |     X 커넥션 풀 고갈 /|
   |                     |                    |     X 타임아웃 등     |
   |                     |                    |                     |
   |                     |                    |   INSERT 실패        |
   |                     |                    |<--------------------|
   |                     |                    |                     |
   |                     |                    | [재시도 N회 모두 실패] |
   |                     |                    | → 영구 실패로 판단    |
   |                     |                    |                     |
   |   SREM issued-users user:1 (보상 트랜잭션) |                     |
   |<-----------------------------------------|                     |
   |                     |                    |                     |
   | issued-users 에서    |                    | 실패 로그 저장        |
   | user:1 제거 완료      |                    | (requestId, 사유,   |
   |                     |                    |  시각 등 기록)        |
   |                     |                    |                     |


결과:
  Redis : issued-users에서 user:1 제거 → "아직 통과하지 않은 사용자" 상태로 복원
  DB    : 발급 기록 없음 (정상, 저장 시도 자체가 실패했으므로 정합)
  사용자 : 재요청 시 Redis 판정부터 다시 정상적으로 진행 가능
          (남은 쿠폰 수량이 있다면 다시 SUCCESS 판정을 받을 수 있음)
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
Redis장애나 데이터 유실, Kafka 메시지 중복 소비, Consumer 재처리, 애플리케이션 버그로 Redis를 우회하는 경로 등 다양한 이유로 Redis의 판정이 완벽하지 않을 수 있다.

이때 DB에 Unique제약이 없으면 동일 사용자에게 쿠폰이 여러 번 저장되는 최종 사고로 이어질 수 있다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
Kafka는 메시지를 순서대로 전달하고 저장할 뿐, 메시지의 내용(사용자 중복 여부, 남은 수량)을 판단하는 로직을 갖고 있지 않다. 

판정은 반드시 Redis나 DB같은 상태 저장소에서 이루어져야 하면, Kafka 혼자서는 비즈니스 규칙을 검증할 수 없다.
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis는 빠르지만 임시 상태 저장소이고, 장애, 유실 가능성이 있다. 

DB의 'UNIQUE(event_id, user_id)제약은 Redis판정이 실패하거나 우회되는 모든 경우에 대한 최후의 방어선 역할을 한다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
같은 이벤트에 대해 동일한 사용자가 두 번 이상 발급 기록을 저장하려는 시도를 DB레벨에서 강제로 차단하여, 어떤 경로로 요청이 들어오든 최종 중복 발급을 방지한다.
```

---

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
네트워크 타임아웃으로 인한 클라이언트의 자동 재시도, 사용자의 중복 클릭, Kafka Consumer의 메시지 중복 소비(재균형, 오프셋 커밋 실패 등)등 다양한 원인으로 동일한 논리적 요청이 여러 번 시스템에 도달할 수 있다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis중복 체크는 "이 사용자가 이미 통과했는가"라는 사용자 단위의 중복을 확인하는 것이고, requestId 멱등성은 "이 특정 요청(재시도 포함)을 이미 처리했는가"하는 요청 단위의 중복을 확인하는 것이다.

후자는 동일한 요청이 반복돼도 결과가 한 번만 반영되도록 보장하는 더 세밀한 장치이다.
```

---

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
DB트랜잭션 커밋과 Kafka 메시지 발행은 서로 다른 시스템에 대한 별개의 작업이기 때문에, 하나의 원자적 트랜잭션으로 묶이지 않는다.

DB커밋 직후 네트워크 장애나 Kafka 브로커 문제로 발행이 실패하면, DB에는 기록이 있지만 후속 이벤트는 전달되지 않는 불일치가 생긴다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
'coupon_issue'저장과 'outbox_event'저장을 같은 DB트랜잭션으로 묶어 두면, 최소한 "DB에 기록되었는가"와 "이벤트가 발행되어야 하는가"는 항상 함께 커밋되거나 함께 롤백된다.

이후 별도의 Outbox Publisher가 안정적으로 발행함으로써 저장과 발행 사이의 정합성을 보장한다.
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
Coupon Service가 각 서비스를 동기 호출로 직접 의존하게 되면, 그중 한 서비스(예:알림)가 느려지거나 장애가 나면 쿠폰 발급 자체가 지연되거나 실패할 위험이 생긴다.

즉 본질적으로 관련 없는 부가 기능의 장애가 핵심 기능에 전파된다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
각 서비스가 발급 완료 이벤트를 독립적으로 구독해 처리하므로, 한 서비스의 장애나 지연이 다른 서비스나 핵심 발급 로직에 영향을 주지 않는다.

서비스 간 결합도가 낮아지고 각자 독립적으로 확장,배포할 수 있다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis에는 사용자가 통과한 것으로 기록되어 있고 Kafka에도 메시지가 전달되었지만, 정작 DB에는 발급 기록이 남지 않는 정합성 실패 상황이다.

사용자는 발급을 기대하지만 실제로는 아무결과도 없는 상태가 된다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
일시적 장애(DB 커넥션 순간 오류 등)는 Retry Topic으로 재시도하면 해결될 수 있지만, 메시지 형식 오류처럼 재시도해도 절대 성공할 수 없는 영구 실패는 계속 재시도되면 무한 루프에 빠진다.

DLQ로 격리해 별도로 운영자가 확인, 재처리할 수 있게 해야한다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
Redis에서는 SUCCESS로 판정되어 Set에 사용자가 추가되었는데, 이후 DB 저장이 영구적으로 실패한 경우, Redis의 상태를 되돌려(Set에서 제거) 해당 사용자가 다시 정상적으로 재요청을 할 수 있도록 하는 보상 처리가 필요하다.
```
