# **Redis 기반 선착순 쿠폰 판정 구조 설계**

## **1. 과제 목표**

이번 3주차 과제의 목표는 **Redis를 이용해 선착순 쿠폰 발급 요청을 빠르게 판정하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달하고, Consumer가 뒤에서 실제 쿠폰 발급 처리를 수행하는 구조를 설계했다.

이번 3주차에서는 Kafka 앞단에 Redis를 도입한다.

기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
SUCCESS인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Redis가 필요한 이유

Redis Key 설계

Redis 자료구조 선택

Set 기반 중복 요청 방지

SCARD / SADD를 분리했을 때 생기는 Race Condition

Lua Script를 이용한 원자적 처리

INCR 기반 방식의 장점과 한계

Redis SUCCESS / DUPLICATE / SOLD_OUT 결과에 따른 API 응답 설계

Redis SUCCESS 이후 Kafka 발행 실패 상황 분석

Redis SUCCESS가 최종 쿠폰 발급 성공을 의미하지 않는 이유

Redis, Kafka, DB의 역할 구분

앞으로 4~8주차에서 해결할 문제 연결하기
```

이번 과제의 핵심은 Redis 명령어를 외우는 것이 아니라, **Redis를 시스템 구조 안에서 어떤 역할로 사용할지 설계하는 것**이다.

특히 아래 내용을 반드시 구분해야 한다.

```
Redis SUCCESS
= 선착순 판정 통과

Kafka PENDING
= 발급 요청 메시지가 Kafka에 접수됨

DB ISSUED
= DB에 쿠폰 발급 기록이 최종 저장됨
```

즉, Redis에서 `SUCCESS`가 나왔다고 해서 쿠폰 발급이 최종 완료된 것은 아니다.

## **2. 기본 상황**

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

2주차까지의 구조에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 발급 처리를 수행했다.

하지만 이 구조에서는 모든 요청이 Kafka와 Consumer까지 도달할 수 있다.

예를 들어 쿠폰 수량은 1,000개인데 요청이 100,000건 들어온다면, 실제로는 99,000건은 실패할 가능성이 높은 요청이다.

이번 주차에서는 이 실패할 요청을 DB까지 보내지 않도록 Redis에서 먼저 판정한다.

```
요청 100,000건
  ↓
Redis 선착순 / 중복 판정
  ↓
성공 1,000건만 Kafka 발행
  ↓
실패 99,000건은 SOLD_OUT 또는 DUPLICATE 응답
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Redis에서 다음을 먼저 확인한다고 가정한다.

```
1. 이미 통과한 사용자인가?

2. 쿠폰 수량이 아직 남아 있는가?

3. 선착순 안에 들어온 요청인가?
```

Redis 판정 결과가 `SUCCESS`인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 `DUPLICATE` 또는 `SOLD_OUT`인 경우에는 Kafka에 메시지를 발행하지 않는다.

## **3. 이번 과제의 전제 조건**

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 먼저 로그인 여부와 이벤트 시간을 확인한다.

그 다음 Redis를 이용해 선착순 / 중복 여부를 판정한다.

Redis 판정 결과가 SUCCESS인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 DUPLICATE 또는 SOLD_OUT이면 Kafka에 메시지를 발행하지 않는다.

Redis SUCCESS는 최종 쿠폰 발급 성공이 아니다.

최종 쿠폰 발급 성공은 Consumer가 DB에 쿠폰 발급 기록을 저장한 뒤 결정된다.
```

이번 주차에서 사용할 Redis 결과는 아래 세 가지로 단순화한다.

```
SUCCESS:
Redis 선착순 판정 통과

DUPLICATE:
이미 Redis에서 통과한 사용자

SOLD_OUT:
쿠폰 수량 소진
```

이번 주차에서는 Redis를 사용해 선착순 판정을 수행하지만, 아래 내용은 깊게 다루지 않는다.

```
DB Unique Key 상세 설계

requestId 기반 멱등성 상세 설계

Outbox Pattern 상세 설계

Retry Topic / DLQ 상세 설계

보상 트랜잭션 상세 설계
```

다만 이 문제들이 왜 이후 주차에서 필요한지는 간단히 연결해서 설명해야 한다.

## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |  POST /coupon-events/{eventId}/issue
  v
API Server  (로그인 / 이벤트 시간 검증)
  |
  v
Redis  (중복 + 수량 확인 → 통과 시 등록)
  |  SUCCESS / DUPLICATE / SOLD_OUT
  v
API Server  (SUCCESS만 Kafka 발행, 나머지는 즉시 응답)
  |
  v
Kafka  (coupon.issue.requested)
  |
  v
Consumer
  |
  v
DB  (coupon_issue, UNIQUE(event_id, user_id))
```

### **2. Redis의 역할**

```
Redis는 DB 앞단에서 요청을 빠르게 걸러주는 선착순 판정 필터다. 세 가지 판단을 원자적으로 수행한다.

1. 이 사용자가 이미 통과했는가?  (중복 판정)
2. 쿠폰 수량이 아직 남아 있는가? (수량 판정)
3. 선착순 안에 들어왔는가? (통과 여부 결정)

성공 가능성이 없는 요청을 DB에 도달하기 전에 빠르게 차단하는 것이다. 인메모리 자료구조와 원자 연산(Lua)을 활용해 대량 트래픽에서도 빠른 판정이 가능하다.
```

### **3. Kafka의 역할**

```
Kafka는 Redis를 통과한 요청을 Consumer에게 비동기적으로 안정 전달하는 역할이다.

- 요청 폭주를 완충(buffering)한다.
- Consumer가 처리 가능한 속도로 메시지를 소비하게 한다.
- Consumer 병렬 처리를 가능하게 한다.

단, Kafka 자체는 수량 초과나 중복 발급을 막지 못한다.
```

### **4. DB의 역할**

```
DB는 최종 발급 기록을 저장하는 원본 저장소이자 마지막 방어선이다.

- Redis를 통과하고 Kafka를 거친 요청만 최종 저장한다.
- UNIQUE(event_id, user_id) 제약으로 중복 발급을 최종 방어한다.
- Redis가 놓친 정합성 문제(장애, 유실, 중복 소비)를 DB가 최종 보증한다.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
1. 실패할 요청(품절/중복)까지 Kafka와 Consumer, DB로 보내면 불필요한 처리 부하가 생긴다.
2. 쿠폰 1,000개 이벤트에 10만 건이 몰릴 때, 99,000건은 결국 실패할 요청이다.
   이를 미리 걸러야 Kafka와 DB가 성공 가능성이 있는 요청에 집중할 수 있다.
3. 품절 이후 요청과 중복 클릭이 파이프라인 뒤쪽까지 도달하는 것을 막을 수 있다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
Kafka는 메시지를 전달하고 쌓아두는 역할만 한다. 
수량 초과, 중복 발급, 품절 이후 요청을 자동으로 걸러주지 않는다. 
따라서 모든 요청이 Consumer를 거쳐 DB 판정 단계까지 도달할 수 있고, 실패할 가능성이 높은 99,000건까지 DB가 수량 조회/중복 확인/저장 시도를 반복하게 된다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
1. DB에서 수량 조회 / 중복 확인 / 저장 시도가 대량 반복된다.
2. 동시 요청이 많아 DB Lock 경합이 커지고 DB가 병목이 된다.
3. 성공 가능성이 없는 요청까지 자원을 소모해 전체 처리량이 떨어진다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
품절 이후에는 어차피 발급이 불가능한데도 요청이 계속 Kafka → Consumer → DB까지 간다. 
DB는 매번 수량 없음을 확인하기 위해 조회를 반복하고, 실제 성공 요청의 처리까지 느리게 만든다.
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
한 사용자의 반복 클릭이 여러 개의 메시지로 Kafka에 쌓이고 Consumer가 이를 모두 처리하려 시도한다. DB Unique Key가 없다면 중복 발급 위험이 있고, 있더라도 불필요한 저장 시도와 Lock 경합이 발생한다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
1. 이미 통과한 사용자의 중복 요청 (DUPLICATE)
2. 쿠폰이 소진된 뒤의 요청 (SOLD_OUT)
-> 성공 가능성 있는 요청(약 1,000건)만 Kafka로 발행되고,
   나머지 99,000건은 DB에 도달하기 전에 즉시 응답으로 차단된다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| Redis Key | 자료구조 | 저장하는 값 | 필요한 이유 |
| --- | --- | --- | --- |
| `coupon:{eventId}:issued-users` | Set | 선착순 통과한 사용자 ID  | 중복 요청 방지 + SCARD로 통과 사용자 수 판정 |
| `coupon:{eventId}:metadata` | Hash(또는 캐시) | limit, startAt, endAt | 이벤트 수량/기간 정보를 빠르게 조회 (원본은 DB) |
| `coupon:{eventId}:request-count` | String Counter | 요청 순번(전체 요청 수) | 요청량 모니터링용  |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:metadata
coupon:100:request-count
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
Redis 선착순 판정에 성공한 사용자의 ID가 저장된다. 
Set이므로 같은 사용자는 한 번만 저장되며, SCARD로 현재 통과 사용자 수를 알 수 있다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
INCR로 증가하는 요청 순번 카운터다. 몇 번째로 판정에 들어온 요청인지를 나타낸다. 
그러나 같은 사용자의 중복 요청이나 품절 이후 요청도 카운트를 올리므로 최종 발급 수량과는 다르다. 
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
Redis는 영구 원본 저장소가 아니므로, 이벤트가 끝난 뒤에도 Key가 계속 남으면 메모리를 낭비한다. TTL을 두면 이벤트 종료 후 자동으로 정리되어 메모리 누수를 막을 수 있다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
1. 이벤트 종료 시각 + 여유 기간(예: 1일)을 TTL로 설정해 자동 만료시킨다.
2. 또는 운영 배치가 이벤트 종료 후 issued-users/request-count/metadata Key를 삭제한다.
3. 최종 원본은 DB에 남아 있으므로 Redis Key를 지워도 정합성에 문제 없다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
Set은 같은 값을 중복 저장하지 않는다. 따라서 한 사용자가 여러 번 요청해도 한 번만 저장되어 중복 요청 방지에 자연스럽게 맞고, SCARD로 통과 인원까지 확인할 수 있다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
1 → 새로 추가됨 (기존에 없던 사용자 = 최초 요청)
0 → 이미 존재함 (이미 통과한 사용자 = 중복 요청)
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청: SADD coupon:100:issued-users user:1 → 1 (추가 성공, 선착순 통과)
user:1 두 번째 요청: SADD coupon:100:issued-users user:1 → 0 (이미 존재, 중복 차단)
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
key: coupon:100:issued-users
+-----------------------+
| user:1                |
| user:5                |
| user:20               |
| user:77               |
+-----------------------+
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
아니다. Set은 중복만 자동으로 막는다. 
수량 제한은 SCARD로 현재 인원을 확인하고 limit과 비교하는 로직이 별도로 필요하다. 
또한 SCARD와 SADD를 분리해 실행하면 Race Condition이 생기므로, Lua Script로 묶어 원자적으로 처리해야 완전해진다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD coupon:{eventId}:issued-users -> Set에 저장된 고유 요소의 총 개수를 반환한다.
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
current = SCARD coupon:100:issued-users
if current < limit:
    SADD coupon:100:issued-users userId
    return SUCCESS
else:
    return SOLD_OUT
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
[현재 상태] size = 999
        요청 A                          요청 B
          |                               |
          | SCARD = 999                   |
          |                               | SCARD = 999
          | 999 < 1000 → 발급 가능         |
          |                               | 999 < 1000 → 발급 가능
          | SADD user:A                   |
          |                               | SADD user:B
          v                               v
[결과] size = 1001  <- 쿠폰 1000개인데 1001명 통과
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
A와 B가 SADD를 실행하기 전에 각각 SCARD를 먼저 조회했기 때문이다. 
두 요청 모두 아직 999를 보고 1개가 남았다고 판단한다. 
수량 확인 시점과 추가 시점 사이에 상대 요청이 끼어들어 같은 값을 읽는다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
둘 다 999를 읽고 통과 판단을 내린 뒤 각자 SADD를 실행하므로, Set에는 user:A와 user:B가 모두 추가되어 1,001명이 통과한다. 남은 수량 1개를 두 요청이 동시에 소비한 것이다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
수량 확인(SCARD)과 사용자 추가(SADD)가 분리되어 있어, 그 사이에 다른 요청이 끼어들 수 있기 때문이다. 즉 확인 후 행동 사이에 원자성이 없다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
1. 중복 사용자 확인 (SISMEMBER)
2. 현재 통과 사용자 수 확인 (SCARD)
3. 조건 만족 시 사용자 추가 (SADD)
-> 위 세 작업을 Lua Script로 묶어 하나의 원자적 작업으로 실행해야 한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER — 이미 통과한 사용자인지 확인 (중복 판정)
2. SCARD — 현재 통과 사용자 수 확인 (수량 판정)
3. SADD — 조건 만족 시 사용자 등록 (통과 처리)
```

### **2. Lua Script 처리 흐름 다이어그램**

```
API Server
  |  EVAL Lua Script (userId, limit)
  v
Redis (원자적 실행)
  |
  ├─ 이미 있음?      → DUPLICATE
  ├─ 수량 다 참?     → SOLD_OUT
  └─ 통과 → SADD     → SUCCESS
  |
  v
API Server (결과에 따라 응답)
```

### **3. Lua Script 반환값 설계**

| 반환값 | 의미 | API Server 처리 |
| --- | --- | --- |
| SUCCESS | Redis 선착순 판정 통과 | Kafka 발행 시도 → 성공 시 PENDING 응답 |
| DUPLICATE | 이미 통과한 사용자 | Kafka 발행 안 함, 중복 요청 응답 |
| SOLD_OUT | 쿠폰 수량 소진 | Kafka 발행 안 함, 품절 응답 |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
Redis는 Lua Script를 단일 원자 단위로 실행한다. 스크립트가 도는 동안 다른 명령이 중간에 끼어들 수 없다. 따라서 SISMEMBER → SCARD → SADD가 하나의 덩어리로 실행되어, 확인과 추가 사이에 끼어들기 문제가 사라진다. 두 요청이 동시에 와도 하나씩 순차 처리되므로 수량 초과 통과가 발생하지 않는다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
Redis SUCCESS = 선착순 판정만 통과한 상태이므로 아직 Kafka 발행, Consumer 처리, DB 저장이 남아 있다.

- Kafka 발행이 실패할 수 있다.
- Consumer 처리 중 DB 저장이 실패할 수 있다.
=> 최종 발급 성공은 DB에 발급 기록(ISSUED)이 저장된 시점에 확정된다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
Client → API Server
   | 1. INCR coupon:100:request-count → requestOrder 반환
   | 2. requestOrder <= limit 인지 확인
   | 3. issued-users Set에서 중복 사용자 확인 (SISMEMBER)
   | 4. 통과 가능하면 Kafka 발행
   v
Kafka
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
INCR는 원자적으로 동작하므로, 동시에 많은 요청이 와도 각 요청에 서로 다른 순번을 부여한다. 요청 순번 계산이 단순하고 매우 빠르다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
사용자 중복 제거는 보장하지 못한다. 같은 사용자가 여러 번 요청해도 매번 카운터가 증가하므로, 한 사용자가 여러 순번을 차지할 수 있다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
실제로는 user:1 한 명만 통과해야 하는데, user:1의 중복 요청이 순번 1·2·3을 모두 차지했다. 그 결과 user:2는 순번 4를 받아 품절 처리된다. request-count 기준으로만 판단하면 발급이 사실상 1명(user:1)에게만 이뤄지고 나머지 자리는 낭비된다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
request-count 기준 선착순 자리 (limit = 3)
+---------+---------+---------+---------+
| 순번 1  | 순번 2  | 순번 3  | 순번 4  |
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
   통과      중복      중복      품절
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
request-count는 중복 요청과 품절 이후 요청까지 포함한 요청 순번(전체 요청 수)에 가깝다. 중복 제거가 안 된 값이고, 품절 후 요청도 계속 증가시킨다. 따라서 실제 발급 수량과 일치하지 않는다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
중복이 제거된 issued-users Set의 크기, 즉 SCARD coupon:{eventId}:issued-users로 판단하는 것이 적절하다. 최종적으로는 DB의 coupon_issue 저장 건수가 확정 수량이다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식** | **Set + Lua Script 방식** |
| --- | --- | --- |
| 수량 판단 기준 | request-count 순번 | SCARD로 중복 제거된 통과 사용자 수 |
| 중복 사용자 방지 | 별도 Set 필요 + 원자성 보장 어려움 | SISMEMBER로 스크립트 내에서 자동 처리 |
| 장점 | 순번 계산이 단순하고 빠름 | 수량 제한 + 중복 방지를 원자적으로 한 번에 처리 |
| 단점 | 중복 요청이 자리를 차지, 명령 분리 시 Race Condition | Kafka/DB 실패 시 별도 보상 처리 필요 |
| 최종 권장 여부 | 참고용 | 최종 권장 |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
202 Accepted. 요청은 정상 접수되었지만 최종 발급 처리는 아직 완료되지 않고 비동기로 진행되기 때문이다. 
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
PENDING은 Redis 선착순 통과 + Kafka 접수 성공까지만 의미한다. Consumer의 DB 저장이 아직 남아 있고, 그 과정에서 실패할 수 있으므로 최종 발급 완료가 아니다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
Consumer가 coupon.issue.requested 메시지를 소비해 DB에 발급 기록을 저장한다. UNIQUE(event_id, user_id) 제약으로 중복 저장을 막고, 저장이 성공하면 상태가 ISSUED로 확정된다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409 Conflict. 이미 통과한 사용자와 현재 요청이 1인 1개 규칙과 충돌하는 상황이므로 409가 의미상 적절하다. 
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
이미 통과한 사용자를 다시 발행하면 Consumer가 중복 발급을 시도하게 되어 불필요한 부하와 정합성 위험이 생긴다. Redis가 중복을 걸러냈으므로 여기서 메시지를 발행하면 안 된다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
"이미 발급 요청을 완료했습니다"라는 안내와 함께, 발급 상태 조회 화면이나 마이페이지 쿠폰함으로 유도한다. 버튼을 비활성화하거나 중복 클릭을 프론트에서 막아 요청 자체를 줄이는 방안도 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
409 Conflict, 품절은 서버 오류가 아니라 정상적인 비즈니스 결과이므로 5xx는 부적절하다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
수량이 이미 소진되어 어차피 발급될 수 없는 요청이다. Kafka와 Consumer, DB로 흘려보내면 실패할 요청만 처리하는 낭비가 된다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
품절 후에는 성공 가능성이 0인 요청이 대량으로 몰린다. 이를 Redis에서 즉시 차단하면 Kafka/Consumer/DB의 부하를 크게 줄이고, 아직 처리 중인 정상 요청의 처리 속도를 지킬 수 있다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client
   |
   v
API Server
   | Redis Lua Script 실행
   v
Redis  ← user:1 SADD 완료, SUCCESS 반환
   |
   v
API Server
   | Kafka 발행 시도
   v
Kafka 장애 (발행 실패)
   |
   v
결과: Redis에는 통과 기록 있음 / Kafka에는 메시지 없음
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
issued-users Set에 해당 userId가 이미 추가되어 있다. 즉 Redis 기준으로는 통과한 사용자로 남는다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
발급 요청 메시지가 발행되지 못해 Kafka에는 해당 요청이 존재하지 않는다. Redis 통과 상태와 Kafka 사이에 불일치가 생긴다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
Consumer는 Kafka 메시지를 읽어야만 동작한다. 메시지 자체가 없으므로 DB 저장을 트리거할 방법이 없다. 결국 이 사용자는 Redis만 통과한 채 DB 발급 기록이 영영 생기지 않을 수 있다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
안 된다. PENDING은 Kafka 접수 성공을 전제로 한 응답인데, Kafka 발행이 실패했으므로 접수 자체가 되지 않았다. 사용자에게는 접수 실패 응답을 줘야 한다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
- Redis Set에서 해당 userId 제거
- Kafka 발행 재시도 
- 실패 로그 저장 및 실패/재시도 큐 적재
- 복구 배치에서 불일치 요청 재처리
- 사용자에게 접수 실패 응답 반환 후 재시도 유도
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
보상 처리(Set에서 userId 제거)도 네트워크 오류나 Redis 장애로 실패할 수 있다. 그러면 Redis에는 여전히 통과 기록이 남고 Kafka에는 메시지가 없는 불일치가 지속된다. 보상 처리 자체가 또 다른 실패 지점이 될 수 있다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
- 5주차: requestId 기반 멱등성 (재시도 시 중복 처리 방지)
- 6주차: Outbox Pattern (DB 저장과 이벤트 발행 사이 정합성 보장)
- 8주차: Retry Topic / DLQ / 보상 트랜잭션 (실패 메시지 및 Redis-DB 불일치 복구)
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 빠른 선착순/중복 판정 | 비동기 메시지 전달 및 완충 | 최종 발급 기록 저장 |
| 저장하는 데이터 | 통과 사용자 목록, 카운터 등 임시 상태 | 쿠폰 발급 요청 메시지 | 확정된 발급 기록 (coupon_issue) |
| 강점 | 빠른 조회, 원자 연산(Set/Lua/INCR) | 요청 완충, Consumer 병렬 처리 | 트랜잭션, Unique 제약으로 정합성 보장 |
| 한계 | 영구 원본 저장소로 부적합, 유실 가능 | 수량 초과/중복을 자동으로 못 막음 | 대량 동시 요청 시 Lock 경합 및 병목 |
| 실패 시 문제 | 데이터 유실, Kafka/DB와 상태 불일치 | 발행/소비 실패로 요청 유실 또는 중복 소비 | 저장 실패 시 Redis 성공과 불일치 |
| 이번 주차에서 보는 핵심 | SUCCESS/DUPLICATE/SOLD_OUT 원자 판정 | SUCCESS 요청만 발행받아 비동기 전달 | Redis가 놓친 중복을 최종 방어 |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
Redis SUCCESS = 선착순 판정 통과 
Kafka PENDING = 발급 요청 메시지가 Kafka에 접수됨 
DB ISSUED = DB에 발급 기록이 최종 저장됨
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Client → API Server → Redis (SUCCESS)
                         |
                         v
                      Kafka (PENDING) ← 사용자에게 PENDING 응답
                         |
                         v
                      Consumer → DB (ISSUED) ← 최종 발급 완료
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
1. Redis 장애나 데이터 유실 시 중복 방지 기준이 사라진다.
2. Kafka 메시지 중복 소비/Consumer 재처리로 같은 요청이 두 번 저장될 수 있다.
3. 애플리케이션 버그나 수동 배치가 Redis를 우회하면 중복 발급이 발생한다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
Kafka는 메시지를 전달 및 저장하는 역할만 한다. 모든 요청이 그대로 전달되어 수량 초과와 중복 요청이 걸러지지 않는다. 판정은 Redis와 DB가 담당해야 한다.
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis는 임시 판정 계층이라 장애/유실/우회 가능성이 있다. Kafka 중복 소비나 Consumer 재처리로 중복 저장이 시도될 수 있으므로, DB가 중복 발급을 최종 차단해야 한다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
같은 사용자가 같은 이벤트에서 두 번 저장되는 것을 DB 레벨에서 막는다. 최초 저장은 성공하고, 이미 저장된 조합의 두 번째 시도는 Unique 제약 위반으로 실패해 중복 발급이 차단된다.
```

---

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
네트워크 문제나 브라우저 재시도, 사용자의 반복 클릭으로 같은 요청이 반복될 수 있다. Kafka Consumer도 같은 메시지를 다시 읽을 수 있다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis 중복 체크는 같은 사용자가 이 이벤트를 이미 통과했는가를 본다. requestId 멱등성은 동일한 하나의 요청이 여러 번 처리되어도 결과가 한 번만 반영되는가를 본다. 각각은 사용자 단위, 요청 단위 방어이다.
```

---

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
DB 저장과 Kafka 발행은 서로 다른 시스템이라 하나의 트랜잭션으로 묶이지 않는다. DB 커밋 후 Kafka 발행 직전에 장애가 나면, DB에는 기록이 있는데 후속 서비스는 그 사실을 모르는 불일치가 생긴다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
발급 기록과 outbox_event를 같은 트랜잭션으로 DB에 저장한 뒤, 별도 Publisher가 outbox_event를 읽어 Kafka로 발행한다.
```

---

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
Coupon Service가 후속 서비스를 직접 호출하면 결합도가 높아진다. 알림 서비스가 느려지거나 장애가 나면 쿠폰 발급까지 영향이 미칠 수 있다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
쿠폰 발급 완료 이벤트를 발행하고 각 서비스가 이를 구독하면, 서비스 간 결합도가 낮아진다. 알림 실패가 발급 실패로 이어지지 않고, 각 서비스가 독립적으로 확장/조회 모델을 가질 수 있다.
```

---

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis에는 통과로 남아 있는데 DB에는 발급 기록이 없는 정합성 불일치다. 사용자는 통과했다고 여기지만 실제 쿠폰함에는 반영되지 않는다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
일시적 실패(DB 순간 장애, 네트워크 오류)는 Retry Topic으로 재시도하고, 영구 실패는 DLQ로 격리한다. 실패 유형을 나눠야 무한 재시도에 빠지지 않으면서 요청 유실을 막을 수 있다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
- Redis SUCCESS 이후 Kafka 발행 실패 -> Redis 통과 상태 롤백
- Redis SUCCESS/Kafka PENDING인데 DB 저장이 끝내 실패 -> Redis-DB 불일치 복구
- 운영자가 실패 메시지를 확인하고 수동 재처리하는 과정
```
