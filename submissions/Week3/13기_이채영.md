## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | 로그인 확인
  | 이벤트 시간 확인
  | Redis 선착순 / 중복 판정
  v
Redis
  |
  | SUCCESS / DUPLICATE / SOLD_OUT
  v
API Server
  |
  | SUCCESS인 경우만 Kafka 발행
  v
Kafka Producer
  |
  | coupon.issue.requested
  v
Coupon Issue Consumer
  |
  | 최종 쿠폰 발급 기록 저장
  v
  DB
```

### **2. Redis의 역할**

```
- 쿠폰 발급 요청이 선착순 조건을 만족하는지 빠르게 판정한다.
- 같은 사용자의 중복 요청을 Redis Set을 이용해 차단한다.
- 쿠폰 수량이 모두 소진되었는지 확인한다.
- SUCCESS, DUPLICATE, SOLD_OUT 중 하나의 결과를 반환한다.
- 성공한 요청만 다음 단계(Kafka)로 전달하여 불필요한 요청을 줄인다.
```

### **3. Kafka의 역할**

```
- Redis를 통과한 요청만 비동기적으로 전달한다.
- 요청이 한 번에 몰려도 메시지를 저장하여 Consumer가 순차적으로 처리할 수 있도록 한다.
- API Server와 Consumer를 분리하여 시스템의 안정성과 확장성을 높인다.
- 최종 쿠폰 발급 처리를 Consumer에게 위임한다.
```

### **4. DB의 역할**

```
- 최종 쿠폰 발급 기록을 영구 저장한다.
- 쿠폰 발급의 최종 성공 여부를 관리한다.
- 발급 내역을 조회하거나 관리하는 기준 데이터가 된다.
- Redis의 임시 데이터와 달리 영구적인 원본 데이터를 보관한다.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
- 실패할 요청까지 Kafka에 전달하는 것을 방지할 수 있다.
- Consumer가 불필요한 요청을 처리하지 않아도 된다.
- DB까지 전달되는 요청 수를 크게 줄일 수 있다.
- 쿠폰이 품절된 이후의 요청을 즉시 차단할 수 있다.
- 같은 사용자의 중복 요청이 Kafka와 DB까지 전달되는 것을 막을 수 있다.
- 시스템 전체의 성능과 처리 효율을 높일 수 있다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
- Kafka는 쿠폰 발급 요청을 비동기적으로 전달하는 역할을 한다.
- 하지만 Kafka는 쿠폰 수량 초과 발급을 직접 막아주지 않는다.
- Kafka는 같은 사용자의 중복 요청도 자동으로 차단하지 않는다.
- 따라서 Redis 없이 Kafka와 DB만 사용하면 모든 요청이 Consumer와 DB까지 도달할 수 있다.
- 이 경우 DB가 수량 확인, 중복 확인, 발급 기록 저장을 모두 부담하게 된다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
- 쿠폰 수량은 1,000개인데 요청이 100,000건 들어오면 대부분의 요청은 실패할 가능성이 높다.
- 하지만 Redis가 없다면 실패할 요청도 Kafka에 쌓일 수 있다.
- Consumer는 성공 가능성이 낮은 요청까지 모두 소비해야 한다.
- DB는 100,000건에 가까운 요청에 대해 수량 확인과 중복 확인을 수행해야 한다.
- 결과적으로 Kafka 지연, Consumer 부하, DB 부하가 커질 수 있다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
- 이미 쿠폰이 모두 소진되었는데도 요청이 Kafka에 계속 쌓일 수 있다.
- Consumer는 품절된 요청을 계속 읽고 처리해야 한다.
- DB는 실패할 요청에 대해서도 계속 조회와 검증을 수행해야 한다.
- 사용자는 빠르게 품절 응답을 받지 못하고 불필요하게 기다릴 수 있다.
- 시스템 자원이 실제 성공 가능성이 없는 요청에 낭비된다.
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
- 같은 사용자의 중복 요청이 Kafka에 여러 번 발행될 수 있다.
- Consumer는 같은 사용자의 요청을 여러 번 처리하게 된다.
- DB에서 중복 여부를 계속 확인해야 하므로 부하가 증가한다.
- 중복 방어가 제대로 되어 있지 않으면 같은 사용자가 쿠폰을 여러 번 발급받는 문제가 생길 수 있다.
- 따라서 중복 요청은 최대한 앞단에서 빠르게 차단하는 것이 좋다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
- 이미 쿠폰 발급 요청에 성공한 사용자의 중복 요청을 차단할 수 있다.
- 쿠폰 수량이 모두 소진된 이후의 요청을 차단할 수 있다.
- 선착순 수량 안에 들지 못한 요청을 차단할 수 있다.
- 실패할 가능성이 높은 요청을 Kafka와 DB까지 보내지 않을 수 있다.
- 결과적으로 Redis는 DB 앞단에서 빠르게 요청을 걸러주는 필터 역할을 한다.
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| Redis Key                       | 자료구조             | 저장하는 값                    | 필요한 이유                     |
|---------------------------------|------------------|---------------------------|----------------------------|
| `coupon:{eventId}:issued-users` | Set              | 선착순 통과한 사용자 ID            | 중복 요청 방지 및 현재 발급된 사용자 수 확인 |
| `coupon:{eventId}:metadata`     | Hash (또는 String) | 쿠폰 수량, 이벤트 시작/종료 시간 등의 정보 | 이벤트 정보를 빠르게 조회하기 위해 사용     |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
- Redis Set 형태로 선착순 판정을 통과한 사용자 ID가 저장된다.
- 같은 사용자 ID는 한 번만 저장되므로 중복 요청을 방지할 수 있다.
- SCARD 명령어를 이용하면 현재 통과한 사용자 수를 확인할 수 있다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
- INCR 명령어를 이용하여 요청 순번을 관리한다.
- 각 요청마다 고유한 요청 번호를 부여할 수 있다.
- 요청 순번이 쿠폰 수량을 초과하면 빠르게 품절을 판단할 수 있다.
- 하지만 같은 사용자의 중복 요청도 카운트되므로 최종 발급 수량으로 사용할 수는 없다.
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
- 이벤트 종료 후 불필요한 데이터를 자동으로 삭제할 수 있다.
- Redis 메모리 사용량을 줄일 수 있다.
- 오래된 이벤트 데이터가 계속 남아있는 것을 방지할 수 있다.
- 별도의 삭제 작업 없이 자동으로 Key를 정리할 수 있다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
- 이벤트 종료 후 일정 시간이 지나면 TTL을 이용해 자동 삭제한다.
- 필요하다면 배치 작업을 이용해 만료된 이벤트의 Redis Key를 함께 정리한다.
- Redis는 임시 데이터 저장소이므로 이벤트가 종료된 Key는 계속 유지하지 않는다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
- Redis Set은 동일한 값을 중복으로 저장하지 않는 자료구조이다.
- 이를 이용하면 같은 사용자가 여러 번 쿠폰 발급을 요청해도 한 번만 저장된다.
- 중복 요청을 빠르게 차단할 수 있으며, 별도의 복잡한 중복 검사 로직이 필요하지 않다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
- SADD의 결과가 1이면 새로운 사용자가 Set에 정상적으로 추가되었다는 의미이다.
- SADD의 결과가 0이면 이미 해당 사용자가 Set에 존재하여 추가되지 않았다는 의미이다.
- 따라서 반환값만으로도 새로운 요청인지 중복 요청인지 빠르게 판단할 수 있다.
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
user:1 첫 번째 요청:
-> SADD coupon:100:issued-users user:1
-> 반환값 : 1
-> Set에 추가되고 선착순 판정 통과

user:1 두 번째 요청:
-> SADD coupon:100:issued-users user:1
-> 반환값 : 0
-> 이미 존재하는 사용자이므로 중복 요청으로 차단
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
Redis

coupon:100:issued-users

+-----------+
| user:1    |
| user:5    |
| user:20   |
| user:77   |
| ...       |
+-----------+

같은 user:1을 다시 추가해도 Set에는 한 번만 저장된다.
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
- 아니다.
- Redis Set은 중복 요청을 방지하는 데에는 적합하지만, 쿠폰 수량 제한까지 자동으로 처리하지는 않는다.
- 현재 Set의 크기를 확인하여 수량을 비교하는 과정이 추가로 필요하다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
- `SCARD` 명령어를 사용해 현재 선착순을 통과한 사용자 수를 확인할 수 있다.
- `SCARD`는 Set에 저장된 고유한 요소의 개수를 반환한다.
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
- 먼저 SCARD 명령어로 현재 Set에 저장된 사용자 수를 확인한다.
- 현재 통과 사용자 수가 쿠폰 제한 수량보다 작으면 발급 가능하다고 판단한다.
- 그 다음 SADD 명령어로 사용자를 Set에 추가한다.
- 겉으로는 정상적인 흐름처럼 보이지만, SCARD와 SADD가 분리되어 있기 때문에 동시에 여러 요청이 들어오면 문제가 생길 수 있다.
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

시간 흐름
--------------------------------------------------
user:A -> SCARD 조회 -> 999 확인
user:B -> SCARD 조회 -> 999 확인

user:A -> 999 < 1000 이므로 발급 가능 판단
user:B -> 999 < 1000 이므로 발급 가능 판단

user:A -> SADD coupon:100:issued-users user:A 성공
user:B -> SADD coupon:100:issued-users user:B 성공

결과
--------------------------------------------------
최종 Set 크기: 1,001명
쿠폰 제한 수량보다 1명 더 많이 통과
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
- userA와 userB가 거의 동시에 `SCARD`를 실행했기 때문이다.
- 두 요청 모두 SADD가 실행되기 전의 Set 크기인 999를 조회할 수 있다.
- 따라서 두 요청 모두 아직 쿠폰이 1개 남아 있다고 판단한다.
- 실제로는 한 명만 통과해야 하지만 두 요청이 같은 이전 상태를 보고 발급 가능하다고 판단하게 된다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
- SCARD로 수량을 확인하는 작업과 SADD로 사용자를 추가하는 작업이 하나로 묶여 있지 않기 때문이다.
- user:A가 SCARD를 확인한 뒤 아직 SADD를 실행하기 전에 user:B도 같은 수량을 확인할 수 있다.
- 이후 두 요청이 각각 SADD를 성공하면 Set에 두 명이 모두 추가된다.
- 그 결과 제한 수량은 1,000개인데 실제 통과 사용자는 1,001명이 될 수 있다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
- 핵심 원인은 수량 확인과 사용자 추가가 분리되어 있다는 점이다.
- 여러 Redis 명령을 애플리케이션에서 따로 실행하면 그 사이에 다른 요청이 끼어들 수 있다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
- 사용자가 이미 Set에 존재하는지 확인하는 작업
- 현재 Set 크기가 쿠폰 제한 수량보다 작은지 확인하는 작업
- 조건을 만족하면 사용자를 Set에 추가하는 작업
- 위 작업들이 하나의 원자적 흐름으로 처리되어야 한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER를 이용하여 사용자가 이미 쿠폰을 발급받았는지 확인한다.

2. SCARD를 이용하여 현재 선착순 통과 사용자 수를 확인한다.

3. 쿠폰 수량이 남아 있다면 SADD를 이용하여 사용자를 Set에 추가한다.
```

### **2. Lua Script 처리 흐름 다이어그램**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Lua Script 실행
  v
Redis
  |
  | 1. SISMEMBER (중복 확인)
  | 2. SCARD (수량 확인)
  | 3. SADD (사용자 추가)
  |
  +-- SUCCESS
  +-- DUPLICATE
  +-- SOLD_OUT
  |
  v
API Server
```

### **3. Lua Script 반환값 설계**

| 반환값       | 의미                   | API Server 처리                         |
|-----------|----------------------|---------------------------------------|
| SUCCESS   | 선착순 판정을 통과한 사용자      | Kafka에 쿠폰 발급 요청 메시지를 발행한다.            |
| DUPLICATE | 이미 쿠폰 발급 요청에 성공한 사용자 | 중복 요청 응답을 반환하고 Kafka에는 메시지를 발행하지 않는다. |
| SOLD_OUT  | 쿠폰 수량이 모두 소진된 상태     | 품절 응답을 반환하고 Kafka에는 메시지를 발행하지 않는다.    |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
- SISMEMBER, SCARD, SADD를 각각 따로 실행하면 중간에 다른 요청이 끼어들 수 있다.
- Lua Script는 여러 Redis 명령을 하나의 원자적인 작업으로 실행한다.
- 따라서 중복 확인과 수량 확인, 사용자 추가가 모두 하나의 흐름으로 처리된다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
- Lua Script의 SUCCESS는 Redis의 선착순 판정을 통과했다는 의미일 뿐이다.
- 이후 API Server가 Kafka에 메시지를 정상적으로 발행해야 한다.
- Consumer가 Kafka의 메시지를 읽어 DB에 최종 발급 기록을 저장해야 쿠폰 발급이 완료된다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
- 쿠폰 발급 요청이 들어올 때마다 Redis의 INCR 명령어로 요청 카운터를 1 증가시킨다.
- 증가된 값은 해당 요청이 몇 번째로 들어온 요청인지 나타낸다.
- 증가된 값이 쿠폰 제한 수량 이하이면 선착순 통과 후보로 본다.
- 증가된 값이 쿠폰 제한 수량을 초과하면 SOLD_OUT으로 처리한다.
- 중복 사용자 확인을 위해서는 별도의 Set을 함께 사용할 수 있다.
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
- INCR는 Redis에서 원자적으로 동작한다.
- 동시에 여러 요청이 들어와도 각 요청은 서로 다른 숫자를 받는다.
- ex. 동시에 요청 A, B, C가 들어와도 각각 1, 2, 3과 같은 고유한 순번을 받게 된다.
- 요청 순서를 빠르게 계산하는 데 사용할 수 있다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
- INCR는 사용자 중복 요청을 자동으로 막아주지 않는다.
- 같은 사용자가 여러 번 요청해도 요청할 때마다 카운터가 증가한다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
- user:1이 버튼을 여러 번 누르면서 요청 카운터가 1, 2, 3까지 증가한다.
- 쿠폰 수량이 3개이므로 user:1의 세 요청이 모두 선착순 자리 안에 들어온 것처럼 보인다.
- 이후 user:2가 요청하면 INCR 결과가 4가 되어 품절로 처리될 수 있다.
- 실제로는 user:1 한 명만 통과해야 하지만, 중복 요청이 선착순 자리를 여러 개 소비한 것이다.
- 이처럼 INCR만 사용하면 공정한 선착순 판정이 어렵다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
쿠폰 수량: 3개

request-count 기준 선착순 자리

+---------+---------+---------+---------+
| 순번 1   | 순번 2   | 순번 3   | 순번 4  |
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
| 통과     | 중복     | 중복     | 품절    |
+---------+---------+---------+---------+

문제: user:1의 중복 요청이 선착순 자리를 여러 개 차지했다.
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
- request-count는 쿠폰 발급에 성공한 사용자 수가 아니라 전체 요청 수에 가깝다.
- 같은 사용자가 여러 번 요청해도 매번 증가한다.
- 품절 이후 실패 요청이 들어와도 카운터는 계속 증가할 수 있다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
- 실제 통과 사용자 수는 중복 제거된 사용자 수를 기준으로 판단하는 것이 더 적절하다.
- Redis Set에 저장된 사용자 ID 개수를 기준으로 판단할 수 있다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| 구분        | INCR 기반 방식              | Set + Lua Script 방식          |
|-----------|-------------------------|------------------------------|
| 수량 판단 기준  | 요청 카운터 값                | Set에 저장된 중복 제거 사용자 수         |
| 중복 사용자 방지 | 기본적으로 보장하지 않음           | Set으로 중복 사용자 방지 가능           |
| 장점        | 구현이 단순하고 요청 순번 계산이 빠름   | 수량 제한과 중복 방지를 함께 처리 가능       |
| 단점        | 중복 요청이 선착순 자리를 차지할 수 있음 | Lua Script 설계와 장애 상황 처리가 필요함 |
| 최종 권장 여부  | 참고 방식으로 이해하는 것이 적절함     | 선착순 쿠폰 판정의 기본 구조로 더 적절함      |

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
- HTTP Status Code는 202 Accepted를 사용한다.
- 요청이 정상적으로 접수되었지만, 최종 쿠폰 발급 처리는 아직 완료되지 않았기 때문이다.
- Redis 판정은 통과했고 Kafka 발행도 성공했지만, Consumer가 DB 저장을 완료한 상태는 아니다.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
- PENDING은 쿠폰 발급 요청이 접수되었다는 의미이다.
- Redis에서 SUCCESS가 나왔다는 것은 선착순 판정을 통과했다는 뜻이다.
- Kafka 발행 성공은 Consumer가 처리할 메시지가 Topic에 들어갔다는 뜻이다.
- 하지만 아직 Consumer가 메시지를 읽고 DB에 쿠폰 발급 기록을 저장한 것은 아니다.
- 최종 쿠폰 발급 성공은 DB에 발급 기록이 저장된 뒤 확정된다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```

- Consumer는 coupon.issue.requested Topic에서 쿠폰 발급 요청 메시지를 읽는다.
- 메시지에 포함된 eventId, userId, requestId 등을 확인한다.
- DB에서 최종 중복 여부와 쿠폰 발급 가능 여부를 검증한다.
- 문제가 없으면 DB에 쿠폰 발급 기록을 저장한다.
- 저장이 완료되면 해당 요청의 상태를 ISSUED로 변경한다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
- HTTP Status Code는 `409 Conflict`를 사용할 수 있다.
- 같은 사용자가 이미 해당 이벤트에 대해 쿠폰 발급 요청을 완료했기 때문이다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
- 이미 Redis에서 중복 요청으로 판정된 요청이기 때문이다.
- Kafka에 메시지를 발행하면 Consumer가 처리하지 않아도 되는 중복 요청을 소비하게 된다.
- 같은 사용자의 중복 발급 시도가 여러 번 DB까지 전달되는 것을 막기 위해 Kafka에 발행하지 않는다.
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
- 사용자에게 이미 요청이 접수되었다는 안내 메시지를 보여줄 수 있다.
- 발급 결과가 아직 처리 중이라면 마이페이지나 발급 상태 조회 화면으로 이동시킬 수 있다.
- 버튼을 여러 번 누르지 않도록 발급 요청 후 버튼을 비활성화할 수 있다.
- “이미 쿠폰 발급 요청이 접수되었습니다. 잠시 후 발급 결과를 확인해 주세요.”와 같은 메시지를 제공할 수 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
- HTTP Status Code는 409 Conflict를 사용할 수 있다.
- 사용자의 요청 형식은 올바르지만, 쿠폰 수량이 모두 소진되어 더 이상 발급할 수 없는 상태이기 때문이다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
- 쿠폰이 이미 품절된 상태이기 때문이다.
- Kafka에 메시지를 발행해도 Consumer 단계에서 최종적으로 실패할 가능성이 높다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
- 품절 이후에도 요청이 계속 들어오면 대부분 실패할 요청이다.
- 이러한 요청을 Kafka와 DB까지 보내면 시스템 자원이 낭비된다.
- Redis에서 빠르게 SOLD_OUT을 반환하면 사용자는 즉시 결과를 알 수 있다.
- Kafka, Consumer, DB는 실제 처리해야 할 요청에 집중할 수 있다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Redis Lua Script 실행
  v
Redis
  |
  | SUCCESS 반환
  v
API Server
  |
  | Kafka 메시지 발행 시도
  v
Kafka
  |
  | Kafka 장애 발생
  x
메시지 발행 실패
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
- Redis Set에는 해당 사용자의 ID가 저장된 상태로 남아 있을 수 있다.
- ex. coupon:100:issued-users에 user:1이 추가되어 있을 수 있다.
- Redis 입장에서는 이 사용자가 선착순 판정을 통과한 것으로 기록된다.
- 하지만 Kafka 발행이 실패했기 때문에 실제 발급 처리는 뒤로 진행되지 않는다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
- Kafka에는 해당 쿠폰 발급 요청 메시지가 저장되지 않는다.
- coupon.issue.requested Topic에 메시지가 없으므로 Consumer가 읽을 데이터가 없다.
- Redis에서는 성공으로 기록되었지만 Kafka에는 요청이 없는 상태가 된다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
- Consumer는 Kafka Topic에 저장된 메시지를 소비해서 동작한다.
- Kafka 발행이 실패하면 Topic에 해당 요청 메시지가 존재하지 않는다.
- 따라서 Consumer는 해당 요청이 있었다는 사실을 알 수 없다.
- 결과적으로 DB에 쿠폰 발급 기록을 저장할 수도 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
- 이 경우 사용자에게 PENDING 응답을 주면 안 된다.
- PENDING은 Redis 판정 통과 후 Kafka에 메시지가 정상적으로 접수되었음을 의미해야 한다.
- Kafka 발행에 실패했다면 Consumer가 처리할 수 없기 때문에 실제 발급이 진행되지 않는다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
- Kafka 발행을 재시도한다.
- 일정 횟수 이상 재시도해도 실패하면 실패 로그를 저장한다.
- Redis Set에서 해당 userId를 제거하여 다시 요청할 수 있도록 한다.
- 요청 상태 테이블을 둔다면 해당 요청을 FAILED 상태로 기록한다.
- 복구 배치가 실패 로그를 읽고 Kafka 메시지를 다시 발행하도록 한다.
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
- Kafka 발행 실패 후 Redis에서 userId를 제거하려고 할 때 Redis 네트워크 오류가 발생할 수 있다.
- Redis 장애로 인해 SREM 명령어가 실패할 수 있다.
- API Server가 보상 처리 도중 장애로 종료될 수도 있다.
- 이 경우 Redis에는 여전히 사용자가 통과한 상태로 남고, Kafka에는 메시지가 없는 불일치 상태가 계속될 수 있다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
- requestId 기반 멱등성 처리와 연결된다.
- Outbox Pattern과 연결된다.
- Kafka 발행 재시도 전략과 연결된다.
- Retry Topic, DLQ 처리와 연결된다.
- 보상 트랜잭션과 복구 배치 설계와 연결된다.
- DB Unique Key를 통한 최종 중복 방어와도 연결된다.
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| 구분            | Redis                  | Kafka                           | DB                     |
|---------------|------------------------|---------------------------------|------------------------|
| 주 역할          | 선착순 판정 및 중복 요청 방지      | 쿠폰 발급 요청을 비동기적으로 전달             | 최종 쿠폰 발급 기록 저장         |
| 저장하는 데이터      | 통과 사용자 목록, 임시 상태       | 쿠폰 발급 요청 메시지                    | 쿠폰 발급 기록, 사용자 정보       |
| 강점            | 빠른 조회와 원자적 연산          | 대량의 요청을 안정적으로 처리                | 데이터 영구 저장 및 정합성 보장     |
| 한계            | 최종 발급 기록 저장소로 사용하기 어렵다 | 수량 초과나 중복 발급을 직접 막지 못한다         | 대량 요청이 몰리면 부하가 커질 수 있다 |
| 실패 시 문제       | Redis와 DB 상태가 달라질 수 있다 | 메시지가 전달되지 않아 Consumer가 처리할 수 없다 | 최종 쿠폰 발급 기록이 저장되지 않는다  |
| 이번 주차에서 보는 핵심 | 선착순 판정과 중복 요청 차단       | 성공한 요청만 Consumer에게 전달           | 최종 발급 기록 저장            |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
- Redis SUCCESS : Redis에서 선착순 판정을 통과한 상태이다.
- Kafka PENDING : 쿠폰 발급 요청 메시지가 Kafka에 정상적으로 저장되어 Consumer가 처리할 준비가 된 상태이다.
- DB ISSUED : Consumer가 DB에 쿠폰 발급 기록을 저장하여 최종 발급이 완료된 상태이다.
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Redis Lua Script
  v
Redis
  |
  | SUCCESS
  v
API Server
  |
  | Kafka 발행 성공
  v
Kafka
  |
  | PENDING
  v
Consumer
  |
  | DB 저장 성공
  v
DB
  |
  | ISSUED (최종 쿠폰 발급 완료)
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
- Redis 장애나 데이터 유실이 발생하면 중복 요청을 제대로 막지 못할 수 있다.
- Consumer가 같은 메시지를 여러 번 처리하는 경우 중복 발급이 발생할 수 있다.
- Redis와 DB의 데이터가 일시적으로 불일치할 수도 있다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
- Kafka는 요청을 전달하는 역할만 수행한다.
- 쿠폰 수량이 남아 있는지 판단하지 않는다.
- 같은 사용자의 중복 요청도 자동으로 차단하지 않는다.
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
- Redis는 선착순 판정을 빠르게 수행하기 위한 임시 저장소이다.
- 장애나 데이터 불일치가 발생할 가능성이 있다.
- DB는 최종 데이터를 관리하는 저장소이므로 마지막까지 중복을 방지해야 한다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
- 같은 사용자가 동일한 이벤트의 쿠폰을 여러 번 발급받는 것을 방지한다.
- Consumer가 같은 메시지를 다시 처리하더라도 중복 저장을 막을 수 있다.
- Redis 장애가 발생하더라도 최종 중복 발급을 방지할 수 있다.
```

---

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
- 사용자가 버튼을 여러 번 클릭할 수 있다.
- 네트워크 오류로 인해 요청이 재전송될 수 있다.
- Kafka Consumer가 메시지를 다시 처리할 수 있다.
- 서버 장애 이후 재시도가 발생할 수도 있다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
- Redis는 같은 사용자의 중복 요청을 빠르게 차단하는 역할을 한다.
- requestId는 동일한 요청이 여러 번 처리되는 것을 방지한다.
- Redis는 사용자 기준의 중복 검사이고, requestId는 요청 자체의 중복 처리이다.
```

---

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
- DB 저장 이후 Kafka 장애가 발생할 수 있다.
- 네트워크 문제로 메시지 발행이 실패할 수 있다.
- 이 경우 DB에는 발급 기록이 있지만 Kafka에는 이벤트가 없는 상태가 된다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
- DB 저장과 이벤트 발행의 정합성을 보장하기 위해 사용한다.
- 먼저 DB와 Outbox 테이블에 함께 저장한 뒤 이벤트를 발행한다.
- 이벤트 발행이 실패하더라도 Outbox를 이용해 재발행할 수 있다.
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
- 서비스 간 의존성이 높아진다.
- 하나의 서비스가 장애가 나면 전체 처리 과정이 영향을 받을 수 있다.
- 응답 시간이 길어질 수 있다.
- 시스템 확장이 어려워질 수 있다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
- 각 서비스가 독립적으로 동작할 수 있다.
- 장애가 발생해도 다른 서비스에 미치는 영향을 줄일 수 있다.
- 새로운 기능을 쉽게 추가할 수 있다.
- 시스템 확장성과 유지보수성이 향상된다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
- Redis에는 성공으로 기록되지만 DB에는 발급 기록이 저장되지 않는다.
- 사용자는 쿠폰을 발급받지 못했는데 Redis에서는 이미 통과한 사용자로 남을 수 있다.
- Redis와 DB 사이의 데이터 불일치가 발생한다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
- 일시적인 장애가 발생했을 때 자동으로 재시도하기 위해 필요하다.
- 반복적으로 실패하는 메시지는 DLQ에 저장하여 별도로 관리한다.
- 정상 메시지 처리에 영향을 주지 않으면서 장애를 처리할 수 있다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
- Redis에서는 SUCCESS가 반환되었지만 Kafka 발행이 실패한 경우
- Redis에는 사용자가 저장되었지만 DB 저장이 실패한 경우
- 이처럼 일부 단계만 성공하여 데이터가 불일치할 때 보상 처리가 필요하다.
- ex. Redis에서 해당 사용자를 제거하거나, 실패 로그를 남기고 재처리를 수행할 수 있다.
```
