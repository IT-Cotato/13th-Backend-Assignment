![alt text](image-4.png)

### 2. Redis의 역할

DB와 Kafka 앞단에서 요청의 성공 가능성을 1차적으로 필터링합니다. 단일 스레드 기반의 인메모리 연산을 통해 쿠폰 수량 초과 여부와 사용자 중복 여부를 밀리초(ms) 단위로 빠르게 판정합니다.

### 3. Kafka의 역할

Redis의 선착순 판정을 무사히 통과한 '유효한 요청'들만 모아서 안전하게 비동기 대기열에 보관하고 Consumer로 전달하는 버퍼 역할을 합니다.

### 4. DB의 역할

Consumer의 비즈니스 로직에 따라 최종적인 발급 결과를 영구 저장하며, `UNIQUE` 제약조건 등을 통해 분산 환경의 예외 상황(Redis 유실 등) 속에서도 무결성을 지키도록 마지막으로 막는 역할을 합니다.

### 5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유

10만 건의 요청 중 실제 발급이 가능한 1,000건 외의 99,000건은 실패할 요청입니다. 이 실패할 요청들까지 모두 Kafka와 DB로 흘려보내면 불필요한 디스크 I/O와 네트워크 트래픽 낭비가 발생하므로, 앞단에서 차단해야 합니다.

## 과제 2. Redis가 필요한 이유 설명하기

### 1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점

모든 요청이 여과 없이 DB까지 도달하기 때문에, DB의 락 경합이 심해지고 리소스가 빠르게 고갈됩니다.

### 2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?

유효하지 않은 요청(이미 품절, 중복 유저)을 검증하기 위해 Consumer가 끊임없이 DB에 조회/저장 쿼리를 날리게 되며, 이는 전체 시스템의 응답 지연과 타임아웃 장애로 이어집니다.

### 3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?

품절 사실을 뒤늦게 파악하게 되어 수만 명의 사용자에게 헛된 대기 시간(Lag)을 유발하고, 불필요한 컴퓨팅 리소스(CPU, Memory)를 낭비합니다.

### 4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?

Kafka 대기열과 Consumer 리소스를 한 명의 유저가 독점하게 되며, DB 레벨의 제약조건에 도달해서야 예외가 발생하므로 롤백 리소스가 낭비됩니다.

### 5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?

이미 발급 대기열에 등록된 사용자의 중복 요청(DUPLICATE)과 쿠폰 수량이 1,000개를 초과한 이후의 품절 요청(SOLD_OUT)을 차단할 수 있습니다.

## 과제 3. Redis Key와 자료구조 설계하기

### 1. Redis Key 목록

| Redis Key | 자료구조 | 저장하는 값 | 필요한 이유 |
| --- | --- | --- | --- |
| `coupon:{eventId}:issued-users` | Set | 판정을 통과한 `userId` | 중복 사용자 O(1) 확인 및 `SCARD`를 통한 정확한 통과자 수 제한 |
| `coupon:{eventId}:metadata` | String/Hash | 발급 제한 수량 (limit) | Lua Script 내에서 하드코딩을 피하고 이벤트별 제한 수량을 유연하게 참조하기 위함 |

### 2. 이벤트 ID가 100일 때 실제 Redis Key 예시

* `coupon:100:issued-users`
* `coupon:100:metadata`

### 3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?

선착순 판정을 성공적으로 통과한 사용자들의 고유 ID(`user:1`, `user:2`) 집합이 저장됩니다.

### 4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?

현재까지 인입된 누적 요청의 순번(Sequence)을 기록하는 역할을 합니다. (단, 본 설계에서는 Set의 `SCARD`로 대체합니다.)

### 5. Redis Key에 TTL이 필요한 이유는 무엇인가?

Redis는 비용이 큰 인메모리(RAM) 저장소이므로, 이벤트 종료 후 불필요해진 임시 판정 데이터를 메모리에서 해제하여 공간을 확보해야 합니다.

### 6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?

Key 생성 시점(또는 이벤트 세팅 시점)에 해당 이벤트 종료 시간에 여유 시간(예: 1일)을 더해 `EXPIRE` 설정(TTL)을 걸어두어 자동 소멸되도록 합니다.

## 과제 4. Redis Set 기반 중복 요청 방지 설계하기

### 1. Redis Set을 사용하는 이유

Set은 중복된 값을 허용하지 않는 고유 집합 자료구조이므로, 동일 사용자가 여러 번 요청하더라도 멤버 존재 여부를 O(1) 성능으로 검증하고 추가할 수 있습니다.

### 2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?

* `1`: Set에 존재하지 않던 새로운 값이 성공적으로 추가되었음.
* `0`: Set에 이미 해당 값이 존재하여 추가되지 않았음 (중복 차단).

### 3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?

* **user:1 첫 번째 요청:** `SADD` 실행 시 결과 `1`이 반환되어 통과.
* **user:1 두 번째 요청:** `SADD` 실행 시 이미 값이 있어 결과 `0`이 반환되어 차단.

### 4. Redis Set 구조를 그림으로 표현하기

```text
Key: coupon:100:issued-users
+------------------+
| user:100         |
| user:250         |
| user:999         |
+------------------+

```

### 5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?

아닙니다. Set은 중복 삽입만 막아줄 뿐 요소의 총개수를 제한하는 기능은 없으므로, 추가 전에 현재 크기를 확인하는 로직이 동반되어야 합니다.

### 6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?

`SCARD` 명령어 (Set의 원소 개수 반환)

## 과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기

### 1. `SCARD 후 SADD` 방식의 처리 흐름

현재 통과자 수를 조회(`SCARD`)하고, 앱 서버로 반환하여 크기를 비교(if)한 뒤, 제한을 넘지 않았을 때 추가(`SADD`)하는 흐름입니다.

### 2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램

![alt text](image-3.png)

### 3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?

사용자 A의 `SADD`가 실행되기 직전의 찰나의 순간에 사용자 B가 `SCARD`를 실행하면, B 역시 아직 999명이라고 조회하기 때문입니다.

### 4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유

조회(Check)와 쓰기(Act) 명령어가 분리되어 있어, 두 명령 사이에 다른 스레드의 Context Switch가  발생하여 원자성이 깨졌기 때문입니다.

### 5. 이 문제의 핵심 원인은 무엇인가?

네트워크를 타는 다수의 명령어가 동기화 제어 없이 파편화되어 실행되는 Check-Then-Act 동시성 문제입니다.

### 6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?

`SCARD`(현재 수량 확인)와 `SADD`(데이터 추가)가 단일 트랜잭션처럼 중간 간섭 없이 하나로 묶여야 합니다.

## 과제 6. Redis Lua Script 기반 원자적 처리 설계하기

### 1. Lua Script로 묶어야 하는 작업 목록

1. `SISMEMBER` (중복 유저 확인)
2. `SCARD` (현재 통과자 수 확인)
3. `SADD` (유저 추가)

### 2. Lua Script 처리 흐름 다이어그램

![alt text](image-2.png)

### 3. Lua Script 반환값 설계

| 반환값 | 의미 | API Server 처리 |
| --- | --- | --- |
| `SUCCESS` | 선착순 및 중복 검증 통과 | Kafka에 발급 요청 메시지 발행 후 PENDING 반환 |
| `DUPLICATE` | 이미 발급 요청이 접수된 유저 | 409 Conflict 등의 응답 반환 |
| `SOLD_OUT` | 준비된 수량 도달 | 403 Forbidden 등의 품절 응답 반환 |

### 4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?

Redis는 싱글 스레드 이벤트 루프 모델이므로, Lua Script가 실행되는 동안에는 다른 어떠한 클라이언트의 명령어 처리도 블로킹(대기)되어 완벽한 원자성이 보장되기 때문입니다.

### 5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유

Redis는 "수량 내에 들어왔다"는 자격을 부여했을 뿐, 실제 RDBMS에 데이터가 적재되는 물리적 쓰기 작업은 아직 수행되지 않았기 때문입니다.

## 과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기

### 1. INCR 기반 방식의 기본 흐름

요청이 올 때마다 `INCR` 명령어로 카운터를 1씩 증가시키고 반환받은 숫자가 1,000 이하면 통과, 초과면 차단하는 방식입니다.

### 2. `INCR` 명령어가 보장하는 것은 무엇인가?

해당 키 값의 숫자가 동시성 이슈 없이 **원자적으로 1씩 증가하며, 각각 고유한 순번을 반환한다는 점**을 보장합니다.

### 3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?

그 순번을 발급받은 자가 이전에 이미 순번을 발급받았던 적이 있는지(유저 중복 여부)는 판별하거나 막아주지 못합니다.

### 4. 아래 상황에서 어떤 문제가 생기는지 설명하기

```text
user:1이 고의 또는 오류로 연속 클릭하여 3자리를 모두 독식해 버렸습니다. 정작 정상적으로 참여한 user:2는 카운터 초과로 쿠폰을 받지 못하는 치명적인 불공정 현상이 발생합니다.

```

### 5. 위 상황을 다이어그램으로 표현하기

```text
[Counter: limit 3]
순번 1 ➔ user:1 (통과)
순번 2 ➔ user:1 (통과, 실제론 낭비됨)
순번 3 ➔ user:1 (통과, 실제론 낭비됨)
순번 4 ➔ user:2 (초과, 품절)

```

### 6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유

중복 요청과 비정상 요청이 카운터 숫자에 그대로 포함되므로, 실제 허가된 사용자(발급 건수) 수와 전혀 일치하지 않는 허수이기 때문입니다.

### 7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?

중복이 제거된 고유 사용자들의 집합인 Set의 크기(`SCARD`)를 기준으로 판단해야 합니다.

### 8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기

| 구분 | INCR 기반 방식 | Set + Lua Script 방식 |
| --- | --- | --- |
| 수량 판단 기준 | 단순 누적 요청 횟수 | 고유 유저 수 (Set 크기) |
| 중복 사용자 방지 | 방어 불가 (추가 로직 필요) | 완벽 방어 가능 |
| 장점 | 매우 단순하고 직관적 | 1명당 1장 발급 규칙의 엄격한 제어 |
| 단점 | 중복 유저가 파이(수량)를 깎아먹음 | Lua 작성 및 유지보수의 러닝커브 |
| 최종 권장 여부 | X (비권장) | O (권장) |

## 과제 8. Redis 판정 결과에 따른 API 응답 설계하기

### 상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우

#### 1. API 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 성공적으로 접수되었습니다.",
  "requestId": "req-12345"
}

```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

202 Accepted. 처리가 접수되었지만, 아직 완료되지 않은 비동기 요청을 의미하는 가장 적합한 표준 상태 코드이기 때문입니다.

#### 3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유

Redis와 Kafka라는 임시 관문을 통과하여 대기열에 들어갔을 뿐, DB 쓰기 결과는 아직 확정되지 않았기 때문입니다.

#### 4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?

백그라운드에서 Kafka 메시지를 읽어와 DB의 쿠폰 발급 이력 테이블에 `INSERT` 연산을 수행합니다.

### 상황 B. Redis 결과가 DUPLICATE인 경우

#### 1. API 응답 JSON

```json
{
  "status": "DUPLICATE",
  "message": "이미 참여하신 이벤트입니다."
}

```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

409 Conflict. 서버의 현재 상태(이미 쿠폰 보유)와 클라이언트의 요청이 충돌함을 의미하기 때문입니다.

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

발행해 봐야 Consumer 단의 Unique 제약에서 실패하여 롤백될 운명이므로, 불필요한 인프라 부하 방지를 위해 원천 차단해야 합니다.

#### 4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?

이미 쿠폰함에 지급되었습니다 와 같은 알림을 띄우고, 마이페이지 쿠폰함으로 리다이렉트 시키는 UX를 제공합니다.

### 상황 C. Redis 결과가 SOLD_OUT인 경우

#### 1. API 응답 JSON

```json
{
  "status": "SOLD_OUT",
  "message": "아쉽게도 쿠폰이 모두 소진되었습니다."
}

```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

403 Forbidden (또는 비즈니스 예외 코드 400). 권한의 문제는 아니지만, 비즈니스 룰에 의해 더 이상 해당 자원(쿠폰)에 대한 접근이 허용되지 않음을 나타냅니다.

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

수량이 마감된 상태에서 대기열에 넣어봐야 어차피 처리 불가능하므로, 시스템 파이프라인 낭비를 없애야 합니다.

#### 4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?

이벤트 마감 직후에도 쏟아지는 수만 건의 후행 요청들이 DB 인프라를 타격하지 않도록 보호, Fail-fast 하기 위함입니다.

### 2. Redis에는 어떤 상태가 남아 있을 수 있는가?

발급 완료 집합(`issued-users`) Set에 해당 유저 ID가 추가된 채로 데이터가 남아버립니다.

### 3. Kafka에는 어떤 문제가 생기는가?

아무런 메시지도 적재되지 않는 누락 상태가 됩니다.

### 4. Consumer는 왜 이 요청을 처리할 수 없는가?

자신이 폴링할 지시서(Kafka Message) 자체가 큐에 존재하지 않기 때문에 작동할 근거가 없습니다.

### 5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?

안 됩니다. 요청이 유실되었음에도 접수되었다고 응답하면, 해당 유저는 Redis에 기록이 남아있어 영원히 재시도(`DUPLICATE` 차단)도 못하고 쿠폰도 받지 못하는 사태에 빠집니다.

### 6. 이 상황에서 가능한 보상 처리 방법을 작성하라

* Redis의 Set에서 해당 유저 ID를 다시 제거(`SREM`)하는 롤백 수행.
* 또는 즉각적인 실패(`FAILED`) 응답 후, 오류 내용을 Dead Letter Queue 형태의 별도 로깅 시스템에 기록하여 수동 조치.

### 7. Redis 보상 처리도 실패할 수 있는 이유

Redis도 네트워크를 통신하는 인프라이므로, Kafka 타임아웃 상황과 맞물려 Redis 커넥션마저 단절되거나 스레드 이슈가 있을 경우 보상 명령(`SREM`) 전송 자체가 실패할 수 있습니다.

### 8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?

분산 환경 부분 실패에 대응하기 위한 8주차: Retry/DLQ, 보상 트랜잭션 과 연결됩니다.

## 과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기

### 1. Redis, Kafka, DB 역할 비교표

| 구분 | Redis | Kafka | DB |
| --- | --- | --- | --- |
| 주 역할 | 고속 선착순 필터링 판정 | 비동기 메시지 버퍼 & 대기열 | 데이터 영구 저장 및 최종 정합성 |
| 저장하는 데이터 | 임시 판정용 통과 유저 Set | 쿠폰 발급 지시 메시지 페이로드 | 쿠폰 이력 및 유저 원본 레코드 |
| 강점 | 압도적인 I/O 속도, 원자성 | 시스템 간 Decoupling, 스파이크 완충 | ACID 트랜잭션, 데이터 무결성 |
| 한계 | 데이터 유실 가능성(휘발성) | 중복 발급 등 비즈니스 제어 불가 | 동시 접속(Lock 경합)에 약함 |
| 실패 시 문제 | 판정 불가 또는 보상 트랜잭션 꼬임 | Consumer 처리 중단, 요청 유실 | 데이터 정합성 깨짐 문제 |
| 이번 주차의 핵심 | DB 앞단의 필터 구축 | 안전한 비동기 전송 | 최종 방어지점 명시 |

### 2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이

* **Redis SUCCESS:** 수량 내에 들었고, 처음 왔네. 대기줄로 가도 좋다 (판정 통과)
* **Kafka PENDING:** 번호표 뽑고 대기줄에 대기중 (요청 안전 적재)
* **DB ISSUED:** "완료 후 반영됨" (최종 영구 반영)

### 4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?

Redis 데이터 증발(Eviction, Restart) 후 유저가 재요청하거나, Consumer 자체에서 중복 처리가 일어났을 때, DB가 이를 그대로 허용하여 이중 발급 하는 상황이 벌어집니다.

### 6. 4주차: DB 테이블 설계와 최종 정합성 보장

#### 6-1. Redis를 사용해도 DB Unique Key가 필요한 이유

분산 아키텍처 특성상 발생 가능한 임시 저장소(Redis)의 유실 및 Kafka의 At-least-once 중복 전달 버그를 막기 위해서입니다.

#### 6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제

### 7. 5주차: requestId 기반 멱등성과 중복 처리

#### 7-1. 같은 요청이 여러 번 들어올 수 있는 이유

클라이언트의 네트워크 불안정으로 인한 자동 재시도, 혹은 Consumer가 처리를 완료했으나 Offset Commit 직전 크래시가 발생하여 재시작 시 반복 폴링하는 현상 때문입니다.

#### 7-2. Redis 중복 체크와 requestId 멱등성의 차이

* Redis 중복 체크: 이 사람이 이번 이벤트에 참여한 적 있는가? (비즈니스 룰)
* 멱등성: 이 네트워크 요청 패킷(req-123)이 방금 전 내가 이미 처리한 패킷인가? (시스템 통신 룰)

### 8. 6주차: Outbox Pattern과 이벤트 발행 정합성

#### 8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유

쿠폰 DB Commit 직후 어플리케이션이 외부망(Kafka)을 호출하려는 찰나에 서버 전원이 나가거나 브로커 장애가 발생할 수 있기 때문입니다.

#### 8-2. Outbox Pattern이 필요한 이유

쿠폰 비즈니스 상태 변화(DB)와 알림용 이벤트 발송(Kafka)을 단일 로컬 트랜잭션으로 묶어, 어느 하나만 성공하는 반쪽짜리 데이터 불일치를 막기 위함입니다.

### 10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션

#### 10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?

수량 한 자리를 차지해놓고 실제 쿠폰은 받지 못하여, 기업 입장에서는 쿠폰이 남고 고객 입장에서는 데이터 정합성이 깨지는 현상입니다.

#### 10-2. Retry Topic과 DLQ가 필요한 이유

일시적 장애(DB 타임아웃 등)는 잠시 후 재시도하여 살려내고, 영구적 에러(포맷 불량 등)는 DLQ로 빼내어 큐가 꽉 막히는 Poison Pill 현상을 방지해야 합니다.
