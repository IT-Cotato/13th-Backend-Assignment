# 3주차 과제

# Redis 기반 선착순 쿠폰 판정 구조 설계

## 1. 과제 목표

이번 3주차 과제의 목표는 Redis를 이용해 선착순 쿠폰 발급 요청을 빠르게 판정하는 구조를 설계하는 것이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리하는 비동기 구조를 배웠고, 2주차에서는 Kafka를 이용해 요청을 안전하게 적재하고 Consumer가 뒤에서 처리하는 구조를 다뤘다.  
3주차에서는 여기에 Redis를 추가해, 성공 가능성이 없는 요청을 Kafka와 DB 앞단에서 미리 걸러내는 구조를 설계한다.

이번 과제에서 내가 선택한 기본 설계는 다음과 같다.

- Redis는 `Set + Lua Script` 방식으로 선착순 / 중복 여부를 판정한다.
- Redis 결과가 `SUCCESS`인 경우에만 Kafka에 발급 요청 메시지를 발행한다.
- Consumer가 최종적으로 DB에 쿠폰 발급 기록을 저장한다.
- DB는 `UNIQUE(event_id, user_id)` 같은 제약으로 마지막 정합성을 보장한다고 가정한다.

중요한 상태 구분은 아래와 같다.

```text
Redis SUCCESS
= 선착순 판정 통과

Kafka PENDING
= 발급 요청 메시지가 Kafka에 정상 접수됨

DB ISSUED
= DB에 쿠폰 발급 기록이 최종 저장됨
```

즉, Redis에서 `SUCCESS`가 나왔다고 해서 최종 쿠폰 발급이 완료된 것은 아니다.

## 2. 기본 상황

이번 과제에서는 아래 상황을 기준으로 설계한다.

```text
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 100,000건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

이 구조에서 가장 중요한 문제는 `실패할 요청을 어디서 최대한 빨리 차단할 것인가`이다.  
Kafka만 사용하면 요청은 잘 쌓을 수 있지만, 중복 요청과 품절 이후 요청도 계속 뒤로 흘러간다.  
따라서 이번 주차에서는 Redis가 DB 앞단의 판정 계층 역할을 맡는다.

## 3. 이번 과제의 전제 조건

이번 과제는 아래 전제를 따른다.

```text
1. API Server는 로그인 여부와 이벤트 시간을 먼저 검증한다.
2. 이후 Redis에서 선착순 / 중복 여부를 판정한다.
3. Redis 결과가 SUCCESS인 경우에만 Kafka에 메시지를 발행한다.
4. Redis 결과가 DUPLICATE 또는 SOLD_OUT이면 Kafka에 메시지를 발행하지 않는다.
5. Redis SUCCESS는 최종 발급 성공이 아니다.
6. 최종 발급 성공은 Consumer가 DB에 저장한 뒤 결정된다.
```

이번 주차에서 Redis는 아래 세 가지 결과만 반환한다고 가정한다.

```text
SUCCESS   : 선착순 판정 통과
DUPLICATE : 이미 통과한 사용자
SOLD_OUT  : 수량 소진
```

# 5. 필수 과제

## 과제 1. Redis 기반 선착순 처리 구조 그리기

쿠폰 발급 요청은 Redis에서 먼저 판정하고, 통과한 요청만 Kafka에 발행하는 구조로 설계한다.

### 1. 전체 요청 처리 흐름 다이어그램

```text
+--------+
| Client |
+--------+
    |
    | 1. 쿠폰 발급 요청
    v
+------------+
| API Server |
+------------+
    |
    | 2. 로그인 / 이벤트 시간 검증
    | 3. Redis 선착순 / 중복 판정
    v
+--------------------------------------+
| Redis                                |
|--------------------------------------|
| Lua Script                           |
| - SISMEMBER: 중복 사용자 확인        |
| - SCARD: 현재 통과 인원 확인         |
| - SADD: 통과 사용자 추가             |
+--------------------------------------+
    |
    | 4. SUCCESS / DUPLICATE / SOLD_OUT
    v
+------------+
| API Server |
+------------+
    |
    | 5. SUCCESS인 경우만 Kafka 발행
    v
+-------------------------------+
| Kafka Producer                |
+-------------------------------+
    |
    | 6. coupon.issue.requested
    v
+-------------------------------+
| coupon.issue.requested Topic  |
+-------------------------------+
    |
    | 7. 메시지 소비
    v
+----------------------+
| Coupon Issue Consumer|
+----------------------+
    |
    | 8. DB 저장
    v
+-----------------------------+
| DB                          |
| coupon_issue                |
| UNIQUE(event_id, user_id)   |
+-----------------------------+
```

### 2. Redis의 역할

```text
1. 이미 통과한 사용자 중복 요청 차단
2. 쿠폰 수량이 남아 있는지 빠르게 판정
3. 성공 가능한 요청만 뒤 단계로 통과
4. DB 앞단에서 불필요한 요청을 미리 제거
```

### 3. Kafka의 역할

```text
1. Redis를 통과한 요청을 비동기로 적재
2. 순간적인 트래픽 폭주를 버퍼링
3. Consumer가 처리 가능한 속도로 읽어가도록 분리
```

### 4. DB의 역할

```text
1. 최종 쿠폰 발급 기록 저장
2. 마지막 정합성 보장
3. Redis가 놓친 중복이나 재처리 상황의 최종 방어선 역할
```

### 5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유

```text
1. 품절 요청과 중복 요청까지 Kafka로 보내면 불필요한 메시지가 쌓인다.
2. Consumer와 DB가 실패할 요청까지 처리해야 해서 자원이 낭비된다.
3. 성공 가능성이 있는 요청만 뒤로 넘겨야 전체 시스템 부하를 줄일 수 있다.
```

## 과제 2. Redis가 필요한 이유 설명하기

### 1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점

```text
Kafka는 요청을 전달하고 적재하는 데 강하지만,
이 요청을 실제로 통과시켜도 되는지 판단하지는 못한다.

따라서 Redis가 없으면 중복 요청, 품절 이후 요청, 실패 가능성이 높은 요청도
모두 Kafka -> Consumer -> DB 단계까지 흘러갈 수 있다.
```

### 2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?

```text
1. DB에서 중복 확인, 수량 확인, 저장 시도가 반복된다.
2. 성공 가능성이 거의 없는 요청도 같은 비용으로 처리된다.
3. 동시 요청이 많을수록 DB Lock 경합과 트랜잭션 충돌이 커질 수 있다.
4. Consumer 처리 지연이 커지고 전체 발급 완료 시간이 길어진다.
```

### 3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?

```text
1. 이미 실패가 확정된 요청이 Kafka와 DB 자원을 계속 사용한다.
2. 운영 관점에서 불필요한 메시지 적재량이 늘어난다.
3. 실제 성공 요청 처리보다 실패 요청 처리 비용이 더 커질 수 있다.
4. 사용자는 늦게 실패를 알게 되어 UX도 나빠진다.
```

### 4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?

```text
1. 같은 사용자의 중복 요청이 Kafka에 여러 번 쌓일 수 있다.
2. Consumer가 같은 사용자에 대해 반복 검사를 수행하게 된다.
3. 잘못 설계하면 선착순 자리를 중복 요청이 잠식할 수 있다.
4. 최종적으로 DB Unique Key가 막더라도 앞단 비용은 이미 사용된다.
```

### 5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?

```text
1. 이미 발급 대기 목록에 들어간 사용자의 중복 요청
2. 쿠폰 수량이 소진된 뒤 들어오는 요청
3. 선착순 한도를 초과한 요청
```

## 과제 3. Redis Key와 자료구조 설계하기

이번 과제의 메인 설계는 `Set + Lua Script` 방식이다.  
따라서 `issued-users`를 중심으로 설계하고, `request-count`는 비교용으로만 설명한다.

### 1. Redis Key 목록

| Redis Key | 자료구조 | 저장하는 값 | 필요한 이유 |
| --- | --- | --- | --- |
| `coupon:{eventId}:issued-users` | Set | Redis 선착순 판정을 통과한 사용자 ID | 중복 사용자 방지와 현재 통과 사용자 수 확인 |
| `coupon:{eventId}:metadata` | Hash 또는 String 캐시 | limit, startAt, endAt 같은 이벤트 메타 정보 | 빠른 판정을 위한 보조 정보 캐시 |
| `coupon:{eventId}:request-count` | String Counter | 요청 순번 또는 전체 요청 수 | INCR 기반 비교 설계에서만 사용 |

### 2. 이벤트 ID가 100일 때 실제 Redis Key 예시

```text
coupon:100:issued-users
coupon:100:metadata
coupon:100:request-count
```

### 3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?

```text
이 Set에는 Redis 선착순 판정을 통과한 사용자 식별자가 저장된다.

예:
user:1
user:5
user:20
user:77
```

즉, 이 Set의 의미는 `실제로 Redis에서 통과시킨 사용자 목록`이다.

### 4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?

```text
request-count는 몇 번째 요청인지 계산하는 카운터 역할을 한다.
INCR 결과가 limit 이하이면 통과 후보, 초과하면 SOLD_OUT 후보로 해석할 수 있다.

다만 이것은 최종 발급 수량이 아니라 요청 순번에 가깝다.
중복 사용자가 여러 번 요청하면 숫자가 계속 증가할 수 있기 때문이다.
```

### 5. Redis Key에 TTL이 필요한 이유는 무엇인가?

```text
1. 이벤트 종료 후에도 Key가 계속 남아 있으면 메모리를 낭비한다.
2. 일회성 이벤트 데이터는 영구 저장할 필요가 없다.
3. 운영자가 수동 정리를 놓쳐도 자동 정리되도록 안전장치를 둘 수 있다.
```

### 6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?

```text
1. 이벤트 종료 시점에 TTL을 설정해 자동 만료되게 한다.
2. 예를 들어 이벤트 종료 후 1일 뒤 삭제되도록 둔다.
3. 별도의 정리 배치나 운영 스크립트로 만료되지 않은 Key를 보완 삭제할 수 있다.
```

## 과제 4. Redis Set 기반 중복 요청 방지 설계하기

### 1. Redis Set을 사용하는 이유

```text
Set은 같은 값을 중복 저장하지 않기 때문에
한 사용자가 같은 이벤트에서 여러 번 통과하지 못하게 막기에 적합하다.
또한 SCARD로 현재 통과 사용자 수를 확인할 수 있어 수량 판단에도 활용할 수 있다.
```

### 2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?

```text
1 : 새로운 값이 Set에 추가됨
0 : 이미 존재하는 값이라 추가되지 않음
```

### 3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?

```text
user:1 첫 번째 요청:
SADD coupon:100:issued-users user:1
-> 결과 1
-> 새로 추가됨

user:1 두 번째 요청:
SADD coupon:100:issued-users user:1
-> 결과 0
-> 이미 존재하므로 중복 요청으로 판단 가능
```

### 4. Redis Set 구조를 그림으로 표현하기

```text
key: coupon:100:issued-users

+-----------------------+
| user:1                |
| user:5                |
| user:20               |
| user:77               |
+-----------------------+

의미:
- Set 내부에는 통과한 사용자만 저장된다.
- 같은 사용자는 한 번만 들어갈 수 있다.
```

### 5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?

```text
아니다.
Set은 중복 사용자 저장 방지에는 적합하지만,
수량 확인과 사용자 추가를 분리해서 처리하면 초과 발급이 발생할 수 있다.

따라서 중복 확인, 현재 인원 확인, 사용자 추가를 원자적으로 묶어야 한다.
```

### 6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?

```text
SCARD coupon:100:issued-users
```

## 과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기

가정:

```text
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청
```

### 1. `SCARD 후 SADD` 방식의 처리 흐름

```text
1. 현재 Set 크기를 SCARD로 조회한다.
2. 크기가 1000보다 작으면 발급 가능하다고 판단한다.
3. 이후 SADD로 사용자를 추가한다.
```

### 2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램

```text
[현재 상태]
coupon:100:issued-users size = 999

시간 흐름
---------------------------------------------------
user:A -> SCARD = 999
user:B -> SCARD = 999

user:A -> 999 < 1000, 통과 가능 판단
user:B -> 999 < 1000, 통과 가능 판단

user:A -> SADD user:A 성공
user:B -> SADD user:B 성공
---------------------------------------------------

[최종 상태]
coupon:100:issued-users size = 1001
```

### 3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?

```text
SCARD와 SADD가 분리되어 있기 때문이다.
두 요청 모두 아직 아무도 추가되기 전의 크기 999를 보고
"한 자리 남았다"고 동시에 판단할 수 있다.
```

### 4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유

```text
두 요청 모두 서로 독립적으로 "발급 가능" 판단을 끝낸 뒤
각자 SADD를 수행해 버리기 때문이다.
즉, 확인 시점과 추가 시점 사이에 다른 요청이 끼어들 수 있다.
```

### 5. 이 문제의 핵심 원인은 무엇인가?

```text
수량 확인과 사용자 추가가 하나의 원자적 작업으로 묶여 있지 않다는 점이다.
```

### 6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?

```text
1. 이미 통과한 사용자 여부 확인
2. 현재 통과 사용자 수 확인
3. 수량이 남아 있으면 사용자 추가
```

## 과제 6. Redis Lua Script 기반 원자적 처리 설계하기

### 1. Lua Script로 묶어야 하는 작업 목록

```text
1. SISMEMBER로 이미 통과한 사용자인지 확인한다.
2. SCARD로 현재 통과 사용자 수가 제한보다 작은지 확인한다.
3. 조건을 만족하면 SADD로 사용자를 추가한다.
```

### 2. Lua Script 처리 흐름 다이어그램

```text
API Server
    |
    | tryIssue(eventId, userId)
    v
Redis Lua Script
    |
    +-- SISMEMBER issued-users userId == 1
    |      -> DUPLICATE 반환
    |
    +-- SCARD issued-users >= limit
    |      -> SOLD_OUT 반환
    |
    +-- SADD issued-users userId
           -> SUCCESS 반환
```

### 3. Lua Script 반환값 설계

| 반환값 | 의미 | API Server 처리 |
| --- | --- | --- |
| `SUCCESS` | 중복이 아니고 수량도 남아 있어 Redis 통과 | Kafka에 발급 요청 메시지 발행 시도 |
| `DUPLICATE` | 이미 Redis에서 통과한 사용자 | Kafka 발행 없이 중복 응답 반환 |
| `SOLD_OUT` | 현재 통과 인원이 한도에 도달함 | Kafka 발행 없이 품절 응답 반환 |

### 4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?

```text
중복 확인, 수량 확인, 사용자 추가를 Redis 내부에서 하나의 흐름으로 처리하기 때문에
중간에 다른 요청이 끼어들어 상태를 바꿀 수 있는 틈이 줄어든다.

즉, 애플리케이션에서 명령을 따로 보내는 방식보다
초과 발급 가능성을 훨씬 낮출 수 있다.
```

### 5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유

```text
Redis SUCCESS는 Redis 선착순 판정을 통과했다는 의미일 뿐이다.
이후 Kafka 발행이 실패할 수도 있고,
Consumer가 DB 저장 중 실패할 수도 있다.

최종 발급 완료는 DB 저장까지 성공했을 때만 확정된다.
```

## 과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기

### 1. INCR 기반 방식의 기본 흐름

```text
1. 요청이 들어오면 INCR coupon:{eventId}:request-count 실행
2. 반환된 순번이 limit 이하인지 확인
3. limit 이하이면 통과 후보로 판단
4. 필요하면 Set으로 중복 사용자 여부를 추가 확인
```

### 2. `INCR` 명령어가 보장하는 것은 무엇인가?

```text
동시에 여러 요청이 들어와도 각 요청에 대해 서로 다른 증가된 숫자를 부여한다.
즉, 요청 순번을 원자적으로 계산해 준다.
```

### 3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?

```text
1. 같은 사용자의 중복 요청이 여러 자리를 차지하지 못하도록 막는 것
2. 실제 통과 사용자 수와 request-count를 일치시키는 것
3. 중복 확인과 수량 판단을 함께 끝내는 것
```

### 4. 아래 상황에서 어떤 문제가 생기는지 설명하기

```text
쿠폰 수량: 3개

user:1 첫 번째 요청 -> INCR 결과 1
user:1 두 번째 요청 -> INCR 결과 2
user:1 세 번째 요청 -> INCR 결과 3
user:2 첫 번째 요청 -> INCR 결과 4
```

답변:

```text
문제는 user:1의 중복 요청이 순번 1, 2, 3을 모두 차지할 수 있다는 점이다.
실제로는 user:1 한 명만 통과해야 하지만,
request-count 기준으로는 세 자리가 이미 소비된 것처럼 보인다.

그 결과 user:2는 첫 정상 요청인데도 4번째 요청으로 계산되어 SOLD_OUT 처리될 수 있다.
즉, request-count는 실제 발급 가능 인원 수와 다를 수 있다.
```

### 5. 위 상황을 다이어그램으로 표현하기

```text
request-count 기준 자리

+---------+---------+---------+---------+
| 순번 1  | 순번 2  | 순번 3  | 순번 4  |
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
   통과      중복      중복      품절
```

### 6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유

```text
request-count는 요청이 몇 번째로 판정 단계에 들어왔는지를 나타내는 값에 가깝다.
중복 요청, 품절 이후 요청도 카운터를 증가시킬 수 있으므로
최종 발급 수량과 일치하지 않을 수 있다.
```

### 7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?

```text
coupon:{eventId}:issued-users Set의 크기,
즉 SCARD 결과를 기준으로 판단하는 것이 더 적절하다.

이 값은 중복 제거가 끝난 실제 통과 사용자 수에 가깝기 때문이다.
```

### 8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기

| 구분 | INCR 기반 방식 | Set + Lua Script 방식 |
| --- | --- | --- |
| 수량 판단 기준 | request-count 순번 | issued-users Set 크기 |
| 중복 사용자 방지 | 별도 Set 없이는 불가 | Set 기반으로 직접 가능 |
| 장점 | 단순하고 빠르게 순번 계산 가능 | 중복 확인과 수량 확인을 함께 다루기 좋음 |
| 단점 | 중복 사용자가 선착순 자리를 차지할 수 있음 | Lua Script 설계가 필요하고 구조 이해가 조금 더 필요함 |
| 최종 권장 여부 | 비교 학습용으로는 유용 | 이번 과제의 권장 설계 |

## 과제 8. Redis 판정 결과에 따른 API 응답 설계하기

이번 과제에서는 `SUCCESS`, `DUPLICATE`, `SOLD_OUT` 세 가지 Redis 결과를 기준으로 응답을 설계한다.

### 상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우

#### 1. API 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-20260710-0001"
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```text
202 Accepted를 사용한다.

이유:
요청이 정상적으로 접수되었지만,
최종 발급 처리는 비동기로 진행 중이기 때문이다.
즉, 지금 시점에는 완료가 아니라 접수 상태를 알려주는 것이 맞다.
```

#### 3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유

```text
Kafka에 메시지가 접수된 것까지 확인한 상태일 뿐,
Consumer의 실제 처리와 DB 저장 성공 여부는 아직 확정되지 않았기 때문이다.
```

#### 4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?

```text
1. Kafka에서 coupon.issue.requested 메시지를 소비한다.
2. DB에 coupon_issue 발급 기록 저장을 시도한다.
3. 저장 성공 시 최종 ISSUED 상태가 된다.
4. 실패 시 재시도 또는 실패 처리 흐름으로 간다.
```

---

### 상황 B. Redis 결과가 DUPLICATE인 경우

#### 1. API 응답 JSON

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청이 접수된 사용자입니다."
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```text
409 Conflict를 사용한다.

이유:
요청 자체의 형식은 정상이나,
현재 시스템 상태상 같은 사용자의 중복 요청은 허용되지 않기 때문이다.
```

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

```text
이미 Redis 기준으로 통과한 사용자이므로
같은 사용자 요청을 다시 Kafka에 보내면 불필요한 중복 메시지만 늘어난다.
```

#### 4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?

```text
1. "이미 접수된 요청입니다" 같은 명확한 문구를 보여줄 수 있다.
2. 발급 상태 조회 페이지로 이동시키거나 마이페이지 링크를 제공할 수 있다.
3. 버튼을 비활성화하거나 중복 클릭을 막는 UI를 둘 수 있다.
```

### 상황 C. Redis 결과가 SOLD_OUT인 경우

#### 1. API 응답 JSON

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```text
409 Conflict 또는 410 Gone을 고려할 수 있다.
이번 과제에서는 409 Conflict를 사용하겠다.

이유:
현재 이벤트 상태상 더 이상 발급 가능한 수량이 없어서
요청을 처리할 수 없는 상태이기 때문이다.
```

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

```text
이미 Redis에서 실패가 확정되었기 때문이다.
이 요청을 Kafka로 보내면 Consumer와 DB가 어차피 실패할 요청을 다시 처리하게 된다.
```

#### 4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?

```text
1. 품절 이후 요청은 성공 가능성이 0이다.
2. 이런 요청을 앞단에서 막아야 Kafka와 DB의 낭비를 줄일 수 있다.
3. 사용자도 즉시 품절 사실을 알 수 있어 UX가 좋아진다.
```

## 과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기

가정:

```text
1. 사용자가 쿠폰 발급 요청을 보냈다.
2. API Server가 Redis Lua Script를 실행했다.
3. Redis가 SUCCESS를 반환했다.
4. API Server가 Kafka에 메시지를 발행하려고 했다.
5. Kafka 장애로 메시지 발행에 실패했다.
```

### 1. 이 상황의 전체 흐름 다이어그램

```text
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Redis Lua Script 실행
  v
Redis
  |
  | SUCCESS 반환
  v
API Server
  |
  | Kafka 발행 시도
  v
Kafka
  |
  | 발행 실패
  v
API Server
  |
  | 보상 처리 또는 재시도 필요
```

### 2. Redis에는 어떤 상태가 남아 있을 수 있는가?

```text
issued-users Set에는 해당 userId가 이미 추가된 상태로 남아 있을 수 있다.
즉, Redis 기준으로는 통과 사용자처럼 보이지만,
실제로는 Kafka에 전달되지 못한 어중간한 상태가 된다.
```

### 3. Kafka에는 어떤 문제가 생기는가?

```text
발급 요청 메시지가 Topic에 들어가지 못한다.
즉, 비동기 처리 파이프라인이 시작되지 않는다.
```

### 4. Consumer는 왜 이 요청을 처리할 수 없는가?

```text
Consumer는 Kafka Topic에 적재된 메시지만 읽을 수 있기 때문이다.
메시지가 발행되지 않았으므로 Consumer 입장에서는 이 요청이 존재하지 않는다.
```

### 5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?

```text
안 된다.

PENDING은 적어도 Kafka에 발급 요청이 정상 접수되었음을 전제로 한다.
지금은 Kafka 발행 자체가 실패했으므로
요청이 비동기 처리 파이프라인에 올라가지 못한 상태다.
```

### 6. 이 상황에서 가능한 보상 처리 방법을 작성하라

답변:

```text
- Redis Set에서 userId 제거
- Kafka 발행 실패 로그 저장
- Kafka 발행 재시도
- 별도 복구 배치에서 미전송 건 재처리
- 운영자가 확인할 수 있도록 모니터링 지표와 알림 추가
```

### 7. Redis 보상 처리도 실패할 수 있는 이유

```text
1. API Server 장애로 보상 로직이 끝까지 수행되지 못할 수 있다.
2. Redis 연결 장애가 동시에 발생할 수 있다.
3. Kafka 발행 실패 직후 애플리케이션이 다운되면 보상 전에 중단될 수 있다.
```

### 8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?

```text
1. 5주차의 requestId 기반 멱등성
2. 6주차의 Outbox Pattern과 이벤트 발행 정합성
3. 8주차의 Retry / DLQ / 보상 트랜잭션
```

## 과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기

### 1. Redis, Kafka, DB 역할 비교표

| 구분 | Redis | Kafka | DB |
| --- | --- | --- | --- |
| 주 역할 | 선착순 / 중복 판정 | 요청 비동기 전달 및 버퍼링 | 최종 발급 기록 저장 |
| 저장하는 데이터 | 임시 판정 상태, 통과 사용자 목록 | 발급 요청 메시지 | 영구 발급 이력 |
| 강점 | 매우 빠른 읽기/쓰기, 앞단 필터링에 적합 | 대량 메시지 적재와 비동기 분리에 강함 | 정합성과 영속성 보장 |
| 한계 | 최종 원본 저장소로 쓰기엔 위험 | 중복/품절 판정을 직접 하지 못함 | 고트래픽 순간 판정에 직접 쓰면 부담이 큼 |
| 실패 시 문제 | 중복 판정 누락, 임시 상태 유실 가능 | 요청 전달 중단, Consumer 처리 불가 | 최종 발급 기록 손실 또는 불일치 |
| 이번 주차에서 보는 핵심 | 원자적 선착순 판정 | 성공 요청만 비동기로 적재 | 마지막 방어선 역할 |

### 2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이

```text
Redis SUCCESS:
선착순 판정을 통과했다는 뜻이다.

Kafka PENDING:
발급 요청 메시지가 Kafka에 접수되어 비동기 처리 대기 중이라는 뜻이다.

DB ISSUED:
Consumer가 DB 저장까지 끝내 실제 발급이 완료되었다는 뜻이다.
```

### 3. 세 상태의 차이를 다이어그램으로 표현하기

```text
요청 전
  |
  v
Redis SUCCESS
  |
  | Kafka 발행 성공
  v
PENDING
  |
  | Consumer 처리 + DB 저장 성공
  v
ISSUED
```

### 4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?

```text
1. Redis 장애나 데이터 유실 시 중복 방어가 무너질 수 있다.
2. Kafka 중복 소비나 Consumer 재처리 상황에서 중복 저장이 발생할 수 있다.
3. 운영 중 수동 재처리나 배치 작업이 Redis를 우회할 수 있다.

따라서 DB는 UNIQUE(event_id, user_id) 같은 제약으로 마지막 방어선을 가져야 한다.
```

### 5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유

```text
Kafka는 메시지를 잘 전달할 뿐,
"이 요청을 통과시켜도 되는가"를 판단하지 않는다.

즉, 중복 요청도 적재할 수 있고,
품절 이후 요청도 계속 Consumer까지 전달할 수 있다.
```

### 6. 4주차: DB 테이블 설계와 최종 정합성 보장

#### 6-1. Redis를 사용해도 DB Unique Key가 필요한 이유

```text
Redis는 빠른 판정 계층이지 최종 정합성 계층이 아니다.
장애, 재처리, 운영 실수 등으로 Redis 판정이 완벽하지 않을 수 있으므로
DB에서 마지막으로 중복을 막아야 한다.
```

#### 6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제

```text
같은 사용자가 같은 이벤트 쿠폰을 두 번 저장하려는 시도를 막아준다.
즉, Redis가 놓쳤더라도 DB에서 최종적으로 중복 발급을 차단한다.
```

### 7. 5주차: requestId 기반 멱등성과 중복 처리

#### 7-1. 같은 요청이 여러 번 들어올 수 있는 이유

```text
1. 사용자의 중복 클릭
2. 브라우저 재시도
3. 네트워크 타임아웃 후 재전송
4. Kafka 메시지 재전달 또는 Consumer 재처리
```

#### 7-2. Redis 중복 체크와 requestId 멱등성의 차이

```text
Redis 중복 체크는 "같은 사용자가 같은 이벤트에 여러 번 통과하는 것"을 막는 데 가깝다.
requestId 멱등성은 "같은 요청 자체가 여러 번 처리되는 것"을 막는 데 가깝다.

즉, 하나는 사용자 기준 중복 방지이고,
다른 하나는 요청 단위 재처리 방지다.
```

### 8. 6주차: Outbox Pattern과 이벤트 발행 정합성

#### 8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유

```text
DB 트랜잭션과 Kafka 발행은 서로 다른 시스템에서 일어난다.
따라서 DB commit은 성공했지만,
이후 Kafka 연결 장애나 브로커 문제로 이벤트 발행이 실패할 수 있다.
```

#### 8-2. Outbox Pattern이 필요한 이유

```text
DB 저장과 이벤트 발행 사이의 불일치를 줄이기 위해 필요하다.
발급 기록과 outbox 이벤트를 같은 트랜잭션으로 저장하면
"DB에는 저장됐는데 이벤트는 유실됨" 같은 문제를 더 안정적으로 다룰 수 있다.
```

### 9. 7주차: EDA 기반 서비스 분리와 조회 구조

#### 9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?

```text
1. Coupon Service가 여러 후속 서비스에 강하게 결합된다.
2. 알림 서비스가 느리거나 장애가 나면 쿠폰 발급 처리도 영향을 받을 수 있다.
3. 후속 기능이 늘어날수록 호출 체인이 복잡해진다.
```

#### 9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?

```text
1. 쿠폰 발급과 후속 기능을 느슨하게 분리할 수 있다.
2. 각 서비스가 자신에게 필요한 이벤트만 구독하면 된다.
3. 알림 실패가 곧 쿠폰 발급 실패로 이어지지 않게 만들 수 있다.
```

### 10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션

#### 10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?

```text
Redis 기준으로는 통과한 사용자지만,
DB에는 최종 발급 기록이 없는 불일치 상태가 된다.
이런 경우 재시도, 실패 상태 저장, 보상 처리 전략이 필요하다.
```

#### 10-2. Retry Topic과 DLQ가 필요한 이유

```text
일시적 실패는 재시도로 복구할 수 있지만,
영구적으로 잘못된 메시지는 계속 재시도하면 안 된다.

따라서 일시적 실패는 Retry Topic으로 보내고,
복구 불가능한 메시지는 DLQ로 분리해 관리해야 한다.
```

#### 10-3. 보상 트랜잭션이 필요한 상황 예시

```text
1. Redis SUCCESS 후 Kafka 발행 실패
2. Kafka 발행 성공 후 Consumer의 DB 저장 실패
3. 외부 시스템 호출 성공/실패가 서로 엇갈려 상태가 맞지 않는 경우
```

## 마무리 정리

이번 3주차 설계의 핵심은 아래 다섯 줄로 요약할 수 있다.

```text
1. Redis는 빠른 선착순 / 중복 판정 계층이다.
2. Kafka는 통과한 요청만 비동기로 전달한다.
3. DB는 최종 발급 기록을 저장하는 마지막 방어선이다.
4. 선착순 판정은 원자적으로 처리해야 한다.
5. Redis SUCCESS는 최종 발급 성공이 아니라 통과 결과일 뿐이다.
```
