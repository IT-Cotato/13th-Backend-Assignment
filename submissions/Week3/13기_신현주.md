# Redis 기반 선착순 쿠폰 판정 구조 설계


## 과제 1. Redis 기반 선착순 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
 Client 
   |
   | ① POST /coupon-events/{eventId}/issue
   v
API Server
   |
   | ② 로그인 여부 확인 / 이벤트 시간 확인
   | ③ Redis Lua Script 실행 (EVAL)
   v
 Redis                                    
   |
   | ④ SUCCESS / DUPLICATE / SOLD_OUT 반환
   | 
   v
API Server 
   |
   |-- DUPLICATE → Kafka 발행 안 함 → Client에 DUPLICATE 응답
   |-- SOLD_OUT  → Kafka 발행 안 함 → Client에 SOLD_OUT 응답
   |-- SUCCESS   → ⑤ Kafka Producer로 발급 요청 메시지 발행
                           |
                           |
                           |-- 발행 실패 → Redis 보상 처리 시도
                           |               → Client에 접수 실패 응답
                           |
                           |-- 발행 성공 → Client에 PENDING 응답
                                          |
                                          |
                                          v
                                        Kafka                          
                                          |
                                          | ⑥ 메시지 소비
                                          v
                                 Coupon Issue Consumer
                                          |
                                          | ⑦ 최종 발급 기록 저장
                                          v
                                          DB
```

### 2. Redis의 역할

```
DB 앞단에서 요청을 빠르게 걸러주는 필터 역할을 한다.

1. 쿠폰 수량 제한
   - issued-users Set의 크기로 현재 통과 사용자 수를 확인하고 limit에 도달했으면 SOLD_OUT으로 차단한다.

2. 사용자 중복 요청 방지
   - Set은 같은 값을 중복 저장하지 않으므로 이미 통과한 사용자의 재요청을 DUPLICATE로 차단한다.

3. 성공한 요청만 Kafka로 넘기기
   - SUCCESS인 요청만 Kafka에 발행해 Kafka/Consumer/DB의 불필요한 부하를 줄인다.

```

### 3. Kafka의 역할

```
Redis 판정을 통과한 요청을 Consumer에게 비동기로 안정적으로 전달하는 역할.

- 요청 접수와 실제 발급 처리를 분리한다.
- 요청이 몰려도 메시지를 Topic에 쌓아두고 Consumer가 처리 가능한 속도로 소비하게 해준다.
- Partition을 통해 Consumer 병렬 처리를 가능하게 한다.

```

### 4. DB의 역할

```
최종 쿠폰 발급 기록을 저장하고 정합성을 보장한다.

- Consumer가 처리한 결과를 coupon_issue 테이블에 저장한다.
- UNIQUE(event_id, user_id) 제약으로, Redis가 놓친 중복이나
  Kafka 메시지 중복 소비로 인한 중복 발급을 최종적으로 막는다.
- 발급 상태의 원본 데이터를 보관하며 사용자는 이 기록을 상태 조회 API / 마이페이지로 확인한다.

```

### 5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유

```
쿠폰 수량은 1,000개인데 요청은 100,000건이 들어온다.
Redis 판정 없이 모든 요청을 Kafka에 발행하면 결국 실패할 99,000건까지 Kafka에 적재되고,
Consumer가 소비하고 DB에서 수량 확인/중복 확인/저장 시도를 하게 된다.

- Kafka에 불필요한 메시지가 쌓여 Consumer Lag이 커진다.
- Consumer와 DB가 실패할 요청을 처리하느라 자원을 낭비한다.
- DB Lock 경합이 커져 정작 성공해야 할 요청의 처리도 느려진다.
- 품절 이후 요청도 계속 DB까지 흘러간다.

Redis에서 SUCCESS인 요청만 발행하면 Kafka/Consumer/DB는 성공 가능성이 있는 요청만 처리하면 된다.
또한 DUPLICATE/SOLD_OUT은 Redis 판정 즉시 사용자에게 응답할 수 있어 사용자 경험도 좋아진다.
```

## 과제 2. Redis가 필요한 이유 설명하기

### 1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점

```
1. 성공 가능성이 낮은 요청도 Kafka → Consumer → DB 판정 단계까지 도달한다.
2. DB에서 남은 수량 조회 / 중복 발급 확인 / 저장 시도가 요청마다 반복된다.
3. 동시에 많은 요청이 오면 수량 차감을 위한 DB Lock 경합이 커지고 DB가 전체 시스템의 병목이 된다.
4. 쿠폰이 품절된 이후에도 실패가 확정된 요청이 계속 DB까지 간다.
5. 같은 사용자의 반복 클릭도 그대로 Kafka와 DB까지 전달된다.
6. Kafka는 메시지를 전달/적재만 할 뿐, 수량 초과와 중복 발급을 막아주지 않는다.
```

### 2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?

```
- Kafka Topic에 10만 건의 메시지가 쌓이고, 그중 99%는 결국 실패할 메시지다.
- Consumer는 실패할 메시지까지 모두 소비하고 처리해야 하므로
  Consumer Lag이 크게 증가한다.
- 정작 성공해야 하는 요청의 최종 발급 확정도 함께 늦어진다 (Lag이 커지면 성공 요청도 뒤에서 대기한다)
- Consumer가 DB에 동시 접근하며 Lock 경합 & 커넥션 고갈이 발생할 수 있다.
- 결국 Kafka를 넣어 API Server 부하는 줄였지만 병목이 Consumer와 DB로 이동한 상태가 된다.
```

### 3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?

```
- 이미 결과가 실패로 확정된 요청인데도 Kafka 적재 → Consumer 소비 → DB 조회/저장 시도라는 비싼 경로를 그대로 거친다. 
- 품절 응답을 사용자에게 즉시 줄 수 있는데도 Consumer가 처리할 때까지 사용자는 PENDING만 보게 된다.
- 실패 메시지가 Kafka에 쌓여 정상 요청의 처리까지 지연시킨다.
- DB에는 불필요한 조회/실패 트랜잭션 부하가 계속 쌓인다.
```

### 4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?

```
- 같은 사용자의 요청이 각각 별개의 메시지로 Kafka에 발행된다.
- Consumer가 이 메시지들을 병렬로 처리하면 DB Unique Key 같은 최종 방어선이 없을 경우 같은 사용자에게 쿠폰이 여러 번 발급될 수 있다.
- 중복 발급이 발생하면 "사용자 1명당 1개" 규칙이 깨지고 전체 발급 수량이 1,000개를 초과할 수 있다.
- 중복 요청이 선착순 자리를 여러 개 차지해 실제로 발급받아야 할 다른 사용자가 밀려날 수 있다.
- 불필요한 메시지가 Kafka와 DB의 부하를 키운다.
```

### 5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?

```
1. DUPLICATE: 이미 Redis 선착순 판정을 통과한 사용자의 재요청
   → issued-users Set에 이미 존재하므로 즉시 차단

2. SOLD_OUT: 쿠폰 수량이 소진된 이후에 들어온 요청
   → SCARD가 limit 이상이면 즉시 차단

결과적으로 요청 100,000건 중
- 성공 1,000건만 Kafka로 발행되고
- 나머지 99,000건은 Redis 단계에서 DUPLICATE / SOLD_OUT 응답으로 종료된다.
```

## 과제 3. Redis Key와 자료구조 설계하기

> 본 설계는 3주차 최종 권장 방식인 **Redis Set + Lua Script** 방식을 채택한다.
> 따라서 `request-count`는 필수 Key가 아니며, 통과 사용자 수는 `SCARD issued-users`로 판단한다.
> (아래 표에서는 비교 설명을 위해 `request-count`도 참고용으로 함께 정리한다)

### 1. Redis Key 목록

| Redis Key | 자료구조 | 저장하는 값 | 필요한 이유 |
| --- | --- | --- | --- |
| `coupon:{eventId}:issued-users` | Set | 선착순 판정을 통과한 사용자 ID 목록 (예: `user:1`, `user:5`) | ① Set은 중복 값을 저장하지 않으므로 같은 사용자의 중복 요청을 막을 수 있다. ② `SCARD`로 중복 제거된 실제 통과 사용자 수를 확인해 수량 제한을 판정할 수 있다. **=(필수)** |
| `coupon:{eventId}:metadata` | Hash | `limit`, `startAt`, `endAt` 등 이벤트 메타 정보 | 매 요청마다 DB에서 수량/시간을 조회하지 않고 Redis에서 빠르게 읽기 위한 캐시. 단, 원본은 DB에 두고 Redis에는 캐시만 둔다. **(선택)** |
| `coupon:{eventId}:request-count` | String (Counter) | 이 이벤트로 들어온 요청의 순번(누적 요청 수) | INCR 기반 방식에서 "몇 번째 요청인지"를 원자적으로 계산하기 위한 값. 다만 중복 사용자를 구분하지 못하므로 본 설계에서는 사용하지 않고, 모니터링용 지표 정도로만 활용한다. **(본 설계에서 미사용)** |

### 2. 이벤트 ID가 100일 때 실제 Redis Key 예시

```
coupon:100:issued-users     (Set)
coupon:100:metadata         (Hash, 선택)
coupon:100:request-count    (String Counter, 본 설계에서는 미사용)

예시 상태:
coupon:100:issued-users
-------------------------
 user:1                  
 user:5                  
 user:20                 
 user:77                                   
-------------------------      

SCARD coupon:100:issued-users
= 4  (현재 선착순 통과 사용자 수)
```

### 3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?

```
Redis Lua Script에 통과한 사용자의 식별자가 저장된다
예: user:1, user:5, user:20 ...

특징:
- Set이므로 같은 userId는 한 번만 저장된다
- 이 Set의 SCARD가 곧 중복 제거된 실제 통과 사용자 수다.
- 저장된 값의 의미는 Redis 선착순 판정 통과이지, 쿠폰 발급 완료가 아니다.
  최종 발급 완료 여부는 DB coupon_issue 테이블이 기준이다.
```

### 4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?

```
요청이 들어올 때마다 INCR로 증가시켜 몇 번째 요청인지를 계산하는 역할.
requestOrder <= limit 이면 선착순 후보, 초과하면 SOLD_OUT으로 빠르게 차단할 수 있다.

주의:
- request-count는 요청 순번에 가까울 뿐 중복 제거된 실제 통과 사용자 수가 아니다.
- 같은 사용자가 여러 번 누르면 그때마다 카운터가 증가해 한 사용자가 선착순 자리를 여러 개 차지할 수 있다.
- 품절 이후 요청도 카운터를 증가시킨다.

따라서 본 설계에서는 판정 기준으로 사용하지 않고, 사용했다면 전체 요청 유입량 모니터링 용도 정도로만 본다.
```

### 5. Redis Key에 TTL이 필요한 이유는 무엇인가?

```
1. 메모리 관리:
   Redis는 인메모리 저장소다. 이벤트마다 issued-users Set이 계속 쌓이면 Redis 메모리를 지속적으로 잠식한다.

2. Redis는 임시 판정 상태 저장소이지 영구 원본 저장소가 아니다:
   최종 발급 기록의 원본은 DB에 있다. 이벤트가 끝나면 Redis의 판정 상태는 더 이상 필요하지 않다.

3. 이벤트 종료 후 불필요한 Key가 남으면 운영/장애 분석 시 어떤 Key가 유효한지 혼란을 준다.

따라서 이벤트 종료 시점 + 여유 기간으로 TTL을 설정한다.
TTL은 이벤트 종료 시각보다 충분히 뒤로 잡아야 한다.
```

### 6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?

```
1. TTL 기반 자동 정리
   - 이벤트 생성/시작 시 EXPIRE를 걸어둔다.
     예: 이벤트 종료 후 1일 뒤 만료
     EXPIRE coupon:100:issued-users  <이벤트 종료 + 1일까지의 초>
     EXPIRE coupon:100:metadata      <동일>

2. 배치 정리 (보조)
   - 이벤트 종료 후 정합성 검증 배치를 돌린다.
     Redis issued-users의 사용자 목록과 DB coupon_issue 기록을 대조해
     Redis SUCCESS인데 DB에 기록이 없는 요청을 찾아 복구/재처리한다.
   - 검증이 끝난 뒤 Key를 삭제한다.

3. 주의: 검증 전에 Key를 먼저 지우면 Redis-DB 불일치를 추적할 근거가 사라진다.
   따라서 이벤트 종료 → 정합성 검증 → Key 삭제(또는 TTL 만료) 순서를 지킨다.
```

## 과제 4. Redis Set 기반 중복 요청 방지 설계하기

### 1. Redis Set을 사용하는 이유

```
1. Set은 같은 값을 중복해서 저장하지 않는다.
   → 사용자 1명당 쿠폰 1개 조건을 자료구조 자체로 강제할 수 있다.

2. SADD의 반환값으로 새로 추가되었는지/이미 존재했는지를 한 번의 명령으로 판단할 수 있다.

3. SCARD로 중복이 제거된 실제 통과 사용자 수를 O(1)로 확인할 수 있다.
   → 수량 제한 판정 기준으로 쓰기에 적합하다.

4. SISMEMBER로 특정 사용자의 통과 여부를 빠르게 조회할 수 있다.
```

### 2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?

```
결과 1:
해당 값이 Set에 존재하지 않아서 새로 추가되었다 → 이 사용자는 처음 통과하는 사용자다.

결과 0:
해당 값이 이미 Set에 존재해서 추가되지 않았다 → 이미 선착순 판정을 통과한 사용자다.
```

### 3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?

```
user:1 첫 번째 요청:
SISMEMBER coupon:100:issued-users user:1 → 0 (없음)
SCARD coupon:100:issued-users          → 500 (< limit 1000)
SADD coupon:100:issued-users user:1    → 1 (새로 추가됨)
결과: SUCCESS → Kafka 발행

user:1 두 번째 요청:
SISMEMBER coupon:100:issued-users user:1 → 1 (이미 존재)
결과: DUPLICATE → Kafka 발행 안 함, 중복 응답 반환
```

### 4. Redis Set 구조를 그림으로 표현하기

```
Redis
key: coupon:100:issued-users   (자료구조: Set)

Set members
-------------------------
 user:1                  
 user:5                  
 user:20                 
 user:77                 
 ...                     
-------------------------

SCARD coupon:100:issued-users
= 현재 선착순 통과 사용자 수


[중복 요청 흐름]

user:1  요청 1회차
   |
   v
SADD user:1 → 1 새로 추가
   |
   v
선착순 통과 


user:1  요청 2회차
   |
   v
이미 Set에 user:1 존재
   |
   v
중복 요청 차단 
```

### 5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?

```
아니다. 자동으로 해결되지 않는다.

Set이 자동으로 보장해주는 것은 같은 값의 중복 저장 방지뿐이다.
Set은 최대 몇 개까지만 담아라 같은 크기 제한 기능을 제공하지 않는다.

따라서 수량 제한은 애플리케이션이 직접
SCARD로 현재 크기를 확인하고 limit과 비교하는 로직을 넣어야 한다.

그런데 이 SCARD와 SADD를 별도 명령으로 나누어 실행하면
그 사이에 다른 요청이 끼어들어 Race Condition이 발생하고 쿠폰 수량이 초과 통과될 수 있다. 

→ 그래서 SISMEMBER + SCARD + SADD를
   Lua Script로 묶어 원자적으로 처리해야 한다. 
```

### 6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?

```
SCARD coupon:{eventId}:issued-users

SCARD는 지정된 Set에 저장된 고유 요소의 총 개수를 반환한다.
이 값이 현재까지 선착순 판정을 통과한 실제 사용자 수이며,
limit과 비교해 수량 소진 여부를 판단하는 기준이 된다.
```

## 과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기

### 1. `SCARD 후 SADD` 방식의 처리 흐름

```
current = SCARD coupon:100:issued-users      -- ① 현재 통과 사용자 수 조회
if current < limit:                          -- ② 애플리케이션에서 수량 비교
    SADD coupon:100:issued-users userId      -- ③ 사용자 추가
    return SUCCESS
else:
    return SOLD_OUT

문제:
조회 → 판단 → 추가 가 서로 다른 시점의 별개 명령이다.
조회와 추가 사이에 다른 요청이 끼어들 수 있는 틈이 존재한다.
```

### 2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램

```
[초기 상태]
limit = 1000
SCARD coupon:100:issued-users = 999 -> 남은 수량 1개

  시간          요청 A                          요청 B
  ----------------------------------------------------------------
   t1     SCARD → 999
   t2                                     SCARD → 999
   t3     999 < 1000 → 발급 가능 판단
   t4                                     999 < 1000 → 발급 가능 판단
   t5     SADD user:A → 1 (추가 성공)
   t6                                     SADD user:B → 1 (추가 성공)
   t7     return SUCCESS
   t8                                     return SUCCESS
  ----------------------------------------------------------------

[결과 상태]
SCARD coupon:100:issued-users = 1001

문제:
쿠폰은 1,000개인데 1,001명이 선착순 판정을 통과했다.


[그림]

                요청 A                          요청 B
                  |                               |
                  | SCARD = 999                   |
                  |                               | SCARD = 999
                  |                               |
                  | 발급 가능 판단                 | 발급 가능 판단
                  |                               |
                  | SADD user:A                   |
                  |                               | SADD user:B
                  v                               v
         -------------------------------------------------
              coupon:100:issued-users size = 1001             
                → 쿠폰 수량 초과 통과 (Over-Issue)               
         -------------------------------------------------
```

### 3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?

```
A와 B가 모두 SADD를 실행하기 전에 SCARD를 조회했기 때문이다.

- A가 SCARD로 999를 읽은 시점과 실제로 SADD로 Set을 변경하는 시점 사이에 B가 끼어들어 똑같이 999를 읽었다.
- 두 요청 모두 999 < 1000이니 아직 자리가 하나 남았다는 이미 지난 정보를 근거로 판단한다.
- 수량 비교는 Redis가 아니라 API Server 메모리에서 이뤄지므로 Redis는 두 요청이 같은 자리를 노리고 있다는 사실을 알 수 없다.

```

### 4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유

```
SADD는 그 자체로는 원자적이지만, 수량이 남아 있을 때만 추가하라는 조건은 SADD가 검사해주지 않는다.

A와 B 모두 발급 가능으로 판단한 뒤 각자 SADD를 실행하면 Set에는 user:A와 user:B가 모두 추가된다.(각각 반환값 1)

결과적으로 999 + 2 = 1001명이 Set에 들어가고 1000을 초과한 1,001명이 선착순 판정을 통과하게 된다.
동시 요청이 N개라면 최악의 경우 999 + N명까지도 통과할 수 있다.
```

### 5. 이 문제의 핵심 원인은 무엇인가?

```
수량 확인(SCARD)과 사용자 추가(SADD)가 분리되어 있다는 점

두 명령 사이에 다른 요청이 끼어들 수 있는 시간적 틈이 존재하고,
그 사이에 Set의 상태가 바뀌어도 애플리케이션은 이를 알지 못한다.

검사 시점과 사용 시점이 어긋나는 Race Condition 문제다.
```

### 6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?

```
아래 세 작업이 하나의 원자적 작업으로 묶여서 실행되어야 한다.

1. 이미 통과한 사용자인지 확인          (SISMEMBER)
2. 현재 통과 사용자 수가 limit 미만인지 확인 (SCARD)
3. 조건을 만족하면 사용자를 Set에 추가     (SADD)

Redis는 단일 스레드로 명령을 처리하고 Lua Script를 하나의 명령처럼 원자적으로 실행하므로
이 세 작업을 Lua Script로 묶으면 스크립트 실행 중에는 다른 요청이 끼어들 수 없다.

  --------------------------------------------
   Redis에서 하나의 원자적 작업으로 처리        
  -------------------------------------------
   1. 중복 사용자 확인                          
   2. 수량 초과 여부 확인                       
   3. 사용자 추가                              
  --------------------------------------------
                    |
                    v
   SUCCESS / DUPLICATE / SOLD_OUT 중 하나 반환
```

## 과제 6. Redis Lua Script 기반 원자적 처리 설계하기

### 1. Lua Script로 묶어야 하는 작업 목록

```
1. SISMEMBER coupon:{eventId}:issued-users {userId}
   → 이미 선착순 판정을 통과한 사용자인지 확인 (중복 확인)

2. SCARD coupon:{eventId}:issued-users
   → 현재 통과한 사용자 수를 확인하고 limit과 비교 (수량 확인)

3. SADD coupon:{eventId}:issued-users {userId}
   → 위 두 조건을 모두 통과했을 때만 사용자를 통과 목록에 추가 (사용자 추가)
```

### 2. Lua Script 처리 흐름 다이어그램

```
API Server
  |
  | EVAL script, KEYS[1]=coupon:100:issued-users, ARGV[1]=userId, ARGV[2]=limit
  v
+-------------------------------------------------------------+
| Redis (스크립트 실행 중 다른 요청 끼어들 수 없음 - 원자적)      |
|-------------------------------------------------------------|
|                                                             |
|   SISMEMBER issued-users userId                             |
|          |                                                  |
|          +-- == 1 (이미 존재) ------------> return DUPLICATE |
|          |                                                  |
|          v (== 0)                                           |
|   currentCount = SCARD issued-users                         |
|          |                                                  |
|          +-- currentCount >= limit -------> return SOLD_OUT |
|          |                                                  |
|          v (currentCount < limit)                           |
|   SADD issued-users userId                                  |
|          |                                                  |
|          v                                                  |
|   return SUCCESS                                            |
+-------------------------------------------------------------+
  |
  | SUCCESS / DUPLICATE / SOLD_OUT
  v
API Server
  |
  +-- SUCCESS   → Kafka 발행 시도 → 성공 시 PENDING 응답
  +-- DUPLICATE → 중복 요청 응답 (Kafka 발행 안 함)
  +-- SOLD_OUT  → 품절 응답 (Kafka 발행 안 함)
```

### 3. Lua Script 반환값 설계

| 반환값 | 의미 | API Server 처리 |
| --- | --- | --- |
| SUCCESS | Redis 선착순 판정 통과. 중복 사용자가 아니고 수량도 남아 있어 issued-users Set에 정상 등록됨 | Kafka(`coupon.issue.requested`)에 발급 요청 메시지 발행 시도 → 발행 성공 시 `PENDING` 응답, 발행 실패 시 Redis 보상 처리(SREM) 후 접수 실패 응답 |
| DUPLICATE | 이미 선착순 판정을 통과한 사용자의 재요청 | Kafka 발행하지 않고 즉시 중복 요청 응답(`DUPLICATE`) 반환 |
| SOLD_OUT | 통과 사용자 수가 이미 limit에 도달하여 쿠폰 수량 소진 | Kafka 발행하지 않고 즉시 품절 응답(`SOLD_OUT`) 반환 |

### 4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?

```
Redis는 명령을 단일 스레드로 처리하며, Lua Script는 하나의 명령처럼
원자적으로 실행된다. 즉, 스크립트가 실행되는 동안에는
다른 클라이언트의 명령이 중간에 끼어들 수 없다.

따라서 SISMEMBER → SCARD → SADD 사이에 다른 요청이 Set을 변경할 틈이 사라진다.

과제 5의 상황(999명, 남은 1개)에 적용하면
  요청 A: Lua 실행 → SCARD=999 → SADD user:A → SUCCESS 
  요청 B: Lua 실행 → SCARD=1000 → 1000 >= 1000 → SOLD_OUT

두 요청이 동시에 도착해도 반드시 순차적으로 처리되므로 Set 크기가 limit을 초과하는 일이 발생하지 않는다.
중복 사용자도 SISMEMBER 검사가 같은 원자 단위 안에 있어 확실히 차단된다.

```

### 5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유

```
Redis SUCCESS는 Kafka와 DB 저장 단계로 넘어갈 자격을 얻었다는 의미일 뿐이다.
이후 아래 단계들이 남아 있고, 각 단계에서 실패할 수 있다.

1. Kafka 발행이 실패할 수 있다.
   → Redis에는 통과로 남았지만 Kafka에 메시지가 없어 Consumer가 처리 불가
2. Consumer가 메시지를 소비하지 못하거나 처리 중 장애가 날 수 있다.
3. Consumer가 DB에 저장을 시도했는데 DB 장애로 실패할 수 있다.
   → Redis에는 성공, DB에는 발급 기록 없음 
4. DB Unique 제약에 걸려 저장이 거부될 수도 있다.

```

## 과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기

### 1. INCR 기반 방식의 기본 흐름

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | 1. INCR coupon:{eventId}:request-count
  v
Redis
  |
  | requestOrder 반환 
  v
API Server
  |
  | 2. requestOrder <= limit 인지 확인
  |    → 초과하면 SOLD_OUT 응답
  | 3. SISMEMBER coupon:{eventId}:issued-users userId 로 중복 사용자 확인
  |    → 이미 있으면 DUPLICATE 응답
  | 4. SADD coupon:{eventId}:issued-users userId
  | 5. 통과한 요청만 Kafka 발행
  v
Kafka
```

### 2. `INCR` 명령어가 보장하는 것은 무엇인가?

```
숫자 증가 연산의 원자성을 보장한다.

동시에 수많은 요청이 들어와도 각 요청은 서로 다른 순번을 정확히 하나씩 받는다.
같은 숫자가 두 요청에 중복으로 반환되거나 숫자가 누락되지 않는다.

요청 A → INCR 결과 1
요청 B → INCR 결과 2
요청 C → INCR 결과 3
...

요청마다 서로 다른 고유한 순번을 부여하는 것을 보장한다.
따라서 수량 초과 여부를 매우 빠르게 판단할 수 있다.
```

### 3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?

```
1. 사용자 중복 제거를 보장하지 못한다.
   같은 사용자가 여러 번 요청해도 그때마다 카운터가 증가하므로 한 사용자가 선착순 자리를 여러 개 차지할 수 있다.
2. INCR 이후에 실행되는 다른 명령들(SISMEMBER, SADD)과의 원자성을 보장하지 못한다.
   INCR → 비교 → SISMEMBER → SADD가 애플리케이션에서 나뉘어 실행되면 그 사이에 다른 요청이 끼어들 수 있다.
3. 카운터 값이 곧 실제 발급 사용자 수임을 보장하지 못한다.
   품절 이후 요청, 중복 요청, 이후 단계에서 실패한 요청까지 모두 카운트된다.
4. 롤백을 보장하지 못한다.
   INCR로 순번을 받은 뒤 중복이라 탈락시켜도 그 순번은 이미 소비된 상태다.
```

### 4. 아래 상황에서 어떤 문제가 생기는지 설명하기

```
쿠폰 수량: 3개 (limit = 3)

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
user:1 한 명이 버튼을 세 번 누르는 것만으로 선착순 자리 1, 2, 3번을
모두 소비해버렸다.

- user:1의 2번째, 3번째 요청은 issued-users Set의 SISMEMBER 검사에 걸려 DUPLICATE로 탈락한다.
  즉 실제로 통과한 사용자는 user:1 한 명뿐이다.
- 그런데 request-count는 이미 3까지 올라갔기 때문에
  정상적으로 처음 요청한 user:2는 requestOrder = 4 > limit = 3 이므로 SOLD_OUT 응답을 받는다.

결과:
- 쿠폰 3개 중 실제로는 1개만 발급되었는데 시스템은 품절이라고 응답한다.
- 정당하게 요청한 user:2가 부당하게 탈락한다.
- 쿠폰 2개가 아무에게도 발급되지 않고 남는다.

핵심 원인:
INCR는 숫자 증가만 원자적으로 처리할 뿐
같은 사용자의 중복 요청이 여러 자리를 차지하지 못하게 막는 것은 보장해주지 않는다.
```

### 5. 위 상황을 다이어그램으로 표현하기

```
limit = 3

request-count 기준 선착순 자리

----------------------------------------
| 순번 1  | 순번 2  | 순번 3  | 순번 4  |
----------------------------------------
| user:1  | user:1  | user:1  | user:2 |
----------------------------------------
   통과      중복      중복      품절


[Set 기준으로 본 실제 상태]

coupon:{eventId}:issued-users
------------------
 user:1               SCARD = 1
------------------

실제 통과 사용자 수 : 1명
request-count 값    : 4
쿠폰 수량           : 3개

→ 아직 2개가 남아 있는데도 user:2는 SOLD_OUT 응답을 받았다.
→ request-count(4)와 실제 통과 사용자 수(1)가 완전히 다르다.
```

### 6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유

```
1. 중복 요청이 카운트된다.
   같은 사용자가 여러 번 눌러도 그때마다 INCR가 실행되어 값이 증가한다.
   → 중복 제거된 사용자 수가 아니다.

2. 품절 이후 요청도 카운트된다.
   limit = 1000일 때
   1001번째 요청 → INCR 1001 → SOLD_OUT
   1002번째 요청 → INCR 1002 → SOLD_OUT
   통과하지 못한 요청도 값을 올린다.

3. Redis SUCCESS ≠ 최종 발급 성공이다.
   Redis를 통과했더라도 Kafka 발행 실패, Consumer 장애, DB 저장 실패로 최종 발급되지 않을 수 있다.

request-count = 몇 번째로 판정에 들어왔는지 나타내는 요청 순번
최종 발급 수량 = DB coupon_issue 테이블에 실제로 저장된 발급 기록 건수
```

### 7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?

```
Redis 선착순 판정 단계에서의 실제 통과 사용자 수는 issued-users Set의 크기로 판단하는 것이 적절하다.
  SCARD coupon:{eventId}:issued-users

Set은 중복 값을 저장하지 않으므로, 이 값은 중복이 제거된 고유한 통과 사용자 수를 정확히 나타낸다.
같은 사용자가 아무리 여러 번 요청해도 Set 크기는 늘어나지 않는다.

한편 시스템 전체의 최종 발급 수량은 Redis가 아니라
DB coupon_issue 테이블의 저장 건수를 기준으로 봐야 한다.
Redis는 임시 판정 상태이고, DB가 최종 원본이기 때문이다.
```

### 8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기

| 구분 | INCR 기반 방식 | Set + Lua Script 방식 |
| --- | --- | --- |
| 수량 판단 기준 | `INCR request-count`의 반환값(요청 순번)이 limit 이하인지로 판단. 중복/실패 요청까지 포함된 **전체 요청 수** 기준 | `SCARD issued-users`(중복 제거된 실제 통과 사용자 수)가 limit 미만인지로 판단. **실제 통과 사용자 수** 기준 |
| 중복 사용자 방지 | INCR 자체로는 불가능. 별도로 Set(SISMEMBER/SADD)을 함께 써야 하고, 그마저도 카운터가 이미 증가한 뒤라 자리를 되돌릴 수 없음 | Set 자료구조가 중복 저장을 원천 차단. SISMEMBER 검사가 같은 원자 단위 안에 있어 중복 사용자가 자리를 차지하지 못함 |
| 장점 | 구조가 단순하고 INCR가 매우 빠름. 요청 순번을 명확히 알 수 있어 품절 판단이 간단하고 순번 기반 로그/모니터링에 유리 | 수량 제한과 중복 방지를 하나의 원자적 작업으로 동시에 해결. Race Condition이 발생하지 않음. 판정 결과(SUCCESS/DUPLICATE/SOLD_OUT)를 한 번의 호출로 얻음 |
| 단점 | 중복 요청이 선착순 자리를 소모해 쿠폰이 남는데도 품절 처리될 수 있음. INCR/SISMEMBER/SADD가 분리 실행되면 그 사이에 다른 요청이 끼어들 수 있음. request-count를 발급 수량으로 오해하기 쉬움 | Set이 커지면 Redis 메모리 사용량이 늘어 TTL/정리 전략이 필요. 스크립트가 무거우면 Redis 전체가 블로킹될 수 있음. Kafka 발행 실패·DB 저장 실패에 대한 보상 처리는 여전히 별도로 필요 |
| 최종 권장 여부 | 권장하지 않음 . | 권장. |

## 과제 8. Redis 판정 결과에 따른 API 응답 설계하기

### 상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우

#### 1. API 응답 JSON

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 발급 결과는 마이페이지에서 확인해주세요.",
  "requestId": "req-001"
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```
202 Accepted

- 요청은 정상적으로 접수되었지만 실제 쿠폰 발급 처리는 아직 완료되지 않았다.
- 202 Accepted는 요청을 접수했으나 처리는 아직 완료되지 않았다는
  비동기 처리 구조의 의미를 가장 정확하게 표현한다.
- 200 OK는 요청이 성공적으로 처리 완료되었다는 인상을 주어 발급 완료로 오해를 줄 수 있다.
- 201 Created는 리소스가 생성되었음을 의미하는데
  이 시점에 DB에는 아직 발급 기록이 없으므로 부적절하다.
```

#### 3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유

```
이 시점에 완료된 것은 두 가지뿐이다.
  1) Redis 선착순 판정 통과
  2) Kafka에 발급 요청 메시지 접수 성공

아직 남아 있는 단계:
- Consumer가 메시지를 소비해야 한다. Consumer Lag이 있으면 지연된다.
- Consumer가 DB에 발급 기록을 저장해야 한다.
- DB 장애나 Unique 제약 위반으로 저장이 실패할 수도 있다.

Redis SUCCESS  ≠ 최종 발급 성공
Kafka PENDING  ≠ 최종 발급 성공
DB ISSUED      = 최종 발급 성공
```

#### 4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?

```
1. coupon.issue.requested Topic에서 발급 요청 메시지를 읽는다.
2. 메시지의 requestId, eventId, userId를 확인한다.
3. 실제 쿠폰 발급 처리를 수행하고 coupon_issue 테이블에 발급 기록을 저장한다.
   UNIQUE(event_id, user_id) 제약으로 중복 발급을 최종 방어한다.
4. 요청 상태를 PENDING → ISSUED 또는 FAILED로 갱신한다.
5. 처리가 끝난 메시지의 Offset을 Commit한다.

이후 사용자는 requestId 기반 상태 조회 API나 마이페이지에서 결과를 확인한다.
```

### 상황 B. Redis 결과가 DUPLICATE인 경우

#### 1. API 응답 JSON

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다. 발급 결과는 마이페이지에서 확인해주세요."
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```
409 Conflict

- 요청 자체는 형식상 올바르지만 사용자 1명당 1개라는 현재 리소스 상태와 충돌해 처리할 수 없다.
  이런 상태 충돌을 표현하는 표준 코드가 409 Conflict다.
- 200 OK를 주면 클라이언트가 요청이 새로 접수된 것으로 오해할 수 있다.
- 사용자의 잘못된 입력이 아니므로 400 Bad Request보다 409가 더 정확하다.
```

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

```
1. 이 사용자는 이미 선착순 판정을 통과해 발급 요청이 진행 중이거나 완료된 상태다.
   메시지를 또 발행하면 Consumer가 같은 사용자에 대해 발급 처리를 두 번 시도하게 되어
   중복 발급 위험이 생긴다.

2. 결과가 이미 중복으로 확정된 요청이다.
   Kafka에 넣어도 Consumer가 소비하고 DB를 조회한 뒤 실패로 끝날 뿐이다.
   Kafka/Consumer/DB 자원을 낭비하고 Consumer Lag만 키운다.

3. 사용자에게는 Redis 판정 즉시 결과를 알려줄 수 있는데
   Kafka를 거치면 응답이 PENDING이 되어 결과를 늦게 알게 된다.

Redis 판정 결과가 DUPLICATE라는 것 자체가 이미 최종 답이므로 그 자리에서 응답하고 종료한다.
```

#### 4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?

```
1. 명확한 안내 메시지
   이미 쿠폰 발급 요청을 완료했다고 알려주고 현재 처리 상태를 함께 보여준다.
   → 사용자가 실패한 줄 알고 계속 재시도하는 것을 막는다.

2. 결과 확인 경로 제공
   응답에 requestId나 마이페이지 링크를 함께 내려주어 사용자가 결과를 직접 확인하게 한다.

3. 클라이언트 단 방어
   버튼 클릭 직후 버튼을 비활성화하고 로딩 상태를 표시해 중복 요청 자체를 줄인다.
   다만 클라이언트 방어는 우회 가능하므로 서버 판정이 반드시 필요하다.

4. 에러가 아니라 정상 상태로 인지시키기
   붉은 에러 대신 이미 신청 완료됨이라는 중립적 안내로 표시한다.
```

### 상황 C. Redis 결과가 SOLD_OUT인 경우

#### 1. API 응답 JSON

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### 2. 이 응답에 사용할 HTTP Status Code와 이유

```
409 Conflict

- 요청 형식은 정상이지만 쿠폰 수량이 이미 소진되었다는 현재 리소스 상태와 충돌해 처리할 수 없다.
- 클라이언트의 잘못된 입력이 아니므로 400 Bad Request는 부적절하다.
- 서버 오류가 아니므로 5xx는 부적절하다.
- 200 OK로 주면 요청이 정상 접수된 것처럼 보여 오해를 준다.

재고 소진을 더 이상 제공할 수 없는 리소스로 보아 410 Gone을 쓰는 설계도 가능하다.
중요한 것은 2xx를 주지 않는 것이다.
```

#### 3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유

```
1. 결과가 이미 품절로 확정된 요청이다.
   Kafka에 발행해도 Consumer가 소비 후 수량 없음을 확인하고 FAILED로 끝날 뿐이다.

2. 이런 요청이 99,000건이다. 전부 발행하면
   - Kafka Topic에 실패할 메시지가 대량으로 쌓이고
   - Consumer가 그것들을 처리하느라 Lag이 폭증하며
   - 정작 성공해야 할 1,000건의 최종 발급 확정이 늦어진다.

3. 즉시 품절을 알려줄 수 있는데 PENDING을 주면 사용자는 한참 뒤에야 품절 사실을 알게 된다.

Redis의 존재 이유 자체가 실패할 요청을 DB까지 보내지 않는 것이다.
```

#### 4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?

```
1. 하류 시스템 보호
   Kafka, Consumer, DB가 실패가 확정된 요청을 처리하지 않아도 된다.
   DB Lock 경합과 커넥션 고갈을 막고 DB는 최종 발급 기록 저장에만 집중한다.

2. 성공 요청의 처리 속도 보장
   Kafka에 불필요한 메시지가 쌓이지 않으므로 Consumer Lag이 억제되고
   실제로 쿠폰을 받아야 할 1,000명의 발급이 빠르게 확정된다.

3. 즉각적인 사용자 피드백
   품절 사실을 바로 알려줄 수 있어 사용자가 무의미하게 기다리거나 재시도하지 않는다.
   재시도가 줄면 전체 트래픽도 줄어든다.

4. 비용 효율
   Redis 판정은 인메모리 연산이라 매우 저렴하지만
   Kafka 적재 + Consumer 처리 + DB 트랜잭션은 훨씬 비싸다.
   99%의 요청을 가장 싼 계층에서 걸러내는 것이 합리적이다.
```

## 과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기

### 1. 이 상황의 전체 흐름 다이어그램

```
 Client
   |
   | ① 쿠폰 발급 요청
   v
API Server
   |
   | ② Redis Lua Script 실행
   v
 Redis
   |  SISMEMBER → 없음
   |  SCARD     → limit 미만
   |  SADD user:1  ← Set에 등록됨
   |  return SUCCESS
   |
   | ③ SUCCESS 반환
   v
API Server
   |
   | ④ Kafka에 메시지 발행 시도
   v
 Kafka  ✕ 장애 / 네트워크 오류
   |
   | ⑤ 발행 실패 확인
   v
API Server
   |
   | ⑥ 보상 처리 시도: SREM coupon:100:issued-users user:1
   | ⑦ 실패 로그 저장
   v
 Client  ← ⑧ "요청 접수에 실패했습니다. 다시 시도해주세요."


[불일치 상태]
Redis : user:1 통과 기록 있음
Kafka : 메시지 없음
DB    : 발급 기록 없음
```

### 2. Redis에는 어떤 상태가 남아 있을 수 있는가?

```
issued-users Set에 해당 userId가 선착순 통과로 등록된 채 남아 있다.

  coupon:100:issued-users → { ..., user:1 }
  SCARD 값도 1 증가한 상태

문제:
1. 이 사용자는 실제로는 발급 요청조차 접수되지 못했는데 Redis 상으로는 통과한 것으로 되어 있다.
2. 이 사용자가 다시 요청하면 SISMEMBER에 걸려 DUPLICATE로 차단된다.
   → 아무것도 받지 못한 사용자가 재시도조차 못 하게 된다.
3. 이 사용자가 선착순 자리 하나를 점유하고 있어
   실제로 발급받을 수 있었던 다른 사용자가 SOLD_OUT으로 밀려날 수 있다.
   → 쿠폰 1,000개 중 실제 발급은 999개에 그칠 수 있다.
```

### 3. Kafka에는 어떤 문제가 생기는가?

```
Kafka Topic에 해당 요청 메시지가 존재하지 않는다.

- Producer가 Broker로부터 발행 성공 응답을 받지 못했으므로
  이 요청은 시스템에 안전하게 접수되지 않은 상태다.
- 요청이 어디에도 남지 않고 사실상 유실된다.
  별도의 실패 로그나 재시도 큐를 두지 않았다면 복구 근거조차 없다.

Redis에는 통과라는 흔적이 남았는데 Kafka에는 처리해야 할 작업 자체가 없는
Redis ↔ Kafka 상태 불일치가 발생한다.
```

### 4. Consumer는 왜 이 요청을 처리할 수 없는가?

```
Consumer는 Kafka Topic에 적재된 메시지를 읽어서 동작하는 컴포넌트이기 때문이다.

Consumer는 Redis의 issued-users Set을 보고 일하지 않는다.
Kafka에 메시지가 없으면 Consumer 입장에서는 처리할 요청이 애초에 존재하지 않는 것과 같다.

따라서 Consumer는 DB에 발급 기록을 저장하지 않고 사용자의 요청 상태는 영원히 확정되지 않는다.
```

### 5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?

```
안 된다.

PENDING의 의미는 발급 요청 메시지가 Kafka에 정상 접수되었고
Consumer가 곧 처리할 예정이라는 뜻이다.
Kafka 발행이 실패했으므로 이 전제가 성립하지 않는다.

PENDING을 주면
- 사용자는 요청이 접수되었다고 믿고 결과를 기다린다.
- 하지만 Kafka에 메시지가 없어 Consumer는 영원히 처리하지 않는다.
- 사용자는 계속 PENDING 상태만 보게 되고 결과를 영원히 받지 못한다.
- 재시도하려 해도 Redis에 이미 통과로 기록되어 DUPLICATE로 차단된다.
  → 아무것도 못 받고 재시도도 못 하는 최악의 상황에 빠진다.

따라서 Redis 보상 처리를 시도한 뒤 접수 실패 응답을 반환해야 한다.

{
  "status": "FAILED",
  "message": "쿠폰 발급 요청 접수에 실패했습니다. 잠시 후 다시 시도해주세요."
}
```

### 6. 이 상황에서 가능한 보상 처리 방법을 작성하라

```
1. Kafka 발행 재시도
   일시적 네트워크 오류라면 짧은 백오프를 두고 제한된 횟수만 재시도한다.
   무한 재시도는 API 응답 지연을 유발하므로 횟수와 타임아웃을 반드시 제한한다.

2. Redis Set에서 userId 제거
   SREM coupon:{eventId}:issued-users {userId}
   Redis의 통과 기록을 되돌려 선착순 자리를 반납하고 사용자가 다시 시도할 수 있게 한다.

3. 실패 로그 / 실패 상태 테이블 저장
   requestId, eventId, userId, 실패 시각, 실패 원인, 보상 성공 여부를 기록한다.
   복구 배치와 운영자 재처리의 근거가 된다.

4. 복구 배치에서 재처리
   실패 로그를 주기적으로 조회해 Kafka 재발행을 시도하거나
   Redis 보상이 실패한 건을 다시 SREM 처리한다.

5. 사용자에게는 접수 실패 응답 반환
   PENDING이 아니라 다시 시도해달라는 안내.

6. 이벤트 종료 후 정합성 검증 배치
   Redis issued-users 목록과 DB coupon_issue 기록을 대조해
   Redis에는 있는데 DB에는 없는 사용자를 찾아 복구하거나 정리한다.
```

### 7. Redis 보상 처리도 실패할 수 있는 이유

```
보상 처리(SREM) 역시 네트워크를 통한 원격 호출이므로 그 자체가 또 실패할 수 있다.

  1. Redis SUCCESS (SADD 성공)
  2. Kafka 발행 실패
  3. Redis에서 SREM 시도
  4. Redis 네트워크 오류 / Redis 장애 / API Server 프로세스 다운
     → SREM 실패

결과: Redis에는 여전히 user:1이 통과로 남아 있고 Kafka에는 메시지가 없다. 불일치가 유지된다.

근본 원인:
Redis 갱신과 Kafka 발행은 서로 다른 시스템에서 일어나는 별개의 작업이며
이 둘을 하나의 트랜잭션으로 묶을 수 없기 때문이다.

따라서 보상 처리를 넣으면 끝이 아니라
실패 로그 저장, 복구 배치, 상태 테이블, DB Unique Key라는 다층 방어 구조가 필요하다.
```

### 8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?

```
4주차: DB 테이블 설계와 최종 정합성 보장
→ Redis 상태를 100% 믿을 수 없으므로 DB가 마지막 방어선이 되어야 한다.
   UNIQUE(event_id, user_id)로 중복 발급을 최종 차단한다.

5주차: requestId 기반 멱등성과 중복 처리
→ requestId와 요청 상태 테이블을 두면 재시도 요청이 들어와도
   기존 상태를 조회해 안전하게 처리할 수 있다.

6주차: Outbox Pattern과 이벤트 발행 정합성
→ 상태 변경은 성공했는데 메시지 발행은 실패하는 문제의 일반적 해법.
   상태 저장과 발행할 메시지를 같은 트랜잭션으로 저장해 유실을 막는다.

8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션
→ Kafka 발행 재시도, 실패 메시지 격리(DLQ), Redis-DB 불일치 복구를 위한
   보상 트랜잭션과 운영자 재처리 도구를 다룬다. 본 문제의 최종 해결 지점이다.
```

### 2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이

```
Redis SUCCESS
= 선착순 판정을 통과했다.
= 중복 사용자가 아니고 수량도 남아 있어 issued-users Set에 등록되었다.
= Kafka와 DB 저장 단계로 넘어갈 자격을 얻었다는 의미일 뿐이다.

Kafka PENDING
= 발급 요청 메시지가 Kafka Topic에 정상적으로 발행되었다.
= Producer가 Broker로부터 발행 성공 응답을 받았다.
= Consumer가 앞으로 이 요청을 처리할 예정이라는 의미다.

DB ISSUED
= Consumer가 메시지를 소비해 실제 발급 처리를 수행했고
  coupon_issue 테이블에 발급 기록이 최종 저장되었다.
= 이것이 유일한 최종 발급 성공이다.

Redis SUCCESS ≠ 최종 발급 성공
Kafka PENDING ≠ 최종 발급 성공
DB ISSUED     = 최종 발급 성공
```

### 4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?

```
Redis의 중복 차단은 1차 방어선일 뿐, 아래 상황에서 뚫릴 수 있다.

1. Redis 장애가 발생하거나 데이터가 유실될 수 있다.
   → 이미 발급받은 사용자가 다시 통과한다.
2. Redis Key TTL이 이벤트 진행 중에 만료될 수 있다.
   → issued-users Set이 비워지고 중복 통과가 발생한다.
3. Kafka 메시지가 중복 소비될 수 있다.
   Consumer가 DB 저장 후 Offset Commit 전에 죽으면 같은 메시지를 다시 읽어 다시 처리한다.
4. Consumer가 재시도로 같은 요청을 다시 처리할 수 있다.
5. 애플리케이션 버그로 Redis 판정을 우회하는 요청 경로가 생길 수 있다.
6. 운영 중 수동 재처리나 배치 작업이 Redis를 거치지 않고 DB에 직접 쓸 수 있다.

결과: 같은 사용자에게 쿠폰이 두 번 발급되고 전체 발급 수량이 1,000개를 초과할 수 있다.

따라서 DB에 UNIQUE(event_id, user_id) 제약을 두어
어떤 경로로 들어와도 같은 사용자가 같은 이벤트 쿠폰을 두 번 받을 수 없게 해야 한다.
```

### 5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유

```
Kafka의 책임은 메시지를 안정적으로 전달하고 저장하는 것이지
이 요청을 통과시켜도 되는지 판단하는 것이 아니다.

1. Kafka는 비즈니스 규칙을 모른다.
   쿠폰이 몇 개 남았는지, 이 사용자가 이미 받았는지 알지 못한다.
2. 수량 판정을 Consumer와 DB로 미루게 된다.
   10만 건이 전부 Kafka에 쌓이고 Consumer와 DB가 판정 부담을 지게 되어
   DB Lock 경합과 Consumer Lag이 폭증한다.
3. 중복 요청도 그대로 전달된다.
   같은 사용자가 버튼을 여러 번 누르면 각각 별개 메시지로 발행된다.
4. Kafka 자체가 중복 소비를 만들 수 있다.
   Offset Commit 전 Consumer 장애 시 같은 메시지가 재처리된다.
5. Partition이 여러 개면 전체 처리 순서가 보장되지 않아 선착순 보장도 어렵다.

Kafka = 요청을 안정적으로 전달한다.
Redis = 이 요청을 통과시켜도 되는지 빠르게 판단한다.
DB    = 최종 발급 기록의 정합성을 보장한다.
```

### 6. 4주차: DB 테이블 설계와 최종 정합성 보장

#### 6-1. Redis를 사용해도 DB Unique Key가 필요한 이유

```
Redis는 빠른 1차 판정 계층이지 최종 원본 저장소가 아니다.
Redis가 뚫리거나 우회될 수 있는 경로가 다음과 같이 존재한다.

1. Redis 장애 / 데이터 유실 / TTL 조기 만료
2. Kafka 메시지 중복 소비
3. Consumer의 재시도로 인한 같은 메시지 재처리
4. 애플리케이션 버그로 Redis를 거치지 않는 요청 경로 발생
5. 운영자의 수동 재처리 / 배치 작업

이 모든 경로에서 발생하는 중복 발급을 최종적으로 막으려면
데이터가 실제로 저장되는 지점인 DB에 제약을 걸어야 한다.
DB는 트랜잭션과 제약 조건으로 강한 정합성을 보장할 수 있는 유일한 계층이다.
```

#### 6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제

```
한 사용자는 같은 이벤트에서 쿠폰을 한 번만 받을 수 있다는 규칙을 DB 레벨에서 강제한다.

Redis 통과
  |
  v
Kafka 메시지 소비
  |
  v
DB 저장 시도
  |
  |-- 최초 저장이면 → 성공 (ISSUED)
  |
  |-- 이미 (event_id, user_id) 기록이 있으면
      → Unique 제약 위반으로 INSERT 실패
      → 중복 발급 차단

막아주는 구체적 상황:
1. Kafka 중복 소비로 같은 메시지가 두 번 처리되는 경우
2. Consumer 재시도로 같은 요청이 재처리되는 경우
3. Redis 장애나 유실로 같은 사용자가 다시 통과한 경우
4. Redis를 우회한 요청이나 배치가 중복 저장을 시도하는 경우

어떤 경로로 들어와도 (event_id, user_id) 조합은 DB에 단 하나의 행으로만 존재하게 된다.
```

### 7. 5주차: requestId 기반 멱등성과 중복 처리

#### 7-1. 같은 요청이 여러 번 들어올 수 있는 이유

```
1. 사용자의 중복 클릭
   이벤트 시작 순간 사용자가 버튼을 여러 번 연타한다.

2. 네트워크 타임아웃과 클라이언트 재시도
   서버는 요청을 정상 처리했지만 응답이 유실되어 클라이언트가 같은 요청을 다시 보낸다.

3. 브라우저 새로고침이나 뒤로가기 후 재전송

4. API Server의 Kafka 발행 재시도
   발행 성공 응답만 유실된 경우 재시도로 같은 메시지가 두 번 발행될 수 있다.

5. Kafka Consumer의 메시지 중복 소비
   DB 저장 후 Offset Commit 전에 Consumer가 죽으면 재시작 시 같은 메시지를 다시 읽는다.

6. 운영자의 실패 메시지 수동 재처리나 복구 배치 재실행
```

#### 7-2. Redis 중복 체크와 requestId 멱등성의 차이

```
Redis 중복 체크 (issued-users Set)
- 기준: userId (사용자 단위)
- 질문: 이 사용자가 이미 선착순 판정을 통과했는가?
- 목적: 한 사용자가 선착순 자리를 여러 개 차지하지 못하게 막는 것
- 위치: API Server 앞단, 요청 진입 시점의 1차 방어
- 성격: 임시 상태 기반, Redis 장애 시 무력화될 수 있음
- 결과: 두 번째 요청은 DUPLICATE로 거부된다

requestId 기반 멱등성
- 기준: requestId (요청 단위)
- 질문: 이 요청이 이미 처리되었는가?
- 목적: 같은 요청이 여러 번 처리되어도 결과가 한 번만 반영되게 하는 것
- 위치: 요청 상태 테이블 기반, Consumer 처리 시점 포함 전 구간
- 성격: 영속 상태 기반, 시스템 재시도와 중복 소비까지 방어
- 결과: 재요청 시 새로 처리하지 않고 기존 처리 결과를 그대로 반환한다

핵심 차이:
Redis 중복 체크는 다른 요청이지만 같은 사용자를 막는다. → 사용자의 중복 클릭 방어
requestId 멱등성은 완전히 같은 하나의 요청이 재실행되는 것을 막는다.
 → 네트워크 재전송, Kafka 중복 소비, Consumer 재처리 방어

둘은 대체 관계가 아니라 서로 다른 층위의 보완 관계이며
DB Unique Key가 이 둘이 모두 놓친 경우의 최종 방어선이 된다.
```

### 8. 6주차: Outbox Pattern과 이벤트 발행 정합성

#### 8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유

```
DB 저장과 Kafka 이벤트 발행은 서로 다른 시스템에서 일어나는 별개의 작업이고
하나의 트랜잭션으로 묶을 수 없기 때문이다.

Consumer
  |
  | coupon_issue 저장 → 트랜잭션 commit 성공
  v
DB (발급 기록 있음)
  |
  | CouponIssued 결과 이벤트 발행 시도
  v
Kafka 장애 / 네트워크 오류 → 발행 실패

결과:
- DB에는 쿠폰 발급 기록이 있는데
- Notification Service는 알림을 보내지 못하고
- MyPage Service는 쿠폰함을 갱신하지 못하며
- Analytics Service의 통계에도 반영되지 않는다.

DB commit 직후 프로세스가 죽어도 동일한 문제가 발생한다.
3주차의 Redis SUCCESS 후 Kafka 발행 실패와 구조적으로 같은 문제다.
```

#### 8-2. Outbox Pattern이 필요한 이유

```
상태 저장과 이벤트 발행을 원자적으로 묶기 위해서다.

Kafka 발행은 DB 트랜잭션에 참여할 수 없지만
발행해야 할 이벤트를 DB 테이블에 기록하는 것은 트랜잭션에 참여할 수 있다.

Consumer
  |
  | DB Transaction 시작
  |   - coupon_issue 저장
  |   - outbox_event 저장   ← 발행할 이벤트를 같은 트랜잭션에 기록
  | commit
  v
DB
  |
  | (별도 프로세스)
  v
Outbox Publisher
  |
  | outbox_event 조회 → Kafka 발행 → 상태 SENT로 갱신
  v
Kafka

효과:
- coupon_issue 저장과 outbox_event 기록은 항상 함께 성공하거나 함께 실패한다.
  → DB에는 기록이 있는데 발행할 이벤트는 없는 상황이 사라진다.
- Kafka 발행이 실패하면 outbox_event가 PENDING으로 남아 나중에 다시 발행할 수 있다.

주의: Outbox는 DB 부하 감소가 아니라 이벤트 정합성 보장을 위한 패턴이다.
재발행이 일어날 수 있으므로 소비 측은 여전히 멱등해야 한다.
```

### 9. 7주차: EDA 기반 서비스 분리와 조회 구조

#### 9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?

```
Coupon Service
  |
  |--> Notification Service
  |--> MyPage Service
  |--> Analytics Service

문제:
1. 서비스 간 결합도가 높아진다.
   새로운 후속 서비스가 추가될 때마다 Coupon Service의 코드를 수정해야 한다.
2. 장애가 전파된다.
   Notification Service가 느려지거나 죽으면 Coupon Service의 발급 처리까지 지연되거나 실패한다.
   알림 발송 실패가 쿠폰 발급 실패로 이어져서는 안 된다.
3. 응답 시간이 후속 서비스들의 합만큼 길어진다.
4. 일부만 성공하는 부분 실패가 생긴다.
   알림은 갔는데 마이페이지는 갱신 안 됨 → 정합성이 깨진다.
5. 각 서비스가 독립적으로 배포하고 확장하기 어렵다.
```

#### 9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?

```
Coupon Issue Completed Event (Kafka)
  |
  |--> Notification Consumer
  |--> MyPage Consumer
  |--> Analytics Consumer

장점:
1. 결합도가 낮아진다.
   Coupon Service는 쿠폰이 발급되었다는 사실만 이벤트로 발행하면 되고
   누가 그 이벤트를 구독하는지 알 필요가 없다.
2. 장애가 격리된다.
   Notification Consumer가 죽어도 쿠폰 발급 자체는 정상 완료된다.
   메시지는 Kafka에 남아 있으므로 복구 후 이어서 처리할 수 있다.
3. 확장이 쉽다.
   새로운 후속 서비스는 이벤트를 구독하기만 하면 되고 Coupon Service는 수정하지 않아도 된다.
4. 각 서비스가 자신의 속도로 처리한다.
   느린 서비스가 빠른 서비스의 발목을 잡지 않는다.
5. 조회 성능 최적화가 가능하다.
   MyPage Service가 자신의 Read Model을 별도로 구축해 조회 트래픽을 원본 DB와 분리할 수 있다.
```

### 10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션

#### 10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?

```
Redis와 DB 사이의 정합성 불일치 문제다.

  Redis: user:1이 issued-users Set에 통과로 기록되어 있음
  DB   : coupon_issue에 발급 기록 없음

구체적 피해:
1. 사용자는 쿠폰을 받지 못했는데 재요청하면 Redis SISMEMBER에 걸려 DUPLICATE로 차단된다.
   → 아무것도 못 받고 재시도도 못 하는 상태에 갇힌다.
2. user:1이 선착순 자리 하나를 점유하고 있으므로
   실제로는 쿠폰이 남아 있는데도 다른 사용자에게 SOLD_OUT이 나간다.
   → 쿠폰 1,000개 중 999개만 실제 발급되는 기회 손실.
3. Redis 기준 통과 사용자 수와 DB 기준 실제 발급 수량이 달라져 운영/통계 지표가 어긋난다.

Redis 갱신과 DB 저장을 하나의 트랜잭션으로 묶을 수 없기 때문에 구조적으로 발생하는 문제이며
사후 복구로 해결해야 한다.
```

#### 10-2. Retry Topic과 DLQ가 필요한 이유

```
Consumer가 메시지 처리에 실패했을 때 두 극단은 모두 위험하다.

- 실패한 메시지를 그냥 버린다 → 요청이 유실되어 사용자가 쿠폰을 못 받는다.
- 무한히 즉시 재시도한다 → 같은 메시지에서 Consumer가 계속 멈추고(Poison Message)
  뒤의 정상 메시지들이 처리되지 못해 Lag이 폭증한다.

그래서 실패 유형을 나누어 처리한다.

| 실패 유형        | 예시                       | 처리 방향                  |
| 일시적 실패      | DB 일시 장애, 네트워크 오류 | Retry Topic으로 재시도     |
| 영구 실패        | 잘못된 메시지 형식          | DLQ로 이동                 |
| 비즈니스 실패    | 이미 발급받은 사용자, 품절  | 실패 상태 저장 후 정상 종료 |
| 외부 서비스 실패 | 알림 발송 실패              | 발급과 분리해 별도 재시도   |
| 정합성 실패      | Redis 성공 후 DB 저장 실패  | 보상 트랜잭션 검토          |

Retry Topic
일시적 실패는 시간이 지나면 성공할 가능성이 높다.
메인 Topic의 처리를 막지 않도록 별도 Topic으로 분리해 백오프를 두고 제한된 횟수만큼 재시도한다.

DLQ
재시도해도 성공할 수 없는 메시지를 격리 보관한다.
Consumer가 멈추지 않게 하면서도 메시지를 유실하지 않고
운영자가 나중에 원인을 분석하고 수동 재처리할 수 있게 한다.
```

#### 10-3. 보상 트랜잭션이 필요한 상황 예시

```
서로 다른 시스템에 걸친 작업 중 일부만 성공했을 때
이미 성공한 작업의 효과를 되돌리기 위해 필요하다.

1. Redis SUCCESS → Kafka 발행 실패
   보상: SREM으로 issued-users Set에서 userId 제거
   → 선착순 자리를 반납해 사용자가 재시도할 수 있게 한다.

2. Redis SUCCESS → Kafka 발행 성공 → Consumer의 DB 저장 최종 실패
   보상: 재시도를 모두 소진한 뒤 Redis에서 해당 userId 제거,
        요청 상태를 FAILED로 기록, 사용자에게 실패 안내
   → 점유된 선착순 자리를 회수해 쿠폰이 낭비되지 않게 한다.

3. DB 저장 성공 → 후속 이벤트 발행 실패
   보상: Outbox 재발행이나 복구 배치로 이벤트를 다시 발행한다.

4. 이벤트 종료 후 정합성 검증 배치
   Redis issued-users 목록과 DB coupon_issue 기록을 대조해
   - Redis에는 있는데 DB에 없는 건 → 재처리하거나 Redis에서 제거
   - DB에는 있는데 Redis에 없는 건 → DB를 원본으로 인정

주의: 보상 트랜잭션 자체도 실패할 수 있다.
실패 로그 저장, 복구 배치, 운영자 재처리 도구, DB Unique Key라는
다층 방어 구조를 함께 갖춰야 최종적으로 일관된 상태로 수렴한다.
```

## 보너스 과제. 나쁜 Redis 설계의 문제점 찾기

| 문제점 | 왜 문제인가? | 개선 방향 |
| --- | --- | --- |
| SCARD 조회 후 별도로 SADD 실행 | 조회와 추가 사이에 다른 요청이 끼어들어 여러 요청이 모두 같은 낡은 수량(999)을 보고 발급 가능으로 판단한다. limit(1,000)을 초과해 1,001명 이상이 통과할 수 있다 | SISMEMBER + SCARD + SADD를 Lua Script로 묶어 원자적으로 실행한다 |
| INCR request-count만으로 선착순 판정 | INCR는 숫자 증가만 원자적으로 보장할 뿐 사용자 중복을 구분하지 못한다. 한 사용자가 버튼을 3번 누르면 선착순 자리 3개를 차지해 쿠폰이 남았는데도 다른 사용자가 SOLD_OUT을 받는다 | 판정 기준을 중복 제거된 SCARD issued-users로 바꾸고 중복 확인을 같은 원자 단위 안에 넣는다. request-count는 모니터링 지표로만 사용한다 |
| Redis SUCCESS를 그대로 발급 성공으로 응답 | Redis 통과는 선착순 판정 통과일 뿐이다. Kafka 발행, Consumer 처리, DB 저장이 남아 있고 각 단계에서 실패할 수 있다. 성공이라 했는데 실제로는 쿠폰이 없는 상황이 발생한다 | Kafka 발행 성공까지 확인한 뒤 PENDING(202 Accepted)으로 응답하고, 최종 결과는 상태 조회 API나 마이페이지로 확인하게 한다 |
| Kafka 발행 실패를 무시하고 PENDING 응답 | Kafka에 메시지가 없어 Consumer가 영원히 처리하지 않는다. 재시도하면 Redis에 통과로 남아 있어 DUPLICATE로 차단된다. 아무것도 못 받고 재시도도 못 하는 상태가 된다 | 발행 실패 시 Redis 보상 처리(SREM)를 시도하고 접수 실패 응답을 반환한다. 실패 로그를 남겨 복구 배치와 운영자 재처리가 가능하게 한다 |
| DUPLICATE / SOLD_OUT 요청도 Kafka에 발행 | 실패가 확정된 99,000건이 Kafka에 쌓여 Consumer Lag이 폭증하고, 성공해야 할 1,000건의 최종 발급이 늦어진다. Redis를 도입한 의미가 사라진다 | Redis 판정 결과가 SUCCESS인 요청만 Kafka에 발행하고 DUPLICATE/SOLD_OUT은 API Server에서 즉시 응답하고 종료한다 |
| Redis만 믿고 DB에 UNIQUE(event_id, user_id)를 두지 않음 | Redis 장애나 유실, TTL 조기 만료, Kafka 메시지 중복 소비, Consumer 재처리, Redis를 우회하는 배치나 버그 등 Redis 방어가 뚫리는 경로가 많다. 그러면 같은 사용자에게 쿠폰이 두 번 발급된다 | DB에 UNIQUE(event_id, user_id) 제약을 걸어 어떤 경로로 들어와도 중복 저장이 불가능하게 만든다 |
| Redis Key에 TTL과 정리 전략이 없음 | issued-users Set이 이벤트마다 쌓여 Redis 메모리를 잠식한다. 반대로 TTL을 이벤트 진행 중에 만료되게 잡으면 Set이 비워져 이미 통과한 사용자가 다시 통과한다 | 이벤트 종료 시각 + 여유 기간으로 TTL을 설정하고, 이벤트 종료 후 Redis-DB 정합성 검증 배치를 돌린 뒤 Key를 정리한다 |
| 이벤트 수량(limit)의 원본을 Redis에만 저장 | Redis는 인메모리 임시 저장소라 장애 시 데이터가 유실될 수 있다. limit 값이 사라지면 수량 판정 자체가 무너진다 | 수량 제한 같은 중요한 값의 원본은 DB에 두고 Redis에는 빠른 판정을 위한 캐시와 상태만 둔다 |
