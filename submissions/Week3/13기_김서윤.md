# **Redis 기반 선착순 쿠폰 판정 구조 설계**

## **1. 과제 목표**

이번 3주차 과제의 목표는 **Redis를 이용해 선착순 쿠폰 발급 요청을 빠르게 판정하는 구조를 설계하는 것**이다.

1주차에서는 API Server가 모든 쿠폰 발급 처리를 직접 수행하는 구조와, 요청 접수와 실제 처리를 분리하는 비동기 구조를 비교했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달하고, Consumer가 뒤에서 실제 쿠폰 발급 처리를 수행하는 구조를 설계했다.

이번 3주차에서는 Kafka 앞단에 Redis를 도입한다.

기본 흐름은 다음과 같다.

```
Client
  ↓
API Server
  ↓
Redis 선착순 / 중복 판정
  ↓
SUCCESS인 요청만 Kafka 발행
  ↓
coupon.issue.requested Topic
  ↓
Coupon Issue Consumer
  ↓
DB
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Redis가 필요한 이유

Redis Key 설계

Redis 자료구조 선택

Set 기반 중복 요청 방지

SCARD / SADD를 분리했을 때 생기는 Race Condition

Lua Script를 이용한 원자적 처리

INCR 기반 방식의 장점과 한계

Redis SUCCESS / DUPLICATE / SOLD_OUT 결과에 따른 API 응답 설계

Redis SUCCESS 이후 Kafka 발행 실패 상황 분석

Redis SUCCESS가 최종 쿠폰 발급 성공을 의미하지 않는 이유

Redis, Kafka, DB의 역할 구분

앞으로 4~8주차에서 해결할 문제 연결하기
```

이번 과제의 핵심은 Redis 명령어를 외우는 것이 아니라, **Redis를 시스템 구조 안에서 어떤 역할로 사용할지 설계하는 것**이다.

특히 아래 내용을 반드시 구분해야 한다.

```
Redis SUCCESS
= 선착순 판정 통과

Kafka PENDING
= 발급 요청 메시지가 Kafka에 접수됨

DB ISSUED
= DB에 쿠폰 발급 기록이 최종 저장됨
```

즉, Redis에서 `SUCCESS`가 나왔다고 해서 쿠폰 발급이 최종 완료된 것은 아니다.

## **2. 기본 상황**

서비스에서 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트
쿠폰 수량: 1,000개
예상 요청 수: 이벤트 시작 직후 1분 안에 최대 10만 건
발급 조건: 사용자 1명당 하나의 이벤트에서 쿠폰 1개만 발급 가능
응답 방식: 요청 직후 최종 발급 결과를 바로 받지 않아도 됨
결과 확인 방식: 발급 상태 조회 API 또는 마이페이지에서 확인
```

2주차까지의 구조에서는 API Server가 쿠폰 발급 요청을 받으면 Kafka에 메시지를 발행하고, Consumer가 해당 메시지를 읽어 실제 발급 처리를 수행했다.

하지만 이 구조에서는 모든 요청이 Kafka와 Consumer까지 도달할 수 있다.

예를 들어 쿠폰 수량은 1,000개인데 요청이 100,000건 들어온다면, 실제로는 99,000건은 실패할 가능성이 높은 요청이다.

이번 주차에서는 이 실패할 요청을 DB까지 보내지 않도록 Redis에서 먼저 판정한다.

```
요청 100,000건
  ↓
Redis 선착순 / 중복 판정
  ↓
성공 1,000건만 Kafka 발행
  ↓
실패 99,000건은 SOLD_OUT 또는 DUPLICATE 응답
```

이번 주차에서는 API Server가 쿠폰 발급 요청을 받으면 Redis에서 다음을 먼저 확인한다고 가정한다.

```
1. 이미 통과한 사용자인가?

2. 쿠폰 수량이 아직 남아 있는가?

3. 선착순 안에 들어온 요청인가?
```

Redis 판정 결과가 `SUCCESS`인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 `DUPLICATE` 또는 `SOLD_OUT`인 경우에는 Kafka에 메시지를 발행하지 않는다.

## **3. 이번 과제의 전제 조건**

이번 과제에서는 아래 전제를 따른다.

```
API Server는 쿠폰 발급 요청을 받으면 먼저 로그인 여부와 이벤트 시간을 확인한다.

그 다음 Redis를 이용해 선착순 / 중복 여부를 판정한다.

Redis 판정 결과가 SUCCESS인 경우에만 Kafka에 메시지를 발행한다.

Redis 판정 결과가 DUPLICATE 또는 SOLD_OUT이면 Kafka에 메시지를 발행하지 않는다.

Redis SUCCESS는 최종 쿠폰 발급 성공이 아니다.

최종 쿠폰 발급 성공은 Consumer가 DB에 쿠폰 발급 기록을 저장한 뒤 결정된다.
```

이번 주차에서 사용할 Redis 결과는 아래 세 가지로 단순화한다.

```
SUCCESS:
Redis 선착순 판정 통과

DUPLICATE:
이미 Redis에서 통과한 사용자

SOLD_OUT:
쿠폰 수량 소진
```

이번 주차에서는 Redis를 사용해 선착순 판정을 수행하지만, 아래 내용은 깊게 다루지 않는다.

```
DB Unique Key 상세 설계

requestId 기반 멱등성 상세 설계

Outbox Pattern 상세 설계

Retry Topic / DLQ 상세 설계

보상 트랜잭션 상세 설계
```

다만 이 문제들이 왜 이후 주차에서 필요한지는 간단히 연결해서 설명해야 한다.

## **과제 1. Redis 기반 선착순 처리 구조 그리기**

쿠폰 발급 요청이 들어왔을 때 Redis를 이용해 선착순 여부와 중복 여부를 판정하는 구조를 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

API Server

Redis

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

DB
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | 로그인 여부 / 이벤트 시간 검증
  v
Redis
  |
  | Lua Script로 중복 여부와 수량 확인
  | SUCCESS / DUPLICATE / SOLD_OUT 반환
  v
API Server
  |
  | SUCCESS인 경우만 Kafka Producer 호출
  v
Kafka Producer
  |
  | coupon.issue.requested 메시지 발행
  v
coupon.issue.requested Topic
  |
  | Consumer Group이 메시지 소비
  v
Coupon Issue Consumer
  |
  | DB에 최종 쿠폰 발급 기록 저장
  v
DB
```

### **2. Redis의 역할**

```
Redis는 API Server와 Kafka 사이에서 선착순 판정 필터 역할을 한다. 기준은 하단 참고.
1. 이미 통과한 사용자인가?
2. 쿠폰 수량이 남아 있는가?
3. 이번 요청을 Kafka로 넘겨도 되는가?
따라서 Redis의 SUCCESS는 최종 발급 성공이 아니라 Kafka와 DB 단계로 넘어갈 수 있는 선착순 판정 통과를 의미한다.
```

### **3. Kafka의 역할**

```
Kafka는 Redis를 통과한 쿠폰 발급 요청을 Consumer에게 비동기로 전달하는 역할을 한다.
Kafka는 API 서버로부터 오는 레디스 성공요청만 Topic에 발행하고, Consumer가 처리 가능한 속도로 메시지를 가져가게 한다.
Kafka는 발급 요청을 안정적으로 전달하고 처리 속도를 완충하는 메시지 브로커 역할을 한다.
```

### **4. DB의 역할**

```
DB는 최종 쿠폰 발급 기록을 저장하는 원본 저장소 역할을 한다.
Consumer가 Kafka 메시지를 소비한 뒤 DB에 발급 내역을 저장하고, UNIQUE(event_id, user_id) 같은 제약 조건으로 중복 발급을 마지막으로 방어한다.
```

### **5. Redis를 통과한 요청만 Kafka에 발행해야 하는 이유**

```
Redis를 통과하지 못한 요청은 이미 중복 요청이거나 품절 이후 요청이다.
이 요청들까지 Kafka에 발행하면 Consumer와 DB가 결국 실패할 요청을 처리해야 한다.
쿠폰 수량보다 훨씬 많은 요청이 들어오는 상황에서는 실패할 요청들이 Kafka와 DB 부하를 만든다.
따라서 Redis에서 SUCCESS로 판정된 요청만 Kafka에 발행해야 Kafka, Consumer, DB가 실제로 처리해야하는 요청에 집중할 수 있다.
```

## **과제 2. Redis가 필요한 이유 설명하기**

2주차 Kafka 기반 구조만으로는 해결하기 어려운 문제를 분석하고, Redis가 필요한 이유를 설명한다.

아래 상황을 기준으로 작성한다.

```
쿠폰 수량: 1,000개
요청 수: 100,000건
발급 조건: 사용자 1명당 1개만 발급 가능
```

### **1. Redis 없이 Kafka와 DB만 사용하는 구조의 문제점**

```
Redis 없이 Kafka와 DB만 사용하면 모든 요청이 일단 Kafka에 들어간다.
쿠폰 수량은 1,000개뿐인데 100,000건의 요청이 모두 Kafka와 Consumer를 거쳐 DB까지 도달할 수 있다.
이 경우 DB가 수량 확인, 중복 확인, 저장 시도를 모두 감당해야 하므로 DB Lock 경합과 부하가 커진다.
또한 같은 사용자의 반복 요청이나 품절 이후 요청도 뒤늦게 DB에서 실패 처리되므로 시스템 자원을 불필요하게 사용하게 된다.
```

### **2. 모든 요청이 Kafka, Consumer, DB까지 도달하면 어떤 문제가 생기는가?**

```
모든 요청이 Kafka, Consumer, DB까지 도달하면 Consumer Lag이 커지고 DB에 불필요한 조회와 저장 시도가 집중된다.
실제로 성공 가능한 요청은 1,000건인데 나머지 99,000건도 수량 확인과 중복 확인을 위해 DB에 접근한다.
그 결과 DB 사용량, Lock 경합, 트랜잭션 대기 시간이 증가하고 정상 요청 처리까지 느려질 수 있다.
```

### **3. 쿠폰이 이미 품절된 뒤에도 요청이 계속 처리되면 어떤 문제가 생기는가?**

```
쿠폰이 이미 품절되었는데도 요청이 계속 처리되면 실패가 확정된 요청이 계속 Kafka에 쌓이고 Consumer와 DB까지 도달한다.
사용자 입장에서는 응답이 늦어지고, 시스템 입장에서는 의미 없는 메시지 처리와 DB 조회가 계속 발생한다.
특히 이벤트 직후 트래픽이 몰릴 때 품절 이후 요청을 빠르게 차단하지 못하면 전체 시스템 병목이 발생할 수 있다. 
```

### **4. 같은 사용자가 버튼을 여러 번 누르면 어떤 문제가 생기는가?**

```
같은 사용자가 버튼을 여러 번 누르면 동일 사용자의 요청이 여러 개 Kafka에 발행될 수 있다.
이 경우 Consumer는 같은 사용자의 발급 요청을 반복 처리해야 하고, DB에서는 중복 발급 여부를 계속 확인해야 한다.
DB Unique Key가 없다면 중복 발급 위험이 생기고, Unique Key가 있더라도 중복 저장 실패 처리가 반복되어 불필요한 부하가 발생한다.
```

### **5. Redis를 도입하면 어떤 요청을 앞단에서 차단할 수 있는가?**

```
1. 이미 Redis Set에 존재하는 사용자의 중복 요청
2. 쿠폰 제한 수량이 모두 소진된 뒤 들어온 요청
3. 선착순 기준을 통과하지 못한 요청
```

## **과제 3. Redis Key와 자료구조 설계하기**

쿠폰 이벤트별로 Redis Key를 어떻게 설계할지 작성한다.

이번 과제에서는 아래 Key를 예시로 고려한다.

```
coupon:{eventId}:issued-users

coupon:{eventId}:request-count

coupon:{eventId}:metadata
```

단, 모든 Key를 반드시 사용해야 하는 것은 아니다.

Set + Lua Script 방식을 선택한다면 `request-count` 없이 `SCARD coupon:{eventId}:issued-users`로 통과 사용자 수를 판단할 수도 있다.

자신이 선택한 구조에 맞게 필요한 Key를 설계한다.

### **1. Redis Key 목록**

| **Redis Key** | **자료구조** | **저장하는 값** | **필요한 이유**                                                              |
| --- | --- | --- |-------------------------------------------------------------------------|
| `coupon:{eventId}:issued-users` | Set | Redis 선착순 판정을 통과한 사용자 ID 목록 | 사용자 중복 요청을 막고, `SCARD`로 현재 통과 사용자 수를 판단하기 위해 필요하다.                      |
| `coupon:{eventId}:request-count` | String Counter | `INCR`로 증가하는 요청 순번 또는 요청 수 | INCR 기반 방식을 비교하거나 요청 순번을 추적할 때 사용할 수 있다. 최종 발급 수량은 아니다!!                |
| `coupon:{eventId}:metadata` | Hash | 쿠폰 제한 수량, 이벤트 시작/종료 시간 등 이벤트 메타 정보 | API Server가 Redis 판정에 필요한 이벤트 정보를 빠르게 조회하기 위해 사용할 수 있다. 원본 데이터는 DB에 둔다. |

### **2. 이벤트 ID가 100일 때 실제 Redis Key 예시**

```
coupon:100:issued-users
coupon:100:request-count
coupon:100:metadata
```

### **3. `coupon:{eventId}:issued-users`에는 어떤 값이 저장되는가?**

```
coupon:{eventId}:issued-users에는 Redis 선착순 판정을 통과한 사용자 ID가 저장된다.
Set은 같은 값을 중복 저장하지 않기 때문에 같은 사용자의 반복 요청을 빠르게 판정할 수 있다.
```

### **4. `coupon:{eventId}:request-count`를 사용한다면 어떤 역할을 하는가?**

```
coupon:{eventId}:request-count는 INCR 기반 방식을 사용할 때 요청 순번을 계산하는 카운터 역할을 한다.
요청이 들어올 때마다 INCR로 값을 1씩 증가시키고, 증가 결과가 제한 수량 이하인지 확인할 수 있다.
다만 중복 사용자 요청도 카운터를 증가시킬 수 있으므로 request-count를 최종 발급 수량으로 보면 안 된다.
```

### **5. Redis Key에 TTL이 필요한 이유는 무엇인가?**

```
Redis는 빠른 판정을 위한 임시 상태 저장소이기 때문에 이벤트가 끝난 뒤에도 Key가 계속 남아 있으면 메모리를 불필요하게 사용한다.
또한 오래된 이벤트의 issued-users, request-count, metadata가 남아 있으면 운영 중 혼동이 생길 수 있다.
따라서 이벤트 종료 후 일정 시간이 지나면 삭제되도록 TTL을 설정하는 것이 좋다.
```

### **6. 이벤트가 끝난 뒤 Redis Key를 어떻게 정리할 것인가?**

```
이벤트 종료 후 결과 정산과 장애 복구에 필요한 시간이 지난 뒤 Redis Key를 삭제한다.
최종 발급 기록은 DB에 남기고 Redis에는 빠른 판정에 필요한 임시 데이터만 유지한다.
```

## **과제 4. Redis Set 기반 중복 요청 방지 설계하기**

Redis Set을 이용해 같은 사용자의 중복 요청을 어떻게 막을 수 있는지 설명한다.

### **1. Redis Set을 사용하는 이유**

```
Redis Set은 같은 값을 중복 저장하지 않는 자료구조이기 때문에 사용자 중복 요청을 방지할 수 있다, 
사용자 ID를 Set에 저장하면 첫 요청은 새 값으로 추가되고, 같은 사용자의 두 번째 요청은 이미 존재하는 값으로 판단된다.
또한 SCARD로 Set에 저장된 고유 사용자 수를 확인할 수 있어 현재 선착순 통과 인원도 계산할 수 있다.
```

### **2. `SADD` 명령어의 결과값 1과 0은 각각 무엇을 의미하는가?**

```
SADD 결과값 1은 해당 값이 Set에 새로 추가되었다는 의미이다.
즉, 이 사용자는 아직 통과한 적이 없는 사용자로 볼 수 있다.
SADD 결과값 0은 해당 값이 이미 Set에 존재한다는 의미이다.
즉, 같은 사용자가 이미 요청을 통과했으므로 중복 요청으로 판단할 수 있다.
```

### **3. 같은 사용자가 두 번 요청했을 때 Redis Set에서 어떤 일이 일어나는가?**

```
SADD coupon:100:issued-users user:1 실행 결과가 0이 된다.
이미 Set에 user:1이 존재하므로 중복 요청으로 판단한다.
```

### **4. Redis Set 구조를 그림으로 표현하기**

```
Redis Set: coupon:100:issued-users

+-----------------------------+
| user:1                      |
| user:5                      |
| user:20                     |
| user:77                     |
+-----------------------------+

user:1이 다시 요청하면 이미 Set에 존재하므로 DUPLICATE
새로운 user:100이 요청하고 수량이 남아 있으면 Set에 추가 후 SUCCESS
```

### **5. Redis Set만 사용하면 쿠폰 수량 제한까지 자동으로 해결되는가?**

```
아니다. Redis Set은 중복 사용자 방지에는 효과적이지만 Set만 사용한다고 해서 수량 제한까지 자동으로 안전하게 해결되지는 않는다.
수량 제한을 하려면 SCARD로 현재 Set 크기를 확인하고 제한 수량과 비교해야 한다.
이때 SCARD와 SADD를 애플리케이션에서 따로 실행하면 Race Condition이 생길 수 있으므로 Lua Script로 묶어 원자적으로 처리하는 것이 안전하다.
```

### **6. Set에 저장된 사용자 수를 확인하기 위해 어떤 명령어를 사용할 수 있는가?**

```
SCARD 명령어를 사용할 수 있다.
이 명령은 해당 Set에 저장된 고유 사용자 수를 반환한다.
```

## **과제 5. 잘못된 Redis 명령 조합의 Race Condition 분석하기**

아래 방식은 위험할 수 있다.

```
1. SCARD로 현재 통과 사용자 수를 확인한다.
2. 수량이 남아 있으면 SADD로 사용자를 추가한다.
```

아래 상황을 기준으로 Race Condition을 분석한다.

```
쿠폰 제한 수량: 1,000개
현재 통과 사용자 수: 999명
남은 쿠폰 수량: 1개

동시에 user:A와 user:B가 요청한다.
```

### **1. `SCARD 후 SADD` 방식의 처리 흐름**

```
1. API Server가 SCARD coupon:100:issued-users로 현재 통과 사용자 수를 조회한다.
2. 조회 결과가 limit보다 작으면 아직 수량이 남아 있다고 판단한다.
3. SADD coupon:100:issued-users userId로 사용자를 Set에 추가한다.
4. 추가 후 SUCCESS를 반환한다.

문제는 1번 수량 확인과 3번 사용자 추가가 하나의 원자적 작업이 아니라는 점이다.
```

### **2. user:A와 user:B가 동시에 요청했을 때 시간 순서 다이어그램**

```
초기 상태: coupon:100:issued-users size = 999, limit = 1000

시간 1: user:A 요청 → SCARD 결과 999
시간 2: user:B 요청 → SCARD 결과 999
시간 3: user:A → 999 < 1000 이므로 발급 가능 판단
시간 4: user:B → 999 < 1000 이므로 발급 가능 판단
시간 5: user:A → SADD user:A 성공, Set size = 1000
시간 6: user:B → SADD user:B 성공, Set size = 1001

결과: 쿠폰 제한 수량은 1000개인데 1001명이 Redis를 통과할 수 있다.
```

### **3. 왜 두 사용자 모두 발급 가능하다고 판단할 수 있는가?**

```
user:A와 user:B가 거의 동시에 SCARD를 실행하면 둘 다 같은 시점의 Set 크기인 999를 볼 수 있다.
두 요청 모두 아직 1개가 남아 있다고 판단한 뒤 SADD를 실행한다.
수량 확인 이후 사용자 추가 전까지 다른 요청이 끼어들 수 있기 때문에 두 사용자 모두 발급 가능하다고 판단할 수 있다.
```

### **4. 최종적으로 쿠폰이 1,001개 통과될 수 있는 이유**

```
SCARD 결과를 기준으로 두 요청이 모두 통과 가능하다고 판단한 뒤 각각 SADD에 성공할 수 있기 때문이다.
Set 입장에서는 user:A와 user:B가 서로 다른 값이므로 둘 다 정상적으로 추가된다.
그 결과 기존 999명에 user:A와 user:B가 모두 추가되어 최종 Set 크기가 1001이 될 수 있다.
```

### **5. 이 문제의 핵심 원인은 무엇인가?**

```
수량 확인과 사용자 추가가 분리되어 있다는 점이다.
SCARD와 SADD는 각각의 명령 자체는 원자적으로 실행되지만, 두 명령의 조합 전체가 하나의 원자적 작업은 아니다.
따라서 SCARD와 SADD 사이에 다른 요청이 끼어들어 경쟁상태가 발생한다.
```

### **6. 이 문제를 해결하려면 어떤 작업들이 하나로 묶여야 하는가?**

```
SISMEMBER, SCARD, SADD를 Lua Script로 묶어 한 번에 처리해야 한다.
```

## **과제 6. Redis Lua Script 기반 원자적 처리 설계하기**

Redis Lua Script를 사용해 중복 확인, 수량 확인, 사용자 추가를 하나의 원자적 작업으로 처리하는 구조를 설계한다.

완벽한 Lua 문법을 작성하는 것이 목적이 아니다.

중요한 것은 아래 세 작업이 하나의 흐름으로 처리되어야 한다는 점을 설명하는 것이다.

```
SISMEMBER

SCARD

SADD
```

### **1. Lua Script로 묶어야 하는 작업 목록**

```
1. SISMEMBER로 이미 통과한 사용자인지 확인한다.

2. SCARD로 현재 통과 사용자 수가 제한 수량보다 작은지 확인한다.

3. 조건을 만족하면 SADD로 사용자를 issued-users Set에 추가한다.
```

### **2. Lua Script 처리 흐름 다이어그램**

```
API Server
  |
  | EVAL Lua Script
  v
Redis
  |
  | 1. SISMEMBER로 userId 중복 확인
  |    이미 있으면 DUPLICATE 반환
  |
  | 2. SCARD로 현재 통과 사용자 수 확인
  |    currentCount >= limit 이면 SOLD_OUT 반환
  |
  | 3. SADD로 userId 추가
  |    추가 성공 후 SUCCESS 반환
  v
API Server
  |
  | SUCCESS이면 Kafka 발행
  | DUPLICATE 또는 SOLD_OUT이면 즉시 응답
```

### **3. Lua Script 반환값 설계**

| **반환값** | **의미** | **API Server 처리** |
| --- | --- | --- |
| SUCCESS | Redis 선착순 판정 통과 | Kafka 메시지 발행을 시도하고, 발행 성공 시 PENDING 응답을 반환한다. |
| DUPLICATE | 이미 Redis Set에 존재하는 사용자 | Kafka에 발행하지 않고 중복 요청 응답을 반환한다. |
| SOLD_OUT | 쿠폰 제한 수량이 모두 소진됨 | Kafka에 발행하지 않고 품절 응답을 반환한다. |

### **4. Lua Script를 사용하면 Race Condition을 어떻게 줄일 수 있는가?**

```
Lua Script를 사용하면 Redis가 스크립트 전체를 하나의 작업처럼 실행한다.
따라서 SISMEMBER, SCARD, SADD 사이에 다른 요청이 끼어들 수 없다.
수량을 확인한 직후 다른 사용자가 먼저 추가되는 상황을 막을 수 있으므로 SCARD 후 SADD 방식에서 발생하던 Race Condition을 줄일 수 있다.
```

### **5. Redis Lua Script가 성공했다고 해서 최종 쿠폰 발급이 완료된 것은 아닌 이유**

```
Redis Lua Script의 SUCCESS는 선착순 판정을 통과했다는 의미일 뿐이다.
아직 Kafka에 메시지가 정상 발행되었는지, Consumer가 메시지를 소비했는지, DB에 최종 발급 기록이 저장되었는지는 보장하지 않는다.
최종 쿠폰 발급 완료는 Consumer가 DB에 발급 기록을 저장하고 DB 정합성 검증까지 통과했을 때 결정된다.
```

## **과제 7. INCR 기반 선착순 판정 방식의 장점과 한계 분석하기**

Redis에서 `INCR` 기반으로 선착순 판정을 하는 방법을 분석한다.

이 방식은 요청이 들어올 때마다 `request-count`를 증가시키고, 그 값이 제한 수량 이하이면 통과 후보로 보는 방식이다.

```
coupon:{eventId}:request-count
```

필요하다면 중복 사용자 관리를 위해 Set을 함께 사용할 수도 있다.

```
coupon:{eventId}:issued-users
```

### **1. INCR 기반 방식의 기본 흐름**

```
1. 사용자가 쿠폰 발급 요청을 보낸다.
2. API Server가 INCR coupon:{eventId}:request-count를 실행한다.
3. Redis는 증가된 요청 순번을 반환한다.
4. 반환된 값이 쿠폰 제한 수량 이하이면 선착순 후보로 본다.
5. 필요하다면 issued-users Set으로 중복 사용자인지 확인한다.
6. 통과 가능하다고 판단한 요청만 Kafka에 발행한다.
```

### **2. `INCR` 명령어가 보장하는 것은 무엇인가?**

```
INCR 명령어는 카운터 증가 자체의 원자성을 보장한다.
동시에 여러 요청이 들어와도 각 요청은 서로 다른 증가 결과를 받는다.
```

### **3. `INCR` 명령어가 보장하지 못하는 것은 무엇인가?**

```
INCR은 사용자 중복 여부를 보장하지 못한다.
같은 사용자가 버튼을 여러 번 누르면 그 요청들도 모두 카운터를 증가시킬 수 있다.
또한 INCR 결과가 제한 수량 이하라고 해서 해당 사용자가 중복이 아니거나 최종적으로 DB에 발급 기록이 저장된다는 것을 보장하지 않는다.
```

### **4. 아래 상황에서 어떤 문제가 생기는지 설명하기**

```
쿠폰 수량: 3개

user:1 첫 번째 요청 → INCR 결과 1
user:1 두 번째 요청 → INCR 결과 2
user:1 세 번째 요청 → INCR 결과 3
user:2 첫 번째 요청 → INCR 결과 4
```

답변:

```
user:1의 중복 요청이 request-count의 1, 2, 3번 자리를 모두 차지한다.
쿠폰 수량이 3개라면 INCR 기준으로는 user:1의 세 요청이 선착순 범위 안에 들어온 것처럼 보인다.
그 결과 실제로는 user:1 한 명만 유효한 사용자인데 user:2의 첫 요청은 INCR 결과 4가 되어 SOLD_OUT으로 처리될 수 있다.
즉 중복 요청이 선착순 자리를 낭비하는 문제가 생긴다.
```

### **5. 위 상황을 다이어그램으로 표현하기**

```
request-count 기준 선착순 자리

+---------+---------+---------+---------+
| 순번 1  | 순번 2  | 순번 3  | 순번 4  |
+---------+---------+---------+---------+
| user:1  | user:1  | user:1  | user:2  |
+---------+---------+---------+---------+
   통과      중복      중복      품절

문제: 한 사용자의 반복 요청이 여러 순번을 차지해 다른 사용자의 기회를 밀어낼 수 있다.
```

### **6. `request-count`를 최종 발급 수량으로 보면 안 되는 이유**

```
request-count는 요청이 몇 번 들어왔는지를 나타내는 값에 가깝다.
중복 사용자 요청, 품절 이후 요청, 실패한 요청도 카운터를 증가시킬 수 있다.
따라서 request-count는 최종 발급 수량이 아니라 요청 순번 또는 전체 요청 수에 가까운 값이다.
최종 발급 수량은 DB에 실제 저장된 발급 기록 수와 구분해야 한다.
```

### **7. 실제 통과 사용자 수는 어떤 기준으로 판단하는 것이 더 적절한가?**

```
실제 통과 사용자 수는 중복이 제거된 issued-users Set의 크기로 판단하는 것이 더 적절하다.
즉 SCARD coupon:{eventId}:issued-users로 현재 Redis 선착순 판정을 통과한 고유 사용자 수를 확인하는 방식이 더 안전하다.
최종 발급 완료 수는 DB의 coupon_issue 저장 건수를 기준으로 판단해야 한다.
```

### **8. INCR 기반 방식과 Redis Set + Lua Script 방식을 비교하기**

| **구분** | **INCR 기반 방식** | **Set + Lua Script 방식** |
| --- | --- | --- |
| 수량 판단 기준 | `request-count`를 증가시킨 결과값 | `issued-users` Set의 크기 |
| 중복 사용자 방지 | Set을 별도로 함께 사용해야 함 | `SISMEMBER`와 `SADD`로 한 흐름에서 처리 가능 |
| 장점 | 구현이 단순하고 요청 순번을 빠르게 계산할 수 있음 | 중복 확인, 수량 확인, 사용자 추가를 원자적으로 묶을 수 있음 |
| 단점 | 중복 요청도 카운터를 증가시켜 선착순 자리를 낭비할 수 있음 | Lua Script 작성과 Redis 장애/보상 처리를 함께 고민해야 함 |
| 최종 권장 여부 | 단순 참고 방식으로는 가능하지만 최종 발급 수량 기준으로는 부적절함 | 이번 구조에서 더 권장되는 방식 |

---

## **과제 8. Redis 판정 결과에 따른 API 응답 설계하기**

API Server는 Redis 판정 결과에 따라 서로 다른 응답을 반환해야 한다.

이번 과제에서는 아래 세 가지 결과를 기준으로 API 응답을 설계한다.

```
SUCCESS

DUPLICATE

SOLD_OUT
```

단, `SUCCESS`인 경우에도 사용자에게 최종 발급 성공 응답을 주면 안 된다.

`SUCCESS`인 경우에는 Kafka 발행 성공까지 확인한 뒤 `PENDING` 응답을 준다고 가정한다.

HTTP Status Code는 자유롭게 정하되, 왜 그렇게 정했는지 이유를 함께 작성한다.

---

### **상황 A. Redis 결과가 SUCCESS이고 Kafka 발행도 성공한 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다.",
  "requestId": "req-001"
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
HTTP Status Code는 202 Accepted를 사용할 수 있다.
이유는 요청이 Redis 판정을 통과했고 Kafka에도 접수되었지만, 최종 쿠폰 발급 처리는 아직 완료되지 않았기 때문이다.
202 Accepted는 요청이 접수되었고 비동기 처리가 진행될 수 있음을 표현하기에 적합하다.
```

#### **3. 이 응답이 최종 쿠폰 발급 성공을 의미하지 않는 이유**

```
이 응답은 Redis 선착순 판정과 Kafka 발행이 성공했다는 의미일 뿐이다.
아직 Consumer가 메시지를 소비하지 않았고, DB에 쿠폰 발급 기록도 저장되지 않았다.
Consumer 처리 중 DB 장애, 중복 메시지, 트랜잭션 실패 등이 발생할 수 있으므로 PENDING을 최종 발급 성공으로 보면 안 된다.
```

#### **4. 이 응답 이후 Consumer는 어떤 처리를 수행하는가?**

```
Consumer는 coupon.issue.requested Topic에서 메시지를 읽는다.
그 후 이벤트 ID, 사용자 ID, requestId 등을 기준으로 실제 쿠폰 발급 가능 여부를 최종 확인하고 DB에 발급 기록을 저장한다.
DB 저장이 성공하면 사용자의 쿠폰 발급 상태는 ISSUED가 된다.
```

---

### **상황 B. Redis 결과가 DUPLICATE인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "DUPLICATE",
  "message": "이미 쿠폰 발급 요청을 완료한 사용자입니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
HTTP Status Code는 409 Conflict를 사용할 수 있다.
같은 이벤트에서 이미 쿠폰 발급 요청을 통과한 사용자가 다시 요청한 상황이므로, 현재 리소스 상태와 충돌하는 중복 요청으로 볼 수 있기 때문이다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
DUPLICATE 요청은 이미 Redis에서 통과한 사용자에 대한 반복 요청이다.
이 요청을 Kafka에 다시 발행하면 Consumer와 DB가 같은 사용자의 발급 요청을 다시 처리해야 한다.
중복 발급 위험이 커지고, DB Unique Key가 있더라도 불필요한 중복 저장 실패 처리가 발생한다/
```

#### **4. 같은 사용자가 여러 번 요청했을 때 사용자에게 어떤 UX를 제공할 수 있는가?**

```
사용자에게는 이미 처리중이라는 안내를 제공할 수 있다.
버튼을 비활성화하거나 로딩/접수 완료 상태를 보여주고, 발급 상태 조회 API로 PENDING, ISSUED, FAILED 상태를 확인하도록 유도할 수 있다.
```

---

### **상황 C. Redis 결과가 SOLD_OUT인 경우**

#### **1. API 응답 JSON**

```json
{
  "status": "SOLD_OUT",
  "message": "쿠폰이 모두 소진되었습니다."
}
```

#### **2. 이 응답에 사용할 HTTP Status Code와 이유**

```
HTTP Status Code는 409 Conflict를 사용할 수 있다.
요청 형식 자체는 올바르지만 쿠폰 수량이 이미 소진되어 더 이상 발급 요청을 접수할 수 없는 상태이기 때문이다.
또는 정책에 따라 200 OK로 품절 상태를 응답할 수도 있지만, 여기서는 발급 요청이 현재 이벤트 상태와 충돌한다고 보아 409를 선택한다.
```

#### **3. 이 경우 Kafka에 메시지를 발행하면 안 되는 이유**

```
SOLD_OUT 요청은 이미 쿠폰 수량이 모두 소진된 이후의 요청이다.
이 요청을 Kafka에 발행해도 Consumer와 DB 단계에서 실패할 가능성이 높다.
따라서 Kafka, Consumer, DB의 부하를 줄이기 위해 품절 요청은 Redis에서 즉시 차단하고 Kafka에 발행하지 않아야 한다.
```

#### **4. 품절 이후 요청을 Redis에서 빠르게 차단하는 것이 왜 중요한가?**

```
품절 이후 요청은 성공 가능성이 없는데도 이벤트 트래픽 대부분을 차지할 수 있다.
Redis에서 빠르게 SOLD_OUT을 반환하면 Kafka 메시지 적재량, Consumer 처리량, DB 조회/저장 시도를 크게 줄일 수 있다.
결과적으로 시스템 전체 부하를 줄이고 사용자에게도 빠른 응답을 제공할 수 있다.
```

## **과제 9. Redis SUCCESS 이후 Kafka 발행 실패 상황 분석하기**

Redis에서 `SUCCESS`가 나왔지만 Kafka 발행에 실패할 수 있다.

아래 상황을 읽고 질문에 답한다.

```
1. 사용자가 쿠폰 발급 요청을 보냈다.

2. API Server가 Redis Lua Script를 실행했다.

3. Redis가 SUCCESS를 반환했다.

4. API Server가 Kafka에 메시지를 발행하려고 했다.

5. Kafka 장애로 메시지 발행에 실패했다.
```

### **1. 이 상황의 전체 흐름 다이어그램**

```
Client
  |
  | 쿠폰 발급 요청
  v
API Server
  |
  | Redis Lua Script 실행
  v
Redis
  |
  | SUCCESS 반환
  | issued-users Set에 userId 저장됨
  v
API Server
  |
  | Kafka 메시지 발행 시도
  v
Kafka 장애
  |
  | 발행 실패
  v
API Server
  |
  | PENDING 응답 불가
  | Redis 보상 처리 또는 재시도 필요
  v
Client
```

### **2. Redis에는 어떤 상태가 남아 있을 수 있는가?**

```
Redis에는 해당 사용자가 선착순 판정을 통과한 상태가 남아 있을 수 있다.
예를 들어 coupon:100:issued-users Set에 userId가 이미 추가되어 있을 수 있다.
즉 Redis 기준으로는 SUCCESS 상태인데 Kafka에는 메시지가 없는 불일치 상태가 생긴다.
```

### **3. Kafka에는 어떤 문제가 생기는가?**

```
Kafka에는 해당 쿠폰 발급 요청 메시지가 존재하지 않는 문제가 생긴다.
API Server가 Kafka에 메시지를 발행하지 못했으므로 coupon.issue.requested Topic에 이 요청이 적재되지 않는다.
따라서 Kafka 기준으로는 발급 요청이 접수되지 않은 상태이다.
```

### **4. Consumer는 왜 이 요청을 처리할 수 없는가?**

```
Consumer는 Kafka Topic에 있는 메시지만 읽어서 처리한다. 
Kafka 발행이 실패하면 coupon.issue.requested Topic에 해당 요청 메시지가 없기 때문에 Consumer는 이 요청의 존재를 알 수 없다.
따라서 DB 저장 처리도 수행할 수 없다.
```

### **5. 사용자에게 `PENDING` 응답을 줘도 되는가? 그 이유는?**

```
PENDING 응답을 주면 안 된다.
PENDING은 Redis 판정 통과뿐 아니라 Kafka에 발급 요청 메시지가 접수되었다는 의미까지 포함해야 한다.
Kafka 발행에 실패한 상태에서 PENDING을 응답하면 사용자는 요청이 접수되었다고 생각하지만 Consumer는 처리할 메시지를 받지 못하는 불일치가 생긴다.
```

### **6. 이 상황에서 가능한 보상 처리 방법을 작성하라**

예시는 다음과 같다.

```
- Redis Set에서 userId 제거
- 실패 로그 저장
- Kafka 발행 재시도
- 복구 배치에서 재처리
```

답변:

```
- Redis Set에서 해당 userId를 제거해 선착순 자리를 복구한다.
- Kafka 발행 실패 로그를 저장한다.
- Kafka 발행을 즉시 재시도한다.
- 재시도 큐나 복구 배치에서 나중에 다시 발행한다.
- 요청 상태를 ACCEPT_FAILED로 저장하고 사용자에게 다시 시도하도록 안내한다.
- 운영자가 재처리할 수 있도록 requestId, eventId, userId, 실패 원인을 기록한다.
```

### **7. Redis 보상 처리도 실패할 수 있는 이유**

```
Redis 보상 처리도 네트워크 오류, Redis 장애, timeout, API Server 장애 때문에 실패할 수 있다.
예를 들어 Kafka 발행 실패 후 Redis Set에서 userId를 제거하려는 순간 Redis 연결이 끊기면 보상 처리 자체가 수행되지 않는다.
이 경우 Redis에는 성공 상태가 남고 Kafka에는 메시지가 없는 불일치가 계속 유지될 수 있다.
```

### **8. 이 문제는 앞으로 어떤 주차 내용과 연결되는가?**

```
이 문제는 5주차 requestId 기반 멱등성, 6주차 Outbox Pattern, 8주차 Retry / DLQ / 보상 트랜잭션과 연결된다.
특히 Redis SUCCESS 이후 Kafka 발행 실패는 시스템 사이 상태 불일치 문제이므로 재시도, 실패 로그, 복구 배치, 보상 처리 전략이 필요하다.
```

## **과제 10. Redis, Kafka, DB 역할 구분과 이후 주차 연결하기**

Redis, Kafka, DB는 모두 쿠폰 발급 시스템에서 중요하지만 역할이 다르다.

각 구성 요소의 역할을 비교하고, 4~8주차에서 어떤 문제를 해결할지 연결해서 작성한다.

---

### **1. Redis, Kafka, DB 역할 비교표**

| **구분** | **Redis** | **Kafka** | **DB** |
| --- | --- | --- | --- |
| 주 역할 | 선착순 / 중복 여부를 빠르게 판정 | 발급 요청 메시지를 비동기로 전달 | 최종 쿠폰 발급 기록 저장 |
| 저장하는 데이터 | 통과 사용자 Set, 요청 카운터, 임시 메타 정보 | `coupon.issue.requested` 메시지 | 쿠폰 이벤트, 쿠폰 발급 내역, 사용자별 발급 상태 |
| 강점 | 빠른 조회와 원자 연산, DB 부하 감소 | 요청 완충, Consumer 비동기 처리, 처리량 조절 | 트랜잭션과 Unique Key로 최종 정합성 보장 |
| 한계 | 최종 원본 저장소가 아니며 장애나 유실 가능성이 있음 | 중복 발급과 수량 초과를 자동으로 막지 못함 | 대량 요청을 직접 모두 받으면 Lock 경합과 부하가 커짐 |
| 실패 시 문제 | Redis 성공 상태와 Kafka/DB 상태가 불일치할 수 있음 | 메시지가 발행되지 않거나 중복 소비될 수 있음 | 최종 발급 기록이 저장되지 않아 사용자 상태가 불일치할 수 있음 |
| 이번 주차에서 보는 핵심 | SUCCESS / DUPLICATE / SOLD_OUT 판정 | SUCCESS 요청만 발행하는 구조 | Redis 통과 이후 최종 발급은 DB에서 결정됨 |

---

### **2. Redis SUCCESS, Kafka PENDING, DB ISSUED의 차이**

```
Redis SUCCESS는 Redis에서 선착순과 중복 판정을 통과했다는 의미이다.

Kafka PENDING은 Redis SUCCESS 이후 Kafka에 발급 요청 메시지가 정상적으로 접수되어 Consumer가 나중에 처리할 예정이라는 의미이다.

DB ISSUED는 Consumer가 메시지를 처리하고 DB에 쿠폰 발급 기록을 최종 저장했다는 의미이다.

따라서 Redis SUCCESS와 Kafka PENDING은 중간 상태이고, 최종 발급 성공은 DB ISSUED이다.
```

### **3. 세 상태의 차이를 다이어그램으로 표현하기**

```
Client 요청
  |
  v
Redis Lua Script
  |
  | SUCCESS
  | = 선착순 판정 통과
  v
Kafka 발행 성공
  |
  | PENDING
  | = 발급 요청 메시지 접수
  v
Consumer 처리
  |
  v
DB 저장 성공
  |
  | ISSUED
  | = 최종 쿠폰 발급 완료
  v
사용자 쿠폰함 반영
```

### **4. Redis만 믿고 DB Unique Key를 두지 않으면 어떤 문제가 생길 수 있는가?**

```
Redis 장애, Redis 데이터 유실, 애플리케이션 버그, 운영자 수동 재처리, Kafka 중복 소비 같은 상황에서 같은 사용자의 발급 요청이 DB에 여러 번 저장될 수 있다.
Redis는 빠른 1차 판정 계층이지 최종 정합성을 보장하는 원본 저장소가 아니다.
따라서 DB에 UNIQUE(event_id, user_id)를 두지 않으면 마지막 방어선이 사라져 중복 발급이 발생할 수 있다.
```

### **5. Kafka만 사용하면 수량 초과와 중복 발급을 막기 어려운 이유**

```
Kafka는 메시지를 저장하고 전달하는 역할을 하지만, 쿠폰 수량이나 사용자 중복 여부를 자동으로 판단하지 않는다.
같은 사용자가 여러 번 요청하면 Kafka에는 여러 메시지가 들어갈 수 있고, 쿠폰이 품절된 뒤에도 메시지가 계속 쌓일 수 있다.
따라서 Kafka만으로는 수량 초과와 중복 발급을 막기 어렵고 Redis의 빠른 판정과 DB의 최종 제약 조건이 함께 필요하다.
```

---

### **6. 4주차: DB 테이블 설계와 최종 정합성 보장**

#### **6-1. Redis를 사용해도 DB Unique Key가 필요한 이유**

```
Redis를 사용해도 Redis와 DB 사이에는 Kafka, Consumer, 네트워크, 애플리케이션 로직이 존재한다.
이 과정에서 Kafka 메시지 중복 소비, Consumer 재시도, Redis 데이터 유실, 수동 재처리 같은 상황이 발생할 수 있다.
따라서 DB는 UNIQUE(event_id, user_id)를 통해 같은 사용자가 같은 이벤트 쿠폰을 두 번 발급받지 못하도록 최종 방어선을 제공해야 한다.
```

#### **6-2. `UNIQUE(event_id, user_id)`가 막아주는 문제**

```
UNIQUE(event_id, user_id)는 같은 사용자가 같은 쿠폰 이벤트에서 발급 기록을 두 번 저장하는 것을 막아준다.
즉 Kafka 중복 메시지, Consumer 재처리, 사용자의 반복 요청, 운영 배치 재실행 등으로 같은 발급 시도가 다시 들어와도 DB 레벨에서 중복 발급을 차단할 수 있다.
```

---

### **7. 5주차: requestId 기반 멱등성과 중복 처리**

#### **7-1. 같은 요청이 여러 번 들어올 수 있는 이유**

```
같은 요청은 네트워크 timeout, 사용자의 새로고침이나 버튼 연타, API Server 응답 실패, 클라이언트 자동 재시도, Kafka Consumer 재처리 등으로 여러 번 들어올 수 있다.
분산 시스템에서는 요청이 한 번만 전달된다고 가정하기 어렵기 때문에 멱등성 설계가 필요하다.
```

#### **7-2. Redis 중복 체크와 requestId 멱등성의 차이**

```
Redis 중복 체크는 같은 이벤트에서 같은 사용자가 이미 선착순 판정을 통과했는지 확인하는 것이다.
requestId 기반 멱등성은 동일한 요청이 네트워크 문제나 재시도 때문에 여러 번 들어와도 한 번만 처리되도록 보장하는 것이다.
즉 Redis 중복 체크의 기준은 주로 eventId + userId이고, requestId 멱등성의 기준은 동일 요청 식별자인 requestId이다.
```

### **8. 6주차: Outbox Pattern과 이벤트 발행 정합성**

#### **8-1. DB 저장은 성공했지만 Kafka 이벤트 발행이 실패할 수 있는 이유**

```
DB 저장과 Kafka 이벤트 발행은 서로 다른 시스템에서 일어난다.
DB 트랜잭션은 성공했지만 그 직후 Kafka 장애, 네트워크 오류, API Server 또는 Consumer 장애가 발생하면 이벤트 발행이 실패할 수 있다.
이 경우 DB에는 발급 기록이 있는데 다른 서비스는 발급 완료 이벤트를 받지 못하는 불일치가 생긴다.
```

#### **8-2. Outbox Pattern이 필요한 이유**

```
Outbox Pattern은 DB 저장과 이벤트 발행 사이의 정합성을 맞추기 위해 필요하다.
비즈니스 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장한 뒤, 별도의 Publisher가 Outbox 테이블을 읽어 Kafka에 발행한다.
이렇게 하면 DB 저장은 성공했는데 이벤트 발행 사실이 사라지는 문제를 줄일 수 있다.
```

### **9. 7주차: EDA 기반 서비스 분리와 조회 구조**

#### **9-1. 쿠폰 발급 후 알림, 마이페이지, 통계를 직접 호출하면 어떤 문제가 생기는가?**

```
쿠폰 발급 후 알림, 마이페이지 갱신, 통계 적재를 모두 발급 처리 흐름 안에서 직접 호출하면 발급 API 또는 Consumer가 여러 서비스에 강하게 의존하게 된다.
알림 서비스나 통계 서비스가 느리거나 장애가 나면 쿠폰 발급 처리까지 지연되거나 실패할 수 있다.
또한 기능이 늘어날수록 발급 로직이 복잡해지고 서비스 간 결합도가 높아진다.
```

#### **9-2. 이벤트 기반으로 분리하면 어떤 장점이 있는가?**

```
이벤트 기반으로 분리하면 쿠폰 발급 서비스는 발급 완료 이벤트만 발행하고, 알림/마이페이지/통계 서비스는 그 이벤트를 구독해서 각자 필요한 처리를 수행할 수 있다.
이렇게 하면 서비스 간 결합도를 낮추고, 장애 전파를 줄이며, 새로운 후속 처리를 추가할 때 발급 핵심 로직을 크게 수정하지 않아도 된다.
```

### **10. 8주차: Retry / DLQ / 장애 처리와 보상 트랜잭션**

#### **10-1. Redis SUCCESS 이후 DB 저장 실패는 어떤 문제인가?**

```
Redis SUCCESS 이후 DB 저장 실패는 Redis에는 선착순 통과 상태가 남아 있지만 DB에는 최종 발급 기록이 없는 불일치 문제이다.
사용자는 쿠폰 발급 요청이 접수되었다고 생각할 수 있지만 실제 쿠폰함에는 쿠폰이 없을 수 있다.
따라서 재시도, 실패 상태 저장, 보상 처리, 사용자 상태 조회 설계가 필요하다.
```

#### **10-2. Retry Topic과 DLQ가 필요한 이유**

```
Retry Topic은 일시적인 장애로 실패한 메시지를 나중에 다시 처리하기 위해 필요하다.
DLQ는 여러 번 재시도해도 계속 실패하는 메시지를 별도로 보관해 원인을 분석하고 수동 또는 배치로 복구하기 위해 필요하다.
이를 통해 장애 메시지가 정상 메시지 처리를 계속 막는 상황을 줄일 수 있다.
```

#### **10-3. 보상 트랜잭션이 필요한 상황 예시**

```
1. Redis SUCCESS 후 Kafka 발행 실패로 Redis Set에서 userId를 제거해야 하는 경우
2. Kafka 발행은 성공했지만 DB 저장이 최종 실패해 사용자에게 실패 상태를 반영해야 하는 경우
3. DB 발급 기록은 저장되었지만 후속 이벤트 발행 실패로 Outbox 재발행이 필요한 경우
4. 쿠폰 발급 처리 중 일부 상태만 성공하고 나머지 상태가 실패해 이전 상태로 되돌리거나 별도 복구 작업이 필요한 경우
```
