# **5주차 과제**

# **requestId 기반 멱등성과 중복 처리 구조 설계**

> 모든 답변은 각 문항 아래의 코드블록 안에 작성한다. 표 형식 문항도 코드블록 안의 표를 수정해 제출한다.
>

## **1. 과제 목표**

이번 5주차 과제의 목표는 **같은 API 요청이나 Kafka 메시지가 여러 번 전달되더라도 최종 쿠폰 발급 결과가 한 번만 반영되도록 멱등 처리 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

4주차에서는 DB의 조건부 `UPDATE`, `UNIQUE(event_id, user_id)`, Transaction을 이용해 최종 수량과 사용자 중복 발급을 방어했다.

이번 5주차에서는 다음 문제를 추가로 해결한다.

```
같은 논리적인 요청이 여러 번 전달되었는가?

같은 사용자가 새로운 요청을 다시 보낸 것인가?

Consumer가 이미 성공한 메시지를 다시 읽은 것인가?

요청이 아직 처리 중인가?

이전에 성공하거나 실패했다면 어떤 결과를 다시 반환해야 하는가?
```

기본 흐름은 다음과 같다.

```
Client
  |
  | Idempotency-Key: requestId
  v
API Server
  |
  | 인증된 userId 확인
  | requestHash 생성
  v
Redis
  |
  | 사용자 + requestId 기준 판정
  v
coupon_issue_request
  |
  | PENDING 요청 상태 저장
  v
Kafka
  |
  | requestId가 포함된 메시지 전달
  v
Coupon Issue Consumer
  |
  | requestId 기준 처리 권한 획득
  v
DB Transaction
  |
  | 수량 증가
  | 발급 기록 저장
  | 요청 상태 확정
  v
Kafka Offset Commit
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Idempotency-Key와 requestId의 역할

같은 요청과 같은 사용자의 차이

Kafka Producer 멱등성과 비즈니스 멱등성의 차이

requestId와 Kafka Partition + Offset의 차이

requestHash를 이용한 잘못된 키 재사용 방지

coupon_issue_request 요청 상태 테이블 설계

PENDING / PROCESSING / ISSUED / FAILED 상태 전이

동일 requestId 동시 요청의 최초 등록자 결정

Consumer의 조건부 상태 전이와 처리 권한 획득

발급 수량, 발급 기록, 요청 상태를 묶는 DB Transaction

UNIQUE 위반 Rollback 이후 상태 확정

DB Commit과 Kafka Offset Commit의 순서

중복 메시지를 예외가 아니라 멱등 성공으로 처리하는 방법

Redis, DB, Kafka 사이의 일시적 불일치와 복구 방향
```

이번 과제의 핵심은 다음과 같다.

```
중복 전달을 완전히 없애는 것이 목표가 아니다.

같은 요청이 여러 번 전달되더라도
최종 비즈니스 결과가 한 번만 반영되게 만드는 것이 목표다.
```

## **2. 기본 상황**

서비스에서 다음 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 ID: 100

이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트

전체 쿠폰 수량: 1,000개

발급 조건:
사용자 1명당 해당 이벤트 쿠폰 1개만 발급 가능

DBMS: PostgreSQL

DB 격리 수준: READ COMMITTED

최종 발급 성공 기준:
coupon_event.issued_count 증가,
coupon_issue 저장,
coupon_issue_request ISSUED 변경이
하나의 트랜잭션으로 Commit된 시점
```

사용자 `userId = 10`이 다음 요청을 보낸다.

```
POST /api/coupon-events/100/issue
Authorization: Bearer ...
Idempotency-Key: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31
```

서버 내부에서는 `Idempotency-Key`를 `requestId`로 사용한다.

```
{
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "eventId": 100,
  "userId": 10,
  "requestedAt": "2026-07-24T12:00:00+09:00"
}
```

하지만 실제 시스템에서는 다음 상황이 발생할 수 있다.

```
상황 1.
서버는 요청을 처리했지만 응답만 유실되어
Client가 같은 requestId로 재시도한다.

상황 2.
사용자가 버튼을 여러 번 눌러
서로 다른 requestId로 같은 쿠폰을 다시 요청한다.

상황 3.
애플리케이션 코드가 같은 메시지를 send()로 두 번 발행한다.

상황 4.
Consumer가 DB Commit 후 Offset Commit 전에 종료되어
같은 Kafka Record를 다시 읽는다.

상황 5.
원본 Topic의 메시지가 Retry Topic으로 이동하여
Partition과 Offset은 달라졌지만 같은 requestId가 다시 전달된다.

상황 6.
같은 requestId가 다른 eventId 또는 다른 userId 요청에 재사용된다.
```

이 모든 상황을 단순히 `UNIQUE(event_id, user_id)` 하나로만 처리할 수는 없다.

```
UNIQUE(event_id, user_id)
→ 같은 사용자의 최종 중복 발급을 막는다.

requestId
→ 같은 논리적인 요청의 재처리를 식별한다.

requestHash
→ 같은 requestId가 다른 요청에 재사용되는 것을 막는다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
Client는 쿠폰 발급 요청을 보내기 전에 UUID 형식의 requestId를 생성한다.

같은 논리적인 요청을 재시도할 때는
최초 요청과 동일한 requestId를 재사용한다.

새로운 논리적인 작업에는 새로운 requestId를 사용한다.

userId는 Request Body가 아니라
인증된 사용자 정보에서 가져온다.

requestHash는 다음 Canonical String을 기준으로 생성한다.

COUPON_ISSUE|eventId|authenticatedUserId

Hash 알고리즘은 SHA-256을 사용한다.
```

이번 과제에서는 3주차의 Redis 구조를 다음처럼 확장한다고 가정한다.

```
Redis 판정 기준

- eventId + userId
- 해당 사용자의 최초 requestId
```

Redis Lua Script의 반환값은 다음 네 가지로 사용한다.

| **반환값** | **의미** |
| --- | --- |
| `SUCCESS` | 새로운 사용자가 새로운 requestId로 선착순 판정을 통과함 |
| `IDEMPOTENT_RETRY` | 같은 사용자와 같은 requestId가 다시 들어옴 |
| `DUPLICATE_USER` | 같은 사용자가 다른 requestId로 다시 요청함 |
| `SOLD_OUT` | Redis 기준 제한 수량에 도달함 |

이번 과제에서는 Redis를 통과한 요청만 DB 요청 상태 테이블에 저장하는 방식을 기본으로 사용한다.

```
Redis SUCCESS
→ coupon_issue_request PENDING 저장
→ Kafka 발행

Redis DUPLICATE_USER / SOLD_OUT
→ coupon_issue_request를 만들지 않음
→ Kafka에 발행하지 않음
```

요청 상태는 다음 네 가지로 단순화한다.

```
PENDING
PROCESSING
ISSUED
FAILED
```

최종 실패 코드는 다음 예시를 사용할 수 있다.

```
SOLD_OUT
DUPLICATE_USER
INVALID_EVENT
REQUEST_MISMATCH
```

다음 오류는 최종 비즈니스 실패가 아니라 일시적 시스템 오류로 본다.

```
DB 연결 일시 실패
Deadlock
네트워크 Timeout
Connection Pool 일시 부족
Consumer 프로세스 장애
```

일시적 시스템 오류가 발생하면 요청 상태를 `FAILED`로 확정하지 않고 트랜잭션을 Rollback한 뒤 Kafka 재전달을 통해 다시 처리한다.

이번 주차의 기본 Consumer 처리는 짧은 DB 작업이므로 다음 범위를 하나의 트랜잭션으로 묶는다.

```
PENDING → PROCESSING 처리 권한 획득
coupon_event.issued_count 증가
coupon_issue INSERT
coupon_issue_request ISSUED 또는 FAILED 변경
```

이번 주차에서는 아래 내용을 상세 구현하지 않는다.

```
Outbox Publisher 상세 구현

Retry Topic과 DLQ 상세 정책

쿠폰 발급 취소와 재발급

외부 결제나 외부 API 호출이 포함된 장시간 작업

Redis와 RDB를 하나의 분산 트랜잭션으로 묶는 방법
```

다만 Redis, DB, Kafka 사이에서 어떤 불일치가 발생할 수 있는지와 복구 방향은 설명해야 한다.

Client의 최초 요청부터 Kafka Offset Commit까지의 전체 흐름을 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

Idempotency-Key

API Server

Redis Lua Script

coupon_issue_request

coupon_event
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
+--------+
| Client |
+--------+
    |
    | POST /api/coupon-events/100/issue
    | Authorization: Bearer ...
    | Idempotency-Key: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31
    v
+---------------------------------------------------+
| API Server                                        |
|---------------------------------------------------|
| 1. 인증 토큰에서 userId 추출                       |
| 2. Idempotency-Key 형식/길이 검증                  |
| 3. requestId = Idempotency-Key                    |
| 4. requestHash = SHA-256(COUPON_ISSUE|100|10)     |
+---------------------------------------------------+
    |
    v
+---------------------------------------------------+
| Redis Lua Script  (사용자/수량/requestId 원자 판정) |
|---------------------------------------------------|
| eventId + userId 통과 여부 확인                    |
| 잔여 수량 확인                                     |
| user -> 최초 requestId 매핑 확인 및 저장           |
+---------------------------------------------------+
    |
    +-- SOLD_OUT         -> 품절 응답
    |                       (DB 행 없음 / Kafka 발행 없음)
    |
    +-- DUPLICATE_USER   -> 사용자 중복 응답
    |                       (DB 행 없음 / Kafka 발행 없음)
    |
    +-- IDEMPOTENT_RETRY -> coupon_issue_request 조회
    |                       -> 기존 상태 그대로 반환
    |                       (새 Kafka 발행 없음)
    |                       * 행이 없으면 복구/보상 대상
    |
    +-- SUCCESS
           |
           v
+---------------------------------------------------+
| coupon_issue_request  (요청 상태 테이블)           |
|---------------------------------------------------|
| INSERT (request_id, event_id, user_id,            |
|         request_hash, status='PENDING', ...)      |
| ON CONFLICT (request_id) DO NOTHING               |
+---------------------------------------------------+
    |
    +-- affected rows = 0  (동시 요청 / 기존 요청)
    |      -> 기존 행 조회
    |        request_hash 같음 -> 기존 상태 반환
    |        request_hash 다름 -> 409 IDEMPOTENCY_KEY_REUSED
    |                              (Kafka 발행 금지)
    |
    +-- affected rows = 1  (최초 등록자)
           |
           v
+---------------------------------------------------+
| Kafka Producer                                    |
|---------------------------------------------------|
| key   = requestId                                 |
| value = { requestId, eventId, userId,             |
|           requestedAt }                           |
+---------------------------------------------------+
    |
    +-- 발행 실패/Timeout
    |      -> 202 Accepted 반환하지 않음
    |      -> 재발행 시도, PENDING 복구 배치 대상
    |
    v
+---------------------------------------------------+
| Topic: coupon.issue.requested                     |
+---------------------------------------------------+
    |
    |  (발행 확인 후 API Server -> Client : 202 Accepted, status=PENDING)
    |
    v
+---------------------------------------------------+
| Coupon Issue Consumer                             |
|---------------------------------------------------|
| requestId로 coupon_issue_request 조회              |
| 메시지 <-> 요청 행 일치 검증                       |
|   (requestId / eventId / userId)                  |
|   불일치 -> 발급 금지, DLQ·운영 확인 후보          |
+---------------------------------------------------+
    |
    v
+===================================================+
| DB Transaction  (단일 트랜잭션)                    |
|===================================================|
|                                                   |
| (1) coupon_issue_request : 처리 권한 획득          |
|     UPDATE ... SET status='PROCESSING'            |
|     WHERE request_id=:id AND status='PENDING'     |
|       0행 -> 기존 상태 재조회                      |
|              ISSUED / FAILED -> 멱등 성공 종료     |
|       1행 -> 계속 진행                             |
|              |                                    |
|              v                                    |
| (2) coupon_event : 수량 확보                       |
|     UPDATE issued_count = issued_count + 1        |
|     WHERE id=:eventId                             |
|       AND issued_count < total_quantity           |
|       0행 -> DB 기준 SOLD_OUT (이벤트 존재 시)      |
|              request FAILED/SOLD_OUT -> COMMIT     |
|       1행 -> 계속 진행                             |
|              |                                    |
|              v                                    |
| (3) coupon_issue : 발급 기록 저장                  |
|     INSERT (event_id, user_id, status, issued_at) |
|       UNIQUE(event_id, user_id) 위반               |
|              -> 전체 ROLLBACK                      |
|                 (issued_count 증가도 함께 취소,    |
|                  상태는 PENDING으로 복귀)          |
|                 -> 별도 트랜잭션에서                |
|                    PENDING -> FAILED/DUPLICATE_USER|
|       성공 -> 계속 진행                            |
|              |                                    |
|              v                                    |
| (4) coupon_issue_request : 최종 상태 확정          |
|     UPDATE ... SET status='ISSUED',               |
|                    coupon_issue_id=:issueId       |
|     WHERE request_id=:id AND status='PROCESSING'  |
|       0행 -> 전체 ROLLBACK                         |
|       1행 -> COMMIT                                |
|                                                   |
| * 일시적 DB 오류(Deadlock, 연결 실패 등)           |
|   -> FAILED 저장 없이 ROLLBACK                     |
|   -> 예외 재전파 -> Kafka 재전달로 재처리          |
+===================================================+
    |
    | COMMIT 성공  (= 최종 발급 성공 확정 시점)
    v
+---------------------------------------------------+
| Kafka Offset Commit                               |
|---------------------------------------------------|
| DB 결과 확정 이후에만 수행                         |
| 멱등 성공 종료(ISSUED/FAILED 중복 메시지)도 Commit |
+---------------------------------------------------+

[비동기 결과 조회 경로]

Client --> GET /api/coupon-issue-requests/{requestId}
             |
             v
       coupon_issue_request
       WHERE request_id = :requestId
         AND user_id = :authenticatedUserId
```

### **2. 하나의 requestId가 전체 흐름에서 어떻게 전달되는지 작성하기**

아래 흐름을 완성한다.

```
HTTP Idempotency-Key
        |
        v
애플리케이션 requestId
        |
        v
coupon_issue_request.request_id
        |
        v
Kafka Message requestId
        |
        v
Consumer 멱등 처리
```

### **3. 각 구성 요소의 역할**

```
| **구성 요소** | **역할** |
| --- | --- |
| Redis | eventId + userId + 최초 requestId를 Lua Script로 원자적으로 판정해, 성공 가능성이 없는 요청을 DB 앞단에서 차단한다. 사용자 중복 요청과 수량 초과 요청을 걸러 DB 부하를 줄이는 필터이며, SUCCESS는 선착순 자리 확보를 의미할 뿐 최종 발급 성공을 의미하지 않는다. |
| Kafka | API Server와 Consumer를 분리하고, 순간적인 요청 폭주를 저장·완충한다. requestId를 포함한 메시지를 전달하는 통로이며, At-Least-Once 전제이므로 같은 메시지가 한 번 이상 전달될 수 있다. |
| coupon_issue_request | 하나의 논리적 요청(requestId)의 생명주기와 결과를 저장한다. PENDING / PROCESSING / ISSUED / FAILED 상태와 실패 코드를 보관해, 중복 요청에 일관된 결과를 반환하고 조건부 상태 전이로 여러 Consumer 중 하나만 처리 권한을 갖도록 만든다. request_hash로 같은 키가 다른 요청에 재사용되는 것을 막는다. |
| coupon_event | 이벤트의 전체 수량(total_quantity)과 발급 수량(issued_count)을 보관한다. `issued_count < total_quantity` 조건부 UPDATE로 DB 기준 전체 수량 초과를 최종 방어한다.  |
| coupon_issue | 실제 발급에 성공한 기록만 저장한다. UNIQUE(event_id, user_id)로 같은 사용자의 최종 중복 발급을 막는 마지막 방어선이며, Redis 데이터가 유실되거나 다른 requestId로 우회해도 중복 행 저장을 차단한다. 성공 행만 존재하므로 대기·처리 중·실패 상태는 표현할 수 없다. |
| Kafka Offset | Consumer Group이 해당 Partition을 어디까지 읽었는지 기록하는 소비 위치다. Kafka 관점의 처리 완료 표시일 뿐 비즈니스 결과가 아니며, 반드시 DB 결과가 확정된 뒤에 Commit해야 유실이나 중복 반영을 피할 수 있다. |
```

### **4. 각 단계의 성공이 의미하는 것**

```
| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis `SUCCESS` | 해당 사용자가 이 이벤트의 선착순 판정을 통과해 Redis 기준으로 자리를 확보했다. | x |
| request `PENDING` | 요청이 DB에 등록되어 요청 자체는 유실되지 않는 상태다. 다만 Kafka 발행 전인지 발행 후 Consumer 처리 전인지는 이 상태만으로 구분할 수 없다. | x |
| request `PROCESSING` | 한 Consumer가 조건부 UPDATE로 처리 권한을 획득해 발급 로직을 수행 중인 상태다. 다른 Consumer는 같은 요청의 처리 권한을 얻을 수 없다. | x |
| request `ISSUED` | issued_count 증가, coupon_issue 저장, 요청 상태 변경이 하나의 트랜잭션으로 Commit된 최종 성공 상태다. | o |
| request `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 실패 상태이며, failure_code로 원인을 구분한다. 일시적 시스템 오류는 이 상태로 저장하지 않는다. | x |
| Kafka Offset Commit | Consumer Group이 해당 Record를 소비 완료로 표시한 것이다. 새 요청 처리 성공뿐 아니라 ISSUED·FAILED 중복 메시지를 무변경 종료한 경우에도 수행한다. | x |
```

### **5. 최종 쿠폰 발급 성공으로 판단할 수 있는 시점**

```
최종 쿠폰 발급 성공으로 판단할 수 있는 시점은
다음 세 작업이 하나의 DB 트랜잭션으로 Commit된 시점이다.

1. coupon_event.issued_count 증가
2. coupon_issue INSERT (event_id, user_id)
3. coupon_issue_request 상태를 ISSUED로 변경 (coupon_issue_id 연결)

세 작업은 함께 성공하거나 함께 실패해야 하며,
Commit이 완료되기 전까지는 어떤 단계도 발급 성공으로 볼 수 없다.
```

### **6. 요청이 여러 번 도착해도 최종 결과가 한 번만 반영되어야 한다는 의미**

```
요청이 여러 번 도착해도 최종 결과가 한 번만 반영되어야 한다는 것은, 중복 전달 자체를 없앤다는 뜻이 아니라 중복이 발생하더라도 비즈니스 결과가 한 번만 확정된다는 뜻이다.

이번 과제에서는 두 가지로 나타난다.

아직 결과가 확정되지 않은 경우 같은 requestId를 여러 처리자가 동시에 다루더라도 PENDING -> PROCESSING 조건부 UPDATE에서 한 처리자만 1행을 얻고 나머지는 0행을 받아 발급 로직을 실행하지 않는다.

이미 결과가 확정된 경우 같은 요청이 다시 전달되면 기존 ISSUED 또는 FAILED 상태를 확인하고 새 발급 로직을 실행하지 않는다.
API는 저장된 결과를 반환하고, Consumer는 아무 변경 없이 종료한 뒤 Offset을 Commit한다.

결과적으로 메시지 전달 횟수는 한 번 이상일 수 있지만
issued_count 증가, coupon_issue 저장, 요청 상태 확정은 한 번만 일어난다.
```

## **과제 2. 중복 유형과 멱등성 경계 구분하기**

같아 보이는 중복도 원인과 방어 장치가 다르다.

아래 상황을 읽고 각각 어떤 중복인지 구분한다.

### **1. 상황별 중복 유형 분석**

```
| **상황** | **같은 논리적 요청인가?** | **식별 기준** | **주요 방어 장치** |
| --- | --- | --- | --- |
| 응답 유실 후 같은 requestId로 API 재시도 | o | requestId | Redis Lua Scrpit를 통해 IDEMPOTENT_RETRY |
| 반복 클릭으로 다른 requestId가 생성됨 | x | eventId+userId | Redis Lua Script의 DUPLICATE_USER 판정으로 앞단 차단, 최종 방어선은 DB UNIQUE 제약 |
| 애플리케이션이 같은 requestId 메시지를 `send()` 두 번 호출 | o | requestId | Consumer 멱등성. 동일 requestId에 대해 조건부 상태 전이로 최초 처리자만 발급 로직을 실행하고, 나머지는 기존 최종 상태를 확인한 뒤 무변경 종료 후 Offset을 Commit한다.|
| DB Commit 후 Offset Commit 전 장애로 같은 Record 재전달 | o | requestId | Consumer 멱등성. 재전달된 메시지의 requestId로 요청 상태를 조회해 ISSUED를 확인하고, 새 발급 없이 정상 처리로 보고 Offset을 Commit한다. |
| 원본 Topic과 Retry Topic에 같은 requestId가 존재 | o | requestId | Consumer 멱등성. Offset 기준으로는 서로 다른 레코드로 보이므로 requestId를 기준으로 판단해야 한다. 조건부 상태 전이로 한 경로만 처리 권한을 얻는다.|
| 같은 requestId가 다른 eventId에 재사용됨 | x | requestHash | API 단계에서 기존 행의 request_hash와 비교해 불일치 시 409 Conflict(IDEMPOTENCY_KEY_REUSED)로 거절하고 Kafka에 발행하지 않는다. Consumer 단계에서는 메시지와 요청 행의 eventId·userId 일치 검증에서 걸러 REQUEST_MISMATCH로 처리하고 발급을 금지한다. |
```

### **2. 같은 요청과 같은 사용자의 차이**

아래 두 상황의 차이를 설명한다.

```
상황 A
requestId = req-001
이 요청이 여러 번 전달됨

상황 B
requestId = req-A, req-B, req-C
모두 eventId = 100, userId = 10
```

답변:

```
A는 같은 요청이 여러 번 전달된 상황이고, B는 같은 사용자가 여러 요청을 보낸 상횡이다. 두 상황의 최종 결과는 두 경우 모두 쿠폰 1장 발급으로 같다. 하지만 A에서는 같은 requestId가 사용되어 재시도가 기존 성공 결과를 반환하고, B에서는 requestId가 다르기 때문에 두 번째 이후 요청이 중복 발급 실패로 확정된다는 점이 다르다.
```

### **3. 중복 방어 장치별 역할 비교**

```
| **장치** | **식별 기준** | **막는 문제** | **막지 못하는 문제** |
| --- | --- | --- | --- |
| Redis 사용자 판정 | eventId+userId, requestId | 수량 초과, 중복 요청, 같은 requestId 재요청 문제 | Kafka 뒤에서 발생하는 재전달 중복 문제 |
| requestId | requestId | requestId가 같은 요청에 대한 멱등성 | 같은 사용자가 같은 이벤트에 새로운 요청을 보냈을 때 중복 발급 |
| requestHash | requestId+requestHash | 동일한 requestId를 사용한 다른 요청 | 같은 사용자의 중복 발급 |
| `UNIQUE(event_id, user_id)` | eventId+userId | 같은 유저의 중복 발급 문제 | requestId가 같은 요청에 대한 멱등성 |
| Kafka Partition + Offset | Kafka Partition + Offset | 정상 Commit된 메시지의 재소비를 막아, Consumer 재시작 시 이어서 소비하도록 소비 범위를 제어 | 같은 requestId라도 Partition·Offset이 달라지면 동일 요청임을 식별할 수 없음 |
```

### **4. Kafka Producer 멱등성이 막는 중복**

다음 흐름을 기준으로 설명한다.

```
애플리케이션이 send() 한 번 호출
→ Broker 저장 성공
→ ACK 유실
→ Producer 내부 재시도
```

```
애플리케이션은 send()를 한 번만 호출했고, ACK 유실이나 네트워크 오류 때문에 Producer가 동일한 전송 요청을 내부적으로 다시 보낸다. 따라서 최초 전송과 내부 재시도는 같은 Sequence Number를 사용한다.

Broker는 (Producer ID, Partition)별로 마지막에 저장한 Sequence Number를 기억하고 있으므로, 이미 저장한 번호가 다시 들어오면
같은 전송의 재시도로 판단하고 중복 저장하지 않는다.
```

### **5. 애플리케이션이 send()를 두 번 호출하면 Producer 멱등성으로 막을 수 없는 이유**

```
kafkaTemplate.send(topic, message);
kafkaTemplate.send(topic, message);
```

```
Kafka Producer는 send() 호출 단위로 Sequence Number를 부여하기 때문에 send()를 두 번 호출하는 경우 Sequence Number가 달라지게 된다. 그 결과 Broker는 이를 중복으로 판단하지 못하게 되고 새 전송으로 판단하여 두 요청을 모두 저장하게 된다.
```

### **6. requestId와 Kafka Partition + Offset의 차이**

```
requestId: 하나의 논리적인 쿠폰 발급 요청을 식별하는 비즈니스 식별자

Partition + Offset: Kafka 내부에서 해당 Record가 저장된 물리적 위치를 나타내는 값
```

### **7. Consumer 멱등성의 기준을 Offset이 아니라 requestId로 두어야 하는 이유**

아래 상황을 포함해서 설명한다.

```
원본 Topic
Partition 0 / Offset 100 / req-001

Retry Topic
Partition 2 / Offset 35 / req-001
```

```
같은 논리적 요청이라도 Kafka상의 저장 위치는 달라질 수 있다.

원본 Topic   : Partition 0 / Offset 100 / req-001
Retry Topic  : Partition 2 / Offset 35  / req-001

두 Record는 Partition과 Offset이 모두 다르지만 동일한 req-001 요청이다.
Offset을 멱등성의 기준으로 삼으면 Consumer는 Retry Topic의 Record를 처음 보는 레코드로 판단해 발급 로직을 다시 실행하게 되고, issued_count가 두 번 증가하거나 발급 행이 다시 생성되어 최종 결과가 두 번 반영된다.

반대 방향의 문제도 있다.
DB Commit 후 Offset Commit 전에 Consumer가 종료되면 같은 Partition의 같은 Offset을 가진 기존 Record가 그대로 재전달된다. 이때는 위치가 동일함에도 이미 처리가 완료된 요청이므로 재실행해서는 안 된다.

즉 Partition + Offset은 Kafka 내부의 저장 위치일 뿐이므로 같은 위치가 다시 전달되기도 하고, 같은 요청이 다른 위치에 존재하기도 한다. 하나의 requestId가 여러 Partition + Offset을 가질 수 있는 1:N 관계이므로 위치만으로는 동일 요청 여부를 판단할 수 없다.

반면 requestId는 재발행이나 Topic 이동과 무관하게 유지되는 비즈니스 식별자이므로, Consumer 멱등성의 기준은 Offset이 아니라 requestId여야 한다.
```

## **과제 3. Idempotency-Key와 requestHash 설계하기**

HTTP API에서 동일한 논리적 요청의 재시도를 식별할 수 있도록 `Idempotency-Key`와 `requestHash`를 설계한다.

### **1. Idempotency-Key의 의미**

```
클라이언트가 동일한 요청의 재시도임을 서버에 알려주기 위해 전달하는 고유한 식별자
```

### **2. 누가 requestId를 생성해야 하는가?**

다음 두 방식을 비교하고 이번 구조에 더 적합한 방식을 선택한다.

```
방식 A
Client가 요청 전 requestId 생성

방식 B
API Server가 요청을 받은 뒤 requestId 생성
```

```
| **방식** | **장점** | **단점** |
| --- | --- | --- |
| Client 생성 | 응답 유실이나 네트워크 타임아웃으로 결과를 알 수 없을 때, 최초 요청과 동일한 requestId를 재사용해 재시도할 수 있다. | 외부에서 들어오는 값이므로 서버가 형식·길이·문자 종류를 반드시 검증해야 하고, 추측하기 어려운 값이어야 한다. 서버 간 내부 호출처럼 클라이언트가 키를 만들기 어려운 환경에서는 적용하기 어렵다. |
| API Server 생성 | 값의 형식과 유일성을 서버가 직접 통제할 수 있어 별도의 입력 검증이 필요 없고, 클라이언트 구현 부담이 없다. | 응답이 유실되면 클라이언트가 생성된 requestId를 알 수 없어 재시도 시 같은 값을 사용할 수 없다. 서버는 재시도마다 새 requestId를 부여하므로 서로 다른 요청으로 인식하게 되어, 멱등 처리의 핵심 목적인 응답 유실 후 재시도 방어를 달성할 수 없다. |
```

내가 선택한 방식:

```
Client 생성 방식
```

선택한 이유:

```
서버가 생성하는 방식에서는 위와 같이 재시도마다 새로운 식별자가 부여되어 서버 관점에서 서로 다른 두 요청으로 보인다. 이 경우 Redis는 IDEMPOTENT_RETRY를 판정할 수 없고 coupon_issue_request에도 별개의 행이 생성되므로, requestId 기반 멱등 처리 자체가 성립하지 않는다.

반면 클라이언트가 요청 전에 UUID를 생성해 두면 응답을 받지 못한 상황에서도 동일한 값으로 재시도할 수 있어, 서버는 req-001이 이미 등록된 요청인지 확인하고 새 작업을 만들지 않은 채 기존 상태와 결과를 반환할 수 있다.

이번 구조에서 방어해야 하는 대표적인 중복은 서버는 요청을 처리했지만 응답만 유실되어 클라이언트가 다시 요청하는 경우로, Client 방식이 이를 방어하기에 유리하다고 생각하여 선택하였다.
```

```
| **상황** | **같은 requestId 재사용 또는 새 requestId 생성** | **이유** |
```


답변:

```
허용 형식

반드시 UUID여야 하는 것은 아니지만, 서비스 전체에서 유일하고 추측하기 어려우며 길이와 문자 형식을 검증할 수 있는 값이어야 하므로 UUID를 선택한다.

UUID v4 문자열 형식만 허용한다.
8-4-4-4-12 자리의 16진수와 하이픈으로 구성되며, 정규식으로 검증한다.

^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$

예: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31

최대 길이

36자로 고정한다. (UUID 문자열 길이)
DB 컬럼도 UUID 타입으로 선언해 저장 시점에 형식을 한 번 더 강제한다.

길이 검증은 정규식 검증보다 먼저, API 앞단에서 수행한다.
지나치게 긴 키를 그대로 받으면 로그와 DB 인덱스에 불필요한 부담을 주고, 과도한 길이의 입력이 그대로 저장소까지 전달되기 때문이다.

빈 값 처리

Idempotency-Key 헤더가 없거나 빈 문자열이면 요청을 처리하지 않고 400 Bad Request로 거절한다.

서버가 임의로 값을 생성해 대체하지 않는다. 서버가 생성하면 클라이언트가 그 값을 알 수 없어 재시도 시 동일한 값을 사용할 수 없고, 멱등 처리가 성립하지 않기 때문이다.

{
  "errorCode": "IDEMPOTENCY_KEY_REQUIRED",
  "message": "Idempotency-Key 헤더가 필요합니다."
}

허용하지 않는 문자

- 16진수(0-9, a-f, A-F)와 하이픈 외의 모든 문자
- 공백, 개행, 탭 등 공백 문자
- 슬래시, 콜론, 물음표 등 URL·경로에 의미를 갖는 문자
- 따옴표, 세미콜론, 주석 기호 등 SQL·로그 조작에 사용될 수 있는 문자
- 제어 문자 및 비출력 문자
- 한글, 이모지 등 멀티바이트 문자

허용 목록(whitelist) 방식으로 검증하며,
위 정규식을 만족하지 않으면 400 Bad Request로 거절한다.

DB 유일성 보장 방식

coupon_issue_request.request_id를 UUID 타입 Primary Key로 선언해 DB가 유일성을 최종 보장한다.

request_id UUID PRIMARY KEY

애플리케이션에서 SELECT로 존재 여부를 먼저 확인한 뒤 INSERT하는 방식은 Check-Then-Act 경쟁이 발생하므로 사용하지 않는다.
동일 requestId 동시 요청의 최초 등록 권한은 사전 조회가 아니라 Primary Key 제약으로 결정한다.

INSERT INTO coupon_issue_request (...)
VALUES (...)
ON CONFLICT (request_id) DO NOTHING;

affected rows = 1  -> 최초 등록자
affected rows = 0  -> 기존 행 조회 후 request_hash 비교로 재시도 여부 판정

API 앞단의 형식 검증은 잘못된 입력을 조기에 걸러 부하를 줄이는 역할이고, 유일성 자체는 DB Primary Key가 보장한다.
```

### **5. requestHash를 만드는 Canonical String 작성하기**

이번 과제의 기준은 다음과 같다.

```
작업 종류: COUPON_ISSUE
이벤트 ID: 100
인증된 사용자 ID: 10
```

Canonical String:

```
COUPON_ISSUE|{eventId}|{authenticatedUserId}

작업 종류, 이벤트 ID, 인증된 사용자 ID를 이 순서로 고정하고 구분자 |로 연결한다.
```

SHA-256 결과를 저장할 컬럼:

```
request_hash CHAR(64) NOT NULL

SHA-256 결과는 256비트이며, 16진수 문자열로 표현하면 항상 64자다. 길이가 고정되어 있으므로 VARCHAR가 아닌 CHAR(64)를 사용하고
NOT NULL로 선언해 모든 요청 행이 해시를 갖도록 강제한다.
```

## **과제 4. coupon_issue_request 테이블과 상태 전이 설계하기**

동일한 요청의 처리 상태와 최종 결과를 저장하기 위한 `coupon_issue_request` 테이블을 설계한다.

### **1. coupon_issue_request와 coupon_issue의 역할 차이**

```
| **테이블** | **저장하는 대상** | **표현할 수 있는 상태** |
| --- | --- | --- |
| coupon_issue_request | 발급 요청 | PENDING, PROCESSING, ISSUED, FAILED |
| coupon_issue | 발급 성공한 요청 | SUCCESS |
```

### **2. 요청 상태 모델 설명하기**

```
| **상태** | **의미** | **최종 상태 여부** |
| --- | --- | --- |
| `PENDING` | 요청 행이 생성되었지만 최종 처리가 끝나지 않은 상태다. Redis 판정을 통과한 요청이 coupon_issue_request에 등록된 직후의 상태이며, DB 저장 후 Kafka 발행 전인 경우와 Kafka 발행 성공 후 Consumer 처리 전인 경우를 모두 포함한다.  | 처리가 시작되지 않았거나 진행 중일 수 있으며, 이후 ISSUED 또는 FAILED로 확정된다. |
| `PROCESSING` | Consumer가 조건부 UPDATE로 처리 권한을 획득해 발급을 처리 중인 상태다. 한 requestId에 대해 한 처리자만 이 상태로 전이시킬 수 있으므로 처리 권한 표시 역할을 한다. | 처리 권한을 얻었을 뿐이며, 수량 소진·UNIQUE 위반·일시적 오류로 Rollback되면 PENDING으로 되돌아갈 수 있다. |
| `ISSUED` | coupon_event.issued_count 증가, coupon_issue 저장, 요청 상태 변경이 하나의 트랜잭션으로 Commit된 최종 성공 상태다. | 최종 상태이며 다른 상태로 전이할 수 없다. 같은 requestId가 다시 전달되면 이 결과를 그대로 반환하거나 무변경 종료한다. |
| `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 실패 상태다. failure_code로 원인을 구분하며 SOLD_OUT, DUPLICATE_USER, INVALID_EVENT, REQUEST_MISMATCH 등을 사용한다. | 최종 상태이며 다른 상태로 전이할 수 없다. 중복 메시지가 와도 기존 실패 결과를 사용한다. |
```

### **3. 상태 전이 다이어그램 작성하기**

아래 허용 상태 전이와 금지 상태 전이를 구분해서 표현한다.

```
허용 후보
PENDING → PROCESSING
PROCESSING → ISSUED
PROCESSING → FAILED

금지 후보
ISSUED → PROCESSING
ISSUED → FAILED
FAILED → PROCESSING
FAILED → ISSUED
```

```
허용 상태 전이

PENDING     -> PROCESSING    조건부 UPDATE로 처리 권한 획득
PROCESSING  -> ISSUED        수량 확보와 발급 기록 저장이 함께 Commit됨
PROCESSING  -> FAILED        SOLD_OUT 등 최종 비즈니스 실패 확정

금지 상태 전이

ISSUED  -> PROCESSING   확정된 성공을 다시 처리 중으로 되돌릴 수 없다
ISSUED  -> FAILED       확정된 성공을 실패로 덮어쓸 수 없다
FAILED  -> PROCESSING   확정된 실패를 다시 처리 중으로 되돌릴 수 없다
FAILED  -> ISSUED       확정된 실패를 성공으로 덮어쓸 수 없다

ISSUED와 FAILED는 최종 상태이므로 어떤 상태로도 전이할 수 없다.
오래된 Consumer나 중복 메시지가 최신 결과를 변경하지 못하도록
모든 상태 변경 SQL에 출발 상태를 조건으로 포함한다.

UPDATE coupon_issue_request
SET status = 'ISSUED', ...
WHERE request_id = :requestId
  AND status = 'PROCESSING';   -- 출발 상태를 반드시 명시

조건 없이 상태를 덮어쓰면 위 금지 전이가 실제로 발생할 수 있다.
```

### **4. 단일 트랜잭션 구조에서 외부 조회 시 PROCESSING이 거의 보이지 않을 수 있는 이유**

```
단일 트랜잭션 구조에서는 처리 권한 획득부터 최종 상태 변경까지가
하나의 트랜잭션 안에서 처리된다.

BEGIN;
  PENDING -> PROCESSING     -- 처리 권한 획득
  coupon_event 수량 확보
  coupon_issue INSERT
  PROCESSING -> ISSUED      -- 최종 상태 확정
COMMIT;

PROCESSING은 이 트랜잭션 내부에서만 존재하는 중간 상태이며,
Commit 시점에는 이미 ISSUED 또는 FAILED로 변경된 뒤다.

외부 트랜잭션에서는 커밋되지 않은 변경을 볼 수 없으므로
(PostgreSQL READ COMMITTED 기준, 커밋된 데이터만 조회 가능)
다른 트랜잭션이 이 요청을 조회하면 다음과 같이 보인다.

Commit 이전  -> PENDING              (변경 전 상태가 그대로 보임)
Commit 이후  -> ISSUED 또는 FAILED    (최종 상태가 보임)

따라서 외부 관점에서는 PENDING -> ISSUED 또는 PENDING -> FAILED로 보이며, 중간의 PROCESSING은 관측되지 않는다.
```

```sql
    completed_at TIMESTAMPTZ,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- 존재하지 않는 이벤트에 대한 요청 행이 생성되지 않도록 보장한다.
    CONSTRAINT fk_coupon_issue_request_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),

    CONSTRAINT fk_coupon_issue_request_issue
        FOREIGN KEY (coupon_issue_id) REFERENCES coupon_issue(id),

    -- 하나의 발급 행이 여러 성공 요청에 연결되는 것을 막는다.
    CONSTRAINT uk_coupon_issue_request_issue
        UNIQUE (coupon_issue_id),

    CONSTRAINT chk_coupon_issue_request_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'ISSUED', 'FAILED')),

    -- FAILED일 때만 실패 정보를 갖는다.
    CONSTRAINT chk_coupon_issue_request_failure
        CHECK (
            (status = 'FAILED' AND failure_code IS NOT NULL)
            OR
            (status <> 'FAILED'
                AND failure_code IS NULL
                AND failure_message IS NULL)
        ),

    -- 최종 상태에서만 완료 시각을 갖는다.
    CONSTRAINT chk_coupon_issue_request_completed
        CHECK (
            (status IN ('ISSUED', 'FAILED') AND completed_at IS NOT NULL)
            OR
            (status IN ('PENDING', 'PROCESSING') AND completed_at IS NULL)
        ),

    -- ISSUED일 때만 발급 기록과 연결된다.
    CONSTRAINT chk_coupon_issue_request_issue_result
        CHECK (
            (status = 'ISSUED' AND coupon_issue_id IS NOT NULL)
            OR
            (status <> 'ISSUED' AND coupon_issue_id IS NULL)
        ),

    -- PROCESSING일 때는 처리 시작 시각이 반드시 있어야 한다.
    CONSTRAINT chk_coupon_issue_request_processing
        CHECK (
            (status = 'PROCESSING' AND processing_started_at IS NOT NULL)
            OR
            (status <> 'PROCESSING')
        )
);
```

### **6. 요청 상태 테이블에 `UNIQUE(event_id, user_id)`를 두지 않는 이유**

아래 이력이 모두 저장되어야 한다는 점을 포함해서 설명한다.

```
req-A → ISSUED
req-B → FAILED / DUPLICATE_USER
```

```
요청 상태 테이블에 UNIQUE(event_id, user_id)를 두면 한 사용자의 요청 이력을 하나만 저장할 수 있게 되어, 같은 사용자의 두 번째 이후 요청을 아예 기록할 수 없다.

req-A → eventId 100 / userId 10 → ISSUED
req-B → eventId 100 / userId 10 → FAILED / DUPLICATE_USER

req-A와 req-B는 requestId가 서로 다른 별개의 논리적 요청이므로
각각 독립된 행으로 저장되어야 한다.
UNIQUE(event_id, user_id)가 있으면 req-B의 INSERT가 제약 위반으로 실패해 요청 자체를 접수할 수 없게 된다.

이 경우 실패 이유를 조회하지 못하거나, 요청 이력이 남지 않는 문제가 발생할 수 있다. 
따라서 UNIQUE(event_id, user_id)를 두면 안된다.
```

### **7. Redis가 `IDEMPOTENT_RETRY`를 반환했지만 DB에 요청 행이 없는 경우**

이 상태가 발생할 수 있는 이유를 설명한다.

```
Redis 판정과 DB 요청 등록은 하나의 트랜잭션으로 묶이지 않는다.
따라서 Redis에는 통과 기록이 남았지만 coupon_issue_request INSERT가 완료되지 않은 중간 구간이 존재한다.
```

이 상태를 무조건 정상 `PENDING`으로 응답하면 안 되는 이유:

```
요청 행이 없다는 것은 Kafka 메시지도 발행되지 않았다는 뜻이다.
Consumer는 이 요청의 존재 자체를 알 수 없으므로 아무도 처리하지 않는다. 즉 영원히 완료되지 않는 요청을 정상 접수로 위장하게 되며,
Redis의 선착순 자리 하나가 아무에게도 발급되지 않은 채 소모된다.
```

재조회·복구·보상 방향:

```
1. 짧은 시간 후 재조회
   다른 서버의 INSERT가 아직 커밋되지 않았을 수 있으므로
   즉시 실패로 판단하지 않고 짧은 간격으로 다시 조회한다.

2. DB 등록 재시도
   재조회에도 행이 없으면 같은 requestId로
   coupon_issue_request INSERT와 Kafka 발행을 다시 시도한다.
   Redis 자리는 이미 이 requestId의 것이므로
   새 자리를 차지하는 것이 아니며, ON CONFLICT DO NOTHING으로
   동시 복구가 겹쳐도 안전하다.

3. 일정 시간 이상 지속되면 Redis 자리 보상
   복구가 계속 실패하면 Redis에서 해당 사용자 기록을 삭제하고
   차감한 수량을 되돌린다.
   보상은 Lua Script 안에서 원자적으로 수행하며,
   현재 사용자에게 저장된 requestId가 복구 대상 requestId와
   동일한지 반드시 확인한 뒤 삭제한다.
   확인하지 않으면 그 사이 자리를 차지한
   다른 요청의 기록을 삭제할 수 있다.
```

### **8. Redis가 `SUCCESS`를 반환했지만 DB INSERT가 충돌한 경우**

다음 상황을 고려한다.

```
과거 요청 req-001은 DB에 존재한다.
Redis 데이터는 초기화되었다.
Client가 req-001을 다시 전송한다.
Redis는 새로운 요청으로 판단해 SUCCESS를 반환한다.
DB INSERT는 request_id 충돌로 0행이다.
```

아래 항목을 작성한다.

```

INSERT가 0행이므로 request_id = req-001인 기존 행을 조회해
저장된 request_hash와 이번 요청의 request_hash를 비교한다.

해시 같음
-> 같은 논리적 요청의 재시도다.
   Redis가 초기화되어 IDEMPOTENT_RETRY를 판정하지 못했을 뿐이며,
   DB 기준으로는 이미 등록·처리된 요청이다.
   기존 행의 상태(PENDING / ISSUED / FAILED)를 그대로 사용한다.

해시 다름
-> 잘못된 Idempotency-Key 재사용이다.
   409 Conflict, IDEMPOTENCY_KEY_REUSED로 거절한다.
   
Kafka 발행 여부: x

Redis에서 새로 차지한 자리 처리: 

Redis는 이 요청을 새로운 요청으로 판단해 SUCCESS를 반환했으므로수량을 차감하고 user 10 -> req-001 기록을 새로 저장한 상태다.
그러나 실제로는 이미 DB에 등록된 기존 요청이므로 새 발급이 일어나지 않는다.

보상하지 않으면 Redis 기준 잔여 수량만 1 감소한 채 아무에게도 발급되지 않는 자리가 생긴다.

보상 방법
- Lua Script 안에서 원자적으로 수행한다.
- 현재 user 10에 저장된 requestId가 req-001과 동일한지 확인한 뒤
  기록을 삭제하고 차감한 수량을 되돌린다.
- 확인 없이 삭제하면 그 사이 정당하게 자리를 차지한
  다른 요청의 기록을 지울 수 있다.

다만 기존 행이 이미 ISSUED라면 실제 발급이 일어난 요청이므로,
DB의 issued_count 기준으로는 정상이며
Redis 카운터만 실제보다 더 차감된 상태다.
이 경우에도 중복 차감분을 되돌려 Redis와 DB의 기준을 맞춘다.
```

### **9. 최초 요청 접수 성공 응답 설계하기**

HTTP Status Code:

```
202 Accepted
```

응답 JSON:

```
{
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다."
```

이 응답이 최종 발급 성공을 의미하지 않는 이유:

```
202 Accepted는 요청이 비동기 처리 흐름에 들어갔다는 의미일 뿐이다.
```

## **과제 6. Consumer의 조건부 상태 전이와 처리 권한 설계하기**

Kafka 메시지가 중복 전달되더라도 한 Consumer만 실제 발급 로직을 수행하도록 처리 권한 획득 방식을 설계한다.

### **1. Kafka 메시지와 요청 상태 행의 일치 검증**

다음 필드를 비교한다.

```
| **필드** | **Kafka Message** | **coupon_issue_request** | **불일치 시 처리** |
| --- | --- | --- | --- |
| requestId | 메시지 payload의 requestId (예: req-001) | request_id (Primary Key) | DB 요청 등록과 Kafka 메시지가 불일치하는 상태이므로 발급 처리를 하지 않는다 |
| eventId | 메시지 payload의 eventId (예: 100) | event_id | 손상된 메시지이거나 잘못된 재사용이므로 다른 이벤트의 쿠폰이 발급되는 것을 막아야 한다 |
| userId | 메시지 payload의 userId (예: 10) | user_id | 다른 사용자에게 쿠폰이 발급되는 결과로 이어질 수 있으므로 반드시 차단한다 |
```

메시지 내용 불일치를 재시도 대상으로 두기 어려운 이유:

```
메시지 내용과 DB 요청 행의 내용이 다른 것은 일시적 상태가 아니라
데이터 자체가 잘못된 상황이다.
DB 연결 실패나 Deadlock처럼 잠시 후 다시 처리하면 성공할 수 있는 오류와 달리, 메시지의 eventId나 userId가 요청 행과 다르다는 사실은 시간이 지나거나 재전달된다고 해서 달라지지 않는다.
```

### **2. SELECT 후 UPDATE 방식의 Race Condition 분석하기**

위험한 흐름은 다음과 같다.

```
1. 상태를 SELECT한다.
2. PENDING인지 애플리케이션에서 확인한다.
3. PROCESSING으로 UPDATE한다.
```

두 Consumer가 동시에 실행되는 시간 순서 다이어그램을 작성한다.

```
시간       Consumer A                  Consumer B
------------------------------------------------------------
T1         status 조회 → PENDING
T2                                     status 조회 → PENDING
T3         처리 가능 판단
T4                                     처리 가능 판단
T5         PROCESSING 저장
T6                                     PROCESSING 저장
T7         발급 처리 시작              발급 처리 시작
```

### **3. 조건부 UPDATE로 처리 권한 획득하기**

SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
```

### **4. 영향받은 row 수의 의미**

```
affected rows = 1
→ 내가 PENDING을 PROCESSING으로 변경했다. 처리 권한 획득

affected rows = 0
→ 요청이 없거나, 다른 Consumer가 처리했거나, 이미 최종 상태다.
```

### **5. 두 Consumer가 동시에 같은 requestId를 처리할 때 DB 내부 동작**

현재 상태는 `PENDING`이다.

```
Consumer A: 
→ Row Lock 획득 → PROCESSING 변경 → affected rows = 1

Consumer B:
→ A의 트랜잭션 종료까지 대기
→ 최신 상태로 WHERE 조건 재평가
→ status가 더 이상 PENDING이 아니므로 0행
```

`READ COMMITTED`에서 두 번째 Consumer의 `WHERE status = 'PENDING'` 조건이 어떻게 처리되는지 설명한다.

```
같은 행을 갱신하려 하지만 A가 Lock을 보유하고 있으므로 A의 트랜잭션이 종료될 때까지 대기한다.
A가 종료된 뒤 잠금이 해제되면, B는 자신이 처음 읽었던 값이 아니라
갱신된 최신 버전의 행으로 WHERE 조건을 다시 평가한다.
이때 status는 더 이상 PENDING이 아니므로 조건을 만족하지 않고
affected rows = 0을 얻는다.
처리 권한을 얻지 못했으므로 발급 로직을 실행하지 않고, 기존 상태를 조회해 ISSUED 또는 FAILED면 멱등 성공으로 종료한다.
```

### **6. REPEATABLE READ 이상에서 달라질 수 있는 점**

```
트랜잭션은 시작 시점의 스냅샷을 기준으로 데이터를 본다.
갱신하려는 행이 자신의 스냅샷 이후에 다른 트랜잭션에 의해 변경·커밋된 것을 발견하면, 최신 버전으로 조건을 재평가하는 대신 직렬화 오류를 발생시킨다.
```

### **7. affected rows가 0일 때 상태별 처리**

```
| **조회 결과** | **의미** | **Consumer 처리** | **Offset 처리 방향** |
| --- | --- | --- | --- |
| 요청 행 없음 | DB 요청 등록과 Kafka 메시지가 불일치하는 상태 | 발급 처리를 하지 않는다. 다른 서버의 INSERT가 아직 커밋되지 않았을 수 있으므로 즉시 실패로 확정하지 않고 짧은 재시도 후 다시 조회한다. 재시도에도 행이 없으면 시스템 결함으로 판단한다. | 즉시 Commit하지 않는다. 짧은 재시도 후에도 해결되지 않으면 DLQ로 보내고 Commit한다. 운영 확인 및 복구 대상으로 메트릭에 기록한다. |
| `PENDING` | 조건부 UPDATE 직후 다시 조회했는데 여전히 PENDING이라면, 다른 처리자가 PROCESSING으로 바꿨다가 Rollback해 상태가 되돌아갔거나 조회 시점의 경합으로 인한 일시적 상태 | 최종 상태가 아니므로 멱등 성공으로 종료해서는 안 된다. 처리되지 않은 요청이 남을 수 있으므로 재처리 대상으로 둔다. | Commit하지 않는다. 예외를 던져 Kafka 재전달로 넘기고, 재전달된 메시지가 다시 처리 권한 획득을 시도하게 한다. |
| `PROCESSING` | 다른 Consumer가 처리 권한을 보유한 상태 | 발급 처리를 하지 않는다. 즉시 Commit하면 기존 처리자가 실패했을 때 요청이 고착되고, 무조건 즉시 재시도하면 처리 중인 작업과 계속 충돌한다. Lease를 사용하는 구조라면 lease_until 만료 여부를 확인해 만료되었을 때만 권한을 회수한다. | 즉시 Commit하지 않는다. 지연 후 재시도하거나 lease 만료를 확인한 뒤 처리한다. 오래된 PROCESSING은 별도 복구 대상이다. |
| `ISSUED` | 이미 성공한 요청의 중복 메시지 | 새 발급 로직을 실행하지 않는다. 어떤 변경도 하지 않고 정상 처리로 간주해 종료한다. 예외를 던지면 이미 성공한 요청이 Retry Topic을 왕복하다 DLQ로 이동하므로 예외로 처리하지 않는다. | Commit한다. 최종 상태를 확인하고 아무 변경 없이 끝내는 것도 성공적인 처리다. |
| `FAILED` | 이미 최종 실패로 확정된 요청의 중복 메시지 | 새 발급 로직을 실행하지 않고 기존 실패 결과를 유지한다. FAILED를 ISSUED로 덮어쓰지 않으며, 아무 변경 없이 종료한다. | Commit한다. 최종 상태가 확정된 요청이므로 더 이상 재처리할 필요가 없다. |
```

### **8. ISSUED 또는 FAILED 중복 메시지를 예외로 던지면 안 되는 이유**

아래 잘못된 흐름을 기준으로 설명한다.

```
ISSUED 확인
→ DuplicateMessageException
→ Retry Topic
→ 다시 ISSUED 확인
→ 다시 예외
→ DLQ
```

```
ISSUED와 FAILED는 최종 상태여서 재시도해도 결과가 바뀌지 않으므로, 예외를 던져 재시도 흐름을 타게 하면 이미 정상 완료된 요청이 불필요하게 Retry Topic을 왕복하다 DLQ로 이동하게 되기 때문이다.
```

### **9. 최종 상태를 확인하고 아무 변경 없이 종료하는 것도 성공적인 처리인 이유**

```
메시지의 목적은 req-001의 쿠폰 발급을 처리하는 것이다.
요청 상태가 ISSUED라면 issued_count 증가, coupon_issue 저장, 요청 상태 변경이 모두 커밋되어 목적이 이미 달성된 상태다. FAILED라면 발급하지 않는 것으로 결과가 확정된 상태다.

따라서 아무것도 하지 않는 것은 처리를 건너뛴 것이 아니라, 요구된 결과가 이미 존재함을 확인하고 그것을 유지한 것이기 때문에 성공적인 처리가 되는 것이다.
```

## **과제 7. 발급 트랜잭션과 Rollback 이후 상태 확정 설계하기**

처리 권한 획득부터 최종 요청 상태 변경까지를 하나의 DB 트랜잭션으로 설계한다.

### **1. 트랜잭션에 포함할 작업과 포함하지 않을 작업 구분하기**

```
| **작업** | **발급 트랜잭션 포함 여부** | **이유** |
| --- | --- | --- |
| PENDING → PROCESSING | o | 처리 권한 획득이 트랜잭션의 시작점이다. 조건부 UPDATE가 1행을 반환한 처리자만 이후 단계를 진행하며, Row Lock을 트랜잭션 종료까지 유지해 여러 Consumer 중 하나만 발급 로직을 실행하도록 보장한다. 이후 단계가 실패하면 이 전이도 함께 취소되어 상태가 PENDING으로 복귀하므로, 재전달된 메시지가 다시 권한 획득을 시도할 수 있다. |
| coupon_event 수량 확보 | o | 발급 성공의 필수 조건이다. 수량만 증가하고 발급 기록 저장이 실패하면 실제 사용자 없이 쿠폰 한 장이 소모되므로, 발급 기록·요청 상태와 반드시 함께 Commit되거나 함께 Rollback되어야 한다. |
| coupon_issue INSERT | 0 | 최종 발급 사실을 기록하는 작업이다. 이 행만 저장되고 수량 증가가 반영되지 않으면 전체 수량 제한을 신뢰할 수 없게 된다. UNIQUE(event_id, user_id) 위반 시 전체 트랜잭션이 Rollback되어야 수량 증가도 함께 취소된다. |
| request ISSUED / FAILED 변경 | o | 요청 상태와 실제 발급 결과가 어긋나지 않도록 함께 커밋해야 한다. 상태만 ISSUED가 되고 발급 기록이 없으면 조회 API는 성공을 반환하지만 실제 쿠폰이 존재하지 않는다. 반대로 발급만 되고 상태가 갱신되지 않으면 중복 메시지가 다시 발급을 시도한다. |
| 이메일 발송 | x | 외부 네트워크 호출이므로 응답 시간이 길고 실패 시점을 예측하기 어렵다. 트랜잭션 안에서 호출하면 Row Lock과 DB Connection을 오래 점유하고, 메일 서버 장애가 핵심 발급 트랜잭션에 전파된다. 발급 결과 이벤트로 분리해 커밋 이후 비동기로 처리한다. |
| 앱 푸시 발송 | x | 이메일과 동일하게 외부 시스템 호출이다. 푸시 발송 실패 때문에 이미 확정된 발급이 Rollback되어서는 안 되며, 발급 성공과 알림 발송은 실패해도 되는 정도가 다르다. 별도 이벤트로 분리한다. |
| 마이페이지 조회 모델 갱신 | x | 발급 결과로부터 파생되는 조회용 데이터이므로 핵심 발급 결과와 원자성을 함께 보장할 필요가 없다. 갱신이 지연되어도 최종적으로 일관되면 충분하며, 트랜잭션에 포함하면 커밋 지연과 Lock 경합만 늘어난다. |
| 외부 API 호출 | x | 응답 시간과 실패 시점을 통제할 수 없고, 롤백해도 외부 시스템의 변경은 되돌릴 수 없어 원자성이 성립하지 않는다. 외부 서비스 장애가 발급 흐름 전체로 전파되므로 트랜잭션 밖에서 처리한다. |
```

### **2. 전체 발급 트랜잭션 흐름 다이어그램**

다음 경로를 모두 포함한다.

```
처리 권한 획득 0행

수량 UPDATE 0행

coupon_issue INSERT 성공

coupon_issue UNIQUE 위반

최종 ISSUED 변경 0행

일시적 DB 오류
```

```
Consumer 메시지 수신
  |
  | requestId로 coupon_issue_request 조회
  | 메시지와 요청 행 일치 검증 (requestId / eventId / userId)
  |
  +-- 요청 행 없음
  |     -> 발급 처리 안 함
  |        짧은 재시도 후에도 없으면 DLQ / 운영 확인
  |
  +-- 내용 불일치
  |     -> 발급 금지
  |        FAILED / REQUEST_MISMATCH 확정, DLQ 후보
  |        (재시도해도 결과가 바뀌지 않음)
  |
  +-- 일치
        |
        v
BEGIN TRANSACTION
  |
  v
(1) coupon_issue_request 처리 권한 획득
    UPDATE ... SET status = 'PROCESSING'
    WHERE request_id = :requestId AND status = 'PENDING'
  |
  +-- affected rows = 0
  |     -> 기존 상태 재조회
  |          |
  |          +-- ISSUED   -> 이미 성공한 요청의 중복 메시지
  |          |               새 발급 없음, 무변경 종료
  |          |               COMMIT -> Offset Commit
  |          |
```

### **3. 정상 발급 SQL 흐름 완성하기**

```
BEGIN;

-- 1. PENDING 요청의 처리 권한 획득
--    상태 확인과 변경을 하나의 SQL로 원자적으로 처리한다.
--    여러 Consumer가 동시에 실행해도 정확히 하나만 1행을 얻는다.
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows = 1인 경우에만 다음 단계로 진행한다.
-- 0행이면 기존 상태를 재조회해 ISSUED / FAILED면 멱등 성공으로 종료한다.

-- 2. 수량이 남아 있을 때만 issued_count 증가
--    조건부 UPDATE로 DB 기준 전체 수량 초과를 최종 방어한다.
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
-- affected rows = 1인 경우에만 INSERT를 수행한다.
-- 0행이면 DB 기준 SOLD_OUT으로 확정하고
-- request를 FAILED / SOLD_OUT으로 변경한 뒤 COMMIT한다.

-- 3. 최종 발급 기록 저장
--    UNIQUE(event_id, user_id)가 사용자 중복 발급을 최종 차단한다.
INSERT INTO coupon_issue (
    event_id, user_id, status, issued_at
)
VALUES (
    :eventId, :userId, 'ISSUED', CURRENT_TIMESTAMP
)
RETURNING id;
-- 반환된 id를 :couponIssueId로 사용한다.
-- UNIQUE 위반 시 전체 트랜잭션을 ROLLBACK하고
-- 별도 트랜잭션에서 FAILED / DUPLICATE_USER로 확정한다.

-- 4. 요청 상태를 ISSUED로 변경
--    출발 상태를 조건에 포함해 최종 상태 덮어쓰기를 방지한다.
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';
-- 반드시 1행이어야 한다.
-- 0행이면 요청 상태와 발급 결과가 어긋나므로 전체를 ROLLBACK한다.

COMMIT;
```

### **4. 각 단계에서 반드시 확인할 영향받은 row 수**

```
| **단계** | **정상적으로 기대하는 row 수** | **기대값과 다를 때 처리** |
| --- | --- | --- |
| 처리 권한 획득 | 1 | 0행이면 처리 권한을 얻지 못한 것이므로 발급 로직을 진행하지 않는다. 즉시 실패로 처리하지 않고 기존 상태를 재조회해 구분한다. ISSUED 또는 FAILED면 이미 확정된 요청의 중복 메시지이므로 무변경 종료 후 Offset을 Commit한다. PROCESSING이면 다른 처리자가 작업 중이므로 즉시 Commit하지 않고 지연 후 재시도하거나 lease 만료를 확인한다. 요청 행이 없으면 DB 등록과 메시지가 불일치하는 상태이므로 재조회 후 DLQ·운영 확인 대상으로 보낸다. |
| 수량 UPDATE | 0 or 1 | 1행이면 수량을 확보했으므로 coupon_issue INSERT로 진행한다. 0행은 오류가 아니라 DB 기준 수량 소진을 의미한다. 이벤트 존재는 FK와 메시지 검증으로 보장되고 필터 조건이 수량뿐이므로 SOLD_OUT으로 확정하고, 같은 트랜잭션에서 request를 FAILED / SOLD_OUT으로 변경한 뒤 Commit한다. 발급 행은 생성하지 않는다. 상태·기간 조건을 함께 걸었다면 0행의 원인이 여러 개이므로 별도 SELECT로 SOLD_OUT과 INVALID_EVENT를 구분해야 한다. |
| 최종 ISSUED 변경 | 1 | 0행이면 요청 상태와 발급 결과가 어긋난 상태다. 이미 다른 처리자가 상태를 변경했거나 롤백으로 출발 상태가 달라진 경우이며, 발급 결과만 커밋하면 coupon_issue는 존재하는데 요청 상태는 ISSUED가 아닌 불일치가 남는다. 따라서 전체 트랜잭션을 ROLLBACK하고 예외를 재전파해 Kafka 재전달로 재처리한다. FAILED로 확정하지 않는다. |
```

### **5. 마지막 ISSUED 상태 변경이 0행인데 발급 결과만 Commit하면 안 되는 이유**

```
발급 결과만 commit 하는 경우 요청 상태와 실제 발급 결과가 어긋난다.
최종 발급 여부의 판단 기준은 coupon_issue_request.status다.
발급 행은 존재하는데 상태가 ISSUED가 아니면 기준 데이터가 실제와 다른 값을 가리키게 된다.

상태가 FAILED로 바뀌어 있었다면 사용자는 발급 실패로 안내받지만 실제로는 쿠폰이 발급되어 수량 한 장이 소모된 상태다. 상태가 PENDING이면 조회 API는 계속 처리 중을 반환한다.
```

### **6. DB 기준 수량이 소진된 경우 처리**

조건부 UPDATE가 0행이고 이벤트가 존재하며 수량이 모두 소진된 것으로 확정되었다고 가정한다.

요청 상태를 `FAILED / SOLD_OUT`으로 변경하는 SQL을 작성한다.

```
UPDATE coupon_issue_request
SET status = 'FAILED',
    failure_code = 'SOLD_OUT',
    failure_message = '쿠폰이 모두 소진되었습니다.',
    completed_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';
```

발급 행 생성 여부:

```
생성하지 않는다.

수량을 확보하지 못했으므로 발급이 일어나지 않았다.
coupon_issue는 발급에 성공한 기록만 저장하는 테이블이므로 실패한 요청의 행을 만들지 않는다.
```

같은 메시지가 다시 들어왔을 때 처리:

```
FAILED는 최종 상태이므로 재시도해도 결과가 바뀌지 않는다.
재전달된 메시지는 조건부 UPDATE에서 0행을 받고, 기존 상태가 FAILED임을 확인한 뒤 발급 로직을 실행하지 않고 아무 변경 없이 종료한 다음 Offset을 Commit한다.
예외를 던지면 이미 확정된 요청이 Retry Topic을 왕복하다 DLQ로 이동하므로 예외로 처리하지 않는다.
```

### **7. 서로 다른 requestId로 같은 사용자가 다시 발급을 시도한 경우**

이 시나리오는 Redis 관리자 admission 기록이 유실되거나 만료되어 req-B가 SUCCESS로 통과한 상황을 가정한다. 이때 DB의 UNIQUE(event_id, user_id)가 최종 방어선이 된다.

```
기존 요청
req-A / eventId=100 / userId=10 / ISSUED

새 요청
req-B / eventId=100 / userId=10 / PENDING
```

`req-B` 처리 중 `coupon_issue` INSERT에서 `UNIQUE(event_id, user_id)` 위반이 발생했다.

아래 항목을 설명한다.

```
첫 번째 트랜잭션의 상태:
Rollback된다.
PostgreSQL에서는 제약 조건 위반이 발생하면 해당 트랜잭션이 Abort 상태가 되어 더 이상 사용할 수 없다.

PENDING → PROCESSING 전이의 결과: 
요청 상태는 다시 PENDING이 된다.
처리 권한 획득 UPDATE도 같은 트랜잭션 안에서 수행되었으므로
Rollback 대상에 포함된다.
Rollback 이후 DB에 남는 값은 PENDING이다.

앞에서 증가한 issued_count의 결과:
증가 이전 값으로 되돌아간다.
coupon_event 조건부 UPDATE가 1행을 반환해 수량을 확보했더라도
같은 트랜잭션이므로 Rollback 시 증가가 무효화된다.

같은 트랜잭션에서 FAILED로 바꿀 수 있는가?:
바꿀 수 없다.
제약 조건 위반으로 트랜잭션이 이미 Abort 상태가 되었으므로 같은 트랜잭션에서 UPDATE를 실행해도 무시된다.
설령 실행이 가능하더라도 그 변경 역시 Rollback 대상이므로 FAILED 상태가 저장되지 않는다.
따라서 새 트랜잭션에서 해당 과정이 이루어져야한다.
```

### **8. UNIQUE 위반 Rollback 후 별도 트랜잭션 처리 순서**

```
1. 현재 발급 트랜잭션을 ROLLBACK한다.
   제약 조건 위반으로 트랜잭션이 Abort 상태가 되어 더 이상 사용할 수 없다.
   PENDING -> PROCESSING 전이와 issued_count 증가가 함께 취소되며,
   요청 상태는 PENDING으로 복귀한다.

2. 새 트랜잭션을 시작한다.
   상태 확정 작업은 롤백된 트랜잭션과 완전히 분리된 별개의 트랜잭션에서 수행한다.

3. 기존 coupon_issue를 확인한다.
   event_id + user_id로 조회해 같은 사용자가 이미 발급받았음을 확인하고,
   실패 원인이 DUPLICATE_USER임을 확정한다.
   이 확인은 UNIQUE 위반이 사용자 중복 때문이 맞는지 검증하는 절차이며,
   운영 로그와 메트릭 기록에도 사용한다.

4. 현재 요청을 FAILED / DUPLICATE_USER로 확정한다.
   출발 상태는 PROCESSING이 아니라 PENDING이다.
   Rollback으로 전이가 취소되어 DB에 남은 값이 PENDING이기 때문이다.

   UPDATE coupon_issue_request
   SET status = 'FAILED',
       failure_code = 'DUPLICATE_USER',
       failure_message = '이미 발급받은 사용자입니다.',
       completed_at = CURRENT_TIMESTAMP,
       updated_at = CURRENT_TIMESTAMP
   WHERE request_id = :requestId
     AND status = 'PENDING';

   affected rows를 반드시 확인한다.
   1행이면 정상 확정, 0행이면 다른 처리자가 이미 상태를 변경했거나
   출발 상태가 다른 것이므로 현재 상태를 재조회해 판단한다.

5. COMMIT한다.
   요청 상태가 최종 실패로 확정되었으므로 Kafka Offset을 Commit한다.
   FAILED는 최종 상태이므로 같은 메시지가 다시 전달되어도
   기존 결과를 확인하고 아무 변경 없이 종료한다.
```

### **9. Rollback 후 요청 상태를 어떤 출발 상태에서 FAILED로 변경해야 하는가?**

잘못된 SQL:

```
UPDATE coupon_issue_request
SET status = 'FAILED'
WHERE request_id = :requestId
  AND status = 'PROCESSING';
```

올바른 SQL을 작성한다.

```
UPDATE coupon_issue_request
SET status = 'FAILED'
WHERE request_id = :requestId
  AND status = 'PENDING';
```

왜 `PROCESSING`이 아닌지 설명한다.

```
PROCESSING 이었던 상태가 Rollback 되면서 기존의 상태였던 PENDING으로 되돌아 갔기 때문이다.
```

### **10. 일시적 DB 오류가 발생한 경우**

다음 항목을 작성한다.

```
요청 상태: PENDING

issued_count: 증가 없음

coupon_issue: 생성되지 않음

FAILED 저장 여부: x

Kafka Listener 예외 처리:
예외를 잡아서 정상 처리로 종료하지 않고 다시 던진다.
Listener에서 예외가 전파되면 Offset이 Commit되지 않으므로
Kafka가 같은 메시지를 다시 전달한다.
재전달된 메시지는 요청 상태가 PENDING이므로 PENDING -> PROCESSING 권한 획득을 다시 시도해 정상적으로 처리된다.
```

### **11. 최종 비즈니스 실패와 일시적 시스템 오류 비교**

```
| **오류** | **최종 FAILED 저장 여부** | **Kafka 재시도 여부** | **이유** |
| --- | --- | --- | --- |
| DB 연결 일시 실패 | x | o | 일시적 시스템 오류이므로 잠시 후 다시 처리하면 성공할 수 있다. 트랜잭션을 Rollback해 상태를 PENDING으로 되돌리고, Listener에서 예외를 재전파해 Offset을 Commit하지 않는다. 재전달된 메시지가 처리 권한 획득을 다시 시도한다. |
| Deadlock | x | o | 동시 처리 과정에서 발생하는 일시적 충돌이며, 경합이 해소된 뒤 재처리하면 성공할 수 있다. Rollback으로 상태가 PENDING으로 복귀하므로 재전달된 메시지가 정상적으로 처리된다. |
| SOLD_OUT | o | x | DB 기준 수량이 소진되어 재처리해도 결과가 바뀌지 않는 최종 비즈니스 실패다. 같은 트랜잭션에서 FAILED로 확정하고 Commit한 뒤 Offset을 Commit한다. 중복 메시지가 와도 기존 FAILED를 확인하고 무변경 종료한다. |
| DUPLICATE_USER | o | x | 같은 사용자가 다른 requestId로 이미 발급받아 UNIQUE(event_id, user_id)에 위반된 상태이며, 재처리해도 항상 같은 위반이 발생한다. UNIQUE 위반으로 Rollback한 뒤 별도 트랜잭션에서 PENDING을 출발 상태로 FAILED를 확정하고 Offset을 Commit한다. |
| 메시지와 요청 행 불일치 | o | x | 손상된 메시지이거나 잘못된 발행으로 데이터 자체가 어긋난 상태이며, 재전달되어도 항상 같은 불일치가 발생한다. 발급 처리를 금지하고 요청 행이 존재하면 REQUEST_MISMATCH로 확정한다. 자동 재시도 대상이 아니라 DLQ 및 운영 확인 대상으로 분류한다. |
```

## **과제 8. Kafka Offset과 중복 메시지 처리 설계하기**

DB 비즈니스 결과와 Kafka 소비 위치를 안전하게 연결하도록 Offset 처리 순서를 설계한다.

### **1. 안전한 처리 순서 작성하기**

아래 흐름을 완성한다.

```
1. Kafka 메시지를 읽는다.

2. requestId로 coupon_issue_request를 조회해 메시지와 요청 행의 내용이 일치하는지 검증한다. (requestId / eventId / userId)
불일치하면 발급을 진행하지 않고 DLQ·운영 확인 대상으로 분류한다.

3. DB 트랜잭션을 시작한다.

4. 요청 처리 권한을 얻는다.
PENDING -> PROCESSING 조건부 UPDATE를 실행하고 affected rows를 확인한다. 1행이면 계속 진행하고, 0행이면 기존 상태를 재조회해
ISSUED 또는 FAILED이면 새 발급 없이 멱등 성공으로 종료한다.

5. 수량과 발급 기록을 처리하고 요청 상태를 최종 상태로 변경한다.
coupon_event 조건부 UPDATE로 수량을 확보하고 coupon_issue를 INSERT한 뒤 request를 ISSUED로 변경한다. 수량 UPDATE가 0행이면 DB 기준 SOLD_OUT으로 확정하고 request를 FAILED / SOLD_OUT으로 변경한다. 각 단계의 affected rows를 반드시 확인하고, 상태 변경 SQL에는 출발 상태를 조건으로 포함한다.

6. DB 트랜잭션을 Commit한다.
issued_count 증가, coupon_issue 저장, 요청 상태 확정이 함께 반영되어 최종 발급 결과가 확정된다.

7. Kafka Offset을 Commit한다.
```

### **2. DB 결과 확정과 Offset Commit의 역할 차이**

```
| **항목** | **의미** |
| --- | --- |
| DB Commit | | **항목** | **의미** |
| --- | --- |
| DB Commit | 비즈니스 관점의 처리 완료다. coupon_event.issued_count 증가, coupon_issue 저장, coupon_issue_request 상태 확정이 하나의 트랜잭션으로 반영되어, 쿠폰 발급 결과가 최종적으로 확정된 시점을 의미한다. 이 시점 이후에는 같은 요청이 다시 처리되어도 기존 결과가 그대로 유지되며, 최종 발급 여부의 판단 기준이 된다. 사용자가 상태 조회 API로 확인하는 결과도 이 커밋된 데이터다. |
| Kafka Offset Commit | Kafka 관점의 소비 완료 표시다. Consumer Group이 해당 Partition의 어느 위치까지 메시지를 읽었는지 기록하는 것이며, 이후 Consumer가 재시작되면 이 위치 다음부터 소비한다. 비즈니스 결과와는 무관하며, 발급에 성공한 경우뿐 아니라 FAILED로 확정된 요청이나 중복 메시지를 무변경 종료한 경우에도 수행한다. |
```

### **3. Offset을 먼저 Commit한 뒤 DB 처리가 실패하는 상황**

```
1. Offset Commit
2. DB 처리 시도
3. DB 장애
```

Kafka 상태:

```
해당 Record의 Offset이 이미 Commit되어 소비 완료로 표시된다.
Consumer Group의 소비 위치는 다음 Offset으로 이동한다. 
Consumer가 재시작되더라도 마지막 Commit Offset부터 읽으므로 이 Record는 다시 전달되지 않는다.
```

DB 상태:

```
발급 처리가 수행되지 않았다.

- coupon_issue_request : PENDING 상태 그대로 남는다.
- coupon_event         : issued_count가 증가하지 않는다.
- coupon_issue         : 발급 행이 생성되지 않는다.

트랜잭션이 시작되기 전이거나 도중에 장애가 발생했으므로 Rollback되어 어떤 변경도 반영되지 않는다.
```

사용자 요청에 발생하는 문제:

```
Kafka는 처리가 끝났다고 기억하지만 DB에는 발급 결과가 없다.
두 시스템의 기록이 영구적으로 어긋난 상태가 된다.

Consumer가 재시작되어도 해당 Record는 재전달되지 않으므로 이 요청을 처리할 기회가 다시 오지 않는다.

즉 사용자 요청이 유실된 것과 같은 결과가 된다.
아무도 처리하지 않는 PENDING 요청으로 남으며, 오래된 PENDING을 찾는 복구 배치나 운영자의 수동 개입 없이는 해소되지 않는다.
```

### **4. DB Commit 후 Offset Commit 전에 Consumer가 종료되는 상황**

```
DB Commit 성공
→ Consumer 종료
→ Offset Commit 실패
```

Consumer 재시작 후 발생하는 일:

```
Offset이 Commit되지 않았으므로 Kafka는 해당 Record를 아직 소비하지 않은 것으로 기록하고 있다.
새 Consumer가 마지막 Commit Offset부터 읽으므로 같은 Partition의 같은 Offset을 가진 기존 Record가 그대로 재전달된다.
```

request 상태가 `ISSUED`인 경우 처리:

```
재전달된 메시지를 정상적으로 처리하고 새 발급은 수행하지 않는다.
이후 Offset을 Commit해 Kafka 기록을 DB 결과와 일치시킨다.
```

### **5. 같은 Kafka Record 재전달과 같은 requestId의 다른 Record 비교**

```
| **구분** | **Partition** | **Offset** | **requestId** |
| --- | --- | --- | --- |
| Offset 미반영으로 동일 Record 재전달 | 같음 | 같음 | 같음 |
| Producer가 같은 요청을 두 번 발행 | 같음 | 다름 | 같음 |
```

두 현상을 모두 requestId로 방어해야 하는 이유:

```
requestId는 재발행이나 Topic 이동, 재전달과 무관하게 유지되는 비즈니스 식별자이므로, 두 현상 모두 requestId로 동일 요청임을 식별하고 조건부 상태 전이와 요청 상태 조회로 중복 반영을 막을 수 있기 때문이다.
```

### **6. 자동 커밋 사용 시 확인해야 할 항목**

```
1. 자동 커밋 사용 여부
2. 수동 Acknowledgment 방식
3. Listener 예외 발생 시 Offset 처리
4. DB Rollback 시 메시지 재전달 방식
5. Retry Topic 이동 시 원본 레코드 완료 처리
```

### **7. At-Least-Once와 비즈니스 결과의 차이**

아래 문장을 완성한다.

```
메시지 전달 횟수
→ 최소 한 번

쿠폰 발급 결과
→ 한 번만 반영
```

### **8. 다음 상태에서 Offset 처리 방향 작성하기**

```
| **request 상태 또는 처리 결과** | **Offset 처리 방향** | **이유** |
| --- | --- | --- |
| 새 `PENDING` 요청 처리 성공 | DB Commit 이후 Offset을 Commit한다 | issued_count 증가, coupon_issue 저장, request ISSUED 변경이 하나의 트랜잭션으로 커밋되어 최종 결과가 확정되었다. 비즈니스 처리가 완료되었으므로 같은 메시지를 다시 전달받을 필요가 없다. 반드시 DB Commit 성공을 확인한 뒤 Offset을 Commit한다. |
| 기존 `ISSUED` 요청 중복 메시지 | Commit한다 | 이미 발급이 확정된 요청이므로 새 발급 로직을 실행하지 않고 무변경 종료한다. 요구된 결과가 DB에 이미 존재하므로 정상 처리이다. Offset을 Commit해 Kafka 기록을 DB 결과와 일치시킨다. |
| 기존 `FAILED` 요청 중복 메시지 | Commit한다 | 재시도해도 결과가 바뀌지 않는 최종 상태다. 기존 실패 결과를 유지하고 아무 변경 없이 종료하며, 더 이상 재처리할 필요가 없으므로 Commit한다. |
| 일시적 DB 오류로 Rollback | Commit하지 않는다 | 결과가 확정되지 않았고 재처리하면 성공할 수 있는 상태다. request는 PENDING으로 복귀하고 issued_count 증가와 발급 행 저장이 모두 취소되었다. Listener에서 예외를 재전파해 Offset을 커밋하지 않고 Kafka 재전달로 넘긴다. 여기서 Commit하면 요청이 유실되어 아무도 처리하지 않는 PENDING으로 남는다. |
| 요청 행 없음 | 즉시 Commit하지 않는다 | DB 요청 등록과 Kafka 메시지가 불일치하는 상태다. 다른 서버의 INSERT가 아직 커밋되지 않았을 수 있으므로 짧은 재시도 후 다시 조회하고, 그래도 행이 없으면 시스템 결함으로 판단해 DLQ로 보낸 뒤 Commit한다. 확인 없이 바로 Commit하면 복구 기회가 사라지고, 무한 재시도하면 처리량만 소모된다. 복구 대상으로 메트릭에 기록한다. |
| 메시지 내용 불일치 | 재시도하지 않고 DLQ로 보낸 뒤 Commit한다 | 손상된 메시지이거나 잘못된 발행으로 데이터 자체가 어긋난 상태이며, 재전달되어도 항상 같은 불일치가 발생한다. 발급을 금지하고 요청 행이 존재하면 REQUEST_MISMATCH로 확정한다. 자동 재시도 대상이 아니라 운영자가 원인을 확인해야 하는 문제이므로, 원본 Topic에서는 완료 처리해 다른 메시지 처리를 막지 않는다. |
```

## **과제 9. Redis, DB, Kafka 불일치와 복구 정책 설계하기**

Redis, DB, Kafka는 하나의 로컬 트랜잭션으로 묶이지 않는다.

따라서 각 경계에서 생길 수 있는 불일치를 분석하고 복구 방향을 설계한다.

### **1. 장애 시점별 상태와 복구 방향**

```
| **장애 상황** | **Redis 상태** | **DB 요청 상태** | **Kafka 상태** | **복구 방향** |
| --- | --- | --- | --- | --- |
| Redis SUCCESS 후 DB 요청 행 INSERT 전 장애 | 통과 기록 존재 | 요청 행 없음 | 메시지 없음 | 동일 requestId 재시도 시 Redis는 IDEMPOTENT_RETRY를 반환하지만 DB 행이 없다. 정상 PENDING으로 단정하지 않고 짧은 간격으로 재조회한 뒤 같은 requestId로 DB 등록과 Kafka 발행을 재시도한다. 일정 시간 이상 지속되면 Redis 자리를 보상한다. 보상은 Lua Script 안에서 현재 사용자에게 저장된 requestId가 복구 대상과 동일한지 확인한 뒤 기록 삭제와 수량 복구를 원자적으로 수행한다. |
| DB에 PENDING 저장 후 Kafka 발행 전 장애 | 통과 기록 존재 | PENDING | 메시지 없음 | Consumer가 요청의 존재를 알 수 없으므로 아무도 처리하지 않고 PENDING에 남는다. Kafka 발행이 확인되지 않았다면 202 Accepted를 반환하지 않고 즉시 재발행을 시도한다. 즉시 재시도까지 실패하면 (status, updated_at) 인덱스로 오래된 PENDING을 조회하는 복구 배치가 같은 requestId로 재발행한다. |
| Kafka 발행 성공 후 API 응답 유실 | 통과 기록 존재 | PENDING | 메시지 존재 | 시스템 내부는 정상 상태이며 클라이언트만 결과를 알지 못한다. 별도의 복구가 필요 없고, 클라이언트가 동일한 requestId로 재시도하면 Redis IDEMPOTENT_RETRY 또는 DB의 request_id 충돌로 재시도임을 식별해 새 작업을 만들지 않고 기존 상태를 반환한다. |
| Consumer가 DB 처리 전 종료 | 통과 기록 존재 | PENDING | 메시지 존재 | Offset이 커밋되지 않았으므로 같은 Record가 재전달된다. 재전달된 메시지가 PENDING -> PROCESSING 처리 권한 획득을 다시 시도해 정상적으로 처리된다. |
| DB Commit 후 Offset Commit 전 종료 | 통과 기록 존재 | ISSUED | 메시지 존재 | Kafka는 미처리로, DB는 확정으로 기록되어 두 기록이 어긋난다. 이 구간의 장애는 완전히 제거할 수 없으므로 중복 전달을 허용하고 Consumer 멱등성으로 흡수한다. 재전달된 메시지는 조건부 UPDATE에서 0행을 받고 ISSUED를 확인한 뒤 새 발급 없이 무변경 종료하고 Offset을 Commit한다. |
| DB ISSUED 후 Redis 데이터 유실 | 통과 기록 소실 | ISSUED | 처리 완료 | DB는 정상이므로 최종 발급 결과에는 문제가 없다. 다만 Redis 앞단 필터가 무력화되어 이미 발급받은 사용자의 새 요청이 DUPLICATE_USER로 차단되지 않고 SUCCESS로 통과한다. 이 요청은 Consumer에서 coupon_issue의 UNIQUE(event_id, user_id) 위반으로 걸러져 FAILED / DUPLICATE_USER로 확정되며, DB 조건부 UPDATE가 수량 초과도 최종 방어한다. |
```

### **2. Redis SUCCESS 후 DB 요청 행이 없는 상태**

이 상태가 발생하는 흐름을 다이어그램으로 작성한다.

```
Client
  |
  | Idempotency-Key: req-001
  v
API Server
  |
  | 인증 userId 확인 / requestHash 생성
  v
Redis Lua Script
  |
  | 사용자 판정 통과
  | 수량 차감 (issued-count + 1)
  | user:10 -> req-001 저장
  |
  | -> SUCCESS 반환
  v
coupon_issue_request INSERT 시도
  |
  X  장애 발생
     - API Server 프로세스 종료
     - DB 연결 실패 / Connection Pool 고갈
     - 트랜잭션 Rollback
     - INSERT 직전 네트워크 단절
  |
  v
결과 상태
```

동일 requestId 재시도 시 처리 방향:

```
다른 API Server의 INSERT가 아직 커밋되지 않아 일시적으로 보이지 않는 것일 수 있으므로 즉시 실패로 판단하지 않는다.

재조회에도 행이 없으면 같은 requestId로 DB 등록을 재시도한다.
INSERT는 ON CONFLICT (request_id) DO NOTHING으로 수행해 동시 복구가 겹쳐도 안전하게 만든다.
Redis 자리는 이미 req-001의 것이므로 새로운 자리를 차지하는 것이 아니며 수량을 다시 차감하지 않는다.
```

일정 시간 이상 지속될 때 가능한 보상:

```
DB 등록 재시도가 계속 실패해 Redis 기록만 남은 채 일정 시간이 경과하면 Redis 자리를 반환한다.

보상 내용은 해당 사용자의 admission 기록 삭제와 차감된 수량 복구이며, 이 두 작업은 Lua Script 안에서 원자적으로 수행한다.
```

보상 시 현재 Redis 자리의 requestId 소유권을 확인해야 하는 이유:

```
소유권을 확인하지 않고 해당 사용자의 기록을 삭제하면 그 사이 자리를 차지한 다른 사용자의 요청 기록이 지워질 수 있다.
```

### **3. PENDING 저장 뒤 Kafka 발행 실패**

최종 상태를 작성한다.

```
Redis: 통과 기록 존재

DB: PENDING 상태 존재

Kafka: 메시지 발급 x
```

이 요청이 계속 `PENDING`에 남는 이유:

```
PENDING에서 다른 상태로 전이시킬 수 있는 주체는 Consumer뿐이고, Consumer를 동작시키는 유일한 수단은 Kafka 메시지다.
메시지가 없으면 Consumer는 이 요청의 존재 자체를 알 수 없으므로 처리 권한 획득도, 발급도, 상태 확정도 일어나지 않는다.
```

복구를 위해 필요한 인덱스 또는 조회 조건:

```sql
CREATE INDEX idx_coupon_issue_request_status_updated
ON coupon_issue_request (status, updated_at);

SELECT request_id, event_id, user_id
FROM coupon_issue_request
WHERE status = 'PENDING'
  AND updated_at < CURRENT_TIMESTAMP - INTERVAL '5 minutes';
```

복구 방향:

```
Kafka 발행이 확인되지 않았다면 202 Accepted를 반환하지 않는다.
클라이언트가 접수되었다고 믿는데 실제로는 아무도 처리하지 않는
상태가 되기 때문이다.

먼저 즉시 재발행을 시도한다.
대부분의 일시적 오류는 Producer 레벨 재시도에서 해결된다.

즉시 재시도까지 실패했거나 그 도중 API Server가 종료된 경우를 위해 복구 배치를 둔다.
위 인덱스로 오래된 PENDING 요청을 조회해 같은 requestId로 다시 발행한다.
이때 이미 발행에 성공했던 요청이 함께 조회되어 중복 발행될 수 있으나, Consumer가 조건부 상태 전이로 흡수하므로 안전하다.
```

### **4. Kafka 발행 Timeout이 모호한 이유**

아래 두 상황을 설명한다.

```
상황 A
Broker가 메시지를 저장하지 못하고 Timeout

상황 B
Broker는 메시지를 저장했지만 ACK만 유실되어 Timeout
```

Producer가 두 상황을 구분하기 어려운 이유:

```
Producer가 Broker의 처리 결과를 알 수 있는 유일한 수단은 ACK다.
Timeout은 정해진 시간 안에 ACK를 받지 못했다는 사실만 알려줄 뿐,
ACK가 오지 않은 원인까지 알려주지는 않는다.
```

같은 requestId로 재발행했을 때 가능한 Kafka Record:

```
상황 A였다면 저장된 Record가 없으므로 재발행으로 하나만 생성된다.

Offset 100 -> req-001

상황 B였다면 이미 저장된 Record가 있으므로
재발행으로 같은 requestId의 Record가 하나 더 생성된다.

Offset 100 -> req-001
Offset 101 -> req-001
```

Consumer가 안전하게 처리할 수 있는 이유:

```
Consumer 멱등성의 기준이 Offset이 아니라 requestId이기 때문이다.
두 Record는 Offset이 다르지만 payload의 requestId가 동일하므로 Consumer는 이를 하나의 논리적 요청으로 인식한다.
```

### **5. Outbox Pattern이 줄일 수 있는 불일치**

아래 두 작업을 하나의 DB 트랜잭션으로 묶는 구조를 작성한다.

```
coupon_issue_request INSERT

outbox_event INSERT
```

다이어그램:

```
Client
  |
  | Idempotency-Key: req-001
  v
API Server
  |
  | 인증 userId 확인 / requestHash 생성
  v
Redis Lua Script
  |
  | SUCCESS
  v
+--------------------------------------------------+
| DB Transaction                                   |
|--------------------------------------------------|
|                                                  |
|  coupon_issue_request INSERT                     |
|    request_id   = req-001                        |
|    status       = 'PENDING'                      |
|    request_hash = ...                            |
|                                                  |
|  outbox_event INSERT                             |
|    aggregate_id = req-001                        |
|    topic        = coupon.issue.requested         |
|    payload      = { requestId, eventId,          |
|                     userId, requestedAt }        |
|    status       = 'PENDING'                      |
|                                                  |
|  -> 두 INSERT가 함께 Commit되거나 함께 Rollback   |
+--------------------------------------------------+
  |
  | COMMIT
  v
202 Accepted (status = PENDING)

[별도 Publisher - 비동기]

Outbox Publisher (폴링 또는 CDC)
  |
  | SELECT * FROM outbox_event
  | WHERE status = 'PENDING'
  | ORDER BY created_at
  v
Kafka Producer
  |
  | key = requestId
  v
coupon.issue.requested Topic
  |
  +-- 발행 성공
  |     -> outbox_event status = 'PUBLISHED'
  |
  +-- 발행 실패 / Timeout
        -> outbox_event PENDING 유지
        -> 다음 폴링에서 재시도
        -> 결과가 모호해 중복 Record가 생길 수 있으나
           Consumer 멱등성으로 흡수한다
```

### **6. Outbox Pattern이 해결하지 못하는 구간**

아래 구간을 기준으로 설명한다.

```
Redis 선착순 판정
↔
DB 요청 상태 저장
```

```
Outbox Pattern은 같은 DB 안의 두 테이블에 대한 쓰기를 하나의 로컬 트랜잭션으로 묶는 기법이다.
coupon_issue_request와 outbox_event는 모두 같은 DB에 있으므로
원자성이 성립한다.

그러나 Redis는 별개의 저장소이며 DB 트랜잭션에 참여하지 않는다.
Redis Lua Script가 실행되면 수량 차감과 admission 기록이 즉시 반영되고, 이후 DB 트랜잭션이 Rollback되어도 함께 되돌아가지 않는다.
```

### **7. 최종 발급 결과의 기준 데이터**

다음 중 최종 발급 여부를 판단할 기준을 선택하고 이유를 설명한다.

```
Redis 통과 기록

Kafka 메시지 존재 여부

coupon_issue DB 기록

coupon_issue_request 상태
```

선택:

```
coupon_issue_request 상태 (status = 'ISSUED')
```

이유:

```
최종 발급 성공은 issued_count 증가, coupon_issue 저장,
coupon_issue_request ISSUED 변경이 하나의 트랜잭션으로 Commit된 시점에 확정된다.
coupon_issue_request는 이 세 작업과 같은 트랜잭션에 속하면서 요청 단위로 결과를 조회할 수 있는 유일한 데이터다.
```

### **8. 재실행 가능한 설계 정리하기**

```
| **단계** | **중복 또는 재실행 방어 기준** |
| --- | --- |
| Redis 판정 | eventId + userId로 사용자 중복을 확인하고, 해당 사용자에게 저장된 최초 requestId와 비교해 같은 요청의 재시도인지 구분한다. |
| DB 요청 등록 | request_id Primary Key와 ON CONFLICT DO NOTHING으로 최초 등록자를 결정한다. |
| Kafka 재발행 | 같은 requestId로의 재발행을 허용한다. |
| Consumer 처리 | requestId로 요청 행을 조회해 메시지와 eventId·userId가 일치하는지 검증한 뒤, PENDING → PROCESSING 조건부 UPDATE로 처리 권한을 획득한다. 1행을 얻은 처리자만 발급 로직을 실행하고, 0행이면 기존 상태를 확인해 ISSUED·FAILED면 무변경 종료한다. |
```

### **9. 운영 메트릭과 경고 항목 설계하기**

아래 항목을 포함해 최소 5개 작성한다.

```
오래된 PENDING 요청 수

오래된 PROCESSING 요청 수

requestId 충돌 횟수

Redis SUCCESS 후 DB 행 누락 횟수

Kafka 발행 실패 횟수

멱등 중복 메시지 처리 횟수
```

```
| **메트릭** | **의미** | **경고가 필요한 조건** |
| --- | --- | --- |
| 오래된 PENDING 요청 수 | 접수된 뒤 일정 시간이 지나도록 최종 상태로 확정되지 않은 요청의 수 | 정상 처리 소요 시간(발행 + Consumer 대기 + 처리)의 최대치를 넘는 PENDING이 존재하면 경고한다 |
| 오래된 PROCESSING 요청 수 | 처리 권한을 획득한 뒤 최종 상태로 확정되지 않은 요청의 수 | 단일 트랜잭션 구조에서는 값이 0에 가까워야 하므로, 소수라도 일정 시간 이상 유지되면 경고한다. 별도 Claim 커밋 방식이라면 lease 만료 시간을 초과한 PROCESSING이 존재할 때 경고한다. |
| requestId 충돌 횟수 | INSERT가 ON CONFLICT로 0행을 반환한 횟수 | 해시 불일치(IDEMPOTENCY_KEY_REUSED)는 정상 흐름에서 발생하지 않아야 하는
값이므로 낮은 임계값에서 경고한다. |
| Redis SUCCESS 후 DB 행 누락 횟수 | Redis 판정을 통과했으나 coupon_issue_request INSERT가 완료되지 않아, Redis에는 통과 기록이 있는데 DB에 요청 행이 없는 상태의 발생 횟수 | 정상 흐름에서는 발생하지 않아야 하므로 1건이라도 기록하고, 짧은 시간에 반복되면 경고한다. DB 연결 이상이나 API Server 비정상 종료의 신호일 수 있다. |
| Kafka 발행 실패 횟수 | 요청 행 저장 후 Kafka 발행이 실패하거나 Timeout된 횟수. 즉시 재시도로 해결된 건수와 최종 실패 건수를 분리해 집계한다. | 최종 실패가 발생하면 해당 요청이 PENDING에 고착되므로 즉시 경고한다. 재시도 성공 건수가 급증하면 브로커나 네트워크 상태 악화의 선행 신호로 본다. |
```

## **과제 10. 나쁜 멱등 설계의 문제점 찾기**

아래 시스템은 `requestId`를 사용하고 있지만 안전한 멱등 구조라고 보기 어렵다.

```
1. API Server가 요청을 받을 때마다 새로운 requestId를 생성한다.

2. 같은 requestId가 들어오면 요청 내용은 확인하지 않고
   기존 결과를 무조건 반환한다.

3. 요청 상태는 coupon_issue에 성공 기록만 저장한다.

4. Consumer는 SELECT로 PENDING을 확인한 뒤
   조건 없이 PROCESSING으로 UPDATE한다.

5. 최종 상태 변경 SQL에 이전 상태 조건이 없다.

6. request가 ISSUED이면 DuplicateMessageException을 던진다.

7. Kafka Offset은 DB 처리 전에 자동 Commit될 수 있다.

8. DB Deadlock도 즉시 request FAILED로 저장한다.

9. coupon_issue UNIQUE 위반 후 같은 트랜잭션에서
   request를 FAILED로 변경하려고 한다.

10. UNIQUE 위반 트랜잭션이 Rollback된 뒤에도
    WHERE status = 'PROCESSING'으로 FAILED 변경을 시도한다.

11. 상태 조회 API는 requestId만 알면 누구나 조회할 수 있다.

12. Idempotency-Key 재사용 가능 기간보다 먼저
    coupon_issue_request 행을 삭제한다.
```

### **1. 문제점과 개선 방향 작성하기**

최소 10개 이상 작성한다.

```
| **문제점** | **왜 문제인가?** | **개선 방향** |
| --- | --- | --- |
| API Server가 요청을 받을 때마다 새로운 requestId를 생성한다 | 응답이 유실된 뒤 클라이언트가 재시도하면 서버가 또 다른 requestId를 부여하므로 서로 다른 요청으로 인식된다. | 클라이언트가 요청 전에 UUID를 생성해 Idempotency-Key 헤더로 전달하고, 재시도 시 동일한 값을 재사용한다. 서버는 이 값을 requestId로 사용하며 형식과 길이를 앞단에서 검증한다. |
| 같은 requestId가 들어오면 요청 내용을 확인하지 않고 기존 결과를 무조건 반환한다 | 같은 키가 다른 eventId나 다른 userId 요청에 재사용되어도 탐지할 수 없다. | Canonical String(COUPON_ISSUE\|eventId\|authenticatedUserId)을 SHA-256으로 해시한 request_hash를 저장하고 비교한다. 해시가 같으면 재시도로 보아 기존 상태를 반환하고, 다르면 409 Conflict / IDEMPOTENCY_KEY_REUSED로 거절하며 Kafka에 발행하지 않는다. |
| 요청 상태를 coupon_issue에 성공 기록만 저장한다 | coupon_issue에는 발급에 성공한 행만 존재하므로 대기 중, 처리 중, 실패 상태를 표현할 수 없다. 사용자가 상태를 조회해도 아직 처리 중인지 실패한 것인지 구분할 수 없고, 실패 원인도 알려줄 수 없다. 중복 메시지가 왔을 때 어떤 결과를 반환해야 하는지 판단할 근거도 없다. | 별도의 coupon_issue_request 테이블을 두고 PENDING / PROCESSING / ISSUED / FAILED 상태와 failure_code를 저장한다. coupon_issue는 발급 성공 기록만 담당하고, 요청의 생명주기는 요청 상태 테이블이 담당한다. |
| Consumer가 SELECT로 PENDING을 확인한 뒤 조건 없이 PROCESSING으로 UPDATE한다 | 확인과 변경 사이에 다른 Consumer가 끼어드는 Check-Then-Act 경쟁이 발생한다. | 상태 확인과 변경을 하나의 SQL로 원자적으로 처리한다. WHERE request_id = :requestId AND status = 'PENDING' 조건부 UPDATE를 사용하고, affected rows가 1인 처리자만 발급 로직을 진행한다. |
| 최종 상태 변경 SQL에 이전 상태 조건이 없다 | 요청의 현재 상태와 무관하게 덮어쓰므로 ISSUED → FAILED, FAILED → ISSUED 같은 금지 전이가 실제로 발생한다. | 모든 상태 변경 SQL에 출발 상태를 조건으로 포함하고 affected rows를 확인한다. ISSUED와 FAILED는 최종 상태이므로 어떤 상태로도 전이하지 않는다. |
| request가 ISSUED이면 DuplicateMessageException을 던진다 | 재시도해도 결과가 바뀌지 않는 최종 상태인데 재시도 흐름을 타게 된다. | 최종 상태를 확인하고 아무 변경 없이 종료한 뒤 Offset을 Commit한다. |
| Kafka Offset이 DB 처리 전에 자동 Commit될 수 있다 | DB 처리가 실패해도 Kafka는 해당 메시지를 소비 완료로 기록하므로 재전달되지 않는다. | 자동 커밋을 끄고 수동 Acknowledgment로 전환해 DB 트랜잭션 Commit 이후에만 Offset을 Commit한다. |
| DB Deadlock도 즉시 request FAILED로 저장한다 | Deadlock은 재처리하면 성공할 수 있는 일시적 시스템 오류인데 최종 실패로 확정된다. | 일시적 오류는 FAILED로 저장하지 않고 Rollback한 뒤 Listener에서 예외를 재전파해 Kafka 재전달로 넘긴다. |
| coupon_issue UNIQUE 위반 후 같은 트랜잭션에서 request를 FAILED로 변경하려고 한다 | PostgreSQL에서는 제약 위반이 발생한 트랜잭션이 Abort 상태가 되어 이후 어떤 SQL도 실행되지 않는다. 실행되더라도 그 변경 역시 Rollback 대상이므로 FAILED가 저장되지 않는다. | 현재 트랜잭션을 Rollback하고 새 트랜잭션을 시작한다. |
| UNIQUE 위반 트랜잭션이 Rollback된 뒤에도 WHERE status = 'PROCESSING'으로 FAILED 변경을 시도한다 | Rollback으로 PENDING → PROCESSING 전이가 취소되어 DB에 실제로 남아 있는 값은 PENDING이다. | 출발 상태를 PENDING으로 지정한다. |
| 상태 조회 API는 requestId만 알면 누구나 조회할 수 있다 | requestId를 아는 것만으로 다른 사용자의 발급 여부, couponIssueId, 실패 사유가 노출된다. | 조회 조건에 인증 토큰에서 추출한 userId를 반드시 포함한다. |
| Idempotency-Key 재사용 가능 기간보다 먼저 coupon_issue_request 행을 삭제한다 | 클라이언트가 아직 재사용할 수 있는 키인데 서버에는 요청 행이 없는 구간이 생긴다. 재시도가 신규 요청으로 접수되어 새 PENDING 행이 생성되고 Kafka 메시지가 발행되므로 같은 논리적 요청의 결과가 두 번 반영될 수 있다. | Idempotency-Key 유효 기간 <= 요청 상태 보관 기간이 되도록 정책을 정한다. |
```

### **4. 중복 메시지를 정상적으로 종료시키는 처리 흐름 작성하기**

```
공통 원칙

최종 상태가 확정된 요청의 중복 메시지는 예외를 던지지 않는다.
새 발급 로직을 실행하지 않고 아무 변경 없이 종료한 뒤 Offset을 Commit한다.
최종 상태를 확인하고 아무것도 변경하지 않는 것도 성공적인 처리다.

ISSUED:

Consumer는 메시지를 받으면 requestId로 요청 행을 조회해
메시지와 eventId, userId가 일치하는지 검증한 뒤
PENDING -> PROCESSING 조건부 UPDATE를 시도한다.
현재 상태가 ISSUED이므로 조건을 만족하지 않아 affected rows는 0이 된다.

0행을 즉시 실패로 처리하지 않고 기존 상태를 재조회해 ISSUED임을 확인한다.
이 요청은 issued_count 증가, coupon_issue 저장,
요청 상태 변경과 coupon_issue_id 연결이 모두 커밋된 상태이므로
이 메시지가 요구하는 결과가 이미 DB에 존재한다.

따라서 새 발급 로직을 실행하지 않고 상태도 변경하지 않는다.

이후 정상 처리로 종료하고 Kafka Offset을 Commit한다.

FAILED:

처리 흐름은 ISSUED와 동일하다.
조건부 UPDATE가 0행을 반환하고, 기존 상태를 재조회해 FAILED임을 확인한다.

FAILED는 재시도해도 결과가 바뀌지 않는 최종 실패 상태이며
failure_code에 SOLD_OUT이나 DUPLICATE_USER 등 원인이 기록되어 있다.
같은 메시지를 다시 처리해도 동일한 실패가 반복되므로
발급을 시도할 이유가 없다.

기존 실패 결과를 그대로 유지하고 FAILED를 ISSUED로 덮어쓰지 않는다.
상태 변경 SQL에 출발 상태 조건이 포함되어 있으므로
오래된 처리자가 확정된 결과를 변경할 수도 없다.

아무 변경 없이 정상 처리로 종료하고 Kafka Offset을 Commit한다.
```

### **5. 이번 5주차 설계에서 최종적으로 지켜야 하는 불변식 정리하기**

최소 6개 작성한다.

```
1. 하나의 논리적 요청은 requestId로 식별되며, 요청당 coupon_issue_request 행은 정확히 하나만 존재한다.  
   - request_id를 Primary Key로 두고 INSERT ... ON CONFLICT DO NOTHING으로 수행한다.  
   - 동일 requestId가 동시에 들어와도 한 행만 등록된다.  
   - 사전 SELECT로 존재 여부를 확인하지 않는다.  

2. 같은 requestId에는 항상 같은 request_hash가 대응한다.  
   - requestId와 request_hash가 같으면 같은 요청의 재시도이므로 기존 상태를 반환한다.  
   - request_hash가 다르면 잘못된 Idempotency-Key 재사용이므로 409 Conflict로 거절한다.  
   - 해시가 다른 요청은 Redis 판정이나 Kafka 발행으로 진행시키지 않는다.  

3. 하나의 requestId에 대해 실제 발급 로직은 한 번만 실행된다.  
   - PENDING -> PROCESSING 조건부 UPDATE에서 1행을 얻은 처리자만 발급을 수행한다.  
   - 0행을 받은 처리자는 기존 상태를 확인하고 아무것도 변경하지 않는다.  
   - 상태 확인과 변경은 반드시 하나의 SQL로 원자적으로 수행한다.  

4. issued_count 증가, coupon_issue 저장, coupon_issue_request 최종 상태 변경은 함께 성공하거나 함께 실패한다.  
   - 세 작업은 하나의 트랜잭션에 속하며 부분 성공을 허용하지 않는다.  
   - 어느 하나라도 기대한 영향 행 수와 다르면 전체를 Rollback한다.  
   - 외부 API 호출과 알림 발송은 이 트랜잭션에 포함하지 않는다.  

5. ISSUED와 FAILED는 최종 상태이며 다른 상태로 전이하지 않는다.  
   - 모든 상태 변경 SQL은 출발 상태를 WHERE 조건에 포함하고 영향받은 행 수를 확인한다.  
   - 확정된 결과를 오래된 처리자나 중복 메시지가 덮어쓸 수 없다.  
   - 출발 상태는 논리적 기대값이 아니라 Rollback 이후 DB에 실제로 남아 있는 값에 맞춘다.  

6. 한 사용자는 한 이벤트에서 최대 한 장의 쿠폰만 발급받는다.  
   - coupon_issue의 UNIQUE(event_id, user_id)가 최종 방어선이다.  
   - Redis 기록이 유실되어 다른 requestId가 통과하더라도 중복 발급 행은 저장되지 않는다.  
   - 요청 상태 테이블에는 이 제약을 두지 않아 실패한 요청의 이력도 함께 보관한다.  

7. 발급 수량은 total_quantity를 초과하지 않는다.  
   - issued_count < total_quantity 조건부 UPDATE로만 수량을 확보한다.  
   - 0행이면 DB 기준 SOLD_OUT으로 확정한다.  
   - Redis 카운터는 앞단 필터일 뿐 최종 수량의 근거가 아니다.  

8. 일시적 시스템 오류는 FAILED로 확정하지 않는다.  
   - DB 연결 실패, Deadlock, Timeout, Connection Pool 부족은 재처리하면 성공할 수 있다.  
   - Rollback 후 예외를 재전파해 Kafka 재전달로 넘긴다.  
   - 최종 상태로 확정해야 하는 것은 SOLD_OUT, DUPLICATE_USER, REQUEST_MISMATCH처럼 재시도해도 결과가 바뀌지 않는 실패뿐이다.  

9. Kafka Offset은 DB 결과가 확정된 뒤에만 Commit한다.  
   - Offset을 먼저 Commit하면 재전달 기회가 사라져 요청이 유실된다.  
   - 유실은 복구할 수 없다.  
   - 중복 전달은 멱등 처리로 흡수할 수 있으므로 두 실패 모드 중 중복 쪽을 허용한다.  

10. 요청 상태 보관 기간은 Idempotency-Key 유효 기간보다 짧지 않다.  
    - Idempotency-Key 유효 기간 ≤ 요청 상태 보관 기간  
    - 보관 기간이 더 짧으면 아직 재사용 가능한 키의 요청 행이 사라져 재시도를 신규 요청으로 오인하고 결과가 두 번 반영될 수 있다.  

11. 상태 조회는 인증된 사용자 본인의 요청에 대해서만 허용한다.  
    - 조회 조건에 반드시 인증된 userId를 포함한다.  
    - requestId는 요청을 식별하는 값이지 접근 권한을 증명하는 값이 아니다.
```
