# 13기_배선아 5주차 과제

# **requestId 기반 멱등성과 중복 처리 구조 설계**

## **1. 과제 목표**

이번 5주차 과제의 목표는 **같은 API 요청이나 Kafka 메시지가 여러 번 전달되더라도 최종 쿠폰 발급 결과가 한 번만 반영되도록 멱등 처리 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

4주차에서는 DB의 조건부 `UPDATE`, `UNIQUE(event_id, user_id)`, Transaction을 이용해 최종 수량과 사용자 중복 발급을 방어했다.

이번 5주차에서는 다음 문제를 추가로 해결한다.

```
같은 논리적인 요청이 여러 번 전달되었는가?

같은 사용자가 새로운 요청을 다시 보낸 것인가?

Consumer가 이미 성공한 메시지를 다시 읽은 것인가?

요청이 아직 처리 중인가?

이전에 성공하거나 실패했다면 어떤 결과를 다시 반환해야 하는가?
```

기본 흐름은 다음과 같다.

```
Client
  |
  | Idempotency-Key: requestId
  v
API Server
  |
  | 인증된 userId 확인
  | requestHash 생성
  v
Redis
  |
  | 사용자 + requestId 기준 판정
  v
coupon_issue_request
  |
  | PENDING 요청 상태 저장
  v
Kafka
  |
  | requestId가 포함된 메시지 전달
  v
Coupon Issue Consumer
  |
  | requestId 기준 처리 권한 획득
  v
DB Transaction
  |
  | 수량 증가
  | 발급 기록 저장
  | 요청 상태 확정
  v
Kafka Offset Commit
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Idempotency-Key와 requestId의 역할

같은 요청과 같은 사용자의 차이

Kafka Producer 멱등성과 비즈니스 멱등성의 차이

requestId와 Kafka Partition + Offset의 차이

requestHash를 이용한 잘못된 키 재사용 방지

coupon_issue_request 요청 상태 테이블 설계

PENDING / PROCESSING / ISSUED / FAILED 상태 전이

동일 requestId 동시 요청의 최초 등록자 결정

Consumer의 조건부 상태 전이와 처리 권한 획득

발급 수량, 발급 기록, 요청 상태를 묶는 DB Transaction

UNIQUE 위반 Rollback 이후 상태 확정

DB Commit과 Kafka Offset Commit의 순서

중복 메시지를 예외가 아니라 멱등 성공으로 처리하는 방법

Redis, DB, Kafka 사이의 일시적 불일치와 복구 방향
```

이번 과제의 핵심은 다음과 같다.

```
중복 전달을 완전히 없애는 것이 목표가 아니다.

같은 요청이 여러 번 전달되더라도
최종 비즈니스 결과가 한 번만 반영되게 만드는 것이 목표다.
```

## **2. 기본 상황**

서비스에서 다음 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 ID: 100

이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트

전체 쿠폰 수량: 1,000개

발급 조건:
사용자 1명당 해당 이벤트 쿠폰 1개만 발급 가능

DBMS: PostgreSQL

DB 격리 수준: READ COMMITTED

최종 발급 성공 기준:
coupon_event.issued_count 증가,
coupon_issue 저장,
coupon_issue_request ISSUED 변경이
하나의 트랜잭션으로 Commit된 시점
```

사용자 `userId = 10`이 다음 요청을 보낸다.

```
POST /api/coupon-events/100/issue
Authorization: Bearer ...
Idempotency-Key: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31
```

서버 내부에서는 `Idempotency-Key`를 `requestId`로 사용한다.

```json
{
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "eventId": 100,
  "userId": 10,
  "requestedAt": "2026-07-24T12:00:00+09:00"
}
```

하지만 실제 시스템에서는 다음 상황이 발생할 수 있다.

```
상황 1.
서버는 요청을 처리했지만 응답만 유실되어
Client가 같은 requestId로 재시도한다.

상황 2.
사용자가 버튼을 여러 번 눌러
서로 다른 requestId로 같은 쿠폰을 다시 요청한다.

상황 3.
애플리케이션 코드가 같은 메시지를 send()로 두 번 발행한다.

상황 4.
Consumer가 DB Commit 후 Offset Commit 전에 종료되어
같은 Kafka Record를 다시 읽는다.

상황 5.
원본 Topic의 메시지가 Retry Topic으로 이동하여
Partition과 Offset은 달라졌지만 같은 requestId가 다시 전달된다.

상황 6.
같은 requestId가 다른 eventId 또는 다른 userId 요청에 재사용된다.
```

이 모든 상황을 단순히 `UNIQUE(event_id, user_id)` 하나로만 처리할 수는 없다.

```
UNIQUE(event_id, user_id)
→ 같은 사용자의 최종 중복 발급을 막는다.

requestId
→ 같은 논리적인 요청의 재처리를 식별한다.

requestHash
→ 같은 requestId가 다른 요청에 재사용되는 것을 막는다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
Client는 쿠폰 발급 요청을 보내기 전에 UUID 형식의 requestId를 생성한다.

같은 논리적인 요청을 재시도할 때는
최초 요청과 동일한 requestId를 재사용한다.

새로운 논리적인 작업에는 새로운 requestId를 사용한다.

userId는 Request Body가 아니라
인증된 사용자 정보에서 가져온다.

requestHash는 다음 Canonical String을 기준으로 생성한다.

COUPON_ISSUE|eventId|authenticatedUserId

Hash 알고리즘은 SHA-256을 사용한다.
```

이번 과제에서는 3주차의 Redis 구조를 다음처럼 확장한다고 가정한다.

```
Redis 판정 기준

- eventId + userId
- 해당 사용자의 최초 requestId
```

Redis Lua Script의 반환값은 다음 네 가지로 사용한다.

| **반환값** | **의미** |
| --- | --- |
| `SUCCESS` | 새로운 사용자가 새로운 requestId로 선착순 판정을 통과함 |
| `IDEMPOTENT_RETRY` | 같은 사용자와 같은 requestId가 다시 들어옴 |
| `DUPLICATE_USER` | 같은 사용자가 다른 requestId로 다시 요청함 |
| `SOLD_OUT` | Redis 기준 제한 수량에 도달함 |

이번 과제에서는 Redis를 통과한 요청만 DB 요청 상태 테이블에 저장하는 방식을 기본으로 사용한다.

```
Redis SUCCESS
→ coupon_issue_request PENDING 저장
→ Kafka 발행

Redis DUPLICATE_USER / SOLD_OUT
→ coupon_issue_request를 만들지 않음
→ Kafka에 발행하지 않음
```

요청 상태는 다음 네 가지로 단순화한다.

```
PENDING
PROCESSING
ISSUED
FAILED
```

최종 실패 코드는 다음 예시를 사용할 수 있다.

```
SOLD_OUT
DUPLICATE_USER
INVALID_EVENT
REQUEST_MISMATCH
```

다음 오류는 최종 비즈니스 실패가 아니라 일시적 시스템 오류로 본다.

```
DB 연결 일시 실패
Deadlock
네트워크 Timeout
Connection Pool 일시 부족
Consumer 프로세스 장애
```

일시적 시스템 오류가 발생하면 요청 상태를 `FAILED`로 확정하지 않고 트랜잭션을 Rollback한 뒤 Kafka 재전달을 통해 다시 처리한다.

이번 주차의 기본 Consumer 처리는 짧은 DB 작업이므로 다음 범위를 하나의 트랜잭션으로 묶는다.

```
PENDING → PROCESSING 처리 권한 획득
coupon_event.issued_count 증가
coupon_issue INSERT
coupon_issue_request ISSUED 또는 FAILED 변경
```

이번 주차에서는 아래 내용을 상세 구현하지 않는다.

```
Outbox Publisher 상세 구현

Retry Topic과 DLQ 상세 정책

쿠폰 발급 취소와 재발급

외부 결제나 외부 API 호출이 포함된 장시간 작업

Redis와 RDB를 하나의 분산 트랜잭션으로 묶는 방법
```

다만 Redis, DB, Kafka 사이에서 어떤 불일치가 발생할 수 있는지와 복구 방향은 설명해야 한다.

## **과제 1. requestId 기반 전체 멱등 처리 구조 그리기**

Client의 최초 요청부터 Kafka Offset Commit까지의 전체 흐름을 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

Idempotency-Key

API Server

Redis Lua Script

coupon_issue_request

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

coupon_event

coupon_issue

Kafka Offset Commit
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | POST /api/coupon-events/100/issue
  | Idempotency-Key: req-001
  v
API Server
  |
  | 1) 인증된 userId 확인 (Token → userId)
  | 2) requestId 형식 검증 (UUID)
  | 3) requestHash 생성 (SHA-256(COUPON_ISSUE|100|10))
  v
Redis Lua Script
  |
  | eventId + userId + requestId 기준 원자적 판정
  |
  +---> SOLD_OUT         → 품절 응답 반환 (DB 등록 없음)
  +---> DUPLICATE_USER   → 중복 사용자 응답 반환 (DB 등록 없음)
  +---> IDEMPOTENT_RETRY → DB에서 기존 요청 상태 조회 후 반환
  +---> SUCCESS
           |
           v
       coupon_issue_request INSERT (status = PENDING)
           |
           | Kafka 발행 성공 여부 확인
           +---> 발행 실패 → 발행 재시도 또는 실패 응답
           |
           v
       Kafka Producer
           |
           | publish (key = requestId)
           v
       coupon.issue.requested Topic
           |
           | consume
           v
       Coupon Issue Consumer
           |
           | 1) 메시지와 요청 행 일치 검증
           |    (requestId, eventId, userId 비교)
           |
           | 2) 기존 상태 확인
           |    ISSUED / FAILED → 멱등 성공 종료 → Offset Commit
           |
           | 3) 조건부 UPDATE로 처리 권한 획득
           |    PENDING → PROCESSING
           |
           v
       DB Transaction
           |
           | 1) PENDING → PROCESSING 처리 권한 획득
           |    (affected rows = 0 → 기존 상태 확인 후 종료)
           |
           | 2) coupon_event 조건부 UPDATE
           |    issued_count < total_quantity → +1
           |    (0행 → SOLD_OUT → request FAILED → Commit)
           |
           | 3) coupon_issue INSERT
           |    UNIQUE(event_id, user_id)
           |    (UNIQUE 위반 → Rollback → 별도 트랜잭션에서 FAILED 확정)
           |
           | 4) coupon_issue_request ISSUED 변경
           |    (0행 → 전체 Rollback)
           |
           v
       Commit
           |
           v
       Kafka Offset Commit
```

### **2. 하나의 requestId가 전체 흐름에서 어떻게 전달되는지 작성하기**

아래 흐름을 완성한다.

```
HTTP Idempotency-Key
        |
        v
애플리케이션 requestId
        |
        v
coupon_issue_request.request_id
        |
        v
Kafka Message requestId (key = requestId)
        |
        v
Consumer 멱등 처리
```

### **3. 각 구성 요소의 역할**

```
| **구성 요소** | **역할** |
| --- | --- |
| Redis | eventId + userId + requestId 기준 원자적 판정, 수량 초과와 사용자 중복을 ㅈ앞단에서 차단 |
| Kafka | 발급 요청 메시지를 비동기로 전달하는 메시지 브로커, 순간 트래픽 완충 |
| coupon_issue_request | 요청의 생명주기와 처리 결과를 저잘, 멱등 판단의 기준 데이터 |
| coupon_event | 전체 수량(total_quantity)과 DB 기준 발급 수량(issued_count) 저장 |
| coupon_issue | 최종 발급에 성공한 사용자별 기록 저장, UNIQUE(event_id, user_id)로 중복 방어 |
| Kafka Offset | Consumer가 어디까지 메시지를 처리했는지 Kafka에 기록, DB 결과 확정 후 커밋 |
```

### **4. 각 단계의 성공이 의미하는 것**

| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis `SUCCESS` | 새로운 사용자가 선착순 판정을 통과 | X |
| request `PENDING` | 요청이 DB에 등록되어 처리 대기 중 | X |
| request `PROCESSING` | Consumer가 처리 권한을 획득해 발급 처리 중 | X |
| request `ISSUED` | 수량 증가·발급 기록·상태 변경이 트랜잭션으로 커밋 | O |
| request `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 실패 상태 | X |
| Kafka Offset Commit | Kafka 관점에서 메시지 처리 완료로 기록 | X |

### **5. 최종 쿠폰 발급 성공으로 판단할 수 있는 시점**

```
coupon_event.issued_count 증가, coupon_issue 저장, coupon_issue_request ISSUED 변경이 하나의 DB 트랜잭션으로 Commi된 시점이다.
coupon_issue_request.status = 'ISSUED'이고 coupon_issue_id가 연결되어 있는 것이 최종 발급 성공의 기준이다.
```

### **6. 요청이 여러 번 도착해도 최종 결과가 한 번만 반영되어야 한다는 의미**

```
물리적으로 메시지나 API 요청이 여러 번 도달하는 것은 허용한다.
다만 coupon_event.issued_count 증가, coupon_issue INSERT, coupon_issue_request ISSUED 변경은 단 한 번만 실제로 반영된다.

같은 requestID가 다시 들어오면 새 발급 로직을 실행하지 않고 이미 저장된 상태와 결과를 그대로 반환한다.

이것이 멱등성의 의미로, 전달 횟수를 통제하는 것이 아니라 DB 결과의 중복 반영을 막는 것이 핵심이다.
```

## **과제 2. 중복 유형과 멱등성 경계 구분하기**

같아 보이는 중복도 원인과 방어 장치가 다르다.

아래 상황을 읽고 각각 어떤 중복인지 구분한다.

### **1. 상황별 중복 유형 분석**

| **상황** | **같은 논리적 요청인가?** | **식별 기준** | **주요 방어 장치** |
| --- | --- | --- | --- |
| 응답 유실 후 같은 requestId로 API 재시도 | O, 같음 | requestId | coupon_issue_request 상태 확인 |
| 반복 클릭으로 다른 requestId가 생성됨 | X, 다름 | eventId + userId | Redis DUPLICATE_USER, DB UNIQUE |
| 애플리케이션이 같은 requestId 메시지를 `send()` 두 번 호출 | O, 같음 | requestId | Consumer requestId 멱등 처리 |
| DB Commit 후 Offset Commit 전 장애로 같은 Record 재전달 | O, 같음 | requestId | ISSUED 상태 확인 후 멱등 성공 종료 |
| 원본 Topic과 Retry Topic에 같은 requestId가 존재 | O, 같음 | requestId | Consumer requestId 멱등 처리 |
| 같은 requestId가 다른 eventId에 재사용됨 | X, 다른 요청 재사용 | requestId + requestHash | requestHash 불일치 -> 409 Conflict |


### **2. 같은 요청과 같은 사용자의 차이**

아래 두 상황의 차이를 설명한다.

```
상황 A
requestId = req-001
이 요청이 여러 번 전달됨

상황 B
requestId = req-A, req-B, req-C
모두 eventId = 100, userId = 10
```

답변:

```
상황 A는 req-001이라는 동일한 논리적 요청이 네트워크 문제나 Kafka 재전달 등으로 여러 번 도착한 경우다.
서버는 기존 coupon_issue_request의 상태와 결과를 반환하면 되고 새로운 발급 로직을 실행하지 않는다.

상황 B는 같은 사용자(userId=10)가 eventId=100에 대해 새로운 requestId 기준에서는 세 요청이 모두 다른 신규 요청으로 보인다.
이 중복은 Redis의 eventId+userId 판정과 DB의 UNIQUE(event_id, user_id)가 막는다.

정리하면, 
같은 요청(같은 requestId)의 재전달 -> requestId 기반 멱등 처리로 방어
같은 사용자(다른 requestId)의 중복 발급 시도 -> Redis + DB UNIQUE로 방어
```

### **3. 중복 방어 장치별 역할 비교**

| **장치** | **식별 기준** | **막는 문제** | **막지 못하는 문제** |
| --- | --- | --- | --- |
| Redis 사용자 판정 | eventId + userId | 동일 사용자 반복 요청, 수량 초과 앞단 차단 | Redis 데이터 유실 시 중복 통과 |
| requestId | requestId | 동일 논리적 요청의 재처리 | 다른 requestId로 온 같은 사용자의 중복 발급 |
| requestHash | requestId + 요청 의미 | 같은 키를 다른 요청에 재사용하는 오류 | requestId 자체가 다른 경우 |
| `UNIQUE(event_id, user_id)` | eventId + userId | 최종 사용자 중복 발급 | 동일 requestId 재처리 시 상태 판단 |
| Kafka Partition + Offset | Partition 내 위치 | Consumer가 읽은 위치 기록 | 비즈니스 중복 (같은 requestId 다른 Offset) |


### **4. Kafka Producer 멱등성이 막는 중복**

다음 흐름을 기준으로 설명한다.

```
애플리케이션이 send() 한 번 호출
→ Broker 저장 성공
→ ACK 유실
→ Producer 내부 재시도
```

```
애플리케이션이 send()를 한 번 호출했을 때, Broker 저장 성공 후 ACK가 유실되면 Kafka Producer가 내부적으로 같은 Sequence Number로 재전송한다.
Broker는 이미 저장한 Sequence Number임을 확인하고 중복 Record를 다시 저장하지 않는다.

즉 하나의 send() 호출 -> Producer 내부 재전송 -> 브로커 중복 저장 방지가 Kafka Producer 멱등성이 막는 범위다.
```

### **5. 애플리케이션이 send()를 두 번 호출하면 Producer 멱등성으로 막을 수 없는 이유**

```java
kafkaTemplate.send(topic, message);
kafkaTemplate.send(topic, message);
```

```
두 번의 send() 호출은 Kafka Producer 입장에서 서로 다른 두 개의 전송 요청이다.
각 호출에는 새로운 Sequence Number가 부여된다.

첫 번째 send() -> Sequence Number = 25 -> 저장
두 번째 send() -> Sequence Number = 26 -> 저장

Broker는 두 번째 호출을 첫 번째의 재시도가 아니라 정상적인 새 Record로 판단하므로 둘 다 저장된다.
Producer 멱등성은 하나의 send()의 내부 재시도만 막을 수 있다.
```

### **6. requestId와 Kafka Partition + Offset의 차이**

```
requestId:
어떤 쿠폰 발급 요청인지는 나타내는 비즈니스 식별자다.
같은 requestId는 동일한 논리적 요청을 의미한다. Retry Topic 이동 등으로 Partition과 Offset이 바뀌어도 requestId는 유지된다.

Partition + Offset:
Kafka 안에서 특정 Record가 어느 위치에 저장되어 있는지를 나타내는 물리적 위치다. 같은 requestId라도 재발행되면 다른 Partition, 다른 Offset에 저장될 수 있다.
```

### **7. Consumer 멱등성의 기준을 Offset이 아니라 requestId로 두어야 하는 이유**

아래 상황을 포함해서 설명한다.

```
원본 Topic
Partition 0 / Offset 100 / req-001

Retry Topic
Partition 2 / Offset 35 / req-001
```

```
두 Record는 Partition과 Offset이 다르지만 같은 비즈니스 요청인 req-001을 나타낸다.

Offset 기준으로 멱등성을 판단하면 원본과 Retry Topic의 Record를 서로 다른 요청으로 보아 두 번 발급 로직을 실행한다.

requestId 기준으로 판단하면 두 Record 모두 req-001로 식별되어 이미 ISSUED 또는 FAILED 상태인 경우 새 발급 없이 종료한다.

물리적 위치가 달라도 같은 논리적 요청이므로 멱등성의 기준은 반드시 requestId여야 한다.
```

## **과제 3. Idempotency-Key와 requestHash 설계하기**

HTTP API에서 동일한 논리적 요청의 재시도를 식별할 수 있도록 `Idempotency-Key`와 `requestHash`를 설계한다.

### **1. Idempotency-Key의 의미**

```
클라이언트가 동일한 요청의 재시도임을 서버에 알려주기 위해 HTTP 헤더로 전달하는 고유한 식별자다.

네트워크 오류로 응답을 받이 못해 같은 요청을 다시 보내더라도 동일한 Idempotency-Key를 사용하면 서버는 새로운 요청이 아니라 기존 요청의 재시도로 판단할 수 있다.

서버 내부에서는 이 값을 requestId로 사용한다.
```

### **2. 누가 requestId를 생성해야 하는가?**

다음 두 방식을 비교하고 이번 구조에 더 적합한 방식을 선택한다.

```
방식 A
Client가 요청 전 requestId 생성

방식 B
API Server가 요청을 받은 뒤 requestId 생성
```

| **방식** | **장점** | **단점** |
| --- | --- | --- |
| Client 생성 | 재시도 시 동일 requestId 재사용 | Client 구현 의존, 잘못된 형식 생성 가능 |
| API Server 생성 | 형식 보장 가능, Client 구현 단순 | 응답 유실 시 Client가 기존 requestId를 알 수 없음 |

내가 선택한 방식:

```
Client 생성
```

선택한 이유:

```
응답이 유실된 경우 Client가 동일한 requestId로 재시도해야 서버가 같은 요청의 재시도임을 인식할 수 있다.

API Server가 생성하면 응답 유실 시 Client가 기존 requestId를 알 수 없어 재시도할 때마다 새로운 requestId가 생성되어 멱등 처리가 불가능해진다.
```

### **3. 같은 requestId를 재사용해야 하는 상황과 새로 생성해야 하는 상황**

| **상황** | **같은 requestId 재사용 또는 새 requestId 생성** | **이유** |
| --- | --- | --- |
| 네트워크 Timeout 후 동일 작업 재시도 | 같은 requestId 재사용 | 같은 논리적 작업의 재시도이므로 서버가 동일 요청으로 인식해야 함 |
| 응답 유실 후 동일 작업 재시도 | 같은 requestId 재사용 | 서버가 이미 처리했을 수 있으므로 기존 결과를 확인해야 함 |
| 모바일 앱 재연결 후 동일 작업 전송 | 같은 requestId 재사용 |연결이 끊겼을 뿐 같은 작업이므로 재사용해야 함  |
| 다른 쿠폰 이벤트 발급 요청 | 새 requestId 생성 | 다른 이벤트이므로 완전히 다른 논리적 작업 |
| 기존 요청을 취소하고 새로운 작업 시작 | 새 requestId 생성 | 이전 요청과 의미가 다른 새 작업 |


### **4. requestId의 형식과 검증 규칙 설계하기**

아래 항목을 포함한다.

```
허용 형식

최대 길이

빈 값 처리

허용하지 않는 문자

DB 유일성 보장 방식
```

답변:

```
허용 형식: UUID v4 (예: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31)

최대 길이: 36자 (UUID 형식 기준, 하이픈 포함)

빈 값 처리: Idempotency-Key 헤더가 없거나 빈 값이면 400 Bad Request 반환

허용하지 않는 문자: UUID 형식(16진수 + 하이픈)에 맞지 않는 문자는 모두 거절

DB 유일성 보장 방식: coupon_issue_request.request_id를 UUID PRIMARY KEY로 설정  
                DB 레벨에서 Primary Key 제약으로 최종 유일성을 보장한다
```

### **5. requestHash를 만드는 Canonical String 작성하기**

이번 과제의 기준은 다음과 같다.

```
작업 종류: COUPON_ISSUE
이벤트 ID: 100
인증된 사용자 ID: 10
```

Canonical String:

```
 COUPON_ISSUE|100|10
```

SHA-256 결과를 저장할 컬럼:

```
request_hash CHAR(64) NOT NULL
(SHA-256은 256비트 = 64인자 16진수 문자열)
```

### **6. 전체 JSON 문자열을 그대로 Hash하면 안 되는 이유**

아래 두 JSON을 기준으로 설명한다.

```json
{ "eventId": 100, "userId": 10 }
```

```json
{"userId":10,"eventId":100}
```

```
두 JSON은 의미상 같은 요청이지만 문자열이 다르기 때문에 SHA-256 해시 결과가 서로 다르다.
필드 순서, 공백, 들여쓰기 등 직렬화 방식에 따라 같은 요청인데도 다른 hash가 생성될 수 있다.
따라서 의미 있는 필드만 정해진 순서로 정규화한 뒤 해시해야 한다.
```

### **7. requestHash에 포함할 값과 포함하지 않을 값 구분하기**

| **값** | **포함 여부** | **이유** |
| --- | --- | --- |
| 작업 종류 `COUPON_ISSUE` | O | 같은 requestId가 다른 종류의 요청에 재사용되는 것을 막기 위해 |
| eventId | O | 어떤 이벤트 쿠폰 발급 요청인지 식별하는 핵심 값 |
| 인증된 userId | O | 누구의 요청인지 식별하는 핵심 값 |
| 요청 전송 시각 | X | 재시도 시 시각이 달라지므로 같은 요청도 다른 hash가 생성됨 |
| Trace ID | X | 매 요청마다 다른 값이 생성되어 일관성이 없음 |
| 매번 바뀌는 nonce | X | 재시도마다 달라지므로 동일 요청 식별 불가 |
| Gateway가 추가한 가변 Header | X | 클라이언트가 제어할 수 없는 값으로 재시도마다 달라질 수 있음 |

### **8. Request Body의 userId를 requestHash에 그대로 사용하면 안 되는 이유**

```
사용자가 Request Body에 다른 사람의 userId를 넣어 요청할 수 있다.

예를 들어 userId=20을 Body에 넣어 다른 사용자 명의로 발급을 시도할 수 있는데, requesHash에 Body의 userId를 사용하면 이 조작이 그대로 반영된다.

반드시 Authorization Token에서 추출한 인증된 userId를 사용해야 한다.
```

### **9. 같은 requestId에 다른 내용이 들어온 경우 처리 설계**

```
기존 요청
requestId = req-001
requestHash = hash(COUPON_ISSUE|100|10)

새 요청
requestId = req-001
requestHash = hash(COUPON_ISSUE|200|10)
```

```
사용자 응답:
{
  "requestId": "req-001",
  "errorCode": "IDEMPOTENCY_KEY_REUSED",

}
```

## **과제 4. coupon_issue_request 테이블과 상태 전이 설계하기**

동일한 요청의 처리 상태와 최종 결과를 저장하기 위한 `coupon_issue_request` 테이블을 설계한다.

### **1. coupon_issue_request와 coupon_issue의 역할 차이**

| **테이블** | **저장하는 대상** | **표현할 수 있는 상태** |
| --- | --- | --- |
| coupon_issue_request | 요청의 생명주기, 처리 상태, 최종 결과 | PENDING, PROCESSING, ISSUED, FAILED |
| coupon_issue | 최종 발급에 성공한 사용자별 기록만 | ISSUED만 (성공 기록만 존재) |

### **2. 요청 상태 모델 설명하기**

| **상태** | **의미** | **최종 상태 여부** |
| --- | --- | --- |
| `PENDING` | 요청 행이 생성되었지만 Consumer의 최종 처리가 끝나지 않은 상태 | X |
| `PROCESSING` | Consumer가 처리 권한을 획득해 발급을 처리 중인 상태 | X |
| `ISSUED` | 수량 변경, 발급 기록, 상태 변경이 함께 Commit된 최종 성공 상태 | O |
| `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 실패 상태 | O |

### **3. 상태 전이 다이어그램 작성하기**

아래 허용 상태 전이와 금지 상태 전이를 구분해서 표현한다.

```
허용 후보
PENDING → PROCESSING
PROCESSING → ISSUED
PROCESSING → FAILED

금지 후보
ISSUED → PROCESSING
ISSUED → FAILED
FAILED → PROCESSING
FAILED → ISSUED
```

```
PENDING
  |
  v
PROCESSING
  |
  +---> ISSUED   (수량 확보 + coupon_issue 저장 + 상태 변경 Commit 성공)
  |
  +---> FAILED   (SOLD_OUT, DUPLICATE_USER, INVALID_EVENT 등 최종 비즈니스 실패)

금지 전이:
ISSUED  → PROCESSING  ❌
ISSUED  → FAILED      ❌
FAILED  → PROCESSING  ❌
FAILED  → ISSUED      ❌
```

### **4. 단일 트랜잭션 구조에서 외부 조회 시 PROCESSING이 거의 보이지 않을 수 있는 이유**

```
PENDING -> PROCESSING -> ISSUED/FAILED 전이를 하나의 트랜잭션 안에서 처리하는 경우, 트랜잭션이 커밋되기 전까지 외부에서는 변경 내용이 보이지 않는다.

따라서 외부 조회자가 볼 수 있는 상태는 트랜잭션 시작전의 PENDING과 트랜잭션 커밋 후의 ISSUED 또는 FAILED뿐이다.
PROCESSING은 트랜잭션 내부의 처리 권한 표시로 사용되므로 외부에서는 거의 보이지 않는다.
```

### **5. coupon_issue_request DDL 작성하기**

아래 컬럼을 포함한다.

```
request_id

event_id

user_id

request_hash

status

failure_code

failure_message

coupon_issue_id

requested_at

processing_started_at

completed_at

created_at

updated_at
```

아래 제약 조건을 포함한다.

```
request_id Primary Key

coupon_event Foreign Key

coupon_issue Foreign Key

coupon_issue_id UNIQUE

status CHECK

FAILED일 때만 failure_code 필수

ISSUED 또는 FAILED일 때 completed_at 필수

ISSUED일 때만 coupon_issue_id 필수

PROCESSING일 때 processing_started_at 필수
```

```sql
CREATE TABLE coupon_issue_request (
    request_id              UUID PRIMARY KEY,

    event_id                BIGINT NOT NULL,
    user_id                 BIGINT NOT NULL,

    request_hash            CHAR(64) NOT NULL,

    status                  VARCHAR(20) NOT NULL,

    failure_code            VARCHAR(50),
    failure_message         VARCHAR(255),

    coupon_issue_id         BIGINT,

    requested_at            TIMESTAMPTZ NOT NULL,
    processing_started_at   TIMESTAMPTZ,
    completed_at            TIMESTAMPTZ,

    created_at              TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_request_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),

    CONSTRAINT fk_coupon_issue_request_issue
        FOREIGN KEY (coupon_issue_id) REFERENCES coupon_issue(id),

    CONSTRAINT uk_coupon_issue_request_issue
        UNIQUE (coupon_issue_id),

    CONSTRAINT chk_coupon_issue_request_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'ISSUED', 'FAILED')),

    CONSTRAINT chk_coupon_issue_request_failure
        CHECK (
            (status = 'FAILED' AND failure_code IS NOT NULL)
            OR
            (status <> 'FAILED'
                AND failure_code IS NULL
                AND failure_message IS NULL)
        ),

    CONSTRAINT chk_coupon_issue_request_completed
        CHECK (
            (status IN ('ISSUED', 'FAILED') AND completed_at IS NOT NULL)
            OR
            (status IN ('PENDING', 'PROCESSING') AND completed_at IS NULL)
        ),

    CONSTRAINT chk_coupon_issue_request_issue_result
        CHECK (
            (status = 'ISSUED' AND coupon_issue_id IS NOT NULL)
            OR
            (status <> 'ISSUED' AND coupon_issue_id IS NULL)
        ),

    CONSTRAINT chk_coupon_issue_request_processing
        CHECK (
            (status = 'PROCESSING' AND processing_started_at IS NOT NULL)
            OR
            (status <> 'PROCESSING')
        )
);
```

### **6. 요청 상태 테이블에 `UNIQUE(event_id, user_id)`를 두지 않는 이유**

아래 이력이 모두 저장되어야 한다는 점을 포함해서 설명한다.

```
req-A → ISSUED
req-B → FAILED / DUPLICATE_USER
```

```
두 이력이 모두 테이블에 남아야 한다.
사용자가 req-B의 실패 이유를 조회할 수 있어야 하기 때문이다. UNIQUE(event_id, user_id)를 두면 req-A가 ISSUED인 상태에서 req-B를 저장할 수 없어 이력이 사라진다.

같은 사용자가 같은 이벤트 쿠폰을 한 번만 받는 규칙은 coupon_issue 테이블의 UNIQUE(event_id, user_id)가 담당한다.
coupon_issue_request는 요청 이력을 모두 보관하는 역할이므로 이 제약을 두면 안 된다.
```

### **7. 상태 변경 SQL에 출발 상태를 조건으로 포함해야 하는 이유**

잘못된 예:

```sql
UPDATE coupon_issue_request
SET status = 'ISSUED'
WHERE request_id = :requestId;
```

올바른 상태 전이 SQL을 직접 작성한다.

```sql
UPDATE coupon_issue_request
SET status              = 'ISSUED',
    coupon_issue_id     = :couponIssueId,
    completed_at        = CURRENT_TIMESTAMP,
    updated_at          = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PROCESSING';
```

### **8. 최종 상태 변경의 영향받은 row 수가 0인 경우**

가능한 원인을 작성한다.

```
1.해당 requset_id가 존재하지 않는다.

2. 현재 상태가 PROCESSING이 아니다.

3. 다른 Consumer가 먼저 같은 행을 최종 상태로 변경한다.
```

### **9. 운영 복구를 위한 인덱스 설계하기**

오래된 `PENDING` 또는 `PROCESSING` 요청을 찾기 위한 인덱스를 작성한다.

```sql
CREATE INDEX idx_coupon_issue_request_status_updated
ON coupon_issue_request (status, updated_at);
```

### **10. 요청 상태 보관 기간과 Idempotency-Key 유효 기간의 관계**

아래 식을 완성하고 이유를 설명한다.

```
Idempotency-Key 유효 기간
≤
요청 상태 보관 기간
```

이유:

```
Idempotency-Key가 유효한 기간 동안은 Client가 같은 Key로 재시도할 수 있다.

만약 요청 상태 행이 Idempotency-Key 유효 기간보다 먼저 삭제되면, 재시도 시 기존 행이 없으므로 서버가 과거 요청을 신규 요청으로 잘못 인식해 중복 처리가 발생한다.
```

## **과제 5. API Server의 멱등 요청 접수 흐름 설계하기**

API Server가 Redis 판정, 요청 상태 등록, Kafka 발행을 어떤 순서로 처리할지 설계한다.

이번 과제에서는 Redis를 통과한 요청만 DB에 저장하는 방식을 기본으로 한다.

### **1. API Server 전체 처리 흐름 다이어그램**

다음 결과를 모두 포함한다.

```
SUCCESS
IDEMPOTENT_RETRY
DUPLICATE_USER
SOLD_OUT
requestId 충돌
Kafka 발행 실패
```

```
Client 요청 수신 (Idempotency-Key: req-001)
  |
  | requestId 형식 검증 (UUID 아니면 400)
  | 인증된 userId 추출
  | requestHash 생성 (SHA-256(COUPON_ISSUE|100|10))
  v
Redis Lua Script 실행
  |
  +---> SOLD_OUT       → 418 or 409 응답 (DB 등록 없음, Kafka 발행 없음)
  +---> DUPLICATE_USER → 409 응답 (DB 등록 없음, Kafka 발행 없음)
  +---> IDEMPOTENT_RETRY
  |       |
  |       v
  |     DB에서 기존 요청 상태 조회
  |       |
  |       +---> PENDING  → 202 (기존 PENDING 상태 반환, Kafka 재발행 없음)
  |       +---> ISSUED   → 200 (기존 성공 결과 반환)
  |       +---> FAILED   → 200 (기존 실패 결과 반환)
  |       +---> 행 없음  → 재조회·복구·보상 정책 실행
  |
  +---> SUCCESS
           |
           v
       coupon_issue_request INSERT (ON CONFLICT DO NOTHING)
           |
           | affected rows = 0
           +---> 기존 행 requestHash 확인
           |       +---> hash 같음  → 기존 상태 반환 (재시도로 처리)
           |       +---> hash 다름  → 409 Conflict (IDEMPOTENCY_KEY_REUSED)
           |
           | affected rows = 1 (최초 등록 성공)
           v
       Kafka 발행 시도
           |
           +---> 발행 실패 → 재시도 후에도 실패 시 실패 응답 (PENDING 상태 유지, 복구 배치 대상)
           |
           v
       202 Accepted 응답 (requestId + PENDING 반환)
```

### **2. Redis 결과별 API 처리**

| **Redis 결과** | **DB 요청 상태 등록** | **Kafka 발행** | **API 응답 방향** |
| --- | --- | --- | --- |
| `SUCCESS` | PENDING 저장 | 발행 | 202 Accepted (requestId + PENDING) |
| `IDEMPOTENT_RETRY` | 등록 안 함 | 발행 안 함 | 기존 DB 상태 조회 후 반환 (200 or 202) |
| `DUPLICATE_USER` | 등록 안 함 | 발행 안 함 |409 Conflict (사용자 중복 발급 거절)  |
| `SOLD_OUT` | 등록 안 함 | 발행 안 함 | 409 Conflict (품절 응답) |

### **3. 동일 requestId 동시 요청에서 SELECT 후 INSERT가 안전하지 않은 이유**

아래 흐름을 시간 순서로 완성한다.

```
시간       API Server A               API Server B
----------------------------------------------------------
T1         req-001 존재 여부 SELECT
T2                                    req-001 존재 여부 SELECT
T3         결과: 없음 → 신규 요청 판단
T4                                    결과: 없음 → 신규 요청 판단
T5         INSERT 시도
T6                                    INSERT 시도 (A가 아직 커밋 전)
T7         INSERT 성공 (최초 등록자)
T8                                    INSERT 성공 → 중복 등록 발생
```

문제의 이름:

```
Check-Then-Act Race Condition
(조회와 삽입 사이에 다른 트랜잭션이 끼어들어 중복 처리가 발생하는 문제)
```

### **4. DB 유일성 제약을 이용한 최초 등록자 결정 SQL 작성하기**

PostgreSQL의 `ON CONFLICT DO NOTHING`을 사용한다.

```sql
INSERT INTO coupon_issue_request (
    request_id,
    event_id,
    user_id,
    request_hash,
    status,
    requested_at
)
VALUES (
    :requestId,
    :eventId,
    :userId,
    :requestHash,
    'PENDING',
    :requestedAt
)
ON CONFLICT (request_id) DO NOTHING;
```

### **5. INSERT 영향받은 row 수 처리**

```
affected rows = 1
→ 내가 최초 등록자다. Kafka 발행을 진행한다.

affected rows = 0
→ 이미 같은 request_id 행이 존재한다.
  기존 행의 request_hash를 조회해 동일 요청인지 다른 요청인지 구분한다.
```

### **6. 기존 행의 requestHash 확인 결과에 따른 처리**

```
| **조건** | **판단** | **처리** |
| --- | --- | --- |
| requestId 같음 + requestHash 같음 | 같은 요청의 재시도 | 기존 상태 조회 후 응답 반혼, Kafka 재발행 없음 |
| requestId 같음 + requestHash 다름 | 잘못된 Key 재사용 | 409 Conflict (IDEMPOTENCY_KEY_REUSED) |
```

### **7. Redis가 `IDEMPOTENT_RETRY`를 반환했지만 DB에 요청 행이 없는 경우**

이 상태가 발생할 수 있는 이유를 설명한다.

```
Redis에는 userId -> requestId 매칭이 저장되어 있어 IDEMPOTENT_RETRY를 반환했지만,

Redis SUCCESS 직후 DB INSERT전에 API Server 장애가 발생한 경우 또는 DB INSERT가 실패한 경우 DB에는 해당 request_id 행이 없는 상태가 될 수 있다.
```

이 상태를 무조건 정상 `PENDING`으로 응답하면 안 되는 이유:

```
DB행이 없다는 것은 요청이 완전히 접수되지 않은 상태일 수 있다.

정상 PENDING으로 응답하면 사용자는 처리 중이라 믿지만 실제로는 Kafka 메시지도 없고 Consumer도 처리하지 않아 요청이 유실된 것과 같은 결과가 된다.
```

재조회·복구·보상 방향:

```
1. 짧은 대기 후 DB 행이 생성되었는지 재조회한다.
2. 일정 시간 이상 행이 없으면 DB 등록을 재시도한다.
3. 재시도도 실패하면 Redis에서 해당 사용자의 자리를 보상(수량 복구, Set에서 제거)한다.
4. 복구 대상 목록과 메트릭을 기록한다.
```

### **8. Redis가 `SUCCESS`를 반환했지만 DB INSERT가 충돌한 경우**

다음 상황을 고려한다.

```
과거 요청 req-001은 DB에 존재한다.
Redis 데이터는 초기화되었다.
Client가 req-001을 다시 전송한다.
Redis는 새로운 요청으로 판단해 SUCCESS를 반환한다.
DB INSERT는 request_id 충돌로 0행이다.
```

아래 항목을 작성한다.

```
기존 requestHash 확인:
기존 행의 request_hash와 현재 요청의 request_hash를 비교한다.
같으면 기존 상태 반환, 다르면 409 Conflict.

Kafka 발행 여부:
hash가 같고 기존 상태가 PENDING이면 Kafka 재발행은 하지 않고, 기존 상태를 그대로 반환한다.

Redis에서 새로 차지한 자리 처리:
Redis 데이터가 초기화된 후 동일 요청이 재시도된 것이므로 Redis에서 새로 차지한 수량 카운트와 사용자 Set 등록을 보상해야 한다.

API 응답:
기존 행의 상태(PENDING/ISSUED/FAILED)를 그대로 반환한다.
```

## **과제 6. Consumer의 조건부 상태 전이와 처리 권한 설계하기**

Kafka 메시지가 중복 전달되더라도 한 Consumer만 실제 발급 로직을 수행하도록 처리 권한 획득 방식을 설계한다.

### **1. Kafka 메시지와 요청 상태 행의 일치 검증**

다음 필드를 비교한다.

| **필드** | **Kafka Message** | **coupon_issue_request** | **불일치 시 처리** |
| --- | --- | --- | --- |
| requestId | requestId = req-001 | request_id = req-001 | 처리 불가 → DLQ 후보  |
| eventId | eventId = 100 | event_id = 100 | 처리 불가 → DLQ 후보  |
| userId | user = 10 | user_id = 10 | 처리 불가 → DLQ 후보  |

메시지 내용 불일치를 재시도 대상으로 두기 어려운 이유:

```
내용 불일지는 손상된 메시지이거나 잘못된 재사용으로 발생한 구조적 문제다.

재시도해도 같은 불일치가 반복되므로 문제가 해결되지 않고, 무한 재시도는 Consumer 자원을 낭비하고 처리를 지연시킨다.

운영자가 확인하고 판단해야 하는 문제이므로 DLQ로 분리하는 것이 적절하다.
```

### **2. SELECT 후 UPDATE 방식의 Race Condition 분석하기**

위험한 흐름은 다음과 같다.

```
1. 상태를 SELECT한다.
2. PENDING인지 애플리케이션에서 확인한다.
3. PROCESSING으로 UPDATE한다.
```

두 Consumer가 동시에 실행되는 시간 순서 다이어그램을 작성한다.

```
시간       Consumer A                  Consumer B
------------------------------------------------------------
T1         status SELECT → PENDING
T2                                     status SELECT → PENDING
T3         PENDING 확인 → 처리 가능 판단
T4                                     PENDING 확인 → 처리 가능 판단
T5         PROCESSING UPDATE 시도
T6                                     PROCESSING UPDATE 시도
T7         UPDATE 성공 → 발급 처리 시작
T8                                     UPDATE 성공 → 발급 처리 시작 (중복 처리 발생)
```

### **3. 조건부 UPDATE로 처리 권한 획득하기**

SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status                  = 'PROCESSING',
    processing_started_at   = CURRENT_TIMESTAMP,
    updated_at              = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PENDING';
```

### **4. 영향받은 row 수의 의미**

```
affected rows = 1
→ PENDING 상태를 PROCESSING으로 변경했다. 처리 권한을 획득했으므로 발급 로직을 진행한다.

affected rows = 0
→ 처리 권한을 얻지 못했다. 현재 요청 상태를 다시 조회해 원인을 파악한다. 요청 행이 없거나, 이미 다른 Consumer가 처리했거나, 최종 상태에 있는 것이다.
```

### **5. 두 Consumer가 동시에 같은 requestId를 처리할 때 DB 내부 동작**

현재 상태는 `PENDING`이다.

```
Consumer A:
WHERE status = 'PENDING' 조건에 해당하는 row에 대한 Row Lock을 획득한다.
issued_count를 PROCESSING으로 변경하고 Commit한다.
affected rows = 1 → 처리 권한 획득.

Consumer B:
Consumer A가 Row Lock을 보유 중이므로 같은 row 업데이트 대기.
A가 Commit하면 Lock 해제.
B는 최신 상태(PROCESSING)로 WHERE status = 'PENDING' 조건 재평가.
조건 불만족 → affected rows = 0.
```

`READ COMMITTED`에서 두 번째 Consumer의 `WHERE status = 'PENDING'` 조건이 어떻게 처리되는지 설명한다.

```
READ COMMITTED 격리 수준에서는 락이 해제된 후 최신 커밋된 값을 읽는다.

Consumer A가 Commit하면 해당 row의 status는 PROCESSING
Consumer B는 대기 후 최신 값(PROCESSING)으로 WHERE 조건을 재평가하므로 status = 'PENDING' 조건을 만족하지 못해 0행이 반환
```

### **6. REPEATABLE READ 이상에서 달라질 수 있는 점**

```
REPEATABLE READ 이상에서는 트랜잭션 시작 시점의 스냅샷을 사용한다.

Consumer B가 트랜잭션을 시작한 후 Consumer A가 Commit했더라도 B는 자신의 스냅샷(PENDING)을 기준으로 조건을 평가하므로 UPDATE 시 직렬화 충돌이 발생한다.

B는 트랜잭션 전체를 Rollback하고 재시도해야 한다.
```

### **7. affected rows가 0일 때 상태별 처리**

| **조회 결과** | **의미** | **Consumer 처리** | **Offset 처리 방향** |
| --- | --- | --- | --- |
| 요청 행 없음 | 메시지와 DB 요청 등록 불일치 | 복구 정채 실행, 운영 알림 | Retry 또는 DLQ |
| `PENDING` | 동시 처리 중인 다른 Consumer 대기 | 재시도 또는 잠시 후 재확인 | Offset 커밋 보류 |
| `PROCESSING` | 다른 Consumer가 처리 권한 보유 중 | 즉기 재시도 지양, lease 만료 후 재시도 | Offset 커밋 보류 |
| `ISSUED` | 이미 최종 성공한 중복 메시지 | 새 발급 없이 멱등 성공 | Offset Commit |
| `FAILED` | 이미 최종 실패한 중복 메시지 | 새 처리 없이 멱등 성공 처리  | Offset Comit |

### **8. ISSUED 또는 FAILED 중복 메시지를 예외로 던지면 안 되는 이유**

아래 잘못된 흐름을 기준으로 설명한다.

```
ISSUED 확인
→ DuplicateMessageException
→ Retry Topic
→ 다시 ISSUED 확인
→ 다시 예외
→ DLQ
```

```
이미 정상 완료된 요청인데 예외로 처리하면 불필요한 Retry Topic 이동, DLQ 누적, 알림 발생이 반복된다.

또한 운영 부하가 증가하고 실제 문제가 있는 메시지와 구분이 어려워진다.

따라서 최종 상태를 확인하고 아무 변경 없이 Offset만 커밋하는 것이 올바른 처리다.
```

### **9. 최종 상태를 확인하고 아무 변경 없이 종료하는 것도 성공적인 처리인 이유**

```
멱등성의 목표는 중복 전달이 발생해도 비즈니스 결과가 한 번만 반영되게 하는 것이다.

ISSUED나 FAILED를 확인하고 종료하는 것은 "이 메시지의 비즈니스 결과가 이미 정상적으로 반영되었음"을 확인하는 행위다.

따라서 새로운 변경이 없더라도 Kafka 관점에서 해당 메시지 처리가 완료된 것이므로 Offset을 커밋해 다음 메시지로 넘어가는 것이 올바른 동작이다.
```

## **과제 7. 발급 트랜잭션과 Rollback 이후 상태 확정 설계하기**

처리 권한 획득부터 최종 요청 상태 변경까지를 하나의 DB 트랜잭션으로 설계한다.

### **1. 트랜잭션에 포함할 작업과 포함하지 않을 작업 구분하기**

```
| **작업** | **발급 트랜잭션 포함 여부** | **이유** |
| --- | --- | --- |
| PENDING → PROCESSING | O | 처리 권한 획득과 발급 결과가 원자적으로 묶여야 한다 |
| coupon_event 수량 확보 | O | 수량 증가와 발급 기록이 동시에 성공,실패해야 정합성이 유지된다 |
| coupon_issue INSERT | O | 발급 기록과 상태 변경이 함께 커밋되어야 한다 |
| request ISSUED / FAILED 변경 | O | 상태 변경이 발급 결과와 같은 트랜잭션에 있어야 일관성이 보장된다 |
| 이메일 발송 | X | 외부 API 응답이 느리면 DB Row Lock 시간이 늘어난다 |
| 앱 푸시 발송 | X | 외부 서비스 장애가 발급 트랜잭션에 전파된다 |
| 마이페이지 조회 모델 갱신 | X | 별도 이벤트로 분리해 비동기 처리하는 것이 적합하다 |
| 외부 API 호출 | X | 응답 시간과 실패 여부를 예측할 수 없어 트랜잭션 범위 밖에 두어야 한다 |
```

### **2. 전체 발급 트랜잭션 흐름 다이어그램**

다음 경로를 모두 포함한다.

```
처리 권한 획득 0행

수량 UPDATE 0행

coupon_issue INSERT 성공

coupon_issue UNIQUE 위반

최종 ISSUED 변경 0행

일시적 DB 오류
```

```
Consumer 메시지 수신
  |
  v
DB Transaction 시작
  |
  v
PENDING → PROCESSING 조건부 UPDATE
  |
  +---> 0행
  |       |
  |       v
  |     기존 상태 조회
  |       +---> ISSUED / FAILED → 멱등 성공 종료 → Offset Commit
  |       +---> PROCESSING     → 다른 Consumer 처리 중 → 재시도
  |       +---> 행 없음        → 복구 정책 실행
  |
  +---> 1행 (처리 권한 획득)
           |
           v
       coupon_event 조건부 UPDATE (issued_count + 1)
           |
           +---> 0행 (수량 소진)
           |       |
           |       v
           |     request FAILED / SOLD_OUT 변경 → Commit → Offset Commit
           |
           +---> 1행 (수량 확보)
                    |
                    v
                coupon_issue INSERT
                    |
                    +---> 성공
                    |       |
                    |       v
                    |     request ISSUED 변경
                    |       +---> 1행 → Commit → Offset Commit
                    |       +---> 0행 → 전체 Rollback (상태 불일치)
                    |
                    +---> UNIQUE 위반
                    |       |
                    |       v
                    |     전체 Rollback (issued_count 증가도 취소)
                    |       |
                    |       v
                    |     새 트랜잭션: coupon_issue 기존 기록 확인
                    |       |
                    |       v
                    |     request FAILED / DUPLICATE_USER (WHERE status = 'PENDING')
                    |       → Commit → Offset Commit
                    |
                    +---> 일시적 DB 오류
                            |
                            v
                          전체 Rollback
                            |
                            v
                          request 상태 PENDING 유지
                            |
                            v
                          Kafka 재전달 대기 (Offset Commit 안 함)
```

### **3. 정상 발급 SQL 흐름 완성하기**

```sql
BEGIN;

-- 1. PENDING 요청의 처리 권한 획득
UPDATE coupon_issue_request
SET status                  = 'PROCESSING',
    processing_started_at   = CURRENT_TIMESTAMP,
    updated_at              = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PENDING';
-- affected rows = 1인 경우에만 계속 진행

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at   = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;
-- affected rows = 1인 경우에만 INSERT 진행

-- 3. 최종 발급 기록 저장
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:eventId, :userId, 'ISSUED', CURRENT_TIMESTAMP)
RETURNING id;

-- 4. 요청 상태를 ISSUED로 변경
UPDATE coupon_issue_request
SET status          = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at    = CURRENT_TIMESTAMP,
    updated_at      = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PROCESSING';

COMMIT;
```

### **4. 각 단계에서 반드시 확인할 영향받은 row 수**

| **단계** | **정상적으로 기대하는 row 수** | **기대값과 다를 때 처리** |
| --- | --- | --- |
| 처리 권한 획득 | 1 | 0행 -> 기존 상태 조회 후 멱등 처리 또는 재시도 |
| 수량 UPDATE | 1 또는 0 | 0행 -> SOLD_OUT으로 판단, request FAILED 변경 후 Commit |
| 최종 ISSUED 변경 | 1 | 0행 -> 상태 불일치 -> 전체 Rollback |

### **5. 마지막 ISSUED 상태 변경이 0행인데 발급 결과만 Commit하면 안 되는 이유**

```
coupon_issue에는 발급 기록이 있지만 coupon_issue_request.status가 PROCESSING에 머물러 사용자가 상태 조회 API에서 ISSUED를 볼 수 없는 불일치 상태가 된다.

또한 coupon_issue_request.coupon)issue)id가 연결되지 않아 어떤 발급 기록과 연결된 요청인지 추적이 불가능해진다.

세 작업(수량 증가, 발급 기록, 상태 변경)은 반드시 함께 Commit되거나 함께 Rollback되어야 한다.
```

### **6. DB 기준 수량이 소진된 경우 처리**

조건부 UPDATE가 0행이고 이벤트가 존재하며 수량이 모두 소진된 것으로 확정되었다고 가정한다.

요청 상태를 `FAILED / SOLD_OUT`으로 변경하는 SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status          = 'FAILED',
    failure_code    = 'SOLD_OUT',
    failure_message = '쿠폰이 모두 소진되었습니다.',
    completed_at    = CURRENT_TIMESTAMP,
    updated_at      = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PROCESSING';
```

발급 행 생성 여부:

```
coupon_issue를 생성하지 않는다.

수량을 확보하지 못했으므로 발급 기록이 있어서는 안 된다.
```

같은 메시지가 다시 들어왔을 때 처리:

```
coupon_issue_request.status = 'FAILED'이므로 Consumer가 기존 FAILED를 확인하고 새 발급 없이 멱등 성공 처리 후 Offset을 커밋한다.
```

### **7. 서로 다른 requestId로 같은 사용자가 다시 발급을 시도한 경우**

이 시나리오는 Redis 관리자 admission 기록이 유실되거나 만료되어 req-B가 SUCCESS로 통과한 상황을 가정한다. 이때 DB의 UNIQUE(event_id, user_id)가 최종 방어선이 된다.

```
기존 요청
req-A / eventId=100 / userId=10 / ISSUED

새 요청
req-B / eventId=100 / userId=10 / PENDING
```

`req-B` 처리 중 `coupon_issue` INSERT에서 `UNIQUE(event_id, user_id)` 위반이 발생했다.

아래 항목을 설명한다.

```
첫 번째 트랜잭션의 상태:
coupon_issue UNIQUE(event_id, user_id) 위반이 발생해 트랜잭션 전체가 aborted 상태가 된다.
PostgreSQL에서는 제약 조건 위반이 발생한 트랜잭션을 계속 사용할 수 없다.

PENDING → PROCESSING 전이의 결과:
트랜잭션 전체가 Rollback되므로 PENDING → PROCESSING 전이도 함께 취소된다.
Rollback 후 request_b의 status는 다시 PENDING으로 돌아간다.

앞에서 증가한 issued_count의 결과:
트랜잭션 Rollback으로 issued_count 증가도 취소된다. 수량은 원래 값으로 복구된다.

같은 트랜잭션에서 FAILED로 바꿀 수 있는가?:
바꿀 수 없다. PostgreSQL에서 제약 조건 위반이 발생한 트랜잭션은 ROLLBACK 외의 모든 SQL 명령이 오류를 반환한다.
반드시 Rollback 후 새 트랜잭션을 시작해야 FAILED로 변경할 수 있다.
```

### **8. UNIQUE 위반 Rollback 후 별도 트랜잭션 처리 순서**

```
1. 현재 트랜잭션 Rollback (UNIQUE 위반으로 인해 전체 취소)

2. 새 트랜잭션 시작

3. coupon_issue에서 (event_id, user_id) 기존 기록 조회

4. 기존 기록이 존재하면 -> 사용자 중복 발급 시도임을 확인

5. coupon_issue_request를 FAILED / DUPLICATE_USER로 변경하고 Commit
```

### **9. Rollback 후 요청 상태를 어떤 출발 상태에서 FAILED로 변경해야 하는가?**

잘못된 SQL:

```sql
UPDATE coupon_issue_request
SET status = 'FAILED'
WHERE request_id = :requestId
  AND status = 'PROCESSING';
```

올바른 SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status          = 'FAILED',
    failure_code    = 'DUPLICATE_USER',
    failure_message = '이미 발급받은 사용자입니다.',
    completed_at    = CURRENT_TIMESTAMP,
    updated_at      = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PENDING';
```

왜 `PROCESSING`이 아닌지 설명한다.

```
UNIQUE 위반으로 트랜잭션 전체가 Rollback되면 PENDING → PROCESSING 전이도 함께 취소된다.

Rollback 후 status는 PROCESSING이 아니라 PENDING으로 돌아가고, WHERE status = 'PROCESSING'으로 조건을 걸면 항상 0행이 반환되어 요청이 영원히 PENDING 상태에 남는다.
```

### **10. 일시적 DB 오류가 발생한 경우**

다음 항목을 작성한다.

```
요청 상태: PENDING (Rollback으로 PROCESSING 전이가 취소됨)

issued_count: 변경 없음 (Rollback으로 원래 값 유지)

coupon_issue: 생성되지 않음 (Rollback)

FAILED 저장 여부: 저장 X

Kafka Listener 예외 처리: 예외를 다시 던져 Kafka 재처리 정랙으로 넘기고, 재전달된 메시지는 PENDING 상태에서 다시 처리 권한 획득을 시도한다.
```

### **11. 최종 비즈니스 실패와 일시적 시스템 오류 비교**

```
| **오류** | **최종 FAILED 저장 여부** | **Kafka 재시도 여부** | **이유** |
| --- | --- | --- | --- |
| DB 연결 일시 실패 | X | O | 잠시 후 재시도하면 성공할 수 있는 일시적 오류 |
| Deadlock | X | O |Deadlock은 재시도하면 일반적으로 해결  |
| SOLD_OUT | O | X | 수량 소진은 재시도해도 결과가 바뀌지 않는 비즈니스 실패 |
| DUPLICATE_USER | O | X | 이미 발급받은 사용자는 재시도해도 발급 허용 X |
| 메시지와 요청 행 불일치 | O | X | 구조적 오류로 재시도해도 해결 X |
```

## **과제 8. Kafka Offset과 중복 메시지 처리 설계하기**

DB 비즈니스 결과와 Kafka 소비 위치를 안전하게 연결하도록 Offset 처리 순서를 설계한다.

### **1. 안전한 처리 순서 작성하기**

아래 흐름을 완성한다.

```
1. Kafka 메시지를 읽는다.

2. 메시지와 요청 행의 내용(requestId, eventId, userId)를 검증한다.

3. DB Transaction을 시작한다.

4. 조건부 UPDATE로 PENDING -> PROCESSING 처리 권한을 획득한다.

5. 수량 확보, 발급 기록 저장, 요청 상태 최종 변경을 처리한다.

6.DB Transaction을 Commit한다.

7. Kafka Offset을 Commit한다.
```

### **2. DB 결과 확정과 Offset Commit의 역할 차이**

| **항목** | **의미** |
| --- | --- |
| DB Commit | 비즈니스 관점의 처리 완료. 수량, 발급 기록, 요청 상태가 영구적으로 반영 |
| Kafka Offset Commit | Kafka 관점의 처리 완료. 이 메시지는 소비했으니 다음 메시지로 넘어가도 된다는 표시 |

### **3. Offset을 먼저 Commit한 뒤 DB 처리가 실패하는 상황**

```
1. Offset Commit
2. DB 처리 시도
3. DB 장애
```

Kafka 상태:

```
해당 메시지의 Offset이 커밋되어 Kafka는 처리 완료로 기록한다.

Consumer가 재시작되어도 이 메시지를 다시 받지 않는다.
```

DB 상태:

```
발급 처리가 실패했으므로 coupon_issue기록이 없다.

coupon_issue_request는 PENDING 상태를 유지하고, issued_count는 변경이 없다.
```

사용자 요청에 발생하는 문제:

```
사용자는 요청 접수 응답(202)를 받았지만 실제로는 아무 처리도 이루어지지 않은 상태가 된다.

Kafka가 메시지를 완료로 기록했기 때문에 재전달도 없다.
```

### **4. DB Commit 후 Offset Commit 전에 Consumer가 종료되는 상황**

```
DB Commit 성공
→ Consumer 종료
→ Offset Commit 실패
```

Consumer 재시작 후 발생하는 일:

```
Kafka는 Offset이 커밋되지 않았으므로 마지막 커밋된 Offset 이후부터 메시지를 다시 전달한다.

같은 Record가 새 Consumer에게 재전달된다.
```

request 상태가 `ISSUED`인 경우 처리:

```
Consumer가 메시지를 다시 받아 처리를 시도하고, PENDING → PROCESSING 조건부 UPDATE에서 0행이 반환된다.

기존 상태를 조회하면 ISSUED임을 확인하고, 새 발급 로직 없이 멱등 성공으로 처리하고 Offset을 커밋한다.
```

### **5. 같은 Kafka Record 재전달과 같은 requestId의 다른 Record 비교**

| **구분** | **Partition** | **Offset** | **requestId** |
| --- | --- | --- | --- |
| Offset 미반영으로 동일 Record 재전달 | 동일 | 동일 | 동일 |
| Producer가 같은 요청을 두 번 발행 | 같거나 다를 수 있음 | 다름 | 동일 |

두 현상을 모두 requestId로 방어해야 하는 이유:

```
두 현상 모두 Consumer 입장에서는 같은 requestId를 가진 메시지가 다시 도착하는 상황이다.

Offset이 같으면 완전히 동일한 Record이고, Offset이 다르면 재발행된 새 Record이지만 requestId는 같다.

어느 경우든 coupon_issue_request 상태를 requestId로 조회하면 ISSUED 또는 FAILED를 확인하고 중복 처리 없이 종료할 수 있다.
```

### **6. 자동 커밋 사용 시 확인해야 할 항목**

```
1. 자동 커밋 간격(auto.commit.interval.ms) 설정 확인

2. enable.auto.commit = false로 비활성화하고 수동 커밋 사용 여부 확인

3. Listener에서 예외 발생 시 Offset이 커밋되는지 여부 확인

4. DB Rollback 시 메시지 재전달을 위해 Offset이 커밋되지 않는지 확인

5. Retry Topic 이동 시 원본 Record의 Offset 커밋 처리 방식 확인
```

### **7. At-Least-Once와 비즈니스 결과의 차이**

아래 문장을 완성한다.

```
메시지 전달 횟수
→ 한 번 이상일 수 있다. 동일 메시지가 여러 번 전달될 수 있음을 허용한다.

쿠폰 발급 결과
→ 반드시 한 번만 반영된다. requestId기반 멱등 처리와 DB 제약 조건이 중복 반영을 막는다.
```

### **8. 다음 상태에서 Offset 처리 방향 작성하기**

| **request 상태 또는 처리 결과** | **Offset 처리 방향** | **이유** |
| --- | --- | --- |
| 새 `PENDING` 요청 처리 성공 | DB Commit 후 Commit | 정상 처리 완료 |
| 기존 `ISSUED` 요청 중복 메시지 | 즉시 Commit | 이미 성공한 요청이므로 새 처리 없이 완료 처리 |
| 기존 `FAILED` 요청 중복 메시지 | 즉시 Commit | 이미 최종 실패한 요청이므로 새 처리 없이 완료 처리 |
| 일시적 DB 오류로 Rollback | Commit 안 함 | Kafka 재전달로 다시 처리해야 하므로 Offset을 커밋하지 않음 |
| 요청 행 없음 | Retry 또는 DLQ | 복구 정책 실행 후 판단 |
| 메시지 내용 불일치 | DLQ 후보 | 재시도해도 해결되지 않으므로 운영 확인 대상으로 분리 |

## **과제 9. Redis, DB, Kafka 불일치와 복구 정책 설계하기**

Redis, DB, Kafka는 하나의 로컬 트랜잭션으로 묶이지 않는다.

따라서 각 경계에서 생길 수 있는 불일치를 분석하고 복구 방향을 설계한다.

### **1. 장애 시점별 상태와 복구 방향**

| **장애 상황** | **Redis 상태** | **DB 요청 상태** | **Kafka 상태** | **복구 방향** |
| --- | --- | --- | --- | --- |
| Redis SUCCESS 후 DB 요청 행 INSERT 전 장애 | 통과 기록 존재 | 행 없음 | 메시지 없음 | DB 등록 재시도, 실패 시 Redis 자리 보상 |
| DB에 PENDING 저장 후 Kafka 발행 전 장애 | 통과 기록 존재 | PENDING | 메시지 없음 | Kafka 발행 재시도, 복구 배치로 오래된 PENDING 처리 |
| Kafka 발행 성공 후 API 응답 유실 | 통과 기록 존재 | PENDING | 메시지 없음 | Client 재시도 시 IDEMPOTENT_RETRY 처리 |
| Consumer가 DB 처리 전 종료 | 통과 기록 존재 | PENDING | Offset 미커밋 | Kafka 재전달 후 Consumer 재처리 |
| DB Commit 후 Offset Commit 전 종료 | 통과 기록 존재 | ISSUED | Offset 미커밋 | Kafka 재전달 시 ISSUED 확인 후 멱등 성공 처리 |
| DB ISSUED 후 Redis 데이터 유실 | 통과 기록 없음 | ISSUED | Offset 커밋됨 | 영향 없음. 최종 기준은 DB이므로 정상 처리 완료 |
``

### **2. Redis SUCCESS 후 DB 요청 행이 없는 상태**

이 상태가 발생하는 흐름을 다이어그램으로 작성한다.

```
Redis Lua Script
  |
  | SUCCESS 반환
  v
API Server
  |
  | DB INSERT 시도
  X 장애 발생 (네트워크 오류, DB 연결 실패 등)
  |
  v
Redis: userId → requestId 매핑 존재
DB:    coupon_issue_request 행 없음
Kafka: 메시지 없음
```

동일 requestId 재시도 시 처리 방향:

```
Redis에서 IDEMPOTENT_RETRY를 반환하지만 DB에 행이 없다.

이 상태를 정상 PENDING으로 반환하지 않고 DB 등록을 다시 시도한다.
```

일정 시간 이상 지속될 때 가능한 보상:

```
일정 시간(예: 30초) 이상 DB 행이 생성되지 않으면 Redis에서 해당 사용자의 수량 카운터를 복구하고 사용자 Set에서 제거하여 다른 사용자가 자리를 얻을 수 있도록 한다.
```

보상 시 현재 Redis 자리의 requestId 소유권을 확인해야 하는 이유:

```
보상 중에 새로운 요청이 Redis 판정을 통과해 같은 userId에 다른 requestId가 저장되어 있을 수 있다.

현재 Redis에 저장된 requestId가 보상하려는 requestId와 같은지 Lua Script로 원자적으로 확인한 뒤 제거해야 다른 사용자의 정상 처리를 방해하지 않는다.
```

### **3. PENDING 저장 뒤 Kafka 발행 실패**

최종 상태를 작성한다.

```
Redis: 통과 기록 존재 (userId -> requestId 매핑)

DB: coupon_issue_request status = PENDING

Kafka: 메시지 없음
```

이 요청이 계속 `PENDING`에 남는 이유:

```
Consumer는 Kafka 메시지를 기반으로 처리하는데 Kafka에 메시지가 없으므로 Consumer가 이 요청을 알 수 없다.

아무도 처리하지 않으므로 PENDING 상태가 지속된다.
```

복구를 위해 필요한 인덱스 또는 조회 조건:

```sql
SELECT request_id, event_id, user_id, status, created_at
FROM coupon_issue_request
WHERE status     = 'PENDING'
  AND created_at < NOW() - INTERVAL '5 minutes';
```

복구 방향:

```
오래된 PENDING 요청을 주기적으로 조회하는 복구 배치를 운영하고, afka 발행을 재시도한다.

발행이 지속적으로 실패하면 Kafka 장애 여부를 확인하고 운영 알림을 발송한다.

Outbox Pattern을 도입하면 DB PENDING 저장과 Outbox 이벤트를 같은 트랜잭션으로 묶어
발행 실패를 줄일 수 있다.
```

### **4. Kafka 발행 Timeout이 모호한 이유**

아래 두 상황을 설명한다.

```
상황 A
Broker가 메시지를 저장하지 못하고 Timeout

상황 B
Broker는 메시지를 저장했지만 ACK만 유실되어 Timeout
```

Producer가 두 상황을 구분하기 어려운 이유:

```
상황 A: Broker가 메시지를 저장하지 못하고 Timeout을 반환한 경우
         → 실제로 메시지가 존재하지 않는다.

상황 B: Broker는 메시지를 정상 저장했지만 ACK만 네트워크 오류로 유실된 경우
         → 메시지는 이미 Topic에 존재한다.

Producer는 ACK를 받지 못했다는 사실만 알 뿐 Broker가 실제로 저장했는지 알 수 없으므로 두 상황을 구분하지 못한다.
```

같은 requestId로 재발행했을 때 가능한 Kafka Record:

```
Offset 100 → requestId = req-001 (원본, 상황 B에서 이미 저장됨)
Offset 101 → requestId = req-001 (재발행)

동일 requestId를 가진 Record가 두 개 생성될 수 있다.
```

Consumer가 안전하게 처리할 수 있는 이유:

```
Consumer가 첫 번째 Record(Offset 100)를 처리해 request가 ISSUED가 된다.

두 번째 Record(Offset 101)가 도착하면 Consumer가 ISSUED 상태를 확인하고 새 발급 없이 멱등 성공 처리 후 Offset을 커밋한다.

requestId 기반 멱등 처리가 중복 발급을 막는다.
```

### **5. Outbox Pattern이 줄일 수 있는 불일치**

아래 두 작업을 하나의 DB 트랜잭션으로 묶는 구조를 작성한다.

```
coupon_issue_request INSERT

outbox_event INSERT
```

다이어그램:

```
DB Transaction
  |
  +---> coupon_issue_request INSERT (status = PENDING)
  |
  +---> outbox_event INSERT
  |     (event_type = 'COUPON_ISSUE_REQUESTED', payload = {requestId, eventId, userId})
  |
  v
Commit (두 작업이 함께 성공하거나 함께 실패)

별도 Outbox Publisher
  |
  | outbox_event 조회
  v
Kafka 발행
  |
  | 발행 성공 → outbox_event 완료 처리
  | 발행 실패 → outbox_event PENDING 유지 → 재시도
```

### **6. Outbox Pattern이 해결하지 못하는 구간**

아래 구간을 기준으로 설명한다.

```
Redis 선착순 판정
↔
DB 요청 상태 저장
```

```
Redis 선착순 판정 ↔ DB 요청 상태 저장 구간은 Outbox Pattern으로 해결할 수 없다.

Redis와 DB는 서로 다른 저장소이므로 하나의 트랜잭션으로 묶을 수 없고, Outbox Pattern은 DB와 Kafka 사이의 정합성을 보장하는 패턴이지 Redis와 DB 사이의 원자성을 보장하지 않는다.

따라서 Redis SUCCESS 후 DB 등록 실패 상황은 Outbox Pattern과 별개로 복구 정책이 필요하다.
```

### **7. 최종 발급 결과의 기준 데이터**

다음 중 최종 발급 여부를 판단할 기준을 선택하고 이유를 설명한다.

```
Redis 통과 기록

Kafka 메시지 존재 여부

coupon_issue DB 기록

coupon_issue_request 상태
```

선택:

```
coupon_issue DB 기록
```

이유:

```
Redis는 인메모리 저장소로 데이터가 유실될 수 있고 Redis SUCCESS는 선착순 판정 통과를 의미할 뿐 최종 발급 성공이 아니다.

Kafka 메시지 존재 여부는 Consumer가 처리했는지를 나타내지 않는다. 메시지가 있어도 아직 처리 중이거나 실패했을 수 있다.

coupon_issue_request 상태는 요청 처리 상태를 나타내지만 시스템 장애 상황에서 일시적으로 부정확할 수 있다.

coupon_issue DB 기록은 DB 트랜잭션으로 커밋된 영구 기록이다. ACID 트랜잭션의 보장을 받으므로 가장 신뢰할 수 있는 최종 기준이다.
```

### **8. 재실행 가능한 설계 정리하기**

| **단계** | **중복 또는 재실행 방어 기준** |
| --- | --- |
| Redis 판정 | userId + requestId 기준 Lua Script 원자적 판정, 동일 사용자 재진입 차단 |
| DB 요청 등록 | request_id PRIMARY KEY + ON CONFLICT DO NOTHING으로 중복 등록 방지 |
| Kafka 재발행 | 같은 requestId로 재발행 허용, Consumer 멱등 처리로 흡수 |
| Consumer 처리 | requestid 기반 조건부 상태 전이, UNIQUE(event_id, user_id), DB Tracsaction |

아래 항목을 포함해 최소 5개 작성한다.

```
오래된 PENDING 요청 수

오래된 PROCESSING 요청 수

requestId 충돌 횟수

Redis SUCCESS 후 DB 행 누락 횟수

```

| --- | --- | --- |

| Kafka 발행 실패 횟수 | Kafka 연결 또는 브로커 이상 가능성 | 분당 10건 이상 발생 시 |

## **과제 10. 나쁜 멱등 설계의 문제점 찾기**

아래 시스템은 `requestId`를 사용하고 있지만 안전한 멱등 구조라고 보기 어렵다.

```
1. API Server가 요청을 받을 때마다 새로운 requestId를 생성한다.

2. 같은 requestId가 들어오면 요청 내용은 확인하지 않고
   기존 결과를 무조건 반환한다.

3. 요청 상태는 coupon_issue에 성공 기록만 저장한다.

4. Consumer는 SELECT로 PENDING을 확인한 뒤
   조건 없이 PROCESSING으로 UPDATE한다.

5. 최종 상태 변경 SQL에 이전 상태 조건이 없다.

6. request가 ISSUED이면 DuplicateMessageException을 던진다.

7. Kafka Offset은 DB 처리 전에 자동 Commit될 수 있다.

8. DB Deadlock도 즉시 request FAILED로 저장한다.

9. coupon_issue UNIQUE 위반 후 같은 트랜잭션에서
   request를 FAILED로 변경하려고 한다.

10. UNIQUE 위반 트랜잭션이 Rollback된 뒤에도
    WHERE status = 'PROCESSING'으로 FAILED 변경을 시도한다.

11. 상태 조회 API는 requestId만 알면 누구나 조회할 수 있다.

12. Idempotency-Key 재사용 가능 기간보다 먼저
    coupon_issue_request 행을 삭제한다.
```

### **1. 문제점과 개선 방향 작성하기**

최소 10개 이상 작성한다.

| **문제점** | **왜 문제인가?** | **개선 방향** |
| --- | --- | --- |
| API Server가 요청마다 새 requestId 생성 | 재시도 시 서버가 매번 다른 requestId를 만들어 동일 요청을 식별할 수 없다 | Client가 요청 전 requestId를 생성하고 재시도 시 재사용 |
| 요청 내용 확인 없이 기존 결과 무조건 반환 | 같은 requestId에 다른 요청 내용이 들어와도 기존 결과를 반환해 엉뚱한 결과 노출 | requestHash를 비교해 내용이 다르면 409 Conflict 반환 |
| 성공 기록만 coupon_issue에 저장 | PENDING, PROCESSING, FAILED 상태를 표현할 수 없고 사용자가 결과를 조회할 수 없다 | coupon_issue_request 테이블을 별도로 설계해 요청 생명주기 관리 |
| SELECT 후 조건 없이 PROCESSING UPDATE | 두 Consumer가 동시에 PENDING을 확인하고 둘 다 처리 권한을 얻어 중복 처리 발생 | WHERE status = 'PENDING' 조건을 포함한 조건부 UPDATE 사용 |
| 최종 상태 변경 SQL에 이전 상태 조건 없음 | ISSUED나 FAILED를 다른 상태로 덮어쓸 수 있고 오래된 Consumer가 최신 결과를 변경 | WHERE status = 'PROCESSING' 조건을 반드시 포함 |
| ISSUED 확인 시 DuplicateMessageException | 이미 성공한 요청이 Retry Topic과 DLQ를 계속 순환하며 불필요한 재처리 발생 | 최종 상태 확인 후 아무 변경 없이 Offset만 커밋하는 멱등 성공 처리 |
| DB 처리 전 Kafka Offset 자동 커밋 | DB 처리 실패 시 Kafka는 완료로 기록해 메시지가 재전달되지 않아 요청 유실 발생 | enable.auto.commit = false, DB Commit 후 수동 Offset 커밋 |
| Deadlock을 즉시 request FAILED로 저장 | Deadlock은 재시도하면 성공할 수 있는 일시적 오류인데 최종 실패로 확정해 사용자 불이익 발생 | 일시적 오류는 Rollback 후 Kafka 재전달로 재처리, FAILED는 비즈니스 실패에만 사용 |
| UNIQUE 위반 후 같은 트랜잭션에서 FAILED 변경 시도 | PostgreSQL에서 제약 위반 트랜잭션은 aborted 상태로 ROLLBACK 외 모든 SQL 오류 발생 | Rollback 후 새 트랜잭션에서 FAILED 변경 |
| Rollback 후 WHERE status = 'PROCESSING'으로 FAILED 변경 | Rollback으로 status가 PENDING으로 돌아가 0행이 반환되어 요청이 영원히 PENDING에 남음 | WHERE status = 'PENDING' 조건으로 변경 |
| requestId만으로 상태 조회 허용 | 다른 사용자의 발급 결과가 노출되는 정보 유출 발생 | WHERE user_id = :authenticatedUserId 조건 추가 |
| Idempotency-Key 유효 기간보다 먼저 행 삭제 | 재시도 시 기존 행이 없어 서버가 과거 요청을 신규 요청으로 오인해 중복 처리 발생 | 요청 상태 보관 기간 ≥ Idempotency-Key 유효 기간 유지 |

### **2. 다음 잘못된 SQL을 안전한 조건부 상태 전이로 수정하기**

잘못된 SQL:

```sql
UPDATE coupon_issue_request
SET status = 'PROCESSING'
WHERE request_id = :requestId;
```

수정 SQL:

```sql
UPDATE coupon_issue_request
SET status                  = 'PROCESSING',
    processing_started_at   = CURRENT_TIMESTAMP,
    updated_at              = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status     = 'PENDING';
```

### **3. 다음 잘못된 최종 성공 SQL을 수정하기**

```sql
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId
WHERE request_id = :requestId;
```

수정 SQL:

```sql
UPDATE coupon_issue_request

    coupon_issue_id = :couponIssueId,

    updated_at      = CURRENT_TIMESTAMP

  AND status     = 'PROCESSING';
```

### **4. 중복 메시지를 정상적으로 종료시키는 처리 흐름 작성하기**

```

FAILED:

→ 새로운 처리 없이 기존 실패 결과 유지

→ Kafka Offset Commit
```
