# **5주차 과제**

# **requestId 기반 멱등성과 중복 처리 구조 설계**

> 모든 답변은 각 문항 아래의 코드블록 안에 작성한다. 표 형식 문항도 코드블록 안의 표를 수정해 제출한다.
>

## **1. 과제 목표**

이번 5주차 과제의 목표는 **같은 API 요청이나 Kafka 메시지가 여러 번 전달되더라도 최종 쿠폰 발급 결과가 한 번만 반영되도록 멱등 처리 구조를 설계하는 것**이다.

1주차에서는 요청 접수와 실제 발급 처리를 분리했다.

2주차에서는 Kafka를 이용해 쿠폰 발급 요청을 비동기적으로 전달했다.

3주차에서는 Redis를 이용해 사용자 중복 요청과 수량 초과 요청을 빠르게 차단했다.

4주차에서는 DB의 조건부 `UPDATE`, `UNIQUE(event_id, user_id)`, Transaction을 이용해 최종 수량과 사용자 중복 발급을 방어했다.

이번 5주차에서는 다음 문제를 추가로 해결한다.

```
같은 논리적인 요청이 여러 번 전달되었는가?

같은 사용자가 새로운 요청을 다시 보낸 것인가?

Consumer가 이미 성공한 메시지를 다시 읽은 것인가?

요청이 아직 처리 중인가?

이전에 성공하거나 실패했다면 어떤 결과를 다시 반환해야 하는가?
```

기본 흐름은 다음과 같다.

```
Client
  |
  | Idempotency-Key: requestId
  v
API Server
  |
  | 인증된 userId 확인
  | requestHash 생성
  v
Redis
  |
  | 사용자 + requestId 기준 판정
  v
coupon_issue_request
  |
  | PENDING 요청 상태 저장
  v
Kafka
  |
  | requestId가 포함된 메시지 전달
  v
Coupon Issue Consumer
  |
  | requestId 기준 처리 권한 획득
  v
DB Transaction
  |
  | 수량 증가
  | 발급 기록 저장
  | 요청 상태 확정
  v
Kafka Offset Commit
```

이번 과제에서 중요하게 볼 내용은 다음과 같다.

```
Idempotency-Key와 requestId의 역할

같은 요청과 같은 사용자의 차이

Kafka Producer 멱등성과 비즈니스 멱등성의 차이

requestId와 Kafka Partition + Offset의 차이

requestHash를 이용한 잘못된 키 재사용 방지

coupon_issue_request 요청 상태 테이블 설계

PENDING / PROCESSING / ISSUED / FAILED 상태 전이

동일 requestId 동시 요청의 최초 등록자 결정

Consumer의 조건부 상태 전이와 처리 권한 획득

발급 수량, 발급 기록, 요청 상태를 묶는 DB Transaction

UNIQUE 위반 Rollback 이후 상태 확정

DB Commit과 Kafka Offset Commit의 순서

중복 메시지를 예외가 아니라 멱등 성공으로 처리하는 방법

Redis, DB, Kafka 사이의 일시적 불일치와 복구 방향
```

이번 과제의 핵심은 다음과 같다.

```
중복 전달을 완전히 없애는 것이 목표가 아니다.

같은 요청이 여러 번 전달되더라도
최종 비즈니스 결과가 한 번만 반영되게 만드는 것이 목표다.
```

## **2. 기본 상황**

서비스에서 다음 선착순 쿠폰 이벤트를 진행한다고 가정한다.

```
이벤트 ID: 100

이벤트 이름: 여름맞이 5,000원 할인 쿠폰 이벤트

전체 쿠폰 수량: 1,000개

발급 조건:
사용자 1명당 해당 이벤트 쿠폰 1개만 발급 가능

DBMS: PostgreSQL

DB 격리 수준: READ COMMITTED

최종 발급 성공 기준:
coupon_event.issued_count 증가,
coupon_issue 저장,
coupon_issue_request ISSUED 변경이
하나의 트랜잭션으로 Commit된 시점
```

사용자 `userId = 10`이 다음 요청을 보낸다.

```
POST /api/coupon-events/100/issue
Authorization: Bearer ...
Idempotency-Key: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31
```

서버 내부에서는 `Idempotency-Key`를 `requestId`로 사용한다.

```json
{
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "eventId": 100,
  "userId": 10,
  "requestedAt": "2026-07-24T12:00:00+09:00"
}
```

하지만 실제 시스템에서는 다음 상황이 발생할 수 있다.

```
상황 1.
서버는 요청을 처리했지만 응답만 유실되어
Client가 같은 requestId로 재시도한다.

상황 2.
사용자가 버튼을 여러 번 눌러
서로 다른 requestId로 같은 쿠폰을 다시 요청한다.

상황 3.
애플리케이션 코드가 같은 메시지를 send()로 두 번 발행한다.

상황 4.
Consumer가 DB Commit 후 Offset Commit 전에 종료되어
같은 Kafka Record를 다시 읽는다.

상황 5.
원본 Topic의 메시지가 Retry Topic으로 이동하여
Partition과 Offset은 달라졌지만 같은 requestId가 다시 전달된다.

상황 6.
같은 requestId가 다른 eventId 또는 다른 userId 요청에 재사용된다.
```

이 모든 상황을 단순히 `UNIQUE(event_id, user_id)` 하나로만 처리할 수는 없다.

```
UNIQUE(event_id, user_id)
→ 같은 사용자의 최종 중복 발급을 막는다.

requestId
→ 같은 논리적인 요청의 재처리를 식별한다.

requestHash
→ 같은 requestId가 다른 요청에 재사용되는 것을 막는다.
```

## **3. 이번 과제의 전제 조건**

이번 과제에서는 다음 전제를 따른다.

```
Client는 쿠폰 발급 요청을 보내기 전에 UUID 형식의 requestId를 생성한다.

같은 논리적인 요청을 재시도할 때는
최초 요청과 동일한 requestId를 재사용한다.

새로운 논리적인 작업에는 새로운 requestId를 사용한다.

userId는 Request Body가 아니라
인증된 사용자 정보에서 가져온다.

requestHash는 다음 Canonical String을 기준으로 생성한다.

COUPON_ISSUE|eventId|authenticatedUserId

Hash 알고리즘은 SHA-256을 사용한다.
```

이번 과제에서는 3주차의 Redis 구조를 다음처럼 확장한다고 가정한다.

```
Redis 판정 기준

- eventId + userId
- 해당 사용자의 최초 requestId
```

Redis Lua Script의 반환값은 다음 네 가지로 사용한다.

| **반환값** | **의미** |
| --- | --- |
| `SUCCESS` | 새로운 사용자가 새로운 requestId로 선착순 판정을 통과함 |
| `IDEMPOTENT_RETRY` | 같은 사용자와 같은 requestId가 다시 들어옴 |
| `DUPLICATE_USER` | 같은 사용자가 다른 requestId로 다시 요청함 |
| `SOLD_OUT` | Redis 기준 제한 수량에 도달함 |

이번 과제에서는 Redis를 통과한 요청만 DB 요청 상태 테이블에 저장하는 방식을 기본으로 사용한다.

```
Redis SUCCESS
→ coupon_issue_request PENDING 저장
→ Kafka 발행

Redis DUPLICATE_USER / SOLD_OUT
→ coupon_issue_request를 만들지 않음
→ Kafka에 발행하지 않음
```

요청 상태는 다음 네 가지로 단순화한다.

```
PENDING
PROCESSING
ISSUED
FAILED
```

최종 실패 코드는 다음 예시를 사용할 수 있다.

```
SOLD_OUT
DUPLICATE_USER
INVALID_EVENT
REQUEST_MISMATCH
```

다음 오류는 최종 비즈니스 실패가 아니라 일시적 시스템 오류로 본다.

```
DB 연결 일시 실패
Deadlock
네트워크 Timeout
Connection Pool 일시 부족
Consumer 프로세스 장애
```

일시적 시스템 오류가 발생하면 요청 상태를 `FAILED`로 확정하지 않고 트랜잭션을 Rollback한 뒤 Kafka 재전달을 통해 다시 처리한다.

이번 주차의 기본 Consumer 처리는 짧은 DB 작업이므로 다음 범위를 하나의 트랜잭션으로 묶는다.

```
PENDING → PROCESSING 처리 권한 획득
coupon_event.issued_count 증가
coupon_issue INSERT
coupon_issue_request ISSUED 또는 FAILED 변경
```

이번 주차에서는 아래 내용을 상세 구현하지 않는다.

```
Outbox Publisher 상세 구현

Retry Topic과 DLQ 상세 정책

쿠폰 발급 취소와 재발급

외부 결제나 외부 API 호출이 포함된 장시간 작업

Redis와 RDB를 하나의 분산 트랜잭션으로 묶는 방법
```

다만 Redis, DB, Kafka 사이에서 어떤 불일치가 발생할 수 있는지와 복구 방향은 설명해야 한다.

## **과제 1. requestId 기반 전체 멱등 처리 구조 그리기**

Client의 최초 요청부터 Kafka Offset Commit까지의 전체 흐름을 다이어그램으로 작성한다.

반드시 아래 구성 요소를 포함해야 한다.

```
Client

Idempotency-Key

API Server

Redis Lua Script

coupon_issue_request

Kafka Producer

coupon.issue.requested Topic

Coupon Issue Consumer

coupon_event

coupon_issue

Kafka Offset Commit
```

### **1. 전체 요청 처리 흐름 다이어그램**

```
Client
  |
  | Idempotency-Key: requestId
  v
API Server
  | - 인증된 userId 확인
  | - requestId 형식 검증
  | - requestHash 생성
  v
Redis Lua Script
  | - 선착순 수량 판정
  | - eventId + userId 중복 판정
  | - 최초 requestId 저장
  |
  +-- IDEMPOTENT_RETRY → DB에 저장된 기존 요청 상태 반환
  +-- DUPLICATE_USER   → 중복 사용자 응답, Kafka 발행 안 함
  +-- SOLD_OUT         → 품절 응답, Kafka 발행 안 함
  +-- SUCCESS
        |
        v
coupon_issue_request
  | - requestId를 PK로 PENDING 상태 저장
  v
Kafka Producer
  |
  | requestId가 포함된 메시지 발행
  v
coupon.issue.requested Topic
  |
  v
Coupon Issue Consumer
  | - 메시지와 요청 상태 행의 내용 검증
  | - PENDING → PROCESSING 조건부 UPDATE
  v
DB Transaction
  | - coupon_event의 issued_count 조건부 증가
  | - coupon_issue 실제 발급 결과 저장
  | - coupon_issue_request를 ISSUED 또는 FAILED로 변경
  v
DB Commit
  |
  v
Kafka Offset Commit
```

### **2. 하나의 requestId가 전체 흐름에서 어떻게 전달되는지 작성하기**

아래 흐름을 완성한다.

```
HTTP Idempotency-Key
        |
        v
API Server의 requestId
        |
        v
coupon_issue_request.request_id
        |
        v
Kafka Message의 requestId
        |
        v
Consumer 멱등 처리
```

### **3. 각 구성 요소의 역할**


| **구성 요소** | **역할** |
| --- | --- |
| Redis | 선착순 수량을 판정하고 같은 사용자의 중복 요청을 빠르게 차단하며, 최초로 통과한 requestId를 저장한다. |
| Kafka | 쿠폰 발급 요청을 비동기로 전달한다. Consumer 처리 실패 시 Offset이 Commit되지 않았다면 메시지를 다시 처리할 수 있게 한다. |
| coupon_issue_request | requestId를 기준으로 요청의 PENDING, PROCESSING, ISSUED, FAILED 상태와 발급 결과 및 실패 이유를 저장한다. |
| coupon_event | 쿠폰 이벤트의 전체 수량과 발급 수량을 저장한다. 조건부 UPDATE를 통해 전체 수량을 초과하지 않도록 최종 방어한다. |
| coupon_issue | 실제 쿠폰 발급 결과를 저장한다. UNIQUE(event_id, user_id)를 통해 같은 사용자의 최종 중복 발급을 방지한다. |
| Kafka Offset | Consumer가 Partition의 메시지를 어디까지 처리했는지 기록한다. DB 결과가 Commit된 이후 Offset을 Commit한다. |


### **4. 각 단계의 성공이 의미하는 것**


| **단계** | **의미** | **최종 발급 성공 여부** |
| --- | --- | --- |
| Redis `SUCCESS` | Redis 기준으로 선착순 판정을 통과한 상태이다. | X |
| request `PENDING` | 요청이 DB에 접수되었지만 아직 최종 처리가 완료되지 않은 상태이다. | X |
| request `PROCESSING` | Consumer가 처리 권한을 얻어 쿠폰 발급을 처리 중인 상태이다. | X |
| request `ISSUED` | 수량 증가, 발급 결과 저장, 요청 상태 변경이 하나의 DB 트랜잭션으로 Commit된 상태이다. | O |
| request `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 비즈니스 실패가 확정된 상태이다. | X |
| Kafka Offset Commit | Kafka가 해당 Record의 처리가 완료되었다고 판단할 수 있도록 처리 위치를 반영한 상태이다. ISSUED뿐 아니라 FAILED 또는 멱등 처리된 중복 메시지도 Offset을 Commit할 수 있다. | 이것만으로는 판단할 수 없음 |


### **5. 최종 쿠폰 발급 성공으로 판단할 수 있는 시점**

```
최종 쿠폰 발급 성공은 coupon_issue_request의 상태가 ISSUED로 변경된
DB 트랜잭션이 Commit된 시점이다.

Redis SUCCESS와 Kafka 메시지 발행은 쿠폰을 발급받기 위한 중간 과정일 뿐이다.
coupon_event의 issued_count 증가, coupon_issue 발급 결과 저장,
coupon_issue_request의 ISSUED 변경이 모두 하나의 트랜잭션으로 Commit되어야
실제 쿠폰 발급이 완료되었다고 판단할 수 있다.
```

### **6. 요청이 여러 번 도착해도 최종 결과가 한 번만 반영되어야 한다는 의미**

```
요청이나 Kafka 메시지가 물리적으로 여러 번 전달되는 것 자체를 막는다는 의미가 아니다.
같은 requestId의 요청이 여러 번 들어오더라도 기존 요청 상태와 결과를 확인하고,
실제 쿠폰 발급 로직은 한 번만 수행되도록 하는 것이다.

최초 요청만 쿠폰 수량 증가와 발급 결과 저장을 수행하고,
이미 ISSUED 또는 FAILED인 요청은 기존 결과를 유지한 채 정상적으로 종료한다.
따라서 메시지는 여러 번 전달될 수 있지만 최종 쿠폰 발급 결과는 한 번만 반영된다.
```

## **과제 2. 중복 유형과 멱등성 경계 구분하기**

같아 보이는 중복도 원인과 방어 장치가 다르다.

아래 상황을 읽고 각각 어떤 중복인지 구분한다.

### **1. 상황별 중복 유형 분석**

| **상황** | **같은 논리적 요청인가?** | **식별 기준** | **주요 방어 장치** |
| --- | --- | --- | --- |
| 응답 유실 후 같은 requestId로 API 재시도 | 예 | requestId | requestId와 coupon_issue_request에 저장된 기존 상태 및 결과 |
| 반복 클릭으로 다른 requestId가 생성됨 | 아니오 | 서로 다른 requestId와 같은 eventId + userId | Redis의 사용자 중복 판정과 DB의 UNIQUE(event_id, user_id) |
| 애플리케이션이 같은 requestId 메시지를 `send()` 두 번 호출 | 예 | requestId | Consumer의 조건부 상태 전이와 기존 최종 상태 확인 |
| DB Commit 후 Offset Commit 전 장애로 같은 Record 재전달 | 예 | 같은 Partition + Offset과 requestId | Consumer의 조건부 상태 전이와 기존 ISSUED 상태 확인 |
| 원본 Topic과 Retry Topic에 같은 requestId가 존재 | 예 | requestId | Topic, Partition, Offset이 아닌 requestId 기준 Consumer 멱등 처리 |
| 같은 requestId가 다른 eventId에 재사용됨 | 아니오. 잘못된 Idempotency-Key 재사용이다. | requestHash 불일치 | API에서 409 Conflict 반환 후 Redis 판정과 Kafka 발행 금지 |

### **2. 같은 요청과 같은 사용자의 차이**

아래 두 상황의 차이를 설명한다.

```
상황 A
requestId = req-001
이 요청이 여러 번 전달됨

상황 B
requestId = req-A, req-B, req-C
모두 eventId = 100, userId = 10
```

답변:

```
상황 A는 같은 requestId가 여러 번 전달된 것이므로 같은 논리적 요청의 재시도이다.
새로운 발급 작업을 만들지 않고 coupon_issue_request의 기존 상태와 결과를 반환해야 한다.

상황 B는 같은 사용자와 이벤트이지만 requestId가 서로 다르므로 각각 새로운 논리적 요청이다.
requestId만으로는 막을 수 없으며 Redis의 eventId + userId 중복 판정으로 빠르게 차단하고,
DB의 UNIQUE(event_id, user_id)로 최종 중복 발급을 방지해야 한다.
```

### **3. 중복 방어 장치별 역할 비교**

| **장치** | **식별 기준** | **막는 문제** | **막지 못하는 문제** |
| --- | --- | --- | --- |
| Redis 사용자 판정 | eventId + userId와 최초 requestId | 같은 사용자의 반복 요청과 Redis 기준 수량 초과를 빠르게 차단한다. | Redis 데이터 유실이나 우회 경로에서 발생하는 최종 DB 중복 발급은 막지 못한다. |
| requestId | requestId | 같은 논리적 요청의 API 재시도와 Kafka 중복 메시지를 식별한다. | 사용자가 새로운 requestId로 같은 쿠폰을 다시 요청하는 것은 막지 못한다. |
| requestHash | requestId와 Canonical String으로 만든 요청 내용 | 같은 requestId가 다른 eventId나 userId 요청에 재사용되는 것을 막는다. | 다른 requestId로 들어온 사용자 중복 요청은 막지 못한다. |
| `UNIQUE(event_id, user_id)` | eventId + userId | 같은 사용자의 최종 중복 발급 결과 저장을 막는다. | 같은 requestId의 처리 상태와 기존 성공 또는 실패 결과는 알 수 없다. |
| Kafka Partition + Offset | Topic의 Partition과 Record 위치 | Consumer가 Kafka 메시지를 어디까지 처리했는지 기록한다. | 다른 Offset이나 Retry Topic에 존재하는 같은 requestId의 중복 메시지는 막지 못한다. |


### **4. Kafka Producer 멱등성이 막는 중복**

다음 흐름을 기준으로 설명한다.

```
애플리케이션이 send() 한 번 호출
→ Broker 저장 성공
→ ACK 유실
→ Producer 내부 재시도
```

```
Kafka Producer 멱등성은 애플리케이션이 한 번 호출한 send()가
ACK 유실과 같은 이유로 Producer 내부에서 재시도될 때 발생하는 중복 저장을 막는다.

최초 전송과 내부 재시도에는 같은 Producer ID와 Sequence Number가 사용된다.
Broker는 이미 저장한 Sequence Number인지 확인하고 같은 Record를 다시 저장하지 않는다.
```

### **5. 애플리케이션이 send()를 두 번 호출하면 Producer 멱등성으로 막을 수 없는 이유**

```java
kafkaTemplate.send(topic, message);
kafkaTemplate.send(topic, message);
```

```
애플리케이션이 send()를 두 번 호출하면 Producer는 이를 내부 재시도가 아니라
서로 다른 두 번의 정상 전송 요청으로 판단한다.

첫 번째 호출과 두 번째 호출에는 서로 다른 Sequence Number가 부여되므로
Producer 멱등성이 활성화되어 있어도 두 Record가 모두 저장될 수 있다.
따라서 Consumer가 메시지의 requestId와 기존 요청 상태를 확인해 중복 처리를 막아야 한다.
```

### **6. requestId와 Kafka Partition + Offset의 차이**

```
requestId:
어떤 비즈니스 요청인지를 나타내는 식별자이다.
같은 논리적 요청이 재시도되거나 다른 Topic으로 이동해도 같은 값을 유지한다.

Partition + Offset:
Kafka Topic 안에서 Record가 저장된 위치이다.
재전달된 같은 Record라면 유지되지만 재발행되거나 Retry Topic으로 이동하면 달라질 수 있다.
```

### **7. Consumer 멱등성의 기준을 Offset이 아니라 requestId로 두어야 하는 이유**

아래 상황을 포함해서 설명한다.

```
원본 Topic
Partition 0 / Offset 100 / req-001

Retry Topic
Partition 2 / Offset 35 / req-001
```

```
원본 Topic과 Retry Topic은 Partition과 Offset이 서로 다르지만
requestId가 req-001로 같으므로 같은 논리적 요청이다.

Partition과 Offset을 기준으로 판단하면 두 메시지를 서로 다른 요청으로 잘못 처리할 수 있다.
Consumer는 requestId로 coupon_issue_request의 상태를 확인하고,
PENDING → PROCESSING 조건부 UPDATE에 성공한 경우에만 실제 발급을 처리해야 한다.

조건부 UPDATE가 0행이면 기존 상태를 다시 조회한다.
이미 ISSUED 또는 FAILED라면 발급 로직을 다시 실행하지 않고
정상적인 멱등 처리로 종료한 뒤 Offset을 Commit한다.
```

## **과제 3. Idempotency-Key와 requestHash 설계하기**

HTTP API에서 동일한 논리적 요청의 재시도를 식별할 수 있도록 `Idempotency-Key`와 `requestHash`를 설계한다.

### **1. Idempotency-Key의 의미**

```
Idempotency-Key는 같은 논리적인 요청의 재시도임을 서버에 알려주는 고유한 키이다.
클라이언트는 최초 요청 전에 값을 만들고 Timeout이나 응답 유실로 같은 작업을 재시도할 때
같은 키를 사용해야 한다. 서버는 이 값을 requestId로 사용해 새로운 작업을 만들지 않고
기존 요청의 상태와 결과를 반환한다.
```

### **2. 누가 requestId를 생성해야 하는가?**

다음 두 방식을 비교하고 이번 구조에 더 적합한 방식을 선택한다.

```
방식 A
Client가 요청 전 requestId 생성

방식 B
API Server가 요청을 받은 뒤 requestId 생성
```


| **방식** | **장점** | **단점** |
| --- | --- | --- |
| Client 생성 | 최초 요청과 재시도에 같은 requestId를 사용할 수 있다. | 클라이언트가 키 생성과 재사용 규칙을 지켜야 한다. |
| API Server 생성 | 클라이언트가 requestId 생성 방법을 알 필요가 없다. | 응답이 유실되면 클라이언트가 기존 requestId를 알 수 없어 재시도가 새로운 요청으로 처리될 수 있다. |


내가 선택한 방식:

```
Client가 요청 전에 requestId를 생성하는 방식을 선택한다.
```

선택한 이유:

```
서버가 요청을 받은 뒤 생성하면 응답 유실 시 클라이언트가 기존 requestId를 알 수 없다.
Client가 최초 전송 전에 생성해야 같은 논리적 작업의 재시도에 같은 값을 사용할 수 있다.
```

### **3. 같은 requestId를 재사용해야 하는 상황과 새로 생성해야 하는 상황**


| **상황** | **같은 requestId 재사용 또는 새 requestId 생성** | **이유** |
| --- | --- | --- |
| 네트워크 Timeout 후 동일 작업 재시도 | 같은 requestId 재사용 | 서버가 이미 처리했을 가능성이 있는 같은 논리적 작업이다. |
| 응답 유실 후 동일 작업 재시도 | 같은 requestId 재사용 | 서버 처리 결과만 전달되지 않았을 수 있으므로 기존 결과를 확인해야 한다. |
| 모바일 앱 재연결 후 동일 작업 전송 | 같은 requestId 재사용 | 연결만 끊겼을 뿐 사용자가 의도한 작업은 동일하다. |
| 다른 쿠폰 이벤트 발급 요청 | 새 requestId 생성 | eventId가 다른 새로운 논리적 작업이다. |
| 기존 요청을 취소하고 새로운 작업 시작 | 새 requestId 생성 | 기존 요청의 재시도가 아니라 새로 시작한 작업이다. |


### **4. requestId의 형식과 검증 규칙 설계하기**

아래 항목을 포함한다.

```
허용 형식

최대 길이

빈 값 처리

허용하지 않는 문자

DB 유일성 보장 방식
```

답변:

```
허용 형식: UUID 표준 문자열 형식

최대 길이: UUID 문자열 기준 36자

빈 값 처리: 필수 Header이므로 400 Bad Request를 반환한다.

허용하지 않는 문자: UUID 형식에 포함되지 않는 문자와 공백은 허용하지 않는다.

DB 유일성 보장 방식: request_id를 UUID 타입의 Primary Key로 저장한다.
```

### **5. requestHash를 만드는 Canonical String 작성하기**

이번 과제의 기준은 다음과 같다.

```
작업 종류: COUPON_ISSUE
이벤트 ID: 100
인증된 사용자 ID: 10
```

Canonical String:

```
COUPON_ISSUE|100|10
```

SHA-256 결과를 저장할 컬럼:

```
coupon_issue_request.request_hash CHAR(64)
```

### **6. 전체 JSON 문자열을 그대로 Hash하면 안 되는 이유**

아래 두 JSON을 기준으로 설명한다.

```json
{ "eventId": 100, "userId": 10 }
```

```json
{"userId":10,"eventId":100}
```

```
두 JSON은 의미가 같지만 필드 순서와 공백이 달라 원본 문자열은 서로 다르다.
JSON 전체 문자열을 그대로 Hash하면 같은 요청인데도 다른 requestHash가 만들어질 수 있다.
따라서 요청 의미를 결정하는 필드만 고정된 순서로 조합한 Canonical String을 Hash해야 한다.
```

### **7. requestHash에 포함할 값과 포함하지 않을 값 구분하기**


| **값** | **포함 여부** | **이유** |
| --- | --- | --- |
| 작업 종류 `COUPON_ISSUE` | 포함 | 어떤 종류의 논리적 작업인지 구분하는 값이다. |
| eventId | 포함 | 어떤 쿠폰 이벤트를 요청했는지 결정한다. |
| 인증된 userId | 포함 | 실제 요청 소유자를 결정하는 신뢰할 수 있는 값이다. |
| 요청 전송 시각 | 미포함 | 같은 요청을 재시도할 때마다 달라질 수 있다. |
| Trace ID | 미포함 | 관측용 값이며 재시도할 때 달라질 수 있다. |
| 매번 바뀌는 nonce | 미포함 | 같은 요청에서도 값이 바뀌어 Hash가 달라질 수 있다. |
| Gateway가 추가한 가변 Header | 미포함 | 비즈니스 요청 내용이 아니며 환경과 재시도에 따라 달라질 수 있다. |


### **8. Request Body의 userId를 requestHash에 그대로 사용하면 안 되는 이유**

```
Request Body는 사용자가 임의로 변경할 수 있으므로 그대로 신뢰하면
다른 사용자의 ID를 넣어 요청하거나 다른 사용자의 결과에 접근할 수 있다.
requestHash와 요청 상태에는 인증 토큰에서 확인한 authenticatedUserId를 사용해야 한다.
```

### **9. 같은 requestId에 다른 내용이 들어온 경우 처리 설계**

```
기존 요청
requestId = req-001
requestHash = hash(COUPON_ISSUE|100|10)

새 요청
requestId = req-001
requestHash = hash(COUPON_ISSUE|200|10)
```

아래 항목을 작성한다.

```
HTTP Status Code: 409 Conflict

에러 코드: IDEMPOTENCY_KEY_REUSED

Kafka 발행 여부: 발행하지 않는다.

기존 요청 상태 변경 여부: 변경하지 않는다.

사용자 응답: 동일한 요청 식별자가 다른 요청에 사용되었다고 반환한다.
```

## **과제 4. coupon_issue_request 테이블과 상태 전이 설계하기**

동일한 요청의 처리 상태와 최종 결과를 저장하기 위한 `coupon_issue_request` 테이블을 설계한다.

### **1. coupon_issue_request와 coupon_issue의 역할 차이**

| **테이블** | **저장하는 대상** | **표현할 수 있는 상태** |
| --- | --- | --- |
| coupon_issue_request | requestId를 기준으로 쿠폰 발급 요청의 생명주기와 결과를 저장한다. | PENDING, PROCESSING, ISSUED, FAILED와 실패 이유를 표현할 수 있다. |
| coupon_issue | 실제로 발급에 성공한 쿠폰 결과를 저장한다. | 성공한 발급 결과만 표현할 수 있다. |

### **2. 요청 상태 모델 설명하기**

| **상태** | **의미** | **최종 상태 여부** |
| --- | --- | --- |
| `PENDING` | 요청 행은 생성되었지만 최종 처리가 끝나지 않은 상태이다. | 아니오 |
| `PROCESSING` | Consumer가 처리 권한을 얻어 쿠폰 발급을 처리 중인 상태이다. | 아니오 |
| `ISSUED` | 수량, 발급 기록, 요청 상태가 함께 Commit된 최종 성공 상태이다. | 예 |
| `FAILED` | 재시도해도 결과가 바뀌지 않는 최종 비즈니스 실패 상태이다. | 예 |

### **3. 상태 전이 다이어그램 작성하기**

아래 허용 상태 전이와 금지 상태 전이를 구분해서 표현한다.

```
허용 후보
PENDING → PROCESSING
PROCESSING → ISSUED
PROCESSING → FAILED

금지 후보
ISSUED → PROCESSING
ISSUED → FAILED
FAILED → PROCESSING
FAILED → ISSUED
```

```
PENDING
  |
  v
PROCESSING
  |
  +--------------------+
  |                    |
  v                    v
ISSUED               FAILED

허용 상태 전이
- PENDING → PROCESSING
- PROCESSING → ISSUED
- PROCESSING → FAILED

금지 상태 전이
- ISSUED → PROCESSING
- ISSUED → FAILED
- FAILED → PROCESSING
- FAILED → ISSUED
```

### **4. 단일 트랜잭션 구조에서 외부 조회 시 PROCESSING이 거의 보이지 않을 수 있는 이유**

```
PENDING → PROCESSING과 최종 ISSUED 또는 FAILED 변경을 하나의 트랜잭션에서 처리하기 때문이다.
트랜잭션이 Commit되기 전 외부 조회는 마지막으로 Commit된 PENDING을 보고,
Commit된 뒤에는 최종 상태를 본다. 따라서 PROCESSING은 트랜잭션 내부의 처리 권한 표시로 사용되고
외부 조회에서는 거의 보이지 않을 수 있다.
```

### **5. coupon_issue_request DDL 작성하기**

아래 컬럼을 포함한다.

```
request_id

event_id

user_id

request_hash

status

failure_code

failure_message

coupon_issue_id

requested_at

processing_started_at

completed_at

created_at

updated_at
```

아래 제약 조건을 포함한다.

```
request_id Primary Key

coupon_event Foreign Key

coupon_issue Foreign Key

coupon_issue_id UNIQUE

status CHECK

FAILED일 때만 failure_code 필수

ISSUED 또는 FAILED일 때 completed_at 필수

ISSUED일 때만 coupon_issue_id 필수

PROCESSING일 때 processing_started_at 필수
```

```sql
CREATE TABLE coupon_issue_request (
    request_id UUID PRIMARY KEY,
    event_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    request_hash CHAR(64) NOT NULL,
    status VARCHAR(20) NOT NULL,
    failure_code VARCHAR(50),
    failure_message VARCHAR(255),
    coupon_issue_id BIGINT,
    requested_at TIMESTAMPTZ NOT NULL,
    processing_started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_coupon_issue_request_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),
    CONSTRAINT fk_coupon_issue_request_issue
        FOREIGN KEY (coupon_issue_id) REFERENCES coupon_issue(id),
    CONSTRAINT uk_coupon_issue_request_issue
        UNIQUE (coupon_issue_id),
    CONSTRAINT chk_coupon_issue_request_status
        CHECK (status IN ('PENDING', 'PROCESSING', 'ISSUED', 'FAILED')),
    CONSTRAINT chk_coupon_issue_request_failure
        CHECK (
            (status = 'FAILED' AND failure_code IS NOT NULL)
            OR
            (status <> 'FAILED' AND failure_code IS NULL AND failure_message IS NULL)
        ),
    CONSTRAINT chk_coupon_issue_request_completed
        CHECK (
            (status IN ('ISSUED', 'FAILED') AND completed_at IS NOT NULL)
            OR
            (status IN ('PENDING', 'PROCESSING') AND completed_at IS NULL)
        ),
    CONSTRAINT chk_coupon_issue_request_issue_result
        CHECK (
            (status = 'ISSUED' AND coupon_issue_id IS NOT NULL)
            OR
            (status <> 'ISSUED' AND coupon_issue_id IS NULL)
        ),
    CONSTRAINT chk_coupon_issue_request_processing
        CHECK (status <> 'PROCESSING' OR processing_started_at IS NOT NULL)
);
```

### **6. 요청 상태 테이블에 `UNIQUE(event_id, user_id)`를 두지 않는 이유**

아래 이력이 모두 저장되어야 한다는 점을 포함해서 설명한다.

```
req-A → ISSUED
req-B → FAILED / DUPLICATE_USER
```

```
coupon_issue_request는 실제 발급 결과가 아니라 사용자가 보낸 모든 논리적 요청의 이력을 저장한다.
같은 사용자가 여러 requestId로 요청할 수 있으므로 UNIQUE(event_id, user_id)를 두면 안 된다.

req-A의 ISSUED 이력과 req-B의 FAILED / DUPLICATE_USER 이력이 모두 남아야
두 번째 요청이 실패한 이유도 조회할 수 있다. 사용자별 최종 발급 1회 제한은
coupon_issue의 UNIQUE(event_id, user_id)가 담당한다.
```

### **7. 상태 변경 SQL에 출발 상태를 조건으로 포함해야 하는 이유**

잘못된 예:

```

3. 다른 Consumer가 먼저 상태를 변경했거나 현재 상태가 기대한 출발 상태와 다르다.
```

### **10. 요청 상태 보관 기간과 Idempotency-Key 유효 기간의 관계**

아래 식을 완성하고 이유를 설명한다.

```
Idempotency-Key 유효 기간 <= 요청 상태 보관 기간
```

이유:

```
Idempotency-Key가 아직 유효한데 요청 상태를 먼저 삭제하면
과거 requestId의 재시도를 새로운 요청으로 잘못 인식할 수 있다.
따라서 요청 상태는 키를 재사용할 수 있는 기간보다 같거나 길게 보관해야 한다.
영구 저장도 가능하지만 데이터 증가를 고려해 만료 또는 아카이브 정책을 정할 수 있다.
```

## **과제 5. API Server의 멱등 요청 접수 흐름 설계하기**

API Server가 Redis 판정, 요청 상태 등록, Kafka 발행을 어떤 순서로 처리할지 설계한다.

이번 과제에서는 Redis를 통과한 요청만 DB에 저장하는 방식을 기본으로 한다.

### **1. API Server 전체 처리 흐름 다이어그램**

다음 결과를 모두 포함한다.

```
SUCCESS
IDEMPOTENT_RETRY
DUPLICATE_USER
SOLD_OUT
requestId 충돌
Kafka 발행 실패
```

```
Client 요청
  |
  v
API Server
  | - 인증된 userId 확인
  | - requestId 검증
  | - requestHash 생성
  v
Redis Lua Script
  |
  +-- IDEMPOTENT_RETRY
  |     → DB 기존 행 조회
  |     → 행과 Hash가 정상이면 기존 상태 반환
  |     → DB 행이 없으면 재조회 및 복구 대상
  |
  +-- DUPLICATE_USER
  |     → DB 요청 등록 안 함
  |     → Kafka 발행 안 함
  |     → 사용자 중복 응답
  |
  +-- SOLD_OUT
  |     → DB 요청 등록 안 함
  |     → Kafka 발행 안 함
  |     → 품절 응답
  |
  +-- SUCCESS
        |
        v
coupon_issue_request PENDING INSERT
        |
        +-- affected rows = 0
        |     → 기존 requestHash 확인
        |     +-- Hash 같음 → 기존 상태 반환, Redis 자리 보상
        |     +-- Hash 다름 → 409 Conflict, Redis 자리 보상
        |
        +-- affected rows = 1
              |
              v
        Kafka 메시지 발행
              |
              +-- 성공 → 202 Accepted / PENDING
              +-- 실패 → 202 반환 금지, 발행 재시도 또는 복구 대상으로 기록
```

### **2. Redis 결과별 API 처리**

| **Redis 결과** | **DB 요청 상태 등록** | **Kafka 발행** | **API 응답 방향** |
| --- | --- | --- | --- |
| `SUCCESS` | requestId를 PK로 PENDING 등록을 시도한다. | 최초 INSERT 1행인 경우 발행한다. | 발행까지 성공하면 202 Accepted와 PENDING을 반환한다. |
| `IDEMPOTENT_RETRY` | 새로 등록하지 않고 기존 요청 행을 조회한다. | 새로 발행하지 않는다. | 기존 PENDING, ISSUED, FAILED 상태와 결과를 반환한다. DB 행이 없으면 복구 대상으로 처리한다. |
| `DUPLICATE_USER` | 등록하지 않는다. | 발행하지 않는다. | 같은 사용자가 다른 requestId로 요청한 중복 사용자 응답을 반환한다. |
| `SOLD_OUT` | 등록하지 않는다. | 발행하지 않는다. | Redis 기준 품절 응답을 반환한다. |


### **3. 동일 requestId 동시 요청에서 SELECT 후 INSERT가 안전하지 않은 이유**

아래 흐름을 시간 순서로 완성한다.

```
시간       API Server A               API Server B
----------------------------------------------------------
T1         req-001 SELECT → 없음
T2                                    req-001 SELECT → 없음
T3         신규 요청이라고 판단
T4                                    신규 요청이라고 판단
T5         INSERT 및 Kafka 발행 시도
T6                                    INSERT 및 Kafka 발행 시도
```

문제의 이름:

```
동시성 문제
```

### **4. DB 유일성 제약을 이용한 최초 등록자 결정 SQL 작성하기**

PostgreSQL의 `ON CONFLICT DO NOTHING`을 사용한다.

```sql
INSERT INTO coupon_issue_request (
    request_id,
    event_id,
    user_id,
    request_hash,
    status,
    requested_at
)
VALUES (
    :requestId,
    :eventId,
    :userId,
    :requestHash,
    'PENDING',
    :requestedAt
)
ON CONFLICT (request_id) DO NOTHING;
```

### **5. INSERT 영향받은 row 수 처리**

```
affected rows = 1
→ 최초 등록자이므로 Kafka 메시지 발행을 진행한다.

affected rows = 0
→ 기존 행을 조회한 뒤 requestHash와 현재 상태를 확인한다.
```

### **6. 기존 행의 requestHash 확인 결과에 따른 처리**

| **조건** | **판단** | **처리** |
| --- | --- | --- |
| requestId 같음 + requestHash 같음 | 같은 논리적 요청의 재시도이다. | Kafka를 새로 발행하지 않고 기존 요청 상태와 결과를 반환한다. |
| requestId 같음 + requestHash 다름 | 같은 키를 다른 요청에 잘못 재사용했다. | 409 Conflict를 반환하고 Redis 판정과 Kafka 발행을 진행하지 않는다. |

### **7. Redis가 `IDEMPOTENT_RETRY`를 반환했지만 DB에 요청 행이 없는 경우**

이 상태가 발생할 수 있는 이유를 설명한다.

```
최초 요청이 Redis SUCCESS로 사용자 자리와 requestId를 저장한 뒤
DB INSERT를 완료하기 전에 API Server가 종료되거나 DB 오류가 발생할 수 있다.
재시도 시 Redis에는 최초 requestId가 남아 있어 IDEMPOTENT_RETRY가 반환되지만 DB 행은 없다.
```

이 상태를 무조건 정상 `PENDING`으로 응답하면 안 되는 이유:

```
DB에 요청 상태 행이 없고 Kafka 메시지도 발행되지 않았을 수 있으므로
Consumer가 처리할 수 없는 요청을 정상 접수된 것처럼 응답하게 된다.
```

재조회·복구·보상 방향:

```
DB 행을 재조회하고, 계속 없다면 같은 requestId로 DB PENDING 등록을 재시도한다.
등록에 성공하면 Kafka 메시지를 발행한다. 일정 시간 이상 복구할 수 없다면
Redis에 저장된 현재 requestId가 복구하려는 요청과 같은지 확인한 뒤 Lua Script로 자리를 보상한다.
이 과정의 로그와 메트릭도 남긴다.
```

### **8. Redis가 `SUCCESS`를 반환했지만 DB INSERT가 충돌한 경우**

다음 상황을 고려한다.

```
과거 요청 req-001은 DB에 존재한다.
Redis 데이터는 초기화되었다.
Client가 req-001을 다시 전송한다.
Redis는 새로운 요청으로 판단해 SUCCESS를 반환한다.
DB INSERT는 request_id 충돌로 0행이다.
```

아래 항목을 작성한다.

```
기존 requestHash 확인: 기존 행과 현재 요청의 Hash를 비교한다.

Kafka 발행 여부: Hash가 같다면 기존 상태를 반환하고 새로 발행하지 않는다. 다르면 409를 반환한다.

Redis에서 새로 차지한 자리 처리: 현재 자리의 requestId를 확인한 뒤 Lua Script로 중복 반영된 자리를 보상한다.

API 응답: Hash가 같으면 기존 상태와 결과, 다르면 409 Conflict를 반환한다.
```

## **과제 6. Consumer의 조건부 상태 전이와 처리 권한 설계하기**

Kafka 메시지가 중복 전달되더라도 한 Consumer만 실제 발급 로직을 수행하도록 처리 권한 획득 방식을 설계한다.

### **1. Kafka 메시지와 요청 상태 행의 일치 검증**

다음 필드를 비교한다.

| **필드** | **Kafka Message** | **coupon_issue_request** | **불일치 시 처리** |
| --- | --- | --- | --- |
| requestId | message.requestId | request_id | 요청 행이 없으면 등록 불일치이므로 발급하지 않고 재시도, 복구 또는 DLQ 정책으로 처리한다. |
| eventId | message.eventId | event_id | 다르면 손상된 메시지이므로 발급하지 않고 DLQ 또는 운영 확인 대상으로 처리한다. |
| userId | message.userId | user_id | 다르면 다른 사용자에게 발급될 수 있으므로 발급하지 않고 DLQ 또는 운영 확인 대상으로 처리한다. |


메시지 내용 불일치를 재시도 대상으로 두기 어려운 이유:

```
같은 메시지를 다시 처리해도 eventId나 userId가 DB 요청 행과 같아지지 않기 때문이다.
일시적 장애가 아니라 손상된 메시지 또는 잘못된 requestId 재사용이므로 운영 확인이나 DLQ 대상이다.
```

### **2. SELECT 후 UPDATE 방식의 Race Condition 분석하기**

위험한 흐름은 다음과 같다.

```
1. 상태를 SELECT한다.
2. PENDING인지 애플리케이션에서 확인한다.
3. PROCESSING으로 UPDATE한다.
```

두 Consumer가 동시에 실행되는 시간 순서 다이어그램을 작성한다.

```
시간       Consumer A                  Consumer B
------------------------------------------------------------
T1         status 조회 → PENDING
T2                                     status 조회 → PENDING
T3         처리 가능하다고 판단
T4                                     처리 가능하다고 판단
T5         PROCESSING으로 UPDATE
T6                                     PROCESSING으로 UPDATE
T7         발급 처리 시작              발급 처리 시작
```

### **3. 조건부 UPDATE로 처리 권한 획득하기**

SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
```

### **4. 영향받은 row 수의 의미**

```
affected rows = 1
→ PENDING을 PROCESSING으로 변경했으므로 처리 권한을 획득했다.

affected rows = 0
→ 요청이 없거나 다른 Consumer가 처리했거나 이미 최종 상태이다. 현재 상태를 다시 조회한다.
```

### **5. 두 Consumer가 동시에 같은 requestId를 처리할 때 DB 내부 동작**

현재 상태는 `PENDING`이다.

```
Consumer A: Row Lock을 획득하고 PENDING → PROCESSING 변경에 성공해 1행을 반환한다.

Consumer B: A의 트랜잭션이 종료될 때까지 대기한 뒤 조건을 다시 확인해 0행을 반환한다.
```

`READ COMMITTED`에서 두 번째 Consumer의 `WHERE status = 'PENDING'` 조건이 어떻게 처리되는지 설명한다.

```
Consumer B는 A의 트랜잭션이 끝난 뒤 최신 Commit 상태를 기준으로 WHERE 조건을 다시 평가한다.
상태가 더 이상 PENDING이 아니므로 조건에 맞지 않아 affected rows가 0이 된다.
```

### **6. REPEATABLE READ 이상에서 달라질 수 있는 점**

```
REPEATABLE READ 이상에서는 대기 후 최신 상태로 조건을 다시 평가하는 대신
직렬화 오류가 발생할 수 있다. 애플리케이션은 이 오류를 일시적 오류로 보고
DB 트랜잭션 전체를 Rollback한 뒤 재시도해야 한다.
```

### **7. affected rows가 0일 때 상태별 처리**

| **조회 결과** | **의미** | **Consumer 처리** | **Offset 처리 방향** |
| --- | --- | --- | --- |
| 요청 행 없음 | DB 요청 등록과 Kafka 메시지가 불일치한다. | 발급하지 않고 등록 복구, 재시도 또는 DLQ 정책으로 처리한다. | 바로 Commit하지 않고 복구 정책에 따른다. |
| `PENDING` | 아직 처리 권한을 얻을 수 있는 요청이다. | 조건부 UPDATE를 다시 시도한다. | DB 결과가 확정되기 전에는 Commit하지 않는다. |
| `PROCESSING` | 다른 Consumer가 처리 중이거나 별도 Claim이 남아 있다. | 단일 트랜잭션 여부를 확인하고 재시도 또는 lease 정책을 적용한다. | 바로 Commit하지 않고 처리 결과를 확인한다. |
| `ISSUED` | 이미 성공한 요청의 중복 메시지이다. | 발급하지 않고 기존 결과를 유지한 채 정상 종료한다. | Commit한다. |
| `FAILED` | 이미 최종 실패가 확정된 중복 메시지이다. | 실패 로직을 다시 실행하지 않고 기존 결과를 유지한다. | Commit한다. |

### **8. ISSUED 또는 FAILED 중복 메시지를 예외로 던지면 안 되는 이유**

아래 잘못된 흐름을 기준으로 설명한다.

```
ISSUED 확인
→ DuplicateMessageException
→ Retry Topic
→ 다시 ISSUED 확인
→ 다시 예외
→ DLQ
```

```
ISSUED는 이미 원하는 비즈니스 결과가 완료된 상태이다.
이를 예외로 처리하면 같은 메시지가 Retry Topic에서 계속 재시도된 뒤
정상 완료된 요청이 DLQ로 이동하는 문제가 생긴다.
ISSUED와 FAILED는 기존 결과를 유지하고 정상 처리로 종료해야 한다.
```

### **9. 최종 상태를 확인하고 아무 변경 없이 종료하는 것도 성공적인 처리인 이유**

```
멱등 처리의 목표는 Consumer 코드를 한 번만 실행하는 것이 아니라
최종 비즈니스 결과가 한 번만 반영되도록 하는 것이다.
이미 ISSUED 또는 FAILED라면 원하는 최종 결과가 저장되어 있으므로
아무 변경 없이 기존 결과를 유지하고 Offset을 Commit하는 것도 성공적인 처리이다.
```

## **과제 7. 발급 트랜잭션과 Rollback 이후 상태 확정 설계하기**

처리 권한 획득부터 최종 요청 상태 변경까지를 하나의 DB 트랜잭션으로 설계한다.

### **1. 트랜잭션에 포함할 작업과 포함하지 않을 작업 구분하기**

| **작업** | **발급 트랜잭션 포함 여부** | **이유** |
| --- | --- | --- |
| PENDING → PROCESSING | 포함 | 한 Consumer만 처리 권한을 갖도록 하고 실패 시 PENDING으로 함께 Rollback해야 한다. |
| coupon_event 수량 확보 | 포함 | 발급 결과 저장과 함께 성공하거나 함께 취소되어야 한다. |
| coupon_issue INSERT | 포함 | 수량을 사용한 경우 실제 발급 결과도 반드시 저장되어야 한다. |
| request ISSUED / FAILED 변경 | 포함 | 실제 발급 결과와 사용자가 조회하는 요청 상태가 일치해야 한다. |
| 이메일 발송 | 미포함 | 외부 작업이 느리거나 실패하면 DB Connection과 Lock을 오래 점유한다. |
| 앱 푸시 발송 | 미포함 | 핵심 발급 결과를 먼저 Commit한 뒤 별도 이벤트로 처리한다. |
| 마이페이지 조회 모델 갱신 | 미포함 | 발급 결과 이벤트를 통해 비동기로 갱신할 수 있다. |
| 외부 API 호출 | 미포함 | 외부 장애가 핵심 발급 트랜잭션에 전파되면 안 된다. |

### **2. 전체 발급 트랜잭션 흐름 다이어그램**

다음 경로를 모두 포함한다.

```
처리 권한 획득 0행

수량 UPDATE 0행

coupon_issue INSERT 성공

coupon_issue UNIQUE 위반

최종 ISSUED 변경 0행

일시적 DB 오류
```

```
Kafka 메시지 수신
  |
  v
DB Transaction 시작
  |
  v
PENDING → PROCESSING 조건부 UPDATE
  |
  +-- 0행
  |    → 기존 상태 조회
  |    → ISSUED/FAILED이면 변경 없이 멱등 성공 종료
  |
  +-- 1행
       |
       v
coupon_event 수량 조건부 UPDATE
       |
       +-- 0행
       |    → request PROCESSING → FAILED / SOLD_OUT
       |    → Commit
       |
       +-- 1행
            |
            v
      coupon_issue INSERT
            |
            +-- UNIQUE 위반
            |    → 첫 트랜잭션 Rollback
            |    → 별도 트랜잭션에서 PENDING → FAILED / DUPLICATE_USER
            |
            +-- 성공
                 |
                 v
      request PROCESSING → ISSUED 조건부 UPDATE
                 |
                 +-- 0행 → 전체 Rollback
                 +-- 1행 → DB Commit

일시적 DB 오류
→ 전체 Rollback
→ 예외를 Listener 밖으로 전달
→ Kafka 재처리
```

### **3. 정상 발급 SQL 흐름 완성하기**

```sql
BEGIN;

-- 1. PENDING 요청의 처리 권한 획득
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
-- affected rows가 1인 경우에만 계속 진행한다.

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET issued_count = issued_count + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :eventId
  AND issued_count < total_quantity;

-- 3. 최종 발급 기록 저장
INSERT INTO coupon_issue (
    event_id,
    user_id,
    status,
    issued_at
)
VALUES (
    :eventId,
    :userId,
    'ISSUED',
    CURRENT_TIMESTAMP
)
RETURNING id;

-- 4. 요청 상태를 ISSUED로 변경
UPDATE coupon_issue_request
SET status = 'ISSUED',
    coupon_issue_id = :couponIssueId,
    completed_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';

COMMIT;
```

### **4. 각 단계에서 반드시 확인할 영향받은 row 수**

| **단계** | **정상적으로 기대하는 row 수** | **기대값과 다를 때 처리** |
| --- | --- | --- |
| 처리 권한 획득 | 1행 | 0행이면 현재 상태를 조회해 중복 메시지, 다른 처리자, 요청 행 누락을 구분한다. |
| 수량 UPDATE | 0행 또는 1행 | 0행이고 수량 소진이 확정되면 FAILED / SOLD_OUT으로 변경한다. |
| 최종 ISSUED 변경 | 반드시 1행 | 0행이면 발급 결과와 요청 상태가 불일치하므로 전체 트랜잭션을 Rollback한다. |

### **5. 마지막 ISSUED 상태 변경이 0행인데 발급 결과만 Commit하면 안 되는 이유**

```
coupon_event의 수량과 coupon_issue 발급 결과는 저장되었지만
사용자가 조회하는 요청 상태는 ISSUED가 아닌 불일치가 발생하기 때문이다.
수량 증가, 발급 결과, 요청 최종 상태는 하나의 비즈니스 결과이므로
마지막 상태 변경이 0행이면 전체 트랜잭션을 Rollback해야 한다.
```

### **6. DB 기준 수량이 소진된 경우 처리**

조건부 UPDATE가 0행이고 이벤트가 존재하며 수량이 모두 소진된 것으로 확정되었다고 가정한다.

요청 상태를 `FAILED / SOLD_OUT`으로 변경하는 SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status = 'FAILED',
    failure_code = 'SOLD_OUT',
    failure_message = '쿠폰이 모두 소진되었습니다.',
    completed_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PROCESSING';
```

발급 행 생성 여부:

```
coupon_issue 발급 행을 생성하지 않는다.
```

같은 메시지가 다시 들어왔을 때 처리:

```
기존 FAILED / SOLD_OUT 상태를 확인하고 발급 로직을 다시 실행하지 않는다.
정상적인 멱등 처리로 종료한 뒤 Offset을 Commit한다.
```

### **7. 서로 다른 requestId로 같은 사용자가 다시 발급을 시도한 경우**

이 시나리오는 Redis 관리자 admission 기록이 유실되거나 만료되어 req-B가 SUCCESS로 통과한 상황을 가정한다. 이때 DB의 UNIQUE(event_id, user_id)가 최종 방어선이 된다.

```
기존 요청
req-A / eventId=100 / userId=10 / ISSUED

새 요청
req-B / eventId=100 / userId=10 / PENDING
```

`req-B` 처리 중 `coupon_issue` INSERT에서 `UNIQUE(event_id, user_id)` 위반이 발생했다.

아래 항목을 설명한다.

```
첫 번째 트랜잭션의 상태: PostgreSQL의 UNIQUE 위반으로 계속 사용할 수 없으므로 전체 Rollback한다.

PENDING → PROCESSING 전이의 결과: 같은 트랜잭션의 변경이므로 취소되어 다시 PENDING이다.

앞에서 증가한 issued_count의 결과: 같은 트랜잭션의 변경이므로 증가가 취소된다.

같은 트랜잭션에서 FAILED로 바꿀 수 있는가?: 제약 위반이 발생한 트랜잭션은 사용할 수 없으므로 불가능하다.
```

### **8. UNIQUE 위반 Rollback 후 별도 트랜잭션 처리 순서**

```
1. UNIQUE 위반이 발생한 첫 번째 발급 트랜잭션을 Rollback한다.

2. 새로운 트랜잭션을 시작한다.

3. 기존 coupon_issue를 조회해 실제 사용자 중복 발급인지 확인한다.

4. 현재 요청을 PENDING → FAILED / DUPLICATE_USER로 조건부 변경한다.

5. 영향받은 행 수와 현재 상태를 확인한 뒤 Commit한다.
```

### **9. Rollback 후 요청 상태를 어떤 출발 상태에서 FAILED로 변경해야 하는가?**

잘못된 SQL:

```sql
UPDATE coupon_issue_request
SET status = 'FAILED'
WHERE request_id = :requestId
  AND status = 'PROCESSING';
```

올바른 SQL을 작성한다.

```sql
UPDATE coupon_issue_request
SET status = 'FAILED',
    failure_code = 'DUPLICATE_USER',
    failure_message = '이미 발급받은 사용자입니다.',
    completed_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
```

왜 `PROCESSING`이 아닌지 설명한다.

```
UNIQUE 위반으로 첫 번째 트랜잭션이 Rollback되면서
그 안에서 수행한 PENDING → PROCESSING 전이도 함께 취소되기 때문이다.
따라서 새 트랜잭션이 보는 실제 상태는 PROCESSING이 아니라 PENDING이다.
```

### **10. 일시적 DB 오류가 발생한 경우**

다음 항목을 작성한다.

```
요청 상태: 트랜잭션 Rollback으로 PENDING이다.

issued_count: 증가가 취소된다.

coupon_issue: 생성되지 않는다.

FAILED 저장 여부: 일시적 오류이므로 저장하지 않는다.

Kafka Listener 예외 처리: 예외를 밖으로 다시 던져 Offset을 Commit하지 않고 Kafka 재처리를 유도한다.
```

### **11. 최종 비즈니스 실패와 일시적 시스템 오류 비교**

| **오류** | **최종 FAILED 저장 여부** | **Kafka 재시도 여부** | **이유** |
| --- | --- | --- | --- |
| DB 연결 일시 실패 | 아니오 | 예 | 잠시 후 DB 연결이 복구되면 성공할 수 있는 일시적 오류이다. |
| Deadlock | 아니오 | 예 | 트랜잭션을 다시 실행하면 성공할 수 있다. |
| SOLD_OUT | 예 | 아니오 | 수량이 소진되어 재시도해도 결과가 바뀌지 않는다. |
| DUPLICATE_USER | 예 | 아니오 | 이미 같은 사용자에게 발급된 최종 비즈니스 실패이다. |
| 메시지와 요청 행 불일치 | 예, REQUEST_MISMATCH | 아니오. DLQ 또는 운영 확인 | 같은 메시지를 반복해도 내용 불일치가 해결되지 않는다. |

## **과제 8. Kafka Offset과 중복 메시지 처리 설계하기**

DB 비즈니스 결과와 Kafka 소비 위치를 안전하게 연결하도록 Offset 처리 순서를 설계한다.

### **1. 안전한 처리 순서 작성하기**

아래 흐름을 완성한다.

```
1. Kafka 메시지를 읽는다.

2. DB 트랜잭션을 시작한다.

3. PENDING → PROCESSING 조건부 UPDATE로 처리 권한을 얻는다.

4. coupon_event 수량과 coupon_issue 발급 결과를 처리한다.

5. 요청 상태를 ISSUED 또는 FAILED로 확정한다.

6. DB 트랜잭션을 Commit한다.

7. Kafka Offset을 Commit한다.
```

### **2. DB 결과 확정과 Offset Commit의 역할 차이**

| **항목** | **의미** |
| --- | --- |
| DB Commit | 수량, 발급 결과, 요청 상태라는 비즈니스 결과를 확정한다. |
| Kafka Offset Commit | Consumer가 Kafka Record를 어디까지 완료했는지 기록한다. |

### **3. Offset을 먼저 Commit한 뒤 DB 처리가 실패하는 상황**

```
1. Offset Commit
2. DB 처리 시도
3. DB 장애
```

Kafka 상태:

```
Offset이 이미 Commit되어 Kafka는 해당 Record가 처리되었다고 판단한다.
```

DB 상태:

```
DB 장애로 발급 결과가 저장되지 않고 트랜잭션이 Rollback된다.
```

사용자 요청에 발생하는 문제:

```
Kafka가 Record를 다시 전달하지 않으므로 쿠폰 발급 요청이 유실된 것과 같은 결과가 발생한다.
```

### **4. DB Commit 후 Offset Commit 전에 Consumer가 종료되는 상황**

```
DB Commit 성공
→ Consumer 종료
→ Offset Commit 실패
```

Consumer 재시작 후 발생하는 일:

```
Offset이 Commit되지 않았으므로 같은 Partition과 Offset의 Record가 다시 전달된다.
```

request 상태가 `ISSUED`인 경우 처리:

```
조건부 UPDATE는 0행이고 현재 상태를 조회하면 ISSUED이다.
새 발급 로직을 실행하지 않고 정상적인 멱등 처리로 종료한 뒤 Offset을 Commit한다.
```

### **5. 같은 Kafka Record 재전달과 같은 requestId의 다른 Record 비교**

| **구분** | **Partition** | **Offset** | **requestId** |
| --- | --- | --- | --- |
| Offset 미반영으로 동일 Record 재전달 | 동일 | 동일 | 동일 |
| Producer가 같은 요청을 두 번 발행 | Key가 같다면 일반적으로 동일 | 서로 다름 | 동일 |

두 현상을 모두 requestId로 방어해야 하는 이유:

```
첫 번째는 같은 Kafka Record가 다시 전달되고, 두 번째는 서로 다른 Record가 생성된다.
Kafka 위치는 다를 수 있지만 비즈니스 요청은 같으므로 requestId와 기존 요청 상태를 기준으로
실제 쿠폰 발급 결과가 한 번만 반영되도록 해야 한다.
```

### **6. 자동 커밋 사용 시 확인해야 할 항목**

```
1. enable.auto.commit 설정과 실제 자동 Commit 시점을 확인한다.

2. 수동 Acknowledgment 방식과 AckMode를 확인한다.

3. Listener 예외 발생 시 Offset이 Commit되는지 확인한다.

4. DB Rollback 시 같은 메시지가 재전달되는지 확인한다.

5. Retry Topic 또는 DLQ 이동 시 원본 Record의 완료 처리를 확인한다.
```

### **7. At-Least-Once와 비즈니스 결과의 차이**

아래 문장을 완성한다.

```
메시지 전달 횟수
→ 한 번 이상일 수 있다.

쿠폰 발급 결과
→ DB의 멱등 처리로 한 번만 반영되어야 한다.
```

### **8. 다음 상태에서 Offset 처리 방향 작성하기**

| **request 상태 또는 처리 결과** | **Offset 처리 방향** | **이유** |
| --- | --- | --- |
| 새 `PENDING` 요청 처리 성공 | DB Commit 후 Offset Commit | 비즈니스 결과가 먼저 확정되어야 한다. |
| 기존 `ISSUED` 요청 중복 메시지 | Commit | 이미 성공한 결과를 유지하는 정상적인 멱등 처리이다. |
| 기존 `FAILED` 요청 중복 메시지 | Commit | 최종 실패가 이미 확정되어 재시도해도 결과가 바뀌지 않는다. |
| 일시적 DB 오류로 Rollback | Commit하지 않음 | 예외를 전파해 Kafka가 다시 처리하도록 해야 한다. |
| 요청 행 없음 | 바로 Commit하지 않음 | DB 등록과 Kafka 메시지 불일치이므로 재시도, 복구, DLQ 정책이 필요하다. |
| 메시지 내용 불일치 | 발급 금지, DLQ 저장 성공 후 원본 Offset Commit | 반복해도 해결되지 않는 오류이므로 정상 발급 재시도 대상이 아니다. |

## **과제 9. Redis, DB, Kafka 불일치와 복구 정책 설계하기**

Redis, DB, Kafka는 하나의 로컬 트랜잭션으로 묶이지 않는다.

따라서 각 경계에서 생길 수 있는 불일치를 분석하고 복구 방향을 설계한다.

### **1. 장애 시점별 상태와 복구 방향**

| **장애 상황** | **Redis 상태** | **DB 요청 상태** | **Kafka 상태** | **복구 방향** |
| --- | --- | --- | --- | --- |
| Redis SUCCESS 후 DB 요청 행 INSERT 전 장애 | 사용자와 requestId의 통과 기록이 존재한다. | 요청 행이 없다. | 메시지가 없다. | 같은 requestId로 DB 등록을 재시도하고, 장시간 실패하면 Redis 자리를 보상한다. |
| DB에 PENDING 저장 후 Kafka 발행 전 장애 | 통과 기록이 존재한다. | PENDING이다. | 메시지가 없다. | 오래된 PENDING을 찾아 같은 requestId로 재발행하거나 Outbox로 복구한다. |
| Kafka 발행 성공 후 API 응답 유실 | 통과 기록이 존재한다. | PENDING 또는 이후 최종 상태이다. | 메시지가 존재한다. | Client가 같은 requestId로 재시도하면 새 작업 없이 기존 DB 상태를 반환한다. |
| Consumer가 DB 처리 전 종료 | 통과 기록이 존재한다. | PENDING이고 발급 결과가 없다. | Offset이 반영되지 않았다. | 같은 Record를 재전달해 새로운 트랜잭션에서 처리한다. |
| DB Commit 후 Offset Commit 전 종료 | 통과 기록이 존재한다. | ISSUED이고 발급 결과가 존재한다. | 완료 Offset이 없다. | 재전달 시 기존 ISSUED를 확인하고 발급 없이 Offset을 Commit한다. |
| DB ISSUED 후 Redis 데이터 유실 | 통과 기록이 없어질 수 있다. | ISSUED이고 발급 결과가 존재한다. | 처리 완료 또는 재전달 가능하다. | DB를 최종 기준으로 사용하고 DB UNIQUE로 중복 발급을 막으며 필요하면 Redis를 복구한다. |

### **2. Redis SUCCESS 후 DB 요청 행이 없는 상태**

이 상태가 발생하는 흐름을 다이어그램으로 작성한다.

```
Client req-001
  |
  v
Redis Lua Script SUCCESS
  | - userId → req-001 저장
  | - Redis 수량 반영
  v
API Server 장애 또는 DB 오류
  |
  +-- coupon_issue_request 행 없음
  +-- Kafka 메시지 없음
```

동일 requestId 재시도 시 처리 방향:

```
Redis는 IDEMPOTENT_RETRY를 반환하지만 DB 행이 없으므로 정상 PENDING으로 단정하지 않는다.
짧게 재조회한 뒤 동일 requestId로 DB PENDING 등록을 재시도하고,
등록에 성공한 경우에만 Kafka 메시지를 발행한다.
```

일정 시간 이상 지속될 때 가능한 보상:

```
DB 등록을 계속 복구할 수 없다면 Redis Lua Script로 해당 사용자의 통과 기록을 삭제하고
사용한 Redis 수량을 되돌린다. 복구 대상과 보상 결과는 로그와 메트릭으로 남긴다.
```

보상 시 현재 Redis 자리의 requestId 소유권을 확인해야 하는 이유:

```
복구가 지연되는 동안 같은 사용자 자리에 다른 requestId가 저장되었을 수 있다.
현재 저장된 requestId가 req-001인지 확인하지 않고 삭제하면 정상적인 다른 요청의 자리를 없앨 수 있다.
```

### **3. PENDING 저장 뒤 Kafka 발행 실패**

최종 상태를 작성한다.

```
Redis: 사용자와 requestId의 통과 기록이 존재한다.

DB: coupon_issue_request가 PENDING이다.

Kafka: 메시지가 없다.
```

이 요청이 계속 `PENDING`에 남는 이유:

```
Kafka 메시지가 없으므로 Consumer가 요청의 존재를 알 수 없고 발급 처리를 시작할 수 없기 때문이다.
```

복구를 위해 필요한 인덱스 또는 조회 조건:

```sql
CREATE INDEX idx_coupon_issue_request_status_updated
ON coupon_issue_request (status, updated_at);

SELECT request_id, event_id, user_id, requested_at
FROM coupon_issue_request
WHERE status = 'PENDING'
  AND updated_at < CURRENT_TIMESTAMP - INTERVAL '1 minute';
```

복구 방향:

```
오래된 PENDING 요청을 복구 배치가 조회하고 같은 requestId로 Kafka 메시지를 재발행한다.
최초 발행이 성공했지만 ACK만 유실된 경우 중복 Record가 생길 수 있으므로
Consumer는 requestId 기준으로 멱등 처리한다. 더 안전하게는 요청 행과 Outbox 행을 함께 저장한다.
```

### **4. Kafka 발행 Timeout이 모호한 이유**

아래 두 상황을 설명한다.

```
상황 A
Broker가 메시지를 저장하지 못하고 Timeout

상황 B
Broker는 메시지를 저장했지만 ACK만 유실되어 Timeout
```

Producer가 두 상황을 구분하기 어려운 이유:

```
Producer가 받는 결과는 둘 다 Timeout이다. Broker가 실제로 저장하지 않았는지,
저장했지만 ACK만 네트워크에서 유실되었는지 Producer 관점에서는 확인하기 어렵다.
```

같은 requestId로 재발행했을 때 가능한 Kafka Record:

```
Offset 100 / requestId = req-001
Offset 101 / requestId = req-001

서로 다른 Record가 생길 수 있지만 비즈니스 요청은 같다.
```

Consumer가 안전하게 처리할 수 있는 이유:

```
첫 번째 메시지만 PENDING → PROCESSING 처리 권한을 얻어 실제 발급을 수행한다.
두 번째 메시지는 기존 ISSUED 또는 FAILED 상태를 확인하고 발급 없이 정상 종료하기 때문이다.
```

### **5. Outbox Pattern이 줄일 수 있는 불일치**

아래 두 작업을 하나의 DB 트랜잭션으로 묶는 구조를 작성한다.

```
coupon_issue_request INSERT

outbox_event INSERT
```

다이어그램:

```
API Server
  |
  v
DB Transaction
  | - coupon_issue_request PENDING INSERT
  | - outbox_event INSERT
  v
Commit
  |
  v
Outbox Publisher
  | - 미발행 Outbox 조회
  | - Kafka 발행
  | - 실패 시 같은 Outbox 행으로 재시도
  v
Kafka
```

### **6. Outbox Pattern이 해결하지 못하는 구간**

아래 구간을 기준으로 설명한다.

```
Redis 선착순 판정
↔
DB 요청 상태 저장
```

```
Outbox는 같은 DB 안의 coupon_issue_request와 outbox_event만 하나의 트랜잭션으로 묶는다.
Redis와 DB는 서로 다른 저장소이므로 Redis SUCCESS와 DB 요청 등록 사이의 불일치는 해결하지 못한다.
이 구간에는 DB 등록 재시도나 Redis 자리 보상 정책이 별도로 필요하다.
```

### **7. 최종 발급 결과의 기준 데이터**

다음 중 최종 발급 여부를 판단할 기준을 선택하고 이유를 설명한다.

```
Redis 통과 기록

Kafka 메시지 존재 여부

coupon_issue DB 기록

coupon_issue_request 상태
```

선택:

```
coupon_issue DB 기록과 coupon_issue_request의 ISSUED 상태
```

이유:

```
Redis SUCCESS는 선착순 통과이고 Kafka 메시지는 처리할 작업이 존재한다는 의미일 뿐이다.
최종 발급은 coupon_event 수량 증가, coupon_issue 저장, 요청 상태 ISSUED 변경이
하나의 DB 트랜잭션으로 Commit된 결과를 기준으로 판단해야 한다.
```

### **8. 재실행 가능한 설계 정리하기**

| **단계** | **중복 또는 재실행 방어 기준** |
| --- | --- |
| Redis 판정 | eventId + userId와 최초 requestId를 Lua Script에서 원자적으로 확인한다. |
| DB 요청 등록 | request_id Primary Key와 requestHash, ON CONFLICT DO NOTHING으로 최초 등록자를 결정한다. |
| Kafka 재발행 | 같은 requestId를 유지해 중복 Record 생성을 허용하고 Consumer 멱등 처리로 흡수한다. |
| Consumer 처리 | PENDING → PROCESSING 조건부 UPDATE, DB UNIQUE, 하나의 발급 트랜잭션으로 방어한다. |

### **9. 운영 메트릭과 경고 항목 설계하기**

아래 항목을 포함해 최소 5개 작성한다.

```
오래된 PENDING 요청 수

오래된 PROCESSING 요청 수

requestId 충돌 횟수

Redis SUCCESS 후 DB 행 누락 횟수

Kafka 발행 실패 횟수

멱등 중복 메시지 처리 횟수
```

| **메트릭** | **의미** | **경고가 필요한 조건** |
| --- | --- | --- |
| 오래된 PENDING 요청 수 | 접수됐지만 일정 시간 동안 최종 처리되지 않은 요청 수 | 평소 기준보다 급증하거나 처리 SLA를 넘은 요청이 존재할 때 |
| 오래된 PROCESSING 요청 수 | 처리 권한을 얻은 뒤 고착된 요청 수 | 단일 트랜잭션 예상 시간을 넘긴 PROCESSING이 존재할 때 |
| requestId 충돌 횟수 | 동일 requestId INSERT가 충돌한 횟수 | 평소 재시도 수준을 넘거나 requestHash 불일치가 발생할 때 |
| Redis SUCCESS 후 DB 행 누락 횟수 | Redis는 통과했지만 요청 상태가 저장되지 않은 횟수 | 1건 이상 지속되거나 짧은 시간에 반복될 때 |
| Kafka 발행 실패 횟수 | PENDING 저장 후 Kafka 발행에 실패한 횟수 | 연속 실패하거나 실패율이 임계치를 넘을 때 |
| 멱등 중복 메시지 처리 횟수 | ISSUED 또는 FAILED 상태에서 중복 메시지를 정상 종료한 횟수 | 갑자기 급증해 Producer 중복 발행이나 Offset 문제를 의심할 때 |

## **과제 10. 나쁜 멱등 설계의 문제점 찾기**

아래 시스템은 `requestId`를 사용하고 있지만 안전한 멱등 구조라고 보기 어렵다.

```
1. API Server가 요청을 받을 때마다 새로운 requestId를 생성한다.

2. 같은 requestId가 들어오면 요청 내용은 확인하지 않고
   기존 결과를 무조건 반환한다.

3. 요청 상태는 coupon_issue에 성공 기록만 저장한다.

4. Consumer는 SELECT로 PENDING을 확인한 뒤
   조건 없이 PROCESSING으로 UPDATE한다.

5. 최종 상태 변경 SQL에 이전 상태 조건이 없다.

6. request가 ISSUED이면 DuplicateMessageException을 던진다.

7. Kafka Offset은 DB 처리 전에 자동 Commit될 수 있다.

8. DB Deadlock도 즉시 request FAILED로 저장한다.

9. coupon_issue UNIQUE 위반 후 같은 트랜잭션에서
   request를 FAILED로 변경하려고 한다.

10. UNIQUE 위반 트랜잭션이 Rollback된 뒤에도
    WHERE status = 'PROCESSING'으로 FAILED 변경을 시도한다.

11. 상태 조회 API는 requestId만 알면 누구나 조회할 수 있다.

12. Idempotency-Key 재사용 가능 기간보다 먼저
    coupon_issue_request 행을 삭제한다.
```

### **1. 문제점과 개선 방향 작성하기**

최소 10개 이상 작성한다.

| **문제점** | **왜 문제인가?** | **개선 방향** |
| --- | --- | --- |
| API Server가 매번 requestId 생성 | 응답 유실 후 재시도가 새로운 요청으로 처리된다. | Client가 최초 요청 전에 생성하고 동일 작업 재시도에 같은 값을 사용한다. |
| 같은 requestId의 요청 내용을 확인하지 않음 | 같은 키에 다른 eventId나 userId가 연결될 수 있다. | Canonical String의 requestHash를 비교하고 다르면 409를 반환한다. |
| coupon_issue 성공 기록만 저장 | PENDING, PROCESSING, FAILED와 실패 이유를 표현할 수 없다. | coupon_issue_request 요청 상태 테이블을 별도로 둔다. |
| SELECT 후 조건 없는 PROCESSING UPDATE | 두 Consumer가 모두 PENDING을 보고 발급을 시작할 수 있다. | WHERE status = 'PENDING' 조건부 UPDATE와 row 수를 확인한다. |
| 최종 상태 변경에 이전 상태 조건 없음 | 오래된 Consumer가 ISSUED나 FAILED를 덮어쓸 수 있다. | WHERE status = 'PROCESSING'을 포함한다. |
| ISSUED 중복 메시지에 예외 발생 | 정상 완료 요청이 반복 재시도된 뒤 DLQ로 이동할 수 있다. | 기존 결과를 유지하고 정상 처리 후 Offset을 Commit한다. |
| DB 처리 전에 Offset 자동 Commit | DB 실패 시 Kafka가 메시지를 다시 전달하지 않아 요청이 유실된다. | DB Commit 뒤 수동 Acknowledgment로 Offset을 Commit한다. |
| Deadlock을 즉시 FAILED 처리 | 다시 시도하면 성공할 수 있는 일시적 오류를 최종 실패로 확정한다. | 전체 Rollback 후 예외를 전파해 Kafka 재처리한다. |
| UNIQUE 위반 후 같은 트랜잭션에서 FAILED 변경 | PostgreSQL 제약 위반 트랜잭션은 계속 사용할 수 없다. | 첫 트랜잭션 Rollback 후 별도 트랜잭션에서 실패를 확정한다. |
| Rollback 후 PROCESSING에서 FAILED 시도 | PROCESSING 변경도 Rollback되어 실제 상태가 PENDING이므로 항상 0행이다. | WHERE status = 'PENDING'으로 FAILED / DUPLICATE_USER를 변경한다. |
| 상태 조회 시 소유자 미확인 | requestId를 아는 다른 사용자가 결과를 조회할 수 있다. | requestId와 인증된 userId를 함께 조회 조건으로 사용한다. |
| 키 유효 기간보다 먼저 요청 행 삭제 | 같은 requestId 재시도를 새로운 요청으로 잘못 판단한다. | 요청 상태 보관 기간을 Idempotency-Key 유효 기간 이상으로 설정한다. |

### **2. 다음 잘못된 SQL을 안전한 조건부 상태 전이로 수정하기**

```sql
UPDATE coupon_issue_request
SET status = 'PROCESSING'
WHERE request_id = :requestId;
```

수정 SQL:

```sql
UPDATE coupon_issue_request
SET status = 'PROCESSING',
    processing_started_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE request_id = :requestId
  AND status = 'PENDING';
```

### **4. 중복 메시지를 정상적으로 종료시키는 처리 흐름 작성하기**

```
ISSUED: 기존 성공 결과를 유지하고 새 발급 로직을 실행하지 않는다. 정상 처리 후 Offset을 Commit한다.

FAILED: 기존 실패 코드와 결과를 유지하고 실패 로직을 다시 실행하지 않는다. 정상 처리 후 Offset을 Commit한다.
```
