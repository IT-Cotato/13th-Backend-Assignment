# 5주차 과제: requestId 기반 멱등성과 중복 처리 구조 설계

---

## 과제 1. requestId 기반 전체 멱등 처리 구조 그리기

### 1. 전체 요청 처리 흐름 다이어그램

```
Client
  │ POST /api/coupon-events/100/issue
  │ Idempotency-Key: req-001
  ▼
API Server
  │ (1) 인증 → authenticatedUserId 추출
  │ (2) requestHash = SHA-256("COUPON_ISSUE|100|10")
  │ (3) Redis Lua Script 실행 (eventId + userId + requestId)
  ▼
Redis
  ├── DUPLICATE_USER → 409 반환 → Client
  ├── SOLD_OUT       → 409 반환 → Client
  ├── IDEMPOTENT_RETRY
  │       └── coupon_issue_request 조회 → 현재 상태 반환 → Client
  └── SUCCESS
        │
        ▼
      coupon_issue_request INSERT (status=PENDING)
        │ request_id = req-001
        │ (ON CONFLICT DO NOTHING으로 최초 등록자 결정)
        │
        ▼
      Kafka Producer
        │ { requestId, eventId, userId, requestHash }
        ▼
      coupon.issue.requested Topic
        │
        ▼
      Coupon Issue Consumer
        │
        ├─ Kafka 메시지 필드 ↔ coupon_issue_request 행 일치 검증
        │
        ├─ BEGIN TRANSACTION
        │    │
        │    ├─ 1. PENDING → PROCESSING 조건부 UPDATE (처리 권한 획득)
        │    │      0행 → ROLLBACK → 상태 확인 후 분기
        │    │
        │    ├─ 2. coupon_event.issued_count 조건부 UPDATE
        │    │      0행 → FAILED/SOLD_OUT 기록 후 ROLLBACK → COMMIT(FAILED)
        │    │
        │    ├─ 3. coupon_issue INSERT
        │    │      UNIQUE 위반 → ROLLBACK → 별도 트랜잭션에서 FAILED/DUPLICATE_USER 기록
        │    │
        │    └─ 4. coupon_issue_request ISSUED 변경
        │
        └─ COMMIT
              │
              ▼
        coupon_event (issued_count 증가)
        coupon_issue (발급 기록 저장)
        coupon_issue_request (ISSUED 확정)
              │
              ▼
        Kafka Offset Commit
```

### 2. 하나의 requestId가 전체 흐름에서 어떻게 전달되는지 작성하기

```
HTTP Idempotency-Key: req-001
        |
        v
API Server → requestId = "req-001"으로 사용
        |
        v
coupon_issue_request.request_id = "req-001"으로 저장
        |
        v
Kafka 메시지 payload에 requestId = "req-001" 포함
        |
        v
Consumer 멱등 처리: coupon_issue_request WHERE request_id = "req-001"로 상태 확인 및 전이
```

### 3. 각 구성 요소의 역할

```
| **구성 요소**          | **역할**                                                              |
| ---                   | ---                                                                   |
| Redis                 | 선착순/중복/재시도 빠른 판정. SUCCESS/IDEMPOTENT_RETRY/DUPLICATE_USER/SOLD_OUT 반환 |
| Kafka                 | SUCCESS 판정 요청을 비동기로 Consumer에 전달. 처리 속도 완충          |
| coupon_issue_request  | 요청별 처리 상태(PENDING/PROCESSING/ISSUED/FAILED) 저장. 멱등 처리 기준 |
| coupon_event          | 이벤트 수량(issued_count) 관리. 수량 초과 방지의 기준                 |
| coupon_issue          | 실제 발급된 쿠폰 기록 저장. UNIQUE(event_id, user_id)로 중복 최종 방어 |
| Kafka Offset          | DB Commit 이후에 커밋해 at-least-once 메시지 전달 보장                |
```

### 4. 각 단계의 성공이 의미하는 것

```
| **단계**             | **의미**                                                  | **최종 발급 성공 여부** |
| ---                 | ---                                                       | ---                   |
| Redis `SUCCESS`     | 선착순 판정 통과. 중복 아님 + 수량 내                       | 아니다                |
| request `PENDING`   | 요청이 DB에 등록되어 처리 대기 중                           | 아니다                |
| request `PROCESSING`| Consumer가 처리 권한을 획득해 발급 트랜잭션 진행 중          | 아니다                |
| request `ISSUED`    | 발급 트랜잭션 Commit 완료. 쿠폰 실제 발급됨                 | 그렇다                |
| request `FAILED`    | 수량 소진, 중복 발급 시도, 비즈니스 실패로 최종 처리 불가     | 아니다                |
| Kafka Offset Commit | 해당 메시지 처리 완료를 Kafka에 알림. 재전달 방지            | 직접 의미하지 않음. 처리 완료 후속 단계 |
```

### 5. 최종 쿠폰 발급 성공으로 판단할 수 있는 시점

```
coupon_event.issued_count 증가, coupon_issue INSERT, coupon_issue_request ISSUED 변경이 하나의 DB 트랜잭션으로 Commit된 시점이다.
이 시점에 coupon_issue 테이블에 발급 기록이 영속적으로 저장되며, coupon_issue_request.status가 ISSUED로 확정된다.
```

### 6. 요청이 여러 번 도착해도 최종 결과가 한 번만 반영되어야 한다는 의미

```
같은 requestId를 가진 요청이 네트워크 재전송, 버튼 중복 클릭, Kafka 중복 소비 등으로 여러 번 처리 단계에 도달하더라도,
쿠폰은 정확히 한 번만 발급되어야 한다.
이미 ISSUED 상태라면 추가 발급 없이 기존 결과를 그대로 반환하고 Offset을 커밋한다.
중복 처리를 예외가 아니라 "이미 성공적으로 처리된 요청"으로 인식하는 것이 핵심이다.
```

## 과제 2. 중복 유형과 멱등성 경계 구분하기

### 1. 상황별 중복 유형 분석

```
| **상황**                                            | **같은 논리적 요청인가?** | **식별 기준**                 | **주요 방어 장치**                         |
| ---                                                | ---                    | ---                          | ---                                       |
| 응답 유실 후 같은 requestId로 API 재시도             | 그렇다                  | requestId 동일               | coupon_issue_request 상태 조회 후 기존 결과 반환 |
| 반복 클릭으로 다른 requestId가 생성됨               | 아니다                  | userId + eventId 동일         | Redis DUPLICATE_USER, DB UNIQUE(event_id, user_id) |
| 애플리케이션이 같은 requestId 메시지를 send() 두 번 | 그렇다                  | requestId 동일               | Consumer의 requestId 기준 멱등 처리        |
| DB Commit 후 Offset Commit 전 장애로 같은 Record 재전달 | 그렇다               | requestId + Partition + Offset 동일 | Consumer PROCESSING 권한 획득 실패 → ISSUED 확인 후 정상 완료 |
| 원본 Topic과 Retry Topic에 같은 requestId 존재      | 그렇다                  | requestId 동일(Offset 다름)   | Consumer의 requestId 기준 멱등 처리        |
| 같은 requestId가 다른 eventId에 재사용됨            | 아니다                  | requestHash 불일치            | requestHash 검증으로 REQUEST_MISMATCH 반환  |
```

### 2. 같은 요청과 같은 사용자의 차이

```
상황 A: requestId = req-001이 여러 번 전달됨
→ 같은 논리적 요청의 재전달 또는 재시도다.
→ 네트워크 유실, Consumer 재처리 등으로 발생한다.
→ requestId로 식별해 이미 처리됐으면 기존 결과를 반환한다. 추가 발급하지 않는다.

상황 B: req-A, req-B, req-C 모두 eventId=100, userId=10
→ 같은 사용자가 새로운 논리적 요청을 여러 번 보낸 것이다.
→ 버튼 중복 클릭, 앱 재실행 등으로 발생한다.
→ requestId가 다르므로 멱등 재시도가 아니라 별개의 요청이다.
→ Redis DUPLICATE_USER로 첫 번째 이후 요청을 차단하고, DB UNIQUE(event_id, user_id)가 최종 방어한다.
```

### 3. 중복 방어 장치별 역할 비교

```
| **장치**                   | **식별 기준**             | **막는 문제**                                        | **막지 못하는 문제**                            |
| ---                       | ---                      | ---                                                 | ---                                            |
| Redis 사용자 판정           | userId + eventId         | 같은 사용자의 신규 중복 요청(DUPLICATE_USER), 수량 초과 | 다른 requestId로 오는 요청의 내용 일치 여부 확인  |
| requestId                 | requestId                | 같은 논리적 요청의 중복 처리                           | 같은 requestId로 다른 내용이 오는 경우            |
| requestHash               | 작업종류+eventId+userId   | 같은 requestId로 다른 요청 내용이 오는 경우(재사용 오용) | 새로운 requestId로 오는 사용자 중복 발급           |
| `UNIQUE(event_id, user_id)`| eventId + userId         | DB 레벨 최종 중복 발급 방어                            | 수량 초과(다른 사용자), 요청 상태 추적             |
| Kafka Partition + Offset  | Partition + Offset 위치  | 동일 Record 재전달 위치 추적                           | 같은 requestId가 다른 Offset으로 재발행된 경우     |
```

### 4. Kafka Producer 멱등성이 막는 중복

```
애플리케이션이 send()를 한 번 호출 → Broker가 메시지를 저장했지만 ACK가 유실됨
→ Producer가 내부적으로 재시도 → Broker에 동일 메시지가 두 번 도착할 수 있음

Kafka Producer 멱등성(enable.idempotence=true)은 Producer ID(PID)와 Sequence Number를 이용해
동일한 Producer가 같은 순서 번호로 재전송한 메시지를 Broker가 중복으로 식별하고 단 한 번만 저장하도록 보장한다.
즉, 네트워크 ACK 유실로 인한 Producer 내부 재시도 중복을 막는다.
```

### 5. 애플리케이션이 send()를 두 번 호출하면 Producer 멱등성으로 막을 수 없는 이유

```java
kafkaTemplate.send(topic, message);
kafkaTemplate.send(topic, message);
```

```
Kafka Producer 멱등성은 동일한 PID + Sequence Number 조합의 재전송을 막는다.
애플리케이션이 send()를 두 번 호출하면 각 호출에 서로 다른 Sequence Number가 부여된다.
Broker 입장에서는 서로 다른 두 개의 정상 메시지처럼 보이므로 둘 다 저장한다.
Producer 멱등성은 애플리케이션 로직 버그로 인한 중복 발행을 막는 기능이 아니다.
이 중복은 Consumer에서 requestId 기준으로 처리해야 한다.
```

### 6. requestId와 Kafka Partition + Offset의 차이

```
requestId:
비즈니스 레벨의 요청 식별자다. Client가 생성하며 재시도 시 동일한 값을 재사용한다.
Retry Topic 이동, Producer 재발행 등으로 Partition과 Offset이 달라져도 requestId는 변하지 않는다.
같은 논리적 요청임을 식별하는 유일한 기준이다.

Partition + Offset:
Kafka 레벨의 메시지 위치 식별자다. 동일한 Kafka Record를 가리킨다.
Retry Topic으로 이동하면 Partition과 Offset이 바뀐다. 같은 requestId라도 위치가 달라질 수 있다.
Consumer Offset 관리에는 사용하지만 비즈니스 중복 방어 기준으로 사용하면 안 된다.
```

### 7. Consumer 멱등성의 기준을 Offset이 아니라 requestId로 두어야 하는 이유

```
원본 Topic: Partition 0 / Offset 100 / requestId = req-001
Retry Topic: Partition 2 / Offset 35  / requestId = req-001

두 Record는 Partition과 Offset이 다르지만 같은 논리적 요청이다.
Offset 기준으로 중복을 판단하면 Retry Topic의 Record를 전혀 다른 요청으로 처리해 중복 발급이 발생한다.
requestId를 기준으로 coupon_issue_request 상태를 확인하면,
어느 Topic에서 왔든 이미 ISSUED면 추가 발급 없이 정상 완료 처리할 수 있다.
```

## 과제 3. Idempotency-Key와 requestHash 설계하기

### 1. Idempotency-Key의 의미

```
HTTP 요청에 포함된 헤더로, 같은 논리적 요청임을 식별하는 클라이언트 생성 고유값이다.
서버는 이 키를 requestId로 사용해 같은 요청이 여러 번 도달해도 한 번만 처리하고 동일한 결과를 반환한다.
재시도 시 동일한 Idempotency-Key를 재사용하고, 새로운 작업에는 새 키를 생성한다.
```

### 2. 누가 requestId를 생성해야 하는가?

```
| **방식**       | **장점**                                                        | **단점**                                              |
| ---           | ---                                                            | ---                                                  |
| Client 생성   | 재시도 시 동일한 requestId 재사용이 자연스럽다. 서버 응답 없이 생성 가능 | Client가 UUID를 올바르게 생성하지 않으면 충돌 가능      |
| API Server 생성| 서버에서 형식을 통제할 수 있다                                  | 최초 응답이 유실되면 Client가 requestId를 모른 채 재시도해야 하므로 멱등성 달성이 어렵다 |
```

내가 선택한 방식:

```
Client 생성 방식
```

선택한 이유:

```
멱등성의 핵심은 "같은 논리적 요청을 재시도할 때 동일한 requestId를 사용하는 것"이다.
서버가 requestId를 생성하면 응답이 유실된 경우 Client가 requestId를 알 수 없어 재시도 시 새 requestId를 사용하게 되며 멱등성이 깨진다.
Client가 미리 UUID를 생성한 뒤 헤더에 포함하면 응답 유실 후 재시도에도 동일한 requestId를 사용할 수 있다.
```

### 3. 같은 requestId를 재사용해야 하는 상황과 새로 생성해야 하는 상황

```
| **상황**                        | **같은 requestId 재사용 또는 새 requestId 생성** | **이유**                                              |
| ---                            | ---                                           | ---                                                   |
| 네트워크 Timeout 후 동일 작업 재시도 | 같은 requestId 재사용                         | 서버가 이미 처리했을 수 있으므로 동일 요청으로 식별해야 한다   |
| 응답 유실 후 동일 작업 재시도       | 같은 requestId 재사용                         | 서버가 처리 완료했을 수 있으므로 기존 결과를 돌려받아야 한다   |
| 모바일 앱 재연결 후 동일 작업 전송  | 같은 requestId 재사용                         | 앱이 재연결되어도 이전에 시작한 작업의 결과를 확인해야 한다    |
| 다른 쿠폰 이벤트 발급 요청         | 새 requestId 생성                             | 다른 논리적 작업이므로 고유한 식별자가 필요하다              |
| 기존 요청을 취소하고 새로운 작업 시작 | 새 requestId 생성                            | 새로운 논리적 작업이므로 이전 requestId와 연결되면 안 된다   |
```

### 4. requestId의 형식과 검증 규칙 설계하기

```
허용 형식: UUID v4 (8-4-4-4-12 형식, 소문자 16진수 + 하이픈)
예시: 4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31

최대 길이: 36자 (UUID v4 표준 길이)

빈 값 처리: Idempotency-Key 헤더가 없거나 빈 문자열이면 400 Bad Request 반환

허용하지 않는 문자: 소문자 16진수(0-9, a-f)와 하이픈(-)만 허용. 대문자, 특수문자, 공백 불가

DB 유일성 보장 방식: coupon_issue_request.request_id를 PRIMARY KEY로 설정해 DB 레벨에서 중복을 방지한다
```

### 5. requestHash를 만드는 Canonical String 작성하기

Canonical String:

```
COUPON_ISSUE|100|10
```

SHA-256 결과를 저장할 컬럼:

```
CHAR(64) NOT NULL
(SHA-256은 항상 64자의 16진수 문자열을 반환하므로 CHAR(64)가 적절하다)
```

### 6. 전체 JSON 문자열을 그대로 Hash하면 안 되는 이유

```json
{ "eventId": 100, "userId": 10 }
```

```json
{"userId":10,"eventId":100}
```

```
두 JSON은 의미가 동일하지만 필드 순서와 공백이 달라 Hash 결과가 다르다.
JSON 직렬화 라이브러리나 언어에 따라 키 순서가 달라질 수 있어 같은 요청인데 서로 다른 requestHash가 만들어진다.
Canonical String은 정해진 순서와 형식으로 값을 연결하므로 어떤 환경에서도 동일한 입력에 동일한 Hash가 보장된다.
```

### 7. requestHash에 포함할 값과 포함하지 않을 값 구분하기

```
| **값**                      | **포함 여부** | **이유**                                                     |
| ---                        | ---         | ---                                                          |
| 작업 종류 `COUPON_ISSUE`    | 포함         | 같은 requestId가 다른 작업 유형에 재사용되는 것을 막기 위해 필요하다 |
| eventId                    | 포함         | 어떤 이벤트에 대한 요청인지 특정해야 한다                         |
| 인증된 userId              | 포함         | 실제 요청자를 식별한다. 인증 정보에서 추출해야 한다               |
| 요청 전송 시각              | 포함 안 함   | 재시도마다 값이 달라져 같은 요청의 Hash가 달라진다               |
| Trace ID                   | 포함 안 함   | 요청마다 새로 생성되는 인프라 식별자로 비즈니스 내용과 무관하다   |
| 매번 바뀌는 nonce          | 포함 안 함   | 재시도마다 달라지면 같은 요청의 Hash가 달라진다                  |
| Gateway가 추가한 가변 Header| 포함 안 함   | 서버 내부에서 일관되게 제어할 수 없어 Hash 결과가 달라질 수 있다 |
```

### 8. Request Body의 userId를 requestHash에 그대로 사용하면 안 되는 이유

```
Request Body의 userId는 Client가 임의로 조작할 수 있다.
악의적인 요청자가 다른 사용자의 userId를 Body에 넣어 보내도 서버가 구분하지 못한다.
인증 토큰에서 추출한 authenticatedUserId를 사용해야 서버가 검증한 실제 요청자를 기준으로 Hash를 생성할 수 있다.
```

### 9. 같은 requestId에 다른 내용이 들어온 경우 처리 설계

```
기존 요청: requestId = req-001, requestHash = hash(COUPON_ISSUE|100|10)
새 요청:   requestId = req-001, requestHash = hash(COUPON_ISSUE|200|10)

HTTP Status Code: 409 Conflict

에러 코드: REQUEST_MISMATCH

Kafka 발행 여부: 발행하지 않는다

기존 요청 상태 변경 여부: 변경하지 않는다. 기존 요청은 그대로 유지된다

사용자 응답: "이미 다른 내용으로 사용된 요청 ID입니다. 새로운 Idempotency-Key를 사용해 요청해주세요."
```

## 과제 4. coupon_issue_request 테이블과 상태 전이 설계하기

### 1. coupon_issue_request와 coupon_issue의 역할 차이

```
| **테이블**              | **저장하는 대상**                                  | **표현할 수 있는 상태**               |
| ---                   | ---                                              | ---                                  |
| coupon_issue_request  | 요청 단위 처리 상태. requestId별 처리 이력과 결과 추적 | PENDING / PROCESSING / ISSUED / FAILED |
| coupon_issue          | 실제 발급 완료된 쿠폰 기록                         | ISSUED (성공 기록만 저장)              |
```

### 2. 요청 상태 모델 설명하기

```
| **상태**       | **의미**                                              | **최종 상태 여부** |
| ---           | ---                                                   | ---              |
| `PENDING`     | 요청이 접수되어 Kafka에 발행됐지만 Consumer가 아직 처리하지 않음 | 아니다          |
| `PROCESSING`  | Consumer가 처리 권한을 획득하고 발급 트랜잭션을 진행 중     | 아니다          |
| `ISSUED`      | 쿠폰 발급 트랜잭션이 Commit 완료됨                       | 그렇다          |
| `FAILED`      | 수량 소진, 중복 발급, 비즈니스 실패로 처리가 최종 실패됨      | 그렇다          |
```

### 3. 상태 전이 다이어그램 작성하기

```
[PENDING] ──────────────────→ [PROCESSING]
              (처리 권한 획득)        │
                                    ├──→ [ISSUED]  (발급 성공)
                                    └──→ [FAILED]  (수량 소진, UNIQUE 위반 등)

금지 전이:
[ISSUED]     → [PROCESSING]  금지 (최종 상태)
[ISSUED]     → [FAILED]      금지 (최종 상태)
[FAILED]     → [PROCESSING]  금지 (최종 상태)
[FAILED]     → [ISSUED]      금지 (최종 상태)
[PENDING]    → [ISSUED]      금지 (PROCESSING 단계를 반드시 거쳐야 함)
[PROCESSING] → [PENDING]     금지 (역방향 전이 불가)
```

### 4. 단일 트랜잭션 구조에서 외부 조회 시 PROCESSING이 거의 보이지 않을 수 있는 이유

```
PENDING → PROCESSING 전이, 수량 UPDATE, coupon_issue INSERT, ISSUED 변경이 하나의 트랜잭션 안에서 실행된다.
트랜잭션이 Commit되기 전까지 변경 내용은 외부에서 보이지 않는다(READ COMMITTED 기준).
트랜잭션이 매우 짧은 DB 작업으로 구성되므로 PROCESSING 상태가 외부에 노출되는 시간이 거의 없다.
COMMIT 이후에는 바로 ISSUED 또는 FAILED로 확정된 상태만 보인다.
```

### 5. coupon_issue_request DDL 작성하기

```sql
CREATE TABLE coupon_issue_request (
    request_id             VARCHAR(36)   NOT NULL,

    user_id                BIGINT        NOT NULL,
    request_hash           CHAR(64)      NOT NULL,
    status                 VARCHAR(20)   NOT NULL DEFAULT 'PENDING',
    failure_code           VARCHAR(50)   NULL,
    failure_message        VARCHAR(500)  NULL,
    coupon_issue_id        BIGINT        NULL,
    requested_at           TIMESTAMP     NOT NULL,
    processing_started_at  TIMESTAMP     NULL,
    completed_at           TIMESTAMP     NULL,
    created_at             TIMESTAMP     NOT NULL DEFAULT NOW(),
    updated_at             TIMESTAMP     NOT NULL DEFAULT NOW(),

    CONSTRAINT pk_coupon_issue_request
        PRIMARY KEY (request_id),

    CONSTRAINT fk_coupon_issue_request_event
        FOREIGN KEY (event_id) REFERENCES coupon_event(id),

    CONSTRAINT fk_coupon_issue_request_issue
        FOREIGN KEY (coupon_issue_id) REFERENCES coupon_issue(id),

    CONSTRAINT uq_coupon_issue_request_issue_id
        UNIQUE (coupon_issue_id),

    CONSTRAINT chk_status

    CONSTRAINT chk_failure_code_when_failed

    CONSTRAINT chk_completed_at_when_final
        CHECK ((status NOT IN ('ISSUED', 'FAILED')) OR completed_at IS NOT NULL),

    CONSTRAINT chk_coupon_issue_id_when_issued
        CHECK (status != 'ISSUED' OR coupon_issue_id IS NOT NULL),

    CONSTRAINT chk_processing_started_at_when_processing

);
```

### 6. 요청 상태 테이블에 `UNIQUE(event_id, user_id)`를 두지 않는 이유

```
coupon_issue_request는 요청 단위 이력 테이블이다. 같은 사용자가 같은 이벤트에 여러 번 요청하면 각 요청마다 행이 생성된다.
예를 들어 req-A → ISSUED, req-B → FAILED/DUPLICATE_USER 이력이 모두 저장되어야 한다.
UNIQUE(event_id, user_id)를 두면 첫 번째 요청 이후의 요청은 INSERT 자체가 불가능해 이력을 남길 수 없다.
중복 발급 방지는 coupon_issue 테이블의 UNIQUE(event_id, user_id)와 Redis가 담당한다.
```

### 7. 상태 변경 SQL에 출발 상태를 조건으로 포함해야 하는 이유

```sql
-- 잘못된 예: 현재 상태가 무엇이든 ISSUED로 변경됨. 이미 FAILED인 행도 덮어쓴다
UPDATE coupon_issue_request
SET status = 'ISSUED'
WHERE request_id = :requestId;
```

올바른 상태 전이 SQL:

```sql
UPDATE coupon_issue_request
SET    status       = 'ISSUED',
       coupon_issue_id = :couponIssueId,
       completed_at = NOW(),
       updated_at   = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PROCESSING';
```

### 8. 최종 상태 변경의 영향받은 row 수가 0인 경우

```
1. 해당 request_id 행이 존재하지 않는 경우

2. 행은 존재하지만 이미 ISSUED 또는 FAILED인 최종 상태인 경우 (다른 Consumer가 먼저 처리 완료)

3. 행이 아직 PENDING 상태인 경우 (PROCESSING으로 전이가 실패했는데 이후 로직이 잘못 실행된 경우)
```

### 9. 운영 복구를 위한 인덱스 설계하기

-- 오래된 PENDING/PROCESSING 요청 조회 (복구 배치용)

    ON coupon_issue_request (status, created_at)
    WHERE status IN ('PENDING', 'PROCESSING');

### 10. 요청 상태 보관 기간과 Idempotency-Key 유효 기간의 관계

```
Idempotency-Key 유효 기간
≤
요청 상태 보관 기간
```

이유:

```
Client가 Idempotency-Key를 재사용해 재시도하는 동안 서버에 해당 요청의 처리 기록이 남아 있어야 한다.
요청 상태가 먼저 삭제되면 서버가 기존 처리 결과를 확인할 수 없어 같은 requestId를 새 요청으로 처리해 중복 발급이 발생한다.
Idempotency-Key 유효 기간이 끝나기 전까지는 반드시 요청 상태 행이 DB에 유지되어야 한다.
```

## 과제 5. API Server의 멱등 요청 접수 흐름 설계하기

### 1. API Server 전체 처리 흐름 다이어그램

```
HTTP 요청 수신 (Idempotency-Key: req-001)
  │
  ├─ 인증 확인 (authenticatedUserId 추출)
  ├─ requestId 형식 검증 (UUID v4)
  ├─ requestHash 생성 (SHA-256("COUPON_ISSUE|100|10"))
  │
  ▼
Redis Lua Script 실행
  │
  ├── SOLD_OUT
  │       └── 409 응답 반환
  │
  ├── DUPLICATE_USER
  │       └── 409 응답 반환
  │
  ├── IDEMPOTENT_RETRY
  │       └── coupon_issue_request WHERE request_id = req-001 조회
  │             ├─ 행 없음 → (Redis/DB 불일치) → 복구 처리 후 응답
  │             ├─ PENDING → 202 { status: PENDING } 반환
  │             ├─ ISSUED  → 200 { status: ISSUED } 반환
  │             └─ FAILED  → 200 { status: FAILED, failureCode: ... } 반환
  │
  └── SUCCESS
        │
        ▼
      coupon_issue_request INSERT
      (ON CONFLICT DO NOTHING)
        │
        ├── affected rows = 1 (최초 등록 성공)
        │       │
        │       ▼
        │     Kafka 발행
        │       ├── 발행 성공 → 202 { status: PENDING } 반환
        │       └── 발행 실패
        │               └── coupon_issue_request 삭제 또는 FAILED 기록
        │                   Redis에서 해당 userId 자리 복구(SREM)
        │                   500 또는 503 응답 반환
        │
        └── affected rows = 0 (requestId 충돌 - 이미 존재)
                │
                ▼
              기존 행 조회 (requestHash 비교)
                ├── requestHash 일치 → IDEMPOTENT_RETRY와 동일하게 처리
                └── requestHash 불일치 → 409 REQUEST_MISMATCH 반환
```

### 2. Redis 결과별 API 처리

```
| **Redis 결과**      | **DB 요청 상태 등록** | **Kafka 발행**    | **API 응답 방향**                        |
| ---                | ---                 | ---              | ---                                     |
| `SUCCESS`          | PENDING INSERT      | 발행              | 202 Accepted { status: PENDING }        |
| `IDEMPOTENT_RETRY` | 하지 않음            | 하지 않음         | 기존 coupon_issue_request 상태 그대로 반환 |
| `DUPLICATE_USER`   | 하지 않음            | 하지 않음         | 409 Conflict (이미 발급 신청됨)           |
| `SOLD_OUT`         | 하지 않음            | 하지 않음         | 409 Conflict (수량 소진)                 |
```

### 3. 동일 requestId 동시 요청에서 SELECT 후 INSERT가 안전하지 않은 이유

```
시간       API Server A                    API Server B
----------------------------------------------------------
T1         SELECT: req-001 없음             -
T2         -                               SELECT: req-001 없음
T3         (행 없음 확인 완료)              (행 없음 확인 완료)
T4         INSERT req-001 → 성공            -
T5         -                               INSERT req-001 → 성공 (중복 등록!)
T6         Kafka 발행                       Kafka 발행 (중복 발행!)
```

문제의 이름:

```
TOCTOU (Time-of-Check-to-Time-of-Use) Race Condition
```

### 4. DB 유일성 제약을 이용한 최초 등록자 결정 SQL 작성하기

```sql
INSERT INTO coupon_issue_request (
    request_id, event_id, user_id, request_hash,
    status, requested_at, created_at, updated_at
)
VALUES (
    :requestId, :eventId, :userId, :requestHash,
    'PENDING', :requestedAt, NOW(), NOW()
)
ON CONFLICT (request_id) DO NOTHING;
```

### 5. INSERT 영향받은 row 수 처리

```
affected rows = 1
→ 최초 등록 성공. Kafka 발행을 진행한다.

affected rows = 0
→ 이미 같은 request_id 행이 존재한다.
  기존 행을 조회해 requestHash를 비교하고 IDEMPOTENT_RETRY 또는 REQUEST_MISMATCH로 처리한다.
```

### 6. 기존 행의 requestHash 확인 결과에 따른 처리

```
| **조건**                       | **판단**           | **처리**                                              |
| ---                           | ---               | ---                                                  |
| requestId 같음 + requestHash 같음 | 멱등 재시도       | 기존 coupon_issue_request 상태를 조회해 그대로 반환한다 |
| requestId 같음 + requestHash 다름 | requestId 오용    | 409 REQUEST_MISMATCH 반환. Kafka 발행 안 함           |
```

### 7. Redis가 `IDEMPOTENT_RETRY`를 반환했지만 DB에 요청 행이 없는 경우

이 상태가 발생할 수 있는 이유를 설명한다.

```
Redis에는 userId의 통과 기록이 남아 있지만 DB INSERT가 실패한 경우다.
예를 들어 Redis SUCCESS 직후 DB 연결 오류로 INSERT가 실패하거나, INSERT 후 Kafka 발행 실패로 요청 행을 롤백/삭제했을 수 있다.
Redis와 DB가 하나의 트랜잭션으로 묶이지 않으므로 둘 사이에 불일치가 발생할 수 있다.
```

이 상태를 무조건 정상 `PENDING`으로 응답하면 안 되는 이유:

```
DB에 요청 행이 없으면 Kafka 메시지도 없고 Consumer 처리도 이루어지지 않는다.
PENDING으로 응답하면 사용자는 결과를 기다리지만 실제로는 아무것도 처리되지 않아 영원히 대기 상태가 된다.
```

재조회·복구·보상 방향:

```
1. DB에 요청 행 없음을 확인한다.
2. Kafka에 메시지가 발행됐는지 알 수 없으므로 보수적으로 처리한다.
3. Redis에서 해당 userId의 통과 기록을 제거(SREM)해 사용자가 재시도 가능하도록 복구한다.
4. 사용자에게 일시적 오류임을 안내하고 새 요청(새 requestId)으로 재시도를 유도한다.
5. 또는 기존 requestId로 coupon_issue_request를 다시 INSERT해 Kafka 재발행을 시도하는 복구 배치를 운영한다.
```

### 8. Redis가 `SUCCESS`를 반환했지만 DB INSERT가 충돌한 경우

```
기존 requestHash 확인: 기존 행의 requestHash와 현재 요청의 requestHash를 비교한다.

Kafka 발행 여부:
  requestHash 일치 → 기존 상태 확인 후 IDEMPOTENT_RETRY와 동일하게 처리. Kafka 재발행 불필요.
  requestHash 불일치 → 409 REQUEST_MISMATCH 반환. Kafka 발행 안 함.

Redis에서 새로 차지한 자리 처리:
  Redis에 새로 추가된 userId 기록(SREM)을 제거한다.
  이전 요청의 requestId로 Redis에 이미 자리가 있을 수 있으므로 신중하게 처리한다.

API 응답:
  requestHash 일치 → 기존 coupon_issue_request 상태 반환 (PENDING/ISSUED/FAILED)
  requestHash 불일치 → 409 REQUEST_MISMATCH
```

### 9. 최초 요청 접수 성공 응답 설계하기

HTTP Status Code:

```
202 Accepted
```

응답 JSON:

```json
{
  "requestId": "4372dbe5-8cc8-4bfa-9cdf-1cd5e9f77b31",
  "status": "PENDING",
  "message": "쿠폰 발급 요청이 접수되었습니다. 잠시 후 마이페이지에서 결과를 확인해주세요."
}
```

이 응답이 최종 발급 성공을 의미하지 않는 이유:

```
PENDING은 요청이 접수되어 처리 대기 중임을 의미한다.
이후 Consumer가 메시지를 읽고 DB 트랜잭션을 Commit해야 실제로 쿠폰이 발급된다.
수량 소진, UNIQUE 위반 등으로 Consumer 처리가 실패하면 FAILED가 될 수 있다.
```

## 과제 6. Consumer의 조건부 상태 전이와 처리 권한 설계하기

### 1. Kafka 메시지와 요청 상태 행의 일치 검증

```
| **필드**    | **Kafka Message**        | **coupon_issue_request** | **불일치 시 처리**                              |
| ---        | ---                      | ---                      | ---                                           |
| requestId  | payload.requestId        | request_id               | 불일치 불가(조회 조건). 행 없으면 복구 불가 실패 처리 |
| eventId    | payload.eventId          | event_id                 | 메시지 내용 불일치 → DLQ 이동. 재시도 금지       |
| userId     | payload.userId           | user_id                  | 메시지 내용 불일치 → DLQ 이동. 재시도 금지       |
```

메시지 내용 불일치를 재시도 대상으로 두기 어려운 이유:

```
메시지 내용과 DB 기록이 다른 것은 일시적 오류가 아니라 데이터 일관성 문제다.
재시도해도 같은 불일치가 반복되므로 Retry Topic을 통해 재시도할수록 Retry Topic이 쌓인다.
이 경우는 운영자가 직접 원인을 파악해야 하므로 DLQ로 격리해 수동 처리하는 것이 적합하다.
```

### 2. SELECT 후 UPDATE 방식의 Race Condition 분석하기

```
시간       Consumer A                      Consumer B
------------------------------------------------------------
T1         SELECT status → PENDING         -
T2         -                               SELECT status → PENDING
T3         (PENDING 확인)                  (PENDING 확인)
T4         UPDATE status = 'PROCESSING'    -
T5         -                               UPDATE status = 'PROCESSING' (중복 권한 획득!)
T6         쿠폰 발급 처리                   쿠폰 발급 처리 (중복 처리!)
T7         COMMIT                          COMMIT (중복 발급 발생 가능)
```

### 3. 조건부 UPDATE로 처리 권한 획득하기

```sql
UPDATE coupon_issue_request
SET    status                = 'PROCESSING',
       processing_started_at = NOW(),
       updated_at            = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PENDING';
```

### 4. 영향받은 row 수의 의미

```
affected rows = 1
→ PENDING 상태에서 PROCESSING으로 전이 성공. 이 Consumer가 처리 권한을 획득했다. 발급 트랜잭션을 진행한다.

affected rows = 0
→ 처리 권한 획득 실패. 다른 Consumer가 이미 처리 중이거나, 최종 상태(ISSUED/FAILED)이거나, 행이 없는 경우다.
  현재 상태를 조회해 원인을 파악하고 분기한다.
```

### 5. 두 Consumer가 동시에 같은 requestId를 처리할 때 DB 내부 동작

```
Consumer A: PENDING → PROCESSING UPDATE 실행 → 해당 row에 행 수준 배타 락 획득 → 성공 (affected = 1)

Consumer B: PENDING → PROCESSING UPDATE 실행 시도 → Consumer A가 락을 보유 중이므로 대기
            Consumer A가 COMMIT하면 Consumer B는 갱신된 status = 'PROCESSING'으로 조건을 재평가
            WHERE status = 'PENDING' 조건이 false → affected = 0 → 처리 권한 획득 실패
```

`READ COMMITTED`에서 두 번째 Consumer의 `WHERE status = 'PENDING'` 조건이 어떻게 처리되는지 설명한다.

```
READ COMMITTED는 UPDATE 실행 시 가장 최근에 Commit된 값을 읽는다.
Consumer A가 COMMIT하면 Consumer B는 락 해제 후 재평가를 수행한다.
이때 status는 이미 'PROCESSING'으로 변경되어 있으므로 WHERE status = 'PENDING' 조건이 false가 된다.
결과적으로 affected rows = 0이 반환되어 Consumer B는 처리 권한을 얻지 못한다.
```

### 6. REPEATABLE READ 이상에서 달라질 수 있는 점

```
REPEATABLE READ에서는 트랜잭션 시작 시점의 스냅샷을 기준으로 읽는다.
하지만 UPDATE 문은 항상 최신 Commit된 값에 락을 시도한다(PostgreSQL의 경우 현재 커밋된 값으로 재평가).
PostgreSQL의 REPEATABLE READ에서도 UPDATE의 WHERE 조건은 최신 Commit된 행을 기준으로 평가하므로
실질적인 동작 차이는 크지 않다. 다만 SELECT FOR UPDATE와 같은 명시적 락에서는 차이가 생길 수 있다.
```

### 7. affected rows가 0일 때 상태별 처리

```
| **조회 결과**  | **의미**                               | **Consumer 처리**                          | **Offset 처리 방향**    |
| ---           | ---                                    | ---                                       | ---                    |
| 요청 행 없음   | DB에 해당 requestId 기록 없음            | 복구 불가 실패로 DLQ 이동                    | Offset 커밋하지 않음    |
| `PENDING`     | 다른 Consumer가 먼저 처리 중이거나 일시적 경합 | 잠시 대기 후 재시도 또는 다음 Poll에서 처리  | Offset 커밋하지 않음    |
| `PROCESSING`  | 다른 Consumer가 현재 처리 권한 보유 중    | 중복 처리 방지. 이 메시지는 건너뜀. Offset 커밋 | Offset 커밋            |
| `ISSUED`      | 이미 성공적으로 처리 완료된 중복 메시지    | 멱등 성공. 추가 처리 없이 종료              | Offset 커밋            |
| `FAILED`      | 이미 최종 실패로 확정된 중복 메시지       | 멱등 성공. 추가 처리 없이 종료              | Offset 커밋            |
```

### 8. ISSUED 또는 FAILED 중복 메시지를 예외로 던지면 안 되는 이유

```
ISSUED 확인
→ DuplicateMessageException
→ Retry Topic
→ 다시 ISSUED 확인
→ 다시 예외
→ DLQ

이 흐름은 정상적으로 처리 완료된 메시지를 계속 오류로 분류한다.
Retry Topic을 불필요하게 소비하고 DLQ에 정상 처리된 메시지가 쌓인다.
운영자가 DLQ를 확인할 때 실제 오류와 구분이 어려워진다.
ISSUED/FAILED는 이미 처리 완료된 상태이므로 예외가 아니라 멱등 성공으로 처리하고 Offset을 커밋해야 한다.
```

### 9. 최종 상태를 확인하고 아무 변경 없이 종료하는 것도 성공적인 처리인 이유

```
멱등성의 목표는 같은 요청이 여러 번 처리되어도 최종 비즈니스 결과가 한 번만 반영되는 것이다.
ISSUED를 확인하고 추가 발급 없이 Offset을 커밋하는 것은 "이 메시지는 이미 올바르게 처리됐음"을 확인한 것이다.
중복 메시지가 도달했을 때 아무런 부작용 없이 정상 종료되는 것 자체가 멱등 처리의 성공이다.
```

## 과제 7. 발급 트랜잭션과 Rollback 이후 상태 확정 설계하기

### 1. 트랜잭션에 포함할 작업과 포함하지 않을 작업 구분하기

```
| **작업**                       | **발급 트랜잭션 포함 여부** | **이유**                                              |
| ---                           | ---                    | ---                                                   |
| PENDING → PROCESSING          | 포함                    | 처리 권한 획득. 트랜잭션 범위 안에서 원자적으로 전이해야 함  |
| coupon_event 수량 확보         | 포함                    | 수량 초과 방지와 발급 기록 저장이 원자적으로 묶여야 함        |
| coupon_issue INSERT            | 포함                    | 발급 기록과 상태 변경이 함께 성공하거나 실패해야 함           |
| request ISSUED / FAILED 변경  | 포함                    | 발급 결과와 요청 상태가 항상 일치해야 함                    |
| 이메일 발송                    | 포함 안 함              | 외부 시스템 호출. 트랜잭션이 길어지고 이메일 서버 장애가 발급에 영향 |
| 앱 푸시 발송                   | 포함 안 함              | 위와 동일. EDA로 별도 처리                              |
| 마이페이지 조회 모델 갱신        | 포함 안 함              | 별도 이벤트로 처리. 조회 모델 갱신 실패가 발급에 영향 주면 안 됨 |
| 외부 API 호출                  | 포함 안 함              | 응답 시간 불확실. 트랜잭션 Hold 시간이 길어져 Lock 경합 증가 |
```

### 2. 전체 발급 트랜잭션 흐름 다이어그램

```
BEGIN TRANSACTION
  │
  ├─ [1] PENDING → PROCESSING 조건부 UPDATE
  │       affected = 0
  │         └─ ROLLBACK → 현재 상태 조회
  │               ├─ ISSUED/FAILED → 멱등 성공, Offset 커밋
  │               └─ 기타 → 재시도 또는 DLQ
  │
  │       affected = 1 (처리 권한 획득)
  │         │
  ├─ [2] coupon_event issued_count 조건부 UPDATE
  │       affected = 0
  │         └─ request FAILED/SOLD_OUT 변경
  │             COMMIT (FAILED 확정)
  │             Offset 커밋
  │
  │       affected = 1
  │         │
  ├─ [3] coupon_issue INSERT
  │       UNIQUE 위반
  │         └─ ROLLBACK
  │             (별도 트랜잭션)
  │             coupon_issue 기록 조회
  │             request FAILED/DUPLICATE_USER 변경
  │             Offset 커밋
  │
  │       INSERT 성공
  │         │
  ├─ [4] coupon_issue_request ISSUED 변경
  │       affected = 0
  │         └─ ROLLBACK (발급 결과만 Commit하면 안 됨)
  │
  │       affected = 1
  │         │
  └─ COMMIT
        │
  Offset 커밋

  [일시적 DB 오류 발생 시]
  ROLLBACK → Kafka Listener 예외 발생 → 재시도 (PENDING 상태 유지)
```

### 3. 정상 발급 SQL 흐름 완성하기

```sql
BEGIN;

-- 1. PENDING 요청의 처리 권한 획득
UPDATE coupon_issue_request
SET    status                = 'PROCESSING',
       processing_started_at = NOW(),
       updated_at            = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PENDING';
-- affected rows = 0이면 ROLLBACK 후 상태 확인

-- 2. 수량이 남아 있을 때만 issued_count 증가
UPDATE coupon_event
SET    issued_count = issued_count + 1
WHERE  id           = :eventId
  AND  issued_count < total_quantity;
-- affected rows = 0이면 SOLD_OUT → request FAILED 기록 후 COMMIT

-- 3. 최종 발급 기록 저장
INSERT INTO coupon_issue (event_id, user_id, status, issued_at)
VALUES (:eventId, :userId, 'ISSUED', NOW());
-- UNIQUE 위반이면 ROLLBACK → 별도 트랜잭션에서 FAILED 기록

-- 4. 요청 상태를 ISSUED로 변경
UPDATE coupon_issue_request
SET    status          = 'ISSUED',
       coupon_issue_id = :couponIssueId,
       completed_at    = NOW(),
       updated_at      = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PROCESSING';

COMMIT;
```

### 4. 각 단계에서 반드시 확인할 영향받은 row 수

```
| **단계**          | **정상적으로 기대하는 row 수** | **기대값과 다를 때 처리**                          |
| ---              | ---                       | ---                                              |
| 처리 권한 획득     | 1                         | ROLLBACK. 상태 조회 후 ISSUED/FAILED면 멱등 성공 처리 |
| 수량 UPDATE       | 1                         | SOLD_OUT. request FAILED/SOLD_OUT 기록 후 COMMIT  |
| 최종 ISSUED 변경  | 1                         | ROLLBACK. 발급 결과만 남기면 정합성이 깨지므로 전체 취소 |
```

### 5. 마지막 ISSUED 상태 변경이 0행인데 발급 결과만 Commit하면 안 되는 이유

```
coupon_issue INSERT와 issued_count 증가는 성공했지만 coupon_issue_request가 ISSUED로 변경되지 않으면
요청 상태 테이블은 PROCESSING으로 남는다.
이 상태에서 사용자가 상태를 조회하면 PROCESSING이 보이고,
재시도 시 Consumer가 처리 권한 획득을 다시 시도할 수 있다.
모든 변경이 원자적으로 Commit되어야 DB 전체 상태가 일관성을 유지한다.
```

### 6. DB 기준 수량이 소진된 경우 처리

```sql
UPDATE coupon_issue_request
SET    status        = 'FAILED',
       failure_code  = 'SOLD_OUT',
       failure_message = '쿠폰 수량이 모두 소진되었습니다.',
       completed_at  = NOW(),
       updated_at    = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PROCESSING';
```

발급 행 생성 여부:

```
coupon_issue INSERT는 하지 않는다. 수량 소진으로 발급 자체가 불가하므로 발급 기록이 생성되지 않는다.
```

같은 메시지가 다시 들어왔을 때 처리:

```
coupon_issue_request 상태가 FAILED이므로 Consumer가 처리 권한 획득 시 affected = 0이 된다.
상태 조회 결과 FAILED이므로 멱등 성공으로 처리하고 Offset을 커밋한다.
```

### 7. 서로 다른 requestId로 같은 사용자가 다시 발급을 시도한 경우

```
첫 번째 트랜잭션의 상태:
ROLLBACK. coupon_issue INSERT에서 UNIQUE(event_id, user_id) 위반이 발생해 트랜잭션 전체가 취소된다.
앞에서 이미 실행한 issued_count 증가, PROCESSING 전이도 모두 롤백된다.

PENDING → PROCESSING 전이의 결과:
ROLLBACK으로 취소된다. req-B의 coupon_issue_request는 다시 PROCESSING에서 이전 상태로 돌아가지 않는다.
PostgreSQL에서는 ROLLBACK 후 행은 이전 Commit된 상태(PENDING)로 복구된다.

앞에서 증가한 issued_count의 결과:
ROLLBACK으로 함께 취소된다. issued_count는 증가 전 값으로 돌아간다.

같은 트랜잭션에서 FAILED로 바꿀 수 있는가?:
없다. PostgreSQL에서 제약 조건 위반이 발생하면 트랜잭션이 aborted 상태가 된다.
aborted 상태에서는 ROLLBACK 외에 어떤 SQL도 실행할 수 없다.
FAILED 변경은 ROLLBACK 후 별도 트랜잭션에서 수행해야 한다.
```

### 8. UNIQUE 위반 Rollback 후 별도 트랜잭션 처리 순서

```
1. ROLLBACK 실행 (이전 트랜잭션의 모든 변경 취소)

2. 새 트랜잭션 시작

3. coupon_issue 테이블에서 (event_id=100, user_id=10) 기록 조회
   → 기록이 있으면 DUPLICATE_USER 확정

4. coupon_issue_request req-B를 FAILED/DUPLICATE_USER로 변경
   (WHERE status = 'PENDING' 조건 - 아래 과제 7-9 참고)

5. 새 트랜잭션 COMMIT 후 Offset 커밋
```

### 9. Rollback 후 요청 상태를 어떤 출발 상태에서 FAILED로 변경해야 하는가?

```sql
UPDATE coupon_issue_request
SET    status         = 'FAILED',
       failure_code   = 'DUPLICATE_USER',
       failure_message = '이미 발급받은 이벤트입니다.',
       completed_at   = NOW(),
       updated_at     = NOW()
WHERE  request_id = :requestId
  AND  status     = 'PENDING';
```

왜 `PROCESSING`이 아닌지 설명한다.

```
ROLLBACK이 실행되면 해당 트랜잭션에서 실행했던 PENDING → PROCESSING 전이도 함께 취소된다.
따라서 ROLLBACK 후 req-B의 상태는 다시 PENDING이 된다.
별도 트랜잭션에서 FAILED로 변경할 때는 WHERE status = 'PENDING'을 조건으로 사용해야 한다.
WHERE status = 'PROCESSING'을 쓰면 조건이 맞지 않아 affected = 0이 되어 FAILED 변경에 실패한다.
```

### 10. 일시적 DB 오류가 발생한 경우

```
요청 상태: FAILED로 변경하지 않는다. 트랜잭션이 ROLLBACK되므로 PENDING 상태가 유지된다.

issued_count: ROLLBACK으로 증가 전 값으로 복구된다.

coupon_issue: INSERT가 ROLLBACK되어 발급 기록이 생성되지 않는다.

FAILED 저장 여부: 저장하지 않는다. 일시적 오류는 재시도로 해결 가능하므로 FAILED로 확정하지 않는다.

Kafka Listener 예외 처리: 예외를 발생시켜 Kafka Listener가 해당 메시지를 재처리하게 한다.
                           Offset을 커밋하지 않아 Consumer 재시작 후 같은 메시지를 다시 읽는다.
```

### 11. 최종 비즈니스 실패와 일시적 시스템 오류 비교

```
| **오류**              | **최종 FAILED 저장 여부** | **Kafka 재시도 여부** | **이유**                                             |
| ---                  | ---                    | ---                 | ---                                                 |
| DB 연결 일시 실패      | 저장 안 함              | 재시도               | 일시적 인프라 오류. 재시도로 정상 처리 가능              |
| Deadlock             | 저장 안 함              | 재시도               | 일시적 경합. 잠시 후 재시도하면 해결 가능                |
| SOLD_OUT             | 저장 함                 | 재시도 안 함         | 수량 소진은 비즈니스 최종 실패. 재시도해도 결과가 바뀌지 않음 |
| DUPLICATE_USER       | 저장 함                 | 재시도 안 함         | 이미 발급받은 사용자. 재시도해도 결과가 바뀌지 않음        |
| 메시지와 요청 행 불일치 | 저장 안 함 (DLQ)        | 재시도 안 함         | 데이터 정합성 문제. 재시도해도 해결 불가. 운영자 개입 필요   |
```

## 과제 8. Kafka Offset과 중복 메시지 처리 설계하기

### 1. 안전한 처리 순서 작성하기

```
1. Kafka 메시지를 읽는다.

2. Kafka 메시지 필드와 coupon_issue_request 행을 조회해 내용 일치를 검증한다.

3. 조건부 UPDATE로 PENDING → PROCESSING 처리 권한을 획득한다.
   (0행이면 현재 상태를 조회해 ISSUED/FAILED면 멱등 성공 처리 후 Offset 커밋)

4. DB 트랜잭션 실행:
   coupon_event issued_count 증가 + coupon_issue INSERT + coupon_issue_request ISSUED 변경

5. DB 트랜잭션 COMMIT.

6. 비즈니스 결과 확정 (ISSUED 또는 FAILED).

7. Kafka Offset을 Commit한다.
```

### 2. DB 결과 확정과 Offset Commit의 역할 차이

```
| **항목**           | **의미**                                                         |
| ---               | ---                                                             |
| DB Commit         | 쿠폰 발급 결과가 영속 저장되어 비즈니스적으로 완료됨. 데이터 정합성 확정 |
| Kafka Offset Commit | 이 메시지를 성공적으로 처리했음을 Kafka에 알림. Consumer 재시작 시 이 메시지를 다시 읽지 않도록 처리 위치를 기록 |
```

### 3. Offset을 먼저 Commit한 뒤 DB 처리가 실패하는 상황

Kafka 상태:

```
Offset이 이미 Commit되었으므로 Consumer가 재시작해도 이 메시지를 다시 읽지 않는다.
해당 메시지는 Kafka 관점에서 처리 완료로 간주된다.
```

DB 상태:

```
DB 처리가 실패했으므로 coupon_issue 기록도 없고 coupon_issue_request도 ISSUED로 변경되지 않는다.
요청이 PENDING 상태로 남거나 아무 변경도 없는 상태다.
```

사용자 요청에 발생하는 문제:

```
사용자는 PENDING 응답을 받았거나 처리 결과를 기다리지만, 쿠폰은 영원히 발급되지 않는다.
메시지가 재전달되지 않으므로 복구 방법이 없다. 요청이 유실된 것과 같은 결과가 된다.
```

### 4. DB Commit 후 Offset Commit 전에 Consumer가 종료되는 상황

Consumer 재시작 후 발생하는 일:

```
Offset이 Commit되지 않았으므로 Consumer는 재시작 후 같은 Kafka Record를 다시 읽는다.
동일한 requestId로 coupon_issue_request를 다시 처리하려 한다.
```

request 상태가 `ISSUED`인 경우 처리:

```
Consumer가 PENDING → PROCESSING 조건부 UPDATE를 시도하면 affected = 0이 된다.
상태 조회 결과 ISSUED이므로 멱등 성공으로 처리한다.
추가 발급 없이 Offset을 커밋하고 정상 종료한다.
```

### 5. 같은 Kafka Record 재전달과 같은 requestId의 다른 Record 비교

```
| **구분**                          | **Partition** | **Offset** | **requestId** |
| ---                              | ---          | ---        | ---           |
| Offset 미반영으로 동일 Record 재전달 | 동일          | 동일        | 동일           |
| Producer가 같은 요청을 두 번 발행    | 동일 또는 다름 | 다름        | 동일           |
```

두 현상을 모두 requestId로 방어해야 하는 이유:

```
첫 번째 경우는 Partition+Offset이 같으므로 동일 Record임을 알 수 있지만,
두 번째 경우는 Offset이 달라 Partition+Offset으로는 같은 요청임을 알 수 없다.
requestId는 두 경우 모두 동일하므로 requestId를 기준으로 coupon_issue_request 상태를 확인하면
어떤 원인의 중복이든 멱등하게 처리할 수 있다.
```

### 6. 자동 커밋 사용 시 확인해야 할 항목

```
1. auto.commit.interval.ms 설정값이 DB 처리 시간보다 짧은지 확인한다.
   짧으면 DB 처리 완료 전에 Offset이 자동 커밋될 수 있다.

2. DB 처리 중 Consumer가 종료될 때 Offset이 이미 커밋됐는지 확인한다.
   커밋됐다면 메시지가 재전달되지 않아 발급이 유실될 수 있다.

3. 자동 커밋이 Poll 루프와 연동되므로 긴 처리 시간이 커밋 타이밍에 영향을 주는지 확인한다.

4. 예외 발생 시 Offset이 커밋됐는지 확인한다. 자동 커밋은 예외 여부와 관계없이 주기적으로 커밋될 수 있다.

5. 자동 커밋 환경에서는 멱등 처리(requestId 기반 상태 확인)가 더욱 중요하다.
   메시지가 재전달되지 않더라도 DB 처리 실패를 감지할 수 있는 복구 배치가 필요하다.
```

### 7. At-Least-Once와 비즈니스 결과의 차이

```
메시지 전달 횟수
→ At-Least-Once 보장. 같은 메시지가 한 번 이상 Consumer에 전달될 수 있다.
  메시지 유실은 없지만 중복 전달은 발생할 수 있다.

쿠폰 발급 결과
→ Exactly-Once 비즈니스 결과를 목표로 한다. requestId 기반 멱등 처리로 메시지가 여러 번 전달되어도
  쿠폰은 정확히 한 번만 발급된다. 메시지 전달 횟수와 무관하게 비즈니스 결과는 한 번만 반영된다.
```

### 8. 다음 상태에서 Offset 처리 방향 작성하기

```
| **request 상태 또는 처리 결과** | **Offset 처리 방향** | **이유**                                       |
| ---                           | ---               | ---                                           |
| 새 `PENDING` 요청 처리 성공     | DB Commit 후 커밋  | 정상 처리 완료. 재전달 방지                       |
| 기존 `ISSUED` 요청 중복 메시지  | 즉시 커밋           | 이미 성공 처리됨. 추가 발급 없이 멱등 성공 처리      |
| 기존 `FAILED` 요청 중복 메시지  | 즉시 커밋           | 이미 최종 실패 확정. 재처리해도 결과가 달라지지 않음  |
| 일시적 DB 오류로 Rollback       | 커밋하지 않음        | 재시도 필요. 메시지 재전달을 통해 다시 처리해야 함   |
| 요청 행 없음                    | 커밋하지 않음        | 복구 불가 상태. DLQ로 이동해 운영자 개입 필요       |
| 메시지 내용 불일치               | 커밋하지 않음        | DLQ로 이동. 재시도해도 해결 불가                  |
```

## 과제 9. Redis, DB, Kafka 불일치와 복구 정책 설계하기

### 1. 장애 시점별 상태와 복구 방향

```
| **장애 상황**                            | **Redis 상태**             | **DB 요청 상태**   | **Kafka 상태**              | **복구 방향**                                              |
| ---                                    | ---                       | ---              | ---                         | ---                                                      |
| Redis SUCCESS 후 DB 요청 행 INSERT 전 장애 | userId 통과 기록 존재       | 행 없음           | 메시지 없음                  | Redis에서 userId SREM. 사용자 재시도 유도                   |
| DB에 PENDING 저장 후 Kafka 발행 전 장애  | userId 통과 기록 존재       | PENDING          | 메시지 없음                  | 오래된 PENDING 감지 배치가 Kafka 재발행                      |
| Kafka 발행 성공 후 API 응답 유실          | userId 통과 기록 존재       | PENDING          | 메시지 존재 (Offset 미커밋)  | Client가 같은 requestId로 재시도 → IDEMPOTENT_RETRY → 현재 상태 반환 |
| Consumer가 DB 처리 전 종료              | userId 통과 기록 존재       | PENDING          | 메시지 존재 (Offset 미커밋)  | Consumer 재시작 후 같은 메시지 재처리                        |
| DB Commit 후 Offset Commit 전 종료      | userId 통과 기록 존재       | ISSUED           | 메시지 존재 (Offset 미커밋)  | Consumer 재시작 → ISSUED 확인 → 멱등 성공 → Offset 커밋      |
| DB ISSUED 후 Redis 데이터 유실           | 해당 userId 기록 없음       | ISSUED           | -                           | DB가 최종 기준. 사용자 재요청 시 DUPLICATE_USER 또는 DB UNIQUE 위반으로 차단 |
```

### 2. Redis SUCCESS 후 DB 요청 행이 없는 상태

이 상태가 발생하는 흐름을 다이어그램으로 작성한다.

```
Redis Lua Script → SUCCESS (userId Set에 추가됨)
  │
  ▼
API Server → coupon_issue_request INSERT 시도
  │
  ├── DB 연결 오류 / INSERT 실패
  │
  ▼
Redis: userId 통과 기록 존재
DB: coupon_issue_request 행 없음
Kafka: 메시지 없음
```

동일 requestId 재시도 시 처리 방향:

```
Redis는 IDEMPOTENT_RETRY를 반환한다.
DB에 행이 없음을 확인한다.
Redis/DB 불일치 상태이므로 정상 PENDING으로 응답하면 안 된다.
Redis에서 userId를 SREM해 자리를 해제하고, 사용자에게 일시적 오류를 안내해 새 requestId로 재시도를 유도한다.
또는 같은 requestId로 DB INSERT 재시도를 통해 복구할 수도 있다.
```

일정 시간 이상 지속될 때 가능한 보상:

```
Redis에서 해당 userId SREM으로 통과 기록 제거 후 사용자가 재시도 가능하도록 복구한다.
또는 coupon_issue_request를 다시 INSERT하고 Kafka 메시지를 재발행한다.
복구 배치가 오래된 Redis 통과 기록과 DB 불일치를 감지해 자동 복구한다.
```

보상 시 현재 Redis 자리의 requestId 소유권을 확인해야 하는 이유:

```
Redis에는 userId의 통과 기록과 최초 requestId가 함께 저장된다.
SREM 전에 Redis의 requestId가 복구 대상 requestId와 일치하는지 확인해야 한다.
다른 requestId가 이미 자리를 차지한 경우(다른 요청이 Redis에 다시 등록된 경우) 잘못된 자리를 제거하면 안 된다.
```

### 3. PENDING 저장 뒤 Kafka 발행 실패

최종 상태를 작성한다.

```
Redis: userId 통과 기록 존재

DB: coupon_issue_request PENDING 상태로 남음

Kafka: 메시지 없음
```

이 요청이 계속 `PENDING`에 남는 이유:

```
Kafka 발행에 실패했으므로 Consumer가 메시지를 읽지 못한다.
Consumer는 처리할 메시지가 없으므로 상태를 변경하지 않는다.
PENDING 상태 변경을 트리거할 수단이 없어 요청이 PENDING에서 벗어나지 못한다.
```

복구를 위해 필요한 인덱스 또는 조회 조건:

```sql
-- 오래된 PENDING 요청 감지용
SELECT * FROM coupon_issue_request
WHERE  status     = 'PENDING'
  AND  created_at < NOW() - INTERVAL '5 minutes';

-- 인덱스
CREATE INDEX idx_coupon_issue_request_status_created
    ON coupon_issue_request (status, created_at)
    WHERE status = 'PENDING';
```

복구 방향:

```
오래된 PENDING 요청을 감지하는 배치가 주기적으로 실행된다.
해당 requestId로 Kafka 메시지를 재발행한다.
재발행 시 requestId가 포함되어 있으므로 Consumer가 coupon_issue_request를 조회해 정상 처리한다.
```

### 4. Kafka 발행 Timeout이 모호한 이유

```
상황 A: Broker가 메시지를 저장하지 못하고 Timeout
Kafka Topic에 메시지가 없다. 재발행하면 하나의 메시지가 생긴다.

상황 B: Broker는 메시지를 저장했지만 ACK만 유실되어 Timeout
Kafka Topic에 이미 메시지가 있다. 재발행하면 같은 requestId의 메시지가 두 개 생긴다.
```

Producer가 두 상황을 구분하기 어려운 이유:

```
Producer 입장에서는 Timeout이 발생하면 Broker가 저장했는지 저장하지 못했는지 알 수 없다.
ACK 유실과 저장 실패 모두 Producer에게는 응답을 받지 못한 것으로 보인다.
```

같은 requestId로 재발행했을 때 가능한 Kafka Record:

```
상황 A: 재발행된 메시지 1개만 존재
상황 B: 원래 메시지 + 재발행 메시지 총 2개가 존재 (같은 requestId, 다른 Offset)
```

Consumer가 안전하게 처리할 수 있는 이유:

```
Consumer는 requestId를 기준으로 coupon_issue_request 상태를 확인한다.
첫 번째 메시지로 ISSUED가 확정되면 두 번째 메시지는 ISSUED를 확인하고 멱등 성공으로 처리한다.
Kafka Record가 몇 개이든 requestId 기반 멱등 처리로 발급은 정확히 한 번만 이루어진다.
```

### 5. Outbox Pattern이 줄일 수 있는 불일치

다이어그램:

```
BEGIN TRANSACTION
  │
  ├─ coupon_issue_request INSERT (status=PENDING)
  │
  └─ outbox_event INSERT
       { requestId, eventId, userId, topic: "coupon.issue.requested" }
COMMIT

[별도 Outbox Publisher]
  outbox_event 조회 (미발행 이벤트)
    → Kafka 발행 성공 → outbox_event 발행 완료 처리
    → Kafka 발행 실패 → 재시도 (outbox_event는 DB에 남아 있음)
```

### 6. Outbox Pattern이 해결하지 못하는 구간

```
Redis 선착순 판정과 DB 요청 상태 저장은 별개의 시스템이므로 하나의 트랜잭션으로 묶을 수 없다.
Redis SUCCESS 후 DB INSERT 전 장애가 발생하면 Redis에는 userId가 남고 DB에는 행이 없는 불일치가 생긴다.
Outbox Pattern은 DB 트랜잭션 내부의 Kafka 발행 보장에만 적용되며,
Redis 판정 → DB 저장 구간의 불일치는 보상 처리(Redis SREM)나 복구 배치로 별도 해결해야 한다.
```

### 7. 최종 발급 결과의 기준 데이터

선택:

```
coupon_issue DB 기록
```

이유:

```
Redis는 인메모리로 장애 시 유실 가능하고 발급 완료 기록을 영속적으로 저장하지 않는다.
Kafka는 메시지 전달 상태를 관리하지 발급 결과를 저장하지 않는다.
coupon_issue_request는 요청 처리 상태이며, ISSUED라도 coupon_issue 기록이 없으면 발급이 완료되지 않은 것이다.
coupon_issue 테이블에 기록이 있는 것만이 쿠폰이 실제로 발급됐음을 영속적으로 보장한다.
```

### 8. 재실행 가능한 설계 정리하기

```
| **단계**         | **중복 또는 재실행 방어 기준**                                  |
| ---             | ---                                                          |
| Redis 판정       | userId + eventId + requestId로 SUCCESS/IDEMPOTENT_RETRY 구분  |
| DB 요청 등록      | ON CONFLICT DO NOTHING + requestHash 비교로 최초 등록자 결정  |
| Kafka 재발행      | requestId 포함. Consumer가 requestId 기준으로 멱등 처리       |
| Consumer 처리    | coupon_issue_request 조건부 UPDATE로 처리 권한 획득. ISSUED/FAILED면 멱등 성공 처리 |
```

### 9. 운영 메트릭과 경고 항목 설계하기

```
| **메트릭**                         | **의미**                                         | **경고가 필요한 조건**                     |
| ---                               | ---                                             | ---                                      |
| 오래된 PENDING 요청 수             | Kafka 발행 실패 또는 Consumer 장애로 처리 안 된 요청 | PENDING 상태가 5분 이상 지속되는 건수 > 10  |
| 오래된 PROCESSING 요청 수          | Consumer 장애로 처리 권한 획득 후 완료 안 된 요청   | PROCESSING 상태가 1분 이상 지속되는 건수 > 5 |
| requestId 충돌 횟수               | 같은 requestId로 다른 내용이 오는 오용 시도         | 단위 시간당 5건 이상                       |
| Redis SUCCESS 후 DB 행 누락 횟수   | Redis/DB 불일치 발생 빈도                         | 단위 시간당 1건 이상                       |
| Kafka 발행 실패 횟수              | PENDING으로 남는 요청 발생 빈도                    | 단위 시간당 10건 이상                      |
```

## 과제 10. 나쁜 멱등 설계의 문제점 찾기

### 1. 문제점과 개선 방향 작성하기

```
| **문제점**                                             | **왜 문제인가?**                                                      | **개선 방향**                                              |
| ---                                                  | ---                                                                  | ---                                                       |
| 1. API Server가 요청마다 새 requestId를 생성            | Client가 재시도 시 새 requestId로 요청하게 되어 중복 발급 위험. 멱등성 불가 | Client가 요청 전 requestId를 생성하고 헤더로 전송           |
| 2. 같은 requestId면 내용 확인 없이 기존 결과 반환         | requestId 오용(다른 eventId에 재사용)을 감지하지 못해 잘못된 결과를 반환   | requestHash 비교로 내용 일치 여부를 먼저 확인               |
| 3. 성공 기록만 coupon_issue에 저장 (요청 상태 테이블 없음) | PENDING/PROCESSING 상태 추적 불가. 처리 중 장애 시 복구 기준 없음        | coupon_issue_request 테이블로 요청 처리 상태를 별도 관리    |
| 4. Consumer가 SELECT 후 조건 없이 PROCESSING UPDATE    | Race Condition 발생. 두 Consumer가 동시에 처리 권한 획득 가능            | WHERE status = 'PENDING' 조건부 UPDATE로 처리 권한 원자적 획득 |
| 5. 최종 상태 변경 SQL에 이전 상태 조건 없음              | FAILED나 ISSUED인 행을 덮어쓸 수 있어 최종 상태가 변조됨               | WHERE status = 'PROCESSING' 조건을 포함한 조건부 UPDATE 사용 |
| 6. ISSUED면 DuplicateMessageException 예외 발생         | 정상 처리된 중복 메시지가 Retry Topic → DLQ로 이동. 운영 혼란 발생       | ISSUED 확인 시 예외 없이 멱등 성공으로 처리 후 Offset 커밋   |
| 7. Kafka Offset 자동 커밋으로 DB 처리 전 커밋 가능       | DB 처리 실패 시 메시지가 유실됨. 발급 없이 요청이 사라짐                 | 자동 커밋 비활성화. DB Commit 후 수동으로 Offset 커밋       |
| 8. DB Deadlock도 즉시 FAILED로 저장                    | 일시적 오류를 최종 실패로 확정해 사용자가 재시도할 수 없게 됨             | Deadlock은 재시도 가능. ROLLBACK 후 Kafka 재전달로 재처리   |
| 9. UNIQUE 위반 후 같은 트랜잭션에서 FAILED 변경 시도      | PostgreSQL에서 제약 위반 후 트랜잭션이 aborted 상태가 되어 추가 SQL 불가 | ROLLBACK 후 새 트랜잭션에서 FAILED 변경                   |
| 10. ROLLBACK 후 WHERE status='PROCESSING'으로 FAILED 변경 | ROLLBACK으로 상태가 PENDING으로 돌아갔으므로 조건이 맞지 않아 0행        | WHERE status = 'PENDING'으로 조건 변경                    |
| 11. 상태 조회 API에 인증 없이 requestId만으로 조회 가능    | 타인의 요청 상태(쿠폰 발급 여부 등)를 조회할 수 있어 개인정보 노출 위험    | user_id = authenticatedUserId 조건을 반드시 포함           |
| 12. Idempotency-Key 유효 기간 전에 요청 상태 행 삭제      | 삭제 후 재시도 시 서버가 기존 처리 기록을 찾지 못해 중복 처리 발생 위험    | 요청 상태 보관 기간 ≥ Idempotency-Key 유효 기간 보장        |
```

### 2. 다음 잘못된 SQL을 안전한 조건부 상태 전이로 수정하기

UPDATE coupon_issue_request

       processing_started_at = NOW(),

### 4. 중복 메시지를 정상적으로 종료시키는 처리 흐름 작성하기

```
ISSUED:
  coupon_issue_request 상태 조회 → ISSUED 확인
  → 추가 발급 없이 정상 종료
  → Kafka Offset 커밋
  → 로그: "중복 메시지 멱등 처리 완료 (ISSUED)"

FAILED:
  coupon_issue_request 상태 조회 → FAILED 확인
  → 추가 처리 없이 정상 종료
  → Kafka Offset 커밋
  → 로그: "중복 메시지 멱등 처리 완료 (FAILED: {failureCode})"
```

### 5. 이번 5주차 설계에서 최종적으로 지켜야 하는 불변식 정리하기

```
1. 하나의 requestId는 하나의 논리적 요청만 나타낸다.
   같은 requestId로 다른 내용의 요청이 처리되어서는 안 된다. (requestHash 검증으로 보장)

2. 같은 requestId가 여러 번 처리되더라도 coupon_issue 발급 기록은 정확히 한 번만 생성된다.
   (조건부 PROCESSING 전이 + UNIQUE(event_id, user_id)로 보장)

3. coupon_issue_request 상태는 한 방향으로만 전이된다.
   ISSUED와 FAILED는 최종 상태이며 다른 상태로 되돌아갈 수 없다. (조건부 UPDATE의 출발 상태 조건으로 보장)

4. Kafka Offset은 반드시 DB Commit 이후에 커밋된다.
   DB 처리 결과가 확정되기 전에 메시지를 처리 완료로 표시하지 않는다.

5. 일시적 시스템 오류(Deadlock, 연결 실패 등)는 FAILED로 확정하지 않고 재시도한다.
   FAILED는 비즈니스 최종 실패(수량 소진, 중복 발급)에만 사용된다.

6. 요청 상태 보관 기간은 Idempotency-Key 유효 기간보다 짧을 수 없다.
   유효 기간 내에 재시도하는 요청이 항상 기존 처리 결과를 돌려받을 수 있어야 한다.
```
